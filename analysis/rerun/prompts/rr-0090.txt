Like Comment Story Updates Inspiration AI agents are becoming increasingly capable at reasoning, but I became interested in a different problem: What happens to the human context they need to reason well? People constantly produce valuable context through observations, measurements, decisions, hypotheses, conversations, and experience. Much of it remains unstructured: spoken aloud, written in notes, or trapped inside applications that were designed for humans rather than agents. My initial idea was simple: let a person describe something naturally, preserve what they actually said, and make that context reusable by an AI agent later. But that immediately raised a harder question: If AI helps structure that memory, how do we prevent the AI's interpretation from silently becoming part of the human evidence? That question became the foundation of Companion. Companion is a human-to-agent memory layer : Human context → Confirmed memory → WebMCP → Agent reasoning The application owns the evidence. The agent owns the reasoning. What Companion does Companion starts with unrestricted natural-language human input. A person can describe an observation without learning a schema or filling out a complex structured form. Companion proposes a subject, but the person reviews and can correct both the original text and the subject before confirming it. Once confirmed, the original evidence is preserved first. AI then helps construct a semantic representation of that evidence, but model output does not automatically become factual memory. Semantic construction happens in two stages: Semantic discovery finds candidate relations. Epistemic classification determines how each candidate is supported by the confirmed source. Relations are classified as: SOURCE_EXPLICIT SOURCE_STRONGLY_IMPLIED AGENT_INFERRED Only source-grounded relations are eligible for factual memory after deterministic validation. AGENT_INFERRED relations are kept outside that factual boundary and are never silently exposed as human-confirmed facts. This means AI can help build the memory without being allowed to redefine the evidence. Why WebMCP The next problem was retrieval. My first instinct was to make Companion intelligent enough to decide which stored information an agent needed. Experiments changed that design. If the external agent already understands the user's question and will ultimately reason over the answer, adding another AI inside Companion to predict what that agent needs duplicates intelligence and creates another place where interpretation can go wrong. Instead, Companion exposes two read-only WebMCP capabilities: get_companion_vocabulary Returns a deterministic, reusable vocabulary of factual semantic relations available for a subject. query_companion_memory Retrieves exactly the factual relations identified by the vocabulary IDs selected by the external agent. This creates an incremental protocol: Agent inspects vocabulary → selects evidence → retrieves it → evaluates sufficiency → requests more if necessary → reasons Companion does not interpret the question, rank evidence, decide sufficiency, or generate the final answer. WebMCP is a particularly good fit because it gives the application a discoverable and invocable capability without coupling Companion to one specific agent runtime. The same architecture could be implemented with custom APIs and agent-specific integrations. WebMCP changes the integration boundary: Companion can expose its memory capability directly from the application so compatible agents can discover what evidence exists, request only the evidence they need, and reason over it without Companion being coupled to a specific agent runtime. What becomes possible is a collaboration in which a human can capture context naturally once, while multiple compatible agents can later discover and retrieve that confirmed memory through a shared application-owned interface. How I built it Companion was built as a sequence of small architectural experiments rather than by implementing the first design that seemed plausible. The core pipeline became: Human natural-language context ↓ Human review and confirmation ↓ Persist confirmed raw evidence ↓ Stage A: semantic discovery ↓ Candidate semantic graph ↓ Stage B: epistemic classification ↓ Deterministic validation ↓ Factual memory / inference boundary ↓ Reusable factual vocabulary ↓ WebMCP deterministic lookup ↓ External-agent reasoning The AI-assisted part is deliberately bounded. Everything that can be checked mechanically—IDs, references, schema compliance, candidate correspondence, source excerpts, routing, lookup—is validated deterministically. One design principle emerged from this: Pay for intelligence once, then reuse the structured result deterministically. The confirmed rawText remains the authoritative primary source. Semantic memory stays traceable to it, and semantic-processing failure cannot erase the original evidence. Persistent semantic IDs are also owned by Companion rather than by the model, preventing temporary model-generated identifiers from becoming accidental persistent authority. Challenges I faced Semantic correctness is not factual correctness One of the biggest lessons came from deliberately trying to break the semantic builder. A model can identify a relationship that is completely reasonable and still not be justified by the source. For example, observations may strongly suggest a diagnosis. That does not mean the human actually reported that diagnosis. This forced me to separate semantic discovery from epistemic classification . A useful semantic candidate is not automatically a fact. Preventing silent information loss Another problem appeared when increasing epistemic strictness. A strict prompt could reduce unsupported inference but also cause legitimate semantic relations to disappear. The solution was a no-deletion architecture: Stage A discovers candidates first, and Stage B must classify every candidate exactly once. That makes three different failures observable: discovery failure, classification failure, inferred semantic content that should not become factual memory. Deciding where retrieval intelligence belongs I also experimented with retrieval strategies. The important realization was that Companion does not need to understand the user's question if the external agent already does. The external agent can inspect Companion's reusable vocabulary, choose the IDs it needs, retain previous context, and request additional evidence incrementally. That removed an unnecessary intelligent selector from Companion and produced a cleaner responsibility boundary. Keeping the demo honest The public challenge demo uses synthetic evidence and browser-session-local memory. It intentionally does not claim production readiness, universal semantic correctness, or objective truth. Human confirmation means that the representation corresponds to what the human confirmed. It does not mean the human statement itself is objectively true. That distinction became important enough to be part of the architecture rather than just a disclaimer. A useful agent-memory system needs to know where human evidence ends and machine interpretation begins. I also learned that adding more AI is not always the answer. What it does Kurdish Calendar Agent lets a browser agent complete one coherent planning workflow: Find Nawroz in the calendar’s real event data. Convert March 21 across Gregorian, Kurdish Bashur, Kurdish Rojhalat, Persian, and Hijri calendars. Compare candidate meeting times for Erbil, London, Toronto, or other IANA time zones. Open March 21 in the visible calendar so the person can verify the selected date and events. Stage an editable event plan containing the conversions, local times, and notes. The plan remains a private, unsaved draft. No tool can publish, save, send, share, or book anything. The person reviews the details, edits the draft, and explicitly chooses whether to copy it. Why WebMCP is a strong fit Without WebMCP, an agent must scrape labels, infer calendar state, guess which controls to click, and reconstruct structured date and time-zone information from the page. Those steps are brittle and difficult to verify. WebMCP exposes the calendar’s real capabilities as five explicit, schema-validated browser tools. The agent receives structured event records, calendar conversions, and local-time comparisons, while UI-affecting tools update the same calendar the person sees. This creates a reliable collaboration loop: the agent performs repetitive research and coordination, and the human verifies and controls the final action. What people and agents can do together A person can make one request—“Plan Nawroz 2026 for my family in Erbil, London, and Toronto”—instead of manually combining an event search, five calendar systems, daylight-saving-aware time-zone calculations, calendar navigation, and message drafting. The agent does the structured work and visibly opens the selected day. The person validates the result in context, adjusts the notes, and decides whether to copy it. The workflow is more capable than ordinary page automation while remaining human-controlled. How we built it The application registers five imperative tools with document.modelContext.registerTool() : kurdish_calendar_find_events kurdish_calendar_convert_date kurdish_calendar_compare_global_times kurdish_calendar_open_date kurdish_calendar_stage_event_plan Each tool uses a strict JSON input schema, structured output, concise text output, and honest behavior annotations. Registrations share an AbortSignal ; a partial registration failure aborts the complete set. Event search uses the same data as the visible calendar. open_date updates the real calendar UI, while stage_event_plan opens the real editable review panel. The implementation uses Next.js, React, TypeScript, Tailwind CSS, Vitest, and the WebMCP API. The public site is deployed on Vercel. Existing project and challenge-period work Kurdish Calendar, its localization, date-conversion utilities, event data, and public website existed before the challenge. During the challenge, we meaningfully extended it with native WebMCP tool contracts and implementations, lifecycle-safe tool registration and cleanup, agent-driven calendar navigation, international time-zone comparison and ranking, an editable private event-plan review panel, explicit human-control safeguards, updated 2026 event data, and automated tests plus WebMCP-enabled browser verification. The public repository’s dated commit history and pull requests distinguish the challenge work from the pre-existing product. Challenges The hardest part was designing a workflow that genuinely belonged in a calendar instead of exposing tools only for novelty. We reduced the initial toolset to five actions that all contribute directly to one user goal. We also had to handle calendar conversions, daylight-saving-aware time zones, browser lifecycle cleanup, visible UI synchronization, multilingual RTL layouts, and server/client date hydration consistently. Accomplishments A complete five-tool WebMCP workflow on a real deployed product. Visible calendar navigation rather than hidden tool-only output. Calendar conversion across five displayed systems. DST-aware comparison across international locations. A private, editable plan with explicit human approval before copying. English, Kurdish, Arabic, and Persian support. Automated tests and production browser verification with no page errors or horizontal overflow. What we learned The strongest WebMCP tools are not generic wrappers around buttons. They expose stable product semantics that an agent can compose while preserving visible context and human control. Fewer coherent tools produced a better experience than a larger disconnected tool catalog. What's next We plan to add user-selected cities, reusable family time-zone groups, richer event filtering, export formats, and more regional calendar data. Saving, sending, or sharing will remain explicit human actions rather than autonomous tool behavior.
