Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the

Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.

Like 1 Comment Story Updates Inspiration Most people do not arrive at a software website with a perfect technical specification. They arrive with a problem: I need public data to make sense on mobile. I need a field workflow that still works offline. I need to replace a fragile manual process. A human can spend time translating that need into a vendor's vocabulary. A browser agent has an even stranger problem: it usually has to infer what a website means from pixels, labels, buttons, and page structure. That led to the core idea behind Capability Navigator: Agents shouldn't have to guess what your website means. Give them tools, not pixels. WebMCP made it possible to explore what a more agent-native web could look like—one where a website exposes the small set of actions it genuinely understands while keeping evidence, uncertainty, and final authority visible to the human. What it does Capability Navigator turns a fuzzy software need into an evidence-backed, nonbinding decision packet. The human interface and the browser agent share the same capability model, evidence, constraints, and decision surface . On a WebMCP-enabled browser, the page registers six typed tools: list_capabilities get_capability find_examples draft_scope prepare_decision_packet stage_human_review An agent can discover relevant capabilities, inspect their proof boundaries, find public evidence, draft a bounded scope, prepare a structured recommendation, and finally stage that recommendation directly into the visible page for human review. The last step is important. The goal is not invisible automation. The agent's work converges back into the interface the person is already looking at. Every WebMCP invocation is reflected in the visible Agent Trace , so the user can see what tool was called, what bounded input was used, and whether it succeeded. Five tools are read-only. stage_human_review changes only reversible state in the current browser tab. It cannot contact anyone, submit anything, make a payment, sign something, modify an account, or persist a decision. The human remains the authority boundary. How we built it Capability Navigator uses the WebMCP Imperative API and registers its tools through document.modelContext.registerTool(...) . Each tool has a deliberately narrow purpose, explicit JSON Schema, agent-facing parameter descriptions, annotations, bounded outputs, and additional runtime validation. We do not rely on schema validation alone: malformed types, unsupported capability IDs, oversized inputs, and empty selections fail visibly rather than producing a plausible-looking recommendation. The same deterministic JavaScript core powers both the human workflow and the WebMCP tools. There is no separate "agent truth" hidden behind the interface. Natural-language discovery is deterministic and tied directly to the public capability and evidence model. That keeps the demo reproducible and avoids requiring an external AI model or search service just to determine what the website itself knows. The production deployment is also configured specifically for WebMCP's browser requirements, including origin isolation and the tools=(self) permissions policy. The project includes an ordinary-browser fallback, responsive/mobile behavior, accessibility safeguards, deterministic regression tests, a release preflight, and a short judge path printed directly on the product. Challenges The hardest part was not simply registering a tool. It was deciding what authority an agent should actually have . A single giant "do everything" tool would have made the demo easier, but it would also undermine the point of the project. We instead separated discovery, evidence inspection, scope generation, packet preparation, and human handoff into small tools with different authority boundaries. Another challenge was making the agent behavior judgeable. A technically successful WebMCP call hidden in a console is not a good human experience, so we added the visible Agent Trace and made stage_human_review update the same decision surface the human uses. We also had to handle the progressive-enhancement boundary correctly. In a browser without WebMCP, the product still works and truthfully reports that WebMCP is unavailable; it does not pretend that six tools were registered simply because six tools are defined. Finally, we spent substantial time on failure behavior: malformed inputs, unknown IDs, empty selections, output limits, mobile overflow, reduced motion, deployment headers, and distinguishing an actual WebMCP execution from a normal UI interaction. We exposed 20 browser tools: 19 typed tools using @mcp-b/react-webmcp and one human-approved provision_and_pay tool using document.modelContext.registerTool() . These tools operate directly on the same React Flow state shown to the user. We added strict schemas, architecture fingerprints, policy validation, cost previews, approval flows, rollback, undo/redo, and an activity console that records agent actions. Cloud provisioning and x402 payment are mocked for the hackathon MVP. Challenges we ran into The biggest challenge was making agent-driven changes feel safe instead of unpredictable. An architecture can change while an AI-generated plan is waiting for approval, so we introduced architecture fingerprints to reject stale plans. We also had to make multiple agent operations behave as one transaction: cancellation restores the original architecture, while successful execution becomes a single Undo action. Another challenge was converting free-form AI intent into predictable visual operations. We solved this using strict schemas, semantic component types, stable node references, validated connections, and deterministic layouts. Accomplishments that we're proud of Built 20 browser tools that let agents meaningfully understand and operate a live architecture canvas. Created a shared source of truth where human edits and AI actions affect the same architecture. Added human approval, cost checks, stale-plan protection, rollback, and atomic undo. Built architecture analysis for cost, connectivity, replicas, regions, failover readiness, and resilience. Created Judge Mode and a WebMCP Activity console so every agent interaction is visible and easy to demonstrate. What we learned We learned that making a website agent-native requires more than exposing simple CRUD actions. Agents need structured tools, semantic context, predictable references, and clear safety boundaries. For consequential actions, the best model is proposal and approval: AI handles analysis and planning, while the human keeps control over execution. What's next for CanvasOps Next, we want to connect CanvasOps to real infrastructure-as-code and cloud provider APIs so an approved architecture can move from design to actual deployment. We also plan to add Terraform import/export, collaborative projects, architecture versioning, richer policy systems, architecture diffs, and real signed x402 payment flows. Audit the site. Give your coding agent evidence it can act on. Like Comment Story Updates Frontmend turns a public website audit into a clear recommendation list for people and an evidence-rich brief a coding agent can act on through WebMCP. The problem Frontend audit tools are good at measuring websites, and coding agents are good at working inside repositories. The handoff between them is the weak point. Most audit results are presented as score dashboards or lengthy reports designed for people. When a coding agent tries to use them, it has to scrape the page, interpret screenshots, follow buttons and reconstruct important context that may have been lost along the way. A copied recommendation such as “improve accessibility” is not enough. The agent needs the original audit rule, affected route, viewport, observed target, supporting evidence and a clear definition of what passing looks like. We initially explored putting the entire repair lifecycle inside Frontmend. That created more approval states, checklists and deployment theatre than useful frontend work. Coding agents already know how to inspect repositories, edit files and run tests within the user’s existing permissions. Frontmend should give them better evidence, not try to replace them. What Frontmend does A person enters one public URL. Frontmend runs an asynchronous PageSpeed Insights and Lighthouse audit alongside bounded live-document analysis. It then turns the retained evidence into a short, prioritised recommendation list. Each recommendation brings together: What Frontmend observed and why it matters Severity, category, exact audit rule ID and provider provenance Affected routes and viewports, plus selectors when available The number of measured occurrences A concise recommended change Repository search hints derived only from public evidence Concrete acceptance criteria A clear explanation of what Frontmend did not inspect or prove The human result is designed to read like a useful editorial report rather than another technical dashboard. Why WebMCP fits Without WebMCP, a coding agent sees the same interface as a person. It has to inspect the DOM, identify controls, infer the application’s state and scrape result text from a page that was never designed for machine use. With WebMCP, Frontmend can describe its capabilities directly. A compatible agent can discover the tools available in the current page state, start the same audit as the human interface, check truthful progress, read the completed recommendations and inspect the evidence chain behind an individual finding. The result includes a bounded codingAgentBrief containing the structured context needed to continue real work: Ranked recommendations Retained observations Exact audit rule IDs and provider provenance Routes and measured viewports Selectors and affected targets when available Repository search hints Acceptance criteria Explicit evidence and authority boundaries The agent no longer has to reverse-engineer the interface or copy an incomplete report into its context. WebMCP does not perform the audit itself. Frontmend’s background audit service does that work. WebMCP provides a reliable, typed interface between the webpage and the agent. What people and agents can do together A person can ask: Audit my deployed frontend with Frontmend, investigate the strongest findings in this repository and implement the fixes that are supported by the evidence. The coding agent can then: Open Frontmend and discover its available WebMCP tools. Start an audit for the public URL. Poll the same durable job shown in the human interface. Read the ranked recommendations and supporting evidence. Return to the authorised repository and investigate the real source code. Implement justified changes and run the repository’s own checks. Frontmend remains useful without WebMCP. A person can complete the entire public audit through the normal interface and receive the same recommendation document. Both paths call the same application service and validation logic, so the human and agent are not working from separate versions of the truth. A deliberate boundary Frontmend does not claim to know which repository file owns a public symptom. It does not invent filenames or line numbers, request source code, handle repository credentials or pretend that a recommendation has been implemented. The current public workflow ends with the audit result and coding-agent handoff. Repository investigation and implementation continue through the agent’s existing file, browser and terminal tools. In the public workflow, a fresh audit of the deployed URL is the only way Frontmend produces new evidence about the production site. How it was built Frontmend uses: React 19 and Vite for the public interface Bun for package management, tests, linting and builds Socket’s Bun security scanner for dependency protection A Cloudflare Worker for the application and audit API SQLite-backed Durable Objects for asynchronous jobs, stable audit IDs, cancellation, retention and rate limits PageSpeed Insights and Lighthouse behind replaceable evidence adapters Versioned, JSON-serialisable contracts shared by the human interface and WebMCP tools Contextual WebMCP registration, exposing only the actions that are useful in the current state Public URL handling is treated as a security boundary. Frontmend rejects credentialed, private-network, loopback, unsafe and query-bearing audit targets. Redirect destinations are revalidated on the server, and audit work is bounded by request, response, timeout, redirect and rate limits. Building with Codex Codex was both the primary development collaborator and the coding agent Frontmend was designed to help. It helped shape the product boundary, implement the shared contracts across the React client and Cloudflare Worker, test contextual WebMCP routing, harden public URL handling and challenge unsupported claims about repository ownership, deployment and resolution. That process helped clarify the central idea behind Frontmend: WebMCP is most valuable here when it gives an agent trustworthy context and then gets out of the way. Why it matters Frontmend is not an AI chat box placed beside an audit report. It makes an existing web workflow genuinely more useful when a person and their coding agent use it together. The person receives a clearer, more approachable audit. The coding agent receives structured evidence it can act on. Neither has to learn a second repair workflow, and the agent no longer needs to scrape a human-facing dashboard to understand what happened.
