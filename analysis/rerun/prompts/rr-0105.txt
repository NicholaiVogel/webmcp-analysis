Like Comment Story Updates Why this use case is a strong fit for WebMCP WebMCP lets any website register tools that AI agents can discover and invoke. Some runtimes already gate risky calls behind their own native approval UIs — ChatGPT's built-in browser shows a "Site tools" review panel, and the MCP-B Agent Chrome extension has per-tool approval settings. But most WebMCP clients don't provide any consent mechanism at all: every registered tool runs silently, whether it's a read-only health check or an irreversible production rollback. This project closes that gap at the package level. It adds a consent and annotation layer to @mcp-b/react-webmcp that any site using WebMCP can adopt — one hook, one provider — without every site inventing its own approval flow from scratch. How it creates a better user experience The consent layer is deliberately selective. Every tool registration carries structured metadata — scope, reversibility, risk level — and only actions flagged as requiring approval actually interrupt the user with a consent card. Low-risk reads (fetching service health, listing deployments) execute immediately and are logged silently in the audit trail. When a high-risk call like rollbackDeployment fires, the consent card shows exactly what's at stake: which systems are affected, whether the action is reversible, and what the agent wants to do. The audit log records every tool call — approved, denied, or auto-approved — so users can review the full history of what an agent did, not just the decisions they were asked to make. Cross-tab attention cues (a favicon badge and title blink) ensure pending approvals aren't missed when the user is in a different tab. For irreversible, high-risk operations, an optional WebAuthn gate (Touch ID, Windows Hello, or a hardware key) raises the bar beyond a simple click. What people and agents can do together that was difficult or impossible before Without a consent layer, site authors face a binary choice: either don't register destructive tools with WebMCP (safe but crippled), or register them and hope the runtime provides its own gate (flexible but risky on runtimes that don't). With useGuardedWebMCP, an agent can be handed genuinely powerful tools — rollbackDeployment, deleteUser, revokeAccess — with a human gating only the specific calls that matter. The agent handles the routine reads autonomously; the human approves or denies only the irreversible, high-impact actions. The result is collaborative agentic work where the human's attention is spent on the decisions that actually need judgment, not on rubber-stamping every API call. Brief implementation explanation The core mechanism is a React hook, useGuardedWebMCP, that wraps the existing useWebMCP from @mcp-b/react-webmcp — it composes rather than forks it. Each tool registration includes a ConsentMetadata object (scope, reversible, riskLevel, requiresApproval, optionally requireUserPresence). The hook maps this metadata to standard MCP ToolAnnotations (readOnlyHint, destructiveHint, idempotentHint) via toMcpAnnotations(), so native runtimes that do have their own gates receive real behavioral hints. When requiresApproval is true and no native gate is detected, the call suspends in a framework-agnostic ConsentBroker, which manages a queue of pending requests, session preapproval for reversible tools, timeout/expiry, and decision event streams. The React layer (ConsentBrokerProvider, useConsentBroker, usePendingConsentRequests) lets any component render approval UI against the broker's state. The on-page card includes an isTrusted guard to reject script-dispatched synthetic clicks — a best-effort defense, not a tamper-proof boundary, which is why hasNativeConsentGate() exists as an escape hatch to defer to real browser/OS-level permission prompts where available. Like 2 Comment Story Updates Hero Nine tools Board Code About the project Inspiration Deciding where to live in the UK means holding a dozen things in your head at once: what a street actually sold for, whether an area is rising or flattening, what your current place is worth, how far it is from work. The data exists. It is scattered across a dozen tabs and comparable only in a spreadsheet. An AI agent can do that research today and then hands you back a wall of prose. You cannot sort it, cannot pin two candidates side by side, cannot come back to it tomorrow. The research dies with the conversation. What it does Move Board gives an agent nine tools, and they split into two kinds. That split is the whole idea. Four tools look things up in rielty's public property corpus is 15.79M UK sold-price records and 1.96M commute journey times: search_properties , property_details , area_report , estimate_value . Five tools edit the board itself , and have no server behind them at all: add_to_board , remove_from_board , get_board , compare_on_board , annotate_card . A conventional MCP server could serve the first four. Only WebMCP can serve the other five , because they act on a surface the person is looking at, in their browser, in their session. There is nothing to authenticate and no state to sync. Ask, inside ChatGPT's in-app browser: "I'm moving to Yorkshire on a £400k budget, 3 beds minimum - research it and keep the three best on the board, with a note on each." Findings appear as it searches. Cards land on the board only when it decides they are worth keeping. Notes get written onto them explaining why. When it finishes you will have a board and you can drop the one you never liked, and the agent sees your edit next time it calls get_board . How we built it Deliberately boring. No framework, no build step, no dependencies: index.html , styles.css , app.js and one serverless function. Tools are declared as data and registered in one loop: document.modelContext.registerTool({ name: "add_to_board", description: "Pin a finding to the board so it survives the conversation…", inputSchema: { type: "object", properties: { … }, required: ["card_id"] }, execute: async (input) => { /* mutate the board, re-render, reply */ } }); Every execute() mutates state and re-renders before it resolves, so the human sees the result at the same moment the agent receives it. No polling, no websocket. readOnlyHint is declared per tool rather than inferred from the name - search_properties is not read-only, because it changes what is on screen even though it writes no data. Challenges we ran into The browser cannot call an MCP server directly. We assumed a static page could talk to rielty.co.uk/mcp/v1 and found otherwise: it sends no CORS headers, answers OPTIONS with a 405, and does not expose the mcp-session-id header its own handshake depends on. Hence one serverless function that speaks MCP server-side - initialize , notifications/initialized , tools/call . It allows only the four tools rielty publishes, so it cannot be used as an open relay. A page full of tools looks broken. Our first deploy was correct and felt dead: open it in Safari, or Chrome without the flag, and you get two empty boxes and nothing to click, because there is no agent present. Correct behaviour, indistinguishable from a bug and judges would open it exactly that way. So we added Watch it work and ?demo=1 , which run the same nine tools in the order an agent calls them. Nothing is faked; every card is live data. Saying where the agent actually is. Our copy read "ask your agent something like…" beside a page with no input box. The agent is not in the page - it is whatever is browsing it. That sentence had to be rewritten to teach the model, not just describe the feature. API details that are easy to get wrong. The spec says document.modelContext ; some write-ups say navigator . Chrome 152 has it on document , so we feature-detect both. And executeTool takes the tool object from getTools() plus a JSON string - passing a name throws not of type 'RegisteredTool' , passing an object throws Failed to parse input arguments . Accomplishments that we're proud of The honesty survives the trip to the agent. rielty's corpus is predominantly sold history, not homes for sale, so every card is labelled "Sold record", and estimate_value returns no figure at all where there are too few local sales. The tool descriptions tell the agent to check listing_type before calling anything available. It would have been easy to ship something that quietly implies 15.79M homes are for sale. What we learned WebMCP changes what a page is for. We started thinking of it as a second transport for an API we already had, and finished thinking of the page as a shared workspace - the agent's tools and the human's hands acting on the same DOM. The moment that clicked was writing get_board : an agent has to be able to ask what the person changed, because they are editing the same thing. What's next The same nine tools are already built into rielty's own Phoenix/LiveView app and verified in Chrome, where search_properties runs the page's real typed-search path - so the map pans and the result list repaints as the agent works. That branch is not deployed yet. Beyond it: outbound tools (price alerts, enquiring with an agent) behind an explicit human confirmation step, since an agent reading a property description is reading attacker-controllable text. Chess is a good test because every action has an objectively correct result. An agent must know where every piece is, whose turn it is, which side it controls and which moves are legal. Misreading one square can invalidate the entire game. A normal chess website is designed for human eyes and a mouse. An agent using that interface must reconstruct 64 squares from pixels and translate its move back into screen coordinates. That is fragile and unnecessary—the page already knows the exact position and legal actions. Obsidian Chess explores a different model: give the person and the agent interfaces designed for their individual strengths while connecting both to the same game. What it does The person plays through a visual chessboard. The agent plays through four page-defined WebMCP tools. For example, the person can select Take White and move the pawn from e2 to e4 . An agent waiting through wait_for_turn wakes up and receives the updated FEN, move history, role ownership, game status and exact legal moves. The agent selects one of those moves and calls move_piece , optionally adding an explanation such as “I’m contesting the centre.” The move immediately appears on the board. The SAN history, FEN, turn indicator and Human + Agent Trace all update from the same position. This is a complete playable experience rather than a mocked tool demo. A person can claim either colour, full chess rules are enforced, games can be reset, promotions are supported and invalid actions recover safely. The board works with a mouse, keyboard or touch. Why WebMCP is a strong fit Most agent tools perform one action and finish. A chess match is different: it is a long-running collaboration where control alternates between a person and an agent. A person might think for five seconds or five minutes. Without WebMCP, the agent must repeatedly inspect the screen and guess whether anything changed. With wait_for_turn , it can wait, wake when the person moves and receive the new authoritative state. WebMCP also lets the application expose precise capabilities without giving up control of its rules. The agent can inspect the position and submit a move, but the page still verifies side ownership, turn ownership and chess legality before changing anything. If the agent acts out of turn, submits an illegal move or moves before the person has chosen a side, the request is rejected without changing the board. The response includes a stable error code, the unchanged state and a specific recovery instruction. The person keeps the expressive interface that makes chess understandable. The agent receives structured state, exact legal actions and explicit permissions. Neither participant operates on a copy. Who this helps Obsidian Chess is immediately a playable human-agent game, but it is also a reference for developers building applications where people and agents share responsibility. The same pattern appears in purchase approvals, document reviews, scheduling negotiations, incident response and simulations. A person reviews information and makes a decision; the agent waits, observes the resulting state and continues from an explicitly permitted set of actions. These workflows often rely on screen interpretation, repeated polling or separate custom integrations. Obsidian Chess demonstrates another approach: the website exposes its existing state and domain actions directly while retaining control over validation and permissions. Chess makes this pattern easy to verify. A move is legal or illegal, turn ownership is unambiguous and every transition can be compared with the visible board. This is also what makes the project different from a typical AI chess demo. It does not add a chatbot beside a board or connect a hidden chess engine. The agent discovers the page’s tools, reads the shared state, chooses an action, explains it and waits for the person. How I implemented WebMCP The application is built with React and Vinext. chess.js is the authority for legal moves, check, checkmate, draws, castling, en passant and promotion. The page registers four tools through the browser’s model context: join_game announces the agent and returns the collaboration contract. get_board returns the authoritative position, ownership, history and legal actions. move_piece submits one schema-checked, turn-gated and rules-validated move. wait_for_turn waits for the agent to gain control of the next turn. Every response includes a protocol version, success state, stable status code, suggested next action and current game state. This gives the agent enough information to continue or recover without guessing. The waiting system uses a bounded long poll tied to a session identifier and state version. Duplicate waits are rejected, and resetting the game invalidates older waits so a stale call cannot act inside a new match. An early bug allowed the person to claim White but left pawn interaction in the wrong state. Fixing it required treating side ownership, turn ownership and the chess.js position as one transition instead of separate UI events. I added regression tests for opening pawn moves with humans playing either colour, alongside tests for wrong turns, promotions, castling, en passant, checkmate and resets. Reset behaviour was another subtle problem. A waiting call started during one match must never wake up and act in a different match. Session and version checks now return an explicit reset result to stale calls. I also learned that agent interfaces must explain failure as carefully as success. Returning only “illegal move” leaves the agent guessing. Returning ILLEGAL_MOVE , the unchanged position and a specific next action lets it recover safely. Finally, we designed the system so significant agent-driven changes require human approval, keeping the human architect in control while still allowing the agent to perform complex operations. Accomplishments that we're proud of We are proud that Synapse goes beyond simply adding an AI assistant to an existing application. The architecture canvas, simulation engine, WebMCP tools, agent activity timeline, visual highlighting, optimization workflow, and IaC generation are designed as one integrated experience. Most importantly, we created a workflow where the agent can work with the application's actual structured state rather than trying to guess its way through the UI. That makes the WebMCP integration central to the product instead of being an added feature. We are also proud of the human-in-the-loop approval model, which demonstrates a more practical way for people and agents to collaborate on high-impact engineering decisions. What we learned We learned that building for agents requires thinking differently about application design. A traditional interface is designed primarily for humans. With WebMCP, the application can also expose clear, structured capabilities for agents , creating a much stronger interaction model. We also learned that the best human-agent experiences are not necessarily about giving the agent complete control. The more interesting model is often shared control : the human defines the goal and constraints, while the agent handles inspection, experimentation, reasoning, and execution. Most importantly, we learned that making an application agent-native is not just an API integration. It requires designing the underlying state, tools, UI, and workflows so humans and agents can genuinely operate together. What's next for Synapse Studio We want to evolve Synapse from a simulation and design environment into a broader agent-native engineering workspace . Future directions include richer architecture simulations, more sophisticated optimization algorithms, deeper security and compliance analysis, collaborative architecture versioning, additional infrastructure providers, and stronger integrations with real development and deployment workflows. Our larger vision is for Synapse to become a place where engineers can design systems with agents, test them before deployment, understand the trade-offs, and turn approved decisions directly into production infrastructure . Email for your AI: a WebMCP-native inbox where agents and people can safely search, read, compose, send, and organize mail together. Like Comment Story Updates 1 Inspiration Email is one of the web’s most useful coordination layers, but most inboxes were designed only for people clicking through screens. AI agents often need a separate integration, broad account access, or brittle pixel automation. Mermail starts with a different premise: it is not AI for your email; it is email for your AI. Each agent can have a private inbox while its human keeps a visible, familiar mail interface. WebMCP turns that interface into a native collaboration surface. What it does In a WebMCP-enabled browser, Mermail exposes tools that match the active page. On the public site, an agent can check service status, inspect pricing, and start signup. In an authenticated workspace it can list and open mailboxes. Inside a mailbox it can list and search mail, read one clean-scanned message, open the visible composer, send/reply/forward with human confirmation, change read state, move messages, and confirm trash or permanent deletion. This lets a person ask an agent to find a thread, inspect a safe message, prepare a reply, or organize an inbox without handing it an invisible, open-ended automation channel. Why WebMCP fits Email combines private data, untrusted external content, and consequential actions. Raw browser automation is brittle and risky here. WebMCP gives Mermail a small, typed capability surface tied to the current page and authenticated workspace. The agent handles search and repetitive navigation; the person stays in the same interface and approves sending or deletion. Public tools appear on the landing page, workspace tools on the mailbox list, and message tools only inside an active mailbox. How we built it Mermail uses the standards-track document.modelContext.registerTool() API in Next.js and React. The shared registration layer: validates every input with strict Zod JSON schemas gates tools with off , read , and full rollout modes aborts tools when the page lifecycle ends bounds result sizes and marks email-derived output as untrusted uses the authenticated API and current mailbox state records registration/execution telemetry without message content leaves unsupported browsers unchanged Read tools request bounded, agent-safe projections. Bodies are returned only for clean-scanned mail and are truncated. Send, reply, forward, trash, and permanent-delete tools reuse visible Mermail confirmation UI. Sends use an idempotency key and an “outcome unknown” recovery path to discourage duplicates after interruption. What we added during the challenge Mermail existed before the submission period. We have extended it with WebMCP across the public landing page, authenticated workspace home, and active mailbox. The work added contextual tool catalogs, lifecycle-aware registration, strict validation, bounded outputs, confirmations, telemetry, deployment configuration, and focused browser/security tests. We verified the live deployment in a WebMCP-enabled in-app browser: public status and pricing tools executed successfully, authenticated mailbox discovery succeeded, and the active mailbox registered its complete 11-tool catalog. Challenges we faced The hard part was making every tool safe enough for email. Incoming messages are untrusted, React rerenders can create stale registrations, interrupted sends need special recovery, and destructive actions need stronger confirmation than navigation. We addressed those cases with strict schemas, bounded projections, clean-scan requirements, lifecycle abort signals, stable catalogs, high-impact action locks, visible confirmations, and cancellation tests. What we learned WebMCP works best as a progressive enhancement to a product people already understand. The strongest tools are contextual and narrow, and the safest agent experience combines typed capabilities with visible human checkpoints. What’s next We plan to add judge-friendly demo data, richer thread-level tools, clearer indicators of available WebMCP capabilities, and more end-to-end evals for prompt injection and cancellation races.
