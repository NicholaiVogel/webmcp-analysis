## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the

sums.

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under

API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.

For PowerPoint export, I ended up building the exporter directly. Comake converts its presentation model into the OOXML files used by PowerPoint and creates the .pptx ZIP archive in the browser. Challenges we ran into The hardest part was not making an agent click buttons. The harder problem was figuring out what collaboration between a human and an agent should actually mean. For example, an agent needs more than the entire presentation document. It needs to know what the human is looking at right now and which elements the human selected. At the same time, that focus can change without the presentation itself changing. That led me to separate document revisions from focus revisions and expose the current human context directly through WebMCP. Another challenge was concurrent editing. An agent might read revision 10, spend some time planning an edit, and then submit its changes after the human has already created revision 11. I didn't want Comake to accept stale operations and accidentally destroy the user's work, so writes are revision-aware and atomic. Reversibility was another important problem. If an agent makes ten changes to improve a slide, undoing those changes one by one would be a bad experience. Comake groups accepted agent operations into attributed ChangeSets, which can be inspected and reverted as a unit. Building a usable slide editor itself also took a lot of work. Selection, multi-selection, resizing, element ordering, keyboard interaction, presentation mode, and translating the same visual model into a valid PowerPoint file all have a lot of small edge cases. Accomplishments that we're proud of I'm especially proud that Comake is not just a presentation editor with an AI chat box added beside it. The agent is working with the actual application model. It can understand the user's current focus and exact selection, reason about the geometry of a slide using structured data, and make changes through the same canonical editing system used by the human. I'm also proud that Comake is not bound to one specific agent. There is no proprietary agent runtime required by the application. The integration boundary is WebMCP, so the presentation workspace itself becomes agent-capable. Another part I'm proud of is making agent actions attributable and reversible. I think being able to see what an agent changed — and undo that entire change if it was wrong — is important if humans and agents are going to work on the same artifact. And writing the PowerPoint exporter from the underlying format was probably one of the more unexpected parts of this project. Being able to create something together with an agent and then export it as a normal PowerPoint file makes Comake useful outside of the demo itself. What we learned The biggest thing I learned is that designing tools for an agent is also product design. It is not enough to expose every internal function as a tool. The agent needs a good starting point, compact ways to understand the current state, stable identifiers, clear schemas, and errors that tell it how to recover. I also learned how important human context is. Giving an agent the whole document is not the same as telling it, "this is what the human is working on right now." Selection and focus are a surprisingly powerful communication channel between a human and an agent. I also started thinking differently about undo and history. When an agent can perform many operations in one task, attribution and reversibility become much more important than they are in a normal single-user editor. Most importantly, WebMCP showed me that an application does not have to choose between being built for humans or being built for agents. The same web application can provide a visual interface for the human and a structured interface for the agent, with both working on the same underlying state.
