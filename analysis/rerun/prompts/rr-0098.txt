# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value

- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

What it does Toolsmith registers five permanent tools on document.modelContext . One of them, forge_tool , takes a name, a JSON Schema and a JavaScript body, and turns them into a real WebMCP tool the same agent can call seconds later — but only after a human grants it. The loop: the agent calls read_workbench to learn your real column names → calls forge_tool to build the button that isn't there → the page renders it as pending , code on screen and editable, not registered → you press Test run to execute it against your real data before it exists → you press Grant it , which calls registerTool with its own AbortController → the agent presses its new button in the same conversation → Take it back aborts that signal and the button leaves the registry immediately. The count in the header — "buttons the agent can press" — is the honest answer to what can this agent do right now? And a person decided every one of them. How WebMCP is used This is not a wrapper around an existing app; the spec's lifecycle is the product. Every built button is registered via registerTool(tool, { signal }) with its own AbortController . Unregistration isn't a side feature here — aborting that signal is the revocation mechanism the entire safety argument rests on. The tool surface is genuinely dynamic and authored at runtime by the agent talking to the page. getTools() and the toolchange event drive the live count in the header. annotations.untrustedContentHint on every built button, because its output is computed by code an agent wrote minutes ago. annotations.readOnlyHint on the two read-only tools. forge_tool accepts the child tool's inputSchema as a JSON string, validates it, and passes it to registerTool as a real JSON Schema object — schema round-tripping through a tool call. Native document.modelContext when present; otherwise a vendored @mcp-b/global polyfill. The header pill says which one you got. A button you didn't read is not a button you granted Self-extension is only acceptable if refusing is as cheap as granting. So: nothing registers before a human approves; the schema and function body stay on screen and editable, with a Test run that executes against real data before registration; each call spawns a fresh Web Worker with fetch , XMLHttpRequest , WebSocket , EventSource , importScripts , storage and navigator deleted from the global scope before the code is compiled (verified: built code sees typeof fetch === "undefined" ); a 3-second leash terminates runaway loops; editing a granted button unregisters it and sends it back for re-approval; reloading returns every button to pending, never to granted; and every call, with arguments and results, lands in the activity log. The agent stages a bounded next step; the human approves it for review, while execution remains NOT_EXECUTED and the machine stays untouched Inspiration I started Machine Passport from a very practical problem I keep running into: having several machines does not mean you actually know which one is ready for a specific job. A machine can have the best CPU, the most RAM, or the strongest GPU and still be the wrong machine for an unattended workload because qualification is incomplete, recovery is unproven, deployment is fragile, or an important security fact is simply unknown. That led to the question behind the whole project: What if an AI agent could help choose the safest machine for the job from evidence — without giving the agent authority to change the machine? That is Machine Passport. The central idea is simple: The fastest machine is not always the safest machine for the job. What it does Machine Passport turns machine evidence into a versioned passport and then evaluates readiness for a specific role across four dimensions: FIT DEPLOYMENT QUALIFICATION SECURITY The result is deterministic rather than an LLM opinion. One rule became especially important while building it: UNKNOWN stays UNKNOWN. If evidence is missing or a collector could not obtain it, Machine Passport does not silently turn that absence into a pass or a fail. In the public demo, Atlas has the strongest hardware, but for an unattended AI workload it is NOT_READY . Beacon is a more modest machine, yet it is READY_WITH_LIMITATIONS and has no hard blockers. That difference is the product. Why WebMCP matters Without WebMCP, Machine Passport is already useful as a human dashboard. With WebMCP, the page becomes something an agent can work with directly. Instead of trying to infer machine state from rendered UI or DOM structure, the page exposes five typed tools over the same state the human sees: list_machines get_machine_passport assess_role_readiness compare_machines stage_change_proposal The first four are genuinely read-only. The fifth can stage a bounded proposal in application state. That means I can ask: Which machine is safest for an overnight AI workload, what blocks the runner-up, and what is the smallest safe next step? The agent can inspect the evidence, compare the machines, explain the result, and stage the proposed next step. The proposal then appears in the same page for human review. That shared state is the part I find most interesting about WebMCP: the human and the agent are not operating two separate versions of reality. Human authority is part of the design I deliberately did not give the WebMCP tools SSH, PowerShell, device access, or machine mutation. Machine Passport is the pre-action decision layer . The agent can inspect and stage. The human decides. Even after the human clicks Approve for Review , the proposal still says: execution_state = NOT_EXECUTED That is not unfinished functionality. It is the authority boundary of this version. Agents inspect and stage. Humans decide. Machines stay untouched. How I built it The public challenge version is intentionally small and inspectable. It is a static web application with: a normalized MachinePassport schema, strict JSON validation, explicit evidence provenance, deterministic readiness rules, conservative UNKNOWN semantics, five WebMCP tools, shared proposal state, and a human review interface. The public app uses three clearly synthetic machines: Atlas, Beacon, and Relay . The same frozen import and readiness core was also privately validated against one sanitized real machine passport . I kept that claim deliberately narrow. This is not a fleet-management product and I am not claiming production deployment. The current version has 157 deterministic tests , including malformed imports, UNKNOWN preservation, readiness aggregation, proposal transitions, blocker semantics, retry-safe staging, and machine-mutation invariants. Challenges I faced One of the most useful lessons came from testing the real agent journey instead of only testing the code. During a live ChatGPT run, an identical tool retry initially created a duplicate proposal. That exposed something unit tests had not made obvious enough: an agent-facing action needs to tolerate repeated calls. I changed staging so that an identical active request returns the existing proposal instead of creating another one. Another issue was blocker semantics. A limitation on an otherwise healthy readiness dimension was being presented too strongly. I changed the policy so a finding becomes a blocker only when its evidence intersects a dimension that is actually NOT_READY or UNKNOWN . Those fixes reinforced the same lesson: the contract exposed to an agent has to be stricter than the UI alone suggests.
