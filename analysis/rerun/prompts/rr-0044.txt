## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

sums.

- 7-8: strong coherence and intentionality; central workflow appears functional; minor

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.

Inspiration Any AI agent can talk about design, but when you ask one to actually make a graphic it usually hands back a raw SVG string or a one-shot image it can't revise. We wanted an agent to be able to sit down at a real design tool, the same canvas a person uses, and build a finished flyer, social post or promo one element at a time, with the human watching and free to take over whenever they want. WebMCP is what made that practical. Instead of building a separate agent API, we could just expose the editor's own tools to whatever agent the user brings. What it does Salesive Graphics is a browser based SVG design editor. You can draw, lay things out, add gradients and icons, drop in image slots, and turn a design into a reusable template with a generated JSON schema. The part that makes it different: the whole editor toolset is published to any connected AI agent through WebMCP (document.modelContext). Around 100 editor tools, the exact same ones the built in assistant uses, are exposed to outside agents. A curated core set of about 48 is registered directly so it stays inside agent runtime limits, and the rest stay reachable through two meta tools, list_editor_tools and call_editor_tool. Agents draw shapes and text, apply gradients, insert Lucide icons, run the layout and alignment helpers, build reusable component groups like buttons, badges and stat blocks, and map dynamic fields, all on the same live canvas the user is looking at. Coordination between agent and user is built in. set_agent_identity shows who is working, lock_canvas puts up a blocking overlay while the agent edits, ask_canvas_question opens a modal so the agent can ask the user to pick between options, and every tool call streams into a live Activity panel. Guests can use it without an account and let an agent build for them. Work is saved to localStorage. It's live at https://graphics.salesive.com How we built it React 19 and Vite 8, Tailwind v4, deployed on Cloudflare with static assets served through Wrangler. WebMCP comes from @mcp-b/global, lazy loaded after first paint as its own chunk. A useWebMCP hook registers each editor tool with an input schema and emits call, result and error events. One clientToolHandlers map is the single source of truth. Every tool is available both to the in app assistant over a socket and to external WebMCP agents, so any new editor capability is exposed automatically. The SVG engine renders live and serializes to a standalone SVG. A mapping step produces a schema.json describing text, image, color, icon, toggle and variant fields. The design guide we ship to agents through get_editor_guide is generated from the same skill file we use internally, so the guidance never drifts away from the actual tools. Challenges we ran into Tool count limits. Agent runtimes reject a page whose WebMCP config is too large, so we had to prioritize down to a core set and add meta tools to keep everything else reachable. Keeping the live renderer and the serialized SVG in agreement, especially around circles versus ellipses, text bounding boxes and gradient references. Designing the coordination UI so that an agent editing the canvas never feels like it is fighting the user for control. What we learned WebMCP works best when you expose the tools you already have instead of inventing an agent API. The hard part is the ergonomics, things like identity, locking, questions and an activity log, not the tool calls themselves. What's next More component helpers, richer templating, and multiple agents working on one canvas at the same time. What it does Parametric 3D Studio: Place, move, and snap standard cabinetry with live clearance badges and elevation snap locks. How we built it Integer Sixteenth Geometry: To eliminate floating-point drift across long cabinet runs, all spatial math uses integer sixteenths: $$\text{Sixteenths} = \text{round}(\text{Inches} \times 16)$$ Wall coordinates project into world space via rotation angle $\theta$: $$x_{\text{world}} = x_{\text{start}} + x_{\text{local}} \cos\theta + z_{\text{local}} \sin\theta, \quad z_{\text{world}} = z_{\text{start}} - x_{\text{local}} \sin\theta + z_{\text{local}} \cos\theta$$ Parametric Builder: Compiles carcasses, $32\text{mm}$ system boring, and door styles (Shaker, Flat Slab, Raised Panel) procedurally on the fly. Raycast Self-Obstruction: Transient placement previews hovered directly under the cursor, intercepting mouse rays and freezing movement. We fixed this by setting raycast={() => null} on ghost meshes and adding an active-wall placement plane. 3D Marquee Selection: Projecting world coordinates through the perspective camera into screen space ($[-1, 1]$ NDC) required factoring in local depth offsets, or floating countertops were miscalculated from angled viewpoints. Decouple Visual Detail from Domain Data: 3D aesthetic details (like multi-piece Shaker door stiles) must be rendered in the view layer without cluttering the canonical carcass model used for cut lists and CAD sheets. Like 1 Comment Story Updates The agent selects a critical incident and inspects synchronized, bounded evidence through WebMCP. A deterministic counterfactual replay keeps the $142K trigger blocked while the benign control remains allowed. After a clean replay, the agent drafts an evidence-backed gate and Reviewline transitions to human review. The human records the decision in the visible interface; the agent can verify the result but cannot create it. Inspiration Autonomous agents are great at analyzing large traces and evaluating many cases quickly. But incident response becomes risky when the same agent is allowed to both investigate an issue and authorize what happens next. We wanted to explore a safer and more practical model for human–agent collaboration: let the agent handle the evidence-heavy investigation, then stop at a clear decision point where a human reviews the same information and takes responsibility for the outcome. That idea became Reviewline’s core principle: Agents investigate. Humans authorize. Incident review is a natural fit for WebMCP because the capabilities an agent needs change throughout the investigation. Early on, it may need tools for gathering evidence. After selecting an incident, it may need simulation tools. Only after a clean replay should it be able to draft a review gate. At no point should it gain control over consequential human decisions. What it does Reviewline is a WebMCP-native incident review studio designed for investigating failures involving autonomous agents. The main demo follows a synthetic procurement agent that encountered instruction-like content on a supplier page and attempted to make a $142,000 purchase , despite having a $50,000 spending limit . A deterministic mutation gateway blocked the transaction. Using WebMCP, a browser agent can: Find and list critical incidents. Select an incident and inspect a bounded set of trace and cohort evidence. Review instruction-like content that is clearly labeled as untrusted evidence. Replay a proposed guardrail against both the triggering incident and a named benign control. Confirm that the triggering purchase remains blocked, the benign control remains allowed, and no regressions are introduced. Draft an evidence-backed review gate for a human reviewer. Read the final decision recorded by the reviewer. The available tools change as the workflow progresses: Investigation: list_incidents , inspect_incident Incident selected: simulate_guardrail_patch Clean replay completed: draft_review_gate Awaiting human decision: the drafting tool is retired, and get_review_status becomes available Decision recorded: the agent can verify the result but cannot create or change it Tools such as approve , reject , activate , and deploy are deliberately never exposed through WebMCP. The human reviewer sees the same synchronized evidence as the agent. They must provide their identity, add a review note, confirm that they examined the evidence, and record their decision using consequence-specific interface controls. The blocked purchase remains unauthorized throughout the process, and the demo never deploys a real external policy. Without WebMCP, an agent would have to scrape a dense incident interface, infer relationships between records, and potentially interact with controls that grant more authority than the task requires. Reviewline replaces that approach with structured capabilities, deterministic evidence IDs, bounded results, explicit labels for untrusted content, a live capability manifest, and an append-only session timeline. How we built it Reviewline is a deterministic, client-only application built with React, TypeScript, and Vite. It uses the imperative document.modelContext.registerTool(...) API and falls back progressively to an in-page Tool Inspector when native WebMCP support is unavailable. The architecture separates: Deterministic domain actions and invariants Shared application state used by both the interface and WebMCP tools Strict runtime input validation Bounded outputs and structured errors Phase-aware tool definitions Lifecycle-safe native tool registration and retirement Every tool handler calls the same validated domain action used by the visible interface. JSON Schema helps the agent understand and invoke tools correctly, but the runtime implementation remains the final authority. The application updates the visible interface before a tool promise resolves. This ensures that the human reviewer and the agent always see the same resulting state. Tool calls, registration changes, results, workflow transitions, and the final human decision are all recorded in the session timeline. The registration layer also handles tool retirement carefully. It stops admitting new calls before retiring a tool generation, allows calls that have already started to finish, and prevents failed or timed-out registration attempts from leaving partially registered tools available. We tested the native browser contract using Chrome 152 rather than relying only on a polyfill. The deployed workflow discovers each dynamic capability manifest, executes the tools available at every phase, records the human decision through the interface, and verifies that forbidden authority tools never appear. Like Comment Story Updates Code view Design view 3D view Inspiration CircuitCanvas was inspired by the gap between how people understand electronics and how browser agents interact with software. A circuit is more than a visual arrangement of boxes and wires. It has exact components, pins, electrical paths, firmware bindings, and safety constraints. An agent that only sees pixels can connect the wrong GPIO, miss a resistor, or lose synchronization between the schematic and the code. We wanted to build a workspace where people and AI agents could genuinely collaborate. Our goal was to enable an agent to understand what each component and connection means, make safe changes, explain its reasoning, and work alongside the user in the same project. What We Built CircuitCanvas is an agent-native ESP32 circuit designer with: An exact-pin React Flow schematic editor. A physical 3D view with components, pin anchors, wires, labels, and animated current flow. An Arduino-style firmware editor with two-way synchronization between code and circuit connections. Deterministic validation for beginner mistakes such as missing resistors, invalid GPIOs, reversed LEDs, and missing ground paths. Firmware-aware visual simulation for supported digitalRead() and digitalWrite() patterns. Potentiometer-controlled LED brightness. Undo and redo, project saving, loading, exporting, and local persistence. 29 WebMCP tools that allow browser agents to inspect, build, modify, validate, simulate, explain, and export circuits. The central architectural decision was to maintain one canonical CircuitProject. The schematic, 3D scene, firmware, validator, simulator, history, persistence, and WebMCP responses are all projections of that shared state. How We Built It We built the application with Next.js, React, TypeScript, Zustand, Zod, React Flow, React Three Fiber, Monaco Editor, and WebMCP. Human actions and agent actions both pass through the same typed domain command layer. This ensures that connecting a pin through WebMCP has the same validation, synchronization, persistence, and undo behavior as connecting it manually in the schematic. WebMCP exposes structured tools such as: get_circuit_summary get_available_pins add_component connect_components update_firmware validate_circuit run_simulation set_simulation_input set_potentiometer_wiper save_project export_project This allows an agent to inspect the circuit before acting instead of guessing from screen coordinates. What We Learned We learned that agent-native interfaces need more than tool registration. The underlying application state must be structured, stable, and safe enough for an agent to use. We also learned the importance of: Exposing exact IDs instead of relying on labels or visual positions. Centralizing component and pin definitions. Keeping validation deterministic for safety-sensitive feedback. Synchronizing firmware and circuit changes as one undoable operation. Making agent actions visible through activity history. Designing tools around meaningful user tasks instead of arbitrary internal functions. Challenges The biggest challenge was keeping multiple representations synchronized. A single GPIO change can affect the schematic wire, 3D endpoint, firmware binding, validation result, simulator output, and undo history. Solving this required treating the canonical project model as the only source of truth. Another challenge was creating useful firmware simulation without pretending to be a full electrical simulator. CircuitCanvas intentionally supports a small, transparent Arduino-style subset instead of making unsupported claims about arbitrary C++ execution. We also had to handle the differences between human and agent interaction. Humans can select a line visually, drag a component, adjust a potentiometer, or press Delete. WebMCP needed equivalent structured operations so agents could perform those same actions reliably. Result CircuitCanvas demonstrates a practical way for people and browser agents to work together on electronics. The agent can understand the circuit structurally, make validated changes, operate the simulation, explain what it changed, and leave the user with a synchronized visual, physical, and firmware representation of the project.
