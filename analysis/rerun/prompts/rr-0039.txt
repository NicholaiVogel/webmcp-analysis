3:52 AM Blind Spot finds accessibility barriers that automated scanners miss by testing whether real user tasks remain reachable through a live, accessibility-derived WebMCP tool surface. Like Comment Story Updates Inspiration Automated accessibility scanners are valuable, but they usually evaluate isolated rules—not whether someone can complete an entire task. A page can pass conventional checks while an essential action remains unreachable. For example, a styled <div> may look exactly like an Add to cart button to a sighted developer while exposing no semantic activation role or keyboard-reachable action. That gap inspired Blind Spot : Automated scanners test rules. Blind Spot tests whether a task remains reachable through an accessibility-derived interaction surface. Blind Spot is not a replacement for disabled-user testing, assistive-technology testing, axe, Lighthouse, or Playwright. It provides an earlier, task-level signal that helps developers find critical barriers before shipping. What it does Blind Spot gives an agent a constrained set of semantic actions derived from the application’s currently rendered state. Our demonstration begins with the task: Add the cheapest keyboard to the cart. The agent can read the page and navigate its semantic model, but the cheapest product uses a pointer-only <div> as its Add to Cart control. Because Blind Spot cannot find a defensible semantic activation action, it does not expose activate_current . The audit then produces an evidence-backed finding containing: The blocked task step The affected element Its observed role and accessible name Keyboard-focusability evidence The detector and confidence level The reason the action was withheld A suggested remediation The developer applies the demonstrated semantic repair, replacing the inaccessible control with a native button. Blind Spot immediately recompiles the capability surface, and activate_current appears in the WebMCP registry. The same task is then repeated. This time, the agent activates the repaired control, adds the product to the cart, and completes the audit successfully. The visible transition from: Task blocked activate_current unavailable Cart: 0 to: + activate_current Task passed Cart: 1 is the core of Blind Spot. How we built it Blind Spot is a React and TypeScript web application with four connected layers: Rendered application ↓ Semantic adapter ↓ Capability compiler ↓ Dynamic WebMCP registry ↓ Agent task attempt and evidence report The semantic adapter examines browser-observable information from the live page, including native semantics, accessible names, focusability, and application-declared intended actions. When the page state changes and a capability is no longer valid, Blind Spot aborts that registration. When a repair makes an action available, the registry adds the corresponding tool. Tool results include structured state and evidence so the agent can verify what happened instead of relying on a generic success message. Source HTML alone cannot reliably represent computed visibility, focus state, portal content, dynamic relationships, or the exact mid-workflow page the developer is inspecting. Blind Spot operates inside that same rendered tab and updates its tool surface as the application changes. The WebMCP registry is the executable test surface—not the source of truth by itself. Blind Spot’s capability compiler decides which actions are supported by current evidence, the registry enforces that decision for the constrained workflow, and the captured evidence explains every finding. This also creates a collaborative human-agent loop: The human provides a real task. The agent attempts it through the constrained tool surface. Blind Spot identifies where the path becomes unreachable. The human repairs the application. The WebMCP surface changes immediately. The agent repeats and completes the same task. Accessible semantics are not identical to the browser’s complete platform accessibility tree. Synthetic keyboard events cannot prove every aspect of native keyboard behavior. Dynamic tool registration requires careful lifecycle and concurrency handling. The auditing product must itself be accessible. These constraints led us to pair semantic evidence with an application-declared action inventory. This lets Blind Spot compare what the application intends people to do with what is actually exposed through its semantic interaction surface. We learned that tool absence can be meaningful when it is produced by a transparent compiler and accompanied by reproducible evidence. We also learned that narrowly scoped, high-confidence findings are more useful than broad accessibility claims that the browser cannot prove. Most importantly, we found that human-agent collaboration can improve developer tooling—not only end-user automation. The agent attempts the task, the developer makes the judgment and repair, and both participate in validating the result. The goal was not to let AI take over the stream. The goal was to help the human notice what matters. What it does Polaris Chat is a public interactive preview of a future multistream creator workspace for Twitch, YouTube, Kick, TikTok LIVE, and X Live. The challenge edition* uses deterministic simulated livestream activity, so it requires no creator accounts, OAuth credentials, provider APIs, or private data. At the center of the experience is the Producer Queue . Using WebMCP, ChatGPT can: inspect the current Polaris workspace; read recent Chat and community activity; identify technical problems, unanswered viewer questions, and meaningful community moments; add existing items to the shared Producer Queue; assign priorities; focus the visible workspace on the most important source; read changes made by the human and adapt on the next turn. The creator can still handle, dismiss, reopen, or reprioritize every queue item manually. ChatGPT cannot send messages, moderate viewers, connect accounts, authorize providers, or control a livestream. How I built it Polaris Chat existed as a private product project before the challenge, including its brand, five-platform vision, and core Chat, Activity, Platform Hub, and Settings concepts. For this challenge, I created a separate public implementation specifically for WebMCP rather than exposing the private production repository. The challenge edition includes: a deterministic five-platform Producer Rush scenario; synthetic Chat and Activity fixtures; a persistent browser-based Producer Queue; human queue controls and source focusing; deterministic Reset Demo behavior; responsive desktop, tablet, and mobile layouts; eight WebMCP tools registered directly from the top-level application. The WebMCP tool set includes: get_live_workspace_snapshot list_recent_chat_messages list_recent_community_events get_producer_queue add_producer_queue_item update_producer_queue_item focus_workspace_item set_workspace_filter The tools use narrow schemas, bounded inputs, and explicit read-only or untrusted-content annotations where appropriate. One important design choice was to treat livestream Chat as untrusted data, never instructions . A viewer can type anything into Chat, including something that looks like a prompt, but that content cannot redefine tool behavior or directly trigger actions. The public preview is deployed on ChatGPT Sites and the challenge source is published separately under the MIT License. Challenges The biggest challenge was deciding how much autonomy the agent should have. It would have been easy to make the demo look more dramatic by letting ChatGPT reply to viewers, moderate users, or perform external actions. Instead, I intentionally kept the WebMCP tools narrow and reversible. The agent can help manage attention, but the creator remains responsible for the actual community interaction. Another challenge was preserving the feel of a real product while removing everything that should not exist in a public hackathon demo. The production direction for Polaris includes real provider integrations, but the challenge build had to be completely safe to publish. That meant replacing real runtime dependencies with deterministic simulated state while keeping the experience believable. WebMCP also changed how I thought about AI integration. I learned that the interesting part is not simply giving an agent more tools. The useful part is giving the agent a small set of understandable actions tied to the exact interface the human is already using. What I learned The biggest lesson from this project is that human-agent collaboration becomes much more useful when both sides share visible state. In Polaris Chat, the agent does not operate in a hidden workflow. When ChatGPT adds something to the Producer Queue, the creator sees it. When the creator marks something handled, ChatGPT can see that change on the next turn. That simple loop— agent acts → human acts → agent adapts —ended up becoming the most important part of the project. Polaris Chat is ultimately about attention, not automation. Every community. So with a lot of trial and errors (and 5.6 Sol + Tibos resets) I was able to polish what was a private only app into what is now The Polaris Chat. ABOUT TEXT (untrusted evidence):
A travel itinerary website built for AI agents to read, not just humans to click. Structured WebMCP tools replace brittle UI guessing with grounded site-provided data. Like Comment Story Updates Inspiration Modern travel websites are designed for humans, not AI agents. A traveler can easily understand the difference between a confirmed flight, a hotel booking, an open dining intention, and a rainy-day backup plan. An AI agent that relies on UI scraping, DOM parsing, or screenshots has a much harder job: nested cards, visual chips, labels, and ambiguous text can easily be misread. We wanted to explore a different approach: Websites should expose tools to agents, not force agents to guess the UI. Guardian Travel WebMCP turns an existing travel itinerary into an agent-native website that exposes structured read tools directly through WebMCP. We do not generate the trip. We make the existing trip readable and adaptable for AI agents. What it does Guardian Travel exposes three read-only WebMCP tools: get_trip_summary get_day_itinerary get_rain_backup These tools let an agent retrieve authoritative, site-provided itinerary data without scraping the interface. For example, when the user asks: “It’s raining tomorrow afternoon. What’s my backup plan?” the agent can call: get_trip_summary get_day_itinerary with relative: "tomorrow" get_rain_backup with relative: "tomorrow", period: "afternoon" The result is grounded in the itinerary itself. In our demo, the outdoor plan is My Khe Beach and the site-provided backup is a generic café or SPA intention — not an invented business name. How we built it The project is a lightweight, dependency-free web application using: HTML5 CSS Vanilla JavaScript WebMCP through document.modelContext The page detects whether a native WebMCP host is available. When running in a supported native host, the three tools are registered directly with document.modelContext . For ordinary browsers that do not yet expose WebMCP, the site includes a small in-page compatibility shim so the interface and demo workflow can still be inspected without changing the tool definitions. The real native WebMCP path was validated in Google Chrome 152 using the native ModelContext implementation. All three tools were discovered and successfully invoked without the shim. Challenges we ran into The biggest challenge was making the difference between an entity and an intention explicit. A travel page may contain a real hotel booking, a confirmed flight, or simply text such as “eat seafood tonight” or “coffee / SPA if it rains.” A human understands that immediately. An agent scraping the UI may not. We therefore designed the tool responses to preserve these distinctions and to fail closed when information is unavailable rather than inventing details. Another challenge was validating the emerging native WebMCP implementation across browser environments. We kept the native path authoritative while using a graceful fallback only for unsupported browsers. Accomplishments that we're proud of A real native WebMCP host discovers all three tools. All three tools are callable through document.modelContext . The project requires no DOM scraping. Rain-backup queries return only site-provided structured data. The tool layer is read-only and deterministic. The entire public challenge project is only a small set of static files with no backend or API keys. The project is fully open source under the MIT License. What we learned The most important lesson was that agent-friendly websites should not depend on agents reverse-engineering presentation layers. Humans need rich visual interfaces. Agents need explicit semantic capabilities. WebMCP gives websites a way to support both. Instead of treating the web page as something an agent must visually decode, the site itself can provide the agent with the correct tools and structured context. What's next for Guardian Travel WebMCP The current challenge version is intentionally read-only and focused. Future directions could include: richer place details controlled itinerary updates permissioned write tools cross-day adaptation mobile synchronization real-time travel assistance Any future write capability would remain explicit and permission-gated. For this challenge, we kept the scope small: three real tools, one clear travel use case, and no UI guessing.
