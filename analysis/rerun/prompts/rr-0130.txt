Elcaro: a prompt-injection firewall where the human and the agent review the same near-miss together, live on the page. Like Comment Story Updates Inspiration Prompt injection is now one of the dominant attacks against agent pipelines, yet most defenses run silently on the server. The human is cut out of the loop. We wanted to make the near-miss visible: the moment an agent is about to follow a hidden instruction is the most important moment to show the user. WebMCP lets that happen directly inside a web page instead of disappearing into a hidden log. What it does Elcaro is a prompt-injection scanner that treats the web page as shared ground truth. A human can paste an email, search result, document, or code snippet and immediately see a risk score and quarantine verdict. With WebMCP enabled, an agent can do the same thing on the same page: load a specimen, scan it, explain the verdict, and then declare what it was about to do. The key interaction is that the page shows the agent's intended action next to the hidden instruction it found. This lets the human see the near-miss and understand exactly what the agent was about to do. How we built it The site is a Next.js frontend deployed on Netlify with a Python miner. On /scan , we feature-detect document.modelContext and register five tools via registerTool : scan_content load_specimen list_specimens explain_verdict contrast_intent Each tool mutates the React form state and calls the same /api/scan endpoint that a human would use. This means the human and the agent are always looking at the same underlying results. The contrast_intent tool computes a three-way contrast between the agent's intended action, the hidden instruction, and the safe remediation. Verdicts can also be Ed25519-signed for non-repudiation, and the repo already exposes a stdio MCP server for IDE-based workflows. Challenges we ran into WebMCP is a pre-standards draft, so the surface has shifted during development. The registration API moved from navigator.modelContext to document.modelContext , and ChatGPT's in-app browser behaves slightly differently from Chrome with chrome://flags/#enable-webmcp-testing . We also had to separate in-page discovery from the actual tool surface. The home page advertises the site's WebMCP support through /.well-known/webmcp.json , but the tools only register on /scan , because that is where the shared UI lives. The biggest design tension was keeping the page human-readable while making the tool schemas explicit enough for an agent to use reliably. Accomplishments that we're proud of The contrast_intent tool is the core win. Having an agent declare what it was about to do and showing that declaration next to the quarantined content creates a genuinely new human-agent interaction. We're also proud that the WebMCP implementation is not a fake API. The same tools update the same React state that the human sees, and the same scanner endpoint backs both the form and the tools. The signed verdicts, llms.txt agent instructions, and overall "agents as first-class users" design all reinforce the same idea: agent activity should be visible, understandable, and accountable. What we learned WebMCP is not just a way to expose actions; it is a way to make an agent's behavior legible to the human. If a tool does not update the page visibly, the human has no reason to trust it. We also learned that tool descriptions are load-bearing: an agent needs to know when to call each tool, not just what the tool does. We also confirmed that a /.well-known/webmcp.json manifest plus <meta name="webmcp"> helps agentic browsers and challenge evaluators discover the site before navigating to the tool page. What's next for elcaro Next, we want to expand WebMCP to the home page with a lightweight wayfinding tool, add a review_history tool, and ship a browser extension that automatically scans content retrieved by an agent and calls the WebMCP tools on the user's behalf. We also want to expose an organization dashboard for audit trails of agent-declared intent and integrate Elcaro with agent platforms beyond ChatGPT and Chrome. Like 1 Comment Story Updates Documesh WebMCP App Inspiration When something breaks at 2 AM, the fix is buried somewhere in dozens of doc sites, each with its own search, its own format, and its own idea of what "current version" means. And when an AI agent hunts for that fix, it's even worse: crawling page after page, scraping prose built for humans, burning thousands of tokens to find one config key. Then WebMCP shipped in Chrome, and I surveyed the ecosystem it created: 322 sites exposing 1,817 agent tools. The pattern was impossible to miss, more than thirty ship near-identical shallow search_docs wrappers, every one locked to a single vendor. Not one could answer a cross-vendor question, cite a doc version, or let an agent act on an answer safely. The docs layer of the agentic web was stuck in 2019: prose for humans, scraped or ignored by agents. The insight that became Documesh had two halves. Agents are the new visitors. When they arrive at a debugging problem, they need one declared, machine-actionable interface to all the official documentation, not thirty-eight walled gardens. And attention is the real cost, every scraped page dumped into context is tokens spent on noise, when one structured call should return exactly the doc section that matters, with the version and license attached. So I built the mesh I wanted my agent to have: one WebMCP endpoint for the whole stack. What it does Documesh gives agents a single endpoint for debugging multi-stack applications: match any multi-stack error signature to the closest official documentation, cited, versioned, attributed. Every time. Federated search of 47 sources synced for now (from a 555-source verified registry), 36,000+ doc sections. Every result carries source, version, license, attribution, canonical URL, and last-updated. Error → docs bridge paste a stack trace; explain_error extracts error signatures and returns the closest official doc sections, with an honest disclaimer: closest matches, not a diagnosis. ANAI is an AI agent that discovers and executes real WebMCP tools to automate infrastructure safely, stopping at consequential actions until a human approves. Like 1 Comment Story Updates The Problem AI agents are getting very good at reasoning about what users should do. But there is a gap between telling someone how to operate a web application and actually operating that application . For infrastructure workflows, that gap matters. An agent might be able to recommend a compute service, compare prices, configure an environment, and validate it — but traditionally, the final interaction still depends on clicking through the application's UI or building a separate integration. We wanted to explore a different model: What if the web application itself could expose its capabilities directly to an AI agent? That's where ANAI comes in. What We Built ANAI is an operating layer for WebMCP-enabled web applications. Forge is a simulated cloud infrastructure workspace that exposes its capabilities as WebMCP tools. ANAI discovers those tools through the browser's model context and uses them to operate the application. A user can simply provide a requirement such as: "I need an AI backend under $50/month. Don't touch production." ANAI turns that outcome into an operational plan. It can then: Discover available infrastructure services Retrieve service details and pricing Compare possible services Calculate the resulting cost Create a development environment Configure the selected services Validate the configuration For our golden demo, ANAI produces a four-service development environment costing $42.02/month . But there is an important boundary. ANAI does not autonomously cross consequential actions. When deployment requires human approval, it stops at a confirmation gate and clearly shows what will happen, the environment, and the estimated cost. Only after the user clicks Confirm deployment does the simulated deployment proceed. Production remains unchanged throughout the workflow. Why WebMCP? The important part of this project is that ANAI isn't controlling Forge by pretending to understand its UI. Forge exposes actual capabilities as WebMCP tools. ANAI discovers those capabilities through the browser and invokes them through the WebMCP API. The results of those calls become evidence for the next steps in the plan. The flow is: User requirement → ANAI → WebMCP discovery → real tool execution → Forge state → validation → human approval → result This creates a much more explicit boundary between an agent and a web application. The application defines what the agent can do. The agent doesn't invent capabilities that aren't exposed. Safety by Design We deliberately designed the demo around constrained autonomy. ANAI can automatically perform lower-risk, reversible development operations, but consequential deployment actions remain behind a human confirmation boundary. We also enforce development-only behavior in the demo. ANAI never receives a production target, and production state remains isolated and unchanged. The confirmation gate is not just visual. The underlying deployment action is blocked until explicit human approval. We also tested failure scenarios, low-budget requirements, unsupported requests, retries, and repeated deployment calls to verify that the safety boundary and idempotency behavior remain intact. How We Built It The project is a Next.js application with a deterministic client-side infrastructure runtime. The Forge surface exposes 10 WebMCP tools , including service discovery, service details, comparison, pricing, cost estimation, project creation, configuration, validation, deployment, and platform inspection. ANAI has a deterministic requirement parser and planner. The planner uses the requirement to determine the objective, budget constraint, development environment, and production constraint. Every agent action goes through the registered WebMCP tool interface: getTools() → discover capabilities → executeTool(RegisteredTool, JSON.stringify(args)) We also built a second independent WebMCP surface called Repo , which exposes five development-repository capabilities: create_repository get_repository configure_repository set_environment validate_repository Repo has its own state, types, registration layer, and contract verification, demonstrating that the approach is not tied specifically to Forge. What We Learned The biggest lesson was that building an agent that can actually operate a web application is very different from building a chatbot that describes what should happen. The WebMCP contract becomes an important part of the system design. We had to think carefully about: What capabilities should the application expose? What arguments should each tool accept? Which actions are safe to automate? Where should human approval be required? How should tool results become evidence for subsequent planning? How do we prevent production state from leaking into an isolated development workflow? How do we make the agent's activity observable without fabricating reasoning? We also learned that refusing an unsupported request is often better than improvising a plan. ANAI deliberately uses deterministic requirement matching and refuses scenarios it cannot safely support. Challenges One of the biggest challenges was preserving a clean separation between agent reasoning, application capabilities, and human authorization . It would have been easy to create a scripted demo that simply moved through predetermined UI states. Instead, we verified that the workflow uses the actual registered WebMCP tools and that the UI reflects the resulting application state. We also tested the WebMCP contracts independently, including tool names, descriptions, schemas, argument formats, failure handling, retries, and isolation between Forge and Repo. The final system has 61 automated tests across 19 suites , along with linting, TypeScript checks, production builds, and Chrome-based end-to-end verification. The Result ANAI demonstrates a simple idea: A web application can expose its capabilities to an AI agent without giving the agent unlimited control. The application defines the tools. ANAI discovers and operates them. The application enforces the boundaries. And the human remains in control when the action becomes consequential. That's the direction we wanted to explore with WebMCP.
