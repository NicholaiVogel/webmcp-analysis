# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Through WebMCP, an AI agent can discover structured tools exposed by Counterfactual, read the user's financial assumptions, create alternative scenarios, simulate their outcomes, and compare them. Counterfactual turns those scenarios into explorable futures with dynamic visualizations that show how each decision affects the user's finances and protected goals. Users can change an assumption at any time and immediately see every future recalculate. A built-in WebMCP Flight Recorder makes the agent's behavior visible by recording each tool it discovers and invokes, along with its arguments, risk level, origin, status, and results. Rather than receiving only the agent's final recommendation, users can inspect the actual sequence of actions that produced it. Most importantly, Counterfactual distinguishes between exploring a future and making it real . Read-only and simulation tools can run freely, but when an agent attempts a consequential action, Counterfactual pauses execution and requires explicit human approval. The result is a simple principle: agents can explore autonomously, but humans retain control over commitment. How I built it I built Counterfactual with Next.js, TypeScript, Tailwind CSS, and client-side state . Its scenario engine uses deterministic calculations so the agent's conclusions and the visual interface always operate from the same source of truth. Counterfactual exposes structured WebMCP tools through document.modelContext.registerTool() . These include tools for reading financial state, defining a decision, protecting goals, creating scenarios, comparing outcomes, simulating purchases, and committing to a selected scenario. Every invocation, whether initiated manually or by an external agent, passes through the same execution and logging pipeline. That testing uncovered an issue that was invisible through Counterfactual's own UI but appeared when a tool was invoked through the actual WebMCP path. Fixing it helped ensure the project works through the protocol itself rather than only through a scripted demo. Challenges I ran into The biggest challenge was building against an experimental standard whose API and browser support are still evolving. Counterfactual needed to target the current document.modelContext API while remaining usable in browsers and agents relying on earlier or unsupported implementations. Another challenge was maintaining a single source of truth across the agent, editable controls, scenario calculations, visual branches, and Flight Recorder. A tool call could not simply generate an answer—it had to operate on the same live state the user was seeing and immediately update the rest of the experience. The final challenge was designing meaningful human oversight without making the agent feel unnecessarily constrained. Requiring approval for every tool call would defeat much of the value of an agent, while allowing every action to execute automatically would remove meaningful user control. Users can see what the agent is doing, inspect how it reached its recommendation, modify the assumptions themselves, explore alternative futures, and ultimately reject or approve the proposed action. Structured tools allow an agent and an interface to share the same capabilities and application state without relying on fragile DOM interpretation or browser automation. Tandem is a spaced-repetition study board where students and AI agents share live context, improve weak topics, and build lasting study plans through WebMCP. Like 1 Comment Story Updates Inspiration Study apps remember what a student has practiced, while AI assistants are good at explaining difficult ideas. The problem is that these two sides usually do not share context. A chat assistant cannot reliably see the card on screen, understand which topics the student repeatedly misses, or make its explanation available during the next study session. I built Tandem to explore what happens when a study app and an agent work on the same persistent state instead of communicating through copied text or brittle interface automation. What it does Tandem is a working spaced-repetition study board for students and their AI agents. The student can create decks, study flashcards, reveal answers, grade recall, inspect weak topics, and follow a revision plan. Through WebMCP, an agent can directly access the structured learning state and help with the same workflow. For example, the agent can: Rank topics using real lapse counts and difficulty data Start a study session focused on the weakest material See the exact card currently on screen Check whether an earlier explanation actually improved the student’s results Replace an ineffective explanation and save the new one directly on the card Build a revision plan from the exam date and weak-topic history Request permission to remove a card without being able to approve the deletion itself Agent actions and human actions appear together in a visible activity feed, so the collaboration remains understandable rather than happening invisibly. Why WebMCP This use case needs more than an agent clicking through a website. A student should not have to repeatedly explain which deck, topic, or card they are viewing. Tandem exposes that information as typed WebMCP tools. When the student says “the card currently on screen,” the agent can call get_study_state and receive the exact card, session position, reveal state, and study progress. WebMCP also lets the agent work with durable application state. An explanation written with annotate_card becomes part of the card and remains available in future sessions instead of disappearing in a chat transcript. The tool surface changes with the application state. Tandem exposes 16 live tools on the dashboard. When a study session begins, session-specific tools such as reveal_answer , grade_current_card , queue_cards , and end_session become available, bringing the live surface to 19 tools. They are withdrawn again when the session ends. Human and agent collaboration Tandem deliberately keeps important decisions with the student. For destructive actions, delete_card does not delete anything. It creates a permission request in the interface and returns a pending result. The student sees exactly which card would be removed and how many recorded reviews would be lost. Only the student can press the confirmation button. The agent can later read the decision through get_approval , but it cannot approve its own request. This creates a clear division of responsibility: the agent can inspect, explain, organize, and propose, while the student remains responsible for studying, grading, and irreversible decisions. How I built it Tandem is built with React 19, TypeScript, and Vite and deployed on Vercel. Study data is stored locally in the browser, so the project requires no account or backend. The WebMCP adapter registers tools through document.modelContext , supports contextual registration and withdrawal, and reads current application state when each tool executes. Every tool has a typed input schema, a detailed agent-facing description, structured output, and safety annotations. The app includes 20 tools covering deck inspection, card search and editing, study sessions, note-impact analysis, revision planning, interface highlighting, and human approval. Challenges One challenge was ensuring that tools never operated on stale React state. The executors therefore read the current store at call time instead of capturing an old snapshot when they are registered. Another challenge was designing a dynamic tool surface without duplicate registrations. The registry compares the tools that should currently exist with the tools already registered and changes only the difference. The most important design challenge was human approval. A simple confirm: true argument would only be the agent claiming that permission had been given. Tandem instead separates requesting, deciding, and reading the result into different actions, with the actual decision taking place in the user interface. Accomplishments I am especially proud that Tandem is a complete study product rather than a static WebMCP demonstration. The same structured tools used by the agent affect the real interface and persistent study data. The project includes automated coverage for the spaced-repetition scheduler, tool schemas, contextual tool registration, note-impact calculation, revision planning, approval boundaries, accessibility states, and an end-to-end agent simulation. What I learned Building Tandem changed how I think about agent-enabled websites. A useful tool description is not just API documentation; it explains when an agent should use the tool and where the human boundary begins. I also learned that WebMCP is most valuable when it exposes domain logic and live context that would be difficult to reconstruct from screenshots or interface automation. What’s next Next, I would add optional cross-device synchronization, richer study analytics, document-to-deck importing, and longer-term measurements of whether agent-written explanations improve retention across multiple review cycles.
