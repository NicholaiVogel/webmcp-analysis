CacheLens uses WebMCP to let ChatGPT inspect LLM traces, find prompt-cache waste, explain why it happens, and simulate fixes that cut API cost. Like Comment Story Updates CacheLense WebMCP Inspiration LLM applications repeatedly send large amounts of identical context: system prompts, tool definitions, policies, and conversation history. Prompt caching can make that repeated input dramatically cheaper—but only while the cacheable prefix remains stable. A seemingly harmless change near the beginning of a prompt can invalidate cache reuse for everything that follows. Dynamic metadata, changing instructions, timestamps, or volatile content placed at the wrong cache boundary can quietly cause an application to pay to process thousands of largely unchanged tokens again. The difficult part is that developers usually cannot see why this is happening. That led to CacheLens: a developer tool for making prompt-cache behavior observable, identifying where prefix reuse breaks, explaining likely causes, estimating the financial impact, and recommending concrete fixes. The WebMCP Challenge suggested a natural next step: instead of requiring developers to manually interpret every trace and diagnostic, let ChatGPT inspect CacheLens directly through structured capabilities exposed by the live application. What it does CacheLens WebMCP turns prompt-cache diagnostics into a collaborative workflow between the developer, the web application, and ChatGPT. A developer can open a CacheLens trace and ask questions such as: Why is my cache hit rate low? Where is the cacheable prefix breaking? Which content is changing? How many stale tokens are being unnecessarily rewritten? What is that costing me? For an identified break, how much could be saved if the stable and volatile content were split correctly? Through WebMCP, ChatGPT discovers three domain-specific tools directly from the page: list_traces explain_cache_behavior estimate_split_savings Rather than scraping the DOM or requiring the user to copy diagnostic data into chat, the agent asks CacheLens directly for the underlying analysis. For example, one real captured trace reports a 44.3% provider-measured cache hit rate , 3 of 3 avoidable prefix breaks , and 28,175 stale tokens rewritten . CacheLens identifies the volatile cache boundary and can estimate the savings for a specific affected turn while clearly stating the assumptions and limitations of that estimate. The human remains in the loop through the CacheLens interface while ChatGPT reasons over the same application state through WebMCP. The workflow becomes: observe → diagnose → explain → estimate → improve How we built it CacheLens captures and analyzes LLM request traces while preserving the structure needed to understand prompt-prefix reuse. Its existing analysis engine compares successive requests, determines where stable prefixes diverge, separates stale tokens from genuinely new tokens, attributes likely causes, and estimates cache-related waste. For WebMCP, we deliberately reused that analysis rather than creating a second implementation. A thin serialization layer projects CacheLens analysis objects into safe application data. A small read-only HTTP server exposes the trace catalog and analysis endpoints, and a lightweight browser interface registers the three WebMCP tools through document.modelContext . The WebMCP tools use constrained inputs: trace identifiers are resolved through an explicit server-side catalog rather than arbitrary filesystem paths, and the tools expose no shell commands, writes, credentials, or mutation operations. The tools are intentionally higher-level than UI automation. CacheLens does not expose actions such as "click this button." It exposes meaningful developer operations: list available traces, explain cache behavior, and estimate the savings associated with splitting a specific identified cache break. That became one of the most important design principles of the project: WebMCP is most useful when a website exposes meaningful application capabilities, not simply another way to operate its interface. Challenges The first challenge was identifying cache waste accurately. Prompt caching is prefix-sensitive, so a small mutation can force a much larger region of otherwise unchanged input to be rewritten. Detecting that two strings differ is easy. Determining which divergence caused expensive cache invalidation—and separating stale tokens from genuinely new ones—is considerably more useful. The second challenge was presenting the result in terms developers care about. Token counts alone are abstract, so CacheLens connects structural changes to cache behavior and estimated cost while distinguishing measured provider usage from heuristic token estimates. The WebMCP integration introduced another challenge: deciding what an AI agent should actually be allowed to do. Exposing every internal operation would create a large and confusing tool surface. Exposing only low-level UI controls would miss the purpose of WebMCP. We settled on three small, read-only, domain-specific tools corresponding to real developer questions. We also deliberately avoided a tempting feature: a general-purpose "simulate fix" tool. CacheLens does not currently model arbitrary prompt reorganizations or predict a new cache-hit rate. Instead, estimate_split_savings performs one narrow counterfactual supported by measured analysis: for an identified cache break, estimate the cost difference if the unchanged portion could have been read from cache rather than rewritten. Keeping that boundary explicit made the result more defensible. What we learned The project reinforced an important lesson about AI infrastructure: optimization problems are often observability problems first. Like Comment Story Updates Problem Data-rich websites make people do the mechanical work of understanding them: find the right chart, decode its visual grammar, hunt through tooltips, compare distant points, and repeat the process whenever the question changes. General-purpose agents can try to interpret screenshots, but pixels are an unreliable source for exact figures, units, and provenance. Exporting the data into another tool removes it from the page where its context and visual evidence live. This is especially costly for people who cannot rely on charts visually. A screen reader can traverse a table row by row, but a chart often collapses to “image.” The underlying problem is broader, though: conventional dashboards present answers chosen by their designers instead of letting each person interrogate the underlying evidence directly. Auricle opens with this gap in plain sight: 2,026 rows. Zero answers. Four real climate datasets are available as semantic tables, but no dashboard or on-page chatbot is present. Solution Auricle turns the webpage itself into an interviewable climate instrument. The page exposes WebMCP tools backed by its own data. A user asks through their browser agent; the agent calls the page's tools; Auricle computes an exact, source-attributed answer and mirrors the result into the shared page. Ask “Show me warming over time” and the page creates a NASA temperature chart. That action also registers the chart's five-tool family at runtime. Ask “When was the hottest year?” and Auricle answers +1.28 °C in 2024 while highlighting the point in gold. Ask “Play the century as sound” and it sonifies 146 years as a rising tone with a peak cue. Ask for warming stripes and the same data appears in a second, queryable form. The result is not a chatbot bolted onto a dashboard. The browser agent supplies the conversation; the site supplies authoritative tools, data, visual state, speech-ready answers, and sonification. Every chart on the screen exists because somebody asked for it. Why This Matters Auricle demonstrates a new interaction model for the agentic web: people and agents compose and interrogate a live dashboard together without exporting data or guessing at pixels. The page remains the source of truth, the human directs the inquiry, and everyone in the session shares one evolving surface. For blind and low-vision users, page-owned tools can replace pixel interpretation with exact, source-backed spoken answers and sonification. For everyone else, the same system makes complex evidence faster to explore and easier to verify. Accessibility is therefore a demanding proof case for a broadly useful product—not the boundary of Auricle's audience. The reusable contribution is an agent-accessibility grammar: Orient the agent before asking it to act. Make the tool surface follow the user's focus. Return narratable answers with figures, units, and provenance. Mirror every agent action into the visible and accessible page state. Treat non-visual encodings such as sound as first-class capabilities. This pattern can extend beyond climate data to finance, health, public policy, and any data-rich site where fixed dashboards or visual-only answers limit exploration. Key Features Dashboard by conversation: the initial publication has no charts; create_view commissions each requested view. Dynamic WebMCP surface: five global tools exist at boot, while dataset-specific families register, change with focus, and unregister when their final view is removed—21 tools across the complete experience. Exact page-owned answers: queries run against baked NASA, Our World in Data, and NOAA data, with figure, unit, and source in every narrated return. Shared visual evidence: tool calls create views, highlight points and ranges, and leave a provenance footnote on the page. Accessible HTML foundation: semantic landmarks, real data tables, chart labels, keyboard-operable controls, reduced-motion support, and a visually hidden aria-live answer log. Sonification: time series become a roughly three-second pitch sweep with a distinct peak cue. Nine visualization forms: line, area, warming stripes, vertical and horizontal bars, share bars, scatter, live, and stat views. Self-describing experience: describe_screen tells a newly arrived agent what is present, focused, available, and possible next. Architecture Auricle is a static Vite + React + TypeScript application deployed on Vercel with no backend. Source datasets are fetched by a keyless script and baked into JSON, so the production experience does not depend on runtime data APIs. A framework-agnostic registry wraps each internal tool definition into the WebMCP document.modelContext.registerTool shape. Five orientation and workspace tools register at page load. When create_view commissions a dataset, an AbortController-scoped family registers for that dataset; focus changes replace the active family, and removing the last view aborts it. The simulated live CO₂ view re-registers its family on each bounded tick so its tool description reflects current session state. The Mauna Loa “live” movement is a clearly labeled bounded simulation seeded from the latest baked NOAA weekly mean; it is not presented as a real-time NOAA stream. Sonification and warming stripes have established prior art. Like Comment Story Updates 3D view Plan view SVG isometric view ShuiSpace Inspiration Imagine you're trying to change the layout of your room. The choices you have are to either use a design tool with a steep learning curve, do the change in reality or click photos and send them to an LLM. The LLM might return back a new arrangement, but it has never entered your room. It doesn't know the dimensions and actual space available. I wanted to see what it looks like when the tool and the agent are the same thing, when the agent isn't describing my room from the outside, but working on it with me, using the geometry the app already has. What it does ShuiSpace is a room designer with nineteen actions: place something, move it, swap it, pin it, measure a walkway, check the budget, check whether a piece gets through the door, ask where something should go. I can use all nineteen by clicking and dragging. My agent can call the same nineteen directly, because the page publishes them as WebMCP tools. They reach the same functions, hit the same collision checks, and produce the same undo entries. Things follow from that: The proposal waits for me. propose_layout stages its placements as translucent ghosts on the plan, shows what the change would do — "3 items · clears 1 issue · $312.00 left of the budget" — and the tool call does not return until I click Accept or Reject. If I reject it, my agent receives that as a decision it can act on, not as a timeout. This is the whole reason the project is a WebMCP project: a server-side MCP can compute a layout, but it cannot wait for me to look at it. Refusals carry a way out. An agent told "no" gives up. An agent told which item is in the way moves that item. Every failure returns a machine-readable reason , a human-readable message , and where relevant the id of the thing that blocked it. There's also an activity feed showing both hands in one list, in the order things happened, so you can see the collaboration rather than take my word for it. How I built it React 19, TypeScript, Zustand and Vite, deployed as static assets on Cloudflare Workers. Three views of the same plan — an SVG floor plan, an SVG isometric, and a three.js 3D view that's lazy-loaded — all behind one small adapter interface so the tools don't know or care which one you're looking at. Two rules did most of the architectural work: Tools and UI call the same store actions. This is the one principle the whole thing rests on, and it's what makes the WebMCP surface trustworthy rather than a parallel API that drifts. Derived data is recomputed, never stored. Violations, budget, free space and stacking heights are all selectors. That's what lets the app answer a hypothetical — "what would this proposal do?" — using exactly the machinery it uses to draw the real thing. Tools register through document.modelContext , and the hook feature-detects so the app degrades to an ordinary room designer in browsers without WebMCP. There's also a built-in tool console that drives the identical registry by hand, which meant I could develop the tool surface before I had any agent that could see it. What I learned That the interesting part of an agent-facing API isn't the happy path; it's what a refusal contains, and whether a human can stay in the loop without the loop breaking. .
