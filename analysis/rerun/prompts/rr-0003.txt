ChatGPT: sources/multi-provider Exact term authorization Exact term revalidation test: authorized 10:00, proposed 10:30 - BLOCK, with 0 provider calls Signpost explores what happens when a user's compound request becomes a journey across independently operated WebMCP sites. Inspiration WebMCP gives individual websites a way to expose structured capabilities to browser agents. Those capabilities are exposed locally, while a user's compound objective can span several independently owned providers. I wanted to see whether a generic agent could compose that kind of journey without requiring any one provider, resolver, or platform to own it. For the challenge, that meant separating the problem: providers declare what they can do, Signpost resolves where those capabilities are available, and the agent decides which capabilities it needs and in what sequence. Consequential providers retain control over whether their own mutations may execute. The user can therefore begin with the outcome they want rather than a prearranged itinerary across specific sites: "order a coffee, book a basic haircut, and check this palette." What it does Signpost is a stateless capability resolver. An agent asks where a capability can be performed, and Signpost returns matching provider surfaces from declarations published by those providers. Signpost never receives the user's full objective. It doesn't decompose the request, maintain a session, choose the next step, or own an itinerary. The agent remains responsible for deciding what capabilities it needs and what to do next. For providers, this preserves a different boundary: they declare their own capabilities at their own origins rather than surrendering ownership of those capabilities to the system composing the journey. For the challenge, I built three independently deployed WebMCP reference providers: Deckhouse Coffee: order coffee Chair & Comb: find and book an appointment Hex Registry: check a hex value against a palette In the live demo, ChatGPT receives one request spanning all three. It determines the capabilities it needs, resolves them through Signpost, navigates to each provider, discovers its WebMCP tools, and completes the journey. For consequential actions, the agent can propose an action but cannot grant itself authority to execute it. Deckhouse Coffee and Chair & Comb display the exact material terms for user authorization at the provider. The pending invocation waits, then resumes and revalidates those terms immediately before execution. Only a valid, matching, single-use authorization permits the provider mutation. Signpost also keeps evidence separate from agent narration. Participating surfaces record authorization decisions, provider calls, and provider results so the evidence view can show what actually happened without becoming part of the agent's planning state. How I built it Participating providers publish small capability declarations describing what can be done at their origin. Signpost fetches those declarations and exposes one WebMCP tool: resolve_surface({ capability }) Matching is deliberately transparent: lexical retrieval with limited fuzzy matching, rather than another model in the loop. The result tells the agent where a capability is available, but never what it should do next. Each reference provider is an independent WebMCP surface and knows nothing about the others. Consequential providers place authorization and execution control at their own mutation boundary. The execution seam reuses @zioladev/execution-control@0.1.0 , a small package I published before the challenge. Its rule is intentionally narrow: only allow permits execution; block and indeterminate do not. The exact-term authorization flow, await/resume integration, reference providers, trusted-activation guard, evidence capture, and multi-provider Signpost flow were built during the challenge. I also included a deterministic drift test. It authorizes one set of material terms, presents different terms at execution, and verifies that the execution boundary returns BLOCK with zero provider calls. Challenges and what I learned The hardest challenge was not building too much into Signpost . Once an agent begins moving across several sites, it is tempting to give the resolver a session, itinerary, cursor, or concept of "next." Those features make orchestration easier, but they also change what Signpost is. I moved those responsibilities back to the generic agent, so the resolver remained stateless and journey blind. Cross-origin execution made that boundary practical rather than theoretical. Each provider had to stand independently on its own origin, while the agent could return to Signpost whenever it needed to locate another capability. The consequential flows evolved during the challenge as well. My first authorization design returned a "needs authorization" result and required the agent to retry after approval. I replaced it with await/resume: the original invocation now waits for authorization and then revalidates immediately before execution. That removed an unnecessary human-to-agent signaling round trip and narrowed the interval between authorization and use. That improvement made deliberate term drift difficult to demonstrate naturally in the live flow. Rather than weaken the runtime to manufacture a better demo, I moved that failure case into a deterministic test against the same execution boundary. A much smaller bug reinforced why I wanted the resolver to stay inspectable. An early provider description used words such as "ordered" while explaining what the provider didn't do. The lexical resolver matched it to an order query anyway. It was doing exactly what its transparent scoring rules said it should do. The failure was easy to understand and correct without introducing an opaque ranking layer. The larger lesson was that these responsibilities do not have to collapse into one agent system. A generic agent can choose the journey without becoming the capability registry, the source of execution authority, or the sole narrator of what happened. What's next Signpost is a reference implementation, not an attempt to prescribe how web-scale capability discovery must work. The broader question is what infrastructure an agent-operable web needs when agents begin moving across independently owned sites to complete a compound objective. Signpost explores one possible separation: The agent owns why and sequence. Signpost answers where. Providers own what. Consequential providers control whether a mutation may execute. Evidence records what happened. An agent-native ticketing experience where people and AI agents discover, compare, reserve, and prepare tickets for Bolivian cultural events together using WebMCP. Like Comment Story Updates Initial WebMCP state — the demo event is loaded and the shared cart starts empty. WebMCP reserves tickets and the human-visible Shared Cart updates with the temporary hold. Checkout prepared — the agent stops before payment and explicit human confirmation is required. Human experience — users can open the full seating map and select seats manually without WebMCP. 1. Three seats selected and reserved in the standard human checkout flow before payment. Inspiration Ticket buying is usually designed for only one kind of user: a human clicking through a website. But AI agents are increasingly helping people search, compare options, and complete multi-step tasks. We wanted to explore what ticketing could look like if a website were designed for both humans and agents from the beginning. AyMateo already had a pre-existing ticketing platform with event pages, seat inventory, temporary holds, carts, and checkout infrastructure. For the WebMCP Challenge, we extended that platform with a structured agent-native interaction layer instead of building a disconnected chatbot or a demo that only returns static data. Our goal was simple: let an AI agent help a person discover a Bolivian cultural event, compare tickets, reserve real inventory, and prepare checkout while the human can see and understand every action happening on the same page. What it does AyMateo Tickets exposes seven WebMCP tools directly from the website: search_events get_event_details get_ticket_options add_tickets_to_cart remove_tickets_from_cart get_cart_summary prepare_checkout An agent can search for cultural events using natural language, retrieve structured ticket information, reserve tickets, inspect the cart, and prepare an order. The important part is that these actions are not isolated from the normal website. When the agent adds tickets, the human-visible Shared Cart updates too. The same browser session contains the ticket hold, prices, expiration state, and prepared checkout. The Agent Activity panel also makes the agent's actions visible instead of hiding them behind an invisible automation. Humans can still use the normal ticketing experience, including the full seating map. Payment is intentionally excluded from the WebMCP action surface. prepare_checkout only creates a pending order, and final payment still requires explicit human confirmation. How we built it The project uses Next.js, React, TypeScript, PostgreSQL, Prisma, Docker, and WebMCP's imperative API. On the /webmcp page, the application registers tools through: document.modelContext.registerTool(...) Each tool connects to real server-side ticketing logic rather than mocked frontend state. Event discovery reads published events and current ticket availability from PostgreSQL. Ticket mutations create real temporary seat holds using the same transactional inventory system used by the human ticketing experience. The WebMCP page and the normal website share the same browser checkout session, which allows human and agent actions to stay synchronized. For the challenge deployment, we created an isolated WebMCP environment with its own PostgreSQL database and fictitious Bolivian cultural-event data. The demo is publicly available over HTTPS at: https://webmcp.aymateo.com/webmcp The public submission repository is also separated from the private development history and was scanned for secrets before publication. Challenges we ran into One of the biggest challenges was making WebMCP interaction truly stateful. Searching for an event is easy, but reserving tickets means the agent must interact with temporary inventory holds, browser-session state, expiration rules, backend validation, and the same cart the human sees. We also encountered browser lifecycle issues while registering imperative WebMCP tools. Tool execution needed to remain stable even when React state changed, so registration and handler lifecycles had to be carefully separated. Another challenge was natural-language discovery. A strict substring search worked for controlled test inputs but could fail when an agent sent a phrase such as "Find me a Bolivian cultural or folklore event under Bs 100." We improved the search logic so it remains deterministic while handling meaningful words from natural agent requests. Finally, we wanted the agent to be useful without giving it unsafe authority. That led us to draw a clear boundary: agents may search, compare, reserve, and prepare checkout, but they cannot complete payment. Accomplishments that we're proud of We are especially proud that WebMCP is not just decorative in this project. The agent can perform a complete, visible journey: event discovery → ticket comparison → real temporary reservation → shared cart → prepared checkout. The ticket reservation is backed by actual PostgreSQL inventory and transactional seat-hold logic rather than a fake demo cart. We also built the experience so that human and agent interactions remain inspectable. The Shared Cart and Agent Activity panels show what the agent changed, while the normal seating-map experience remains available for people who prefer to interact manually. The complete WebMCP flow is deployed publicly and has been tested end-to-end using the Model Context Tool Inspector. What we learned The biggest lesson was that agent-native websites should not necessarily replace human interfaces. WebMCP is most interesting when the agent and human can collaborate with the same application state. Structured tools give an agent a safer and more reliable way to interact with a website than interpreting buttons and rendered text, while the visual interface still gives the human context, control, and confidence. We also learned that tool design matters as much as implementation. Clear schemas, read-only annotations, untrusted-content boundaries, backend validation, and explicit limits on high-impact actions are essential when an agent can mutate real application state. What's next for AyMateo Tickets The next step would be expanding the agent-native experience beyond a single-event demo. Future work could include richer event discovery, multiple performances, accessibility preferences, price and seating recommendations, and agent-assisted seat selection on the visual seating map. We would also like to explore standardized confirmation flows for actions with higher impact while preserving the principle demonstrated here: AI agents can do the repetitive searching, comparing, and preparation, while humans remain in control of the final decision. A cooperative escape-room game where a human and an AI agent use WebMCP tools to investigate a mysterious facility, solve its puzzles, and unlock the exit. Like Comment Story Updates Inspiration Most WebMCP demos focus on task automation. I wanted to test a different use: making the tool interface part of a game. Relay Room is an asymmetric escape room. The player can see the room and use its controls, but cannot access the remote systems. Relay can operate those systems through WebMCP, but cannot see the room. Progress depends on the information they exchange through an AI agent connected in the browser. What it does Relay Room is played by one person and Relay (the AI agent, as in ChatGPT or Gemini in WebMCP in Chrome). The player reads visual clues, connects cables and activates controls. Relay receives a private manual and eight WebMCP tools to inspect the facility, decode signals, operate remote systems and release the exit door. This version has only one simple level to understand the game mechanics. The game has three stages, randomized puzzles, scoring, saved progress, voice lines, a solo test mode and offline support as an installable PWA. How I built it I used Next.js, React and TypeScript. The WebMCP integration uses the imperative API, with eight tools registered through document.modelContext.registerTool() . The interface and the WebMCP handlers share the same game state. Visual clues stay in the interface. WebMCP only exposes the manual, system state and remote actions that Relay is allowed to use. Local storage keeps the current mission and best score. Challenges The first problem was deciding what each participant was allowed to know and do. If a tool reveals the visual clues, the player is no longer necessary. If the tools expose too little information, Relay cannot reason about the puzzle. I also had to account for two connection paths: Chrome with a compatible WebMCP extension and the built-in browser in ChatGPT Desktop. They have different setup and permission flows, so the onboarding explains both options and verifies that the eight tools are available before starting. I think we are still in early stages of user experience for doing these kinds of interaction. What I learned WebMCP tool descriptions are part of the interface. Relay needs to know when to call each tool, what it changes and what to do with the result. Capability detection is not enough. The page also needs to explain which browser or client to use, where it must remain open and which permissions the player needs to approve. There is a need for a future version of WebMCP to register listeners, so the page can also send messages to connected agent.
