# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Why WebMCP The key idea is not simply giving an agent functions to call. It is letting the human UI and the browser agent collaborate over the same application state . Without WebMCP, an agent would need to scrape rendered UI text or depend on a separate API that could drift from what the human actually sees and edits. ShowBranch exposes exactly five WebMCP tools: list_products get_activity create_preview_branch apply_branch_updates get_branch_diff These tools let the agent work directly with products, human activity, preview branches, and diffs. How we built it ShowBranch is built with Next.js, React, TypeScript, and WebMCP , and is deployed on Vercel . Human edits store complete before-and-after snapshots. Agent batches are applied atomically, and the application tracks branch lifecycle and main revisions so stale merges can be detected rather than silently applied. Challenges we ran into The biggest challenge was making the agent useful without giving it unnecessary authority. We wanted the agent to generalize confidently across related products, while ensuring those proposals stayed isolated from the canonical state until a human review. A second challenge was making human correction part of the collaboration loop rather than treating it as a one-off UI edit. A correction inside the branch needed to become structured evidence that the agent could reliably discover and use in its next revision. Activity ordering introduced another subtle problem. An agent reading only an older branch should not mistake that branch's latest event for the globally latest human activity. ShowBranch therefore tracks scoped and global activity information so newer demonstrations are not silently overlooked. We also had to handle atomic preview updates, stale-branch detection, registration cleanup, and exact reset behavior. Finally, the security boundary needed to be described precisely. ShowBranch removes merge from the WebMCP capability surface and exposes merge through the human UI, while broader browser-automation permissions remain the responsibility of the browser or host. We also learned that human corrections become much more powerful when they are stored as structured activity rather than treated as ephemeral UI interactions. One correction can teach the agent a catalog-specific rule without requiring the human to rewrite the entire instruction. WebMCP makes this interaction natural because the agent works with the application's semantic state instead of reconstructing intent from rendered text. What's next for ShowBranch ShowBranch is intentionally a focused demonstration of this interaction pattern. Future directions include: persistent branches and activity history; state-aware WebMCP tool registration; richer approval and permission policies; multi-user review workflows; larger catalogs and persistent backends; and applying the same ShowOnce + BranchMode pattern beyond product classification. Deployed on GitHub Pages. • The playtest engine — world-book scanning, regex rendering, JSON-Patch variable state — is ported from an existing Python tool (playtest_engine.py) to JavaScript, and checked against it with a golden-parity test suite that replays fixed multi-round conversations through both engines and asserts byte-identical output. 81 tests total (unit + golden + Playwright e2e). • Each of the ten tools is a plain, DOM-free function unit-tested on its own; only one module (registerTools.js) ever touches document.modelContext, and registration is fault-tolerant (per-tool try/catch, a timeout cap) because the API is still experimental. • Tool descriptions and the whole UI are bilingual (Traditional Chinese / English) and follow a page toggle, so the agent reads whichever language the creator is working in. Challenges I ran into • WebMCP is early-preview. The agent side — a browser that actually calls the registered tools, not just accepts them — exists today only in ChatGPT's Codex browser and in Chrome behind a flag. Working out which environment actually calls the tools (a plain ChatGPT account registers them but never calls them) took real testing. • Getting the agent to emit the exact wrapper the engine parses. Solved by having the tool report the precise format error back to the agent — which turned into a good demonstration that the tool's output, not the agent's "verified, no warnings" self-report, is what tells you whether something worked. • Keeping the split honest: everything deterministic and stateful on the page, only the in-character writing on the agent — and resisting the urge to let the agent "help" with the bookkeeping. Accomplishments that I'm proud of • The full write → playtest → cross-scenario QA loop runs through typed, self-describing tools with zero prompt scaffolding. The agent discovers the whole call sequence from the tool metadata alone. • compare_scenarios computes a QA signal (world-book entries that trigger inconsistently across branches) that no existing character-card tooling produces. • Golden-parity tested against the original Python engine, so the ten tools an agent calls are backed by code that doesn't guess. What I learned • WebMCP's real value is the division of labour: the page can hand the agent exact state — which entry is inside a cooldown right now , whether a patch actually applied — that the agent could never reconstruct from the rendered page. • Self-describing tools plus honest error reporting removes almost all of the prompt engineering. The tool descriptions are written for the agent, and the agent just follows them. Like Comment Story Updates Inspiration We started somewhere else. The first idea was a size recommender — obvious fashion-commerce problem. Then we opened DevTools on a live AJIO product page and found something that reframed the whole project. Sitting in window.__PRELOADED_STATE__ , invisible to any agent driving the DOM, was a size chart already converted to centimetres , an explicit measurementType: "Garment Measurement" provenance flag, live per-size stock counts, and — the thing we didn't expect — a crowd fit distribution: Perfect 64% · Tight 15% · Too Tight 5% · Loose 11% · Too Loose 3% over 2,100 raters The page already knew this garment runs small. It had no way to tell an agent. But the moment that actually defined the product came later. Our first working version ranked a ₹320 polo as the top buy for a client dinner. It was cheap, in stock, not a duplicate, and technically satisfied every constraint. It was also completely wrong — a polo does not become client-dinner appropriate because it is cheap. That is the failure mode of every shopping agent we've used. They can only say buy , so they optimise for the one signal they can read: price and availability. We rebuilt the engine around a different question — what if the agent could say no? What it does Mustermind is a wearability decision layer. You give it an occasion, a budget, a PIN code, a deadline, fits you avoid, and a rough list of what you already own. It scores live AJIO products on four axes: product facts, your constraints, purchase risk, and rewear value. Every garment gets one of four verdicts: Verdict Meaning buy Worth buying for this occasion restyle You can already assemble this look from what you own wait Right piece, wrong price or arrives too late skip Violates a stated constraint, duplicates something owned, or can't be delivered Every verdict carries the factors behind it, and every factor is tagged with its source — you, product data, or the rules. A real card from the running app: RESTYLE — You can get this look from what you own U.S. Polo Assn. · Men Button Down-Collar Tailored Fit Shirt · ₹1,175 + Within budget [user] ₹1,175 against a ₹3,000 ceiling − Close to what you own [rules] You already have White Shirts; this adds a colour, not a category · Rewear value [rules] Pairs with 1 item you already own + Right register [rules] Shirts suits client dinner + Fit confidence [product] 90% — garment measurements published, 77 fit ratings + Suggested size M [product] 16% of 77 raters found this loose vs 5% tight, so one size down · Deliverable, no date [product] Serviceable at 560029; the delivery API did not return a date That last line matters as much as the verdict. The delivery API returned no date, so the app doesn't invent one. Load the default brief and Mustermind recommends nothing. Two restyles, five skips, four different skip reasons. Then tell the agent "I could stretch to ₹5,500" and a blazer becomes the single buy — on screen, with the reason visible, and the change written to a Decision Ledger showing that you made it. How we built it Zero npm dependencies. Node 20 and vanilla HTML/CSS/JS. Nothing to install, no lockfile, no bundler — a judge can read the entire thing. It ships as a ~55 MB Alpine container running non-root. Five WebMCP tools , registered on document.modelContext with navigator.modelContext as a fallback probe, behind feature detection: Tool readOnlyHint untrustedContentHint get_current_style_brief ✅ — get_product_truth ✅ ✅ evaluate_wearability ✅ ✅ record_user_tradeoff — — prepare_purchase_handoff — — Five, deliberately. Tool selection degrades as the set grows, and each description is written as product surface — when to call it, what changes state, and when to ask instead of assert . The verdict engine is a rule engine, not a model. This was a deliberate constraint: the agent has to narrate why a verdict is what it is, and a scorer you cannot read gives it nothing to say. Gradient boosting would have scored marginally better and been useless on camera. Crowd fit becomes a directional prior. Too Tight and Too Loose count double — they signal a full size off, not a preference: $$\text{skew} = \frac{\left(t + 2t^{+}\right) - \left(l + 2l^{+}\right)}{100}$$ where $t, l$ are the tight and loose percentages and $t^{+}, l^{+}$ the too tight / too loose ones. We call RUNS_SMALL above a weighted gap of 6. At the rater counts these products carry, the standard error on a $p \approx 0.20$ proportion over $n = 2100$ is $$\sigma = \sqrt{\frac{p(1-p)}{n}} \approx 0.0087 \approx 0.9\ \text{pp}$$ so a 6-point weighted gap is several standard errors — signal, not noise. Below 50 raters we return INSUFFICIENT_DATA and refuse to call it at all. Two public AJIO sources , called server-side only: the PDP aggregator and the delivery-promise API, with a 60-second cache and hard timeouts. The style-code invariant is strict — only codes this server obtained from AJIO's own search, or ships fixtures for. Never a code supplied by the browser. No anti-bot sensor header is sent, stored or committed anywhere. If a call would need one, the app falls back to clearly-labelled fixtures instead. There's a grep in the verification step that fails the build if such a string ever appears in the tree. 55 assertions, no test framework. node scripts/selfcheck.js . Challenges we ran into The WebMCP API is not the MCP API. Our tools returned {content:[{type:'text',text:...}]} — the envelope a remote MCP server uses. Chrome's execute returns a plain string . Every result would have arrived as a stringified wrapper the agent had to unwrap. We also assumed an unregisterTool method; there isn't one — unregistration is an AbortSignal passed at registration. Both were caught only by reading Chrome's docs against our own code. The silent one: origin isolation. WebMCP is only exposed in origin-isolated documents. Without Origin-Agent-Cluster: ?1 , document.modelContext is simply undefined — no error, no warning, nothing to debug. You'd naturally blame your Chrome version and go chasing an upgrade that was never the problem. Real data is hostile in small ways. numUserRatings is "2.1K" , a display string — parse it naively and you fabricate a rater count. Percentages arrive as "15 %" , with a space. The size chart is a superset of what's purchasable (8 charted, 5 buyable on one real product), so recommendations must come from the intersection. One live product returned a fittingType of " " — whitespace, which is truthy, and rendered a factor row with blank evidence. A truthful API answer that was useless. Our demo fixtures had invented SKUs. The live delivery API dutifully returned "not serviceable" for them — which is true, and means the SKU doesn't exist , not that the garment can't be delivered. We were putting fabricated products on real-looking hard fails. Fixture products no longer consult live delivery. A regression we caused ourselves. When live search landed, it loaded eight real style codes — and the PDP allowlist, which only knew about fixtures, rejected every one. The app rendered empty under a confident "Live AJIO data" badge. Fixing it meant sharpening the invariant rather than loosening it: codes AJIO's own search returned are server-obtained, so they earn a session allowlist; browser-supplied codes never do. Then the fix had its own bug — the search cache outlived the session allowlist, so the first Reset handed back codes the adapter then refused. Both are now regression-tested. Knowing when to stop being clever. The hardest call was making wrong register a hard stop instead of a weighted negative.
