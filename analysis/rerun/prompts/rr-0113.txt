## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

- 7-8: strong coherence and intentionality; central workflow appears functional; minor

- 3-4: thin prototype; contradictions between surfaces; placeholder content.

Most of the time I am still talking to an AI about the application I am using instead of letting the AI actually work with me inside it. I wanted to explore a simple question: what if I and an AI agent could work on the same live application state? I chose architecture diagrams because they make this easy to see. The website decides. The human commits. Recovery Desk is a deterministic airline disruption-recovery simulation built to explore a question that matters far beyond aviation: What if a website did not expose every action to an AI agent all the time, but instead changed what the agent was allowed to do as the situation evolved? Inspiration Most agent demos focus on whether an AI can call a tool. I wanted to explore a harder problem: when should that tool exist at all? In high-stakes workflows, reading information, proposing a change, cancelling something, and committing a final decision should not carry the same authority. Recovery Desk uses an airline operations-control scenario to make that distinction visible. A fictional airline faces a hub closure and must recover its schedule while respecting aircraft position, crew duty, minimum turn time, and the disruption window. The airline scenario is the testbed. The core idea is state-governed WebMCP capabilities . What it does Recovery Desk exposes seven WebMCP tools: get_disruption get_schedule check_plan_legality propose_reassignment reset_draft cancel_flight commit_recovery_plan But they are not all available at the same time . The website moves through six operational states: DISRUPTED → DRAFTING → CANCELLATION_REQUIRED → DRAFT_LEGAL → AWAITING_APPROVAL → COMMITTED As state changes, the website dynamically changes the capabilities exposed through WebMCP. For example, cancel_flight is a destructive capability. It is not exposed by default. When the current plan leaves an unresolved flight with no feasible aircraft reassignment, the website can enter CANCELLATION_REQUIRED and expose cancel_flight . Once that destructive action is no longer appropriate, the capability is withdrawn. When the draft becomes legal, commit_recovery_plan becomes available. Calling it still does not commit the plan. It moves the workflow to AWAITING_APPROVAL and waits for an explicit human decision. Only human approval commits the recovery plan. Agent proposes → Website validates → Capabilities change → Human authorizes → System commits. How I built it Recovery Desk is a deterministic client-side application with the WebMCP layer separated from the recovery logic. The site registers tools through the browser's Model Context API and dynamically manages their availability according to the current application state. The recovery engine uses integer-minute scheduling and explicit rules for: hub closure aircraft position minimum aircraft turn time crew duty limits Agent mutations affect a draft , never the committed plan directly. Every mutating, destructive, or human-gated action re-checks the current phase at invocation time. This also provides stale-tool defense: if an agent attempts to invoke a capability that is no longer valid in the current state, the website rejects the call without performing the mutation. The application maintains an audit trail of tool calls, state transitions, rejected actions, approval requests, and final human decisions. The demo The deterministic recovery walkthrough deliberately creates and repairs operational conflicts. The operator retimes flights while the website continuously validates the evolving draft. Eventually, the current draft leaves MA442 without a feasible aircraft reassignment, causing the site to enter CANCELLATION_REQUIRED . At that point, cancel_flight dynamically appears. After the remaining recovery actions and cancellation of MA442 produce a legal draft, the destructive capability is withdrawn and commit_recovery_plan becomes available. The agent can request the commit, but the website opens a human approval gate. A human can Reject , leaving the committed schedule unchanged and preserving the draft for further work, or Approve , which is the only path that commits the recovery plan. After commitment, mutating capabilities disappear and the interface returns to three read-only WebMCP tools. Challenges The hardest part was not registering tools. It was defining authority boundaries between the agent, the website, and the human. I also learned that capability availability must be treated as part of application state rather than as a static tool list. Another challenge was keeping the demonstration deterministic enough that the same state transitions can be inspected and reproduced. The current feasibility helper intentionally evaluates aircraft reassignment against the current draft . It is not a global optimization engine and does not claim to exhaustively search every possible retiming, resequencing, aircraft, and crew combination. That limitation helped clarify the real purpose of the project: Recovery Desk is not presented as a production airline optimizer. It is a testbed for state-governed agent capabilities . What I learned WebMCP can represent more than a collection of functions that an agent can call. A website can use its own domain state to determine: what an agent may read, what it may propose, when a destructive capability becomes appropriate, when that capability must disappear, and where human authority must remain absolute. That suggests a broader pattern for agentic websites in finance, healthcare operations, enterprise administration, infrastructure, procurement, and other workflows where actions have different levels of consequence. Recovery Desk demonstrates a simple principle: giving an agent tools is useful; giving it the right tools at the right moment is safer and more powerful. Stale protection: An outdated proposal is rejected, preventing old AI work from overwriting new human evidence. Human-sealed result: The final export records decisions, evidence revisions, and a SHA-256 integrity hash. Why I made InkWitness Old handwritten documents are often difficult to read. Some letters are faded, damaged or missing. AI can help, but it may also guess a word with too much confidence. In historical records, one wrong name or place can create a lasting mistake. That problem gave me the idea for InkWitness: let the AI help with the investigation, while keeping the final decision with a person. How it works InkWitness uses a synthetic historical ledger with three unclear words. The agent can examine each word, compare it with other letters written by the same hand, check possible answers and suggest a reading. The evidence it uses appears on the page, so the person can understand why that suggestion was made. A suggestion is not automatically accepted. Only the person using InkWitness can accept it, reject it or decide that the word should remain illegible. Why WebMCP matters The person and the agent work on the same visible desk. They are not working with separate copies of the information. The desk also keeps track of revisions. For example, if a person adds a new clue after the agent reads the page, the agent’s old proposal is no longer safe. InkWitness rejects it with STALE_REVISION. The agent must read the latest version and reconsider the evidence. This prevents old AI work from replacing newer human work. How I built it I built the project with HTML, CSS and JavaScript. It has eight native WebMCP tools that allow the agent to read the desk, inspect unclear words, compare handwriting, check possible readings and prepare proposals. The WebMCP tools and the buttons on the page use the same state and functions. I also included manual testing controls so the workflow can still be demonstrated in a normal browser. No real historical documents or personal data are used in the demonstration. The difficult part The hardest part was deciding exactly what the agent should and should not be allowed to do. The agent can investigate and make suggestions, but its tools do not include accepting a reading, declaring a word illegible or sealing the final record. Those actions belong only to the person reviewing the document. I also had to make sure an outdated agent action could not overwrite a newer change. That is why every proposal must include the desk revision that the agent previously read. What I learned This project taught me that making AI safer does not always mean making it less useful. The agent can still do the repetitive work of comparing letters and organizing evidence, while the person handles decisions that require judgment. I also learned how WebMCP can connect an agent directly to the information and controls inside a webpage. Final record After every word has been reviewed, the agent can prepare a provenance packet. The person then chooses whether to seal and export it. The exported receipt includes the evidence, revisions, proposals and human decisions. Its SHA-256 hash helps detect later changes, but it does not prove identity or document authenticity. HumanKey explores a stronger model: the page itself declares exactly what an agent may do, and consequential authority appears only after a visible human decision. What it does HumanKey is a WebMCP control plane for proof-carrying delegation. A human defines a mission envelope with a goal, spending ceiling, required evidence, and an approval threshold. The agent can read the mission, inspect verified evidence, stage a reversible action, evaluate deterministic policy, request approval, verify a receipt, and export an audit bundle. The key interaction is dynamic capability exposure. The demo starts with seven discoverable WebMCP tools. A synthetic $1,840 supplier release passes evidence and policy checks but exceeds a $1,000 human-approval threshold, so the commit capability does not exist. When the human visibly clicks Approve, commit_approved_action is registered and Chrome discovers an eighth tool. After the agent commits the synthetic action, the capability unregisters itself and the surface returns to seven tools. The committed action emits a SHA-256 receipt over the canonical mission/action record. verify_action_receipt independently recomputes the hash and confirms the receipt. Every state transition is attributed to the human, the agent, or the deterministic policy engine. No real payment API is connected; all demo data is synthetic. How I built it HumanKey uses both declarative and imperative WebMCP. The reversible staging step is an annotated HTML form exposed as stage_release_action , while mission, evidence, policy, approval-request, receipt-verification, and audit-export operations are imperative tools registered through document.modelContext.registerTool() . The approval-gated commit tool is registered only after human approval and removed using an AbortController after its in-flight execution resolves. The experience was validated against Chrome's native document.modelContext.getTools() and executeTool() APIs. Native QA produced the expected 7 -> 8 -> 7 lifecycle and an exact SHA-256 receipt verification result of valid: true . The app is a static HTTPS site hosted on GitHub Pages with a public MIT-licensed repository. Challenges I ran into The hardest part was making authority a real browser capability boundary rather than a hidden boolean. The commit tool must not exist before approval, must become discoverable immediately after approval, and must unregister safely without cancelling its own in-flight execution. Native Chrome QA exposed that lifecycle edge case and the implementation was corrected accordingly. Accomplishments that I'm proud of The agent cannot self-approve because the consequential tool literally does not exist before the human decision. Human-visible UI and agent-visible capability state stay synchronized. The final synthetic action produces a verifiable SHA-256 receipt and an auditable provenance trail. The demo works against native Chrome WebMCP rather than only a mock implementation. What I learned WebMCP can do more than make forms easier for agents. It can make authorization itself part of the website's structured capability surface. That creates a reusable pattern for procurement, finance operations, deployment gates, compliance workflows, and any task where automation is valuable but final authority should remain human. What's next for HumanKey The next step is to generalize the mission/evidence/approval/receipt pattern into reusable components that sites can adopt for high-consequence agent workflows, with richer evidence adapters, signed receipts, and policy modules while preserving the same visible human checkpoint model. Like Comment Story Updates Step 1 Processing Result Icon Inspiration In a world of AI there is too much noise, this is a simple tool to leverage that very same AI to help cut through the noise to get to the signal of your YouTube videos. What it does TLDW is one web page where you paste a YouTube link and gets the captions, with the moment each line was said. An AI agent opening the page finds two WebMCP tools instead of buttons: get_transcript(url) hands it the captions as timestamped segments, and render_explainer(slides, url) draws whatever the agent wrote back onto the page, every timestamp a link that opens the video at that second, then reads it aloud. The thinking runs on the visitor's own ChatGPT plan, in their own session. How its built Built entirely with AI, Both tools are registered with document.modelContext.registerTool, with navigator.modelContext as a fallback for older builds, each with a JSON schema an agent can read. Errors are returned, never thrown, so a failure arrives as a result the agent can act on. Every fetch has three outcomes, not two: ok, not_measured with a reason, or a structured error, because a tool that cannot tell a failed measurement from a real zero will report the first as the second. Captions come from a transcript API first with a direct fetch behind it, held in memory for ten minutes and never written down. The page is served by a Cloudflare Worker. Read-aloud uses the browser's own voices by default with a voice picker; one opt-in experimental entry renders a natural voice on our server and streams it back. An agent whose browser has no WebMCP yet can paste the same slides into a Render box on the page and get the identical result. It was built from nothing in one evening, live on stream, by a fleet of AI bodies run by one human, with two independent reviews on every change. Challenges We (Myself and my AI Team) only had ~8 total hours for this as that's when I found out about the competition, then immediately started live streaming the start to finish. We had about ~3 hours of prep while waiting for the reset then 5 hours to build. The spec moved while we built: our first registration was on navigator.modelContext only, and Chrome's stable build binds document.modelContext, so the tools registered and nobody could see them. YouTube refuses caption fetches from a server, so the free path failed silently until we made refusal a first-class result and put a transcript API in front of it. Agents that fetched the captions then answered in chat instead of drawing on the page, until the tool text put the obligation before the data. And the browser's speech queue armed from the speak call rather than from what was drawn, so a slide with the wrong shape left a full explainer on screen and nothing to play. Each one was found by a second reader, not by the author. The page registers two tools, the agent calls them, the explainer appears with timestamps that jump into the YouTube video if you want to watch a particular segment in full, and it also comes with a reads aloud bar with play back controls and voice selection that uses your browser supported voices and 2 x experimental neural voices.
