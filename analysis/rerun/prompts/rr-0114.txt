## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the

sums.

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.

It scans a repo, a diff, or a pull request and hands back a 0-100 score, a grade, and every hit quoted as file:line . Instant, offline, deterministic, and the same input gives the same output forever. The scoring is deliberately boring so you can argue with it: $$\text{score} = \min\left(100,\ \frac{100 \times \sum_{r} w_r \cdot d(h_r)}{1000 \times \max(L_{\text{eff}},\ 420)}\right)$$ where $w_r$ is a rule's weight, $h_r$ its hit count, $d$ a damping function so one repeated house idiom cannot fail a whole codebase, and $L_{\text{eff}}$ the effective scanned lines. --explain prints that arithmetic per run. No black box to trust. why it is a card game A wall of 200 findings is a linter, and linters get disabled. So findings come back as a deck you swipe. Left says the finding is fair. Right says it is a false positive, and disputed cards come back out as slop-disable directives you paste into your code, which the CLI and the GitHub Action then honour on every later run. Your disagreement becomes configuration instead of a shrug. There is also a confession mode on the share card. It stamps YES, I WROTE THIS WITH AI on the image. Everyone is doing it. The pretending is the annoying part. It has already earned its keep on repos much larger than mine. Pointed at openai/openai-python (1,542 files) it surfaced real findings, and the same run surfaced six defects in my own rules. what I actually learned A scanner's most important property is staying quiet. I spent most of my time not adding rules. I read every finding on a large, well-written repo by hand and asked whether a maintainer would act on it. 61 findings became 12. None of the six bugs I found this way would have surfaced from unit tests, because every rule passed its own fixtures. Some of them were embarrassing in a useful way. dead-defaults split parameter lists on bare commas, so a comma inside dict[str, Any] invented parameters that did not exist. happy-path-only matched \bopen( , which caught tarfile.open() and wave.open() and read every with open(...) as unhandled I/O, when a context manager is the failure path. duplicate-helper flagged every f / async_f pair in an async library at 95% similarity, which is a Python constraint and not a mistake. swallowed-error flagged __del__ , where suppressing exceptions is correct and the tool was asking for the code to be made worse. And the one I liked most: every rule read prose as code. A rule that matches source text will happily match a sentence describing the pattern it looks for. This repo scored itself a grade worse because two of its own explanatory comments contain .catch(() => {}) . Comments are masked before matching now. Each of those is pinned in test/false-positives.test.ts , which exists for one job: keep fixed rules fixed. Then WebMCP. I liked it immediately, and for a reason that is more about how I work than about the spec. I am usually looking at a page and I want my agent looking at the same page. Every other integration shape makes you pick one: either the agent works somewhere you cannot see, or you do it yourself. The rule I gave myself was that the tool layer owns no state at all. It gets a small handle assembled in main.ts out of the exact functions the click handlers call. There is no second code path, so there is no way for an agent to reach a result the page is not showing, or to record a verdict the deck does not reflect. A tool-driven scan fills the visible input, flips the visible tab, and runs the same progress panel a click does. Three tools are meaningless before a scan exists, so they are not registered until one lands and are unregistered when results clear, using the AbortSignal that registerTool takes as its second argument. The page emits its own state event, the WebMCP layer syncs registration to it, the browser fires toolchange . An agent reading the tool list is reading the page's real state rather than a manifest. Cancellation is threaded all the way down. execute receives a signal , it reaches githubFiles and every fetch under it, composed with the existing per-request timeout through AbortSignal.any . challenges False positives, by a distance. Everything above about the openai-python pass was the hard part of the project, not a footnote to it. It is still not fully solved. hardcoded-config is my noisiest rule and I will tell you exactly how: it flags process.env.SITE_URL || 'https://example.com' , which is a literal inside an environment-variable fallback, which is the configuration it is demanding. The deck is a stack, but an agent asked about one specific rule wants that card now, not in fourteen swipes. Re-rendering the stack broke the animation on cards already leaving, so swapToFront swaps the rendered contents of two positions instead. There is no reliable authorship signal in source text and anything claiming otherwise is guessing. It measures whether code carries the patterns that AI-assisted code carries more often. Students provide a lightweight profile, search a curated catalog of 30 named programme records, inspect match, mismatch, and unknown evidence, compare up to three candidates, and turn a selected route into a planning checklist. A catalog record is not automatically presented as an open application or a verified match: each result exposes its official provider link, review date, evidence scope, cycle status, and unresolved facts. WebMCP is central to the experience. Six typed page-defined tools expose search, eligibility, comparison, shortlisting, checklist generation, and checklist updates to an agent. The tools use the same deterministic TypeScript domain layer and browser-local state as the visible interface, so agent actions and student actions stay synchronized. State-changing tools require explicit student confirmation, and the app never submits a scholarship application. This improves scholarship research because agents can filter and normalize structured evidence while students retain the judgment calls: resolving country or course rules, choosing among tied candidates, verifying the official source, and approving saved work. Unknown facts add no ranking points, so missing evidence cannot silently become a recommendation. The release was tested on the live Vercel deployment in ChatGPT’s in-app browser. All six tools were discovered. A clean Nigeria + Computer Science + any-level + any-funding run returned 25 candidates, preserved unknown criteria in the top-three eligibility checks, populated a three-way comparison, and generated three source-aware Chevening planning tasks. Built with Next.js 16, React 19, TypeScript, browser-native document.modelContext.registerTool registration, deterministic domain functions, local browser persistence, and Vercel. The public repository contains the complete source, demo assets, setup instructions, automated tests, and MIT license. Codex helped scope the product, implement and test WebMCP, audit all 30 catalog records against official-source evidence, correct high-risk facts, harden persistence and confirmation boundaries, verify the live workflow, and render the narrated demo. A WebMCP-powered lost-and-found where agents investigate clues, compare evidence, and narrow the search — while humans make the final decision. Like 1 Comment Story Updates Agents search and compare. Humans decide. Lost something? Start with what you remember. The investigation can begin with an imperfect memory. A catalog built for humans and agents. Inspiration When I was a kid, I loved treasure maps. Someone would hide something and leave you a clue. You would search, realize your first guess wasn't quite right, discover another clue, and slowly narrow down the possibilities. Looking back, I think the part I enjoyed most wasn't actually finding the treasure. It was getting closer. When I started experimenting with WebMCP, that memory came back to me. I wanted to find a use case where an agent wasn't simply pressing buttons faster than a human, but was actually helping with the reasoning between those actions. Lost and found felt like a surprisingly natural fit. When we lose something, we rarely remember perfect database fields. We remember fragments. “I lost something on a key ring.” Then, after thinking about it: “Wait, it had a small bear charm.” That became Agent Lost & Found : an experiment in what happens when a human and a browser agent investigate the same problem together. What I built Agent Lost & Found is a lost-and-found catalog with WebMCP built directly into the website. People can still browse the catalog like a normal website. But a WebMCP-enabled browser agent doesn't have to interpret search boxes, filters, buttons, and item cards to understand what the site can do. Instead, the website exposes seven structured investigation tools: search_lost_items get_item_details get_search_facets compare_items get_match_evidence get_active_case request_claim Together, these let an agent search the catalog, inspect candidates, compare possible matches, analyze evidence, find useful follow-up clues, resume an existing investigation, and eventually ask the human to review a possible match. -- From a vague memory to a specific match The demo begins with an intentionally incomplete clue: “I lost something on a key ring.” There isn't enough information to immediately know which item is correct. And I didn't want the agent to pretend otherwise. Instead, it can search the catalog, inspect the remaining candidates, and use the available information to narrow the investigation. Then the human remembers one small detail: “It had a small bear charm.” That clue doesn't start a new search. It becomes part of the existing case. The candidates are evaluated again, and LF-017, a bear keychain, moves toward the top of the investigation because the new clue provides much stronger evidence for it. This simple interaction became the core of the project for me. The agent doesn't need the human to remember everything at once. The human doesn't need to manually restart the search every time another detail comes back. They build the investigation together. Making the ranking explain itself Once I had progressive clues working, another problem appeared. If LF-017 moves up after I mention the bear charm, the interface shouldn't just show me a different ranking. It should be able to explain what changed. So each investigation step stores score snapshots and evidence breakdowns. When the evidence changes, Agent Lost & Found can compare the new state with the previous one and show Candidate Movement . A candidate may move up because a new clue matches. Another may move down because the new information contradicts it. Evidence is separated into three states: Matched Unknown Contradiction That distinction became more important than I expected. If the catalog doesn't contain information about a particular feature, that doesn't automatically mean the item contradicts the human's memory. Sometimes the correct answer is simply: We don't know yet. For the same reason, the number shown by the application is called a Match Score . It is a deterministic matching score based on the available evidence — not an AI confidence probability. I wanted the user to be able to inspect why an item ranked highly instead of being asked to trust an unexplained number. The Casefile Once the investigation became multi-step, I ran into another very ordinary problem: I refreshed the page. Everything disappeared. That didn't feel right. If a human and an agent are investigating something together, the investigation itself should exist independently of a single page session. So I introduced a versioned Casefile . It stores the active investigation, including the original description, clues, candidate state, score history, ranking history, timeline, strongest match, and claim-review state. After a refresh, the application validates and restores the Casefile. The agent can then call: get_active_case and continue from the same investigation. One small detail mattered to me here: restoring state should not mean inventing history. The application restores the Casefile, but it does not replay fake tool calls or create Agent Activity for actions that never happened. The investigation continues from real state. Why WebMCP? I understood WebMCP differently after building this project. At the beginning, I mostly thought: “Websites can expose actions as tools.” That's useful, but it turned out not to be the most interesting part. For me, the more interesting idea became shared state between the website, the human, and the agent . Without WebMCP, an agent interacting with a lost-and-found website would need to interpret an interface built for humans: locate the search field, understand the filters, inspect cards, and infer what changed after each interaction. With WebMCP, the website can expose its actual capabilities as structured tools while keeping the normal visual interface for people. More importantly, both operate on the same underlying investigation. The human interface and WebMCP tools share the same search, matching, evidence, ranking, and Casefile logic. When the agent investigates something, the human can see the result. When the human adds or corrects a clue, the next agent action sees that updated state. That was the point where the project stopped feeling like: “AI controlling a website.” It started feeling more like: a human and an agent using the same product together. The tool I deliberately didn't build There was one tool I deliberately left out. If the agent finds a strong match — for example, LF-017 after the bear-charm clue — should it be allowed to claim the item automatically? Technically, I could expose: confirm_claim I decided not to. The agent can call: request_claim which opens the claim review interface for the human. But the final confirmation still requires a human action. This isn't a technical limitation. It's a product decision. Searching through candidates is useful work to give an agent. Comparing evidence is useful. Finding the next clue worth asking about is useful. But deciding that a real item belongs to someone has consequences. Building this made me realize that not every action that can become an agent tool necessarily should become one. That eventually became the principle behind the project: Agents investigate. Humans decide. How I built it Agent Lost & Found is built with React, TypeScript, Vite, and WebMCP , and deployed on Cloudflare Pages . For this hackathon version, the application uses a deterministic catalog of 30 lost items backed by structured metadata. The catalog is intentionally small. I wanted the investigation to be reproducible and inspectable. A judge should be able to understand why LF-017 appeared rather than having the result hidden behind a huge dataset or an opaque model. The human interface and WebMCP layer share the same underlying engines for: search and normalization matching and ranking evidence classification clue handling score snapshots candidate movement Casefile persistence I also built a deterministic demo/presenter mode for evaluation.
