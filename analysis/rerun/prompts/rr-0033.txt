Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  here; the agent is central to the product, not a bolt-on.

- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

- 7-8: strong coherence and intentionality; central workflow appears functional; minor

- 3-4: thin prototype; contradictions between surfaces; placeholder content.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.

Reproduce any application state and see the real UI instantly. Like 1 Comment Story Updates Inspiration When testing a web application, the difficult part is often not the test itself. It is getting the application into the exact state you need to inspect. An expired account. A trial user. An unauthenticated session. A specific error state. Reproducing these states can require creating users, changing database records, configuring subscriptions, or manually navigating through multiple steps. I wanted to remove that setup work. Repro lets you describe the application state you want to see, reproduce it, and inspect the real UI immediately. We don't run your tests. We create the state you need to see. What it does Repro exposes application-state reproduction through three stable WebMCP tools: list_states reproduce_state reset_state Instead of creating a separate tool for every test scenario, Repro treats application states as data. For example, an agent can discover an available state such as free_expired . Repro applies that state to an isolated Repro session, and the application's existing UI renders normally. This makes it possible for humans and agents to inspect production-like UI states without creating real users, payments, emails, or other production side effects. How I built it Repro is published as the repro-webmcp npm package. The basic workflow is: npm install -D repro-webmcp npx repro scan npx repro setup repro scan statically analyzes an existing JavaScript or TypeScript application and discovers semantic application states from existing code, including conditional UI branches, enums, literal states, mocks, fixtures, and tests. The discovered states become the source of truth for Repro. repro setup prepares the runtime, browser registration, and integration boundary. For simple supported state architectures, the connection can be generated automatically. For more complex applications, a coding agent connects one generic bridge to the existing state boundary. Repro generates a project-specific .repro/AGENTS.md integration guide containing both its standard integration rules and evidence discovered during the scan. A coding agent can use this to connect Repro once to the application's existing state boundary. The important distinction is that the agent does not generate a separate test fixture for every state. It creates one generic bridge between Repro and the application's normal state/rendering system. Dogfooding on an existing application I tested Repro on a separate existing application that was not built for this challenge. Before installing Repro, it contained zero manually defined Repro states. Running repro scan discovered 20 candidate application states from the existing source code. For this more complex application, I gave the generated integration instructions to Codex. Codex implemented one generic bridge to the application's existing authentication/session state. After that, the same three WebMCP tools could reproduce states such as authenticated and unauthenticated, while the real application UI continued to render through its normal code path. This dogfooding also exposed an important setup bug: the browser bootstrap was still loading an older hand-written configuration instead of the scan-generated states. I fixed the runtime/setup flow and published the fix as repro-webmcp@0.1.4 . Challenges The hardest problem was finding the right boundary between automation and application-specific integration. Automatically discovering states is possible, but automatically modifying arbitrary application state safely is much harder. Real applications use different stores, authentication systems, module structures, and rendering architectures. I initially considered generating state-specific fixtures, but that would simply move the manual test-setup problem somewhere else. The architecture evolved into: automatic state discovery + a stable runtime + one generic application bridge when necessary. Another challenge was safety. Reproducing an expired subscription should not require modifying a real subscription. Reproducing an authenticated user should not require creating a production user. Repro therefore focuses on reproducing the application state consumed by the UI rather than recreating the entire backend environment. What I learned The biggest thing I learned is that WebMCP becomes especially useful when the interface exposed to agents is semantic rather than tied to individual UI actions. An application may contain 20, 100, or more reproducible states, but Repro still needs only three WebMCP tools. The vocabulary remains stable while the application's states remain data. I also learned a lot from testing the npm package against an application that was not designed around Repro. That immediately revealed assumptions that were invisible in the purpose-built demo and changed the final architecture. What's next After the challenge, I want to expand Repro's automatic integration support across more application architectures and frameworks. One limitation discovered during dogfooding is multi-page applications: full-page navigation can create a new document where the WebMCP bootstrap must be initialized again. I plan to add automatic multi-entry-point instrumentation for this case. I am also interested in exploring the same concept beyond web applications, including state reproduction for SwiftUI applications and simulator-based development workflows. The long-term goal is simple: Make application state an interface that both developers and agents can discover, reproduce, and inspect safely. ABOUT TEXT (untrusted evidence):
A visual workspace where people and AI agents turn ideas into connected plans and maps using WebMCP, without losing important context in chat. Like Comment Story Updates A product roadmap where scope, progress, evidence, and agent-created relationships stay visible on one connected canvas. Nodebook exposes 15 WebMCP tools for reading context, creating maps, updating plans, adding evidence, and focusing important paths. The inspector makes agent work reviewable with linked maps, named comments, evidence, delivery status, and human-controlled locks. A learning map connects concepts, evidence, exercises, and an interactive quiz so people and AI can build understanding together. Inspiration AI assistants can help plan a product, research an idea, or explain a difficult concept. But their best work often ends up buried inside a chat. The person then has to copy the result into a document, rebuild the relationships, and explain the same context again in the next conversation. I built Nodebook to give people and AI assistants a shared visual workspace. The person chooses the direction, while the assistant helps organize the work directly on the canvas. What Nodebook does Nodebook is an infinite visual canvas for planning, tracing, and learning. A workspace can contain three kinds of connected maps: Build maps for features, scope, progress, risks, and evidence Trace maps for user journeys, system flows, and failure paths Learn maps for concepts, examples, exercises, and quizzes People can create and edit nodes, decide what is in scope, track delivery, attach evidence, leave comments, and lock important decisions. An AI assistant can read the same workspace through WebMCP. It can understand which node the person selected, create connected maps, update plans, add evidence and comments, and highlight important paths. For example, a person can select “Crash-safe recovery,” click “Trace,” and ask the assistant to map the recovery process. The assistant can read that selection, create the complete flow, connect it to the original feature, highlight the riskiest path, and leave an explanation, all without the person copying the project into the prompt. Why WebMCP is a strong fit Nodebook is useful because the person and the assistant work with the same information. Without WebMCP, an assistant would need to interpret screenshots, click through the interface, or ask the person to repeatedly copy information into a chat. Those approaches are slow and can lose important details. With WebMCP, Nodebook gives the assistant clear actions for reading and changing the workspace. The assistant receives the exact nodes, relationships, comments, evidence, and selected task. Its changes then appear immediately on the canvas, where the person can inspect and edit them. This creates a better experience than an embedded chatbot. The conversation is not the final product. The shared, lasting workspace is. How I implemented WebMCP Nodebook registers 15 browser tools with document.modelContext.registerTool() . These tools allow an assistant to: Read the workspace, maps, nodes, comments, and human selection Search across titles, descriptions, tags, evidence, and comments Create linked Build, Trace, and Learn maps Add or update nodes and connections Make scope and delivery updates Attach evidence and attributed comments Focus nodes and highlight important paths Every request is checked before it changes the workspace. Invalid links, missing nodes, duplicate IDs, unsafe source URLs, oversized requests, and broken connections are rejected. Each successful assistant action is applied as one undoable change. Locked nodes are skipped, and assistants are not given a tool that permanently deletes nodes. This keeps important decisions under human control. How it was built Nodebook is built with Next.js, React, TypeScript, and React Flow. Dagre arranges assistant-created maps into a predictable layout. Zustand manages the workspace, while Zod checks tool requests and imported files. The workspace is saved in the browser using IndexedDB. There are no accounts, API routes, analytics, cloud database, or Nodebook storage server. People can export the complete workspace as JSON and import it again later. The included demo contains a product roadmap, user journeys, a learning map, release checks, evidence, comments, locked decisions, and a research parking lot. Challenges The hardest part was making assistant actions feel like real product actions instead of hidden changes. I needed to make sure that a large graph update either succeeded completely or changed nothing. I also had to keep the visible canvas, undo history, browser storage, and WebMCP responses in agreement. Another challenge was balancing useful assistant access with human control. Nodebook solves this with strict validation, visible activity, attributed comments, undo support, locked nodes, and human-only deletion. Accomplishments I am proud that Nodebook is a complete working application rather than only a WebMCP experiment. It includes: 15 working WebMCP tools A detailed, editable demo workspace Linked maps with breadcrumbs Evidence and human-assistant comments Scope, progress, and learning states Path highlighting and automatic layout Undo and redo for assistant changes Local browser persistence Safe JSON import and export Automated unit and browser tests What I learned I learned that good human-AI collaboration needs more than a prompt box. The assistant needs clear actions and reliable context. The person needs to see what changed, understand why it changed, and remain able to edit, lock, or undo the result. WebMCP makes that possible using the website’s real data and actions. What’s next Next, I would improve keyboard navigation, test larger workspaces, add more starter templates, and make recovery guidance even clearer. I would also explore shareable, read-only workspace snapshots while keeping Nodebook’s main promise: the person owns the workspace and stays in control.
