Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  be replicated comparably well by a general agent driving the UI.

- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

An agent can act. A person can see what happened. The evidence can be independently verified. Like Comment Story Updates Inspiration AI agents are starting to do things on the web, not just read it. That raises a question I kept coming back to: if an agent says an action succeeded, what does the person supervising it actually have to work with? A chat message that says “done” is not the same thing as evidence. And if another source disagrees, I do not want the system to guess which one is right. That is the idea behind AI Evidence in Action. The demo uses a synthetic refund because it is easy to understand, but the real subject is human supervision of AI actions on the web. What it does The page exposes four WebMCP tools: request_refund get_evidence compare_evidence verify_evidence An agent can use those tools directly in the same application the human is watching. As the agent works, the page shows the tool-call timeline, what the demo site reported, what the demo destination reported, where the records match or conflict, and what verification can and cannot establish. There are three bounded outcomes: AGREEMENT DISAGREEMENT INSUFFICIENT EVIDENCE The demo never guesses which source is correct. The records are signed with standard Ed25519 public-key cryptography over SHA-256 commitments. The verifier checks the signatures, makes sure the two records actually belong to the same claim, and then independently recomputes the whole comparison. There is also a Test tamper detection control. It makes a throwaway copy of the evidence, changes one comparison value, leaves the signed records untouched, and runs that altered copy through the real verifier. The verifier rejects the changed copy while the original evidence remains verified. Everything in the challenge scenario is synthetic. Both demo sources are operated in the same deployment by the same demonstration operator, and the page says that plainly. The signatures establish integrity and demo-key attribution; they do not prove that a real-world refund happened. Why WebMCP fits this use case What interested me about WebMCP is that the agent does not need a separate hidden integration or an API console that the human never sees. The webpage itself can expose bounded tools through document.modelContext , and the agent can act through the same application state the human is supervising. That creates a much better interaction model for this problem. The agent can act, but the person can still see the evidence appear, inspect the source records, follow the comparison, and take over if needed. The application does not ask the human to re-enter information it already learned from earlier tool calls. For this demo, the useful pattern is simple: act → record → compare → verify Without WebMCP, I could still build an API behind the page, but the important part of this project would be missing: the shared surface between the human, the agent, and the website. How I built it I kept the project deliberately small and public-safe: vanilla JavaScript, HTML, and CSS in the browser, a Netlify function for the synthetic signed records, and a standalone Node.js verifier that can check a downloaded evidence bundle without contacting the site. The WebMCP tools are registered directly with document.modelContext.registerTool(...) . I tested the final implementation in Chrome for Testing 152 with WebMCP enabled. All four tools were registered, discovered, and executed through the native WebMCP runtime. The evidence verifier checks three separate things: Integrity — recompute the SHA-256 commitment and verify each Ed25519 signature against the published demo public keys. Pairing — require the signed claim_id , request_id , and scenario to match before two records can be compared. Comparison consistency — recompute the complete comparison from the verified records and compare it with what was recorded. The final build has 162 automated tests, including browser-facing tests for the shared evidence flow, mobile layout, pair-splice rejection, full-comparison tamper detection, and the local tamper demonstration. Challenges I ran into I am not a coder by background, so a big part of this project was learning where a convincing demo can accidentally claim more than it proves. The hardest part was not getting an agent to call a tool. It was defining the evidence honestly. A website saying “success” does not prove an external outcome. A valid signature does not make the signed statement true. A missing second record does not mean failure. And two individually valid records do not belong together just because they both have valid signatures. Those distinctions led to several changes during the build. I added explicit pair binding, made the comparison independently recomputable, and treated missing evidence as its own result instead of forcing it into success or failure. One of the most useful tests came late in the project. I took two genuinely production-signed records from different claims and combined them. Every signature was valid, but the verifier still refused the pair as CLAIM_PAIR_MISMATCH . That was exactly the behavior I wanted. Accomplishments I’m proud of I am proudest of the fact that disagreement is visible rather than smoothed over. In the main demo, the site can report SUCCESS_DECLARED while the destination reports ACTION_ABSENT . The page shows that specific mismatch to both the human and the agent instead of turning it into a confidence score or pretending to know which source is right. I also like that the verification is not trapped inside the originating page. A person can download the evidence bundle and the verifier and check it again offline using only the published public keys. The tamper test is another part I am glad we added. The recorded and recomputed verdict can remain exactly the same, but changing a lower-level comparison value is still detected. That makes the verification claim much more concrete than simply saying “the signatures are valid.” What I learned WebMCP makes the webpage itself a useful shared workspace between a person and an AI agent. The bigger lesson for me is that agent UX should not stop at “the agent completed the task.” As agents take more consequential actions, people need to be able to see what happened, see what the available evidence actually supports, and distinguish that from what remains unknown. Uncertainty needs an honest result too. Sometimes the right answer really is INSUFFICIENT EVIDENCE . What’s next This challenge project is intentionally narrow. The scenario is simulated; the evidence workflow is real. The interaction pattern is what I want to keep exploring: a human and an agent working in the same application, with visible evidence that can be checked independently instead of simply trusted. The agent can act. The human can see what happened. And the evidence can be independently verified. When I heard about the WebMCP hackathon I got really stoked, since I had been wanting to try WebMCP more. I also already had a good demo scenario - at the conference AgentCon Stockholm earlier this year I gave a talk on agentic applications and used a PC part picker to demonstrate how to use AG-UI to share state between an agent and an app (still live here ). It was a good example of an agentic application, but the website had to ship the AI-assistant and foot the inference bill. WebMCP inverts that, which is an interesting idea. The user brings the agent, and the site hands it tools. So we (Andreas Adner and my friends Rafsan Huseynov (in the US) and David Lorenze (in Spain)) expanded upon this idea and built RigBuilder, a PC Builder where an agent can help you out, using WebMCP. What it does RigBuilder is an agent-native PC part picker. It is also a compatibility and constraint solver , making sure that all parts fit together and are within your budget. Your agent (ChatGPT's desktop browser, or Chrome 149+ with an agent) drives the build through 14 WebMCP tools and the agent gets access to validation and a gets a state revision back on every call. For example, ask for "a quiet, compact 1440p gaming PC under $1500" and the agent helps you assemble it. Swap the case by hand and say "fix whatever broke" and the agent reads your change from the shared state. Ask to get under $1400 and the page's optimizer computes the swap plan for the agent to present, and so on and so forth. Ask to see it, and render_build tool produces a brand-free impression of your parts using an OpenAI imagegen model (expect mixed results, it's AI after all ;-) There is a also a second user group - admins. An admin can curate the part catalogue in an WebMCP-enabled admin experience, where he for example can get help from his agent to research a newly launched part on the web and add it to the catalogue with the help of the agent. And RigBuilder is also a complete manual part picker, if you don't have an agent. :-) How we built it React/Vite/TypeScript with Zustand, and a single Cloudflare Worker: D1 for the catalog, R2 for renders and part cards, KV for share links, a Durable Object for the daily render quota, a Rate-Limiting binding for bursts, Turnstile for the render gate, Cloudflare Access to gate access to the admin side. The WebMCP surface was the priority, so it got the most design effort. Every tool returns the same envelope: validated build, conflicts, revision, so the agent never has to guess what changed. Shared state is versioned: a write based on stale knowledge is rejected even if the agent never learned about revisions, because the guard defaults to the revision the agent last saw. Tool descriptions carry untrustedContentHint where web-sourced text enters. The render_build tool sends only part ids and enums; the Worker rebuilds the prompt and cache hash itself and never trusts a client prompt or image. The catalog is 448 hand-authored parts, 82 verified against manufacturer spec pages with recorded sources; every tool result says which is which. Challenges The main challenge was deciding what the WebMCP tools should actually do. We did not want to expose a simple "remote-control" layer that simply mapped tools to normal user interactions - buttons and clicks. The tools needed to give the agent capabilities beyond what a user could accomplish: validating an entire build, identifying conflicts, optimizing against a budget, and returning a complete, structured view of the resulting state. Finding the right level of abstraction was a challenge. Each tool had to be powerful enough to add real value, but focused enough for an agent to understand when and how to use it. Shared state created another WebMCP-specific problem: both the human and the agent can modify the build. The agent might plan its next action from a state that the user has already changed manually. We solved this with versioned state and revision guards that reject stale writes, while still allowing agents to use the tools without explicitly managing revision numbers on every call. From my experiments with AG-UI I have realized that shared state between agent and app is a major unlock when it comes to agentic applications - and WebMCP is really good fit here. Finally, we had to treat the agent as capable but not inherently trusted. Tool inputs are validated by the application, web-sourced catalog text is marked as untrusted, and sensitive operations are reconstructed and checked on the server. WebMCP makes an application dramatically more accessible to agents, but it comes with some new and specific challenges when it comes to security. What we learned WebMCP changes who and what you design for. When the agent becomes the interface, tool descriptions form the foundation of the interaction model. Designing a good agent experience requires the same care as designing a visual one; that care simply moves into the tools, their contracts, and the state they share with the page. This is a pretty interesting shift. It's also an interesting challenge that we can't really make that many assumptions with regard to the agent that is consuming the WebMCP tools. We also learned that the entire “add an AI assistant” architecture can disappear/morph. RigBuilder has no embedded model, inference bill, or chat widget. The user brings the agent, while the application contributes its tools, domain knowledge, and interface. There is no assistant bolted onto the side anymore - also a major shift. What's next Lots of stuff to do. More verified parts, exact cards for the whole catalog, live pricing, and the part I care most about - bringing the same pattern back to the business applications I work with in my day job. Fenoa is a social platform for short fiction where creators publish stories and communities remix them into new branches, with humans, AI, and WebMCP agents working on the same living story state. Like 1 Comment Story Updates Inspiration Fenoa started from a simple idea I kept coming back to: What if a story did not have only one continuation? A creator could write the setup, publish it, and someone else could take the same characters in a completely different direction. Maybe one person continues the story normally. Another changes one decision. Someone else introduces a new character. Another person takes Episode 2 and turns it into a completely different branch. That sounded much more interesting to me than treating a story like one fixed document. Most writing tools are still built around a fairly linear workflow. You write something, edit it, and eventually publish the final version. Even with AI, the interaction is usually still "ask for some text, copy the text, edit the text." I wanted Fenoa to feel more like a living network of short fiction. A creator can publish a short story or mini-drama, and the community can keep branching it into new versions without destroying the original. While building that, another problem became obvious. Once stories start branching, continuity gets difficult very quickly. Who knows which secret? Which characters trust each other? What rules are still true? Did something already happen in another episode? What did the original creator say should never change? That is why Fenoa also keeps structured story state underneath the writing. The reader mostly sees the story. But underneath it, Fenoa understands the characters, relationships, facts, rules, constraints, episodes, and branch history. That structure also turned out to be a very natural fit for WebMCP. What it does Fenoa is a social platform for short fiction and remixable stories. Creators can build a fictional setup, turn it into a short story or mini-drama, publish it, and let other people create their own branches from it. The simplest way to think about it is: Create a story → publish it → remix it → branch it again. A Fenoa world can contain: a premise genre and tone characters relationships important facts secrets rules story constraints locations a story spark A creator can write all of this manually. There is also a built-in Creative Partner that can help develop the idea. For example, a creator can start with a rough concept and ask the Creative Partner to help build characters, motivations, relationships, tensions, and rules. The important part is that the AI output does not stay trapped inside a chat message. When the creator chooses to apply it, Fenoa turns the useful parts into real structured story data that can still be edited manually. Creators can also generate artwork for their story and publish it. Once published, another person can start a remix. A remix is a new branch of the story. It inherits the original context, but it can develop in its own direction. For example: continue the original story change an important event introduce a new character switch point of view create a darker or funnier version turn one moment into a larger mini-series remix an existing remix The original story is never overwritten. Each branch keeps its own creative direction, episodes, branch-specific characters, rules, constraints, and lineage. Short stories and mini-dramas I did not want Fenoa to become a long-form novel editor. The format is intentionally closer to short fiction and episodic mini-dramas. A branch can contain a small sequence of episodes, each focused on one clear development in the story. That makes remixing much more approachable. Someone does not need to read a 100,000-word novel before contributing something. They can understand the setup, read a few short episodes, and take the story somewhere new. I think this also fits the way people already consume creative content online. Shorter stories are easier to discover, easier to share, and much easier to remix. The Creative Partner Fenoa has a built-in Creative Partner for both world creation and remix development. It is meant to feel more like a collaborator than an automatic "write everything for me" button. A creator can ask it to: suggest possibilities challenge an idea connect existing story elements resolve continuity problems build structured story content For example, during the demo I start with a fairly simple comedy idea. The Creative Partner helps turn that into actual characters, motivations, relationships, world rules, and story material. Later, inside a remix, it can also help create episodes around a new direction. The creator can then open those episodes and change them manually. That combination was important to me. AI can move the story forward, but the human never loses control of the work. Remix Studio Remix Studio is where a branch becomes its own story. It brings together three things: The episodes being written The Creative Partner The current story context The story context matters because a remix is not just another blank prompt. It inherits information from the story it came from. That can include: characters relationships facts story rules constraints branch-specific changes episode history A creator can also add decisions that should remain true inside the branch. For example, a character might not be allowed to know a certain secret yet, or a specific fact may need to remain true throughout the story. Those decisions become part of the branch state instead of living only inside someone's memory or prompt history. Why WebMCP matters in Fenoa This is probably the part of the project I found most interesting technically. Fenoa already had a structured representation of the story. WebMCP gave me a way to expose that meaning directly to browser agents. Without something like WebMCP, an agent interacting with a creative app would often have to inspect the page, understand the UI, find the correct buttons, and infer what the visible text means. That is possible, but it is a very indirect way of working with the product. In Fenoa, the page can expose semantic tools instead. The current WebMCP tools are: Tool What it does get_branch_state Reads the current remix and its story state get_episode Reads one episode together with its version and relevant constraints update_episode Updates an existing episode move_episode Changes episode order add_branch_character Adds a character specifically to the current remix set_story_constraint Adds a constraint that the story should respect update_branch_rule Adds, changes, or removes a branch-specific rule Publishing is intentionally not exposed as an agent action. That remains a human decision. A shared story state The part I cared about most was making sure WebMCP was not a completely separate automation layer. Fenoa has three different ways a story can change: the human editor the built-in Creative Partner a WebMCP client All three work on the same underlying story state. For example, a person can edit Episode 1 manually and add a story constraint. A WebMCP client can then read the branch and see that latest state. It can read Episode 2, including its current version and relevant constraints. It can then update Episode 2. The Remix Studio reflects the change because the WebMCP action is modifying the same real branch that the human is working on. There is no separate copy of the story created just for the agent. That was one of the main architectural goals of the project. How we built it Fenoa is built with Next.js, React, and TypeScript. Firebase is used for: authentication Firestore realtime data Cloud Storage production hosting Firestore realtime listeners are especially useful inside Remix Studio because changes can appear without requiring the user to manually reload the story.
