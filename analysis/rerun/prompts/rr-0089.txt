Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

When promises break, Advocate acts. Like 1 Comment Story Updates Inspiration A contract can tell you exactly what you are owed. That doesn't mean getting it is easy. When an obligation is missed, the person on the other side suddenly has another job: find the right clause, verify the breach, calculate the remedy, prepare the notice, submit the action, and keep enough evidence to prove what happened afterward. AI can already explain a contract. We wanted to see if the browser could do the harder part: turn the obligation into action. But that immediately created a second question. If an agent can take consequential actions on your behalf, where should its authority stop? That question became Advocate. We built Advocate to let an agent do the tedious work of investigating and preparing an enforcement action, while reserving the final consequential decision for the human. What it does Advocate is a browser-native WebMCP enforcement simulation. Our demo starts with a contract requiring an approved invoice to be settled within 15 calendar days. The invoice has remained unpaid for another 32 days, with $12,840 in principal at stake. From there, Advocate runs one complete workflow: Contract → Entitlement → Approval → Action → Receipt The website exposes four WebMCP tools: fetch_contract_clause(clause_id) Finds the controlling contractual obligation. compute_statutory_penalty(jurisdiction, delay_days, base_amount) Calculates the simulated entitlement from structured claim data. generate_enforceable_demand_notice(claim_payload) Prepares the action the agent intends to take. file_dispute_record(action_id, proof_hash) Executes the simulated filing after authorization. The first part can happen autonomously. Advocate can inspect the contract, determine the breach, calculate the claim, and prepare the next step without repeatedly interrupting the user. Then it stops. Immediately before notice generation and filing, Advocate requires explicit human authorization. That approval generates a SHA-256 proof tied to the exact execution intent, timestamp, and nonce. Only after that authorization can the filing continue. The completed run produces a receipt containing the action ID, filing timestamp, claim hash, authorization proof hash, statutory citation used by the simulation, ledger sequence, and final receipt hash. So Advocate doesn't end with: "The agent says it did it." It ends with a record of what the user approved and what the system executed. How we built it The most important technical decision was to build the workflow around WebMCP instead of browser automation. A traditional browser agent has to inspect a page, guess which DOM elements matter, click through the interface, and hope the website has not changed. With WebMCP, Advocate exposes the underlying capabilities directly as typed tools. Each of our four tools has a JSON schema defining exactly what the agent can provide and what operation the website will perform. We register those tools against the current document.modelContext WebMCP producer API, with a compatibility path for the earlier navigator.modelContext surface. We deliberately did not create one giant enforce_contract() tool. Splitting the workflow into four tools makes every transition visible: evidence → calculation → preparation → execution It also gives the website a natural place to apply authorization before the consequential operation. Every invocation feeds Advocate's telemetry stream with schema validation, typed inputs, execution state, outputs or errors, and latency. Human authorization The approval step is separate from the agent's reasoning. When the user approves the proposed enforcement action, Advocate creates a SHA-256 proof from the execution intent, timestamp, and nonce. Like Comment Story Updates tuto 3d map map home login Inspiration Wildfires evolve quickly, while response teams must coordinate people, resources, weather data, and evacuation decisions under pressure. I wanted to explore how AI could support incident commanders without replacing their judgment. What it does FireNow is a real-time wildfire simulation and decision-support web app. It helps teams visualize a scenario, simulate fire behavior, compare response strategies, prepare tactical plans, and coordinate resources. AI can read the operational situation and use WebMCP tools to make relevant recommendations. However, it cannot directly commit a response plan: every proposed plan stays reversible until a human operator reviews and approves it. How I built it I built FireNow as a modern web application with React, TypeScript, MapLibre, and a local wildfire simulation engine. The interactive map displays fire progression, weather conditions, available units, threatened areas, and proposed interventions. I created 21 WebMCP tools with structured JSON inputs and outputs. These tools let an AI agent inspect the situation, list resources, run simulations, compare plans, prepare actions, and request human approval through commit_plan . Plans can also be cancelled with revert_plan . Challenges I faced The main challenge was designing a useful human-AI workflow without giving AI uncontrolled operational authority. I solved this with a staged-plan model: AI can analyze, simulate, and prepare actions, but a human must validate the final plan. Another challenge was making the WebMCP integration clear and robust across different browser environments. I focused on precise tool schemas, structured responses, meaningful errors, and a visible interface that explains the current tool status. What I learned I learned that the most valuable AI experiences are not fully autonomous. In high-stakes situations, AI should make complex information easier to understand, compare options, and reduce workload—while humans remain accountable for final decisions. Like 1 Comment Story Updates 3-in-the-loop-human-agent-research-workbench how-it-works human-approve-reject-retry-sourcing-method human-approved-artifact-ready flow-chart Inspiration Three in the Loop began with a practical question: what should research look like when a human, an agent, and a website work together in the same live workspace? We began with the WebMCP specification, Chrome developer and agent/tool security guidance, OpenAI developer demonstrations, community/practitioner demonstrations, and repeated internal dogfooding. Together, those sources made the website-declared tool model concrete. Our product question was what should remain under human control. Research was the test case we kept returning to. It rewards speed in gathering and punishes speed in judging. So we built the smallest workbench that could test the boundary between useful research delegation and human evidence judgment. Repeated dogfooding refined that boundary until it matched the workflow. What it does Three in the Loop is for researchers, analysts, and technical teams doing fast-moving evidence-based research where recency, authority, and provenance matter. It is a research workspace shared by a person and a WebMCP-enabled agent in the same live browser workspace: Human defines → Agent researches → Human curates → Agent synthesizes → Human approves You set the research question, audience, and evidence limit. The agent reads the workspace, searches OpenAlex, inspects sources, and proposes evidence. Then it stops. You accept or reject each proposal in the Workbench and control evidence membership. The agent drafts an Evidence Brief whose findings may cite only human-accepted evidence. You edit and review the brief, mark it reviewed, approve it, and download the approved Markdown. The Research Cycle shows whose turn it is at every stage. A WebMCP activity readout records real tool calls as they land, so agent work is visible without exposing private reasoning. The application embeds no model and makes no OpenAI API calls; intelligence comes from a compatible external agent using the site’s bounded tool surface. Why WebMCP The interesting question was never whether an agent can search. It was which operations the site should expose as structured tools and which decisions should remain in the human workflow. WebMCP lets the site declare that boundary on its structured tool surface. Three in the Loop exposes exactly five tools: get_research_workspace search_sources get_source_details propose_evidence draft_evidence_brief Accepting evidence and approving the brief are deliberately absent from the WebMCP tool surface. They are buttons, not tools. For the operations the site does expose, the agent can use structured calls instead of scraping the interface or imitating human clicks. Both actors work against the same bounded browser workspace. It is the same page, with the turn changing hands. Challenges The hard problem was not building tools. It was deciding where useful delegation should stop. We began with read-only tools and added exactly two state-changing operations when the workflow needed them: propose_evidence can stage a proposal, and draft_evidence_brief can place or replace a review-required draft. Evidence acceptance or rejection, evidence membership, brief editing and review, and final approval remain outside the WebMCP tool surface. That boundary looks obvious in hindsight. It took repeated use to find it. Two smaller problems followed. The site cannot know that a person has spoken to an agent or that the agent is thinking, so it only reports AGENT WORK IN PROGRESS after a real WebMCP call lands in the current stage. And persistent rehearsal state kept reviving old missions, so the workspace now uses session-scoped browser storage: same-tab refreshes survive, while a new browser session starts clean. What we learned We began by treating the tool as the main unit of WebMCP design: name it well, type it well, keep it narrow. That is necessary. It is not what made the product work. What made it work was the handoff. The agent works until evidence selection returns control to the human. The human changes the evidence set. The agent continues from that decision, not from scratch, and drafts from the accepted evidence. The human reviews and signs off. Each time we clarified one of those transitions, the product became simpler and more useful. Looking at tools in isolation never explained the workflow as clearly as the handoffs did. Next time, we would design the journey between the person, the agent, and the page first; the tool set should follow from that journey. The final product does not try to show how much the agent can do alone. It shows how clear the responsibility is at every step. What's next The application is frozen for submission. What follows is evaluation before expansion. Planned assurance work includes deterministic checks of workflow invariants, WebMCP registration and cancellation lifecycle testing, response and serialized-output measurement, model-facing indirect prompt-injection evaluations, browser-agent evaluations of human-authority boundaries, and adversarial retesting after approved hardening. Product directions remain open too: richer evidence comparison without a fake credibility score, additional structured research providers, reusable research sessions, and collaboration. Expansion follows evidence from the evaluations while preserving the principle that made the product useful: The agent gathers. You decide what counts.
