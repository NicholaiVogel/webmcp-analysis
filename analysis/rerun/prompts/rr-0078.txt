## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

sums.

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.

Inspiration Smart glasses usually come bundled with a vendor-specific operating system, assistant, and app ecosystem. That creates a strange mismatch: the assistant on the glasses often knows less about the user than the agent they already use every day. WebHUD flips that model. The glasses become a display, the web page becomes the adaptive interface, and the user keeps their preferred agent, memory, apps, and language. What it does WebHUD is an interactive WebMCP-enabled heads-up display. A WebMCP-capable agent supplies structured data and the user's purpose; WebHUD chooses the interface that fits the current context. The same venue comparison becomes: a wide comparison table on desktop; focused, swipeable cards in a simulated glasses lens. That reflow happens locally without another agent call. People and agents co-drive the same surface: voice expresses intent; keyboard, touch, a Bluetooth ring, or a locally processed palm gesture changes focus; surface_get_view_state tells the agent what the user is currently looking at, enabling references such as “this one.” WebHUD can present calendars, email decks, documents, images, people, choices, comparisons, triage queues, maps, and walking routes. Why WebMCP WebMCP is central to the product rather than an added integration. The page registers structured tools through document.modelContext.registerTool , with a legacy navigator.modelContext fallback. The main smart-responsive contract is surface_present . The agent declares one of six purposes— glance , browse , inspect , compare , choose , or triage —and provides semantic items. WebHUD maps that request to an appropriate renderer for desktop, phone, or glasses. Tool registration is dynamic. For example, map_show_route exists only while a compatible map is active. The page emits tool changes as capabilities appear and disappear, reducing irrelevant or unusable actions. Every presentation call returns a receipt describing what was rendered, giving the agent reliable feedback instead of forcing it to guess what appeared. Better human-agent collaboration Without WebHUD, the user must repeatedly describe which item they mean or ask the agent to navigate one step at a time. With WebHUD, the human can swipe to an email or venue and then speak naturally. Gesture supplies context; voice supplies intent. This makes small displays practical without forcing every interaction through speech. Privacy and safety Camera frames stay inside the browser tab and are processed locally. View-state responses expose identifiers and titles rather than email bodies or image pixels. Map location is supplied explicitly by the user; the page does not read device GPS. Sensitive actions remain agent-controlled and human-confirmed. WebHUD has no application backend. How it was built WebHUD is a static TypeScript and Vite application deployed using Cloudflare Workers static assets. Key components include: WebMCP registration and dynamic re-registration; centralized surface and focus state; desktop, phone, and glasses renderers; keyboard, ring/controller, touch, and palm-input adapters; Leaflet maps with walking routes and fallback estimates; vendored MediaPipe assets for local hand tracking; automated tests and GitHub Actions verification.
