# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Edit live websites with your team and a browser agent. Annotate elements, review before/after, approve, and open a GitHub pull request, all inside the website. Cool, huh?! 😎 Like Comment Story Updates Inspiration I was heavily inspired by React Grab by Aiden Bai for this project, but I wanted to make it such that the live prod website could be malleable by anyone on the team who has suggestions and who probably don't know how to use GitHub or Figma or an IDE to make edits. What it does MetaEdit turns a live website into a shared review space. A visitor opens the normal site. A collaborator adds metaedit. to the hostname, enters the shared demo token, and can click an element or draw a freeform region over several elements. A WebMCP-capable browser agent can read those annotations, inspect the selected UI, and propose a preview-only revision. Collaborators see the request, the proposed result, reactions, approvals, and history together. The eye control switches between the current page and the proposed result. Upon approval of those changes, they can publish a pull request (PR). Under the hood, MetaEdit creates a GitHub branch, commits the revision evidence, and opens a PR. The live site is not changed directly. How I built it This is a React/Vinext app served by a Cloudflare Worker. Cloudflare D1 stores annotations, revisions, approvals, and activity. A Durable Object keeps presence and page-space cursor positions live over WebSockets. The page registers a small set of WebMCP tools through document.modelContext , so an agent can work from the shared page context without cloning the repository. The publish path uses the GitHub REST API and keeps the edit contract narrow: text, style, or visibility changes in the selected target. The app was prompted from start to finish in Codex as Codex has always been my go-to tool. Challenges and lessons Honestly, I was very close to overengineering the entire thing. I had to take control of the model and decide what I wanted for the MVP. It was also kind of harder trying to juggle multiple free accounts to get this up and running. Keep the reason. Change the store. Like Comment Story Updates Decision Receipt: explain the winner, losses, accepted trade-off, and counterfactual. One Question Engine: ask the smallest human-owned question that can change first place. Common Room: import the checksum-bound Passport and rank 24 samples down to three. Form House: capture and edit explicit evidence before export. Answer reversal: H01 flips the winner while the carried evidence stays visible. Inspiration Shopping agents can search faster than people, but speed does not solve the harder problem: preferences are fragmented across stores, and recommendations rarely show which trade-off decided the outcome. We wanted an agent that remembers only what a person explicitly approved—and knows when to stop and ask. What it does Decision Passport is a two-store WebMCP journey. At Form House , a person records why a sample chair was a yes, maybe, or no. The agent turns those explicit reasons into an editable decision-passport-v1 ; the person can correct or remove any rule before export. The agent carries that checksum-bound envelope to Common Room , where it reduces 24 fictional sample chairs to three evidence-backed options. A deterministic One Question Engine simulates both sides of the unresolved trade-off and asks the smallest question whose answer can change first place. The final Decision Receipt explains why the winner won, why the alternatives lost, which trade-off was accepted, and what would reverse the result. Why WebMCP is the right interface WebMCP is the product boundary, not a decorative integration. It lets the agent operate each store's live, inspectable state and carry an exact user-approved object across origins. Dynamic registration exposes only the next valid tool. Tool annotations distinguish read-only operations and untrusted text. The same E01 – E04 evidence trace remains visible from the corrected rule, through checksum handoff and shortlist, to one human-owned H01 answer and the final receipt. People stay in control of meaning; the agent handles the tedious transfer and comparison work. How we built it We used React, TypeScript, Vinext, Tailwind CSS, Zod, and the WebMCP imperative API. Nine single-purpose tools span two store-specific deployments. Form House changes its exposed tool set as evidence becomes reviewable; Common Room exposes exactly one next tool at a time. Strict Zod contracts and a deterministic checksum validate transferred data. Scoring, hinge simulation, ranking, and receipt generation are deterministic, so judges can reproduce the same result without an API key, model call, account, or live commerce data. Challenges we ran into The central design challenge was preserving human agency without reducing the experience to a chatbot. Every preference needed to remain traceable to an explicit statement. The final question also had to be genuinely consequential, so the engine simulates both answers and asks only when the winner changes. Technically, we kept every tool bounded, every state reproducible offline, and the two origins cleanly separated while preserving one coherent visual protocol. Accomplishments that we're proud of A complete two-store WebMCP journey with nine bounded tools A visible, editable, portable decision contract A question whose two answers provably produce different winners A deterministic receipt with a counterfactual Responsive, keyboard-visible, reduced-motion-aware interfaces No login, payment, tracking, browser history, hidden behavioral inference, or model API required A public 77-second captioned demo of the working flow What we learned Agents become more trustworthy when their action space shrinks as the task progresses. Portable context is also more useful when it is explicit, editable, checksum-bound, and visibly distinct from the one decision that remains human-owned. What's next The hackathon prototype intentionally stays narrow. A future version could standardize portable decision contracts across participating merchants and add other considered-purchase categories while preserving explicit consent, source evidence, and the human-owned decision hinge.
