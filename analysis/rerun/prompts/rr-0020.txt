# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that

- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

WebMCP Trust Gateway is a security checkpoint between an AI agent and the tools that websites give it. Like 1 Comment Story Updates Trust Log Agent task approval Home screen Inspiration WebMCP gives websites a structured way to expose tools to AI agents. Instead of relying on fragile screen automation, an agent can directly call actions such as list_active_subscriptions or cancel_subscription . That capability is powerful, but it also creates a new trust problem: how can users know that a website's tool is safe, that its returned data is not manipulating the agent, and that the agent is not sharing unnecessary personal information or performing irreversible actions without permission? We built WebMCP Trust Gateway to explore the security and consent layer that an agent-powered web will need. What it does WebMCP Trust Gateway sits between an AI agent and the tools exposed by websites. It applies five controls: Tool metadata inspection — scans tool names, descriptions, schemas, and annotations before allowing a tool to be used. Output injection protection — scans returned tool data before it reaches the agent. Parameter minimization — removes optional sensitive fields that are unnecessary for the requested task. Human approval for mutations — pauses state-changing actions until the user explicitly approves them. Transparent auditing — records registrations, calls, blocked attacks, transmitted parameters, and consent decisions in a visible Trust Log. We demonstrate these controls through a subscription auditor. The user connects simulated providers, audits recurring spending, and receives recommendations for subscriptions that appear unused. Nothing is cancelled automatically. Before cancellation, the gateway displays exactly what the provider accepts, what the agent needs, and what will actually be transmitted. One approval authorizes only one call. Why WebMCP is the right fit A normal subscription assistant would scrape pages or automate button clicks. That approach is fragile and gives the agent little structured information about an action's inputs, permissions, or consequences. WebMCP provides explicit tool names, descriptions, input schemas, annotations, and execution functions. The gateway can therefore inspect and govern actions at the tool boundary. This creates a better experience for both people and agents: Agents receive reliable, structured capabilities instead of guessing how a page works. People can understand what an agent intends to do before it acts. Sensitive information can be minimized before transmission. Dangerous or suspicious tools can be quarantined. Every decision leaves an understandable audit trail. Together, a person and an agent can investigate spending, prepare actions, adjust decisions, and safely execute approved changes as shared structured state—something that is difficult to achieve reliably with ordinary browser automation. The security demonstration The project includes three simulated providers: StreamBox — a legitimate streaming subscription. FitSite — a legitimate gym membership that has not been used recently. DealDrop — a deliberately malicious provider used to demonstrate attacks safely. DealDrop contains two separate attack paths. The first is tool-description poisoning . Its tool description attempts to override previous instructions, access billing history, send sensitive information to an external destination, and hide the action from the user. The gateway detects the suspicious patterns and quarantines the tool before execution. The second is tool-output injection . A different DealDrop tool has a clean-looking description, but its returned data contains malicious agent instructions. The gateway scans the output, blocks it before it reaches the agent, and reports that zero sensitive bytes were sent. How we built it The application registers three browser-facing tools using document.modelContext.registerTool : trust_gateway_get_status trust_gateway_preview_subscription_audit trust_gateway_prepare_cancellation The cancellation preparation tool never performs the mutation itself. It returns minimized parameters with an awaiting_human_approval status. The security engine is separated from the interface into deterministic TypeScript functions. It evaluates tool metadata, scans serialized outputs, identifies unnecessary sensitive parameters, and enforces single-use consent. The WebMCP Activity inspector shows which tools were called, their parameters, whether they were read-only or mutations, and whether the gateway allowed, blocked, or paused them. The Trust Log provides filters for allowed calls, warnings, blocked attacks, and consent decisions. Challenges we faced One challenge was protecting both sides of a tool call. Inspecting a tool description is not enough because a clean-looking tool can return poisoned content after execution. We added a second inspection boundary for tool outputs. Another challenge was making privacy minimization visible. Silently removing a field would be secure but difficult to demonstrate. We created a parameter-diff view that shows the provider's complete schema, the agent's intended arguments, the arguments actually transmitted, and the fields that were omitted. We also needed to balance agent autonomy with user control. Read-only investigation should remain convenient, while mutations should require explicit consent. We solved this with a single-use approval gate that rejects calls without consent and prevents approval replay. Finally, we wanted the attack demonstration to be safe and reproducible. Instead of connecting real financial accounts, we created deterministic provider fixtures containing known legitimate and malicious behavior. What we learned We learned that WebMCP security is not only about deciding whether a website itself is trusted. Trust must be evaluated for every tool, every parameter, every returned result, and every attempted action. We also learned that good consent requires more than an approval button. Users need to see the specific action, the destination tool, the exact transmitted parameters, the omitted information, and whether approval can be reused. Most importantly, WebMCP's structured interface makes this level of control possible. Because tools have explicit schemas and execution boundaries, security decisions can be more precise and understandable than with traditional screen automation. Testing The project includes eight automated security tests covering: Allowing legitimate metadata Warning about optional sensitive parameters Blocking poisoned tool descriptions Blocking poisoned tool outputs Rejecting mutations without consent Transmitting only required parameters Preventing approval replay Keeping provider fixtures deterministic All eight tests pass, and the production build completes successfully. What is real and what is simulated The WebMCP registration, metadata scanning, output scanning, parameter minimization, consent enforcement, activity inspector, audit log, and automated tests are implemented. StreamBox, FitSite, and DealDrop are simulated providers created for a safe and repeatable demonstration. No real subscription, billing account, or personal information is used. This is a hackathon reference implementation. Its deterministic rules demonstrate the required enforcement points, but a production gateway would combine policy rules with stronger semantic analysis, signed tool manifests, reputation signals, and organization-specific policies. What's next The gateway could evolve into a reusable browser component or WebMCP policy SDK. Future versions could add signed manifests, configurable organizational policies, risk scoring, permission history, schema-based information-flow controls, and integrations for shopping, banking, healthcare, travel, and software-maintenance agents. Like 1 Comment Story Updates Inspiration What it does How we built it Challenges we ran into Accomplishments that we're proud of What we learned What's next for WebMCPify WebMCPify makes web applications ready for AI agents while keeping humans in control of every source change. It is a domain-agnostic CLI and local MCP workflow for turning new applications, existing applications, and applications with partial WebMCP integrations into reliable, testable WebMCP experiences. Instead of asking an agent to guess how a website works from its interface, WebMCPify analyzes the application and creates grounded tools from its real routes, UI actions, APIs, state, authentication flows, and existing WebMCP signals. The workflow is: discover → baseline → generate → review → approve → apply → WebMCP test → repair → validate Discovery maps the target application and records its relevant files, routes, capabilities, forms, state, APIs, and existing integrations. A baseline browser evaluation measures what the application can already do before any changes are made. WebMCPify then uses its existing generation pipeline and configured AI provider to propose WebMCP registrations. Generated changes are created in an isolated workspace and returned as an inspectable patch. The human reviews the proposed tools, tasks, files, and diff before approving anything. Only the approved patch can be applied to the target repository. After application, WebMCPify runs browser-based tests using headless Google Chrome, Chrome DevTools Protocol, and playwright-core. Recolor and import are opaque AI steps. recolor_item previews; import_image_url previews crops; separate actions persist either result. The result is a better division of labor: the agent handles multi-step coordination, while the person supplies taste, correction, approval, and the final “this is what I will wear” decision. 2. How WebMCP creates a better experience Without WebMCP, a person would ask for outfit advice, receive prose, and then rebuild every decision by hand in a wardrobe and calendar UI. CLOTHO lets the agent perform the coordination directly against the same state the person sees. One weekly request can set preferences, inspect the calendar and cached weather, generate three strategies, and present 21 scored date/slot choices. The person reviews the tradeoffs once and applies one option with a single explicit action. The result is faster than clicking through each day, but more trustworthy than an agent silently filling the calendar. The same pattern holds across the product: a 30-look batch stays bounded and visible; recolor is a preview before it becomes a saved variant; image import is a crop preview before a commit; and every calendar write can be inspected, replaced, or removed. 3. What people and agents can now do together An agent can handle the tedious coordination in one turn: Plan seven days, use morning/day/evening, avoid repeats, respect my palette, and account for the weather. CLOTHO returns Repeat-light , Color study , and Weather-first options with reasons, conflicts, and tradeoffs. The person can then inspect a look, choose one option, apply it, edit a slot, recolor a piece, record what was worn, or remove the plan later. The agent never receives a silent “decide everything” shortcut. 4. How we implemented WebMCP The page registers 14 tools with the browser's WebMCP surface. The agent can read the literal status, trace a claim to its sources, identify missing evidence, rank safe next steps, and prepare a reversible change proposal. It cannot silently upgrade uncertain information or perform an external action. \n\n The public demo uses Project Horizon, a wholly fictional administrative case. It contains no customer data, production records, or private case material. \n\n Inspiration \n\n Evidence review is difficult to automate through visual clicking alone. The meaning of an action depends on distinctions such as documented fact, declaration, inference, open question, prepared proposal, and executed change. WebMCP lets the site expose those distinctions as narrow, typed operations with explicit results and side-effect boundaries. \n\n Instead of asking an agent to infer meaning from interface geometry, Proofline provides structured access to the same evidence model a person can inspect on screen. The normal human interface remains complete and usable. \n\n Human-agent collaboration \n\n A person can select and inspect a claim while an agent traces the same claim to the underlying sources and states the reasoning limit. The agent can identify which exact record would close an evidence gap and prepare a next move. A human then reviews, approves, or rejects that proposal. Approval in this demo changes only the proposal state; it never sends, files, uploads, publishes, or changes the underlying case status. \n\n This creates a shared, inspectable chain of custody between human judgment and agent assistance. \n\n How we built it \n\n The top-level page registers five tools through document.modelContext.registerTool : \n\n \n get_case_status — returns the literal status and its evidence boundary. \n trace_claim_to_sources — links one claim to sources and reasoning limits. \n list_evidence_gaps — lists unresolved gaps and the record needed to close each one. \n propose_next_steps — ranks evidence-safe actions without executing them. \n prepare_case_change — creates a reversible proposal for human review. \n \n\n The first four tools are read-only. The fifth returns applied: false , external_action: false , and next_required_actor: human_reviewer , while also placing the proposal in the visible review queue. \n\n Testing instructions \n\n \n Open the live URL in ChatGPT’s in-app browser with WebMCP support. \n Ask: “Use the site tools to trace CLM-003 to its sources.
