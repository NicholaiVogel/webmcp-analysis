Countersign is the third option - your agent drafts, you countersign. Why this use case is a strong fit for WebMCP The baseline value is obvious: instead of an agent scraping a DOM and hoping the button it clicked was the right one, the site declares an explicit, typed contract. For money, "hoping" is not a strategy. But the deeper fit is a gap in the platform. The published WebMCP IDL has no confirmation or consent primitive. requestUserInteraction() appears in Chrome's own tool-security guidance as a draft idea, but it does not exist in the published spec - I checked the IDL, and cross-party consent management is still an open discussion . So an agent-native app that touches money has to answer that question itself, today, using only the primitives that do exist: AbortSignal , annotations , and ordinary application state. Countersign is a concrete answer rather than a wait for the platform to catch up. What people and agents can do together that was difficult before Hand an agent real financial authority while keeping a hard, site-owned veto on the two steps that actually move money. Sending an invoice and marking one paid always stop and ask. That trade-off barely exists today; it's normally all-or-nothing. Two mechanisms make it inspectable rather than a trust exercise: 1. Tiered confirmation. send_invoice raises a light, single-screen approval - sending is routine. mark_invoice_paid always raises a heavier one, and if the amount the agent reports doesn't match the invoice, the approve button stops saying "Approve" and instead says "Accept $2,400 instead of $3,000." You cannot wave the mismatch through without reading it. Decline, and the tool returns a plain DECLINED - ... string instead of throwing, so the agent reports back honestly rather than silently retrying. 2. Untrusted-content quarantine. One owner-controlled WebMCP contract for the existing web: four read-only tools, governed extensions, deployed live across eleven stacks. Like Comment Story Updates What it is Corsen Context gives an existing website an owner-controlled WebMCP read layer without replacing the human interface. The page registers explicit tools through document.modelContext.registerTool(...) ; every call executes against a bounded, same-origin MCP endpoint (protocol 2025-11-25) and returns canonical public URLs and clean Markdown. Four read-only core tools are shared by every integration: search_site , get_page_content , list_content and get_sitemap . Live flagship: https://webmcp.corsen.ai (WordPress). Source: https://github.com/CorsenAI/corsen-context (MIT). Built by Corsen AI , France. Why WebMCP fits Browser agents currently parse interfaces built for people, guess which page is authoritative, and cannot tell what a site allows them to do. With Corsen Context the website itself exposes a small, typed, owner-selected capability layer. The capabilities live with the page instead of being reverse-engineered from the DOM, and the site owner decides what is exposed and can revoke it without touching the human pages. What people and agents can do together A person states a goal ("compare the editions, tell me what you may buy for me and what I must do myself"). The agent reads the owner's rules, calls the tools and returns grounded answers with sources. Governance is explicit and per product on the flagship store: the ten per-stack editions (9 EUR) carry agentPurchase: allowed : an agent acting for its user may complete the ordinary checkout; the production licence (29 EUR, slug corsen-context ) carries agentPurchase: forbidden with the owner's reason, so the agent hands that URL back to the human; the only write-shaped tool, request_expert_call , is annotated non-read-only and is refused server-side for every agent call ( human_only ) before anything is stored or emailed. The person keeps the decisions; the agent does the reading. How WebMCP is implemented A language-neutral tools.manifest.json declares tool names, JSON schemas and WebMCP annotations ( readOnlyHint , untrustedContentHint ). The generated browser bridge registers each tool with document.modelContext.registerTool(...) and forwards execute() to the same-origin MCP JSON-RPC endpoint; the browser never reimplements a tool and sends no cookies, credentials or API key. A TypeScript core (npm @corsenai/corsen-context 2.0.1 with Next.js and Astro adapters) and an independent PHP implementation (WordPress plugin 1.5.16 on WordPress.org) are checked against the manifest by parity tests. Eleven public deployments run the same four-tool core: the WordPress flagship, Express, Next.js, Astro, static HTML, Ghost, Strapi, Directus, Wagtail, MediaWiki and a Netlify template. A public verifier checks the ten stacks against one SHA-256 contract hash ( 3786c5d0d401cb9862291c9e3903ff0bd35925326b7dbc9be75f15ded2604ef4 ). For a document editor, that means the agent has to figure out what the user is looking at, where content belongs, and what actions are available. \n\n We wanted to try a different approach using WebMCP : let the website expose its actual application state and capabilities as structured tools that an AI agent can call directly. \n\n That became Co/Draft — a document where humans and agents edit together. \n\n The core interaction is deliberately simple. I built Median Viz using LinkedIn demographics to explore a different model Like Comment Story Updates Inspiration One day, while my wife and I were watching a video from USAFacts, she wondered aloud how the animated data visualizations in the video were created. I started explaining the usual process—acquiring and cleaning the data, processing it, and then building dashboards with the right dimensions, filters, and pivots. Halfway through the explanation, I realized it might be easier to just build an example application that shows her how they work. That became Median Viz . I started with a few animated Plotly visualizations—a pie chart, a bar race, and a U.S. map—then turned them into a small web application, open-sourced it on GitHub, and deployed it on Vercel. When the WebMCP Challenge was announced, my cofounder and I were also exploring how to analyze LinkedIn Ad Set demographics for client campaigns. The two ideas suddenly connected. Instead of asking an AI agent to infer what a visualization means from the page alone, what if the application could tell the agent exactly what data, analytical capabilities, constraints, and current state were available? That became the /studio experience in Median Viz: a workspace designed so that humans and agents can understand and work on the same analysis through WebMCP. What it does Data visualization tools are usually built as human-operated dashboards for exploring complex data across different dimensions. They can be powerful, but they are also difficult for AI agents to understand because the agent has to infer which filters, dimensions, metrics, and actions the application actually supports. I built Median Viz Studio using LinkedIn Ad Set demographics as the example domain. Through WebMCP , the application exposes its analytical capabilities directly to ChatGPT. The agent can discover what dimensions are available, understand the current workspace, configure an analysis, apply filters, animate changes over time, and explain the results in plain language. The key idea is that the human and the agent are not working in separate experiences. They operate on the same live workspace . A filter selected by the human immediately becomes context for the agent, while a WebMCP action taken by the agent is reflected in the same controls and visualization the human sees. How we built it Median Viz is a Next.js/React application using Plotly for interactive and animated visualizations. The /studio route models a LinkedIn-style B2B audience analysis workflow using the supported demographic dimensions, including Job Function, Seniority, Industry, Company, Company Size, Region, and others. For the public demo, I use representative LinkedIn B2B audience-performance data for a fictional company, Northstar Media , with metrics such as CPC, CTR, impressions, spend, and conversions. The Studio exposes seven semantic tools through WebMCP : three read-only tools that let the agent inspect the dataset, workspace, and current result, and four guarded mutation tools that let it configure an analysis, apply filters, control animation, or reset the view. These tools operate on the same underlying workspace capabilities used by the human interface rather than manipulating Plotly or DOM elements directly. The application also preserves domain rules. For example, LinkedIn demographic dimensions are reported independently, so the system will reject an invalid request such as comparing Job Function directly with Seniority rather than inventing an unsupported intersection. Time-series animation is represented as shared workspace state, and the Agent Activity panel makes WebMCP-driven changes visible to the user. Challenges we ran into One of the main challenges came directly from a problem we were already thinking about in our startup: how do you keep human and agent actions in sync when both can change the same workspace? I wanted a filter or view selected by the user to immediately become context for the agent, while also making sure an agent action did not overwrite a newer human change. There were also important domain constraints to preserve. LinkedIn demographic dimensions are reported independently, so an analysis such as Job Function × Seniority is not valid. I wanted Median Viz to reject requests the underlying data cannot support rather than letting the agent invent an answer. Similarly, derived metrics such as CPC and CTR need to be calculated from aggregated values rather than by averaging row-level ratios. Finally, because this is a public demo based on a problem we encounter with real customer campaigns, privacy was a hard requirement. The public Studio uses representative demo data and fictional identities , so no real customer information is exposed. A user can change a filter manually, ChatGPT can immediately understand that new state, and an agent action is reflected back in the same visualization and controls. I was also happy with the way animation evolved. The human gets a visual, time-based experience, while the agent gets structured state it can reason over. Taking the project from an experiment, through WebMCP integration, to a deployed application and a working public demo was especially rewarding. An agent works better with structured state and evidence than when it has to infer meaning from a screenshot or DOM. Domain constraints are a feature. Giving an agent explicit boundaries can make it both safer and more useful. Shared state matters more than tool count. The most interesting interactions happened when a human action became immediate context for the agent, and vice versa. Explore better ways to analyze and compare independently reported demographic dimensions without violating the underlying data semantics —for example through side-by-side views, sequential filtering, or coordinated comparisons rather than unsupported intersections. Extend the human-agent collaboration model beyond the demo, including longer analytical workflows where humans and agents progressively refine the same workspace. Like Comment Story Updates Inspiration What it does How we built it Challenges we ran into Accomplishments that we're proud of What we learned What's next for Sigmora Live Relay Inspiration Going live is when creators most need cross-platform promotion—and when they can least afford to leave the stream to edit, rewrite, upload, and check posts. Sigmora Live Relay turns one selected live event into a reviewable 12-second vertical campaign on a shared release board. What it does The page exposes eight narrow WebMCP tools. An agent reads the visible brand and destination context, finds or declares the source live event, drafts the relay, polls generation, revises copy, queues exact destination accounts, releases the human-approved revision, and checks each destination independently. Every tool call updates the same board the creator sees. The consequential checkpoint remains human. Queue items are bound to exact account IDs and one immutable revision. The creator reviews those items in the UI and approves them there; approval is deliberately not exposed as a tool. Any revision invalidates the receipt. Release requires that receipt plus an idempotency key, and partial failure can never be reported as total success. Why WebMCP This is a strong WebMCP fit because the useful context and collaboration live on the open page: current creative state, selected destinations, approval, and receipts. Without WebMCP, an agent must infer buttons and duplicate state. With WebMCP, it uses an explicit contract while the person keeps visual control. People and agents can now share one live workspace: the agent handles multi-step coordination while the creator remains present with the audience and retains authority over publication. How we built it The challenge implementation is framework-free TypeScript built around document.modelContext.registerTool(...), closed JSON Schemas, typed result envelopes, an observable shared controller, page-scoped teardown, a strict HTTP adapter, and a deterministic local provider. The normal manual interface continues to work when WebMCP is absent. The eight tools cover context, source discovery, drafting, job polling, revision, exact destination queuing, approved release, and independent status verification. Unit and end-to-end tests exercise schemas, lifecycle cleanup, revision invalidation, idempotency, partial failure, and the manual fallback. Challenges The hardest design problem was preserving human authority without making the agent workflow brittle. We solved it with an immutable approval receipt bound to an exact revision and destination set, plus clear state transitions visible to both sides. Another challenge was truthful partial failure: each destination receives an independent receipt, so a mixed outcome stays mixed. What we learned WebMCP is most compelling when it is not simply a hidden automation API. The shared page should remain the source of truth, and the tool contract should expose exactly the capabilities that benefit from agent reasoning while keeping consequential consent visible and human. What's next The public reference is intentionally simulated and says so throughout the UI and tool results. Next we would connect the strict provider adapter to real publishing APIs, preserving the same approval, idempotency, readback, and partial-failure guarantees. Tell Prism what a WebMCP is for, then test whether its tools actually deliver. Like Comment Story Updates Prism turns a declared WebMCP purpose into an evidence-backed scorecard. Inspiration What it does How we built it Challenges we ran into Accomplishments that we're proud of What we learned What's next for Prism Inspiration WebMCP evaluation can become a checklist of surface-level signals: did the page register tools, do they have schemas, and can the browser call them? Those checks matter, but they do not answer the product question. A commerce tool set, an editor, and a project workspace need different capabilities and different human-approval boundaries. Prism starts with the job to be done. It evaluates whether a WebMCP implementation covers that journey, whether mutations affect the same state a person sees, and whether consequential decisions remain visible and human-controlled. What it does Prism combines a purpose-aware evaluation dashboard with an open-source, local-first browser companion. A person selects Commerce, Project Operations, Content Editor, or defines a Custom contract. That contract states the intent, expected capabilities, and the action that must remain human-approved. The browser companion then runs on the target page, discovers its live WebMCP tools, executes only selected checks, and records schemas, annotations, timing, and privacy-preserving before-and-after evidence. Prism maps that evidence to four dimensions: purpose coverage; contract quality; observable mutation proof; and runtime hygiene. Every score includes journey-level evidence and a repair that can be tested again. A weak cart mutation, for example, does not merely lose points: Prism explains that the runner could not verify the visible state change and recommends returning a state revision plus a read-back check. Prism is itself a WebMCP app. Its four page-side tools let an agent read the selected contract, switch profiles, run a deterministic evaluation, and read the same score and evidence shown to the person. How we built it The dashboard is React and TypeScript on Vinext, deployed through ChatGPT Sites. Its scoring engine consumes a versioned runner snapshot and keeps the report deterministic and interpretable. The Manifest V3 companion uses the active page's document.modelContext.getTools() and document.modelContext.executeTool() APIs. It runs in the target origin because a hosted iframe or HTTP request cannot truthfully inspect another page's WebMCP tools. It hashes visible before-and-after state, supports an explicit read-back check, and exports only evidence metadata—not page text or tool output. The dashboard registers get_evaluation_context , choose_evaluation_profile , run_sample_evaluation , and get_latest_evaluation with narrow object schemas, annotations, validation, and lifecycle cancellation. The mutation tools update the same React state rendered in the visible interface. Challenges we ran into The hardest design constraint was the browser execution boundary. Cross-origin discovery would have been convenient, but it would also have been misleading. Separating collection from evaluation made the architecture more honest and gave us a useful privacy boundary. Behavioral evidence also needed careful calibration. A DOM digest proves that something visible changed, but not that the semantic change was correct. Prism therefore distinguishes visible-state evidence from stronger tool read-back evidence and does not claim either one proves the target application's human-approval policy. Accomplishments that we're proud of Purpose-specific contracts prevent irrelevant tool count from dominating the score. Every deduction is tied to visible evidence and an actionable repair. The companion is local-first, minimal-permission, and requires a fresh confirmation for mutation checks. Prism's own WebMCP mutations and reads agree with its visible UI. The dashboard, companion, source, tests, and judge guide form one coherent open-source release. What we learned WebMCP quality is not just API design. It is the relationship among intent, page state, agent authority, and the evidence available to a person. The most useful evaluator is therefore not a universal pass/fail scanner; it is a repeatable contract between the product team and the experience they intend to ship. What's next Next, Prism can add reusable contract packs, richer assertions for semantic read-back, shareable evaluation histories, and CI adapters that compare a new snapshot with a reviewed baseline. The same model could support accessibility audits, agent regression testing, and organization-specific approval policies.
