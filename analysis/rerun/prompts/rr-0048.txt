Like Comment Story Updates Inspiration Agents are getting good at acting on the web, but almost every agentic product still asks you to pick one of two shapes. An agent that advises : it talks about your work from a chat panel, and you translate its advice into the application by hand. An agent that operates : it acts through tools or APIs, and you find out afterwards what changed. Both give something up. The first leaves the agent outside the work. The second takes the human out of the loop at exactly the moment the stakes are highest. We wanted to know what a third shape looks like: what if the application itself were the shared surface, where a human and an agent reason about the same problem, and the human keeps authority over what becomes real? That question is what made WebMCP interesting to us. Not as a way to make an existing app agent-compatible, but as a way to let a page say these are the actions that make sense right now — and to have that answer change as the human works. What it does MUTUA demonstrates the model through one focused scenario: software launch recovery . A team is four weeks from a September 30 launch. Chrome’s WebMCP security guide also discusses prompt injection and untrusted tool output as security risks. But we could not find a tool which can test WebMCP tools specifically for these problems. That led us to build Guard Studio. What it does Guard Studio is a security testing workbench for WebMCP tools. You can import a tool by inserting the definition, uploading a JSON file, or providing a hosted URL. Once imported, Guard Studio checks: whether the tool is read-only, write, or sensitive risky or missing schema definitions prompt injection patterns in tool descriptions sensitive-data related instructions suspicious sample outputs overall risk score It also provides a red-team bench where developers may run attack samples such as token exfiltration, obfuscated jailbreaks, poisoned tool descriptions, and silent actions. If it finds a problem, Guard Studio can generate a hardened registerTool() version with a stricter schema, output limits, audit events, and approval checks. We also added a human approval queue. Guard Studio also exposes five WebMCP tools, so an agent can run the audit flow directly. How we built it The frontend is built using React + Vite and deployed on Vercel. The backend is a stateless FastAPI service hosted on Render. We kept the architecture simple. No database and no user accounts. Every request is independent. The frontend registers five WebMCP tools using document.modelContext.registerTool(). If WebMCP isn't available in the browser, or if the backend isn't reachable, the application falls back to a built-in local scanner. For scanning, the production version uses a deterministic pattern-based approach. Currently, we check nine different injection pattern families, including: ignore previous instructions data exfiltration hidden instructions silent actions sensitive-data requests The scanner checks tool descriptions, schemas, and sample payloads. The backend also has an optional model-based mode using Meta Prompt Guard 2 through Hugging Face Transformers. We kept this optional because running the model needs more memory than the free deployment currently provides. For the approval flow, the WebMCP tool’s execute() method returns a Promise. The Promise is completed only after the user clicks Approve or Deny. If there is no response for two minutes, the request is automatically denied. Will You Stay Human? — Heart in the Machine is a Metropolis-inspired moral decision game about that boundary. The agent may assist, explain, and act, but the human must remain responsible for deciding how much authority to delegate. I wanted to turn this abstract question into something people could experience through concrete, everyday situations. What it does The player enters Machine City and meets Futura, an AI agent connected directly to the live game through WebMCP. Across one persistent session, the player encounters four playable dilemmas: writing an apology to someone they hurt; completing homework where AI assistance is permitted; creating a shortlist of job candidates; checking a rapidly spreading claim before sharing it. For every dilemma, the human chooses one of three approaches: MIND — The Machine helps; I decide HAND — I leave it to the Machine HEART — I decide and act The choice is initially tentative. Futura presents a direction-specific reflection and asks the player to consider the other side. The player can still change direction. Only after the human explicitly confirms the decision can its consequence be revealed. Each confirmed choice changes the Human Balance across five dimensions: Convenience Control Connection Freedom Responsibility The Human Balance is not a morality score. It shows what the player kept for themselves and what they handed to the Machine. Why WebMCP A fair criticism of many agent demonstrations is that the AI can simply automate the entire experience. If the agent can also make and confirm the decision, the human role becomes theatrical. Here, that boundary is the product. WebMCP turns the agent into a real participant in the game rather than an external chatbot or a scripted narrator. The agent can: enter Machine City; present the next valid dilemma; read authoritative, structured game state; reflect on the player’s actual tentative selection; reveal the consequence of the decision that was truly confirmed. It would have been easier to expose every interaction as a tool and let the agent complete the entire flow. But that would contradict the project’s central idea. The player could see the available directions but could not clearly understand what they were deciding about. I corrected this by introducing a presentation sub-state inside the existing human-selection phase. The dilemma now receives a dedicated screen with its full context and a clear transition into the choices. This improved the dramaturgy and comprehension without changing the domain state machine or any WebMCP contract. Another challenge was keeping three layers synchronized: the cinematic browser experience; the persistent domain state; the agent’s structured WebMCP view. Revision checks, explicit identifiers, allowed-action lists, and automated contract tests became essential for preventing those layers from drifting apart. Its real value is that an agent can participate in a live web experience through structured capabilities while the application retains authority over state, permissions, and human boundaries. I also learned that domain state and presentation state are not always the same. A technically correct transition can still fail as a human experience if the player is not given enough time and context to understand what is happening. A studio where a person and an AI agent co-create flyers, posters and social posts on a live canvas. Agent-driven through WebMCP tools, images generated on-device via WebGPU. Like Comment Story Updates Inspiration Every design tool is a wall of menus, and every "AI design" demo is a black box that hands you a finished picture. We wanted the third thing: a person and an agent at the same canvas, where the agent does the tedious work and the person keeps the final say. WebMCP made that buildable. A page can declare exactly what an agent may do, so the agent does not have to guess at the UI, and the human's consent can be part of the protocol instead of a dialog bolted on afterwards. What it does WebMCP Design Studio is a live canvas for flyers, posters and social posts. Say "make a spring yard sale flyer, Saturday 8am to 2pm, 14 Orchard Lane" and the agent creates the design, generates the artwork, sets the type and lays it out. Nothing is committed until you approve it. Every edit lands in a pending batch, approve-batch exists as a tool only while there is something to approve, undo appears with it, and a toolchange event fires as they come and go, so any agent can see the moment a human is required. Seventeen tools cover the whole loop: designs, elements, image generation on-device or through the fleet, background removal, restyling, export, memory of your preferences, and a production log that lets the agent tell you what the studio has made this week. A protocol feed shows every registration and call as it happens. How we built it Vite, React and TypeScript, with a fabric.js canvas. One ToolRegistry reconciles the design state onto document.modelContext when the native API is present and onto a spec-shaped polyfill when it is not, so the same tools work in ChatGPT's browser, in Chrome with the WebMCP flag, and everywhere else. The studio's own in-page agent drives the page through the same getTools and executeTool surface an external agent would, so the WebMCP surface is exercised by real traffic. The consent controls are also registered declaratively as a , the spec's second path. Images come from an on-device WebGPU model or from Sana on our fleet through the studio's own proxy; text comes from Bonsai 27B with an automatic fallback lane. It deploys as a static site on GitHub Pages with 205 tests behind it. Challenges we ran into Making consent a protocol object rather than a UI element took the most design work: the batch, the disappearing tools and the toolchange events had to agree exactly. The fleet side fought back too. Under load, the 27B text model crashed and the image lane timed out behind Cloudflare's 100-second cut, so we built a second text lane with automatic fallback, moved image generation onto a resident GPU path, and set honest timeouts everywhere. The demo itself was re-shot after the first cut used artwork from an unrelated production pack instead of the flyers the studio actually makes. Accomplishments that we're proud of The consent boundary lives in the tool surface itself, so any WebMCP agent inherits it. The app eats its own protocol. Image generation runs fully on-device when the browser can do it. And the studio is used for real work: its production log is a week of actual pieces, readable by the agent through a tool. What we learned Declaring capabilities changes how you design the app. Once every action was a tool with a schema, the pending batch and the approve step became obvious, and the UI got simpler rather than more crowded. We also learned that a demo built for agents is judged in the agent's environment: cross-origin, preflight and timeout behavior matter as much as the tools. What's next for WebMCP Design Studio Print-ready export with bleed, richer declarative tools for the whole rail, a daily production routine that keeps the log growing on its own, and the studio as a room inside the Aitherium playground, where the same agent that drafts your flyer can also hand it to your community.
