# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

LingoMargin turns any text into a personalized language lesson where learners and agents collaborate through contextual annotations, grammar missions, and review practice powered by WebMCP. Like Comment Story Updates Inspiration Language learners increasingly use AI to understand given texts, but the usual workflow is fragmented: read in one place, copy a confusing sentence into chat, receive an explanation elsewhere, and manually save useful vocabulary. I wanted to explore a more natural model where the learner and agent share the same reading workspace. The learner stays focused on the text while the agent understands the current passage, proficiency level, annotations, exercises, and learning progress. What LingoMargin does LingoMargin turns any passage into an interactive, level-appropriate language lesson. Learners can paste their own text or request a new passage by specifying a language, level, length, and topic. They can select unfamiliar phrases, save vocabulary, inspect contextual explanations, complete Grammar Detective missions, review mistakes, and export learning material. The agent can directly update the workspace by: Adding selective vocabulary, grammar, and cultural annotations Creating hidden-answer Grammar Detective missions Generating contextual review activities Leaving feedback in the margin Producing new level-appropriate passages Every agent action creates a visible change in the interface. The learner decides what to study and can undo passage replacements when needed. How I built it LingoMargin is built with React, TypeScript, Vinext, and WebMCP, and is deployed using ChatGPT Sites. The application registers six tools through document.modelContext.registerTool() : get_learning_context annotate_text create_grammar_mission create_activity add_feedback create_generated_passage These tools give the agent structured access to the current lesson and allow it to make precise, verifiable updates. Mutating tools return confirmation describing what changed, while the learner immediately sees the result in the passage or margin. The workspace is stored locally in the browser. Passage content and learning state are shared with an agent only when the learner asks for help through a WebMCP tool. Challenges The main challenge was designing genuine human-agent collaboration instead of attaching a chatbot to a reading app. Annotations had to remain anchored to exact character ranges while preventing duplicates and overlaps. Grammar missions needed to accept the complete intended phrase without incorrectly accepting tiny fragments. Agent-generated activities also required validation so malformed exercises could not enter the interface. Another challenge was preserving learner control. Replacing a passage clears lesson-specific state, so I added confirmation, recovery, and one-step undo. I also had to make the relationship between the page and adjacent agent chat understandable without filling the interface with technical WebMCP terminology. Finally, the workspace needed to remain usable on mobile, where the mission must appear before a potentially long passage. What I learned WebMCP changes interface design, not just integration code. A useful agent-native application needs carefully scoped tools, observable outcomes, reliable validation, and clear boundaries between human and agent responsibilities. The best result came from giving each participant a distinct role: the agent analyzes and adapts the lesson, while the learner notices, selects, answers, and decides what becomes knowledge. An agent-native search and rescue incident board. Your agent plans. The incident commander decides. Like Comment Story Updates Inspiration Wilderness search and rescue is run by volunteers on whiteboards. The first hours decide most outcomes, and the incident commander is juggling a probability map, six tired teams, fading daylight, weather, and a radio. The math of search theory (probability of area, probability of detection, expected gain) has been understood for decades, but nobody at a trailhead at dusk has time to run it. The National Missing and Unidentified Persons System listed over 26,000 active missing-person cases in early 2026, and the National Park Service alone runs thousands of searches a year. That is exactly the shape of problem where a human and an agent are better together than either alone. The agent has breadth: it can read every segment and every team and run the numbers in seconds. The human has judgment: they can see the terrain, hear the radio, and know which volunteer is done for the day. WebMCP is the first thing that lets both of them work on the same live board. Why this use case fits WebMCP A chatbot cannot do this job. The state that matters is on the page: which segments have been searched, at what coverage, who is where, what is staged and what is approved. With WebMCP the agent reads that state directly through typed tools instead of screenshots, its actions render on the board instantly, and the human can intervene at any moment. The agent sees the new state on its next call. It also fits because the domain demands a hard line between advising and acting. WebMCP tools run in the page, so the page decides what the agent can do and when. GridBoard uses that to enforce a rule no prompt could: there is no tool that dispatches a team. What humans and agents can do together The commander says "we lost daylight, replan the east side." The agent reads the briefing, ranks segments by expected gain for each available team, and stages two assignment proposals with rationale, estimated POD and expected gain. The commander approves one, rejects one with a reason, and both decisions are logged with who proposed and who decided. The commander drags their attention to a segment and says "Ground 2 found a blue glove here." The agent logs the clue in the focused segment under Ground 2's name. A team radios in. The commander marks them returning; a debrief_team tool appears for the agent, it records the coverage, and remaining probability shifts across the whole map. The agent hits a call it should not make alone ("hold the drone for night thermal, or launch now?") and asks the commander a question with options. Only the human can answer it. Two people can bring two agents. A planning agent may propose for any team. A team lead's agent, checked in for Ground 2, can only propose for Ground 2. None of this was possible before: an agent that can run the search math on the live board, whose every action is attributed and reversible, and that structurally cannot dispatch. How WebMCP is implemented All tools are registered with document.modelContext.registerTool in src/tools.js , and the registered set is reconciled against board state after every change. Three classes. Eight read tools ( readOnlyHint: true ) so the agent never clicks through the UI to read; read_log also carries untrustedContentHint because log entries are field reports written by other people and agents. One navigation tool, focus_segment . Write tools appear only after check_in with a name and role, and every write is attributed to that name. Capability follows state. check_in exists only while no agent is checked in. mark_clue exists only while a segment is focused, so a clue lands in the right place. withdraw_proposal exists only while a proposal is staged. debrief_team exists only while a team is returning. approve_proposal never exists. Staged, then approved. propose_assignment validates the request (team and segment exist, rationale is at least a sentence, the team is not spent, no duplicate for that team), computes estimated POD and expected gain, and stages a card. The team does not move until the commander's Approve button. Agent experience. Inputs are natural-language names ("K9 Juno", "Pika Overlook"), not ids. Errors come back as { ok, error, hint } so the agent self-corrects: a wrong team name returns the list of known teams. The Site tools tab shows the human the live tool list, flashes tools as they appear, and lists which tools are locked and why. Verified in the real thing. npm test covers the engine and the registration logic. test/e2e-chrome.mjs launches real Chrome with WebMCP enabled, confirms the browser accepted the registrations (it rejects a duplicate name with InvalidStateError ), drives the tools as an agent would, and checks that the tool set changes with board state and that a proposal never moves a team. Built with Vanilla JavaScript, SVG, Vite, Vercel. No framework, no backend, no API keys. Search theory: Bayesian POA update, cumulative POD, expected gain. What's next A small realtime backend so a commander, a planner and three team leads can bring their own agents to one shared board. Import of real segment polygons from CalTopo/SARTopo. Night operations mode with thermal UAV constraints.
