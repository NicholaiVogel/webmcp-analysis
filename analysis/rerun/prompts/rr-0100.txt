# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Most AI browser agents today are essentially screen-scrapers: they take screenshots, guess button coordinates, or try to parse messy DOM trees. That approach is slow, breaks the moment a CSS class changes, and fails completely when interacting with a canvas element or stateful WebGL scenes. When the W3C published the WebMCP draft, we saw a much cleaner path: expose typed, client-side functions directly from the browser runtime to the model. Instead of treating the web app like a static document an external bot has to inspect from the outside, the user and the agent can mutate the exact same application state in real time, whether that means extruding a 3D CAD mesh at 60 FPS or running financial risk analytics without backend roundtrips. The showcase is built with Angular 22, Three.js, and Bun, organized into four primary layers: First, Angular 22 signals and directives. Rather than wrapping tools in heavy abstractions, we built directives like webmcpTool that bind directly to reactive signals. When a user adjusts an input or the agent calls a tool, state updates synchronously with zero change-detection penalty. Second, the Three.js spatial engine and push-pull extrusion. We built a SceneActionBus to decouple asynchronous tool promises from the Three.js render loop. The agent can draw planar 2D profiles and extrude solid 3D geometry along the face normal vector, while camera movements interpolate across spherical coordinates for smooth transitions. The agent can also call a screenshot tool to pull the raw WebGL drawing buffer and visually verify its own modifications. Third, in-browser memory with IndexedDB and BM25. Rather than standing up an external vector database, we built an episodic memory store on IndexedDB paired with a pure TypeScript BM25 search implementation. Relevance scoring runs standard Robertson-Spärck Jones IDF directly on the client using tuned parameters (k1 = 1.2 and b = 0.75), allowing the agent to retrieve user preferences and historical actions in sub-millisecond lookups completely offline. Fourth, a dynamic SubAgents SDK and multi-domain business intelligence. Injecting dozens of tool schemas into every prompt quickly blew through token budgets. We created an SDK that dynamically filters tools per domain, allowing the main agent to delegate tasks to specialized workers (such as analytics or 3D specialists). These workers run isolated multi-turn loops, compute normalized anomaly risk scores across metrics, and return concise execution receipts signed with a client-side SHA-256 hash. We tackled several technical hurdles along the way. Calling Three.js mutations straight out of asynchronous HTTP promises caused frame drops, so we created a queue in SceneActionBus that holds incoming tool commands and executes them strictly on animation frame ticks. Exposing every tool simultaneously caused models to hallucinate arguments or hit context caps; scoping tools dynamically by route and delegating to subagents cut token usage by roughly 85%. Additionally, server-side rendering under Node and Bun crashed whenever code referenced browser globals like window, navigator, or IndexedDB. We resolved this by building an in-memory emulator (WebMcpEmulator) that activates during SSR and in browsers lacking native WebMCP support, eliminating hydration mismatches. Through this process, we achieved 511 unit and integration tests passing on Bun in under 1.5 seconds. The project demonstrated that agent autonomy does not require a heavy backend or remote vector database; native browser primitives like IndexedDB, WebGL, and Signals are remarkably capable when wired directly to function calling. Furthermore, Angular's dependency injection model fits WebMCP tool registration naturally by treating tools as standard injectable providers. Moving forward, our next steps include publishing the webmcp-angular library as an open-source npm package, adding WebXR support to let agents interact with 3D scenes in headsets like Apple Vision Pro and Meta Quest, and compiling OpenCASCADE geometry routines to WebAssembly for true solid modeling directly in the browser. Let your agent see everything and spend nothing — WebMCP tools that read your ledger and audit trail, with no route back to move money. Like Comment Story Updates Inspiration The premise: the agent is assumed compromised. Not "the agent might make a mistake" — assumed compromised, the same way you'd design a system if you knew an adversary was already inside it. Every design decision in Pocket Change follows from that one sentence: if you're going to hand an AI agent a wallet, the system has to hold up even when the agent itself is the threat, not just when it's well-behaved. What it does Pocket Change gives an AI agent bounded, revocable spending authority — enough to actually get things done, never enough to do real damage. A person authorises a mandate : a ceiling, a purpose, an expiry. The agent can act only within that mandate. Every payment request passes through a gateway enforcing nine deterministic checks — depth, budget floor, fan-out, per-node budget, cycle detection, conservation of spend, and a hard rail cap — none of which a model can argue its way around, including ours. Every decision (allowed, denied, or escalated to a human) is written to a hash-linked audit log, so the log can prove nothing was altered after the fact — not that it was never rewritten wholesale, but that no entry was quietly edited in place. Payments run through Razorpay in test mode — never real money — while the authority model itself is designed to be real. For this hackathon, the console also exposes six WebMCP tools , so an agent working through the browser can read everything about its own authority — spend status, counterparty history, the audit trail, the shape of an in-progress run, which safety layers are actually enforcing right now — without ever being handed a tool that can move money, mint a token, widen a mandate, or approve a held payment. It can look, and it can propose ( draft_requisition , which mints nothing), but the only path to actually spending still runs through a person clicking a button in the console. How we built it Gateway : a FastAPI service enforcing the nine checks server-side, so no client — including the browser console — can bypass them. Reads are public; writes require the demo token. Capability tokens : Biscuit tokens carry attenuated authority, so a delegated task can only ever have equal or narrower permissions than its parent, never wider. Decomposition/funnel model : complex requests get broken into a tree of smaller tasks, each with its own budget, depth limit, and fan-out cap — the console renders this tree live over SSE. Console frontend : a five-pane live view (via SSE) of an in-progress run, plus frontend/webmcp.js , which registers the six read/propose-only tools with the browser's WebMCP API ( navigator.modelContext.registerTool ), each one calling the same GET routes and /intake endpoint the console itself uses — no separate, more-privileged backend door for agents. Deployment : Cloud Run ( asia-south1 ), --min-instances=1 to avoid a cold-start during judging, --no-cpu-throttling . 424 Python tests and 20 Node tests, including a dedicated adversarial suite trying to get the gateway to approve something it shouldn't. Challenges we ran into The WebMCP spec itself is still moving. Documentation (including Chrome's own developer docs) describes the API as document.modelContext , but the actual shipped implementation in current Chrome exposes it as navigator.modelContext instead — with a separate navigator.modelContextTesting surface ( listTools() , executeTool() ) for verifying registration without a live agent. This meant tools were silently failing to register — no error, just an empty tool list — until we traced it back to a single feature-detection check on the wrong global. Deciding what not to build was harder than building what we did. It would have been easy to add a WebMCP tool for /delegate or /pay — more "impressive" on paper — but that would have meant putting a spendable capability inside a public page. The interesting engineering problem was making the read-only boundary airtight, not working around it. What we learned Emerging browser APIs ship inconsistently even across "the same" browser family — testing against the real, current implementation (not the docs) caught a bug that unit tests alone never would have, since Node has no navigator global to catch the mismatch. A safety boundary is most convincing when it's structural (no route exists) rather than behavioral (a tool declines to). No one has to trust that an agent chose not to spend; there's simply nothing on the other end of the wire that could. What's next for Pocket Change Extending WebMCP coverage as the spec stabilizes — particularly once cross-document tool discovery ( getCrossDocumentScriptToolResult , which we noticed on the navigator.modelContextTesting prototype but didn't use) has clearer semantics.
