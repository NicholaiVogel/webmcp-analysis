A living museum record rebuilt by communities, curators, and WebMCP agents. An agent can help reconstruct history, it cannot decide whose history becomes official. Like 2 Comment Story Updates Main Page Collection Page (Moonbird Mask) Curator Page Inspiration Museum labels sound finished. Behind a lot of them there is a hole: a stretch of years where nobody wrote down who owned the thing, a place name copied off a dealer's invoice instead of asked from the people who made it, a phrase like "ceremonial use" standing in for knowledge that somebody still has. The people who could fill those holes usually have nowhere to put what they know. When they do send something in, it either sits in an inbox forever or gets quietly folded into the official text with no name on it. We wanted to see what that process looks like with agents in it. The problem showed up right away. An agent that reads accession records and drafts label language is genuinely useful. An agent that can also publish is an agent deciding whose version of history becomes official, and that is not a thing we wanted to build. So the rule became: research is free, the record needs a curator. What it does RE:TURN is a museum collection where the record is treated as unfinished. Eight fictional objects, each with a public label, a provenance timeline, and the gaps in that timeline marked rather than smoothed over. A visitor can flip any label to see the questions behind it. They can submit a photograph, a document, or an oral history, and they choose at that moment whether it may be published, published without their name, or kept private for internal research only. On the other side, a curator works the inbox. Community material arrives marked submitted, not verified, and it sits beside the official record instead of inside it. A curator agent can compare a submission against the accession record, build a timeline, and draft new label wording. Nothing it drafts goes public on its own. The draft lands in a human's queue with the evidence attached, and a person approves it, edits it, or turns it down. Why this is a good fit for WebMCP The interesting question in this domain is not "can an agent do the work." It is "who is allowed to decide." Those two things need to come apart, and WebMCP is the first browser API we have used where they come apart cleanly. Tools are declared by the page, scoped to a role, and executed by the page. The site decides what an action means. The model does not get to reinterpret it. That let us put a policy gateway behind every single tool call and make the answer an agent gets back into a real part of the interface rather than an HTTP status. There are five answers. applied means it was within authority and it is done. pending_approval means a person now holds it, and here is an id to poll. denied means the policy refused, here is the code and here is what would change the outcome. invalid means the caller made a mistake, and here is the field. Error means nothing was written. Thirteen policy codes are reachable through the tool surface. submitted_sole_authority fires when an agent tries to change an official label citing only community material. consent_not_public blocks publishing something a contributor did not agree to publish. approval_snapshot_mismatch catches a stale draft trying to overwrite a label that changed while the approval was waiting. A fourteenth code, outside_agent_surface, exists so that it can never fire: deletion and physical return are classified CRITICAL and no tool maps to them at all. What people and agents can do together that was hard before Someone's knowledge can reach the record without being swallowed by it. A contributor sends a photograph with a consent choice. A curator agent compares it against the verified 1968 invoice, finds the contradiction, and drafts language for it. All of that happens without publishing anything, and the contribution keeps its own voice on the page instead of dissolving into the museum's. Before, those were two disconnected things. A contact form on one side that swallowed submissions, and a collections system on the other that only staff could see. An agent can also be refused in a way it can act on. Ask for a label change backed only by community material and you do not get a 400 with a sentence in it. You get submitted_sole_authority, a recovery line telling you what would work, and a referral id, because the gateway handed that refusal to a curator. The agent polls the id and carries on with something else. Being told no becomes a step in the workflow. Two agents can also work the same object from opposite sides without reaching each other's tools. A community page registers 10 tools. The curator console registers 15. The server re-checks the role on every call, so registration is a convenience rather than the security boundary. One more thing we are happy with: files stay files. Binaries never cross the tool surface. A photograph goes up through an ordinary multipart POST, and the agent then reads its id with list_my_uploads and binds it with attach_assets. The whole contribution completes through tools without a single byte passing through a tool call. How it creates a better experience For a contributor, the main thing is that consent is asked where the choice is made, and the record keeps the promise. If you pick "public, with my name," the form asks for the name right there. We had to learn this one the hard way, which is in the challenges section below. Length limits are enforced as you type instead of at the end of a five-step form, and every submission gets a receipt page showing what happened to it, including any question the curator sent back. For a curator, the console and the agent surface never disagree. When the gateway hands something to a person, it shows up in the console, in list_pending_approvals, in check_approval, and in the summary count. All four, or an agent is working from a different picture of the queue than the human sitting next to it. Approvals are snapshot-checked, so a draft that has gone stale cannot quietly publish over a newer label. For a reader, community material is visible and labelled as submitted. Only public_attributed carries a name. Label revisions show a word-level diff of what changed and when. How we implemented WebMCP Three files do the work. lib/webmcp/tools.ts is the catalogue. Twenty-three tools, each with a name, a description, JSON-Schema properties, a role, and readOnly / untrusted annotations. One declaration, read by three consumers: the browser registration, the server's argument validation, and the tool panel in the console. lib/webmcp/register.ts hands them to the browser. context.registerTool({ name: tool.name, description: tool.description, inputSchema: { type: 'object', properties: tool.properties ?? {}, required: tool.required ?? [], additionalProperties: false, }, annotations: { readOnlyHint: tool.readOnly, untrustedContentHint: tool.untrusted ?? false }, signal, execute: async (args) => (await fetch(`/api/tools/${tool.name}`, { method: 'POST', headers: { 'content-type': 'application/json' }, body: JSON.stringify(args ?? {}), })).json(), }); context is document.modelContext, falling back to navigator.modelContext on browsers that still only expose the older one. Registration follows the session role. additionalProperties: false makes the published schema say exactly what the server enforces, so an undeclared argument comes back refused with a list of what the tool actually takes, rather than being dropped in silence. app/api/tools/[name]/route.ts is what runs. Because execute posts to the same route any HTTP client would use, the tool surface and the HTTP surface cannot drift apart. Every consequential call goes through evaluatePolicy, a pure function with no I/O, before anything is written.
