What it does Zenith Studio is a browser-native pixel-art workspace where people and AI agents edit the same live canvas. You can draw manually, edit palettes, organise projects, work with animation frames, and export assets. Through WebMCP, an agent can inspect the open artwork, make precise pixel edits, check tile seams or animation consistency, and help refine the result. Both collaborators use the same document and undo history. An agent’s edit appears on the canvas you are already using. If it gets something wrong, your normal undo command takes it back. The agent can read and write this compact representation, while the editor renders it onto the canvas. A shared TypeScript document model enforces palette and coordinate constraints and manages undo/redo. Human controls and agent tools operate on that same model, so there is no separate agent document to synchronise. The Next.js and React frontend contains the editor, WebMCP integration, animation timeline, and IndexedDB persistence. Heavy pixelisation runs in a Web Worker. A Hono backend handles model requests and keeps API credentials outside the browser. Deterministic drawing and pixelisation run locally. Like Comment Story Updates The final finding stays beside its cited excerpt, ready for human review, source checking, and Markdown export. The Evidence Room connects four WebMCP tools to one caseboard that the agent and the person can inspect together. One selected window becomes a bounded diff with both source captures and an explicit untrusted text warning. Index records produce six exact capture windows before any archived page body is downloaded. Why I built it Web archives contain real evidence, but working with them still feels like manual archaeology. Find snapshots, open a pile of tabs, compare dates, copy URLs, then try to remember which version actually proved the point. I wanted to ask a browser agent a sharper question: "How did this page change, and can you show me the exact captures that prove it?" This project also has some history. @agntn/archives started in April 2025 as one TypeScript interface over several web archives. It gradually gained caching, lazy provider loading, typed metadata and more sources. In 2026 it grew into a proper agent tool: first native OMP and Pi extensions, then an MCP server, archived body reads, pagination, capture diffs and finally a Nuxt explorer running on Cloudflare Workers. The WebMCP Challenge was a good reason to build the missing piece. Not another chat box, and not four aliases for buttons. I wanted the page itself to become a shared investigation room for a person and an agent. What it does Archive Evidence Room registers four native WebMCP tools through document.modelContext : scope_archive_case defines one historical question and checks which archives have evidence. find_change_windows finds consecutive captures without downloading archived bodies. inspect_archive_change reads one selected pair and returns a short cited diff. pin_archive_finding records whether that diff supports, contradicts or only adds context to the question. Every call updates the same visible caseboard. The agent can do the repetitive archive work, but the person still sees the dates, original URL, provider, underlying Memento archive, diff and final interpretation. No invisible research session and no uncited answer at the end. WebMCP is progressive enhancement here. Without the experimental browser API, the full workflow still works by hand. How I built it The UI is Nuxt 4, Vue and Docus. The server runs on Cloudflare Workers. I used the existing cached /api/coverage , /api/snapshots and /api/diff routes instead of creating a second archive backend for the hackathon. Those routes call the same @agntn/archives executors already used by MCP, OMP and Pi. Discovery is index first. The room requests between 3 and 12 capture records, groups them by exact URL and provider, keeps Memento captures inside the same underlying archive, then ranks useful windows. Archived bodies are fetched only after someone chooses a window to inspect. The result is much faster and much kinder to public archive infrastructure than reading everything up front. The caseboard keeps provenance all the way through. A diff can resolve to captures slightly different from the index rows, so the final citation comes from the diff result, not stale listing metadata. Findings store the interpretation beside the evidence instead of mixing both into one generated paragraph. What was hard Public web archives disagree about almost everything: timestamp formats, URL normalization, replay endpoints, metadata and failure behavior. A plausible diff between unrelated records would be worse than no result, so I made the pairing rules deliberately strict. Cancellation was more subtle. Browser abort signals had to travel through $fetch , Nitro, cache misses and the archive executor. Sharing one cached promise also shared one caller's cancellation with another caller. That was wrong. Each cache miss now owns its request and one closed tab cannot kill another investigation. The other problem is trust. Archived HTML can contain instructions written specifically to manipulate an agent. Treating that as normal tool output would be ridiculous. The room exposes only a bounded text excerpt, marks it as untrusted, renders it as escaped text and keeps it separate from the finding written by the agent. What I learned The useful WebMCP abstraction is not "let the agent click my UI." It is a small protocol with state the user can inspect. caseId and changeId make the steps explicit, while the shared board makes mistakes visible. I also learned that archive research needs honest negative results. No capture in one bounded query does not mean a page never existed. A partial diff cannot prove text was absent outside the compared prefix. The product gets better when those limits stay visible instead of being polished into confidence. WebMCP made this particularly interesting because it allows websites to expose structured capabilities directly to AI agents instead of forcing agents to infer how to operate a user interface. Build WebMCP services from business workflows—agent-ready and Cloudflare-ready. Like Comment Story Updates Core ERP service graph generated from one Mantle Manifest. Typed data models include constraints, indexes, and agent-ready operations. A handoff package guides a coding agent from the backend contract to a deployable site. API, MCP, and WebMCP interfaces are generated and documented together. Mantle Builder uses WebMCP to rapidly create your own WebMCP-enabled business service and take it to Cloudflare. Describe the workflow in agent chat; the agent builds and validates the Mantle contract, previews its API, MCP, WebMCP, and Admin surfaces, then hands it to a coding agent to finish the frontend, authentication, and production deployment. Inspiration Companies adopting agent workflows quickly run into business-logic gaps. Agents can reason and browse, but the organization's real rules—who can do what, which records exist, how an order or request moves, and which operations are public or staff-only—are still trapped in documents and bespoke code. Conventional app builders also make the human perform every configuration step through a visual editor. We wanted a shared workspace where a person supplies intent and approval while an agent supplies structured implementation. What it does Mantle Builder lets a person describe a workflow and lets their agent build the service behind it through WebMCP. What is Mantle? Mantle is the open-source, config-as-code runtime beneath the Builder. An agent writes four atoms—Schema, View, Procedure, and Trigger—in one YAML Manifest; Mantle validates the contract and carries the runtime complexity. The same contract can power real consumer-facing services such as commerce, reservations, and application flows while immediately producing API, MCP, WebMCP, and Admin surfaces. Agents get the tools missing from their workflows, while operations teams get one place to manage customers, orders, requests, and queues. The agent works through four typed WebMCP tools: builder_get_started — inspect the active project, Mantle grammar, presets, and exact next calls. builder_apply_preset — start from a tested business workflow. builder_apply_manifest_patch — compile and safely activate confirmed changes. builder_execute_preview — run the service as a mock actor, inspect mutations, and follow the result in Admin. The prompt requires the agent to interview the user about actors, data, operations, permissions, and entry points, summarize the proposal, and wait for confirmation before changing the project. Every accepted change immediately appears inside an embedded Mantle Admin developer console. The person can inspect schemas, procedures, triggers, interfaces, and operational Admin views. The agent can execute the service as an anonymous visitor, member, or owner, compare canonical entries before and after mutations, and watch Admin follow the affected View, collection, or record. When the contract is ready, the user downloads a coding-agent handoff containing the complete Manifest, pinned Mantle references, a frontend WebMCP registration example, and deployment guidance. A coding agent can then add the consumer-owned frontend, authentication, provider configuration, and production wiring. Why WebMCP WebMCP turns Mantle Builder from a one-way generator into a shared control surface for people and agents. An agent can author the service, seed data, and exercise public, member, and staff workflows through typed preview tools. Each action updates the same persistent sandbox the human is viewing, while the embedded Admin console follows the affected page, collection, or record. The agent acts; the human can watch, inspect, and approve the result as it happens. This closes the loop from intent to implementation to verification. Teams can create MCP and WebMCP services that fill gaps in existing agent workflows, while operations still gets a trusted interface for managing customers, orders, requests, and queues. How we built it The React host registers Mantle-derived capabilities with document.modelContext . WebMCP calls enter one serialized mutation path where inputs and project revisions are validated. Valid Mantle resources compile into a runtime plan; a browser-hosted adapter and mock environment power the service preview. Mantle Admin runs in a same-origin iframe and talks to the host runtime over a constrained message bridge. Project Manifests and canonical preview entries autosave to IndexedDB. The production host is deployed as a Cloudflare Worker. What we learned A useful agent interface needs more than tool registration. The tools must expose enough grammar and current state for an agent to act reliably, mutations need optimistic revision checks, invalid candidates must never replace the last working project, and the human needs a visual way to verify what the agent created. Built during the challenge The implementation began on September 2, 2026. The WebMCP authoring flow, Mantle preview, project persistence, coding-agent handoff, browser testing, and Cloudflare production deployment were all created during the submission period. The public commit history distinguishes this work from the pre-existing Mantle Core dependency. Current limitations Builder project Manifests and preview records persist only in the current browser; they are not production data or synced across devices. Preview authentication is intentionally mocked. The Builder supports declarative Views and builtin Procedure handlers; custom handler refs, a consumer frontend, production authentication, and provider wiring are completed after the coding-agent handoff. Woven - From model request to user-confirmed pickup receipt. One request, two complete carts. From one request to a pickup-ready order. Ask once. Review once. Confirm once. Why Woven is a strong fit for WebMCP Shopping agents can recommend individual products, but a real mission still requires quantities, compatibility, budget, current stock, pickup, and consent to work together. Woven turns that multi-step job into a structured collaboration between an agent and the person already using the page. On the fictional Woven Trail Market storefront, the agent does not guess at buttons or scrape the interface. Seven purpose-built site tools let it start or inspect a mission, rerank the visible cart comparison, select an offered cart, apply only a merchant-approved compatible alternative, refresh current price and stock, and verify an existing simulated receipt. How it creates a better user experience The canonical request asks for a rainy-weekend camping kit for two first-time campers that fits in one car boot and is pickup-ready today. Woven Trail Market shows the best two complete carts, each from one merchant and one pickup location, and explains how every quantity and component satisfies the brief. The lead proof is exact: 7 units, 5 categories, 89 L packed, and a 3,000 mm rainfly. Agent calls update the same React storefront the person can see. When the agent calls compare_carts , Woven reranks the visible inline kits rather than returning a disconnected text result. The person can review the same carts, prices, stock, compatibility proof, alternatives, and selected state. That removes repeated searching and cart reconstruction without hiding the decision from the person. What people and agents can do together now The agent can translate one outcome-oriented request into bounded, reversible preparation work across product choice, constraints, current catalog facts, and comparison. The person can inspect and steer that work in the same page, then retain sole control of the irreversible step. That boundary is intentional. Woven does not register identity verification, checkout preview, confirmation secrets, or purchase authorization as WebMCP tools. The agent may prepare and recommend; the person must complete the clearly labeled demo identity handoff, review exact expiring terms, and directly confirm or continue to a merchant. Inventory, identity, merchants, and payment authorization are simulated, Woven accepts no card credentials, and it cannot make a live charge. How WebMCP was implemented The dedicated top-level /webmcp storefront document registers seven imperative tools through document.modelContext.registerTool : start_mission , get_mission , compare_carts , select_cart , swap_cart_item , refresh_carts , and verify_receipt . Each tool has a closed JSON schema. Read-only operations carry read-only annotations, content-bearing results are marked untrusted where appropriate, and every registration is attached to an AbortSignal so navigation removes the page's tool surface. The server sends Origin-Agent-Cluster: ?1 and Permissions-Policy: tools=(self) . Human submission, WebMCP, and the existing MCP App enter the same server-owned mission router, deterministic commerce verifier, SQLite state, and checkout controls. The agent cannot mark a cart checkout-eligible. Connected catalog facts may support a cart; cited web research remains research-only. Price, stock, compatibility, identity session, exact amount, nonce, expiry, and idempotency are revalidated at the human confirmation boundary. Inspiration Search gives links, but buying still takes work. A first-time camper has to size the shelter, duplicate sleep gear, check rain ratings, fit everything into one car, find one pickup location with stock, and rebuild the cart at checkout. Woven was built around a simple product promise: everything works together. What it does One natural-language mission becomes verified complete carts; the storefront shows the best two in solid comparison cards. The agent and person share a visible storefront state, current selection, merchant-approved alternatives, and refreshable catalog state. The agent can do reversible preparation through WebMCP while identity and exact transaction confirmation stay human-only. How we built it Woven is one Node.js and TypeScript service with a dedicated React storefront, seven top-level WebMCP site tools, HTTP and stdio MCP transports, deterministic cart verification, bounded LangGraph.js orchestration for non-camping missions, SQLite persistence, and a simulated payment adapter. Tests assert the exact tool surface, schemas, cleanup lifecycle, shared UI behavior, security headers, and absence of identity or purchase tools. Challenges The hardest design decision was deciding what not to expose. Treating a tool call as payment consent would erase the trust boundary. Woven exposes only reversible preparation work and keeps identity, exact terms, secrets, and final confirmation outside the agent's tool surface. The second challenge was preserving one source of truth across WebMCP, the MCP App, and the browser experience. All surfaces now share the same server routing, validation, persistence, cart rules, and confirmation boundary. Accomplishments Seven browser-discoverable WebMCP tools over a complete product workflow. Tool calls update the visible storefront instead of a parallel agent-only state. Two visible complete one-merchant kits with exact budget, volume, weather, quantity, stock, pickup, source, and verification proofs. One truthful glass activity surface; commerce cards and authorization controls remain solid, and total connector failure never fabricates a result. Merchant-approved substitutions, refreshable facts, signed simulated receipts, and deterministic failure behavior. Human-only identity and purchase confirmation enforced by the server and omitted from WebMCP. Automated tests plus desktop and mobile verification. What we learned WebMCP is strongest when the browser is not merely another API client. Its value is shared context: the agent can act through precise tools while the person sees and controls the same product state. Tool omission is also product design; the absence of a purchase tool makes Woven's consent model clearer and safer. Challenge-period provenance Woven was created during the challenge period.
