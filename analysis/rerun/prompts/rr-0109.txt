# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Inspiration Independent developers routinely finish a build and accidentally describe the whole release as complete. But “the source exists,” “the build passed,” “the artifact installed,” “it launched,” “a human completed the journey,” and “the exact version is public” are six different facts. That evidence gap becomes more dangerous when agents help with release work. An agent can summarize logs and record observations, but it cannot honestly claim that a person played a game, that a real device test happened, or that an external store accepted and published a version unless evidence for that exact boundary exists. Release Evidence Desk turns that problem into a visible, shared workspace: proof, not vibes, for small-app releases. What it does A person creates a release project, records exact claims, attaches dated evidence, and sees evidence-derived verdicts across five tracks: Source Build Install / Runtime Human Play External Release The desk separates six release boundaries, highlights contradictions, quarantines unreviewed observations, exposes concrete gaps, generates an ordered verification plan, and exports a privacy-scrubbed handoff. The built-in anonymous demo is intentionally blocked. It has confirmed Source and Build proof, an install note awaiting human review, no confirmed Runtime proof, a contradicted Human Play claim, and no verified External Release status. That honest “2 of 6” is the product’s point. Why WebMCP is essential The most useful context is already in the live page: the active release candidate, exact claim IDs, confirmed evidence, pending review, contradictions, and gaps. A separate chatbot would duplicate or drift from that state. Screen automation would have to infer meaning from visual cards. WebMCP gives the agent a precise contract over the same live page the human is using. A real workflow can run in sequence: Read the current snapshot. Audit every release claim. List the missing evidence. Generate an ordered release plan. Record a human-supplied observation. Export a sanitized handoff. Every state-changing result is immediately visible in the interface and operation log. The write path is deliberately asymmetric. Agent-proposed supporting evidence is always marked pending human review , so it can appear in the UI without upgrading a claim. Contradictions may reduce confidence immediately. Only a human can confirm supporting evidence. WebMCP is therefore not a decorative integration—it is the trust boundary for the product. Human–agent collaboration The human identifies the exact project, target, and release candidate. The agent reads current claim IDs and coverage from the page. The agent separates supported, contradicted, pending, and unknown statements. The agent plans the next checks with explicit developer, tester, and release-owner responsibilities. When the human supplies a new observation, the agent records it and the page updates live. The human confirms or rejects proposed supporting proof. Either side can generate a privacy-safe Markdown or JSON handoff without turning unperformed work into a Pass. How we built it The page uses the real WebMCP imperative API and registers six tools with document.modelContext.registerTool(...). Every tool has an exact name, bounded description, strict JSON Schema, additionalProperties disabled, independent runtime validation, corrective errors, annotations, and structured observable output. get_project_snapshot — active project, revision, coverage, evidence tracks, and claim IDs. list_missing_evidence — missing claims, proof gaps, contradictions, and pending review. audit_release_claims — evidence-derived claim verdicts. add_evidence_item — validated live-state mutation with a human-review quarantine. generate_release_plan — ordered verification actions derived from current gaps. export_sanitized_handoff — Markdown or JSON with emails, secrets, private paths, and private URLs scrubbed. React renders the control-room interface. TypeScript owns the proof model and tool contracts. Versioned localStorage keeps projects local-first and reload-safe. Vitest and Playwright test the state invariants, error contracts, keyboard flows, persistence, and responsive UI. Vercel hosts a static production build with no account, backend, paid API, telemetry, or runtime network dependency. Challenges The hardest problem was not registering tools. It was preventing a convenient write tool from becoming a confidence-escalation shortcut. We separated claims from evidence-derived verdicts, separated Install from Runtime within one visual lane, introduced a human-review state for supporting agent observations, and made verdicts pure functions of confirmed evidence. We also created corrective errors for wrong claim IDs, mismatched evidence types, unsupported bounds, and unsafe handoff requests. A second challenge was keeping browser capability claims honest. Ordinary CI Chromium uses a small registration harness to exercise production contracts. Native WebMCP was verified separately in ChatGPT’s in-app browser and in flag-enabled Chrome 151 and 152. The public demo records the actual native getTools() and executeTool(...) workflow. Those proof layers remain explicitly separate. Accomplishments A coherent five-track, six-boundary release evidence model. Six non-trivial WebMCP tools supporting a complete multi-tool workflow. Agent write → visible UI update → pending human review → reload persistence. Empty projects remain 0/6 and incomplete; missing state never becomes a Pass. Positive, invalid-input, empty-data, and state-sync cases for every tool. Responsive desktop and mobile layouts with keyboard access. Privacy-scrubbed Markdown and structured JSON handoffs. A public, audible 2:02 demo showing native discovery, audit, planning, guarded write, persistence, empty-state protection, handoff, and the prior-work boundary. What we learned Agent-ready does not mean agent-controlled. The best collaboration surface gives an agent precise affordances while preserving human authority over evidence the agent cannot physically observe. WebMCP makes that separation explicit in the tool contract, state model, and interface. That repository remains a read-only conceptual source and is not this submission. Release Evidence Desk is a clean, independent web application created after the WebMCP Challenge opened. Its UI, data model, state engine, WebMCP implementation, tests, visual assets, documentation, and Git history are new. No source code, assets, or Git history were copied from the earlier project, and the earlier project was not converted into an MCP server. What is next The submitted version will remain frozen throughout judging. A future separate fork could add import adapters for common CI receipts, signed evidence bundles, team review roles, and shareable read-only snapshots while preserving the same evidence boundary. PaperQuant is a WebMCP-native quantitative research lab where Codex turns live crypto hypotheses into reproducible evidence—rigorous backtests, visible workflows, zero real-capital risk. Like 1 Comment Story Updates Research before risk What if an AI agent could sit beside you inside a professional trading terminal—not merely talk about a chart, but investigate the same market, run the same experiment, and show every action while you remain in control? PaperQuant Lab turns one natural-language hypothesis into visible, reproducible crypto research. A human opens the live laboratory and asks Codex to investigate. Codex discovers 22 typed WebMCP tools attached to that exact page, configures the chart, gathers market evidence, launches a deterministic historical study, explains what passed and what did not, and overlays the signals for the human to inspect. No hidden browser clicking. No pixel scraping. No real money. The problem Trading learners and quantitative researchers face a fragmented workflow: inspect a chart in one product; copy prices into a notebook; write or run code elsewhere; manually reconcile signals, assumptions, and P&L; trust that the agent understood the same state the human saw. Conventional browser agents make this worse on dense trading screens. They infer controls from the DOM, lose semantic context, and can silently drift away from the market, timeframe, indicator set, or account state the user intended. PaperQuant makes the trading laboratory itself agent-native. The judge journey Open the laboratory and ask: Give me the read-only observer URL. Set BTCUSDT perpetual to 1h, enable Hull Suite, VWAP, RSI and ADX, inspect completed candles, order-book depth and recent trades, then run the BTC filtered EMA study from 2023-01-01 through 2025-12-31 with $100,000 research capital. Poll it, explain technical status, data quality and profitability separately, and overlay its markers. Do not change my paper account. PaperQuant then performs a complete, inspectable research loop: Discover — Codex reads the page's live capability contract. Configure — market, instrument, timeframe, and multiple indicators change atomically in the visible UI. Inspect — completed candles, indicator values, liquidity imbalance, and aggressor flow become structured evidence. Research — an asynchronous, checksum-keyed strategy run executes on historical Binance data. Explain — technical status, data quality, assumptions, annual results, walk-forward performance, and profitability are reported separately. Show — buy, sell, short, cover, stop, and target markers appear on the same chart. Protect — the paper account remains unchanged unless the human explicitly requests a simulated order. Every agent operation appears in a collapsible, sanitized workflow console. A high-entropy observer URL mirrors the session read-only in a second tab or device, making human-agent collaboration visible rather than hidden behind a chat response. Why WebMCP is essential PaperQuant does not expose a thin demo command or a second agent-only backend. The top-level document registers 22 strict-schema tools through document.modelContext.registerTool , and every handler calls the same typed application controller used by the React interface. The tools cover: capability discovery and market search; Spot and USD-M perpetual market context; atomic multi-indicator chart configuration; completed-candle and signal inspection; order-book and aggregate trade-tape evidence; paper account, order, prediction, and history operations; strategy discovery, save, run, poll, cancel, regression, artifact, and chart-overlay operations. This is the core WebMCP advantage: the page publishes stable domain operations instead of asking an agent to guess what pixels mean. The implementation includes strict JSON Schemas, bounded inputs, structured success/error envelopes, cancellation and cleanup, read-only and untrusted-content annotations, idempotency keys for retryable writes, and explicit user-intent gates for simulated financial mutations. Navigating away removes the tools cleanly. Without WebMCP, the normal human interface remains fully usable. A complete product, not a proof of concept The live build includes: real Binance public quotes, depth, aggregate trades, and 1m–1M candlesticks; active USDT market search across Spot and USD-M perpetuals; expandable candlestick charts and multi-indicator overlays; Hull Suite ribbon, VWAP, EMA/SMA, Bollinger Bands, Supertrend, Ichimoku, RSI, MACD, Stochastic RSI, ATR, and ADX/DMI; a versioned paper account with long/short positions, reduce-only behavior, funding entries, idempotency protection, and a maximum 2× simulated leverage ceiling; 20 versioned strategy hypotheses with a full regression report; annual and rolling walk-forward performance, trade ledger, equity curve, assumptions, provenance, scientific hashes, and immutable compressed artifacts; browser-isolated Python signal experiments; D1-backed owner sessions, read-only observation, quotas, and a live workflow console. The interface is designed so a first-time judge understands the product immediately, enters the laboratory in one click, and sees Codex and the human sharing the same state. Research integrity over impressive-looking numbers PaperQuant refuses to turn missing data into fake confidence. Signals are evaluated on completed UTC candles and filled no earlier than the next candle open. Fees, spread, slippage, and funding are separated. Risk sizing and maximum leverage are enforced. When stop and target occur in the same bar, the conservative stop-first rule wins. A strategy result has two independent questions: Did the engine and rules execute correctly and reproducibly? Did the strategy make money? PASS answers the first question, never the second. Data gaps produce PARTIAL_DATA ; fundamentally unavailable history produces BLOCKED_DATA . Blocked strategies remain visible in the 20-row report instead of disappearing or receiving fabricated performance. This honesty is especially important for learners who may otherwise mistake an attractive backtest for evidence of a safe strategy. Safety by construction Every balance, fill, fee, funding entry, and profit-and-loss value is simulated. PaperQuant has: no private exchange API keys; no deposits or withdrawals; no real-order pathway; no account mutation from a backtest; no paper trade without explicit user intent; exact confirmation requirements for destructive reset operations. Exchange and strategy output is treated as untrusted content and cannot authorize a later action. Architecture The Vinext/React application runs on ChatGPT Sites. Binance public APIs provide live market data. Sites D1 stores sessions, strategies, quotas, idempotency records, and compact research metadata. Sites R2 stores immutable artifacts. A separate authenticated Python worker retrieves and verifies official Binance archives, runs deterministic studies, and returns compact results plus compressed evidence without receiving Sites storage credentials. The result is a credible end-to-end product: live browser tools, shared UI state, asynchronous quantitative workloads, provenance, safety controls, and repeatable tests. Why it can matter PaperQuant begins with crypto education, but the interaction model applies anywhere a high-stakes expert interface must become safely operable by humans and agents together: finance, operations, scientific instruments, analytics, and engineering consoles. WebMCP lets the website become the trusted collaboration boundary. The human keeps context and authority; the agent gains typed capabilities; the product records the evidence. PaperQuant does not ask users to trust an AI trader. It gives them an AI research partner whose work they can watch, reproduce, and challenge before risking anything. The shift roster co-pilot. Like Comment Story Updates agent console detail dashboard Inspiration Every independent café, bakery, and corner shop has the same Sunday-night ritual: the owner sits down with a spreadsheet, drags names into cells, and then blows up the group chat trying to get coverage for next week. One wrong cell — a 17-year-old scheduled past 21:00, someone double-booked, a close with no keyholder — and it's a labour-law problem, not just an annoyed group chat. What made this click as a WebMCP idea is that scheduling is a trust problem, not a data problem. A manager will happily let an agent read the roster. They will never let it act on it unless they can see every move and take it back. WebMCP is the first thing that makes that possible: tools that run in the user's own authenticated browser, on the live page, where every action is observable, attributable, and undoable. So we built wcrew around that exact contract. What it does wcrew is a shift roster co-pilot for small hourly teams (5–30 staff). It replaces the spreadsheet with a live weekly board where a manager and a browser agent fix the roster together: Compliance you can see — skills, availability, under-18 curfew, 11-hour rest, 10-hour daily cap, 5 consecutive days, keyholder coverage, 1.5× overtime, and a $5,200 budget are checked in real time, with the exact rule broken and a suggested fix. An agent that acts through 15 typed tools — the agent can check compliance, explain any assignment before making it, rank swap candidates, auto-fill open shifts with a deterministic solver (three strategies), and publish — all on the live board. Dry-run before mutate — auto_fill previews a plan produced by the same code path as the apply, so what you see is what you get. A trust contract — every agent action is logged actor:agent , one-undo reversible, and destructive actions pause on a human confirmation modal. An in-page agent console — runs the same 15 tools in any browser (no Chrome flag, no agent platform) so the demo is one click away for anyone. How we built it 15 structured tools on document.modelContext ( src/webmcp.js ), each with a natural-language description and JSON Schema, executing against a pure, zero-dependency scheduling engine. Single source of truth — evaluateAssignment powers explain_assignment , assign_shift , check_compliance , and the solver, so "explain" and "do" can never disagree. Deterministic solver — greedy, hardest-shift-first with a one-level repair pass, so the same input always yields the same plan. Actor-tagged store — a tiny undo/redo store where human edits and agent tool-calls go through the same commit path. Prompt-injection defense — staff notes are untrusted; tools surface them between --- BEGIN UNTRUSTED --- delimiters and warn the agent not to follow instructions inside (there's a live canary in the seed data). Origin isolation — Origin-Agent-Cluster: ?1 + Permissions-Policy: tools=(self) served by tools/serve.mjs and _headers . Vanilla JS, no build step, no backend — runs anywhere; state lives in localStorage . Challenges we ran into WebMCP is brand new. The spec is still a draft and document.modelContext only exists behind Chrome 149+ with a testing flag (or ChatGPT's in-app browser). That meant the demo would silently degrade to "human-only" for most judges — so we built the in-page agent console that exercises the identical tool definitions everywhere. Making the dry-run honest. Most demos fake a preview. We wired auto_fill --dry_run through the exact solver the apply path uses, including the repair pass, so the numbers in the preview are real. The trust contract is easy to say, hard to build. Observable, attributable, undoable required a shared store, actor tags, a confirm bridge the agent can't bypass, and locked shifts the solver respects. Prompt injection is a first-class concern the moment you expose user content to an agent. We had to assume staff notes are adversarial and design tool descriptions + delimiters around that. Origin isolation is load-bearing — document.modelContext is gated behind Origin-Agent-Cluster , which rules out plain static hosts like GitHub Pages and forced us to configure headers on Cloudflare Pages. Accomplishments that we're proud of 15 tools sharing one engine, so answers are computed, not guessed . A trust contract where the agent proposes and the human decides — the thing we think makes WebMCP more than a "chat sidebar." An honest dry-run produced by the same code path as the apply. A real prompt-injection canary and untrusted-content handling. An agent console that makes the whole thing demo-able in any browser, no setup. What we learned WebMCP's real value isn't tool-calling — it's trust : keeping the human's authenticated session, UI, and undo power in the loop. One engine for explain and do is the single biggest reliability win for agent-driven UIs. Prompt injection isn't theoretical: the moment you hand user content to an agent, you have to design for it. Platform details (origin isolation, permissions policy) decide whether WebMCP even works — get them right early. A research review canvas where researchers and browser agents search, read, synthesize, and audit evidence together through WebMCP. Like 1 Comment Story Updates Inspiration Research is not a straight line. Researchers discover candidate papers, decide what deserves attention, inspect evidence, challenge interpretations, and synthesize. Existing AI workflows usually split that process between a chat window and a separate research tool, leaving people to copy results by hand and making agent decisions hard to audit. PaperTrail imagines the open web as a shared research room where humans and browser agents work on the same living page. What it does PaperTrail is a collaborative literature-review canvas organized around the meaning of the work: Inbox stages relevant articles found by a person or agent. To Read holds candidates that merit review. Reading is active evidence work: paper details, citation context, findings, limitations, and questions. Synthesized contains only completed cases that have contributed to a cited conclusion. A researcher can click Go Live and share the canvas. A colleague can join from another browser, and their agent can search the internet for relevant scholarly articles, add a focused candidate, read evidence, annotate it, compare sources, create a decision brief, and audit the result. Every contribution appears on the same board with author badges, tool-call receipts, and a visible activity trail. The human keeps control over selection, questions, source verification, and what is considered complete. Why WebMCP This workflow needs more than an agent collaborating as a peer. PaperTrail exposes 16 typed WebMCP tools over its real research model, including literature search, workspace state, selection-aware context, paper details, citation contexts, notes, comparisons, artifacts, verification, and export. Because the tools are registered by the page, agents can discover the available actions, receive structured state, and write first-class objects directly into the research canvas. Researchers see the results immediately and can inspect the exact receipt behind each agent-written claim. This removes copy-and-paste handoffs while preserving human judgment and provenance. A complete human+agent research flow The researcher opens a question and takes the canvas live. A collaborator and their browser agent join from a second session. The agent searches for relevant work and contributes one focused candidate to To Read . The researcher curates another candidate and selects the active case. The agent reads details and citation context, then records a grounded finding and an evidence boundary in Reading . The researcher adds a question that changes the direction of the synthesis. The agent compares sources and publishes a cited decision brief. A second agent audits the conclusion from its own browser. The researcher verifies sources and moves only the completed case to Synthesized . What was difficult before is now native to the page: multiple researchers and agents can extend, question, and audit the same evolving body of work across browsers without losing context or authorship. How we built it PaperTrail uses vanilla HTML, CSS, and JavaScript ES modules with no build step. The top-level document registers WebMCP tools with document.modelContext.registerTool, closed JSON Schemas, honest read/write annotations, and an AbortController lifecycle. The tools operate on a DOM-independent state model and return structured results with provenance metadata. Live collaboration uses a Vercel API and Neon-backed operation log to replicate human edits and agent tool calls across shared links. Scholarly discovery and citation evidence are sourced through public research APIs. The app includes source verification, Markdown/BibTeX/JSON export, and a local compatibility layer so the workflow remains demonstrable when native WebMCP is unavailable. Challenges and lessons The hardest problem was preserving causality across live sessions: an agent action must be visible, attributed, replayable, and safe to challenge. We learned that successful human-agent collaboration depends less on automating every step than on making state, authorship, evidence boundaries, and handoffs explicit. Like Comment Story Updates 1 A natural-language investigation request leads the agent to autonomously discover and invoke EvidenceFlow’s WebMCP tools. Chrome WebMCP Tool Activity confirms the full workflow: incident discovery, evidence retrieval, and finding creation. An evidence-linked AI finding enters EvidenceFlow as pending-human-review, with confidence and human review controls visible. Human review remains meaningful: the investigator requests more evidence when the AI conclusion goes beyond what the evidence supports. Inspiration Cyber incident investigations require analysts to distinguish carefully between what the evidence actually shows and what is merely an interpretation or hypothesis. AI agents can help investigate, summarize, correlate, and organize large amounts of technical evidence. But their conclusions should remain traceable to the underlying data and subject to meaningful human review. EvidenceFlow was inspired by that problem: how can humans and AI agents investigate cybersecurity evidence together without losing the distinction between evidence, inference, and validated conclusions? What it does EvidenceFlow is a human-agent workspace for cybersecurity incident investigation. Using WebMCP, an AI agent can: discover available incidents; retrieve structured incident evidence; analyze events chronologically; propose a finding linked to specific evidence IDs; assign a confidence level; recommend a next investigative action. Every agent-generated finding enters the application as pending-human-review . A human investigator can then Approve, Reject, or request more evidence through the application interface. EvidenceFlow deliberately exposes no WebMCP tool for approving or rejecting findings. Validation remains a separate human-review step outside the WebMCP tool surface. The current demo uses a synthetic SSH authentication incident. How I built it EvidenceFlow is a static web application built with HTML, CSS, and JavaScript and deployed through GitHub Pages. The application exposes three browser-native WebMCP tools through document.modelContext : list_incidents get_incident_events propose_finding Together they create the agent workflow: incident → evidence → agent analysis → evidence-grounded proposal → human review The implementation also treats incident evidence as untrusted data and includes bounded inputs, evidence-reference validation, duplicate-reference rejection, text-only DOM rendering, and mandatory pending-human-review status for agent proposals. I tested the tools in Chrome with WebMCP support and the WebMCP Model Context Tool Inspector on the public GitHub Pages deployment. I also validated an agent-driven investigation workflow in which the agent autonomously selected and executed the registered WebMCP tools from a natural-language investigation request. Challenges I ran into One challenge was designing the boundary between agent capability and human authority. It would have been easy to expose a tool that allowed the agent to complete the entire workflow automatically. Instead, I chose to make proposal and validation separate operations. Another challenge was WebMCP client interoperability. Different agent environments behaved differently when discovering and invoking browser-exposed tools. Direct testing through Chrome and the WebMCP Model Context Tool Inspector helped distinguish EvidenceFlow’s WebMCP behavior from client-specific orchestration behavior. I also performed a security review of the WebMCP interaction surface and added limits and validation to prevent oversized or malformed agent inputs from unnecessarily consuming browser resources. Key accomplishments EvidenceFlow demonstrates an integrated WebMCP investigation workflow rather than simply exposing isolated tools. From a natural-language investigation request, an agent can discover an incident, retrieve structured evidence, analyze that evidence, and create a proposed finding linked to specific evidence IDs. The resulting finding is not automatically validated. It enters the application as pending-human-review , preserving a clear boundary between agent-generated analysis and human validation. The prototype makes three stages of the investigation explicit: evidence → inference → human review That separation became one of the central design principles of EvidenceFlow. What I learned I learned that exposing an application to AI agents is not only about giving the agent more capabilities. Tool boundaries, data provenance, validation, failure behavior, and human oversight all become part of the application design. WebMCP provides an interesting way to make those capabilities explicit at the browser level rather than requiring an agent to infer application behavior only from the visual interface. My background is in law and digital law rather than software engineering, and that strongly influenced this approach: traceability, evidence, authority, and review became design requirements rather than secondary considerations. What's next for EvidenceFlow The current prototype intentionally uses synthetic evidence and does not connect to live security infrastructure. A future architecture could ingest and normalize evidence from systems such as: SIEM / EDR / IDS / firewalls / authentication systems / cloud logs and expose that normalized investigation context to agents through the same WebMCP layer. Future versions could also add authenticated backends, persistent audit trails, reviewer identity and authorization, incident-ingestion pipelines, and integrations with real security platforms. The long-term idea is not to replace existing security infrastructure, but to add a controlled human-agent investigation layer on top of it. ABOUT TEXT (untrusted evidence):
A shared economic laboratory where humans and AI agents investigate, manipulate, explain, and test the same visible country through WebMCP. Like Comment Story Updates Inspiration Most web agents still have to infer what a page means from pixels, text, and UI controls. That works for simple interactions, but it becomes brittle when the application has domain state, history, causality, and actions with different safety implications. CountryLab explores a different model: the webpage itself exposes the semantic operations an agent actually needs. What it does CountryLab is an interactive miniature country with a deterministic economy. A human can inspect regions and metrics, change interest rates, taxes, spending, and tariffs, trigger shocks such as floods or oil shocks, and advance the simulation through time. The same application exposes 17 semantic WebMCP tools to an agent. Instead of scraping charts or clicking blindly, the agent can: read the exact current country state; inspect regions and sectors; query event, metric, and causal history; make explicitly requested live policy or event changes; run isolated counterfactual experiments without overwriting the live country; and visibly focus the map, WHY inspector, or scenario comparison so the human sees the same evidence. The flagship workflow is: A human floods the port and advances the simulation. The agent observes the changed world through WebMCP. It investigates event, region, metric, and causal history. It traces a chain such as flood → trade/import disruption → supply pressure → inflation . The human asks the agent to prove the claim without changing the live country. CountryLab creates an isolated alternate timeline that removes only the selected flood and replays later interventions at their original points in time. The agent compares both timelines and opens the result in the webpage. The original live country remains unchanged. Why WebMCP is a strong fit CountryLab depends on domain semantics that are difficult and unreliable to recover through ordinary browser automation. An agent should not have to infer numeric state from charts, reconstruct chronology from visual labels, or guess whether an action mutates the live simulation or runs a safe experiment. WebMCP gives the agent structured access to: exact simulation state instead of visual inference; stable region, sector, event, snapshot, and scenario identifiers; bounded metric and event history; deterministic causal provenance; explicit live-world actions; isolated counterfactual experimentation; and visible UI-focus tools that return the agent's reasoning to the human interface. This turns the webpage into a shared experimental instrument rather than a collection of buttons for an agent to automate. How it improves the user experience Without WebMCP, an agent would need to infer values and chronology indirectly, reconstruct causal relationships from presentation, and simulate UI clicks to manipulate the country. That is brittle and loses the important distinction between observation, live mutation, and isolated experimentation. With WebMCP, the agent can begin read-only, understand exactly what the human changed, gather deterministic evidence, run a safe alternate timeline, compare outcomes, and visibly show the proof. Human actions are immediately visible to subsequent agent reads, and agent live actions immediately update the same interface because both use the same application-service and shared-state layer. What humans and agents can do together A human can create a disaster or policy situation visually and ask open-ended questions such as: “Something changed. Investigate what happened.” “Why did inflation rise? Show me the chain.” “Prove the flood caused the increase, but do not change my live country.” The agent can independently gather evidence, identify the relevant event and metrics, retrieve deterministic causal provenance, formulate a counterfactual test, run the alternate timeline, compare outcomes, and open the visible comparison for the human. The human can intervene again at any time, and the next WebMCP read observes the same updated world. How WebMCP was implemented CountryLab uses the imperative document.modelContext.registerTool(...) API with capability detection and registration-scoped AbortSignal cleanup. The 17 tools are grouped into four categories: Observation: country state, region/sector inspection, metric history, event history, causal history. Explicit live mutations: policy changes, shocks, emergency response, time advancement, snapshots. Isolated experiments: counterfactual runs and scenario comparison. Visible explanation: region highlighting, metric focus, causal-chain display, and scenario-comparison display. Tool schemas use strict object shapes, enums, numeric bounds, and additionalProperties: false . Read-only tools carry readOnlyHint: true . Live mutation tools explicitly describe their effects. The WebMCP layer does not contain economic formulas. Both the React/Phaser human interface and WebMCP actions use the same application service and Zustand state over the deterministic economy engine. Counterfactual event removal branches from saved event-time checkpoints and replays subsequent recorded live interventions into both branches. That allows the comparison to mean “same later history, except this event,” while keeping the live world untouched. Testing CountryLab has been tested with ChatGPT's WebMCP-capable agent browser. The deployed app exposes exactly 17 CountryLab tools and the human UI continues to work normally when WebMCP is unavailable. A recommended judge flow is: Open the live site. Trigger Flood · Port and advance six months. Ask: “Something changed. Investigate what happened.” Ask: “Why did inflation rise? Show me the chain.” Ask: “Prove the flood caused the increase, but do not change my live country.” Confirm the scenario comparison opens and the live world remains unchanged. Built with React, Phaser, TypeScript, Zustand, Vite, WebMCP, and a deterministic in-browser economy/counterfactual engine. Accuracy note CountryLab is an educational toy causal model. It demonstrates transparent directional relationships and deterministic experimentation; it is not a real-world economic forecasting or policy-advice system.
