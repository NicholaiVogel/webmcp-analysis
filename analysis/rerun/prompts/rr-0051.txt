# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Main Page Select your seat with AI Inspiration Buying tickets looks simple until real-world constraints appear: a group needs seats together, the budget is total rather than per seat, someone prefers a specific zone, accessibility matters, and availability may change while options are being compared. Traditional interfaces leave the user repeatedly adjusting filters and visually scanning a large map. We built Ticketnauta Seat Concierge to explore a better model: let an AI agent handle the combinatorial search while the person keeps visual context, judgment, and control. Seat selection is an ideal WebMCP use case because it combines structured data, live page state, visual comparison, and consequential actions such as temporary holds. The project is a completely isolated demonstration. It does not connect to real Ticketnauta inventory, customers, sessions, payments, or production APIs. What it does Ticketnauta Seat Concierge lets people and browser agents collaborate on the same interactive seat map. A user can ask: Find four contiguous seats under MX$7,000, prioritize centered seats, show me alternatives, and ask before holding the best option. A compatible browser agent can then use nine purpose-built WebMCP tools to: Search fictional events. Inspect event details, zones, prices, and availability. Find contiguous seat combinations by quantity, total budget, zone, and priority. Highlight recommended seats on the visible map. Select an option. Create or release a temporary hold. Read the cart and hold expiration. Complete an explicitly confirmed simulated checkout. The interface shows ranked alternatives, accessible-seat markers, selected seats, unavailable seats, prices by zone, a cart summary, and a live hold countdown. Every agent action is reflected immediately on the page. The conversation timeline distinguishes built-in guided interactions from actual browser-agent calls using separate GUIDED and WEBMCP labels. This makes the experience transparent and avoids presenting a local command parser as an external AI agent. Every event, venue, seat, price, hold, and checkout result in the demo is fictional. No payment is collected and no ticket is issued. How we built it The WebMCP tools are registered directly from the main document—without an iframe—using document.modelContext.registerTool() . Each tool has a narrow JSON Schema, rejects undeclared properties, and reuses the same application functions as the visible interface. This keeps manual interactions, guided requests, and browser-agent calls synchronized. We deliberately separated tool responsibilities: Read-only tools handle event search, details, seat recommendations, and cart state. Visual page actions handle highlighting and selection. Consequential actions handle holds, release, and simulated checkout. Checkout requires the explicit confirmation value SIMULATE_CHECKOUT . The frontend uses dependency-free HTML, CSS, JavaScript, and an interactive SVG seat map. The backend is a .NET 10 ASP.NET Core Minimal API using Npgsql and PostgreSQL . An idempotent bootstrap creates and seeds only the isolated webmcp_demo PostgreSQL schema. Temporary holds use transactional availability checks and event-level locking to prevent conflicting reservations. Expired holds become available again, and the reset operation deletes only runtime demo records. The application is packaged with a multi-stage Dockerfile and Docker Compose. It includes health checks, Windows/WSL/Linux instructions, an optional self-contained PostgreSQL profile, and a Cloudflare Tunnel profile. The public demonstration runs through HTTPS without opening router ports. Challenges we ran into The first challenge was designing tools at the correct level. A single tool that “buys the best seats” would hide too many decisions, while extremely small tools would force the agent to reproduce ordinary UI automation. We designed a focused middle layer where discovery, recommendation, visual feedback, selection, holds, and checkout remain separate. Another challenge was keeping three interaction paths synchronized: manual controls, the guided concierge, and external WebMCP calls. Every path had to update the same map, recommendations, cart, and activity timeline without creating contradictory state. Seat recommendations also required more than sorting by price. The algorithm must preserve contiguity, enforce a total budget, consider zones and accessibility, rank proximity or center position, and still return useful alternatives. Temporary holds introduced concurrency and expiration concerns. We addressed these with PostgreSQL transactions, availability checks, advisory locking, explicit release, and automatic expiration. Finally, WebMCP is still experimental and requires a compatible browser agent and a secure HTTPS context. We built a deterministic guided experience so visitors can understand the product even without WebMCP support, while clearly identifying which calls come from a real browser agent. Accomplishments that we're proud of We are proud that this is a complete, working journey rather than a static interface or isolated tool demonstration. The project includes: Nine discoverable WebMCP tools with strict schemas. A responsive and accessible interactive seat map. Multi-constraint contiguous-seat recommendations. Visible alternatives and map highlighting. PostgreSQL-backed temporary holds and expiration. Explicit release and simulated checkout flows. A transparent activity timeline for human and agent actions. A fully isolated fictional dataset. A reproducible .NET 10, PostgreSQL, Docker, and Cloudflare deployment. Most importantly, the agent does not replace the interface. It collaborates through it, and the person can see and evaluate every meaningful action. What we learned We learned that WebMCP is not simply a way to add a chatbot to a website. Its real value is giving an agent a structured, browser-mediated contract for what the page can safely do. Tool design is product design. Names, descriptions, schemas, result shapes, and action boundaries directly influence whether an agent behaves predictably. We also learned that visual transparency remains essential. Even when an agent can find the mathematically best option, people still want to compare alternatives, understand tradeoffs, inspect the map, and approve consequential actions. Finally, separating read-only operations from state-changing actions makes both the implementation and the user experience easier to reason about. What's next for Ticketnauta Seat Concierge Next, we would expand the fictional demo with richer venue layouts, additional accessibility preferences, multilingual requests, more detailed explanations for recommendation scores, and automated WebMCP regression tests. We would also explore configurable approval policies so users can decide which actions an agent may perform automatically and which always require confirmation. The larger vision is an open web where agents do not need to guess how interfaces work from pixels. Websites can expose safe, narrow, purpose-built capabilities while people retain context, visibility, and final control.
