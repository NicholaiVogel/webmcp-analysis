Like Comment Story Updates demo What's next for blockchain-agent-treasury Inspiration AI agents can move quickly, but payments should not require giving an agent a private key or asking it to guess through wallet UI. We built x402 Agent Treasury around a safer division of labor: the agent handles discovery and exact preparation, while the person keeps custody and makes the final signing decision. What it does The deployed app exposes seven narrow WebMCP tools directly from the page. An agent can: list five configured EVM, Solana, and Gno payment rails distinguish testnet-ready paths from independently locked mainnets prepare wallet-bound, short-lived x402 terms inspect the live Gno Pearl gateway and scheduled indexer search canonical Pearl activity open the matching human review screen retrieve one exact durable payment receipt The consequential boundary stays visible. Preparation never signs or settles. The wallet review shows network, asset, amount, recipient, payer, resource, and expiry before a person approves. How we built it The application uses Next.js, React, and TypeScript on Vercel, with Neon PostgreSQL as the authoritative challenge, payment, and audit store. The top-level page registers imperative tools through document.modelContext.registerTool(). Each tool has a strict JSON Schema, bounded output, cancellation support, and read-only or state-changing annotations. The chain-neutral payment layer supports Base Sepolia USDC through EIP-1193 and EIP-712/EIP-3009, Solana Devnet USDC through Wallet Standard and a sponsored v0 transaction, and Gno Pearl WUGNOT through Adena and TM2 RPC. Ethereum, Solana, and Gno mainnet paths remain independently fail-closed. Server-issued challenge IDs, payment IDs, expected payer, recipient, amount, asset, resource hash, expiry, and unsigned payload fingerprints are bound together. The server rechecks the terms immediately before signing and prevents replay or cross-challenge substitution. Chrome support is delivered as a progressive enhancement with explicit origin isolation and a same-origin WebMCP permissions policy. The same deployed page also works in ChatGPT's in-app browser. Challenges we ran into The hardest part was preserving human authority without reducing WebMCP to a read-only demo. The agent needed enough power to prepare useful work, but not enough power to silently change recipients, tokens, networks, or settlement endpoints. Multichain signing also differs significantly. EVM uses typed authorization, Solana uses a short-lived blockhash and signed v0 message, and Gno uses Adena-encoded transactions. We kept one agent-facing workflow while retaining chain-specific verification. Chrome's experimental implementation additionally requires the testing flag and an origin-isolated document. We added explicit Origin-Agent-Cluster and tools permissions headers and verified that all seven registrations complete in a fresh Chrome tab. Accomplishments that we're proud of a working public WebMCP deployment with seven registered tools one coherent human-agent handoff across three chain families independently locked mainnet gates durable PostgreSQL challenge and receipt records tamper, replay, policy, settlement, and WebMCP safety coverage 119 automated tests passing on the submission build What we learned Agent-native interfaces are strongest when tools expose intent and constraints, not when they merely automate clicks. For sensitive actions, a prepared object shared by the agent, server, UI, and wallet is a better collaboration primitive than an invisible autonomous action. What's next We plan to add continuously indexed Gno activity, complete recorded real-wallet testnet acceptance on every rail, and expand the same human-approved pattern to paid compute and storage workflows. The Friction Before Stargazing There is a gap between being interested in the night sky and actually going outside to observe it. Someone might think: I want to see the stars tonight. I wonder what I can see while traveling. I want to go stargazing with my kids. But turning that interest into an actual observation requires several decisions. Beginners need to figure out: What is visible from their location When to observe Which direction to look Which stars are easy to find How twilight and city lights affect visibility What to record during the observation Surveys of the general public in Japan show a noticeable drop-off between people who consciously look at the Moon and stars and those who go on to use telescopes or attend stargazing events. The problem is not simply a lack of interest in astronomy. There is friction between curiosity and action. Interactive Star Lab turns “I want to see the stars” into an actionable observation plan. A Different Approach from Smartphone Star Maps Modern smartphone astronomy apps are already very good at answering: What is that star above me? Using GPS, cameras, orientation sensors, and AR, they can help users identify objects in the sky with very little setup. Interactive Star Lab is not intended to replace that experience. It focuses on an earlier question: I want to observe the sky soon. What should I look for, and how should I prepare? Astronomy software can expose precise controls for latitude, longitude, date, time, azimuth, altitude, field of view, magnitude, light pollution, and other conditions. That flexibility is useful for experienced users. A beginner who says, “I want to spend 30 minutes stargazing in Hakata at 8 PM tomorrow,” however, probably does not want to translate that goal into a set of astronomical parameters. Interactive Star Lab takes a different approach. It runs in a web browser and does not depend on AR or a particular set of device sensors. Instead of adding more controls, it tries to reduce the number of decisions a user has to make before starting an observation. Turning Intent into Settings with WebMCP WebMCP connects a user's intent to the astronomy application. For example, a user can ask an Agent: I want to stargaze in Hakata for about 30 minutes at 8 PM tomorrow. Pick a few stars that are easy for a beginner to find and create an observation plan. The user does not need to look up Hakata's latitude and longitude. The Agent can interpret “Hakata,” resolve it to geographic coordinates, and pass those values to Interactive Star Lab through WebMCP. The same approach works for places that are not built into the application as presets, such as: Near Osaka Castle Around the Fukuoka City Science Museum Near a hotel while traveling The application therefore does not need a predefined list of every possible observing location. The LLM handles human expressions and incomplete intent. Interactive Star Lab handles deterministic astronomical calculations from location and time. AI can handle the ambiguity. The astronomy engine handles the precision. Instead of asking the user to decompose a goal into configuration fields, WebMCP lets the Agent translate that goal into application operations. From an Observation Plan to the Real Sky Interactive Star Lab calculates the sky for a specified location and time and supports the workflow from planning to observation. Sky Simulation The application displays the sky for a selected location, date, time, and viewing direction. It can show stars, star names, constellation lines, and constellation names.
