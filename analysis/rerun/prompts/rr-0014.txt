Like Comment Story Updates Inspiration WebMCP solves an important problem for agentic websites: instead of forcing an AI agent to guess at a page's DOM, a site can expose explicit, typed tools. But that creates a second question: How do you give an AI agent enough power to be genuinely useful without also giving it the authority to approve its own actions? For consequential systems, that distinction matters. An agent may need to investigate, challenge, repair, or prepare an action — while approval must remain somewhere else. Release Sentinel explores that boundary using software release approval as a concrete test case. Our principle is simple: agent acts → Gatekeeper decides → human verifies What it does Release Sentinel is a WebMCP-powered security lab for AI-assisted software releases. A vulnerable software release begins at NO_GO . The AI agent receives useful capabilities through WebMCP. It can inspect the release, inspect the trust boundary, run bounded attacks, compare gate revisions, find and minimize counterexamples, propose remediation, rebuild a candidate, and request fresh verification. What it cannot do is authorize the release. The demo first lets the agent try the available attacks against the authority boundary. Advisory GO votes, replay attempts, forged authority, evidence tampering, severity downgrades, blocker deletion attempts, and prompt injection still do not give the agent release authority. So the agent has to solve the real problem instead. It compares the production gate against an independent Coverage Arena reference oracle, identifies an observed security escape, minimizes it, and creates a bounded remediation proposal. That proposal is explicitly PROPOSAL_ONLY . The candidate is then rebuilt to a new SHA-256, fresh evidence is generated, and the deterministic Gatekeeper performs verification again. Only the Gatekeeper can return the final GO or NO_GO . A human can independently verify the resulting proof context, but human verification is not release authority either. How we built it The browser registers exactly 12 typed WebMCP tools through document.modelContext.registerTool() . They are divided into three capability classes: READ — inspect release state, trust boundaries, coverage, and proofs CHALLENGE — run attacks and find counterexamples PROPOSE — request bounded remediation and rebuilding There is intentionally no set_verdict , force_go , arbitrary shell execution, arbitrary filesystem access, evidence editor, policy-disable tool, or Gatekeeper override. That absence is tested as part of the security contract. Inputs use strict schemas with bounded enums and forbidden extra fields. The agent selects package-owned identities rather than supplying arbitrary source code, fixture paths, or executable content. We also built run_attack_suite as browser-side composition instead of adding a more powerful server endpoint. It reads the bounded attack catalog and invokes the same registered attack capability repeatedly. The browser gets better ergonomics without expanding server authority. The release decision itself remains in a separate deterministic Go Gatekeeper using signed, hash-bound evidence. Challenges we ran into The hardest challenge was making the security model understandable. An earlier version of the Proof Arena was technically accurate but difficult to read. A judge would encounter concepts such as proof-context binding, overblocks, and PROPOSAL_ONLY before understanding the story. We added a guided demo and plain-language narration without weakening the security model. Another challenge was resisting convenient shortcuts. For example, implementing the attack suite as one powerful server endpoint would have been easy. Instead, we kept the server surface narrow and composed the workflow in the browser over the existing bounded tools. That required more work, but better demonstrates the architectural value of WebMCP. Accomplishments that we're proud of The final system demonstrates a useful agent that remains structurally unable to authorize its own success. The agent can attack the release gate, identify a real weakness, propose a fix, rebuild the software, and request verification — yet final authority remains outside the WebMCP capability plane. The project also includes: 12 typed WebMCP tools strict bounded schemas agent-readable recovery errors browser-side capability composition an independent Coverage Arena a deterministic Go Gatekeeper signed and hash-bound evidence source-hash transition visibility a Human Proof Checkpoint frozen trust and coverage kernel manifests Python, Go race, browser, and WebMCP contract verification What we learned WebMCP is not only about making browser agents more capable. The more important architectural question is which capabilities should never become authority . Typed tools make agent interaction clearer, but tool design also defines the security boundary. The capabilities that are deliberately absent can be just as important as the capabilities that are exposed. We also learned that browser-side composition is a powerful WebMCP pattern: useful agent workflows can become more ergonomic without automatically creating broader server privileges. What's next Release approval is our test case, but the pattern is broader. Any consequential website may need agents that can act without being allowed to authorize — for example administrative systems, payments, infrastructure, or other sensitive workflows. The next step would be turning this pattern into a reusable primitive: capability classes plus a verifiable assertion that final authority is not reachable from the WebMCP capability plane. In mechanical engineering, having a good idea is only the beginning. The idea must become real geometry, materials, joints, forces, sensors, controls, and measurable results. In web development, I learned how a good interface and AI can make a complicated tool easier for more people to use. This made me ask one question: What if AI could do more than generate a picture or description of a machine? What if it could enter the same engineering workspace as the human, build the machine part by part, test it, see what failed, and improve it? This is why I built ForgeTwin. I wanted someone to describe a physical goal in normal language, without knowing every CAD command, and then watch an AI agent turn that goal into an editable, animated, and testable mechanical system. As an engineer, one principle was very important to me: A design should not be trusted only because it looks convincing. It should be tested with physics and evidence. Don’t generate it. Engineer it. What it does ForgeTwin is a browser-based AI engineering sandbox. The user describes a machine or mechanical goal, and ForgeTwin creates a versioned physical world from reusable parts. For example, a user can ask: “Build a conveyor that sorts red and blue boxes at 20 boxes per minute.” “Build an electric go-kart with four wheels, steering, accelerator and brake pedals.” “Build a brazing fixture that positions a heat exchanger and two copper pipes within 2 mm.” ForgeTwin then: Understands the requested machine, functions, and measurable requirements. Creates an engineering plan instead of returning only text. Breaks the design into assemblies and reusable low-level components. Gives every component dimensions, material, mass, position, and orientation. Adds physical connections, joints, motors, sensors, actuators, and control logic. Builds the machine in an interactive 3D workspace while the user watches. Runs a fixed-step 60 Hz Rapier simulation. Reads telemetry, collisions, movement, and requirement measurements. Finds the reason when a requirement fails. Changes the related geometry, physical property, actuator, motor, or controller and runs the test again. The app is not limited to conveyors. Its 39-part reusable vocabulary covers structures, power transmission, controls, road vehicles, motorcycles, aircraft, rotorcraft, tracked mobility, and articulated robots. It can compose cranes, lifts, bicycles, go-karts, motorcycles, cars, rovers, robotic arms, humanoid robots, gearboxes, suspension systems, airplanes, helicopters, solar trackers, bridges, warehouse systems, agriculture machines, recycling systems, HVAC fixtures, medical lifting mechanisms, and new systems made from smaller primitives. The current app includes 19 editable challenge briefs , but these are examples, not locked machine templates. The user can change the prompt, dimensions, load, speed, or target. If a special component is not already available, the planner can build it from lower-level parts such as beams, plates, tubes, shafts, wheels, pulleys, joints, sensors, and motors. The user can also: Use the built-in AI without entering credentials, or temporarily use their own OpenAI API key. Edit the existing design with natural-language chat instead of starting over. Select, move, resize, and rotate parts in X, Y, and Z. Orbit the full camera through 360 degrees with mouse or touch. Use a rotation gizmo, snapping, or numeric angle entry. Lock a manual change so the AI redesigns around it instead of moving it back. Animate the operating sequence of different machine families. Run physics and replay a failure in slow motion. Use X-Ray Mode to inspect joints, sensor paths, axes, collision boxes, actuator paths, and velocity information. Inspect requirement evidence and see what passed, failed, or was not evaluated. Undo changes, restore revisions, and compare a failed design with the improved design. Export the current world as PNG, JPG, PDF, STL exchange geometry, or complete ForgeTwin JSON data. How I built it ForgeTwin is built with Next.js, React, TypeScript, Tailwind CSS, Three.js, React Three Fiber, Drei, Rapier, and Zod . The main idea is that the machine is not saved as one opaque 3D model. It is stored as a shared engineering graph containing: Assemblies and individual bodies Dimensions, materials, mass, and rigid-body properties Position, rotation, and machine orientation Mechanical, power, and signal connections Fixed, revolute, prismatic, spherical, spring, rope, gear, and belt joints Motors, sensors, actuators, and control rules Simulation runs, telemetry, collisions, and failure evidence Human-owned edits and immutable revision history The 3D editor renders this graph procedurally. The same graph is used by the human interface, the built-in model agent, the physics simulator, the activity feed, exports, and an external WebMCP agent. The hosted AI uses GPT-5.6 Sol through the OpenAI Responses API . To keep generation faster and more reliable, the model creates a compact engineering intent: the object identity, architecture, motion, controls, primitive vocabulary, and requirements. ForgeTwin then expands that intent into the complete body-and-joint graph, validates it, repairs safe topology problems, and executes the design through guarded tools. The hosted key stays on the server, so judges can use the full AI experience without adding a key. A visitor can still connect their own key for the current browser tab. That key is kept only in memory and is not stored. If model access is unavailable, ForgeTwin also has a deterministic local engineering path for the main design, physics, optimization, and supported chat-edit operations. I also created one universal coordinate convention for every machine: +X is front, -X is rear, +Y is up, -Z is left, and +Z is right . This helped fix many problems with lights, wheels, propellers, steering, windshields, and joint axes. The design validator checks for missing supports, hubs, axles, joints, steering links, bad proportions, wrong orientations, floating components, incorrect joint axes, overlaps, blocked windshields, and unrequested systems. For example, a go-kart uses front wheel hubs, spindles, steering knuckles, separate kingpin axes, tie rods, a steering rack, column, and Ackermann-style steering instead of making the whole wheel rotate around one incorrect axis. Rapier runs the connected rigid-body world at a fixed 60 Hz and records replay frames and collision events. Some advanced engineering results, including aerodynamics, flexible cables, structural stress, detailed tire behavior, and some manufacturing processes, still use clearly labeled reduced-order checks. ForgeTwin is a concept-validation sandbox, not a replacement for certified CAD, FEA, CFD, medical approval, or safety analysis. Why WebMCP is essential WebMCP is what makes ForgeTwin an AI-operable engineering workspace instead of only a website with an AI button. ForgeTwin exposes 29 small, typed, state-aware WebMCP tools , including: inspect_workspace inspect_primitive_catalog set_design_goal create_assembly create_component set_dimensions , set_material , and set_mass move_component and rotate_component connect_components and create_joint add_motor , add_sensor , and add_actuator set_motor_speed , set_sensor_range , and set_actuator_timing set_control_logic and update_control_logic run_simulation inspect_telemetry , inspect_failure , and measure_constraint optimize_design remove_component and remove_joint compare_designs and restore_revision I did not create one giant generate_machine tool. Like Comment Story Updates Diagram Canvas Export as Mermaid WebMCP Invocation Logs Available Architecture Nodes Available Process Nodes Node Inspector Inspiration Architecture diagrams live in slides and whiteboards, but AI agents usually scrape the DOM or dump Mermaid in chat. When I saw the WebMCP Challenge, I wanted a canvas where agents work on structured graph semantics , not pixels, on the same page as the engineer. What it does ArchFlow is a browser-native architecture diagram editor powered by WebMCP. Describe a system in plain language; a browser agent builds it on the canvas through structured tools. You approve every structural change, see tool calls in an activity log, and co-edit the same live graph — add nodes manually, let the agent adapt, auto-layout, annotate, validate, export Mermaid. Live demo: https://archflow-two-xi.vercel.app How we built it Fully frontend — React, TypeScript, Vite, React Flow, Zustand, Ajv, Dagre. No backend, no LLM API keys. The graph is the source of truth. 13 WebMCP tools on document.modelContext expose read, mutate, layout, validate, annotate, and diff operations. Mutations go through an operation engine and a human approval modal before applying. Deployed on Vercel. Challenges we ran into WebMCP is experimental — API surface and registration timing vary by browser Agents need structured operations, not DOM scraping Balancing safety (approval modals) with speed (batch ops, auto-approve mode) Atomic multi-step changes with temp IDs and single-step undo Accomplishments that we're proud of Agent builds a full architecture from a blank canvas via natural language 13 real WebMCP tools with JSON Schema validation Human-in-the-loop approval with zero mutation on reject Fully frontend, open source (MIT), live on Vercel What we learned ArchFlow doesn't embed an LLM — the browser agent is the AI, and the website is the tool server. That kept the app fully frontend with no API keys, while still enabling real collaboration. WebMCP replaces fragile DOM scraping with structured tool calls — agents discover capabilities, invoke them with typed inputs, and get deterministic results back. Tool design matters as much as the UI: schemas, descriptions, batch semantics, and approval flows all shape how well agents actually work. Human-in-the-loop isn't a limitation — engineers want to inspect and approve changes, not have agents silently rewrite their diagrams. What's next for ArchFlow Near term: C4 and BPMN views, Mermaid/Terraform import, richer validation (PII flows, single points of failure, latency budgets). Medium term: Diagram diffs between versions, templates for common patterns (event-driven, serverless, multi-tenant SaaS), and linking nodes to real resources like repos or cloud services. Long term: Multiplayer editing with WebMCP as the agent interface, team workspaces with review workflows, and exports into design docs and ADRs. The goal stays the same: humans sketch visually, agents refactor structurally, both on one live graph.
