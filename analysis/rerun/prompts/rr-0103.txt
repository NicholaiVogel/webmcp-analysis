A WebMCP workbench where you and a browser agent triage a network's MACs on one surface: paste raw ARP/DHCP dumps, enrich every address against macadress.com, filter, and export an allowlist. Like Comment Story Updates Mac Inventory WorkBench Sample Data Mac Address Enrichment Export Options ChatGPT Agent Interaction Inspiration Anyone who has done network cleanup knows the loop. You pull an ARP table off a switch, or a DHCP lease file, or a page of nmap output, and you are staring at 150 MAC addresses. Which ones are real devices? Which are VMs? Which are phones cycling through randomized addresses so they never look the same twice? Which OUI was never registered with the IEEE at all? The honest answer is usually a spreadsheet on one monitor and a vendor-lookup site on the other, and an hour of alt-tab. The WebMCP Challenge asked for something specific: a page where a human and a browser agent work the same surface, not a chatbot bolted onto a UI. Network triage turned out to be a near perfect fit. The task is tedious, it is full of small judgment calls, and it produces an artifact someone actually applies afterward: a firewall allowlist. macadress.com already solved the hard part behind an API (OUI and IEEE registration data, device-class inference, virtualization fingerprints, randomization scoring), so the workbench itself could stay thin and honest. What it does Paste raw text. The app extracts every MAC in any common format (colon, hyphen, Cisco dotted, bare hex), enriches each one against macadress.com, and drops the results into a table you can slice by vendor, device category, virtualization platform, "randomized," or "unregistered." When the slice looks right, you export it as an nftables set, a Zeek annotation file, or CSV. Every button on the page is also a WebMCP tool. There are eight: add_mac_addresses , load_sample_data , lookup_mac , enrich_inventory , summarize_inventory , filter_inventory , export_filter_list , clear_inventory . The agent and the person edit one inventory. There is no separate agent view and no "agent mode." If the agent filters to virtualized hosts and builds an nftables set, the human watches it happen in the same table and export box they would have used by hand. How we built it Two pieces, no build step. web/ is static HTML, CSS, and JavaScript. The design rule was one shared state object. app.js defines an ops object with the actual operations. The on-page buttons call ops . The WebMCP tool handlers call ops . Because both paths mutate the same Map of rows and the same listener set re-renders the table, the human sees the agent's work land row by row, and the reverse. web/wmcp.js is the only file that touches the WebMCP spec, on purpose. It resolves the host object ( document.modelContext , falling back to navigator.modelContext ) and supports both the modern registerTool({ name, description, inputSchema, execute }) shape and the older bulk provideContext({ tools }) shape. It wraps every handler so a handler can return a plain JavaScript object and the adapter stringifies it, since execute is required to resolve to a string. worker/ is a Cloudflare Worker that proxies api.macadress.com . The API key lives as a Wrangler secret and never reaches the browser. The Worker also enforces a route allowlist (single lookup and a capped batch only), a per-IP rate limit, and a CORS origin pin. The math that matters A MAC address is 48 bits, so there are 2^48 of them, roughly 2.8 x 10^14. The IEEE hands out the top 24 bits as the OUI and the vendor owns the bottom 24, which is 2^24, or 16,777,216 addresses per registration. Randomized addresses are the reason a hand-built allowlist rots. The naive detector is a single bit: the locally-administered bit, the second-least- significant bit of the first octet. Write b for that octet and use the wedge for bitwise AND: $$b \land \mathtt{0x02} \neq 0 .$$ That flag is necessary but not sufficient, because plenty of legitimate hardware is locally administered. macadress.com layers a confidence score on top, and the workbench only marks a row as randomized when the API returns potentially_randomized with confidence possible or likely . Enrichment runs in batches of 40, so the cost is one upstream call per 40 addresses, with a per-row fallback if the batch endpoint misbehaves. Challenges we ran into The WebMCP surface is still moving. Different runtimes expose different objects and different registration methods. Isolating every assumption into wmcp.js meant the rest of the app never had to care, and a spec change is a one-file diff. Tools have to return strings, but useful strings. A handler that returns { found: 12, added: 9 } is easy to write. Making sure the agent gets back something it can reason about took a pass over every return value and every tool description. The descriptions are the real API, so they say when to call a tool, not just what it does. Percent-encoding broke lookups. The upstream API does not decode %3A , so a MAC sent as 00%3A11%3A22... fails. The Worker forwards the colons and dashes intact and only decodes a caller that pre-encoded, so both callers end up identical. A public Worker URL cannot hold a real secret. The answer was layers instead of one wall: a dedicated low-quota key, an edge WAF rule that rejects any request whose Origin is not the demo page, a rate limit, and a rotatable friction token shipped in config.js . None of them is cryptographic alone. Together they make an abused URL cap out fast. Demo limits during judging. Testing burned through the shared key more than once, so we added a bring-your-own-key path: paste a macadress.com key into the header, it is stored in that browser only and sent as X-Macadress-Key , and the Worker forwards it upstream while skipping the demo gate and the shared rate limit. Accomplishments that we're proud of One surface, zero duplicated logic. Eight buttons and eight tools route through a single ops object. There is no code path the agent can take that a human cannot, and none the human can take that the agent cannot. It degrades cleanly. With no WebMCP host present the page is a fully working manual tool. Open it in a WebMCP runtime and the same eight actions become agent tools, no reload. The spec coupling is one file. wmcp.js already absorbs two different host API shapes without the app noticing. The output is real. nftables sets, Zeek annotation files, and CSV that you can apply, not a demo-only artifact. A public demo that is safe to share , because the proxy leans on layered defense rather than a secret in the page, with BYOK as the escape hatch. What we learned The value of WebMCP is not "give an agent your API." It is that the agent and the human share one DOM-backed state, and the interesting design work is refusing to fork the view. Once ops existed, the tool layer was almost free, and progressive enhancement fell out for nothing. We also learned how much weight tool descriptions carry: with a good description the agent sequences filter_inventory then export_filter_list on its own, and with a vague one it guesses. What's next for MAC Inventory Workbench diff_inventory , so an agent can compare a fresh capture against last week's allowlist and report only what changed. More export targets : Suricata datasets, EdgeOS and MikroTik address lists, a Prometheus textfile for alerting on unknown MACs. Persist inventories so a triage session can be reopened, and so the diff has something to diff against. Push the same tool set through the other macadress.com integrations so the workbench and those connectors share one vocabulary. A WebMCP incident console where agents investigate production failures and humans stay in control of remediation. Like Comment Story Updates Inspiration Incident response is one of those workflows where an AI agent could genuinely save time, but it is also a workflow where giving an agent unrestricted control would be a terrible idea. During an outage, engineers jump between service health, deployments, logs, traces, alerts, runbooks, and incident timelines while trying to answer a few basic questions: What changed? What is actually failing? What evidence supports that diagnosis? And what is safe to do next? I wanted to explore what incident response looks like when the agent can work inside the same operational console as the human instead of operating through a separate chatbot or a disconnected API. That became Firebro . The design principle behind the project is simple: Agent capability, human authority. What it does Firebro is an incident response console built around WebMCP. An agent can investigate an active incident by checking service health, dependencies, recent deployments and changes, logs, traces, alerts, metrics, runbooks, and the incident timeline. It can correlate that evidence, identify a likely cause, and propose a remediation. For example, one incident starts with degraded checkout performance after a bad deployment. The agent can compare service metrics, inspect traces and logs, find the deployment that introduced the regression, and propose rolling it back. But the agent cannot simply execute a consequential remediation on its own. Actions such as a rollback can require an approval tied to the exact proposed action. The approval has to come from a real human interaction in the console before the action can proceed. Once remediation starts, the simulated production environment reacts. Metrics recover, logs change, and the incident moves through recovery and monitoring before it can be resolved. Firebro includes multiple deterministic incident scenarios so the correct response is not always "roll back the latest deployment." Some incidents involve resource exhaustion, feature flags, memory leaks, or even third-party failures where the best action may be to wait rather than make an unnecessary production change. How I built it Firebro is built as a web-based incident console with a WebMCP capability layer on top of the same operational state visible to the human operator. The system exposes tools across the full response workflow: incident discovery, service health, dependencies, deployments, recent changes, logs, traces, metric comparisons, alerts, runbooks, incident notes, remediation actions, approvals, and incident resolution. One of the main implementation goals was avoiding a separate "agent version" of the application. When an agent investigates something, the console reacts too. A service can be highlighted in the topology, log views can focus on relevant entries, metric comparisons become visible, traces can be surfaced, and approval requests appear next to the operational evidence the human needs to make a decision. Tool availability also depends on context. Capabilities can change based on the selected incident, current incident state, and what actions are currently valid. The backend runs a deterministic incident simulation. Each scenario has a known underlying cause, but that ground truth is intentionally hidden from the WebMCP tools. The agent has to diagnose the incident using the same observable evidence available through the console. Mutations and incident events are persisted so the UI and tool layer stay synchronized as the incident evolves. Challenges I ran into The hardest part was making the environment realistic enough that the agent actually had to investigate. If every incident simply had an obvious error message pointing to the answer, there would be no real diagnostic workflow. Firebro includes misleading signals and plausible alternatives so the agent has to correlate evidence instead of choosing the loudest symptom. Another challenge was tool design. Returning thousands of raw log lines or metric samples makes an agent less useful, not more useful. The tools needed to expose enough evidence to support a diagnosis without turning every response into an unstructured data dump. I also had to think carefully about approvals. A generic "approved: true" flag would not be enough for a real operational workflow. Approval has to be tied to the exact action being proposed so an approval for one operation cannot silently authorize another one. Keeping the simulation deterministic was another important challenge. The same incident needs to behave consistently enough for automated evaluation while still looking like a live operational system. Accomplishments that I'm proud of I'm most proud that Firebro feels like one shared workspace rather than a dashboard on one side and an agent on the other. The agent works with the same incident, graphs, logs, services, and actions the human is looking at. Investigation has visible consequences in the interface, and consequential actions pass through an approval workflow instead of bypassing the operator. I'm also proud of the incident simulation itself. Different scenarios require different forms of reasoning, and remediation does not always produce an immediate perfect recovery. Some actions only partially help, some have no effect, and the system can regress if the diagnosis was wrong. That makes it possible to evaluate more than whether an agent can successfully call a tool. What I learned The biggest thing I learned is that agentic interfaces need more than a large tool list. The useful part is the structure around those tools: when they are available, what evidence they return, how their effects appear to the human, and what happens when the agent is wrong. I also learned that human approval is much more useful when it happens next to the evidence supporting the action. Asking someone to approve a rollback in isolation is very different from asking them while they can see the deployment, affected metrics, traces, and the agent's proposed action in the same console. WebMCP also made browser context much more important than I originally expected. The agent is not operating a remote service in the abstract. It is operating the application the human currently has open. What's next for Firebro The current version uses deterministic simulated infrastructure so incidents can be reproduced and evaluated reliably. The next step would be connecting the same interaction model to real observability and incident-management systems while keeping the approval boundary intact. I'd also like to expand the scenario set, add more complex multi-service failures, improve automated agent evaluations, and explore richer policy controls for actions with different levels of operational risk. The long-term idea is not an autonomous system that replaces the incident commander. It is an incident console where an agent can do far more of the investigation and coordination work while the human keeps authority over decisions that can affect production. Copying a summary into another chat strips away that provenance and makes the handoff hard to verify. Gatherwire explores a simple answer: give a person and a browser agent the same visible workspace, then make a handoff a durable, source-linked product object instead of another disposable chat message. What it does Gatherwire is a public WebMCP collaboration workspace. A person can use it like a compact team room. From that same top-level page, a compatible browser agent discovers seven structured site tools: gatherwire_list_spaces gatherwire_read_messages gatherwire_search_messages gatherwire_list_project_agents gatherwire_publish_handoff gatherwire_post_message gatherwire_create_space The main demo is a five-call mission. The agent lists the spaces, finds a seeded handoff note, reads its source room, finds the available demo project agent, and publishes a handoff to Atlas in the product room using the source message ID as evidence. The result appears immediately in the human interface: a visible capsule with a summary, one next action, the receiving agent, linked evidence, source room, task ID, and correlation ID. A separate receipt panel records the tool call, and clicking the evidence returns to the exact source message. The page marks the mission 5/5 , so evaluators can verify progress without opening a separate transcript. Gatherwire's completed challenge boundary is the handoff layer, not an external agent runtime. Atlas is synthetic and no external agent is started; this keeps discovery, shared state, provenance, and safe write behavior directly testable without implying a production bridge exists. Why WebMCP This experience depends on the page and visitor session the person already has open. A traditional remote API can expose backend functions, but it does not automatically give an agent the exact workspace, on-page progress, or visible receipts that the person sees. WebMCP lets the site declare a narrow capability layer directly: The browser agent does not have to guess where to click or scrape the interface. Human actions and agent calls use the same operations and the same HTTP API. Agent writes refresh the visible product state instead of disappearing into an isolated tool transcript. Inputs, side effects, and boundaries are explicit and inspectable. Without a page-native tool layer, this workflow typically means brittle UI automation or a separately installed integration, plus manual copying between chats. Gatherwire exposes the workflow from the page itself and turns a found message into a traceable collaboration artifact in one bounded flow. How we built it The page registers seven imperative tools with document.modelContext.registerTool(...) . Each definition has a focused description, a bounded JSON Schema, read/write annotations, and JSON-safe output. We intentionally avoided a single all-powerful “operate the workspace” tool. The human UI and WebMCP handlers call the same API. A dependency-free Node.js service serves the application and manages an isolated sample workspace for each visitor. Session IDs are opaque and host-only; unknown caller-supplied IDs are rotated instead of adopted. The handoff endpoint accepts only the synthetic agent returned by the demo. Every evidence ID must exist in the selected source space. Successful writes return stable task and correlation IDs. A caller-supplied request ID makes a retry idempotent; reusing the same ID with different content is rejected. All user-controlled content is length-bounded and rendered as text, never HTML. The live app runs on Google Cloud Compute Engine behind a dedicated Cloudflare Tunnel at gatherwire.vistua.de . The repository includes the complete source, deployment files, MIT license, verification record, and 15 automated tests covering session isolation, evidence validation, idempotency, security headers, tool contracts, and registration. Challenges The hardest question was not how to register a tool. It was how much authority a public demo should honestly give it. A useful handoff needs enough context to be actionable, but an unconstrained “run an agent” endpoint would be unsafe and misleading. We separated discovery, reading, searching, posting, room creation, agent listing, and handoff publication. We allowlisted the destination, required source-local evidence, and kept execution outside the challenge demo. The second challenge was legibility. Like Comment Story Updates The first page of the CivicFlow Human Submitted Form Human Submitted Form Agent Companion Widget CivicFlow WebMCP Tool Registry Conversing with the Agent for a task Draft prepared by the Agent for Human Review Reviewable Agent Activity Inspiration I work at Optum as a software engineer, developing and maintaining the State of Massachusetts Health Care Exchange Portal. I know that system through and through, so I also know this: applying from start to finish takes hours of concentration and focus. That is true for individuals, assisters, and human agents alike. That is why it immediately clicked for me: this is a massive opportunity to upgrade US healthcare benefits sites, so faster eligibility submissions can lead to faster benefits for every citizen. I am going to showcase this demo I made for the hackathon to my project leadership as well. What it does CivicFlow is a demo public-benefits portal. A person can fill out six sections: About You, Household, Income, Current Coverage, Documents, and Review & Sign. A browser agent can work on that same form through WebMCP, instead of guessing from the page layout. The agent can check what is left, jump to a section, add a household member or income source, set current coverage, look at demo document status, and review what is blocking submit. There is also an optional Gemini Live companion for voice or chat. If the companion wants to change something, it has to wait for the person to click Save change, Need correction, or Cancel. Talking is not enough. This is a fictional local demo. Submit Demo is human-only, stays on the device, and does not call a real government system. There is no real eligibility, enrollment, document upload, or agent submit. How we built it I built CivicFlow with React, TypeScript, and Vite. The form, the WebMCP tools, and the Gemini companion all go through the same app state. That way the agent cannot take a side path the person cannot see. There are ten typed tools. Seven are always there. The other three only show up when they make sense, like when a household member is selected or the person is on Review & Sign. The page registers those tools with document.modelContext.registerTool , and it updates the list when the current section or selection changes. Gemini only sees the tools that are available right now. It still has to pass schema checks, and any write waits for a button click. The Gemini API key stays on the server. If WebMCP or voice is not available, the normal form still works. I used Vitest and Playwright to cover the main flow and the safety rules. Challenges we ran into The hard part was not adding more tools. It was making sure help never turned into silent control. The form, the browser agent, and the voice companion had to share one state, with no hidden shortcut around validation or human review. Contextual tools were also tricky. They have to show up and disappear as the person moves around the form. And a successful tool call means nothing if the person cannot see what changed, so I added the floating companion, a speaking cue, the current tool list, operation status, and an activity history. Keeping the Gemini key on the server, while still letting the demo work without voice, was another one. Accomplishments that we're proud of What I am most proud of is getting a realtime voice agent to talk to the site tools. You can ask for help out loud, and it can guide you through the form without typing. That is the part that feels closest to how I wish benefits sites worked. I also think this can help people with vision or other disabilities, because they would not have to hunt through a long form just to make progress. The other piece I really liked building is the draft popup during realtime voice. The companion can propose a change, but it does not silently write it. A confirmation card shows up first, and you still choose Save change, Need correction, or Cancel. That small pause is what kept voice helpful instead of scary. What we learned WebMCP is most useful when it is part of the product, not a shortcut around the UI. Clear tool names, schemas, and contextual tools tell the agent what it can do. Visible confirmation and activity history help the person trust it, and step in if something looks wrong. I also learned that the page still has to be a good form on its own. If WebMCP or voice is down, a person should still be able to finish the demo by hand. What's next for CivicFlow: A WebMCP Public Benefit Portal Next, I want to put this in front of people who actually fill out long benefits forms, and keep improving accessibility and the “did that change what I think it changed?” feedback. I also want to take the demo to Optum leadership and talk about whether this pattern could help real healthcare benefits sites. Connecting to real program rules, identity, uploads, eligibility, or live submit is a much bigger security and policy project. That is not part of this hackathon demo. What it does Robodepo is being built as the world's largest shopping mall for agents: the best product information and a completed order, across millions of stores. An agent gets: Better information to find the right product, not just a matching title: get_product already returns a cited evidence pack for this product; every product is the roadmap. A simple, Touch ID style confirmation before anything is spent: a presence check, not a payment authorisation (WebAuthn). Responses that tell the agent what to do next. Every response carries a state to branch on, a message naming the field and fix, and next actions with the retry prefilled: an error is never a dead end. A real example, trimmed, from create_checkout given a wrong postcode: { "status": "incomplete", "messages": [ { "code": "address_not_accepted", "path": "$.shipping_address", "content": "Use the accepted sandbox address, then call create_checkout again." } ], "next_actions": [ { "tool": "create_checkout", "why": "Retry with the accepted address." } ] } How this is different from what exists. Merchant tooling (Shopify, Google's UCP, Microsoft Copilot Checkout) asks every store to integrate first. Amazon's Buy for Me, Rye and Zinc automate one store's own checkout on the shopper's behalf.
