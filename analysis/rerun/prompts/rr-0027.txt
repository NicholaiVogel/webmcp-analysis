Like Comment Story Updates WebMCP-powered inference routing lab comparing Round Robin with capacity- and load-aware routing on heterogeneous workers Inspiration AI inference infrastructure is increasingly heterogeneous: workers can have very different capacities, yet simple strategies such as Round Robin still treat them as interchangeable. A slow worker can build a large queue while faster capacity remains available elsewhere. At the same time, browser agents often interact with applications indirectly by inspecting interfaces, finding controls, and deciding what to click. For infrastructure software, however, operations like comparing routing policies or inspecting a bottleneck have much richer semantics than the buttons that trigger them. ThermalMesh Lab grew from one question: What if an AI agent could understand and operate inference infrastructure through domain-level tools instead of automating a dashboard by sight? What it does ThermalMesh Lab is a browser-based simulator for heterogeneous AI inference clusters. Users can configure workers with different abstract capacities, generate deterministic workloads, and compare two routing strategies: Round Robin — equal distribution without considering capacity or load. Inference-Aware (ThermalMesh) — a simplified strategy using capacity, load, and estimated completion time. The simulator exposes TTFT, queue latency, throughput, completed and unfinished requests, worker utilization, and queue depth. The same application can also be operated by an AI agent through WebMCP Site Tools. An agent can configure the cluster and workload, run benchmarks, compare policies, inspect bottlenecks, and apply a routing strategy. Humans and agents share the same application state, so every agent action is immediately reflected in the dashboard. ThermalMesh Lab is a browser-based simulation, not a hardware benchmark. How we built it ThermalMesh Lab is built with React, TypeScript, and Vite and runs entirely in the browser. The simulation engine generates a deterministic seeded request trace and gives both routing policies the same workload, making comparisons reproducible. WebMCP is integrated through document.modelContext.registerTool() . The application exposes seven domain-level Site Tools: get_cluster_state configure_cluster configure_workload run_benchmark compare_routing_policies inspect_bottlenecks apply_routing_policy The WebMCP layer does not maintain separate agent state. Site Tools and the visible React interface call the same validated application/store operations. We also implemented a state-dependent tool lifecycle. After a valid comparison, ThermalMesh Lab dynamically exposes an eighth tool: apply_winning_configuration If the cluster or workload changes, the comparison becomes stale and that tool is removed. In the deployed application this creates a live: 7 tools → comparison → 8 tools → scenario change → 7 tools lifecycle driven entirely by application state. The application requires no backend, database, authentication, or paid API and is deployed as a static site on Cloudflare Pages. Challenges we ran into The biggest challenge was making WebMCP a real application interface rather than a collection of tools that simply mimic button clicks. Operations such as compare_routing_policies and inspect_bottlenecks needed to represent actual infrastructure semantics while keeping the human UI and agent perfectly synchronized. Dynamic registration also introduced lifecycle problems. We had to prevent duplicate or stale registrations, ensure tools always operated on current state, and remove the winning-policy tool immediately when its comparison became invalid. The simulator itself required careful handling as well. Both policies needed identical request traces, overloaded scenarios had to remain numerically safe, and unfinished requests could not appear as misleading zero-latency samples. One of our first live agent tests produced an unexpected result: the agent realized its initial workload had completely saturated the cluster, reduced the workload, reran the comparison, and then selected a better routing policy. That showed us both the potential of semantic tools and the importance of precise tool descriptions when working with autonomous agents. Accomplishments that we're proud of We are especially proud that WebMCP is not an isolated demo layer. The human interface and the AI agent genuinely operate the same application. In live testing, ChatGPT successfully discovered the Site Tools, configured the cluster and workload, compared routing strategies, analyzed the bottleneck, and applied the selected routing policy. The state-dependent lifecycle also works end to end: 7 base tools → comparison → 8 tools → invalidation → 7 tools We are also proud that the simulator does not artificially make Inference-Aware routing win. With homogeneous, lightly loaded workers, both strategies can produce effectively identical results. Under heterogeneous load, differences emerge naturally. In one live test: Round Robin completed 620 requests Inference-Aware routing completed 741 requests TTFT p95 fell from roughly 23.1 seconds to 1.7 seconds Unfinished requests fell from 123 to 2 More importantly, the agent was able to explain why: Round Robin continued sending equal traffic to a much slower worker, creating a large queue, while Inference-Aware routing shifted work toward available capacity. What we learned The biggest lesson was that WebMCP becomes much more powerful when tools represent application semantics rather than UI actions . A tool such as compare_routing_policies gives an agent far more reliable context than asking it to discover controls, run separate simulations, locate the results, and infer how the metrics relate. We also learned that agent capabilities do not need to remain static. Exposing apply_winning_configuration only when a valid comparison exists gives the agent an interface that reflects what the application can meaningfully do at that moment. The simulator taught us another important lesson: overloaded-system benchmarks can be misleading when unfinished work is ignored. A policy may appear to have better median latency simply because its slowest requests never complete inside the observation window. We therefore treat completion and unfinished work as first-class comparison signals rather than hiding them. What's next for ThermalMesh Lab The challenge version intentionally focuses on a small, reliable WebMCP experience. Next, we would like to add additional well-defined routing baselines such as Weighted Round Robin and Least Queue , along with richer workload patterns, request classes, worker failures, and longer-running experiments. ThermalMesh Lab could also evolve into a broader agent-native environment where agents design experiments, compare multiple strategies, explain tradeoffs, and iteratively search for better infrastructure configurations. The broader idea we want to explore is simple: Instead of teaching AI agents how to click through infrastructure software, make infrastructure software directly understandable to agents. If every site can expose genuine tools, what is the single shared capability that would make all of them better at once? Memory. Not an assistant's private chat history sealed in a vendor cloud, but structured context that any participating site can read and write, with the person holding the delete key. What it does Tether is a shared memory layer for the agent-native web, plus two working sites that prove context survives the jump between them. DesignLab is the producer, a small design studio. Ask the agent to remember your preferences and its save_preference tool applies them to the canvas and writes them to Tether in the same call. Its create_project tool asks Tether what you prefer, then configures six things it never asked about: language, theme, layout density, framework, package manager, and styling, down to the lock file and the install command. The Tether control plane shows every memory with its source site, the tool that wrote it, tags, a confidence score, and a timestamp. Inspect, search, edit, add, or permanently delete any of it. The two demo sites are an illustration. The direction is a shared memory layer that any experience can build on, where the person keeps the keys. Like Comment Story Updates Payoff - Joke Payoff - Ramen Inspiration Short-form storytellers often know exactly what they want an audience to feel: a laugh, a reveal, a gut punch, or a moment of warmth. The hard part is knowing whether that feeling actually landed. Today, creation, feedback, and revision are usually disconnected. A creator may copy a storyboard into an AI chat, summarize audience reactions, discuss possible changes, then manually recreate those changes elsewhere. Along the way, important context gets lost: what the creator originally wanted, which audience saw which version, and whether a revision actually improved the story. We built Payoff to keep the creative intent, storyboard, audience evidence, diagnosis, and revision history in one place. We also wanted AI agents to work inside that same live creative workspace. With WebMCP, an external agent can read the actual story and audience evidence, reason about what is happening, and help make precise changes without forcing the creator to copy everything into a separate chat. What it does Payoff helps creators develop and test short narrative videos through one continuous loop: Create → Refine → Test → Understand → Revise → Test again A creator starts with a premise, the feeling they want the audience to have, and a format. Payoff turns that intent into a six-beat visual storyboard with dialogue, emotional beats, visual direction, and generated scene artwork. Creators can test the story with an AI Audience for fast provisional feedback or prepare a target-blind Human Audience study for real viewers. Payoff compares the intended emotional payoff with how the story actually landed and highlights what worked, where it drifted, and the biggest opportunity to improve it. The creator then chooses what to change. Payoff proposes a revision, the creator reviews and applies it, and the new story becomes an immutable, untested version ready for another audience loop. WebMCP adds a second structured interface to the same workspace. An external agent can read the live brief, storyboard, AI feedback, and audience evidence, then perform narrow, version-checked story operations after the creator provides direction. The agent helps diagnose and execute. The creator still makes the creative decision. How we built it Payoff is built with React, TypeScript, and Vite. A framework-independent PayoffStore holds the versioned creative workspace and is shared by both the React interface and WebMCP tools. The production application runs as a Node.js service on Google Cloud Run, serving both the frontend and server-side API routes. We use the OpenAI Responses API with structured outputs for storyboard generation, audience simulation, human-response synthesis, diagnosis, revision proposals, and semantic scene review. Gemini generates character references, environments, and storyboard imagery. Each story beat includes a structured visual specification covering the setting, visible characters, focal action, focal object, composition, emotional cue, and continuity requirements. Generated scenes are checked for narrative correctness and can go through one bounded repair step before being accepted. Payoff exposes eight tools through Chrome's native document.modelContext WebMCP API: four read tools and four narrow write tools. Writes require the active version returned by a previous read, so an agent cannot silently overwrite a newer human edit. We also built deterministic demo fixtures, content-hash-based visual caching, IndexedDB persistence, and extensive automated testing. The current project passes 109 unit tests and 20 end-to-end Chrome scenarios. Challenges we ran into One of the hardest problems was making sure the human interface and an external agent were truly working on the same story. Maintaining separate state for the UI and WebMCP would have created subtle synchronization problems. We instead made both use the same store and the same production domain commands. A WebMCP edit therefore creates the same immutable version and triggers the same UI update as a human edit. Visual continuity was another major challenge. An image could look attractive but still be wrong for the story by revealing a clue too early, changing a character, or hiding the object that makes the emotional turn understandable. We addressed this with structured visual contracts, continuity references, semantic review, and bounded repair. Audience provenance was equally important. AI simulation should never look like real audience research, and human feedback must remain attached to the exact version viewers actually saw. Every revision is therefore marked untested, and evidence from an older version is never silently carried forward. Finally, live model calls made testing and recording slow, expensive, and nondeterministic. We built a deterministic demo mode that preserves the real UI, schemas, state transitions, revision logic, and evidence rules while replacing only nondeterministic provider outputs. Accomplishments that we're proud of We are most proud that Payoff closes the full creative learning loop instead of stopping at generation. The creator's intent, storyboard, audience evidence, diagnosis, revisions, and WebMCP tools all operate on one coherent versioned workspace. An external agent can inspect the same state the creator sees. Agent writes are version checked, stale changes are rejected, and successful edits immediately become part of the visible story history. We also built a clear separation between AI Audience simulation and real Human Audience evidence. Payoff communicates where feedback came from and keeps every result bound to the exact story version that produced it. The deterministic Looks Great demo reproduces the full creator journey using the real product paths, backed by 109 unit tests and 20 end-to-end browser scenarios. What we learned We learned that the most valuable part of an AI creative product is not generation alone. It is preserving context and trust across repeated creative decisions. WebMCP became most useful when we exposed small, composable operations instead of a broad command like "make this story better." The agent can inspect evidence, reason about the problem, and help execute a change, while the creator still chooses the creative tradeoff. We also learned that visual storytelling needs more structure than a good image prompt. Explicitly defining the focal action, characters, spatial relationships, important objects, and withheld clues produced much more reliable story scenes. And we learned that failure behavior matters. A failed image request, stale agent write, or model timeout should never destroy the creator's work or contaminate evidence from another version. What's next for Payoff The next major step is hosted Human Audience collection, so creators can share a study link and receive validated responses directly inside Payoff instead of importing them manually. We also want to add collaborative team workspaces, richer video and animatic playback, better comparison of audience results across revisions, integrations with existing creative-production tools, and support for more WebMCP-capable agents and browsers. Longer term, we want to study which kinds of audience signals actually help creators improve an emotional payoff, and turn Payoff into a shared creative workspace where humans, audiences, and AI agents can continuously learn from each other.
