Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the

Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

The third challenge was separating technical failure from scientific evidence. A diverged run must remain repairable, while a valid negative result must remain immutable. Treating both outcomes as a simple failed status would undermine the research record. The final challenge was making the demonstration deterministic without hiding the real workflow. The benchmark is intentionally small, but it still performs actual training in a Web Worker and produces metrics, curves, configuration differences, logs, and a decision boundary. I also learned that sharing storage is the easy part of human-agent collaboration. The harder part is sharing meaning: which contract governed a run, why a node exists, whether a measurement is valid, and who approved the next step. Explicit state transitions, frozen inputs, provenance links, and narrow tools made those boundaries easier for both the human and the agent to understand. A shared visual canvas where people and their agents draw, discuss, and decide together. Like Comment Story Updates Inspiration Visual collaboration tools were built for people clicking through the same interface. Agents usually sit outside that room: they see a screenshot or pasted summary, but not the live board, the user's selection, the open discussion, or the latest revision. Pinboard puts people and the agents they bring into one shared visual workspace. What it does Pinboard combines an Excalidraw canvas, anchored discussions, decisions, and realtime multiplayer editing. In a WebMCP-capable browser, the active board registers typed tools that let an agent read the board semantically, edit canvas elements, add diagrams near the user's focus, ask questions, reply, and record decisions. Agent contributions are labelled Agent via <participant> . Writes require the revision the agent read and an idempotency key. If somebody changes the board first, Pinboard rejects the stale mutation instead of overwriting newer work. Why WebMCP The browser already has the context the agent needs: the current board, visible area, selected objects, active discussion, and latest revision. WebMCP exposes that context directly as structured tools, so the agent does not need to infer state from pixels or guess its way through the UI. Alice and Bob can share one durable board while each person's agent works from that person's private focus. Selection and viewport never become shared presence. How we built it The frontend uses React 19, TypeScript, Vite, Tailwind CSS, and Excalidraw. Anonymous solo boards stay in IndexedDB. Multiplayer runs on Cloudflare Workers. Every room maps to one SQLite-backed Durable Object that serializes canvas state, discussions, decisions, revisions, sessions, one-use WebSocket tickets, and idempotency records. Native hibernatable WebSockets carry realtime updates, while Firebase Authentication gates room creation and multiplayer sessions. The WebMCP adapter feature-detects document.modelContext , builds its tool list from live board state, and registers tools with abortable lifecycles. Zod provides runtime validation and JSON Schema. Challenges The hard part was keeping human edits, agent writes, private attention, reconnects, and dynamic tools consistent under concurrency. We added revision conflicts, idempotent operations, bounded payloads, semantic pagination, capability-link protection, and deterministic failure tests. Accomplishments Pinboard works as a useful human canvas without WebMCP. With WebMCP enabled, an agent can understand the live board and contribute to the exact place its user means. Pinboard hosts no model and needs no model API key; participants bring their own agent. What we learned Agent-native UI needs stronger contracts than click automation. Tools need current context, explicit trust boundaries, bounded reads, conflict behavior, and visible provenance. WebMCP gave us the browser-level surface for that work. What's next The MVP deliberately omits invite revocation, roles, file uploads, audit export, and approval-gated agent actions. Those are next after the core collaboration loop. Olympus MCP Harness started from one simple idea: “The model reasons. The machine executes.” As WebMCP moves AI agents from reading websites to acting on them, execution becomes a trust boundary. Olympus was built to engineer that boundary. Why WebMCP WebMCP turns website capabilities into structured tools that agents can invoke directly instead of guessing their way through the UI. Olympus builds on that boundary: WebMCP structures the action. Olympus governs the execution. Unlike a backend MCP integration, WebMCP works inside the live page and shared user session. Olympus uses that browser-native boundary to govern execution without replacing the existing web experience. WebMCP defines how an agent can interact with the application, while Olympus determines whether an invocation is valid, allowed, safe to execute, and successfully completed. What it does Olympus MCP Harness is the execution control layer behind WebMCP. WebMCP handles the agent-to-web boundary through structured tools. Olympus then: Inspects the invoked capability Validates tool arguments Authorizes execution according to risk and policy Executes the machine action Verifies the result Recovers from safe failures when appropriate Traces the full execution path High-risk actions, such as checkout, remain behind explicit human approval. People + agents together Olympus enables controlled delegation . A user can delegate an outcome instead of manually operating every interface step. The agent reasons, discovers WebMCP tools, searches, compares, and prepares actions. Olympus governs execution, while the human only needs to intervene when a high-risk action requires approval. This creates a new interaction model: agents can autonomously handle routine actions while humans remain in control of consequential ones. The goal is neither full autonomy nor manual browsing. It is controlled delegation. In the demo, the agent can search, inspect, compare, and prepare a laptop purchase through WebMCP tools, while Olympus keeps checkout behind an explicit approval boundary. Who It's For E-commerce and retail web apps : Olympus demonstrates how AI agents can safely help users search products, compare options, prepare a cart, and approach checkout without turning high-risk purchase actions into blind automation. WebMCP developers : developers exposing real actions to AI agents and needing a reliable layer for validation, authorization, approval, recovery, verification, and observability. Human users and judges : they can see the current model decision, harness stage, machine action, execution trace, and a non-skippable approval gate for high-risk actions. WebMCP-capable agents and clients : such as ChatGPT’s in-app browser or Chrome with WebMCP enabled. The agent interacts through document.modelContext tools rather than relying on brittle UI actuation for the core workflow. The laptop storefront is the concrete retail demo; the harness pattern is designed to generalize to other WebMCP workflows. How we built it I built Olympus using the native WebMCP imperative API with: document.modelContext.registerTool(...) The app exposes five structured tools: search_products get_product compare_products add_to_cart checkout Each WebMCP tool is intentionally thin and routes execution through the same Olympus harness.run(...) path, where validation, policy, approval, execution, recovery, verification, and tracing are enforced. The application is built with Next.js, React, TypeScript, and deployed on Vercel. Olympus runs behind WebMCP site tools inside the live browser context, preserving the page’s existing state and user experience while adding execution policy, verification, and traceability. Tested natively with ChatGPT’s in-app browser Olympus was tested directly in ChatGPT’s in-app browser.
