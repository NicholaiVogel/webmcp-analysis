Inspiration AI benchmarks are approaching a ceiling. Most are static: a model receives a problem, produces an answer, and gets a score. That works until models begin saturating the task distribution. At that point, another fixed set of harder questions only moves the ceiling temporarily. Real scientific discovery does not look like a standardized test. The hard part is often not solving a narrowly posed problem with a known answer, but searching an enormous space of trajectories, designs, hypotheses, and even frameworks i.e deciding which experiment to run next, which question to ask, and which assumption to discard. Systems like AlphaGo showed the power of pairing an enormous search space with a cheap, unambiguous verifier. Other breakthroughs such as AlphaFold similarly benefited from unusually strong computational supervision and dense ground truth. We wanted to ask what an equivalent substrate could look like for computational science. MotionArena is our small working answer: replace narrow static benchmarks with dynamic simulation environments that offer large continuous search spaces, cheap verification, and a much steeper hill for increasingly capable agents to climb. Physics and physical simulation are especially attractive substrates because their environments can also evolve toward progressively higher fidelity - spatially, temporally, and physically - rather than remaining a fixed collection of questions. What MotionArena does TL;DR: MotionArena frames human-motion reconstruction as a continuous search problem. The environment withholds a ground-truth physical trajectory. The agent receives a natural-language prior and must reconstruct the hidden motion using a learned motion model. It can run repeated rollouts, inspect aggregate feedback, refine specific temporal spans, and iteratively improve its best candidate. The browser makes that process visible in real time: the left avatar shows the agent's mutable reconstruction, while the right shows the immutable reference for the human spectator. Instead of revealing the correct answer, the environment returns deterministic reward based on physical trajectory agreement — including pose alignment, root motion, velocity, and contact behavior. The paradigm shifts from: question → answer → score to: observe → propose → simulate → verify → improve Why WebMCP matters WebMCP turns the browser from a visualization into an agent-operable research environment. Without WebMCP, an agent has to reverse-engineer buttons, sliders, canvases, and DOM state. MotionArena instead exposes the meaningful actions of the environment directly: inspect_episode run_rollout inspect_reward refine_span submit_best These tools operate on the exact same state rendered in the browser. When the agent launches a rollout, the motion on screen changes. When its score improves, the rollout history changes. The browser becomes both the laboratory and the observable audit trail of the search. This is the WebMCP capability we find most exciting: websites can expose not merely UI controls, but the action space of an environment . Why human motion? Open-ended motion generation normally has no unique ground truth. If two people are told to "climb upward," many different motions may be valid. So we changed the problem. MotionArena uses withheld trajectory reconstruction . The environment starts from a captured human motion and hides part of it. The agent therefore faces a huge space of possible reconstructions, while the environment retains an objective reference trajectory. Generation is hard. Verification is cheap. Once a candidate exists, comparing it against the withheld trajectory is inexpensive and deterministic. That gives us the structure we were looking for: large search space + learned world model + cheap verifier. How we built it We use MoMask as the learned human-motion prior. It generates candidate trajectories represented as BVH motion, which we retarget onto matching VRM characters for visualization. Three.js renders two synchronized avatars: the mutable reconstruction and the immutable reference. Both use the same character, camera, timing, and environment so differences in motion are immediately visible. The scientific reward is calculated in canonical motion space rather than from the rendered avatar. This matters because BVH-to-VRM retargeting can introduce visual differences that should not affect the underlying score. A shared environment state connects the renderer, verifier, rollout history, and WebMCP tools. Frontier agents can repeatedly search the MoMask inference space, while smaller browser-local policies can optimize residual motion corrections directly. The problem we are really exploring MotionArena is not primarily about producing one better animation. It is a prototype for a different way of measuring model capability. A capable scientific agent should increasingly be able to: choose useful experiments, search large continuous or combinatorial spaces, learn from failed attempts, allocate expensive computation intelligently, discover weaknesses in its current world model, and improve solutions under objective feedback. What it does KOTOAGE is a small 3D dungeon (Three.js, WebGL) with a hamlet and five floors. The player explores, fights, levels up (XP, four stats, skill points). When the page runs in a WebMCP-capable browser (ChatGPT's in-app browser, or Chrome with chrome://flags/#enable-webmcp-testing ), the game registers 8 tools on document.modelContext . An agent can then discover them and act on the live game state: Tool Real effect in the game etat_joueur reads health, mana, floor, gear, counters donner_potion heals the player (small +2, large +6), shown on the HUD ouvrir_mur turns a wall cell into floor; the 3D walls are rebuilt placer_piege places a trap on a floor cell inspirer gives a contextual hint about the place or the floor defier spawns real enemies (guardian, warrior, horde) raconter narrates a floor (1 to 5, 0 = the hamlet) braignak_etude asks Braignak, the dungeon's watcher, for one of his five studies — or gives him a new one to run Every successful call is announced to the player by the "voice of the world" on the HUD. The in-game chat also forwards the player's requests to the co-game-master when the WebMCP bridge is active. Without WebMCP, the game runs exactly the same: the bridge adds zero dependency to rendering. Braignak, the watcher — the eighth tool is a character Braignak is one of our own agents, and his job outside the game is the one he keeps inside it: he looks, and he reports. He never touches anything. In the dungeon he floats beside the player and repeats aloud what the co-game-master just did. The eighth tool interrogates him. He has already led five studies in this dungeon — the walls that open, the guardian of the landing, the traps, the potions, where strength comes from — and answers from his own work. Give him a subject he has never studied and he leaves you: he walks around the room, thinking, then comes back, tells you what he counted, once , and forgets it. How I built it index.html is a self-contained ES module (Three.js + WebGL). It exposes a small bridge window.__webmcpConnexion (grid, player, walls, traps, creatures, HUD). webmcp/webmcp.js is the pure contract layer: tool names, JSON schemas, validation, no DOM. webmcp/integration.js wires the contract to the live game when document.modelContext exists: a Proxy on the grid, accessors on health, traps and challenges. Each agent call becomes a real world change. Hosting: a public Google Cloud Storage bucket, HTTPS, no server. Proof, with zero dependencies: 35 contract tests, 15 integration tests on a DOM harness, 8 tests on the chat bridge, and a real-browser check ( tests/test_webmcp_live_cdp.py ) that launches headless Chrome over the Chrome DevTools Protocol, loads the live URL, and verifies the 7 tools are registered and that etat_joueur and donner_potion change the game state. Challenges I ran into Proving it in a real browser, not just in unit tests: I wrote a tiny CDP client by hand (WebSocket handshake, masked frames) because I wanted a proof with no dependency. Keeping the game intact when WebMCP is absent: the integration layer must do nothing, and that is tested. Making the agent a game master, not a cheat code: the tools give trials (walls, traps, enemies, hints), and the chat bridge answers with an action, never a gift. Accomplishments that I'm proud of 7 tools, each with a visible, physical effect in a 3D world. 46 automated proofs, plus a live-browser check on the hosted page. A game that stays fully playable without WebMCP. What I learned WebMCP turns a web page into something an agent can do things to , not just read. The hard part is not registering tools, it is deciding what an agent should be allowed to change so that the experience stays a game. A WebMCP workshop that preserves missing proof, the next action, and human checkpoints for interrupted solo builders. Like Comment Story Updates What VERROCCHIO does VERROCCHIO is a WebMCP workshop for time-constrained solo builders whose projects are repeatedly interrupted. It keeps the next action, missing proof, active work, and human checkpoints together so an AI can help without turning an unverified claim into “done.” The browser exposes four bounded, state-aware WebMCP tools: inspect_workshop reads the live mission, missing proof (MANCA), active work, and the next bounded action. call_fermo stops when evidence, scope, safety, or intent is ambiguous. propose_workshop_draft validates and returns an unsigned plan that waits for human FIRMA. return_work_result records a structured CLAIMED result without marking its evidence verified. Human-only actions—FIRMA approval, evidence verification, resume, publication, and final submission—are deliberately absent from the WebMCP tool surface. Why WebMCP is a strong fit A person and an agent must act on the same live project state. With ordinary DOM automation, an agent has to rediscover controls and infer whether visible text is a claim, approval, or proof. WebMCP gives the page an explicit contract and exposes only the transitions the agent is allowed to perform at that moment. The result is not simply fewer clicks. It is a clearer division of responsibility: the agent can inspect, draft, stop, and return bounded work; the human retains purpose, approval, evidence judgment, publication, and submission. Better experience for interrupted solo work A solo builder working around a full-time job carries coordination that a conventional team would normally distribute: rules, next actions, interruption recovery, evidence review, and stops before irreversible actions. VERROCCHIO makes that coordination visible and resumable. The core flow is: MANCA → unsigned plan → human FIRMA → bounded work → CLAIMED → human VERIFIED or CHANGES_REQUESTED After an interruption, the builder can reopen the workshop and see what is still missing, what is active, and exactly where human attention is required. What people and agents can now do together The agent works directly with structured browser state instead of guessing from screenshots or page text. It can propose the smallest valid next plan, detect ambiguity, and return a result with checks, evidence references, and remaining risk. The human can adopt or reject that plan and verify the claim without surrendering the decisions that matter. Implementation VERROCCHIO is a React and Vite application with browser-local persistence. Tools are registered through document.modelContext.registerTool ; their availability changes with workshop phase. Every mutation requires the state version returned by inspection and an idempotency key. Stale state is rejected, identical retries reuse the existing receipt, and conflicting reuse fails. The current ChatGPT or Codex host supplies reasoning, so the app does not require its own OpenAI API key.
