Traditional optimization software can solve these problems, but describing a model often requires specialized mathematical knowledge. AI assistants make natural-language interaction easier, but an LLM should not be trusted to invent a schedule and claim it is valid. ConstraintLab combines the strengths of both: Humans express goals and judge trade-offs. AI agents translate intent into structured actions. A deterministic solver computes and validates the schedule. We built ConstraintLab to explore what an agent-native optimization workspace could look like—one where the human interface, AI agent, solver, and audit history all operate on the same canonical application state. What It Does ConstraintLab is a browser-based job-shop scheduling workspace. Users can: View jobs, machines, dependencies, deadlines, and downtime windows. Inspect schedules through an interactive Gantt chart. Add or edit scheduling constraints manually. Ask a WebMCP-capable AI agent to inspect and modify the model. Run a real mixed-integer linear programming solver in the browser. Detect when a solved schedule becomes stale after the model changes. Receive deterministic explanations when a model is infeasible. Review every human, agent, and solver action in an audit timeline. A typical interaction looks like this: “Machine 2 will be unavailable between 1 PM and 3 PM, and Job 7 must finish before noon.” The agent discovers ConstraintLab’s site tools, adds typed constraints, and requests a solve. The HiGHS solver—not the language model—computes the resulting schedule. If another request creates a contradiction, ConstraintLab reports the genuine infeasible result and identifies the relevant constraints using deterministic conflict analysis. How We Built It ConstraintLab is built with React, TypeScript, Vite, Zustand, Zod, Web Workers, WebAssembly, HiGHS, WebMCP, Vitest, and Netlify. The most important architectural decision was to maintain one canonical application state. Human interface ──┐ ▼ Domain actions ▲ AI agent ─────────┘ │ Canonical Zustand store ├── Solver ├── Gantt chart └── Audit timeline The interface and WebMCP handlers call the exact same domain actions. There is no separate “agent state” or hidden model that can drift away from what the user sees. ConstraintLab exposes nine typed site tools: get_problem_state add_job update_job add_constraint remove_constraint set_objective solve_problem get_solution analyze_infeasibility Every tool input is validated with Zod, and write operations are validated again inside the domain layer. Agent arguments are treated as requests—not as trusted data. For optimization, we compile the scheduling problem into a CPLEX LP-format model and send it to HiGHS running inside a Web Worker. This prevents the WebAssembly solver from blocking the interface. The objective is to minimize makespan: $$ \min C_{\max} $$ For every job (j), completion must satisfy: $$ C_{\max} \geq S_j + p_j $$ where (S_j) is its start time and (p_j) is its duration. Precedence, deadlines, machine assignments, availability windows, and non-overlapping jobs are represented as linear constraints. Binary ordering variables handle jobs that may compete for the same machine. The resulting assignments are translated back into application objects and applied through a single solver-result domain action. We also track a modelVersion . Every structural edit increments this version, and every solution records which version it solved. If the two differ, the interface immediately displays: Model changed — re-solve required. Challenges We Ran Into One major challenge was correctly separating language understanding from mathematical correctness. The agent is useful for translating a human request into typed tool calls, but it must never become the scheduling engine. Keeping that boundary strict influenced the entire architecture. The solver integration was another challenge. HiGHS accepts LP-format text rather than a convenient JavaScript model object, so we built an explicit model compiler and solution translator. Variable names had to remain stable enough to map solver columns back to jobs and resources. Scheduling downtime is more complicated than adding a simple bound. A job must occur either before or after an unavailable window, which requires additional binary decisions and big-(M) constraints. Infeasibility explanations were also difficult. A solver can report that a model is infeasible without producing an explanation suitable for a user. Instead of asking an LLM to guess, we built typed, rule-based checkers that examine deadlines, precedence chains, locked starts, resource assignments, and machine availability.
