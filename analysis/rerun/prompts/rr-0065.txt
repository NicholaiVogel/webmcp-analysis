ClassSignal turns student mistakes into testable hypotheses that teachers and AI agents investigate together. Like Comment Story Updates Inspiration Teachers often know which questions students answered incorrectly, but not why. The same wrong answer can come from several different misconceptions, and choosing an intervention too early can reinforce the wrong idea. We wanted to explore a more useful role for AI in education: not automatically diagnosing students or giving them answers, but helping teachers turn uncertainty into a small, testable experiment. What it does ClassSignal is a shared Misconception Lab where teachers and AI agents investigate student reasoning together. ChatGPT can use WebMCP to inspect structured classroom evidence, compare competing explanations, and create a 60-second diagnostic probe directly inside the teacher’s workspace. The teacher can edit that probe, and the agent can inspect and reason about the exact revision. After explicit teacher approval, the probe appears in the student workspace. The student answers and explains their reasoning, producing new evidence that updates the hypothesis ranking and unlocks a targeted intervention for teacher review. ClassSignal also includes six-question guided practice, Socratic hints that do not reveal assessed answers, saved student reasoning, intervention approval controls, and an activity feed that attributes teacher, student, and agent actions. How I built it ClassSignal is built with React 19, TypeScript, Vite, Mantine’s default theme, Mantine Charts, and Recharts. We implemented WebMCP using @mcp-b/global and @mcp-b/react-webmcp . The application exposes 12 structured tools for: Inspecting classroom and student evidence Analyzing competing misconceptions Creating and inspecting diagnostic probes Publishing teacher-approved probes Analyzing new student evidence Previewing and applying interventions Providing answer-safe guided support Measuring learning outcomes The human interface and WebMCP tools operate on the same React state. This means an agent-created probe appears in the open page without a refresh, teacher edits become visible to the agent on its next call, and student responses change what the teacher and agent can do next. The demonstration uses deterministic fictional data stored in localStorage , allowing the complete experience to be reset and reproduced reliably without collecting real student information. Challenges we ran into The hardest challenge was making the project feel genuinely native to WebMCP rather than like a conventional dashboard with a chatbot attached. Our first version focused too heavily on analytics and tool count. Although the tools worked, the experience was not memorable. We redesigned the product around one collaborative loop: competing hypotheses, an agent-created experiment, a teacher revision, controlled publication, new student evidence, and an unlocked intervention. We also had to carefully separate preview operations from consequential actions. Publishing student-facing content and applying interventions require explicit confirmation, while student-support tools enforce answer safety inside their execution logic. Other challenges included keeping browser-local state consistent across teacher and student routes, preventing duplicate actions, handling rapid React form updates, making six questions navigable and reviewable, and maintaining responsive layouts without introducing a custom design system. Accomplishments that we're proud of We are most proud that the agent creates something meaningful inside the teacher’s existing workflow instead of only summarizing data. The teacher can improve the agent-created probe, and that human contribution becomes new context the agent can inspect. The student then contributes evidence that changes the shared state and determines which action becomes available. The sample size remains visible. Student-facing publication requires teacher approval. Intervention application requires separate approval. Guided-help tools do not reveal assessed answers. What we learned We learned that exposing many tools does not automatically create a compelling agent experience. The important question is whether people and agents can contribute different capabilities to the same workflow. WebMCP became most valuable when the website remained the trusted owner of state, the agent contributed structured reasoning and creation, and the teacher controlled consequential decisions. Instead of making the AI appear certain, ClassSignal shows competing explanations and gives the teacher a practical way to collect better evidence. Finally, we learned that a strong WebMCP demonstration needs visible state transitions. A judge should be able to see that an agent action changed the application, a human edit changed what the agent knew, and a student response changed the next available decision. What's next for ClassSignal Next, we would test the workflow with professional teachers and learning-science experts before making stronger educational claims. We would replace the demonstration heuristic with a validated evidence model that aggregates multiple student responses over time. We would also add secure authentication, server-enforced roles, a production database, separate teacher and student sessions, classroom-management integrations, and longitudinal intervention measurement. The long-term goal is not to automate teacher judgment. It is to give teachers and their agents a shared laboratory for asking better questions before acting on student data. What it does Proust’s Reader is an EPUB reader. It helps you understand a difficult sentence by untangling its structure inside the original text. Like Comment Story Updates External agent actually operated NOVA NOVA state machine Actual scientific analysis WebMCP discovery NOVA LAB NOVA LAB is a scientific laboratory built for the agentic web. The idea started with a simple question: what happens when an AI agent can do more than read a website or generate an answer? What if the website itself exposed executable capabilities that the agent could discover and operate? NOVA explores that idea through scientific experimentation. Instead of building an AI chatbot that tells a user what an experiment might show, NOVA provides a stateful environment where an external agent can design an experiment, request human authorization, execute it, retrieve persisted observations, analyze the evidence, save a finding, and replicate the experiment. The current demonstration uses plant growth as the experimental domain. The experiment can vary environmental conditions such as temperature and water and measure simulated plant-growth outcomes. How it works The interaction begins outside NOVA. A user gives an external agent a scientific question such as: Investigate what environmental conditions maximize plant growth. Don't assume the answer—design and test an experiment. The agent discovers NOVA's capabilities through WebMCP rather than being given a private NOVA-specific API integration. NOVA exposes six WebMCP tools: create_experiment run_experiment get_results analyze_results save_finding replicate_experiment The resulting flow is: Human → External Agent → WebMCP → NOVA → Experiment → Evidence → Analysis → Replication NOVA owns the state and execution. The external agent provides reasoning and orchestration. Human authorization Experiments cannot simply be executed because an agent requested them. Creating an experiment places it into an AWAITING_APPROVAL state. A human must approve it before execution is authorized. This authorization boundary is enforced by the server and state machine, not by relying on the agent to behave correctly. The experiment then progresses through: DRAFT → AWAITING_APPROVAL → APPROVED → RUNNING → COMPLETED → ANALYZED → REPLICATED Rejected experiments can return to the draft state for revision. Evidence, not fabricated answers NOVA persists the experiment and its observations rather than generating a result only for display. The current simulation produces synthetic experimental observations using deterministic simulation with stochastic noise. This is explicitly disclosed in the application. After execution, the agent can retrieve the persisted observations and request statistical analysis. NOVA calculates effects, confidence intervals, p-values, interaction effects, and condition means from the stored observations. The experiment can then be independently replicated using a new seed. The replication evaluates whether the direction of the result is consistent, whether confidence intervals overlap, and whether the relative effect difference remains below the defined threshold. Provenance NOVA preserves provenance throughout the experiment lifecycle, including experiment IDs, simulation version, seeds, timestamps, observations, analysis records, findings, replications, and state-transition events. This makes it possible to trace a conclusion back to the experiment and measurements that produced it. Why WebMCP The interesting part of NOVA is not simply that it can simulate plant growth. The project explores a different interaction model for the web: a website can expose meaningful capabilities that an external agent can discover and execute. The agent does not need to be given NOVA's internal implementation or a custom integration created specifically for the demonstration. It encounters the website and its exposed capabilities through WebMCP. That allows the website to remain responsible for its own state, validation, authorization, execution, persistence, and evidence while the external agent handles reasoning and orchestration. What I learned Building NOVA required thinking about a website as more than a collection of pages and API endpoints. The WebMCP layer became a capability boundary between the external agent and the application. I also learned that exposing tools is not enough by itself. Each tool has to connect to the same application logic used by the website, preserve authorization rules, validate inputs, produce persistent state changes, and leave an auditable event trail. The most important design decision was therefore keeping the WebMCP tools thin: they expose capabilities, while the server remains the source of truth for scientific state and authorization. Challenges The hardest parts were making the system genuinely stateful and ensuring that an agent could not bypass the experiment lifecycle. A successful tool call had to correspond to a real application operation rather than a simulated response. This meant connecting WebMCP execution to validation, authorization, the experiment state machine, PostgreSQL persistence, statistical analysis, and provenance. Another challenge was making the synthetic simulation useful for experimentation without presenting synthetic results as real scientific measurements. NOVA therefore labels its generated observations and preserves the simulation version and seed as part of the experimental provenance. NOVA is intentionally a constrained scientific demonstration, but the underlying interaction model is the focus: an external agent discovers and operates an executable, stateful environment exposed by the web.
