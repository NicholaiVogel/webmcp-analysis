BLOCKED REVIEW REQUIRED Human authority stays outside the agent SHIPPED SHIPGATE's release state and authority model Inspiration SHIPGATE started with one question Should an agent have access to a consequential action before the conditions for that action are satisfied? Most agent systems expose tools continuously and rely on the model to decide when not to use them. I wanted to test a different model where trusted application state changes what the agent can actually do. That became SHIPGATE. Evidence becomes capability. Instead of keeping deployment authority permanently available, SHIPGATE changes the browser's WebMCP tool surface as release evidence and human decisions change. What SHIPGATE does SHIPGATE turns release state into agent authority. A release moves through four states BLOCKED → REVIEW_REQUIRED → READY → SHIPPED In BLOCKED , the agent can inspect evidence and request evaluation, but ship_release is not registered. When the hard evidence passes, request_signoff becomes available. The agent can request approval, but it cannot approve itself. Human confirmation stays outside WebMCP. Only after human approval does the release become READY and ship_release appear as a registered WebMCP capability. After shipping, that capability retires and temporary rollback_release authority appears. Two rules shaped the project. The agent can request evidence, but it cannot author the evidence. The agent can request authority, but it cannot grant authority to itself. Why WebMCP WebMCP is the mechanism, not an interface added afterward. SHIPGATE uses the browser's actual tool inventory to represent the agent's current authority. BLOCKED → ship_release absent REVIEW_REQUIRED → request_signoff available READY → ship_release available SHIPPED → ship_release retired and rollback_release available temporarily This improves the experience for both sides. People can see what authority the agent currently has and what evidence or human decision is still missing. Agents do not need to reason over a deployment tool that should not yet be available. The collaboration is explicit. The agent gathers evidence and asks for judgment. The human contributes authority the agent cannot give itself. The application turns those inputs into the capabilities that exist. WebMCP closes that gap: the page itself registers tools with document.modelContext , so an agent like ChatGPT or Claude can call them against the live page and the player's own session, instead of guessing from a transcript. The interesting problem wasn't wiring up tool calls. It was making sure an agent with real tools couldn't say anything about the board that wasn't true — the same grounding problem the rest of the coach has, now with a model that can also act . The coach-engine logic underneath Every WebMCP tool call ultimately reads from one deterministic pipeline, not from the model's own reasoning: Each position in a game is analyzed by Stockfish (objective best move and evaluation) and Maia-2 (what a human at a given rating would likely play) in parallel. A pure Rule Extractor compares the two and picks Critical Moments — plies where the position's win probability swung enough to matter. Evaluations are converted from centipawns to a win-probability curve first, since a swing means different things near equal and near winning: $$ \text{WinProb}(cp) = \frac{1}{1 + 10^{-cp/400}}, \qquad \left|\,\text{WinProb}(cp_{i+1}) - \text{WinProb}(cp_i)\,\right| \ge \tau $$ Each Critical Moment becomes a typed fact record (best line, refutation, verdict) before any prose exists, and a validator gate rejects any later explanation that doesn't match those facts ply-for-ply. The WebMCP layer doesn't get to skip this. Every board tool call returns a Coaching Board Snapshot — the same typed facts, plus which line is active and where the viewed ply sits on the game's own line — so the agent is handed grounded state on every call instead of being trusted to ask for it. How I built WebMCP support One authored map, not a second one. Coach tools already carried a coachToolSurface map of which tools the installed Coach App vs. the model may call. Adding the Coaching Board meant widening that map with a "web" target rather than maintaining a parallel list — the two surfaces share list_critical_moments , open_review_moment , and evaluate_player_line against the same data, distinguished by per-tool description, not by renaming. Register inside the auth gate, never at module load. Board routes pass through an asynchronous Beta Access check before a player is known. Tools register on an effect keyed by the authorized player ID and tear down through the AbortSignal registerTool accepts, so there's no window where an agent can discover and call board tools before identity resolves or after sign-out. Push the grounding policy into every result, not just instructions. Descriptions carry the rules once, at registration; each result also carries a constraint block for the facts it just returned, because nothing in WebMCP obliges an agent to re-read state before answering — an agent that skips the read produces fluent, confident, wrong coaching a player can't detect. Keep durable writes off the surface. The agent can stage a game import; only the player's own button press commits it. Challenges I faced Proving it actually grounds, not just that it compiles. A scripted deixis suite driving the board through a real WebMCP host measured 7/8 on referring expressions ( "that line," "the other one" ) but over-called tools on a non-deictic trap prompt roughly one run in five — enough signal to trust the mechanism, not enough to gate a release on yet. No production host to test against on demand. Storybook turned out to be a legitimate WebMCP host for driving the real board tools headlessly through Playwright with --enable-features=WebMCP , since neither ChatGPT's desktop app nor a locked devtools profile could be automated directly. A stale tab looks identical to a broken one. A board left open for hours answered every tool call with a bare "unavailable," which looked like a server-side bug; it was a client holding a dead connection. Fixing it meant turning any client-side throw into a typed unavailable result (rather than an opaque failure) so the agent — and future debugging — could tell "stale" from "actually broken." A withdrawn move can wedge every future write. The throughline: giving a model real hands on the board is only safe once every fact it can act on, and every fact it hands back, traces to the same deterministic pipeline the rest of the coach already trusts. What's next for Quorum - **Calendar integration**, so your agent votes from your real availability instead of being told your constraints. - **Agent-to-agent negotiation rounds** - agents exchange counter-proposals automatically until they converge on a shortlist, and humans only see the final choice to ratify. - **Invites addressed to agents**: send an event link straight to someone's assistant, which handles everything and pings its human only for approval. - **Richer constraints in tools** - recurring meetings, time-zone fairness scoring, and "must attend / optional" roles that agents can reason about. Like Comment Story Updates GIF WebMCP Director focusing and comparing measured visual ranges inside the BeatScope player. Inspiration BeatScope started from a simple problem: music visualizations often look impressive, but the timing logic behind them is usually locked inside one demo. I wanted to turn musical timing into reusable, deterministic data that could drive different visual systems — and also be understood by coding agents. The WebMCP Challenge made it possible to take that idea one step further: instead of making an agent inspect the DOM or guess how the player works, BeatScope can expose its musical state directly as structured browser tools. What it does BeatScope Director adds an in-browser WebMCP collaboration layer to BeatScope. An AI agent can inspect the loaded track, query timing and energy at any moment, read bounded musical events, find visually interesting ranges, compare sections, focus the timeline, control playback, and create loops — all inside the same player the user is watching. It currently exposes eight WebMCP tools through document.modelContext.registerTool() , including: get_project_context get_state_at_time get_events find_visual_moments compare_ranges focus_range control_playback set_loop_range The agent does not receive the source audio. It works from BeatScope's already-computed analysis, while the user's normal local upload and playback workflow remains unchanged. How I built it I kept BeatScope's existing architecture and analysis pipeline intact and added WebMCP as a separate browser integration layer. Both the existing stdio MCP server and the new WebMCP Director read the same Rhythm IR and deterministic runtime, so they describe the same track with the same semantics; only the transport and lifecycle are different. The WebMCP layer is split into schemas, queries, actions, responses, and registration lifecycle code. Read-only tools are explicitly separated from tools that modify the page. Agent actions are visible in the UI and can be reversed by the user. I also built a reproducible WebMCP demo with rights-safe synthesized audio, browser smoke tests, snapshots, benchmarks, and CI coverage. Challenges The hardest part was keeping the agent useful without letting it invent musical meaning. BeatScope deliberately reports measurable facts such as beats, transients, frequency-band energy, and neutral structural repetition. It does not pretend that an onset is a kick or snare, or that a repeated section must be a verse or chorus. Another challenge was browser control. Playback actions have to respect autoplay restrictions, variable-tempo timing, cancellation, page lifecycle, and user ownership of the final state. I also wanted WebMCP to fail gracefully: if document.modelContext is unavailable, BeatScope still behaves like the normal player instead of breaking. What I learned WebMCP works best when it is not just a wrapper around buttons. The most useful tools expose the application's actual domain model. In BeatScope, that means giving the agent direct access to deterministic rhythm, structure, energy, and playback state instead of forcing it to reconstruct those concepts from the interface. I also learned that human-agent collaboration feels much safer when agent actions are visible, bounded, and reversible. The user still owns the player; WebMCP simply gives the agent a structured way to participate.
