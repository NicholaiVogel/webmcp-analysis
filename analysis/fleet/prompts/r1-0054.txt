Like 1 Comment Story Updates OpenAgentLab + Action Ledger What happens when a website stops being something an AI agent merely reads and becomes something the agent can actually operate? WebMCP makes that future possible by allowing websites to expose structured capabilities directly to agents. I built OpenAgentLab + Action Ledger to explore the next problem that immediately follows: How do we make agent actions trustworthy when they can change real application state? It is a developer workbench for observing, testing, governing, and safely executing agent-native web actions . The included Acme Issues application is intentionally simple. The interesting part is not the issue tracker itself; it is the infrastructure around an agent deciding whether to search, inspect, close, or permanently delete an issue. The project turns agent actions into something humans can preview, approve, verify, audit, evaluate, and—in reversible cases—undo . Inspiration Web interfaces were designed around an assumption: a human sees the interface, understands the consequences, and clicks the button. WebMCP changes that interaction model. An agent can discover a capability such as: search_issues get_issue close_issue delete_issue and invoke it directly from the website. That is powerful, but it raises a deeper question. If an agent can call delete_issue , a confirmation dialog alone does not create a trustworthy system. We also need to know: Did the agent choose the correct tool? What exactly will change? Is the operation reversible? Did a human actually authorize this specific action? Did the underlying resource change after the preview? Could a retry accidentally execute the mutation twice? Can we verify what happened afterward? Can developers detect a dangerous tool contract before shipping it? That became the core idea behind OpenAgentLab. Instead of treating agent tooling as a collection of API endpoints, I wanted to treat it as a governed action lifecycle . What it does OpenAgentLab exposes four native site capabilities through WebMCP: search_issues get_issue close_issue delete_issue Read operations are exposed as read-only tools. Consequential operations work differently. When an agent invokes a write tool, the mutation does not execute immediately . The server creates an Action Ledger proposal containing the target resource, reason, risk, declared side effects, reversibility, and a before/after preview. The agent receives a sanitized response indicating that the action is awaiting human confirmation. The approval credential itself stays on the human UI path rather than being returned to the agent. The user can then review exactly what is about to happen and choose Reject or Approve & execute . The Action Ledger The heart of the project is a state machine that explicitly separates intent from effect : PROPOSED ↓ PREVIEWED ↓ AWAITING_CONFIRMATION ↓ APPROVED ↓ EXECUTING ↓ EXECUTED ↓ VERIFIED Rejection, failure, and rollback are explicit branches rather than hidden side effects. Invalid lifecycle transitions are rejected. Every ledger entry records information such as the tool and schema fingerprint, redacted arguments, reason, risk, affected resources, declared side effects, preview, confirmation policy, execution result, provenance IDs, and transition history. Ledger entries and transitions are hash-linked to their predecessors, making accidental history modification detectable. I deliberately describe this as tamper-evident rather than tamper-proof . The project does not pretend a locally controlled application provides cryptographic non-repudiation. Human control is enforced at the execution boundary One of the most important design decisions was making approval a server-side execution requirement , not simply a UI state. For guarded operations the runtime: requires the action to be in AWAITING_CONFIRMATION ; validates a high-entropy approval credential; verifies its persisted hash; compares credentials safely; re-checks the resource revision against the preview; prevents duplicate mutation through idempotent execution behavior; executes the capability; verifies the resulting state. This also protects against stale previews . If an issue changes after the human saw the preview but before approval reaches the execution boundary, the mutation is rejected instead of applying an obsolete decision. Real undo, not cosmetic undo close_issue is explicitly modeled as reversible. After successful execution and verification, OpenAgentLab stores the previous issue state. A user can choose Undo , at which point the runtime checks that the resource has not changed unexpectedly and restores the previous state while recording a ROLLED_BACK transition. delete_issue , by contrast, is explicitly irreversible and never advertises undo. That distinction is visible both to the human and in the tool contract exposed to the agent. Testing the agent contract itself One of the ideas I am most excited about is treating tool descriptions as executable safety infrastructure . The flagship scenario is: “Clean up old resolved issues.” The expected operation is close_issue , while delete_issue is explicitly forbidden. The project can intentionally expose a weak delete_issue contract: Remove an issue from the issue tracker. For an ambiguous cleanup request, that contract can lead to selection of the destructive tool. Like Comment Story Updates Grapevine Ops Center Grapevine Field Inbox "moblie app" Grapevine Warehouse Inventory Grapevine Partner Directory Inspiration We grew up in Boone, North Carolina, in the heart of the western Appalachian Mountains. Almost two years ago, Hurricane Helene devastated the region. As we worked to support relief efforts back home, one major problem kept coming up: logistics . Roads and bridges were gone, and conditions could change by the hour. But people still had their phones. Locals, responders, and volunteers were sharing what they saw through social media, texts, and calls, creating a constant stream of updates from the field. Meanwhile, people coordinating supplies could be miles away, working from information that was already outdated. The ground truth was out there. Getting it to the right people fast enough to act on it was the hard part. That experience stuck with us. When we started thinking about what to build for this hackathon, we kept coming back to one question: what could this look like if AI agents and WebMCP were part of the response infrastructure? Project Grapevine is our fictional simulation of that idea. The name is a play on "heard it through the grapevine," except we're exploring what that network could look like when people, sensors and AI agents can all contribute to it. In our scenario, a large relief organization is trying to move supply trucks into communities affected by a devastating flash flood. They have an AI agent helping coordinate logistics, responders on the ground and sensors reporting current conditions. What it does Project Grapevine gives an AI agent tools to help coordinate a disaster response while keeping people in control of consequential decisions. The simulation starts with a common problem: the command center needs to move supplies into an affected area, but its route information may already be outdated. Instead of relying on stale information, the agent can use WebMCP tools to find people and simulated sensors near the route (aerial drone footage) and request current conditions directly from the field. Grapevine connects two workspaces: Live Ground Truth: The agent checks the regional baseline, identifies nearby responders and sensors, and prepares a structured request asking whether a route is passable. Once a person authorizes the request, a responder or sensor can report current conditions. That response flows back to the agent as structured evidence, including information about the source and its quality. Resource Coordination: At the same time, the agent can review the crisis brief, search available relief partners, evaluate what resources they can provide, and build a shortlist. From there, it prepares a work plan for human review and approval. The important part is how those workflows connect. Grapevine won't allow the coordination plan to be approved until current route evidence has been received. A passable report unlocks final approval. A caution or blocked report keeps it locked. The agent does the legwork: finding sources, gathering information, comparing resources and preparing a plan. People provide the ground truth, and a person makes the final call. How we built it We built Grapevine around the idea that an agent shouldn't have to navigate a website the same way a person does. Instead, the application exposes specific workflows directly to the agent through WebMCP. We started building Project Grapevine on August 31. Everything here, including all ten WebMCP tools across the workspaces, was built new for this submission. Each workspace registers its own tools using document.modelContext.registerTool . The Live Ground Truth workspace exposes five tools for finding available sources, checking existing information, asking a source for an update, retrieving the response and rating its quality. Resource Coordination exposes another five for reading the crisis brief, finding response partners, reviewing their capabilities, creating a shortlist and preparing a coordination request. We used Zod schemas to keep inputs structured and validated, while WebMCP tool annotations distinguish between read-only operations and actions that require human control. The agent can do a lot of the work on its own, but it can't make the final decision. Behind the scenes, a Cloudflare Worker and D1 database maintain shared workflow state across the agent, operations dashboard and field responder inbox. An agent can stage a request at the command center, have it appear on a responder's device, and then pull that response back into the workflow as new evidence. React manages the visible approval states and keeps the final coordination action locked until the required ground truth has been collected. One intentional design decision was what we didn't expose to WebMCP. The field responder inbox registers no tools at all. It's a human surface by design. The agent coordinates the request, but the person in the field provides the ground truth. Challenges we ran into One of our biggest challenges wasn't figuring out what the agent could do. It was designing around what it should do . Building with WebMCP means thinking about two users at the same time : the agent using the tools and the humans doing the work. That made the UX more complicated than we expected. We had to think through the full workflow, what information the agent needed, what a person needed to see and where automation should stop. Just because an agent can take an action doesn't mean it should. Especially in a disaster response situation That became one of the most important design principles behind Grapevine. We intentionally added approval gates before consequential actions. An agent can identify a response partner and prepare a work request, for example, but a person has to approve it before it's sent. The same is true for publishing a request to Facebook. The agent can do the research and prepare the action, but the human still makes the call. Those controls aren't instructions buried in a prompt. They're enforced by the application itself. We think that's an important consideration when designing with WebMCP. Human experience still matters. In many cases, the best agent workflow isn't the one that automates everything. It's the one that removes friction while being deliberate about where human judgment belongs. Trust was another part of that challenge. Simulated sensors are clearly identified, different source types have different capabilities, and the agent can evaluate the quality of the evidence it receives. If information is incomplete or conflicting, Grapevine surfaces that uncertainty rather than pretending it has an answer. Accomplishments that we're proud of We're proud that we took a real-world event with real coordination challenges and turned it into a working example of how humans and AI agents could collaborate differently during disaster response events. Hurricane Helene hit our hometown in September 2024. We watched our own community struggle, respond and come together in its aftermath. That experience became the foundation for Grapevine. We're also proud that Grapevine became a working end-to-end workflow rather than just a demonstration of an agent calling a few tools or navigating a website. For example, in our demo, the agent uses drone reconnaissance to identify a possible fallen tree, asks a responder to visually confirm it and then helps coordinate a team to clear the road.
