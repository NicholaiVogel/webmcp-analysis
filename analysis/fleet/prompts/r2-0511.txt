Every AI action gets a signed receipt with a deep link your screen reader can verify directly — so you never have to trust an agent's word for what it just did. Like Comment Story Updates The verification gap nobody talks about Blind and low-vision users already use AI agents to operate the web — filling forms, managing lists, navigating sites with dozens of menus. The part that still doesn't work is trust. A sighted user glances at the screen and knows instantly whether an action succeeded. A screen reader user has no equivalent glance. Today, verifying what an agent did means re-navigating the whole page by hand, which erases most of the time an agent was supposed to save. A study of 16 screen-reader-using programmers found that verifying AI output, not producing it, was consistently the most time-consuming part of their workflow. That's the problem Prove It is built to solve. What it does Prove It is a household task manager where every action an AI agent takes — adding a task, marking it done, changing its priority, deleting it — produces a structured, inspectable receipt : what changed, exactly where it lives in the page, and what to say if it failed. Every receipt includes a deep link . Clicking it moves real keyboard and screen-reader focus straight to the element that changed, so the person hears their own assistive technology confirm the action in its own words — not a paraphrase from the agent, and not a guess from re-navigating the page. Failures get the same treatment. If the agent tries something invalid — an unknown task, a bulk delete it isn't allowed to perform — that produces an error receipt too. Proving what an agent didn't do, and why, is as important as proving what it did. How I built it The whole app runs on one function, performTool(name, args) , which is the single source of truth for all seven tools ( list_tasks , add_task , set_task_status , update_task_priority , delete_task , focus_task , get_last_receipt ). That one function is wired to two transports: Native WebMCP. On load, the page feature-detects document.modelContext / navigator.modelContext and calls registerTool() for each tool with a strict JSON Schema. Any WebMCP-aware agent — Chrome's built-in agent with the WebMCP flag on, or ChatGPT's in-app browser — can discover and call these tools directly, no code changes required. In-page demo agent (fallback). If WebMCP isn't available in the browser, the same seven tool schemas are sent to the Claude API as tools , so anyone can test the full loop — natural language in, tool call, receipt, verify — in an ordinary browser with no flags. Every write tool returns { tool, changeType, timestamp, target: {selector, description}, before, after, errors } . changeType is created , updated , deleted , verified , or error . Receipts render as a literal torn-paper "receipt tape" in the UI — a visual metaphor for the whole concept: a printed proof of exactly what happened. The negative test There is no delete_all_tasks or bulk-export tool, on purpose. The agent is instructed to delete tasks one at a time and to ask before any bulk action — so "prove it" also covers proving the agent can't do something irreversible, because the capability was never exposed as a tool in the first place, not because a prompt told it to behave. Challenges I ran into The trickiest part wasn't the receipts — it was making the deep link mechanism actually work for a screen reader, not just look like it does. Early on, clicking a receipt just scrolled to an element and added a CSS glow, which does nothing for someone who can't see the glow. The fix was making sure every deep-linked element is a real, focusable DOM node ( tabindex="-1" where it isn't natively focusable) with an aria-label that reflects its current state, and that the deep link calls .focus() on that exact node. The visual highlight is a bonus for sighted collaborators, not the verification mechanism itself. The other challenge was keeping one tool contract honest across two very different transports. Rather than writing tool logic twice, performTool() is called by both the native registerTool().execute() handlers and the in-page agent loop, so a receipt means the same thing regardless of which agent produced it. What I learned Verifiability isn't a feature you bolt onto an agent's output after the fact — it has to be a structural property of the tool contract itself: a real DOM target, a real before/after diff, a real focus event. WebMCP's tool registration model turns out to be a genuinely good fit for this, because the receipt an agent returns and the page's actual state can be forced to be the same object, not two things that merely claim to agree. Reproduce any application state and see the real UI instantly. Like 1 Comment Story Updates Inspiration When testing a web application, the difficult part is often not the test itself. It is getting the application into the exact state you need to inspect. An expired account. A trial user. An unauthenticated session. A specific error state. Reproducing these states can require creating users, changing database records, configuring subscriptions, or manually navigating through multiple steps. I wanted to remove that setup work. Repro lets you describe the application state you want to see, reproduce it, and inspect the real UI immediately. We don't run your tests. We create the state you need to see. What it does Repro exposes application-state reproduction through three stable WebMCP tools: list_states reproduce_state reset_state Instead of creating a separate tool for every test scenario, Repro treats application states as data. For example, an agent can discover an available state such as free_expired . Repro applies that state to an isolated Repro session, and the application's existing UI renders normally. This makes it possible for humans and agents to inspect production-like UI states without creating real users, payments, emails, or other production side effects. How I built it Repro is published as the repro-webmcp npm package. The basic workflow is: npm install -D repro-webmcp npx repro scan npx repro setup repro scan statically analyzes an existing JavaScript or TypeScript application and discovers semantic application states from existing code, including conditional UI branches, enums, literal states, mocks, fixtures, and tests. The discovered states become the source of truth for Repro. repro setup prepares the runtime, browser registration, and integration boundary. For simple supported state architectures, the connection can be generated automatically. For more complex applications, a coding agent connects one generic bridge to the existing state boundary. Repro generates a project-specific .repro/AGENTS.md integration guide containing both its standard integration rules and evidence discovered during the scan. A coding agent can use this to connect Repro once to the application's existing state boundary. The important distinction is that the agent does not generate a separate test fixture for every state. It creates one generic bridge between Repro and the application's normal state/rendering system. Dogfooding on an existing application I tested Repro on a separate existing application that was not built for this challenge. Before installing Repro, it contained zero manually defined Repro states. Running repro scan discovered 20 candidate application states from the existing source code. For this more complex application, I gave the generated integration instructions to Codex. Codex implemented one generic bridge to the application's existing authentication/session state. After that, the same three WebMCP tools could reproduce states such as authenticated and unauthenticated, while the real application UI continued to render through its normal code path. This dogfooding also exposed an important setup bug: the browser bootstrap was still loading an older hand-written configuration instead of the scan-generated states. I fixed the runtime/setup flow and published the fix as repro-webmcp@0.1.4 . Challenges The hardest problem was finding the right boundary between automation and application-specific integration. Automatically discovering states is possible, but automatically modifying arbitrary application state safely is much harder. Real applications use different stores, authentication systems, module structures, and rendering architectures. I initially considered generating state-specific fixtures, but that would simply move the manual test-setup problem somewhere else. The architecture evolved into: automatic state discovery + a stable runtime + one generic application bridge when necessary. Another challenge was safety. Reproducing an expired subscription should not require modifying a real subscription. Reproducing an authenticated user should not require creating a production user. Repro therefore focuses on reproducing the application state consumed by the UI rather than recreating the entire backend environment. How I built it TuneQL uses Next.js, React, TypeScript, PGlite, Zustand, and IndexedDB. PostgreSQL runs inside a browser worker, and the workspace data stays on your device. The UI and all 20 WebMCP tools go through the same command layer, so things like query validation, constraints, benchmarks, activity history, and revision checks behave the same in both places. Challenges and learning One of the harder parts was keeping the PGlite worker, saved workspace, UI, and agent actions all in sync. I also realised pretty quickly that you can’t judge an optimization from just one timing. So TuneQL does a few warm-up runs, runs the benchmark multiple times, and checks the full result instead of just comparing the few rows shown in the preview. Like Comment Story Updates Inspiration I am both a mechanical engineer and a web developer , and this project came from combining these two parts of my experience. In mechanical engineering, having a good idea is only the beginning. The idea must become real geometry, materials, joints, forces, sensors, controls, and measurable results. In web development, I learned how a good interface and AI can make a complicated tool easier for more people to use. This made me ask one question: What if AI could do more than generate a picture or description of a machine? What if it could enter the same engineering workspace as the human, build the machine part by part, test it, see what failed, and improve it? This is why I built ForgeTwin. I wanted someone to describe a physical goal in normal language, without knowing every CAD command, and then watch an AI agent turn that goal into an editable, animated, and testable mechanical system. As an engineer, one principle was very important to me: A design should not be trusted only because it looks convincing. It should be tested with physics and evidence. Don’t generate it. Engineer it. What it does ForgeTwin is a browser-based AI engineering sandbox. The user describes a machine or mechanical goal, and ForgeTwin creates a versioned physical world from reusable parts. For example, a user can ask: “Build a conveyor that sorts red and blue boxes at 20 boxes per minute.” “Build an electric go-kart with four wheels, steering, accelerator and brake pedals.” “Build a brazing fixture that positions a heat exchanger and two copper pipes within 2 mm.” ForgeTwin then: Understands the requested machine, functions, and measurable requirements. Creates an engineering plan instead of returning only text. Breaks the design into assemblies and reusable low-level components. Gives every component dimensions, material, mass, position, and orientation. Adds physical connections, joints, motors, sensors, actuators, and control logic. Builds the machine in an interactive 3D workspace while the user watches. Runs a fixed-step 60 Hz Rapier simulation. Reads telemetry, collisions, movement, and requirement measurements. Finds the reason when a requirement fails. Changes the related geometry, physical property, actuator, motor, or controller and runs the test again. The app is not limited to conveyors. Its 39-part reusable vocabulary covers structures, power transmission, controls, road vehicles, motorcycles, aircraft, rotorcraft, tracked mobility, and articulated robots. It can compose cranes, lifts, bicycles, go-karts, motorcycles, cars, rovers, robotic arms, humanoid robots, gearboxes, suspension systems, airplanes, helicopters, solar trackers, bridges, warehouse systems, agriculture machines, recycling systems, HVAC fixtures, medical lifting mechanisms, and new systems made from smaller primitives. The current app includes 19 editable challenge briefs , but these are examples, not locked machine templates. The user can change the prompt, dimensions, load, speed, or target. If a special component is not already available, the planner can build it from lower-level parts such as beams, plates, tubes, shafts, wheels, pulleys, joints, sensors, and motors. The user can also: Use the built-in AI without entering credentials, or temporarily use their own OpenAI API key. Edit the existing design with natural-language chat instead of starting over. Select, move, resize, and rotate parts in X, Y, and Z. Orbit the full camera through 360 degrees with mouse or touch. Use a rotation gizmo, snapping, or numeric angle entry. Lock a manual change so the AI redesigns around it instead of moving it back. Animate the operating sequence of different machine families. Run physics and replay a failure in slow motion. Use X-Ray Mode to inspect joints, sensor paths, axes, collision boxes, actuator paths, and velocity information. Inspect requirement evidence and see what passed, failed, or was not evaluated. Undo changes, restore revisions, and compare a failed design with the improved design. Export the current world as PNG, JPG, PDF, STL exchange geometry, or complete ForgeTwin JSON data. How I built it ForgeTwin is built with Next.js, React, TypeScript, Tailwind CSS, Three.js, React Three Fiber, Drei, Rapier, and Zod . The main idea is that the machine is not saved as one opaque 3D model. It is stored as a shared engineering graph containing: Assemblies and individual bodies Dimensions, materials, mass, and rigid-body properties Position, rotation, and machine orientation Mechanical, power, and signal connections Fixed, revolute, prismatic, spherical, spring, rope, gear, and belt joints Motors, sensors, actuators, and control rules Simulation runs, telemetry, collisions, and failure evidence Human-owned edits and immutable revision history The 3D editor renders this graph procedurally. The same graph is used by the human interface, the built-in model agent, the physics simulator, the activity feed, exports, and an external WebMCP agent. The hosted AI uses GPT-5.6 Sol through the OpenAI Responses API . To keep generation faster and more reliable, the model creates a compact engineering intent: the object identity, architecture, motion, controls, primitive vocabulary, and requirements. ForgeTwin then expands that intent into the complete body-and-joint graph, validates it, repairs safe topology problems, and executes the design through guarded tools. The hosted key stays on the server, so judges can use the full AI experience without adding a key. A visitor can still connect their own key for the current browser tab. That key is kept only in memory and is not stored. If model access is unavailable, ForgeTwin also has a deterministic local engineering path for the main design, physics, optimization, and supported chat-edit operations. I also created one universal coordinate convention for every machine: +X is front, -X is rear, +Y is up, -Z is left, and +Z is right . This helped fix many problems with lights, wheels, propellers, steering, windshields, and joint axes. The design validator checks for missing supports, hubs, axles, joints, steering links, bad proportions, wrong orientations, floating components, incorrect joint axes, overlaps, blocked windshields, and unrequested systems. For example, a go-kart uses front wheel hubs, spindles, steering knuckles, separate kingpin axes, tie rods, a steering rack, column, and Ackermann-style steering instead of making the whole wheel rotate around one incorrect axis. Rapier runs the connected rigid-body world at a fixed 60 Hz and records replay frames and collision events. Some advanced engineering results, including aerodynamics, flexible cables, structural stress, detailed tire behavior, and some manufacturing processes, still use clearly labeled reduced-order checks. ForgeTwin is a concept-validation sandbox, not a replacement for certified CAD, FEA, CFD, medical approval, or safety analysis.
