=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Every event is stored once and projected per viewer, so unauthorised fields never appear in another participant's HTTP body or WebSocket frame. The test suite asserts this at the wire, not at the function boundary. Revision discipline instead of pretend realtime. Every mutation carries the agent's last-seen revision. A stale one returns a structured sync_required with a delta instead of acting on old state. That fits an agent that participates in bursts far better than a subscription it never really holds. Consent an agent cannot forge. An agent may recommend a grant, but a change beyond what the user delegated only stages . Staging mints a single-use code delivered on the participant's own realtime channel. The applying command must carry it back, and the code never appears in any tool result. Eligibility, minimal-conflict-set detection and the impasse counterfactuals are all deterministic. No model is allowed to invent a feasibility fact. 364 automated tests across three lanes: 222 unit, 128 three-user API, and 14 Playwright specs driving three isolated browser contexts. Challenges I ran into Privacy that is neither a lie nor a hole. The rule I settled on is that a private need's effect is always public and its content never leaves its owner. Both halves matter. Hiding the effect would make the count inexplicable, and leaking the content is the whole thing I was avoiding. It took a real redesign to stop routing private predicates through shared state "just for rendering", and a wire-level test suite to prove I had. Proving a human consented, honestly. My first cut let a bearer token commit an agreement over plain HTTP without ever touching the page. The realtime-only nonce closes that. It still is not proof a human clicked, because the realtime channel authenticates with the same token. Rather than overclaim, I wrote the residual threat model down in KNOWN-LIMITATIONS.md . Keeping the interface domain-agnostic. It is hard not to type a domain word into a heading. What saved it was a rule on the server side. The server returns the facets present across the current result set, each with a mandatory unknown count, and the client renders whatever it gets. There is no domain branch anywhere in the front end, which is also what lets a human and an agent reason over the same vocabulary. Deployment, on the last evening. I had prepared a Coolify deployment and abandoned it at the gate. Its Traefik has documented WebSocket failures on compose stacks, and the room is a WebSocket. The January 2026 disclosure put eleven critical CVEs in a control plane that runs as root. Its baseline would have claimed a quarter of a 4 GB box before Postgres started. The existing compose file was already a correct production stack. It needed twenty lines of Caddy in front, not a PaaS. That deploy went out with nineteen minutes to spare, after a self-inflicted detour in which a redeploy overwrote the host's generated Postgres password and stranded the database behind credentials nothing had written down. Two rendering bugs that looked like design problems. Vite's dependency optimiser broke MapLibre's worker, so the basemap never drew. A CSS animation setting transform silently overwrote a positioning translate and threw pins at their anchors. Both cost hours before either was understood. Accomplishments that I'm proud of An agent that can advocate for a constraint it never discloses. The agent screens places locally and returns per-place verdicts. The council folds them into eligibility, and peers see the aggregate effect with no route back to the cause. That is the capability I most wanted WebMCP to make possible, and it works. Until we added WebMCP :) What it does Every page of competitortracker.io now registers 11 WebMCP tools - in production, in four languages, for any agent riding along in the visitor's browser. Three groups: Q&A over the site's own words. search_site , get_page , get_pricing , compare_with_rival , about_competitor_tracker . An agent can answer any question about the product from what the pages actually say — the agent and the human are never told different things. Public competitor data. search_companies , get_company , list_industries , get_industry , get_recent_changes over our open CC BY 4.0 data: 300+ tracked companies, 50 industries, and the dated, classified change feed. This is the product doing its actual job in the agent's hands, not a description of it. Agent signup. start_tracking_competitors : the agent names the companies you care about, we create an unclaimed organization (no email, nothing charged, self-deletes in four days), and hand back a claim link plus a short-lived read token. The tool then tells the agent the follow-up move: wait ~15 seconds, call GET /v1/changes with the token, and lead with what changed at your competitors — then hand over the claim link so the human takes ownership. So the full arc works with zero forms: ask a question, see real competitor changes, get tracking set up, claim it - all before you have an account. How we built it The site is Hugo on Cloudflare Workers, and most of the machinery already existed for AI crawlers: every page has a markdown twin, llms.txt is a curated per-page index, and our competitor data ships as an open JSON tree. So the WebMCP layer needed no search backend and no new data - the tools are framework-free ES modules that read what the site already publishes, plus one POST to our live agent-signup API. Details we care about: A 411-byte loader rides every page; the ~13 KB tool bundle is injected only when a modelContext runtime actually exists. Ordinary visitors pay nothing. The two required headers ( Permissions-Policy: tools=(self) , Origin-Agent-Cluster: ?1 ) ship from our edge worker, the single chokepoint for all responses. Every execute() is wrapped so no failure ever throws - a browser agent runtime has no defined behavior for an uncaught rejection, so every path returns a result the agent can read. Telemetry counts calls, never contents: tool name, page, language, outcome. The module is open source (MIT) - the loader, registration helper and validation utils are generic enough to point at your own tools. Challenges we ran into The spec moved under us. The getter lives on document.modelContext but half the browsers on the origin trial still carry navigator.modelContext ; we probe both. And unregisterTool() / provideContext() are gone from the spec - teardown is aborting the signal you registered with. Generated code confidently suggests the removed API. Testing without a runtime. No browser in our CI has WebMCP, so we built a Node harness that runs the real tool modules with stubbed browser globals against the live site and API — every tool, every error path. Honest copy is a design constraint here. A 503 from the signup API must never be spoken as "we don't track that company," and the 15-second wait is a write-settle margin, not "we're fetching your data now" - the change history is already published. Agents repeat what tools tell them, so the tool result text is a product surface. How do I test this? It took some time to figure out how to test WebMCP in Chrome. Accomplishments that we're proud of It's live on our real production site , not a hackathon sandbox - every page, every language, behind a one-line kill switch. The signup flow keeps the human in charge without a single confirmation dialog: the org holds no money, sends no email, expires unclaimed, and the claim page is the confirmation step. The whole thing reuses surfaces we'd already built for fetching agents (markdown twins, llms.txt , open data) - the pre-account story just needed the last mile into the tab. Fifteen seconds after asking, an agent shows you what your competitors changed. That's the demo, and it's real. What we learned A tool declaration is a hint to a cooperative agent, never a security boundary — validation lives server-side, and the published-catalog-only rule (the tool never fetches a URL you supply) is the guarantee the whole feature stands on. The right scope for in-page tools isn't feature parity with our MCP server (50 tools behind OAuth). The web page is the before-the-account surface; the MCP server is after . Drawing that line made every other decision easy. Sites that already publish machine-readable views get WebMCP almost for free. The work we'd done for crawlers became the engine for in-tab agents.
