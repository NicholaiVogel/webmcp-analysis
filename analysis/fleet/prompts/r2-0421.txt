Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Detection is deterministic: regular expressions plus real checksums (ISO 13616 for IBANs, Luhn for payment cards, the Spanish DNI/NIE and CIF control characters, the official Italian VAT algorithm). Never an LLM. A model would answer differently on the same document from one run to the next, and sending a document to a model to ask what to hide from that model defeats the purpose. The one that carries the argument is mask_document_in_page , and what matters is what it doesn't take: document.modelContext.registerTool({ name: "mask_document_in_page", description: "Masks the personal data in the document the user has already loaded into this page, without the caller ever receiving the document.", inputSchema: { type: "object", properties: { customTerms: { /* ... */ } } }, execute: async (input) => maskPageDocument(input), }); No text parameter. Galleon lets Codex pay publishers for original content, delivering valuable answers while funding writers to produce more knowledge. Like Comment Story Updates Inspiration Publishers earn through subscriptions and advertising. Agents do not look at ads, and they often need one authoritative source rather than a full subscription. A publisher's work can become more useful to agents while generating less revenue for the people who created it. Galleon asks a simple question: what if a webpage could quote an exact price to an agent, let the person approve it, and return the licensed source with its canonical citation? What it does Galleon gives an AI agent an authenticated wallet with human-controlled spending limits. A participating publisher exposes two WebMCP tools. inspect_source returns free metadata, provenance, the exact price, access rights, and a signed offer. unlock_source redeems a short-lived entitlement and returns the full article as formatted Markdown with its canonical citation. Payment authority never enters the publisher page. After the person approves the exact source, price, and rights, the agent calls purchase_offer through the user's local Galleon wallet MCP. The wallet validates the offer, enforces spending policy, records the purchase, and returns an entitlement scoped to that source and publisher. The complete flow is intentionally small: const offer = await inspect_source({}); await human.approve({ source: offer.source.title, price: offer.offer.display_price, rights: offer.offer.rights, }); const purchase = await purchase_offer({ offer_token: offer.offer.offer_token, expected_amount_minor: offer.offer.amount_minor, expected_currency: offer.offer.currency, idempotency_key: crypto.randomUUID(), }); const article = await unlock_source({ entitlement_token: purchase.entitlement.token, }); return { markdown: article.source.markdown, citation: article.source.citation, }; The current prototype uses test credits. Why WebMCP WebMCP lets the commercial terms travel with the source. The agent discovers the offer on the page instead of scraping a paywall or sending the user through a separate checkout. We pair WebMCP with a traditional MCP because they represent different trust boundaries. WebMCP belongs to the publisher page and exposes page-scoped source tools. The wallet MCP belongs to the user and holds identity, balance, policy, and purchase authority. Together, they let a person and an agent buy one authoritative source without exposing payment credentials or moving the article into an intermediary catalog. We believe the end-state of Galleon is one where the human browsing experience remains the same as it has historically been and ad-supported, while agents are metered for their consumption. How we built it We built and deployed Galleon on floo , which helped us ship a multi-service application with Codex and allocate necessary resources such as our postgres database. Codex was our primary agentic development tool. We used Codex to implement the TypeScript application, inspect the repository, test the real browser journey, exercise the WebMCP tools, review trust boundaries, diagnose deployment failures, and iterate on the product experience. The system has three parts: A consumer application for accounts, test-credit wallets, spending policies, and purchases. An authenticated wallet MCP that validates offers, records retry-safe ledger transactions in PostgreSQL, and issues short-lived entitlements. An independently hosted publisher that registers inspect_source and unlock_source through document.modelContext.registerTool(). Offers and entitlements are signed and bound to the content, publisher origin, and browser session. The publisher receives only the entitlement. It never receives the user's wallet credential. Challenges we ran into The first challenge was the economics of very small purchases. Traditional credit-card checkout is poorly suited to charging a few cents whenever an agent needs one source. We built a test-credit wallet and balanced ledger to prove the interaction before connecting production financial infrastructure. The second challenge was separating trust correctly. The publisher needs proof of purchase but must never receive the wallet credential. The wallet must pay the correct publisher but must never trust unsigned claims from page JavaScript. This led us to connect page-scoped WebMCP tools and the authenticated wallet MCP with signed, short-lived capabilities. Live testing also exposed a cross-service signing-key mismatch. Separate service containers generated separate keys, so the wallet correctly rejected the publisher's offer. We moved the key into shared secret-backed configuration and added tests for the multi-service boundary. Accomplishments that we're proud of We built a coherent product experience, not only a tool demo. A user can create an account, fund a test wallet, connect Codex, inspect a paid source, approve the exact terms, purchase it, and unlock it on the publisher's own website. The publisher retains its content and canonical URL. The user retains payment authority. The agent receives the evidence and citation it needs. We think that this idea of building a consumer-grade wallet and payments infrastructure could really benefit publishers who need a way to transform their businesses for the AI era. What we learned WebMCP and MCP are complementary. WebMCP provides contextual tools controlled by the publisher. MCP provides durable authority controlled by the user. We also learned that agent payments are a capability and trust problem before they are a checkout problem. Origin binding, session binding, explicit approval, retry safety, and narrow entitlements make the experience understandable and safe. What's next for Galleon Our next step is focused: connect Galleon to real financial infrastructure and work directly with publishers to help them earn from agent demand. The prototype uses test credits today. The goal is real settlement that supports the people producing the knowledge agents depend on. What it does StudyTree is a turn-based learning game on a shared canvas. A human and an AI agent take turns building a knowledge tree around a single learning question. The human clicks and types. The agent can only change the board by calling registered tools. Voice is the agent's controller. Node types: 🌱 Root (the learning question) · 💡 Concept · 📚 Resource · ⚡ Skill · ❓ Gap Moves: Plant, Branch, Prune, Mark Gap, Mark Clear, and a human-only Undo of the agent's last move. Rules: 10 moves total, alternating turns. Win with 5+ nodes and zero gaps remaining when the moves run out. Lose if gaps are still open. The game works through two agent surfaces, and both go through the same six tools: WebMCP an in-browser agent (like ChatGPT's built-in browser) calls tools registered on document.modelContext . ElevenLabs voice an on-canvas voice panel connects to a public ElevenLabs agent that invokes the same moves as client tools. get_board is read-only and free; the other five are the legal moves. Tool arguments accept a node's label as well as its id, so a voice agent can say "branch from First Principles" instead of spelling out n3 . How I built it The build was almost entirely agent-driven, in stages: Voice dump. I started by talking the idea out loud with a Grok voice bot and let it spit the concept back to me. Cloud agent scaffold. That spec went into a Cursor Cloud agent, which spun up the first version. I pulled it down and tested it on a local port inside the Codex browser. Refinement. I brought in Claude Opus 5 to refine the architecture and tighten the tool layer. Redesign. When Claude 5.1 dropped yesterday, I had it re-evaluate the whole design. I pulled visual references from Cosmos for inspiration and had it pick apart the game mechanics. That's where it evolved from "a tree you build" into a real turn-based pairing between human and agent. Stack: Vite · React 19 · TypeScript · React Flow (canvas) · Zustand (state) Architecture: there is exactly one implementation of each move, in the Zustand store. Three entry points reach it: human buttons ──┐ WebMCP tools ──┼──→ applyMove() ──→ store action ──→ React re-render voice tools ──┘ Neither agent surface can touch the DOM or skip a rule, because both call the identical store actions the human's buttons call. Adding a move means adding it once in moves.ts , and both surfaces pick it up. WebMCP registration is feature-detected, so nothing breaks in browsers without it, and the ElevenLabs SDK is code-split so the board is interactive before the voice stack loads.
