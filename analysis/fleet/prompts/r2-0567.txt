=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates The problem Rostering is a constraint problem that looks like a conversation. A manager says "give Tom Friday off" and means "re-solve a 210-variable integer program under thirty-three rules, and tell me if it can't be done." Language models are very good at the conversation and very bad at the program. Ask one to build a ten-person week with coverage minimums, keyholder cover, eleven-hour rest, contract ceilings and floors, and five separate absences, and it will produce something that looks like a roster. It will not be optimal, it will usually break a rule, and when the week is genuinely impossible it will hand you a schedule anyway, because producing plausible text is what it does. Nobody notices a wrong roster in the tool. They notice it on a Friday night when the cafe cannot legally open. What we built A web page that gives the agent the thing it does not have: a real mixed-integer solver, HiGHS, compiled to WebAssembly and running in the tab. The agent talks to the manager and edits the rules; the solver decides. Every answer is one of exactly three: optimal, meaning no better roster exists under these rules; infeasible, meaning none exists at all; or timeout. There is no fourth branch where it guesses. Why this is a strong fit for WebMCP Three properties of this problem are the argument for putting tools in the page rather than behind an API. First, the engine has to be where the data is: rosters contain names, pay rates and the reasons people are absent, which is the least uploadable data a small business owns, and WebMCP lets the computation happen inside the tab the manager already trusts. There is no server in this project at all - no account, no upload, no database - and it ships as a static export, so "the roster never leaves your browser" is true of the deployment as well as of the code. Second, the answer has to be a fact rather than a message: an in-page tool returns a value the model did not author, and "infeasible" plus six rule ids is not something an agent can talk its way around. Third, both parties need to be looking at the same thing - the manager watches the grid fill in as the agent solves, and the agent sees the rules the manager just changed. Choosing which rule gives way is a judgement about people, and neither the agent nor the solver is entitled to make it. They can ask "will anyone take my Friday night?" and get the list of colleagues the solver has verified can take it without breaking the week - each one checked by re-solving the entire roster with that person pinned to that shift - rather than asking in a group chat. A test fails the build on any capability that is neither exposed to agents nor carries a written reason for being withheld; three are withheld and each says why in the source. The tool surface is a function of state rather than a constant. Tools are registered when they become possible and aborted when they stop being: explain_conflict only exists while the roster is actually infeasible, publish_roster only once there is a clean solved week, and the manager and staff views expose different surfaces entirely. The browser's site-tools count changes as you work, because the tool list is the state of the page. WebMCP has no confirmation API - the spec lists user prompting as an open question, and requestUserInteraction, which several write-ups describe, does not exist in any shipping build. What Agentready Network does Agentready Network is a local-first registry and runtime of reviewed action packs . A pack describes what a site can do, on exactly which origin, with which risk labels. The runtime turns that pack into live WebMCP tools inside the user's own signed-in session, then wraps every call in the safety the vendor never provided: Exact origins. A pack binds to one host and a reviewed fingerprint. Drift fails closed. Declarative, never executable. Manifests are JSON. The registry cannot ship code into your browser. Bounded, untrusted output. Results are allowlist-projected, byte-capped, and labeled contentTrust: "untrusted" . Tool output is content, not instruction. Human authority on consequences. Reads flow. Writes need a preview. Consequential actions need one exact, single-use approval bound to origin, tool, and normalized arguments. Change an argument and the grant is void. Verified closure. After a consequential action an inspector reads authoritative state and issues a receipt with no cookies, secrets, or raw bodies. Unknown outcome is reported as in_doubt , never as success. One concrete job, end to end The demo is not a feature tour. It is one incident. An alert fires in Grafana. Customer bookings in Cal.com are about to be affected. Neither site has WebMCP. The agent discovers the reviewed Grafana and Cal.com packs, installs them for this origin, and reads authoritative state. It never receives a credential. The agent prepares the exact continuity action and states what will change and how it will be inspected. The incident is still investigating . The human grants that exact action once, from a control the agent cannot reach. The agent executes once. The inspector verifies and issues one receipt. The incident is resolved . We poison the fingerprint. The pack refuses to run. We export the recorder draft. Every secret is gone before it can be published. Agents investigate. Humans authorize. Outcomes are verified. The user is the integration layer. Let an agent read freely and prepare freely, while every consequential step waits for a human decision the agent physically cannot forge. Hand a reviewer a receipt, not a screenshot, as proof of what changed. Teach a site once by observing its own traffic, then reuse that pack every session. Why WebMCP, specifically Screenshot-and-click pays the full cost on every step: a screenshot, a vision pass, a click that misses when the viewport shifts. We measured it. Creating one Grafana data source took nine browser actions and 55 seconds by DOM driving, and one WebMCP tool call in 20 milliseconds. A whole diagramming task took 44 calls versus 5. These are single-trial measurements from our audit work, not a benchmark suite, but the shape is unmistakable. The cost moves from per-action to per-app, and it never comes back. WebMCP also gives us the one thing a bookmarklet never had: a standard discovery surface. Any agent that speaks document.modelContext finds our tools without knowing we exist. How we built it Registry, Pack Lab, and runtime in plain HTML, CSS, and JavaScript. No framework. Every tool is registered with the current imperative API, document.modelContext.registerTool(tool, { signal }) , so tools unregister cleanly when a view unmounts. A Chrome MV3 extension injects reviewed read tools into the exact controlled Cal.com and Grafana origins and bridges receipts back to the registry. Reviewed adapters for Cal.com and Grafana were reverse-engineered on the wire, not from source. The recorder wraps fetch and XMLHttpRequest , clusters observed traffic, drafts tools, auto-flags mutating endpoints, and strips secrets before anything is published. Approval, inspection, drift, and redaction are enforced in the shared runtime, so every pack inherits them and no pack can opt out. Node's built-in test runner covers the trust boundaries. All tests pass on the submitted commit. What we deliberately did not claim The public judge path is a deterministic fixture so nobody needs an account. The same runtime drives the real Cal.com and Grafana adapters against controlled localhost instances; the video shows the controlled Grafana and Cal.com state alongside the public lab. The extension checkpoint is read-only. Remembered approvals, arbitrary-site install, generic DOM automation, and automatic rollback are out of scope. Figma taught us the frontier. Its control plane is reachable in-session; its canvas rides a binary WebSocket inside a Worker that no page-context patch can see. We published only what we proved and marked canvas manipulation unsupported. What we learned Discovery is observation, not code reading. Every tool we guessed from source was wrong. Every tool we drafted from the wire worked. Minification cannot rename what crosses the network. Injection inverts the safety burden onto the installer. The vendor never audited these tools, so we had to. That is why approval, inspection, and redaction live in the runtime and not in the pack. Chrome DevTools > Application > WebMCP: 13 tools registered by the page, 18 calls counted, 0 failed. Inspiration Accounts-payable teams review thousands of invoices a month. The work splits cleanly in two: matching numbers against a purchase order and a goods receipt, which an agent does perfectly and a human hates, and looking at the scanned page to see whether the number the agent read is really the number printed there, which a human does in two seconds and an agent cannot do at all. Today the two halves live in different tools, and an agent that approves a duplicate is a segregation-of-duties failure with a dollar sign on it. Every WebMCP showcase app I found was consumer or commerce: pizza, flights, greeting cards. None had money at stake, a mandatory human sign-off, or an audit trail. Countersign is the control: the agent proposes, the human countersigns, and both are on the record. What it does Countersign is an invoice-review workbench with thirteen WebMCP tools registered in the page. In the ChatGPT desktop browser (or Chrome 149+ with the WebMCP flag) you say "Work through my review queue" and the agent: lists the queue and opens an invoice on your screen; runs a three-way match against the PO and the goods receipt, line by line, with the vendor's price tolerance and tax arithmetic; searches every other invoice for duplicates ( INV-2291 and 2291 normalize to the same number); checks the vendor profile, including the bank account printed on the document against the one on file; draws a highlight on the scanned page for every number it cites, so you verify it where it is printed; flags typed, severity-rated issues; proposes GL codes for invoices with no PO; posts comments you can reply to; requests your countersign . A card slides in with its recommendation. The tool call waits up to 25 seconds for your click. Only your click can approve. Every tool call and every human click lands in one audit log. Ten synthetic invoices ship with the demo, each with one planted fact: a quantity overbill, a price above tolerance, a duplicate of an approved invoice, a changed bank account under a stamp, a missing PO, a two-cent tax rounding error, and one whose line description tries to instruct the agent to approve it. A scanned invoice table is the worst possible actuation target on the web: dense, tabular, low contrast, and often stamped over. Countersign exposes the extraction and the matching logic as typed tools with JSON Schemas, and it exposes them in the reviewer's page , where the same call that returns a value can also draw the evidence on screen. The tools are state-scoped. Four queue tools are registered for the life of the page. Nine invoice tools appear only while an invoice is open and are unregistered when the workbench returns to empty, so the agent works on the same document the human is looking at and cannot check invoice A while the reviewer looks at B. That is a WebMCP-native idea: the page's UI state is the agent's context. How it creates a better user experience The reviewer never re-types or re-computes. The agent never touches money without a click. What people and agents can do together that was difficult before A remote MCP server can read the same data, but it cannot draw a box on the reviewer's screen, cannot open a card inside their signed-in session, and cannot make its own call block on their click on the same page. With WebMCP the agent and the reviewer share one document, one state, and one audit log. How we built it Imperative WebMCP API only , registered from a client component in the top-level page. One document.modelContext.registerTool(definition, { signal }) call site in lib/webmcp/registry.ts , with a navigator.modelContext fallback for Chrome 149. Zod 4 schemas as the single source of truth : z.toJSONSchema produces the advertised schema, safeParse validates every call, and the wrapper turns errors into sentences that name the recovery step ("Call list_invoices to see valid ids."). Chrome's budgets enforced in code : defineTool throws in development if a name exceeds 30 characters, a description 500, or a parameter description 150; every output is clamped to 1,500 characters and stays valid JSON. Annotations carry readOnlyHint on reads and untrustedContentHint on anything that returns document text. Two-phase countersign : request_countersign creates a pending decision and races the reviewer's click, a 25-second timeout, and the AbortSignal. On timeout it returns pending and the agent polls get_decision . Repeat calls are idempotent. setStatus is typed so it cannot take 'approved' ; the only path that writes it is resolveDecision , and a test scans the source to prove that only the countersign card calls it. Client-only : Next.js 16, React 19, a zustand store persisted to localStorage , Tailwind 4. No server, no login, a Reset button.
