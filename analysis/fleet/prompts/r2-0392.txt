# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

The result is not “an agent that shops instead of you.” It is a store where the agent helps you shop better. Why WebMCP I have built hundreds of MCP servers, so I came into this challenge focused on the agent experience: progressive tool disclosure, tight token budgets, strong tool descriptions, validated inputs, and errors that agents can recover from. WebMCP changed the design question. The challenge is not only how to expose agent capabilities. It is how to add an agent to a web experience without taking the experience away from the person using it. With WebMCP, the page exposes the meaningful actions of shopping as structured tools: search products, check a size, save sizes, find reviews, check prices, discover similar items, understand shopper signals, and manage the bag. The agent can act reliably, but the person keeps the visual store, the product discovery, and the final decisions. How we built it We built one Node.js service with one shared shopping-tool layer across three surfaces: In-page WebMCP: 16 typed tools registered on document.modelContext , with compatibility fallbacks and a declarative search form. Remote MCP: The same tools are available through streamable HTTP at /mcp for Codex, Cursor, Gemini CLI, and ChatGPT developer-mode connectors. Human UI: The storefront calls the same endpoints, so humans and agents operate on the same session state. Remote agent calls mirror into the open storefront over Server-Sent Events. Every action is visible in a live activity feed, attributed to either the shopper or the agent, and the UI stays interactive throughout. The catalog uses read-only public fashion data. Reviews combine public Reddit, YouTube, and web signals. A lightweight price-history store learns from product observations over time. We also built end-to-end tests for both real streamable-HTTP MCP calls and in-page WebMCP tool calls. Challenges and what we learned The hardest problem was designing for two users at once: the agent needs reliable, compact, recoverable tools; the person needs a rich, understandable shopping experience. We used progressive disclosure so agents see the right tools at the right moment, kept tool responses focused to avoid wasting context, and designed clear error responses so an agent can recover instead of getting stuck. But the bigger lesson was that agent capability is not the product by itself. The product is the experience around it. People need to see products, explore freely, and develop their own taste. Zada makes that discovery more personal by placing the agent inside the storefront, not between the shopper and it. Built entirely during the submission period. Like Comment Story Updates What VERROCCHIO does VERROCCHIO is a WebMCP workshop for time-constrained solo builders whose projects are repeatedly interrupted. It keeps the next action, missing proof, active work, and human checkpoints together so an AI can help without turning an unverified claim into “done.” The browser exposes four bounded, state-aware WebMCP tools: inspect_workshop reads the live mission, missing proof (MANCA), active work, and the next bounded action. call_fermo stops when evidence, scope, safety, or intent is ambiguous. propose_workshop_draft validates and returns an unsigned plan that waits for human FIRMA. return_work_result records a structured CLAIMED result without marking its evidence verified. Human-only actions—FIRMA approval, evidence verification, resume, publication, and final submission—are deliberately absent from the WebMCP tool surface. Why WebMCP is a strong fit A person and an agent must act on the same live project state. With ordinary DOM automation, an agent has to rediscover controls and infer whether visible text is a claim, approval, or proof. WebMCP gives the page an explicit contract and exposes only the transitions the agent is allowed to perform at that moment. The result is not simply fewer clicks. It is a clearer division of responsibility: the agent can inspect, draft, stop, and return bounded work; the human retains purpose, approval, evidence judgment, publication, and submission. Better experience for interrupted solo work A solo builder working around a full-time job carries coordination that a conventional team would normally distribute: rules, next actions, interruption recovery, evidence review, and stops before irreversible actions. VERROCCHIO makes that coordination visible and resumable. The core flow is: MANCA → unsigned plan → human FIRMA → bounded work → CLAIMED → human VERIFIED or CHANGES_REQUESTED After an interruption, the builder can reopen the workshop and see what is still missing, what is active, and exactly where human attention is required. What people and agents can now do together The agent works directly with structured browser state instead of guessing from screenshots or page text. It can propose the smallest valid next plan, detect ambiguity, and return a result with checks, evidence references, and remaining risk. The human can adopt or reject that plan and verify the claim without surrendering the decisions that matter. Implementation VERROCCHIO is a React and Vite application with browser-local persistence. Tools are registered through document.modelContext.registerTool ; their availability changes with workshop phase. Every mutation requires the state version returned by inspection and an idempotency key. Stale state is rejected, identical retries reuse the existing receipt, and conflicting reuse fails. The current ChatGPT or Codex host supplies reasoning, so the app does not require its own OpenAI API key. Like Comment Story Updates Inspiration What it does KATA KATA is a system that allows users to teach a web application a new agent capability simply by demonstrating a workflow. Instead of requiring developers to manually write a dedicated API or WebMCP integration for every repeated action, a user performs the task a small number of times. KATA records the semantic application actions behind those demonstrations, compares the traces, identifies what stays constant and what varies, infers typed parameters, compiles the repeated behavior into a deterministic workflow, and installs it as a new WebMCP tool. For example, a researcher may repeatedly save a paper, assign it a priority, and add an “architecture” tag. KATA can recognize the common structure and create a tool such as: triage_architecture_paper(workId) An AI agent can then discover and execute that newly learned capability through WebMCP. The important distinction is that KATA does not record mouse coordinates or replay brittle DOM clicks. It records semantic application commands. The human UI and the agent both ultimately use the same command system, so a learned tool invokes real application behavior rather than a separate simulation. KATA also avoids generating arbitrary executable code. Learned workflows are represented as structured, validated programs built from a finite set of supported commands. Inputs are validated before execution, the complete batch is preflighted before mutation, and invalid workflows fail without partially applying actions. The deeper idea behind KATA is user-extensible application APIs: the API available to an AI agent no longer has to be completely defined by the developer ahead of time. Users can teach software the workflows that matter to them, and the application can safely turn those workflows into agent-usable capabilities.
