=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Inspiration The interesting question is not whether an agent can click a button. It is what happens to state that a person cannot see. We wanted a browser workspace where the capability an agent holds is a contract a person read and approved, and where every use of it is visible in the same interface the person is looking at. What it does Bridge Studio discovers meaningful workflows in the visible page and turns them into typed WebMCP tool proposals. Each proposal states its inputs and whether it reads or changes state. A person approves the contract before it is registered. When an agent uses an approved tool, the same interface updates, a live execution flow narrates what the protocol is doing, and the action is recorded in a durable trace. Signal Lab is the argument. Its configure_analysis tool collapses thirteen brittle UI interactions — coupled sliders, multi-select cohorts, linked date ranges, a chart brush — into one semantic call with a JSON Schema that enforces enums, array uniqueness, numeric bounds, date patterns, and cross-field invariants ( endDate > startDate , confidenceMax > confidenceMin ). A click-driven automation can get halfway through that sequence and leave the dashboard in a state no human asked for. A typed tool either applies the whole configuration or is rejected with a reason. Voyager Stays and Civic Desk keep the read-only and consequential-write cases visible, plus a guarded external-origin preview that demonstrates a boundary: compatibility must not mean bypassing browser security. How we built it The app uses the WebMCP Imperative API through document.modelContext.registerTool() . Three workspace tools register at startup. Page-specific tools are registered only after explicit human review and are revoked through AbortController signals when the user navigates away — with the reason shown in the trace. Every execute returns the spec-shaped { content: [{ type: "text", text }] } result. JSON Schema bounds every input, and a validator enforces types, enums, patterns, string and numeric bounds, array cardinality and uniqueness, and rejects unexpected fields. readOnlyHint communicates risk to the agent; untrustedContentHint is true on every tool, including the action trace, because the trace carries agent-supplied text and must never be laundered back as trusted context. The frontend is standards-based HTML, CSS, and JavaScript with no runtime framework and no build-time dependencies — the chart is hand-written SVG. Node's built-in test runner covers address handling, the full validator surface, the Signal Lab contract, and the annotation invariants. The deployment sends Content-Security-Policy with frame-ancestors 'none' , because an approval dialog that can be framed is not an approval. Challenges The hardest design problem was respecting the difference between native site tools and browser automation. Arbitrary pages cannot be safely inspected from another origin. ToolForge - an SDK that writes your web app's WebMCP tools Like Comment Story Updates Inspiration WebMCP solves an interesting problem: a website can expose tools directly to an agent. The harder part is getting websites to actually expose those tools. Most product teams aren't going to stop and learn a new browser API, decide which parts of their application should become tools, write schemas for them, and then maintain those schemas as the product changes. I wanted to make that process much cheaper. Rather than build another agent-native app, I built ToolForge: a way to take an existing website and turn its existing behaviour into WebMCP tools. What it does Add one script to a site you already run: <script src="https://toolforge-omega.vercel.app/toolforge.js"></script> Then use the site normally for about thirty seconds. ToolForge watches the network requests the site makes and uses them to work out what the API is doing. An agent then turns that information into WebMCP tool definitions. Before a tool is shown to you for approval, it is run in a sandbox with test arguments. If it doesn't work, you never have to approve it. Once you approve a tool, ToolForge exports it as an ordinary JavaScript file that you can commit to your repository. The live demo is a ceramics shop with a real API. Its seven WebMCP tools were created this way, exported, and committed. The same page also contains the ToolForge interface that created them, so you can see both sides working together. The page starts with one tool. Everything else is opt-in. Why this works well with WebMCP The interesting part of WebMCP isn't simply that a page can expose tools. It's that the tool surface belongs to the page and can change while a conversation is already in progress. That's what ToolForge relies on. An agent can call forge_tool , have a new tool registered in the page, and immediately have that tool available alongside the existing ones. I tested this in ChatGPT desktop's in-app browser rather than treating it as a theoretical feature. At the start, the page exposes one tool. The agent can install the toolkit, after which the page exposes six. No reload is needed. The agent can then use one of the newly created tools to interact with the shop. That only works because the tools belong to the document itself. It also matters that ToolForge learns from the page rather than trying to generate tools from a description of the application. The network traffic and DOM are right there in the browser, so the tool definitions can be based on what the application actually does. ToolForge won't draft a tool until it has seen a real request. What this changes for developers For a developer, the starting point is no longer a blank page. Instead of reading the WebMCP spec, designing a tool surface from scratch, and writing schemas by hand, you use your application and then review the result. The exported JavaScript is deliberately boring. Each tool includes its provenance and a SHA-256 hash, so the output can be reviewed and committed like any other source file. It also works with a strict Content-Security-Policy. The goal isn't to hide the implementation. It's to make the first version cheap enough that a developer can inspect it, change it, and own it. What the experience is like for the person using the site The agent's actions stay visible in the page. Every tool call appears in an activity feed in plain English, with the raw payload available when you want to inspect it. When a tool needs approval, the dialog shows the code that will run, its schema, and the result of the dry run that has already happened against the real API. If that test changed data, the interface says so. So the approval isn't based purely on a model-generated description. You can see something that has already run and decide whether you want to allow it. Nothing is installed automatically either. The page starts with one read-only tool, and additional groups can be enabled explicitly. What becomes possible The most interesting behaviour I've seen is the agent filling in gaps in the tool surface itself. One run started with a request for a low-stock report. The agent inspected the existing catalogue endpoint, noticed that it returned stock in descending order, and created a tool that presented the same information in the useful order instead. In another run, the page already had seven tools. When asked to create a complete tool surface, the agent inspected what was already available and decided that the shop already had good catalogue, basket, and order coverage. It added only an operational inventory tool that was missing. That distinction matters. The page provides the context about what already exists. The agent decides what is still useful. The result isn't just a fixed list of tools generated once and forgotten. A reload also doesn't have to end the conversation. The transcript and model-side history survive, orphaned tool calls are handled explicitly, and the agent checks which tools are still available before continuing. How I implemented WebMCP There are three WebMCP bindings I needed to account for, and they aren't exposed as the same object. src/kernel/webmcp.ts detects which one is available and uses it: document.modelContext.registerTool({ name: "search_products", description: "Search the product catalog", inputSchema: { /* ... */ }, execute: async (input) => { /* ... */ }, }); Binding Host document.modelContext ChatGPT desktop's in-app browser navigator.modelContext Chrome 149, Edge 147 navigator.modelContextTesting Chrome behind chrome://flags/#enable-webmcp-testing A few implementation details ended up being important. Incremental updates. When registerTool and unregisterTool are available, ToolForge updates the existing surface rather than rebuilding it. The host's visible tool count can therefore increase or decrease as tools are added and revoked. Where only provideContext is available, the complete surface is replaced atomically. Late attachment. ChatGPT can attach the WebMCP host after the page has loaded. Detection therefore retries rather than assuming the host is present at startup. Without this, a page could mark its desired tools as already registered and then never reconcile them when the host appeared. Approval during execution. Tools can request user interaction through the agent handle's requestUserInteraction , so approval happens as part of the tool call rather than as a separate step afterwards. Separate application and generated tools. The page exposes inspect_app for the tools the application already provides and forge_tool for creating new ones. Generated tools can't take the name of an existing application tool. How ToolForge learns the API Watching requests fetch and XMLHttpRequest are patched at module scope, before the application's own scripts run. That means ToolForge can see requests made during the initial page load as well as requests triggered by later interactions. Requests are grouped into endpoints. Paths are templated from observed variations, and request, query, and response schemas are inferred from actual traffic. There are a couple of safeguards against overfitting. Identifier-like fields aren't turned into enums just because only a few values have appeared. If six requests contain six different SKUs, that doesn't mean those six SKUs are the only valid values. Path parameters are also inferred conservatively. Two paths are only collapsed into a parameter when both segments look like values rather than route names. Otherwise something like /api/cart and /api/products could incorrectly turn into /api/:id . Redacting data Actual values don't get sent to the model. Authorization and Cookie headers are discarded. Sensitive and personal fields are replaced with their names, and common patterns such as JWTs, email addresses, phone numbers, card numbers, and long opaque strings are detected and removed.
