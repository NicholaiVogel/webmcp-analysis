## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates VibeCheck: what people actually said Inspiration It started from a habit I didn't think about until I tried to explain it: whenever I'm deciding on something real — a laptop, a bank, a framework — I don't trust the first page of search results. I type the question, then I add "reddit" to the end of it, and I read threads until a picture forms in my head. Marketing pages tell you what a product wants to be. Threads tell you what it actually is. That habit is the whole product. I wasn't trying to build a search engine or a recommendation engine — those already exist and mostly disappoint. I was trying to build the reading part: gather what real people said, and then get out of the way while a person does the one thing a model can't do for them, which is decide who to believe. The WebMCP angle came second, but it clicked hard once I saw it: an agent helping you decide on a laptop is useless if it can't see that you already rejected one source as a shill, or that you pinned a claim as the one that actually matters to you. That state lives in your head and on your screen — not in a database, not in a prompt. WebMCP is the only way an agent gets to touch it directly, in your session, live. That's not a nice-to-have integration; it's the reason the product exists in this shape at all. What I learned The biggest lesson wasn't technical — it was that "gather opinions" is a much harder problem than "run a search." A raw discussion-source query returns a pile of ambiguity: half the results are Facebook groups and LinkedIn posts dressed up as discussion, snippets are truncated mid-sentence, and search engines match your question almost literally, so a natural question like "is the Mac Mini a good device for developers?" returns nothing while "mac mini developers" returns real threads. I ended up writing a whole normalization layer just to translate a person's actual sentence into something a search API will respect. The second lesson was about trust modeling. Early on, "support" for a claim was just a count of sources. That's wrong — three people reposting the same affiliate blurb isn't consensus, it's an echo. So the real signal isn't $n$, it's a weighted sum: $$ \text{raw}(claim) = \sum_{s \in \text{evidence}} w(s), \qquad w(s) = \begin{cases} 0 & \text{rejected by you} \ 1.5 & \text{trusted by you} \ 0.4 & \text{low-signal source} \ 1 & \text{ordinary discussion source} \end{cases} $$ and the bar you see is that raw score normalized against the best-supported claim on the whole board: $$ \text{weight}(claim) = \min\left(1,\ \frac{\text{raw}(claim)}{\max_{c \in \text{claims}} \text{raw}(c)}\right) $$ The moment I had that formula, the UI basically designed itself: the support bar isn't decoration, it's the math made visible, and rejecting a source visibly collapses the segment it owned. Watching a claim go from "consensus" to "thin" in real time, just because you clicked reject on one Facebook post, is the whole pitch of the app in one interaction. How I built it The architecture is deliberately small: one state shape, one reducer, and both the UI and the six WebMCP tools read and write through it. That constraint — "nothing the agent does is invisible on screen, and nothing you do on screen is invisible to the agent" — came from a very specific failure mode I wanted to avoid: tools that quietly mutate state the human can't see, which turns "collaboration" into "surveillance." The pipeline underneath is two calls: SerpApi's google_forums engine finds the threads, and an LLM (routed through OpenRouter so it can run on a free model with a paid fallback) does three jobs in one pass — decide if a thread is actually relevant, decide if the poster sounds like they own the thing or is just relaying secondhand, and cluster the recurring points into claims with evidence attached. Everything downstream — the reducer, the support math, the UI — trusts that shaping completely, so getting it right mattered more than almost anything else in the project. Challenges Credit discipline was a real design constraint, not an afterthought. SerpApi's free tier is 250 searches a month, and every extra fallback call eats into that. I built a two-stage gather — google_forums first, alone, and only fall back to a second, broader search if the first came back too thin — plus a disk cache for local dev so iterating on the UI costs nothing. Tuning how thin is too thin turned out to be its own ongoing problem: real google_forums responses are noisier than I expected, often dominated by Facebook and LinkedIn results that read as discussion but aren't, which pushes the fallback to fire more often than I originally assumed it would. Getting the LLM to stop hallucinating specificity was harder than getting it to extract claims at all. Search snippets are cut off mid-sentence — literally ending in "…" — and the model's instinct is to complete the thought plausibly. A plausible completion that the source never actually said is a fabrication wearing a citation. I had to write explicit rules against finishing a snippet's sentence, against reusing a source's distinctive phrasing verbatim, and against letting one source's detail leak into another source's evidence line. None of that is exotic prompt engineering — it's just the unglamorous work of writing rules for every way a language model quietly lies with confidence. And the last one is the most human: making the board itself feel worth staying on, not just correct. It's easy to build something that's functionally right and viscerally forgettable — an accurate list of claims with checkboxes is not a product anyone wants to spend time in. Getting the support bar to move like something real, making rejection feel like a decision rather than a checkbox, giving the empty state a reason to click something instead of stare at a search box — that's the part with no spec, just taste, and it's the part I kept coming back to rewrite. Like Comment Story Updates Inspiration Important conversations often become harder when speech, language, or processing gets difficult. We wanted to reverse that responsibility. How I Choose asks whether the communication partner adapted to the person—not whether the person performed correctly. I wanted to explore the merchant side of that future: who makes sure the underlying product catalog is understandable enough for those agents to use? Based on my research, catalog hygiene was the first pain point in the Shopify Reddit Community's "most annoying manual task" thread. Product catalogs often contain missing identifiers, vague descriptions, incomplete image alt text, inconsistent variants, and weak taxonomy. These issues affect traditional search today and can make products harder for AI shopping agents to understand and recommend. Catalog Health Copilot turns catalog maintenance into a collaborative workflow between a Shopify merchant (human) and an AI agent via webMCP. What it does Catalog Health Copilot connects to a Shopify development store and audits its products across six areas: Identifiers Product content Media SEO Commercial data Agent readiness It converts those findings into a prioritized issue queue and health score. From the same live page or dashboard, a merchant and their agent can: Scan the catalog. Find the highest-impact issues. Open a specific issue and inspect its context. Generate an OpenAI-assisted fix for text. Review or edit the proposed field-level change. Apply approved changes to Shopify. Re-fetch the product and verify the live result. Preview how a shopping agent interprets the product before and after the fix. The web app remains usable as an ordinary web application when WebMCP is unavailable or when humans are using it. WebMCP adds a structured collaboration layer rather than replacing the interface. Catalog auditing involves large amounts of repetitive inspection, prioritization, drafting, and verification. An agent is well suited to that labor, while the merchant should retain judgment over brand voice and product accuracy. Instead of asking an agent to guess its way through buttons and page layouts, the application exposes ten WebMCP tools : scan_catalog , get_health_score , list_issues , show_issue , generate_fix , apply_fix , apply_approved , dismiss_issue , verify_fix , and preview_agent_view . This lets the agent work with structured product data while keeping its actions visible in the same interface the merchant is viewing. When the agent selects an issue, creates a draft, or applies a fix, the page updates too. The result is a governed scan → explain → draft → review → apply → verify workflow that would be fragile and difficult to coordinate through visual browser automation alone. How I built it The frontend is built with React, TypeScript, and Vite. All WebMCP tools are registered in the top-level document using: document.modelContext.registerTool(...) The tools call the same catalog-controller functions used by the visible interface. This gives the human and the agent shared state, permissions, progress, and verification results. A Cloudflare Worker serves the application and its API routes. It connects server-side to: Shopify Admin GraphQL API for catalog reads and controlled product updates OpenAI API for context-aware fix drafts, with deterministic templates as a fallback Cloudflare rate limiting and observability for protecting sensitive endpoints and recording mutation outcomes Shopify and OpenAI credentials never reach the browser. Safe demo-store writes The public demo intentionally allows controlled writes so judges can experience the complete WebMCP workflow. I added several server-enforced safeguards: Only products carrying the catalog-health-seed tag can be modified. Variant and image IDs must belong to the selected seeded product. Only an explicit allowlist of product fields is writable. A request can contain no more than ten changes. Write and OpenAI endpoints have independent rate limits. ALLOW_LIVE_WRITES provides an emergency kill switch. Every attempted mutation is logged with its outcome. A guarded reset command restores the deterministic 30-product demo catalog. These restrictions let the demonstration remain interactive without exposing a production storefront. Challenges I faced One major challenge was designing for WebMCP as a genuine product capability rather than attaching tools to an existing interface. ChatGPT’s in-app browser requires tools to be registered imperatively in the top-level document, so the application could not be an iframe or embedded Shopify Admin app. Another challenge was keeping the visible interface synchronized with agent activity. I solved this by routing both UI controls and WebMCP tools through the same controller instead of creating separate automation logic. The most important challenge was safe write access. A public demonstration needs to be easy for you, the judges, to use, but unrestricted Shopify mutations would be inappropriate. I would also expand the checks using storefront analytics and order history to identify products that are technically available but consistently undiscoverable.
