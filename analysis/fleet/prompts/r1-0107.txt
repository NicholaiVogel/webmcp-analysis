# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Description Input use cases Inspiration Sharing a document with an AI agent often begins with an unreliable manual process: remove formatting, repair broken structure, extract useful references, look for sensitive information, and decide what is safe to share. Traditional browser automation adds uncertainty because agents must guess which controls to use and how to interpret the page. We built MarkDown Stripper to create a safer, structured handoff between people and agents. WebMCP was a natural fit because it lets the application expose precise capabilities while keeping the person in control of the same visible workspace. What it does MarkDown Stripper is a local-first document preparation workspace. It imports Markdown, TXT, HTML, DOCX, PDF, and image files, then converts them into Plain, Readable, or AI-ready text. It extracts references, identifies unresolved references, performs OCR, and detects potentially sensitive information locally. Through WebMCP, an agent can inspect bounded document state, prepare an AI-ready handoff, run a privacy scan, check readiness, and redact findings that the person selected by ID. Sensitive content reads and export actions remain blocked until the person reviews the document and explicitly approves that exact version. If the document or relevant processing state changes, approval is automatically invalidated. Why this use case strongly fits WebMCP Document handoff is a multi-step, stateful workflow, not a single button click. An agent needs to understand the document’s current state, choose appropriate conversion settings, inspect risks, make controlled changes, and verify whether the result is ready. With conventional browser automation, the agent must infer all of this from labels, coordinates, and changing page layouts. WebMCP gives the agent narrow, typed operations that express the application’s real capabilities and return structured, verifiable results. It allows the agent to act reliably without creating a separate interface or bypassing the person. The result is a genuinely collaborative workflow in which the agent handles repetitive preparation while the human retains authority over sensitive content. How it improves the user experience The user no longer has to manually clean a document, hunt for references, run separate privacy checks, and repeatedly explain the page state to an agent. The agent can prepare the visible document, run local checks, and report exactly what still needs attention. Every mutation remains visible in the normal interface, privacy findings have stable IDs, long results are returned in bounded pages, and the readiness tool provides clear next steps without exposing document text. The approval gate makes the boundary understandable: preparation can be delegated, but content cannot be read, copied, or downloaded by the agent until the person approves the current version. What people and agents can now do together A person can import or paste a document and ask an agent to prepare it for a safe AI handoff. The agent can switch the output to AI-ready context, preserve useful references, open Insights, run the local privacy scan, and explain which findings require review. As agents gain more ability to interact with software directly, I wanted to explore a simple question: how do you let an agent perform useful verification work without also giving that same agent authority over whether the test passed? CUF Challenge Edition demonstrates that separation. What it does The demo verifies a synthetic multi-tenant authorization boundary. A Support actor in Tenant A may access Tenant A tickets, but must never access Tenant B tickets. Through WebMCP, an agent can discover CUF’s tools, run verification cases, retrieve evidence, inspect the latest result, and export a sealed challenge artifact. The agent never supplies the final verdict. CUF’s deterministic kernel returns: PASS when the expected boundary is enforced FAIL when a cross-tenant regression is observed INCONCLUSIVE when the authorization outcome cannot be established The most important safety property is that missing evidence never becomes a false PASS. I verified the deployed application end to end in a WebMCP-capable Chrome build. The browser discovered the production tools and invoked them through the WebMCP interface rather than by directly calling the application JavaScript. The verified results were: Healthy → PASS Regression → FAIL Unavailable → INCONCLUSIVE I also tested attempted verdict overrides. The run tool does not expose a verdict input, and attempts to force a verdict did not change CUF’s deterministic result. Challenges we ran into The biggest challenge was preserving the separation between orchestration and judgment. It would have been easy to let the agent inspect evidence and then decide whether the system passed. That would undermine the entire point of the demo. Instead, CUF mechanically classifies the observations and applies deterministic verdict rules outside the agent. Another challenge was proving that the WebMCP implementation actually worked through a real browser environment, not just proving that the underlying JavaScript functions worked. The final deployment was tested in a WebMCP-capable Chrome build, where the tools were discovered and executed through document.modelContext. Created a new footer Using only WebMCP tools WebMCP Site Tools discovered by ChatGPT on the demo site Inspiration ChatGPT's browser shipped WebMCP support on August 25th. Respira already gives agents safe, structured access to WordPress through MCP: 319 tools, staged edits, approvals, rollback. So the question wrote itself: what happens when the agent is not on the other end of a connector, but standing on the same page as you? What it does Open a Respira-powered WordPress site inside ChatGPT's browser and sign in. The page registers a curated set of site tools on document.modelContext : read the site's context, list and read pages, stage an edit as a reviewable duplicate, approve or reject it , audit SEO and readability, find and fix WooCommerce catalog gaps. Every staged draft also returns a tokenized preview link, so the proposed change can be shown to someone with no WordPress login. The agent-only tools are the point. Approve-duplicate and reject-duplicate would be meaningless as buttons, but as site tools they give the agent a safe write path with a human approval gate, on the page you are both looking at. Nothing goes live without a yes, and everything rolls back. How i built it WordPress has an Abilities API, and an open-source bridge ( code-atlantic/webmcp-abilities , GPL) that maps abilities to WebMCP tools. Respira registers its production tool catalog as abilities, the bridge exposes them to the page, and a REST layer executes them with WordPress's own authentication and per-tool permission callbacks. The patched, working bridge is open source at respira-press/webmcp-for-wordpress . Challenges i ran into The bridge had never actually worked in a real agent browser, and finding out why became the project. Four bugs, each masking the next: Discovery ran as an anonymous visitor. The tools fetch sent cookies without WordPress's REST nonce: 401, zero tools registered, on every default-configured site. Execution died at WordPress core's door. The bridge put its CSRF token in the header core reserves for its own nonce, so core rejected every call before the handler ran. ChatGPT's modelContext is a frozen object implementing only registerTool . The bridge's batch provideContext call threw silently and nothing registered. Ability names contain a slash that stock Apache rejects when URL-encoded , so execution 404ed on every Apache host. i debugged blind inside ChatGPT's browser with an on-page diagnostic badge: a screenshot from inside the agent browser was the only ground truth. Then one more wall: 296 registered tools tripped ChatGPT's per-page limit and disabled WebMCP for the document entirely. The fix was editorial, not technical: a curated, page-scoped set of ~30 tools. Accomplishments i am proud of As far as i can tell, this is the first WordPress site with working WebMCP site tools in ChatGPT . Every fix shipped to production the same day in Respira for WordPress v8.7.1, so paying customers run this code today. What i learned The gap between "implements the spec" and "works in a real agent browser" is where all the work lives. And agent browsers impose an attention budget: fewer, better-scoped tools beat an exhaustive catalog. What's next Anonymous visitor tools (public read-only search and product Q&A), per-role tool sets, and landing the bridge fixes upstream so every WordPress site gets a working WebMCP path. We wanted the agent and operator to work from the same visible page without giving the agent invisible authority. What it does VoiceGuard is a synthetic voice-operations cockpit with four WebMCP site tools. An agent can inspect the current call state, audit visible guardrails, draft short operator guidance, or stage a pause request. The first two tools are read-only. The latter two change only visible draft or request state. A trusted human click is required before guidance can be applied or the synthetic call can be paused. The public demo deliberately exposes no tool for dialing, sending guidance, speaking, listing contacts, starting campaigns, transferring or hanging up. Every call, person, transcript and metric on the page is fictional. Why WebMCP is a strong fit Supervision depends on live shared context: phase, latency, transcript, policy signals and pending actions. WebMCP lets the browser agent discover narrow, schema-defined actions directly on that same page instead of scraping the DOM or calling a detached backend. Tool calls update a visible activity trace, so the operator can see what the agent read or prepared. This makes the experience faster and less ambiguous while preserving the human-first interface. The agent finds the signal. The human owns the action. How we implemented WebMCP The static top-level page registers four imperative tools with document.modelContext.registerTool . Each tool has a narrow JSON Schema, bounded text inputs and explicit read-only or untrusted-content annotations. The two draft-only tools return structured proof that no call action was executed. Human review buttons require trusted click events. The optional ?inspector=1 view is a transparent native test client. It uses document.modelContext.getTools() and executeTool() to show the exact JSON returned by Chrome's WebMCP implementation. The app has no backend and makes no network request after loading. Challenges we ran into The main challenge was designing useful agent actions without quietly creating an unsafe control plane. We removed every direct call action and separated drafting from execution. We also treated transcript text as untrusted page content, bounded all inputs, made tool activity visible, and built native Chrome tests that prove the page remains live until a human confirms a pause. Accomplishments Four working top-level WebMCP tools with native Chrome discovery and execution tests. A polished responsive shared workspace rather than a hidden JSON-only demo. Visible synthetic-data and autonomy boundaries throughout the product. A clean-room public repository with no production dependency or credential. Automated static, browser, responsive, safety and public-deployment checks. What we learned The most interesting WebMCP design question is not how many actions an agent can take. It is which actions should remain deliberately unavailable. Narrow tools, shared state and visible confirmation can make an agent more useful without making it less accountable. What's next Next we would connect the same interface contract to an authenticated pilot, add role-based tool availability, retain privacy-safe audit events, and test the workflow with real operators under explicit consent and legal review. None of those future production capabilities are represented as part of this synthetic contest demo.
