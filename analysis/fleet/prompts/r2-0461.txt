# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

It understand teh world in a different way than i do, i usually point to things, mention 'here, there, this thing'. To an agent that is meaningless. I wanted to figure out a way to have a shared language that makes agent collaboration as seamless as possible, and i focused on working in a canvas for an agent. \n\n What it does \n\n When you select anything on the canvas it creates a short lived keyword that becomes the reference between you and the agent for that specific selection. You can select a group of elements and it creates a shared reference for the group, you can also select different empty regions. This makes describing things to an agent really simple when you are working with it, and you dont have to be sending out screenshots of the Ui for the agent to understand what you are talking about. \n\n How we built it \n\n I used NextJS, WebMCP, and Codex to build the infinite canvas with different media types. The keywords are meant to be stored locally and all the mcp tools as well so this is a really lightweight implementation that does not require having a stored state, or stored realtime session in a db. There are also dynamic tools when you double click on any element depending on its type, so you can have the agent operate differently depending on media type. \n\n Challenges we ran into \n\n I would say the biggest challenge was making the tools description and names as relevant as possible for the agent to make sense of them in a way that felt natural to interact with. In the beginning it would find the keywords but not have the necessary context on how the app worked, so its interactions with the user where sometimes confusing. In the beginning i solved this by giving the agent a tool with a really long description that explained the app, the tool was not meant to be used, it was jsut to have the agent read the context of the app. \n\n Accomplishments that we're proud of \n\n I am really proud of how natural the interaction with the agent felt at the end. When i began playing around with the canvas and the agent, it felt really simple to just instruct the agent on what i wanted without having to overcomplicate my speech trying to describe an element. \n\n What we learned \n\n I learned how WebMCP works, this was my first project for the challenge. Having the mcp be registered in the html make sit so that any change in the UI can be immediately referred to by the agent. I also learnt about the Abort Signals for the agent, for destructive actions. \n\n What's next for Shared Reference Canvas \n\n I would love to see this become some sort of package where maybe its a extension for the browser or an app where any interface we use can also have these shared references as we everyday talk more with agents, and have to spend a painful amount of time describing our world that can sometimes be confusing to describe. \n\n \n\n \n Built With \n\n codex nextjs vercel webmcp \n \n\n \n Try it out \n\n \n \n \n webmcp-shared-canvas.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Ari Sabogal \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Ari Sabogal \n started this project\n \n —\n \n a day ago \n \n \n\n

A reproducible WebMCP benchmark for agents making economic decisions under pressure.\n \n\n \n \n\n \n \n \n \n \n \n Like\n \n \n\n \n\n \n \n Comment\n \n\n \n \n \n\n \n \n \n \n \n \n \n Story \n \n \n \n \n Updates \n \n \n \n \n \n \n\n\n \n \n\n\n \n \n \n \n\n \n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n\n\n \n \n \n \n\n \n \n \n \n \n \n \n \n\n\n \n \n \n \n\n \n \n \n \n 1 2 \n\n\n\n \n Inspiration\\n\\nBrowser agents can complete a task and still leave reviewers unable to answer basic questions: What actions did the agent take? Did the policy really improve the outcome? Can the result be reproduced? MarketBench makes those questions measurable.\\n\\n## What it does\\n\\nMarketBench is an interactive evaluation lab for browser-agent market policies. A visitor selects a scenario and seed, runs a 12-week simulation, and gets:\\n\\n- a clear business outcome and plain-language insight\\n- the full WebMCP tool-call and state history\\n- integrity hashes for trace and final state\\n- a deterministic baseline comparison\\n- three-seed aggregates with mean, standard deviation, and worst-seed results\\n- downloadable evidence for audit and replay\\n\\n## How we built it\\n\\nThe app is a React and TypeScript web application deployed on Vercel. WebMCP exposes typed browser tools for configuring and running experiments. The evaluation engine uses versioned deterministic fixtures for three scenarios and three seeds, so baseline and signal-aware policy runs can be reproduced exactly. Each step records its input, tool call, output, state transition, and hash.\\n\\nThe comparison view aggregates the same fixed seed set rather than presenting a single lucky run. It visualizes distributions and reports mean, standard deviation, and worst seed. The repository includes tests for determinism, trace completeness, hashes, aggregate math, and export structure.\\n\\n## Challenges\\n\\nThe main challenge was making rigor understandable. A raw trace is useful to an engineer but intimidating to a first-time visitor. We rebuilt the experience around a three-step flow, visible progress, a human-readable takeaway, compact trace summaries, and expandable evidence. We also made the distinction between deterministic policy fixtures and model output explicit.\\n\\n## Accomplishments\\n\\n- Full trace, state, and history export with integrity hashes\\n- Transparent baseline vs signal-aware comparisons\\n- Three-seed aggregate metrics and charts\\n- A first-run experience that explains the value before exposing technical detail\\n- A live, reproducible demo with tested fixtures\\n\\n## What we learned\\n\\nAgent evaluation needs both observability and a decision-relevant metric. Traces explain how an outcome happened; controlled repeated runs show whether the policy actually helped. Neither alone is enough.\\n\\n## What is next\\n\\nNext, MarketBench can add imported real-world task traces, more scenario packs, signed evaluation bundles, and CI checks that compare agent-policy revisions before deployment. \n\n \n\n \n Built With \n\n webmcp \n \n\n \n Try it out \n\n \n \n \n marketbench.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Andrés Santos Sanz \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Andrés Santos Sanz \n started this project\n \n —\n \n 3 days ago \n \n \n\n
