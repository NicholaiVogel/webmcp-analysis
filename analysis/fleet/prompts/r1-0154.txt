# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Infinite Canvas is a browser-based visual design canvas where people and AI agents inspect, create, and edit the same live document through native WebMCP tools. Problem Visual design applications are built for pointer-and-keyboard interaction. An AI agent approaching the same application usually has to infer state from pixels, guess which controls to click, and repeat brittle UI actions. That makes substantial design work slow, unreliable, and difficult for a person to supervise. Solution For this WebMCP Challenge proof of concept, one agent brief starts three named hypotheses in isolated editable branches. A person can keep working on the original while the lanes run, inspect status and layout checks, cancel a lane, promote one branch only if the source revision is still current, and undo that promotion in one history step. Why WebMCP Visual design is state-heavy and precision-dependent: selections, trees, styles, tokens, pages, and history. The app registers structured tools through document.modelContext.registerTool, so an agent operates on the live document model instead of guessing from rendered pixels. The same MobX stores and handlers power both the visible editor and agent calls. What people and agents can do together The person keeps working visually while delegating a bounded exploration task. The agent reads the real selection and tree, starts three hypotheses, and reports progress. The person can compare structured editable branches, cancel work, promote a result, or undo it. A fingerprint-based stale-revision check rejects a completed branch when the person changed the original instead of silently overwriting that work. Implementation The hosted build exposes 54 tools: 34 core canvas tools, 14 design-lab tools, and six experiment tools: start_design_experiment, get_experiment_status, compare_experiment, cancel_experiment_lane, promote_variant, and undo_experiment_commit. Experiment jobs are orchestrated together, while writes to the single editor document are serialized. Operation IDs make retries idempotent; cancellation is cooperative; promotion is atomic and undo-compatible. Live demo Open the public URL and use the judge prompt in the repository README. No login is required. For a 3D editor that's close to hopeless, because the interesting state isn't on screen at all. It's a scene graph, a modifier stack, a spline running through a forest field. What it does Morphus is a WebGPU 3D world editor that runs entirely in the browser. It sculpts terrain, grows forests, blocks out levels, casts combat VFX, and lays out procedural cities. With WebMCP it registers all 154 of its tools with the browser, so an agent can build a world in the page the person is looking at . No server, no API key, no separate MCP process. Ask it for a landscape and it calls create_mesh_terrain , then terrain_sculpt_stroke along a path of world-space points, then create_forest_field and grow_forest_field to plant a stand of trees along a spline. A heavy GPU application becomes operable by a model that never has to render a frame. A browser agent and the in-app Copilot run identical code paths and cannot drift apart. The payoff showed up when we built the city. Nine new tools became agent-drivable the moment they existed, with no bridge changes, no registration code, and no separate schema to maintain. The surface went from 145 to 154 by writing the features. Everything else followed the platform's guidance rather than working around it: Annotations derived, not hand-listed. readOnlyHint comes from the tool's name prefix, because a hand-kept list of read tools beside 154 declarations goes stale the first time someone adds a get_ . A tool wrongly marked read-only is worse than one left unmarked, because it invites an agent to call a mutation speculatively. Lifetimes via AbortSignal . There is no unregisterTool . Aborting the registration controller is how tools go away, so they disappear cleanly with the editor. A second signal on execute cancels a call mid-flight, which matters when a sculpt covers a 4 km terrain. A visible record. Tools run in the page, so the only trace of a call is the one the page chooses to show. The menu bar carries an AGENT readout: tools registered, and the name of the last call. What it does Rove turns a natural shopping request—such as “Find three shirts, three pants, sneakers, and a fragrance for four days in Cancún under C$450”—into a structured research mission. The browser agent can: Read the user-approved style profile. Translate the request into quantities, categories, occasions, and budgets. Claim prioritized retailer research targets. Browse live retailer pages. Progressively publish grounded products with direct images and canonical links. Enrich products with availability, pricing, materials, and variants. Report research progress and unresolved needs. Add exact products to the shared cart. At the same time, the human can: Watch products arrive progressively. Filter and compare recommendations. Inspect retailer provenance. Accept the complete edit or replace only selected items. Request completely fresh research without duplicate links. Save completed prompts and accepted products locally. Manage a cross-retailer cart called “Your Thread.” Rove keeps completed missions separate from the current mission, so previous research remains useful without confusing the active task. How we built it Rove is a client-only application built with Nuxt 4, Vue 3, strict TypeScript, Tailwind CSS, and the imperative WebMCP API. It registers 17 tools through document.modelContext , covering profile setup, mission planning, retailer scheduling, candidate publication, product enrichment, recommendation review, research history, and cart management. The most important architectural decision was giving the interface and WebMCP tools the same typed domain action layer. Agent actions do not update a separate hidden system: they produce the same visible state changes as human actions. A deterministic research scheduler ranks retailer targets based on: Requested categories and quantities. Remaining unmet needs. Style and occasion relevance. Department compatibility. Per-item and overall budgets. Retailer capabilities. Scarce categories such as fragrance. Published candidates pass through validation for retailer domains, canonical product URLs, mission identity, budgets, duplicate history, and required imagery. Recommendation order combines relevance, budget fit, profile alignment, availability, freshness, and retailer diversity. The application uses browser-local persistence and requires no backend, database, account, API key, embedded chatbot, or OpenAI API call. It is deployed as a static Netlify application and remains usable when WebMCP is unavailable. Challenges we ran into The hardest challenge was making agent research behave like a reliable product workflow instead of an open-ended chat. Retailer information is inconsistent. Some products have sizes and colours, while fragrances and accessories may have neither. We had to introduce category-aware variant handling so a perfume could not accidentally inherit an invalid clothing colour or size. Selective replacement was another difficult problem. When the user rejected one product, the system initially risked replacing or hiding accepted products. We redesigned the review workflow so accepted products remain visible and only explicitly rejected items become new research targets. We also had to solve duplicate prevention across repeated missions. Rove now retains previously surfaced and accepted product links so “research again” can use past preferences as context without relisting the same products. Product imagery created additional complexity because retailer image URLs vary and can fail after publication. We added direct-image validation, visible fallbacks, and consistent image framing so missing or differently sized assets do not break the interface. Finally, we had to balance a sophisticated agent workflow with a simple human experience. Mission state, research queues, replacement context, saved history, and the cart all needed to remain understandable without exposing internal orchestration details. Accomplishments that we're proud of We are especially proud that Rove feels like a complete fashion product rather than a WebMCP demonstration screen. Key accomplishments include: Seventeen working WebMCP tools with closed schemas and clear annotations. One shared action boundary for human and agent operations. Progressive multi-retailer research with visible state changes. Quantity-aware and budget-aware mission fulfilment. Selective product replacement without disturbing accepted items. Fresh research that avoids previously listed links. Category-aware cart variants for clothing, fragrance, and accessories. Saved missions with locally preserved prompts and accepted edits. A polished, responsive, accessible Rove interface. A deterministic test suite with 68 passing tests, strict type checking, and verified production builds. What we learned We learned that useful agent experiences depend more on state design and tool contracts than on one large prompt. Small, purpose-built tools with explicit schemas gave the browser agent clearer responsibilities and made failures easier to understand. A persisted state machine also made the collaboration resilient: the agent could report what it had completed, what remained unresolved, and what it should do next. We also learned that human control must be visible. Users need to see what the agent changed, preserve decisions they already approved, and request corrections without restarting the entire workflow. Most importantly, WebMCP works best when it is integrated into the product’s real domain model. The tools should not sit beside the application—they should operate the application. What's next for Rove Next, we want to expand Rove with: More retailer adapters and stronger regional availability support. Better price and inventory freshness indicators. Optional, privacy-conscious cross-device synchronization. Visual style references and wardrobe-aware recommendations. Stronger accessibility and mobile interaction testing. User-controlled retailer preferences and sustainability signals. Cleaner retailer checkout handoffs while keeping purchasing on official retailer sites. Evaluations that measure duplicate rate, budget adherence, research completion, and recommendation acceptance. Our long-term vision is for Rove to become the open-web workspace where people and agents build confident shopping decisions together. Give AI agents useful access, without giving away Human authority. Like Comment Story Updates Inspiration As AI agents become capable of using websites and taking actions on behalf of users, I kept coming back to one question: How do we give an AI agent useful access without also giving it full trust or Human authority? This becomes especially important in high-stakes applications. In cybersecurity, finance, administration, or access management, an Agent may be useful for gathering information and making recommendations, but a wrong action can have real consequences. I did not want to build another cybersecurity copilot that simply reads logs and produces a verdict. Instead, I used a synthetic security incident as a proving ground for a broader idea: a web application should decide what an Agent is allowed to do at every stage, preserve Human context and judgment, and keep consequential authority separate from Agent reasoning. That became TraceLayer . What TraceLayer does TraceLayer is a WebMCP-native reference architecture for Human-Agent collaboration in high-stakes web applications. The demo follows one synthetic cybersecurity case involving suspicious account and connected-application activity. ChatGPT investigates the case using structured tools exposed directly by the TraceLayer webpage through WebMCP. During the investigation, the Agent can read evidence, inspect entities, connect related events, link evidence, and maintain an assessment. But its capabilities are not static. As the case progresses, TraceLayer changes the Agent's WebMCP surface. During investigation, it can gather and record evidence. During response review, investigation writes disappear and the Agent can only read the case and propose a response. Once a consequential proposal is pending approval, the Agent becomes read-only. There is deliberately no WebMCP tool for authorization or execution . The Human also contributes something the Agent cannot determine from the exposed investigation data. In the demo, a login appears to originate from Singapore. The Agent initially treats that location as supporting evidence of compromise. The Human checks an internal company network reference and adds organizational context showing that the address is actually a sanctioned corporate VPN exit. The original event is never rewritten. Instead, the Agent reads the updated shared case and creates a new assessment that supersedes its earlier interpretation. This creates a collaboration loop where: Agent reasoning → Human context → Agent reassessment rather than treating the Agent's first answer as final. Why authentication matters The most important boundary appears when the Agent proposes a consequential action. Simply placing an Approve button on a webpage is not enough. A browser Agent may also be capable of interacting with ordinary webpage controls, so a click by itself is not strong evidence that a Human approved the decision. TraceLayer separates three responsibilities: Agent: investigates and proposes. Human: provides organizational context and authorizes consequential decisions. SYSTEM: performs an approved operation. Signing in with ChatGPT establishes the account identity, but identity alone is still not approval. For consequential actions, TraceLayer uses a fresh WebAuthn user-verification ceremony tied to the exact proposal and current case state. Only after that verification does TraceLayer record the Human authorization. A separate SYSTEM record then performs the simulated security action. In short: The Agent proposes. The Human authorizes. SYSTEM executes. The authorization flow is real. The cybersecurity telemetry and response effects in the demo are synthetic and simulated. How I built it TraceLayer is a browser-first application built around a single shared case state. The Human interface and the WebMCP interface both operate on the same underlying domain functions, so the Agent is not interacting with a separate demo backend or a scripted copy of the case. TraceLayer exposes seven generic WebMCP tools: get_case_state query_events inspect_entity correlate_entities link_evidence record_assessment propose_response_action The page dynamically registers only the tools appropriate for the current stage of the investigation. Application policy remains authoritative even if an Agent has stale knowledge of a previously available capability. The incident contains 40 immutable synthetic events. Some evidence is externally controlled and even contains instruction-like text aimed at automated review. TraceLayer still exposes that content as evidence, but that content does not gain authority over application policy, tool availability, authorization, or execution. The final workflow is: INVESTIGATING → RESPONSE_REVIEW → PENDING_AUTHORIZATION → POST_ACTION_REVIEW → CASE_COMPLETE At completion, TraceLayer produces an inspectable Decision Trail showing what the Agent assessed and proposed, what context and decisions came from the Human, and what actions were performed by SYSTEM. Challenges The hardest part was not getting the Agent to investigate the incident. ChatGPT could solve the synthetic case surprisingly quickly. The harder problem was designing an interaction where the Human genuinely mattered. Early versions risked becoming the familiar pattern of: AI recommends → Human clicks approve That was not enough. The Human needed to contribute knowledge that changed the investigation itself, not just appear at the end as a ceremonial approval button. That led to the organizational-context handoff and assessment-supersession model. Another major challenge was authority. At first, Human and SYSTEM actions were represented only as application-level actor labels. Testing showed that an Agent with normal browser interaction could potentially initiate ordinary UI controls. That forced a much stronger design: authenticated identity, real WebAuthn user verification, exact proposal binding, fresh challenges, replay protection, and separate SYSTEM execution. I also spent significant time trying to break the implementation rather than only proving the happy path. The final project includes tests for stale capabilities, replay attempts, wrong revisions, wrong users, rejected proposals, raw-evidence immutability, deterministic reset, hostile-content behavior, and multi-user authority isolation. The final suite contains 128 automated tests , alongside TypeScript, lint, build, accessibility, responsive, and published-host validation. What I learned The biggest lesson was that Agent capability and Human authority are different things . Giving an Agent access to useful tools does not mean it should inherit the authority of the Human using the application. I also learned that Human-Agent collaboration becomes much more meaningful when both sides contribute something distinct. The Agent is good at searching, correlating, and maintaining structured reasoning across machine-scale information. The Human contributes organization-specific knowledge, judgment, and verified authority over consequences. And the application itself has an important role: it controls which capabilities exist, preserves state, enforces valid transitions, and records how decisions were reached. WebMCP made this especially interesting because the capability boundary lives directly in the application. The webpage is not just displaying information to an Agent. It can expose a structured capability surface that changes as the application state changes. Why this is practical TraceLayer is not intended to replace existing SIEM, EDR, identity, or enterprise systems. Those systems can remain the telemetry and execution layers. TraceLayer demonstrates the Human-Agent control layer that can sit above them: where an Agent investigates, the Human contributes local knowledge and controls important decisions, and the application constrains what the Agent is allowed to do at each step.
