=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A decision board an agent and a person edit together: the agent researches and scores, you override what you disagree with, and it reasons from your judgment instead of arguing with it. Like Comment Story Updates Why this use case fits WebMCP A decision is not a request. It is a workspace two parties keep changing. Most agent integrations are request-shaped: you ask, the agent answers, the answer arrives as text. That shape is a poor fit for deciding anything real, because the interesting part is not the conclusion, it is the twenty small judgments underneath it, each of which a person may want to disagree with. WebMCP fits because it puts the agent's hands on the same surface the person is looking at. The agent is not describing a decision board to me in prose. It is editing the one on my screen, and I am editing it back, in the same session, with no copy-paste between us. A conventional MCP server could fetch the same search results. It could not put them on my screen, and it could not see that I moved a weight from 3 to 5 thirty seconds later. How it makes the experience better You can see the work. Options, criteria, weights, and scores appear on the board as the agent creates them, each tagged with who set it. Nothing is buried in a transcript you have to scroll back through. You can interrupt at the level of a single judgment. If the agent scored one county a 4 on unmet need and you know that is wrong, you click that cell and change it. You do not have to re-litigate the whole analysis in prose to correct one number. The evidence stays attached. Every live search the agent runs pins to the board with source, date, and link, so a claim and the thing it came from stay in the same place. You can disagree with a specific source rather than with the model's tone. What people and agents can do together that was hard before Correct an agent mid-analysis and have it actually absorb the correction. The board records who set every score. When you override a value the agent chose, that override is flagged in the state the agent reads back through get_board . The agent sees that a human overrode it there and continues from your number. The scoring tool goes further and refuses to overwrite a human-set cell at all. It returns a message telling the agent to state what it would have scored and why, and leave the decision to you. That is a deliberate stance: an agent working alongside someone should not quietly overrule them, and WebMCP is the first place I have been able to encode that as a property of the tool rather than a hope about the prompt. The result is a genuine division of labor. The agent is better at breadth, running twelve searches and drafting twelve rationales. The person is better at knowing that the third one is wrong. Before this, those two things happened in different windows. How WebMCP is implemented Seven tools registered on document.modelContext in public/index.html : Tool What it does get_board read question, options, criteria, every score with its author, the ranking, and unscored cells. readOnlyHint: true set_decision set the decision question add_option add an option, idempotent so retries are safe add_criterion add a criterion weighted 1 to 5 gather_evidence live SerpApi search (web / news / related), pinned to the board score_option score one cell with a rationale; refuses to overwrite a human explain_verdict ranking, margin, most leveraged criterion. readOnlyHint: true Registration goes through an AbortController signal, which is how WebMCP unregisters; there is no unregisterTool . Every tool carries a title as well as a name , so a client listing site tools shows a readable label. Every execute returns the MCP content shape { content: [{ type: "text", text }] } so results pass through client normalization unmodified, and receives the AbortSignal from its options argument, which gather_evidence passes into fetch so a cancelled call cancels the request. Tools are registered from the top-level document, since WebMCP does not discover tools inside iframes. The page feature-detects and degrades to a normal manual tool when no agent is present, so it is a complete product either way. gather_evidence is marked untrustedContentHint . It pulls arbitrary third-party web content into the agent's context, which is the case that hint exists for. Everything rendered from those results is HTML-escaped and outbound links carry noopener noreferrer . Score entry is an inline editor rather than window.prompt , because embedded and in-app browsers routinely suppress prompt() and that would have silently broken the override path in exactly the clients this runs in. The board is keyboard operable and the activity log is an aria-live region. Everything runs client-side except the SerpApi proxy, a zero-dependency Netlify function that keeps the API key server-side. No framework, no bundler, no lockfile. Two files. Inspiration AI agents are increasingly able to make decisions and take action across real workflows. As their autonomy grows, a harder question follows: Where should agent authority end, and where should human authority begin? AI Delegation Boundary began as a way for us to understand WebMCP by building with it. While developing the project, we realized that WebMCP could support more than letting an Agent operate a web page. The web application could hold the current boundary, constraints, human judgments, and approval state, while the Agent reasons and acts through tools exposed by that page. That led to the core idea: Make AI delegation itself something a human and an Agent can examine, challenge, revise, and approve together. What it does AI Delegation Boundary helps a human decide what an AI Agent may do on its own. A human first defines the work being considered. The Agent then uses WebMCP tools exposed by the page to: Inspect the current delegation boundary. Propose a revision. Challenge that revision with a concrete scenario. Re-test it against Guardrails and previous human decisions. Inspect the revision history and current state. When the Agent finds a case that requires judgment, it stops and returns control to the human. The human decides whether that case should be: Agent-only Human review Not delegated That judgment becomes a regression test for future revisions. The collaboration loop is: Proposal → Challenge → Human Judgment → Re-test → Human Approval → Apply The Agent cannot approve its own revision. Only the exact revision explicitly approved by the human can be applied. How we built it AI Delegation Boundary is built with React, TypeScript, Vite, and WebMCP, and is deployed on GitHub Pages. The web application holds the delegation boundary, Guardrails, human judgments, revision state, approval, and applied state. WebMCP exposes five normal tools to the Agent: Inspect the delegation workspace Propose a boundary revision Challenge the current revision Review the current revision Inspect revision history After the exact current revision receives explicit human approval, an additional apply capability becomes available. There is no dedicated AI backend. The conversational Agent works directly through the WebMCP tools exposed by the page. Our architectural principle is: Conversation is the Agent; state and authority live in the web app. Review combines three different controls: Guardrails — deterministic invariants that must not be violated Known Decisions — previous human judgments preserved as regression tests Agent Challenges — concrete scenarios generated to actively challenge the current boundary Challenges we ran into The hardest part was not exposing tools to an Agent. It was designing the authority model around them. We needed to ensure that the Agent could propose and challenge changes without granting itself additional authority. We also had to make sure that: human judgments became reusable tests, a changed boundary required a fresh Agent Challenge, approval referred only to the exact state the human reviewed, and an Agent could never silently approve or expand its own authority. Another challenge was the Human-Agent handoff. We did not want users to type tool names, revision numbers, or challenge scenarios manually. The browser therefore tells the user what happens next, where the next action takes place, and provides copy-ready handoffs when control moves back to ChatGPT. Accomplishments that we're proud of We built a complete Human-Agent governance loop through WebMCP. The Agent can inspect, propose, challenge, and re-test changes to its delegation boundary, while the human retains final judgment and approval. Human judgments do not disappear after one decision. They become regression tests that constrain future revisions. We also made the Agent capability surface depend on human authority: five normal tools are available during collaboration, and the apply capability becomes available only after explicit human approval of the exact current revision. Most importantly, WebMCP is not used here simply as a remote-control layer for a website. It is part of the mechanism that separates Agent action from human authority . What we learned Building AI Delegation Boundary changed how we think about WebMCP. The interesting part is not simply that an AI Agent can operate a website. A web application can hold state, constraints, and authority while an Agent reasons and acts through that surface. This allows the collaboration itself to be designed: what the Agent may change, what it must challenge, when it must stop, what only a human may decide, and when additional capability may become available. For us, WebMCP became a way to connect Agent reasoning with a governed web surface. What's next for AI Delegation Boundary AI Delegation Boundary is a focused implementation of a broader problem we are exploring through SOLIFAN and ReadinessOps: How can organizations expand the practical use of AI Agents while deliberately retaining the judgments and authority that should remain human? Next, we want to connect this model to real organizational workflows, richer evidence, additional delegation factors, and reusable governance patterns across different Agent environments. The problem Remote web help today relies on screenshots, phone calls, screen sharing, remote control software, or handing over a password. Screenshots lose context. Screen sharing and remote control require both people to be free at the same time and give one person full access to the other's session. Credential sharing gives up account security entirely. None of these let a second person's own agent pick up where the first person left off, on the second person's own account. What ShowOnce does A sender demonstrates a real task once, live, inside a fully interactive connected demo application called Northstar Benefits (an employee benefits portal). ShowOnce does not screen-record or ask the sender to pick steps manually: because the demo app's UI and ShowOnce both call the same shared domain command layer, every meaningful action the sender takes (selecting a plan, changing a preference, confirming an address) is automatically captured as a semantic event. Those events are compiled into a portable, sanitized procedure — intent only, no selectors, credentials, sessions, or screenshots. A recipient opens the resulting handoff link. They can act on it directly in the same live app, rendered against their own account state, or they can ask a WebMCP-capable agent (for example, ChatGPT's in-app browser, or Chrome with WebMCP enabled) to "do what [the sender] showed me." When an agent is used, it invokes real document.modelContext tools registered by ShowOnce — the exact same commands the human UI uses — so the visible, live Northstar Benefits app updates in front of the recipient as the agent works. Nothing is simulated or faked. ShowOnce compares the demonstrated procedure against the recipient's actual state and decides, deterministically, what still applies, what can be safely applied, what differs materially, and what must be left for a human to decide. For any consequential, identity-bearing action — actually submitting the renewal — an agent can get the recipient all the way to a final reviewable summary, but no further. A human must check a personal attestation checkbox and click "Confirm & submit" themselves. That single click is the only human step, and no WebMCP tool can ever perform it. How WebMCP is used Real document.modelContext.registerTool(...) registrations, made client-side once the recipient route mounts (see src/webmcp/registerTools.ts ). Strict JSON Schemas for every tool's input, with no free-form or untyped arguments. readOnlyHint and untrustedContentHint annotations so a calling agent knows which tools only read state and which tools are handling handoff-authored content. AbortController -based lifecycle: tools are registered with a scoped signal and unregister themselves cleanly when the recipient route unmounts. A single shared executeCommand() domain layer used by both the human UI and every WebMCP tool, so there is exactly one implementation of the business logic behind "select a plan" or "set paperless" — not a UI code path and a separate agent code path. A human-only, atomic final step: WebMCP tools can read state, apply safe preferences, and prepare a renewal summary, but the recipient_attestation semantic event that authorizes submission can only ever be issued by a human clicking a button in the browser — executeCommand() refuses it outright if the source is 'webmcp' .
