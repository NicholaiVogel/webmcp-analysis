# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Every rejection becomes a rule the agent cannot break again Like Comment Story Updates Rejecting a table opens rule capture. The app turns that correction into a rule and applies it to future proposals. The agent replans around the new rule and finds 16 seats elsewhere. The layout reaches 144 seats with zero violations. Asked for 40 more seats, the agent proposes five tables through WebMCP. Nothing changes yet because proposals are previews until approved. Willowmere Hall on load. 96 seats, eight built-in rules, and three locked objects the agent cannot move. What it is ConstraintCanvas is a venue floor planner where a human and an agent work on the same canvas at the same time. You place the stage, lock anything that cannot move, and decide which sponsor gets the front booth. The agent handles the tedious parts, like fitting more seats without breaking egress, finding clearance violations, and explaining exactly which rule blocked a placement. The floor planner is only the demo. The real idea is what happens when the human says no. Inspiration Agent corrections are usually temporary. You tell the model not to do something, that instruction lives in context, and a few turns later you may have to repeat it. That felt like the wrong place to store human judgment. If I say seating must never block a door, that should not just be prompt context. It should become application state that is visible, editable, and enforced. In ConstraintCanvas, rejecting an agent proposal can create a named rule with provenance. That rule is added to a visible rulebook and enforced against every future proposal. The agent does not need to remember better. The application enforces the correction. Why this use case fits WebMCP The site owns the semantics. The application knows what counts as blocking an exit in metres. An agent using DOM automation would have to infer geometry from pixels. With WebMCP, the floor state and rules are exposed directly as structured data. State is shared. The human and agent both modify the same floor plan during the same session. Read, preview, and write are separated. Six of the nine tools use readOnlyHint . Tools that can affect the floor only generate previews, and the user approves changes before they are applied. That separation lives in the tool contract rather than in prompt instructions. Refusals are structured. A blocked proposal returns the rule ID, rule statement, offending item, and numeric shortfall. The agent can replan using actual constraint data instead of guessing why a call failed. What people and agents can do together The core use case is constrained spatial planning. The human defines the boundaries and important decisions. The agent optimises inside them. The application guarantees that those boundaries are respected. Without that enforcement, the human either does the optimisation manually or delegates it and rechecks every result. WebMCP enables a third model: delegate the arithmetic, keep the judgment, and turn corrections into persistent constraints. How WebMCP was implemented ConstraintCanvas registers nine tools with document.modelContext.registerTool , grouped into inspection, proposal, explanation, and constraint authoring. Two headers are required before document.modelContext is exposed: Origin-Agent-Cluster: ?1 Permissions-Policy: tools=(self) Tools are defined as descriptors and registered through a shared bridge that wraps every execute call. This keeps logging and refusal handling at the tool boundary instead of duplicating it inside each implementation. Each tool has its own abort controller so the surface can be withdrawn and republished cleanly. Results are returned as JSON. The most interesting part is that the tool contract changes at runtime . When a user ratifies a new rule, the proposal tools are re-registered with the active constraints included in their description , then the surface emits toolchange . That means a correction changes what the agent is told it can do before the next call is created, not only what the application rejects afterwards. Validation runs in three passes: Check locks as hard boundaries. Compare rule violations before and after the proposal. Convert valid proposals into a preview for human approval. The differential check is important because an existing violation should not block a proposal that actually improves the layout. How I built it The app uses Next.js 16, React 19, TypeScript, SVG, and IBM Carbon design tokens. It is deployed on Vercel. There is no state library and no canvas library. The constraint engine is intentionally simple. Placement uses a greedy search with scoring rather than a general solver. The priority is not algorithmic complexity. It is producing layouts that remain valid and explainable. Eight built-in rules use the same evaluation engine as user-created rules. For egress, the app runs a flood fill outward from doors across the floor grid. Straight-line distance is not enough because an object can be physically close to an exit while still being blocked by surrounding furniture. Circulation also enforces a minimum free-area ratio: $$ \frac{A_{\text{floor}} - \sum_i w_i h_i}{A_{\text{floor}}} \ge 0.70 $$ This gives seat maximisation a hard upper bound. The app also includes a small agent panel that calls getTools and executeTool against the same surface, so the full interaction can be demonstrated without a separate agent browser. Challenges Different WebMCP implementations exposed different APIs. The spec describes ModelContext as an EventTarget , so I initially used addEventListener for toolchange . That worked in Chrome but failed in ChatGPT's implementation, causing React to unmount and render a blank page. Native calls are now feature detected against a minimum surface of registerTool , with regression tests for reduced implementations. Bad refusals waste agent turns. An early optimise_layout refusal only returned: Unknown objective. The agent had no way to discover valid inputs and spent several calls guessing. Refusals now require a next_step , and invalid values return the accepted alternatives. Thinking models preserve metadata across tool calls. Gemini 3 attaches a thought signature to function call parts. I initially rebuilt the response from extracted tool calls and dropped that metadata. The server route now forwards the original model turn unchanged. Valid layouts can still look wrong. Early plans passed every rule but broke the visual rhythm of existing seating. The optimiser now detects repeated furniture spacing and includes alignment in its scoring function. Model calls needed caching. One planning task could use five or six requests because the agent repeatedly inspected unchanged state. Inspection results are now cached per conversation and invalidated when a proposal changes the floor. What I learned A tool contract should be written as if it is the agent's only source of truth. A refusal should explain what failed and what the agent can do next. Otherwise it becomes a dead end that wastes tokens and tool calls. I also learned not to assume that one implementation of an emerging standard represents all of them. Most importantly, WebMCP is not only useful because a webpage can expose tools. The more interesting capability is that the tool surface itself can change at runtime. That allows a human correction to become part of the application's active contract, which is much stronger than asking the model to remember it. A WebMCP incident console where agents investigate production failures and humans stay in control of remediation. Like Comment Story Updates Inspiration Incident response is one of those workflows where an AI agent could genuinely save time, but it is also a workflow where giving an agent unrestricted control would be a terrible idea. During an outage, engineers jump between service health, deployments, logs, traces, alerts, runbooks, and incident timelines while trying to answer a few basic questions: What changed? What is actually failing? What evidence supports that diagnosis? And what is safe to do next? I wanted to explore what incident response looks like when the agent can work inside the same operational console as the human instead of operating through a separate chatbot or a disconnected API. That became Firebro . The design principle behind the project is simple: Agent capability, human authority. What it does Firebro is an incident response console built around WebMCP. An agent can investigate an active incident by checking service health, dependencies, recent deployments and changes, logs, traces, alerts, metrics, runbooks, and the incident timeline. It can correlate that evidence, identify a likely cause, and propose a remediation. For example, one incident starts with degraded checkout performance after a bad deployment. The agent can compare service metrics, inspect traces and logs, find the deployment that introduced the regression, and propose rolling it back. But the agent cannot simply execute a consequential remediation on its own. Actions such as a rollback can require an approval tied to the exact proposed action. The approval has to come from a real human interaction in the console before the action can proceed. Once remediation starts, the simulated production environment reacts. Metrics recover, logs change, and the incident moves through recovery and monitoring before it can be resolved. Firebro includes multiple deterministic incident scenarios so the correct response is not always "roll back the latest deployment." Some incidents involve resource exhaustion, feature flags, memory leaks, or even third-party failures where the best action may be to wait rather than make an unnecessary production change. How I built it Firebro is built as a web-based incident console with a WebMCP capability layer on top of the same operational state visible to the human operator. The system exposes tools across the full response workflow: incident discovery, service health, dependencies, deployments, recent changes, logs, traces, metric comparisons, alerts, runbooks, incident notes, remediation actions, approvals, and incident resolution. One of the main implementation goals was avoiding a separate "agent version" of the application. When an agent investigates something, the console reacts too. A service can be highlighted in the topology, log views can focus on relevant entries, metric comparisons become visible, traces can be surfaced, and approval requests appear next to the operational evidence the human needs to make a decision. Tool availability also depends on context. Capabilities can change based on the selected incident, current incident state, and what actions are currently valid. The backend runs a deterministic incident simulation. Each scenario has a known underlying cause, but that ground truth is intentionally hidden from the WebMCP tools. The agent has to diagnose the incident using the same observable evidence available through the console. Mutations and incident events are persisted so the UI and tool layer stay synchronized as the incident evolves. Challenges I ran into The hardest part was making the environment realistic enough that the agent actually had to investigate. If every incident simply had an obvious error message pointing to the answer, there would be no real diagnostic workflow. Firebro includes misleading signals and plausible alternatives so the agent has to correlate evidence instead of choosing the loudest symptom. Another challenge was tool design. Returning thousands of raw log lines or metric samples makes an agent less useful, not more useful. The tools needed to expose enough evidence to support a diagnosis without turning every response into an unstructured data dump. I also had to think carefully about approvals. A generic "approved: true" flag would not be enough for a real operational workflow. Approval has to be tied to the exact action being proposed so an approval for one operation cannot silently authorize another one. Keeping the simulation deterministic was another important challenge. The same incident needs to behave consistently enough for automated evaluation while still looking like a live operational system. Accomplishments that I'm proud of I'm most proud that Firebro feels like one shared workspace rather than a dashboard on one side and an agent on the other. The agent works with the same incident, graphs, logs, services, and actions the human is looking at. Investigation has visible consequences in the interface, and consequential actions pass through an approval workflow instead of bypassing the operator. I'm also proud of the incident simulation itself. Different scenarios require different forms of reasoning, and remediation does not always produce an immediate perfect recovery. Some actions only partially help, some have no effect, and the system can regress if the diagnosis was wrong. That makes it possible to evaluate more than whether an agent can successfully call a tool. What I learned The biggest thing I learned is that agentic interfaces need more than a large tool list. The useful part is the structure around those tools: when they are available, what evidence they return, how their effects appear to the human, and what happens when the agent is wrong. I also learned that human approval is much more useful when it happens next to the evidence supporting the action. Asking someone to approve a rollback in isolation is very different from asking them while they can see the deployment, affected metrics, traces, and the agent's proposed action in the same console. WebMCP also made browser context much more important than I originally expected. The agent is not operating a remote service in the abstract. It is operating the application the human currently has open. What's next for Firebro The current version uses deterministic simulated infrastructure so incidents can be reproduced and evaluated reliably. The next step would be connecting the same interaction model to real observability and incident-management systems while keeping the approval boundary intact. I'd also like to expand the scenario set, add more complex multi-service failures, improve automated agent evaluations, and explore richer policy controls for actions with different levels of operational risk. The long-term idea is not an autonomous system that replaces the incident commander. It is an incident console where an agent can do far more of the investigation and coordination work while the human keeps authority over decisions that can affect production. The broker now partitions results by tool.origin. executeTool() takes a JSON string and returns a JSON string, not objects, so arguments and results both need serialising and the response needs parsing twice. Registering a tool that already exists throws InvalidStateError: Duplicate tool name. Our toolchange handler was not awaiting its own callback, so two refreshes could overlap and the second collided with the first. Verification was its own problem: WebMCP does not exist in headless Chrome, so a normal headless test captures an empty, broken page. Every check drives a real headful Chrome over the DevTools Protocol instead, and cross-origin iframes are out-of-process, which needs Target.setAutoAttach with flatten: true to reach them at all. Accomplishments that we are proud of The central claim is measured rather than asserted. tools/verify-agent.js walks the entire agent path and scans every byte the assistant can see for the record values: leakedSecrets: [] across 9,940 bytes. tools/verify-revocation.js proves the revocation path against production, not a mock. ?selftest=1 runs seven assertions inside the live page, so a judge can check the claims without reading any code. Thirty-six unit tests cover the program graph and the envelope. The control case is the part we would point at first. A tool registered without exposedTo is not merely undocumented or unlisted; the broker genuinely cannot reach it, and the page lets you try. What we learned The important design decision was making the broker compose rather than forward. Proxying twelve agency predicates straight to the assistant would have been less code and a worse product: the agent would carry the burden of knowing which agency holds what, and every question would cross the boundary individually. Six facades that each consult several origins gave a better agent experience and a smaller disclosure surface at the same time. The second lesson was that a privacy claim is worth only as much as its instrumentation. "No records are disclosed" is easy to write and easy to break by accident, so the ledger counts real crossings and the verifier greps the agent's own view for the secret values. What is next for Vouchsafe The predicates here are hand-written per agency. The natural next step is a declarative attestation schema, so an agency can publish which predicates it answers without writing a tool by hand, and a signed attestation reference, so a determination can be re-verified later by a third party from the ref alone. Beyond benefits, the same shape fits anywhere a decision needs facts that are legally forbidden to pool: clinical eligibility, immigration casework, school enrolment, tenancy checks. The interesting property is not that the data stays put. It is that the consent to ask is a browser primitive an ordinary person can withdraw. Like Comment Story Updates Inspiration Agents are getting good at acting on the web, but almost every agentic product still asks you to pick one of two shapes. An agent that advises : it talks about your work from a chat panel, and you translate its advice into the application by hand. An agent that operates : it acts through tools or APIs, and you find out afterwards what changed. Both give something up. The first leaves the agent outside the work. The second takes the human out of the loop at exactly the moment the stakes are highest. We wanted to know what a third shape looks like: what if the application itself were the shared surface, where a human and an agent reason about the same problem, and the human keeps authority over what becomes real? That question is what made WebMCP interesting to us. Not as a way to make an existing app agent-compatible, but as a way to let a page say these are the actions that make sense right now — and to have that answer change as the human works. What it does MUTUA demonstrates the model through one focused scenario: software launch recovery . A team is four weeks from a September 30 launch. Five engineers, a $420,000 budget, a stated tolerance of 15 % workload overload. Everything is on track. Then one QA engineer becomes unavailable. You mark it in the interface. The workspace recomputes: peak load 134 %, overload 34 %, launch slipping two working days. You ask the agent to keep the September launch without increasing burnout . It reads the same state you are looking at, and creates Proposal A — on time, +$12,000 , overload down to 4 % , but the Analytics dashboard deferred out of launch scope. Your plan has not changed. This is a proposal, sitting beside reality, with every operation spelled out in a readable diff. Analytics is a commitment you made, so you lock it. Proposal A immediately shows a conflict — it is never rewritten behind your back, just re-measured against your new constraint and frozen for comparison. You ask for another option. Proposal B — on time, +$4,000 , 9 % overload, no scope loss , every lock respected. It gets there differently: instead of dropping a feature, it defers work that was never a launch commitment, splits QA effort across whoever has the skill and the room, and books the smallest useful block of contractor capacity. You compare them side by side, on numbers the application computed. Then the moment the whole project is built around. Look at the Agent Capabilities panel: commit_proposal is not there. The agent does not have the capability to make this real. You click Approve Proposal B , and it appears. You say use B . The agent commits. The plan becomes September 30, 9 % overload, $424,000, full scope — and every step, human and agent, is in the timeline with its author. The four primitives Shared state. One store backs the interface and every WebMCP tool. There is no agent-side copy of reality that can drift out of date. Proposal state. Agent changes are explicit reversible operations applied to a cloned plan. Exactly one tool can touch canonical state, and it is gated. Human locks. A locked item cannot be rescoped, delayed, reassigned or resized. The lock is enforced when an operation is attempted and re-evaluated against proposals that already exist. Dynamic capability surface. The set of registered WebMCP tools is a function of workflow phase. Comparison does not exist before simulation. Commit does not exist before approval. How we used WebMCP Twelve semantic capabilities, grouped by what they are for: Observe — get_workspace_state , get_active_scenario , inspect_constraint , list_conflicts Propose — create_proposal , modify_proposal , add_constraint , lock_entity Evaluate — simulate_proposal , compare_scenarios Finalize — discard_proposal , commit_proposal They are never all registered at once. A capability map turns the current phase into a tool set, and the registry synchronises against the WebMCP host on every material state change — registering what became meaningful, unregistering what did not. The Capability Inspector in the interface renders the live registry , not the map, so what a judge reads is exactly what an agent can call. There is deliberately no tool for approval . That transition belongs to the interface, and to the person using it. How we built it Next.js 15, React 19, TypeScript, Zustand, Zod, Tailwind CSS. No backend, no database, no ML, no external API on the golden path. Every material mutation — from a click or from a tool — follows the same path: validate, apply, bump the state version, re-score every scenario, recompute the phase, refresh the WebMCP registry, append an audit event, persist. The consequence engines are pure functions. The agent chooses operations ; the application computes consequences : deadline slip, per-person load, recovery spend, scope loss, constraint results. No model calculates anything, which is why the demo replays identically and the tests can assert exact figures. The recovery planner is deterministic and is not a lookup table. It implements two policies with genuinely different trade-offs — one that will spend more and sacrifice scope to keep tasks whole, one that preserves scope by fragmenting work and buying the minimum outside capacity. Rewriting it silently would have destroyed the story we were telling, so proposals are re-scored after every change and surface as conflicts instead. Calibrating the dataset. The demo numbers had to fall out of the engine, not be typed into a component. The Capability Inspector exists so that the contract between the application and the agent is something you can watch change. Level two, the agent can participate — it creates and modifies visible, reversible proposals.
