=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Inspiration An agent loses its context, and it does not just lose information. It loses the prohibitions. The approach you ruled out last week. The dependency you refused. The step it already finished. A conversation summary keeps the highlights and sacrifices exactly what constrains, because a constraint reads like a detail right up until someone breaks it. So you explain it again. And the agent proposes, with confidence, the thing you eliminated together on Tuesday. We wanted to know whether that was actually measurable, or just a feeling. It is measurable. What it does Keydler takes those constraints out of the conversation and puts them on a web page that an agent reads and writes through WebMCP: rules in force, work done with its evidence, approaches ruled out with the reason , and the next action. The part that matters is not that the human approves things. It is that the human can change the rules while the agent is working, and the page guarantees the agent finds out. Every agent write carries the version it read. A human write never does. So when you add a rule mid-flight, the agent's next write is refused: STALE STATE You are attempting to log work based on task state v5. Current state is v6. No write took place. Call what_changed with since_version: 5 to see only what moved. It asks for the delta, reads the new rule, and adapts. Without that refusal it would overwrite the rule you had just set, and neither of you would know ; you would find out from the result. Fourteen tools, four read and nine write, plus one that opens the log when none exists. Browser-local: no account, no server, nothing leaves the device. The measurement Without the log, an agent proposed the ruled-out approach again in 8 cases out of 8. With the log, in 0. Eight tasks, two conditions, one binary question. We got the design wrong first, and that failure taught us the product. Our initial tasks ruled out classic anti-patterns ; localStorage for tokens, OFFSET pagination. The control scored zero : a capable model avoids those unprompted, and rules them out by name without being asked. There was nothing to measure. So we inverted it. What has to be ruled out is not the bad answer. It is the good answer, set aside for a local reason. Ban the Redis token bucket because operations refused Redis. Ban cursor pagination because a backfill broke id monotonicity. Those are the right answers everywhere except here, for reasons no model can deduce. Each write carries a mutation_id and an argument fingerprint: the same id with the same arguments replays the original reply verbatim; the same id with different arguments is refused and audited, rather than acknowledged as work that never happened. A shared workspace where WebMCP agents discover context-aware tools, prepare visible work, and apply sensitive actions only after human approval. Like Comment Story Updates Inspiration## Inspiration A website should be able to tell an AI agent what it can do, rather than making the agent infer every operation from visual controls. We built WebMCP Operator Workspace to explore a practical question: how can a human and an agent share an operational workspace while keeping capabilities contextual and sensitive decisions human-controlled? What it does The application presents a fictional hotel refrigeration incident across two pages: Case Workspace and Asset Inspector. In Case Workspace, an agent can read the incident, prepare a work plan, draft a customer update, select equipment components and prepare contextual observations. Prepared work appears in the interface for the human to review. The capability surface changes with context: Case Workspace initially exposes 11 tools. Selecting a component activates two additional tools, bringing the total to 13. Clearing the selection withdraws those tools, returning to 11. Navigating to Asset Inspector exposes six tools for that page. For sensitive proposals, the application separates preparation from approval. Applying a pending proposal is blocked. A human reviews it and clicks Approve in the page. The agent can then apply that proposal once; repeating it is rejected. There is no registered WebMCP tool to approve a proposal. On Asset Inspector, the agent can prepare an inspection note, but the final form save remains a human UI action. How we built it The project is a standalone application built with HTML, CSS and JavaScript, hosted on GitHub Pages. It registers structured capabilities through document.modelContext.registerTool(). Contextual tools are withdrawn using AbortSignal, and each document registers its relevant tool surface. A semantic capability tree describes declared pages, interface regions and capabilities. It distinguishes application contracts from runtime observations: observing an unexpected tool does not automatically add it to the application's authorized surface. Navigation uses declared page identifiers rather than arbitrary URLs. Proposal handling uses explicit states and single-use approval consumption. The reviewed candidate passed 49 automated tests covering application contracts and behaviors, including approval states, replay rejection and contextual lifecycle scenarios. GitHub Actions runs the test suite. Challenges we faced The main challenge was separating three concepts: discovering a capability, preparing work and having authority to apply a sensitive proposal. Contextual tools must disappear when their context ends. Registration failures must not leave a partially active surface. Navigation must expose the destination page's capabilities rather than preserve stale assumptions. We also needed the interface to distinguish a prepared draft from a saved note, and an approved proposal from an applied action. What we learned WebMCP is useful not only for exposing operations, but also for making the agent-facing interface reflect the current application context. Visible shared state helps the human understand what the agent prepared. Explicit approval states make the transition from proposal to application understandable and testable. Accomplishments We combined contextual tool registration, a multipage capability surface, visible agent-prepared work and a human approval workflow in one publicly accessible application. The result demonstrates a complete application-level sequence: proposal, blocked premature application, human approval, single application and replay rejection. How to try it Open the live application with a WebMCP-compatible agent client and enter the workspace. Ask the agent to read the case, select condenser_fan, prepare an observation and clear the selection. Next, request a sensitive-action proposal and observe the blocked attempt before approving it manually. Ask the agent to apply the approved proposal and then repeat the same proposal to test replay rejection. Finally, navigate to asset-inspector and prepare an inspection note without submitting the human form. The application does not require our developer tunnel, proprietary Universal MCP runtime or credentials. An ordinary browser can display the human interface, but agent invocation requires a WebMCP-compatible client. Scope and limitations All incident, customer and equipment data is fictional. State is in memory and local to the active page; reloads and navigation do not promise persistence. Drafts do not send messages. Applying a proposal records a local demo event; it does not dispatch a technician or operate real equipment. The approval boundary demonstrates application workflow enforcement, not server-side authentication or protection against arbitrary browser automation. The accompanying video is an AI-generated explanation created with NotebookLM, not a screen recording of execution. What's next We would explore further usability testing and carefully scoped operational integrations. Persistence, identity and server-enforced authorization would require additional design before production use. Marginalia is an agent-driven epistemological margin for the web: it knows what you know, ingests what you read, and bridges them — connections, meaning, citations, assistance, integrated knowledge. Like Comment Story Updates Inspiration Every AI reading tool today is a chat box beside the text: ask, get a smooth answer, move on. That smoothness is the enemy of understanding — and it never knows what you already know. Two of my own projects had already designed the fix twice without a surface for it: an expand-and-annotate reader in an open-source LaTeX research environment, and "annotated reading versions" of papers in a learning system I'm building around evidence-gated mastery. The missing piece was a way for an agent to work inside the reading, live, while I read. WebMCP is exactly that piece. The name is a homage to the oldest form of this idea: marginalia — commentary written in the margins of a text, never in the text. What it does Marginalia is a reader where a human and their agent work on the same page. The page holds the document, your marks, and your own notes; the agent brings what it knows about you; WebMCP tools are where the two meet. No tool can write to the source. The agent lives in the margin. Open a paper, an article, or a docs page. Tell your agent what you already know — it records that as proposed knowledge you confirm with a tap — and the document reshapes around you: sections you've mastered fold to a stub with a reason , sections you haven't get expansions, glosses, [figures,] and connections to your own notes. Density isn't a global dial; it's a function of what you know about the concepts in each section. An expert in one domain and a novice in another is the normal case. Three layers, never merged, each toggleable: source (immutable), you (your marks), agent (its artifacts — attributed, reasoned, removable, with one button to remove them all). Switch the agent layer off and you are looking at the untouched text. The demo reads across a century: Rutherford's 1911 scattering paper (public domain), a 2025 Curious Kids essay from The Conversation on where atoms come from (CC BY-ND — and the layer rule is ND-compliance by construction: the text is byte-identical, everything else is margin), and Chrome's own WebMCP documentation (CC BY 4.0), which the agent annotates using the very tools registered on the page it's reading. How we built it Vanilla ES modules, no build step, one static page deployed on Netlify. Page state is a single frozen-source / mutable-margin store; every WebMCP tool validates its input and then calls the store, so the rules are enforced in code, not in a prompt. Tools registered via the WebMCP imperative API: get_reading_state , get_section_text , get_knowledge , upsert_knowledge , set_section_depth , annotate , search_notes , insert_figure [adjust to what shipped]. Every tool returns structured errors with a next_step written in coach voice for the agent to relay ("hiding a section requires a confirmed knowledge entry — ask the reader to confirm first"). [Your notes never leave the browser: drop a folder of Markdown and the agent queries a client-side index through search_notes .] [Math renders with KaTeX in both source and margin.] [SVG figures pass a sanitizer before rendering.] Two rules do most of the work: the layer rule (there is no write-to-source tool — enforcement by absence) and the pending-reshape rule (the agent never reshapes the section you are currently reading; changes land as pending and apply when you arrive). The document never moves under you. Why WebMCP and not an MCP server: the state that matters — the document, the click you just made, your notes, the artifacts already in the margin — is page state you are editing live. A server can't see it; the page can, and hands it to the agent on the next call. And the layer rule is only enforceable where the tools live: a page can simply not register a write tool. A prompt can be argued out of; a missing function cannot. Challenges we ran into Building against a protocol that is a week old, in a few hours, with a team of one human orchestrating several coding agents in parallel: one file per lane, an integrator merging, "tested" meaning a screenshot in the PR. [Getting tools visible in the ChatGPT in-app browser vs. the Chrome inspector extension — the API surface is still moving, so we register on both names and log which one took.] Licensing was its own design problem: the demo content had to be legally copyable into a public repo and shown on video, which is how a 1911 paper, a CC BY-ND essay and CC BY docs ended up sharing a stage. Accomplishments that we're proud of A document that visibly reshapes as you say what you know — with a reason under every fold. An ethical constraint (AI never writes into human text) that is also a technical guarantee and, incidentally, what makes CC BY-ND content legal to read this way. Honest states everywhere: refusals explain themselves, "no notes loaded" is a state, not an error. What we learned The interesting WebMCP apps aren't the ones where the agent fills in forms. They're the ones where the page holds something the agent can't have — here, the reader's live behaviour and their own archive — and the tool schema encodes a relationship: the agent proposes, the page referees, the human decides. What's next for Marginalia Integration with knowledge bases, memory systems and testing.
