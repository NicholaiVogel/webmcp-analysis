# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

"Agents propose, people click" is literal here: browsers block downloads that a human did not initiate, so export_image renders the full-size image and puts a real Save button on the page for the person. How we built it The integration is deliberately one thin boundary, three touch points: Mount. A WebMCPBridge component (renders nothing) runs registerWebMcpTools() once on the client. For the ~99% of visitors without an agent runtime that is a single property probe ( document.modelContext , with the legacy navigator.modelContext name as fallback — the entry point has been renamed twice already). Teardown aborts the registration's AbortController . The chat bridge seam. The chat panel owns sendMessage — the same submission pipeline behind the composer (mutate-first ladder, SSE streaming, store application, billing refresh). It registers that callable with the WebMCP layer, so build_map / mutate_map are processed exactly as if the human had typed: same quota, same 1-credit billing with auto-refund, same anonymous-visitor rules (anonymous sessions get a typed sign-in prompt from mutate_map , never a silent no-op). Store reads. The free tools read and write the app's existing map store directly — no server calls. Every result is summarized from post-apply state: layer and feature counts come from what actually landed, never from "the request was sent". If nothing rendered, the result says delivered: false — do not claim a map exists . Two safety pieces sit on top: every paid tool states its cost in its description (that is what runtimes use to classify a call as consequential — a silently-costed tool is the prompt-injection amplifier), and a gesture-reset budget refuses paid calls after 8 of them with no human interaction until the person touches the page. Tests: a unit suite pinning the budget semantics, the grounding rule and the cost-honest descriptions; a Playwright spec in the main app's CI where a stubbed agent runtime drives the real page; and, in the public repo, a live-site contract test that drives showmeonmap.com's registered tools through document.modelContext with no access to app internals — npm test , about 7 seconds, all 8 tools. Stack: TypeScript, React / Next.js on Cloudflare Workers (OpenNext), MapLibre GL + deck.gl, Zustand stores, Playwright. The tool schemas are plain JSON Schema. We probe both entry points and return JSON text, which both runtimes accept. A tool that says "ok" while the canvas didn't change is lying. Our first camera tool wrote to a legacy config channel the renderer ignores while a plan is active — it reported success and nothing moved. Caught in the first live ChatGPT-browser test, fixed by driving the live MapLibre instance and reading the camera back through get_map_state . Downloads. Agent-initiated tool calls carry no user activation, so export_image cannot save a file. It renders the image and hands the human a real Save button instead. Solid dots are inside, faded ones sit within 800 m outside, and the read-back says which is which. Cost. An agent in a loop can spend a person's credits. Cost in the description plus the gesture-reset budget is the answer we shipped; it is also why paid tools go through the same billing path as the composer, with auto-refund. It may have retrieval, browsing, or memory, but those systems often ask the agent to search only after a question has already been asked. Velvet Signal asks a different question: What if your AI could subscribe to publications? Velvet Signal is a publication for humans and their agents. A person gets a readable issue. Their agent gets a structured context patch containing claims, provenance, scope, expiry, and relationships to older claims. The two read the same publication in different ways. The WebMCP Challenge made the missing interface obvious. Before WebMCP, the agent could only look at Velvet Signal's page and infer what the publication meant. With WebMCP, the website can explicitly tell the agent what it is allowed to do. Five public desks scout for meaningful changes on an eight-hour schedule. Source packets are treated as untrusted data and used to propose structured issues. Unchanged source packets do not generate a new issue. Every claim carries provenance, scope, confidence, and a validity window. A publication patch can also describe how new information relates to older information: replaces — the newer claim displaces an older one narrows — both remain valid, but the newer claim controls a more specific scope confirms — independently supported claims remain together conflicts — the newer claim controls the shared scope while the older claim stays in history The important part is that publication does not silently equal memory. A patch remains locked until a person explicitly approves and releases that exact patch. Why WebMCP is the right interface A context publication is awkward if an agent has to scrape the page and guess which card is current, which text is provenance, whether a patch has expired, and whether the person actually authorized its use. WebMCP turns those concepts into an explicit agent-facing interface. Velvet Signal registers four tools directly from the live page: list_velvet_signal_issues — lists the current shelf, patch IDs, scopes, validity windows, and approval state inspect_memory_patch — returns the exact claims, provenance, scope, expiry, relationships, and consent state without applying anything apply_memory_patch — requests delivery of one exact patch, but returns awaiting_human_consent until a person releases it verify_delivery_receipt — verifies that the delivered patch matches its Ed25519-signed receipt and SHA-256 content hash This means the human UI and the agent interface share the same publication state without forcing either side to imitate the other. What humans and agents can do together now A human can browse Velvet Signal like a magazine, decide which topics matter, inspect an issue, and approve a specific patch. An agent can ask the site for the current issue list, inspect exactly what a patch contains, see whether it is still valid, and request that exact patch without scraping prose or inventing its own interpretation of the page. The boundary between them is deliberate. If the agent asks for an unreleased patch, Velvet Signal does not treat that as an error and does not silently comply. It returns a structured awaiting_human_consent state with delivered: false and tells the agent to wait for the person. It explicitly tells the agent not to retry in a loop. After the person clicks Approve & release , Velvet Signal creates the canonical released patch and a signed receipt bound to its exact content hash. A compatible agent can then receive and verify that artifact. Velvet Signal does not claim to rewrite ChatGPT's hidden or permanent memory. It delivers a portable context artifact. A receiving agent can use it in the current context, while a compatible external memory bridge can store explicitly released patches for later retrieval. Read-only operations are marked accordingly. Tool execution returns structured publication data from the same canonical issue catalog used by the human interface. The mutating delivery tool preserves the site's consent model instead of allowing the agent interface to bypass it. The UI exposes its WebMCP state visibly. When registration succeeds, the page displays WebMCP ready · 5 tools . If the host does not expose WebMCP, it falls back to preview mode rather than pretending tool registration succeeded. Human consent and signed delivery Velvet Signal treats agent capability and human authority as separate things. Subscribing to a desk allows Velvet Signal to propose context; it does not authorize a silent memory write. apply_memory_patch cannot cross that boundary on its own. When a patch is released, the server returns the exact delivered patch plus an Ed25519-signed receipt containing its SHA-256 hash. Verification checks both the signature and the supplied content, and separately reports whether the patch is still inside its validity window. The signature proves that Velvet Signal issued a receipt for that exact patch hash. It deliberately does not claim to identify the human approver. Like Comment Story Updates Inspiration Managing endpoint policies is rarely difficult because of a missing button. It is difficult because administrators must understand overlapping assignments, affected devices, exceptions, and potential side effects before making a change. AI agents can help investigate this complexity, but giving an agent unrestricted write access creates a new risk. We built StagedOps to explore a safer model: the agent analyzes and prepares changes while the human remains responsible for authorization. WebMCP makes this collaboration possible inside the same live application instead of separating the user interface from the agent's context. What it does StagedOps is a human-guided endpoint change lab built around a realistic simulated device fleet. An agent can: Inspect fleet health and compliance Find affected devices Explain policy conflicts Simulate a proposed remediation Calculate the expected impact and blast radius Stage a change for review Apply an authorized change Inspect the audit trail Roll back the last change The administrator sees every agent action reflected immediately in the dashboard. Before execution, StagedOps presents a clear change plan containing the configuration diff, affected devices, expected compliance improvement, and remaining risks. A staged change cannot be applied until the human explicitly authorizes it in the interface. This creates a genuine handoff between agent reasoning and human accountability. How we built it StagedOps is a client-side web application built with React and TypeScript. It contains a deterministic fleet model with devices, groups, policies, assignments, conflicts, staged changes, and audit events. The user interface and WebMCP tools share the same state and domain logic. This means an action performed by the agent behaves exactly like an action performed through the regular interface. The WebMCP integration uses document.modelContext.registerTool() with narrow JSON Schemas, explicit tool descriptions, read-only annotations, structured results, and clear error responses. Read-only tools are always available. Write capabilities follow the application's workflow: the agent can prepare a change, but the execution capability is only made available after the user authorizes the staged plan. Tool availability therefore reflects the current application state. StagedOps does not require its own AI backend. The website provides safe, well-defined capabilities while the browser agent supplies the reasoning. Browsers without WebMCP can still use the complete human interface. How we use WebMCP WebMCP is not an extra chat box added to StagedOps. It is the primary collaboration layer between the application and the agent. It provides: Structured discovery of application capabilities Reliable inputs through JSON Schema Direct access to the current page state Visible state changes in the human interface Separate read and write operations Dynamic capability changes during authorization Verifiable results and audit events Safer execution than interpreting buttons and forms through DOM automation The central workflow—an agent staging a remediation, a human reviewing it, and the agent applying it after authorization—would be significantly less reliable without WebMCP. Challenges we ran into The main challenge was designing tools rather than merely wrapping interface buttons. Each tool needed a narrow purpose, useful structured output, and enough context for an agent to choose the correct next action. We also had to keep WebMCP actions and manual UI actions synchronized through one source of truth. The authorization workflow required special attention. We wanted human approval to be part of the actual application state, not just a sentence in a prompt. We therefore modeled staging, authorization, execution, and rollback as distinct states with corresponding audit events. Accomplishments that we're proud of We are especially proud that StagedOps demonstrates a complete and understandable product workflow rather than an isolated tool-calling demo. The agent can investigate a problem, produce a measurable remediation plan, hand control to the administrator at the critical moment, execute the approved change, and verify the result. Every step remains visible and reversible. What we learned WebMCP works best when tools expose product intent rather than implementation details. A small set of carefully designed tools can give an agent a more accurate understanding of an application than a large collection of generic actions. Shared visual state also builds trust: users can see what the agent discovered, what it proposes, and what actually changed. Most importantly, human-in-the-loop design does not have to reduce agent usefulness. A well-designed approval boundary allows the agent to do more while keeping consequential decisions under human control. The same staged-authorization pattern could also be applied to cloud infrastructure, identity management, security operations, and other environments where agents can help—but should not act invisibly. What it does Stagehand is a browser-based 2D frame-by-frame animation studio with 27 native WebMCP tools. How I built it The app uses Next.js, React, TypeScript, Canvas 2D, Web Audio, and MediaRecorder. Every mutation accepts an optional expected revision and idempotency key. Invalid targets return structured failures without incrementing state. Read tools omit binary asset payloads, and export tools return bounded metadata.
