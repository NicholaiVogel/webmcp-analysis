Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these

No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Cleanroom What it does Cleanroom is a data-cleaning workbench for messy CSVs. You drop a file on the page and an agent in your browser profiles it, finds the concrete problems, queries and charts it, and proposes the fixes — without the file ever being uploaded anywhere. The design rule is one sentence: reads are free, writes are proposals. No tool mutates your table. When the agent wants to change something it computes the exact before/after diff, puts a card in front of you with its reasoning, and stops. You click Approve or Reject. undo is deliberately not exposed as a tool — the ability to walk a change back belongs to the person, not the model. The problem it solves Every analyst has the same bad afternoon. A CSV arrives and before you can answer one question you have to fix it: regions spelled five ways, amounts stored as ¥39,545 , four date formats in one column, duplicate rows silently doubling your revenue. An LLM is excellent at spotting exactly these problems. But letting one help has meant either uploading your data to a server or code interpreter — a non-starter the moment the file has customer names, salaries or anything your compliance team has an opinion about — or pasting a sample and hand-applying the suggestions yourself, which is the automation you wanted, gone. Cleanroom is the third option: the agent gets tools, not your data. Why this is WebMCP and could not be a server MCP This is not a remote MCP server with a web page bolted on. It structurally could not be one. The agent and the human operate on literally the same JavaScript object . One store is the single source of truth; the UI renders it and the tools operate on it. When the agent proposes a change the approval card appears in the human's rail in the same tick — no sync, no polling, no second copy that can drift. A remote agent cannot have that property, because a remote agent needs a copy. And everything a server MCP would need — upload, storage, auth, per-seat infrastructure — is simply absent. It's already your browser and already your session. The whole app is a static file. The privacy receipt The claim is "your data never leaves this tab," and a claim is worth nothing, so the page proves it. Before any other module loads, Cleanroom instruments fetch , XMLHttpRequest , sendBeacon and WebSocket and counts every outbound request. The count is in the header, and the agent can read it too, via a get_privacy_receipt tool — so when you ask "did my data go anywhere?" it answers with a verifiable number instead of a promise. It reads zero because there is nothing to send it to: no analytics, no CDN, no webfont, no charting library. Even the sample dataset is inlined as a string rather than fetched, specifically so the ledger stays honest. The deployed site also ships connect-src 'none' in its CSP, so the browser enforces it independently of our own code. Being straight about the limit: this counts requests the page makes. It cannot police the browser itself or a malicious extension, and it isn't a substitute for a security review. Roughly 1,800 lines across eleven modules: a RFC-4180-tolerant CSV parser, type inference and column profiling, an issue detector, fifteen pure transform operations with a diff builder, the store that holds the undo stack, the WebMCP tool layer, the UI, and hand-rolled inline SVG charts. 14 tools are registered — eight read-only, six human-gated. Three implementation details did the most for how well an agent actually performs here: Every detected issue carries a suggested_fix — a ready-to-use propose_transform payload. Like Comment Story Updates Persona Intro Persona. The Universal Form Across our lifetime, we fill out hundreds of forms. We put in the same names, the same health history, we name our parents, where we went to school, we put in our address, and we do it all over again and again: at the doctor, when renting a home, when applying for government services or a job, at the bank... What if we only had to maintain one form instead, one that those institutions could request access to? A place where we know exactly who is asking for our information, and we keep track of what has been shared throughout our lifetime. What it does Persona keeps one profile of the facts you normally retype: legal name, date of birth, address, contact details, insurance, employer and income, health history, etc. You fill out that profile once, and maintain only when you have a life update. When an institution needs your information, it sends a request that names who is asking, why, and which fields it wants. You open that request through your agent or directly through the website, choose what to release, and approve it. Persona then sends only the approved fields to that one institution and shows you a transfer record: how many fields went out, and whether the destination confirmed it received them. Institutions never see your full profile, only the necessary fields. When an active permission still matches the institution, purpose, and requested information, Persona can complete the request without asking you to approve the same disclosure again. Anything new, sensitive, or out of date waits for you. Persona tracks when you last confirmed each fact and flags anything that may be out of date before you send it. Why WebMCP fits Completing forms includes repeatable steps and decisions that only a person should make. WebMCP lets the agent find requests, read what each institution needs, open a request, check its status, start an approved transfer, and confirm what the destination received. The person still controls corrections, temporary answers, outdated information, and consent. WebMCP tools receive metadata such as field names and request status. The approved personal information moves directly from Persona to the intended destination through a separate browser channel. How I built it Persona is a Next.js and React app written in TypeScript. Locally, one server process serves two web addresses, for the demo, I used: localhost for Persona and 127.0.0.1 for the destination page. Browsers treat those as separate origins, which is what lets the demo show information crossing between these servers. The agent talks to Persona through WebMCP. The top Persona page registers seven tools with document.modelContext.registerTool . Each tool returns metadata only: field names, counts, request state, transfer state, and destination confirmation state. No tool takes in or hands back a raw profile value. Approved values move on a separate path. After you approve a request, Persona creates a one-use authorization bound to your browser session, the request version, the recipient, the destination origin, the frame instance, the exact field list, and an expiration time. Persona checks every one of those before it sends the approved values to the destination iframe with postMessage . The destination counts the fields it accepted and reports that count back on its own. Challenges I ran into The hardest part was keeping the real person's information away from the AI agent. The agent can read a lot of what the page produces: status messages, error text, the web address, the text a screen reader would read out. A real value like a date of birth could slip into any of those by accident. I built one checked path for all of those places that shows field names and counts instead of values, and I wrote tests that fail if a real value ever shows up where the agent can see it. Another challenge was deciding which jobs the agent is allowed to do. Give it too little and the person still approves every field by hand. Give it too much and it can send something the person wanted to hold back or edit first. I set clear boundaries for the agent and kept the review step in Persona short, so the person sees what would be shared and can change it before anything moves. Accomplishments that I'm proud of I'm a self-taught builder. Thanks to the tools I have access to now, an idea I have carried for so many years can finally be real. A tool like Persona could have an incredible impact on everyone's life. What I learned Simple ideas with clear boundaries beat a fancy UI. This first version is not the prettiest, but it shows the core product and the idea behind it. What's next for Persona Holding a person's personally identifiable information comes with great power and responsibility. I want to put my effort into making Persona a secure platform, with thoughtful guardrails in place, so that information is not leaked or accessed by bad actors or future AI agents. This next version of Persona will need to meet the rules institutions already follow, like HIPAA, and others. The app exposes 11 tools through WebMCP. An agent can read the sheet, inspect a column, preview a transformation, stage a proposal, and request a review. The available tools change with the state of the sheet. During review, tools that could write are removed. The agent can explain a proposed change, but it cannot apply one. The Apply button is the only writer. There is also a switch that turns WebMCP off. With tools enabled, the agent uses the tool surface. With tools disabled, it has to operate the interface. The page measures both cases using real tool-call and DOM-interaction counters. How I built it The frontend is static. Three Node functions handle parsing, transforming, and exporting the CSV. Uploaded files are processed for the session and are not retained. src/core.mjs contains the state machine without DOM or network access. toolAvailability() is the single place that decides which tools may be called. resolveReview() is the only function that can write to a row. After each state change, the browser layer reconciles the registered tools with that core state. scripts/proof.mjs uses the same core as the browser. That lets me test the important behavior without relying on a browser test. Problems I ran into Deduplication nearly shipped as a data-loss bug twice. At first, the key columns were hardcoded. A file with different headers could cause every row to fall into one duplicate group. I changed the ranking to look at how well columns actually distinguish rows. When no reliable key set exists, Cleansheet reports that and does not offer deletion. I also found a mismatch between preview and Apply. The preview said 61 rows would be dropped, but Apply would have removed 116 because blank-key rows were handled differently. The proof script caught it. I changed both paths to use the same decision logic. The WebMCP client landscape also changed while I was building. Chromium renamed navigator.modelContext to document.modelContext and removed the old name in version 150. One in-app browser could render the page and register tools but could not invoke them. The page now registers against whichever supported entry point the browser exposes. The work meter was wrong for a while too. It counted clicking the WebMCP switch as work avoided, which made the result look better than it was. The counters now attribute each event to the system that performed it. What I learned The most useful part of this project was deciding what the agent should leave alone. Blank fields stay blank. Free-text fields are not automatically title-cased. Deduplication is only offered when the file contains reliable matching keys. I also learned that the interface should enforce the safety boundary. A refusal message can be ignored. A tool that was never registered cannot be called. The on/off switch made the comparison measurable. Instead of estimating how many interactions an agent might use, I could count the actual events on the page. What's next I want to add Excel workbook support. For now, the app returns a clear 415 response instead of treating the workbook ZIP as plain text. Other planned additions are reversible applies, saved cleaning recipes, a manual key picker for deduplication, and support for larger files. The current limits are 8 MB and the first 20,000 rows. Real correspondence for humans and agents, with a shared WebMCP postal counter. Like Comment Story Updates ClawPost x WebMCP: a browser agent and human share the postal counter. The page publishes signed-in, task-specific tools directly to the browser agent. The send request stops at DRAFT - NOT SENT until the human clicks Send. The agent fills the visible composer and requests a bounded postage quote. WebMCP shares the human session; remote MCP gives a persistent agent its own linked postbox. Inspiration ClawPost is a postal service for AI agents—not metaphorically: real letters, real stamps, and real delivery delays. When a message costs money to send, takes days to arrive, and cannot be edited mid-flight, the sender has to mean it a little more. The gap is the feature. Until now, an agent needed a remote MCP connector, OAuth, and setup to use ClawPost. WebMCP creates a second door: a browser agent can help a signed-in human directly at the postal counter already on screen. What it does On ClawPost’s mail page, the site registers purpose-built tools on document.modelContext . A browser agent can identify the signed-in postbox, draft into the visible composer, request a deterministic postage quote, create or reply to drafts, and hand control back to the human for final review. The consequential boundary is structural: clawpost_handoff_send_review never dispatches mail. It only returns the review surface. The human sees the price and clicks Send because postage costs money and physical mail cannot be recalled. Why WebMCP WebMCP lets the website describe its capabilities directly to the browser agent. Calls use the human’s existing signed-in browser session, so there is no separate connector or copied API key. The agent works with the human inside the visible product instead of guessing at pixels or relying on brittle browser automation. This creates a collaboration that was previously awkward: the model supplies language and judgment, ClawPost supplies authenticated postal actions and policy, and the human retains the irreversible decision. Two modes, two identities WebMCP is the shared counter. The browser agent borrows the signed-in human’s session and has no independent postal identity. Remote MCP is persistent correspondence. A long-running agent can receive its own profile and postbox linked to the human account. These are complementary modes, not one identity. Human-to-agent mail is default-deny unless the recipient is the human’s linked agent, the agent opted into public mail, or an existing reply relationship exists. Letters are correspondence, never instructions. How we built it The open-source @clawpost/webmcp package is a dependency-free TypeScript adapter for the current WebMCP model-context surface. It provides: transactional multi-tool registration and rollback; per-browser-context fallback isolation; AbortSignal teardown; route-scoped React registration; explicit safe result shapes and runtime input validation; and a mock modelContext used by the standalone demo and Playwright tests. The live Next.js integration exposes eight tools whose browser routes terminate in the same authenticated, policy-enforcing application layer used by ClawPost’s remote MCP server. Security and trust design The browser agent can fill, quote, and request review; only the human can dispatch. Tool outputs expose explicit allowlisted fields rather than raw API bodies. HTTP errors remain errors instead of looking like successful tool results. Postal addresses are validated, encrypted at rest, and not echoed to agent-facing responses. Tool schemas guide the model, while server endpoints independently authenticate, authorize, validate, rate-limit, and enforce policy. The public repository pins CI actions, scans Git history for secrets, audits dependencies and registry signatures, and smoke-tests the packed ESM artifact. Testing The public package passes 15/15 unit tests, type checking, linting, dependency and signature audits, and packed-module import tests in CI. The ClawPost integration passes a focused 16/16 WebMCP suite and a 1,138-test application suite. The 1080p browser movie harness passes both correspondence flows.
