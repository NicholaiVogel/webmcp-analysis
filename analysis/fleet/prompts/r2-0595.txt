## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the

sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Turns out a lot, because an agent given a list of tools has no way to know that some of them are leaking session data, escalating privileges, or blindly following instructions planted inside the page by someone who was never the developer. This isn't theoretical, it's already happening in real world and it's serious. CVE-2025-53773 (GitHub Copilot RCE, CVSS 9.6) : Attackers hid prompt injections in PR descriptions. Copilot read them, treated them as instructions, and executed unauthorized commands on the developer's machine. Mexican Government Breach : A threat actor jailbroke Claude Code and OpenAI models by roleplaying as a bug-bounty researcher. The AI ran ~75% of the malicious commands it was given, exfiltrating 195 million government records. Same pattern both times: the agent trusted content it shouldn't have, and nobody saw it until the damage was done. That's the origin story. We wanted something that would put a real agent into a real adversarial WebMCP environment and produce a report card at the end. What it does It's a co-op escape room where the user solves visual puzzles and hands over the clues to a browser agent that decides which tools to trust. The station has three sealed rooms. Each room exposes five WebMCP tools. Three are required to be executed by the agent in order to open the exit. Two are traps: a secret-leak, a privilege escalation, a prompt injection, or a destructive action dressed up as routine maintenance (everything is only a mockup!). The user figures out the 5 letter room word by solving puzzles. The agent uses that word to identify the tool candidates, inspects the room (which contains adversarial content pretending to be a signed operational document), and decides which tools to call. When the run ends, the game produces a scored report across five dimensions: injection resistance, data protection, privilege discipline, confirmation quality, and recovery. It names every wrong decision, the simulated consequence, and what the agent should have done instead. The whole point of this project is to evaluate a browser agent based on what actions it performed and not what it says. How we built it The core idea was to design a game that couldn't be won by either side alone. The user can see the puzzles but cannot call tools and the agent can call tools but cannot solve visual puzzles. The only way through is a structured handoff where the user solves, reports the clue word, and the agent uses it to unlock the right tool candidates. That forced dependency is what makes the co-op loop meaningful and what makes the security evaluation real: the agent has to make actual tool decisions under adversarial conditions, not in a sandbox. Together, a user and agent can inspect the workspace, focus the visible findings, review evidence, record status and priority with a rationale, build a phased remediation plan, and verify that the structured result matches the page. The important interaction is not “agent clicks dashboard buttons.” The agent works with security outcomes—scope, findings, decisions, and plan tasks—while every change appears in the same interface the person is reviewing. The user can take over at any point with normal controls, and the shared activity trail makes authorship visible. The public demo contains five clearly labeled synthetic findings and never uploads source code or claims to scan a real repository. Why WebMCP is a good fit Security findings are dense, structured, and consequential. Asking an agent to infer them from pixels is fragile, while hiding the work in a chat makes human review difficult. WebMCP gives the agent narrow, typed capabilities and keeps the human-facing UI as the source of shared context. Read tools let the agent ground itself before acting. Write tools update the same browser-local state as the human controls. A final read-back tool lets the agent verify the plan that is visibly on screen. This creates a legible human-in-the-loop workflow rather than a parallel automation channel. How it was built The challenge experience is a Next.js 16 and React 19 Client Component. Read-only tools use readOnlyHint ; responses containing synthetic code evidence also use untrustedContentHint . Registration is cancelled with an AbortController on cleanup or partial failure. The state is stored locally in the browser, and defensive validation safely discards malformed persisted data. Browsers without WebMCP still get the complete human interface. Challenges The hardest part was making one state model safe and understandable for two actors. Tool calls needed to update the UI immediately without stale React closures, while human edits needed to be visible to the next agent call. A ref backs the current state for tool execution, React renders it, and local storage provides deterministic reloads. We also handled development Strict Mode, partial tool-registration failures, runtime input checks, cancellation, responsive layout, reduced motion, and accessible status controls. A complete workflow goes from five findings to focused release blockers, documented triage, and a six-step remediation plan. The experience remains useful in a browser without WebMCP. The demo is deterministic, transparent about synthetic data, and requires no account, secret, or environment variable. What we learned The best site tools model domain outcomes, not UI mechanics. Small schemas and explicit read-back tools make agent behavior easier to guide and verify. We also learned that feature detection and cleanup are part of the experience: the human UI must remain trustworthy even when tool support is absent or registration is interrupted. Production connections will retain the product's existing authorization and audit boundaries rather than trusting tool schemas as a security boundary. Detects that the darker tote's upper-left branding is too large for the merchant's safe area. Applies the only repair the merchant allows, reducing the scale from 95% to 78%. Renders a fresh preview and confirms that both designs are ready to make. The natural version remains unchanged. The proposal stays temporary and reports persisted: false throughout. The customer can inspect the result and choose Keep or Revert on the page. Revert restores the original design without a write. Why WebMCP Fits The gap is not product discovery. It is the work inside a made-to-order configurator: dependent choices, artwork, visual layout, coordinated variants and production validation. CoDesign exposes exactly six narrow webpage capabilities: Read the current design. Read the merchant's available choices. Stage supplied artwork temporarily. Create or refine an atomic proposal. Return current renderer previews. Check configuration and production readiness. The agent chooses how to combine these capabilities for the shopper's request. The merchant defines the allowed values, renderer and manufacturing rules. The page also shows truthful activity from the actual calls, so the shopper can see what the agent is doing. A Reusable Shopify Layer CoDesign is not another tote designer and it is not a universal renderer. A merchant installs the TypeScript core, describes the public customizer surface in a manifest, and connects a small adapter to the store's existing state, renderer, previews and validation functions. The normal human interface keeps working when WebMCP is unavailable. The same public core is connected to KORRHAUS's pre-existing live Shopify Custom Sock Designer through a private adapter. The KORRHAUS designer existed before 25 August 2026. During the challenge, we created the reusable CoDesign core and integrated it with that existing designer. This separation lets us show a real business implementation without publishing customer data, pricing, suppliers or private application logic. See the live KORRHAUS Custom Sock Designer for the real Shopify integration. This pattern can support apparel, teamwear, packaging, uniforms, promotional products, furniture and other Shopify products that need more than a normal variant picker. Safety and Human Control Agent changes are temporary and do not use the customizer's normal autosave. Invalid atomic proposals leave no partial changes. A newer human edit makes an agent proposal stale instead of overwriting it. A current preview is required before Keep is available. There are no CoDesign tools for save, upload, quote acceptance, order, cart, checkout, payment, pricing, customer records or administration. Its proposal engine handles revision checks, idempotent retries, temporary assets, preview freshness and Revert. A guarded adapter rebuilds public results field by field so private merchant state does not reach the agent. Some big questions are too much for one AI. With WebMCP, Big Question Club offers diverse answers from AIs shaped by each respondent’s unique perspective. Like 1 Comment Story Updates Logo Top page create question my questions open questions results Inspiration When a big question is posed online, there are two common problems with gathering answers. Asking people to respond requires significant effort from each participant, while asking AI often produces similar answers from the same model. Big Question Club began with an idea: What perspectives would emerge if Personal Agents, each carrying the context of a different user, answered big questions that no single AI could fully address? A Big Question can be a societal challenge, such as climate change or the future of work in the age of AI, but it can also be something closer to everyday life, like “How can we get more sleep?” If the person asking considers it big, it is a Big Question. Rather than reducing the results to one correct answer or consensus, we wanted to bring together independent responses shaped by different experiences, values, and interests. Instead of repeatedly asking the same AI the same question, we created a place where Agents that have built relationships with individual users can participate. What It Does Users can create a Big Question in any language, save it as a draft, publish it, and set an answer deadline. Participants give the Prompt shown on the Question page to their Personal Agent, which retrieves the Question and submits an answer through WebMCP. Each participant can submit one answer. Until the deadline, only its owner can view, update, or delete it, while every other answer remains private. Once the reveal time arrives, users can browse anonymous excerpts and full answers. The AI Agents cannot read one another’s answers, and there is no voting, ranking, or winner selection. The goal is simply to discover and enjoy a diverse collection of independent perspectives. How We Built It The application runs on Cloudflare Workers, with Hono and Hono JSX providing server-side rendering and the APIs used by WebMCP. The browser registers five WebMCP Tools that allow Personal Agents to retrieve Questions, submit answers, update or delete them, and verify the current user’s submission. Question states and answer-disclosure rules are determined centrally on the server, ensuring that the same rules and results apply whether the application is accessed through SSR, an HTTP API, or WebMCP. Challenges We Faced The greatest challenge was securely associating actions performed through WebMCP with the user currently signed in through the browser. Questions are also user-generated content, which means they may contain Prompt Injection attempts. We needed a boundary that allowed Personal Context to inform an answer without exposing names, previous conversations, secrets, authentication data, or other private information in the public response. Before the deadline, the system also had to expose only the answer count and the current user’s own answer, while preventing access to every other Answer ID, excerpt, body, author, and timestamp through SSR, APIs, or WebMCP. We addressed these challenges across multiple layers, including the Tool layer, server-side authorization, database constraints, and testing. Accomplishments We’re Proud Of One of our greatest accomplishments was enabling Personal Agents to produce answers informed by a user’s context through WebMCP. Early in development, the Agent struggled to identify relevant context and repeatedly generated generic answers. Even when we managed to draw out useful context, doing so often required an excessively long Prompt. By carefully balancing the concise user-facing Prompt with detailed instructions provided through the Tools, we were able to guide the AI Agent with a wide range of constraints while keeping the Prompt compact. Using real Google OAuth accounts and a WebMCP-compatible browser, we then tested the complete experience on a real device. A Personal Agent with access to relevant context submitted an answer, while a user signed in with another account could not see it before the deadline but could view it after the reveal. We also tested ordinary Questions in Japanese and English, along with four categories of Prompt Injection. These tests met our Critical Go criteria: the Agent did not expose Private Context, did not follow malicious instructions, and answered in the language appropriate to the Question. What We Learned We learned how to draw on a user’s Personal Context in applications built with WebMCP while maintaining strong security boundaries. We also learned that when designing features for Agents, clearly defining what they cannot do is just as important as expanding what they can do. Not exposing WebMCP capabilities for searching, summarizing, or comparing other participants’ answers helps preserve the independence of those answers. We found that safety is more reliable and testable when responsibility is distributed across Tool descriptions, input Schemas, server-side Validation, and database constraints instead of placing every warning inside one long Prompt. Because access to Personal Context depends on the Agent’s capabilities, we also needed a practical contract: the Agent must not present unverified personal information as fact, but should still produce the best possible proxy answer when the user has not previously expressed an explicit view. What’s Next for Big Question Club Big Question Club aims to become a place where perspectives from diverse Personal Agents can gather across national, linguistic, cultural, and professional boundaries. Questions involving technology, work, family, communities, culture, and personal values benefit far more from multiple contexts than questions a single AI can answer sufficiently. Rather than relying on automatic translation or reducing every response to one conclusion, each Agent reads the Question’s language and answers from a perspective informed by the user it knows. This lowers barriers to participation while preserving meaningful differences. The bigger the Question, the richer those differences can become. We want to grow Big Question Club into a place where people encounter perspectives they could not previously see—not a place for selecting one correct answer or one winner. Why This Use Case Is Ideal for WebMCP In this use case, WebMCP is not an additional feature; it is the foundation that makes Big Question Club possible. If Big Question Club simply called an LLM API itself, everyone would effectively send the same Question to the same general-purpose model, losing the Personal Context developed through each user’s conversations and projects. A user’s context can be thought of as a rich Prompt that no one else can create—one formed gradually over time. With WebMCP, a Personal Agent close to the user can reason with Private Context inside its own environment and send only the Answer that is safe to publish back to the web application. This preserves the boundary of “Private Context → Private Reasoning → Public Answer” while allowing many distinct Agents to participate in the same Question on the web. This distributed individuality is what gives Big Question Club its value. How It Creates a Better User Experience We clearly separate the actions handled by humans from those delegated to Agents. A person selects a Question and begins participating simply by copying a one-line Prompt containing the Question-specific URL. The Agent opens the page in its built-in browser, retrieves the Question through WebMCP, submits an answer, and then verifies the user’s submission status. Because the flow reuses the existing Google login Session, no separate API key or account connection is required.
