It can't redline a clause. It definitely can't negotiate. It can answer questions about using DocuSign, so it can help me find the sign button. That's it. And whatever AI DocuSign ships next will live in their platform. Both parties can have DocuSign accounts, and maybe someday their agent helps both. But then it's one company's AI on both sides of an adversarial negotiation. It can't represent either party, and it doesn't know what each side's own agent already knows: your situation, your other clients, your limits, everything from every other conversation you've had with it. An agent that represents you can't be a feature of a platform. It has to be yours. So the idea: make the contract page neutral ground and let each party bring their own agent. Mine knows me. Theirs knows them. Neither one works for the platform. The page is just the table. WebMCP is what makes that work: the tools live in the page itself, so each side's agent can use them no matter which agent it is. ChatGPT on one side, Claude on the other, doesn't matter. What it does Mutual Assent AI is contract negotiation where agents do the haggling and humans do the signing. It works on any templated two-party agreement. The NDA is just the first template, and it's what the demo shows. An author creates an NDA from a template and sends a link. Each party gets their own capability link, their own seat at the table. The signer opens it and hands it to whatever agent they use. No briefing needed. His agent already knows he does prior work for other clients and won't go past a two year term, so it just confirms: protect the prior work, cap the term at two years? He says yes and it gets to work. None of that context ever touches my server. The agents negotiate term by term, in the document itself. Proposals show up as redlines with the reasoning attached. When an agent hits something above its pay grade, it stops and asks its human. When all terms are agreed, both humans review the final redline and sign. Agents can't sign. There's no signing tool for them to call, and that's on purpose. At the end you get an executed NDA plus a Certificate of Negotiation: a sealed, hash-verified record of which agent proposed what, under whose authority, and which human approved it. E-signature proves who signed. This also proves how the deal was reached. How I built it I built it with Sol 5.6 in Codex using loop engineering: worker models build against the spec in an automated loop, and a judge model checks their output and sends back anything that doesn't pass. I wrote the spec, watched the loops, and made the final calls on what shipped. It's hosted on Vercel, with Supabase behind it and Resend for the emails. Nano Banana helped with the graphics. WebMCP tools register directly in the page: read the deal, propose a term, respond to a proposal, escalate to the human, mark ready to sign. They register and unregister based on your role and the deal's phase, so an agent can't take an action the page doesn't offer its human. The design keeps the contract front and center. Proposals show up as redlines right in the clause, marked with which side's agent made them, so a human can glance at the page and see where the negotiation stands. Templates are just data, a list of terms with options, and the tools generate from the template. Swap in a different template, same engine negotiates a different contract. That's why the next document type is about an hour of work. Challenges The hard part wasn't building the negotiation, it was making WebMCP's benefits visible. They're structural: tools ship with the page, identity comes from the link, no platform sits between the parties. Like any great technology, it's invisible when done right. It just looks like a live web page. The nastiest bug was a security hole. Both parties originally shared one URL, which meant either side could propose, accept, and sign as the other, poisoning the audit trail the whole product depends on. I fixed it with independent 128-bit capability tokens per party, server-side role resolution on every request, and a rule that no response ever contains the other party's token. What I learned Agent identity is the interesting problem. Everything in the WebMCP showcase is one human plus their agent collaborating. Two parties is harder: the sides have opposing interests, there's no shared platform mediating, and when agents did part of the negotiating, you need a trustworthy record of who did what. That's what the certificate is for, and it turned out to matter more than I expected when I started. Also, WebMCP turns out to be a gift for legacy systems. My demo doesn't show this, but it was a lightbulb moment for me. In an old internal app, the business rules live in the pages and the only reliable way to do anything is through the UI. Building a normal MCP server means recreating those rules outside the app, basically a rewrite. With WebMCP you add tools to the pages you have, calling the same functions the buttons already call. Validation, permissions, sessions all come along for free. Systems that were never getting an API can go agent-ready from the front end alone. What's next More templates. Consulting SOWs are next because I'll use them myself. Then user testing with real freelancers and small firms sending real contracts, since that's where I'll find out what people actually trust an agent to negotiate. Once the idea is validated, I'll start charging for it. The long game is a neutral table for every two-party document: leases, offer letters, creator deals. Like 1 Comment Story Updates ProofPilot Dashboard WebMCP Agents Inspiration AI agents are getting really good at researching, analyzing information, and taking actions for us. But when the decision actually matters, there is a bigger question: How much authority should we give the agent? Imagine a team choosing an AI coding assistant, a vendor, or a software architecture. Getting an AI to say “I recommend option A” isn't particularly difficult anymore. The harder part is understanding why it recommends A, what evidence supports that recommendation, what evidence disagrees with it, what happens if our priorities change, and whether the agent should be allowed to change the decision at all. That was the idea behind ProofPilot: Decisions you can interrogate. We wanted to build a workspace where an AI agent could do meaningful work alongside a human without quietly becoming the person making the final decision. What we built ProofPilot is a human-controlled decision workspace where an AI agent can investigate, analyze, challenge, and propose — while the human stays in control of consequential decisions. The workflow is simple: Agent investigates → analyzes → proposes → human approves → state changes → audit trail. The human starts by defining the decision, the available options, and the criteria that matter. The agent can then work with that live decision through WebMCP. It can inspect the current decision state, search and add evidence, compare options, find contradictions, run sensitivity analysis, evaluate scenarios, and analyze risk. But there is an important boundary. If the agent wants to make a consequential change — for example, changing a criterion's weight or proposing the final decision — it cannot apply that change directly. Instead, ProofPilot turns it into a pending proposal. The human can inspect the proposal, approve it or reject it, and only after approval does the decision state change. The change is then recorded in the audit trail. This means the agent and the human are working on the same decision, rather than the human having to copy information between a chatbot and a separate decision-making tool. Why WebMCP WebMCP is a core part of ProofPilot because we wanted the agent to interact with the application's actual capabilities and live state, rather than simply reading a webpage or relying on browser automation. Instead of building a separate integration for one particular AI client, ProofPilot exposes its decision capabilities as WebMCP tools directly from the application. We currently expose 13 tools: get_decision_state get_evidence search_evidence add_evidence compare_options detect_contradictions run_sensitivity_analysis analyze_decision_risk evaluate_scenario propose_weight_change propose_decision request_human_review generate_decision_brief These tools cover investigation, evidence, analysis, governance, and output. Because they operate on the application's live decision state, a WebMCP-capable agent can investigate and reason about the same information that the human is looking at. The key idea is simple: Giving an agent access to a tool does not mean giving it authority to make the decision. Read and analysis tools can execute normally. Actions that can change consequential decision state become proposals and require explicit human approval. That's the boundary we wanted ProofPilot to enforce. How we built it The frontend is built with React, Vite, Tailwind CSS, Wouter, and TanStack Query. The backend uses Express, TypeScript, Zod, and Vitest. One thing we were careful about was not making the LLM the source of truth for the actual decision score. ProofPilot uses a deterministic multi-criteria decision engine for weighted scoring. The system also handles confidence, risk analysis, contradiction detection, evidence gaps, sensitivity analysis, and scenario evaluation. The agent is responsible for investigating and proposing. The application is responsible for calculating and enforcing the decision logic. WebMCP tools are registered in the frontend through the model context API. Each tool has its own description, input schema, and execution logic connected to the application's functionality. We also built a Developer view where the registered WebMCP tools and their schemas can be inspected. We wanted the agent-facing interface to be visible and understandable rather than something hidden behind the UI. Challenges The hardest part wasn't registering the WebMCP tools. It was deciding where the agent's authority should stop. We wanted the agent to be capable enough to do real work. A read-only chatbot wouldn't be very useful. At the same time, we didn't want an agent to quietly change weights or make a final decision just because it had access to the corresponding function. That led us to the proposal-based governance model. Consequential actions first become pending proposals. The human reviews them, approves or rejects them, and only then can the active decision state change. We also had to make the underlying decision engine predictable and explainable. Rather than letting an LLM invent a final score, we separated the agent's investigation from the application's deterministic analysis. It gives the agent a way to interact with the application's real functionality and state, while the application itself can decide what each tool is actually allowed to do. For us, the result is a different kind of agentic workflow: The agent does the investigation. The system does the analysis. The agent makes the proposal. The human makes the consequential decision. And the entire process is recorded. That's what ProofPilot is about. Not just getting an answer from an AI, but being able to question the reasoning behind the answer, understand the evidence, challenge the assumptions, and stay in control of what happens next. Like 1 Comment Story Updates Inspiration The web has become incredibly powerful, but most websites still expect humans to adapt to their interfaces. Every site has its own navigation, layout, sidebars, recommendations, ads, and information hierarchy. We wondered: what if the interface could adapt to what the user is actually trying to accomplish? That led to WebReform AI. Instead of building another AI that simply tells you what to click, we wanted to build an interface layer where an agent can understand a webpage and safely reshape it around the user's intent. WebMCP made this idea especially interesting because it gives agents a structured way to interact with real web capabilities instead of relying entirely on brittle browser automation. What it does WebReform AI lets users express what they want to accomplish on a webpage in natural language. An agent can use WebMCP tools to understand the current page and perform actions such as: Focusing on the most relevant content Hiding distracting elements Reorganizing information Creating a task-focused view Highlighting useful content Restoring the original interface The important part is that these operations happen on the real webpage. WebReform AI analyzes the page into a semantic representation, generates a structured transformation plan, validates it, and applies the changes through a deterministic transformation engine. Every transformation is designed to be reversible, so the user remains in control. How we built it WebReform AI is built as a Chrome extension with a lightweight, dependency-free architecture. The main pipeline is: User Intent → AI Planner → Semantic PageModel → Transformation DSL → Validator → Transformation Executor → Real DOM The extension analyzes webpages into a bounded semantic PageModel rather than sending an entire raw DOM to the model. The planner produces structured transformation operations instead of arbitrary JavaScript. We integrated WebMCP through document.modelContext.registerTool() and exposed structured tools for page analysis, querying, focusing, hiding, reorganizing, creating focused views, and restoring the original page. We also built a deterministic fallback planner so the core transformation system can still be demonstrated without depending entirely on an external AI model. Challenges we ran into The biggest challenge was making the concept work across different websites without building a separate integration for every website. Modern websites have constantly changing DOM structures, dynamically loaded content, nested layouts, and very different ways of representing similar information. A transformation that works perfectly on one page can easily break another. We therefore had to build around semantic page understanding rather than relying on fixed website-specific selectors. Another major challenge was making AI-generated actions safe. We didn't want the model generating arbitrary JavaScript and directly modifying the page. Instead, we created a strict transformation DSL with validation and a controlled executor. Getting WebMCP, the extension messaging layer, the semantic analyzer, the AI planner, and the real DOM to work together reliably was another significant part of the project. Accomplishments that we're proud of We're proud that WebReform AI goes beyond simply describing webpages or automating clicks. The agent can interact with structured WebMCP capabilities that cause actual, visible changes to the webpage. We built a complete pipeline from natural-language intent to semantic page understanding, structured planning, validation, real DOM transformation, and restoration. We're also particularly proud of the reversible transformation system. The user doesn't lose control of their original interface—changes can be rolled back and the original page can be restored. Most importantly, we built the system to be generic. The goal isn't to make one perfect GitHub demo; it's to create a reusable interface layer that can adapt different kinds of websites around different human goals. What we learned We learned that making an AI agent useful on the web isn't only about giving it more powerful actions. The representation of the webpage matters just as much. Giving the agent a bounded semantic representation makes it easier to reason about the page while also reducing the amount of raw information that needs to be processed. We also learned that safety and reversibility are essential when an agent is allowed to modify a user's interface. A powerful agent should not mean an uncontrollable interface. Most importantly, WebMCP changed how we think about agent-to-web interaction. Instead of treating websites as something an agent has to mechanically operate, structured web capabilities can give agents a much cleaner way to understand and interact with them. What's next for WebReform AI The hackathon version is only the beginning. Next, we want to make WebReform AI substantially more robust across complex websites and dynamic applications, improve its semantic understanding, and expand the types of transformations agents can safely perform. We also want to explore deeper agent-driven workflows where the interface continuously adapts as the user's goal changes, while still keeping the human in control. Longer term, the vision is bigger than a browser extension: WebReform AI could become an adaptive interface layer for the web, giving websites a way to expose structured capabilities to agents while allowing those agents to reshape the experience around individual human intent.
