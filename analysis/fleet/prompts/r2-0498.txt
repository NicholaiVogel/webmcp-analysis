# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

One React hook that gates risky AI tool calls behind human approval; with risk metadata, audit logging, and optional biometric verific. so agents handle the routine while humans approve what matters. Like Comment Story Updates Why this use case is a strong fit for WebMCP WebMCP lets any website register tools that AI agents can discover and invoke. Some runtimes already gate risky calls behind their own native approval UIs — ChatGPT's built-in browser shows a "Site tools" review panel, and the MCP-B Agent Chrome extension has per-tool approval settings. But most WebMCP clients don't provide any consent mechanism at all: every registered tool runs silently, whether it's a read-only health check or an irreversible production rollback. This project closes that gap at the package level. It adds a consent and annotation layer to @mcp-b/react-webmcp that any site using WebMCP can adopt — one hook, one provider — without every site inventing its own approval flow from scratch. How it creates a better user experience The consent layer is deliberately selective. Every tool registration carries structured metadata — scope, reversibility, risk level — and only actions flagged as requiring approval actually interrupt the user with a consent card. Low-risk reads (fetching service health, listing deployments) execute immediately and are logged silently in the audit trail. When a high-risk call like rollbackDeployment fires, the consent card shows exactly what's at stake: which systems are affected, whether the action is reversible, and what the agent wants to do. The audit log records every tool call — approved, denied, or auto-approved — so users can review the full history of what an agent did, not just the decisions they were asked to make. Cross-tab attention cues (a favicon badge and title blink) ensure pending approvals aren't missed when the user is in a different tab. For irreversible, high-risk operations, an optional WebAuthn gate (Touch ID, Windows Hello, or a hardware key) raises the bar beyond a simple click. What people and agents can do together that was difficult or impossible before Without a consent layer, site authors face a binary choice: either don't register destructive tools with WebMCP (safe but crippled), or register them and hope the runtime provides its own gate (flexible but risky on runtimes that don't). With useGuardedWebMCP, an agent can be handed genuinely powerful tools — rollbackDeployment, deleteUser, revokeAccess — with a human gating only the specific calls that matter. The agent handles the routine reads autonomously; the human approves or denies only the irreversible, high-impact actions. The result is collaborative agentic work where the human's attention is spent on the decisions that actually need judgment, not on rubber-stamping every API call. Brief implementation explanation The core mechanism is a React hook, useGuardedWebMCP, that wraps the existing useWebMCP from @mcp-b/react-webmcp — it composes rather than forks it. Each tool registration includes a ConsentMetadata object (scope, reversible, riskLevel, requiresApproval, optionally requireUserPresence). The hook maps this metadata to standard MCP ToolAnnotations (readOnlyHint, destructiveHint, idempotentHint) via toMcpAnnotations(), so native runtimes that do have their own gates receive real behavioral hints. When requiresApproval is true and no native gate is detected, the call suspends in a framework-agnostic ConsentBroker, which manages a queue of pending requests, session preapproval for reversible tools, timeout/expiry, and decision event streams. The React layer (ConsentBrokerProvider, useConsentBroker, usePendingConsentRequests) lets any component render approval UI against the broker's state. The on-page card includes an isTrusted guard to reject script-dispatched synthetic clicks — a best-effort defense, not a tamper-proof boundary, which is why hasNativeConsentGate() exists as an escape hatch to defer to real browser/OS-level permission prompts where available. Like 1 Comment Story Updates Inspiration Everyone has signed a contract they didn't fully read. The current answer is to paste it into a chat window, which gets you advice about the document: a paragraph you then retype into the file yourself. We wanted the agent working inside the contract, with one hard rule: it can suggest anything and change nothing. What it does Redline is a contract review workspace for humans and their agents. The agent reads the agreement clause by clause, flags risks with severity and plain-English consequences, compares terms against a market-standard playbook, and drafts replacement language. Every change it suggests arrives as a redline — old text struck through, proposed text in green, reasoning attached, that a human accepts or rejects. Accepting is the only action that alters the contract, and no agent can take it. Why this is a strong fit for WebMCP Contract review is stateful, multi-step, and unforgiving of hallucination, exactly where screen-scraping agents fail and where a typed tool surface shines. Three things WebMCP makes possible that a chat upload cannot: The output is document state, not prose. A suggestion is an object anchored to clause 6 with an accept button, an author, and a status, not a sentence to transcribe. The document is live. Tools read the contract as it currently stands, so "re-check the clauses I just changed" works. An upload is a snapshot that goes stale immediately. The safety is structural. Any AI with write access is safe only while it behaves. Here there is no mutation tool registered, and the server refuses any write tagged as an agent. "Please don't edit without asking" versus "there is no API to edit" is the whole difference. Typed schemas help too: flag_risky_clause requires a clause id that exists, so the agent cannot cite clause 27 of a 13-clause contract the way chat routinely does. How it creates a better user experience You stop being a transcription layer between a chat window and a document. The agent does the reading, the comparing, and the drafting; you do the deciding, on a screen that shows exactly what would change, why, and who suggested it. Rejections carry reasons the agent can read back, so the review gets sharper as it goes. And because the tool surface is public, you bring your own agent, the one that knows your last eight contracts, your rates, and your risk tolerance. A document dropped into a fresh chat window knows nothing about the person dropping it. What people and agents can do together that was difficult before Work on the same legal document simultaneously, with a guarantee specifying who can change it. Before WebMCP, an agent either had no access (advice you retype) or full access (write permission you have to trust). Redline is the third option: full analytical reach, zero write capability , enforced by which tools exist rather than by how well the model behaves. The phase model makes that dynamic. In analysis, the agent has 8 tools and literally cannot propose. In redlining, it has 12. Once the contract is executed, it has 5, all read-only — a signed contract cannot be marked up, and the agent's own capabilities reflect that the moment the phase changes. How we implemented WebMCP Twelve tools registered through document.modelContext.registerTool (with a navigator.modelContext fallback for older Chrome previews), unregistered via AbortSignal whenever the review phase changes: document.modelContext.registerTool({ name: "propose_edit", description: "Propose replacement text for a clause. This does NOT change the contract — it " + "creates a redline the human accepts or rejects.", inputSchema: { type: "object", properties: { clauseId: { type: "string" }, proposedText: { type: "string" }, rationale: { type: "string", maxLength: 400 }, }, required: ["clauseId", "proposedText", "rationale"], additionalProperties: false, }, execute: async (input) => { const { proposalId } = await api.propose(reviewId, { type: "replace", ...input, via: "agent" }); return `Proposal ${proposalId} created. Status: pending_human_approval — the contract ` + `is unchanged until a human accepts it. Use list_proposals for the outcome.`; }, }, { signal: phaseController.signal }); Two design decisions did most of the work: Errors are written to be recovered from. "Error: no clause c27. Valid ids are: c1, c2, …" tells the agent how to fix its own mistake instead of leaving it to guess. Descriptions are prompts. Each says when to call the tool and what to read first, which is why agents chain them sensibly without being told the order. Stack: Express + vanilla JS, server-sent events for live sync across everyone reviewing, Upstash Redis in production so reviews survive serverless cold starts. Challenges we ran into Making the guarantee real rather than rhetorical. It isn't enough to omit an accept tool; the server also rejects any resolve request tagged via: "agent" , and phase changes are human-only. Defense in depth, so the claim survives a hostile reading. Writing tool descriptions models actually follow. Early versions had agents proposing edits to clauses they hadn't read. Explicitly saying so in the description fixed it. The WebMCP surface is still moving between document.modelContext and the earlier navigator.modelContext , so registration goes through a small adapter. What we learned Capability design is the safety story. Every guardrail you can move from the prompt into the tool surface is a guarantee instead of a hope — and phase-scoped registration means the answer to "what can this agent do right now?" is a list you can print, not a judgment call. What's next for Redline Upload your own contract; a shared playbook per organization so proposals match house style; multi-party review where the other side's agent negotiates back; and export to tracked-changes DOCX so the redlines land in the tools lawyers already use. Human evidence. Agent structure. Shared control for safer electronics troubleshooting. Like Comment Story Updates Inspiration Hardware troubleshooting often becomes an unstructured stream of chat messages, photos, measurements, guesses, and repeated questions. The person can touch the physical system, but the agent can organize far more context than a person wants to track manually. BenchPilot gives both sides one inspectable workspace without letting the agent pretend it observed the hardware. What it does BenchPilot is a shared diagnostic canvas for safe low-voltage electronics. The human records symptoms and de-energized measurements. The app maps device topology, ranks evidence-linked hypotheses, maintains a safe test plan, preserves an append-only history, and produces a diagnostic report. In a WebMCP-capable browser, BenchPilot registers 12 typed tools over the same live case state. An agent can read the case and canvas, focus visible components, propose safe test steps, record only values explicitly supplied by the human, organize hypothesis updates, draft a cautious plan, and undo its own accepted changes. Every write is visible, attributed, reviewable, and reversible. Why WebMCP WebMCP is the product's collaboration layer, not a decorative integration. A troubleshooting agent needs structured topology, stable entity IDs, evidence provenance, unit and power-state validation, and a safe way to change the same workspace the person sees. Scraping page text cannot reliably provide those guarantees. BenchPilot's WebMCP tools use strict schemas and compact result envelopes. Human and agent actions share one command layer, so validation, revision checks, history, proposals, and undo behave identically from either interface. The site remains fully useful when WebMCP is unavailable. How we built it BenchPilot uses Vinext/Next.js App Router compatibility, React 19, TypeScript, Tailwind CSS, Zustand, Zod, @xyflow/react, Drizzle migrations, and Cloudflare D1 on OpenAI Sites. A deterministic NEMA 17 seed and rule engine make the flagship journey repeatable without an external LLM or physical hardware. Safety is enforced at the domain boundary: allowlisted test templates, strict type/unit pairs, disconnected-power requirements for resistance, session/case isolation, optimistic revision checks, rate limits, proposal review, actor attribution, and targeted undo. The release gate includes unit tests, WebMCP contract tests, production builds, and desktop/mobile browser journeys. Challenges The hardest design problem was balancing useful agent autonomy with human ownership of physical truth. BenchPilot lets the agent organize and propose while preventing it from silently inventing measurements or replacing canonical wiring. We also kept tool results compact while still returning revision, changed IDs, and a visible verification target. Accomplishments that we're proud of Twelve discoverable WebMCP tools operating on live shared state. A production-verified read, focus, proposal, human accept, and targeted undo loop. Deterministic D1-backed guest sessions with no login or paid API dependency. Unsafe energized resistance writes rejected at the API/domain boundary. Responsive manual fallback, accessible canvas list, and shareable report. Public MIT-licensed source with automated release gates. What we learned The best human-agent interfaces make authority boundaries visible. Structured tools help, but collaboration becomes trustworthy only when users can see why the agent acted, review the exact change, and reverse it without damaging human evidence. WebMCP rewards strong internal state design: stable IDs, provenance, revisions, and narrow commands improve both the agent experience and the manual product. What's next for BenchPilot Next steps include team case sharing, richer but still allowlisted device templates, instrument imports that preserve provenance, image-assisted label capture, and organization-level diagnostic playbooks. The safety boundary will remain deliberately narrow until each new procedure has explicit validation and review behavior.
