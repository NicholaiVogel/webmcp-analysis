# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Live-code together. Like Comment Story Updates The agent isn't controlling another Strudel session. It's playing in yours. Strudel WebMCP lets a browser agent join the exact live Strudel REPL a human is already performing with. You type, select code, and drag inline sliders as normal; the agent reads and edits that same unsaved CodeMirror document, evaluates its changes in the same running scheduler, and can record what the result sounds like — under a permission dial you own. No embedded LLM, no MCP server, no WebSocket bridge, no session ID. Live demo: https://strudel-webmcp.vercel.app Repository: https://github.com/alliecatowo/strudel-webmcp Why WebMCP Live coding is a bad fit for every earlier agent-integration shape, because the thing an agent needs to touch — the unsaved editor buffer, the exact cursor and selection, the inline slider values, the scheduler that is playing right now — exists in one browser tab and changes every second. A file-based or bridged integration has to keep a second copy of that in sync, and the copy is stale the moment a slider moves. WebMCP has no second copy. The tool call is a method on the same page, over the same document, in the same tab the human is looking at. Nothing to install, nothing to configure, no bridge that can drift. That makes something ordinary that was previously very hard: a human dragging a filter-cutoff slider with the mouse while an agent, in the same instant, rewrites a different line of the same unsaved buffer — and neither can clobber the other's most recent change. What the agent can do Thirteen tools, registered through document.modelContext.registerTool (src/webmcp/tools.ts), all backed by one adapter over the live (src/strudel/adapter.ts): Read live context: playback state, cursor, the human's current selection, what is sounding now, the agent mode, and any pending proposal, solo or recording. Read the exact current source, unsaved edits included, optionally by line range. Apply precise range edits, or replace the whole source — in review mode both become proposals. Evaluate through Strudel's own Update path (host.editor.evaluate()), so an agent edit becomes audible exactly the way a human's does, without stopping the clock; or solo just a range; or audition a pending proposal. Play, stop, and select-and-scroll to a range so the human sees what the agent means. Record the live output — master, or one .analyze("id") voice — and get dBFS and band analysis back, plus a playable take left in the page. List and extend the sound registry the running scheduler actually resolves s("...") against. Snapshot the source as a named version; switch the editor theme. Every mutating tool requires the codeHash from a previous read, computed fresh from the live document, and is refused with STALE_CODE if anything changed since — including a slider drag, because Strudel's slider widgets rewrite the source's numeric literals directly. The human's most recent edit always wins. The permission dial has three positions. Read: the agent can look, record and point, nothing else. Review: every edit arrives as a proposal with a diff the human auditions, accepts or discards — the source is unchanged until you say so. Live: edits apply directly. What people and agents can do together You keep performing. The agent reads the exact state you're in — down to the characters you have selected — and makes structural edits to the lines you didn't ask it to leave alone, then evaluates them into the same running pattern. Both of you act through the one Strudel instance; the audio reflects both immediately because neither owns a separate copy. In review mode the agent pitches instead of acting: "swap the kick for a different one" appears as a diff you can hear before it lands. And the agent has ears: ask "is the bass too loud?" and it records four seconds of the live output, answers from measured dBFS band energy, and suggests a concrete gain change. Who this is for Live coders, algorave performers, and people learning music through code — an audience for whom the editor buffer is the whole instrument, and for whom anything that isn't that exact buffer is useless mid-performance. Today, getting an agent into that instrument means standing up an MCP server, a bridge, and usually a modified frontend before a single note changes. That is real friction for a hobbyist or student and dead weight for a performer who wants a second pair of hands for eight bars. The claim is direct: browser-native creative tools shouldn't need to embed a model or ship a dedicated connector to be legible to an agent. The page can expose the instrument the human already has open. Strudel is the proof; the pattern — unsaved live document, precise agent edits, human-owned permission dial — applies to any browser-native creative or editing tool with real-time state worth exposing. Live coding is a specialized audience, but the engine underneath it is not niche: @strudel/core , the pattern engine every Strudel-based tool depends on, drew about 30,000 npm downloads in the 30 days ending August 29, 2026, and the wider @strudel/* family this project embeds — mini-notation, transpiler, WebAudio backend, CodeMirror integration, the REPL itself — adds roughly 76,000 more over the same window. The seam this project adds is generic to any of those downstream tools, not specific to this demo's drum pattern. Compared with the existing Strudel MCP bridges Existing Strudel MCP projects drive Strudel through an MCP server, a WebSocket or SSE bridge, and often a special frontend or a session ID copied between browser and agent. They work. The difference is what it takes to start: a connector, a bridge, session synchronization, and MCP configuration on one side; opening the page on the other. Here the page publishes its own controls, and the browser agent already accompanying the user joins the REPL with no external bridge, no session ID, no agent-specific server, and no second source of truth. Why this is different from "AI + music" Most "AI + music" demos are generation: describe a vibe, get a clip, no instrument in the loop. Most WebMCP demos so far are forms and dashboards. This is neither. It is a person and a browser agent performing through the same live instrument — one typing, selecting, dragging and listening; the other reading exact state, making precise edits, evaluating, and pointing back into the source. The review-mode propose/audition/accept loop goes further: the agent gets a way to pitch a change and let the human hear it before committing, which has no analogue in a form-filling demo. How it's built A static site — no server, no bridge — wrapping the official Strudel REPL and CodeMirror editor. The adapter is the only code that touches @strudel/repl internals; the tools, schemas, registration and error helpers sit above it. Unit tests (Vitest) cover hashing, position and offset conversion, edit validation, stale-hash rejection, source-size bounds and error normalization. Playwright end-to-end tests run against the real <strudel-editor> , including one that physically moves an inline slider and confirms a stale agent write against the pre-slider hash is rejected, and a modes suite covering read denials, the proposal lifecycle, solo, both recording modes, samples, snapshots and themes.
