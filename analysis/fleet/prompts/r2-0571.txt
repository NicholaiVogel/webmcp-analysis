## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that

A bouquet that was just invented in conversation isn't a product; twelve loose stem lines don't tell the merchant "this is one bouquet," and two bouquets in one cart are indistinguishable mush. Page-level WebMCP tools + a Cart Transform close exactly that gap: the agent works inside the store's own rules and inventory, hands off to Shopify's standard tools for checkout, and the human approves on the same page they're browsing. The UX win is concrete: what used to be a phone call, a LINE thread, and a free-text note field becomes a structured, priced, stock-checked bouquet built right on the product page — and one clean line in the cart instead of a dozen loose stems. The tools: bouquet_get_rules , bouquet_list_components , bouquet_create , bouquet_get_state , bouquet_add_items , bouquet_remove_items , bouquet_set_wrap , bouquet_set_note , bouquet_validate , bouquet_commit , bouquet_discard . How we built it Storefront (Theme App Extension, app embed): registers the 11 tools via document.modelContext.registerTool() — imperative API, top-level document (ChatGPT does not detect tools inside iframes). Tools and the composer panel mutate one shared draft store (persisted to localStorage), so agent calls re-render the panel instantly and human edits are readable back through bouquet_get_state , including a per-stem diff against what's already in the cart. Backend (React Router 7 + TypeScript on Fly.io, SQLite/Prisma): tools call the store's own domain via Shopify App Proxy ( /apps/composer/* ) — signed, same-origin, zero CORS. We verified WebMCP execute runs in the normal page context (not a sandbox), which makes this possible. The catalog endpoint reads the Admin GraphQL API, exposing composer.* metafields (role, color, meaning, occasions, pet-safe) as the agent-facing florist knowledge. Cart write: Shopify.actions.updateCart (Storefront Actions API) with hidden _bundle_id / _bundle_name line attributes, Ajax Cart API fallback — then navigate to /cart , which is always correct regardless of theme. Bundling (Shopify Function, Rust → WASM): groups cart lines by _bundle_id and emits a LinesMerge operation under a "Custom Bouquet" parent variant ( requiresComponents: true , price $0 — the merged line's price is the components' sum). Config lives in a metafield on the Cart Transform; missing config = no-op, so checkout never breaks. Fixture-tested with @shopify/shopify-function-test-helpers . Merchant setup: an idempotent admin setup page — one click seeds the demo florist (14 stems with metafields, 2 wraps, an arrangement fee, the merge parent kept UNLISTED: purchasable by direct variant reference for the merge, hidden from search), another activates the transform after shopify app deploy . Challenges we ran into Exposing WebMCP tools on a Shopify store. A Theme App Extension turned out to be the right surface: its app embed runs in the storefront's top-level document, which is where agents such as ChatGPT discover tools. We then named and scoped the bouquet_* tools so they complement — rather than overlap with — Shopify's standard storefront tools, which already handle search, cart and checkout. Staying in sync with the store's theme. Writing to the cart from a tool succeeded on the server, but the theme's cart icon and drawer did not reflect the change. The theme owns that state and only reacts to its own events, so we moved the commit path to Shopify's Storefront Actions API, which fires those events, and navigate to the cart page after a commit so the result is always visible. Co-composing with the agent, not through it. Our first approach drove every cart change through WebMCP alone, and the shopper ended up doing more work — each small tweak became another round of conversation. So we built the embedded composer: the agent's proposal lands in an on-page panel that the shopper can edit by hand, and the agent reads those edits back. Splitting the work this way is what finally made the experience feel good. Accomplishments that we're proud of The full loop works end-to-end from ChatGPT: conversation → draft → hand-edit → agent rebalance → commit → one merged bouquet line → checkout. The math is exact. Five lines (3 roses, 4 tulips, 2 eucalyptus, wrap, fee) merge into "Warm Birthday Bouquet — $39.50", precisely the sum of its parts; a second bouquet stays its own line, and checkout expands each into its recipe. A real shared workbench. Remove a stem by hand and the panel shows "Removed / Restore", the agent sees changes_since_cart , and "Update cart · +$3.00" shows the delta before you approve. It's a product, not a rig: idempotent one-page seed of the demo florist, graceful fallback in browsers without WebMCP, and a Rust Function with fixture tests. What we learned Chat is not always the best interface. When you build with WebMCP, it's tempting to think of every interaction as a conversation. But some things — like removing one stem or trying a different wrap — are faster to do by hand than to describe in words. To give customers a good experience, we learned to combine chat with other kinds of UI, rather than force everything through the agent. WebMCP tools have to coexist with other apps' tools. Publishing tools with WebMCP turned out to be easy. That is exactly why it needs care: on a platform like Shopify, our tools run on the same page as Shopify's own tools and, in the future, tools from other developers' apps. Tool names, descriptions and responsibilities need to be designed so that agents can tell them apart and use them together. Explaining this to customers is hard.

The human should report reality. The agent should handle the research and replanning. Both should work on the same live artifact. What it does daymaker.fun is a shared DayOps board for humans and agents. A person describes or edits the real needs of the day. The agent reads the same live state, researches appropriate places, and uses five focused WebMCP tools to structure the brief, add source-backed stops, update statuses, and reorder the proposed schedule. Each accepted change appears immediately in the interface. Fixed requirements stay visible, stale writes are rejected, and each revision can be shared with another device through a self-contained portable link. Unlike a traditional itinerary generator, daymaker.fun is designed for recovering a plan after reality changes. The person keeps direct control of requirements; the agent handles the tedious restructuring and research. Why WebMCP Without WebMCP, an agent can describe a revised day but cannot reliably read the current board or apply structured changes to the exact artifact the person is viewing. DOM clicking would be brittle, and the chat answer would drift away from the plan. daymaker.fun exposes five focused tools: get_mission_state reads the live brief, Needs, schedule, locks, sources, revision, and portable URL. update_day_context structures or updates the planning context. update_mission_stop changes an existing stop by stable ID. add_mission_stop adds one researched, source-backed stop. reorder_mission_stops reorders future stops while preserving locked commitments. These tools call the same typed domain transitions as the human UI. WebMCP is therefore the shared state and action layer that makes the product possible, not an add-on. How we built it daymaker.fun is a local-first React 19 and TypeScript application built with Vite. Mission is the single domain source of truth. Human controls and the WebMCP adapter dispatch actions through the same pure transition layer and store. Strict Zod schemas validate every tool input, and optimistic revision checks prevent stale agents from overwriting newer human changes. The top-level page registers five imperative tools through document.modelContext.registerTool(), feature-detects support, and owns their lifecycle with one abort signal. In browsers without WebMCP, the normal human interface remains usable. Each tab holds one mission in memory. Portable links serialize the validated mission as UTF-8 JSON, gzip it, encode it as unpadded base64url, and place it in the URL fragment. The recipient gets the exact point-in-time plan without an account or backend, and the fragment is not sent to the host. Codex helped build, debug, test, deploy, and document the application, including the cross-device portable-link hotfix. Challenges we ran into The hardest problem was choosing a small tool surface that gives the agent enough control without overlapping actions or hiding consequential changes. We also had to preserve fixed requirements, make agent changes immediately legible, reject stale revisions, and make long portable links reliable across devices and Safari. Accomplishments that we're proud of A complete human–agent loop from editable real-world Needs to a visible, source-backed schedule. Five narrow WebMCP tools backed by one shared domain model. Runtime validation, invariant checks, and revision-safe mutations. Cross-device plan snapshots without a backend. A responsive interface that remains useful without WebMCP. 102 unit/component tests and 8 Playwright end-to-end tests passing in the final preflight. What we learned Agent-native UX is not chat placed next to an app. It is a well-designed shared state model, a small set of precise actions, and immediate visual verification. The most useful WebMCP tools were the ones that cleanly connected reasoning to existing product behavior. What's next for daymaker.fun Consent-based live location, collaborative missions, weather and transit adapters, richer route evaluation, and reusable DayOps templates for families, events, road trips, and field teams. Like Comment Story Updates Inspiration AI agents and CRM automation are only as reliable as the data they act on. A CRM can appear operational while still containing missing ownership, stale deals, weak activity signals, or malformed fields that undermine routing, reporting, automation, and eventually agent behavior. CRM Health Doctor started as a deterministic CRM reliability diagnostic: evaluate known conditions, calculate health scores, and produce a prioritized review queue rather than asking an LLM to guess what is wrong. For the WebMCP Challenge, I wanted to explore a different question: What if an AI agent and a human reviewer could inspect the same deterministic CRM evidence directly on the page, without giving the agent write access to the CRM? That became the WebMCP human-agent co-review layer. What it does CRM Health Doctor evaluates a synthetic CRM dataset using explicit deterministic rules and produces: an overall CRM health score category-level scores a prioritized issue queue record-level evidence deterministic review guidance For the WebMCP Challenge, I extended that report with three browser-native, read-only tools: get_crm_health_summary list_priority_issues explain_priority_issue Instead of asking the agent to infer findings from visible HTML, the page exposes bounded structured state through WebMCP. The most important interaction is the synchronization between agent and human. When the agent prioritizes or explains a record such as C-008 , the corresponding row is automatically focused and highlighted on the report page. This creates an observable co-review workflow where the agent and the human are reviewing the same evidence. Who this is for The immediate audience is CRM administrators, RevOps teams, and automation/AI practitioners preparing CRM systems for agent-assisted operations. These teams already depend on ownership, activity, lifecycle, and pipeline data for routing, reporting, automation, and AI workflows; unreliable CRM state makes every downstream system less trustworthy. Why WebMCP changes the interaction Without this WebMCP layer, the human can inspect the report visually while an agent must either infer state from the rendered interface or receive a separate backend integration. Here, the page itself exposes a governed structured interface to the agent and simultaneously shows the human which evidence the agent selected. The browser becomes a shared review surface rather than two disconnected experiences. How I built it The diagnostic layer is implemented in Python using deterministic normalization, rules, scoring, prioritization, and remediation mappings. The generated report is a self-contained static HTML page containing safely embedded synthetic report state. The WebMCP browser layer is implemented in JavaScript and registers three tightly scoped read-only tools. Tool inputs are validated, outputs are bounded, and CRM-derived strings are treated as untrusted evidence rather than instructions. The architecture is deliberately simple: Synthetic CRM fixture → Deterministic Python diagnostic engine → Precomputed safe report state → Static HTML report → WebMCP tools → Agent + human co-review The public challenge deployment is hosted on Render as a static site. It requires no backend, database, authentication service, or live CRM connection. CRM Health Doctor existed before the WebMCP Challenge. The pre-existing work includes the deterministic diagnostic engine, scoring logic, fixtures, and original report UI. The challenge-period contribution adds: structured WebMCP-safe report state three browser-native read-only tools strict tool input contracts bounded structured outputs deterministic remediation mappings visible synchronization between agent selection and the report UI graceful behavior when WebMCP is unavailable public WebMCP deployment and validation The repository includes explicit provenance documentation, a challenge-delta document, and a tagged pre-WebMCP baseline. Challenges I ran into Making agent behavior observable Returning correct structured data was only part of the problem. I wanted the human reviewer to see exactly what the agent was reasoning about. That required connecting tool execution to deterministic visual behavior on the page, including scrolling, row focus, highlighting, and an accessible status update. Keeping the trust boundary narrow It would have been easy to turn the demo into an autonomous remediation agent. I intentionally did not. The public challenge version has: no live customer CRM data no CRM write path no raw HubSpot record IDs no network calls from the deployed page strict tool inputs bounded outputs deterministic remediation guidance explicit human-review requirements Working with an evolving WebMCP environment WebMCP is still evolving and browser behavior remains experimental. I validated the implementation through both ChatGPT's in-app browser and a WebMCP-enabled Chrome build. During testing, I encountered a difference in how the experimental Chrome build expected tool arguments to be passed. Rather than hiding that implementation detail, I documented the exact validated invocation flow in the public repository. Accomplishments I'm proud of I am most proud that the final challenge build is small, explainable, and observable. The project successfully demonstrates: three working WebMCP tools on a public deployment deterministic CRM health evaluation bounded structured agent access visible synchronization between agent actions and the report UI explicit human review instead of autonomous writes validation in both ChatGPT and WebMCP-enabled Chrome a reproducible synthetic demo with no customer data The strongest moment in the demo is simple: the agent identifies C-008 as a priority issue, and the same record is immediately highlighted for the human reviewer. That interaction is the core idea behind the project. What I learned The biggest lesson was that agent UX is not only about giving a model more context. A stronger pattern is: deterministic evidence → bounded tool → agent reasoning → visible human review WebMCP makes the browser itself a useful coordination surface between the agent and the user. Instead of asking an agent to scrape or visually interpret a dashboard, a page can expose exactly the structured state the agent is allowed to reason over while keeping consequential decisions under human control. I also learned that deterministic systems and AI agents do not need to compete with each other. Deterministic logic can establish the evidence and operating boundaries, while the agent provides interpretation and interaction on top of that trusted layer. What's next for CRM Health Doctor CRM Health Doctor is still a narrow prototype, not a production CRM auditing platform. The next logical direction is an agent-readiness layer for CRM operations . The broader workflow is: CRM evidence → Deterministic reliability assessment → Prioritized review queue → Governed agent analysis → Human approval → Controlled remediation Future work could include: broader diagnostic coverage authenticated multi-portal assessment historical reliability trends richer evidence sources configurable policy thresholds controlled remediation workflows with explicit approval gates integration with CRM and operational MCP tools after reliability checks pass The larger opportunity is not simply to let an AI agent operate a CRM. It is to help determine when the CRM data and operating controls are reliable enough for an agent to act safely in the first place .
