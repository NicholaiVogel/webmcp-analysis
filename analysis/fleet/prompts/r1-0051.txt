# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Working concepts: The six level source ecology A number of possible reporting outputs WebMCP research brief Save as you go: the research notebook The Atlas Relay map and evidence demo A thesis proof of concept - creating purpose built tools for the project The agent manages a live feed Inspiration My thesis research asks how ordinary commercial systems such as platforms, data services, advertising tools, registries, domains, hosting, payment services, and ecommerce infrastructure, might be co-opted to help information operations travel, scale, and persist. Public reporting often begins and ends with the most visible elements of these activities: a post, advert, account, headline, campaign, or a platform takedown. But the less visible enabling relationships remain scattered across datasets, platform disclosures, investigative reporting, archives, registries, and infrastructure records. I had already been imagining a larger online observatory project that could connect these traces, but the WebMCP Challenge supplied the missing interaction model. Rather than placing a chatbot beside a static dashboard, I wanted a researcher and an AI agent to work on the same inspectable terrain. That way the agent could search, organise, follow relationships, and surface current reporting, while the human researcher retained control over the provenance, uncertainty, and interpretation of evidence, and what deserved to enter the research record. This Hyphosphere project grew from that junction of needs and observations. It is a proof of concept for the thesis, as well as an experiment in research methods: a way to make the enabling ecommerce assemblage visible, without treating every single suggestive pattern as a conclusion. It helps to prevent premature closure on a messy and interesting problem. What it does Hyphosphere presents a human–agent research environment for tracing the commercial infrastructure behind online information operations. A visitor can: follow a reproducible investigation across cases, services, datasets, and reporting; distinguish verified, supported, inferred, and disputed relationships; inspect each research artifact’s provenance, original citation, reason for inclusion, and ecommerce-stack position; explore six layers of the enabling commercial stack; search curated records and linked source collections; ask an agent to assemble a compact, visible research brief; receive current, directly linked reporting through an agent-mediated signal feed; pause the feed, inspect citations, and retain selected leads; save discoveries and agent briefs in a device-local notebook; export retained research notes in Markdown; and preview possible outputs such as timelines, cluster summaries, micro case studies, and network visualisations. The project is deliberately not just a dashboard of troll posts. It begins with what is publicly visible, but then it helps the researcher examine the wider field of services, platforms, data, interfaces, and infrastructure that may enable an operation. How I built it The application was built as a responsive React research console and iterated with Codex. Its data model connects research objects through typed relationships, while preserving separate evidence states and six ecommerce-stack levels. A deterministic demonstration corpus supports the principal Atlas Relay investigation, so that judges can reproduce the same path. The page registers twelve WebMCP tools through document.modelContext.registerTool(...) . These tools can: follow a relationship; open supporting evidence; change the evidence threshold; reveal the source terrain; save a discovery; draft a possible research output; list source collections; search curated and linked sources; assemble a research brief; save an agent brief; publish current signals; and save an individual signal to the notebook. Human interface controls and WebMCP tools call on the same underlying React actions. This means an agent does not operate an invisible parallel system: its actions produce visible changes in the interface that the researcher can inspect and guide. The live signal feed is also agent-mediated rather than presented as an autonomous page crawler. A connected agent finds current material relevant to the research topic, as defined by the researcher, and supplies constrained, HTTPS-linked records through publish_signal_feed . The page then validates and displays those records with labels for source, relevance, information-warfare, and ecommerce-stack. The prototype notebook uses browser-local storage, with Markdown export providing a portable research trail. These are materials a researcher may later cite and repurpose in their work. Challenges I ran into The central challenge was balancing agent initiative with evidentiary caution. If automation silently produced a polished conclusion, it would undermine the very research method the application was intended to support. I therefore made agent actions visible, preserved citations, labelled with levels of uncertainty, and left final decisions about retention and interpretation with the researcher. A second challenge was how to use this to communicate a complex research idea to people who might be unfamiliar with information operations or online commercial infrastructure. The interface needed to explain the research problem, but without becoming an extended essay. Stable tabs, progressive disclosure, a guided investigation, interactive stack levels, and recurring visual cues helped make the concept navigable. I also encountered practical interaction problems: controls that changed content outside the viewport, competing menus, inactive-looking buttons, responsive layouts that concealed summoned material, and panels that obstructed the evidence beneath them. Repeated browser walkthroughs helped to consolidate the navigation and make interactions produce visible, comprehensible responses. Finally, WebMCP’s emerging implementation required careful debugging. Tool registration initially produced promise rejections until execution handlers were placed correctly inside each tool definition. The repaired implementation now exposes and executes all twelve tools. Accomplishments that I'm proud of Twelve functioning WebMCP tools operate a meaningful shared page state. Agent actions are visible and inspectable rather than hidden behind a chat response. A reproducible investigation, and an agent-mediated current-research path, co-exist without being confused. External leads retain direct citations, provenance, stack positions, and reasons for inclusion. The notebook brings discoveries, research briefs, and current signals together. The six-level stack model makes largely invisible enabling infrastructure easier to understand. The interface gives newcomers several ways to explore the topic, without forcing any pre-determined conclusions. The project has developed a distinctive visual identity based on branching relationships, layered infrastructure, and colourful research artifacts. What I learned Building the instrument has become part of the research discovery for the wider project. Designing the WebMCP actions revealed where agent assistance is genuinely valuable: searching, structuring, comparing, labelling, and bringing scattered material into a common field. It also clarified where human judgement must absolutely remain explicit: assessing provenance, interpreting relationships, recognising context, and deciding whether a lead actually belongs in the research record. I learned that an agent-native interface needs more than just exposed functions. 49 free browser audio tools, now agent-operable via WebMCP. One sentence; your agent does the work; audio never leaves your tab. Like Comment Story Updates Say it once — your agent trims, cleans, levels and exports across 49 browser tools, and the audio never leaves your tab. From the homepage, the agent calls list_tools and open_tool to route itself to the right tool. The agent drives the real waveform and controls while you watch — and nothing is uploaded. ihateaudio is 49 free audio tools that run entirely in your browser — trim, convert, clean, split, master — with no upload, no account, and no file‑size limit. For the WebMCP Challenge, we made every one of them operable by an AI agent, and wired them together so a single request runs as a complete, cross‑tool workflow. The problem Ask any AI agent to fix a recording and it hits a wall. It can't hear, it can't run a DSP chain, and its only real option is "upload it to some server." That's exactly what people with a private voice note, an unreleased track, or a confidential interview won't do. Audio has been a blind spot for agents. What it does Open ihateaudio.com in an agent browser and say: "I have a voice note — make it podcast‑ready." The agent: Calls list_tools , reads the site's catalog, and open_tool to open the trimmer. You choose the file — once. (A web page can't read your disk; that's the privacy guarantee, not a limitation.) set_trim keeps the part that matters, then send_to_tool hands the result to the silence remover — already loaded, no re‑upload. set_silence_removal tightens the pauses; every candidate cut is highlighted on the waveform. send_to_tool → normalizer, set_loudness_target({ platform: "podcast" }) . render_preview , then export_download when you say so. One sentence. Four tools. One click from you. The agent ran the pipeline; you kept the judgment. Why WebMCP is the right fit The agent stands on the same page as the person and uses tools the page itself defines. It gets back numbers — a duration, a list of quiet gaps, a slider value — never the audio. The samples never leave the tab. Generic pixel‑guessing automation can't drive a waveform with drag handles, or a threshold slider whose effect is a re‑scan of every sample. set_silence_removal({ threshold: -45, minimumGapSec: 0.5 }) does it exactly, and you watch it happen. What people and agents can do together that was impossible before A whole job, hands‑free after one click — trim, clean, level, export, across four tools, from one sentence. Human judgment stays human. Which pause matters, whether the voice still sounds natural — you decide, on the waveform. The agent measures and sets. Zero‑upload agent audio. Loudness, true peak, and quiet‑gap timing are computed in the tab and returned as numbers. An agent reasons about a recording it will never hold. One toolkit, learned once. Five base tools on every page plus one named action per tool. Learn the trimmer, you already know the equalizer. How we built it The site's 49 pages share one runtime, so the WebMCP layer lives in one place and every page inherits it: Host boundary detects document.modelContext (ChatGPT) and navigator.modelContext (Chrome), registers on every host found, and degrades to an ordinary editor when neither exists. Site tools on every page: list_tools (a catalog built at deploy time from each page's own manifest, so names can't drift) and open_tool (replies before navigating, so the host never loses a result). Base tools on every tool page: inspect, set format, render_preview , send_to_tool (a lossless hand‑off via IndexedDB), load_audio_from_url , and export_download . 33 named actions — set_trim , set_silence_removal , set_equalizer (8 bands), set_stems (4 stems), and more — each a real JSON schema. Agent values are clamped to the control's range and applied by firing the same events a human drag does, so live drawings and previews respond. 40 browser tests shim a WebMCP host on both document and navigator , call every action on every page, and assert the visible controls, reports, and the tool‑to‑tool hand‑off. Built with Astro + TypeScript, the Web Audio API, a WASM ffmpeg/AI tier, and IndexedDB, deployed on Cloudflare Workers. New for the Challenge (prior work vs. new work) ihateaudio existed before as a browser audio‑tool site.
