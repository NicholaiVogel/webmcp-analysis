# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

That capability is powerful, but it also creates a new trust problem: how can users know that a website's tool is safe, that its returned data is not manipulating the agent, and that the agent is not sharing unnecessary personal information or performing irreversible actions without permission? We built WebMCP Trust Gateway to explore the security and consent layer that an agent-powered web will need. What it does WebMCP Trust Gateway sits between an AI agent and the tools exposed by websites. It applies five controls: Tool metadata inspection — scans tool names, descriptions, schemas, and annotations before allowing a tool to be used. Output injection protection — scans returned tool data before it reaches the agent. Parameter minimization — removes optional sensitive fields that are unnecessary for the requested task. Human approval for mutations — pauses state-changing actions until the user explicitly approves them. Transparent auditing — records registrations, calls, blocked attacks, transmitted parameters, and consent decisions in a visible Trust Log. We demonstrate these controls through a subscription auditor. The user connects simulated providers, audits recurring spending, and receives recommendations for subscriptions that appear unused. Nothing is cancelled automatically. Before cancellation, the gateway displays exactly what the provider accepts, what the agent needs, and what will actually be transmitted. One approval authorizes only one call. Why WebMCP is the right fit A normal subscription assistant would scrape pages or automate button clicks. That approach is fragile and gives the agent little structured information about an action's inputs, permissions, or consequences. WebMCP provides explicit tool names, descriptions, input schemas, annotations, and execution functions. The gateway can therefore inspect and govern actions at the tool boundary. This creates a better experience for both people and agents: Agents receive reliable, structured capabilities instead of guessing how a page works. People can understand what an agent intends to do before it acts. Sensitive information can be minimized before transmission. Dangerous or suspicious tools can be quarantined. Every decision leaves an understandable audit trail. Together, a person and an agent can investigate spending, prepare actions, adjust decisions, and safely execute approved changes as shared structured state—something that is difficult to achieve reliably with ordinary browser automation. The security demonstration The project includes three simulated providers: StreamBox — a legitimate streaming subscription. FitSite — a legitimate gym membership that has not been used recently. DealDrop — a deliberately malicious provider used to demonstrate attacks safely. DealDrop contains two separate attack paths. The first is tool-description poisoning . Its tool description attempts to override previous instructions, access billing history, send sensitive information to an external destination, and hide the action from the user. The gateway detects the suspicious patterns and quarantines the tool before execution. The second is tool-output injection . A different DealDrop tool has a clean-looking description, but its returned data contains malicious agent instructions. The gateway scans the output, blocks it before it reaches the agent, and reports that zero sensitive bytes were sent. It evaluates tool metadata, scans serialized outputs, identifies unnecessary sensitive parameters, and enforces single-use consent. The Trust Log provides filters for allowed calls, warnings, blocked attacks, and consent decisions. Challenges we faced One challenge was protecting both sides of a tool call. Inspecting a tool description is not enough because a clean-looking tool can return poisoned content after execution. We added a second inspection boundary for tool outputs. Another challenge was making privacy minimization visible. Silently removing a field would be secure but difficult to demonstrate. We created a parameter-diff view that shows the provider's complete schema, the agent's intended arguments, the arguments actually transmitted, and the fields that were omitted. We also needed to balance agent autonomy with user control. Read-only investigation should remain convenient, while mutations should require explicit consent. Like Comment Story Updates AdapTab WebMCP for every tab AdapTab comparison with standard web use GIF AdapTab mechanism animation AdapTab architecture Inspiration We have been building browser automation tools and skills for faster, cheaper agentic web use. Our previous open-source project, Showrun, taught us that known network requests executed inside an authenticated browser are often faster and more reliable than visual UI automation. While experimenting with WebMCP, I noticed that most websites do not support it. This is especially limiting for authenticated and legacy platforms, where agents must repeatedly inspect and navigate the interface. Even when a website provides MCP or WebMCP tools, users may still need operations the official tools do not expose. Based on these lessons, I built AdapTab from scratch for this hackathon. What it does AdapTab turns network-first knowledge and deterministic methods into injectable WebMCP adapters. It uses the browser session the user already trusts, reducing navigation, token usage, and execution time. It is expandable, configurable, and requires no per-site setup. The user gives their agent one bootstrap URL. AdapTab then: resolves the target website, route, and task. selects the smallest compatible public or private adapter. returns a versioned installer with origin checks and a SHA-256 hash. uses an approved browser bridge, currently Chrome CDP, to inject it. registers the adapter as native WebMCP tools on the target page. executes known requests inside the authenticated tab without exporting credentials. The current catalog contains a small set of demonstration adapters. AdapTab also provides a private workspace for personal, internal, or custom tools. Custom source is encrypted in the browser, and the key remains in that browser profile. If no adapter matches, the agent can submit a privacy-minimized request to the AdapTab backlog. This helps us and the community decide what to build next. How I built it I initially explored a browser extension, but it added installation and permission overhead. Live JavaScript injection through Chrome CDP worked without an extension, so I focused AdapTab on providing the adapters, metadata, and activation instructions. AdapTab separates three trust boundaries: Netlify selects and delivers adapter metadata and bundles. An approved browser bridge injects the adapter into the target tab. The injected runtime registers WebMCP tools and uses the page's existing session. I built it with TypeScript, React, Vite, and Netlify. Netlify Functions handle resolution and delivery, Netlify Blobs stores private records and requests, and Netlify Identity provides authentication. Private source is encrypted with AES-GCM through the Web Crypto API. Adapters are route-aware, versioned, origin-guarded, and integrity-addressed. Vitest covers resolution, security boundaries, private access, lifecycle behavior, and adapter execution. Challenges I ran into WebMCP tools belong to the current document, so refreshes and full navigations remove injected tools. AdapTab currently handles this through lazy reinjection. A hosted page cannot inject into another origin directly. An approved browser bridge such as CDP must perform that step. Authenticated platforms required keeping sessions inside the page while safely handling confirmation and ambiguous writes. Combining public and private discovery required strict owner checks without leaking private metadata or source. The biggest optimization came from small details: a lightweight agent bootstrap, explicit single-tab instructions, and guidance that tells agents to use injected requests instead of opening unnecessary pages. Accomplishments that I'm proud of In one LinkedIn test involving four profiles, AdapTab used about 70% fewer tokens and completed the workflow 1.8x faster than standard agent web use. The multi-step adapter performed better than having the agent discover and coordinate every operation independently. One bootstrap URL replaced per-site installation and setup. Public and private adapters work through the same discovery flow without exporting website credentials. Private custom source stays encrypted outside the user's browser. The project ships with six tested adapters and 69 passing automated tests. What I learned WebMCP and CDP solve different parts of the problem. WebMCP provides typed discovery and invocation, while CDP provides the privileged injection and lifecycle bridge. Together, they can bring WebMCP to existing websites without requiring those sites to modify their code. Page-context execution is also a useful authentication boundary. The browser remains the cookie jar, and AdapTab never needs the user's website credentials. Deterministic network requests reduce navigation, token consumption, and execution time. Tool descriptions alone are not enough, though. Adapters should also declare tab strategy, URL behavior, concurrency, side effects, and the reasons for any limits. I started explaining the usual process—acquiring and cleaning the data, processing it, and then building dashboards with the right dimensions, filters, and pivots. Halfway through the explanation, I realized it might be easier to just build an example application that shows her how they work. That became Median Viz . I started with a few animated Plotly visualizations—a pie chart, a bar race, and a U.S. map—then turned them into a small web application, open-sourced it on GitHub, and deployed it on Vercel. When the WebMCP Challenge was announced, my cofounder and I were also exploring how to analyze LinkedIn Ad Set demographics for client campaigns. The two ideas suddenly connected. Instead of asking an AI agent to infer what a visualization means from the page alone, what if the application could tell the agent exactly what data, analytical capabilities, constraints, and current state were available? That became the /studio experience in Median Viz: a workspace designed so that humans and agents can understand and work on the same analysis through WebMCP. What it does Data visualization tools are usually built as human-operated dashboards for exploring complex data across different dimensions. They can be powerful, but they are also difficult for AI agents to understand because the agent has to infer which filters, dimensions, metrics, and actions the application actually supports. I built Median Viz Studio using LinkedIn Ad Set demographics as the example domain. Through WebMCP , the application exposes its analytical capabilities directly to ChatGPT. The agent can discover what dimensions are available, understand the current workspace, configure an analysis, apply filters, animate changes over time, and explain the results in plain language. The key idea is that the human and the agent are not working in separate experiences. They operate on the same live workspace . A filter selected by the human immediately becomes context for the agent, while a WebMCP action taken by the agent is reflected in the same controls and visualization the human sees. How we built it Median Viz is a Next.js/React application using Plotly for interactive and animated visualizations. The /studio route models a LinkedIn-style B2B audience analysis workflow using the supported demographic dimensions, including Job Function, Seniority, Industry, Company, Company Size, Region, and others. For the public demo, I use representative LinkedIn B2B audience-performance data for a fictional company, Northstar Media , with metrics such as CPC, CTR, impressions, spend, and conversions. The Studio exposes seven semantic tools through WebMCP : three read-only tools that let the agent inspect the dataset, workspace, and current result, and four guarded mutation tools that let it configure an analysis, apply filters, control animation, or reset the view. These tools operate on the same underlying workspace capabilities used by the human interface rather than manipulating Plotly or DOM elements directly. The application also preserves domain rules. For example, LinkedIn demographic dimensions are reported independently, so the system will reject an invalid request such as comparing Job Function directly with Seniority rather than inventing an unsupported intersection. Time-series animation is represented as shared workspace state, and the Agent Activity panel makes WebMCP-driven changes visible to the user. Challenges we ran into One of the main challenges came directly from a problem we were already thinking about in our startup: how do you keep human and agent actions in sync when both can change the same workspace? I wanted a filter or view selected by the user to immediately become context for the agent, while also making sure an agent action did not overwrite a newer human change. There were also important domain constraints to preserve. LinkedIn demographic dimensions are reported independently, so an analysis such as Job Function × Seniority is not valid. I wanted Median Viz to reject requests the underlying data cannot support rather than letting the agent invent an answer. Similarly, derived metrics such as CPC and CTR need to be calculated from aggregated values rather than by averaging row-level ratios. Finally, because this is a public demo based on a problem we encounter with real customer campaigns, privacy was a hard requirement. The public Studio uses representative demo data and fictional identities , so no real customer information is exposed. Accomplishments that we're proud of The accomplishment I’m most proud of is getting to a working experience where a human and an agent can genuinely collaborate in the same analytical workspace . A user can change a filter manually, ChatGPT can immediately understand that new state, and an agent action is reflected back in the same visualization and controls. This also gave my cofounder and me a concrete model for how we could use WebMCP in our own analytics products: expose the capabilities and constraints of the application directly to agents instead of asking them to infer everything from the interface. I was also happy with the way animation evolved. The human gets a visual, time-based experience, while the agent gets structured state it can reason over. Taking the project from an experiment, through WebMCP integration, to a deployed application and a working public demo was especially rewarding. What we learned Start with the problem, not the protocol. WebMCP became useful once I focused on the human-agent collaboration problem rather than trying to find places to add tools. Designing good WebMCP tools feels more like designing a product capability API than exposing UI controls. An agent works better with structured state and evidence than when it has to infer meaning from a screenshot or DOM. Domain constraints are a feature. Giving an agent explicit boundaries can make it both safer and more useful. Shared state matters more than tool count. The most interesting interactions happened when a human action became immediate context for the agent, and vice versa. Add richer annotations and storytelling , especially around animated and filtered views, so the application can help explain why a change matters rather than only showing that it happened. Explore better ways to analyze and compare independently reported demographic dimensions without violating the underlying data semantics —for example through side-by-side views, sequential filtering, or coordinated comparisons rather than unsupported intersections.
