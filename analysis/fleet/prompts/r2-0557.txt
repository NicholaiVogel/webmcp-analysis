# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A read-only, evidence-aware architecture map where people and AI agents inspect the same project graph, trace verified paths, expose bypasses, and preserve uncertainty through WebMCP. Like Comment Story Updates Project Atlas maps capabilities, consumers, backend owners, data, audit contracts, and observed evidence in one shared view. Inspiration Large software projects become difficult to understand and control when screens, routes, permissions, services, data stores, audit rules, and runtime behavior drift apart. Architecture diagrams become outdated, code searches show only fragments, and AI agents often have to reconstruct context from filenames, screen text, or incomplete documentation. This can hide duplicated rules, missing server-side checks, unknown consumers, and direct paths that bypass the approved architecture. We built DSH Project Atlas to give people and AI agents one shared, evidence-aware view of a project. What it does DSH Project Atlas is a read-only architecture Explorer. It represents a software project as a semantic graph containing user interfaces, browser routes, APIs, capabilities, backend handlers, owned data, audit contracts, and observed runtime evidence. A person explores the graph visually, while an AI agent uses five structured WebMCP tools to work with the same exact entities: inspect_project_overview ; focus_graph_entity ; trace_architecture_path ; list_security_findings ; compare_architecture_layers . Atlas distinguishes verified relationships from Needs Proof, Unknown, Blind Spot, and Review states. It also keeps architectural bypasses visible instead of hiding them. Unknown or fuzzy entity requests fail closed: Atlas rejects the request, changes nothing, and preserves the current selection. Atlas is deliberately not an IDE or production control plane. It cannot edit code, execute SQL, modify databases, grant permissions, start builds, deploy releases, or access production. It gives an agent architectural insight without mutation authority. How we built it The shared interface is built with React and TypeScript. The application registers five WebMCP tools through a literal document.modelContext.registerTool() boundary. Every tool has a closed JSON input schema, exact entity identifiers, bounded results, and no access to databases, credentials, shell commands, files, or deployment systems. The repository also contains a dependency-free, project-neutral semantic graph core. It provides: deterministic entity and relationship identifiers; canonical JSON output; SHA-256 integrity; source provenance; graph validation and querying; explicit uncertainty; conservative analyzers for JavaScript/React, Python, C#, SQL, and common service configuration. The public demonstration uses a fully synthetic project called Orchid Commerce. It contains no customer data, employee data, credentials, private source code, or production information. Orchid Commerce is a safe demonstration dataset, not a limitation of the engine. For a real project, the core can analyze an explicit allowlisted source manifest. A project-specific adapter can then add evidence-backed routes, APIs, capability IDs, ownership rules, policy contracts, audit relationships, and separately collected runtime observations. Each project receives its own isolated namespace, graph artifact, and WebMCP allowlist. Challenges we ran into The most difficult challenge was representing uncertainty honestly. A graph can look authoritative even when some relationships are inferred, incomplete, stale, or unsupported. We therefore made uncertainty a first-class part of the data model and interface. Another challenge was making the agent useful without giving it dangerous authority. The WebMCP tools can change only the shared visual focus, path, findings view, and architecture comparison. They cannot mutate the project. We also needed the human and agent experiences to remain synchronized. When the agent focuses an entity or traces a path, the person must see the same action immediately and be able to verify the conclusion. Finally, we needed to fit a large capability map into one understandable workspace while keeping bypasses, blind spots, evidence, ownership, and security boundaries visually distinct. Accomplishments that we're proud of We are proud that Project Atlas: gives people and AI agents one shared architecture map; exposes capability paths and ownership boundaries; visibly preserves bypasses and blind spots; rejects unknown entities without changing state; provides five bounded read-only WebMCP tools; includes a reusable project-neutral semantic graph core; supports deterministic and source-backed graph generation; separates expected architecture from observed runtime behavior; includes automated tests and a public-data boundary validator; can be adapted to real projects without exposing private data; is publicly released under the Apache License 2.0. What we learned AI collaboration becomes safer and more useful when context and authority are separated. An agent does not need direct access to source code, databases, or production to help investigate architecture. It needs stable identities, verified relationships, provenance, and honest uncertainty. We also learned that “not observed” must never be presented as “safe.” A candidate relationship must not become a verified architectural fact without reliable evidence. WebMCP makes this collaboration practical because the agent receives structured project context while the person sees the same entities and actions in the interface. What's next for DSH Project Atlas Our next steps are: a reusable loader for generated project graphs; project-specific semantic adapters; isolated multi-project namespaces; richer provenance and ownership views; controlled graph regeneration after verified code changes; additional framework analyzers; improved architecture history and comparison; integration with DSH development workflows. Developers and coding agents will continue to edit and test code in approved development environments. DSH or another controlled pipeline will regenerate the architectural evidence, and Atlas will display the resulting graph, deviations, bypasses, and unresolved unknowns. Atlas will remain a read-only Explorer. Future development will improve its ability to explain and verify real projects without turning it into a privileged command channel. WebMCP lets the agent operate the same durable case the person sees. Tools update the visible source board, diagnostic proposals, evidence graph, pending human attestations, plan, and history. Tool availability changes with case state, so the browser agent discovers only actions that are valid now. How it creates a better user experience Repair Relay does not return a wall of generic advice. It asks for the safest physical observation most likely to change the answer. Agent-relayed physical evidence is not silently accepted. It appears as a pending statement in the page. The person confirms it, corrects it, or rejects it. Only then can the evidence graph and plan change. Safety is enforced before diagnostics. Consequential changes remain pending. Approval waits for the trusted human control. The complete case survives refresh, every mutation has provenance, and Undo restores the previous snapshot. What people and agents can do together In the showcase case, the agent finds the live Dyson V8 record, checks CPSC, gathers current repair material, and proposes low-risk checks that distinguish filter restriction from airway blockage, battery weakness, and motor fault. The person reports that bright light is almost completely blocked by the dry removable pre-filter. The browser cannot obtain that physical result. Repair Relay holds the relayed statement until the person confirms it. The confirmed observation raises filter restriction, weakens competing causes, and stages a revised plan with assumptions and stop conditions. The agent can open the approval checkpoint but cannot approve. The call resolves only after the person acts in the page. Refresh preserves the case; Undo restores the previous snapshot. How WebMCP was implemented The TypeScript client uses imperative document.modelContext.registerTool registration with a compatibility path for the earlier preview surface. Eight focused tools share the same CaseService as the human interface: search_products open_repair_case get_case_context search_repair_sources add_observation propose_diagnostic_steps record_test_result approve_repair_plan Tools use closed JSON Schemas, runtime revalidation, compact structured output, typed failures, trust annotations, stable identifiers, idempotency keys, and AbortController lifecycle cleanup. Registration is state-driven. Mutating tools disappear while human evidence is pending, and plan approval exists only during the human-review state. The Cloudflare Worker and D1 database store guest sessions, canonical cases, source cache, idempotency responses, and append-only before/after events for real rollback. CPSC is treated as the official safety source. iFixit is clearly labelled as community repair guidance. Challenges The hardest boundary was distinguishing “the agent relayed what the person said” from “the person confirmed that physical observation.” Treating those as the same event made the agent appear successful while bypassing the product’s central trust claim. The final flow makes that transition explicit and blocks downstream mutation until it is resolved. The second challenge was keeping a rich evidence model understandable. The interface now prioritizes the active decision, describes evidence as relative support rather than calibrated confidence, and collapses secondary provenance and history details until needed. Release boundary The source repository is canonical Repair Relay. A public deployment URL and public narrated YouTube demo must be attached only after the exact release commit passes public-origin WebMCP, live-source, persistence, and refresh verification. The previous Label Relay deployment and video are not evidence for this product. Procedures that people and agents write, run and improve together. When a step no longer matches reality, the run records it, and the agent turns that into a fix. Like Comment Story Updates A procedure held as structured data. Each step carries an instruction, a check saying what proof looks like, and an optional condition. Inspiration We run a small agency and a SaaS product on our own infrastructure, so we live on written procedures. Onboarding a client, restoring a backup, rotating a credential. They get written once, carefully, and then the software underneath them changes. A tab is renamed, a field moves, a step becomes somebody else's job. Within months a good portion of the document is wrong. What struck us is why that happens. The moment you discover a procedure is wrong is precisely the moment you cannot fix it. You are mid-task, under time pressure, and correcting the document is somebody else's job. So you work around it silently and move on, and the next person hits the same wall. WebMCP suggested a way out. If the procedure is something an agent can read and edit while you are standing in front of it, then finding the error and fixing it stop being separate jobs. What it does Runbook Studio holds a procedure as structured data rather than prose. Every step has a title, an instruction, an optional check stating what proof looks like, and an optional condition that sends the run to a different step when something is already true. Because the steps are data, three things become possible in one place. Write it with the agent. Ask it to split a vague step, add checks, reorder, or add a condition, and watch the document rearrange. Every change the agent makes is marked on the page. Run it with the agent. A run walks the steps in order, honouring conditions. At each step you confirm the check, or you record a blocker saying what you found instead. Improve it from the run. The blocker is pinned to the step that failed. Afterwards, the agent reads it and amends that step to match reality. That loop is the point. Documentation that gets better every time somebody uses it. The model is domain-neutral. Three examples ship with the app: onboarding a client into a CRM, restoring a database from a backup, and a cooking recipe. How we built it Next.js and TypeScript, client-side state, no database, no authentication. Self-hosted on our own infrastructure behind nginx-proxy. The only server-side component is an optional route that proxies to an OpenAI-compatible endpoint for the built-in agent, rate limited and turn capped. 13 tools are registered on document.modelContext, covering the full lifecycle: reading the runbook, editing steps, setting checks and conditions, running, recording blockers, and turning blockers into amendments. Design decisions worth naming: Tool descriptions are the interface: they are written for a model to read, not a developer. We tested selection accuracy by giving the raw getTools() output to models with no other context and checking which tools they chose for real instructions. Descriptions were tuned until selection was reliable across independent models. The annotations are used properly. readOnlyHint on read tools, untrustedContentHint wherever user-written content flows back to the model. Chrome's budgets are respected: names under 30 characters, descriptions under 500, parameter descriptions under 150, and an output guard that trims oversized responses with a hint to use a narrower tool instead. Tools stay same-origin. exposedTo is unset, so no cross-origin frame can call them. Registration takes an AbortSignal: the execution-time signal is treated as optional, since it is not supplied in the Chrome build we tested against. The app also ships with its own agent, so it needs no browser flag and no ChatGPT to try. A built-in harness discovers the page's tools with getTools() and runs them with executeTool(), either manually or by sending a sentence to a model that chooses the tools itself. With no model configured, manual mode still works with zero setup. Verification was done against Chrome for Testing with native WebMCP, driving executeTool through Playwright and asserting on the resulting DOM, so no tool is reported working on the basis of code inspection alone. Challenges we ran into The API is new and the documentation moves. Older material uses navigator.modelContext; current Chrome uses document.modelContext. The API is undefined outside a secure context, which makes several obvious testing approaches fail silently rather than loudly. Steering a model reliably. Given only tool descriptions, a model would sometimes re-read every step, propose a change instead of making it, or keep editing after finishing. We fixed this with server-side guards rather than by making the tools more forgiving, because the tools have to behave correctly for any agent, not only ours. We could not test in ChatGPT's in-app browser. Our development machine is old enough that it is capped at a Chrome version predating WebMCP, and it cannot run the ChatGPT desktop app at all. So we never saw our own app inside the environment the judges will use. We compensated rather than hoped. Every tool was verified against Chrome for Testing 152 with native WebMCP, headless on our server, driving executeTool through Playwright and asserting on the resulting DOM. We separately tested tool-selection accuracy by giving the raw getTools() output to models with no other context, checking they chose the right tools for real instructions before we relied on the descriptions. The constraint turned out to be productive. Because we could not lean on ChatGPT, we built the app its own agent instead, which means anyone can try it with no browser flag, no desktop app and no API key. That is a better product than the one we would have shipped with easier hardware. Failure has to be as easy as success. If recording a blocker were harder than confirming a step, people would confirm and move on, and the loop would never close. Both controls sit together, same size, one click apart. Accomplishments that we're proud of The loop actually closes. A blocker recorded during a run becomes an amendment to the document, and the procedure is measurably more accurate afterwards than it was before somebody used it. Every tool was individually verified as firing and changing the page, not assumed correct from reading the code. The whole app is operable by keyboard, agent changes are announced through a live region, and it works with no browser flag at all. What we learned Naming is not cosmetic when a model is one of the readers. We renamed "branch" to "condition" throughout the interface, because "branch" is developer language borrowed from version control and told a first-time reader nothing. The tool kept its original name for the model. The two audiences did not want the same word. We also found that the work we did on semantic structure, accessible names and live-region announcements serves agent legibility as much as assistive technology. Both consume the page as structure rather than pixels. Building well for one turned out to be building well for the other. What's next for Runbook Studio Multiple checks per step, richer conditions, and shared runbooks so a blocker recorded by one person amends the procedure for everybody.
