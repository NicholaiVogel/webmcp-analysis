# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Not the keys. Browser agents can now understand and act inside live software. But there is a problem: once an agent enters a shared workspace, what is it actually allowed to touch? Presence is a trust layer for live human agent collaboration. Instead of giving an agent the same authority as the human, Presence gives it an explicit seat with bounded capabilities. Humans and agents can work in the same live state without silently sharing control. The idea Presence reduces agent collaboration to four primitives: Seat Where an agent may be present. Scope What the agent may do. Revision The state the agent observed before acting. Receipt What actually happened during the session. Together they create a simple rule: Presence does not trust an agent to respect a boundary. The application enforces the boundary. The demo The demo uses one responsive project with three live surfaces: Desktop is the reference. Tablet is the agent's seat. Mobile belongs to the human. A browser agent discovers Presence through WebMCP and asks to join as a responsive collaborator. The human can inspect the requested capabilities before admitting it. Once admitted, the agent can inspect the project and propose work for Tablet while the human continues editing Mobile. Then comes the important part. The agent attempts to modify Mobile. Presence rejects the operation because Mobile is outside its granted scope. The same agent can successfully propose a Tablet change because Tablet belongs to its seat. Its work remains provisional: even the agent itself cannot publish it. Only a human acceptance can make the proposal canonical. Presence also tracks the revision an agent observed. If the human changes the project while the agent is acting on older state, the stale operation is rejected before it can mutate canonical state . The human's newer work remains untouched. Every significant action is recorded in a structured audit trail. Accepted proposals produce a verification receipt containing the agent identity, granted scope, revisions, operations, protected surfaces, and before/after state fingerprints. Finally, the human can revoke the seat. The agent loses its authority while accepted work remains part of the project. Why WebMCP WebMCP makes the website itself an agent interface. Presence exposes semantic operations for discovering the workspace, inspecting available roles and constraints, requesting admission, inspecting project state, proposing scoped changes, reviewing state, and releasing a role. The agent does not need DOM coordinates or a scripted sequence of clicks. It can reason about the application's actual concepts while Presence remains responsible for authorization and state integrity. How I built it Presence is built with React, TypeScript, Vite, Zustand, and WebMCP. The UI and WebMCP tools operate on the same domain model. Mutations pass through the Presence domain layer, where admission, scope, ownership, and revision rules are enforced before canonical state can change. Agent proposals are provisional by default. Agents cannot publish their own work. Humans retain final authority. Presence also records structured audit events, computes deterministic state fingerprints, and generates verification receipts after accepted proposals so the collaboration can be inspected and verified after the fact. Challenges The hardest part was not exposing tools to an agent. It was deciding what should happen after an agent discovers those tools. A useful agent needs enough authority to accomplish real work, but giving it unrestricted access destroys the distinction between assistance and control. That led to the central design principle behind Presence: Authority should be explicit, scoped, temporary, and visible. Another challenge was concurrency. If an agent begins working from one revision while a human continues editing, the system cannot simply trust that the agent's eventual change is still safe. Presence revalidates the expected revision at mutation time and blocks stale operations before they reach canonical state. Presence explores what software could look like when agents are not merely chatbots beside an application, but participants inside it with boundaries the application can actually enforce. What's next The responsive workspace is one demonstration of the model, not the limit of it. Presence already applies the same collaboration model to a second application, demonstrating that the security model is not tied to responsive design. The same Seat, Scope, Revision, and Receipt primitives could govern agents working inside operations software, content systems, developer environments, and other collaborative applications. The larger idea is simple: As agents enter live software, applications need a way to decide not only what agents can understand, but where they may act. Canter is a hosting control plane built for AI agents to operate and humans to govern. Like Comment Story Updates Inspiration Agents can write code, but running what they build still pushes them toward either brittle shell access or infrastructure credentials that are far too powerful. We built Canter around a different boundary: the agent proposes an exact, inspectable Change; the human governs authority and high-impact execution; and the control plane produces evidence of what actually happened. What it does Canter is an agent-operated, human-governed hosting control plane. An agent can inspect a System, draft a Change, and review an immutable execution plan without receiving provider credentials. Every proposed deployment is bound to an exact digest, policy is explicit, apply can require human approval, and execution produces durable receipts. For the WebMCP Challenge, Canter makes that workflow discoverable directly from the website. The site advertises same-origin agent discovery, provides WebMCP read and review tools, and points capable agents to the authenticated remote MCP contract for durable work. Browser tools cannot borrow the human session to bypass approval: a sensitive Change still needs a focused, short-lived review capability and an explicit human action. How we built it The control plane is written in Go with PostgreSQL-backed durable state. The product interface uses Next.js, React, and TypeScript. A typed System contract compiles into a deterministic execution graph before provider adapters can mutate infrastructure. The same semantic objects—Systems, Changes, exact digests, policy envelopes, operations, and evidence—are shared across the CLI, HTTP API, remote MCP, and WebMCP surfaces. The website registers its WebMCP tools through document.modelContext.registerTool. The public /.well-known/canter and /llms.txt routes explain the same-origin device flow, API, and Streamable HTTP MCP endpoint without exposing provider details. Authenticated agent installations are durable and revocable, with independent inspect, draft, and apply authority. Challenges we ran into The hard part was not exposing more tools. It was preserving a trustworthy authority boundary across several interfaces. We had to ensure browser tools remain read and review only, authorization binds to one immutable digest, replayed or expired approval links fail safely, execution can resume after interruption, and a failed release does not silently become desired state. Accomplishments that we're proud of One small vocabulary across web, CLI, API, MCP, and WebMCP: inspect System, draft Change, review exact digest, authorize, apply, inspect evidence. Agents never receive provider credentials or arbitrary infrastructure access. Human approval can be mandatory for apply while agents retain useful inspect-and-draft authority. Execution is evidence-producing, restart-safe, and able to contain unhealthy releases. The browser experience makes policy, pending work, exact plans, and agent authority visible at a glance. What we learned Agent infrastructure needs fewer ambient privileges and better semantic contracts. WebMCP is most useful when it is an adapter into a governed product model, not a shortcut around it. The strongest interface is one where both the agent and the human can see the same proposed Change and the same evidence. What's next for canter.dev We want to expand the provider adapter set, improve focused Change review, add more public verification recipes, and make the same governed deployment loop available to more coding agents without weakening the human boundary.
