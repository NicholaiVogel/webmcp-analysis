Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality

But letting one help has meant either uploading your data to a server or code interpreter — a non-starter the moment the file has customer names, salaries or anything your compliance team has an opinion about — or pasting a sample and hand-applying the suggestions yourself, which is the automation you wanted, gone. Cleanroom is the third option: the agent gets tools, not your data. Why this is WebMCP and could not be a server MCP This is not a remote MCP server with a web page bolted on. It structurally could not be one. The agent and the human operate on literally the same JavaScript object . One store is the single source of truth; the UI renders it and the tools operate on it. When the agent proposes a change the approval card appears in the human's rail in the same tick — no sync, no polling, no second copy that can drift. A remote agent cannot have that property, because a remote agent needs a copy. And everything a server MCP would need — upload, storage, auth, per-seat infrastructure — is simply absent. It's already your browser and already your session. The whole app is a static file. The privacy receipt The claim is "your data never leaves this tab," and a claim is worth nothing, so the page proves it. Before any other module loads, Cleanroom instruments fetch , XMLHttpRequest , sendBeacon and WebSocket and counts every outbound request. The count is in the header, and the agent can read it too, via a get_privacy_receipt tool — so when you ask "did my data go anywhere?" it answers with a verifiable number instead of a promise. It reads zero because there is nothing to send it to: no analytics, no CDN, no webfont, no charting library. Even the sample dataset is inlined as a string rather than fetched, specifically so the ledger stays honest. The deployed site also ships connect-src 'none' in its CSP, so the browser enforces it independently of our own code. Being straight about the limit: this counts requests the page makes. It cannot police the browser itself or a malicious extension, and it isn't a substitute for a security review. How I built it Vanilla JavaScript, ES modules, no framework and no runtime dependencies — a dependency that phones home would undermine the entire premise. Roughly 1,800 lines across eleven modules: a RFC-4180-tolerant CSV parser, type inference and column profiling, an issue detector, fifteen pure transform operations with a diff builder, the store that holds the undo stack, the WebMCP tool layer, the UI, and hand-rolled inline SVG charts. 14 tools are registered — eight read-only, six human-gated. Three implementation details did the most for how well an agent actually performs here: Every detected issue carries a suggested_fix — a ready-to-use propose_transform payload. The agent goes from "what's wrong?" to a queued, reviewable fix in one hop instead of guessing at an API shape. This cut the model's flailing more than anything else I tried. Errors are instructions. Every failure names the valid inputs — Column "reigon" does not exist. Available columns: order_id, order_date, region, … — and is returned as text rather than thrown, so the agent reads the recovery path instead of hitting an opaque host error. Results are context-window shaped. Profiles and aggregates are summaries by construction; raw rows are returned only on request and hard-capped at 200. A 100,000-row file is fully workable without a single row entering the model's context. Challenges WebMCP's API moved while it was being standardised — some hosts expose navigator.modelContext , the current spec draft uses document.modelContext , and earlier builds took a batch provideContext({tools}) instead of per-tool registerTool . Rather than bet on one, the registration shim feature-detects all of them and reports which it found, so the header tells the user the truth about their browser instead of failing silently. Tool results are returned in three shapes at once — MCP-style content , structuredContent , and a bare data object — so the same tool behaves identically across hosts. The harder problem was designing the pause . An agent that has to stop and wait is easy to build badly: it either blocks forever or barrels ahead assuming approval. propose_transform returns pending_human_approval with an explicit next_step , and a separate await_decision tool blocks on the human with a timeout and tells the agent what to say if it expires. Getting the agent to reliably not assume its change landed was most of the prompt-shaped work. What I learned Designing tools for an agent is interface design, and the same thing that makes an API pleasant for a junior engineer — good names, errors that say what to do next, results scoped to what you actually need — is what makes a model competent instead of erratic. The suggested_fix field was the clearest demonstration: same model, same data, dramatically better behaviour, purely from shaping the return value. The second thing: an approval gate makes an agent more useful, not less. Once a change is reviewable before it lands, you stop hedging your prompts and start letting it try things. What's next Multi-table joins under the same proposal model — the agent proposes the key and shows you the match rate before committing. Recipe export — the change log is already ordered and structured; emit it as a runnable script so a one-off clean becomes a repeatable pipeline. Approval policies — "auto-approve whitespace fixes, always ask about dropped rows." The gate exists; this is a rule layer on top of it. Try it In ChatGPT's browser or Chrome with WebMCP enabled, open the page and ask: "What's wrong with this data? Don't change anything yet — just tell me what you'd fix and why." "Clean it up. Propose each fix separately so I can review them, and ask me before you touch anything that's a judgement call." In any other browser the built-in Agent Console calls the same registered tool objects a host calls — an inspector, not a mock — so you can see exactly what the agent sees. Architects speak in design intent. WebMCP lets AI understand, sketch, and act inside the same live architectural workspace. Like Comment Story Updates Inspiration Architectural AI tools are becoming very good at generating images, but the workflow is still surprisingly fragmented. An architect has design intent, preferences, project history, references, sketches, and ongoing conversations with an AI assistant. Yet when that architect opens an image-generation application, most of that context disappears. The agent is forced to operate a visual interface like a human — clicking buttons, navigating galleries, and guessing what is on screen. We wanted to explore a different model: What if the AI already understood the architect, and the architectural web application exposed its real design capabilities directly to that agent? That is the idea behind AIR with WebMCP. What it does AIR is an architectural AI design workspace for exploring, developing, and refining design ideas. With WebMCP, AIR becomes a workspace shared by both the architect and the AI agent. The agent can: read the current AIR canvas and design state structurally load an existing architectural design without navigating the Gallery UI explore multiple architectural directions using AIR's native Explore and Batch workflow mark an exact architectural region with AREA sketch a proposal directly onto AIR's canvas with Draw read an architect's modifications to that sketch back as structured design context execute an agreed design change through AIR's native generation workflow access higher-level workspace capabilities such as project context, moodboards, and video The important difference is that the agent does not imitate AIR's interface. The agent uses AIR's capabilities. Human + agent collaboration The goal is not full automation. Architectural design moves repeatedly between exploration and judgment. A typical AIR + WebMCP workflow can look like this: ChatGPT brings its ongoing understanding of the architect into the current AIR design. AIR explores several design possibilities. The architect chooses a direction. The agent identifies an exact architectural area worth developing. The agent sketches an idea on the shared canvas. The architect modifies that sketch directly. The agent reads the architect's change back as design context. Only after agreement does AIR execute the design. This creates a design conversation on the actual artifact instead of a sequence of disconnected prompts. Before WebMCP, an agent would need to infer screen state and reproduce human browser interactions. With WebMCP, the website exposes structured, high-level architectural actions directly. Why WebMCP AIR is a strong fit for WebMCP because architectural applications contain far more meaning than their visible controls expose. A button labelled "AREA" is not the important concept. The important concept is: "This is the exact architectural surface we are discussing." A Draw tool is not simply a drawing widget. It can become: a shared visual language between an architect and an agent. WebMCP lets AIR expose these meanings directly through structured capabilities rather than browser-coordinate automation. That makes agent interactions faster, more reliable, and — most importantly — more useful as part of an actual design process. How we built it AIR exposes high-level capabilities through document.modelContext.registerTool(...) . The WebMCP layer is intentionally thin. It does not recreate the product or automate the UI. Instead, WebMCP adapters connect directly to AIR's existing application state and native workflows. Examples include: air_get_canvas_context air_apply_canvas_markup air_execute_design_request air_execute_sketch_request air_finish_image workspace, moodboard, context, and video capabilities Canvas markup uses normalized image coordinates so AREA and Draw remain independent of screen size and browser layout. Shared markup also carries structured lineage. This allows AIR to distinguish an agent-authored sketch from a sketch that the architect subsequently modified, turning the visible canvas into two-way design context. The same principle applies throughout the integration: If AIR already has a native capability, WebMCP exposes that capability instead of teaching the agent how to click its UI. What was built during the WebMCP Challenge AIR 4.0 existed before the challenge. The work submitted here is the WebMCP extension developed after the challenge began on August 25, 2026. During the challenge period we added the agent-native capability layer, including structured canvas context, high-level design execution, direct asset intake, shared Draw and AREA markup, human-edit readback, workspace/context capabilities, and the human-agent collaborative workflow demonstrated in the video. The public repository contains a runnable open-source Challenge Edition focused specifically on this new WebMCP interaction model, while the live AIR application demonstrates the integration inside the full architectural product. Accomplishments The part we are most excited about is not that an agent can control another application. It is that the agent and architect can now communicate through the same design artifact. The architect can say less. The agent can understand more. And AIR becomes the place where that understanding becomes visible and actionable. FAIR understands design. AIR acts on it. What's next The next step is to connect this interaction model with deeper architectural research and reasoning. An agent should eventually be able to move naturally between precedent research, material and construction knowledge, project constraints, design exploration, visual markup, and final architectural decisions — while the architect remains in control of the moments that require judgment. We see WebMCP as an important foundation for that future: a web where professional applications are designed not only for people or agents, but for both working together. Governed agent Like Comment Story Updates Inspiration What it does How we built it Inspiration WebMCP gives agents structured access to websites. Causal Mission Gate explores the next question: what should happen when an agent can act, but the user still owns the authority to commit important effects? The project is built around one principle: Capability does not imply authority. A user should be able to state a simple objective without having to engineer every operational step. The system should manage complexity, autonomy, evidence, and escalation while preserving human sovereignty over critical effects. What it does Causal Mission Gate converts simple user intent into a governed mission. A request such as: Review this release and leave it ready if it is safe. becomes a structured mission contract with: objective and success conditions operating profile causal deliberation mode policy boundary reversibility requirements escalation conditions exact human authority for critical effects Routine preparation can run autonomously under management-by-exception. Critical effects cannot proceed until the human approves the exact current intent. That approval is: bound to the mission bound to the current version bound to the exact intent digest time-limited single-use After execution, the system produces an attributable receipt and verifies the audit chain. How we built it The application is built with Node.js, JavaScript, Docker, and a WebMCP tool surface registered through document.modelContext.registerTool() . The WebMCP surface exposes 11 bounded tools for: system inspection mission shaping governance queue inspection attention planning executive digest provisional observation governed execution evidence verification decision support Human authority actions are deliberately excluded from agent tools. Approval, rejection, delegation, ratification, and rollback remain human-controlled. Server-side governance validates: mission state expected version exact intent digest approval freshness one-time use policy constraints evidence integrity Challenges we ran into One important failure appeared during the final deployment test. A valid exact approval expired before execution. The server correctly denied the request, but the mission remained in an approved state without a clean path back to human review. Instead of bypassing the control, we treated the failure as a state-machine defect. The fix introduced an explicit transition: APPROVED → expiry → WAITING_APPROVAL The system now preserves the same exact intent, records the expiration event, and requires a new human authorization. A regression test was added, bringing the final suite to 90 passing tests. The lesson was: Expiry is not merely a denial condition; it is a state transition. Accomplishments that we're proud of 11 WebMCP tools with a deliberately bounded capability surface exact-effect human authorization one-time and expiring approvals management by exception causal deliberation attributable execution receipts hash-chained audit evidence 90 passing automated tests a public live deployment a complete flow from simple intent to governed PASS What we learned High autonomy does not require giving up human sovereignty. The important design boundary is not simply “human in the loop” versus “fully autonomous”. Authority, autonomy, visibility, and initiative can be separated. An agent can prepare, inspect, evaluate, and execute within policy while still being unable to manufacture the authority required for a critical effect. What's next The next step is extending the same governance model to longer-running autonomous missions where human decisions may be delayed. Reversible provisional effects, causal attention management, and durable evidence can allow useful work to continue without silently converting autonomy into authority. The broader goal is simple: The user states intent. The system manages complexity. Causality governs deliberation. Policy governs action. Evidence proves the result.
