# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

I wanted to paste a public GitHub repository into a simple application and get a useful map of what was actually inside it. I built the first version of RocketTurtle around that idea: help someone understand an unfamiliar repository before they start changing it. Then I wanted to improve it. Around that time, I found the Devpost WebMCP Hackathon and started learning what WebMCP actually was. That immediately made the original RocketTurtle idea more interesting. RocketTurtle already reduced how much of a repository a human needed to inspect. With WebMCP, I realized that the same idea can apply to an agent . Why must a coding agent read an entire repository before it can understand where to work? That question became the basis of the WebMCP version of RocketTurtle. What It Does RocketTurtle is a repository understanding layer for humans and AI agents. For the WebMCP extension, I went back to first principles and asked: If an agent is about to work inside an unfamiliar repository, what does it need to know before it writes code? That produced five steps: Understand → Locate → Inspect → Check → Verify Those five steps became five WebMCP tools. 1. analyze_repository — Understand Before anything else, the agent needs a map. This tool analyzes the repository structure, technologies, complexity, important files, risks, and supporting evidence. 2. map_change_surface — Locate Understanding the repository is not enough. If the goal is to change authentication, fix a feature, or update some behavior, the agent needs to know which parts of the repository are likely connected to that goal. This tool maps the requested change to likely relevant files and risky areas. 3. inspect_file_context — Inspect After finding a likely file, the agent needs focused information about that file. This tool inspects one selected text file and returns useful structural context without requiring the agent to explore the complete repository first. 4. validate_change_plan — Check Before an agent edits code, it can explain what it plans to change. RocketTurtle checks that plan against the available repository context and identifies risks or missing evidence. RocketTurtle does not make the code change. The coding agent remains responsible for the code. 5. get_verification_context — Verify Finally, the agent needs to know how the repository expects changes to be tested. This tool finds existing tests, scripts, build commands, lint commands, CI signals, and other useful verification context. Together, the five tools create one workflow: Understand → Locate → Inspect → Check → Verify The user provides the goal. RocketTurtle provides focused repository context. The coding agent uses that context before it acts. How I Built It I extended the existing RocketTurtle MVP instead of creating a separate application for the hackathon. The WebMCP layer reuses RocketTurtle's existing: GitHub access logic Repository analyzer Types API routes Vercel deployment I then added the logic required for the five WebMCP tools. Each tool has: A clear tool name A defined input schema An execution function Structured output Error handling Input and output boundaries The browser exposes these tools through document.modelContext , which lets a WebMCP-capable client discover and invoke RocketTurtle's repository tools. I kept one boundary throughout the project: RocketTurtle understands and checks. The coding agent writes the code. RocketTurtle does not: Generate code Edit repository files Create pull requests Replace the coding agent It gives the agent focused repository context before the agent starts changing code. Challenges I Faced One of the hardest problems was deciding how much repository information each tool must return. If RocketTurtle returns the entire repository, it defeats the purpose. If it returns too little information, the agent cannot make a useful decision. I had to design each tool around one specific question in the agent's workflow. Another major challenge was safety. Repository content is untrusted input. The WebMCP layer therefore needed boundaries around: Repository access File paths File types File sizes Tool inputs Tool outputs Testing also became much more important than I initially expected. Seeing five registered tools in a browser was not enough. I tested cases such as: Valid inputs Invalid inputs Missing repositories Missing files Unsupported files Large inputs Tool output limits Tool cleanup behavior The complete five-tool workflow I also had to make these changes without breaking the existing RocketTurtle application. That forced me to keep the WebMCP extension focused instead of redesigning the entire product around the hackathon. What I Learned The biggest thing I learned is that giving an AI agent more context is not always the answer. A better question is: What is the minimum useful context that the agent needs for its next decision? That idea now defines how I think about RocketTurtle. AI can generate code extremely quickly. But before generation comes understanding. An agent still needs to know: What already exists? Where does the relevant functionality live? What files are connected? What can break? Does the proposed plan make sense? How does this repository verify a change? WebMCP gave me a way to turn those questions into tools that an agent can call directly. WebMCP is solving the core problem by letting websites expose structured tools through window.modelContext , but developers currently have no tooling to answer basic questions: What does my website actually look like to an agent? Are my WebMCP tools exposing the right schemas? Where in the interaction flow is the agent getting confused or blocked? We built Deep Age to be the diagnostic tool we wished we had: a way to test-drive any website with an AI agent, record everything that happens step-by-step, and get practical fixes when things break. What it does Deep Age takes a URL and a task, such as "Search for a dark roast coffee and add 2 bags to cart" , runs an automated browser session, and records what happens. Inspects In-Page WebMCP Tools: Checks window.modelContext and document.modelContext to see what tools the site exposes, their parameter schemas, and whether they work. 5-Layer State Scrubber: Captures a snapshot at every step, including the URL and viewport, scroll position and modal state, the interactive accessibility tree with indexed element IDs ( e1 , e2 , etc.), active tools in memory, and network logs. Friction Triage & Code Fixes: If an agent gets stuck—for example, by finding a search API in network traffic with no corresponding WebMCP tool—Deep Age generates the TypeScript code needed to register that tool. State Transition Graph: Maps the paths and page states the agent navigated through, making it easier to understand where and why a workflow failed. SQLite Catalog Export: Pulls the site's discovered routes and entity data into a clean .sql script that can be queried locally. Security & PII Scanner: Checks page text for indirect prompt injection attempts and masks basic PII such as emails, card numbers, and phone numbers before sending data to the model. Remote MCP Server: Provides an SSE endpoint so you can run Deep Age directly from Cursor, Claude Desktop, or Antigravity. How we built it Backend & Browser Engine: Node.js, TypeScript, and Puppeteer / Cloudflare Browser Rendering ( @cloudflare/puppeteer ). We use Puppeteer to drive headless Chromium, intercept network requests, and inject scripts that monitor DOM mutations and read window.modelContext . Frontend Workbench: React 18, Vite, and Tailwind CSS. We built a custom visual timeline scrubber and state graph viewer to step through each action chronologically. MCP Integration: We implemented the Model Context Protocol (2024-11-05 spec) as an SSE endpoint hosted on a Cloudflare Worker, giving IDEs remote access to our analysis tools. Demo Store: A small reference storefront app with toggleable WebMCP tools, allowing us to test both broken and fully instrumented web flows. Challenges we ran into Windows MCP Subprocesses: Running local CLI MCP servers via npx gave us persistent headaches on Windows due to PowerShell pipe escaping and process isolation bugs. We ended up moving to a remote SSE server over HTTPS, which solved the issue across Windows, Mac, and Linux. Tracking Elements Across Re-renders: Modern single-page apps constantly remount DOM nodes, making raw CSS selectors and XPath unreliable between steps. We had to build a lightweight accessibility tree parser that assigns stable element references based on semantic roles. Capturing Tool State at the Right Time: Hooking into window.modelContext dynamically without racing the page's own script loading required careful timing in the browser injection lifecycle. Accomplishments that we're proud of The 5-layer state scrubber makes it genuinely easy to see the exact moment an agent got confused and what DOM elements it was looking at. The drop-in patch generator produces working document.modelContext.registerTool snippets based on observed network traffic. The remote SSE MCP server connects cleanly to Cursor and Claude Desktop on the first try without local dependency issues. The full end-to-end loop: Test the site, see the failure, copy the fix, and verify that it works. What we learned Without explicit tool contracts like WebMCP, agents are forced to guess based on visual coordinates and text scraping, which is brittle and slow. Debugging an agent failure requires seeing the intersection of the DOM, network requests, and in-memory tools at the exact moment of failure. A simple error log or screenshot isn't enough. Agent observability is fundamentally different from traditional web observability. You need to understand not just what the website did, but what the agent saw, what it believed it could do, and how the state changed between actions. What's next for Deep Age Browser Extension: A lightweight Chrome extension that lets you inspect WebMCP tools on any tab without running a separate headless browser session. CI/CD Integration: A GitHub Action to test-drive web apps on pull requests and catch regressions that break agent workflows before they hit production. Better Schema Inference: Improve the automatic patch generator to draft more accurate input schemas directly from recorded fetch/XHR payloads. Agent-updated shared state with the Core $295 recommendation and human authority preserved. DMXReady Agent Ready Websites are becoming interfaces for agents. DMXReady is the platform for building them. Inspiration Most AI website experiences still do one of two things: AI builds the page, or a chatbot is layered on top of it. We wanted to explore a different interaction model: What if the website itself could declare useful actions to an AI agent while the person stayed on the same page, saw the same changes, and remained in control? That is DMXReady Agent Ready. What it does The challenge app is a working Smart Website planning experience with five browser-native WebMCP tools. An agent can read the plan options, set the visitor's intent, compare the relevant choices, show the recommended path, and prepare that direction for human review. Every tool updates the same visible website the person is using. There is no hidden agent-only result that leaves the person guessing about what happened. Why WebMCP is a strong fit Without WebMCP, an agent has to infer what a page can do from labels, buttons, forms, and page structure. WebMCP lets the page explicitly describe useful capabilities with structured schemas. That improves the experience because: the agent can discover supported actions directly; tool inputs are structured and bounded; agent actions visibly update the same page; the person can continue from the result immediately; and the ordinary human experience still works when WebMCP is unavailable. What people and agents can do together A visitor can explain a real business goal in natural language and ask the agent to use the website. The agent can then inspect the options, apply the visitor's intent, compare the relevant plans, surface a recommendation, and prepare it for review while the visitor watches the website change. The person remains in the experience rather than being sent through a separate chatbot flow or opaque automation. Human authority by design The final tool stops at Prepared, not submitted . It does not create an order, charge money, provision a website, publish, change DNS, or approve launch. The challenge demonstrates useful agent capability while keeping consequential actions outside the reference flow. How we implemented WebMCP The live page registers five tools with document.modelContext.registerTool(...) . Each tool has an explicit JSON input schema and calls existing page-level application functions rather than creating a second agent-only implementation. Registrations use an AbortSignal , inputs are bounded and normalized, and the page fails closed if WebMCP is not available. The normal website remains functional in a standard browser. Challenge-period work DMXReady existed before August 25, 2026. The work being submitted for this challenge is the public Agent Ready WebMCP reference implementation and its human-agent interaction layer: tool registration, shared visible state, Activity evidence, tests, browser acceptance, and the submission proof package. The pre-existing private DMXReady platform is not being submitted as challenge-period work and is not required to run this reference app. What we learned WebMCP is most compelling when it makes the website itself easier for an agent to use, instead of turning the agent into a screen-scraper or creating an entirely separate chatbot experience. Our live Chrome acceptance exercised all five tools against the deployed page. The test journey resolved a plumbing-company scenario to the Core plan at $295/month, updated the visible state and Activity trail, and ended at prepared_not_submitted . Why it matters The web is becoming a place where people and agents will increasingly work together. Websites should be designed for that reality from the start. Build the website once. Let people and authorized agents use it together.
