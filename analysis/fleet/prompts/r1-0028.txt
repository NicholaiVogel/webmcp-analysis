# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Web2MCP watches the requests a site makes as you browse, learns their shape, and injects them into the page as native WebMCP tools an in-browser AI agent can call. Like Comment Story Updates chrome extension agent use case Inspiration WebMCP is a beautiful idea — websites exposing their functionality to AI agents as callable tools. But it has a chicken-and-egg problem: it only works if the website adds it. Almost no site has, and most never will. Meanwhile, every one of those sites is already making perfectly good API calls in your browser, right now, as you use it. So we asked: what if the agent didn't need the site's cooperation at all? What if you could just browse a site normally, and have its APIs turn into agent-callable tools automatically — learned from the traffic the site already produces? What it does Web2MCP is a browser extension that records the API calls a website makes while you browse and injects them as native WebMCP tools an in-browser AI agent can call. Records every JSON API a page calls — its own backend and third-party APIs — while filtering out static assets and trackers. Aggregates requests into endpoint templates (/users/123 → /users/{id}), inferring JSON Schemas and required fields from what it observes. Injects each endpoint as a WebMCP tool via document.modelContext. Calls replay from the page's own context, so cookies and captured auth headers just work. Pools by website, so subdomains and pages share one tool set; shows a live tool count on the toolbar badge; lists tools in a popup (including the site's own first-party WebMCP tools); and lets you disable injection per site. No config, no schemas to write, no per-endpoint wiring. How we built it WXT + TypeScript + React for a Manifest V3 extension. A MAIN-world content script patches window.fetch and XMLHttpRequest to observe traffic and to register/replay tools; an ISOLATED-world bridge relays messages to a background service worker that does all aggregation, schema inference, and local storage. Injection uses the browser's native WebMCP registerTool API; replay uses the saved native fetch so tool calls never re-trigger recording. The "brain" — URL templating, schema inference, tool naming, aggregation, filtering — is pure, dependency-free modules covered by vitest (60+ tests). A landing page and privacy policy shipped on Cloudflare Pages. Challenges we ran into We tested on real sites, and the real world fought back — which turned out to be the most valuable part. Anti-automation is everywhere. We hit three distinct walls: Linear injects auth in a service worker below the page's fetch (invisible to us → 401); X and GitHub use one-time nonces (x-client-transaction-id, x-fetch-nonce) that expire after a single use (→ 422); Xiaohongshu signs the request body client-side (x-s), so changing any argument breaks the signature (→ 406). We had to map — and honestly document — exactly where record-and-replay can and can't work. Agents under-supply parameters. An LLM calling a search tool would omit sortBy or invent a sessionId, getting empty results. The fix: surface the real recorded request body as an example and merge the agent's fields over it, filling in what it left out. The little things: a signal destructuring crash that broke every tool call, extension-context invalidation after reloads, JSON responses truncated mid-object, and getting WebMCP itself enabled in a custom Chromium browser (via a Finch/variations study). Accomplishments that we're proud of It's genuinely zero-config. Browse a site and its tools appear — with a badge counting them and a popup listing them. It works end-to-end on real sites. We watched an agent successfully call a live government job-search API and read GitHub data through tools Web2MCP recorded — cross-domain, authenticated, no keys. It's honest. We built the "Works great / Can't replay" boundary into the product and the site instead of overselling. It's smart about the data it already has — auto-filling session tokens and merging partial request bodies from real recordings so agents stop failing on missing fields. Users stay in control — per-site disable, one-click clear, everything stored locally and nothing leaves the device. What we learned The real boundary of record-and-replay: it works whenever the request's content isn't itself part of authentication — cookie-authed apps, static tokens, read endpoints, your own products. It can't beat mechanisms designed to stop exactly this (SW-injected auth, one-time tokens, body signatures). Knowing that boundary precisely is more useful than pretending it doesn't exist. Agents need examples, not just schemas. A JSON Schema tells a model the shape; a real recorded request tells it what actually works. Honesty is a feature. Being upfront about limits made the product more trustworthy, not less. What's next for Web2MCP Chrome Web Store release and broader reach as WebMCP ships in stable browsers. Smarter body handling — deep merge, and richer per-parameter examples. First-party passthrough — surface and manage a site's own WebMCP tools alongside recorded ones. An adapter path for hardened sites — optionally invoke the site's own signing/request code (or fall back to driving the real UI) for signature- and nonce-protected APIs. Sharing & sync — export a site's recorded tool set so a team can reuse it. We ended up using tonejs-instruments for the melodic instruments and the TR-808 Fischer collection for drums. Another challenge was sample coverage. We didn't want to ship a separate audio file for every possible musical note, but we also didn't want aggressive pitch shifting to make the instruments sound unnatural. Accomplishments that we're proud of The biggest one is simply getting the idea to work end to end. What we learned One of the biggest things we learned is that AI doesn't need to generate the final media itself to be really useful in a creative workflow. The AI can reason about those building blocks and use them to construct something, then keep changing that same composition over time. We also learned that WebMCP feels much more useful when the agent is operating a real application rather than just returning text. Seeing the agent add a track, place clips, change sounds, and react to a human edit made the difference much clearer to us. It feels less like asking an AI for an answer and more like working with another person in the same creative space. We'd like to expand the sound library with more carefully selected instruments and sounds, and make it easier to browse and audition them. We also want to improve the composition side so the AI can handle more complex musical structure while still keeping every part editable. Another natural direction is better project management and sharing, so people can move their compositions between devices and continue working on them without relying only on local browser storage or manually downloading files. And beyond that, we'd like to explore more ways for the AI and the human to work together in the same timeline, with more precise editing and better control over arrangements. PantryPilot instead publishes a typed contract: 8 tools registered on document.modelContext with JSON Schema inputs and structured JSON results, exactly per the WebMCP spec. \n\n What humans and agents can do together \n\n \n Humans: add groceries by hand, swap a dinner when the mood strikes, check off shopping items in the store. \n Agents: read the pantry, triage what is about to spoil, plan 7 dinners expiry-first, derive an aisle-consolidated shopping list, log groceries and cooked meals. \n Together: the ask that used to mean a hundred UI turns - plan my week around what is expiring, then tell me what to buy - becomes one tool call, while the human keeps every final decision. \n \n\n How WebMCP is implemented \n\n js/webmcp.js defines the tool table and calls document.modelContext.registerTool({name, description, inputSchema, execute}) for each of: get_pantry, add_pantry_items, consume_pantry_items, find_recipes, plan_week, get_plan, get_shopping_list, suggest_use_it_up. The exact same implementations also power the built-in Agent Console, so anyone can exercise the agent surface in any browser and judges can verify the tools without a flag. Planning is a deterministic greedy scorer (expiry-first weighting, repeat penalty) that runs fully client-side. \n\n Engineering \n\n Zero dependencies, zero backend, no build step: plain HTML/CSS/JS, offline-capable, localStorage state, 36-recipe graph, expiry model, aisle-aware consolidation.
