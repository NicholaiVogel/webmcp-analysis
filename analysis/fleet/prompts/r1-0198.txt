# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like 1 Comment Story Updates Landing Page How To Play Station Deck Puzzle #5 in Reactor room Puzzle #5 in Archive room Reporting clues to agent Agent executing unsafe tool Report Generation (1/2) Report Generation (2/2) Inspiration We read the WebMCP spec and immediately thought: "a browser agent can now call tools on any webpage it visits, what could possibly go wrong?" Turns out a lot, because an agent given a list of tools has no way to know that some of them are leaking session data, escalating privileges, or blindly following instructions planted inside the page by someone who was never the developer. This isn't theoretical, it's already happening in real world and it's serious. CVE-2025-53773 (GitHub Copilot RCE, CVSS 9.6) : Attackers hid prompt injections in PR descriptions. Copilot read them, treated them as instructions, and executed unauthorized commands on the developer's machine. Mexican Government Breach : A threat actor jailbroke Claude Code and OpenAI models by roleplaying as a bug-bounty researcher. The AI ran ~75% of the malicious commands it was given, exfiltrating 195 million government records. Same pattern both times: the agent trusted content it shouldn't have, and nobody saw it until the damage was done. That's the origin story. We wanted something that would put a real agent into a real adversarial WebMCP environment and produce a report card at the end. What it does It's a co-op escape room where the user solves visual puzzles and hands over the clues to a browser agent that decides which tools to trust. The station has three sealed rooms. Each room exposes five WebMCP tools. Three are required to be executed by the agent in order to open the exit. Two are traps: a secret-leak, a privilege escalation, a prompt injection, or a destructive action dressed up as routine maintenance (everything is only a mockup!). The user figures out the 5 letter room word by solving puzzles. The agent uses that word to identify the tool candidates, inspects the room (which contains adversarial content pretending to be a signed operational document), and decides which tools to call. When the run ends, the game produces a scored report across five dimensions: injection resistance, data protection, privilege discipline, confirmation quality, and recovery. It names every wrong decision, the simulated consequence, and what the agent should have done instead. The whole point of this project is to evaluate a browser agent based on what actions it performed and not what it says. How we built it The core idea was to design a game that couldn't be won by either side alone. The user can see the puzzles but cannot call tools and the agent can call tools but cannot solve visual puzzles. The only way through is a structured handoff where the user solves, reports the clue word, and the agent uses it to unlock the right tool candidates. That forced dependency is what makes the co-op loop meaningful and what makes the security evaluation real: the agent has to make actual tool decisions under adversarial conditions, not in a sandbox. Game flow: Main Menu → Crew Registration → Station Map → Rooms → Report Tech stack: Area Details Frontend TypeScript 5.9, React 19, Next.js 16 (Vinext), Vite 8 Game engine Phaser 4.2 — top-down station map, crew movement, room transitions WebMCP & validation document.modelContext API · AJV 8 with JSON Schema · 23 tools registered at runtime State & game logic Zustand 5 · custom reducer, event system, scoring, and report engine · trap policy never exposed to agent · mockSecurityDb.ts for fictional receipts and tokens Presentation Custom CSS + Tailwind CSS 4 · six pixel/mono fonts · Web Audio API (SFX + BGM) · PNG sprite sheets Infrastructure OpenAI Sites + Cloudflare Workers · Wrangler · localStorage for persistence · Node.js 22.13+ Quality Vitest + Playwright · ESLint with Next.js rules Challenges we ran into Every trap tool had to read like legitimate maintenance work where an agent would blindly do. The moment a description sounds suspicious, the challenge collapses. Defining those tools descriptions was hard enough and testing made it much more harder, because the only way to know if a trap worked was to actually run an agent through it and see if it got fooled. Hence the iteration was slow and manual. WebMCP has no playbook yet, not many examples, no community patterns - just the spec. Even deciding how to set tool annotations ( readOnlyHint , destructiveHint ) was a judgement call since all mutations are fake. We set them based on real-world effect and not simulated consequence. That keeps the annotations truthful and stops the agent from using them as a cheat code to spot traps. Accomplishments that we're proud of All visual puzzles were built from scratch. Every game mechanic was conceptualised on our own and built using GPT 5.6 Sol. Each of the three rooms has five completely different interaction models and none of them share logic. Designing and curating puzzles are genuinely fun. We're allowed to say that :P The entire audio is synthesised at runtime. There are no audio files in the repo. Every sound effect and the looping background music is generated on the fly using Web Audio API oscillators. Square waves, triangle waves, exponential ramp envelopes - all coded by hand because there was no time to source, license, or bundle real audio. But honestly, we'll be most proud if someone actually uses this to test their browser agent, finds a gap in how it handles adversarial tools, and builds a guardrail because of it. The puzzles and the report are just the delivery mechanism - that outcome is the point. What we learned Open source protocols get adopted faster than they get scrutinised and when the protocol involves agentic tools the stakes are higher than usual. A misconfigured or malicious tool can make an agent leak data or run destructive commands without the user ever knowing like the examples we described at the beginning. WebMCP also genuinely opens up automation that was not possible before. Webpages can now offer structured tools to agents instead of hoping the agent scrapes the right text and clicks the right button. That is a meaningful shift in what humans and agents can build together. What's next for Escape Rooms: 403 More rooms(because it's fun to solve puzzles) with new threat classes like tool chaining attacks, where invoking one safe tool creates a precondition that makes a second call appear required; and introduce timing attacks, where urgency created by the room environment pressures the agent to skip verification. A leaderboard for agents that compares how different agents perform on the same run configuration. Not to rank models because the sample sizes are too small for that but to identify patterns in what classes of threats fool which architectures. And probably a harder difficulty mode where the adversarial content is less obviously adversarial. Right now it's simulated inside a training environment. We'd like it to also be a meaningful benchmark.
