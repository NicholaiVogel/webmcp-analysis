# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Make maps multiplayer. Like Comment Story Updates CoMapper Make maps multiplayer. CoMapper is a WebMCP reference implementation for shared spatial work. Users and agents explore, filter, inspect, style, and export the same live map state. Inspiration Maps shape our world. We use them to navigate, predict, plan, and understand the world around us. And yet, as the old saying goes: Tabula non est terra. (The map is not the territory.) For millennia, we've built tools for working with maps: the compass, sextant, surveying instruments, satellite imagery, GIS, spatial databases. Now agents can use those same tools. CoMapper asks: what happens when humans and agents collaborate on cartography? What it does CoMapper turns attributed GeoJSON into a shared spatial workspace. It validates mixed geometry, infers useful fields and controls, creates stable feature identifiers, and keeps the map, results, inspector, filters, and selection synchronized. Its WebMCP tools reflect the current page state. Dataset discovery and workspace inspection are always useful. Result-level actions appear once a search produces visible features. Styling and filtering accept fields declared by the active dataset. Feature actions accept visible result IDs. Agents can search, inspect, select, filter, style, and prepare CSV or GeoJSON exports. Their actions resolve into the same interface users are viewing. Prepared downloads appear as explicit controls in the workspace. Demo Scenario For the challenge demo, CoMapper includes a Toronto dataset with 269 features: 158 neighbourhoods, 86 technology-company locations, and 25 mobility, talent, and ecosystem anchors. The scenario gives the collaboration loop a focused question: build a shortlist for a potential OpenAI office. The first pass surfaces a density-led set of candidates. Users broaden the search beyond downtown, ask for a shorter list, inspect the evidence, and request an export. Each prompt continues from the state already visible on the map. The Toronto question is one worked example. The same interaction model applies wherever location, evidence, and human judgment meet: logistics, infrastructure, field operations, urban planning, environmental analysis, site selection, and emergency response. The demo also surfaces the limits of its evidence. A real property decision would require current rents, vacancy, floorplates, zoning, incentives, employee origins, and travel-time analysis. Why WebMCP WebMCP lets the application expose the context it already understands. CoMapper registers page-bound tools with document.modelContext.registerTool(...) and refreshes the available surface as the workspace changes. Each tool calls the same React action used by the interface. A search updates the result ledger and map. A selection opens the inspector. A filter changes the visible evidence. A prepared export reveals a download control. Users and agents remain synchronized around one state model. CoMapper demonstrates four reusable principles: Page state determines capability. Tools appear when their inputs and effects are valid. The interface remains authoritative. Tool actions resolve into visible application state. Schemas enforce scope. Fields, result IDs, limits, and spatial frames are validated. Users retain control. Evidence gaps stay visible and downloads require an explicit action. Stack CoMapper uses React, TypeScript, Vite, MapLibre GL JS, Zod, Cloudflare Workers, and the OpenAI Sites Vite plugin. The browser-side data pipeline accepts GeoJSON, validates its geometry, infers fields and controls, creates stable feature IDs, and normalizes the dataset into a shared search response. The bundled Toronto atlas follows the same path as an imported local dataset. The map, result ledger, inspector, and WebMCP tools all consume that response. The tool layer uses narrow JSON Schemas with Zod validation. Searches accept one spatial frame: radius, visible bounds, or a drawn polygon. Feature actions are limited to visible result IDs. Styling and filtering use fields declared by the active dataset. Connected text carries an untrusted-content hint. Tool registration follows page state and uses an AbortController for cleanup. Search calls receive the invocation cancellation signal. Tool results return updated visible state and provenance for the next step. The public demo runs entirely in the browser with its bundled fixture. Evaluation requires no account, database, API key, or paid model call. Challenges Three details shaped the implementation. First, tool state had to match page state. Result-specific tools need current rows, fields, and IDs, so registration changes as users move through the application. Second, spatial datasets mix geometry types and overlapping evidence. CoMapper keeps points and polygons legible together, gives points click priority where geometries overlap, and preserves the camera while layer state changes. Third, every agent action needed a visible and trustworthy boundary. Search limits, field allowlists, visible-ID checks, provenance, cancellation, and user-controlled download reinforce the same interaction model. Accomplishments Users and agents work with the same live application state. Tools adapt to the active dataset and current results. Follow-up prompts revise the evidence within the active workflow. Imported GeoJSON and the bundled fixture share one data pipeline. Inspection keeps source fields, provenance, and evidence gaps visible. Agent-prepared downloads remain explicit user actions. The public demo is deterministic, attributed, and ready immediately. Takeaways WebMCP is especially effective when a website is already an instrument. The most useful tools expose a few high-confidence operations, inherit the application's constraints, and return their effects to the interface. Shared state also changes the role of follow-up prompts. A correction becomes an input to the active workspace: users can see what changed, challenge the direction, and continue from the same evidence. The broader opportunity is software where visual interaction and agent action form one inspectable loop. What's next The next step is to develop the reference implementation into a reusable spatial-workbench pattern: pluggable dataset adapters and validation profiles; saved workspaces and collaboration history; richer spatial operators, joins, and travel-time analysis; reusable tool contracts for other MapLibre applications; and review flows for teams working with consequential spatial decisions.
