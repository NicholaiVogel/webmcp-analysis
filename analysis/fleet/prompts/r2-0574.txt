## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  be replicated comparably well by a general agent driving the UI.

- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

- 3-4: thin prototype; contradictions between surfaces; placeholder content.

relative to existing concepts, ambition, memorable/surprising use of the medium, and

WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.

- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

MCPx makes those actions reliable. What it does MCPx is a reliability runtime for multi-step WebMCP workflows. The main idea is simple. For consequential actions, MCPx thinks about three things: Execute → Inspect → Compensate For example: create_route → get_route → delete_route Execute performs the action. Inspect asks the application for the actual state of that action. Compensate provides a way to safely undo it if the larger workflow fails. This becomes especially useful when something goes wrong after an action has already been sent. Instead of immediately assuming failure, MCPx can put the operation into an explicit state called IN_DOUBT . It then asks the application that owns the resource for ground truth. If the resource actually exists: IN_DOUBT → RECONCILING → RECOVERED The workflow continues without blindly performing the original mutation again. If something later fails for certain, MCPx stops the workflow and asks the human operator before performing destructive rollback. Like 1 Comment Story Updates Vitals Incident Room Dashboard Vitals Incident Room Agent Capabilities Vitals Incident Room Architecture Inspiration Vitals started with a simple frustration: when a production incident happens, engineers rarely investigate it in one place. They jump between dashboards, logs, traces, deployment history, alerts, and remediation tools, manually connecting the dots under pressure. While exploring WebMCP, I saw an opportunity to rethink that workflow. AI agents are increasingly capable of reasoning about complex engineering problems, but traditionally they have had to interact with web applications through the UI or through completely separate integrations. That creates a gap between what an agent can reason about and what it can actually do. So I asked: What if the observability application itself could expose its capabilities directly to an AI agent, while the engineer and agent remained in the same workspace? That became Vitals Incident Room , an experiment in what an agent-native incident-response workflow could look like. I wanted to go beyond "add a chatbot to a dashboard." The goal was to make the agent a genuine participant in the incident lifecycle while keeping the human in control of consequential decisions. What it does Vitals Incident Room is a WebMCP-powered incident-response workspace where engineers and AI agents investigate, remediate, and verify production incidents together. For demonstration, a checkout-api service experiences a severe latency and error-rate regression shortly after deployment v2.8.3 . The agent can discover and invoke structured WebMCP tools to: inspect service health, query metrics, compare deployments, inspect distributed traces, search operational logs, analyze the gathered evidence, prepare a remediation, apply an approved remediation, verify recovery. The investigation can look like: get_service_health ↓ query_metrics ↓ compare_deployments ↓ inspect_trace ↓ search_logs ↓ analyze_incident The agent correlates those signals and identifies the most likely cause: a database query regression introduced in v2.8.3 . It can then prepare a rollback to the last known-good version. However, the agent cannot authorize its own action. prepare_remediation ↓ HUMAN APPROVAL ↓ apply_remediation ↓ verify_recovery ↓ RESOLVED The remediation changes the application's simulated system state, and the final verification checks that both latency and error rate have actually returned to acceptable levels. The result is a shared workflow rather than a chatbot sitting beside an observability dashboard. How I built it Vitals Incident Room extends existing Vitals observability work with a focused browser-based Incident Room designed specifically around WebMCP. The application is built with TypeScript and React, with a deterministic simulated observability environment so the complete workflow can be reproduced without requiring real production credentials or infrastructure. The architecture separates the WebMCP layer from the application domain: Architecture Layer Component Responsibility Human Engineer Reviews evidence and authorizes consequential actions Web App Incident Room Presents shared incident state and workflow Agent Interface WebMCP Tool Surface Exposes structured capabilities to the AI agent Agent AI Agent Discovers tools, gathers evidence, analyzes the incident, and executes approved actions Observability Metrics · Logs · Traces · Deployments Provides the signals used for diagnosis Analysis Evidence Correlation Combines signals into a ranked root-cause hypothesis Remediation Prepare → Approve → Execute Proposes and safely applies the remediation Verification Recovery Checks Confirms latency and error-rate recovery before resolution Core flow: Engineer → Incident Room → WebMCP → AI Agent → Observability Data → Evidence Analysis → Remediation Proposal → Human Approval → Execution → Verification The WebMCP layer exposes nine focused tools with explicit schemas and annotations. Read-only investigation capabilities are separated from state-changing operations, and operational logs are explicitly treated as untrusted content. I also made the demo stateful. A rollback doesn't simply change a label from "failed" to "resolved"; it changes the simulated deployment, latency, error rate, and database-query performance. Verification then reads that new state. This gives us a deterministic cause-and-effect loop: v2.8.3 ↓ latency regression ↓ agent investigation ↓ rollback to v2.8.2 ↓ metrics recover ↓ incident resolved Most importantly, I designed the human approval boundary outside the WebMCP action surface. The agent can prepare a remediation, but only the engineer can authorize it. Challenges I ran into The biggest challenge was deciding how much of Vitals to expose. Vitals already covers a broad observability workflow, and my first instinct was to make everything agent-accessible. That quickly became the wrong direction. A large collection of loosely connected tools would demonstrate API coverage, but not why WebMCP fundamentally changes the product. I narrowed the project to one complete incident-response journey and treated everything else as secondary. Another challenge was making an agent-driven workflow believable without depending on real production infrastructure. I solved that with deterministic metrics, logs, traces, deployment history, and mutable runtime state. This lets us make the entire experience reproducible while preserving realistic relationships between the signals. I also had to think carefully about authority and safety. An agent that can investigate an incident and then immediately authorize its own rollback creates a dangerous feedback loop. I separated proposal, approval, execution, and verification so the human remains responsible for the consequential decision. Finally, WebMCP is an emerging browser capability, so I had to pay close attention to tool schemas, browser support, registration behavior, tool annotations, and the difference between a WebMCP-capable webpage and the agent consuming those tools. Accomplishments that I'm proud of I'm most proud that the project evolved beyond a conventional "AI + dashboard" demo. The agent can actually compose multiple capabilities exposed by the webpage: Health + Metrics + Deployment history + Traces + Logs ↓ Evidence-based diagnosis I'm also proud of the human-in-the-loop safety model. A consequential action cannot be executed until it has been explicitly authorized by the engineer, and recovery is not declared until the post-action state passes verification. Another accomplishment is that the demo is completely deterministic. I can reset the environment and reproduce the same incident, investigation, remediation, and recovery sequence without relying on external production systems. Incident Room also deliberately treat operational log data as untrusted content. That distinction matters in an agentic environment because data discovered by a tool should not automatically become an instruction to the agent. Most importantly, Vitals Incident Room gave us a concrete answer to a question the project started with: What does an observability application look like when an AI agent is a first-class participant rather than an add-on chatbot? What I learned My biggest lesson was that WebMCP is most interesting when it changes the workflow, not when it merely exposes functions. A collection of tools is easy to demonstrate. Designing a workflow in which an agent can discover, compose, and act on those tools while sharing state with a human is much more interesting. I also learned that tool design is effectively part of product design. Names, descriptions, schemas, output structures, side-effect annotations, and error behavior all influence how reliably an agent can use an application. A browser room planner an AI furnishes from your words, placing, checking, and fixing the layout through the page's WebMCP tools. Like Comment Story Updates Inspiration In September 2024 I moved to a new country, into an empty apartment I'd only seen in photos. A year later, almost to the week, I moved again. Different place, same problem. Both times it went like this: you stand in the middle of a bare room with a phone full of furniture tabs and no real sense of scale, you order things that don't quite fit, and you spend evenings pushing an imaginary couch around in your head. It isn't just me. Every fall a wave of people do exactly this: new students, new arrivals, first apartments, furnishing a room they can only picture in fragments. What you want in that moment is simple: what do I need, how would it look, what will it cost, and once it's all in, is there any floor left to stand on? That's a planning problem, and planning is exactly what an agent should be good at. But a chatbot can only describe your room back to you. It can't move anything in it. WebMCP changes that: a page can hand its own capabilities to an agent as tools. So I built the page worth handing over. What it does Roomwright is a 3D room planner that runs entirely in the browser. You draw a room, set the doors and windows, and place furniture from a catalogue of parametric pieces. Every item has real dimensions and required clearances. Orbit it, drop to a floor plan, resize or recolor anything, and it keeps a running shopping list with a total. Every one of those actions is exposed to an agent as a WebMCP tool . There are 19 of them. So instead of clicking, you can say: "Studio apartment, 4.6 by 7 metres, door on the south wall, two windows on the east. Bed against the back wall, a sofa splitting off the living area, a small dining set by the window." The agent reads the tools the page offers and builds the whole thing: resizing the room, cutting the openings, furnishing three zones, running the planner's own clearance checks, catching its own overlaps, and fixing them. Then you take over: "turn the sofa toward the TV, lose that chair." Same room, same undo history, you and the agent trading turns on one canvas. How WebMCP powers it The key decision: the UI and the agent mutate the exact same state. There's a single store, and a button click and a tool call go through the same action. So undo/redo, autosave, shareable-URL persistence, and live layout validation all just work for the agent. There is no agent-specific code path for any of them. Tools register against document.modelContext using the spec's AbortSignal lifecycle, in four groups: Read : get_room , list_catalog , get_shopping_list Build : add_item (resolves a product by id, name, or fragment, so the agent never has to guess), create_custom_item , duplicate_item (with an east-west / north-south mirror so "a chair on each side" is actually symmetric), remove_item Arrange and check : move_item , rotate_item , resize_item , set_variant , set_room_dimensions , set_opening , remove_opening , suggest_spot (grids the room and returns candidate positions), check_layout (overlaps, blocked doors/windows, clearance failures, walkways under 0.75 m, narrowest gap) Show : select_item (highlights a piece, opens its inspector), set_view , reset_layout suggest_spot and check_layout matter most. They give the agent a feedback loop, not just setters. It places, checks, notices a conflict, and re-plans, visibly, in the activity log. How I built it React 19 + TypeScript + Vite React Three Fiber + drei + @react-three/postprocessing for synthetic image-based lighting (no HDRI file), real shadow-mapped shadows, screen-space AO, and a restrained post pass Parametric furniture : every piece is authored geometry keyed on its kind, not a glTF download, so the bundle stays small and every dimension is real Zustand for the single shared store, Tailwind CSS v4 for the UI Device-aware quality tiers (High / Medium / Low, auto-detected from the GPU string and core count, with a live framerate monitor that steps down) so it runs on a laptop, not just a workstation Deployed on GitHub Pages Challenges The spec is still moving. Early references used navigator.modelContext ; the current spec uses document.modelContext and has no unregisterTool . You unregister by aborting an AbortSignal . I probe both and use the signal lifecycle, with a short retry in case the host injects the API after first paint. Shared post-processing broke drei's ContactShadows. EffectComposer sets gl.autoClear = false , and ContactShadows relies on autoClear to wipe its render target, so moving a piece smeared shadow trails across the floor. Fixed by dropping ContactShadows for a directional shadow map plus per-frame screen-space AO. The agent kept guessing product ids. It saw sofa-halden and tried coffee-milo (the real id is table-milo ). Fuzzy resolution plus returning the full catalogue on a miss fixed it in one step. Symmetry. duplicate_item offset copies by a fixed diagonal, so "a lounge chair on each side" never mirrored. Added a real mirror across the room's centre line, and floor lamps now auto-aim at the room centre so a mirrored pair points the right way. Testing WebMCP is hard today. Only ChatGPT's desktop in-app browser exposes document.modelContext (plus Chrome 149 behind a flag), and it's gated by account type. What I learned The leverage in WebMCP isn't the tool calls. It's the shared state . The moment the agent and the human mutate the same model, everything the app already does (undo, validation, persistence) becomes something the agent does too, for free. Design the state model well and the agent integration is almost nothing. And tool descriptions are the API. Fuzzy product resolution, mirror options, and full-catalogue errors did more for reliability than any prompting. The agent behaves well when the tools let it. What's next Real glTF furniture and user uploads, photo-assisted room capture, L-shaped and multi-room layouts, a path-traced render mode. And a retailer-facing version: drop these tools onto product pages, and every shopping agent can lay out a real room instead of guessing. Like Comment Story Updates Mechanism Canvas lets agents test competing chemistry paths while the learner keeps control of the final answer. The learner sets agent permissions, hint limits, and commit authority before any agent work begins. The agent explores competing mechanisms in isolated branches while the learner’s draft stays sealed. A deterministic validator rejects the incomplete path and approves the complete SN2 mechanism. The Observatory reveals available tools, agent actions, validator results, and the full proof trail. The agent can return a checked proposal, but only the learner can move it onto the canvas. After reviewing the evidence, the learner commits the approved electron-flow mechanism. An interactive 3D inspector connects curved-arrow reasoning with molecular geometry and lone pairs. About Mechanism Canvas Inspiration I kept coming back to a mismatch between how students solve organic chemistry problems and how AI tutors usually communicate. Reaction mechanisms live in diagrams. The important details are the atoms, bonds, lone pairs, curved arrows, and the order in which electrons move. A separate chat window sees almost none of that unless the student stops and translates the drawing into prose. Giving an agent broad control of the drawing surface creates a different problem. It can finish the exercise before the learner has worked through it. I wanted to see whether an agent could help inside the real mechanism canvas while the student still controlled the consequential part: what actually gets added to the answer. That became the central idea behind Mechanism Canvas. The agent gets a safe place to explore. The page checks the chemistry. The learner decides what comes back. What I built Mechanism Canvas is an organic chemistry workspace where a student and a WebMCP agent can work with the same structured mechanism. The page exposes meaningful chemistry objects instead of screen coordinates, so the agent can refer to a particular atom, bond, lone pair, or revision without guessing from pixels. The main demo is a counterfactual (S_\mathrm{N}2) lab. The agent tests two electron-flow paths away from the learner's draft. In the first branch, it forms the new bond but forgets the coupled leaving-group cleavage. The production validator rejects that attempt. The second branch contains both moves, so the validator approves it. The checked branch then reaches a visible proposal gate. It still does not change the learner's mechanism. The learner can inspect the evidence, add the proposal to the draft, request one more check, and make the final commit. An incorrect agent attempt becomes useful evidence instead of damage that has to be undone. The site also works as a complete manual tutor when WebMCP is unavailable. Direct agent collaboration is an extra layer on top of the same interface rather than a separate agent-only experience. How I built it I built the app with React, TypeScript, and Vite. The mechanism canvas is backed by a structured graph with stable IDs for atoms, bonds, electron sources, and curved-arrow moves. A deterministic chemistry engine evaluates proposed steps against six reviewed fixtures. The model can suggest and explore, but it does not decide whether a mechanism is chemically valid. The WebMCP layer registers 26 imperative tools through document.modelContext.registerTool . Each tool uses a closed JSON schema and calls the same TypeScript store commands as the visible interface. Mutating calls re-read live state and check the current revision, scope, and learner-granted permissions before they run. Tool discovery changes with the task. Coach mode begins with 16 available tools. Opening the two-path lab adds the branch controls. Starting a six-action comparison session narrows the surface to the capabilities needed for that job. Once the action budget is used, the work tools disappear and only four evidence controls remain. A cached tool cannot restore access that the learner has already closed. I also built a Collaboration Contract where the learner sets the agent's maximum role and hint level. An intent-bound session freezes the job, problem, revision, and action budget. The Live Run Observatory shows which capability batches the host accepted, and a Proof Ledger records privacy-minimized before-and-after receipts from the actual tool callback boundary. Around that core, I added keyboard-operable SVG structures, local persistence, reversible commits, state diffs, electron-flow replay, and a lazy-loaded Three.js molecular inspector. The finished project is a static GitHub Pages site with no backend, account, or credentials required. Challenges The hardest engineering problem was keeping tool discovery honest while the page changed. A fixed list of 26 tools would technically work, but it would hide the learner's current intent inside descriptions. My first dynamic version swung too far in the other direction: every small store notification could publish a transient capability batch. Those batches were real, but they did not represent a stable state that a judge or learner could understand. I changed the registration layer to coalesce related updates, wait for the complete batch, and record only surfaces the host had accepted. Proof was another difficult part. A model saying that it called a tool is only a claim. I needed the page to show whether the callback ran, whether the expected state changed, and whether the main draft stayed untouched. The Proof Ledger now wraps the real callback boundary, and the Observatory evaluates its seven demo claims from those receipts. I also had to make failure safe without making it invisible. The two lab branches have real revisioned state and use the same validator as the main canvas, but they remain isolated until the learner chooses a checked proposal. That separation took more work than simply giving the agent an undo button. It is also the part that makes the workflow useful for learning. What I learned I learned that an agent's tool list is part of the user interface. A capability name, its schema, when it appears, and when it disappears all communicate authority. Encoding the learner's intent in that surface made the boundary much clearer than relying on prompt instructions alone. I also learned how well deterministic software and agent reasoning can complement each other. The agent is good at generating alternatives and explaining a choice. The chemistry engine is good at enforcing exact constraints every time. Keeping those jobs separate made the result easier to trust. Most of all, this project changed how I think about mistakes in learning software. A wrong attempt does not have to be erased or quietly corrected. When it is isolated, checked, and kept visible, it can show the learner exactly why the complete mechanism needs both electron-flow moves. What's next The current chemistry engine is intentionally limited to reviewed fixtures. I would like to add an instructor authoring flow for new mechanisms and study how different permission contracts affect the explanations students give. The same pattern could also work in circuit design, geometry, and other visual STEM tools where exploration is useful but ownership should stay with the learner. Like Comment Story Updates Inspiration Faultline started after a friend quit his job and we began practicing system design interviews together. We could talk through architectures back and forth, but we kept asking the same question: is this actually right? I wanted a better way to practice than negotiating with an human/LLM for an answer. I wanted a game where you make a design decision and find out whether it works. What it does Faultline is a systems design/interview prep game. Fvery level gives you a problem, requirements, a workload, and a set of components; you design the system, and the simulator tells you the results. With WebMCP, an agent can join the live session, inspect the current design, and point out relevant parts of the canvas. Designed to act like another engineer in the room, the agent will help with questions but won't fully take over. Can also act to be interviewed where the agent will walk through realistic follow ups you might hear in a system design round. How we built it I started with the game itself. Parts like letting player build freely, simulator being the source of truth, and providing the agent with structured evidence from the components as opposed to the answer. Each level has its own rules, including what components are available, the performance of the components, and the requirements. For the agents I needed to decided for most states of the game what the agent might need to reasonable answer a question, and I did so through dynamically exposing tools, keeping data as fresh as possible, and intent routing for most common commands for reliable play. Challenges we ran into The hardest part was keeping the agent reliable while a player rapidly changes an architecture. It needs the most up to date info for every call, but resending every detail was too slow. The app needed to only be frustrating with the challenges, so the agent experience for help needed to be fast just as much as it needed high quality responses. Getting the right current context to the agent efficiently and providing it with only the tools necessary for the state took a lot of fiddling around with. Accomplishments that we're proud of I am proud of how the agents acts. I've had friends play with it, were unable to beat the level first couple tries and begrudgingly gave into using the coach, where they were surprised with the interactions. It really keeps you as the focus as just acts as a background tool so that you don't get stuck forever. This is best shown in the interview tool that asks follow up questions to let users practice the back and forths after designing the solution by using specific interviewer tools and keeping architecture facts straight as info changes. What we learned This was my first time working with WebMCP, and I learned a lot about building for external agents inside a app. In particular, I learned more about tool routing, intent routing, and evaluations for checking whether an agent picks the best tool for the moment. Was also first time I tried to make like an app with a wide spread audience over to fill specific niches/needs. What's next for Faultline I would like to make it a daily game where you do one game a day just to keep yourself sharp. I would also like to keep expanding the coach's toolset and personality. I think during interview process if it could change the rules of the simulation and make you live build to solve a question would be pretty interesting and fun.
