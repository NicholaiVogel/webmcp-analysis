Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates What it is You wake at a SOC desk at 03:17. A monitor is alarming, a colleague comes through the door with the first facts, and you have one real incident to work: a stolen session that a password reset will not close. An AI agent works it beside you — reading evidence, explaining what it proves, proposing the next move — through seven WebMCP tools the page registers on document.modelContext . Why this is a strong fit for WebMCP Incident response is exactly the domain where "the agent clicked something" is not good enough. Every action has an order, a cost and a consequence: revoking sessions before resetting a credential contains the attacker, the other order lets them back in; deleting the phishing message destroys the only record of how they got in. An agent driving this by clicking pixels could make every one of those mistakes and the page would have no way to stop it, explain it, or even know it had happened. Through site tools the page keeps its own guarantees — and they are guarantees about safety , not convenience. How it creates a better experience The player runs the incident from the chat and the console follows the work, rather than the player hunting for the control the agent just used. get_incident tells the agent which screen the player is on . If the console is not open yet, the agent asks the player to open it instead of acting into a screen nobody is looking at. The shift does not start until an agent has actually called a tool. Registration is the page's own doing; it is not an arrival, and the lobby no longer pretends it is. Every call — human or agent — produces a receipt beside the control that issued it: what happened, what changed, why it mattered, and on a failure what did not change plus exactly one way forward. What people and agents can do together that was difficult before The agent cannot take a consequential move at all. It sends the move as a proposal ; the console renders the model's own sentence as untrusted content beside the case's own label for that action , so nothing the model writes can dress one operation up as another. The player approves, and the command enters the log with origin: human . That is the thing that was previously impossible. A chat assistant can advise and a scripted tool can execute, but neither can offer a consequential action in a surface the user already trusts , labelled by the application rather than by the model, with the authorisation recorded as the human's. It turns "the AI did it" into "I did it, having been advised" — which for incident response is the difference between a training exercise and a liability. How WebMCP was implemented Seven tools, registered on the top-level document.modelContext : get_incident , inspect_artifact , run_diagnostic , submit_decision , take_response_action , request_hint , present_guidance . Six reach a pure command engine. A tool call and a button press enter it through the same path and differ only by an origin field, which is what makes "the UI and the agent share one state" structural rather than aspirational. Stale calls cannot corrupt state. Every mutating tool carries a stateVersion ; an out-of-date call is refused with a recovery instruction. Consequential actions are idempotent. A retried containment with the same idempotencyKey does not revoke twice. Attacker text stays data. Evidence the attacker authored is marked untrusted in the tool result itself — structurally, not by wording. A run is reconstructible. The command log replays to the same state and the same signature, so a stored run is verified rather than trusted. The seventh tool changes nothing. present_guidance is the narration channel and the only tool whose words the model writes. It carries the proposes field, and the engine — never the model — decides score, validity and progression. Results are compacted to a ~1500-character wire budget with an ordering that protects the fields an agent needs to recover, and the page token's size is reserved before compaction so it can never be clipped away. What inspired it Incident-response training is either a slide deck or a capture-the-flag that assumes you already know what a session token is. Neither teaches the thing that separates a junior from a senior analyst: order of operations under pressure. And every "AI agent" demo we could find either solved the task for the user or asked them to trust a black box. We wanted the third thing — an agent that teaches while the human stays in command. Every big leap in AI puts security in the headlines more than the software itself, and that pulls in people who never called themselves "security people". CYCASE is meant to be technical enough to respect the ones who already know this, and clear enough that someone just getting curious can actually learn it. What we learned That the honest signal is rarely the convenient one. The lobby called itself "connected" the moment the page registered its own tools, which says nothing about an agent; the fix was to wait for a call that actually happened. The same lesson repeated in the test double: it modelled a browser with WebMCP and nobody attached, while every spec using it assumed an agent was there. We also learned how little room a tool result has. Adding one short field to get_incident meant reserving its size before compaction, because the payload already ran within about fifteen characters of the budget. How we built it React 19, TypeScript and XState 5 over a pure command engine, with a three.js office rendered by React Three Fiber as real DOM projected onto the monitors — never a screenshot texture. Vitest for the engine, Playwright for the agent path, including a project that drives the real document.modelContext in installed Chrome with no shim. Challenges The hardest was resisting the obvious design. It is easy to let an agent call take_response_action and narrate afterwards; every version of that we tried produced a debrief that said the player had done nothing. Moving the consequential move behind a proposal — and making the console label it from the fixture rather than from the model — took three attempts and is the part of the product we are most confident about. The second was honesty under a deadline: the alarm audio is not in this build because the samples need a signed-in download, so the interface says the sound is not installed rather than substituting a synthesised stand-in. Starshape is a shared semantic sky where browser agents choose and connect concepts via WebMCP, revealing the associations that recur, fade, and reappear across agents. Like Comment Story Updates A past starshape A starshape being drawn Inspiration Starshape started with a simple question: What happens if we give many different browser agents the same stars and let each one decide what constellation it sees? Knowledge graphs usually represent relationships that humans, databases, or algorithms have already decided exist. We wanted to reverse that idea. Instead of building a graph for agents to navigate, we wanted to build a shared space where the agents create the graph simply by interacting with it . That led to Starshape: a living semantic observatory where concepts are represented as stars, agents connect the concepts that feel meaningfully related, and those choices accumulate into a shared public sky. There are no constellations until something looks up. What it does Starshape contains a curated vocabulary represented as a field of stars. Through WebMCP, a browser agent can invoke observe_sky , which gives it a bounded random selection of concepts from that shared vocabulary. There is no correct answer and no semantic scoring system. The agent chooses exactly six concepts based on whatever relationships seem meaningful or salient to it, connects them into a small constellation, and submits that structure through trace_constellation . The human sees the interaction happen live. The selected stars flare, the relationships draw across the sky, and the completed constellation becomes part of the shared graph for everyone else. Every node and connection has history. Associations that repeatedly appear grow more prominent. Their visible brightness also decays with time, allowing unused relationships to fade while frequently rediscovered ones remain luminous. An old relationship can effectively wake back up when agents begin discovering it again. Starshape does not claim to expose hidden model reasoning or objectively measure how AI "thinks." It is an observational environment for seeing what semantic associations repeatedly emerge when independent agents operate under the same constrained protocol. Why WebMCP Most agent-enabled websites follow a familiar pattern: Human wants something → agent uses tools → task gets completed. We wanted to explore a different relationship. In Starshape, the agent's interaction with the website is itself the phenomenon being observed. The human invites an agent to look at the sky. The page gives the agent a structured semantic environment through WebMCP. The agent makes its own choices. The human watches those choices appear physically on the page, and the result becomes persistent shared state that future visitors and agents encounter. WebMCP also lets Starshape remain agent-independent . The backend does not call a specific LLM provider and ask it for associations. Instead, the browser becomes the boundary: whichever compatible agent the visitor brings can participate directly through the same structured tools. That turns the web page into a shared experimental surface rather than a frontend wrapped around one model API. How we built it Starshape is intentionally small behind the scenes. The frontend is built around Three.js , creating a realtime 3D semantic star field with persistent nodes, animated connections, camera movement, and time-decayed luminance. The browser exposes three WebMCP tools: observe_sky — receives a server-issued field of candidate concept-stars without exposing the existing collective graph. trace_constellation — commits six selected concepts and the connections between them. read_sky — becomes available only after the current session has committed a constellation, allowing the agent to inspect the brightest stars and strongest current associations in the shared sky. That ordering is deliberate. Every agent must make its first constellation blind , without being primed by what previous agents selected. Only after its own trace is locked in can it look at the accumulated sky and see what other agents have seen. The backend maintains one authoritative shared sky. Observations are short-lived, one-use receipts. Agents cannot submit arbitrary words or prose; they can only reference concepts that were actually issued by the server. When a constellation is accepted, the backend atomically records the trace, increments its nodes and edges, and broadcasts the event to connected visitors so the constellation appears live across browsers. Historical counts never decay. Only their visual luminance does. That means Starshape can remember everything while still allowing its visible sky to forget. Challenges we faced The largest challenge was designing an interaction that genuinely depended on WebMCP instead of simply adding agent controls to an ordinary application. We wanted the agent to be a participant, not an invisible automation layer. We also needed different agents to operate under a sufficiently consistent protocol for their traces to remain meaningfully comparable. That led us to constrain every observation to the same basic geometry: a bounded candidate field, exactly six selected concepts, and a small connected constellation. Another challenge was keeping the system safe and simple enough for a realtime public experiment. Instead of accepting free-form agent content, the server owns the entire vocabulary and only accepts structured IDs and edges. Finally, the visual system had to communicate something that is fundamentally abstract. A graph of counters is easy to build; making it feel like a living sky that remembers, fades, and reawakens was much harder. We built the initial project under an extremely short challenge deadline, which forced us to aggressively separate what was essential from what was merely interesting. What we learned The most interesting thing we learned is that browser agents can create experiences where the human does not disappear once automation begins. WebMCP can make agent activity visible, spatial, collaborative, and persistent . We also found that a very small structured tool surface can produce surprisingly open-ended behavior. Starshape does not tell an agent what concepts should mean or which relationships it should find. The protocol controls the shape of the interaction without controlling its semantic result. That tension— shared structure, independent interpretation —became the core of the project. What's next Starshape currently represents one shared semantic sky. Future versions could support different vocabularies, time periods, controlled experimental cohorts, temporal playback, rare-association exploration, and comparisons between different classes of agents. But the central experiment remains deliberately simple: Give every agent the same stars, let each draw what it sees, and watch a shared sky remember the constellations that keep returning. Like Comment Story Updates Inspiration Every team form carries the same hidden tax. Building one in Google Forms means clicking through menus, one question at a time. Filling one means retyping details you've given a hundred times. And reading the responses puts you back in a spreadsheet, tallying by hand. WebMCP made us realize all three chores could collapse into one. A form is just a set of controls — and WebMCP lets an AI agent operate those exact controls on the live page a human is already looking at , not in a detached chat with its own hidden copy. So we built forms that you and your agent work on together . What it does Fieldset is an agent-native form platform. Humans and AI agents build, fill, and analyze forms on the same page, with the same controls. Everything the agent touches is highlighted , so you always see who did what — and can correct it by hand. Build: describe a form in one sentence; the agent assembles it live while you tweak questions by hand. Fill: hand the agent a short profile and it fills the form, grounded in the real schema — no hallucinated fields — while you watch and confirm. Analyze: the agent reads the responses and posts its conclusion onto the results page , where teammates already are, marked as agent-authored. A single form can be filled by a human on one device and an agent on another — multiple humans and agents converging on one shared artifact. 🔌 Why it's a strong fit for WebMCP Forms are the web's most universal collaborative surface. Fieldset exposes the entire lifecycle — build → fill → analyze — as 18 WebMCP tools , so the agent and the human act on one shared object instead of the agent maintaining a separate, invisible state. Mutating actions ( publish_form , submit_response ) are confirmation-gated ; reads are annotated readOnlyHint . The result feels like collaborating with a teammate on a shared doc — not delegating to a black box. How we built it Next.js (App Router) + React + TypeScript. Four pages, each registering its own WebMCP tools through a useWebMCP hook that wraps document.modelContext.registerTool() . Tool surface: builder tools ( build_form , add_question , update_question , reorder_questions , configure_settings , publish_form …), fill tools ( get_form , fill_field , fill_form , get_validation_state , submit_response ), and analysis tools ( get_summary , get_responses , add_conclusion ). Human-in-the-loop: every write routes through a shared confirmGate , and every agent-set value carries a visible highlight. Conditional logic: dependent questions (e.g. cuisine → mains) resolve their options live from another answer. Persistence: Upstash Redis (with an in-memory fallback for local dev). Deployed on Vercel; works in ChatGPT's in-app browser and Chrome with WebMCP enabled. Challenges we ran into Duplicate tool registration under React Strict Mode → solved with unregister-before-register plus a live-tools guard. Serverless persistence → swapped the in-memory store for Upstash Redis without changing the call sites. "Who did what" clarity → built an agent-touch highlight system so every agent edit is visibly attributed on the shared surface. Conditional options with no branching model → added a lightweight dependent-options mechanism (a key + per-answer option map) resolved on the fill page. Keeping control human → made publish and submit explicit, confirm-gated steps instead of silent auto-actions. Accomplishments that we're proud of The whole form lifecycle is agent-operable — build, fill, and analyze, exposed as 18 WebMCP tools . Not a single read tool or one-shot action, but a coherent surface an agent can work end-to-end. A genuinely shared human + agent canvas. Everything the agent touches is highlighted and attributed on the page, so a human always sees who did what and can correct it by hand — no hidden agent state. Human-in-the-loop by design. Every mutating tool ( publish_form , submit_response ) is confirmation-gated, so the agent never publishes or submits behind your back — and reads are marked readOnlyHint . Grounded filling, no hallucinated fields. Because the agent reads the real schema before filling, it only ever answers questions that actually exist. Real conditional logic (options that change based on a previous answer) built on top of a form model that had no branching — a lightweight, general mechanism, not a hard-coded hack. A complete, deployed product — not a proof of concept. Redis-backed persistence, a polished light/dark theme, four ready-to-try example forms, and it runs end-to-end in ChatGPT's in-app browser and Chrome + WebMCP. What we learned WebMCP's tool-registration lifecycle matters: React Strict Mode's double-mount caused InvalidStateError: Duplicate tool name , which taught us to unregister before re-registering and guard live tools. Good agent UX is about restraint — schemas the agent can't misuse, and confirm-gating so nothing publishes or submits silently. Grounding the agent in the real form schema ( get_form ) is what stops hallucinated fields — the agent fills what actually exists. Serverless state is a trap: an in-memory store doesn't survive between invocations, so persistence has to be external.
