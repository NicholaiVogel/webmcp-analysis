CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they

No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher

Every important action remains visible in the interface, and the normal controls remain available as a fallback. How I implemented WebMCP I register the application’s tools directly through document.modelContext.registerTool . The tools are divided into two groups: Flood tools for inspecting capabilities, staging scenarios, requesting approval, starting calculations, monitoring progress, reading results, controlling playback, sampling locations, and comparing runs. Workspace tools for changing study areas, reading the visible scene, moving the camera, and focusing on important results. Each tool has a clear description and a strict input format. Tools that only read information are marked separately from tools that change the application. CausaFlow also protects the workflow in several ways: A calculation cannot begin until the exact staged scenario has been approved. Every scenario change creates a new revision, preventing an agent from approving an older setup by mistake. The user’s request to run a scenario is recorded as explicit authorization. Long-running calculations return progress instead of leaving the agent guessing. Completed results have stable identities and cannot be silently changed during replay or comparison. The agent reads numerical results from the application instead of estimating values from the animation. WebMCP is the access and coordination layer. It does not create the flood results. The calculations come from the flood-simulation software used by CausaFlow. Key demonstration: Hospital Lifeline Hospital Lifeline represents eight drains along a 771-metre hospital access road. With every represented drain blocked, the access checkpoint crosses its 15-centimetre test limit after 270 seconds and reaches a maximum depth of approximately 32.8 centimetres. I tested the zero-drain case and every individual-drain alternative. Reopening D7 was the only single-drain option that kept the checkpoint below the limit. Its maximum depth fell to approximately 12.7 centimetres, and D7 removed approximately 311.6 cubic metres of water. The WebMCP agent can run the blocked case, run the D7 case under the same storm, compare them, and take the user directly to the checkpoint. How I built it I built the interface with Next.js, React, TypeScript, Three.js, and deck.gl. The flood calculations run through ANUGA using Python. I also use EPA SWMM for separate drainage checks. Houston uses frozen USGS elevation data. Velachery uses frozen Copernicus elevation data with OpenStreetMap context. I packaged the application with Docker and deployed it through Coolify. Challenges I faced The first challenge was keeping the agent helpful without giving it too much control. I solved this by exposing small, clearly limited tools instead of one unrestricted command. The second challenge was preventing stale or unapproved scenarios from running. I added revision checks and explicit approval before every calculation. The third challenge was making sure the agent reported real results rather than guessing from the animation. The result tools return exact values, assumptions, warnings, and limitations. I also had to make the flood calculations, terrain files, interface, WebMCP tools, and production deployment work together inside one Docker container. Accomplishments I’m proud of Five complete flood demonstration flows A multi-step WebMCP workflow that works without clicking simulation controls A safe approval boundary before calculations begin Direct result inspection instead of visual guessing Result replay, camera control, and comparison through WebMCP 74 unit and regression tests 23 flood-calculation checks 11 production browser tests A public Docker deployment with no login required What I learned I learned that WebMCP is most useful when a task involves several connected steps, visible state, and important decisions. The agent should not replace the person. The person decides what question to ask and whether a scenario should run. The agent makes the application easier to operate, keeps track of the steps, and returns the evidence needed to understand the result. I also learned that an impressive animation is not enough. A responsible flood tool must show its assumptions, limits, and actual numbers clearly. What’s next I want to add more cities, carefully controlled terrain uploads, downloadable reports, and shared investigation sessions. I also want to test CausaFlow with planners and flood experts to learn which questions and comparisons are most useful in real planning work. CausaFlow is currently a planning and learning tool. A shared canvas for qualitative research where the agent proposes, and the human decides. Like Comment Story Updates Inspiration Coding interview transcripts takes weeks, and most of it is clerical work. The part that matters is small: the handful of quotes that could honestly belong to two different themes. Choosing between them isn't data entry. It's the argument the paper will make. Every AI tool I tried resolved those quotes for me. Hand over a corpus, get back clean labels, and the disagreement that should have shaped the analysis is gone, filed under whichever theme won by a rounding error. I wanted the opposite: the machine grinding through the volume, and the disagreements coming back to me instead of getting quietly filed. What it does Sensemaking Studio is a shared canvas. A researcher drags quotes between themes. An agent works on the same document at the same time: it reads the whole corpus, finds quotes between two themes, ranks them by how contested they are, and presents them to the researcher. Then it stops. The agent has no way to settle a contested quote. This isn't a policy or a line in a prompt. The capability does not exist. It can argue for a reading. It cannot record one. Why WebMCP fits An agent that drives a web app by clicking has to guess what it is looking at, and everything it does arrives as an anonymous mutation. The record cannot tell a researcher's judgment from a stray click. In qualitative research, that record is the product. An analysis is defensible because you can show who decided what and why. Lose the provenance, and you have lost the thing you were making. WebMCP lets the page hand off the operations to an agent instead of the buttons. When the agent moves a quote, it invokes the same command that the researcher's mouse does, so both appear in one log with the author attached. That shared path is also why the guardrail holds. There's no backdoor into the analysis, so the agent's reach stops at the commands that exist. What people and agents can do together now Scoring every quote against two themes and ranking them by how close the contest is: mechanical, and infeasible by hand, somewhere past a few hundred quotes. Deciding any single one: a theoretical judgment that a model should not be making quietly. Those two halves could not sit in the same room before. Batch tools returned a spreadsheet with the ambiguity already resolved and nobody's name on it. Click-driven automation could not read the analysis at all. Now they interleave. The agent surfaces "I don't know whether ChatGPT is actually accurate", filed under policy uncertainty, and points out that the evidence is really about trust. I look. I agree or I don't. I move it. That decision immediately changes what the agent compares against on its next pass, so it gets better at finding my arguments because I keep making them. The workspace also keeps score, running in the right direction. It tracks how often my decisions matched the agent's ranking, so I learn how much to trust it based on my own record rather than its confidence. How I built it Nuxt and Vue, entirely client-side, are deployed as static assets on Cloudflare Workers. One store holds the analysis, and every change goes through it, whether a human or an agent asks. That single write path is what makes attribution reliable instead of aspirational. Thirteen tools register with the browser's model context when a WebMCP host is present, and the page behaves normally when no host is present. Every tool is a research operation rather than a UI action: nothing in the set clicks a card or drags a rectangle. Read-only tools are marked as such and flagged as carrying participant-authored text, so a host knows not to treat an interview quote as an instruction. The scoring is deliberately conservative. A quote has to be clearly relevant to both themes before closeness counts for anything, otherwise two weak scores look like a hard case when they are just noise. Theme definitions are built only from examples that a human confirmed, so the agent's proposals never quietly redefine the thing it is measuring against. 24 unit tests, plus a browser test that registers the full tool set and runs an agent through a complete session from a cold start. I run that against the deployed site too, so the live demo is verified the same way as the local build. Challenges Telling two kinds of hard cases apart took the most thought. A quote that genuinely sits between two themes needs a human. A quote that makes two separate points belongs to both, which is not ambiguity, just dual membership. Measure only how close the scores are, and the two look identical, but they need different handling and a different place in the queue. What I learned My first version had eight tools and a hole I could not see. One of them needed two theme IDs, and nothing in the set returned the list of themes. Reading the docs, it looks complete, because I already know my own theme names. An agent arriving cold was stuck at the first step. Whether an agent can orient itself from nothing turned out to be the only test that mattered. The other lesson is about where a rule has to live. Writing "the agent should not decide" into a prompt is a request, and a model that wants to be helpful will eventually find a way around it. Not building the tool is a different kind of thing, and it's the version I'd rely on. What's next First the dull necessary things. Decisions don't survive a refresh, so the agreement score can't build up over the course of a study. Scoring could be sharper than word overlap. Several researchers should be able to work the same corpus. And it should export into NVivo and ATLAS.ti, where this work actually lives. The bigger thing sits further up the pipeline. Interviews start as audio, and transcription and speaker diarization are both commodity at this point, so putting them on the front of this is mostly integration work. Then you hand it a folder of recordings and get back a live analysis with the contested passages already queued, rather than transcripts you still have to sit down and read. That's the service I'd want to use, and I'd build it under the same restriction. Once most of a pipeline runs unattended, the record of who decided what is doing most of the work of making the output defensible at all. Like Comment Story Updates Inspiration Healthcare conversations contain some of the most valuable information about a patient's condition, but much of that knowledge is lost after every consultation. A patient may explain their symptoms, previous experiences, concerns, and medical journey to one doctor, only to repeat the same story when they visit another provider. Doctors often spend valuable consultation time collecting information and documenting notes instead of focusing on care. We were inspired by a simple question: what if healthcare could remember every conversation? Noa was created to build a continuous memory layer for healthcare, preserving patient stories and transforming them into actionable clinical context. When the WebMCP Challenge launched, we saw an obvious next step. Noa already had structured clinical memory. What it didn't have was a way for agents to reach that memory directly. What it does Noa is a voice-first medical intelligence platform with two core experiences. Before a consultation, patients open a simple web interface and speak naturally about their symptoms, having an AI-guided conversation instead of filling out forms, while Noa asks adaptive follow-up questions and captures their medical story. During consultations, doctors record their conversation with the patient, and Noa converts it into structured clinical documentation, including SOAP notes, patient summaries, triage scores, red flag indicators, and doctor briefings. With WebMCP added, that same clinical intelligence is now reachable by agents directly. A doctor working inside an agent-enabled browser can ask for a patient's history and get a real answer pulled from Noa's records instead of switching tabs and searching manually. An agent can draft a follow-up care plan from an existing SOAP note and hand it to the doctor for review. Voice intake data a patient recorded before their visit can be summarized and surfaced the moment a doctor needs it, cutting the time spent re-explaining a story that was already told. How we built it Noa's core platform runs on AWS. Amazon Bedrock Nova 2 Sonic handles real-time voice conversations and contextual interaction, Amazon Bedrock Nova 2 Lite handles clinical reasoning and structured summaries, Amazon DynamoDB stores patient profiles, consultation sessions, transcripts, and medical memory records, Amazon Cognito manages authentication, and Amazon S3 stores session recordings and generated files. The application is built with Next.js, TypeScript, Tailwind CSS, and WebSocket-based real-time communication. For the WebMCP integration, we built a full agent-facing tool layer on top of that platform. On the server, a spec-compliant JSON-RPC 2.0 endpoint at /api/mcp handles tools/list, tools/call, resources/list, resources/read, prompts/list, and prompts/get, with support for both single-turn requests and SSE streaming for external agents. On the browser side, we implemented the native WebMCP standard directly on document.modelContext, with aliases on window.webmcp and navigator.modelContext, so any page in Noa auto-registers its tools on load and agents in a WebMCP-aware browser can discover and call them without a server round trip. Noa's clinical AI functions, patient and session data, and clinical templates are exposed as MCP tools, resources, and prompts respectively. We used synthetic patient data throughout development and demo to keep the focus on the integration itself. What we built during the challenge A JSON-RPC 2.0 MCP server at /api/mcp, supporting standard MCP methods and SSE streaming for external agents and MCP clients A browser-native WebMCP runtime on document.modelContext (aliased to window.webmcp and navigator.modelContext), letting agents in a WebMCP-enabled browser list and call Noa's tools directly on the page A registry exposing Noa's clinical AI functions as callable tools, including SOAP note generation, clinical insight generation, triage priority scoring, and patient-friendly summary generation Structured clinical resources addressable by URI, covering patient records, consultation sessions, transcripts, and SOAP notes A set of clinical prompt templates exposed through MCP, covering SOAP note generation, triage assessment, and follow-up care planning A React provider that safely attaches the WebMCP runtime across the app and bridges it to Noa's live session state, so an agent can query things like the active consultation or current transcript in real time None of this tooling layer existed before the hackathon. Noa's voice-to-SOAP pipeline and dashboard were already live; the agent-facing protocol, tool registry, and browser runtime were built during the challenge window. Challenges we ran into Designing a system that handles natural human conversation while producing structured clinical information was already hard before WebMCP, since patients describe symptoms differently, give incomplete information, and explain problems in their own words. Adding an agent-facing layer on top raised the stakes on that structure, since a tool an agent calls needs a predictable schema every time, not just an output that reads well to a person. We also had to think carefully about exposing patient data through MCP resources: we used synthetic data throughout and kept access scoped to what a specific tool call needs, rather than exposing broad record dumps. What we learned Building Noa showed us that the future of healthcare AI is not only about generating answers, it's about preserving context. Adding WebMCP showed us the next layer of that: context is only useful if something can act on it. What's next for Noa We want to expand the WebMCP tool surface to cover longitudinal care planning across multiple visits, add scoped permission tiers so different agents can be granted different levels of access to a patient's record, and pursue formal HIPAA compliance review now that clinical data is reachable through an external protocol. Like 1 Comment Story Updates Demo with Bar Chart Demo with Donut Chart Demo with Matrices and Line Chart Inspiration I started Data Canvas with a simple question: what would an analytics app look like if an AI agent worked inside the workspace instead of through a separate chat, API, or UI automation layer? I wanted one thing to stay true throughout the project. If an agent creates a chart, I should see it and keep working with it. If I change a filter, the agent should see that change on its next action. We should not end up with two versions of the analysis. That idea became Data Canvas. What it does Data Canvas is a local-first visual analytics workspace for exploring data in the browser. You can import CSV, TSV, JSON, and NDJSON files, inspect the data, build charts, filter and transform it, create metrics, connect datasets, make selections, add annotations, and undo or redo changes. A WebMCP-connected AI agent works with the same workspace. It can inspect a dataset, analyze it, create or update a visualization, apply filters, highlight data, define metrics, add annotations, and more. Its changes appear directly on the canvas, alongside the work done through the UI. The data and analytical engine run in the browser with DuckDB-Wasm. Data Canvas has no application backend, cloud database, authentication service, or built-in LLM. How I built it The most important architectural decision was to give the UI and WebMCP the same path into the application. Both go through one action dispatcher. A chart created through WebMCP is a normal Data Canvas visualization. A filter created by an agent is the same filter the UI understands. Undo and redo work across actions from either side. DuckDB-Wasm owns the imported rows and runs the analytical queries. Zustand holds workspace state and history. React renders the interface, and ECharts renders the visualizations. The WebMCP layer currently defines 19 semantic tools around real Data Canvas operations. Agents can ask the application to analyze data, create a visualization, apply a filter, define a metric, or connect datasets. They cannot submit arbitrary SQL, JavaScript, DOM selectors, or ECharts configuration. Challenges I ran into The hard part was not registering WebMCP tools. It was making sure I did not build the application twice, once for humans and again for agents. That affected a lot of small decisions. Agent writes carry the workspace revision they observed, so an outdated action cannot overwrite newer human work. Human and agent actions also use the same domain rules instead of maintaining separate implementations. Data access needed the same care. Dumping an entire dataset into every agent call would defeat much of the point of a local-first analytics app. The tools instead expose schemas, statistics, aggregates, bounded previews, and the data needed for a particular analysis. Accomplishments that I'm proud of I'm most proud of the human-agent equivalence in the application. The codebase tests equivalent operations through the human and WebMCP paths and checks that they produce the same workspace state. Agent-created objects remain normal workspace objects, stale writes are rejected, and undo can reverse changes made by either side. I also like that none of this required adding an AI backend to Data Canvas. The application remains a browser-native analytics tool on its own. WebMCP gives an external agent a structured way to participate in it. What I learned I originally thought a capable agent would need very powerful tools. Building Data Canvas pushed me in the opposite direction. The useful tools turned out to be the ones that match operations the application already understands. create_visualization , apply_filter , or create_metric give the agent enough control to do real work while keeping the result valid, visible, and editable in Data Canvas. For me, that is the interesting part of WebMCP. The agent does not need to learn how to click through the interface when the application can expose what those controls actually mean. What's next for Data Canvas The biggest missing piece is local persistence. The current workspace lives in memory, so a reload starts a new session. Next, I want to persist complete workspaces locally and make them portable between browsers while keeping Data Canvas backend-free. I also want to extend the agent evaluations to longer workflows where a human and an agent repeatedly hand the analysis back and forth.
