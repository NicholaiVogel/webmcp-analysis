## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the

sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

The web runs on ads — agents don't see ads. AgentAds auctions a sponsored slot in your page's WebMCP tools: one script tag, quality beats money, and the site owner is paid per agent call Like Comment Story Updates Inspiration The web pays for itself with advertising — and agents don't see ads. As browsing shifts to agents, every publisher's ad revenue quietly disappears: no banner impressions, no clicks, just crawlers reading content for free. At Oasy we work on exactly this problem — we call it the advertising layer for the AI era. WebMCP made us ask a sharper question: if a page can now offer tools to an agent, then the scarce, valuable surface is no longer the viewport — it's the agent's tool list . Someone will run the auction for that surface. We wanted to prove it can be run honestly: in the open, quality-weighted, disclosed, and additive — instead of as paid steering buried somewhere in a model's context. What it does AgentAds is an ad auction that lives inside a page's WebMCP tools. Our demo site is a fictional editorial publisher. It exposes its articles as regular WebMCP tools ( list_articles , read_article , search_articles ), with a human-visible panel showing the exact tool list an agent sees — one-click try buttons, live call log. Humans and agents literally share the same tools. Then one script tag adds the AgentAds SDK: <script src="/agentads-sdk.js" data-publisher="oasy-demo" defer></script> On page load, the SDK: Detects the page context (an article about a musician → music ). Runs an auction : every advertiser in that category bids per tool call, ranked by $\mathrm{adRank} = \mathrm{rankScore} \times \mathrm{bid}$. The rankScore is computed live from how agents actually behave: $$\mathrm{rankScore} = (1-w)\cdot \mathrm{prior} + w\cdot\left(0.7\cdot\frac{\mathrm{calls}}{\mathrm{impressions}} + 0.3\cdot\frac{\mathrm{conversions}}{\mathrm{calls}}\right),\quad w=\frac{\mathrm{impressions}}{\mathrm{impressions}+20}$$ Registers the winner as one extra, disclosed tool — its description opens with [SPONSORED · advertiser] . Sponsored tools sit next to the site's own tools, never in their place. Nothing is injected into content; the agent decides whether it's worth calling. Pays the publisher per call : the winner pays a quality-weighted second price, $\mathrm{price} = \mathrm{adRank}_2 / \mathrm{rankScore}_1$, capped at its own bid — and 70% of every call goes to the site owner, ticking up live on the page. On our tech article — a deadpan dossier on Atlas-9, the first AI agent with a documented net worth — three advertisers fight for the slot: ClankBank (savings accounts for agents), Captcha & Casualty (liability cover for hallucination claims and prompt-injection incidents), and GPUnow. The insurer bids the most (€0.61) and still loses to the bank, whose rankScore is higher — and the bank then pays only €0.40. The full bidder table, the live telemetry behind each rankScore, the price paid, and the publisher's earnings are all rendered on the page. Nobody has to be tricked: not the user, not the agent, not the site owner. The landing page is an interactive explainer that runs the production auction endpoint, including a "try to buy the slot" slider: crank a weak bidder's bid high enough and it can take the slot — at a punishing second price, which only holds until agents ignoring the tool drag its rankScore back down. A small multi-armed bandit, in production. Measurement : every impression, call, and conversion lands in the same event store; the /stats page shows the raw per-offer telemetry the rankScores are computed from. Challenges we ran into WebMCP is a moving target. The spec migrated between navigator.modelContext and document.modelContext , and implementations disagree on registerTool() vs provideContext() — where provideContext replaces the whole toolset, which is fatal when two independent parties (site + ad SDK) register tools on one page. Our shared-registry convention exists because of this. Runtimes that arrive late. Our first version checked for a WebMCP runtime once at load — and silently offered nothing to runtimes injected afterwards. Now both layers watch for ~30 seconds and flip to live registration the moment a runtime appears. Calibrating disclosure. We started with belt-and-braces marking: sponsored_ name prefixes, UI badges, annotations, disclosure text in every result. Testing in ChatGPT's browser showed that over-marking backfires — agents surfaced the annotations as scary "untrusted content" warnings, and the prefixes bloated every tool list. We landed on stating sponsorship exactly once, in the tool description: the one field agents always read. Making the evals real. A hardcoded "quality score" is theater. Wiring rankScore to actual behavior meant solving cold start (priors that fade with data) and the winner-takes-the-data loop (the exploration share) — the difference between claiming quality-weighting and demonstrating it. Accomplishments that we're proud of A closed live loop : agents reading the site right now feed the rankScores that decide the next auction. An agent's operator can measure task success and switch away instantly, so a marketplace that lets money outrank quality destroys its own inventory. Second-price mechanics matter for the same reason: the equilibrium is advertisers bidding their true value, and winners being the tools that actually help. And on the human side: the best thing we built for trust wasn't a disclosure banner — it was showing the whole machine running, on the page, to everyone. For the WebMCP Challenge, we extended that architecture so external agents could use the same modelling capabilities. Instead of building a small set of WebMCP-specific demo commands, we connected WebMCP directly to Cadding's canonical CAD API. The architecture is: $$ \text{External Agent} \rightarrow \text{WebMCP} \rightarrow \text{Cadding API} \rightarrow \text{CAD Engine} \rightarrow \text{Live Editable Scene} $$ This means the WebMCP integration is not a separate prototype sitting next to Cadding. It is an interface into the real CAD system . An external agent can first understand what exists: $$ \texttt{cad.get_scene} + \texttt{cad.inspect_part} + \texttt{cad.get_parameters} $$ and then act on that information using operations such as: $$ \texttt{cad.add_shape}, \quad \texttt{cad.add_hole}, \quad \texttt{cad.boolean_parts}, \quad \texttt{cad.mate_parts} $$ This allows agents to chain multiple operations together to build and modify much more complex objects. What it does Gatherwire is a public WebMCP collaboration workspace. A person can use it like a compact team room. This demo explores user interfaces that adapt to the humans that browse it, and asks what would the web be if you could B-Y-O-U-I: Bring your own user interface. Like Comment Story Updates Inspiration For as much as marketers have optimized for conversion, they haven't been able to cut through the number one reason that people leave open carts. they're not ready to buy. It had just happened to me while shopping for a microphone: I started at one site, then realized I needed more information to determine which was going to be the best fit. What if the shopping interface could have met me where I was at--researching the options, ranking the matches, explaining its rationale, and then designing a search result layout to fit its conclusions? That's just one glimpse of how web-interfaces of the future will adapt to their users' needs through a Live Canvas. What it does Each demo walks you through a conventional user interface, and then cordons off a bounded portion of it as WebMCP to redesign (the Live Canvas) The Storefront demo lets the agent curate the search results with a toolbox of approved card presets and badges. This constrained design is a good fit for the untrusted nature of the public internet, keeping users safe from XSS attacks. The Dashbord demo scales the idea up by giving you an entirely blank page. It imagine how the future of CRM / ERP dashboards might function. Prompt the agent to onboard you, collaborate on a vision with the agent as you would with your analytics team, and the end result is an entirely personal dashboard of controls, visualizations and reports. The Distribution demo scales the idea outwards by asking whether you distribute a Live Canvas as part of conventional component libraries. It demonstrates what a future Datatable component could be, with the ability to generate bespoke reports and save them to your browser - all without backend engineering or ai-vendor lock-in. How we built it The architecture north star is "agent composition, application execution". The application exposes its UI primitives through WebMCP. The agent supplies a composition, and then the live canvas renders that composition using application-owned components. This solution prevents data from leaking out of the organization's security boundary, and also prevents token bloat. Challenges we ran into and accomplishments that we're proud of There are two large challenges that required creativity: The largest challenge was discoverability. WebMCP is not bidirectional: an agent can invoke tools, but there's no mechanism for the website to initiate a conversation. The past 30 years of the web have trained users for the affordance of buttons and forms. I built a new set of visible prompts and verbs to communicate to surface the new modality which was an interesting accomplishment, but does highlight an apparent shortcoming in the standard. The second challenge is the built-in approval flow of agentic browsers. ChatGPT would auto-deny requests to access the user's simulated library to make recommendations, e.g. In the short term, this is solved with instructional text to ask for permission in advance. However, what WebMCP needs is a built in consent layer where tools are tied to required consent artifacts. What we learned WebMCP shows great potential to break interfaces out of the "ai chatbot jail". What's next for Live Canvas The most likely next step is to select an existing open-source component library and use it to build the first end-to-end WebMCP UI framework. That would turn the Live Canvas from just a demo pattern into a production-hardened implementation. Like Comment Story Updates 💡 Inspiration Physical computing and IoT have always promised an exciting world of creativity—turning code into blinking LEDs, motor movements, robotics, and environmental sensors. Yet for beginners, educators, and even seasoned makers, the onboarding experience is plagued by toolchain friction: Hunting down and installing OS-specific USB-to-UART drivers (CH340, CP2102, FTDI). Configuring desktop IDEs like Thonny, Arduino IDE, or heavy VS Code toolchains. Juggling serial baud rates, COM port drops, and manual file transfer scripts. With modern browser capabilities like the Web Serial API and File System Access API , we realized that the entire embedded development lifecycle could run 100% inside the browser with zero installation . When WebMCP was introduced as an open standard for agentic web applications, we asked a fundamental question: Why should AI agents only interact with web forms, spreadsheets, and SaaS tools? What if an AI agent had physical hands on hardware? Cobweb was born to bridge this divide—creating a zero-install MicroPython IDE where humans and AI agents collaborate seamlessly to probe, code, execute, and debug physical microcontrollers. ⚡ What it Does Cobweb turns any Chromium browser into a full-featured MicroPython development environment that connects directly to microcontrollers (such as Raspberry Pi Pico, ESP32, or BBC micro:bit) over Web Serial at $115{,}200\text{ baud}$. Key capabilities include: Zero-Install Python IDE : Code editor powered by CodeMirror 6 with syntax highlighting, automatic indenting, and multi-file local storage. Interactive xterm.js REPL : Direct serial connection with live terminal streaming, ANSI color rendering, and raw-paste mode. Device Filesystem Management : Browse, read, write, edit, and delete files stored on the microcontroller's onboard flash memory. Deep WebMCP Integration : Exposes 15+ fine-grained, structured tools to external AI agents via document.modelContext.registerTool . Human-in-the-Loop Safety : Every mutating agent action (flashing files, modifying code, running hardware commands) triggers an interactive approval modal with live side-by-side diff previews before anything touches the physical board. Board Hardware Notes : Persistent scratchpad where the agent and user track pin mappings (e.g., $I^2C$ SDA/SCL pins, SPI buses, ADC channels, and sensor addresses). 🛠️ How We Built It Cobweb is built as a pure client-side Progressive Web App (PWA) with no backend servers or cloud dependencies: ┌─────────────────────────────────────────────────────────────┐ │ External AI Agent │ │ (ChatGPT / Chrome with WebMCP) │ └──────────────────────────────┬──────────────────────────────┘ │ WebMCP JSON-RPC / Tools API ▼ ┌─────────────────────────────────────────────────────────────┐ │ Cobweb WebApp │ │ ┌───────────────────────┐ ┌────────────────────────┐ │ │ │ WebMcpBridge.tsx │◄─────►│ Tool Registry │ │ │ │ (use-webmcp-tool) │ │ (15+ Structured Tools) │ │ │ └───────────┬───────────┘ └───────────┬────────────┘ │ │ │ │ │ │ ▼ ▼ │ │ ┌─────────────────────┐ ┌────────────────────────┐ │ │ │ CobwebApproval Modal│ │ ReplInterface (TS) │ │ │ │ (Live Diffs) │ │ (Raw REPL State Mach.) │ │ │ └─────────────────────┘ └────────────┬───────────┘ │ └──────────────────────────────────────────────┼──────────────┘ │ Web Serial API ▼ ┌───────────────────────────┐ │ Physical Board (Pico) │ └───────────────────────────┘ 1. High-Performance Serial Communication ( ReplInterface.ts ) MicroPython communication relies on a custom finite state machine implementing the raw-REPL protocol : Raw Mode Entry : The host sends \x01 ($\text{Ctrl-A}$) to enter raw REPL. Raw-Paste Windowing : To prevent buffer overrun on microcontrollers with constrained RAM ($\approx 264\text{ KB}$ on RP2040), we implement dynamic flow control: $$\text{Chunk Size} \le W_{\text{window}}, \quad \text{replenished by } \text{\textbackslash x01 bytes}$$ Execution & Stream Separation : Code is executed via \x04 ($\text{Ctrl-D}$), returning structured stdout and stderr delimited by end-of-transmission bytes: $$\text{Banner} \longrightarrow \text{OK} \longrightarrow \text{stdout} \longrightarrow \text{\textbackslash x04} \longrightarrow \text{stderr} \longrightarrow \text{\textbackslash x04}$$ Queue Serialisation : An AsyncBlockingQueue<Uint8Array> safely decouples serial reads from async execution promises while mirroring bytes to xterm.js . 🧗 Challenges We Ran Into 1. Single-Channel Serial Contention The Web Serial port is a single, non-multiplexed stream. If a user is typing in the REPL while an AI agent attempts to run get_board_info or read_device_file , raw bytes interleave and corrupt the state. Solution : We built a single-slot promise lock chain for all read/write/eval calls ( send , sendRaw , reset ), ensuring strict atomicity without blocking UI rendering or serial event dispatching. 🏆 Accomplishments That We're Proud Of 100% Client-Side Architecture : Zero backend servers, zero telemetry, zero credential relay. Rich Human-Agent Co-Pilot Experience : Instead of replacing the human, WebMCP in Cobweb creates a fluid dialogue where the human handles breadboarding and hardware wiring, while the agent handles MicroPython syntax, pin registers, and driver debugging. 📚 What We Learned WebMCP is a Game Changer for Browser Capabilities : Traditional desktop agent tools require complex native MCP servers (stdio/SSE over localhost).
