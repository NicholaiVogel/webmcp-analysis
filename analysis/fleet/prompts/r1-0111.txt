# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Inspiration Every team has the same five workflows they run by hand every week. Sort the inbox, post the metrics to Slack, follow up on the new leads, fill the report, archive the receipts. The thing nobody admits out loud is that a human in the loop is the most expensive part of automation , not the script. We'd been following Microsoft's Skill Recorder and loved its shape, but it was an Electron app, it required the Copilot CLI, and it didn't have a path for an AI agent to actually call the workflows. WebMCP — a standard for letting web pages expose structured tools to in-browser AI agents — changed that. It said: a website can register its buttons as tools, an agent can see them, and the user can ask the agent to do the thing. We wanted to build that, end to end, on top of Echo. What it does Echo is a multi-composer agent-skill platform. Two halves: The Recorder records a screen via navigator.mediaDevices.getDisplayMedia , ships the frames + a browser-level event timeline to a Describer LLM, and produces a structured SkillPlan (an ordered list of steps, each mapped to a tool from Echo's catalogue, with {{token}} placeholders for anything dynamic). The result is a portable SKILL.md file. The Composer is a 2×2 grid of parallel agents. Each slot owns its own goal, plan, dispatched run, and live progress. Dispatch all four and they run in parallel against a real headless Chromium. The WebMCP integration exposes the whole dashboard to an in-browser agent. Open /compose in Chrome with the WebMCP flag enabled, install the Model Context Tool Inspector extension, and you see 29 tools registered on the page: 5 global tools (available on every Echo page): navigate_echo , get_echo_status , show_toast , wait , echo_ping . 6 composer tools: preview_echo_plan , compose_echo_agent , set_composer_goal , start_planning , dispatch_current_plan , get_composer_state . 7 skills tools: list_skills , get_skill , find_skills_by_name , get_skill_md (returns the portable markdown), create_skill_from_text , dispatch_saved_skill , delete_skill . 5 runs tools: list_runs , get_run , get_run_stats , find_runs_by_goal , cancel_run . 6 agents tools: list_agents , get_agent , dispatch_saved_agent , archive_agent , delete_agent , get_agents_overview . The headline tools: tell the agent dispatch_saved_skill with a skill id and a goal, and a real headless-browser run starts. Tell it get_skill_md with any skill id, and it gets back the full portable markdown it could paste into any other runtime. Tell it compose_echo_agent with a plain-English goal, and it gets back a structured plan, then a runId, then a real stream of progress events. The live site is at echo-one-liard.vercel.app . How we built it The architecture is a single Next.js 16 + React 19 app, deployed on Vercel. The WebMCP layer is a thin src/lib/webmcp/ folder: types.ts — TypeScript declarations for the WebMCP API surface ( document.modelContext.registerTool , the content envelope, the result shape, the annotations). No new dependencies — the API is browser-native. use-webmcp.ts — a React hook that feature-detects document.modelContext , registers a list of tools on mount, and unregisters them atomically on unmount via one AbortController . The tool body is looked up from a ref-map on every invocation so a body-only update never forces a re-register. One file per page: global-tools.ts , composer-tools.ts , skills-tools.ts , runs-tools.ts , agents-tools.ts . Each file exports a buildXxxTools() function that returns the page's tool set. webmcp-badge.tsx — a topbar pill that polls document.modelContext.getTools() every two seconds and shows the live count. Click it for the full list + Inspector link. webmcp-toast-host.tsx — listens for the show_toast tool's echo:webmcp:toast window event and renders a transient notification. Every tool declares its inputs as a JSON Schema ( type: "object" , properties , required , enum ) so the agent can validate before calling. Read-only tools set annotations.readOnlyHint: true ; mutating tools leave it false . The execute function returns a plain JSON-serializable value; the hook wraps it in { content: [{ type: "text", text: JSON.stringify(result) }] } and catches thrown errors as { content: [...], isError: true } . /compose is the headline page — it mounts all five tool sets so the full 29-tool surface is live. The agent does the full "library-inspect → compose-plan → dispatch-run" flow from a single page. Everything else in the project is unchanged: the existing Next.js API routes ( /api/agents/compose , /api/agents/run-autonomous , /api/skills/save ) are what the buttons hit and what the WebMCP tools hit. The WebMCP integration is a pure progressive enhancement — pages work exactly as before if the browser doesn't expose document.modelContext . Challenges we ran into The stale-closure trap. My first pass captured the tool body at registration time. When the page state changed (goal text, plan, runId), the registered tool was still pointing at the old closure. Fixed with the ref-map pattern: the registration wraps the body in a function that looks up the latest body from bodiesRef.current on every invocation. Now a body-only update doesn't force a re-register. Duplicate name collisions across pages. Several tools exist with the same purpose in different files ( list_skills vs list_agents vs list_runs ). Names are unique across the codebase so we never collide, but I added explicit console.warn per failed registration to surface any future collision immediately. An agent landing on /compose for the first time sees 29 tools in a flat list. The tool descriptions had to be clear and self-contained — no "see also", no implicit context. I rewrote every description to be standalone-readable, with explicit inputSchema enums where the value space is bounded (route names, run statuses, agent statuses). What "fully functional" means. The easy win is registering 29 tools. The hard win is making sure the output of every tool is something the agent can act on. get_skill_md returns the portable markdown; dispatch_saved_skill returns a runId and a server message; find_skills_by_name returns summaries with id fields the agent can feed straight into dispatch_saved_skill . A human-sealed WebMCP reading desk that lets agents investigate uncertain handwriting without silently overwriting human evidence basically a shared desk where humans and agents work together Like Comment Story Updates Overview: Eight WebMCP tools help agents inspect handwriting while final decisions stay human-controlled. Stale protection: An outdated proposal is rejected, preventing old AI work from overwriting new human evidence. Human-sealed result: The final export records decisions, evidence revisions, and a SHA-256 integrity hash. Why I made InkWitness Old handwritten documents are often difficult to read. Some letters are faded, damaged or missing. AI can help, but it may also guess a word with too much confidence. In historical records, one wrong name or place can create a lasting mistake. That problem gave me the idea for InkWitness: let the AI help with the investigation, while keeping the final decision with a person. How it works InkWitness uses a synthetic historical ledger with three unclear words. The agent can examine each word, compare it with other letters written by the same hand, check possible answers and suggest a reading. The evidence it uses appears on the page, so the person can understand why that suggestion was made. A suggestion is not automatically accepted. Only the person using InkWitness can accept it, reject it or decide that the word should remain illegible. Why WebMCP matters The person and the agent work on the same visible desk. They are not working with separate copies of the information. The desk also keeps track of revisions. For example, if a person adds a new clue after the agent reads the page, the agent’s old proposal is no longer safe. InkWitness rejects it with STALE_REVISION. The agent must read the latest version and reconsider the evidence. This prevents old AI work from replacing newer human work. How I built it I built the project with HTML, CSS and JavaScript. It has eight native WebMCP tools that allow the agent to read the desk, inspect unclear words, compare handwriting, check possible readings and prepare proposals. The WebMCP tools and the buttons on the page use the same state and functions. I also included manual testing controls so the workflow can still be demonstrated in a normal browser. No real historical documents or personal data are used in the demonstration. The difficult part The hardest part was deciding exactly what the agent should and should not be allowed to do. The agent can investigate and make suggestions, but its tools do not include accepting a reading, declaring a word illegible or sealing the final record. Those actions belong only to the person reviewing the document. I also had to make sure an outdated agent action could not overwrite a newer change. That is why every proposal must include the desk revision that the agent previously read. What I learned This project taught me that making AI safer does not always mean making it less useful. The agent can still do the repetitive work of comparing letters and organizing evidence, while the person handles decisions that require judgment. I also learned how WebMCP can connect an agent directly to the information and controls inside a webpage. Final record After every word has been reviewed, the agent can prepare a provenance packet. The person then chooses whether to seal and export it. The exported receipt includes the evidence, revisions, proposals and human decisions. Its SHA-256 hash helps detect later changes, but it does not prove identity or document authenticity.
