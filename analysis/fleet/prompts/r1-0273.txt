Like Comment Story Updates WebMCP landed in Chrome behind a flag and almost nobody at work had seen it. The pitch — a web page can declare tools that an AI agent calls directly — sounds abstract until you watch it happen. Slides weren't going to do it. So the goal was never "build a product". It was: make the mechanism visible in a room full of people in under five minutes. That single constraint decided everything. If a choice made the app more useful but the mechanism less obvious, the mechanism won. Games turned out to be the right vehicle, for a reason we didn't expect at the start: a game has rules the page can enforce. When an agent tries to move out of turn and the page answers { ok: false, reason: "it's not your turn" }, everyone in the room understands the trust model instantly. You can't get that from a to-do list demo. What it does Duel is a four-game arcade in the browser where your opponent is an external AI agent — and the agent doesn't see pixels. It plays by calling tools the page registers with document.modelContext.registerTool(). Minesweeper duel — a shared 9×9 board, 13 mines, turn-based. Claim a mine correctly and you keep playing. Connect 4 — turn-based, or a one-shot puzzle in single player. Pong — real-time. Yes, real-time, over a request/response protocol. More on this below. Towers of Hanoi — both sides race their own tower against one clock. Five discs, so $2^5 - 1 = 31$ moves is optimal. Nothing leaves the tab. No backend, no API key, no LLM call from the app. The page only registers tools; the intelligence is entirely on the other end of the wire. That's the whole point — the page is the tool provider, not the AI. The design exists to make three moments land: The page announces itself. Open the inspector and the tools are there with names and schemas. Nobody guessed anything. The agent plays, visibly. Every call lands live in the right-hand rail with its arguments and its response. That rail is what turns a game into a WebMCP demo. The tools change on their own. Switch games and an AbortController unregisters the old game's tools and registers the new one's. The inspector's list transforms live. How we built it Vite + TypeScript, no framework, no backend. Every module stays under ~200 lines, which is why each game is split into state / actions / query / render / tools. A dist/ you can serve from anywhere. The interesting engineering isn't the games — it's tool design, and three rules were earned the hard way: Give the agent constraints, not drawings. A tool that dumps the board makes the agent do vision work in text. ms_frontier hands it the deduction already worked out: these cells are provably safe, these are provably mines. c4_analysis does the same. Without those the agent plays badly and the demo falls apart. They are the real work of the project. The description is the code. When the agent plays badly, the fix is almost always in the description string, not the logic. We edited prose far more often than we edited functions. Stop the help short of solving it. Hanoi's hanoi_moves returns the legal moves and says outright that they are not the good ones. Nine tools are registered with document.modelContext.registerTool. Five read, two write the agent's reasoning back into the UI, one gates approval, one verifies recovery. The design rule that mattered most: tools return evidence, never conclusions. There is no analyze_incident(). get_service_health returns p95Ms: 8.13× baseline and stops. The diagnosis has to happen in the model, or the demo is just a scripted animation. Challenges we ran into The API isn't documented yet. I guessed wrong three times. There's no unregisterTool — registration is one-way for the document's lifetime, so React StrictMode's double-mount collides with InvalidStateError: Duplicate tool name; a window-level flag is the only guard that survives both StrictMode and Fast Refresh. And executeTool takes a RegisteredTool handle from getTools(), not a name, with arguments as a JSON string — an object throws Failed to parse input arguments. I found that by writing a probe that tried six encodings. The hardest problem wasn't technical. My rollback worked perfectly when I called it by hand, and the agent refused to call it. It would investigate, propose a plan, get approved — then ask "May I execute the rollback?" and end its turn. Assistants won't invoke destructive tools without re-confirming in chat, and no amount of rewording the tool description changed that. So I inverted it. The rollback now runs inside approvePlan — the click handler. The agent proposes; the human's click executes. That turned a limitation into the better architecture: the agent has no path to production at all. Accomplishments that we're proud of The approval gate is structural, not advisory. The agent has no path to production at all — a human's click is the only thing that changes system state, and approval is bound to the exact service and version proposed. The agent's reasoning is actually part of the workflow. The scenario includes a decoy: a healthy service deployed more recently than the guilty one. An agent that blames the newest deploy gets it wrong. Ours rules it out by combining deploy timing, service health, and dependency direction in the demo scenario. The dashboard reacts to the agent, not the mouse. Service cards highlight as it inspects them; the log panel narrows to its query. That works because the WebMCP tools run inside the page and can update the same state the dashboard displays. I documented an undocumented API. executeTool's signature, the absence of unregisterTool, and the JSON-string argument encoding are all recorded in webmcp.d.ts with the console output that proves them. ## What we learned Tool descriptions are prompts, not documentation. Writing "get valid ids from get_system_status" inside an inputSchema field is what produces tool chaining instead of the agent guessing an id and failing. Return errors, don't throw them. { error, knownIds: [...] } lets an agent self-correct on the next call. An exception dead-ends it, and a stalled agent is the fastest way to lose a demo. External state needs useSyncExternalStore. Tool calls originate outside React, so there's no render pass to piggyback on — and mutating state in place means React never re-renders and the dashboard silently goes stale. Design around the model's caution, not against it. Fighting it cost hours. Accommodating it produced a stronger safety guarantee than the one originally designed. ## What's next for Agent Operations Center More scenarios, randomized — config errors, dependency outages, resource leaks — so the agent can't pattern-match its way to the answer. Competing remedies. Restart, feature flag, and rollback all viable, so the agent has to choose the safest one rather than having only one option. Real backends behind the same tools. Swapping the simulated store for Kubernetes wouldn't change a single tool description. Policy tiers. Low-risk actions auto-approved, high-risk requiring two approvers. Plan, preview, and pack with AI. Just tell ChatGPT what you're bringing, and through WebMCP it automatically generates a physically optimized 3D packing plan broken down by layers and order to pack. Like Comment Story Updates Labled Layers Packed, labeled Empty Closed Duffel bag Backpack Inspiration I always procrastinate packing until the very last minute, then struggle to find what belongs where even if I already have a packing list in mind. After I guess where everything should go and then rearrange my suitcase a dozen times, I finally come to find that it doesn't fit. With AI becoming good at understanding what we need through context and chatlogs, I wanted to create a tool for ChatGPT to express a simple request into something physical and visual that we could actually use. What it does Paqly turns any packing list into a 3D packing plan that you can breakdown into clearly labeled layers. Instead of organizing and planning what to put and where, you can simply tell ChatGPT what you want to bring or even just ask ChatGPT to create a list for you. ChatGPT would then communicate with Paqly directly through WebMCP and create a 3D visual based on the specified suitcase and items. With Paqly, you are able to see where each item should go, which layer it belongs in, the order in which each item should be packed, how much of the suitcase is filled and whether the packing list actually fits. How I built it The core of Paqly is a WebMCP integration that exposes packing functionality directly to AI agents. Rather than requiring an agent to navigate the website like a human and click through forms, Paqly exposes structured tools that allow ChatGPT to send packing information directly to the application. From there, the packing system takes the item dimensions and suitcase constraints, determines an arrangement, groups the result into packing layers, validates the placement, and passes that result into the interactive 3D visualisation. A lot of the work also went into making the output understandable. A mathematically valid arrangement is not very useful if a person cannot tell what they are looking at, so the 3D view includes item labels, separated layers, a re-playable packing order and an interactive suitcase view. Challenges I ran into The hardest part was making the packing plan physically believable rather than just visually impressive. Early versions could technically place objects inside the scene while still producing obviously bad results: items could overlap, float, extend outside the suitcase or leave large amounts of wasted space. This meant I had to treat validation separately from visual rendering and continuously check that the generated arrangement actually made sense. Another challenge was the WebMCP integration itself. I wanted the AI to interact with Paqly through structured WebMCP tools rather than simply using browser automation to click around the interface. Finally, 3D packing is much harder than displaying a normal list. Different objects have different dimensions, orientations and levels of compressibility, while the final result still needs to be simple enough for someone to reproduce with a real suitcase. Accomplishments that I'm proud of I'm most proud that Paqly goes beyond giving packing advice. You can describe what you are trying to pack like thinking aloud and get back an actual spatial plan showing where everything should go, and the combination of AI, WebMCP and interactive 3D makes the result easier to obtain and follow. I'm also proud of how much the physical packing and visualisation improved throughout development. What started as basic object placement became a layered system with packing order, fit validation and a much clearer 3D representation of the suitcase. What I learned The biggest thing I learned is that giving AI tools is much more interesting than simply putting an AI chatbot inside a website. WebMCP lets the AI interact with the actual functionality of Paqly. The AI handles the vibes, while Paqly handles the specialised packing logic and visualisation. I also learned how quickly a 3D system can look correct while being physically wrong. Building this forced me to think much more carefully about constraints, validation and the difference between generating something that looks good and generating something that actually works. What's next for Paqly The next step is making Paqly understand more about the real world. I want it to support a much larger library of real items, better modelling of soft and compressible objects, different suitcase types and more advanced physical optimisation to better simulate a real packing environment. I want it to be able to mathematically find not just the optimal placement for each item, but the optimal fold, the optimal angle, and other features that make a paq perfect.
