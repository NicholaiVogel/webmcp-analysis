# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

CacheLens uses WebMCP to let ChatGPT inspect LLM traces, find prompt-cache waste, explain why it happens, and simulate fixes that cut API cost. Like Comment Story Updates CacheLense WebMCP Inspiration LLM applications repeatedly send large amounts of identical context: system prompts, tool definitions, policies, and conversation history. Prompt caching can make that repeated input dramatically cheaper—but only while the cacheable prefix remains stable. A seemingly harmless change near the beginning of a prompt can invalidate cache reuse for everything that follows. Dynamic metadata, changing instructions, timestamps, or volatile content placed at the wrong cache boundary can quietly cause an application to pay to process thousands of largely unchanged tokens again. The difficult part is that developers usually cannot see why this is happening. That led to CacheLens: a developer tool for making prompt-cache behavior observable, identifying where prefix reuse breaks, explaining likely causes, estimating the financial impact, and recommending concrete fixes. The WebMCP Challenge suggested a natural next step: instead of requiring developers to manually interpret every trace and diagnostic, let ChatGPT inspect CacheLens directly through structured capabilities exposed by the live application. What it does CacheLens WebMCP turns prompt-cache diagnostics into a collaborative workflow between the developer, the web application, and ChatGPT. A developer can open a CacheLens trace and ask questions such as: Why is my cache hit rate low? Where is the cacheable prefix breaking? Which content is changing? How many stale tokens are being unnecessarily rewritten? What is that costing me? For an identified break, how much could be saved if the stable and volatile content were split correctly? Through WebMCP, ChatGPT discovers three domain-specific tools directly from the page: list_traces explain_cache_behavior estimate_split_savings Rather than scraping the DOM or requiring the user to copy diagnostic data into chat, the agent asks CacheLens directly for the underlying analysis. For example, one real captured trace reports a 44.3% provider-measured cache hit rate , 3 of 3 avoidable prefix breaks , and 28,175 stale tokens rewritten . CacheLens identifies the volatile cache boundary and can estimate the savings for a specific affected turn while clearly stating the assumptions and limitations of that estimate. The human remains in the loop through the CacheLens interface while ChatGPT reasons over the same application state through WebMCP. The workflow becomes: observe → diagnose → explain → estimate → improve How we built it CacheLens captures and analyzes LLM request traces while preserving the structure needed to understand prompt-prefix reuse. Its existing analysis engine compares successive requests, determines where stable prefixes diverge, separates stale tokens from genuinely new tokens, attributes likely causes, and estimates cache-related waste. For WebMCP, we deliberately reused that analysis rather than creating a second implementation. A thin serialization layer projects CacheLens analysis objects into safe application data. A small read-only HTTP server exposes the trace catalog and analysis endpoints, and a lightweight browser interface registers the three WebMCP tools through document.modelContext . The WebMCP tools use constrained inputs: trace identifiers are resolved through an explicit server-side catalog rather than arbitrary filesystem paths, and the tools expose no shell commands, writes, credentials, or mutation operations. The tools are intentionally higher-level than UI automation. CacheLens does not expose actions such as "click this button." It exposes meaningful developer operations: list available traces, explain cache behavior, and estimate the savings associated with splitting a specific identified cache break. That became one of the most important design principles of the project: WebMCP is most useful when a website exposes meaningful application capabilities, not simply another way to operate its interface. Challenges The first challenge was identifying cache waste accurately. Prompt caching is prefix-sensitive, so a small mutation can force a much larger region of otherwise unchanged input to be rewritten. Detecting that two strings differ is easy. Determining which divergence caused expensive cache invalidation—and separating stale tokens from genuinely new ones—is considerably more useful. The second challenge was presenting the result in terms developers care about. Token counts alone are abstract, so CacheLens connects structural changes to cache behavior and estimated cost while distinguishing measured provider usage from heuristic token estimates. The WebMCP integration introduced another challenge: deciding what an AI agent should actually be allowed to do. Exposing every internal operation would create a large and confusing tool surface. Exposing only low-level UI controls would miss the purpose of WebMCP. We settled on three small, read-only, domain-specific tools corresponding to real developer questions. We also deliberately avoided a tempting feature: a general-purpose "simulate fix" tool. CacheLens does not currently model arbitrary prompt reorganizations or predict a new cache-hit rate. Instead, estimate_split_savings performs one narrow counterfactual supported by measured analysis: for an identified cache break, estimate the cost difference if the unchanged portion could have been read from cache rather than rewritten. Keeping that boundary explicit made the result more defensible. What we learned The project reinforced an important lesson about AI infrastructure: optimization problems are often observability problems first. Prompt caching can provide substantial savings, but developers cannot optimize behavior they cannot see. We also learned that WebMCP changes the relationship between AI agents and web applications. Instead of treating a website as a collection of pixels, DOM elements, and buttons, an application can explicitly describe the capabilities it intends to offer an agent. For CacheLens, ChatGPT does not need to guess what a chart means or scrape text from a dashboard. It can ask the application directly for the underlying diagnostic information and help the developer reason about it. We validated this end to end in both Google Chrome with WebMCP enabled and ChatGPT's built-in browser . In ChatGPT, all three tools were discovered and invoked through natural-language requests while the page's WebMCP activity panel displayed the corresponding calls. That combination—structured application capabilities, shared live application state, and human oversight—is what makes WebMCP particularly compelling to us. What's next CacheLens can expand beyond individual traces into continuous monitoring of production LLM applications: detecting regressions in cache efficiency, comparing deployments, identifying recurring sources of prompt instability, and surfacing optimization opportunities over time. Its current ingest path focuses on Anthropic-format request traces; additional provider adapters are a natural next step. More broadly, we see WebMCP as a way to turn developer tools from passive dashboards into active collaborators. CacheLens started by answering a simple question: Where is my LLM application wasting tokens? With WebMCP, a developer can now ask that question directly—and let CacheLens and ChatGPT investigate the evidence together. A sticky-note board where the agent is a teammate, not a script. It claims notes, moves them and comments back — running in your browser session, so it never sees a credential. Like Comment Story Updates The agent flags a note as four tasks in one, you answer on the note, it reports back when done. Claim pills show what the agent is working on right now. Badges show which notes it wrote. Every board merged into one view, with the agent's work visible across all of them. Inspiration Adding MCP to Pinnwall was already on my list. I use it as my own sticky-note board and kept wanting an assistant that could tidy it up, but not enough to build a whole server with its own auth just for that. I hadn't heard of WebMCP before this hackathon. It turned out to be the shape I actually needed, so I finally built it. What it does Pinnwall is a sticky-note board with no database. With WebMCP, an agent works it with you. It has 13 tools: read the board, create and move notes, add columns, switch the board you're looking at. It can also claim a note, so a marker appears before it starts, and comment on one to say what it did or ask you something. You answer on the note. Anything the agent writes gets badged, so you can always tell who did what. Why WebMCP fits this A board is shared state that two people edit. Before, I had two bad options: let an agent click through the UI from screenshots, which is slow and breaks every time I touch the CSS, or stand up an MCP server with its own auth and deploy, just so something could edit a board I'm already signed into. WebMCP skips both. The tools run in the page, on my session. The agent can do what I can do and nothing more, there's no key to leak, and access ends when I close the tab. Concretely: one note on my board said "ship pricing page, update the FAQ, brief support, schedule the newsletter." Splitting that by hand is four notes typed, four drags, then delete the original. Now it's one sentence, and I watch the agent claim it, split it, and tell me what it did. Then I answer it on the note. That last part is the bit I didn't expect to care about — the conversation stays on the work instead of disappearing into a chat window. How I built it Node, Express, vanilla JS. No build step, no new dependencies. All the tools sit in one file. Each is registered with document.modelContext.registerTool and calls the same fetch helper the buttons call, so the agent rides my session cookie and hits the same CSRF check and validation as a click. They take names, not ids. move_note({ note: "brief support", column: "Done" }) finds the note from a piece of its text and tells the agent what it matched if there's more than one. Pinnwall itself predates the hackathon. The agent side is all new. WEBMCP.md in the repo has the split. Challenges I ran into Mirroring my REST API one to one gave me tools the agent used badly. It doesn't have ids and it thinks in names, so half its calls missed. Making every tool resolve by name fixed more than anything I did on the server. The board reloads itself after the agent writes. The first version did that even while I was typing in a note, and wiped what I'd written. Now it waits until I stop. Accomplishments that I'm proud of No new dependencies, no API key, no second service. You sign in normally and the agent can do what you can do. It's also additive. Existing Pinnwall installs run unchanged and old notes work without a migration. What I learned The useful part of WebMCP is the session, not the protocol. Running in the page turns authorisation from the hardest part into a non-problem. And you have to build for two actors from the start. Almost every bug worth fixing came from assuming only one of us was touching the board at a time.
