## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.

The model does the judging and the editing, and you get whichever boundaries it computed. I wanted the opposite division of labour. An agent is good at reading a transcript and saying which stretches stand on their own. A human is good at watching the footage and feeling where a cut lands. WebMCP made it possible to put both in the same page, editing the same clip, with the browser keeping both honest about who changed what. A cutlet is a small cut. Small cuts, served fresh. What it does Cutlet is a rough-cut editor for spoken video. It is not a clip finder; no model scores your footage. The page holds the video, a transcript broken into sentences with stable ids, and a rail of clips. The agent reaches all of it through ten WebMCP tools registered on the top-level document. The core loop is anchor and expand : You click the sentence that must survive. The agent reads a window around it and proposes a clip as a range of sentence ids, s0009–s0013 , never floating timestamps. The player runs exactly that range and stops. You drop a line or move an edge. The clip's revision bumps. The agent's next write carries the revision it last saw. Yours is newer, so the write is refused with the real revision in the error. It calls get_editor_state and revises from your edit, not over it. cut_clip c2 keep s0008,s0010,s0011,s0013 → revision 2, 3 pieces, 37s ↓ human drops s0011 in the transcript → revision 5 cut_clip c2 expectedRevision 4 → REFUSED "it is now 5" get_editor_state → sees the real cut The active clip is coloured by who last touched it: blue while it is the agent's proposal, amber the moment you edit it, in the transcript, the timeline and the card. Beyond the loop: "find the best clips in this" makes the agent skim the whole transcript and create one clip per moment, each with a title and a reason. "Cut this to forty seconds" turns a clip into several pieces with gaps, and playback jumps the gaps. Every dropped sentence stays visible, struck through, with a control to put it back. When the recogniser missed a full stop, you select the words you want and make them their own sentence with their own id, so a boundary you can point at becomes a boundary the agent can name. The agent can split too. The agent gets every cut twice: the source transcript, and the sequence as it plays , with each gap marked by what was dropped and how long it ran. Word-level JSON is primary; Whisper, Deepgram and ElevenLabs Scribe all parse, with SRT and VTT as coarse fallbacks. Sentence splitting handles abbreviations, initials, rhetorical pauses and a clause backoff at the length ceiling. Preview is the native <video> element, with the range boundary enforced on requestAnimationFrame , because timeupdate fires at about 4 Hz and visibly overshoots. Export is the single-thread @ffmpeg/core , lazy-loaded on first use. Single-thread means no SharedArrayBuffer , which means no COOP/COEP headers, which is why it deploys to plain static hosting. Tools register through document.modelContext.registerTool on the top-level document, with an AbortController for teardown. Read tools carry readOnlyHint . Keyboard. The transcript is a listbox with one tab stop: arrows move the anchor, shift extends it, Enter plays, ⌘-click banks a range. Ids stop being positional the moment you split. Renumbering after a split would silently repoint every later id at its neighbour, and a stale id that resolves to the wrong sentence is worse than one that fails to resolve. That is why the sequence timeline is read-only, why sentence splitting exists, and why the revision check works at all. Optimistic concurrency turned out to be the right primitive for a human and an agent sharing one document. What's next More WebMCP hosts as they ship. Word-level trims inside a split. Like Comment Story Updates MCPx — a reliability runtime for consequential WebMCP workflows. A real AI Operations Agent observes application state and delegates consequential multi-service operations to MCPx after human approval. Every workflow transition is persisted in a PostgreSQL-backed transaction ledger for inspection and recovery. After approval, MCPx compensates completed operations in reverse dependency order and verifies remote resource removal. Routing recovers from an uncertain write, Frontend fails before commit, and MCPx pauses before destructive compensation for human approval. Inspiration While building with WebMCP, I kept thinking about one question: What happens if an agent performs an action, the application successfully makes the change, but the response never gets back to the agent? For example, imagine an agent creates a routing rule. The route is successfully created, but the acknowledgement gets lost. From the agent's point of view, it looks like the request failed. But did it actually fail? If the agent simply retries, it could create the same resource twice. If it assumes the action worked, it could continue a workflow based on something that may not exist. The problem gets even harder when an agent is working across several applications. Maybe the first three actions succeed and the fourth fails. Now you have resources left behind and someone has to figure out what actually happened. That was the idea behind MCPx . WebMCP makes structured agent actions possible. MCPx makes those actions reliable. What it does MCPx is a reliability runtime for multi-step WebMCP workflows. The main idea is simple. For consequential actions, MCPx thinks about three things: Execute → Inspect → Compensate For example: create_route → get_route → delete_route Execute performs the action. Inspect asks the application for the actual state of that action. Compensate provides a way to safely undo it if the larger workflow fails. This becomes especially useful when something goes wrong after an action has already been sent. Instead of immediately assuming failure, MCPx can put the operation into an explicit state called IN_DOUBT . It then asks the application that owns the resource for ground truth. If the resource actually exists: IN_DOUBT → RECONCILING → RECOVERED The workflow continues without blindly performing the original mutation again. If something later fails for certain, MCPx stops the workflow and asks the human operator before performing destructive rollback. Once approved, it compensates the completed operations in reverse dependency order and checks each application again to confirm that the resources created by that transaction are gone. Why WebMCP? This is where WebMCP became particularly interesting to me. The applications involved in a workflow should remain the source of truth for their own resources. MCPx should not need direct access to every application's database just to determine whether an operation succeeded. Instead, each application can expose structured capabilities through WebMCP. In MCPx, the reference applications register tools using: document.modelContext.registerTool(...) The MCPx Browser Runner discovers tools from the authorized applications using: document.modelContext.getTools({ fromOrigins: [...] }) It then executes the native browser tools through: document.modelContext.executeTool(...) So MCPx coordinates the workflow, while each WebMCP application still owns and understands its own state. That separation is a big part of the project. The demo I built a four-step reference workflow to show what happens when things don't go perfectly: Database → Compute → Routing → Frontend Database succeeds. Compute succeeds. Routing is where things get interesting. For the demo, I intentionally inject an acknowledgement-loss fault after the Routing service commits its resource. MCPx doesn't know yet whether the write happened, so Routing becomes IN_DOUBT . Instead of blindly calling create_route again, MCPx calls get_route . The Routing application confirms that the route actually exists, so MCPx marks the operation RECOVERED and continues. Then Frontend deliberately rejects before committing its operation. This is a confirmed failure, so the transaction stops in AWAITING_COMPENSATION_APPROVAL . The human operator can see what happened and approve the rollback. MCPx then compensates: Routing → Compute → Database After every compensation, it calls the application's inspection tool again to verify that the resource created by this transaction is actually absent. The transaction finally reaches COMPENSATED . Humans and agents working together I didn't want MCPx to become another AI agent. I wanted it to solve a different problem. The way I think about the architecture is: The agent decides what should happen. The human controls important safety boundaries. MCPx makes sure the multi-step operation is executed reliably. WebMCP gives MCPx structured capabilities to work with across the applications. To test that idea outside the MCPx dashboard, I integrated MCPx with FileFlow , a distributed file-processing project I had already built. During the challenge, I extended FileFlow with an AI Operations Agent. The agent can observe real information about the FileFlow pipeline, including queue state, worker heartbeat and failed jobs. For low-risk situations, such as an eligible failed job, the agent can take a bounded recovery action itself. But when it wants to perform a consequential multi-service workspace operation, it asks for human confirmation and then delegates the actual workflow to MCPx through @mcpxx/sdk . That separation became one of my favourite parts of the project: the agent doesn't need to reinvent retries, reconciliation, rollback and transaction durability every time it wants to do something consequential. How I built it MCPx is a TypeScript monorepo containing: a Next.js coordinator and control plane a browser WebMCP Runner a PostgreSQL-backed transaction and event ledger a DAG workflow engine execute / inspect / compensate reliability contracts explicit IN_DOUBT , RECONCILING and RECOVERED states human-approved compensation post-compensation verification four independent WebMCP reference applications the @mcpxx/sdk package for external applications and agents One architectural rule was particularly important to me: MCPx should not secretly bypass WebMCP for the actual reference-service mutations. The SDK can submit a workflow to the MCPx coordinator, but the work waits for an active browser runner. The Browser Runner discovers the appropriate WebMCP tool from the application's origin and executes it through the browser. The result is then reported back to the durable coordinator. Challenges I ran into One of the hardest bugs came from RegisteredTool . At first, it seemed reasonable to discover a WebMCP tool, store it and execute it later. That didn't work. A native RegisteredTool contains browser-owned context associated with the page or frame that registered it. Treating it like normal serializable data caused execution to fail. The solution was to store only the tool's metadata. When MCPx actually needs to execute something, the Browser Runner discovers the tools again and passes the fresh native RegisteredTool directly to executeTool(...) . Another challenge was changing how I thought about failure. I initially thought mostly in terms of success and failure. But after a request has been dispatched, there is a third possibility: we simply don't know yet. That is why IN_DOUBT became such an important state in MCPx. The final challenge was rollback.
