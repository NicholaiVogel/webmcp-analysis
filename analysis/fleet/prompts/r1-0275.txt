# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates CacheLense WebMCP Inspiration LLM applications repeatedly send large amounts of identical context: system prompts, tool definitions, policies, and conversation history. Prompt caching can make that repeated input dramatically cheaper—but only while the cacheable prefix remains stable. A seemingly harmless change near the beginning of a prompt can invalidate cache reuse for everything that follows. Dynamic metadata, changing instructions, timestamps, or volatile content placed at the wrong cache boundary can quietly cause an application to pay to process thousands of largely unchanged tokens again. The difficult part is that developers usually cannot see why this is happening. That led to CacheLens: a developer tool for making prompt-cache behavior observable, identifying where prefix reuse breaks, explaining likely causes, estimating the financial impact, and recommending concrete fixes. The WebMCP Challenge suggested a natural next step: instead of requiring developers to manually interpret every trace and diagnostic, let ChatGPT inspect CacheLens directly through structured capabilities exposed by the live application. What it does CacheLens WebMCP turns prompt-cache diagnostics into a collaborative workflow between the developer, the web application, and ChatGPT. A developer can open a CacheLens trace and ask questions such as: Why is my cache hit rate low? Where is the cacheable prefix breaking? Which content is changing? How many stale tokens are being unnecessarily rewritten? What is that costing me? For an identified break, how much could be saved if the stable and volatile content were split correctly? Through WebMCP, ChatGPT discovers three domain-specific tools directly from the page: list_traces explain_cache_behavior estimate_split_savings Rather than scraping the DOM or requiring the user to copy diagnostic data into chat, the agent asks CacheLens directly for the underlying analysis. For example, one real captured trace reports a 44.3% provider-measured cache hit rate , 3 of 3 avoidable prefix breaks , and 28,175 stale tokens rewritten . CacheLens identifies the volatile cache boundary and can estimate the savings for a specific affected turn while clearly stating the assumptions and limitations of that estimate. The human remains in the loop through the CacheLens interface while ChatGPT reasons over the same application state through WebMCP. The workflow becomes: observe → diagnose → explain → estimate → improve How we built it CacheLens captures and analyzes LLM request traces while preserving the structure needed to understand prompt-prefix reuse. Its existing analysis engine compares successive requests, determines where stable prefixes diverge, separates stale tokens from genuinely new tokens, attributes likely causes, and estimates cache-related waste. For WebMCP, we deliberately reused that analysis rather than creating a second implementation. A thin serialization layer projects CacheLens analysis objects into safe application data. A small read-only HTTP server exposes the trace catalog and analysis endpoints, and a lightweight browser interface registers the three WebMCP tools through document.modelContext . The WebMCP tools use constrained inputs: trace identifiers are resolved through an explicit server-side catalog rather than arbitrary filesystem paths, and the tools expose no shell commands, writes, credentials, or mutation operations. The tools are intentionally higher-level than UI automation. CacheLens does not expose actions such as "click this button." It exposes meaningful developer operations: list available traces, explain cache behavior, and estimate the savings associated with splitting a specific identified cache break. That became one of the most important design principles of the project: WebMCP is most useful when a website exposes meaningful application capabilities, not simply another way to operate its interface. Challenges The first challenge was identifying cache waste accurately. Prompt caching is prefix-sensitive, so a small mutation can force a much larger region of otherwise unchanged input to be rewritten. Detecting that two strings differ is easy. Determining which divergence caused expensive cache invalidation—and separating stale tokens from genuinely new ones—is considerably more useful. The second challenge was presenting the result in terms developers care about. Token counts alone are abstract, so CacheLens connects structural changes to cache behavior and estimated cost while distinguishing measured provider usage from heuristic token estimates. The WebMCP integration introduced another challenge: deciding what an AI agent should actually be allowed to do. Exposing every internal operation would create a large and confusing tool surface. Exposing only low-level UI controls would miss the purpose of WebMCP. We settled on three small, read-only, domain-specific tools corresponding to real developer questions. We also deliberately avoided a tempting feature: a general-purpose "simulate fix" tool. CacheLens does not currently model arbitrary prompt reorganizations or predict a new cache-hit rate. Instead, estimate_split_savings performs one narrow counterfactual supported by measured analysis: for an identified cache break, estimate the cost difference if the unchanged portion could have been read from cache rather than rewritten. Keeping that boundary explicit made the result more defensible. What we learned The project reinforced an important lesson about AI infrastructure: optimization problems are often observability problems first. Prompt caching can provide substantial savings, but developers cannot optimize behavior they cannot see. We also learned that WebMCP changes the relationship between AI agents and web applications. Instead of treating a website as a collection of pixels, DOM elements, and buttons, an application can explicitly describe the capabilities it intends to offer an agent. That combination—structured application capabilities, shared live application state, and human oversight—is what makes WebMCP particularly compelling to us. Its current ingest path focuses on Anthropic-format request traces; additional provider adapters are a natural next step. More broadly, we see WebMCP as a way to turn developer tools from passive dashboards into active collaborators. CacheLens started by answering a simple question: Where is my LLM application wasting tokens? With WebMCP, a developer can now ask that question directly—and let CacheLens and ChatGPT investigate the evidence together. Aergebra is a shared geometry workspace where humans edit shapes and AI reads and acts on the exact same geometry, relationships, and constraints through WebMCP. Like Comment Story Updates The name Algebra comes from al-jabr — "the reunion of broken parts." Aergebra reunites the two broken halves of agent–human work on the web: what the agent sees (screenshots) and what you see (prose about your own screen) — into one live drawing both of you can touch. Inspiration Watch an agent help a human with anything spatial and you see the same failure twice: the agent "sees" the page by screenshotting it and squinting; the human "sees" the agent's work as prose ( "I placed a vertex near the top-left" ). Neither is looking at the thing. We wanted one shared object both kinds of hands can touch: live geometry . What it does Aergebra is a geometry workroom — points, segments, circles, polygons, groups, photo/SVG underlays, a live algebra Inspector — where the document is the truth and the canvas is its projection. With WebMCP the page registers 16 tools via document.modelContext.registerTool() , so an agent in a WebMCP-capable browser gets the whole kit as structured tools: Construct — points/segments/circles/polygons, groups, frames — including over an imported photo. Mean — attach meanings ; the board labels things by what they ARE, never arbitrary letters. Tools accept a meaning as the name: {name: "Table 2"} . Point — aergebra_highlight lights objects up so the human sees exactly what the agent means. No more "the circle on the left". Read as data — aergebra_get_algebra returns the construction as algebra; aergebra_get_view returns the camera as data. The agent never screenshots. Status in colour — a four-colour status vocabulary (at rest / blocked / ready / willing), visible in a legend on the board, so "Nan's path is blocked till Thursday" is one brown line everyone can read. Every mutation — human tap, typed command, or agent tool call — goes through the SAME façade and lands on the same append-only receipt line. Agent calls echo live in the same command-line output a human's typed calls use. One board, one history, two kinds of hands. The demo is a real session The middle of the video is an actual conversation: Andrea tells the agent Saturday's wedding floor plan in plain words ("table 2's nan… speaker cable till thursday… table 4 on hold"); the agent builds, labels, colours and reads the board back — every board change a real WebMCP tool call, captured live. Why this is a strong fit for WebMCP Geometry is the worst case for pixels-in/prose-out and the best case for WebMCP: the page's internal model is already structured, so exposing it as tools is lossless. And it's bidirectional shared state : the agent reads the model as data, writes through receipted tools, and points at what the human is looking at. The human's UI and the agent's tools are projections of one document. Who this is for Anywhere a page's model is already graph/geometry: entity-relationship and data modelling, event floor plans and seating charts (our own business), process and project maps, tutoring. Any canvas-like app — whiteboards, CAD, slides, maps — can copy the pattern. How we built it TypeScript + Vite + JSXGraph, no frameworks. A receipted document model ( src/model.ts ) is the single source of truth; a typed façade ( src/toolapi.ts ) is the ONLY write path; src/webmcp.ts maps it onto document.modelContext.registerTool() (navigator fallback, late-injection retries) with JSON-Schema inputs. A badge reports WebMCP · 16 tools live when a model context is present; without one the page runs unchanged. Tested against native WebMCP in Chrome 152. Built during the submission period Everything in the repository was built during the Challenge submission period; the commit history is the evidence — the engine first, station by station, then the WebMCP integration on top. Challenges One façade kept honest (if the agent's path and the human's path diverge, receipts lie); resolving objects by meaning, not letters; auto-fit that never clips; Windows shells mangling --base=/aergebra/ mid-deploy. What's next User-declared colour meanings ("red = check on nan" is your board's meaning), outline detection over photos, .scu / .acu exports for agents, and a live mission clock — shared geometry applied to time.
