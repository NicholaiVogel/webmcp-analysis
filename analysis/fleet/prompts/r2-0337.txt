# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Inspiration Agent workflows are usually reviewed after they have already become code, prompts, and framework-specific configuration. At that point, important decisions such as branching, tool use, approval gates, parallel work, retries, and failure paths are scattered across files and difficult to understand as one system. I built GraphContract because I wanted humans and coding agents to agree on agent behavior before implementation—not debug that agreement afterward. What it does GraphContract is a human-governed planning layer for agent systems. It gives a person and a coding agent a shared visual canvas where they can design, review, revise, and freeze an agent workflow as a structured contract. A user can start from a blank canvas or a reusable workflow pattern. A coding agent reads the currently accepted graph through WebMCP and proposes a structured revision. GraphContract renders that candidate separately, shows what was added, changed, or removed, and keeps the accepted graph locked until the human decides what happens next. The human can inspect the proposal, request changes, approve it, or reject it. Once the contract is accepted, GraphContract derives deterministic branch scenarios, lets the user inspect each route on the canvas, freezes the reviewed contract, and exports implementation handoff artifacts. The canvas supports typed Start, Task, Agent, Tool, Human, Merge, End, and Subgraph structures; normal, conditional, command, fallback, bounded-loop, and dynamic Send ×N routing; human-in-the-loop gates; sensitive-effect policies; deterministic scenarios; and a read-only runtime projection. How WebMCP powers the collaboration GraphContract deliberately exposes exactly three browser-native WebMCP tools: get_graph reads the accepted contract, its revision identity, validation state, and outstanding human feedback. propose_graph_changes submits typed operations against a known revision and produces a review-only candidate. get_branch_scenarios reads the deterministic paths derived from the accepted graph. The small tool surface is intentional. The agent can inspect and propose, but it cannot approve, reject, freeze, unfreeze, answer human gates, control runtime execution, or download artifacts. Those actions remain visible and human-owned in the interface. This is where WebMCP adds real value. A graph has stable identities, topology, validation rules, revisions, and authority boundaries. Asking an agent to infer those from screenshots or cursor coordinates would be fragile. WebMCP lets the agent work with the graph as structured data while the website remains the source of truth and the place where consequential decisions are made. How I built it The application is built with React, TypeScript, React Flow, Zustand, and Zod. React Flow powers the canvas, Zustand manages the local workspace and proposal lifecycle, and Zod enforces schema and migration boundaries. The public application is deployed on Netlify with a custom domain. I also created a portable GraphContract skill published from the website. A browser-capable coding agent can discover the skill, learn the inspect → propose → review → revise → freeze → handoff lifecycle, and then use the three WebMCP tools consistently. Codex helped throughout the project: researching real agent patterns, shaping the domain model, implementing the canvas and proposal workflow, debugging browser behavior, and building the test library. Challenges I faced The hardest part was not drawing nodes. It was keeping the experience truthful under human–agent collaboration. I needed one accepted graph and a separate proposal candidate; atomic validation without silently repairing agent input; deterministic scenarios that remain bounded around loops and dynamic parallelism; and runtime observations that never become editable design truth. I also had to keep the interface understandable while representing nested subgraphs, human gates, Merge reducers, Send ×N workers, and multiple routing modes. Clear visual diffs with request-changes, approval, and rejection flows. A tool added to the registry appears in both, and edits behave identically — same validation, same undo, same activity toasts, same prompt history — whichever transport the call came in on. How I built it blnq is an Express + Monaco + Yjs app with a plugin system; the MCP server, AI chat, Baseline and spellcheck tools are all plugins. The accessibility engine runs inside the preview iframe and posts results up to the editor, so the panel a human reads and the result an agent reads come from the same run. WebMCP was around 350 lines: a client module that fetches tool descriptors and calls registerTool() for each (with readOnlyHint annotations and MCP-shaped { content } results including images), and a server endpoint that Zod-validates and runs the shared handler. The endpoint is same-origin only and still requires the tab's random bridge ID; the browser handles user consent on its side. What I learned The accessibility audit turned out to be the most valuable thing blnq can hand an agent. A screenshot tells a model roughly what it built; a WCAG report with the offending element and a fix hint tells it exactly what to change. Structured, model-readable audit output beat any amount of prompt engineering. And WebMCP inverts the usual relationship: the page stops being something an agent scrapes and becomes something it calls . Once you have a decent tool registry, the browser becomes the integration layer for free.
