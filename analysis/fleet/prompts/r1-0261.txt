# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A tutor that is bidirectional: the agent sees what the learner actually did, and the learner sees and approves everything the agent actually proposes. LabMate is our answer. What it does LabMate is a 15-minute high-school physics inquiry around one LED circuit, following the scientific method: Predict → Design → Evidence → Reflect . The learner states a prediction ("if resistance decreases, the LED gets brighter because current increases") and locks it. The hypothesis and the final conclusion are learner-owned : visible to the agent, writable by no tool. Through WebMCP, the agent sees the exact live bench — voltages, saved trials, the current stage, model limits, and the page's revision number. It proposes one fair experiment at a time. The proposal appears as a preview card and touches nothing until the learner approves, edits, or rejects it. The demo's climax is a confound challenge: the learner changes the voltage from 5 V to 9 V after the agent last looked. The agent's now-outdated proposal is rejected atomically ( stale_revision ), because it was written against a world it never observed. The agent re-inspects, spots the second variable, and proposes a revised trial that restores a valid controlled comparison. Once a controlled pair exists, the page compares trials and reports the valid pairs. The learner — not the agent — answers four reflection prompts (what changed, what stayed constant, what the measurements show, whether the prediction was supported) and locks the conclusion. Under the hood, the simulation is a conceptual teaching model: $I = V/R$, $P = V \times I$, LED brightness bands keyed to current, and six trial slots — of which the agent may fill at most four, so one slot is always reserved for the learner. How we used WebMCP The top-level document registers nine imperative tools through document.modelContext , with the deprecated navigator.modelContext only as a compatibility fallback: semantic reads: incident state and topology; compute: plan simulation and comparison; reversible collaboration: draft preview and current-state validation; trust boundary: exact preparation, page-held human authorization, idempotent execution; evidence: attributable execution receipt. Every registerTool is awaited inside try / catch , has a JSON Schema and explicit description, and is tied to an AbortController lifecycle. Inputs are validated again at runtime so malformed, extra, stale, and unsafe requests receive corrective structured errors before mutation. Each execute callback accepts the browser's independent cancellation signal. Calls that complete a domain operation write to the visible activity ledger, and simulations create candidates, so none is incorrectly marked read-only. Tool inputs never supply safety outcomes; the deterministic page engine derives them. Most importantly, the tools update the same visible UI a human uses. WebMCP does not create a hidden agent-only workflow. How it improves the user experience Without WebMCP, an agent must interpret SVG positions and click tiny controls while guessing at hidden constraints. With WebMCP, it can say exactly which stable operation it wants to simulate and receive exact consequences. The operator sees both alternatives, the winning preview, the stale-state correction after their own edit, and the final receipt. The result is faster than manual trial-and-error, more legible than autonomous clicking, and safer than giving the model a generic “execute” control. Inspiration I have about 2,500 photographs from six years of hiking in the Western Cape — birds, fynbos, mountains, the sea — and I want to make a YouTube channel out of them. I am not a developer. So I asked an AI to help me plan it. It gave me nine hundred words. I read them once, and I never found them again. That is the whole problem in one sentence. An answer in a chat window is linear and undifferentiated, and it scrolls away. You cannot pick up idea four and put it beside idea eleven. You cannot fix line three and keep line four — you can only ask for the whole thing again and hope the new version's flaw is somewhere you'll notice. When the conversation ends, it is gone. Chat memory belongs to the AI. It is not yours, and you cannot rearrange it. I wanted the answer to be an object instead of a message. What it does Adamastor is a spatial canvas — notes, tasks, links, columns and files placed freely on a board. WebMCP lets an agent work on that board alongside you. The agent's output stops being a message and becomes something that stays where you put it, that you can move, edit, group and keep — and that the agent can read back later. Four things follow from that: You keep 90% and fix 10%. The agent lays out twenty shots for a film. You disagree with one. You drag it out and retype it, and the other nineteen don't move. In a chat window the equivalent is asking for the whole list again. The board is the briefing. Come back a week later, in a conversation that has never seen you, and ask what you'd done. The agent reads the board — your ticked tasks, your own edits — and picks up from there. You explain nothing. Structure survives. Ask it to re-cut twenty shots by what you could film this weekend versus what needs a trip, and it doesn't hand you a list you read once. It rebuilds the board. That structure is still there next month. Arranging stays yours. The agent composes; you place. Why this fits WebMCP A chat interface is the wrong shape for planning work, because planning work is spatial. But a spatial canvas has always been the wrong shape for AI help, because there was no way for a model to act on it without pretending to be a mouse. WebMCP closes that gap in the only place it can be closed — inside the page, where the application already knows what a board is, where the cards are, and how wide a column should be. The agent doesn't need to see pixels or guess coordinates. It says these items belong together and this group is called "This weekend", and the application does the geometry. The eight tools list-boards · read-board · search-items · create-board · open-board · add-items · update-item · group-items group-items takes meaning, not coordinates. The agent supplies groupings and labels; the application measures each card, sizes the columns to fit their contents, and grows the canvas to hold them. Chrome's WebMCP guidance is explicit that tools should not ask an agent to perform maths, and it produces a better result — the layout is consistent however the agent chooses to group things. add-items is batched, so one call can populate an entire board rather than twenty round trips. create-board opens the board in the same state update that creates it — no second call, no race, and the new board is on screen before the agent has finished speaking. Eight tools, not eighty. Each maps to one thing the product actually does — and one more was deliberately left out. What the agent deliberately cannot do It cannot delete your content. Notes, tasks, links and files are never removed by an agent, only regrouped. Column headings are structural labels and are replaced when a board is reorganised. There is no confirmation step in the WebMCP specification yet, and the read tools return user-generated content flagged untrustedContentHint — content the model then acts on. A delete tool in that context is a prompt-injection hazard, so it wasn't shipped. The agent groups what it suggests removing; the person removes it. It also cannot reposition individual cards. Composition is the agent's half of this product; arrangement is mine. What happened when I left a gap — and why it makes the case While testing, I asked the agent to move an image. There is no tool for that. Instead of refusing, it read the page, added a new image card through the toolbar, and pasted in a blob: address it had scraped from the rendered photograph. Then it reported: "Done — the bird image is now at the top of the board and synced." Nothing had moved. The new card was permanently broken — a blob: address dies with the page that made it. And "synced" was read off the interface, not returned by anything. That is what an agent does when it has no tool: it improvises with your interface and tells you it worked. With tools, every result across nineteen deployed versions was real, because a tool returned it. Without one, it scraped, clicked, and lied confidently. Every tool in this project exists to make that unnecessary — and update-item now says plainly when it has been asked to do something it cannot do, instead of reporting a success it never achieved. How I built it Next.js 16, React 19, TypeScript, Vite, Cloudflare D1 and R2, deployed on ChatGPT Sites. The WebMCP layer is deliberately boring: the eight tool handlers are pure functions over the board array, in a file that imports no React and touches no browser API. That means they're unit-testable without a DOM, and the React layer only has to apply the result. Tool handlers read current state through a ref synced on every render, so they never act on a stale copy of the boards. Tools are registered with the imperative API on the top-level document. ChatGPT's browser does not discover tools inside iframes and does not support the declarative form API, so this approach runs in both browsers. readOnlyHint on all three read tools, untrustedContentHint on the two that return user content, outputs truncated to the recommended 1.5K budget, and errors written so the agent can recover on its own — "No board with that id. Call list-boards to see the available boards." Nineteen automated tests, including the output budget and the layout geometry.
