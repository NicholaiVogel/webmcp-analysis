# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

CharDesk instead exposes focused workspace tools for discovering, creating, reading, writing, patching, deleting, and validating Blackboard files. The source remains authoritative; the canvas is a live projection of it. How we built it CharDesk has a protocol-neutral tool layer shared by two thin host adapters: Standard WebMCP for compatible Chrome environments The imperative WebMCP capability supported by ChatGPT Site Tools Both adapters expose the same underlying Blackboard operations, so product behavior does not depend on a particular browser integration. A Blackboard stores source files and layout metadata. Changes are compiled through a shared rendering pipeline into a fixed character grid. This pipeline handles Unicode width, CJK characters, Nerd Font glyphs, ANSI styles, structured diagrams, and multidimensional layouts. The browser keeps the latest valid canvas mounted while an agent edits the source. Challenges we faced One unexpected challenge was tool ownership across browser tabs. Opening several CharDesk pages could cause identical tools to be registered multiple times, leaving the agent unable to choose a target. We built an origin-level gateway lease so only one page exposes the tools, with automatic takeover when that page closes. Chrome and ChatGPT also expose different subsets of the evolving WebMCP API. Instead of spreading compatibility checks throughout the product, we isolated those differences behind capability adapters backed by one canonical tool definition. Another challenge was timing: some hosts inject WebMCP after the application has already loaded. CharDesk therefore uses an adaptive registration handshake rather than assuming the API exists at startup. Finally, we learned that exposing tools is not enough. An agent may know how to write a file without knowing how to create a compelling visual explanation. Embedding CharDesk’s materials and examples as a callable tool gave browser agents the missing creative context. What we learned The most important lesson was that agent-native design is not simply automation layered onto an existing UI. A better pattern is to give agents a precise, structured representation while giving people a rich visual projection of the same underlying artifact. WebMCP makes that relationship discoverable directly from the website, without requiring agents to reverse-engineer the interface. CharDesk explores what becomes possible when the web page is no longer just something an agent operates, but a shared medium in which the human and agent can think together. Every AI action gets a signed receipt with a deep link your screen reader can verify directly — so you never have to trust an agent's word for what it just did. Like Comment Story Updates The verification gap nobody talks about Blind and low-vision users already use AI agents to operate the web — filling forms, managing lists, navigating sites with dozens of menus. The part that still doesn't work is trust. A sighted user glances at the screen and knows instantly whether an action succeeded. A screen reader user has no equivalent glance. Today, verifying what an agent did means re-navigating the whole page by hand, which erases most of the time an agent was supposed to save. A study of 16 screen-reader-using programmers found that verifying AI output, not producing it, was consistently the most time-consuming part of their workflow. That's the problem Prove It is built to solve. What it does Prove It is a household task manager where every action an AI agent takes — adding a task, marking it done, changing its priority, deleting it — produces a structured, inspectable receipt : what changed, exactly where it lives in the page, and what to say if it failed. Every receipt includes a deep link . Clicking it moves real keyboard and screen-reader focus straight to the element that changed, so the person hears their own assistive technology confirm the action in its own words — not a paraphrase from the agent, and not a guess from re-navigating the page. Failures get the same treatment. If the agent tries something invalid — an unknown task, a bulk delete it isn't allowed to perform — that produces an error receipt too. Proving what an agent didn't do, and why, is as important as proving what it did. How I built it The whole app runs on one function, performTool(name, args) , which is the single source of truth for all seven tools ( list_tasks , add_task , set_task_status , update_task_priority , delete_task , focus_task , get_last_receipt ). That one function is wired to two transports: Native WebMCP. On load, the page feature-detects document.modelContext / navigator.modelContext and calls registerTool() for each tool with a strict JSON Schema. Any WebMCP-aware agent — Chrome's built-in agent with the WebMCP flag on, or ChatGPT's in-app browser — can discover and call these tools directly, no code changes required. In-page demo agent (fallback). If WebMCP isn't available in the browser, the same seven tool schemas are sent to the Claude API as tools , so anyone can test the full loop — natural language in, tool call, receipt, verify — in an ordinary browser with no flags. Every write tool returns { tool, changeType, timestamp, target: {selector, description}, before, after, errors } . changeType is created , updated , deleted , verified , or error . Receipts render as a literal torn-paper "receipt tape" in the UI — a visual metaphor for the whole concept: a printed proof of exactly what happened. The negative test There is no delete_all_tasks or bulk-export tool, on purpose. The agent is instructed to delete tasks one at a time and to ask before any bulk action — so "prove it" also covers proving the agent can't do something irreversible, because the capability was never exposed as a tool in the first place, not because a prompt told it to behave. Challenges I ran into The trickiest part wasn't the receipts — it was making the deep link mechanism actually work for a screen reader, not just look like it does. Early on, clicking a receipt just scrolled to an element and added a CSS glow, which does nothing for someone who can't see the glow. The fix was making sure every deep-linked element is a real, focusable DOM node ( tabindex="-1" where it isn't natively focusable) with an aria-label that reflects its current state, and that the deep link calls .focus() on that exact node. The visual highlight is a bonus for sighted collaborators, not the verification mechanism itself. The other challenge was keeping one tool contract honest across two very different transports. Rather than writing tool logic twice, performTool() is called by both the native registerTool().execute() handlers and the in-page agent loop, so a receipt means the same thing regardless of which agent produced it. What I learned Verifiability isn't a feature you bolt onto an agent's output after the fact — it has to be a structural property of the tool contract itself: a real DOM target, a real before/after diff, a real focus event. WebMCP's tool registration model turns out to be a genuinely good fit for this, because the receipt an agent returns and the page's actual state can be forced to be the same object, not two things that merely claim to agree.
