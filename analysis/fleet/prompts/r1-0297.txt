# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

An incident war room where the agent's tools appear and disappear with the incident's phase. It can't roll back production, the tool doesn't exist until a human escalates. Like 1 Comment Story Updates Inspiration Every engineering team I know wants an agent in the incident channel, and every one of them has the same objection: not the button. Reading dashboards, correlating a latency spike against a deploy log, drafting the status page, that's work a machine should do at 3am. Rolling back production is not. The industry's current answer is a line in a system prompt: do not roll back without approval . That's a request, not a control. It's the security model of a sticky note on a server rack. WebMCP suggested a different answer. If tools are registered from the page, and the page knows what state the incident is in, then permission stops being something you ask the model to respect and becomes something the tool surface simply doesn't offer. What it does (→ why this is a strong fit for WebMCP) SIGNAL is an incident response console that a human operator and their agent drive together. The active incident moves through four phases, and the agent's tool surface is recomputed on every transition. In TRIAGE the agent has nine read-only tools: metrics, logs, deploys, topology, plus record_hypothesis to write its reasoning onto a timeline the operator can see. rollback_deploy is not in its list. Tell it to roll back and it doesn't refuse; it reports that it has no such capability, and calls request_escalation . That paints a confirmation surface showing exactly which six capabilities would be granted and what the agent intends to do with them. A named human approves. toolchange fires. Six tools light up. Now it can act, each action still gated behind a confirmation showing the blast radius. When the metrics recover, the agent calls declare_mitigated , which withdraws its own write access , and the surface contracts again to verification tools, then to postmortem tools. This is a strong fit for WebMCP specifically because the permission boundary and the user interface are the same object. The operator isn't reading a description of what the agent can do; they're looking at the browser's own tool registry, rendered. getTools() is the source of truth for both the agent's abilities and the human's understanding of them. No server-side agent framework can offer that, because the human isn't there to see it. How it creates a better user experience Before: an operator with six dashboards open, correlating timestamps by eye under time pressure, while an agent in another window offers suggestions it has no way to verify and no way to execute. With SIGNAL: the operator watches the agent investigate in a shared timeline, sees its hypothesis with the evidence attached, and makes one decision, do I trust this enough to unlock write access instead of twenty small ones. The agent handles correlation; the human handles judgement. Each is doing what it is good at, and the seam between them is a visible, auditable interface rather than a prompt. The status page update is the sharpest example. The agent drafts; the operator gets that draft in a live text field and rewrites it; the tool resolves with their version, and the return value tells the agent it was edited and what actually shipped. That's not approval, it's co-authorship, and the agent's next update matches the operator's register because it can see what they changed. What people and agents can do together that was difficult or impossible before Three things, all specific to tools running in the page rather than on a server. A tool can hand you a decision and wait. request_escalation 's execute() renders a surface listing the exact capabilities to be granted and does not resolve until a human acts. A remote MCP server can return text asking a question. It cannot show you the blast radius, block, and continue with your answer, because it is not in the room. A tool can come back edited. publish_status_update and draft_postmortem both return the human's revision, not a boolean. The agent learns from the diff. The human can see the agent's power, live. The capability panel is fed by document.modelContext.getTools() on toolchange . When the phase changes, tools visibly light up or strike through. Nobody has been able to watch an agent's permissions change before, the registry was always somewhere else. And the inverse: capability scoping by construction. Prompt-based restrictions fail under adversarial input; an unregistered tool has no attack surface. search_logs carries untrustedContentHint for the same reason , log lines are attacker-influenceable and should be treated as data. How we implemented WebMCP Imperative API throughout, 21 tools via document.modelContext.registerTool . The core primitive is a useTool(def, enabled) hook that ties registration to React lifecycle through an AbortController . Phase is derived state in a Zustand store; each tool's enabled flag is a predicate over it. When the phase changes, React unmounts the effect, the controller aborts, and the capability genuinely leaves the registry. This is not a mock, the Tool Inspector extension shows the list shrinking. toolchange plus getTools() drive the capability panel. AbortSignal is threaded from execute(input, { signal }) into every elicitation promise, so cancellation from either side tears down the dialog rather than stranding it. annotations.readOnlyHint marks the ten observational tools; untrustedContentHint marks log search. Telemetry is a deterministic seeded simulation where metrics are a pure function of (service, region, time, mitigations applied), so rolling back the bad deploy actually recovers the curves. There's no second dataset. No backend, no network calls, nothing that can be down when a judge opens it. Challenges Getting the agent to reason about its own permissions rather than bumping into silence. Early on, told to roll back during triage, it would either hallucinate a tool or go quiet. The fix wasn't prompting, it was making get_incident_overview return the agent's current capability set and name request_escalation as the way to ask for more. Tools that describe the system's shape are as important as tools that act on it. The second was tool selection between scale_service and rollback_deploy . Both plausibly address a saturated connection pool. It resolved by putting the reasoning in the description tha, t scaling relieves symptoms but won't fix a bad code path, rather than adding a rule. Accomplishments The moment the agent says "I don't have that capability in this phase, may I escalate?" and it's true, not a scripted refusal. What we learned Tool descriptions are the real interface. The behaviour we wanted came from sentences, not code. And the return value is a prompt: a tool that returns "OK" wastes the most valuable channel it has. What's next Real integrations behind the same phase gate, PagerDuty, Datadog, GitHub. The pattern generalises past incidents to any console with a destructive action: billing, admin panels, clinical systems. The interesting version is a policy engine that derives the tool surface from an org's existing RBAC, so the agent's capabilities are automatically a subset of the operator's. A deterministic crisis simulator where AI investigates through WebMCP, compares interventions, and proposes plans—while humans retain final authority. Like Comment Story Updates The deterministic T+60 result compares the approved response with the do-nothing baseline. Choose one of three deterministic crisis missions and invite a WebMCP-enabled AI teammate. A live flash-flood response with graph-based vehicle movement, named roads, and human-impact forecasting. The AI reads structured city state while the human controls dispatch, routes, priorities, and approval. Full game view: live roads, facilities, incidents, city metrics, and synchronized AI activity. Inspiration Browser agents are usually asked to operate interfaces designed only for human eyes. That becomes fragile when an application contains a live model with more meaning than its visible controls can express. A crisis dashboard may show a blocked road, a failed power station, and an overloaded hospital, but the causal chain connecting them is difficult to reconstruct from pixels or DOM labels. We wanted to explore a different relationship: not an agent that simply clicks faster than a person, but a human and an agent operating the same complex system through complementary interfaces. What it does Pending: Human turns a sixty-minute urban crisis into a shared decision exercise. The deterministic simulation creates cascading infrastructure failures and tracks exposed residents, injuries, untreated critical cases, fatalities, hospital load, road travel time, emergency vehicles, and incident resolution. The AI teammate uses WebMCP to investigate structured city state, trace root causes, forecast the cost of doing nothing, compare three compound response plans, and stage one candidate for review. The player chooses the mission doctrine, dispatches vehicles and routes, can build an independent counterproposal, and makes the final decision. Simulating is never executing. A proposal remains pending until the human presses the visible approval control. There is deliberately no WebMCP approval tool. Why WebMCP Pending: Human is built around state that is richer than its visible dashboard. WebMCP gives the agent a semantic contract over the same facts used by the simulation engine: named roads and facilities, passability, power dependencies, hospital pressure, response routes, at-risk populations, and deterministic future outcomes. This avoids guessing from color, screen position, animation, or fragile markup. It also creates a stronger safety boundary. The agent receives deep investigative and counterfactual capabilities without receiving final authority to act. The tool surface changes with the stage. It begins with one entry capability, then exposes only what is useful at the current checkpoint. One integrated assessment call reads the evidence and issues three exact revision-bound previews; a second call lets the agent exercise judgment by selecting one. Short guidance tools explain and highlight the next human control without clicking it, and an event-wait tool keeps the shared session synchronized. A better human + agent experience The simulation, agent, and human have distinct powers: The simulation owns the facts. Every live and forecasted consequence comes from deterministic TypeScript rules. The agent compares possible futures. It connects evidence across infrastructure systems and explains trade-offs. The human owns the decision. The player sets values, accepts social costs, and authorizes consequential action. City time freezes while the agent analyzes and while a proposal awaits approval, so model latency cannot cause extra simulated deaths. Findings are mirrored into the page transcript, and the approval card shows benefits and costs before the player decides. The human can disagree by building a separate plan without erasing the AI proposal. Together, people and agents can identify a cross-system root cause, establish a shared no-action baseline, compare policy futures under human-selected values, and verify the result against the same rules. Doing this reliably through a human-only interface was previously slow and brittle. How we built it The project is a client-side React and TypeScript application. The road graph, casualty model, scenarios, incident clearance, vehicle travel, forecasts, and scoring all live in one deterministic simulation engine. A shared store manages the live clock, event queue, plan previews, human approval boundary, and teammate transcript. WebMCP tools are registered directly by the page and routed by the current simulation phase. The live workflow uses enter_pending_human_stage, analyze_crisis, propose_emergency_plan, post_next_guidance, focus_next_control, wait_for_city_event, and analyze_turning_point. Granular district, road, facility, hospital, power, routing, forecast, and simulation tools remain available for semantic diagnostics. There is no external AI API inside the application. The WebMCP-enabled browser supplies the agent. There is also no database, login, map API, or hidden backend simulation. Challenges The hardest design problem was keeping a continuous co-op experience responsive when an agent model could take tens of seconds to reason. We introduced time freezing, phase-aware tools, event waiting, and a two-call decision path that batches structured investigation while still requiring the agent to choose among candidates. Another challenge was visual causality. Response vehicles originally felt decorative. We rebuilt movement around the same road graph exposed to WebMCP, made congestion and closures change travel speed, anchored arrivals to visible nodes, and let on-scene units progressively resolve incident markers. Accomplishments Live play and forecasts share one source of truth. Simulating a plan never mutates the live city. Stale previews cannot execute after the city revision changes. AI and human plans remain visible together. High-impact actions cannot bypass human approval. Three difficulty-scaled missions are deterministic and replayable. Forty-two automated tests cover the engine, routing, approval boundary, and agent flow. What we learned WebMCP is most compelling when it exposes meaning that cannot be reliably recovered from the human interface. It is also useful for defining what an agent cannot do. A good agent experience is not the largest possible toolbox; it is a clear sequence of meaningful capabilities, shared state, and explicit authority boundaries. What's next Future work could add a scenario authoring system, richer field observations, and deeper doctrine negotiation while preserving deterministic evaluation and human approval. The current version intentionally prioritizes one complete collaboration loop over an open-ended city model. Pending: Human is a fictional training and interaction-design prototype. All people, casualties, incidents, and outcomes are simulated. AI agents are replaceable. Their work shouldn’t be. Arrastra Relay preserves every decision, proof, and handoff so teams can move faster without losing trust. Like Comment Story Updates The problem AI agents are replaceable. Their work shouldn’t be. Long-running agent work breaks at the handoff. When a task moves to a new conversation, model, provider, or person, the successor usually receives a summary. What it often loses is the authoritative state, supporting evidence, governing policy, and precise definition of done. That gap creates two expensive failure modes: silent drift and confident false completion. Arrastra Relay is a trust layer for agent workflows. Agents can investigate, hand off, and resume work, but the application—not the model—owns the state, the rules, and the authority to declare the job complete. What it does We built a synthetic checkout incident to demonstrate the complete trust chain, including the moment an agent tries to close the incident too early. A human establishes one non-negotiable closure rule: the checkout must be tested after rollback. An investigator agent calls read_incident to receive the authoritative state, current revision, evidence, and handoff contract. It calls submit_handoff with canonical structured data bound to the source-set hash and evidence identifiers. A successor context calls read_handoff and receives the retained artifact, remaining requirements, application receipt, and predecessor summary clearly labeled as untrusted. If the successor attempts to close the incident early, the application returns VERIFICATION_REQUIRED without advancing the revision. run_verification performs the application-owned synthetic checkout and issues a verification receipt. submit_resolution can then bind the handoff, verification receipt, evidence, and final artifact into a committed revision. The human can inspect or export the complete application-owned audit record. The arrastra visualization is not decorative animation. Seven visual beats are driven by real application events; the eighth occurs when the human opens the audit view. If the underlying workflow does not advance, neither does the mill. Why WebMCP is essential WebMCP turns Arrastra Relay from a dashboard into an agent-native application. The page exposes exactly five semantic tools through document.modelContext.registerTool(...) : read_incident submit_handoff read_handoff run_verification submit_resolution The human and the agent operate against the same authoritative application state, but they have different responsibilities. The human can inspect policy, evidence, status, receipts, and history. The agent receives structured tools for performing the workflow. The mutation sequence is intentionally not duplicated with manual buttons. A person cannot impersonate the agent path simply to make the demo advance. All five tools remain registered throughout the session because the refusal is part of the product. An early resolution attempt must reach the application so the application can reject it, preserve the failed attempt, and return the exact corrective action required. Agents also carry forward application-issued source, evidence, and receipt identifiers. They do not invent the hashes or decide whether the evidence is sufficient. Human-agent experience The human sets the rule and retains visibility into every consequential transition. The agent receives structured contracts, current-revision guidance, and actionable errors instead of guessing through a mouse-oriented interface. The application arbitrates between them. A rejected closure attempt becomes evidence that the gate worked. A successful resolution becomes a durable receipt tied to the evidence chain—not another unsupported statement that the task is “done.” Implementation The architecture is intentionally narrow enough to understand and audit: ChatGPT Sites serves the public Worker and static client. D1 stores an independent incident record for each visitor session while sharing that record across the visitor’s browser and conversation contexts. The same deterministic domain and service layer runs locally and in the hosted Worker. Revision checks provide compare-and-swap protection against stale writes. Submitted JSON is parsed, structurally validated, canonicalized, hashed, and retained with explicit evidence identifiers. Predecessor prose is labeled and handled as untrusted data. It never controls the completion gate. The UI, choreography, receipts, and audit table are all derived from application state. What makes it different Agent handoffs are usually treated as context transfer. Arrastra Relay treats them as continuity of authority. A successor receives more than the previous agent’s explanation. It inherits the current state, retained evidence, unresolved obligations, and application-issued receipts—without inheriting the predecessor’s right to be believed. Incident response is the first use case because the cost of a false “done” is easy to see. The same pattern can support other completion-sensitive workflows where teams want the speed of agents without allowing model confidence to become operational truth. Arrastra Relay is not another memory layer or a better summary. It is an application-level control layer for deciding when agent work has actually satisfied the rules. What we learned Trust does not come from a stronger model or a more persuasive handoff. It comes from placing authority at the correct layer. WebMCP callbacks do not establish trustworthy model identity. Hashes can bind an artifact to a record, but they cannot prove that an external-world claim is true. The prototype therefore makes narrow, testable claims: Revisions prevent stale writes. Canonicalization binds retained artifacts to stable hashes. Evidence identifiers preserve the application’s evidence chain. The verification receipt proves that the application ran its defined check. Only the application can advance the incident to resolved. Arrastra Relay does not claim that a hash makes an agent truthful. It demonstrates how an application can keep unsupported confidence from becoming committed state. How we used AI We used AI broadly, but not blindly. OpenAI Codex and ChatGPT, Anthropic Claude, selected NVIDIA-hosted and OpenRouter-hosted models contributed to concept exploration, adversarial threat modeling, test-oracle design, implementation review, and edge-case analysis. Meta AI produced the final entrant-directed interface image, and ElevenLabs provided the Adam narration voiceover. Every outside-model result was treated as a proposal. Claims, code, diffs, and tests were independently checked before adoption. How we used Codex Codex was the primary engineering and verification environment. It reconciled the challenge rules, maintained the project’s decision and assistance ledgers, implemented and reviewed the WebMCP and D1 application, ran the 16-test suite, exercised the complete reject-verify-resolve workflow in a WebMCP-capable browser, verified hosted state and logs, froze the rc3 release candidate, deployed the exact build, and published the matching source tree. Key features Five working WebMCP tools with strict input schemas and bounded outputs. Application-authoritative state shared across contexts within one visitor session. Evidence-linked, canonical structured handoffs. Revision checks and stale-write rejection. Visible rejection of premature completion. Application-owned verification receipts. Evidence-gated final commits. Untrusted predecessor-summary containment. Seven event-driven workflow beats, one human audit beat, and an exportable audit record. A real agent, driving real WebMCP tools, to solve a real problem: figuring out what order to watch a franchise in, and actually getting caught up - not just being told the order. Like Comment Story Updates Inspiration Spotlight already had the hard problem solved on paper: a "Must Watch" graph in Postgres that knows the correct order to watch a franchise in, and a private per-user watch history behind real auth. But that data was only reachable by clicking through the UI yourself. Ask any AI assistant "what order should I watch John Wick in?" and it answers from memory - no idea what you've actually seen, no way to act on the answer. WebMCP looked like the first real answer to that gap: instead of an agent scraping a rendered page or a separate backend replicating the app's auth, the tools just live inside the page's own already-authenticated session. What it does Spotlight registers 9 tools via document.modelContext.registerTool() on top of an app that already tracks streaming and theatrical releases, watchlists, and watch order for movies and shows. The flagship, plan_watch_order , reads the real "Must Watch" graph, cross-references what you've actually watched, and writes only the remaining titles into your real watchlist in the correct order - run it again after finishing a title and it correctly says there's nothing left to add. Two of the tools, mark_watched and reorder_watchlist , don't exist until they'd do something real: they register and unregister themselves live via toolchange as your watchlist's own shape changes. To prove the tool surface is genuinely agent-legible and not just spec-compliant, we also built an in-page chat panel (bring-your-own API key, Groq by default) where a real LLM reads the tool schemas with getTools() and drives them with executeTool() from plain English. How we built it React + TypeScript on the frontend, Postgres (Neon) for the release calendar, watchlists, and the watch-order graph, Vercel serverless functions for the API, and a GitHub Actions pipeline that refreshes release data from TMDB on a schedule. The WebMCP layer lives entirely in src/webmcp/ : every tool wraps the exact same client-side functions the UI's own buttons already call, so there's no parallel "agent" backend and no duplicated logic. Challenges we ran into Chrome's experimental WebMCP flag expects executeTool() 's arguments as a JSON string, not the plain object the spec's own examples show - a real divergence we only found by testing. We also discovered no shipping agent (ChatGPT's desktop app, its Computer-Use mode, Codex) actually routes through document.modelContext yet; all of them fall back to generic DOM automation, which is exactly why we built the in-page chat panel instead of just asking an existing assistant to try it. On the infrastructure side: Vercel's Hobby plan caps you at 12 serverless functions, so guest sign-in had to extend an existing endpoint rather than ship as a new file, and none of OpenAI's, Azure's, or Groq's APIs set CORS headers for browser calls, which meant building a stateless same-origin relay just to let the chat panel talk to an LLM at all. Accomplishments that we're proud of Getting a real language model to call get_watch_order and then plan_watch_order on its own, unscripted, and watching four films land in a real account's watchlist in the correct order - live, not mocked. And handling the "no agent uses this yet" problem honestly instead of hiding it: we verified the gap directly, documented it, and built the one thing that actually demonstrates the tools are ready for when an agent does. What we learned How much of "making an app agent-ready" is really about discipline in the app's own code, not the WebMCP API itself - every tool only stayed simple because it called the same functions the UI already trusted. We also learned firsthand how far ahead the spec is of the ecosystem actually consuming it right now. What's next for Spotlight Once a shipping assistant actually calls document.modelContext on its own, Spotlight's tools are already sitting there waiting - no work required on our end. Beyond that: correct_watch_order already lets a user tell their agent "that link is wrong," which is the seed of letting an agent help curate the underlying graph itself, not just consume it.
