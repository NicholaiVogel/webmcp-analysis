What it does AI Act Shield detects personal data — tax codes, national IDs, VAT numbers, IBANs, payment cards, names, emails, phone numbers, addresses, company names — and replaces each with a placeholder, so the masked draft can safely go to any AI. When the answer comes back, it puts the real values back where they belong. Detection is deterministic: regular expressions plus real checksums (ISO 13616 for IBANs, Luhn for payment cards, the Spanish DNI/NIE and CIF control characters, the official Italian VAT algorithm). Never an LLM. A model would answer differently on the same document from one run to the next, and sending a document to a model to ask what to hide from that model defeats the purpose. Coverage is Italian, Spanish and English/international. The WebMCP part The app is built on one constraint: the text never leaves the browser. That constraint turns out to be exactly what makes a WebMCP tool trustworthy, because registerTool().execute() runs client-side, in the visitor's own tab. The page registers four tools. The one that carries the argument is mask_document_in_page , and what matters is what it doesn't take: document.modelContext.registerTool({ name: "mask_document_in_page", description: "Masks the personal data in the document the user has already loaded into this page, without the caller ever receiving the document.", inputSchema: { type: "object", properties: { customTerms: { /* ... */ } } }, execute: async (input) => maskPageDocument(input), }); No text parameter. The person loads the confidential document into the page; the agent calls the tool passing nothing ; the page reads its own content and returns a masked draft plus the types of what it found. The document never enters the agent's context, so it cannot leak one even if it tried. Asked in plain language to mask a contract — without being told which tool to use — ChatGPT's agentic browser produced this row in the page's own log: 1:48:34 PM external mask_document_in_page {} external means the call came from outside the page rather than from its own buttons. {} means there was nothing to pass. That empty object is the whole project. This is also the case for "people and agents using an app together": the UI and the tools share one page-local state, so the person watching the tab sees the masking happen live and can step in — switch a detected entity off, add a custom term — while the agent works. How I built it Vanilla JavaScript. No framework, no dependencies, no build step — you can clone it and open it. 37 tests on node:test , which is built in, so that promise holds for the test suite too. Served as static files from my own nginx, not a platform: the page is the same folder that nginx serves. The detection engine is a port of the one shipping in iaCiao , my platform for local — edge — AI: 32 iApps across health, security and mobility, all built so the model runs on your device and the data stays there. AI Act Shield is the clearest expression of that idea, which is why I brought it here. An app whose entire value is that the sensitive part never leaves your machine turns out to be the natural shape for a WebMCP tool, because that is exactly where execute() runs. Challenges The ecosystem moved under me during the ten days. ChatGPT Atlas was deprecated days before the deadline. The Model Context Tool Inspector extension reports nothing for my page, because it looks for navigator.modelContext while the specification (26 August 2026) exposes ModelContext on document and never mentions navigator. I left that audit check failing rather than shim an API that does not exist — and left the declarative toolname / tooldescription / toolaction checks failing too, since the spec marks that API "entirely a TODO". ChatGPT's Chrome extension looks like it works and doesn't. Asked to mask the document, it produced a fluent, accurate answer — by reading the DOM, without calling a single tool. That is precisely the difference this project is about, and it would have been very easy to film it as a success. Chrome's origin trial has a quirk. It returns inputSchema as a JSON string and rejects a plain-object argument to executeTool() with "Failed to parse input arguments". Nothing in the spec asks for a pre-serialised input, so the code calls the spec-shaped way first and falls back only when that build refuses. My own buttons sabotaged two takes. The "Agent console" had a button labelled CALL MASK_SENSITIVE_DATA() . Asked to "use the page's tools", the agent clicked it — twice. Not a dim agent: the button had named itself after the API, so it was the closest match to the instruction. Renaming it to "Preview the masking response", and adding a line in llms.txt telling agents to call the tool instead, fixed what a better prompt could not. Cloudflare hid three deploys. Assets are served with a four-hour browser cache, so the page kept running the previous build and no hard refresh changed it. I lost two hours because I was verifying with curl --resolve ...:127.0.0.1 , which goes to the origin and bypasses the edge — always showing me the correct file. What I learned The one that mattered: a tool that takes the sensitive data as a parameter cannot protect it. My first version was mask_sensitive_data(text) . It returns only placeholders, never an original value, and I wrote in my notes that "the agent never saw the tax code". That was false, and I did not notice until, halfway through recording, I asked myself whether pasting the contract into the prompt defeated the point of the app. It did — and so, more quietly, did passing it as a tool argument. Whoever calls that tool must already hold the document. There is a real difference between "the response contains no secrets" and "the caller never receives them" , and only the second is a guarantee. mask_document_in_page exists because of that question. The second lesson: instrument your claims. I added a panel that logs every execute() the page receives and marks whether it came from the page's own buttons or from outside. It exists because you cannot otherwise see WebMCP working — the page looks identical either way. That panel is what caught the Chrome extension reading the DOM, and both takes where the agent clicked a button instead of calling a tool. Without it I would have shipped a video of something that wasn't happening. And a third, smaller one: tests find the bugs you just wrote. Four surfaced in a single session, three of them minutes old — including a legal form matching inside an ordinary word, which rewrote the heading "CONSULTANCY AGREEMENT" as "[COMPANY_NAME_1]REEMENT". Honest limits Detection covers Italian, Spanish and English/international formats. A document in another language will still have its IBANs, cards, emails and international phone numbers found, but not its names, addresses or company forms. No PDF or OCR import in this build. An agent can fill out your visa application, but it can't sign your name. High-stakes paperwork with a permission boundary enforced in code, not just the UI. Like Comment Story Updates Inspiration Most WebMCP demos we looked at treat "the agent" as strictly upside: it fills things in faster, it clicks buttons for you. Nobody was building the other half of the story, the part where an agent's authority has to have a hard edge somewhere. High-stakes paperwork is the clearest place to make that argument: a visa or residency application has dozens of fields an agent can genuinely help with (dates, addresses, transcribing from a passport) and a handful it categorically should not be able to touch, because they're attestations. Signing your name is not a transcription task. So we built a fictional application (the invented "Skyward Residency Program," no real agency or form referenced anywhere) specifically to make that boundary concrete and testable, not just asserted in a README. What it does Consequence is a long, branching application where every field carries a permission class: agent_fillable , human_only , or evidence_required . An agent can fill addresses, employment history, and dates directly. If it calls answer_question on an attestation field, it doesn't fail quietly, it gets back a structured error naming the field and telling it to hand back to the human. For evidence_required fields like a bank-balance summary, the agent can only propose_answer , which lands as pending confirmation, never as answered, until the human accepts it. Every field also carries provenance (who set it, when, from where), and the whole mutation history is hash-chained and replayable, so a final review screen can show exactly who filled what. Conditional branches make the same point about tool existence . Answering that the applicant is self-employed reveals a Self-Employment Details section, and only then do fields like business_income_summary become part of what get_section and list_open_questions read from. The tool surface reconfigures itself based on answers already given. How we built it React + TypeScript + Vite on the client, Cloudflare Workers + a Durable Object as the authoritative backend, same architecture as our other entry, Cadence. webmcp-kit for tool definitions, shared across both apps. ~63 fields across 9 sections (7 base, 2 conditional), each declaring a PermissionClass in seed/schema.ts . One reducer ( src/shared/reducer.ts ) enforces the permission class on every mutation path, client UI, Durable Object, and every WebMCP tool call alike, so there's exactly one place the boundary is defined and no path that can skip it. check_consistency does real cross-field validation: an expired passport, overlapping employment dates, an unexplained income gap, checks that are genuinely tedious for a person and genuinely tractable for an agent, run against real answers in src/shared/derive.ts . submit_application is confirmation-gated and independently refuses while anything required is still open, on top of the per-field refusals. Challenges we ran into Making the refusal mean something. It would have been easy to add a client-side check that just hides the "sign" button for agents. That's not a real boundary, it's a UI suggestion. The actual fix was routing every write, human or agent, through the same reducer, so the refusal is enforced at the one place a mutation can happen, not duplicated (and driftable) across the UI and the tool layer. Seed data with nothing to catch. Early on, the seed application started blank, so check_consistency had zero contradictions to ever find, meaning the tool looked broken on every fresh demo even though the logic was correct. Fixed by seeding two fields that genuinely overlap (an employment start date before the prior job's end date), so the tool has real work to do the moment a judge opens the app. Shared-board demo entropy , the same problem we hit on Cadence: because a Durable Object's seed loads exactly once, repeated testing against one shared instance permanently consumed the demo state. Fixed with per-visitor isolated application instances plus a visible in-app reset button. Accomplishments we're proud of A refusal that's actually structural, not cosmetic: answer_question against a human_only field is rejected by the same reducer a human's own edit goes through, verifiable by reading src/shared/reducer.ts directly rather than taking our word for it. A tool surface that changes shape based on the application's own content, not just page navigation, extending the same dynamic-registration idea from Cadence into conditional business logic. A tamper-evident provenance trail (hash-chained mutation history) that answers "who actually filled this field" with cryptographic backing, not just a database column that could silently be edited later. What we learned The interesting design constraint wasn't "what can the agent do," it was "what can the agent be structurally prevented from doing, in a way that can't be bypassed by a differently-worded tool call." A permission check living only inside one tool's execute function is trivially circumvented by any other code path that touches the same state. Putting the enforcement in the shared reducer instead of the tool layer was the difference between a real guarantee and a suggestion. What's next A real evidence-extraction pipeline behind read_evidence (currently a clearly-labeled stub), a dedicated multi-party reviewer invite flow (the data layer already supports scoped reviewer tool grants), and extending the consistency checks beyond the current date/income rules. Repairs without the runaround. Like Comment Story Updates Inspiration Rental repairs turn into a runaround: the tenant repeats the problem, the property manager chases safety and access details, and contractor prices, availability, approvals, and confirmation live in separate conversations. Tenants should not need another portal just to get a leak fixed, and an agent should not be allowed to approve its own consequential work. What it does Fix This keeps the tenant in SMS and gives the property manager one shared repair case. A repair agent gathers safety and access facts, follows the building's stored contractor agreements in order, and prepares the next action through typed WebMCP tools. The property manager sees the evidence and explicitly approves one contractor call bound to the contractor, agreed price, and permitted time windows. In the recorded controlled-live run, one allowlisted tenant MMS woke the background agent. The agent triaged the repair and replied in the same thread. WebMCP prepared the stored-agreement path for the manager. After one explicit approval, the contractor heard a fixed AI disclosure and pressed 1 before any audio reached OpenAI. The contractor confirmed a time inside both authorized windows, Fix This booked the visit, and the tenant received the confirmation text. The public judge URL is a separate, resettable synthetic Pennsylvania build. It exposes the same shared-case and WebMCP boundaries without sending a real message or placing a real call. Why WebMCP The public build exposes twelve typed tools over the same workflow API and repair record used by the dashboard. The tools cover case discovery, triage, tenant messaging, preferred-contractor ordering, access evidence, contractor confirmation, and booking. The agent acts on structured state instead of guessing through DOM clicks. The most important tool is the one that does not exist: manager approval is deliberately absent from the WebMCP surface. The server rejects booking until the current proposal has matching manager approval, tenant access authorization, and contractor confirmation. What people and agents do together The tenant reports the repair in a channel they already use. The agent handles repeatable fact gathering and prepares the approved-contractor path. The property manager makes the consequential cost and contact decision. The contractor gives affirmative consent before the AI call and confirms the visit. Fix This then records the booking and notifies the tenant in the original thread. That replaces fragmented coordination with one causally ordered, auditable workflow without handing approval to the agent. The controlled-live route validates provider signatures and exact allowlists, deduplicates wake events, serializes work per repair case, journals outbound effects for retry safety, and keeps the fixed disclosure plus keypad-consent gate outside the model.
