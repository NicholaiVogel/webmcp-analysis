# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

I also want to develop LivingPage beyond the current approach of importing URLs into a separate reader. Ultimately, I want the web page you are already viewing to become the "Living Page" itself — changing and growing based on the user's questions. When I saw WebMCP, my first instinct wasn't "let me bolt an AI chatbot onto this," it was "an agent trying to use my scraper right now would have to either click through my UI like a human or scrape my own HTML to figure out what's on the page - both of those are exactly the kind of brittle nonsense my scraper exists to avoid doing to other sites." That felt like the actual point of WebMCP: stop making agents reverse-engineer your app and just hand them a contract for the pipeline you already trust. \n\n What it does \n\n Scrapi exposes four tools on document.modelContext once you're signed in: \n\n scrape_url - runs a URL through the real pipeline (with a Selenium fallback for JS-heavy sites) and hands back structured results.\nget_scrape_history - your past jobs.\nget_scrape_export - export a finished scrape as CSV or JSON.\ncheck_domain_history - looks at everything Scrapi has ever scraped from a given domain and tells you whether it usually needs JS rendering and which detection method actually worked. \n\n Any WebMCP-aware agent can find and call these on its own. I also built a small "Tools" panel inside the app itself that calls the exact same tools through the real document.modelContext.executeTool() API, with a little badge that honestly tells you whether the call went through WebMCP or fell back to a direct call - so Scrapi isn't just publishing tools for someone else's agent, it's using its own. \n\n check_domain_history is the part I'm most proud of. It's a live aggregation over real scrape history, not a guess. Scrape a domain once, and the next check of that domain comes back with an actual answer instead of "unknown." \n\n How we built it \n\n Python and FastAPI on the backend, MongoDB for storage, React and Vite on the frontend, JWT for auth. The scraping side leans on requests + BeautifulSoup/lxml for normal pages and Selenium when a site needs JS rendering. On top of that, frontend/src/webmcp/tools.js defines the four tools with JSON Schema inputs, and a small hook registers them on document.modelContext for any signed-in session and cleans them up on logout. A thin GET /scrape/domain-stats endpoint on the backend is all check_domain_history actually needs - it's just a Mongo aggregation, nothing fancier. Frontend on Vercel, backend on Render, both live. \n\n Challenges we ran into \n\n Honestly, the biggest decision wasn't technical. I originally built this with an in-app agent backed by my own Anthropic API key, so it could actually hold a conversation and decide which tools to call. Then I thought about it properly: I was about to hand out a public demo login sitting in front of my personal API key, for as long as judging lasts, with no idea how many people would hammer it. That's not a risk worth taking for a hackathon. So I pulled the LLM out entirely - deleted the agent backend, the API key, all of it - and kept check_domain_history as a plain WebMCP tool instead of something an LLM had to be prompted into using. It actually made the project more honest: the "gets smarter with usage" claim now rests on a database query I can point to, not a model I'm asking you to trust. \n\n On the technical side, the annoying one was document.modelContext.executeTool() in real Chrome throwing UnknownError: Failed to parse input arguments no matter what I sent it. Turned out Chrome's actual shipped implementation wants the arguments pre-stringified with JSON.stringify(), which isn't what the spec explainer describes. Fixed it by trying the stringified form first and falling back to a plain object if that fails. That fix then surfaced a second bug - the string-vs-object mismatch meant tool results were rendering as one giant escaped line of text - so I normalized every result to the same shape at one central point instead of patching the display separately. There was also a completely unrelated pre-existing bug I only found because I insisted on testing everything manually before pushing: my scraper was advertising Brotli support in its request headers without the Brotli package actually installed, which was silently corrupting results from any site that compressed with it. \n\n Accomplishments that we're proud of \n\n Getting a real WebMCP host and client working against the actual browser API, not a mock - and catching real divergences from the spec along the way. And walking away from the LLM agent instead of shipping it anyway just because it was already built. The version that exists now needs no API key from anyone and costs nothing to run per request, which honestly feels like a better demonstration of what WebMCP is for than the flashier version would have been. \n\n What we learned \n\n That Chrome's actual WebMCP implementation has real, undocumented quirks you won't catch from reading the spec - you have to test against the live API early. And that "smarter with usage" doesn't require a model at all if you're willing to let real data do the talking instead. \n\n What's next for Scrapi \n\n Tracking more signals per domain in check_domain_history - rate-limit behavior, typical page size, common failure patterns - and seeing how it holds up once more WebMCP-capable agents exist to actually call it. \n\n \n\n \n Built With \n\n beautiful-soup fastapi javascript jwt lxml mongodb motor python react render selenium vercel vite webmcp \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n scrapi-two.vercel.app \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Sonu Dutta \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Sonu Dutta \n started this project\n \n —\n \n 2 days ago \n \n \n\n
