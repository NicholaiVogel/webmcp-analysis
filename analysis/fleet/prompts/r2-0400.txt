# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

WebMCP made it possible to explore what a more agent-native web could look like—one where a website exposes the small set of actions it genuinely understands while keeping evidence, uncertainty, and final authority visible to the human. What it does Capability Navigator turns a fuzzy software need into an evidence-backed, nonbinding decision packet. The human interface and the browser agent share the same capability model, evidence, constraints, and decision surface . On a WebMCP-enabled browser, the page registers six typed tools: list_capabilities get_capability find_examples draft_scope prepare_decision_packet stage_human_review An agent can discover relevant capabilities, inspect their proof boundaries, find public evidence, draft a bounded scope, prepare a structured recommendation, and finally stage that recommendation directly into the visible page for human review. The last step is important. The goal is not invisible automation. The agent's work converges back into the interface the person is already looking at. Every WebMCP invocation is reflected in the visible Agent Trace , so the user can see what tool was called, what bounded input was used, and whether it succeeded. Five tools are read-only. stage_human_review changes only reversible state in the current browser tab. It cannot contact anyone, submit anything, make a payment, sign something, modify an account, or persist a decision. The human remains the authority boundary. How we built it Capability Navigator uses the WebMCP Imperative API and registers its tools through document.modelContext.registerTool(...) . Each tool has a deliberately narrow purpose, explicit JSON Schema, agent-facing parameter descriptions, annotations, bounded outputs, and additional runtime validation. We do not rely on schema validation alone: malformed types, unsupported capability IDs, oversized inputs, and empty selections fail visibly rather than producing a plausible-looking recommendation. The same deterministic JavaScript core powers both the human workflow and the WebMCP tools. There is no separate "agent truth" hidden behind the interface. Natural-language discovery is deterministic and tied directly to the public capability and evidence model. That keeps the demo reproducible and avoids requiring an external AI model or search service just to determine what the website itself knows. The production deployment is also configured specifically for WebMCP's browser requirements, including origin isolation and the tools=(self) permissions policy. The project includes an ordinary-browser fallback, responsive/mobile behavior, accessibility safeguards, deterministic regression tests, a release preflight, and a short judge path printed directly on the product. Challenges The hardest part was not simply registering a tool. It was deciding what authority an agent should actually have . A single giant "do everything" tool would have made the demo easier, but it would also undermine the point of the project. We instead separated discovery, evidence inspection, scope generation, packet preparation, and human handoff into small tools with different authority boundaries. Another challenge was making the agent behavior judgeable. A technically successful WebMCP call hidden in a console is not a good human experience, so we added the visible Agent Trace and made stage_human_review update the same decision surface the human uses. We also had to handle the progressive-enhancement boundary correctly. In a browser without WebMCP, the product still works and truthfully reports that WebMCP is unavailable; it does not pretend that six tools were registered simply because six tools are defined. Finally, we spent substantial time on failure behavior: malformed inputs, unknown IDs, empty selections, output limits, mobile overflow, reduced motion, deployment headers, and distinguishing an actual WebMCP execution from a normal UI interaction. What we learned The biggest lesson is that WebMCP is more interesting than "letting an AI click a website faster." The website itself knows the semantics of its domain. When those semantics become a typed browser contract, an agent can operate with far less guesswork—and the developer can define much clearer limits around what the agent may do. We also learned that human-in-the-loop does not have to mean bolting an approval modal onto the end of autonomous behavior . The human and agent can share state from the beginning: the same evidence, the same constraints, and the same visible output. That feels like a promising direction for the open web. What was built during the challenge Maps + Apps and the public case-study evidence used by Capability Navigator existed before the challenge. The WebMCP-specific product layer was built or meaningfully extended during the challenge period: the typed browser tools and schemas, deterministic capability discovery, evidence-aware lookup, decision-packet generation, visible Agent Trace, shared human/agent review surface, reversible local staging, safety validation, ordinary-browser fallback, judge workflow, testing, and challenge release packaging. What's next Capability Navigator is intentionally narrow today, but the pattern is much larger. A travel site could expose trip-planning primitives. A government portal could expose eligibility and application-preparation tools. A healthcare site could expose carefully bounded navigation tools. A software company could expose capability discovery without giving an agent permission to initiate sales actions. The idea is simple: A website should not have to be only a collection of pixels that an agent learns to operate. It can become a collaborator with an explicit contract. Redact sensitive PDFs and images locally with privacy-preserving WebMCP assistance. Like 1 Comment Story Updates Inspiration Sharing a document often means choosing between speed and privacy. Existing redaction workflows are either manual, destructive, or built around uploading a sensitive file to another service. At the same time, giving an AI agent unrestricted access to document contents creates a new disclosure risk. SafeShare explores a narrower, more useful contract: the browser handles the private document locally, while WebMCP gives the agent structured access to the redaction workflow. The agent can help manage masks and verify readiness without tool responses containing the document text, file name, image, or detected private values. What it does SafeShare opens PDFs and images directly in the browser, detects likely sensitive information, and immediately draws editable masks. People can move, resize, delete, or draw masks directly on the page. Preview opacity can be adjusted without weakening the final redaction. When the review is finished, SafeShare creates a flattened PDF or PNG in which every visible mask is permanently fused into the pixels. The original file remains unchanged. A supported browser can also hand the finished copy to the operating system's native share sheet, but only after a human click. Why this is a strong fit for WebMCP Redaction is not a background automation task; it is a shared visual decision. The person and the agent need the same live page, the same selected mask, and the same reversible history. WebMCP makes that collaboration explicit. SafeShare exposes nine narrow tools. An agent can read a privacy-filtered editor summary, list safe mask metadata, focus a mask, explain generic detection signals, add or delete a visible mask, undo a change, run the export safety check, and prepare the final download. The agent cannot download or share the file. The final export remains a deliberate human action. This is substantially better than scraping buttons from the interface: tool inputs are constrained, side effects are described, results are verifiable in the page, and the application can enforce a clear privacy boundary around tool output. What people and agents can do together A person can ask the agent to inventory every mask, focus the least confident detection, explain why it was created, make a reversible correction, and verify the final export — while watching each change happen on the document. Before WebMCP, that required fragile visual automation or a separate integration disconnected from the live editing session. The human contributes contextual judgment and final consent. The agent contributes structured navigation, consistency checks, and reversible execution. Neither replaces the other. How we built it SafeShare is a React and TypeScript application built with Vite. PDF.js renders PDFs, Tesseract.js performs local French and English OCR, and deterministic pattern checks detect common personal data. Every detected region is converted to normalized page coordinates so the same geometry works for display, editing, WebMCP actions, and export. The application feature-detects document.modelContext.registerTool() and registers nine imperative tools from the top-level page. The tools reuse the editor's existing state, validation, undo history, and safety report. Registrations share an AbortSignal for page-lifecycle cleanup. PDF-lib and Canvas produce the final rasterized document. The opacity slider affects only the editor preview; exported masks are always solid. The Web Share API is progressively enabled only when the browser confirms it can share the generated file. Challenges we ran into The main challenge was designing useful agent actions without turning WebMCP into a data-extraction channel. SafeShare's tool results intentionally return categories, IDs, pages, confidence levels and outcomes — not raw values, file names, images, document text, or mask coordinates. We also had to keep coordinates accurate across PDF text extraction, OCR output, responsive zoom, direct pointer editing and final raster export. A single normalized geometry model now drives all of those paths. Finally, native file sharing requires a direct human gesture. SafeShare prepares the current flattened file locally after edits so the operating system share sheet can open immediately from the user's click. Accomplishments that we're proud of A complete redaction product rather than a WebMCP proof of concept. Nine working tools with visible, reversible effects and privacy-filtered results. A human-only final export boundary. Local PDF/image processing with no SafeShare application server. English and French interfaces selected from the browser language. Direct drawing, moving, resizing, deleting, undo/redo, preview opacity and zoom. Flattened PDF and PNG output plus progressive native sharing. Automated tests for privacy boundaries, geometry, detection, history, localization, file validation and sharing. What we learned WebMCP is most powerful when it exposes the semantic operations of a live interface rather than recreating an application's backend API. The best tools are small, observable and honest about side effects. We also learned that privacy is not achieved by calling a tool “read-only”; it comes from deliberately limiting both inputs and outputs and preserving human control over consequential actions. What's next for SafeShare Next steps include more OCR languages, stronger local entity detection, reusable redaction presets, better keyboard editing, and an optional fully local model for document-specific suggestions. The core principle will remain unchanged: document processing belongs in the browser, agent actions should be inspectable, and export should stay under human control.
