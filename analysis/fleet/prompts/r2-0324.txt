=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

What it does Estro is a photo editor that runs entirely in the browser and registers 56 tools with document.modelContext . Zod validates every command at the boundary. WebMCP was treated as an architectural layer, not a feature. The interface and the tools call the same validated domain commands, the same history, and the same transaction path, so a dragged slider and an agent's apply_color_adjustment produce identical history entries. A manage_project operation draws a three-frame sample scene and imports it through the same path a real file takes, so an agent arriving at an empty browser still has something to edit. Import had to be atomic across two stores. A project revision in IndexedDB and original bytes in OPFS can't share a transaction. A persisted intent record moves through prepared, committed, and deleted, and startup recovery finishes or undoes whatever a crash left, so History can never point at a file that isn't there. That only holds if the explanation comes from the same place the effect did. The risk factors that matter most — a second policy on the same address, a claim filed right before renewal, a "no prior claims" answer that doesn't match the file — aren't hard to catch, they're just easy to miss when you're moving fast through a queue of files. We wanted to see if WebMCP could let an AI agent sit inside that same case file, alongside the underwriter, and catch what a tired reviewer on their tenth file of the day might not. Not an agent that decides. One that notices, and says so. What it does Countersign is a shared underwriting workspace. The underwriter reviews a live policy application — applicant details, requested sum insured, policy terms. An AI agent, connected through WebMCP tools registered directly on the page, can read the same case data (claim history, other active policies) and propose changes: a risk flag, a premium loading, a change to the excess or an exclusion — each with a plain-language reason citing the specific data behind it. Every proposal lands in a queue, clearly attributed to the agent, and does nothing to the actual policy until the underwriter accepts or rejects it. Nothing binds without a human. Every action — human or agent — is timestamped in an activity log, so the final policy comes with a defensible trail of who decided what, and why. Working together. Underwriter and agent. AI reads your live underwriting case, catches what you'd miss — fraud patterns, over-insurance, non-disclosure. Proposes. Waits. Nothing binds without you. How we built it The app is a single-page React + Vite frontend, no backend — WebMCP tools run entirely client-side against in-memory state. We registered five tools via navigator.modelContext.registerTool : Two read-only tools — check_claim_history and check_other_policies — that return structured data plus computed signals like aggregate exposure across policies Three propose-only write tools — propose_risk_flag , propose_loading , propose_field_adjustment — that never mutate the policy record directly; they push into a pending-proposals queue that only a human accept/reject action can resolve We modeled the mock case data around real underwriting fraud patterns rather than generic risk scores: claims frequency thresholds, sum-insured-vs-declared-value mismatches, and same-address aggregate exposure across multiple insurers. We tested tool discovery and invocation in Chrome with the WebMCP flag enabled, then verified the full flow again through ChatGPT's desktop browser Site Tools before finalizing. Challenges we ran into Getting the human-in-the-loop boundary right took more iteration than the tools themselves — it was tempting to let "safe" proposals auto-apply, but any auto-apply path undermines the audit story that makes this credible for a regulated workflow, so we held the line at approval-gated everything. We also hit the classic stale-closure bug with tool execute callbacks holding onto old state snapshots when the active applicant changed, which we fixed by reading current state through a ref instead of a captured value. Getting WebMCP tool descriptions specific enough that the agent reliably called the right tool with the right applicant ID — rather than guessing or hallucinating case data — took several rounds of tightening the schema and description wording. Accomplishments that we're proud of We're proud that the propose-only architecture isn't just a safety feature bolted on — it's the actual product insight: an LLM in a regulated decision workflow shouldn't want authority, it should want to be legible. Every accepted or rejected proposal, plus the reasoning behind it, is captured automatically, which means the audit trail underwriting teams need for compliance falls out of the design instead of being built as an afterthought. We also managed to build tools that reflect how underwriters actually think — loading vs. excess vs. exclusion as distinct levers, aggregate exposure as a first-class concept — rather than a generic "risk score" that wouldn't hold up to anyone with real domain knowledge. What we learned WebMCP's biggest value isn't letting an agent do more — it's letting an agent act inside a shared object both parties can see and trust, instead of narrating actions in a chat window disconnected from the real record. We also learned how much of "trust" in a human-AI collaboration tool comes from what the system refuses to do automatically, not what it can do. On the technical side: closures over live app state are the easiest way to introduce subtle bugs when wiring WebMCP tools into a React app, and it's worth designing state access through refs from the start rather than retrofitting it. What's next for Countersign Near-term, we'd add a referral tier — when proposed changes cross an underwriter's authority limit (e.g. aggregate exposure above a threshold), Countersign would route them to a senior underwriter instead of a simple accept/reject, matching how real underwriting authority limits work. We'd also like to make agent reasoning traceable at the data level — clicking a proposal highlights the exact claim or policy row it's citing, so nothing the agent says is a black box. Longer-term, the same propose-and-approve pattern applies well beyond underwriting — claims adjudication, loan structuring, compliance review — anywhere a human needs to stay the final signature on a decision an AI can help inform but shouldn't make alone. Like Comment Story Updates list the agents What is orqis orqis is the shelf for specialist AI agents: a marketplace that is browsable by humans and callable by agents . Generalist LLMs can't render a video, compile LaTeX, or ship a polished landing page. orqis is where those specialist agents live, with one credit balance, schema-validated I/O, refunds on failure, and reviews tied to real invocations only. Live URL: https://orqis.xyz Why this is a strong fit for WebMCP A marketplace of agents is, by definition, something both people and agents need to use. Before WebMCP, an agent visiting orqis.xyz had to scrape cards, guess at filters, and click through checkout forms — slow, brittle, and unsafe when credits are involved. With WebMCP, the page itself tells the agent exactly what it can do: search the catalog, inspect an agent's input schema, invoke it, check a job's status, and leave a review — all through typed tools, on the same page the human is looking at. How it creates a better experience Shared context, shared screen. The human browses categories and reads reviews; their agent (in ChatGPT's browser or Chrome) calls search_agents / invoke_agent against the very same page. Results land in the UI the person is already looking at — no copy-pasting between a chat window and a website. Safety by construction. Tools carry strict input schemas, so an agent can't accidentally spend credits on malformed requests. Failed invocations are refunded automatically. Trust that agents can read. Ratings are only written from real invocations, so an agent choosing between two specialist agents gets signal, not marketing. What people and agents can do together that was hard before "Find me an agent that turns this README into a demo video, run it, and show me the result" — the person says it once; the agent discovers, invokes, polls the async job via webhook, and the result renders on the page for the human to approve. Compare specialist agents side by side: the agent pulls schemas and pricing, the human makes the call. Chain specialists: landing page → image generation → code review, with the human watching each step and stepping in when needed. Tools are context-aware: on /browse the search tool is scoped to the visible filters, and on an agent's detail page invoke_agent is pre-bound to that agent's schema. Execution results update the React state so the human sees exactly what the agent did. Like Comment Story Updates Inspiration Inference-hardware comparisons are easy to get wrong. A leaderboard can silently mix workloads, scenarios, accuracy targets, units, or system-level and per-accelerator numbers. Traditional browser automation makes that worse because an agent has to infer meaning from controls and tables. I wanted a safer collaboration model: the website should expose the exact research operations it supports, the agent should act on the same visible interface as the human, and every answer should remain traceable to immutable benchmark evidence. What it does Inference Chip Index turns official MLPerf Inference v6.0 results into workload-specific, source-linked comparisons. Its leaderboard now exposes four imperative WebMCP tools: list_inference_slices discovers valid exact comparison boundaries. configure_inference_leaderboard changes the filters visible to the human. compare_inference_accelerators compares 2–8 accelerator families inside one exact slice and renders the result on the page. clear_inference_comparison removes the shared comparison without resetting the leaderboard. The central safety rule is simple: a tool cannot claim that one chip is universally fastest. Every comparison is constrained to the same release, Closed division, workload, scenario, accuracy target, metric, and unit. Results include immutable GitHub source URLs and SHA-256 hashes. If evidence is missing, the tool returns an explicit missing-evidence reason instead of inventing a number. How I built it The application uses Next.js App Router, TypeScript, React, and Cloudflare Workers through OpenNext. The normalized data is generated deterministically from the pinned MLPerf Inference v6.0 commit 4d3916ac9cf474b679cdfcf492d43a0559418ad1 . During the WebMCP Challenge submission period I added the browser-native collaboration layer with the imperative document.modelContext.registerTool() API. Pure validation and comparison logic lives in src/webmcp/leaderboard-tools.ts ; registration and visible state updates live in the leaderboard React component. An AbortController unregisters the tools cleanly when the component unmounts. The WebMCP layer reuses the same checked-in dataset and exact-slice invariants as the site. It does not introduce a parallel ranking implementation, fetch untrusted runtime data, invoke paid endpoints, or expose secrets. Tool input schemas reject unknown fields and validate all slice IDs, vendors, submitters, grouping modes, metric views, and accelerator slugs. Challenge-period work The reproducible data index and Lucid API existed before the event. The WebMCP extension was built specifically during the challenge window. Public commits 7b89ee5 through fd9f65f add the imperative tools, shared-state UI, tests, documentation, security header, MIT license, and production URL documentation. The public deployment includes that extension. Challenges I ran into Converting a dense technical leaderboard into a small, predictable tool surface without duplicating ranking logic. Keeping agent actions visible to the human while preserving manual control of the same React state. Preventing incompatible benchmark dimensions from being compared even when an agent supplies plausible-looking inputs. Explaining absent results as evidence gaps rather than treating them as zero. Preserving immutable provenance in every structured response without overwhelming the visual interface. Accomplishments that I am proud of One agent call can build a three-vendor comparison that immediately appears in the human's browser. Every returned row stays inside an exact benchmark slice and links back to immutable source evidence. The tool surface is read-only with respect to servers and payments, while still making useful visible changes locally. The app contains 145 verified results, 50 submitted systems, 13 normalized accelerators, and 9 exact slices. The implementation passes type checking, 21 automated tests, and a production build. What I learned WebMCP is most valuable when it exposes domain invariants, not when it merely turns every button into a tool. A good tool contract can make an unsafe action impossible, keep agent and human context synchronized, and communicate uncertainty as structured data. I also learned that browser-native tools can be a better accessibility and audit surface than invisible automation: the human sees the filters change, sees the comparison render, and can verify the same immutable sources the agent used.
