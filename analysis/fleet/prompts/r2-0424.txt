# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

What it does Data Canvas is a local-first visual analytics workspace for exploring data in the browser. How I built it The most important architectural decision was to give the UI and WebMCP the same path into the application. Both go through one action dispatcher. A chart created through WebMCP is a normal Data Canvas visualization. A filter created by an agent is the same filter the UI understands. Undo and redo work across actions from either side. DuckDB-Wasm owns the imported rows and runs the analytical queries. Zustand holds workspace state and history. React renders the interface, and ECharts renders the visualizations. The WebMCP layer currently defines 19 semantic tools around real Data Canvas operations. Agents can ask the application to analyze data, create a visualization, apply a filter, define a metric, or connect datasets. They cannot submit arbitrary SQL, JavaScript, DOM selectors, or ECharts configuration. Challenges I ran into The hard part was not registering WebMCP tools. It was making sure I did not build the application twice, once for humans and again for agents. That affected a lot of small decisions. Agent writes carry the workspace revision they observed, so an outdated action cannot overwrite newer human work. Human and agent actions also use the same domain rules instead of maintaining separate implementations. Data access needed the same care. Dumping an entire dataset into every agent call would defeat much of the point of a local-first analytics app. The tools instead expose schemas, statistics, aggregates, bounded previews, and the data needed for a particular analysis. Accomplishments that I'm proud of I'm most proud of the human-agent equivalence in the application. The codebase tests equivalent operations through the human and WebMCP paths and checks that they produce the same workspace state. Agent-created objects remain normal workspace objects, stale writes are rejected, and undo can reverse changes made by either side. I also like that none of this required adding an AI backend to Data Canvas. The application remains a browser-native analytics tool on its own. WebMCP gives an external agent a structured way to participate in it. What I learned I originally thought a capable agent would need very powerful tools. Building Data Canvas pushed me in the opposite direction. The useful tools turned out to be the ones that match operations the application already understands. create_visualization , apply_filter , or create_metric give the agent enough control to do real work while keeping the result valid, visible, and editable in Data Canvas. For me, that is the interesting part of WebMCP. The agent does not need to learn how to click through the interface when the application can expose what those controls actually mean. What's next for Data Canvas The biggest missing piece is local persistence. The current workspace lives in memory, so a reload starts a new session. Next, I want to persist complete workspaces locally and make them portable between browsers while keeping Data Canvas backend-free. I also want to extend the agent evaluations to longer workflows where a human and an agent repeatedly hand the analysis back and forth. What inspired me I was tired of the usual AI 3D demo: you type a prompt, a pile of objects appears, and you’re left wondering if it actually understood what you asked for. There’s no real way to work with the scene. You just watch it happen. WebMCP clicked for me because the page can be what the agent uses, not some API off to the side. Tools live on the site. A person can still be there, placing pieces, locking lots, arguing with the result. I wanted that to feel what we were accustomed to. A grid. A bunch of assets. You say "a harbor," or you drop a boat yourself, and the agent has to work in that same language. How I built it Everything runs in the browser. Next.js as a static export, React, Three.js for the isometric view, Zustand for the world. It deploys on a Cloudflare Worker. No login. Nothing on a server that "is" the scene. When the page loads it registers tools on document.modelContext . If something changes the world, it goes through one of those tools. Surprise Me button, share, the kit assets, and a connected agent all hit the same functions. Three.js only reads the state, the agent never talks to the renderer. I made the agent go through and follow a sequence instead of dumping pieces: get_occupancy → plan_scene → compose_scene → populate_zones → create_environment → inspect → validate_scene → repair_scene It thinks in lots ( C4 ), zones ( picnic ), and things like "east of the grill." validate_scene scores the result on six dimensions. Done means the score is high enough, not that a bunch of calls returned in an ok state. The assets are Kenney , CC0. Roughly 1,800 pieces in 22 packs. What I learned An agent can call place_piece 47 times and still not build a picnic. I had been treating a successful tool call as progress. It is not. I ended up scoring the scene and handing back repairs, otherwise it would stop early and look finished. Coordinates were a dead end. "Put this in the picnic zone, facing the grill" is something a model can actually use. (12.4, 0, -3.1) is not. If the agent can knock over what you just placed, you are not collaborating. That is why locks on human placed pieces and "build on this" matter as much as the fancy compose step. WebMCP being the only write path was annoying at first and then useful. I also needed to see what it was doing. The Details panel, the trace, the percentage all dove into what was happening behind the scenes. Otherwise it still feels like a black box, just a prettier one. Challenges I faced The first version technically used WebMCP and still sprayed pieces. My own runner was looping place_piece so the cursor had something to do. The model got a paragraph of instructions instead of a real sequence. Validation was so loose a picnic with no table could score 100. So I split it up. plan_scene does not mutate anything. Layout and objects are compose_scene and populate_zones . Twenty rules, each with a { tool, args, why } if it fails. repair_scene runs those. build_scene is the whole loop for hosts that will not steer. extend_scene is there because "add a harbor" should not delete the village. Most of those bugs were the same issue: the person and the agent are looking at one stage. If that stage is lying, the whole thing falls apart. Getting registerTool working was the easy part. Like Comment Story Updates Inspiration When I started looking into going to the gym, getting a workout plan was easy. ChatGPT could make one in seconds. The problem was actually using it: the routine stayed in the chat, my workout logs lived somewhere else, and ChatGPT had no way to know what I completed or how much weight I used. I built GymDeck to connect those steps. ChatGPT can create the plan directly inside the workout tracker, while GymDeck records what actually happens in the gym. That history gives the agent enough context to recommend what should change next. And the best part of all, it's free! Training should still be a routine. The agent is most useful when it helps improve that routine over time or adapt it when something changes. For example, when equipment is unavailable, time is running short, or the user wants to have a change of scenery. ## What GymDeck does GymDeck is a mobile-first workout tracker designed for human-agent collaboration through WebMCP. A user can: Create and edit a multi-day workout plan Load a saved training day as today’s workout Track sets, reps, weight, effort, notes, rest time, and cardio Replace or reorder exercises during a workout Preserve completed work when a workout changes Review training history, volume, consistency, and personal records Receive clear progression recommendations based on previous performance Accept, edit, ignore, or apply those recommendations to the saved plan Through WebMCP, ChatGPT can read and update the same workout state shown in the interface. It can create a plan, add or replace unavailable exercises, shorten a workout, log sets, review history, recommend a new weight, and apply that change directly to the next session. Every human and agent change is visible in GymDeck’s activity history and recent changes can be undone. ## How I built it GymDeck is built with React and TypeScript and hosted as a browser-based application without a built-in application server. The app exposes 23 tools using document.modelContext.registerTool() . These tools are separated into focused read and write actions, including: Reading the athlete profile, current workout, saved plan, and exercise history Creating or editing training plans Adding, replacing, or reordering exercises Logging and correcting completed sets Adding timed cardio Reviewing progress Generating progression recommendations Applying accepted recommendations to the saved weekly plan The normal interface and WebMCP tools call the same underlying state functions. This keeps the visible workout, history, recommendations, and agent actions synchronized. All important data is stored locally in the browser using versioned persistence. GymDeck works after a refresh and supports JSON import and export, demo data, and a fresh-workspace option. It does not require authentication, an external database, an OpenAI API key, or a chatbot embedded inside the app. ## Challenges I faced The biggest challenge was designing tools that an agent could use reliably. The first versions were too ambiguous. An agent might update only today’s workout when the user meant to change the saved plan, or interpret creating a first plan as replacing existing data. I separated these actions into clearer tools for first-time plan creation, explicit plan replacement, editing saved days, and loading a plan day into today’s workout. Another challenge was keeping history accurate across both human and agent actions. Correcting a completed set now updates its persisted history entry, repeated logging does not accidentally reopen a set, and replacing an exercise preserves work that was already completed. Progression also needed to be more than a generic message. GymDeck now compares recorded performance with the saved prescription, explains why it recommends increasing, maintaining, or reducing a weight, and can apply the accepted change back to every matching exercise in the plan. Finally, WebMCP support depends on the browser hosting the site. GymDeck’s manual workout interface works on mobile, but the complete agent workflow currently requires a WebMCP-capable desktop browser such as ChatGPT’s in-app browser. ## What I learned I learned that WebMCP is not about placing a chatbot inside a website. The important part is giving an external agent a clear and dependable interface to the product’s real state. Tool names, schemas, descriptions, safety boundaries, and return messages matter as much as the visual interface. Small, focused tools were much more reliable than broad actions that tried to handle every possible request. I also learned that a useful agent experience needs visible results. When ChatGPT changes a workout, the user should immediately see what changed, understand why it changed, and remain able to edit or undo it. GymDeck demonstrates how an agent can move beyond giving workout advice and directly help maintain a training routine that improves with the user. Merge Queue gives AI agents a branch instead of giving them the last word. Humans and agents can edit the same live application simultaneously, then safely merge their work without silent overwrites. Like Comment Story Updates Inspiration Most agent demos quietly assume the human stops touching the application while the agent works. That assumption will not survive the real world. A person might reassign an urgent task while an agent reorganizes the project board. A store manager might correct inventory while an agent prepares a merchandising update. Both actions can be reasonable, yet the application normally accepts whichever write arrives last and silently erases the other participant’s intent. Software teams solved a similar problem for source code with branches and three-way merges. We wanted to explore what that collaboration model could look like for everyday web applications. That became Merge Queue: humans keep working, agents get a branch. What it does Merge Queue is a local-first project board where a person and an AI agent can edit the same workspace concurrently without overwriting each other. When the agent begins a task, Merge Queue snapshots the current workspace and creates an isolated agent branch. The agent can stage multiple structured changes—moving tasks, assigning owners, changing priorities, updating deadlines, or archiving stale work—without mutating the live board. Meanwhile, the human continues working normally. When the agent finishes, Merge Queue performs a semantic three-way merge between: Base: the workspace when the agent started Human: the current live workspace Agent: the agent’s proposed workspace For every changed field, the merge engine determines whether: Only the human changed it, so the human value is preserved. Only the agent changed it, so the proposal can merge safely. Both selected the same value, so the duplicate change is collapsed. Both selected different values, so the decision returns to the human. Compatible work is merged automatically. Genuine disagreements appear as focused conflict cards showing the original value, the human’s choice, the agent’s proposal, and the consequence of each decision. The agent can request a merge review, but it cannot approve its own work. There is intentionally no agent-accessible commit tool. The final merge is committed through the visible human interface as one atomic revision. How we built it Merge Queue is a dependency-free web application built with JavaScript, HTML, and CSS. It runs entirely in the browser, persists versioned state locally, and requires no API key or backend service. The application is organized around a shared deterministic command layer. Human interface actions and WebMCP tool calls invoke the same underlying operations, which prevents the agent from using a hidden automation path with different behavior from the visible application. We implemented WebMCP using imperative tools registered on the top-level page with document.modelContext.registerTool . The tool surface allows an agent to: Read the live workspace and its revision Open an isolated agent branch Stage bounded task updates Stage new tasks Inspect the branch diff Generate a semantic merge preview Read unresolved conflicts Request visible human review Check the branch status Abort an uncommitted branch Revert the latest completed merge Each tool uses a narrow JSON Schema, validates its inputs again inside the domain layer, clearly describes its side effects, and returns enough structured information for the agent to verify the result and select the correct next action. Agent proposals are visually distinguished from live state. A moved task can appear as a proposed destination while its original live card remains intact. An activity timeline interleaves human actions, agent proposals, and system merge events so the collaboration remains understandable throughout the workflow. Merge previews are bound to a specific workspace revision. If the human changes the board after a preview is generated, that preview becomes stale and cannot be committed. The merge must be recalculated against the latest human state. Commits are atomic and idempotent. Repeated commit attempts cannot apply the same branch twice. The previous workspace snapshot is retained so an approved merge can be reverted as a new revision without deleting history. We also built a deterministic walkthrough that consistently produces safe changes, duplicate choices, and three meaningful conflicts. This makes the concurrency problem—and the value of the merge—visible in under ninety seconds. Challenges we faced Defining what a “conflict” means outside source code Text files have lines. Application state has meaning. Moving a task and changing its owner are independent operations that should usually merge. Moving the same task into two different workflow stages is a real conflict. Archiving a task while the other participant edits it also requires special handling. We had to model these cases semantically instead of treating every modified object as one large conflict. Preserving live human work The most important invariant was that an agent proposal must never mutate the human workspace before approval. We maintained separate base, human, and agent snapshots and forced every staged operation through the isolated branch. We added tests for independent edits, overlapping edits, creation, archival, stale previews, repeated commits, aborts, and reverts. Designing human control without approval fatigue Confirming every agent action would technically keep the human in control, but it would make the product painful to use. We moved approval from the individual-action level to the merge level. The agent can prepare a substantial body of work, while the human reviews only the places where their intentions actually differ. Making the agent understand what happened A correct interface is not enough if the agent receives an ambiguous result. Every tool response includes the current revision, branch status, affected records, and valid next step. The agent can distinguish between “staged,” “waiting for human resolution,” “ready for approval,” “merged,” and “aborted” without guessing from the page. Remaining useful without WebMCP The complete human interface and deterministic walkthrough work in ordinary browsers. When WebMCP is available, the agent discovers the structured tools and participates directly. When it is unavailable, the project remains a functional demonstration of the merge model rather than displaying a broken screen. What we learned The most important lesson was that safe agent collaboration is not only about restricting what an agent can do. It is also about defining how agent intent coexists with human intent. Audit logs explain what happened after the fact. Approval dialogs interrupt actions before they happen. Merge Queue explores a third primitive: allow both participants to work, calculate where their intentions are compatible, and return only the irreducible decisions to the person. We also learned that tool results are part of the user experience. A useful WebMCP tool needs more than a successful return value—it should explain what changed, what remained untouched, what state the workflow is now in, and what the agent should do next. Most importantly, WebMCP feels strongest when it enables a collaboration model that ordinary browser automation cannot reproduce reliably. Merge Queue is not simply a faster way for an agent to click task-board buttons. It gives the agent a typed, versioned role inside the application. Genuine conflicts remain human decisions. Stale previews cannot commit. Commits are atomic and idempotent. Completed merges remain recoverable. A streamer dashboard with a built-in AI teammate: it proposes themed setups, teaches the UI with guided tours, and edits vertical clips you approve everything Like Comment Story Updates Home Clipit Studio Custom Command Chat Alert Overlay Builder StreamBot — Agent Edition Project Story Inspiration Streamers run a one-person production studio. Before they ever go live, they may have to manage chat commands, alerts, timed promotions, overlays, clipping highlights for TikTok, and countless other pieces of production across a dozen different tabs. Meanwhile, AI agents are still largely stuck outside the product. They screen-scrape interfaces, guess which buttons to click, and operate without a real understanding of the application's state. We wanted to change that. StreamBot is a real streamer dashboard already in production use. The WebMCP Challenge gave us the missing piece: instead of bolting an AI chatbot onto the side of the product, we gave the agent a first-class seat inside the application . The agent uses the same tools as the streamer, operates against the same state, and leaves the same audit trail. That led to the question driving this project: What does setup feel like when a streamer and their AI agent share one workspace, while the human remains in control of anything that matters? What It Does Three experiences define StreamBot Agent Edition. 1. Propose, Don't Just Do The agent isn't simply given unrestricted control. A streamer can say: "Set up my horror night." Instead of immediately changing their dashboard, the agent creates a complete themed proposal: !scary and !brave commands 👻 Follow alerts Timed promotional messages A JUMPSCARE channel-point reward A follower goal bar Other relevant stream configuration The entire setup appears as a review card . The streamer can inspect the proposal, remove anything they don't want, and then hit Approve . Only after approval does the agent execute the changes. Proposal → Review → Approval → Execution It's collaboration with a veto, rather than blind automation. 2. Guides That Teach on the Live UI Agents shouldn't teach users from outdated screenshots or hallucinated interfaces. If a streamer asks: "How do chat alerts work?" The agent first uses discover_targets to inspect the actual DOM and identify the elements currently available on the page. It then uses compose_tour to build a spotlight walkthrough directly against those discovered elements. The result is a guide that operates on the real product, in its current state . No stale screenshots. No guessed buttons. No hallucinated UI. The agent discovers the interface first, then teaches from reality. 3. Skilled Hands, Not Chat The agent isn't limited to answering questions. Inside StreamBot's ClipIt editor, it can stage vertical social edits directly against the mounted editor state. That includes: Vertical layouts Facecam resizing Caption placement Real transcribed captions Designer-created caption presets Editor configuration The agent isn't pretending to edit a clip through text. It's operating the actual editor. How We Built It with WebMCP Route-Scoped Tool Suites Each StreamBot dashboard route registers the tools relevant to the feature currently being viewed. Examples include: Commands Alerts Timed Messages Rewards Canvas ClipIt This is implemented through src/webmcp/suites.ts . The agent only sees tools that are valid for the current context and available to its seat. The Agent Uses the Same API as the UI We didn't create a separate "AI version" of StreamBot's functionality. Every agent tool calls the same endpoints used by the human interface . That means the resulting state is identical regardless of who performed the action. For example: Agent creates !scary → the command immediately appears in the streamer's command list. There is no synchronization layer or second source of truth. Agent actions and human actions operate on the same application state. Tool executions are also written to the account's audit log, just like actions performed by other members of the team. A Bridge into Live Editors For ClipIt, we needed the agent to interact with a mounted editor rather than a traditional API. We built mountClipItEditorCommands , which connects the WebMCP suite directly to the ClipIt store. The bridge dispatches real reducer actions and waits for state convergence before reporting success. That distinction matters. We don't report success because an action was dispatched. We report success when the editor has actually reached the requested state. Human-in-the-Loop Primitives Human approval is built into the tool architecture itself. propose_stream_setup opens a PrepProposalCard and blocks execution until the streamer makes a decision. Our guide tools work similarly: they compose tours from curated block types that can only be placed on targets discovered from the current page. The agent therefore has useful autonomy without having unlimited authority. Permissions The agent is treated as a real seat within StreamBot. Its permissions are governed through: Settings → Your Team Tool suites are only registered in areas where the agent has permission to operate. Challenges 1. Timeouts That Lied Our first ClipIt bridge used pixel changes as proof that an operation had succeeded. That seemed reasonable until we encountered a simple case: A facecam was already in the requested position. The operation succeeded, but because the pixels didn't change, the bridge waited 12 seconds and eventually reported a timeout. We rewrote the system around state convergence instead. A no-op move is now considered a successful operation if the editor is already in the requested state. We also added fail-fast validation using valid-ID lists. 2. Making the Demo Deterministic Transcription and streaming are inherently live, variable, and slow. A two-minute demo can't wait around for production systems to finish processing. We built a simulated backend using: An in-browser API shim A simulated stream engine Deterministic application state This gives us a world that behaves like the real product without depending on unpredictable external timing. For captions, we went further. The demo pipeline uses real ASR transcripts generated with the same model and segmentation approach as production , then bakes those transcripts into the demo environment. The result is deterministic while still containing genuine transcribed speech , rather than lorem ipsum pretending to be captions. 3. Spotlight Honesty Our earliest tours referenced UI elements that didn't actually exist on the current page. That exposed a fundamental problem with agent-generated walkthroughs: The agent was assuming what the interface looked like. We turned the fix into a core design principle: Discover before you teach. Every walkthrough begins with discover_targets . The tour is then composed against what actually exists. What We Learned The biggest lesson was simple: Agents Don't Need More Autonomy. They Need Better Seats. Once the agent shared the human's: Tools Application state Permissions Audit trail Context the interaction fundamentally changed. It stopped feeling like: "Prompt and pray." And started feeling like genuine teamwork: Proposal → Review → Approval → Execution The guardrails aren't friction. Scoped tool suites, approval cards, permission boundaries, and discover-before-teach aren't there to make the agent weaker. They're what make the agent trustworthy enough to delegate to . That's the direction we believe the agent-native web should move toward: AI agents shouldn't sit outside applications, guessing how to use them. They should have a real seat inside the product with the right tools, the right context, and a human who stays in control.
