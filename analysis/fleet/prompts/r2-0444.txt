# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A confident click or agent response could submit an order he never actually reviewed. ExactCue asks a simple question: Can a website promise that the action it commits is still the action the person reviewed? We use a synthetic pharmacy refill because the failure is instantly understandable, while the underlying pattern applies to any consequential browser action. What it does ExactCue gives a person and their browser agent shared custody of one action: The agent prepares. Through WebMCP, it selects two eligible prescriptions and a pickup pharmacy using the tools the page currently allows. Marcus reviews. ExactCue creates one visible, spoken, and machine-readable summary of the exact order, including its current version. The server checks. When Marcus confirms, the server commits only if the pharmacy record is still the version he reviewed. ExactCue proves the result. A successful action earns an authoritative receipt. If the record changed, the outdated refill is blocked, nothing is submitted, and Marcus is guided to the current record. The demo’s signature moment is a real failure test: another request reaches the server first, the record moves from v1 to v2, and Marcus’s original action receives HTTP 409 · NO WRITE . The pharmacy is synthetic. The reusable product idea is current-state-bound actions for browser agents . Why WebMCP is essential Without WebMCP, a browser agent must infer controls from pixels or an accessibility tree. It can click the right-looking button, but the page has not given it a typed contract for the action, the current workflow state, or recovery. ExactCue makes WebMCP load-bearing: The page exposes only the tools valid for the current step. Prescription tools retire when the flow moves to pickup; pickup tools retire at review. The agent and the visible interface operate on the same live order. review_order returns the exact cue as structured data, not just screen text. submit_refill carries the reviewed version and ETag to the server. reload_current_record gives the agent a structured recovery path after a conflict. Remove WebMCP and the agent loses the page-declared workflow contract. Remove the server check and ExactCue loses its central promise. The product needs both. That became the starting point for ClearRights Privacy. The goal is not to replace privacy laws, consent platforms, or legal review. It is to give websites a structured layer that can connect their existing controls to both people and agents, while keeping a clear history of what was prepared, approved, applied, and verified. The central question was: What if a website exposed its privacy controls as a structured, agent-readable model while keeping final authority visibly with the person? This led to one simple principle: Agents prepare privacy changes. People approve them. Websites apply and verify the result. What it does ClearRights Privacy is a headless SDK and reference implementation for privacy settings that people and compatible agents can use together. A developer describes the website's controls once: what each setting does, whether it is required or optional, what data it uses, and what changes when it is enabled or disabled. The human interface and the WebMCP tools then use the same structured model. I built Waypoint Travel, a fictional travel website, to demonstrate the complete flow. An agent can inspect the current configuration, explain individual settings, identify the required services, and prepare a plan based on a natural request such as: Keep booking and account security, but disable personalised recommendations, location suggestions, and partner offers. The proposed plan opens in the same interface the person can use manually. It clearly shows each change and its consequences, but it does not modify the product yet. The agent marks the plan as prepared, while the human check remains separate. The person must hold the visible control to confirm that they reviewed that exact plan. Only after this step does apply_privacy_plan become available as a WebMCP tool. When the tool is invoked, Waypoint applies the complete approved state through an adapter and reads it back from the target system. If the result does not match the plan, the operation fails closed. If it matches, ClearRights creates a verified receipt containing the decision, revision, approval method, adapter, and readback result. The effect is also visible in the product itself: recommendations become generic or personalised, and optional surfaces such as nearby suggestions and partner offers appear or disappear. Preparing a plan alone never changes the experience. Waypoint is a local fictional demonstration, not a compliance product. The same architecture could later connect to a real consent platform, backend, feature-flag system, or data pipeline through host-owned adapters.
