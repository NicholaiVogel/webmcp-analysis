# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Turn any website into an agent opportunity map. Like Comment Story Updates Inspiration AI agents can understand websites, but they still interact with most of them like humans: reading pages, interpreting interfaces, finding controls, and simulating clicks. These workflows are slow, fragile, and often fail when a website’s layout changes. WebMCP offers a better approach. Websites can expose structured tools that agents discover and call directly while keeping people involved in the same visible experience. That inspired us to build WebMCP.ai: a tool that analyzes any public website and identifies the most useful opportunities for making it agent-ready with WebMCP. What it does Users provide a public website URL, and WebMCP.ai researches the website, understands its business and primary workflows, and generates an evidence-backed WebMCP opportunity report. Each report includes: An overall agent-readiness score Scores for discoverability, structured data, agent actions, automation, and MCP potential Ranked WebMCP tool opportunities Proposed tool names, descriptions, and input/output schemas User value, business value, implementation difficulty, and safety ratings Authentication, authorization, validation, confirmation, and audit safeguards Research sources and clearly identified limitations A production-ready implementation prompt for coding agents Users can filter and compare opportunities, select the tools they want to build, and export the report or implementation prompt. WebMCP.ai is itself WebMCP-enabled. It exposes three browser-native tools: analyze_website analyzes a public website and updates the visible report. get_opportunity_report returns the complete current report. select_tools_for_plan selects recommendations and creates a tailored implementation plan. This means an agent can operate WebMCP.ai directly without typing into the URL field or clicking the Analyze button. The agent and user remain in the same interface and share the same application state. How we built it We built WebMCP.ai as a full-stack Next.js application using React and TypeScript. The analysis pipeline first validates the submitted URL and rejects embedded credentials, unsupported protocols, private networks, local addresses, and unsafe redirect destinations. It then performs a bounded crawl of relevant public pages using Cheerio. The extracted content is explicitly marked as untrusted data before being sent to an OpenAI-compatible Responses API. The model researches the website’s business, workflows, public APIs, competitors, and relevant MCP precedents. Its response must match a strict Zod schema before the application accepts it. Opportunity scores are calculated deterministically rather than relying entirely on model judgment. The application then builds a structured implementation prompt containing tool schemas, safeguards, engineering requirements, testing expectations, and acceptance criteria. The WebMCP integration uses the imperative document.modelContext.registerTool API. Tools are registered once with AbortSignal cleanup and reuse the same logic and React state as the visible interface. The application is deployed on Vercel, while the source code and project documentation are hosted publicly on GitHub. Reports remain in browser memory, so no database is currently required. Challenges we ran into One major challenge was working with websites that block automated access, require authentication, or render most useful content through client-side JavaScript. We addressed this by reporting incomplete access honestly and grounding every recommendation in the evidence that was actually available. Analysis requests can also take time because they combine website extraction, research, structured generation, and validation. We introduced bounded timeouts and a fallback analysis path when enriched web research takes too long. Another challenge involved WebMCP lifecycle management inside React. Initially, tool registration could be recreated when the URL or report state changed. We stabilized the callbacks and used references to the latest report so agents retain valid tool handles while the interface updates. Security was equally important. A tool that accepts arbitrary URLs can create server-side request-forgery risks, while crawled content can contain prompt-injection attempts. We added DNS and redirect validation, private-network blocking, content-size limits, bounded crawling, strict schemas, and explicit untrusted-content boundaries. Finally, we had to ensure agents selected the WebMCP tool instead of falling back to browser interaction. Accurate read-only annotations, stable registration, and direct tool descriptions made that behavior reliable. Accomplishments that we’re proud of We are proud that WebMCP.ai does more than generate generic tool ideas. It produces ranked, evidence-backed opportunities connected to real workflows, business value, technical feasibility, and safety requirements. We are especially proud that the application demonstrates the experience it recommends. Agents can call WebMCP tools directly, update the same interface the user sees, retrieve the resulting report, and collaboratively choose an implementation plan. Other accomplishments include: Strictly validated structured model output Deterministic opportunity scoring Transparent evidence and limitations Production-oriented implementation prompts SSRF and prompt-injection defenses Stable WebMCP registration and shared UI state Automated unit, integration, lint, type, build, and end-to-end checks A responsive interface with report and prompt exports What we learned We learned that effective WebMCP tools should not simply reproduce button clicks. The best tools expose stable business capabilities with clear inputs, structured results, and well-defined safety boundaries. Tool metadata also matters more than expected. Names, descriptions, schemas, annotations, and lifecycle behavior determine whether an agent can confidently discover and use a tool. We also learned that agent readiness is not purely a technical score. Authentication, data availability, business value, user trust, implementation effort, and human confirmation all influence whether a workflow should become a tool. Most importantly, WebMCP works best as a collaboration layer. It does not need to replace the interface. It can connect agents to the application’s real capabilities while keeping the user informed and in control. What’s next for WebMCP.ai Next, we want to add: Saved and shareable reports with explicit retention controls Repeatable WebMCP evaluations that measure tool-selection accuracy Before-and-after readiness comparisons Organization workspaces and collaborative reviews Direct export to GitHub issues and engineering backlogs Automated validation of implemented WebMCP schemas Historical monitoring as websites improve their agent readiness Additional analysis of authenticated workflows through approved integrations Our long-term goal is for WebMCP.ai to become the bridge between human-first websites and agent-native experiences: helping teams decide what to expose, why it matters, how to build it safely, and whether it actually improves the experience. A birth triggers 15–40 separate actions scattered across the Social Security Administration, the health insurer, and the employer's HR portal — each with its own login, its own forms, its own deadlines (add a dependent within 30 days or wait for open enrollment), and its own ways of spelling the same name. Humans have always been the integration glue between these portals: re-typing identical data, making format mistakes, missing windows. What it does Type one sentence — "We had a baby girl on June 3rd at General Hospital." Inspiration Cyber incident investigations require analysts to distinguish carefully between what the evidence actually shows and what is merely an interpretation or hypothesis. AI agents can help investigate, summarize, correlate, and organize large amounts of technical evidence. But their conclusions should remain traceable to the underlying data and subject to meaningful human review. EvidenceFlow was inspired by that problem: how can humans and AI agents investigate cybersecurity evidence together without losing the distinction between evidence, inference, and validated conclusions? What it does EvidenceFlow is a human-agent workspace for cybersecurity incident investigation. Using WebMCP, an AI agent can: discover available incidents; retrieve structured incident evidence; analyze events chronologically; propose a finding linked to specific evidence IDs; assign a confidence level; recommend a next investigative action. Every agent-generated finding enters the application as pending-human-review . A human investigator can then Approve, Reject, or request more evidence through the application interface. EvidenceFlow deliberately exposes no WebMCP tool for approving or rejecting findings. Validation remains a separate human-review step outside the WebMCP tool surface. The current demo uses a synthetic SSH authentication incident. How I built it EvidenceFlow is a static web application built with HTML, CSS, and JavaScript and deployed through GitHub Pages. I tested the tools in Chrome with WebMCP support and the WebMCP Model Context Tool Inspector on the public GitHub Pages deployment. I also validated an agent-driven investigation workflow in which the agent autonomously selected and executed the registered WebMCP tools from a natural-language investigation request. Challenges I ran into One challenge was designing the boundary between agent capability and human authority. It would have been easy to expose a tool that allowed the agent to complete the entire workflow automatically. Instead, I chose to make proposal and validation separate operations. Tool boundaries, data provenance, validation, failure behavior, and human oversight all become part of the application design. WebMCP provides an interesting way to make those capabilities explicit at the browser level rather than requiring an agent to infer application behavior only from the visual interface. A capability describes what an agent is allowed to read or do with that component. They solve similar UI problems, but their APIs are not always the same. I had to make sure that the WebMCP-facing semantics stayed consistent even when the underlying implementation was different. Another important challenge was deciding what should not be automatic. Just because an agent can press a button does not mean it should automatically understand the business meaning behind it. For more important actions, Duz UI lets the developer explicitly expose the action instead of guessing based on the button text. It now has a real CLI, a shadcn-compatible registry, migration support, Radix UI and Base UI support, custom component support, a diagnostics command, a live playground, documentation, and automated tests. Not everything in application state should automatically be readable, and not every action should automatically become callable. Another big lesson was that adoption matters. Problem Coding agents can work quickly, but teams of people still need a reliable way to decide what someone's agent may do, prevent two agents from taking the same task, review a plan before implementation, and see what happened after the agent stops. Issue trackers record work for people. Agent transcripts record work inside one conversation. Neither gives people and browser agents a shared, live workflow with explicit ownership and bounded actions. Solution Repo Board is a real-time task board for one GitHub repository. Humans create and groom tasks in a five-column workflow: Todo -> Ready -> In Progress -> In PR -> Done The page exposes WebMCP tools for the actions that are allowed in the current context. A Codex agent can inspect tasks, claim one, attach or revise a plan, start work, report progress, link a pull request, read review state, and check CI. Humans retain authority over sensitive actions such as replacing an active owner, canceling work, and archiving a completed task. The first valid claim wins. Ownership is bound to the signed-in GitHub user and the browser tab, backed by an unguessable per-tab capability. It does not expire because a timer ran out or a WebSocket disconnected. Another agent can take over only after the person using the page confirms it. Why This Matters Agent coordination fails in ordinary, expensive ways: two agents edit the same work, a plan gets separated from its implementation, a stale browser tab continues mutating state, or a human cannot tell whether a status report came from the repository or from the agent itself. Repo Board makes those boundaries visible and enforceable. The person and the agent work against the same task, plan revision, board revision, pull request snapshot, and activity history. The app treats task text, plans, progress reports, and GitHub content as untrusted data. That content cannot select tools, authorize a mutation, choose a repository, or supply secrets. How We Used AI Repo Board does not embed a model or require an OpenAI API key. It gives an AI agent a precise interface to a live product through browser-native WebMCP. The agent discovers only the tools that are valid for the current user, selected task, assignment, and workflow state. For example, an unassigned Ready task exposes claim_task .
