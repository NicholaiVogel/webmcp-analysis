# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

ABOUT TEXT (untrusted evidence):
ANAI is an AI agent that discovers and executes real WebMCP tools to automate infrastructure safely, stopping at consequential actions until a human approves. Like 1 Comment Story Updates The Problem AI agents are getting very good at reasoning about what users should do. But there is a gap between telling someone how to operate a web application and actually operating that application . For infrastructure workflows, that gap matters. An agent might be able to recommend a compute service, compare prices, configure an environment, and validate it — but traditionally, the final interaction still depends on clicking through the application's UI or building a separate integration. We wanted to explore a different model: What if the web application itself could expose its capabilities directly to an AI agent? That's where ANAI comes in. What We Built ANAI is an operating layer for WebMCP-enabled web applications. Forge is a simulated cloud infrastructure workspace that exposes its capabilities as WebMCP tools. ANAI discovers those tools through the browser's model context and uses them to operate the application. A user can simply provide a requirement such as: "I need an AI backend under $50/month. Don't touch production." ANAI turns that outcome into an operational plan. It can then: Discover available infrastructure services Retrieve service details and pricing Compare possible services Calculate the resulting cost Create a development environment Configure the selected services Validate the configuration For our golden demo, ANAI produces a four-service development environment costing $42.02/month . But there is an important boundary. ANAI does not autonomously cross consequential actions. When deployment requires human approval, it stops at a confirmation gate and clearly shows what will happen, the environment, and the estimated cost. Only after the user clicks Confirm deployment does the simulated deployment proceed. Production remains unchanged throughout the workflow. Why WebMCP? The important part of this project is that ANAI isn't controlling Forge by pretending to understand its UI. Forge exposes actual capabilities as WebMCP tools. ANAI discovers those capabilities through the browser and invokes them through the WebMCP API. The results of those calls become evidence for the next steps in the plan. The flow is: User requirement → ANAI → WebMCP discovery → real tool execution → Forge state → validation → human approval → result This creates a much more explicit boundary between an agent and a web application. The application defines what the agent can do. The agent doesn't invent capabilities that aren't exposed. Safety by Design We deliberately designed the demo around constrained autonomy. ANAI can automatically perform lower-risk, reversible development operations, but consequential deployment actions remain behind a human confirmation boundary. We also enforce development-only behavior in the demo. ANAI never receives a production target, and production state remains isolated and unchanged. The confirmation gate is not just visual. The underlying deployment action is blocked until explicit human approval. We also tested failure scenarios, low-budget requirements, unsupported requests, retries, and repeated deployment calls to verify that the safety boundary and idempotency behavior remain intact. How We Built It The project is a Next.js application with a deterministic client-side infrastructure runtime. The Forge surface exposes 10 WebMCP tools , including service discovery, service details, comparison, pricing, cost estimation, project creation, configuration, validation, deployment, and platform inspection. ANAI has a deterministic requirement parser and planner. The planner uses the requirement to determine the objective, budget constraint, development environment, and production constraint. Every agent action goes through the registered WebMCP tool interface: getTools() → discover capabilities → executeTool(RegisteredTool, JSON.stringify(args)) We also built a second independent WebMCP surface called Repo , which exposes five development-repository capabilities: create_repository get_repository configure_repository set_environment validate_repository Repo has its own state, types, registration layer, and contract verification, demonstrating that the approach is not tied specifically to Forge. What We Learned The biggest lesson was that building an agent that can actually operate a web application is very different from building a chatbot that describes what should happen. The WebMCP contract becomes an important part of the system design. We had to think carefully about: What capabilities should the application expose? What arguments should each tool accept? Which actions are safe to automate? Where should human approval be required? How should tool results become evidence for subsequent planning? How do we prevent production state from leaking into an isolated development workflow? How do we make the agent's activity observable without fabricating reasoning? We also learned that refusing an unsupported request is often better than improvising a plan. ANAI deliberately uses deterministic requirement matching and refuses scenarios it cannot safely support. Challenges One of the biggest challenges was preserving a clean separation between agent reasoning, application capabilities, and human authorization . It would have been easy to create a scripted demo that simply moved through predetermined UI states. Instead, we verified that the workflow uses the actual registered WebMCP tools and that the UI reflects the resulting application state. We also tested the WebMCP contracts independently, including tool names, descriptions, schemas, argument formats, failure handling, retries, and isolation between Forge and Repo. The final system has 61 automated tests across 19 suites , along with linting, TypeScript checks, production builds, and Chrome-based end-to-end verification. The Result ANAI demonstrates a simple idea: A web application can expose its capabilities to an AI agent without giving the agent unlimited control. The application defines the tools. ANAI discovers and operates them. The application enforces the boundaries. And the human remains in control when the action becomes consequential. That's the direction we wanted to explore with WebMCP. Tell us what happened and agent turns it into a simple Situation Map for housing, power, documents Like 1 Comment Story Updates Inspiration After a flood or fire, people often have to explain what happened over and over again—to the county, the utility company, housing programs, and different relief organizations. When your home is already damaged, even figuring out which form to start with can be overwhelming. The problem isn't always that nobody wants to help. It's that the help is spread across different websites, forms, and systems that don't really talk to each other. We started wondering: what if an agent could handle some of that coordination for you, without making decisions on your behalf? That is what made WebMCP interesting to us. A website can expose specific tools to an agent while still controlling exactly what the agent is allowed to do. The agent can take care of repetitive work, while the resident stays in control of what gets shared, approved, or submitted. What it does 2030MCP LinkUp is designed for the days after a flood, fire, earthquake, storm, or other disaster. Instead of entering the same information into multiple systems, you explain what happened once. LinkUp turns that into a simple Situation Map showing what it understood, what information is still missing, and which services may be relevant. For example, the system may identify that you need temporary housing, utility support, replacement documents, or disaster relief. The agent can then read provider requirements, organize the information you already provided, and prepare the next step for you. The important part is that it does not make the final decision. It cannot decide whether your story is true, approve your case, or submit something on your behalf without your review. You see what the agent plans to do first and choose whether to continue. How we built it We built LinkUp with Next.js App Router, TypeScript, and Tailwind CSS. The WebMCP layer is built around document.modelContext.registerTool. Instead of registering every tool all the time, LinkUp rebuilds the available tool registry from the current signed case state. That means a tool only becomes available when the user has reached the right step and given the required consent. We also enforce the same boundaries on the server. Route handlers validate signed session data including the user's role, disaster scenario, and origin. We use strict Zod schemas, state version checks, idempotency keys, packet hashes, expiring grants, and rate limits to prevent replay, tampering, or unintended submissions. Every action that changes the case is also recorded in a server-side audit log. For the disaster flows, we created separate provider fixtures for floods, fires, earthquakes, and storms. The provider policy version is selected before evidence is collected, so changing the incident later cannot silently change the rules applied to the case. Testing was a major part of the project. We currently have 108 Vitest tests covering the WebMCP contract, dynamic tool registration and removal, replay prevention, tamper rejection, and session integrity. We also run strict TypeScript checks and GitHub Actions with pinned revisions. Most importantly, we tested the real WebMCP flow in a browser using the native document.modelContext interface. We verified that the send tool appears only after consent and disappears again after it has been used. For Chrome testing, the project also includes a Chrome 149+ path using chrome://flags/#enable-webmcp-testing. To keep the demo easy to run, the entire resident session survives serverless cold starts without requiring a database. Case state is stored in signed, Brotli-compressed cookie chunks with strict size limits. We also test the deployed version with npm run test:golden to make sure a fresh incognito session can complete the full flow from beginning to end. Challenges we ran into The hardest part was making "the human is in control" something the system actually enforces. At first, it is tempting to put instructions in the tool description and say that the agent should ask before doing something important. But that still depends on the model following the instruction. We wanted the restriction to exist at the system level instead. So we moved permissions into the tool registry itself. A consequential tool does not exist until the user has explicitly given consent. After a one-time action is used, the tool removes itself from the registry. That gave us something we could actually test: not just whether the agent behaved correctly, but whether the tool was available at all. Another challenge was writing tool descriptions for an agent rather than for a person. We added clear authority boundaries such as CONSEQUENTIAL, ONE USE, explicit fields that prevent the agent from implying provider approval, and untrustedContentHint for information that comes from free-text user stories. Another challenge was keeping a complete resident session working across serverless instances without a database while still staying inside browser cookie limits. Accomplishments that we're proud of We're proud that LinkUp actually works as a deployed product, rather than being just a mockup of an agent workflow. The WebMCP registry changes live as the resident moves through the process. A one-use send tool appears after consent, can be used once, and then disappears. We also built a read-only audit interface so another agent can inspect what happened without being able to change the case. And instead of using one generic disaster demo, we built separate provider contracts for floods, fires, earthquakes, and storms so the workflow behaves differently depending on the situation. What we learned If a tool should not be available yet, the safest option is not to register it at all. We also learned that tool descriptions matter much more than we expected. They are not just documentation for developers; they are part of the interface the model uses to understand its authority and responsibilities. Clear descriptions made the agent much more likely to ask for review instead of acting as if it had approval from a provider. WebMCP also showed us a different way to think about agent safety. Instead of putting every restriction inside a chat prompt, some of the rules can be enforced directly by the website and its tool lifecycle. What's next for 2030MCP LinkUp First, a server-issued human-presence challenge so consequential actions can verify that a real resident is still present. Second, an encrypted case database for longer-term recovery cases and larger documents. Third, real provider integrations for housing agencies, utilities, local government, and relief organizations. The WebMCP contracts are already structured so providers could publish their own requirement and submission tools. The county, housing, and utility portals in our demo are examples of how those provider-owned integrations could work. The long-term goal is simple: people should not have to rebuild the same disaster story for every organization they need help from. They should explain what happened once, review what gets shared, and stay in control of the process. Canter is a hosting control plane built for AI agents to operate and humans to govern. Like Comment Story Updates Inspiration Agents can write code, but running what they build still pushes them toward either brittle shell access or infrastructure credentials that are far too powerful. We built Canter around a different boundary: the agent proposes an exact, inspectable Change; the human governs authority and high-impact execution; and the control plane produces evidence of what actually happened. What it does Canter is an agent-operated, human-governed hosting control plane. An agent can inspect a System, draft a Change, and review an immutable execution plan without receiving provider credentials. Every proposed deployment is bound to an exact digest, policy is explicit, apply can require human approval, and execution produces durable receipts. For the WebMCP Challenge, Canter makes that workflow discoverable directly from the website. The site advertises same-origin agent discovery, provides WebMCP read and review tools, and points capable agents to the authenticated remote MCP contract for durable work. Browser tools cannot borrow the human session to bypass approval: a sensitive Change still needs a focused, short-lived review capability and an explicit human action. How we built it The control plane is written in Go with PostgreSQL-backed durable state. The product interface uses Next.js, React, and TypeScript. A typed System contract compiles into a deterministic execution graph before provider adapters can mutate infrastructure. The same semantic objects—Systems, Changes, exact digests, policy envelopes, operations, and evidence—are shared across the CLI, HTTP API, remote MCP, and WebMCP surfaces. The website registers its WebMCP tools through document.modelContext.registerTool. The public /.well-known/canter and /llms.txt routes explain the same-origin device flow, API, and Streamable HTTP MCP endpoint without exposing provider details. Authenticated agent installations are durable and revocable, with independent inspect, draft, and apply authority. Challenges we ran into The hard part was not exposing more tools. It was preserving a trustworthy authority boundary across several interfaces. We had to ensure browser tools remain read and review only, authorization binds to one immutable digest, replayed or expired approval links fail safely, execution can resume after interruption, and a failed release does not silently become desired state. Accomplishments that we're proud of One small vocabulary across web, CLI, API, MCP, and WebMCP: inspect System, draft Change, review exact digest, authorize, apply, inspect evidence. Agents never receive provider credentials or arbitrary infrastructure access. Human approval can be mandatory for apply while agents retain useful inspect-and-draft authority. Execution is evidence-producing, restart-safe, and able to contain unhealthy releases. The browser experience makes policy, pending work, exact plans, and agent authority visible at a glance. What we learned Agent infrastructure needs fewer ambient privileges and better semantic contracts. WebMCP is most useful when it is an adapter into a governed product model, not a shortcut around it. The strongest interface is one where both the agent and the human can see the same proposed Change and the same evidence. What's next for canter.dev We want to expand the provider adapter set, improve focused Change review, add more public verification recipes, and make the same governed deployment loop available to more coding agents without weakening the human boundary. The hard part was not learning one single thing. It was keeping up with dozens of small things every day: checking glucose, remembering meals and insulin, and trying to work out why the same routine sometimes produced a completely different result. \n\n A lot of the tools I found felt old, expensive, or disconnected from how I actually wanted to manage everything. At the same time, ChatGPT and other AI tools were becoming genuinely useful. I kept wondering what would happen if an agent could work inside a diabetes app with me, using the information already on the screen instead of making me repeat it all in a separate chat.\nThat idea became BetaTrace. \n\n What it does \n\n BetaTrace is a Type 1 diabetes dashboard that both a person and a browser-based agent can use. \n\n The dashboard lets someone explore glucose readings, meals, insulin entries, trends, and time in range. The WebMCP tools let an agent work with that same demo data: \n\n get_demo_state reads the current synthetic data, including seven days of glucose readings and logged meals. \n\n log_demo_entry records a glucose reading, meal, or insulin dose that the user says has already happened. \n\n reset_demo_data clears added entries and restores the original sample data, but only after the user confirms it. \n\n For example, I can ask an agent to graph my glucose and meals from the past week, log a new meal, and then generate the graph again. The new meal appears in both the dashboard and the agent’s updated graph. \n\n Without WebMCP, the agent would have to inspect the page, guess what each control does, and click through the interface. BetaTrace gives it clear tools with defined inputs and responses. \n\n How I built it \n\n BetaTrace is a React app hosted on Vercel. \n\n The page registers its tools directly with document.modelContext.registerTool(). There is no separate WebMCP server and no polyfill. The dashboard and the agent tools use the same validation and local data, so an entry logged by the agent appears on screen immediately. \n\n For the seven-day graph, get_demo_state returns 336 chronological glucose readings along with the meals recorded during that period. This gives the agent enough real structure to produce a useful graph instead of a rough summary. \n\n The public demo only uses synthetic data stored in the browser. Its WebMCP tools cannot reach Supabase, private accounts, or real patient information. BetaTrace can record an insulin dose that the user says they already took, but it will not calculate or recommend one. \n\n Challenges I ran into \n\n The first version could return a summary of the demo, but that was not enough to make a proper seven-day graph. We had to expose the underlying timeline while keeping the response clear and predictable for the agent. \n\n Keeping the agent and the visible dashboard in sync was another challenge. A successful tool call was not enough. If the dashboard did not update at the same moment, the whole idea of working together inside one page fell apart. \n\n The safety boundaries also took some thought. Health data is not a good place for vague permissions. We limited the demo to synthetic local data, validated every write, blocked dose recommendations, and made reset require confirmation. \n\n Accomplishments that I'm proud of \n\n The part I am most proud of is the full loop. \n\n An agent can read seven days of glucose and meal data, turn it into an interactive graph, log a meal supplied by the user, and then produce a new graph containing that meal. The person sees the same change inside BetaTrace. \n\n It sounds simple when written out, but that shared state is what makes the project feel like collaboration instead of ordinary browser automation. \n\n I am also proud that the safety limitations are part of the design rather than a disclaimer added at the end. The demo is useful enough to prove the idea without pretending that an experimental agent should be making treatment decisions. \n\n What we learned \n\n A button exposed as a tool is not automatically useful. \n\n The tool has to match something a person would naturally ask for. It needs understandable inputs, useful output, proper validation, and clear limits. Building the WebMCP layer forced us to think more carefully about what BetaTrace actually knows and what an agent should be allowed to do with it. \n\n We also learned that the best WebMCP moments are visible. When the agent logs a meal and the dashboard changes immediately, there is no need for a long explanation. You can see that the person and the agent are working with the same application. \n\n What's next for Betatrace \n\n The current version stays inside a synthetic guest demo on purpose. \n\n The next step would be optional authenticated accounts with narrow permissions, a visible history of agent actions, and confirmation for anything sensitive. Users should always be able to see what the agent accessed and what it changed. \n\n Future tools could prepare appointment summaries, compare glucose responses after recurring meals, and help someone collect questions for their care team.
