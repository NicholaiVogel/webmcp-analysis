# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Inspiration Embedded payments, authentication frames, editors, support widgets, and microfrontends often communicate through window.postMessage . When those integrations fail, developers see symptoms instead of causes: initialization vanishes, protocol versions drift, or a valid-looking message arrives from the wrong frame. Ordinary logs rarely preserve timing, event.origin , exact event.source identity, the developer's current selection, and the visible consequence in one place. EmbedDoctor began with a simple question: what if the live browser boundary itself could become a shared debugging workspace for a developer and an AI agent? What it does EmbedDoctor turns invisible iframe failures into browser evidence, a reviewed boundary contract, and a verified repair. The controlled checkout reproduces three real failure classes: Lifecycle race: INIT is sent before the payment widget installs its listener. Protocol drift: the host retries with protocol v1 while the widget accepts v2. Wrong frame identity: a same-origin sibling sends a valid-looking total update from the wrong WindowProxy , changing the checkout from $120.00 to $0.01 . The page records the actual message sequence, lifecycle state, origin, source classification, protocol version, policy verdict, and rendered result. An agent can inspect only the incidents selected by the developer, stage the smallest report-only contract justified by that evidence, replay the same seeded boundary, undo a proposal, and prepare an export. After the developer reviews and approves enforcement, the same seed runs again. READY/ACK initialization succeeds, protocol v2 is required, the exact origin and iframe source are bound, the sibling message is blocked before the application handler, and the checkout remains $120.00 . Why WebMCP The evidence that matters exists inside the active browser session. It includes the current incident selection, real MessageEvent.origin , strict event.source identity, iframe lifecycle, visible draft state, and rendered consequence. A CLI, remote MCP server, or conventional API could support part of this workflow only after adding custom page instrumentation and state synchronization. WebMCP lets the owned page expose semantic operations directly beside the live interface, with no screenshot guessing or copied logs. EmbedDoctor exposes five native tools: embeddoctor.inspect_selected_incidents embeddoctor.stage_boundary_contract embeddoctor.replay_boundary embeddoctor.undo_contract_change embeddoctor.export_contract_bundle Tool availability follows product state. Export is unavailable until a developer-approved contract passes an enforced replay. Every agent action appears in a provenance ledger as WebMCP ; manual fallbacks are visibly separate. Human control The agent can investigate, propose, replay, undo, and export. It cannot approve enforcement. Approval is deliberately absent from the WebMCP surface. The proposed contract remains visible and editable, and only the developer can activate it. This keeps the agent powerful at diagnosis while preserving human authority over a consequential runtime change. How we built it EmbedDoctor uses React 19, TypeScript, Vite, vinext, Tailwind CSS, and a framework-free boundary adapter. The demo contains a top-level checkout, an adopted payment iframe, and a same-origin sibling iframe communicating through real postMessage traffic. One pure evaluator powers both report-only and enforcement modes, so the policy decision stays identical while only forwarding behavior changes. Incidents, scores, evidence IDs, comparison rows, and receipts are derived from captured events rather than assigned by demo phase. Four seeded scenarios show that diagnosis changes with the evidence: Perfect storm: lifecycle, protocol, and frame identity Late listener: lifecycle only Rolling upgrade: protocol only Rogue sibling: source identity only The exported bundle contains the contract, TypeScript runtime adapter, regression tests, evidence metadata, and migration notes. Challenges The hardest challenge was making a lifecycle race reproducible without inventing browser evidence. We replaced independent timers with a causal fixture: listener pending, early INIT, listener installation, retry, observed schema error, and then the sibling mutation. A second challenge was proving why origin checks alone are insufficient. The rogue sender is deliberately same-origin, so it passes an origin allowlist. Only strict equality with the expected iframe's contentWindow catches it. A third challenge was preventing a polished demo from becoming a predetermined animation. Every visible result now traces back to concrete event IDs, and a safety timeout can produce failure but can never manufacture a passing receipt. The risky moment often comes before execution: an AI agent can prepare a technically valid-looking call before the human has verified the artifact, target evidence, limits, scientific intent or authority to spend. I built WebMCP-QCG to make that moment inspectable. Its promise is simple: review before you run. What it does WebMCP-QCG is a browser-native, human-in-the-loop quantum preflight workbench. A human imports a local Q# artifact. QCG keeps the source in session memory, computes a SHA-256 digest over the exact bytes, compiles it locally with the pinned Q# WebAssembly runtime and freezes a dated target-profile snapshot. Its deterministic policy returns exactly one recommendation: reuse_result reject recompile simulate_first ready_for_external_execution The agent can use four progressive WebMCP tools: inspect_quantum_experiment evaluate_quantum_call run_bounded_qsharp_simulation export_quantum_evidence_report The first two appear only after a human-loaded artifact is ready. A bounded simulation tool appears only after a valid simulate_first recommendation and visible human acceptance. Its one-use consent is consumed after invocation. QCG exports a JSON or Markdown evidence receipt binding the artifact, target snapshot, recommendation, human choice and measured effects. The MVP never submits a provider job, uses a provider credential or calls a QPU. Its QPU counter remains zero. Live application: https://qcg.securedme.ca/ Source and reproducible evidence: https://github.com/SeCuReDmE-main-dev/webmcp-hackathon-2026 How I built it The application uses React, TypeScript and Vite. Strict Zod contracts reject unknown properties and bound artifact size, shots, qubits and timeouts. qsharp-lang@1.31.0 runs inside a Web Worker so compilation and the published Bell simulation remain local and cancellable. Raw Q# stays out of WebMCP responses and IndexedDB; only evidence receipts persist locally. All human buttons and WebMCP tools call the same service layer. Tools are registered through document.modelContext with AbortSignal cleanup. The retained HTTPS origin serves the required WebMCP and security headers, the Worker and the pinned WebAssembly asset. Challenges I ran into The hardest design problem was separating three different things: an agent recommendation, a human authorization and an actual effect. Treating them as one state would make a convenient demo and a weak control system. The first live smoke run also exposed a real browser race: the inspection tool could be discovered before the initial WASM analysis finished. I changed the registration lifecycle so artifact tools stay absent until the manifest exists, then repeated the full test on the public origin. A second challenge was restraint. A multi-provider quantum router is an attractive future direction, but the hackathon proof needed one narrow, falsifiable vertical slice. Accomplishments I am proud of A real Q# file produces a byte-exact manifest and zero-diagnostic compiler evidence. Five falsifiable requests exercise all five decisions. Progressive registration is part of the product contract, not decorative plumbing. I also learned that a refusal, reuse decision or request for better evidence can be a useful outcome. Quantum tooling does not become safer by executing more calls; it becomes clearer when every proposed call has a reason, an authority boundary and a receipt. What's next I will test the frozen cases with quantum developers, measure false-ready decisions, refresh target-profile evidence and refine the visual workbench. Future adapters may normalize evidence from additional ecosystems while preserving their native semantics. What it does BeatScope Director adds an in-browser WebMCP collaboration layer to BeatScope. How I built it I kept BeatScope's existing architecture and analysis pipeline intact and added WebMCP as a separate browser integration layer. Playback actions have to respect autoplay restrictions, variable-tempo timing, cancellation, page lifecycle, and user ownership of the final state. I also wanted WebMCP to fail gracefully: if document.modelContext is unavailable, BeatScope still behaves like the normal player instead of breaking. What I learned WebMCP works best when it is not just a wrapper around buttons. The most useful tools expose the application's actual domain model. In BeatScope, that means giving the agent direct access to deterministic rhythm, structure, energy, and playback state instead of forcing it to reconstruct those concepts from the interface. I also learned that human-agent collaboration feels much safer when agent actions are visible, bounded, and reversible. The user still owns the player; WebMCP simply gives the agent a structured way to participate. Like Comment Story Updates Inspiration Most AI agents are fluent in text, but people understand complex ideas faster when they can see structure, position, emphasis, and relationships. Existing collaboration tools usually force one side to compromise: people work through visual interfaces while agents imitate mouse clicks, or agents produce plain text that people must mentally reconstruct. We wanted a medium native to both. CharDesk began with a simple idea: What if the canvas were visual to people, but still made of tokens an agent could read and edit precisely? What CharDesk does CharDesk is a shared visual workspace for humans and AI agents. An agent can create or update a Blackboard through WebMCP. The result immediately appears as a live Unicode canvas that a person can inspect, navigate, and continue discussing with the agent. The same canvas can combine: Unicode and ANSI art Markdown and fenced code Mermaid diagrams Tables, JSON, and YAML Mathematical expressions Scientific plots and Vega-Lite Spatial layouts and character-based slides This makes CharDesk useful for explaining concepts, visualizing research, mapping systems, designing interfaces, presenting stories, and maintaining a shared project workspace. For example, someone can ask: “Explain how a GPU renders one frame.” The agent can turn that request into a structured visual scene containing a pipeline diagram, memory relationships, annotations, and styled interface elements—not just another long answer in chat. Why it is better with WebMCP Without WebMCP, an agent would need to guess how to operate the interface or manipulate individual canvas cells. CharDesk instead exposes focused workspace tools for discovering, creating, reading, writing, patching, deleting, and validating Blackboard files. The source remains authoritative; the canvas is a live projection of it. This gives each participant the representation they work with best: Human sees relationships, hierarchy, and visual emphasis ⇅ CharDesk Blackboard ⇅ Agent reads and edits structured, diffable text Agents can also call chardesk_read_materials to learn the visual language from worked examples. The tool teaches not only how to call the API, but how to compose an effective scene. How we built it CharDesk has a protocol-neutral tool layer shared by two thin host adapters: Standard WebMCP for compatible Chrome environments The imperative WebMCP capability supported by ChatGPT Site Tools Both adapters expose the same underlying Blackboard operations, so product behavior does not depend on a particular browser integration. A Blackboard stores source files and layout metadata. Changes are compiled through a shared rendering pipeline into a fixed character grid. This pipeline handles Unicode width, CJK characters, Nerd Font glyphs, ANSI styles, structured diagrams, and multidimensional layouts. The browser keeps the latest valid canvas mounted while an agent edits the source. If an intermediate update is invalid, CharDesk returns diagnostics without replacing the visible scene with a broken or empty state. The same format also works outside the browser through the CharDesk CLI, making projects portable, inspectable, renderable, and friendly to normal version-control workflows. Challenges we faced One unexpected challenge was tool ownership across browser tabs. Opening several CharDesk pages could cause identical tools to be registered multiple times, leaving the agent unable to choose a target. We built an origin-level gateway lease so only one page exposes the tools, with automatic takeover when that page closes. Chrome and ChatGPT also expose different subsets of the evolving WebMCP API. Instead of spreading compatibility checks throughout the product, we isolated those differences behind capability adapters backed by one canonical tool definition. Another challenge was timing: some hosts inject WebMCP after the application has already loaded. CharDesk therefore uses an adaptive registration handshake rather than assuming the API exists at startup. Finally, we learned that exposing tools is not enough. An agent may know how to write a file without knowing how to create a compelling visual explanation. Embedding CharDesk’s materials and examples as a callable tool gave browser agents the missing creative context. What we learned The most important lesson was that agent-native design is not simply automation layered onto an existing UI. A better pattern is to give agents a precise, structured representation while giving people a rich visual projection of the same underlying artifact. WebMCP makes that relationship discoverable directly from the website, without requiring agents to reverse-engineer the interface. CharDesk explores what becomes possible when the web page is no longer just something an agent operates, but a shared medium in which the human and agent can think together.
