The other half of this project is just personal: I've always liked breaking a game's rules apart and rebuilding them slightly different, trying to find the more-fun version than the original. And I know this isn't uncommon; if you look at the Wikipedia list of chess variants , you'll see hundreds of people who did exactly this. What I learned An important idea turned out to be that the game has to be entirely data and never code. If a rule can be an arbitrary function, you can't validate it, you can't hand it to an agent safely, and you can't run a search against it. A rule someone wrote has to be immediately safe to open and function in the same exact way as alternative rules. I also learned that giving an agent a tool is a design problem in its own right, not a wrapper around an API. The tool listing gets re-sent on every single turn of a conversation, so every tool that isn't earning its place is a tax paid forever. I ended up cutting the workbench's tool listing roughly in half by removing tools for things that the agent doesn't need to do: publishing, voting, starting a match, and keeping only what an agent is actually there for: reading a game, building one, checking it, and handing over a game of it. How I built it Everything centers on a single rule format; board, pieces, movement, capture, and win conditions are expressed as one finite JSON document. That document is read by three different engines that all have to agree: a TypeScript reader in the browser, a Go reader on the server (the authority), and a Rust core compiled to WebAssembly for speed (so bot engine can search millions of positions a second for better quality play). Keeping three implementations honest is done with a shared conformance corpus: a fixed set of recorded positions and legal moves that all three readers are tested against, so a format change that lands in one and not the others shows up as a failing test rather than a live bug. The Rust engine exists because an interpreted alpha-beta search over a general rule format is too slow to be useful. Compiling the document down to a program with names already resolved (offsets baked, kinds as indices) was worth roughly 40× the speed of just trying to make the interpreter faster. That speed is what makes it possible to validate a brand-new game variant by having a bot play hundreds of games against itself in well under a second, checking that one side doesn't always win and the game doesn't always draw. Alpha-beta pruning is what makes that search tractable at all: with good move ordering it cuts the size of the game tree explored from O(b^d) down to roughly O(b^{d/2}) for branching factor b and depth d. The difference between a bot that can check a variant in milliseconds and one that can't. The same rule format also generates the rulebook. Because moves, captures, and win conditions are structured data rather than arbitrary prose, the site can snapshot "interesting" positions from bot self-play and use them to show a stranger how a brand-new game is actually won, without anyone writing documentation/explanations by hand. On top of that sits a shared workbench: a person and an agent editing the same document, through the same functions, at the same time, with an activity ledger, pause, and a confirmation step before anything gets published. I really wanted to support every game, but if I add support for every possible game interaction or mechanic the rule-based game is actually worse than if it was just hard coded. If there's too many options, it's too hard to use and we don't get the benefit of the shared mechanics! Keeping three engines byte-for-byte consistent was a constant source of subtle bugs. Every format change had to be replicated in three places, so I planned ahead and leaned hard on automated equivalence tests between the interpreted and compiled paths rather than trusting careful reading. Measuring whether the bot was actually competent was tricky. The point of the computation engine isn't to beat StockFish at chess, it's to be good enough to know when the game is bad . Proofpress is an agent-produced knowledge management system (AKMS) for that boundary. Agents can propose knowledge and assemble bounded evidence, but proposed knowledge does not become reusable merely because a model generated it or an automated check passed. What it does Proofpress gives an owner a governed workspace for agent-produced knowledge: agents submit evidence-bound candidate conclusions; deterministic checks validate integrity, scope, freshness, and required qualifiers; an optional LM judge provides policy advice without receiving approval authority; a human owner approves, rejects, or requests a revision; successor agents retrieve only admitted, current, in-scope knowledge; append-only activity and lineage preserve who proposed, evaluated, and authorized each decision. Proofpress now exposes product semantics directly from the web application: workspace summary, review queue, evidence, lineage, deterministic checks, semantic activity, policy configuration, and agent access. The agent can find the right candidate, inspect its evidence, run checks, prepare a policy or credential form, and open the exact owner decision surface. The owner sees a progressive-disclosure review: a quick snapshot first, then full evidence, checks, LM advice, history, and lineage. The owner alone records the decision. Once admitted, the conclusion appears in governed context. A successor agent retrieves it only when its identity and scope are eligible. Rejected and revision-requested conclusions remain in the append-only history, but are excluded from governed context. The hosted dogfood runs on Render with persistent storage. The owner workspace renders semantic WebMCP tools from the same product state used by the human UI, rather than exposing coordinates or a parallel demo API. Your agent learns the way !! Like Comment Story Updates Inspiration WebMCP lets a web page hand an AI agent real tools instead of a UI to click through. But that raises a sharp question: if a page exposes a tool, who is allowed to approve a dangerous use of it? Spec issue 288 , filed during the submission window, showed the failure vividly — an agent called a tool, saw the page's own "Approve" button, clicked it itself, and the receipt recorded that a human approved, though no human decided anything. The agent forged its own consent. We wanted approval to be something an agent physically cannot produce, and we wanted humans to author agent capabilities just by doing their normal work — not by writing code. What it does A human demonstrates a task once. DEPUTY watches the semantic steps, compares repeated demonstrations, infers which values are parameters, and synthesizes a typed WebMCP tool — schema, reversibility, provenance, and risk — registered into document.modelContext for agents to discover. Agents can call reversible tools freely. But an irreversible one returns a structured refusal — there's no button to click. To proceed, a human produces a WebAuthn passkey assertion whose challenge is bound to the SHA-256 digest of the exact tool, version, and arguments. Change one argument and the approval is void. Only then is a single-use commit tool briefly registered, the action runs once, and everything lands in a hash-chained, tamper-evident audit log. A QUARANTINE boundary wraps untrusted third-party content in provenance-tagged envelopes under byte and depth budgets, so external text is treated as data, never as commands. How we built it A pnpm/TypeScript monorepo with two decoupled pipelines — synthesis (learning) and security (execution). A Hono + Node backend exposes the API and serves a React 19 + Vite single-page app at one origin (required for WebAuthn). WebAuthn runs on @simplewebauthn; the argument digest uses canonical, NFC-normalized JSON hashing. Persistence is Drizzle ORM over Postgres, deployed on Supabase; the app runs on Render. 175 tests in Vitest, a Playwright end-to-end test with a virtual authenticator, and GitHub Actions CI. Challenges we ran into Getting the WebMCP surface right. The spec moved the getter from navigator to document.modelContext, and retirement is done by aborting the AbortSignal passed to registerTool — not a nonexistent unregisterTool. We built one resolver that finds the host safely and never throws, and made retirement propagate through the real signal. Single-origin WebAuthn. RP ID and origin must agree, so we serve the SPA from the API server and added a startup guard that refuses to boot in production with a localhost RP ID or non-HTTPS origin. Supabase from Render. The direct DB host is IPv6-only, and the Supavisor pooler rejected our first hostname with "tenant not found." We switched to the session pooler on the correct cluster, disabled prepared statements, and created a dedicated BYPASSRLS role so we could enable Row-Level Security without breaking the app. Restart safety. Seeding threw on the second boot; we made it idempotent so restarts against a durable database don't crash. Accomplishments that we're proud of Approval bound to the arguments, not just the action — an attestation that becomes invalid the moment a single value changes. Working, tested implementations for open issues in the spec's own tracker ( 288 approval forgery, 282 structured refusals), with an honest stance on 267 (we decline to claim idempotence from one demonstration). An Agent's-Eye View that shows exactly what an agent sees — the live tool registry, JSON schemas, and the last refusal as a typed object — so the security is visible, not asserted. A live, deployed, database-backed app you can drive end to end in about a minute. What we learned Delegation is a design problem, not just a crypto problem. The strong move isn't "the agent does it for you" — it's a shared artifact: the human authors capability by working, and the agent's authority is bounded, at the type level and cryptographically, by exactly what the human demonstrated and signed for. We also learned how much of "secure delegation" lives in unglamorous details — origin agreement, connection poolers, idempotent boot, and reading the spec's move from navigator to document closely enough to not silently fall back. What's next for Deputy Cryptographic agent identity (spec #105) so the audit log records a verified caller, not a self-asserted one. Host-level turn awareness ( 267 ) to guard non-idempotent tools against double calls. Delegation policies with scopes and expiry, so a human can grant bounded, time-limited authority instead of per-action approvals. Real connectors behind the trusted ActionRegistry (billing, CRM) and a shareable, signed provenance format for learned tools. ABOUT TEXT (untrusted evidence):
A browser-native marketplace where agents discover, inspect, and safely preview paid services before a person authorizes purchase. Like Comment Story Updates Inspiration Visual marketplaces are designed for people, but browser agents still have to infer meaning from buttons and page layout. A service marketplace becomes meaningfully better when the browser exposes a small, stable set of structured tools: the agent can search by intent, inspect exact terms, and preview safely while the person retains the payment boundary. What it does Suede Agent Studio exposes six curated services from its 31-listing public directory through four page-scoped WebMCP tools: find_services searches the published service shelf by job-to-be-done. get_service returns the current price, exact input contract, review policy, data-handling statement, and worked examples. preview_service records a free dry-run receipt without model inference or payment. buy_service uses only prepaid workspace credit after server-side origin, rate-limit, buyability, and exact-price checks. The fixed tool set stays constant as inventory grows, avoiding one tool per service and keeping the browser agent's context bounded. How people and agents work together The agent handles discovery and contract reading. The person keeps control over the meaningful boundary: whether to preview and whether to authorize a purchase. The challenge demo uses synthetic purchase-order and invoice data, stops after a free preview, and performs no purchase or model inference. How we built it The existing Next.js application was extended during the challenge window with a browser compatibility layer, four fixed tool descriptors, page-scoped registration, bounded result formatting, a server-owned purchase contract, mutation guards, and focused regression coverage. Tools are mounted only on /agents and /a/[slug] . Creator-authored catalog text is marked as untrusted. Purchase authority never moves into page JavaScript. The public history preserves the pre-WebMCP baseline ( f4943a1 ) and the challenge implementation ( e2c3b11 ), followed by hardening and evidence commits. The focused WebMCP suite contains 71 tests covering protocol compatibility, shelf parsing, descriptors, preview budgets, server guards, and mount scope. Challenges we ran into WebMCP's shipping namespace changed across Chrome versions, so the compatibility layer supports the current document-scoped API while retaining the origin-trial alias. Registration also handles both synchronous browser bridges and Promise-returning native APIs; a regression test confirms that an undefined return still registers all four tools. We also had to keep every descriptor and result inside strict field budgets, distinguish a durable preview from a read-only operation, and ensure no client-side tool could bypass server-side price and payment authority. Accomplishments we're proud of Four stable tools serve a growing marketplace without context bloat. The agent receives terms and examples before acting. Free preview is honest about what did and did not run. Purchase uses exact-price binding and prepaid credit only. The public demo uses synthetic data and cannot accidentally spend money. The implementation is public, MIT-licensed, and separated from the pre-challenge baseline in Git history. What we learned The strongest WebMCP experiences do not copy every button into a tool. They expose the smallest task-oriented contract that helps the agent reason while preserving human control where risk or irreversible action begins. What's next Expand the service shelf without expanding the tool namespace, add more contract-first preview patterns, and continue testing the same human-agent boundary across compatible browsers.
