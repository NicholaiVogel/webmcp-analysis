## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value

- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates Sealed’s WebMCP privacy boundary: private values stay page-local while agents receive only allowlisted decisions or opaque references. Inspiration AI agents are becoming capable of acting directly on websites, but many useful workflows involve information that should not automatically become part of the agent's context. A rental application is a simple example: an agent may need to know whether an applicant satisfies an income requirement, but it does not need the applicant's actual income. The same applies to identity data, age checks, financial values, health information, and many other private facts. Sealed explores a simple idea: The agent gets the decision — not the secret. What it does Sealed is a reusable WebMCP privacy boundary for agentic web applications. The page exposes a small, state-aware set of WebMCP tools. Public information can move normally, while sensitive facts are evaluated locally inside the page and only allowlisted results are returned to the agent. The primary rental demo shows the full pattern: Public applicant information can be updated by the agent. A private income_3x_rent predicate is evaluated locally. The agent receives only satisfied or not satisfied ; the income itself is returned as value: "withheld" . A passport verification requires explicit human approval. Approval creates a random, session-bound opaque reference that does not encode the passport number. Every private crossing is recorded in a visible Boundary Ledger. Human review returns submitted: false ; Sealed has no final-submission tool. After review, the WebMCP capability surface contracts from five tools to only two safe read/flag operations. A second Membership scenario reuses the same primitives to evaluate age_18_plus without exposing the user's date of birth. Why WebMCP WebMCP is load-bearing in Sealed. Without structured site tools, an agent would have to infer meaning from DOM content, accessibility trees, or screenshots. That is especially problematic around sensitive data because the agent may end up observing more information than the task actually requires. With WebMCP, the page defines the capability boundary explicitly. Sealed registers tools through document.modelContext.registerTool(...) , including: get_application_context set_public_fields flag_uncertain request_private_binding evaluate_private_requirement request_review The available tool surface changes with workflow state. The agent can ask for a useful decision, but no tool exists that returns the underlying private value. How I built it Sealed is built with Next.js, React, TypeScript, and WebMCP and is deployed on Vercel. The privacy boundary has several layers: Fixed private predicates The agent selects from predefined checks such as income_3x_rent or age_18_plus ; it cannot construct arbitrary queries over private values. Local execution Private values are generated and retained page-locally. Predicate evaluation happens inside the application. Guarded egress Private operations pass through a single allowlisted response path that releases only approved fields such as status, requirement, and value: "withheld" . Human-approved opaque bindings Consequential credential binding requires explicit user approval and returns only a random session-bound reference. Boundary Ledger Each private operation records the exact sanitized payload released across the boundary. State-dependent capabilities Once human review is requested, Sealed removes write/private tools and leaves only two safe operations. I reproduced cases where the page showed five registered tools while the agent still reported that site tools were unavailable. Testing against the official Chrome Labs WebMCP demo helped isolate the difference between application behavior and client-session discovery. That led to an important UI correction: Sealed now says “Site tools registered” , rather than claiming that an agent is connected simply because local registration succeeded. I also had to guard against stale sessions, repeat probing of private predicates, response/ledger drift, and accidental leakage through seemingly harmless response fields. It can also make the boundary between a web application and an agent more explicit. The most useful question became: What is the minimum information the agent needs to complete this task?
