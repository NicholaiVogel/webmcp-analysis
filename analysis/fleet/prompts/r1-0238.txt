# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates Inspiration The premise: the agent is assumed compromised. Not "the agent might make a mistake" — assumed compromised, the same way you'd design a system if you knew an adversary was already inside it. Every design decision in Pocket Change follows from that one sentence: if you're going to hand an AI agent a wallet, the system has to hold up even when the agent itself is the threat, not just when it's well-behaved. What it does Pocket Change gives an AI agent bounded, revocable spending authority — enough to actually get things done, never enough to do real damage. A person authorises a mandate : a ceiling, a purpose, an expiry. The agent can act only within that mandate. Every payment request passes through a gateway enforcing nine deterministic checks — depth, budget floor, fan-out, per-node budget, cycle detection, conservation of spend, and a hard rail cap — none of which a model can argue its way around, including ours. Every decision (allowed, denied, or escalated to a human) is written to a hash-linked audit log, so the log can prove nothing was altered after the fact — not that it was never rewritten wholesale, but that no entry was quietly edited in place. Payments run through Razorpay in test mode — never real money — while the authority model itself is designed to be real. For this hackathon, the console also exposes six WebMCP tools , so an agent working through the browser can read everything about its own authority — spend status, counterparty history, the audit trail, the shape of an in-progress run, which safety layers are actually enforcing right now — without ever being handed a tool that can move money, mint a token, widen a mandate, or approve a held payment. It can look, and it can propose ( draft_requisition , which mints nothing), but the only path to actually spending still runs through a person clicking a button in the console. How we built it Gateway : a FastAPI service enforcing the nine checks server-side, so no client — including the browser console — can bypass them. Reads are public; writes require the demo token. Capability tokens : Biscuit tokens carry attenuated authority, so a delegated task can only ever have equal or narrower permissions than its parent, never wider. Decomposition/funnel model : complex requests get broken into a tree of smaller tasks, each with its own budget, depth limit, and fan-out cap — the console renders this tree live over SSE. Console frontend : a five-pane live view (via SSE) of an in-progress run, plus frontend/webmcp.js , which registers the six read/propose-only tools with the browser's WebMCP API ( navigator.modelContext.registerTool ), each one calling the same GET routes and /intake endpoint the console itself uses — no separate, more-privileged backend door for agents. Deployment : Cloud Run ( asia-south1 ), --min-instances=1 to avoid a cold-start during judging, --no-cpu-throttling . 424 Python tests and 20 Node tests, including a dedicated adversarial suite trying to get the gateway to approve something it shouldn't. Challenges we ran into The WebMCP spec itself is still moving. Documentation (including Chrome's own developer docs) describes the API as document.modelContext , but the actual shipped implementation in current Chrome exposes it as navigator.modelContext instead — with a separate navigator.modelContextTesting surface ( listTools() , executeTool() ) for verifying registration without a live agent. This meant tools were silently failing to register — no error, just an empty tool list — until we traced it back to a single feature-detection check on the wrong global. Deciding what not to build was harder than building what we did. It would have been easy to add a WebMCP tool for /delegate or /pay — more "impressive" on paper — but that would have meant putting a spendable capability inside a public page. The interesting engineering problem was making the read-only boundary airtight, not working around it. A safety boundary is most convincing when it's structural (no route exists) rather than behavioral (a tool declines to). No one has to trust that an agent chose not to spend; there's simply nothing on the other end of the wire that could. What's next for Pocket Change Extending WebMCP coverage as the spec stabilizes — particularly once cross-document tool discovery ( getCrossDocumentScriptToolResult , which we noticed on the navigator.modelContextTesting prototype but didn't use) has clearer semantics. Your AI agent creates your product's promo video. You direct it on a shared timeline, review each stage, and decide what ships. Like Comment Story Updates Dark-mode editor: an editable 45-second promo on a shared timeline, with layered visuals and frame-accurate playback. Style frames: review reusable brand, typography, UI and sound elements before the agent builds the animatic. Saved activity: review the agent’s tool calls, captured frames, revisions and human approvals alongside the current film. Modular project files: separate JSON for creative stages, elements, tracks and activity keeps each part easy to inspect. Light-mode storyboards: play each shot’s composition and movement before approving the film’s visual direction. Inspiration I build products, but I don't know how to make a good promo video. Learning motion graphics is a whole other job, and it becomes another thing standing between finishing a product and showing it to people. I wanted my AI agent to help with that. It already understood the product I was building. The missing piece was an editor it could actually use. Asking an agent to control a video timeline through screenshots, dragging, and clicking was a fragile way to work. WebMCP gave me a practical way to expose the editing operations directly. That became PrismLaunch: a promo video editor built for a person and their agent to use together. What it does You give your agent the product, the audience, and the message. It develops the film in PrismLaunch while you review the work in the studio. The process moves through a brief, concepts, script, visual storyboard, style frames, animatic, polish, and final build. Storyboards show the composition and timed movement of each shot. Style frames show the reusable elements and sample compositions the agent plans to use. You can approve each stage or send it back with a note. The agent revises the same project, and a saved activity log records submissions, decisions, and edits. Review panels stay focused on the work; manual editing tools live in the editor. The shared timeline combines text, images, video, audio, shapes, device frames, motion, and editable HTML components. Reusable elements let the agent define a piece once and update its placements throughout the film. The finished composition can be encoded as an MP4 in the browser. I used PrismLaunch to make the promo video for PrismLaunch itself. Watch the promo video made with PrismLaunch . Why WebMCP fits Video editing involves precise operations: placing a clip at a frame, changing its duration, moving it to another layer, adjusting typography, or updating a reusable element. Those operations are much easier to express as structured tools than as a sequence of mouse movements. PrismLaunch exposes tools for project context, creative stages, layers, elements, clips, preview, frame capture, and render requests. The agent can inspect the current project and make a specific edit. The person sees the result in the same editor and gives feedback there. This makes it possible to work with an agent on an editable film throughout the process. Human review is part of that workflow: stage approval and render approval are controls in the studio, not tools exposed for the agent to call. PrismLaunch does not contain its own model. You bring the agent you already use. How I built it I came up with the idea from my own painful experience and used Claude Code to build the core functionality. I then used Codex to test the WebMCP workflow in the browser and fix issues that my Claude Code setup could not directly exercise. The studio uses Next.js, React, and TypeScript. WebMCP tools register via document.modelContext.registerTool , with a compatibility path for browsers that expose the older API location. Zod validates tool inputs, and human edits and agent edits go through the same state and timeline operations. Remotion renders the composition for preview and export, with WebCodecs encoding the MP4 in the browser. Projects can live in a linked local folder or in browser storage, with separate JSON files for each creative stage, element, and track, plus a saved activity log. The app is hosted on Vercel, and its source is available under the MIT license. Challenges and what I learned The hardest part was teaching an AI how to make a good promo when I am still learning video editing myself. I analysed successful promo videos, turned what I learned into a filmmaking guide, and built reusable elements that an agent could combine in its own films. Pacing, hierarchy, and knowing what to leave out mattered as much as having editing tools. Making PrismLaunch's own promo became a practical test of the product. Early storyboards looked too much like scripts, so I built visual boards with positioned subjects and timed movement. The first animatic also exposed a gap in the method: copying storyboard roughs onto a timeline did not produce a finished sequence. I strengthened the filmmaking guide and added a check that refuses animatic submissions while storyboard roughs remain visible. That workflow uncovered product bugs too. I fixed review notes that failed validation, activity that disappeared after reopening, and style-frame reviews that exposed editing tools. I split browser-stored projects into separate files for creative stages, elements, tracks, and activity. I also improved media preparation and playhead synchronisation to address interruptions during playback. Real WebMCP testing exposed issues that the local fallback did not. Multiple components initially registered the same tools, causing partial registration failures. Later, ChatGPT's built-in browser disabled discovery because the growing tool catalogue exceeded its supported limits. I introduced shared registration and five compact toolsets—workflow, graphics, media, elements, and edit—with prism.use_toolset to switch between them. Long sessions can still require reconnecting when a host retains earlier catalogues. Publishing a skill was not enough to ensure an agent received it. Creative WebMCP edits now require that both the operating guide and the filmmaking guide be delivered via prism.read_guide . The agent still has to apply that guidance well. I learned that an agent-friendly editor needs precise tools, inspectable state, visible feedback, and a clear point where the person decides whether the work is ready. What I am proud of PrismLaunch made its own promo video. That took the idea beyond a tool-registration demo and into the task I originally needed help with. I also tested the WebMCP experience in Chrome and ChatGPT's built-in browser. Working through those differences helped turn the editor into something I could actually use with an agent. Current limitations This is an early editor with a small motion library. External agents need a browser and client with native WebMCP support; the fallback registry is only usable within the page. Tool discovery can vary between hosts, and long sessions may require reconnecting if the host retains earlier tool catalogues. Local folder access depends on browser support and a person granting permission. Browser storage is an alternative, but an agent must edit those projects through the page's tools rather than ordinary filesystem tools. MP4 export depends on browser codec support and the resources available on the user's device. What's next I want to build a much richer motion graphics library that agents can draw from when making promo videos: more reusable elements, more visual treatments, and more ways to clearly communicate a product.
