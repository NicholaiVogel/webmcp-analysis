=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A web page that hands a browser agent ten WebMCP tools to write, playtest and QA a SillyTavern character card. The page owns the deterministic bookkeeping; the agent owns the judgment. Like Comment Story Updates A browser agent (ChatGPT Codex, left) drives tableread, calling run_scenario, get_playtest_context and commit_playtest_round round by round. Creator mode: the nine-aspect checklist is complete, card fields filled, and a playtested scenario fills the transcript and QA panels. get_checklist_status returns nine aspects (seven richness aspects, the MVU decision, the beautify direction), each with a decision axis. get_playtest_context lists which world-book entries are live each round; commit_playtest_round applies the regex and the variable patch. The QA panel: rounds run, JSON-Patch misses, world-book entries never triggered, warnings, and every tool call the agent made, in order. Game-publisher mode: compare_scenarios puts two already-run openings side by side and diffs their final variable state. What compare_scenarios is for: world-book entries that fired in some scenarios but not others, an inconsistency a reviewer would miss. The whole card built through tools: every update_card_field / get_checklist_status call, with arguments and result, in the activity log. Inspiration I build SillyTavern character cards, and the hardest part isn't the writing — it's knowing whether the thing actually works. A card isn't one prompt. It's an opening scene, a handful of alternate greetings, a world-book of keyword-triggered lore with sticky and cooldown windows, regex scripts that render status bars, and often a block of variables tracked across the whole conversation. After any edit you have to re-check that every opening still feels like the same character, and that the right lore fires in each branch — by reading transcripts and trying to remember what triggered where. It's exactly the kind of bookkeeping a human skims and an LLM just guesses at. When WebMCP landed, the split was obvious. The page can do the deterministic half perfectly — which entry is in a cooldown right now , whether a variable patch applied, how triggers differ across scenarios — and hand the agent only the part that needs judgment: turning a premise into real choices, and writing the dialogue. So I built the page that does that, and gave the agent ten tools. What it does tableread is a browser-agent-collaborative platform for building and playtesting SillyTavern character cards. It registers ten deterministic tools via document.modelContext.registerTool(), so a WebMCP-capable browser agent (ChatGPT's Codex browser, or Chrome with the WebMCP flag) can: • Write a card from a premise. get_checklist_status returns nine aspects a card needs, each annotated with a "decision axis" — the thing a set of options should actually differ on. The agent proposes two or three concrete directions per gap, the creator picks one, and update_card_field records it. • Playtest it deterministically. run_scenario / get_playtest_context / commit_playtest_round run the card round by round. The page computes exactly which world-book entries are live each round (keyword match, constant, or still inside a sticky/cooldown/delay window), applies the regex "beautify" scripts and the JSON-Patch variable updates, and reports every warning honestly. • QA it across scenarios. compare_scenarios takes a batch of already-run openings and flags which world-book entries fired in every one of them versus only some. That inconsistency is the single most useful "does this card hold up across branches" signal — and it's not something any existing SillyTavern tooling, or an agent working from the rendered page, can compute. The page never calls an LLM. Zero API key. Every line of generated dialogue comes from the calling agent's own model. How I built it • Pure frontend, zero bundler: index.html + native ES modules, served by a ~30-line zero-dependency static file server. Deployed on GitHub Pages. • The playtest engine — world-book scanning, regex rendering, JSON-Patch variable state — is ported from an existing Python tool (playtest_engine.py) to JavaScript, and checked against it with a golden-parity test suite that replays fixed multi-round conversations through both engines and asserts byte-identical output. 81 tests total (unit + golden + Playwright e2e). • Each of the ten tools is a plain, DOM-free function unit-tested on its own; only one module (registerTools.js) ever touches document.modelContext, and registration is fault-tolerant (per-tool try/catch, a timeout cap) because the API is still experimental. • Tool descriptions and the whole UI are bilingual (Traditional Chinese / English) and follow a page toggle, so the agent reads whichever language the creator is working in. Challenges I ran into • WebMCP is early-preview. The agent side — a browser that actually calls the registered tools, not just accepts them — exists today only in ChatGPT's Codex browser and in Chrome behind a flag. Working out which environment actually calls the tools (a plain ChatGPT account registers them but never calls them) took real testing. • Getting the agent to emit the exact wrapper the engine parses. Solved by having the tool report the precise format error back to the agent — which turned into a good demonstration that the tool's output, not the agent's "verified, no warnings" self-report, is what tells you whether something worked. • Keeping the split honest: everything deterministic and stateful on the page, only the in-character writing on the agent — and resisting the urge to let the agent "help" with the bookkeeping. Accomplishments that I'm proud of • The full write → playtest → cross-scenario QA loop runs through typed, self-describing tools with zero prompt scaffolding. The agent discovers the whole call sequence from the tool metadata alone. • compare_scenarios computes a QA signal (world-book entries that trigger inconsistently across branches) that no existing character-card tooling produces. • Golden-parity tested against the original Python engine, so the ten tools an agent calls are backed by code that doesn't guess. What I learned • WebMCP's real value is the division of labour: the page can hand the agent exact state — which entry is inside a cooldown right now , whether a patch actually applied — that the agent could never reconstruct from the rendered page. • Self-describing tools plus honest error reporting removes almost all of the prompt engineering. The tool descriptions are written for the agent, and the agent just follows them. What's next for tableread • A bottom-of-page ideation panel, so option-picking happens in the UI rather than only in chat. • A "load an existing card" import, so creators can QA cards they already have. • Wider agent support as WebMCP rolls out beyond the early-preview browsers.
