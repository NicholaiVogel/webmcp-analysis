=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A search results page optimises a single query. A group chat collects messages. That last part is what made this worth building for WebMCP specifically. A personal agent already knows things about its user that the user would rather not broadcast to five friends. Until now the only way to put that knowledge to work was to hand it to a shared service. I wanted to find out whether an agent could advocate for someone inside a live page, as that person and within an authority they granted, while the reason itself never left their client. What it does Three people open one planning room from a link. They see the same live map and the same brief of what the group has asked for so far. Each person states what matters in a single composer bar and chooses who may see it before they speak . A need can be shared, private, or agent-only. The server evaluates a private need and peers see only its effect on the count. An agent-only need stays with your agent and never reaches the server at all. The app suggests the next thing worth asking about from the data itself, never from a built-in list of categories. Every need becomes a row you can set aside. Press and hold a row and the map shows the room without that need, live. The cost of a need becomes visible instead of argued about. The room recomputes which places still work after every move, and it counts what is merely unverified separately from what actually failed. Missing data is drawn as its own state rather than quietly dropping a place. When nothing satisfies everyone, Spokes does not name who is blocking. It privately offers each person a quantified way out. The organizer sees "widen the area from 800 m to 1.2 km, brings back 4 places". The person who stated a need sees "let this need be nice-to-have, +12 places". Consent is explicit and confirmed on the page. Once the group agrees, the composer gives way to arrival: a travel mode and a one-tap handoff to the map app everyone already has. Alongside all of it, your personal ChatGPT can act in the same session through WebMCP. How I built it A TypeScript monorepo (pnpm). Fastify and a Postgres event log sit behind a WebSocket realtime channel. The front end is React and Vite with MapLibre GL over keyless OpenFreeMap tiles. TypeBox contracts are shared by both sides behind a hashed contract-manifest gate. Place data is a one-time OpenStreetMap extract of Berlin Mitte. The WebMCP surface is 22 tools registered imperatively on document.modelContext at page load, 10 for negotiation and 12 spatial. Each is a narrow function with closed enum schemas, readOnlyHint and untrustedContentHint annotations, and a capped result budget. The page works fully without WebMCP. The tools are an additional way in. Four decisions did most of the work. Two protocols over the WebMCP substrate. WebMCP itself only carries tool names and schemas. So the first sync_session call returns a capability manifest that teaches the agent a domain-independent negotiation protocol (identity, revision sync, privacy tiers, requirements, stances, adjustments, consent, agreement) and a spatial-destination domain layered on top. Server-owned identity and per-viewer projections. Actor identity comes only from the bearer token. No tool argument accepts an actor id. Every event is stored once and projected per viewer, so unauthorised fields never appear in another participant's HTTP body or WebSocket frame. The test suite asserts this at the wire, not at the function boundary. Revision discipline instead of pretend realtime. Every mutation carries the agent's last-seen revision. A stale one returns a structured sync_required with a delta instead of acting on old state. That fits an agent that participates in bursts far better than a subscription it never really holds. Consent an agent cannot forge. An agent may recommend a grant, but a change beyond what the user delegated only stages . Staging mints a single-use code delivered on the participant's own realtime channel. The applying command must carry it back, and the code never appears in any tool result. Eligibility, minimal-conflict-set detection and the impasse counterfactuals are all deterministic. No model is allowed to invent a feasibility fact. 364 automated tests across three lanes: 222 unit, 128 three-user API, and 14 Playwright specs driving three isolated browser contexts. Teach catalog rules by example with WebMCP: an agent turns human edits into isolated preview proposals, learns from corrections, and leaves final merge authority to the human. Like Comment Story Updates An isolated Current vs Preview review showing 10 product proposals and 20 changed fields before a human-controlled merge. Inspiration Catalog rules are often easier to show than explain . A catalog operator may instantly recognize how a product should be classified, but turning that intuition into a complete written rule — and then applying it safely across many related products — is repetitive and error-prone. ShowBranch explores a different human-agent workflow: Teach by doing. Preview before you commit. Instead of writing a long instruction, the human makes one real edit in the product UI. An agent reads that activity through WebMCP, generalizes the demonstrated pattern, and proposes related changes inside an isolated preview branch. If the initial generalization misses a catalog-specific rule, the human can correct one proposal directly in the preview. That correction becomes new activity the agent can read and use to revise related proposals. Final merge authority remains with the human. Human demonstration → Agent preview → Human correction → Agent revision → Human-controlled merge What it does ShowBranch is a catalog-classification demo built around a ShowOnce + BranchMode interaction. A human first edits one product in the main catalog. ShowBranch records the complete before-and-after product state as human activity. The browser agent can then use WebMCP to: read products and human activity; create an isolated preview branch; propose updates to related products; read human corrections made inside that branch; revise proposals based on those corrections; and inspect the final Current vs Preview diff. Agent proposals remain isolated from main until the human reviews them. The review surface shows changed products and fields, proposal rationale, confidence, and human-facing Merge Branch and Discard Branch controls. This creates a collaboration loop where the agent can generalize and adapt without immediately committing its work to the canonical catalog. Why WebMCP The key idea is not simply giving an agent functions to call. It is letting the human UI and the browser agent collaborate over the same application state . Without WebMCP, an agent would need to scrape rendered UI text or depend on a separate API that could drift from what the human actually sees and edits. ShowBranch exposes exactly five WebMCP tools: list_products get_activity create_preview_branch apply_branch_updates get_branch_diff These tools let the agent work directly with products, human activity, preview branches, and diffs. Merge, discard, reset, main editing, and human correction are intentionally excluded from the WebMCP capability surface. Final merge is exposed through the human UI rather than as an agent tool. WebMCP therefore acts as the semantic collaboration layer between the human-facing product experience and the agent. How we built it ShowBranch is built with Next.js, React, TypeScript, and WebMCP , and is deployed on Vercel . The UI and WebMCP tools share the same browser-side domain store for: the canonical product catalog; preview-branch patches; human and agent activity; branch lifecycle state; and main revision state. Preview branches are sparse isolated overlays rather than immediate mutations to main. The effective preview is composed from the current main state plus branch-specific patches. Human edits store complete before-and-after snapshots. A correction made inside a preview branch becomes branch-scoped human activity, so the agent can immediately read that new evidence and revise its proposal. Agent batches are applied atomically, and the application tracks branch lifecycle and main revisions so stale merges can be detected rather than silently applied. WebMCP registration is also all-or-nothing: the page reports WebMCP ready only after all five tools register successfully. The current MVP intentionally keeps state document-local, making the demo account-free, resettable, and easy for judges to reproduce. Challenges we ran into The biggest challenge was making the agent useful without giving it unnecessary authority. We wanted the agent to generalize confidently across related products, while ensuring those proposals stayed isolated from the canonical state until a human review. A second challenge was making human correction part of the collaboration loop rather than treating it as a one-off UI edit. A correction inside the branch needed to become structured evidence that the agent could reliably discover and use in its next revision. Activity ordering introduced another subtle problem. An agent reading only an older branch should not mistake that branch's latest event for the globally latest human activity. ShowBranch therefore tracks scoped and global activity information so newer demonstrations are not silently overlooked. We also had to handle atomic preview updates, stale-branch detection, registration cleanup, and exact reset behavior. Finally, the security boundary needed to be described precisely. ShowBranch removes merge from the WebMCP capability surface and exposes merge through the human UI, while broader browser-automation permissions remain the responsibility of the browser or host. Accomplishments that we're proud of We completed the full human-agent correction loop end to end: Human demonstration → isolated agent preview → human correction → agent revision → human review → merge A single human edit can lead the agent to identify multiple semantically related products rather than blindly applying the same change to every item. The human can then teach a catalog-specific rule inside the preview, and the agent can use that new evidence to revise related proposals while preserving product-specific details. We also implemented: exactly five WebMCP tools with strict capability boundaries; a shared state model used by both the UI and the agent; isolated preview branches with normalized diffs; full before-and-after human activity snapshots; rationale and confidence on agent proposals; Current vs Preview review with aggregate change counts; stale-branch protection; atomic branch updates; human-facing merge and discard controls; and a one-click reset that restores the canonical demo state. The result is a live, account-free demo that judges can reproduce directly in a WebMCP-capable browser. What we learned The biggest lesson was that proposal and commitment should be separate concepts in human-agent systems. An agent does not need unrestricted write access to be useful. It can generalize aggressively inside an isolated branch, receive human corrections as new evidence, and revise its work — while the human retains a clear review and commitment point. We also learned that human corrections become much more powerful when they are stored as structured activity rather than treated as ephemeral UI interactions. One correction can teach the agent a catalog-specific rule without requiring the human to rewrite the entire instruction. WebMCP makes this interaction natural because the agent works with the application's semantic state instead of reconstructing intent from rendered text. What's next for ShowBranch ShowBranch is intentionally a focused demonstration of this interaction pattern. Future directions include: persistent branches and activity history; state-aware WebMCP tool registration; richer approval and permission policies; multi-user review workflows; larger catalogs and persistent backends; and applying the same ShowOnce + BranchMode pattern beyond product classification. The broader idea is simple: Let agents propose and adapt quickly, while keeping consequential commitment understandable and human-controlled. You finish building something cool, and then u need to document it. And somehow, even worse than writing the docs, is drawing the architecture diagram for them. Boxes. Arrows. Labels. Move the box. Fix the arrow. Realize the box is slightly misaligned. Move everything again. Architecture diagrams are incredibly useful for READMEs, system-design discussions, demos, presentations, and explaining how a project actually works, but creating them manually is still tedious. Meanwhile, AI agents have become good at understanding codebases, architectures, and technical ideas. They can explain the system perfectly, but when it comes to actually putting that understanding onto a visual canvas, the human usually ends up doing the drawing. So I built Excalidraw WebMCP . The idea is simple: What if Excalidraw wasn't just a canvas for humans, but a canvas where humans and AI agents could work on together? What it does Excalidraw WebMCP makes Excalidraw agent-native. Humans and browser agents operate on the same live canvas . An agent can understand what is currently on the canvas, reason about the diagram, make structured changes, connect elements, and export the final result. The human stays in the loop and can continue moving, editing, deleting, or adding elements normally through Excalidraw. There is no separate "AI-generated preview" that has to be copied back into the editor. There is just one canvas shared between the human and the agent. How I built it The project is built around a simple rule: There should be one source of truth for the canvas, regardless of whether a human or an agent changes it. The central canvas state and mutation boundary lives in: src/canvas/canvas-controller.ts All changes to the canvas flow through this layer. On top of that, I created a semantic operation layer which translates higher-level operations into actual Excalidraw elements in: src/canvas/semantic-operations.ts The WebMCP layer lives inside src/webmcp/ . It contains the schemas, tool registration, validation, and the execution bridge used by the exposed tools. When the browser provides document.modelContext , the application registers its WebMCP capabilities and allows compatible browser agents to interact with the current board. The canvas is stored locally in the browser using localStorage , keeping the project intentionally lightweight. Challenges I faced 1. Turning drawing actions into semantic operations Drawing applications are very coordinate-heavy. Agents, however, work much better with concepts. I didn't want the interface to expose something like: drawRectangle(x: 417, y: 263, width: 188...) as it would confuse the agent. Instead, I needed an abstraction where the agent could express meaningful operations while the application handled the Excalidraw-specific details. Finding that between agent-friendly semantics and precise canvas geometry was one of the biggest challenges. 2. Keeping connectors and elements stable A diagram is not just a collection of rectangles. Elements have relationships. Connectors need to stay attached to the right shapes, elements need stable identifiers, and updates must avoid unexpectedly breaking the rest of the canvas. 3. Letting humans and agents edit the same state I didn't want an “AI mode” and a separate “human mode.” The agent needed to modify exactly the same board the user was looking at, while keeping normal Excalidraw interaction intact. Designing a single mutation boundary helped make both interaction models coexist without creating two competing versions of the canvas. What I learned WebMCP showed me how powerful browser-native agents can be, and we are only getting started on this tech. I think it could become a major frontier for browser agents, with applications far beyond this project. What's next This project is a prototype , and there is a lot more in Excalidraw that I would love to bring into WebMCP. Right now, the agent can work with the core canvas primitives, but Excalidraw itself has a much richer set of capabilities. The next step would be to expose more of those features through WebMCP so an agent can interact with the canvas almost as completely as a human can. That could include things like image insertion, richer element controls, and Mermaid-to-Excalidraw , where Mermaid syntax can be turned directly into editable Excalidraw diagrams. I also want to make the natural-language → diagram experience much more robust. The current prototype works well for many diagrams, but there is still room to improve how agents reason about layout, spacing, connector placement, and iterative refinement instead of trying to get everything perfect in one pass. Beyond that, I would love to explore: Canvas history and revisions so agents can understand and restore previous states Better real-time human + agent collaboration on the same board Multi-agent collaboration , where multiple agents can contribute to one canvas Deeper support for Excalidraw's existing tools instead of maintaining a smaller agent-specific subset And if I get the opportunity to take this further, I would love to contribute these ideas back toward the actual open-source Excalidraw ecosystem . Excalidraw already has an MCP App Server. I think WebMCP could complement that by making the Excalidraw web app itself natively understandable and operable by browser agents, without treating the browser as just a screen to click around. The end goal is simple: Take everything humans can do inside Excalidraw and make those capabilities equally accessible to agents through WebMCP.
