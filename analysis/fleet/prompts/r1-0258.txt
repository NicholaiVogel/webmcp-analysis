A WebMCP workspace for repairing constrained plans while keeping humans in control Like Comment Story Updates Inspiration A surprising number of everyday operational problems are really placement problems in disguise. You have a set of people, tasks, items, vehicles, or events, a limited number of places or resources, and a collection of rules that determine what can go where. We see this everywhere. Guests need to be assigned to tables. Patients need beds. Employees need shifts. Classes need rooms. Aircraft need gates. Jobs need machines. Inventory needs storage locations. In every case, the basic question is the same: how do you put the right thing in the right place while respecting all the constraints around it? Creating the first plan is only part of the challenge. The harder part often comes later, when reality changes after the plan has already been accepted. A guest suddenly needs an accessible table. Two people can no longer sit together. A VIP needs a specific position. A resource becomes unavailable. A manager makes a last-minute decision that should not be undone. At that point, the goal is not to throw everything away and optimize from scratch. It is to repair the existing plan while preserving as much of what already works as possible. Traditional optimization systems are good at solving structured problems, but people do not usually describe operational changes as formal constraints. They say things like "keep these two apart", "do not move this person", or "this group needs to stay together". An AI agent can help translate that kind of natural-language intent into structured constraints, but there is another problem: the agent may be working from an older version of the plan while a person is still editing the live page. That creates a very real failure mode. A person can make an important manual change, and the agent can later overwrite it simply because it is still acting on stale state. We wanted to explore a collaboration model where that cannot happen silently. We chose seating because it makes the larger idea easy to see. A guest represents an entity that needs to be assigned. A table represents a limited-capacity resource. "Together" and "apart" rules behave like clustering constraints. Accessibility and fixed-table rules represent eligibility and placement requirements. A locked guest represents a human decision that the agent is not allowed to override. Seating Repair is our way of exploring how WebMCP can bring these pieces together: natural-language agency, deterministic constraint solving, live application state, and direct human control, all operating on the same shared planning surface. What it does Seating Repair is a WebMCP application for solving and repairing constrained placement problems while a person and an agent are both working on the same live plan. The demo uses 12 fictional guests and three tables because that makes the idea easy to understand at a glance. But underneath the seating interface, the application is dealing with a more general planning problem: limited-capacity resources, people who must stay together or apart, fixed placements, eligibility requirements such as accessibility, decisions that a human has explicitly locked, and the need to keep as much of the existing plan unchanged as possible. Through WebMCP, a browser agent can read the exact current state of the board, understand the active constraints, add new hard constraints from a person's request, repair the plan, and then validate the result. The goal is not simply to press an "optimize" button and generate a completely new seating arrangement. In a real planning workflow, many existing decisions are already correct and should stay that way. A useful repair needs to preserve what still works, respect every hard constraint, treat human-locked placements as authoritative, change only what is necessary, and verify that the final result is actually valid. This becomes especially important when a person and an agent are working at the same time. If the agent reads the board and a person then moves or locks a guest, the agent is no longer allowed to write using the old version of the plan. That stale write is rejected with STATE_CHANGED. The agent has to read the page again and continue from the decision the person actually made instead of silently overwriting it. In the demo, this is easy to see: a person can move Grandma Rose to a different table and lock her there. The agent can then add another constraint, repair the remaining conflicts, and validate the board while leaving Grandma Rose exactly where the person placed her. Seating is the domain we chose to demonstrate the idea, but it is not the limit of the underlying pattern. The same kind of constrained allocation and repair appears in restaurant and event operations, protocol seating, workforce scheduling, room and resource allocation, patient-to-bed assignment, airport gate reassignment, and many other situations where a working plan has to adapt as constraints and human decisions change. The current build is intentionally focused on demonstrating that shared coordination model clearly. It is not meant to pretend that one seating demo is already a complete product for every one of those industries. Instead, it shows the core interaction pattern: an AI agent can help repair a constrained plan, while the live application remains the source of truth and human decisions remain in control. How we built it We built Seating Repair as a lightweight TypeScript app with Vite. Everything runs in the browser, with no backend and no separate database for the agent. The seating board that the person sees is the same state the WebMCP tools work with. We kept the WebMCP side intentionally simple and exposed only four tools. One reads the current seating state, one adds hard constraints, one repairs the plan, and one validates the result. That was enough to cover the full interaction we wanted to demonstrate without turning the project into a large collection of overlapping tools. We also did not want the language model itself to be responsible for deciding whether a seating plan is correct. The agent can understand a request such as "keep these two apart" or "do not move this guest", but the actual planning is handled by deterministic application code. The repair logic runs in the browser and searches for an arrangement that satisfies all of the current constraints. It checks table capacity, together and apart rules, fixed-table requirements, accessibility, and human locks. When there is more than one valid solution, it prefers one that changes as little of the current plan as possible. Human edits are treated as first-class state changes. A person can move a guest manually and lock that placement. Once a guest is locked, the agent cannot move them during a repair. There is no hidden tool option that lets the agent ignore the lock; the person has to unlock that guest first. One of the main things we wanted to get right was what happens when the human changes the board while the agent is working. Every change to the seating plan increments a revision number. When the agent tries to change the plan, it has to provide the revision it previously read. If the board has changed since then, the write is rejected with STATE_CHANGED. That means the agent cannot quietly apply an old plan over a newer human decision. It has to read the current board again and continue from there. Repairs are also atomic. The solver works on a snapshot first and only updates the live board after it has found a complete valid solution. If the constraints cannot be satisfied, the current plan stays as it was instead of being left in a partially changed state. The manual UI and the WebMCP tools share the same store, validation logic, and constraint model. It gives AI agents structured tools to understand and operate the portal without relying on screenshots, DOM scraping, or UI automation. An agent can: discover the portal’s capabilities and safeguards; search datasets, sources, quality checks, pipeline runs, logs, lineage, and costs; inspect schemas and preview bounded samples of data; open a browser-local DuckDB workspace and write or run SQL; create temporary derived tables and data-quality checks; prepare a table for publication with metadata, field descriptions, transformations, schedule, and attached quality checks. At the same time, the portal gives people visual feedback for every meaningful step. They can inspect the source data, review the SQL, see result grids, follow lineage, understand quality-check failures, and observe mocked staging runs. On critical decisions, such as publishing a table to production, the agent is not doing it automatically. A human must intentionally review and approve it. How we built it Happy Coffee is built with React, TypeScript, Vite, and Tailwind CSS. The development experience runs on DuckDB-Wasm inside the browser. Generated catalog data is loaded into the happy_coffee schema, while temporary derived data is created in a local workspace schema. This means the SQL experience is immediate, portable, and does not require a server-side database. The portal registers structured tools through document.modelContext , and each tool returns a versioned contract with stable IDs, bounded data previews, navigation context, and explicit safeguards. This lets an agent reason about the portal as an application—not as a collection of pixels. The app is deployed on Cloudflare Pages. The underlying problem was not duplicate WebMCP registration itself, but the interaction between registration, diagnostics state updates, effects, and event listeners. \n\n We investigated the lifecycle, added dedicated React lifecycle tests, and fixed the ownership of the WebMCP toolchange listener. We also eliminated a race involving the approval state reference. \n\n Another interesting issue was the browser-generated toolchange event during initial registration. Since the browser emits a tool-change event for each registered tool, registering 10 tools produced unnecessary activity-panel noise. We kept the listener but suppressed those expected initialization events and retained logging for genuine post-registration tool changes. \n\n What we learned \n\n This project taught us that making an application "agent-compatible" is more than exposing a list of functions. \n\n The tools need: \n\n \n Clear schemas and descriptions. \n Predictable inputs and outputs. \n Safe boundaries around state-changing actions. \n Idempotent registration. \n Correct lifecycle management. \n Human approval for consequential actions. \n Observability so developers can understand what the agent is doing. \n \n\n We also learned how important it is to test both the tool layer and the actual React/browser lifecycle. Our standalone WebMCP tests passed while the real browser initially exposed a lifecycle issue, which led us to add dedicated React and Strict Mode tests. \n\n Final result \n\n ShopMate now exposes all 10 intended WebMCP tools, supports human approval for cart mutations, and has automated tests covering registration, discovery, execution, approval, diagnostics, Strict Mode behavior, and listener lifecycle. \n\n The project demonstrates how existing web applications can evolve from interfaces that humans click into interfaces that AI agents can understand and operate through structured browser-native capabilities . \n\n What it does \n\n How we built it \n\n Challenges we ran into \n\n Accomplishments that we're proud of \n\n What we learned \n\n What's next for ShopMate — Agent-Native Shopping with WebMCP \n\n \n\n \n Built With \n\n html javascript next.js react tailwind-css typescript webmcp \n \n\n \n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Abdullah Usman \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Abdullah Usman \n started this project\n \n —\n \n a day ago \n \n \n\n

Like Comment Story Updates AgentCut Home Page Codex WebMCP Chrome WebMcp Inspiration I have basic video editing skills things like splitting clips, adding text, and simple transitions but more advanced editing such as keyframes, motion, and text animation always felt overwhelming. When I learned about WebMCP, I saw an opportunity to change that. Instead of learning every advanced control myself, I could build an editor that exposes those capabilities as structured tools and let an AI agent use them for me. That became the idea behind AgentCut: a lightweight image and video editor where I can describe the result I want, and the agent can use advanced editing features like keyframes, animation, typography, and motion through WebMCP. In practice, it helped me go from using only basic editing tools to creating edits that previously felt like “pro-level” work. What it does AgentCut is a lightweight image and video editor that can be controlled manually or by an external AI agent through WebMCP. The editor supports things like: image adjustments and aspect ratios multiple text layers and curated fonts video trimming and reframing text timing text animation with keyframes video pan and zoom keyframes undo and redo rendered image and video export The difference is that these editing capabilities are also exposed as structured WebMCP tools, so an agent can inspect the project and perform edits from natural-language instructions. How we built it AgentCut is built with React, TypeScript, Vite, Tailwind CSS, HTML Canvas, MediaRecorder, and browser media APIs. The human interface and WebMCP tools operate on the same project state. This means an edit made by the agent immediately appears in the editor and can still be changed manually. AgentCut exposes 29 WebMCP tools covering image editing, video editing, text, keyframes, project inspection, undo/redo, and export. Challenges we ran into The biggest challenge was making agent edits reliable rather than just automating clicks. For example, when an agent changes only the font or size of one text layer, every other property needs to remain untouched. Smooth keyframe playback was another challenge. Early animation felt choppy, so the preview was changed to use frame-synchronized video timing. Video export was also difficult. AgentCut originally downloaded only the source file, but it now renders the actual edited composition and exports the result as MP4 or WebM depending on browser support. Accomplishments that we're proud of I am most proud that AgentCut lets someone like me use editing features that previously felt too advanced. In my demo, I could simply ask the agent to create a travel title, animate only one text layer, add a cinematic push-in, and change the aspect ratio. The agent translated those requests into structured edits and keyframes. The project now has: 29 WebMCP tools independent text layers fonts and styling text and video keyframes smooth animation real rendered video export 97 automated tests covering the editor and WebMCP workflows What we learned The biggest lesson was that giving an AI access to a webpage is not the same as giving it access to the product. WebMCP lets a website expose meaningful capabilities directly to an agent. Instead of trying to visually find and click controls, the agent can work with structured project state and editing actions. I also learned that this can make advanced software much more approachable. The user can focus on describing the result instead of learning every control first. What's next for AgentCut Next I would expand AgentCut with more advanced creative capabilities while keeping the same agent-first approach. Possible additions include: easing and richer animation controls transitions audio editing more typography controls reusable styles and presets multi-clip compositions The goal is to keep the editor simple for humans while exposing increasingly powerful creative tools to AI agents through WebMCP.
