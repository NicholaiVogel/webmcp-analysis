## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates If you can Try it out, your agent can too. Swagger UI WebMCP is a reusable Swagger UI plugin that turns any OpenAPI documentation page into a live, session-scoped agent interface — and splits the decision of what that agent may touch among the four parties who each know something different. The agent calls the API through the exact environment, login, and request pipeline the developer already has open in the page. No AI SDK. No MCP server to install. No bearer token copied anywhere. Live demo: https://openapi-web-mcp.vercel.app Repository: https://github.com/alliecatowo/openapi-web-mcp The problem A developer working against an internal or partner API already has a browser tab where everything is correct: signed in, staging selected in the server dropdown, the right key pasted into Swagger UI's Authorize dialog, and the corporate proxy, CORS rules, and session cookies all working. To let an agent help with that same API, the entire environment has to be rebuilt somewhere else — install or write an MCP server, re-describe the endpoints, copy a bearer token out of the browser into a config file, and keep the two in sync forever. So the agent is useful for writing code about the API and useless for actually driving it. Underneath that is a second problem nobody has a good answer for: once the connector exists, who decides what the agent may touch? Today it is whoever wrote it, once, months ago, holding standing credentials. Audience: developers, QA and support engineers, and solutions/API-partner teams who live in OpenAPI documentation pages every day — and the API publishers who host those pages for them. Every internal and partner API with a Swagger UI docs page is a candidate. The idea: authority splits four ways, and only ever narrows Four parties each hold information the others don't, so each gets exactly the instrument they have the information for: the API publisher knows which endpoints are dangerous, expressed as x-webmcp annotations that travel with the OpenAPI document itself, reviewed and versioned; the page owner knows what this deployment is for, expressed as a webMcp.exposure default and an optional policyResolver; the person at the page knows what is happening right now, expressed as per-operation session locks scoped to this tab only; and the WebMCP client knows what to ask a human, expressed through MCP annotations and structured errors. The rule that makes them compose rather than conflict: every source may only tighten. All of them reduce to a level on the lattice hidden < read < write, the tightest wins, and hidden survives every setting, because refusing exposure is never a privilege escalation. The agent itself does not get a vote — session locks are module state the tools never touch. Why the documentation page is the right place WebMCP's defining property is that the page is the integration: capability lives in the tab, scoped to the session, and dies with it. API docs fit that shape better than almost anything else. The contract already exists and is machine-readable, so tools are derived, not hand-written. The ambient state — selected server, authorized schemes, cookies, interceptors — is simply already true in the tab. Ephemerality is a feature: nobody wants a persistent connector holding standing write access to production. And it generalizes: every Swagger UI page that adds one import becomes an agent surface for whatever API it documents. That surface is not small. swagger-ui-dist alone is pulled from npm roughly 51 million times a month, and Swagger UI is the default, unmodified docs renderer behind FastAPI's /docs route and NestJS's official OpenAPI module — so the install base this plugs into is already deployed, already authenticated, and already pointed at real APIs. (npm registry, 30 days ending 29 Aug 2026; per-package figures in the README.) This is not "write another MCP server" — no standing credentials, no separately maintained tool definitions. And it is not a browser-automation agent clicking through the UI — it calls the API directly through Swagger's own execution pipeline, with a generated tool schema and MCP annotations per operation. What people and agents can do together The human signs in, picks Sandbox, authorizes a scheme in Swagger's own dialog — the agent inherits all of it, live. The person types into the q box of Try it out and stops; the agent reads that value and finishes the call. Every agent execution renders in Swagger UI's own response panel, not a separate agent console. An access control sits next to Try-it-out on every operation: Full access, View only, Read only, Hidden. And the demo API logs whether each write arrived via the agent pipeline or by hand. The thing that was hard before: letting an agent act on a live, authenticated, environment-specific API without provisioning it any standing credentials or infrastructure — and being able to see, constrain, and revoke that in the same place you were already working. The bigger picture The four-way split is in service of something larger than one docs page. It turns an existing, enormous class of page into an agent gateway with no new infrastructure to run or revoke. The per-operation access control doubles as a supervised playground: turn an agent loose on a live API, watch every call land in the same response panel you use yourself, and keep the kill switch one click away. Because agent calls run through Swagger's own execute action — the same code path as Try it out — an agent's call and a human's call are directly comparable, which makes the page a debugging surface. None of that needs different code — it is the same lattice and the same execution path, looked at from four angles. How WebMCP was implemented One import into an existing Swagger UI config is the whole integration. When the browser provides document.modelContext, the plugin enumerates operations from Swagger UI's own resolved spec, resolves local $refs, converts parameters and request bodies into JSON Schema tool inputs, and registers two layers of tools: five stable core tools plus one direct tool per exposed operation, capped at 64 with graceful fallback to discovery and generic execution. The cap is enforced everywhere a tool name is advertised, so search and get can never name a tool that was not registered. Tools can never name a URL. A call resolves against the currently selected Swagger server and does not build its own fetch client — arguments are written into the Swagger store, the page's own execute action runs the request through its configured interceptors, credentials, and selected server, and the result is read back out of the store. Like Comment Story Updates Walking trip planned in Paris New Window to plan a trip Inspiration The WebMCP Challenge asks what the open web looks like when it's built for humans and agents at once. We'd already been building @mapbox/web-mcp-server , a library that registers Mapbox GL JS map interactions as WebMCP tools, and had written up a design thesis for it before ever building a demo: a geospatial AI agent needs two things to be genuinely useful, a data layer (geocoding, search, directions) and a live rendering surface it can actually act on. Most "AI + maps" demos fake the second half: a chat response describing a trip, maybe a static image. WebMCP is the first browser API that lets a page hand an agent direct control over a live map instead, the same way an MCP server hands it a data source. We wanted to prove that idea end-to-end, not just describe it. What it does Open the demo, paste an Anthropic API key, and ask for a trip: "Plan a half-day trip in Paris: the Eiffel Tower, a nearby cafe, and the Louvre, with walking directions between each stop." An agent geocodes the real places, drops pins, pulls a real walking route, draws it on the map, and frames the whole trip, live, while you watch. An itinerary panel and an activity log rebuild themselves from the actual tool calls as they happen, so the WebMCP mechanism is visible, not just its output. How we built it The core is a small TypeScript library ( src/ , strict mode, pure ESM) where every map capability is a factory function, createFlyToTool(map) , createAddMarkerTool(map, markers, stops) , returning a ToolDescriptor that closes over the live mapboxgl.Map instance. registerMapboxTools(map) wires all of them up against navigator.modelContext.registerTool() , plus an onToolCall hook so a host page can observe every call live. On top of that, the demo does two things most WebMCP demos skip. First, it closes the "two data layers" loop from our own design doc for real: alongside the map-control tools, the page registers a small second set, geocode_place , search_category , get_directions , that call Mapbox's public Search Box and Directions REST APIs directly via fetch() . ABOUT TEXT (untrusted evidence):
Signett is an open-source TypeScript toolkit for building reliable, observable, and testable WebMCP applications. Like 1 Comment Story Updates What is Signett Signett is a reliability and evaluation layer for production WebMCP applications. In our live Saleor demo , an agent discovers catalog and checkout tools, finds a product, requests human approval, and submits a purchase request. What makes it special is that the storefront updates only after the purchase is verifiably complete, as provided by Signett. We also simulate a browser response loss after the mutation commits and show how Signett recovers the authoritative result instead of creating a duplicate. What it does WebMCP gives agents a structured way to use website capabilities. Signett adds the execution semantics and developer workflow needed to operate those capabilities reliably. The Signett SDK accomplishes that through several core features: JSON Schema validation before application code runs trusted application context and application-owned authorization human confirmation for consequential effects idempotency and replay coordination operation journaling and ambiguous-failure recovery authoritative postcondition verification cancellation and structured repair guidance privacy-conscious OpenTelemetry traces React bindings for verified UI updates deterministic testing without a model or browser Simple read tools remain lightweight. Consequential tools can use the complete guarded lifecycle. Signett does not replace WebMCP, authentication, backend transaction guarantees, or application business logic. The website continues to own identity, policy, state, consent UI, and every backend effect. Signett creates a structured boundary around those existing capabilities. The wider project includes the TypeScript SDK, a Chrome side-panel agent, a headless evaluation CLI, a local Inspector, OpenTelemetry export, reference applications, reproducible benchmarks, and reviewed evidence. Inspiration - Why Do We Need This? I am a strong believer that the web will be largely agentic in a few years. While we have seen a lot of promise with browser-use agents, what bothered me the most was that these harnesses were trying to operate on websites built for humans, clicking buttons, while they should be using tools/MCPs. Then, I discovered WebMCP and was instantly excited. However, I quickly found that while the protocol is extremely valuable, a real developer trying to make their websites agentic doesn't have an ecosystem built around it. Specifically, I saw several problems: What happens when an agent retries a purchase? What if the backend commits an effect but the response disappears? How does the user retain control over consequential actions? When should the UI update? How does a developer test the interface repeatedly, inspect traces, or detect a regression? These are familiar distributed-systems problems, but agentic websites make them more common and more consequential. Signett was built to answer a specific question: How do we move from “an agent can call this tool” to “an agent can perform this action safely, predictably, and verifiably”? That idea became Signett. How we built it Signett is a TypeScript monorepo with four primary layers. Signett SDK createSignett() creates a WebMCP-facing application surface. signett.expose() compiles the tool’s schema and registers it through the native document.modelContext.registerTool() API. Each tool defines its agent-facing contract and existing application function. Optional hooks add context, authorization, confirmation, idempotency, recovery, verification, output budgets, and lifecycle observation. Signett Chrome Agent The Chrome side-panel agent discovers and invokes only the WebMCP tools exposed by the active page. It deliberately has no DOM or screenshot fallback, so missing or poorly designed capabilities remain visible to developers. Signett Eval The CLI opens the real application in headless Chrome, discovers its live WebMCP inventory, runs saved tasks, and records bounded evidence. Applications can provide their own reset, snapshot, and grading hooks. This means success can be determined from the database or domain model rather than from the agent’s final response. signett check compares evaluation results against a reviewed baseline and can detect regressions in task success, safety, capability discovery, tool selection, argument validity, latency, token usage, and trial coverage. Observability and benchmarks Signett emits lifecycle events covering validation, authorization, confirmation, execution, replay or recovery, output measurement, and verification. These can power an in-page Inspector or be exported as OTLP/HTTP JSON to systems such as Jaeger. Inputs, outputs, application context, error messages, and stack traces are excluded by default. The repository also includes deterministic safety tests, real-agent evaluations, reference integrations, benchmark methodology, and reviewed evidence. Challenges we ran into One of the hardest problems was defining correct behavior after an ambiguous failure: a server may successfully commit an order or payment while the response is lost. Blindly retrying could duplicate the action, but blindly reporting failure would also be incorrect. Signett combines durable idempotency records, operation journals, recovery logic, and authoritative state verification to handle this case explicitly. Authorization and idempotency also interact in subtle ways. Returning a cached result must never bypass a current permission check. Signett therefore reevaluates authorization before every idempotency lookup, including replays. Another challenge was making observability useful without turning it into a privacy risk. Signett records lifecycle metadata and timing information by default, while avoiding tool inputs, outputs, application context, and stack traces unless the application explicitly chooses otherwise. Building high-quality benchmarks to hill-climb on was hard, but I think we got a lot of good-quality evaluations. Check out the benchmarks folder in the open-source repository. Finally, WebMCP is still experimental and evolving. I had to design useful abstractions without hiding the native API or prematurely inventing a competing protocol. Accomplishments that we're proud of Signett became more than a wrapper around tool registration. It now supports an end-to-end developer loop: Expose a native WebMCP capability. Inspect and invoke it in Chrome. Test its execution invariants deterministically. Exercise it with a real model in headless Chrome. Grade the result against the authoritative application state. Inspect its lifecycle through OpenTelemetry. Compare the run with a reviewed baseline. The same live WebMCP tools power the browser agent, the application UI, deterministic tests, and headless evaluations. There is no parallel demo-only tool catalog. We also validated the model against larger applications: Saleor: checkout, approval, lost-response recovery, replay, and authoritative verification Cal.diy: a real agent completed a booking after an injected lost response, with exactly one booking independently observed in Postgres an authenticated payment application used for deterministic safety and repeated agent-effectiveness studies What we learned The biggest lesson was that defining a tool schema is not the same as creating a trustworthy execution boundary. Agentic actions amplify several familiar distributed-systems problems. Retries, concurrency, authorization changes, cancellations, and lost responses become especially important when an agent can make purchases, send payments, or change persistent state. I also learned that the agent’s response is not proof that a task succeeded. Consequential actions need to be verified against the authoritative application state.
