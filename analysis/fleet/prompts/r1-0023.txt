# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

What it does Scopebox separates broad visibility from narrow write authority. The agent can inspect the whole page, but initially has no write capability. A human can frame specific fields, such as Headline and Description. The page then dynamically exposes WebMCP write tools that are valid only for that exact scope. If the agent discovers that another field must change, it cannot expand its own authority. It requests the smallest necessary scope expansion and waits. The main control mechanisms are: Dynamic WebMCP capabilities The tools exposed to the agent change with the current human frame. At Scope v0, the agent can inspect the workspace and active scope. After the human frames writable fields, write and scope-expansion capabilities become available. The problem was actually using it: the routine stayed in the chat, my workout logs lived somewhere else, and ChatGPT had no way to know what I completed or how much weight I used. A user can: Create and edit a multi-day workout plan Load a saved training day as today’s workout Track sets, reps, weight, effort, notes, rest time, and cardio Replace or reorder exercises during a workout Preserve completed work when a workout changes Review training history, volume, consistency, and personal records Receive clear progression recommendations based on previous performance Accept, edit, ignore, or apply those recommendations to the saved plan Through WebMCP, ChatGPT can read and update the same workout state shown in the interface. It can create a plan, add or replace unavailable exercises, shorten a workout, log sets, review history, recommend a new weight, and apply that change directly to the next session. Every human and agent change is visible in GymDeck’s activity history and recent changes can be undone. ## How I built it GymDeck is built with React and TypeScript and hosted as a browser-based application without a built-in application server. These tools are separated into focused read and write actions, including: Reading the athlete profile, current workout, saved plan, and exercise history Creating or editing training plans Adding, replacing, or reordering exercises Logging and correcting completed sets Adding timed cardio Reviewing progress Generating progression recommendations Applying accepted recommendations to the saved weekly plan The normal interface and WebMCP tools call the same underlying state functions. GymDeck works after a refresh and supports JSON import and export, demo data, and a fresh-workspace option. It does not require authentication, an external database, an OpenAI API key, or a chatbot embedded inside the app. ## Challenges I faced The biggest challenge was designing tools that an agent could use reliably. The first versions were too ambiguous. An agent might update only today’s workout when the user meant to change the saved plan, or interpret creating a first plan as replacing existing data. I separated these actions into clearer tools for first-time plan creation, explicit plan replacement, editing saved days, and loading a plan day into today’s workout. Another challenge was keeping history accurate across both human and agent actions. When ChatGPT changes a workout, the user should immediately see what changed, understand why it changed, and remain able to edit or undo it. The agent sees the page it is on and nothing else, while every task I actually wanted spanned sites. Find the delayed orders here, open a ticket there, email me a summary. Then the less comfortable realisation: agents could already do that. They browse, they navigate, some remember. What was missing was not capability. What it does The extension is three parts, and only the last is impossible outside a browser extension: Discovery : a modelContext polyfill installed in the page's MAIN world at document_start, or a native implementation wrapped in place, mirroring every registration out to the service worker. Registry : one list across tabs and sessions: live page tools, remembered sites that are closed right now, and nine action tools of its own, each with a status (AVAILABLE, SITE_CLOSED, AUTH_REQUIRED, TOOL_CHANGED, TOOL_MISSING) . A public crawler can catalogue which sites expose tools, but it is always signed out, so it never sees the ones behind your login. Cross-site execution : the extension runs each step on the site that owns that tool, in your own logged-in tab. The site exposes 13 capabilities of its own through registerTool() , and is where a run stops being something that happened and becomes something you can repeat: every step the agent took, the capability each one used, and a button that runs the whole thing again. Reach on one side, certainty on the other. What I actually built Not a smarter agent, a layer that makes an agents actions accountable and repeatable. Four things it refuses to do: Refuses to invent. A fabricated capability is rejected with the real names listed. Refuses to self-approve. The write prompt takes no approved argument an agent could set for itself, and fails closed where it cannot ask. Refuses to guess. Where judgement is needed, a reason step stops and hands the question back with the data attached. A gate fails closed rather than compare against data that never arrived. Refuses to take the agent's word. The engine writes the run record, so a step marked ok genuinely ran. Steps are JSON only, never generated JS, validated, then checked against the registry. Challenges I ran into Half of real WebMCP tools navigate instead of returning data. Pointed at real commerce sites, I found tools that move the browser rather than return values ,and a navigation drops that tab's tools from the registry, so a site read as "closed" seconds after its own tool had run. The agent may bypass you entirely. One posting straight to the extension's page API got a run id back while nothing was saved. Recording had to become a property of the bridge rather than of how a prompt was phrased, because you do not control the prompt. What I learned Magpie is not a new capability. Neither was WebMCP. Agents operated websites long before the spec scraping the DOM, driving a mouse. What WebMCP added was a contract: the site declares what it supports, with types, instead of the agent inferring it from markup. This project does the same thing one layer up, a contract across pages rather than within one. What's next Watch jobs, where the hard part is not the timer but pre-approving a write with limits validated in code rather than at a prompt. Remote MCP servers feeding the same registry. And a manual builder, so aworkflow can be assembled from proven steps with no agent involved at all.
