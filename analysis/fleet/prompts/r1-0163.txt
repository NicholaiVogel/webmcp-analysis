## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  end-to-end.

- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and

API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that

Audience size is NOT a multiplier.

Like Comment Story Updates 6 agent drivable builds within one command center Inspiration Team Rocket started as six small AI builds for the DC DevFest 2026 Buildathon, where we took third place. When we heard about the OpenAI WebMCP Challenge we could not help ourselves. Every one of those builds already had a human interface worth using, and WebMCP asked a question we wanted to answer: what does it take to hand that same interface to an agent without taking it away from the person? The answer we wanted was not a separate API. It was the same screen, driven from either side. What it does Team Rocket Command Center is six AI apps behind one Next.js site: a kanban board whose cards are segments of one effort-weighted progress bar, a group restaurant picker decided by counting swipes, a policy diff that ranks changes by who they land on, a resume-to-posting gap finder with a two-week plan, an ambient note taker that files what you say, and a reader that illustrates a chapter scene by scene. Each runs on the visitor's own Gemini key. Every build is drivable by an AI agent through WebMCP. Each page registers its actions as tools on document.modelContext , 44 in all, and every tool calls the same function the button calls, so a person and an agent are always looking at the same page. An "Agent is driving" pill in the header names the running tool. A WebMCP button lists what an agent could do on the current page before one arrives. The full surface, with schemas, lives at teamrocket.website/webmcp and is rendered from the same definitions the pages register. Anything destructive stops at an in-page confirm bar and waits for a human. No tool can read, accept or set an API key. How we built it A single client hook, useWebMCPTools , registers a page's tools while it is mounted and unregisters them through the registration's AbortSignal on unmount. It reads document.modelContext , the current spec and Chrome 153+, falls back to navigator.modelContext for Chrome 149 to 152, and degrades to a console.debug where neither exists so the site works in every browser. Each build keeps a static tools.js with names, descriptions and JSON Schemas, and wires handlers in its component next to the state they touch. Handlers read live state through a ref, so a tool always sees the current board, deck or workspace without re-registering on every render. ok() and fail() build the result shape; failures always carry a next-step hint and nothing ever throws. Four site-wide tools live in the shell: list the builds, open one, check which keys are set as booleans, and open the key panel for the human to type into. One tool is declarative: the name form in This or That carries toolname , tooldescription , toolautosubmit and a toolparamdescription , and answers agent-invoked submits with respondWith() . Destructive tools call gate() , which blocks on a confirm bar in the shell and resolves when the human presses Confirm or Cancel, the agent aborts, or a minute passes. The toolactivated and toolcancel events drive the header pill. Everything is committed in small steps in the open, MIT licensed. Challenges we ran into The spec moved under us. Articles still said navigator.modelContext and unregisterTool ; the current draft says document.modelContext with an AbortSignal, and Chrome 149 and Chrome 153 disagree. We read the Chromium IDL rather than the blog posts and support both. Agents arrive through different doors. The Codex Chrome extension drives the DOM and never saw our tools, while Codex's in-app browser called them directly. The first agent to reach the site used the buttons, which is exactly why the human UI had to keep working. That agent also found a real bug. Giving plan() parameters for the tool meant React handed it the click event when a person pressed the button, and the event's DOM node broke JSON serialisation. One-line fix, and a good reminder that adding an agent path can break the human one. Smaller ones: React's compiler lint rejects setting state in effects, so adopting saved state after hydration needed a useSyncExternalStore pattern instead; and transcribing a three-minute demo in one pass drifted ten seconds by the end, so captions are now generated in silence-aligned chunks. Accomplishments that we're proud of 44 tools across six real multi-stage pipelines, not a to-do list, each with the screen as the record of what the agent did. A safety model you can see: the pill, the confirm bar, and zero ways for a tool to touch a key. A tool catalog generated from the same code that registers the tools, so the documentation cannot drift from what is live. Give the site's own player a proper caption track. Add outputSchema to the tools once the spec lands it, and revisit readOnlyHint and consequentialHint as agents start honouring them. Like Comment Story Updates Inspiration Space science is full of ideas that are fascinating but difficult to experience. A light-year is an enormous distance. A signal can travel at the speed of light and still take 23 years to arrive. A spacecraft may have enough fuel to escape or enough time to transmit its discoveries, but not both. A video popped up on my Youtube feed while I was on a walk and gave me the inspiration for the base idea. I wanted to make them something a person could investigate with an AI agent. WORLDLINE began with a simple question: What if WebMCP could turn a webpage into a shared science lesson, where the agent investigates the evidence, the learner contributes their own thinking and the final decision remains human? What WORLDLINE does A probe near a black hole has recorded measurements showing how gravity bends space and changes light. Its computer has processed those measurements into two files. The probe is 23 light-years away and has only 71 seconds of radio contact remaining. An early, powerful burn can help it escape, but turns its antenna away from Earth. A later, gentler burn can keep the antenna connected long enough to send both files, but cannot save the probe. The browser agent receives the mission objective through WebMCP. It reads separate information about the files, radio connection, engine and maneuver limits. It forms hypotheses, predicts what each burn will do and uses a limited simulator to test possible worldlines. A worldline is the path something takes through space and time. Each tested maneuver creates a different possible future. The experience unfolds through three exchanges: The agent investigates the two clearest possibilities: saving the probe and sending the files. The learner calculates the transmission time and predicts why one burn may not achieve both goals. The agent reads that answer, tests a compromise and a counterexample, then explains what the evidence shows. The learner decides what to save. That decision creates one exact, temporary WebMCP action that the agent can execute once. The central calculation is intentionally approachable: $$ 18\text{ MB} + 12\text{ MB} = 30\text{ MB} $$ $$ 30\text{ MB} \div 1.2\text{ MB/s} = 25\text{ seconds} $$ The lesson then connects that calculation to the probe's remaining communication window, antenna alignment and escape requirements. Why WebMCP matters WebMCP is not an extra control attached to a fixed animation. It is the mechanism that makes the lesson responsive. The page initially registers six tools using document.modelContext.registerTool() . These expose separate mission facts, scientific files, maneuver constraints, a bounded simulator and presentation checkpoints. The agent must decide: Which evidence it needs Which possible burns are worth testing What each test is expected to prove Whether the learner's prediction matches the evidence Which outcome it recommends and why The learner's calculation and prediction become part of the shared page state. The agent reads that work and chooses tests that examine it. The resulting explanation develops from the evidence and the learner's participation rather than following a prerecorded sequence. When the learner makes the final choice, the page registers a seventh tool. This tool takes no arguments and is locked to the exact tested maneuver the learner selected. It can run only once. After execution, all planning and action tools disappear, leaving two read-only tools that verify the final state and transmission receipt. The visible lifecycle is: $$ 6 \rightarrow 7 \rightarrow 2\text{ tools} $$ The agent investigates. The learner decides. The page controls the resulting action. How we built it WORLDLINE is built with WebMCP, TypeScript, React and Vite, and is deployed on Vercel. It was coded using Codex. A revisioned TypeScript state machine is shared by the visible experience and the WebMCP tools. It records the mission evidence, simulation budget, tested worldlines, learner calculation, learner prediction, recommendation, human choice and final receipt. Tool schemas are closed and reject unexpected properties. Revision checks prevent stale operations. The simulator permits no more than five tests. The final execution tool closes over the selected maneuver, so the agent cannot change its timing, speed or payload after approval. Every visible path, result, calculation, animation and final receipt is derived from this shared state. Challenges we faced The hardest challenge was making the agent's intelligence visible. Agents can call several tools quickly, but a learner needs time to understand why each test matters. We redesigned the experience so results remain on screen until the learner chooses to continue. We also had to make the difference between agent mode and ordinary page interaction unmistakable. WORLDLINE does not secretly replace a missing agent with a scripted imitation. If WebMCP is unavailable, the page clearly explains what is required. Another challenge was keeping the science understandable without pretending this is a precision spacecraft simulator. The mission is fictional, but its lesson uses clear relationships between file size, transmission speed, communication time, burn timing and speed change. Finally, we needed to preserve human authority without reducing the learner to an approval button. The learner performs the calculation, proposes an explanation and makes the value decision that physics cannot answer. What we learned We learned that WebMCP can support more than task automation. It can give an AI agent access to the structure of an educational experience while allowing the webpage to remain the shared visual workspace. We also learned that a useful educational agent should not simply reveal an answer. It should test competing possibilities, respond to the learner's thinking, explain why an idea succeeds or fails and stop when the remaining question is a human judgment. WORLDLINE is an interactive science lesson about black holes, light-years, spacecraft communication and possible futures. It lets people investigate those ideas with an AI agent instead of merely watching them. However, as local client assistants and autonomous AI agents evolve into the primary portal for research and shopping, web content must become programmatically actionable for machines as well as visually readable for humans. Driven by this shift, we set out to create an agent-native affiliate marketplace. Our goal was to enable seamless visual browsing for users while empowering local AI agents to query structured product catalogs, discover tools, and deliver verified deals using modern browser standards. \n\n \n What it does AffiliateTresur. \n \n\n How we built it \n\n \n Frontend: Built with vanilla HTML5, modern CSS, and JavaScript to keep asset delivery lightweight and responsive. \n Agent Interface: Implemented declarative WebMCP tool handlers that bind directly to DOM forms and programmatic schemas, responding with structured JSON when invoked by browser-level AI agents. \n Edge Hosting & Delivery: Configured for edge deployment via Cloudflare using Wrangler, delivering static assets globally with instant edge caching. \n Version Control & CI/CD: Maintained via GitHub with automated Cloudflare Worker build triggers and custom domain routing on affiliatetresur.com . \n \n\n Challenges we ran into \n\n \n Edge Environment vs. Browser Code: Reconciling Cloudflare Worker deployment pipelines with a purely client-side static application required fine-tuning wrangler.jsonc asset routing rather than compiling edge server handlers. \n Build Configuration Hurdles: Diagnosing configuration file syntax issues—such as multi-root JSON parsing bugs in package.json —and configuring compatibility dates under automated Wrangler pipelines. \n Standardizing Agent Discovery: Aligning custom mock product query filters (spanning hardware, mobile tech, and automotive accessories) with strict WebMCP schema definitions so simulated agents could query data cleanly without format errors. \n \n\n Accomplishments that we're proud of \n\n \n Seamless Tool Discovery: Successfully implemented in-browser agent discovery, enabling Chrome DevTools agent simulators to detect and execute catalog queries instantly. \n Zero-Bloat Architecture: Delivered a full-featured, functional prototype without heavy framework overhead, ensuring sub-second load times and zero unnecessary dependencies. \n Live Domain Deployment: Successfully deployed and routed the platform to the live production custom domain affiliatetresur.com . \n \n\n What we learned \n\n \n Agent-First Web Design: Structuring data and forms for both browser DOM events and agent-invoked events requires thinking about web applications as APIs and visual dashboards simultaneously. \n Declarative Browser Standards: Practical hands-on experience navigating emerging browser AI APIs and testing agent interaction pipelines locally and in staging environments. \n Cloudflare Static Assets on Workers: Mastering modern Wrangler asset-binding patterns to serve high-performance client code reliably at the edge. \n \n\n What's next for AffiliateTresur \n\n \n Live Affiliate API Feeds: Connect the platform beyond mock datasets to real-time affiliate network APIs (e.g., Amazon Associates, CJ, ShareASale) with dynamic pricing updates. \n Autonomous Agent Price Tracking: Enable background agent monitoring where users can instruct their local assistant to alert them when a specific product drops below a target price threshold. \n Decentralized Attribution: Explore cryptographic verification and transparent commission tracking for agent-referred conversions. \n \n\n \n\n \n Built With \n\n agentic frontend html javascript \n \n\n \n Try it out \n\n \n \n \n
