## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

The agent interprets. Poolwart calculates. You verify. Like Comment Story Updates Poolwart turns an agent request into a visible, editable and safety-aware water-care calculation. Inspiration Pool and hot-tub owners often have three disconnected pieces of information: a water volume, a test result, and an active-chlorine percentage printed somewhere on a product label. Translating those values into a dose is tedious, and a generic assistant should not improvise safety-sensitive water-care arithmetic in chat. The useful division of work is different: an agent is good at understanding the messy request and extracting the inputs; a specialist site is good at deterministic, tested calculation; the owner must remain the person who verifies and acts. What it does Poolwart exposes two imperative WebMCP tools: calculate_chlor_topup calculates a dry-granule top-up from a measured free-chlorine value to the target range of the currently open Poolwart segment. calculate_chlor_shock calculates Poolwart's fixed +10 mg/l dry-granule shock increase. Calling a tool does not leave the answer trapped in an invisible tool response. It switches the visible calculator to the right mode, fills every input, and renders the normal dose, warnings, provenance, re-entry guidance, and disclaimer. The person can inspect or change every value and recalculate through the form. Poolwart calculates only. It never controls equipment, purchases a product, or physically doses water. How we built it The site uses imperative top-level registration through document.modelContext.registerTool . Each tool has a narrow JSON Schema with numeric limits and additionalProperties: false , followed by defensive runtime validation. Both the manual form and WebMCP call one shared typed adapter, which delegates the actual arithmetic to the existing, tested @poolwart/wasser package. WebMCP is registered only after client mount and receives an AbortSignal , so tools are removed when the component unmounts or the page changes. Unsupported browsers keep the complete ordinary calculator. The challenge extension adds focused tests for calculation parity, boundaries, schemas, registration, lifecycle signals, result size, invalid inputs, unusually large volumes, and above-target measurements. How WebMCP improves the experience Without WebMCP, a user or browser agent must choose a form mode and transcribe each value. An assistant may instead calculate in chat, losing the specialist formula, segment-specific targets, warnings, and an editable verification surface. With WebMCP, the agent invokes a named capability on the page. Poolwart validates and calculates, then makes the handoff visible to the human. This is a genuine shared workspace: the agent can prepare the calculation, the site can prove what it used, and the person stays in control. What existed before the challenge Poolwart, the manual calculator, its deterministic water-care package, target ranges, safety copy, and server-rendered result pages existed before 2026-08-25. The two imperative WebMCP registrations, English tool contracts, shared form/tool adapter, structured outputs, agent provenance UI, lifecycle cleanup, and their tests were created for this challenge. Extracting the typed adapter removed the risk of the two paths drifting. An adversarial review also found that the pre-existing form treated any value above the lower target threshold as “in target,” including excessive readings. The challenge work now distinguishes above_target , shows a visible warning, and returns re-entry guidance and unusual-volume status to the agent. For safety-sensitive calculations, a narrow tool contract and an explicit human handoff are more valuable than an opaque answer. WebMCP can make the website the shared, inspectable source of truth instead of reducing it to a hidden backend. Inspiration WebMCP gives individual websites a way to expose structured capabilities to browser agents. Those capabilities are exposed locally, while a user's compound objective can span several independently owned providers. I wanted to see whether a generic agent could compose that kind of journey without requiring any one provider, resolver, or platform to own it. For the challenge, that meant separating the problem: providers declare what they can do, Signpost resolves where those capabilities are available, and the agent decides which capabilities it needs and in what sequence. Consequential providers retain control over whether their own mutations may execute. The user can therefore begin with the outcome they want rather than a prearranged itinerary across specific sites: "order a coffee, book a basic haircut, and check this palette." What it does Signpost is a stateless capability resolver. An agent asks where a capability can be performed, and Signpost returns matching provider surfaces from declarations published by those providers. Signpost never receives the user's full objective. It doesn't decompose the request, maintain a session, choose the next step, or own an itinerary. The agent remains responsible for deciding what capabilities it needs and what to do next. For providers, this preserves a different boundary: they declare their own capabilities at their own origins rather than surrendering ownership of those capabilities to the system composing the journey. For the challenge, I built three independently deployed WebMCP reference providers: Deckhouse Coffee: order coffee Chair & Comb: find and book an appointment Hex Registry: check a hex value against a palette In the live demo, ChatGPT receives one request spanning all three. It determines the capabilities it needs, resolves them through Signpost, navigates to each provider, discovers its WebMCP tools, and completes the journey. For consequential actions, the agent can propose an action but cannot grant itself authority to execute it. Deckhouse Coffee and Chair & Comb display the exact material terms for user authorization at the provider. The pending invocation waits, then resumes and revalidates those terms immediately before execution. Only a valid, matching, single-use authorization permits the provider mutation. Signpost also keeps evidence separate from agent narration. Participating surfaces record authorization decisions, provider calls, and provider results so the evidence view can show what actually happened without becoming part of the agent's planning state. How I built it Participating providers publish small capability declarations describing what can be done at their origin. Signpost fetches those declarations and exposes one WebMCP tool: resolve_surface({ capability }) Matching is deliberately transparent: lexical retrieval with limited fuzzy matching, rather than another model in the loop. The result tells the agent where a capability is available, but never what it should do next. Each reference provider is an independent WebMCP surface and knows nothing about the others. Consequential providers place authorization and execution control at their own mutation boundary. The execution seam reuses @zioladev/execution-control@0.1.0 , a small package I published before the challenge. Its rule is intentionally narrow: only allow permits execution; block and indeterminate do not. The exact-term authorization flow, await/resume integration, reference providers, trusted-activation guard, evidence capture, and multi-provider Signpost flow were built during the challenge. I also included a deterministic drift test. It authorizes one set of material terms, presents different terms at execution, and verifies that the execution boundary returns BLOCK with zero provider calls. Challenges and what I learned The hardest challenge was not building too much into Signpost . Once an agent begins moving across several sites, it is tempting to give the resolver a session, itinerary, cursor, or concept of "next." Those features make orchestration easier, but they also change what Signpost is. I moved those responsibilities back to the generic agent, so the resolver remained stateless and journey blind. Cross-origin execution made that boundary practical rather than theoretical. Each provider had to stand independently on its own origin, while the agent could return to Signpost whenever it needed to locate another capability. The consequential flows evolved during the challenge as well. My first authorization design returned a "needs authorization" result and required the agent to retry after approval. I replaced it with await/resume: the original invocation now waits for authorization and then revalidates immediately before execution. Municipal waste rules that AI agents can understand and act on—without guessing, while humans retain control of final decisions. Like Comment Story Updates Inspiration Japan has highly organized waste-disposal systems, but the rules differ between municipalities. The same object may be classified differently depending on the city, quantity, size, material, or safety risk. People also rarely use exact official category names. They say things like: “I have ten of those transparent things sold at convenience stores for rainy days, something I put on the floor to sleep on, and a portable battery for charging my phone.” An AI agent can understand what the user probably means, but it should not invent municipal rules or automatically complete a potentially unsafe action. GomiMCP separates those responsibilities: The municipality declares the rules. The agent interprets the user’s language. The human makes the final decision. What it does GomiMCP is a static WebMCP-powered interface that exposes structured municipal waste rules directly from a webpage. The page registers three WebMCP tools: resolve_item converts ordinary or indirect wording into a canonical waste item. get_disposal_rule returns the municipality’s declared rule for that item. prepare_bulky_pickup prepares an eligible bulky-waste request without finalizing it. In the demo, the agent interprets one indirect Japanese request as ten umbrellas, one futon, and one mobile power bank. It makes eight real WebMCP calls: resolve_item ×3 get_disposal_rule ×3 prepare_bulky_pickup ×2 Under Aoba City’s fictional test rules, ten umbrellas and the futon are classified as bulky waste. GomiMCP prepares both requests and displays a Human Confirmation Gate totaling 800 yen. The mobile power bank is classified as high-risk. Automated preparation is refused, and the result is marked manual_review_required . The agent can prepare eligible requests, but it cannot press the final confirmation button. Nothing is booked until a human explicitly confirms it. How we built it GomiMCP is a static JavaScript application deployed with GitHub Pages. Its tools are registered using document.modelContext.registerTool() . Each tool provides a name, natural-language description, JSON input schema, execution logic, and safety annotations. The implementation separates: Item aliases and canonical identifiers Municipality-specific classifications Conditional rules such as quantity thresholds Fees and reservation requirements Risk levels and automation permissions Human-confirmation requirements Rule provenance and version information The LIVE WEBMCP TRACE displays only actual tool calls made through the page, making the interaction visible and auditable. No backend, database, authentication system, payment integration, or real municipality booking is used. Challenges we ran into The hardest problem was deciding where language interpretation should end and authoritative decision-making should begin. Natural language is flexible, while municipal rules must be precise. Allowing a language model to invent a disposal category would be unsafe. Passing an entire ambiguous sentence directly into a rule engine would also be unreliable. We solved this with a staged flow: The agent interprets each description as one ordinary item concept. GomiMCP resolves that concept to a canonical item. The page applies the selected municipality’s declared rules. Risk policies determine whether automation must stop. Consequential actions stop at a visible Human Confirmation Gate. Another challenge was proving that the tools were actually called. The LIVE WEBMCP TRACE records real page-level tool activity rather than displaying a simulated agent response. Accomplishments that we're proud of We successfully demonstrated: Semantic interpretation of indirect Japanese descriptions Eight real WebMCP tool calls Deterministic results based on municipality and quantity Automatic refusal for a high-risk mobile battery Preparation of two eligible bulky-waste requests A mandatory human-confirmation boundary A visible and auditable trace of every tool call A complete product experience running as a static website We are especially proud that the demo shows a useful division of responsibility: the agent understands the user, the page owns the rules, and the human retains control of the final action. What we learned AI does not need to own every decision to be useful. The model is best used for understanding human intent. The authoritative source should still own the rule, the safety constraint, and the final action boundary. WebMCP makes this division practical. It allows an ordinary webpage to expose structured capabilities to an agent while preserving the page’s existing logic, state, and user interface. We also learned that observability matters. Showing the real tool-call trace makes the system easier to test, explain, and trust. What's next for GomiMCP The current version uses fictional municipalities and test rules derived from official municipal open-data structures. It must not be used as real-world disposal advice. Future work includes: Importing and validating real municipality-maintained rules Expanding rule provenance and version tracking Supporting more item conditions, such as dimensions and remaining contents Adding multilingual municipality-maintained descriptions Providing reusable schemas for additional municipalities Exploring Remote MCP and SDK integrations Testing the same contracts across more WebMCP-aware agents and browsers Our longer-term goal is simple: municipalities should be able to declare their rules once and make them safely usable by people, websites, and AI agents.
