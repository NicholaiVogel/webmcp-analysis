=== RUBRIC (frozen) ===
# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

What it does NexusCanvas is a system-architecture canvas that ChatGPT operates directly through 14 base WebMCP tools plus 3 contextual ones. It runs entirely client-side, meaning no backend, no API keys, no account. The agent can build a whole system in one apply_blueprint call, audit it, model load against it, inject outages, and compile it to Docker Compose. But the point is not that the agent draws. The point is what the page does back: It computes what the model cannot fake. An audit engine finds single points of failure, missing caches, insecure protocols and orphaned queues, and returns a letter grade. The closed-form capacity model walks the graph in topological order, excluding back-edges. For each component, $$C_i = \text{capacityRps}_i \times \text{replicas}_i \times s_i, \qquad s_i = \begin{cases} 0.5 & \text{degraded} \ 1 & \text{otherwise} \end{cases}$$ $$u_i = \frac{\lambda_i}{C_i}, \qquad \text{served}_i = \min(\lambda_i, C_i), \qquad \text{dropped}_i = \lambda_i - \text{served}_i$$ Routers split their served traffic by normalised edge weight; services fan out $\text{served} i \times w {ij}$ per edge, so a weight of $0.2$ reads as a 20% cache-miss rate. Latency stretches as a component saturates, capped so the number stays finite: $$\ell_i(u) = \begin{cases} \ell_i & u < 0.5 \[4pt] \dfrac{\ell_i}{1 - \min(u,\,0.9)} & u \geq 0.5 \end{cases}$$ The discrete-event simulator exists because the closed-form model cannot show cascades. It runs a simulated clock over a binary min-heap event queue with Poisson arrivals, exponential interarrival times drawn as $\Delta t = -\ln(U)/\lambda$ , plus per-component concurrency limits, bounded queues, hop timeouts, bounded retries, and upstream workers held while awaiting downstream calls, so connection-pool exhaustion emerges instead of being asserted. It reports true $p_{50}$, $p_{95}$ and $p_{99}$ from completed-request samples. Randomness is seeded by an FNV-1a hash of the graph and scenario, driving a mulberry32 generator threaded explicitly through the run. Same graph, same seed, bit-identical output, which is what makes it testable, and what makes the agent's claims reproducible. 57 tests cover the engines, tool input validation, the WebMCP adapter against host stand-ins, and the demo sequence. A structural chokepoint is not a SPOF if it is replicated. Adding a replicas == 1 precondition took one line and turned an audit a judge would distrust into one that survives scrutiny. Killing the cache made the database less busy. Like Comment Story Updates fresh-human-review human-review planning-tradeoffs Cutting layout Inspiration A cutting plan is not just an answer—it is a decision about real material. For small workshops and makerspaces, planning starts with measured boards, usable offcuts, required parts, and the material lost to the saw blade. Copying that information into a chatbot creates a second version of the workshop: someone must reconcile the advice with the actual stock and translate it back into a usable cut sheet. Offcut explores a different workflow: let the person and the browser agent work from the same committed measurements, while keeping proposal and approval separate. Cutting-stock optimization is established work. Our contribution is the shared human–agent workflow around it: structured comparison, an exact review handoff, and approval that becomes invalid when its underlying measurements change. What it does Offcut is a shared cutting-stock workbench for straight crosscuts from stock of the same material and cross-section. People can: Enter stock lengths and required part quantities. Set blade kerf and the minimum length considered reusable. Protect stock needed for another job. Compare proportional cutting layouts. Review and approve an exact plan. Export its CSV cut list or print its cut sheet. Through native WebMCP tools, a browser agent can read the committed workshop, request checked alternatives, inspect their constraints, compare results, and stage one complete proposal for review. Three objectives make the trade-offs explicit: Use less stock Handle fewer boards Keep useful offcuts Sawdust, short scrap, reusable remnants, and unopened stock remain separate. How we built it Offcut is a static React and TypeScript application built with Vite and published on GitHub Pages , with public MIT-licensed source. The language model chooses what to explore; the application checks part quantities, stock constraints, and material balance. Manual planning also works without WebMCP. Connecting an agent depends on the browser host’s own model, permissions, and availability. The planner works in integer millimetres and has a bounded search. It reports optimality only when proved—not simply because it found a complete plan. Challenges we faced Keeping approval attached to the right decision Selecting another draft must not transfer approval. Reusing a checked solution must not transfer approval either. Approval belongs to one exact plan ID at one committed workshop revision. Acknowledgement and approval are separate interface actions; neither is a registered agent tool. Export checks the exact approved, fresh, complete plan. This is a tool-capability boundary, not authentication against an agent separately granted browser UI control. Distinguishing unfinished typing from changed measurements An unfinished measurement field is not a new workshop revision. Offcut distinguishes pending edits from saved measurements. Pending edits pause review and approval. Committing an actual change invalidates the previous approval and makes the old plan stale, so the agent must replan and return for a new review. The demo uses a real model through an external recording harness. UI actions are automated for the recording, and waiting time is trimmed. Reuse still creates a new unapproved plan record and preserves the original computation’s proof status. What we learned Shared state matters more than conversational fluency. An agent becomes more useful when it can work with the same revision, identities, and constraints that the person sees. Approval is a state transition, not a reassuring message. Its meaning depends on the exact proposal, the measurements behind it, and what happens when those measurements change. Optimization needs explainable trade-offs. Less scrap, fewer boards, and less opened stock are different goals. The application should expose those differences rather than pretend one score answers every workshop’s priorities. Native tools should expose checked domain operations. The model can explore and explain alternatives without inventing measurements or bypassing the workbench’s release rules.
