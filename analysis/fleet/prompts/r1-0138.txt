## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.

Judge: is there a real audience; is there a real problem, desire, or use case for that

- 3-4: speculative audience or strained fit; impact mostly aspirational.

Audience size is NOT a multiplier.

Like Comment Story Updates What it is Ingram Sheets is a spreadsheet whose calculation engine runs in the browser. It publishes its operations to whichever agent is driving the tab: read a range, write a block, extend a pattern, format, restructure, undo, point at a cell. ChatGPT supplies the model; we supply the sheet and hold no inference key. Why it needs WebMCP The engine is IronCalc compiled to WebAssembly, holding the live workbook in memory. There is no server-side copy of the sheet you are looking at: nothing that could recalculate it remotely, no endpoint that knows where your cursor is. An agent outside the tab has nothing to call. Spreadsheets for models, not models for spreadsheets The engine keeps every intermediate result at a stable address, so the model writes D17 instead of recopying a value it can transcribe wrong. It owns the dependency graph, so the model declares one local relation at a time and the engine keeps the global result consistent. And every write returns the cells whose computed values changed, recalculation ripple included. That return value is the tool contract: the model is corrected at each edit rather than at the end of a script, and it can skip the read that would otherwise confirm what it just did. Working alongside it Person and agent are in the same document at the same time. The agent's writes recalculate on screen, its focus moves across the grid in its own colour, and it can highlight a range and attach a note. Edit a cell while it works and your change is attached to its next tool result, so it re-plans against the current sheet. A code interpreter cannot do this. Its state ends with the session and its output is not editable. In a workbook every intermediate value sits next to the formula that produced it, and whoever knows the discount rate is wrong fixes the cell. How it is built Twelve tools, generated from the Zod schemas that also drive the built-in chat agent, so the two surfaces cannot drift. Every write goes through one controller, so an outside agent gets the same cursor and highlight behaviour as the built-in one, and its edits ride the same compare-and-swap save as a keystroke. Reads are marked readOnlyHint so the host can run them unattended. The two that return cell contents are marked untrustedContentHint : a cell can hold any text, including text shaped like an instruction, and the agent is told up front that what comes back is data. Results are returned as plain text rather than MCP content blocks, because the host serializes whatever a tool returns and the wrapper reaches the model as JSON noise around the grid. Prior work and hackathon work Ingram Sheets is a pre-existing project. WEBMCP.md in the repository separates what shipped before the submission period from what was built during it, with the commit history. Tools are registered with document.modelContext.registerTool(), each with a JSON schema and a callback that shares state with the UI, so an agent's move and a human's move land in exactly the same place. Stockfish 18 runs in the page, compiled to WebAssembly in a Web Worker. There is no backend. Searching happens off the main thread, so the board stays responsive while the engine thinks, and it reaches depth 16 to 18 in about a second. The 7 MB binary downloads on first analysis rather than on page load, and a small UCI client on the page serialises searches and handles aborts, so moving on to a new position cancels the search before it. Challenges I ran into WebMCP has no way to push application state to an agent. The spec has no notification for "the human moved, your turn". The workaround is chess-wait-for-human-move , a long-running call that resolves when the position changes, guarded by a FEN check and a two-minute timeout so it cannot hang. It works, but it is a workaround for a real protocol gap, not a claim that WebMCP does push notifications. A legal move is not a good move. Early on ChatGPT would cheerfully propose legal but tactically losing moves, because the only thing the page told it was which moves were legal. Legality answers whether a move follows the rules, not whether the opponent can immediately punish it. Stockfish now answers the second question, and the model is left to do the part it is actually good at. What I learned Long-running tool calls can bridge WebMCP's current gaps, but they are not push notifications and it is worth being honest about the difference. The pattern that actually emerged is a split of labour: the model explains, deterministic domain tools verify. Stockfish is the strongest version of that in this project. The engine calculates and returns ranked lines with real numbers; the model turns a principal variation into a sentence you can learn something from. Neither is asked to do the other's job, and the failure mode of each is caught by the other. What's next The interesting unfinished work is in the protocol, not the chess. Waiting for a human turn should not need a two-minute long poll, and the open WebMCP design discussions on application-driven observations, human-in-the-loop elicitation and long-running tool progress are all pointing at the same gap from different directions. This project is a small, concrete test case for whatever lands there. A WebMCP-powered healthcare price transparency agent that lets AI search claims, compare procedure prices, and summarize provider data.\n \n\n \n \n\n \n \n \n \n \n \n Like\n \n \n\n \n\n \n \n Comment\n \n\n \n \n \n\n \n \n \n \n \n \n \n Story \n \n \n \n \n Updates \n \n \n \n \n \n \n\n\n \n \n\n\n \n \n \n \n\n \n\n \n \n \n \n \n\n \n \n ClearHealth AI dashboard showing healthcare price transparency data and the three WebMCP capabilities available to AI agents. \n \n \n \n \n \n\n\n \n \n \n \n\n \n \n ClearHealth AI dashboard showing healthcare price transparency data and the three WebMCP capabilities available to AI agents. \n \n \n \n \n \n\n\n \n \n \n \n\n \n \n ClearHealth AI dashboard showing healthcare price transparency data and the three WebMCP capabilities available to AI agents. \n \n 1 2 \n\n\n\n \n Inspiration \n\n Healthcare price-transparency data can be difficult to search, compare, and understand through a traditional web interface. I wanted to explore how WebMCP could make an existing healthcare application more useful to AI agents without removing the human experience. \n\n The project originally started as a healthcare claims and Machine-Readable File (MRF) coding challenge. I extended it for the WebMCP Challenge so that both humans and AI agents can interact with the same underlying healthcare claims data. \n\n Why WebMCP is a Strong Fit \n\n Healthcare price transparency is a strong fit for WebMCP because users often need to search, compare, and summarize structured pricing information rather than simply browse a webpage. Traditional web interfaces are designed primarily for humans, requiring an AI agent to understand the interface and determine how to perform these tasks. \n\n This project exposes three meaningful healthcare capabilities through WebMCP: searching claims, comparing procedure prices, and summarizing provider claims. These operations have clearly defined inputs and structured outputs, making them natural capabilities for an AI agent to invoke. \n\n For example, instead of an agent navigating the application to compare prices for a procedure, it can call compare_healthcare_prices with a procedure code and receive the relevant billed, allowed, and paid statistics. Similarly, an agent can search claims or obtain a provider summary without relying on UI navigation or screen scraping. \n\n This creates a human-and-agent experience in which people can continue using the visual healthcare application, while agents can directly access its core capabilities. WebMCP therefore transforms the website from a human-only interface into one that can be used by both humans and AI agents. \n\n What it does \n\n ClearHealth AI is a healthcare price-transparency application enhanced with WebMCP. \n\n A human can use the web application to explore healthcare claims and pricing information. An AI agent can access the same data through three read-only WebMCP tools: \n\n \n search_healthcare_claims — searches claims using structured filters such as provider name, procedure code, and place of service. \n compare_healthcare_prices — calculates billed, allowed, and paid price statistics for a procedure, including averages, minimums, maximums, totals, and amount differences. \n summarize_provider_claims — provides an aggregate summary of a provider's claims, including claim count, billed, allowed, and paid amounts, average allowed amount, and associated procedures. \n \n\n For example, an agent can search for claims associated with Michael Poole, compare prices for procedure s5301 , and then summarize Michael Poole's claims without having to navigate the application's user interface. \n\n How I built it \n\n The application is built with React and TypeScript and uses a healthcare claims data layer to provide structured data to the WebMCP tools. \n\n The WebMCP implementation is located in: \n\n frontend/src/webmcp/tools.ts \n\n I check whether WebMCP is available and register the tools through: \n\n document.modelContext.registerTool(...) \n\n Each tool provides a unique name, human-readable title, description, structured input schema, read-only annotation, and asynchronous execution function. \n\n The tools are read-only and reuse the application's healthcare claims data without modifying the underlying dataset. \n\n I also use Mantine for UI components, Tailwind CSS for styling, PapaParse for CSV parsing, AG Grid for data presentation, Zod for schema validation, MobX for state management, and React Router for navigation. \n\n Challenges I ran into \n\n The main challenge was deciding which application capabilities would provide real value to AI agents. \n\n Instead of exposing simple UI actions, I focused on meaningful healthcare operations with clearly defined inputs and structured outputs. I also needed to make the WebMCP layer work alongside the existing human-facing application rather than replacing it. \n\n Another challenge was designing the tool outputs so that an agent receives useful structured information that can be directly interpreted and communicated to a user. \n\n Accomplishments that I'm proud of \n\n I successfully extended an existing healthcare claims application with an agent-facing WebMCP layer. \n\n The application now provides three distinct healthcare capabilities that an AI agent can discover and invoke: \n\n \n Search healthcare claims \n Compare healthcare prices \n Summarize provider claims \n \n\n I'm especially proud that the same underlying healthcare data can support both a traditional human interface and direct agent interaction. \n\n I also kept the WebMCP tools read-only so that agent interactions do not modify the underlying claims data. \n\n What I learned \n\n This project helped me understand how WebMCP can provide a structured interface between a web application and AI agents. \n\n I learned that an effective agent-facing interface is not simply about exposing more functionality. The capabilities need to represent meaningful user tasks, have clear inputs and outputs, and be easy for an agent to invoke. \n\n I also learned that WebMCP can complement a human-first interface: people can continue using the application visually while agents can directly access the application's capabilities. \n\n What's next for ClearHealth AI: Healthcare Price Transparency Agent | WebMCP \n\n My next step is to expand the agent capabilities while maintaining clear, read-only boundaries around healthcare data. \n\n Future improvements could include additional healthcare analytics tools, richer natural-language interactions, stronger validation and error handling, and additional ways for humans and AI agents to collaborate when exploring healthcare price-transparency information. \n\n My goal is to continue evolving ClearHealth AI into an application where healthcare data is accessible through both intuitive human experiences and well-defined agent capabilities. \n\n \n\n \n Built With \n\n ag agents ai css grid healthcare mantine mobx papaparse price react router tailwind transparency typescript vercel webmcp zod \n \n\n \n Try it out \n\n \n \n \n frontend-challenge-1-delta.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Chitipolu Sri Sudheera \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Chitipolu Sri Sudheera \n started this project\n \n —\n \n 5 days ago \n \n \n\n
