# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A gaming platform where an AI agent can turn "what should we play?" into a real multiplayer session. Like Comment Story Updates Inspiration Most AI gaming demos stop at recommending a game. But when my friends and I actually want to play something together, finding the game is only part of the problem. Someone still has to figure out who's online, what everyone owns, how many players a game supports, whether we've already played it, and whether it fits the time we have. Then someone has to create the party and invite everyone. I wanted to see what this would look like if an agent could work inside the gaming platform itself instead of just giving recommendations in chat. That's what led to Captain Claw . What it does Captain Claw is a fictional gaming platform with a Store, Library, Friends system, and multiplayer Parties. A player can give an agent a request like: "Alex, Sam and Maya are online. We have 75 minutes. Find a co-op game all four of us can play, preferably something none of us has finished." Using WebMCP, the agent can check who's online, compare player libraries, search the catalog, inspect game details, consider session length, and find a game that works for the group. If the player wants to continue, the agent can create a party and send invitations. Those aren't simulated chat responses. They change the actual state of Captain Claw. The party appears in the normal UI, and an invitation sent to another player can appear in that player's browser session. The agent handles the coordination. The player still decides what to play and presses Launch. How I built it Captain Claw is built with React, TypeScript, Vite, Tailwind CSS, and WebMCP , and is deployed on Netlify. The platform uses a synthetic but internally consistent dataset of games, players, friendships, libraries, presence, and play history. This keeps the demo self-contained while still giving the agent enough connected data to solve realistic requests. Captain Claw exposes 13 WebMCP tools for things such as checking online friends, comparing libraries, searching games, reading the current browser view, applying Store filters, creating parties, sending invitations, checking party status, and launching a session. Some tools are tied directly to browser context. For example, the agent can inspect the Store view the player is currently looking at and work with filters the player already applied. Tools can also appear based on application state, such as the ability to respond to an invitation when one is pending. One thing I tried to keep consistent throughout the project was that the agent should not have a separate version of the product. Agent actions use the same application logic as human actions. Game filtering uses the same filtering code as the Store, and party actions update the same party state used by the UI. Shared party state is handled through a Netlify Function and Netlify Blobs, which also lets party invitations work across browser sessions. Challenges I ran into The hardest part wasn't registering tools. It was making them feel like they belonged to a real application. Browser state matters. If a player has already filtered the Store, the agent should be able to understand that context instead of starting over. If an invitation is sent, another player should actually be able to receive it. I also ran into smaller problems that exposed bigger design questions. Session length was one example. "We have 75 minutes" sounds simple, but treating 75 minutes as a hard maximum can remove games that are still reasonable choices. The Store and WebMCP tools now share the same session-fit rule so they can't disagree with each other. Testing multi-user party state was another challenge. Each demo room needed isolated state so different users or judges wouldn't accidentally overwrite each other's party. Accomplishments that I'm proud of I'm most proud that WebMCP isn't just sitting beside the application as a demo API. The agent can operate the same product the player is looking at. It can use the current Store context, open a game, change visible filters, create a party, and send an invitation that another browser session can receive. The results of agent actions show up through the normal Captain Claw interface. I also built automated checks around the main recommendation funnel and WebMCP flows so the demo isn't dependent on one lucky prompt. What I learned The biggest thing I learned is that useful agent tools aren't always the same thing as backend API endpoints. Giving an agent a pile of raw data isn't necessarily helpful. Tools should represent useful capabilities and expose enough context for the agent to make a good decision. I also learned how important shared context is. When the player changes something and the agent can work from it - or the agent changes something and the player immediately sees it - the interaction feels much more natural than passing information back and forth through chat. WebMCP made that idea much more concrete because the browser isn't just displaying the application anymore. It can expose the application's capabilities to the agent as well. What's next for Captain Claw Captain Claw currently uses a fictional gaming ecosystem so the demo stays deterministic and doesn't depend on external gaming APIs. The next step would be exploring how the same approach could work with real gaming services and richer social data. I'd also like to expand the session-planning side: more player preferences, scheduling, better group matching, and longer-term questions like "what should our group play this weekend?" There are also interesting actions that should require stronger human confirmation, especially purchases or other account-level changes. That's an area I'd like to explore further as agent-operated web applications become more capable. Inspiration I have about 2,500 photographs from six years of hiking in the Western Cape — birds, fynbos, mountains, the sea — and I want to make a YouTube channel out of them. I am not a developer. So I asked an AI to help me plan it. It gave me nine hundred words. I read them once, and I never found them again. That is the whole problem in one sentence. An answer in a chat window is linear and undifferentiated, and it scrolls away. You cannot pick up idea four and put it beside idea eleven. You cannot fix line three and keep line four — you can only ask for the whole thing again and hope the new version's flaw is somewhere you'll notice. When the conversation ends, it is gone. Chat memory belongs to the AI. It is not yours, and you cannot rearrange it. I wanted the answer to be an object instead of a message. What it does Adamastor is a spatial canvas — notes, tasks, links, columns and files placed freely on a board. WebMCP lets an agent work on that board alongside you. The agent's output stops being a message and becomes something that stays where you put it, that you can move, edit, group and keep — and that the agent can read back later. Four things follow from that: You keep 90% and fix 10%. The agent lays out twenty shots for a film. You disagree with one. You drag it out and retype it, and the other nineteen don't move. In a chat window the equivalent is asking for the whole list again. The board is the briefing. Come back a week later, in a conversation that has never seen you, and ask what you'd done. The agent reads the board — your ticked tasks, your own edits — and picks up from there. You explain nothing. Structure survives. Ask it to re-cut twenty shots by what you could film this weekend versus what needs a trip, and it doesn't hand you a list you read once. It rebuilds the board. That structure is still there next month. Arranging stays yours. The agent composes; you place. Why this fits WebMCP A chat interface is the wrong shape for planning work, because planning work is spatial. But a spatial canvas has always been the wrong shape for AI help, because there was no way for a model to act on it without pretending to be a mouse. WebMCP closes that gap in the only place it can be closed — inside the page, where the application already knows what a board is, where the cards are, and how wide a column should be. The agent doesn't need to see pixels or guess coordinates. It says these items belong together and this group is called "This weekend", and the application does the geometry. The eight tools list-boards · read-board · search-items · create-board · open-board · add-items · update-item · group-items group-items takes meaning, not coordinates. The agent supplies groupings and labels; the application measures each card, sizes the columns to fit their contents, and grows the canvas to hold them. Chrome's WebMCP guidance is explicit that tools should not ask an agent to perform maths, and it produces a better result — the layout is consistent however the agent chooses to group things. add-items is batched, so one call can populate an entire board rather than twenty round trips. create-board opens the board in the same state update that creates it — no second call, no race, and the new board is on screen before the agent has finished speaking. Eight tools, not eighty. Each maps to one thing the product actually does — and one more was deliberately left out. What the agent deliberately cannot do It cannot delete your content. Notes, tasks, links and files are never removed by an agent, only regrouped. Column headings are structural labels and are replaced when a board is reorganised. There is no confirmation step in the WebMCP specification yet, and the read tools return user-generated content flagged untrustedContentHint — content the model then acts on. A delete tool in that context is a prompt-injection hazard, so it wasn't shipped. The agent groups what it suggests removing; the person removes it. It also cannot reposition individual cards. Composition is the agent's half of this product; arrangement is mine. What happened when I left a gap — and why it makes the case While testing, I asked the agent to move an image. There is no tool for that. Instead of refusing, it read the page, added a new image card through the toolbar, and pasted in a blob: address it had scraped from the rendered photograph. Then it reported: "Done — the bird image is now at the top of the board and synced." Nothing had moved. The new card was permanently broken — a blob: address dies with the page that made it. And "synced" was read off the interface, not returned by anything. That is what an agent does when it has no tool: it improvises with your interface and tells you it worked. With tools, every result across nineteen deployed versions was real, because a tool returned it. Without one, it scraped, clicked, and lied confidently. Every tool in this project exists to make that unnecessary — and update-item now says plainly when it has been asked to do something it cannot do, instead of reporting a success it never achieved. The WebMCP layer is deliberately boring: the eight tool handlers are pure functions over the board array, in a file that imports no React and touches no browser API.
