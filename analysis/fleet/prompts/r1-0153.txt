## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured

  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

sums.

- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

Product truth, callable by agents. Like Comment Story Updates Inspiration Enterprise buyers rarely encounter one product surface. They compare a marketing page, pricing matrix, docs, trust center, contract language, and actual product behavior. Those surfaces drift. A browser agent can describe each page, but it still has to guess which statement wins. LooPROOF turns that hidden governance problem into a WebMCP-native collaboration surface. The website exposes not only controls, but the product claims, evidence provenance, authority boundary, and claim ceiling an agent needs to reason safely. What it does This challenge build includes a synthetic enterprise SaaS evidence graph with customer-facing claims and authoritative runtime, contract, and repository evidence. LooPROOF deterministically classifies each claim as BLOCK , REVIEW , ALIGNED , or NOT_EVALUATED . A human and an agent can work through the same visible state to: inspect the product-truth summary; find claims blocking an enterprise sales gate; trace every source, locator, value, provenance class, and authority level for a claim; focus the dashboard on the same claim the agent is investigating; stage canonical copy changes in a local-only sandbox; re-run the deterministic gate and reach STAGED_CONSISTENT_NON_ISSUING . LooPROOF deliberately refuses to call a sandbox change “fixed.” Production verification remains a separate authority. Why WebMCP is essential Without WebMCP, an agent must infer the purpose of rows, badges, filters, and buttons from the visual interface. More importantly, it cannot reliably infer LooPROOF's domain contract: runtime evidence outranks marketing copy; model-proposed evidence cannot bind a verdict; a missing evidence edge is NOT_EVALUATED ; and a sandbox patch has a strict claim ceiling. LooPROOF registers 7 imperative WebMCP tools on document.modelContext . Closed schemas give the agent stable claim IDs, explicit inputs, side-effect annotations, and compact structured outputs. Tool execution updates the same state the human sees, creating a shared workspace rather than hidden backend automation. How we built it The app is dependency-free JavaScript, HTML, and CSS. A deterministic TruthEngine evaluates a bundled evidence graph and overlays sandbox patches in memory. The WebMCP adapter registers tools with document.modelContext.registerTool() , uses AbortSignal for lifecycle cleanup, declares read-only and side-effect annotations, and normalizes outputs to compact MCP text content. Node's built-in test runner verifies verdict binding, provenance boundaries, sandbox isolation, reset behavior, and tool-contract limits. GitHub Actions runs the complete verification suite. What is new for this challenge LooPROOF existed as a broader verification-engine concept before the submission period. During the challenge period, it was meaningfully extended through a new standalone public implementation containing: the complete imperative WebMCP tool surface; a shared human-agent state model; a provenance-preserving product-claim evidence graph; the local resolution sandbox; the deterministic re-verification path; a new responsive interface, test suite, security boundary, and challenge documentation. The repository contains synthetic evidence and does not copy or expose the private production implementation. Challenges The central challenge was not exposing more tools. It was preventing agent convenience from weakening evidence semantics. The implementation had to make the useful path easy while refusing unsupported claims. We therefore separated evidence alignment, staged consistency, and production verification into distinct states. Accomplishments 7 working imperative WebMCP tools. A coherent human-agent product experience rather than a wrapper around a chat box. Shared visible state between tool calls and the dashboard. Deterministic verdicts with provenance and authority ordering. A local sandbox that performs zero network, repository, or deployment writes. Explicit refusal to overclaim success. Like Comment Story Updates Modeled sightline metrices Non binding modelled summary Nandan seated 3D view Seatline Overview All five WebMCP tools executed successfully Seatline Kolkata Inspiration Picking a seat in a cinema is actually a decision that has a spatial element disguised as a grid. A standard seat map will let you know if a seat is available, but it won't tell you how the screen will look from that seat. How far away is it? How far to the side will the view be? Will the row in front obstruct the view? For many visitors, particularly those who are concerned about comfort or accessibility, it is only after they get to the theatre that they find out the answers to these questions. The idea on which Seatline Kolkata was based was that picking a seat should be more like previewing a venue than merely choosing a square on a diagram. The setting for this idea was Kolkata's unique cinema culture, which includes heritage theatres, modern multiplexes, luxury auditoriums and various different room shapes. What it does Seatline Kolkata is an experience which puts the guest first and which is non-binding. People are able to look at six venue profiles in Kolkata, select a preview date and time, check the availability of seats, and from any available seat enter a measured 3D view. For each seat sightline figures are provided: Screen distance Horizontal offset Vertical viewing angle Screen angular width Forward-row clearance Overall rating: Exceptional, Great, Good, or Compromised The experience becomes native to the agent via WebMCP. A visitor can then ask: Get me a clear great sightline at Nandan tomorrow evening. The agent has the capability of searching the venue directory, examining the modelled seats, choosing a suitable seat, moving the Three.js camera to that seat's modelled eye point and then opening the seat summary. The visitor will still be in control and can continue to explore manually. Seatline doesn't reserve seats, handle payments, scrape ticketing websites, or take live inventory; the information about availability, prices, showtimes, and room dimensions is merely preliminary data. How I built it Seatline Kolkata makes use of Next.js, React, TypeScript and Three.js and has its deployment on Cloudflare Workers, the trailer media being stored in Cloudflare R2. WebMCP is implemented with five merchant-authored tools: ask_site search_venues inspect_seats select_preview review_summary The tools employ strict schemas and stable identities and make use of the same pure venue, seat-generation, availability and sightline functions as those used by the visible interface, which ensures that the agent's results match those on the visitor's screen. The camera and the metrics are based on the same geometry model; the eye point is determined by the selected seat and this same point is then used when calculating distance, angles, screen width and clearance. This ensures that the experience remains measurable rather than merely decorative. Challenges I ran into The main difficulty was ensuring that there was a single source of truth among the three systems: the semantic seat map, the Three.js scene and the WebMCP tool execution. When an agent made a selection, it had to update the controls, the seat state, the camera mode and the summary dialogue without setting up a second data model. I also needed a form of seat availability that was deterministic and varied from venue to venue, from date to date and from showtime to showtime while ensuring that each venue's default seat remained available. The camera position had to appear physically reasonable without being artificially raised in order to get a better view. In the end, it was necessary for the project to keep it as a static page that loaded quickly, at the same time as storing the large original trailer files in R2 rather than converting them. Accomplishments that I'm proud of I am proud that Seatline Kolkata turns a familiar seat map into a tool which enables spatial decision-making. Rather than just describing the page, the agent carries out the same preview logic that a person would use and then passes the result back to the visual interface. I am likewise proud of the clarity of the product boundary since Seatline is useful before a booking is made without pretending to be a ticketing system or stating that it cannot verify the inventory. What I learned I discovered that good WebMCP tools should convey user intent rather than revealing their internal implementation details; for example, "Find a great seat" is more useful than requesting the agent to directly manipulate the rows and columns. I found that collaboration between humans and agents is most effective when the agent carries out the structured discovery and the person is in charge of visual judgment; the agent can reduce the number of options while the person decides if the view is acceptable. What's next for Seatline Kolkata I would also like to collaborate with the cinemas that are taking part to substitute the representative geometry with the approved auditorium dimensions, include more detailed accessibility annotations, and provide support for both Bengali and English. By means of its authorised partners, Seatline would eventually be able to connect to reliable availability feeds while still maintaining its transparent preview-first experience, and features such as optional secure sign-in, saved comparisons, and the ability to view seats side by side would also increase the product's usefulness for returning visitors. Prism starts with the job to be done. What it does Prism combines a purpose-aware evaluation dashboard with an open-source, local-first browser companion. A person selects Commerce, Project Operations, Content Editor, or defines a Custom contract. That contract states the intent, expected capabilities, and the action that must remain human-approved. The browser companion then runs on the target page, discovers its live WebMCP tools, executes only selected checks, and records schemas, annotations, timing, and privacy-preserving before-and-after evidence. Prism maps that evidence to four dimensions: purpose coverage; contract quality; observable mutation proof; and runtime hygiene. Every score includes journey-level evidence and a repair that can be tested again. A weak cart mutation, for example, does not merely lose points: Prism explains that the runner could not verify the visible state change and recommends returning a state revision plus a read-back check. A DOM digest proves that something visible changed, but not that the semantic change was correct. Prism therefore distinguishes visible-state evidence from stronger tool read-back evidence and does not claim either one proves the target application's human-approval policy. Accomplishments that we're proud of Purpose-specific contracts prevent irrelevant tool count from dominating the score. Every deduction is tied to visible evidence and an actionable repair. Why this use case is a strong fit for WebMCP WebMCP's defining move is that the page declares what an agent may do. That makes the page the right place to put a rule — and the natural unit of a rule is not a permission, it is a phase . A governed proceeding is a state machine with sharp edges: you may seal a position now and not open it; you may open it now and not seal a new one; a ruling may be ratified only once and only from Ruling. Every other agent integration expresses that as validation — a tool that exists always and refuses most of the time. WebMCP lets us express it as existence . In Commit, commit_to_round is registered and reveal_in_round is not. Advance, and commit_to_round is gone — unregistered by aborting its AbortSignal , not hidden, not stubbed, not returning an error.
