# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Teach a website new agent tools by demonstrating once. Like Comment Story Updates Inspiration Web agents are often forced into two extremes: fragile visual automation that guesses where to click, or fixed APIs that only expose workflows developers anticipated in advance. We asked a different question: what if a website could learn a new agent tool from a human demonstration? People already teach coworkers by showing a task once. RoutineForge brings that interaction to the web: the human demonstrates intent inside the real product, the application records the underlying business actions, and WebMCP turns the reviewed routine into a reliable tool an agent can discover and invoke. What it does RoutineForge is a WebMCP-native commerce operations workspace with Home, Orders, Products, Customers, Analytics, and Marketing. Its central feature is Routine Studio: A merchant selects Record workflow . They set a date range and market, select metrics, generate a report, and save it. RoutineForge captures five typed, verified semantic actions—not clicks or selectors. The merchant reviews the trace and chooses which values the agent may supply. They publish the routine as generate_weekly_report . An agent discovers and calls the new WebMCP tool with different inputs. The live page follows the execution and returns a report ID, URL, summary, and five verification receipts. The app also exposes ten atomic WebMCP tools for dashboard state, orders, inventory, customers, campaigns, analytics filters, and reports. The demonstrated routine becomes the eleventh tool. Why WebMCP A reporting API could return numbers, but it would miss the shared, visible teaching surface between a person, an agent, and the application. With WebMCP, the human UI and agent tools use the same business actions, validation rules, state, and feedback. The agent does not reverse-engineer the DOM, and the developer does not maintain a second integration that can drift away from the product. RoutineForge also uses WebMCP dynamically. The site begins with ten developer-defined tools. After a person demonstrates and approves a routine, the page registers a new composite tool at runtime. This explores a future where a website's agent interface is shaped safely through use, not limited to a static tool catalog. How we built it RoutineForge is a client-only React and TypeScript app with no login, backend, API key, or third-party dataset. At its core is an Action Registry of versioned definitions. Each definition includes a JSON Schema, effects, input validation, execution logic, and post-execution verification. A shared Action Bus runs the same definitions for human UI events and WebMCP calls. The recorder stores action IDs, versions, typed inputs, structured outputs, sources, timestamps, and verification evidence. It never records coordinates, screenshots, CSS selectors, or generated JavaScript. The Routine Compiler accepts only registered actions. Every binding must be a demonstrated literal, a reviewed routine input, or a prior step output. The Routine Runner resolves bindings, validates each step, stops safely on failure, and returns structured receipts. The app feature-detects document.modelContext.registerTool() and registers ten atomic site tools. Publishing a taught routine registers generate_weekly_report with its own JSON Schema and verified execution handler. Published routines persist in IndexedDB and re-register after refresh; Reset demo restores deterministic seed data. Challenges The hardest problem was choosing the right abstraction boundary. Raw click recording looks general but is fragile and difficult to verify. A semantic action layer requires deliberate product architecture, but it survives UI changes and produces meaningful evidence. Dynamic publication also had to remain safe: recorded data or agent input can never become executable code. We solved that with a deliberately small binding language and a compiler that references only registered, versioned actions. Finally, agent activity needed to remain legible to a human. RoutineForge synchronizes the visible workspace with each execution and shows step-level receipts in the same interface. Accomplishments Ten atomic WebMCP tools plus a human-taught composite tool registered at runtime. One semantic execution layer shared by human interactions and agent calls. Typed validation and verification at every action boundary. No selectors, coordinates, screenshots, or generated code in recorded routines. Visible synchronization between agent execution and the human dashboard. A public, deterministic deployment with automated tests and no credentials required. What we learned Agent-native design is not simply adding tools beside an interface. The strongest experience comes from making the human UI and agent interface two views over the same semantic application model. Demonstration alone is not authorization; the human review step transforms a trace into a contract. Verification belongs inside each action definition, so composite routines can remain trustworthy. What's next Next we would generalize the compiler across all registered actions, add a visual routine editor, controlled branches and approval checkpoints, versioning and rollback, dry runs, audit logs, and a developer SDK. Our long-term vision is a web where developers provide safe semantic building blocks, people teach the workflows that matter to them, and agents execute those workflows transparently in the applications where work already lives.
