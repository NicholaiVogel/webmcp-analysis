# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

The agent would change a file and I'd immediately think, wait, what else is using this? Then I'd start grepping through the repo myself, trying to figure out what might have been affected. Sometimes I'd trust what the agent said, but I never really liked having to. That was basically the reason I started this project. I wanted to be able to see the blast radius of a change instead of just being told what it was. Then I came across the WebMCP spec and something clicked. What if the graph itself was the thing the agent and I shared? Instead of the agent explaining a dependency graph in a chat message, it could actually show me the graph on screen. I could look at it, click around, and the agent could interact with that same graph. That felt much more useful. How it got built The core of it is actually pretty simple. I use ts-morph to walk through a TypeScript repo and build the import graph. Then a basic BFS handles questions like: What depends on this file? There is deliberately no AI involved in that part. An AI writing code and an AI I'm talking to are really two different things. But they don't need two different interfaces. After that came cycle detection, switching the graph to another GitHub repo, and eventually a propose and approve flow for changes. At that point, a read-only graph didn't feel like enough anymore. The part that ate my whole evening React Flow wouldn't draw a single edge. The nodes showed up perfectly. They were just floating there with absolutely nothing connecting them, which is a pretty bad look for a dependency graph. I spent way too long checking the data, handle IDs, edge configuration, and rewriting parts of the implementation. Eventually I found the actual problem. React Flow uses ResizeObserver to measure nodes before figuring out where edges should start and end. In my setup, that measurement wasn't happening properly. The fix was surprisingly simple. I gave the nodes a fixed size and explicitly defined where the handles were. Suddenly all the edges appeared. It was one of those bugs that takes hours to understand and about two minutes to fix once you finally know what is happening. It also taught me not to immediately assume that something is wrong with the data just because the UI is missing something. Figuring out how ChatGPT actually sees it I thought getting an actual AI agent to use the tools would be the easy part. It wasn't. It wasn't actually opening my app as a live browser page. It was basically reading the static page and trying to figure out what the application did from that. Since the app is React, most of what I cared about doesn't exist in the initial HTML anyway. Once I explicitly opened the app through the browser, everything changed. Instead of guessing, the agent could actually interact with the page and call the tools I had built. It could get the same file list my backend calculated and even tell me which tests would be worth rerunning. That was probably one of the most useful parts of building the whole thing because it made the difference between an AI talking about a tool and an AI actually using one very obvious. What I actually learned The biggest thing I learned is that the AI part wasn't really the hard part. Most of the problems were normal software problems. A rendering library making an assumption about node measurements. A deployment having cold starts. A browser tool behaving differently from a web search tool. Two things having similar names but working in completely different ways. The WebMCP part was actually one of the more enjoyable pieces to build. You ask the agent something, it calls a tool, and you can actually watch the result happen on the screen. That feels very different from an AI giving you a paragraph explaining what it thinks is happening. And honestly, that's the part of CodeAtlas I like most. It isn't trying to replace the developer's understanding of the code. It gives the developer something concrete to look at while the agent works. Deterministic BALANCED Engine : Scores offers mathematically (25% cost, 25% reliability, 20% transit, 10% availability, 10% route experience, 10% org history). Like Comment Story Updates Inspiration Versailles is not just a monument. It is a place shaped by power, ambition, art, diplomacy and history. We wanted players to work out where and when they had arrived through observation and action, rather than turning pages or receiving answers from an AI. Our principle is simple: the player reasons; the agent supports, without taking over. What it does The Hall of Mirrors becomes an interface to time. The player restores five fragments: WITHDRAWAL → POWER → RUPTURE → MEMORY → INFLUENCE . Across 1623, 1682, 1789, 1837–1919 and 2026, the mechanics change with the historical role of Versailles: examine a map, letter and seal; match six royal orders to their recipients; find a concealed passage by observing the woodwork; arrange discovered objects into sequences; and connect evidence about the palace's changing function. The final mirror returns to the present. Versailles is no longer the seat of royal power, but its history gives diplomatic encounters symbolic weight. This is historical interpretation, not political endorsement. Why WebMCP matters WebMCP gives an external agent a bounded, structured view of actual game state. It does not have to guess progress from pixels or inspect unrestricted internal data. The game reports the current phase, discovered evidence, relevant errors and permitted assistance. Zero relevant errors means SILENT and refusal of a hint request. One permits NUDGE ; two or more permit GUIDE . Hints are selected by deterministic game rules, not freely generated by a language model. In the 1682 demonstration, an order goes to the wrong recipient. A real request_hint call returns a reading strategy, not the recipient's name. A later sequence error in 1919 produces a different method hint. The player makes the next choice. How we built it Native HTML, CSS and JavaScript ES modules support a pure state reducer and filtered public projection. The static game needs no account, backend, database or API key. Five tools are registered through document.modelContext.registerTool(): get_mission_state reads filtered state and assistance policy. inspect_evidence examines one to six discovered observations. request_hint requests policy-bounded help. compare_evidence compares two or three discovered observations. submit_hypothesis submits an available hypothesis to normal domain validation. JSON Schema describes inputs; runtime validation and abort signals enforce boundaries. Read tools do not change progress. A valid hypothesis may advance through the normal reducer, but cannot force success, bypass prerequisites or ask for hidden solutions. Challenges and what we learned The main challenge was making assistance useful without replacing historical reasoning. Each era needs a different puzzle, while the agent needs one coherent contract. Filtering discovered evidence, enforcing error thresholds and validating every action matter more than offering unrestricted context. We also kept filming evidence honest: cards labelled RECORDED TOOL RESPONSE are editorial layouts of actual recorded responses, not invented game UI or a simulated autonomous conversation. Filming begins at chapter checkpoints; the video is not an uninterrupted public playthrough. Validation and limitations The reviewed local candidate passed 97 automated tests . Eight boundary tests cover repeated errors, hidden evidence, prerequisites, cancellation, restart and final-fragment idempotence. After the contemporary visual replacement, 17 affected tests passed , and the arrival/welcome interactions were checked in Edge. There is no persistent save : reloading starts a clean game. Tool filtering is not source-code secrecy; the JavaScript remains inspectable. We do not claim measured learning outcomes or universal browser compatibility. Media and provenance The 2:40 jury film uses the author's approved English transcript, narrated by Charles through ElevenLabs . Historical illustrations are AI-assisted reconstructions, not archival photographs. Contemporary 2026 visuals in the prepared release use credited Official White House Photos by Daniel Torok , taken at Versailles on June 17, 2026. No endorsement is implied. Detailed credits and historical sources are included in the repository. Open source The project is released under the MIT License . The complete source code, assets, automated test suite and reproducible setup instructions are available in the linked public GitHub repository. What's next Broader player testing and accessibility refinement, while preserving the central boundary: assistance should help the player reason, not remove the reason to play. One city. One hospital. One chance. GRIDFALL turns WebMCP into a real-time crisis room where a human and an AI agent diagnose cascading failures and restore ICU power together. Like Comment Story Updates Inspiration Critical infrastructure is not a collection of isolated switches. A hospital depends on power, protection systems, data, water, transport access, emergency crews, and decisions made elsewhere in the city. During a cascading failure, the difficult part is not clicking a button—it is understanding which action is safe before the remaining time and redundancy disappear. Most browser agents face an uncomfortable choice: infer important state from pixels and page text, or receive enough authority to act without a meaningful human checkpoint. We built GRIDFALL to explore a third model: the website exposes structured, purpose-built capabilities to an agent, the agent helps a person reason under pressure, and the person remains responsible for consequential actions. What it does GRIDFALL is a real-time city-grid crisis simulation centered on one urgent objective: restore protected power to St Anne ICU before its generator reserve expires. Each mission draws one of 100 validated incident configurations. After a short pre-blackout countdown, infrastructure across the city begins failing. The operator sees an interactive top-down map of power, protection, data, road, water, and emergency-response dependencies, but the correct recovery sequence is never revealed. A WebMCP-capable agent can inspect the live city state, check the hospital, and review the operations that are currently possible. It can then explain the likely benefit, time cost, and systemic risk of one action. In Challenge mode, the agent can only propose the operation: GRIDFALL queues it in Mission Control and waits for the human operator to authorize or reject it. The city does not change until that approval happens. Every authorized decision advances time and can change several connected systems at once. A seemingly useful action may remove telemetry, block an ambulance corridor, consume the only mobile battery, or reconnect the hospital to an unresolved fault. If the remaining recovery path is destroyed, the mission ends immediately instead of making the player wait for a meaningless countdown. Why WebMCP GRIDFALL is designed around collaboration that would be fragile or impossible through ordinary screen reading. The map is optimized for people; the WebMCP tools provide the agent with the same live situation as structured, typed data. This eliminates guesswork about labels, colors, hidden panels, and changing visual state. The experience separates observation, recommendation, and authority. Read-only tools let the agent build situational awareness. The action tool creates a visible proposal. The human sees its consequences and makes the final decision. That boundary is the product, not an afterthought. This pattern applies beyond a game. Industrial dashboards, operations centers, financial workflows, and administrative systems can expose meaningful capabilities to agents while keeping high-impact actions inspectable and under human control. How we implemented WebMCP GRIDFALL registers six browser-native tools with document.modelContext.registerTool : get_city_state returns the current incident, infrastructure status, field clues, and recovery progress. inspect_hospital_status returns ICU demand, protected supply, generator reserve, patients, telemetry, access, cooling water, and active blockers. list_grid_actions returns the currently available operations with their time cost, benefit, risk, and current availability. take_grid_action creates a human-reviewable proposal in Challenge mode. start_random_incident draws a validated mission and starts the pre-blackout sequence. reset_mission safely returns the simulation to standby. The tools never expose the hidden solution or complete dependency order. The agent must reason from observable evidence, just like the operator. Tool results include structured content so the client can use state reliably instead of parsing prose. How we built it GRIDFALL is a client-side React 19 and TypeScript application built with Vinext and deployed on ChatGPT Sites through Cloudflare Workers. The simulation engine models incident generation, dependencies, action resolution, irreversible consequences, win conditions, and early failure detection. The interface renders the city map, live hospital metrics, recovery history, onboarding, Czech and English localization, audio, and the human-authorization flow. We also built a deterministic audit that exercises the complete catalogue of 100 missions and checks that every scenario is solvable, non-trivial, and consistent with critical rules such as battery exclusivity and dependency ordering. Challenges we faced The hardest challenge was deciding how much information to expose. If a tool returned the hidden sequence, the agent would merely read the answer. If it returned too little, the agent would be forced back into visual guessing. We iterated on the schemas until they described evidence, risks, and current possibilities without leaking the solution. We also had to make infrastructure consequences feel logical. Early versions allowed trivial action sequences or visually implied connections that did not match the game rules. We repeatedly rebuilt the dependency graph, map layout, failure conditions, and action descriptions so the simulation communicates why a decision helped or harmed the ICU. Finally, we treated human authorization as a real state boundary. An agent proposal must not silently mutate the simulation, become stale, or be reported as completed before the operator approves it. Accomplishments A complete, playable crisis simulation rather than a single-purpose tool demo Six working WebMCP tools with structured outputs and clear authority boundaries 100 automatically validated incident configurations Explicit human authorization for consequential agent actions Immediate, explainable consequences across interconnected city systems An interactive map with traceable power, protection, data, and access relationships English and Czech localization, onboarding, accessible controls, and sound design A public MIT-licensed repository with no API keys, account, database, or custom agent backend required What we learned The most important lesson was that a tool schema is part of the user experience. Good agent integration is not just a function name and JSON input; it requires carefully designed observability, understandable consequences, and an explicit model of who is allowed to do what. WebMCP made it possible to build one interface for two different strengths: humans understand the spatial story and remain accountable, while agents can rapidly compare structured state and dependencies. The result is stronger than either a conventional dashboard or an autonomous agent acting alone. What's next We would expand GRIDFALL with additional cities, incident families, replayable decision audits, accessibility modes, and scenario-authoring tools for training. The same architecture could also support safe demonstrations using real or synthetic operational telemetry while preserving the proposal-and-authorization boundary at the heart of the project. CommonMesh is my attempt to split those responsibilities clearly. What it does CommonMesh runs one fixed demo: Saturday Community Day at Riverlight Hall in Gothenburg. If the agent tries to commit too early, CommonMesh returns APPROVAL_REQUIRED and records the failed attempt in the activity trail. The trust layer for the agent-native web—test WebMCP tools, gate consequential actions with human approval, and record verified, tamper-evident outcomes with real undo where supported. Like 1 Comment Story Updates OpenAgentLab + Action Ledger What happens when a website stops being something an AI agent merely reads and becomes something the agent can actually operate? WebMCP makes that future possible by allowing websites to expose structured capabilities directly to agents. I built OpenAgentLab + Action Ledger to explore the next problem that immediately follows: How do we make agent actions trustworthy when they can change real application state? It is a developer workbench for observing, testing, governing, and safely executing agent-native web actions . The included Acme Issues application is intentionally simple. The interesting part is not the issue tracker itself; it is the infrastructure around an agent deciding whether to search, inspect, close, or permanently delete an issue. The project turns agent actions into something humans can preview, approve, verify, audit, evaluate, and—in reversible cases—undo . Inspiration Web interfaces were designed around an assumption: a human sees the interface, understands the consequences, and clicks the button. WebMCP changes that interaction model. An agent can discover a capability such as: search_issues get_issue close_issue delete_issue and invoke it directly from the website. That is powerful, but it raises a deeper question. If an agent can call delete_issue , a confirmation dialog alone does not create a trustworthy system. We also need to know: Did the agent choose the correct tool? What exactly will change? Is the operation reversible? Did a human actually authorize this specific action? Did the underlying resource change after the preview? Could a retry accidentally execute the mutation twice? Can we verify what happened afterward? Can developers detect a dangerous tool contract before shipping it? That became the core idea behind OpenAgentLab. Instead of treating agent tooling as a collection of API endpoints, I wanted to treat it as a governed action lifecycle . What it does OpenAgentLab exposes four native site capabilities through WebMCP: search_issues get_issue close_issue delete_issue Read operations are exposed as read-only tools. Consequential operations work differently. When an agent invokes a write tool, the mutation does not execute immediately . The server creates an Action Ledger proposal containing the target resource, reason, risk, declared side effects, reversibility, and a before/after preview. The agent receives a sanitized response indicating that the action is awaiting human confirmation. The approval credential itself stays on the human UI path rather than being returned to the agent. The user can then review exactly what is about to happen and choose Reject or Approve & execute . The Action Ledger The heart of the project is a state machine that explicitly separates intent from effect : PROPOSED ↓ PREVIEWED ↓ AWAITING_CONFIRMATION ↓ APPROVED ↓ EXECUTING ↓ EXECUTED ↓ VERIFIED Rejection, failure, and rollback are explicit branches rather than hidden side effects. Invalid lifecycle transitions are rejected. Every ledger entry records information such as the tool and schema fingerprint, redacted arguments, reason, risk, affected resources, declared side effects, preview, confirmation policy, execution result, provenance IDs, and transition history. Ledger entries and transitions are hash-linked to their predecessors, making accidental history modification detectable. I deliberately describe this as tamper-evident rather than tamper-proof . The project does not pretend a locally controlled application provides cryptographic non-repudiation. Human control is enforced at the execution boundary One of the most important design decisions was making approval a server-side execution requirement , not simply a UI state. For guarded operations the runtime: requires the action to be in AWAITING_CONFIRMATION ; validates a high-entropy approval credential; verifies its persisted hash; compares credentials safely; re-checks the resource revision against the preview; prevents duplicate mutation through idempotent execution behavior; executes the capability; verifies the resulting state. This also protects against stale previews . If an issue changes after the human saw the preview but before approval reaches the execution boundary, the mutation is rejected instead of applying an obsolete decision. Real undo, not cosmetic undo close_issue is explicitly modeled as reversible. After successful execution and verification, OpenAgentLab stores the previous issue state. A user can choose Undo , at which point the runtime checks that the resource has not changed unexpectedly and restores the previous state while recording a ROLLED_BACK transition. delete_issue , by contrast, is explicitly irreversible and never advertises undo. That distinction is visible both to the human and in the tool contract exposed to the agent. Testing the agent contract itself One of the ideas I am most excited about is treating tool descriptions as executable safety infrastructure . The flagship scenario is: “Clean up old resolved issues.” The expected operation is close_issue , while delete_issue is explicitly forbidden. The project can intentionally expose a weak delete_issue contract: Remove an issue from the issue tracker. For an ambiguous cleanup request, that contract can lead to selection of the destructive tool. OpenAgentLab then lets the developer apply an improved contract that makes permanence explicit and tells the agent to prefer close_issue unless permanent deletion was specifically requested. The exact same scenario can be rerun and compared against the previous result. This demonstrates something I learned while building the project: For agents, a tool description is not documentation sitting beside the product. It is part of the product's control surface. A vague contract can become a safety bug. OpenAgentLab therefore evaluates observable evidence such as selected tools, forbidden-tool usage, confirmation requirements, execution outcomes, and ledger state—without depending on private model chain-of-thought. How I built it I kept the architecture intentionally separated into clear trust boundaries. Frontend The workbench is built with React, TypeScript, and Vite . It provides: a Tool Explorer; raw JSON Schema inspection; risk, side-effect, scope, confirmation, and reversibility metadata; behavioral Scenarios; baseline/current evaluation comparisons; Runs and observable traces; the Action Ledger; human confirmation with before/after diffs; a live recent-agent-activity feed; reversible-action undo. WebMCP src/client/webmcp.ts is the only browser-standard-specific boundary. When WebMCP is available, the application registers its four capabilities using: document.modelContext.registerTool(...) The same validated server runtime is used whether an action originates from the application UI or WebMCP. That separation was intentional: the rest of the domain does not need to depend on an evolving browser API. The project also remains usable as a normal workbench when native WebMCP discovery is unavailable. Backend and domain The backend uses Fastify and Node.js . Zod provides runtime validation for tool definitions, scenarios, ledger records, application state, and API inputs. The domain layer contains the schemas, deterministic evaluation logic, fixtures, and Action Ledger state machine. The server runtime owns the actual trust boundary: proposing actions, generating previews, checking approvals, validating revisions, executing capabilities, verifying effects, and managing rollback. The current demo uses a replaceable JSON-backed store with serialized transactions and atomic file replacement. Testing and deployment I built the project to be reproducible rather than demo-only. Review AI-proposed visual edits, protect brand-critical elements, and apply only human-approved changes through a live WebMCP workspace. Like Comment Story Updates FrameGuard is a human-in-the-loop visual change-review workspace for teams that want agent speed without surrendering brand control. Inspiration AI design tools are fast, but they can mutate protected logos, legal copy, and approved layouts without a clear audit trail. FrameGuard makes every proposed visual change explicit, reviewable, and reversible. What it does An agent inspects the visible document and creates a structured proposal. Each change appears immediately in the shared UI with its target, rationale, before/after values, status, and compatibility feedback. Protected elements are visibly blocked. A human can approve changes individually; only approved, compatible changes can be applied. Rejection leaves committed state untouched, undo restores the previous revision, and a review receipt captures the decision trail. How WebMCP is used FrameGuard registers focused page tools against one state authority: inspect_document , create_proposal / propose_adaptation , set_change_approval , apply_approved_changes , reject_change_set , undo_last_change_set , and export_review_receipt . Tool availability follows page state, inputs use bounded schemas, validation fails closed, and every successful call mutates the same React store the human sees—so agent execution and UI never diverge. Human + agent The agent proposes and explains; the human reviews and authorizes. Protected changes cannot be approved or applied. Drafting and preview never alter the committed canvas. How we built it React 19, TypeScript, Vite, Vitest, Playwright, GitHub Pages, and Chrome WebMCP. The project runs entirely in the browser and transmits no review data. Challenges and learning The hardest part was preserving atomicity across proposals, protected targets, partial approvals, undo, and dynamic tool registration. We solved this with deterministic domain functions, a single external-store authority, deep-frozen snapshots, microscopic commits, and 64 unit/component plus 4 end-to-end tests.
