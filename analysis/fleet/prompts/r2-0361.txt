# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Starshape is a shared semantic sky where browser agents choose and connect concepts via WebMCP, revealing the associations that recur, fade, and reappear across agents. Like Comment Story Updates A past starshape A starshape being drawn Inspiration Starshape started with a simple question: What happens if we give many different browser agents the same stars and let each one decide what constellation it sees? Knowledge graphs usually represent relationships that humans, databases, or algorithms have already decided exist. We wanted to reverse that idea. Instead of building a graph for agents to navigate, we wanted to build a shared space where the agents create the graph simply by interacting with it . That led to Starshape: a living semantic observatory where concepts are represented as stars, agents connect the concepts that feel meaningfully related, and those choices accumulate into a shared public sky. There are no constellations until something looks up. What it does Starshape contains a curated vocabulary represented as a field of stars. Through WebMCP, a browser agent can invoke observe_sky , which gives it a bounded random selection of concepts from that shared vocabulary. There is no correct answer and no semantic scoring system. The agent chooses exactly six concepts based on whatever relationships seem meaningful or salient to it, connects them into a small constellation, and submits that structure through trace_constellation . The human sees the interaction happen live. The selected stars flare, the relationships draw across the sky, and the completed constellation becomes part of the shared graph for everyone else. Every node and connection has history. Associations that repeatedly appear grow more prominent. Their visible brightness also decays with time, allowing unused relationships to fade while frequently rediscovered ones remain luminous. An old relationship can effectively wake back up when agents begin discovering it again. Starshape does not claim to expose hidden model reasoning or objectively measure how AI "thinks." It is an observational environment for seeing what semantic associations repeatedly emerge when independent agents operate under the same constrained protocol. Why WebMCP Most agent-enabled websites follow a familiar pattern: Human wants something → agent uses tools → task gets completed. We wanted to explore a different relationship. In Starshape, the agent's interaction with the website is itself the phenomenon being observed. The human invites an agent to look at the sky. The page gives the agent a structured semantic environment through WebMCP. The agent makes its own choices. The human watches those choices appear physically on the page, and the result becomes persistent shared state that future visitors and agents encounter. WebMCP also lets Starshape remain agent-independent . The backend does not call a specific LLM provider and ask it for associations. Instead, the browser becomes the boundary: whichever compatible agent the visitor brings can participate directly through the same structured tools. That turns the web page into a shared experimental surface rather than a frontend wrapped around one model API. How we built it Starshape is intentionally small behind the scenes. The frontend is built around Three.js , creating a realtime 3D semantic star field with persistent nodes, animated connections, camera movement, and time-decayed luminance. The browser exposes three WebMCP tools: observe_sky — receives a server-issued field of candidate concept-stars without exposing the existing collective graph. trace_constellation — commits six selected concepts and the connections between them. read_sky — becomes available only after the current session has committed a constellation, allowing the agent to inspect the brightest stars and strongest current associations in the shared sky. That ordering is deliberate. Every agent must make its first constellation blind , without being primed by what previous agents selected. Only after its own trace is locked in can it look at the accumulated sky and see what other agents have seen. The backend maintains one authoritative shared sky. Observations are short-lived, one-use receipts. Agents cannot submit arbitrary words or prose; they can only reference concepts that were actually issued by the server. When a constellation is accepted, the backend atomically records the trace, increments its nodes and edges, and broadcasts the event to connected visitors so the constellation appears live across browsers. Historical counts never decay. Only their visual luminance does. That means Starshape can remember everything while still allowing its visible sky to forget. Challenges we faced The largest challenge was designing an interaction that genuinely depended on WebMCP instead of simply adding agent controls to an ordinary application. We wanted the agent to be a participant, not an invisible automation layer. WebMCP can make agent activity visible, spatial, collaborative, and persistent . We also found that a very small structured tool surface can produce surprisingly open-ended behavior. IMC Guardian is a tool designed to provide pilots with quick notifications and fast access to information about rapidly changing weather conditions using WebMCP. Like Comment Story Updates About the project IMC Guardian is the stretch project out of the two projects I built for the WebMCP Challenge. It is an aviation weather decision-support prototype for a solo pilot or private jet crew flying a longer route. The main goal is to save time and add a second pair of eyes when weather conditions begin changing. Pilots do not have a shortage of data. They have aircraft instruments, radar, dispatch, ATC, forecasts, advisories, and procedures. The harder problem is recognizing the exact moment when the picture no longer supports the plan. IMC Guardian is designed as an independent challenge layer, not a confirmation machine. A pilot can ask AI to check a proposed route in plain English. Fifteen site-owned WebMCP tools give the agent structured access to the route, airport observations, forecasts, advisories, risk factors, nearby alternates, configurable notifications, validated alerts, incident evidence, and decision options. The application does not tell a pilot that a flight is safe, issue a clearance, direct a maneuver, or replace an official briefing. It organizes the evidence and catches important changes, while the pilot remains in control. Inspiration The idea came from thinking about a long-route solo pilot or private jet pilot trying to keep up with weather while also managing everything else involved in a flight. Conditions can change quickly, especially ceilings and visibility. There can also be a lot of noise when the pilot only needs to know whether an important personal limit has changed. I wanted to see whether WebMCP could let a pilot ask one clear question, rapidly inspect the weather along the route, and configure a focused notification instead of repeatedly checking several different panels and sources. The phrase that kept making sense was “a second pair of eyes.” The interaction is almost as simple as asking, “Guardian, what do you see?” The AI helps watch, organize, and challenge the current picture. It does not become the pilot. Why this matters We added five investigation-backed case studies because the problem is real. Delta Flight 56 encountered severe turbulence in July 2025 after the crew had already discussed and adjusted around weather. The NTSB says the upset lasted about 2.5 minutes, two crew members were seriously injured, and the flight diverted to Minneapolis. Delta Flight 175 encountered a rapidly developing convective cell near Atlanta in 2023. The NTSB found that the low-precipitation buildup was not apparent on the aircraft's weather radar or ATC scopes. Four people were seriously injured and thirteen received minor injuries. The site does more than display that case. A WebMCP evidence replay loads the Delta 175 final-report record, reconstructs the weather timeline, compares the crew's concern with the recorded outcome, and explains what the evidence cannot prove. At 22:30 UTC the crew said conditions were about to get worse. Severe turbulence followed at 22:31:15 UTC. The result is deliberately precise: concern supported, action not judged. The NTSB found that near-real-time Graphic Turbulence Guidance Nowcast capability could have provided earlier awareness to secure the cabin, but the report does not establish that a different route choice or this prototype would have prevented the encounter. Singapore Airlines Flight 321 diverted to Bangkok in 2024 after an extreme acceleration change over developing convective activity. Air Europa Flight 45 diverted to Natal, Brazil after severe turbulence injured dozens of people. Air France Flight 447 is the foundational sensor-disagreement case. The BEA identified pitot-probe icing, erroneous speed indications, a stall, and impact with the ocean. IMC Guardian does not claim it would have prevented any of these events. The cases show why a concise, independent evidence check can matter when weather, workload, and human-machine interaction collide. What it does For the reproducible demonstration, a VFR pilot proposes a flight from Tampa to Tallahassee. Conditions deteriorate along the northern part of the route, the destination reports IFR, and a G-AIRMET for IFR overlaps the corridor. The agent can inspect the evidence, explain why the route risk increased, find comparatively better nearby airports, and compare delaying, diverting, or canceling. The pilot can also configure Second Pair of Eyes to watch a specific metric. In the demo, a 1,500-foot ceiling limit is crossed. WebMCP checks the threshold, forecast context, and overlapping advisory before presenting the alert. The project also includes a live Cesium globe with NASA satellite clouds, Apple WeatherKit context, and a Tampa-to-JFK weather corridor sampled across nine points. That gives the pilot and the agent a fast visual picture of changing conditions ahead. The globe stays focused on Florida so the demonstration supports the route instead of becoming a generic spinning-earth effect. The top of the experience now explains the interaction in three steps: ask once, let WebMCP double-check, and keep the final decision with the pilot. How we built it We built a React and Vite application with a deterministic aviation-risk engine and fifteen imperative WebMCP tools registered through document.modelContext.registerTool . The user interface and the agent share the same route, assessment, alternatives, route watch, notifications, validation, historical replay, decision state, and live tool trace. NOAA Aviation Weather Center is the aviation-data foundation. Its data is reached through a scoped, cached Vercel server-side proxy with a custom user agent. Apple WeatherKit provides supplemental current conditions, cloud cover, temperature, precipitation, and wind. Its signing credentials stay on the server. CesiumJS provides the interactive 3D Earth. NASA EOSDIS GIBS supplies current GOES-East ABI GeoColor satellite imagery through a Web Map Service layer. The globe can animate roughly 90 minutes of recent satellite frames, focus on Florida, and display the demonstration route. Apple WeatherKit adds twelve global samples and nine cached checkpoints along the Tampa-to-JFK corridor. The frontend also includes a live natural-language demonstration using GPT-OSS 120B on Groq. The model interprets the pilot's sentence and chooses an ordered subset of allowlisted tools. The browser executes the actual WebMCP tools and shows every step, along with model token usage. Weather facts come from application tools and identified data sources, not the model's memory. The live session now exposes a safe server receipt so judges can see the complete connection path. It shows the browser request to /api/agent , the server-side call to Groq's OpenAI-compatible chat-completions endpoint, the selected model, response mode, prompt size, 10-tool allowlist, request receipt, latency, and token usage. The Groq credential and hidden system instruction remain on the Vercel server and are never returned to the browser. The page also links Groq's API reference, OpenAI's gpt-oss announcement, and the public server implementation. We created a clearly labeled scenario mode so the judging flow stays reproducible even when live weather changes or a source is temporarily unavailable. Scenario values are never presented as current reports. We also created a historical evidence mode from the NTSB Delta 175 final report and public docket. Three WebMCP tools load the case, compare the documented concern with the recorded event and final findings, and expose the replay's limits. It is a structured investigation replay, not certified live telemetry. Challenges The hardest product challenge was deciding what the system must not do.
