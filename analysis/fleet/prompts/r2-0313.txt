# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they

problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

This is TrustFill. It's a grant application form that an AI agent can fill out for you — but it's built so the agent can never submit anything sensitive without you confirming it first. Like Comment Story Updates Inspiration WebMCP's whole premise is that agents shouldn't have to guess their way through a page — a site can just declare what an agent is allowed to do. Reading Chrome's WebMCP tool security guidance, one line stuck with us: agents are powerful precisely because they act with the user's session already open, which is also exactly why that power needs a boundary. Most of the WebMCP demos we saw were about letting agents do more — search faster, check out faster. We wanted to explore the opposite question: could WebMCP be the thing that lets an agent do less, on purpose, in exactly the right places? High-stakes forms — grant applications, insurance claims, legal filings — are where people are least willing to hand an agent full control. That felt like the right place to test whether "trust" could be a structural property of a tool, not just a line in a system prompt. What it does TrustFill is a grant application — the Riverbend Micro-Grant form — that a WebMCP-aware agent can fill out on your behalf, with a hard boundary baked into the tools themselves. For low-risk fields (business name, address, EIN, founding date), the agent fills them in directly. For anything with real consequences — annual revenue, requested amount, legal certifications — the agent cannot fill them at all; the tool it would need rejects the call outright and requires it to flag the field with a reason instead. The application cannot be submitted while any flagged field is unresolved. A live audit trail records every action, agent or human, in order, so nothing happens invisibly. The result: an agent that's genuinely useful for the boring 80% of a form, and structurally incapable of guessing on the 20% that matters. How we built it The frontend is React + Vite with Tailwind for styling, and all state lives in a single reducer-driven form model — no backend needed for the demo. Six tools are registered through the real WebMCP API, document.modelContext.registerTool , each with an AbortController for clean unregistration on unmount: get_form_state , fill_field , flag_uncertain , request_human_review , submit_form , and get_audit_trail . The two read-only tools carry readOnlyHint annotations so an agent knows they're always safe to call. The critical piece is inside fill_field itself: it checks each field's risk tier and rejects the call for high-risk fields before it ever touches state — the boundary lives in the tool's own code, not in a prompt telling the agent to behave. We registered the deployed Netlify domain for Chrome's WebMCP origin trial so the API is genuinely available to any visiting browser or agent in production, added /.well-known/webmcp and llms.txt so the site is discoverable before an agent even loads the page, and built an explicit demo-mode fallback (with console diagnostics reporting mode=real-webmcp vs mode=demo ) so the concept is visible even in browsers without WebMCP support yet. Challenges we ran into Getting from "works locally with a Chrome flag" to "works for a real visiting agent in production" surfaced problems we didn't expect. The WebMCP API surface itself has been shifting ( navigator.modelContext moved to document.modelContext ), so we had to make sure we were building against the current spec rather than a stale example. Production availability required registering for Chrome's origin trial, and our first token was scoped as third-party by mistake — a mismatch that silently kept the site in demo mode until we re-registered with the correct scope. We also had to learn the hard way that not every "browser agent" actually uses WebMCP tool discovery — some general-purpose browsing tools simulate a human clicking through the UI instead, which looked like a WebMCP failure at first but was really a different agent entirely. Most importantly, testing surfaced a real bug where the Submit button's enabled state wasn't reading from the same blocker logic as the submit_form tool — meaning the UI could have let someone submit with unresolved high-risk fields, which would have quietly undermined the entire premise of the project if we hadn't caught it. Accomplishments that we're proud of The core guarantee isn't a claim, it's enforced in code: fill_field structurally cannot touch a high-risk field, and submit_form and the Submit button now share one blocker calculation, so there's no path to submitting with something unresolved. We verified the full six-tool integration independently with a WebMCP tool inspector showing real, callable schemas — not just our own word for it. And the live audit trail means every decision, whether made by the agent or by the human reviewing it, is visible and traceable rather than happening behind the scenes. What we learned The biggest shift in thinking: safety for agentic web apps doesn't have to live in a prompt at all — it can live in the shape of the tool contract itself, which is a guarantee no amount of clever prompting can quietly break. We also learned that the gap between local, flag-enabled WebMCP testing and real production behavior is bigger than the docs make it sound, and that "an agent used my site" can mean two very different things depending on whether it discovered structured tools or just simulated a human — a distinction worth designing and testing for explicitly, not assuming. Longer term, we'd like to publish the gating pattern itself — reject-by-default on high-risk tool calls, shared blocker logic between tools and UI — as a small reusable library other WebMCP-based forms could adopt directly. The guardrails are the active ingredient, and prompts are guardrails an AI can be talked out of. WebMCP made a different kind possible: architecture . The page owns the tools, so the site decides what the AI may know, say, and be. Ask it for the answer and it refuses, leading with the reason (the answer is in no tool it can call), then asks one smaller question instead. Capability is the guardrail. advance_module does not exist until the gate opens; it materializes in the agent's tool list when mastery is earned. Exam mode revokes the coaching toolset entirely: train aided, test unaided. On screen, the Tool Roster reads 13 tools with the gate closed, 15 when it opens, 2 during the exam . The site's decisions are visible to learner and agent alike. The rubric interview is the centerpiece. The engine's own routing hands the mic to the AI to judge free-form teach-back explanations, then validates its scores against verbatim lesson-text evidence and clamps them. The AI does what only AI can; the site does what AI must not. Zero AI infrastructure: static site, no backend, no API keys. The visitor brings the intelligence; the site brings the authority. Everything also works agent-less. The coach is an interface, not a dependency. We built Grapevine Care to explore how WebMCP can give an agent structured access to the same evolving, page-scoped state as a human coordinator without taking authority away from residents, caregivers, or clinical professionals. What it does Grapevine Care is a fictional, safety-first caregiver-continuity simulation. Its primary experience is one compressed Care Team Day across three residents: At 9:15 AM, Evelyn's visit lacks a verification record. The agent prepares a bounded inquiry; Luis answers in his own voice; the coordinator records the disposition. At 11:30 AM, Elena is available for Walter but lacks resident-specific readiness. We separated preparation from execution, kept resident and caregiver responses on human-only surfaces, made unknowns explicit, and bound consequential proposals to fresh evidence and schedule snapshots. Browser extension that adds WebMCP support for the popular websites that don't have it Like 2 Comment Story Updates Inspiration OpenAI’s post about using WebMCP with Codex made us examine the standard in the context of our browser automation work. Codex already could complete our tasks, but dynamic websites required repeated cycles of inspecting, scrolling, and collecting page content. Each cycle added another model call and more tokens. We wanted to replace those loops with small, structured tools. What it does AnyWebMCP is a Chromium extension that adds WebMCP tools to existing websites. It detects the current domain, loads the matching adapter, and exposes a bounded set of operations to the agent. The tools use the current browser session and return structured results. AnyWebMCP currently supports Amazon, eBay, Hacker News, LinkedIn, Product Hunt, Reddit, Temu, and X. A macOS launcher loads the extension into Codex’s built-in browser. How we built it We created a TypeScript monorepo with separate packages for the extension, shared WebMCP contracts, and each website adapter. Adapters collect data from the DOM, public APIs, or same-origin endpoints, depending on the site. Our Chrome prototype required an unpacked extension, experimental flags, and a remote debugging connection. We wanted the extension inside the browser where our Codex workflows ran. We inspected the macOS Codex build and found that it was Electron-based. It accepted the Chromium flags we needed: --load-extension=<extension> --enable-features=WebMCPTesting We built a launcher that creates a verified runtime copy of the installed Codex app and starts it with those flags. The launcher leaves the installed app untouched and does not include or redistribute Codex. Challenges we ran into The first challenge was installation. Our colleagues understood the extension but found the Chrome debugging setup cumbersome. Chrome also displayed a persistent debugging notification and mixed agent-created tabs with their work browser. Website differences created the second challenge. Each site exposes data through different page structures and endpoints. Dynamic feeds, hidden content, authentication, and tool discovery required bounded recovery logic for each adapter. Accomplishments that we're proud of First of all, we made it successfully work in Codex in-app browser. It's a bit hacky now, but we hope codex in-app browser adds native support for browser extensions at some point. In paired benchmarks, WebMCP reduced median total-token use by up to 90% and completion time by up to 55%. We also added safety boundaries. Most tools are read-only. Drafting tools leave final submission to the user, and commerce tools cannot purchase products or begin checkout. What we learned Structured tools work best when one call replaces several model and browser turns. Tool calls have their own latency, so short tasks may save tokens without finishing faster. We also learned that useful WebMCP tools need site-specific design. A small operation with a clear schema and bounded output helps the agent more than a generic dump of page content. What's next for AnyWebMCP We plan to add adapters based on real browser workflows, simplify installation and updates, and improve the adapter SDK for contributors. We also want to support more desktop platforms and follow the WebMCP standard as browser support develops.
