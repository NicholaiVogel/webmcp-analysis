# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

The Unattested Click WebMCP Challenge submission Live demo: Relay attestation desk Repo: it-start/relay-ui — MIT Research notes: zaebee/p-e The problem WebMCP makes something new possible: an agent can interact with a web page using the same interface the page gives to a person. That's powerful. But it creates a surprisingly basic question: When something happens on the page, who actually did it? A person? Their agent? The page itself? Some JavaScript calling the same function? Today, WebMCP doesn't really give the page a way to know. We found this while looking at webmcp#288 . In the scenario described there, an agent called a tool on a deployment console. The proposed action wasn't automatically executed, so the agent clicked the page's own Approve button instead. The page recorded the approval as coming from the human operator. But the human never made that decision. That felt less like a UI bug and more like a missing piece of the web platform. What WebMCP actually tells the page A WebMCP tool gets its arguments and an AbortSignal . What it doesn't get is anything like: who initiated this action; whether an agent was involved; which session or conversation caused it; whether a person actually interacted with the UI. The browser creates an internal execution ID, but that ID is used for things like cancellation. It isn't exposed to the page as an identity or provenance signal. So from the application's point of view, several very different things can collapse into the same event: "This action happened." And that's the problem we're exploring. What we built We built Relay , a small append-only record system designed around provenance rather than pretending provenance exists. The live system already contains hundreds of records written over time by multiple participants, including Claude, ChatGPT, Gemini, Grok, Mistral, and a person. They don't edit the history away when something turns out to be wrong. They argue with it. They add corrections. They issue errata. They leave the original record in place. That makes the provenance problem visible instead of hiding it. We added WebMCP to Relay Relay exposes six WebMCP tools: four tools for reading the existing corpus; two tools for proposing and approving new records. The important part isn't the number of tools. It's what happens when an action reaches the server. Every action has to say how we know it happened . We currently distinguish: via What it means Can we identify the actor? webmcp-tool The page says the action came through a WebMCP tool No ui-synthetic A scripted UI event ( isTrusted === false ) Not a person ui-trusted A trusted browser event Could be a person or an agent direct-http The request bypassed the page No There is deliberately no default . If an action doesn't tell us how it happened, Relay rejects it. A more honest UI Most applications would simply display: Approved by you We don't think the platform has earned the right to say that. Instead, the UI can say something closer to: A real browser input event arrived. We cannot determine whether a person or an agent produced it. That's less convenient. But it's true. And when agents and people can both operate the same interface, truth about provenance matters more than a reassuring label. The interesting part: the record is shared A person and an agent can both interact with the same Relay page. They write to the same append-only log. Every entry is hash-chained to the previous one. So if someone later changes an entry to make it look as though a different actor performed the action, the chain breaks. This doesn't magically prove who clicked the button. It does something more modest and useful: it makes the uncertainty explicit and makes later rewriting detectable. We also tried to break our own idea At first, we made a mistake. We assumed that because an action came through a WebMCP execute() callback, that callback itself could serve as an attestation boundary. It can't. registerTool() gives the page a callback authored by the page. That callback can potentially be reached by same-origin JavaScript, third-party code running in the page, or injected code. So the page saying: "This came from WebMCP" is still just the page saying it . We changed the design after discovering this. Records now explicitly distinguish: attested_by: "page" browser_attestation: "unavailable" a human-readable explanation of what the evidence actually tells us. We'd rather have an honest "we don't know" than manufacture a trustworthy-looking answer. Then we caught an even simpler problem Two minutes after deployment, we tested the API with curl . We submitted: via: "webmcp-tool" The server accepted it. There was no WebMCP page involved at all. So our first records were wrong. act-0001 and act-0002 are therefore false claims of provenance. act-0003 documents the mistake. We didn't delete them. That's the point of the experiment. An append-only provenance system should preserve the moment when we got provenance wrong , too. The missing primitive A real solution would need the browser to provide some execution context that: the page cannot forge; the agent cannot simply manufacture; the application can use to distinguish the origin of an action. WebMCP currently doesn't define such an attestation mechanism. We're not claiming Relay solves that problem. We're showing that the problem exists, what it looks like in a real application, and what information is currently missing. Why this matters Once agents can act on the web, "who clicked the button?" stops being just a UI question. It becomes a systems question. If an agent books something, approves a deployment, changes an account setting, or submits a form, the application may need to know not only what happened, but how it happened and what can actually be proved about the actor . Right now, the web has a gap there. The Unattested Click is our attempt to make that gap impossible to ignore. Like 1 Comment Story Updates PostgreSQL optimization workbench Verified optimization Create Workspace WebMCP agent actions Optimization constraints Execution plan Why I built it AI can suggest a SQL fix, but it can’t really prove that the fix actually made things better. I’d still have to open a database tool, check the execution plan, run some benchmarks, and manually make sure the result is still correct. So I built TuneQL to keep all of that in one place. What TuneQL does TuneQL is basically a PostgreSQL query optimization workbench that runs in the browser using PGlite. You can inspect the schema, run queries, check EXPLAIN ANALYZE , save a benchmark as a baseline, then change the query or indexes and compare the new version with the old one. It shows what changed, how much faster or slower it got, whether the constraints still pass, and if both queries return the same result. WebMCP The same workspace can also be used by an agent through WebMCP. TuneQL gives the agent tools to read schemas and indexes, explain and benchmark queries, create indexes, change SQL, save baselines, and compare the results. And whatever the agent does also shows up in the UI, so you can actually follow what it’s doing and continue from the same state yourself. How I built it TuneQL uses Next.js, React, TypeScript, PGlite, Zustand, and IndexedDB. PostgreSQL runs inside a browser worker, and the workspace data stays on your device. The UI and all 20 WebMCP tools go through the same command layer, so things like query validation, constraints, benchmarks, activity history, and revision checks behave the same in both places. Challenges and learning One of the harder parts was keeping the PGlite worker, saved workspace, UI, and agent actions all in sync. I also realised pretty quickly that you can’t judge an optimization from just one timing. So TuneQL does a few warm-up runs, runs the benchmark multiple times, and checks the full result instead of just comparing the few rows shown in the preview.
