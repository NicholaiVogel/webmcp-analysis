Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.

- 3-4: speculative audience or strained fit; impact mostly aspirational.

What we learned The consent moment is the whole human-agent interface, and a dialogue that renders a human-authored description is a dialogue that can lie. Better warnings do not fix this; bounded authority does. Checking the executed call against a standing mandate defeats all three attacks with one invariant: an effect may only execute when it matches both the declared tool and the human's current mandate. What's next for ROAST Take the mandate out of the page: a browser-level or agent-level authority layer for WebMCP, mandates expressed in the user's own words and parsed to scopes, and fingerprinted tool manifests so substitution is detectable across the boundary. The write-up and the argument live at crowley.nl/webmcp-challenge/ . Like Comment Story Updates Inspiration Shopping agents are often forced to infer intent from pixels, scrape inconsistent product cards, and guess whether an action is safe. ZShop Agent Cart explores a better contract: the storefront exposes precise capabilities while the shopper keeps a visible, shared workspace and remains in control of consequential choices. What it does ZShop registers five WebMCP tools directly from the live storefront: set_shopping_goal makes the shopper's brief visible to both human and agent. search_products searches the live catalog and returns compact, comparable facts. inspect_product reads current price, stock, fulfilment, description, and option requirements. view_cart reads the authenticated shopper's selected items and total. add_product_to_cart adds simple products through the existing signed-in session. The on-page companion shows the shared goal and a live activity trail, so the human can see what the agent is doing without leaving the shopping experience. Products with variants are deliberately not guessed: the tool returns a product URL and asks the shopper to select options. Checkout remains human-controlled. Why WebMCP is the right fit Commerce mixes fast-changing facts, authenticated state, and actions with different risk levels. WebMCP lets the site describe each capability with a narrow JSON schema and behavioral annotations instead of asking an agent to reverse-engineer the UI. The result is faster and more reliable than click automation, while preserving the storefront's own validation, authentication, and cart rules. Before this extension, a shopper could browse ZShop and an agent could separately offer generic advice. Now they can work in the same live catalog and session: the person states intent and handles preference-heavy decisions; the agent retrieves current facts, narrows choices, and performs bounded cart work; both share visible context. How we built it The Nuxt 4 client plugin detects document.modelContext , then registers typed tools with registerTool . Each tool has a constrained input schema, clear descriptions, and read-only, destructive, idempotent, and open-world hints. Tool handlers call the same production catalog and cart APIs as the storefront and reuse the existing auth token. A Vue composable keeps the shared goal and recent action log reactive in the companion UI. Focused Vitest coverage validates product normalization and rejects malformed search terms and numeric inputs. A CDP-based WebMCP host test injects the browser API, verifies all five registrations, executes the goal and live catalog search tools, and confirms that the human-visible companion updates. Challenges The central design challenge was choosing boundaries, not simply exposing every UI action. Product options cannot be selected safely from incomplete intent, and checkout has financial consequences, so neither is automated. Another challenge was keeping the experience useful outside a WebMCP-enabled browser; the storefront still works normally and the companion explains when agent capabilities are unavailable. Accomplishments Five working WebMCP tools backed by a live multilingual catalog. Shared human-agent context visible in the existing storefront. Authenticated cart access without a second agent-specific account system. Explicit safety boundaries for variants and checkout. Reproducible tests, public source, MIT license, and dated challenge-period commits. What we learned Agent-native UX is strongest when structured capabilities and visible human feedback are designed together. Schemas make actions reliable; the companion makes them understandable. The most important tool behavior can also be a refusal to guess. What's next Next we would add preference memory approved by the shopper, side-by-side comparison cards generated from tool results, and a confirmation protocol for reversible versus consequential actions. We would also localize tool descriptions alongside ZShop's Chinese, English, Thai, and Traditional Chinese interface. Inspiration Agents are now really good at generating HTML/CSS/JS artifacts to help convey understanding to users by visualizing content. There are already services that enable agents to easily host static pages, but these lack interactivity. At the same time, agents are mainly used by one user only, and there isn't that much of a multiplayer mode. When collaborating with coworkers or friends, we have to manually send artifacts/plans, gather feedback, and potentially go through multiple sessions and iterations to reach the final desired state. Multiple agents can work toward the same goal, but in complete isolation. My goal was to try to use a super simple platform to enable a new kind of multiplayer agents × humans collaboration. What it does BuildParty allows anyone to create a party. It is completely their own, and agents can automatically connect to it using WebMCP tools. Each party is initially empty, but any connected agent can add and modify “artifacts”, which are self-contained HTML/CSS/JS components. The owner can share the link so that other users can join on any device, connect their agents, and see changes in real time. Users can interactively add comments and suggestions directly on the page for all agents to see. The page is fully synced, and each change is saved as a revision. The owner can roll back to a previous revision at any time. At the end, the owner can finalize the party, closing any further modifications and compacting all artifacts together into a single HTML page ready to download. Each block supports persistent state so that interactive elements such as text areas, buttons, etc. can work. The flow is very simple for agents: read a specific block, modify it or add a new one, and read comments. This can be used for a range of different use cases: collaborative planning before starting a long implementation, ephemeral agent observability dashboards to see specific progress, and more. How we built it This was built using webmcp for tools, custom-made evaluation with WebMCP-bench using daytona cloud sandboxes, electric for sync and PostgreSQL for the underlying db. Challenges we ran into Evaluating WebMCP capabilities is very hard because, on top of the current agent context, we add a new dimension: the website state. Even if my basic evaluations worked, when manually testing I often ran into cases where the agent could not efficiently figure out which tool to call or in which order. To fix this, I built a small WebMCP evaluation framework based on a finite state machine: each state encodes a website state fixture and the available tools, while transitions to other states define specific tool calls. From this FSM specification, I can automatically implement tool discovery and give agents information about the available flow of tool calls. I also defined an evaluation bench with a set of tasks that consist of an initial state, a target end state with a sequence of expected tool calls, and an initial prompt. With this, I was able to fine-tune tool descriptions and improve the agent's understanding of how to use the website context efficiently. Accomplishments that we're proud of Everything works, and I'm already using it for some use cases! What we learned I learned a lot about what is possible with WebMCP and how to reason about it. I believe that, at some point, we could somehow ditch frontend frameworks as we know them and start with only a state flow/state machine representation of the app, then enable UI components “on demand” that automatically adapt to the user's preferences and needs. This would also be awesome for accessibility, as we could automatically derive not only visual frontends but other frontend formats as well. What's next for BuildParty If there's some interest, I would like to rework the whole artifact engine to make it more robust to agent changes and enable different formats such as Markdown editors, code blocks with interpreters (Jupyter Notebook style), and embedded databases.
