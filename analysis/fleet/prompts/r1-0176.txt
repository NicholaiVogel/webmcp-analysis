# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

The application registers five imperative WebMCP tools through document.modelContext.registerTool(): get_lesson_context start_accessible_audio_guide adapt_learning_experience start_water_cycle_mission prepare_science_answer Each tool uses a constrained JSON Schema and connects directly to the same state used by the visible interface. These tools allow an agent to understand the current lesson without scraping the page, start an accessible Spanish audio guide, apply reversible interface adaptations, open the correct learning activity, and prepare a spoken or typed answer for human review. The prototype also uses the browser’s Speech Recognition API for real microphone input and the Speech Synthesis API for audio guidance. A typed response remains available whenever voice recognition is unsupported or microphone permission is denied. The visual system combines Atkinson Hyperlegible for reading with Geist for interface hierarchy. The experience includes responsive layouts, keyboard navigation, reduced-motion support, high-contrast focus indicators, accessible dialogs, and multiple ways to complete every important interaction. Challenges we faced One of our biggest challenges was determining the correct boundary between agent assistance and student agency. An agent should be able to remove interface friction, but it should not make academic decisions or submit work without meaningful consent. We therefore separated answer preparation from final submission. The WebMCP tool reports submitted: false and opens a visible confirmation dialog. Another challenge was balancing sensory calm with engagement. We wanted to avoid overstimulation without producing a cold or purely functional interface. The narrative involving Leo, Luma, and Ayu gives the lesson continuity, emotional context, and a clear sense of progress. Voice interaction also required careful attention. We designed microphone controls for press-and-hold interaction, keyboard activation, permission errors, and typed fallback. Audio guidance and microphone recording are mutually exclusive so the guide cannot accidentally be transcribed as Leo’s answer. What we learned We learned that WebMCP is more powerful when it represents meaningful product capabilities instead of reproducing individual button clicks. Rather than giving the agent unrestricted control over the page, Entorno Camaleón exposes a small set of understandable and governed actions. This makes agent behavior more reliable, visible, and safer for students. We also learned that accessibility should not be treated as a final compliance step. In this project, accessibility became part of the product concept itself. Multiple response channels, adjustable presentation, predictable navigation, audio guidance, and explicit confirmation improve the experience for a much broader group of learners. What we are proud of We are proud that Entorno Camaleón is both a functional WebMCP demonstration and a complete product story. The deployed prototype includes five working WebMCP tools, real voice input with a typed fallback, accessible audio guidance, a responsive five-chapter learning journey, student-controlled presentation preferences, keyboard and reduced-motion support, an explicit human-confirmation boundary, and a complete manual fallback when WebMCP is unavailable. What is next The next step is to replace the simulated school receipt with an authenticated LMS sandbox and add durable consent and audit records. We would also co-design future versions with neurodivergent students, families, teachers, accessibility specialists, and school administrators. Entorno Camaleón is currently a proof of concept, not a clinical intervention or production LMS integration. Its purpose is to demonstrate how agentic technology can make educational interfaces more flexible without taking control away from the learner. Entorno Camaleón: The learning goal stays the same. The experience finally adapts. Like Comment Story Updates Editor overview AI proposal Screen Blueprint Studio — Project Story Inspiration Text and tables alone make it difficult to visualize a finished web interface, especially for non-engineers and people who have just joined a project. Adding wireframes helps, but teams still have to maintain the relationship between each part of the screen and each part of the specification. Every new field or layout change means updating the visuals, the specification, and the links between them. We wanted to solve this problem not by collecting more documents in one place, but by making the wireframe and the specification two representations of the same structured data. When a screen is assembled from semantic UI components, its visible wireframe, states, behaviors, and API mappings can all live in one blueprint. That structured model also creates a meeting point between human and AI strengths. People can look at the whole screen and make intuitive decisions about layout and wording. AI is good at working with text and structured data, applying repetitive changes, and maintaining relationships consistently. Asking it to infer a screen's meaning from screenshots and coordinates alone does not make full use of those strengths. In Screen Blueprint Studio, people work directly on the canvas, while AI uses the same editing capabilities as named, typed WebMCP tools. WebMCP connects human visual judgment and AI's structural editing on the same live model. What it does Screen Blueprint Studio is a visual editor for building screen specifications from semantic UI components. People can arrange components and edit their content and behavior while viewing the screen. From the same blueprint, they can inspect screen states and transitions and manage how user actions relate to APIs. Through WebMCP, AI can read the current screen, the selected component, and the latest values edited by a person. It can then update structure and behavior using typed operations and stable IDs. Proposed changes appear on the same canvas for a person to accept or reject. If the person adjusts the proposal in the UI, the AI can read and build on that result in its next action. How we built it First, we designed a conceptual model that connects UI components, states, behaviors, screen transitions, and APIs—not just their visual appearance. Next, we turned that model into an editor where people can work directly on the screen and visually inspect its states and relationships. Finally, we identified the available actions that play to AI's strengths, such as understanding text and structure or applying repetitive changes, and exposed them as WebMCP tools. Challenges we ran into The hardest design decision was choosing the right granularity for the tools exposed to an agent. Combining a wide range of actions into a few general-purpose tools produced oversized schemas, while splitting every UI action into its own tool would leave the agent with too many choices. Our first schema mirrored the domain model too closely: it was about 95 KB and contained 376 union branches. We kept the tools organized around user intent, simplified their inputs, and made detailed context available progressively. This reduced the schema to about 29 KB with no union branches, while strict validation remained inside the application. Accomplishments that we're proud of We are most proud of using WebMCP to build a collaborative workflow that plays to the different ways humans and AI understand information and interact, rather than forcing both through the same interface. People edit by viewing the entire canvas and using direct actions such as dragging and selecting. AI reads the same screen specification as text and structure, then changes it through named, typed tools. Because the wireframe and specification share one model, both approaches modify the same underlying work. Comparing other ways to connect AI with an interface shows why WebMCP fit this division of roles: Approach Strength Weakness In-app AI A tailored experience with direct access to internal state External context and confidential project information can be difficult to bring in Backend MCP Direct access to server-side data and external services Browser-local state requires separate synchronization Computer Use Can operate existing interfaces without custom tools Repetitive and bulk changes require many sequential UI actions WebMCP Exposes page context and semantic actions to the user's existing agent Limited to actions designed and exposed in advance With WebMCP, the live page itself exposes its current context and meaningful editing capabilities. Users can give meeting notes or requirements to the agent they already use and ask it to update the screen without leaving that context behind. A person can then review and refine the proposal on the same canvas, and the agent can pick up the result again. Instead of making AI imitate human interaction, we connected people and AI in one creative workflow through interfaces suited to each. What we learned This project deepened our understanding of how people and AI process information and interact differently. LLMs are relatively strong at reading text and structured information and generating changes from it. People are relatively strong at visually grasping the whole screen and fine-tuning details through direct actions such as dragging and scrolling. Effective human-AI collaboration depends on designing for those differences, so each can contribute to the same work in the way that suits it best. What's next for Screen Blueprint Studio Product development has a translation problem. The same intent is repeatedly translated into meeting notes, requirements, designs, tickets, implementation, and tests, losing information each time. We want Screen Blueprint Studio to become a shared language across roles and between people and AI—one where decisions about an interface can be seen, understood, and carried forward as structure. Ultimately, we want ideas born in conversation to retain their meaning all the way through team agreement, implementation, and validation.
