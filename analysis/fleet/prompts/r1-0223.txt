# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Turn any website into an agent opportunity map. Like Comment Story Updates Inspiration AI agents can understand websites, but they still interact with most of them like humans: reading pages, interpreting interfaces, finding controls, and simulating clicks. These workflows are slow, fragile, and often fail when a website’s layout changes. WebMCP offers a better approach. Websites can expose structured tools that agents discover and call directly while keeping people involved in the same visible experience. That inspired us to build WebMCP.ai: a tool that analyzes any public website and identifies the most useful opportunities for making it agent-ready with WebMCP. What it does Users provide a public website URL, and WebMCP.ai researches the website, understands its business and primary workflows, and generates an evidence-backed WebMCP opportunity report. Each report includes: An overall agent-readiness score Scores for discoverability, structured data, agent actions, automation, and MCP potential Ranked WebMCP tool opportunities Proposed tool names, descriptions, and input/output schemas User value, business value, implementation difficulty, and safety ratings Authentication, authorization, validation, confirmation, and audit safeguards Research sources and clearly identified limitations A production-ready implementation prompt for coding agents Users can filter and compare opportunities, select the tools they want to build, and export the report or implementation prompt. WebMCP.ai is itself WebMCP-enabled. It exposes three browser-native tools: analyze_website analyzes a public website and updates the visible report. get_opportunity_report returns the complete current report. select_tools_for_plan selects recommendations and creates a tailored implementation plan. This means an agent can operate WebMCP.ai directly without typing into the URL field or clicking the Analyze button. The agent and user remain in the same interface and share the same application state. How we built it We built WebMCP.ai as a full-stack Next.js application using React and TypeScript. The analysis pipeline first validates the submitted URL and rejects embedded credentials, unsupported protocols, private networks, local addresses, and unsafe redirect destinations. It then performs a bounded crawl of relevant public pages using Cheerio. The extracted content is explicitly marked as untrusted data before being sent to an OpenAI-compatible Responses API. The model researches the website’s business, workflows, public APIs, competitors, and relevant MCP precedents. Its response must match a strict Zod schema before the application accepts it. Opportunity scores are calculated deterministically rather than relying entirely on model judgment. The application then builds a structured implementation prompt containing tool schemas, safeguards, engineering requirements, testing expectations, and acceptance criteria. The WebMCP integration uses the imperative document.modelContext.registerTool API. Tools are registered once with AbortSignal cleanup and reuse the same logic and React state as the visible interface. The application is deployed on Vercel, while the source code and project documentation are hosted publicly on GitHub. Reports remain in browser memory, so no database is currently required. Challenges we ran into One major challenge was working with websites that block automated access, require authentication, or render most useful content through client-side JavaScript. We addressed this by reporting incomplete access honestly and grounding every recommendation in the evidence that was actually available. Analysis requests can also take time because they combine website extraction, research, structured generation, and validation. We introduced bounded timeouts and a fallback analysis path when enriched web research takes too long. Another challenge involved WebMCP lifecycle management inside React. Initially, tool registration could be recreated when the URL or report state changed. We stabilized the callbacks and used references to the latest report so agents retain valid tool handles while the interface updates. Security was equally important. A tool that accepts arbitrary URLs can create server-side request-forgery risks, while crawled content can contain prompt-injection attempts. We added DNS and redirect validation, private-network blocking, content-size limits, bounded crawling, strict schemas, and explicit untrusted-content boundaries. Finally, we had to ensure agents selected the WebMCP tool instead of falling back to browser interaction. Accurate read-only annotations, stable registration, and direct tool descriptions made that behavior reliable. Accomplishments that we’re proud of We are proud that WebMCP.ai does more than generate generic tool ideas. It produces ranked, evidence-backed opportunities connected to real workflows, business value, technical feasibility, and safety requirements. We are especially proud that the application demonstrates the experience it recommends. Agents can call WebMCP tools directly, update the same interface the user sees, retrieve the resulting report, and collaboratively choose an implementation plan. Other accomplishments include: Strictly validated structured model output Deterministic opportunity scoring Transparent evidence and limitations Production-oriented implementation prompts SSRF and prompt-injection defenses Stable WebMCP registration and shared UI state Automated unit, integration, lint, type, build, and end-to-end checks A responsive interface with report and prompt exports What we learned We learned that effective WebMCP tools should not simply reproduce button clicks. The best tools expose stable business capabilities with clear inputs, structured results, and well-defined safety boundaries. Tool metadata also matters more than expected. Names, descriptions, schemas, annotations, and lifecycle behavior determine whether an agent can confidently discover and use a tool. We also learned that agent readiness is not purely a technical score. Authentication, data availability, business value, user trust, implementation effort, and human confirmation all influence whether a workflow should become a tool. Most importantly, WebMCP works best as a collaboration layer. It does not need to replace the interface. It can connect agents to the application’s real capabilities while keeping the user informed and in control. What’s next for WebMCP.ai Next, we want to add: Saved and shareable reports with explicit retention controls Repeatable WebMCP evaluations that measure tool-selection accuracy Before-and-after readiness comparisons Organization workspaces and collaborative reviews Direct export to GitHub issues and engineering backlogs Automated validation of implemented WebMCP schemas Historical monitoring as websites improve their agent readiness Additional analysis of authenticated workflows through approved integrations Our long-term goal is for WebMCP.ai to become the bridge between human-first websites and agent-native experiences: helping teams decide what to expose, why it matters, how to build it safely, and whether it actually improves the experience. Like Comment Story Updates Inspiration Incident response is one of those workflows where an AI agent could genuinely save time, but it is also a workflow where giving an agent unrestricted control would be a terrible idea. During an outage, engineers jump between service health, deployments, logs, traces, alerts, runbooks, and incident timelines while trying to answer a few basic questions: What changed? What is actually failing? What evidence supports that diagnosis? And what is safe to do next? I wanted to explore what incident response looks like when the agent can work inside the same operational console as the human instead of operating through a separate chatbot or a disconnected API. That became Firebro . The design principle behind the project is simple: Agent capability, human authority. What it does Firebro is an incident response console built around WebMCP. An agent can investigate an active incident by checking service health, dependencies, recent deployments and changes, logs, traces, alerts, metrics, runbooks, and the incident timeline. It can correlate that evidence, identify a likely cause, and propose a remediation. For example, one incident starts with degraded checkout performance after a bad deployment. The agent can compare service metrics, inspect traces and logs, find the deployment that introduced the regression, and propose rolling it back. But the agent cannot simply execute a consequential remediation on its own. Actions such as a rollback can require an approval tied to the exact proposed action. The approval has to come from a real human interaction in the console before the action can proceed. Once remediation starts, the simulated production environment reacts. Metrics recover, logs change, and the incident moves through recovery and monitoring before it can be resolved. Firebro includes multiple deterministic incident scenarios so the correct response is not always "roll back the latest deployment." Some incidents involve resource exhaustion, feature flags, memory leaks, or even third-party failures where the best action may be to wait rather than make an unnecessary production change. How I built it Firebro is built as a web-based incident console with a WebMCP capability layer on top of the same operational state visible to the human operator. The system exposes tools across the full response workflow: incident discovery, service health, dependencies, deployments, recent changes, logs, traces, metric comparisons, alerts, runbooks, incident notes, remediation actions, approvals, and incident resolution. One of the main implementation goals was avoiding a separate "agent version" of the application. When an agent investigates something, the console reacts too. A service can be highlighted in the topology, log views can focus on relevant entries, metric comparisons become visible, traces can be surfaced, and approval requests appear next to the operational evidence the human needs to make a decision. Tool availability also depends on context. Capabilities can change based on the selected incident, current incident state, and what actions are currently valid. The backend runs a deterministic incident simulation. Each scenario has a known underlying cause, but that ground truth is intentionally hidden from the WebMCP tools. The agent has to diagnose the incident using the same observable evidence available through the console. Mutations and incident events are persisted so the UI and tool layer stay synchronized as the incident evolves. Challenges I ran into The hardest part was making the environment realistic enough that the agent actually had to investigate. If every incident simply had an obvious error message pointing to the answer, there would be no real diagnostic workflow. Firebro includes misleading signals and plausible alternatives so the agent has to correlate evidence instead of choosing the loudest symptom. Another challenge was tool design. Returning thousands of raw log lines or metric samples makes an agent less useful, not more useful. The tools needed to expose enough evidence to support a diagnosis without turning every response into an unstructured data dump. I also had to think carefully about approvals. A generic "approved: true" flag would not be enough for a real operational workflow. Approval has to be tied to the exact action being proposed so an approval for one operation cannot silently authorize another one. Keeping the simulation deterministic was another important challenge. The same incident needs to behave consistently enough for automated evaluation while still looking like a live operational system. Accomplishments that I'm proud of I'm most proud that Firebro feels like one shared workspace rather than a dashboard on one side and an agent on the other. The agent works with the same incident, graphs, logs, services, and actions the human is looking at. Investigation has visible consequences in the interface, and consequential actions pass through an approval workflow instead of bypassing the operator. I'm also proud of the incident simulation itself. Different scenarios require different forms of reasoning, and remediation does not always produce an immediate perfect recovery. Some actions only partially help, some have no effect, and the system can regress if the diagnosis was wrong. Asking someone to approve a rollback in isolation is very different from asking them while they can see the deployment, affected metrics, traces, and the agent's proposed action in the same console. WebMCP also made browser context much more important than I originally expected. The agent is not operating a remote service in the abstract. It is operating the application the human currently has open. The next step would be connecting the same interaction model to real observability and incident-management systems while keeping the approval boundary intact. I'd also like to expand the scenario set, add more complex multi-service failures, improve automated agent evaluations, and explore richer policy controls for actions with different levels of operational risk. The long-term idea is not an autonomous system that replaces the incident commander. It is an incident console where an agent can do far more of the investigation and coordination work while the human keeps authority over decisions that can affect production. Before: "what am I looking at?" was unanswerable, because a viewport is just numbers. Now: get_visitor_view hands the agent the TOWNS your zoom frames, ranked, with the dominant one named. Zooming on Saintes-Maries-de-la-Mer means Saintes-Maries-de-la-Mer even with every filter on "all towns". "What's on tonight near me" is one distance-ranked call. Before: the agent's plan lived in the chat and died there. Now: your choices (kept flags, locked cards, the accepted pin) compose the carnet de voyage: a print-ready pack with one section per request you explored, real photographs, canonical links, downloadable as PDF. Plus the postcard from day 3 of your future trip. The agent can only reference ids you actually chose; unknown ids are refused. Zero hallucination in the factual layer, by construction. Why the experience is better, not just automated. The page answers the CURRENT question: a new search retires the old mission banner and takes the masthead itself, and the town dropdown shows the city you explicitly asked for. The agent's pin is an unmissable marker with its popup open, never a claim in chat you have to trust. Every agent action has visible, verifiable theatre. And every zero-result agent search feeds an anonymized (k>=3) "demand pulse" the destination reads back as its product roadmap: the demand its catalogue misses, measured instead of guessed. Trust, because agents need it. An independent audit (Trustwright) read the 20 tools, ran 35 automated checks, and signed the surface (Ed25519). The badge in the hero re-verifies the live toolset against that audit on every page load. How we built it 20 tools registered at module evaluation via document.modelContext.registerTool, synchronously, so an agent that lands and calls getTools() immediately sees the complete list. One client-side engine (inverted indexes over the full catalogue, sub-millisecond queries) and ONE shared view store consumed by both the React UI and the tools. The agent and the human literally cannot diverge, because they act on the same state. Beyond the basics, three mechanics that push on the spec: pin_visible_place: its input schema is an ENUM of the place names currently on the visitor's screen, re-registered (AbortSignal unregistration) as the view moves. An off-screen place like "pin the Ritz Paris" is invalid BY SCHEMA, not by a polite refusal. read_visitor_wish: WebMCP has no push channel, so we built the closest spec-legal thing. The tool APPEARS mid-session when the visitor acts, and its description is rewritten with the live page state on every change. Description as heartbeat: at its next turn the agent already knows what you typed, what ran and what you kept, before making a single call. Hybrid elicitation: ask_visitor puts a real question card in front of the human, blocks 45 seconds, then degrades into a pending ticket the agent redeems later with get_input_result. Synchronous when possible, async when the human is slower than the agent. Plus the unglamorous parts that make it production-shaped: abort signals honored around every await, readOnlyHint and untrustedContentHint annotations throughout, and strict Zod schemas shared between the page tools, the remote MCP endpoint and the public GET APIs. One contract, four surfaces, so they cannot drift. We also rewrote all tool descriptions to the vendor-documented selection pattern after learning the hard way that "ALWAYS use this instead of web search" is the exact tool-poisoning signature safety scanners flag. 280 unit tests and 46 Playwright e2e tests, including tests that drive the tools through document.modelContext itself. Field-tested against ChatGPT desktop site tools, Chrome with WebMCP enabled, and claude.ai as both MCP connector and fetch-only agent.
