# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

That's what "people and agents working together" really means the agent picks up on things humans couldn't, but the human keeps the decision power to determine what's a real bug. \n\n How we built it \n\n React 19 + TypeScript + Vite, deployed as a static site with no backend, and all of our WebMCP tooling is client-side as well. \n\n Our five read-only tools are registered as @mcp-b/react-webmcp's useWebMCP hook wraps document.modelContext.registerTool for the current WebMCP API: \n\n typescript \n\n useWebMCP({ \n\n name: 'get_focus_order', \n\n description: 'Returns the real browser tab order starting from a given element...', \n\n inputSchema: getFocusOrderInput, \n\n outputSchema: getFocusOrderOutput, \n\n annotations: { readOnlyHint: true, idempotentHint: true, destructiveHint: false }, \n\n execute: async (input) => ({ steps: getFocusOrder(input.startSelector, input.limit) }), \n\n }); \n\n Five tools are read-only (get_focus_order, simulate_tab_sequence, get_aria_live_state, get_element_role, get_violation_log), each with the correct readOnlyHint/idempotentHint/destructiveHint security annotations from WebMCP's published guidance, and each tool respects the recommended character budgets (500-char descriptions, 150-char parameter descriptions, ~1.5K-char output cap). The one state-changing tool, report_violation, only can stage a finding it can't confirm it. \n\n The actual detection logic exists in a framework-free lib/ layer, separate from the WebMCP wiring, making it independently unit-testable. getFocusOrder correctly implements real browser tab-order rules (positive tabIndex sorted first, per the HTML spec, which is what makes the focus-order bug detectable) and a MutationObserver-based tracker records whether aria-live regions genuinely fire, not just whether the attribute exists. \n\n Challenges we ran into \n\n Two real bugs, both worth being upfront about. First: our initial tool schemas were Zod object maps, following a pattern from a tutorial, but @mcp-b/react-webmcp doesn't declare any Zod dependency at all the Zod support is structurally typed against Zod v3 internals, while the current Zod release is v4. Real, reproducible TypeScript errors, not a guess. We switched to plain JSON Schema the format the package's official examples show first to avoid version-coupling risk. \n\n Second: our unit tests were just failing in strange ways every getFocusOrder test returned an empty array. jsdom (our test environment) doesn't have a real layout engine, so element.offsetParent which our visibility check relied on is always null there. The fix detects whether a real layout engine is present, and only requires that signal when one is, ensuring real-browser behavior is preserved but also making it testable. \n\n Accomplishments that we're proud of \n\n Getting the human-confirmation mechanism to actually work as a real constraint, not just a UI suggestion. The agent's report_violation tool is architecturally incapable of writing to the confirmed violations log that decision is made in the React reducer, not by convention. We're also proud of the fact that every one of the three bugs is a real defect (verified by manually tabbing through and screen-reader spot-checking) and shipped with a real, passing unit test suite covering the actual detection logic, not just a working demo. \n\n What we learned \n\n That "thoughtful use of WebMCP" mostly comes down to restraint a tight set of six tools with correct security semantics beats a sprawling one. The most interesting design decision in this whole project wasn't a tool it was to make the one state-changing tool incapable of actually changing anything on its own. We also learned, concretely, not to trust a tutorial's dependency assumptions over what's actually declared in a package's own package.json. \n\n What's next for AccessCanary \n\n Extending detection to more WCAG behavioral patterns beyond the three shown here (focus restoration after modal close, dynamic content insertion announcements), and testing against real production forms rather than a single mock page, to see how the six-tool approach generalizes beyond the demo. \n\n \n\n \n Built With \n\n chatgpt chrome document.modelcontext git github googlefonts jsdom oxlint react reactdom render typescript vite vitest webmcp \n \n\n \n Try it out \n\n \n \n \n accesscanary.onrender.com \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Samir Shaikh \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n A motivated 3rd-year B.Tech student seeking an internship or hackathon opportunities \n \n \n \n\n \n\n \n\n\n \n

The demo follows one synthetic cybersecurity case involving suspicious account and connected-application activity. ChatGPT investigates the case using structured tools exposed directly by the TraceLayer webpage through WebMCP. During the investigation, the Agent can read evidence, inspect entities, connect related events, link evidence, and maintain an assessment. But its capabilities are not static. As the case progresses, TraceLayer changes the Agent's WebMCP surface. During investigation, it can gather and record evidence. At first, Human and SYSTEM actions were represented only as application-level actor labels. The Agent is good at searching, correlating, and maintaining structured reasoning across machine-scale information. The Human contributes organization-specific knowledge, judgment, and verified authority over consequences. And the application itself has an important role: it controls which capabilities exist, preserves state, enforces valid transitions, and records how decisions were reached. WebMCP made this especially interesting because the capability boundary lives directly in the application. The webpage is not just displaying information to an Agent. It can expose a structured capability surface that changes as the application state changes.
