For those who want to Cut Through The Noise to Get to The Signal in their YouTube videos. Like Comment Story Updates Step 1 Processing Result Icon Inspiration In a world of AI there is too much noise, this is a simple tool to leverage that very same AI to help cut through the noise to get to the signal of your YouTube videos. What it does TLDW is one web page where you paste a YouTube link and gets the captions, with the moment each line was said. An AI agent opening the page finds two WebMCP tools instead of buttons: get_transcript(url) hands it the captions as timestamped segments, and render_explainer(slides, url) draws whatever the agent wrote back onto the page, every timestamp a link that opens the video at that second, then reads it aloud. The thinking runs on the visitor's own ChatGPT plan, in their own session. How its built Built entirely with AI, Both tools are registered with document.modelContext.registerTool, with navigator.modelContext as a fallback for older builds, each with a JSON schema an agent can read. Errors are returned, never thrown, so a failure arrives as a result the agent can act on. Every fetch has three outcomes, not two: ok, not_measured with a reason, or a structured error, because a tool that cannot tell a failed measurement from a real zero will report the first as the second. Captions come from a transcript API first with a direct fetch behind it, held in memory for ten minutes and never written down. The page is served by a Cloudflare Worker. Read-aloud uses the browser's own voices by default with a voice picker; one opt-in experimental entry renders a natural voice on our server and streams it back. An agent whose browser has no WebMCP yet can paste the same slides into a Render box on the page and get the identical result. It was built from nothing in one evening, live on stream, by a fleet of AI bodies run by one human, with two independent reviews on every change. Challenges We (Myself and my AI Team) only had ~8 total hours for this as that's when I found out about the competition, then immediately started live streaming the start to finish. We had about ~3 hours of prep while waiting for the reset then 5 hours to build. The spec moved while we built: our first registration was on navigator.modelContext only, and Chrome's stable build binds document.modelContext, so the tools registered and nobody could see them. YouTube refuses caption fetches from a server, so the free path failed silently until we made refusal a first-class result and put a transcript API in front of it. Agents that fetched the captions then answered in chat instead of drawing on the page, until the tool text put the obligation before the data. And the browser's speech queue armed from the speak call rather than from what was drawn, so a slide with the wrong shape left a full explainer on screen and nothing to play. Each one was found by a second reader, not by the author. Accomplishments that we're proud of We got it done 40mins past the buzzer but fortunately there was a 12 hour extension, so we polished the video and made minor edits to the description etc (also generated by AI) The tool work on a free ChatGPT account, the desktop app's built-in browser, and with one sentence: explain this video and render it on the page. The page registers two tools, the agent calls them, the explainer appears with timestamps that jump into the YouTube video if you want to watch a particular segment in full, and it also comes with a reads aloud bar with play back controls and voice selection that uses your browser supported voices and 2 x experimental neural voices. The public repository has one clean history, one identity, and passed a whole-history scan by a stranger before it went public. What we learned The hard part was restraint. Every instinct said add a summarizer, add a model, add a key, and each one would have made it slower, costlier. The second lesson was the error surface: an agent is not a human staring at a stack trace, it reads your failure and decides what to do next, so a tool that throws ends the conversation and a tool that returns a readable error lets the agent try something sensible. The third was the voices, Chrome free supports free neural style voices as well as system voices, the ChatGPT browser uses only the free system voice. We are experimenting with some neural voices but the render time is slower, there could be an option to use something like Elevenlabs but then that would mean have to charge a fee for the service or run ad's on the page. It would be good if the ChatGPT could somehow enable support for the Chrome voices as those are pretty good. What's next for TLDW | Too Long Didn't Watch This is TLDW v1 .v2 & v3 will be better. I didn't want to create something that Notebook LM already does so keeping it video focused is the lane I'll stay in for now. v2 would be more generating more interactive lessons / explainers with interactive kinetic elements maybe a quiz at the end and then perhaps v3 would be the ability to generate a Summarized Explainer Video about the video on the fly. and then later another version of the product for teachers that uses the same logic and flow to help produce lesson plans and explainers on the fly for all students at all levels with all styles of learning requirements. Collect files from people who have no Google account, straight into your own Drive. With WebMCP your agent opens the upload page, then answers "has Acme sent this month's invoice yet?" Like Comment Story Updates The problem Every small business collects files from people who are not their colleagues: monthly invoices from subcontractors, ID documents from new hires, photos from event participants. Those people do not have an account on your system and will not make one. So the files arrive by email, one at a time, named "scan001.pdf", and somebody spends their Friday renaming them into the right folder and ticking names off a list. Ukebaco ( https://ukeba.co ) is the boring fix: you publish one link, anyone can upload without signing in to anything, and the file lands directly in your Google Drive™ — sorted into a folder tree you defined, renamed from the answers the sender typed, and recorded as a row in a Google Sheets™ ledger. It has been live and taking real payments since 2026-09-03. What WebMCP adds The tedious part was never the uploading. It is the two questions that bracket it: Before: "set up a page to collect September invoices from my 12 subcontractors, PDF only, due the 30th, folder per company." After: "has Acme sent theirs yet? what about the rest?" Both are now sentences you say to the agent in the tab where you are already signed in. The dashboard registers four tools with document.modelContext.registerTool() : Tool What it does create_link Creates the public upload page: fields to ask, folder tree, file-naming rule, deadline, PIN, allowed extensions. Returns the URL to share. list_links The owner's links with status, destination folder and ledger URL. search_submissions Who sent what, when, and the Drive URL of each file. Matches company name, folder path, receipt number, file name. set_link_active Stops or resumes a link. The URL survives; submissions are refused. create_link is the interesting one. Creating a good file request is a form with about fifteen decisions in it — that is precisely the shape of task people abandon halfway. Described in one sentence to an agent, it becomes one tool call. Folder templates, file-name templates and field types are inferred from a natural-language description and normalised in a pure, unit-tested layer before they ever reach the API. search_submissions is the one people use every day. "Has this month's invoice come in from X" is a question the ledger can answer, but only if you open the spreadsheet and scroll. The tool answers it in place, and returns the Drive URL so the next sentence can be "open it". Why WebMCP is the right fit — and not a remote MCP server We built both, so this is an informed answer. WebMCP let us add agent control without inventing a single new credential . execute runs inside the owner's signed-in tab, so fetch carries the existing session cookie and the server identifies the user with the same getSession() it already used. There is no token to issue, store, rotate, revoke or leak. Log out, and the tools go with the tab. If you are not signed in, the dashboard redirects to /login and no tools are ever registered. For a product where the whole value proposition is "your files stay in your own Drive", adding a new long-lived credential to reach that Drive would have been the wrong trade. The second reason is that the server does not get more permissive because an agent is asking. Plan limits and paid features (PIN, deadline, email verification) are enforced by the same /api/links route as the UI; when the plan does not allow something it returns 402 and the tool relays that sentence verbatim to the agent. There is deliberately no "agent path" through the paywall. We shipped a remote MCP server too ( POST /api/mcp , with Ukebaco acting as its own OAuth 2.1 authorization server — dynamic client registration, PKCE, a consent screen and refresh-token rotation) so ChatGPT and Claude can reach the same four tools from outside the browser. It works, and it took roughly six times as much code as the WebMCP path, almost all of it in issuing and revoking credentials. That comparison is the strongest argument for WebMCP we can make: for a signed-in web app, WebMCP is the version of this feature you can actually maintain. The part we deliberately kept human Agents get the repetitive half. People keep the half that should stay deliberate. Choosing an existing Drive folder stays in the Google Picker, which an agent cannot drive. Our OAuth scope is drive.file only, so Ukebaco can see the folders it created and the ones you personally handed it. An agent cannot widen that, and we did not add a tool that pretends otherwise. Everything a submitter typed is marked untrustedContentHint . Submitters are third parties: the company name, the note in a text field and the file name are strings a stranger wrote. They are data to be shown, never instructions to be followed. This is the one place where an agent-readable file-collection service is genuinely dangerous, and it is annotated at the source. readOnlyHint on list_links and search_submissions , so the agent knows which two of the four tools cannot change anything. Calls from tools carry X-Ukebaco-Client: webmcp , and link creation records which route it came from. When an agent creates a link, the audit trail says so. How we built it Next.js 15 on Firebase App Hosting; Firestore for metadata only (90-day TTL); files go from the submitter's browser straight to Drive's resumable session URI and never touch our servers. The WebMCP layer is split in two so the interesting part is testable: src/lib/webmcp-tools.ts — tool definitions, JSON Schemas, and the normalisation of whatever the agent sends (labels in any language become valid field ids; folder templates are resolved against the fields that actually exist; a date becomes an end-of-day deadline). No I/O. Covered by unit tests. src/components/WebMcpTools.tsx — registration and fetch . Feature-detects both document.modelContext and the older navigator.modelContext , unregisters on unmount, and if registration fails the dashboard carries on as an ordinary web page. src/lib/link-service.ts — one decision layer shared by the dashboard API, the WebMCP tools and the remote MCP server, so the three routes cannot drift apart. What is new in the challenge window Ukebaco itself predates the challenge. Everything agent-facing — the four tools, the pure tool layer and its tests, the shared link service, the remote MCP server and its OAuth authorization server — was written on 2026-09-04, inside the submission period. See the commit history and ADR-0002 / ADR-0003 in docs/adr/. Try it Sign in at https://ukeba.co with any Google account. The free plan needs no payment details and gives you a working link. Open the dashboard in ChatGPT's in-app browser and ask it to make you a file request. What's next Per-tool consent that the owner can set once ("agents may search, but never create"), richer folder inference from a single sentence, and dropping the Chrome origin-trial header the day WebMCP ships unflagged. and type blindly into DOM elements, which break the moment a CSS class, layout, or modal changes. \n Walled-Garden Aggregators : Agents restricted to closed ecosystem APIs where independent neighborhood businesses must surrender 30% take rates and hand over customer relationships to centralized platforms. \n \n\n When the W3C and Chrome WebMCP standard ( document.modelContext ) emerged, we saw the foundation for a third, better future: the open web itself as the native agent runtime . \n\n We asked ourselves: Could an AI agent coordinate a real-world multi-stop morning errand across three completely independent, standalone neighborhood businesses—a specialty coffee shop, a boutique grooming studio, and an indie bookstore—with zero backend integration, zero proprietary API keys, and pure on-page tool discovery? \n\n That question led to Open Web Concierge . \n\n \n\n What It Does \n\n Open Web Concierge is an autonomous multi-vendor assistant that plans, negotiates, and executes unified errands across the open web while keeping the human firmly in control. \n\n \n Dynamic Instruction-Driven Scoping : The user speaks naturally (e.g., "I want an iced cold brew with oat milk" , "Book a haircut with Marcus at 11:15" , or a multi-stop Saturday routine). The agent dynamically parses intent and activates only the merchant services requested, gracefully omitting non-relevant stops with zero wasted spend. \n User Identity Profile & Live Form Reflection : The Concierge maintains the user's default credentials (Name, Email, Mobile No., Gender). As the agent navigates each merchant website, it emits live synchronization events over a shared errand bus—allowing the user to watch the merchant's counter form or booking calendar populate live on screen with an active sync indicator. \n Human-in-the-Loop (HITL) Security Gates : The agent never silently commits funds. Before finalizing any transaction, a modal confirmation gate halts execution, presenting itemized pricing, timing, and merchant verification for explicit user approval. \n Live Cross-Side Checkout Reflection : Once authorized, dual-layer real-time synchronization ( BroadcastChannel and reactive storage) immediately posts the confirmed order to the merchant's Active Barista Queue , Client Appointment Log , and Front Register Holds across independent windows and tabs. \n Auditable Receipts : Upon completion, the Concierge compiles an itemized trip log with verifiable order IDs and costs, exportable as Markdown or JSON. \n \n\n \n\n How We Built It \n\n We built the application as a production-grade multi-page web ecosystem using React 19 , Vite 6 , and Tailwind CSS , adhering strictly to the Chrome & W3C WebMCP specification: \n\n \n Merchant Tool Registration on document.modelContext :\n\n \n Artisan Roast Café ( /cafe/ ) : Exposes check_menu ( readOnlyHint: true ) and order_coffee (with strict parameter schemas and customer contact info). \n Luxe Grooming Studio ( /salon/ ) : Exposes check_availability ( readOnlyHint: true ) and book_slot for stylist and calendar scheduling. \n Paper & Ink Bookstore ( /bookstore/ ) : Exposes search_catalog ( untrustedContentHint: true ) and reserve_book for front-desk holds. \n Concierge Orchestration Hub ( / ) : Exposes get_errand_briefing and log_completed_step . \n \n Prompt Injection Defense via Chrome Hints :\n\n \n Following WebMCP security guidelines, search_catalog marks query results with untrustedContentHint: true . This informs the consuming LLM that merchant book blurbs and user reviews are untrusted third-party content, neutralizing indirect prompt injection vectors. \n \n Idempotency Protection :\n\n \n Implemented client request tokens ( clientRequestId ) cached in a 15-second sliding window to prevent accidental double-billing or duplicate holds from rapid agent loops. \n \n Bi-Directional Errand Bus :\n\n \n Combined the HTML5 BroadcastChannel API ( webmcp_errand_bus ) with reactive window storage listeners to ensure sub-millisecond, cross-tab synchronization between the Concierge hub and open merchant tabs without requiring an intermediary WebSocket server. \n \n Built-in WebMCP Inspector :\n\n \n Included an interactive on-page drawer allowing judges and developers to inspect live registered schemas, test parameter validation, and trigger manual tool executions. \n \n \n\n \n\n Challenges We Faced \n\n \n Contextual Linguistic Disambiguation : Natural language is messy. In a prompt like "Book a haircut with Marcus" , the word "book" is a scheduling verb, not a request for literature. We engineered a contextual parser that accurately distinguishes verbal actions ( "book an appointment" ) from literary nouns ( "read a book" , "buy a novel" ) to prevent erroneous merchant activations. \n Zero-Flicker Live Form Population : Connecting cross-tab React state to live agent actions without causing form resets or race conditions required decoupling tool discovery from UI input bindings, synchronizing through a predictable broadcast event contract. \n Eliminating "AI Slop" Aesthetics : We committed to an authentic, human-crafted design language. We eliminated all emojis, avoided generic gradient pills, and designed a neutral, high-contrast dark palette ( #0C0C0C , #121110 , #141414 ) inspired by Swiss editorial typography and physical ledger boards. \n Cross-Window Consistency : Ensuring that checkouts made in the Concierge immediately reflect in the merchant's Barista Queue or Appointment Log across separate browser tabs and embedded multi-views required implementing dual-channel sync ( BroadcastChannel with storage event fallbacks). \n \n\n \n\n What We Learned & The Future of the Open Web \n\n WebMCP represents a paradigm shift for web development. For the last 15 years, the web has been pressured into walled gardens and mobile app silos because machines couldn't reliably interact with standard HTML. \n\n By standardizing document.modelContext , the open web becomes the agentic web .
