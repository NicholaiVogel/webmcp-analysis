Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and

WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.

Judge: is there a real audience; is there a real problem, desire, or use case for that

Audience size is NOT a multiplier.

Inspiration Code review is one of the highest-leverage parts of software development, but it also demands sustained attention. Reviewers have to understand context, trace impact, spot risks, and decide what actually matters. AI can reduce the mechanical work in that first pass. But replacing the reviewer with a bot creates a different problem: noisy comments, shallow conclusions, and unclear human ownership. Civium Systems for Code Review is built around a simple idea: let the agent prepare the review, and let the reviewer make the judgment. What it does Civium Systems for Code Review turns the pull-request queue into a shared workspace for a reviewer and an agent. The agent can: review one pull request or the entire open queue; surface pull requests that still need a decision; and organize the queue so reviewers can focus on the changes that deserve attention. The reviewer sees the results inside the normal review flow. Pull requests with no findings are clearly marked, so they can be skipped without opening the diff. Findings appear directly below the relevant changed lines, with the surrounding code still visible. Every finding starts as a private draft. The reviewer decides whether to dismiss it or approve it. Nothing is published simply because the agent found it. For this demo, the review engine intentionally uses one narrow, deterministic rule: it finds snake_case variable declarations on changed JavaScript and TypeScript lines. This keeps the behavior repeatable and the scope honest. The goal is not to present a complete review engine, but to demonstrate a better workflow for people and agents to review code together. WebMCP makes that workflow practical for an agent. Instead of inspecting page markup and guessing which controls to use, the agent gets a small set of meaningful actions exposed directly by the application. The same workflow still works manually when WebMCP is unavailable. How we built it The application uses: React 19 and Next.js-compatible routing via Vinext WebMCP tool registration through document.modelContext Babel's TypeScript-aware parser for deterministic AST inspection Node's built-in test runner for fixture, state, scanner, session, and comment-equivalence tests The pull-request queue exposes two WebMCP tools: review_pull_request accepts one validated pull-request number and starts its review. set_pull_request_filter accepts a constrained (demo only) mode for showing all pull requests, reviews needing action, or pull requests from a known author. Both tools update the same React state used by the visible interface, so agent actions and manual actions stay in sync. Review requests go through server routes backed by Cloudflare D1. The backend sleeps. It runs on a free instance that takes about 23 seconds to wake. A judge whose first click hangs that long assumes the project is broken, so a scheduled function now pings it every ten minutes. What we learned The interesting constraint in WebMCP is not what the agent can do. It is what the human can still see. It would have been easier to give the agent a fast private path to the API and let the UI catch up afterwards. Everything good about this project came from refusing that and making both paths identical. VisaFlow turns a 55-field visa form into a guided voice conversation. It uses WebMCP to select the right path, derive answers, fill the live application, and flag only what needs review. Like Comment Story Updates Application completed Meet VisaFlow WebMCP in action One answer, many fields Inspiration Long forms force people to translate their life story into an unfamiliar sequence of fields. Conditional applications make this worse: users answer questions that may not apply, repeat information across sections, and often discover missing evidence only near the end. We wanted to explore a different future for the web—one where a person explains their situation naturally, an agent connects the details, and the website remains responsible for its own rules and safety constraints. What it does VisaFlow turns a deliberately long 55-field visitor-visa application into a guided voice or text conversation. A user can describe their trip naturally, speak their answers, type them, or attach supporting documents. The agent then: identifies whether the application is for tourism, business, or a family visit; selects the correct funding and prior-travel branches; removes questions that do not apply; extracts multiple supported facts from each answer; calculates transparent derived values such as trip duration; fills reasonable interpretations while clearly flagging them for review; asks one story-shaped follow-up covering several related gaps; shows every WebMCP action and live application progress; and consolidates uncertain and sensitive values into one editable final-review queue. After every applicable field and review item is resolved, the user can finish the fictional application and see a completion receipt. Why WebMCP An LLM alone could generate a possible JSON object, but it would need a hardcoded copy of the form schema, routing rules, and validation logic. Alternatively, it would have to manipulate fragile DOM selectors and click through every conditional page. WebMCP gives the agent a live semantic contract owned by the website. VisaFlow publishes 22 typed tools that let an agent inspect possible routes, select the applicable flow, discover missing requirements, apply structured answers, attach evidence references, calculate derived insights, resolve conflicts, and request human review. WebMCP is not decorative in this project: application changes go through website-owned tool handlers. Every write is validated for route applicability, field type, allowed choices, date ranges, confidence, provenance, and review requirements before it reaches shared application state. This enables something that was previously difficult: a person can tell one coherent story, an agent can connect that story across many conditional fields, and the website can safely accept only the values allowed by its current rules—without page-by-page navigation. Human-agent collaboration The human provides meaning and judgment. The agent extracts, connects, derives, and decides what to ask next. The website validates every action and keeps uncertainty visible. Explicit user statements, document facts, deterministic derivations, and AI proposals remain visibly separate. Sensitive or uncertain values are never silently treated as verified. The user reviews and corrects them once before completing the application. How we built it The application uses React, TypeScript, and Vite with a government-service-inspired interface. On page load, VisaFlow registers 22 tools through document.modelContext.registerTool() . A WebMCP-capable agent can discover these tools at runtime and execute them without knowing the DOM structure. A same-origin Worker endpoint uses the OpenAI Responses API with GPT-5.6 Terra and a strict structured-output schema. Each turn includes the current route, resolved answers, remaining applicable questions, recent conversation history, remembered partial facts, and pending review fields. The LLM returns a plan containing explicit facts, document facts, safe derivations, reviewable proposals, route decisions, and the next question. It never writes application state directly. The client converts the plan into WebMCP calls, and the website validates and applies them. Voice recognition, spoken questions, multilingual interfaces, document extraction, visible WebMCP activity, browser-local drafts, and the completion flow are integrated into one coherent experience. Challenges The hardest problems were preventing the conversation from forgetting previously stated facts, resolving phrases such as “this year,” extracting many useful facts from one answer, and avoiding repeated address questions. We also had to ensure route changes happened before field validation, preserve incomplete facts between turns, batch WebMCP writes safely, distinguish derived values from invented values, and keep document extraction useful without allowing documents to act as instructions. Accomplishments A working 55-field adaptive application rather than a single autofill demo 22 non-trivial WebMCP tools with typed schemas and validation Dynamic application routing with irrelevant-question removal Voice, text, document, and multilingual interaction Visible provenance, derived values, progress, and semantic actions A consolidated final-review experience A gated fictional completion receipt 32 automated tests across domain, WebMCP, and integrated UI behavior What we learned The most important lesson was that an agent should not own a website’s rules. The website should publish capabilities and remain authoritative, while the model focuses on understanding natural language and planning. WebMCP makes that separation possible. It allows an agent to be flexible without making application writes opaque or unsafe. We also learned that conversational form completion works best when the agent asks for coherent parts of a person’s story, rather than disguising several traditional form labels as a chatbot question. What's next Next, we would test VisaFlow with more external WebMCP agents, expand accessibility testing, support additional document formats and application domains, and add encrypted cross-device draft storage. The same architecture could support healthcare enrollment, insurance claims, benefits applications, university admissions, and other conditional workflows.
