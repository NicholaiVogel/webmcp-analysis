# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Inspiration The web was built for people clicking buttons, not agents trying to complete tasks. When agents rely on screenshots, coordinates, and brittle selectors, even simple workflows become slow and unreliable. WebMCP offers a better interface—but most existing websites do not support it yet. Dominaitrix was inspired by a practical question: what if we could teach the web we already have to speak WebMCP? What it does Dominaitrix is a sideloadable Chrome extension that installs curated WebMCP adapters on supported websites. Each adapter translates a site’s live interface into structured tools that agents can discover and invoke directly. Our adapters currently support: Managing a live ESPN Fantasy Football draft Exploring Domino’s menus and building a cart Reading Hacker News stories and discussions Searching and navigating Wikipedia articles The difference is dramatic. In two ESPN drafts using the same prompt, ordinary browser control successfully drafted only 3 of 16 intended players and followed 1 of 5 roster instructions. With Dominaitrix, the agent drafted 16 of 16 players and followed 5 of 5 instructions. Dominaitrix does not provide the agent. It gives WebMCP-capable agents a faster, safer, and more reliable way to use existing websites. How we built it Dominaitrix consists of three main pieces: A Chrome extension that installs adapters through chrome.userScripts A shared runtime that registers tools through document.modelContext.registerTool() A static adapter registry containing versioned metadata, compatibility information, tool descriptions, and SHA-256 source digests The extension periodically checks the registry, verifies each adapter’s integrity, and installs or updates it on matching pages. Adapters run in an isolated user-script world by default and expose narrowly scoped tools with structured inputs, outputs, and errors. Every adapter is reviewed and tested in the repository before publication. The project includes an adapter template, automated registry generation, integrity validation, and a browser-like test harness for exercising tools without depending entirely on live sites. We also built privacy-conscious local diagnostics. Dominaitrix records minimized health events—such as the adapter version, tool name, outcome, and broad error category—but never records tool arguments, page content, cookies, tokens, or response bodies. Nothing is uploaded automatically. Challenges we ran into The hardest problem was translating dynamic, human-oriented interfaces into stable agent tools. ESPN’s draft room uses virtualized tables, changing position filters, a live clock, and controls whose meaning changes when the user is on the clock. A delayed instruction could accidentally draft a player during the wrong pick. We addressed this by using stable player IDs, requiring the expected pick number for consequential actions, detecting stale state, and verifying the result after every selection. We faced similar issues across sites: hidden application state, asynchronous UI updates, undocumented APIs, route changes, and actions that can return success before the visible interface has actually updated. Distribution created another challenge. Downloadable adapters make rapid compatibility fixes possible, but they also create a trust boundary. We designed a curated registry with no public upload path, exact source digests, restrictive match patterns, explicit execution worlds, and automated consistency checks. Finally, WebMCP and Chrome’s user-script support are still experimental. We had to handle missing APIs, disabled browser settings, unsupported pages, and partial initialization without leaving users with mysterious failures. Accomplishments that we're proud of We are most proud that Dominaitrix demonstrates a measurable improvement rather than merely registering demo tools. The ESPN experiment showed that structured tools can turn a fragile, time-sensitive workflow into one an agent completes accurately and with time to spare. We are also proud that the adapter system is reusable. The same runtime supports experiences as different as drafting a fantasy team, configuring a pizza, exploring a discussion tree, and navigating an encyclopedia. What we learned We learned that agents do not need unrestricted access to a website’s internals. They need a small set of well-designed capabilities with stable identifiers, precise descriptions, bounded results, and actionable errors. We also learned that successful execution must be verified. A click or HTTP response is not proof that the intended state changed—especially during live, asynchronous workflows. Most importantly, WebMCP is valuable even before websites adopt it natively. An adapter layer can provide an immediate bridge while showing site owners what an agent-native interface for their product could look like. What's next for Dominaitrix Next, we want to expand the curated adapter library and make adapters easier to develop, review, test, and maintain. We plan to add stronger compatibility monitoring, richer local diagnostics, safer confirmation patterns for consequential actions, and tooling that detects when a site change breaks an adapter. An agent can only press the buttons a website gives it. Toolsmith lets it build the one that's missing — and lets you decide whether it keeps it. Like Comment Story Updates Inspiration An AI agent can only press the buttons a website gives it — and those were decided by whoever built the site, months ago. When the button you need isn't one of them, the agent does what agents do: it guesses from the DOM, it scrapes, or it hands you a snippet of Python and hopes you run it. Adding a real one today means leaving the conversation entirely: write an MCP server, host it, edit a config file, restart the client. Minutes to days of work, and a permanent new attack surface, for a function you might call once. WebMCP already moved the button surface into the page — where the user's data and session already live, and where a human is already watching. That's enough to close the loop without leaving. (A note on vocabulary: we say "button" in the interface because that's what it is to the person looking at the screen. The spec calls the same thing a tool, and so does our code.) What it does Toolsmith registers five permanent tools on document.modelContext . One of them, forge_tool , takes a name, a JSON Schema and a JavaScript body, and turns them into a real WebMCP tool the same agent can call seconds later — but only after a human grants it. The loop: the agent calls read_workbench to learn your real column names → calls forge_tool to build the button that isn't there → the page renders it as pending , code on screen and editable, not registered → you press Test run to execute it against your real data before it exists → you press Grant it , which calls registerTool with its own AbortController → the agent presses its new button in the same conversation → Take it back aborts that signal and the button leaves the registry immediately. The count in the header — "buttons the agent can press" — is the honest answer to what can this agent do right now? And a person decided every one of them. How WebMCP is used This is not a wrapper around an existing app; the spec's lifecycle is the product. Every built button is registered via registerTool(tool, { signal }) with its own AbortController . Unregistration isn't a side feature here — aborting that signal is the revocation mechanism the entire safety argument rests on. The tool surface is genuinely dynamic and authored at runtime by the agent talking to the page. getTools() and the toolchange event drive the live count in the header. annotations.untrustedContentHint on every built button, because its output is computed by code an agent wrote minutes ago. annotations.readOnlyHint on the two read-only tools. forge_tool accepts the child tool's inputSchema as a JSON string, validates it, and passes it to registerTool as a real JSON Schema object — schema round-tripping through a tool call. Native document.modelContext when present; otherwise a vendored @mcp-b/global polyfill. The header pill says which one you got. A button you didn't read is not a button you granted Self-extension is only acceptable if refusing is as cheap as granting. So: nothing registers before a human approves; the schema and function body stay on screen and editable, with a Test run that executes against real data before registration; each call spawns a fresh Web Worker with fetch , XMLHttpRequest , WebSocket , EventSource , importScripts , storage and navigator deleted from the global scope before the code is compiled (verified: built code sees typeof fetch === "undefined" ); a 3-second leash terminates runaway loops; editing a granted button unregisters it and sends it back for re-approval; reloading returns every button to pending, never to granted; and every call, with arguments and results, lands in the activity log. This is defence in depth, not a security boundary — a Worker shares the origin, and the README says so plainly. It's enough friction that a button written thirty seconds ago can't quietly drain your data while you're still reading the diff. Challenges we ran into The hard part wasn't generating code — it was revocation. A page that lets an agent extend itself is only defensible if taking the capability back is instant and obvious. WebMCP's AbortSignal -based registration turned out to be exactly the right primitive: one controller per button made grant, edit, take-back and page-reload all collapse into the same mechanism. The second hard part was language. Our first build talked about "dynamic tool lifecycles," which is accurate and means nothing to anyone. Calling it a button — something a person already knows they can be given, and can have taken away — made the same code explain itself. What we learned That the interesting part of WebMCP isn't that a page can expose tools. It's that the set of tools is mutable at runtime , and that mutation can be put in a human's hands. Most of the spec's power lives in the { signal } argument that's easy to skim past. What's next for Toolsmith Cross-origin granting via exposedTo , so one page can hand a vetted button to another. Signed button sets, so a team can publish a reviewed collection instead of each person approving their own. And an output schema, so built buttons can declare structuredContent rather than text.
