# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they

No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like 1 Comment Story Updates logo main operating screen scheduling screen About the Project Inspiration Scheduling sounds simple until real-world constraints begin interacting: machines become unavailable, urgent jobs receive deadlines, tasks depend on one another, and operators override assignments. Traditional optimization software can solve these problems, but describing a model often requires specialized mathematical knowledge. AI assistants make natural-language interaction easier, but an LLM should not be trusted to invent a schedule and claim it is valid. ConstraintLab combines the strengths of both: Humans express goals and judge trade-offs. AI agents translate intent into structured actions. A deterministic solver computes and validates the schedule. We built ConstraintLab to explore what an agent-native optimization workspace could look like—one where the human interface, AI agent, solver, and audit history all operate on the same canonical application state. What It Does ConstraintLab is a browser-based job-shop scheduling workspace. Users can: View jobs, machines, dependencies, deadlines, and downtime windows. Inspect schedules through an interactive Gantt chart. Add or edit scheduling constraints manually. Ask a WebMCP-capable AI agent to inspect and modify the model. Run a real mixed-integer linear programming solver in the browser. Detect when a solved schedule becomes stale after the model changes. Receive deterministic explanations when a model is infeasible. Review every human, agent, and solver action in an audit timeline. A typical interaction looks like this: “Machine 2 will be unavailable between 1 PM and 3 PM, and Job 7 must finish before noon.” The agent discovers ConstraintLab’s site tools, adds typed constraints, and requests a solve. The HiGHS solver—not the language model—computes the resulting schedule. If another request creates a contradiction, ConstraintLab reports the genuine infeasible result and identifies the relevant constraints using deterministic conflict analysis. How We Built It ConstraintLab is built with React, TypeScript, Vite, Zustand, Zod, Web Workers, WebAssembly, HiGHS, WebMCP, Vitest, and Netlify. The most important architectural decision was to maintain one canonical application state. Human interface ──┐ ▼ Domain actions ▲ AI agent ─────────┘ │ Canonical Zustand store ├── Solver ├── Gantt chart └── Audit timeline The interface and WebMCP handlers call the exact same domain actions. There is no separate “agent state” or hidden model that can drift away from what the user sees. ConstraintLab exposes nine typed site tools: get_problem_state add_job update_job add_constraint remove_constraint set_objective solve_problem get_solution analyze_infeasibility Every tool input is validated with Zod, and write operations are validated again inside the domain layer. Agent arguments are treated as requests—not as trusted data. For optimization, we compile the scheduling problem into a CPLEX LP-format model and send it to HiGHS running inside a Web Worker. This prevents the WebAssembly solver from blocking the interface. The objective is to minimize makespan: $$ \min C_{\max} $$ For every job (j), completion must satisfy: $$ C_{\max} \geq S_j + p_j $$ where (S_j) is its start time and (p_j) is its duration. Precedence, deadlines, machine assignments, availability windows, and non-overlapping jobs are represented as linear constraints. Binary ordering variables handle jobs that may compete for the same machine. The resulting assignments are translated back into application objects and applied through a single solver-result domain action. We also track a modelVersion . Every structural edit increments this version, and every solution records which version it solved. If the two differ, the interface immediately displays: Model changed — re-solve required. Challenges We Ran Into One major challenge was correctly separating language understanding from mathematical correctness. The agent is useful for translating a human request into typed tool calls, but it must never become the scheduling engine. Keeping that boundary strict influenced the entire architecture. The solver integration was another challenge. HiGHS accepts LP-format text rather than a convenient JavaScript model object, so we built an explicit model compiler and solution translator. Variable names had to remain stable enough to map solver columns back to jobs and resources. Scheduling downtime is more complicated than adding a simple bound. A job must occur either before or after an unavailable window, which requires additional binary decisions and big-(M) constraints. Infeasibility explanations were also difficult. A solver can report that a model is infeasible without producing an explanation suitable for a user. Instead of asking an LLM to guess, we built typed, rule-based checkers that examine deadlines, precedence chains, locked starts, resource assignments, and machine availability. The generated summaries are based on computed scheduling facts. Finally, WebMCP is still an emerging browser capability. We needed feature detection, top-level tool registration, a fallback path, and a clear unavailable state so that the human scheduling interface remains functional even when WebMCP is not enabled. Accomplishments That We’re Proud Of We are especially proud that ConstraintLab demonstrates a complete agent-to-solver loop rather than a simulated AI demo. The AI agent modifies the same state that the human sees. The schedule is computed by a real deterministic MILP solver. Constraints have stable IDs and structured types. Invalid agent inputs are rejected safely. Solver work runs outside the main browser thread. Model edits automatically invalidate stale solutions. Infeasibility explanations come from deterministic analysis. Every human, agent, and solver action is auditable. The entire application works without an AI agent. The complete optimization stack runs inside the browser and can be deployed as a static application. Our headline demo intentionally creates a real contradiction involving Job 4, Machine 2, machine downtime, and a deadline. The solver returns an actual infeasible status, and ConstraintLab identifies the relevant conflict instead of showing a scripted response. What We Learned We learned that the most valuable role for an AI agent in optimization is not solving the mathematics itself. Its value is translating intent, operating tools, and helping users navigate the model. Typed tools are essential. Allowing an agent to submit arbitrary mathematical expressions would make validation, auditing, and explanations significantly less reliable. A deliberately small vocabulary of structured constraints creates a much safer system. We also learned that shared state is more important than chat history. The collaboration feels trustworthy because every agent action appears immediately in the visual workspace, and every human edit is visible to the agent during its next inspection. Finally, infeasibility is not merely an error state. In real optimization work, discovering why requirements conflict can be as valuable as finding an optimal schedule. Checkpoints and reversible model changes. Transactional batches of agent-proposed changes. Interactive rescheduling and assignment locking. Richer deterministic conflict analysis. Larger industrial scheduling models. Import and export support for operational datasets. Additional optimization domains such as workforce, classroom, and logistics planning.
