# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

What DOMHamster does DOMHamster helps coordinate a fictional, non-emergency volunteer operation with eight requests and five available volunteers. The agent can use WebMCP tools to: Read the current requests, volunteers, assignments, and audit history Create a complete assignment draft Check whether the draft is valid Repair scheduling conflicts Prepare a specific draft version for human review Commit the plan after the coordinator approves it Request one contact record when it is actually needed Review a sanitized history of important actions The agent does not have permission to do everything. How the demo works The agent starts by reading the current coordination data and creating a full assignment draft. Train an online classifier with your browser agent while humans control labels and model changes through WebMCP Like 1 Comment Story Updates Label Loop Why we built it Software can rank uncertain samples, update a classifier, and calculate metrics. A person still needs to decide what an ambiguous example means. Most labeling interfaces expose this process as buttons and tables, leaving a browser agent to infer which actions are safe. We wanted the page to publish those operations directly while keeping label decisions under human control. Support-ticket routing gave us a small task with visible results. Label Loop classifies tickets as billing , bug , or access . What it does Label Loop runs an online multinomial Naive Bayes classifier in the browser. The session begins with nine seed examples, twelve unlabeled review candidates, and a fixed nine-item holdout set. The agent ranks unlabeled tickets by predictive entropy and can place up to three in the review queue. A person assigns each label through the page. The agent then trains a batch and evaluates the updated model. The interface shows probabilities, per-class F1, token weights, a confusion matrix, calibration, and log loss. A ledger records label provenance, while a separate trace records WebMCP calls. Model-setting proposals stay pending until a person accepts or rejects them. How we built it The project is a static Vite application with no backend or external model API. The classifier and session state run in page memory, so reloading creates a fresh deterministic session. For a document $d$ and class $c$, the model calculates: $$ P(c \mid d) \propto P(c)\prod_{w \in d}P(w \mid c) $$ Token likelihoods use Laplace smoothing: $$ P(w \mid c)=\frac{N_{w,c}+\alpha}{N_c+\alpha |V|} $$ $N_{w,c}$ is the count of token $w$ in class $c$, $N_c$ is the class token total, and $|V|$ is the vocabulary size. Each confirmed example increments these counts. Review candidates are sorted using normalized predictive entropy: $$ H(p)=\frac{-\sum_{c=1}^{K}p_c\log p_c}{\log K} $$ A value near one means the probabilities are close, so that ticket moves toward the front of the review queue. One-vs-rest log-likelihood differences show which tokens push the model toward each class. Holdout evaluation returns aggregate metrics without returning individual rows. How WebMCP is used The page registers nine tools with document.modelContext.registerTool : Tool Access Job get_training_state Read Model, queue, configuration, and metrics inspect_uncertain_samples Read Entropy-ranked unlabeled tickets inspect_model_diagnostics Read Features, confusion counts, calibration, and loss predict_ticket Read Probabilities, entropy, and route-or-review decision evaluate_model Read Aggregate holdout metrics inspect_training_history Read Checkpoints and label provenance queue_label_review Write A bounded request for human labels train_confirmed_batch Write Incremental training on confirmed examples propose_model_config Write A pending configuration proposal Each definition has JSON Schema and runtime validation. queue_label_review has no label input. Samples move through unlabeled , awaiting-human , confirmed , and trained states, and training accepts only confirmed examples. Configuration changes require a separate human action. Challenges WebMCP browser support was the first practical problem. We verified all nine tools in Chrome 152 and built a deterministic replay for ordinary browsers. Replay events are labeled local replay so they cannot be confused with external calls. The second problem was label provenance. Hiding a control in the interface would not prevent an agent tool from sending the same data. We removed labels from the review-request schema and made the training operation check sample state at runtime. Evaluation tools return aggregate metrics, feature weights, and confusion counts while omitting individual holdout examples and answers. We also corrected a misleading setting whose original name implied automatic training. It is now a review threshold. Predictions below it go to a person, and training remains limited to confirmed examples. What we learned Useful WebMCP tools matched domain operations instead of interface controls. queue_label_review gives the agent a clear capability and limit; a tool such as click_review_button would preserve the ambiguity of the page. Human approval also needs a technical boundary. Label Loop keeps label assignment out of the agent tool set and checks provenance again when training starts. Since the model runs locally, every displayed probability, token weight, and metric can be reproduced without an account or API key. Like Comment Story Updates AI Usage Skill Visualizer — WebMCP Challenge Edition WebMCP E2E workflow completed with PDF generation and reverse handoff Evaluation result with 438/500 score, PDF generation, and successful reverse handoff Generated AI Usage Report with an overall score of 438/500 Chrome extension extracting the ChatGPT conversation log for evaluation Inspiration This project started with a question about my own use of AI. During a conversation with AI, it pointed out something about the way I was using it. That made me wonder: How well am I actually using AI? Then another question came to mind: Isn't everyone using AI in more or less the same way? And if not: What is the difference? That was the starting point for visualizing human AI usage skills. By that time, I had already been using AI for more than two years. Because of that experience, it felt natural to me that the final output alone could not tell you how well someone had used AI. If I wanted to understand how a person used AI, I also needed to look at the conversation process that led to the final result. So the idea was to evaluate the conversation log, the final output, and the relationship between them. That became the foundation of AI Usage Skill Visualizer. As I continued developing it, I noticed something else. Knowing whether someone uses AI, or how much they use it, is not the same as understanding how well they can actually use it. And knowing about AI is not the same as being able to use AI effectively in real work. AI Usage Tracking ≠ AI Usage Skill AI Knowledge ≠ Practical AI Capability From the beginning, the concept was also broader than just building a standalone evaluation application. I wanted to connect the whole process: Use AI → Capture the interaction process → Evaluate human AI usage → Visualize the result → Return the result to the AI workflow At the time, however, I did not have a practical way to directly connect the environment where people were actually using AI with the Visualizer. So I started with what I could actually implement at the time: a standalone application. The first approach was simple. Users manually entered their conversation logs and outputs, and the Visualizer evaluated them. But once I started using it myself, I realized that this manual input process was more cumbersome than I had expected. To reduce that friction, I built a Chrome extension that could bring ChatGPT conversations into the Visualizer. That made the process of importing conversation logs much simpler. There was still another gap between the AI workflow and the Visualizer. This is where WebMCP changed what was possible. Using WebMCP Site Tools, the AI workflow can directly use the Visualizer's capabilities to run the evaluation, generate a PDF report, and read the generated report back into the workflow. By combining that with the Chrome extension and reverse handoff, I was also able to return the evaluation result to the original ChatGPT conversation. The Challenge Edition demonstrates this flow: Chrome Extension × WebMCP × AI Usage Skill Visualizer → Evaluation → PDF Report → Reverse Handoff → ChatGPT Summary WebMCP was not something I added afterward simply because this was a WebMCP Challenge. From the beginning of the idea, I wanted to connect everything from using AI, to evaluating how it was used, to returning the result back to the AI workflow. Using WebMCP finally allowed me to move closer to that original concept in a practical way. Human Focus in AI. What it does AI Usage Skill Visualizer — WebMCP Edition is a Challenge-specific implementation that demonstrates how WebMCP can connect an AI interaction directly to AI usage evaluation. The project combines: Chrome Extension × WebMCP × AI Usage Skill Visualizer The Chrome extension can extract a ChatGPT conversation and provide a path for that conversation to become Visualizer input. For the public Challenge demo, the built-in public sample data is used so that the evaluation workflow can be reproduced consistently. The user starts the analysis from AI Usage Skill Visualizer. From there, Work uses WebMCP Site Tools to continue the workflow. The WebMCP workflow can: receive the conversation log and final output run the Challenge-specific evaluation return structured evaluation results generate a PDF report read the generated report back into the workflow After the evaluation and report workflow are complete, the result is prepared for reverse handoff. The Chrome extension then returns the evaluation prompt to the original Chrome ChatGPT conversation. The extension: identifies the target ChatGPT conversation receives the evaluation payload finds the ChatGPT composer inserts the evaluation prompt verifies the inserted text It deliberately does not click Send or simulate Enter. The final submission remains under human control. After the user manually sends the prompt, ChatGPT summarizes the evaluation inside the original conversation. The complete demonstration flow is: Chrome Extension → WebMCP → AI Usage Skill Visualizer → Evaluation → PDF Report → Reverse Handoff → ChatGPT Summary The Challenge Edition uses deterministic evaluation logic created specifically for this public demonstration. It is intentionally separate from the production AI Usage Skill Visualizer evaluation engine. The important part of this Challenge project is not the simplified score itself. The important part is that WebMCP turns the Visualizer from a separate destination into something that can participate directly in an AI workflow. How we built it I built the WebMCP Challenge Edition as a separate implementation from the production AI Usage Skill Visualizer. The Challenge application uses a lightweight web interface built with HTML, CSS, and JavaScript, together with a local backend for report generation and supporting the end-to-end workflow. The application exposes WebMCP Site Tools that can be discovered and called from Work. The main tools are: evaluate_ai_usage_demo This tool receives structured evaluation input including: conversation_log output It then: receives the submitted conversation log and output displays them in the Visualizer runs the Challenge-specific deterministic evaluation renders the evaluation result returns structured evaluation data through WebMCP create_ai_usage_report This tool receives the evaluation result and generates the PDF report used by the Challenge workflow. The generated PDF is not only a UI result. It becomes a real workflow artifact that can be passed to the next stage. read_generated_report This tool reads the generated report back into the workflow so that Work can verify the result and continue the process. Together, these Site Tools allow Work to move from structured input through evaluation and report generation without requiring the user to manually transfer intermediate results between each stage. The Challenge Edition also integrates with a Chrome extension. The extension plays two roles. First, it can extract a ChatGPT conversation and provide a path for that conversation to become Visualizer input. Second, it supports reverse handoff. After the WebMCP evaluation and report workflow are complete, the evaluation result can be returned to the original Chrome ChatGPT conversation. The extension inserts the evaluation prompt into the ChatGPT composer and verifies that the intended text was inserted correctly. It does not automatically submit the prompt. The user manually clicks Send. This creates an intentional boundary: WebMCP and the extension automate the workflow, while the human retains control of the final submission. For the public demo, the built-in public sample data is used as the evaluation input for reproducibility. The Challenge-specific scoring logic is deterministic and separate from the production evaluation system. No external AI API is required for Challenge scoring.
