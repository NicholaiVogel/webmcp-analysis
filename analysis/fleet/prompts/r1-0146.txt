Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

- 7-8: strong coherence and intentionality; central workflow appears functional; minor

  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that

Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates WebMCP-powered inference routing lab comparing Round Robin with capacity- and load-aware routing on heterogeneous workers Inspiration AI inference infrastructure is increasingly heterogeneous: workers can have very different capacities, yet simple strategies such as Round Robin still treat them as interchangeable. A slow worker can build a large queue while faster capacity remains available elsewhere. At the same time, browser agents often interact with applications indirectly by inspecting interfaces, finding controls, and deciding what to click. For infrastructure software, however, operations like comparing routing policies or inspecting a bottleneck have much richer semantics than the buttons that trigger them. ThermalMesh Lab grew from one question: What if an AI agent could understand and operate inference infrastructure through domain-level tools instead of automating a dashboard by sight? What it does ThermalMesh Lab is a browser-based simulator for heterogeneous AI inference clusters. Users can configure workers with different abstract capacities, generate deterministic workloads, and compare two routing strategies: Round Robin — equal distribution without considering capacity or load. Inference-Aware (ThermalMesh) — a simplified strategy using capacity, load, and estimated completion time. The simulator exposes TTFT, queue latency, throughput, completed and unfinished requests, worker utilization, and queue depth. The same application can also be operated by an AI agent through WebMCP Site Tools. An agent can configure the cluster and workload, run benchmarks, compare policies, inspect bottlenecks, and apply a routing strategy. Humans and agents share the same application state, so every agent action is immediately reflected in the dashboard. ThermalMesh Lab is a browser-based simulation, not a hardware benchmark. How we built it ThermalMesh Lab is built with React, TypeScript, and Vite and runs entirely in the browser. The simulation engine generates a deterministic seeded request trace and gives both routing policies the same workload, making comparisons reproducible. WebMCP is integrated through document.modelContext.registerTool() . The application exposes seven domain-level Site Tools: get_cluster_state configure_cluster configure_workload run_benchmark compare_routing_policies inspect_bottlenecks apply_routing_policy The WebMCP layer does not maintain separate agent state. Site Tools and the visible React interface call the same validated application/store operations. We also implemented a state-dependent tool lifecycle. After a valid comparison, ThermalMesh Lab dynamically exposes an eighth tool: apply_winning_configuration If the cluster or workload changes, the comparison becomes stale and that tool is removed. In the deployed application this creates a live: 7 tools → comparison → 8 tools → scenario change → 7 tools lifecycle driven entirely by application state. The application requires no backend, database, authentication, or paid API and is deployed as a static site on Cloudflare Pages. Challenges we ran into The biggest challenge was making WebMCP a real application interface rather than a collection of tools that simply mimic button clicks. Operations such as compare_routing_policies and inspect_bottlenecks needed to represent actual infrastructure semantics while keeping the human UI and agent perfectly synchronized. Dynamic registration also introduced lifecycle problems. We had to prevent duplicate or stale registrations, ensure tools always operated on current state, and remove the winning-policy tool immediately when its comparison became invalid. The simulator itself required careful handling as well. Both policies needed identical request traces, overloaded scenarios had to remain numerically safe, and unfinished requests could not appear as misleading zero-latency samples. One of our first live agent tests produced an unexpected result: the agent realized its initial workload had completely saturated the cluster, reduced the workload, reran the comparison, and then selected a better routing policy. That showed us both the potential of semantic tools and the importance of precise tool descriptions when working with autonomous agents. Accomplishments that we're proud of We are especially proud that WebMCP is not an isolated demo layer. The human interface and the AI agent genuinely operate the same application. In live testing, ChatGPT successfully discovered the Site Tools, configured the cluster and workload, compared routing strategies, analyzed the bottleneck, and applied the selected routing policy. The state-dependent lifecycle also works end to end: 7 base tools → comparison → 8 tools → invalidation → 7 tools We are also proud that the simulator does not artificially make Inference-Aware routing win. With homogeneous, lightly loaded workers, both strategies can produce effectively identical results. Under heterogeneous load, differences emerge naturally. In one live test: Round Robin completed 620 requests Inference-Aware routing completed 741 requests TTFT p95 fell from roughly 23.1 seconds to 1.7 seconds Unfinished requests fell from 123 to 2 More importantly, the agent was able to explain why: Round Robin continued sending equal traffic to a much slower worker, creating a large queue, while Inference-Aware routing shifted work toward available capacity. What we learned The biggest lesson was that WebMCP becomes much more powerful when tools represent application semantics rather than UI actions . A tool such as compare_routing_policies gives an agent far more reliable context than asking it to discover controls, run separate simulations, locate the results, and infer how the metrics relate. We also learned that agent capabilities do not need to remain static. Exposing apply_winning_configuration only when a valid comparison exists gives the agent an interface that reflects what the application can meaningfully do at that moment. The simulator taught us another important lesson: overloaded-system benchmarks can be misleading when unfinished work is ignored. A policy may appear to have better median latency simply because its slowest requests never complete inside the observation window. We therefore treat completion and unfinished work as first-class comparison signals rather than hiding them. What's next for ThermalMesh Lab The challenge version intentionally focuses on a small, reliable WebMCP experience. Next, we would like to add additional well-defined routing baselines such as Weighted Round Robin and Least Queue , along with richer workload patterns, request classes, worker failures, and longer-running experiments. ThermalMesh Lab could also evolve into a broader agent-native environment where agents design experiments, compare multiple strategies, explain tradeoffs, and iteratively search for better infrastructure configurations. The broader idea we want to explore is simple: Instead of teaching AI agents how to click through infrastructure software, make infrastructure software directly understandable to agents. Saying otherwise would have been an easier pitch and a false one. ## What we learned **Structure is what makes memory shareable.** Category, tags, source, and confidence are what let a second site retrieve something specific, apply it, show its work, and let a person govern the result. Unstructured recall cannot do any of those four things. **Trust surfaces are product features, not compliance overhead.** The lineage drawer and the labelled telemetry stream are what make people believe the rest of it, and they were among the cheapest things in the build. **Explainability is a design constraint, not a feature you add later.** Choosing lexical matching over embeddings looked like a downgrade until we tried to render *why* a memory was applied. The interpretable pipeline turned out to be the product. ## What's next for Tether **Per-site scoped consent and real accounts.** The cross-origin story above, which is the difference between a demo and infrastructure. - **A small client library** so a site joins in a few lines instead of reimplementing the contract. - **Memory decay and conflict resolution.** Preferences change, and the layer should notice when a new statement contradicts an old one instead of accumulating both. - **Richer context types past preferences:** working conventions, project constraints, domain vocabulary. The two demo sites are an illustration. The direction is a shared memory layer that any experience can build on, where the person keeps the keys. You have to distinguish between code that represents the intended architecture and code that exists because an agent needed to make the next step work. Flip back to production and those tools become part of the application. What we learned I learned how far the browser has come as a capable operating system. The tradeoffs compared with local development using a non-browser JavaScript runtime are worth seriously considering. The biggest feature in favor of the browser is that it sandboxes the agent extremely well. The big unlock with coding agents locally was allowing them to interface with software in the same way users do. WebMCP promises a similar unlock, with a very important distinction. Operating system evolution has generally assumed the terminal is safe. Browsers, meanwhile, have spent decades evolving under the assumption that users cannot be trusted. That distinction matters when the user is an agent. A browser-native development environment gives us a mature security model for software agents while still exposing the capabilities they need to operate on real software. Inspiration Approval interfaces often live beside an agent rather than inside the interface the agent can actually use. A screen may say “approved” while the agent’s available actions remain unchanged. LedgerRehearsal asks a narrower question: what if the WebMCP tool surface itself became shared interface state between a person and an agent? The project uses a familiar accounts-receivable scenario because the stakes are easy to understand. An overdue reminder may be reasonable when an invoice is unpaid and wrong seconds later if a payment arrives. The interesting moment is not generating the reminder; it is proving that a previously reviewed permission disappears when its factual basis changes. What it does The agent begins with three safe tools: inspect_accounts , propose_collection_actions , and rehearse_transition . How it was built LedgerRehearsal is a React 19 and TypeScript application built with Vinext for Cloudflare Sites.
