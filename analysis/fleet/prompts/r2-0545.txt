# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

The host holds the social knowledge — who divorced whom, which cousins feud, who must flank the grandmother. But turning that knowledge into a valid arrangement of 24 people across 5 tables is a constraint-satisfaction puzzle that shifts every time an RSVP lands. That second half is exactly what agents are good at and humans hate. WebMCP is the missing contract that lets each player play their half on the same board . What it does SeatCraft is an event seating planner with two first-class users: The host drags guests between tables, locks non-negotiable seats (the couple sits at the head table, period), and states messy truths as rules: Aunt Carol and Uncle Jim — apart (divorced 2019) . The agent works through 15 WebMCP tools registered on navigator.modelContext : guest/table CRUD, seating moves, a three-type constraint system ( together / apart / at_table , each with a human-readable note), a violations reporter, and auto_seat — a solver that honors every rule and never moves a host-locked guest . When the agent tries to move a locked seat, it's refused with a message telling it to ask the host. The human always wins. How we built it Deliberately zero-dependency: vanilla JS, no build step, no backend — a static page hosted on GitHub Pages. Four modules share one state store (localStorage-persisted, pub/sub): the human UI (drag/drop, locks, rule chips, violation badges), the WebMCP tool surface, a constraint solver (union-find clustering of must-sit-together pairs, group-affinity greedy fill, pairwise-swap repair), and the shared model. A human drag and an agent seat_guest call are literally the same mutation with a different source tag — that's the whole thesis in one line of code. Tools register on the browser's native navigator.modelContext when present (Chrome's WebMCP for testing flag today); otherwise a small spec-shaped shim provides the identical API, so extension bridges and the built-in Agent Console drive the same surface native browsers will. Challenges we ran into Making the solver's output socially plausible, not just constraint-valid — early versions satisfied every rule while exiling one work friend to the family table. The lock system (agent-proof seats) and violations-in-every-response did more for human-agent collaboration than any additional tool would have. Agent-readable refusals are a feature, not an error. What's next for SeatCraft Per-seat placement with adjacency rules, multi-event templates, exportable place cards, and native testing as Chrome's flag rolls toward stable in Q4 2026. The problem Frontend audit tools are good at measuring websites, and coding agents are good at working inside repositories. The handoff between them is the weak point. Most audit results are presented as score dashboards or lengthy reports designed for people. When a coding agent tries to use them, it has to scrape the page, interpret screenshots, follow buttons and reconstruct important context that may have been lost along the way. A copied recommendation such as “improve accessibility” is not enough. LINECALL advances the schedule from R1 to R2, displays a visible receipt, and removes the temporary apply capability. The active tool lifecycle is therefore: [ 4 \rightarrow 5 \rightarrow 4 ] A second test asks the agent to move the Opening sequence. Cue Q014 is human-locked, so LINECALL blocks the change. There is no tool that allows the agent to remove the lock or approve its own request. How we built it LINECALL is built with React 19, Vite 8, modern CSS, the WebMCP Imperative API, and Node’s built-in test runner. The WebMCP layer uses document.modelContext.registerTool to expose five purpose-built tools: linecall_get_run_snapshot linecall_compare_retime_options linecall_preview_segment_retime linecall_set_cue_readiness linecall_apply_approved_retime The tools use strict JSON schemas, explicit revision checks, deterministic plan IDs, and WebMCP trust annotations. The schedule engine is deliberately separate from the language model. It owns: Chronology validation. Minimum spacing rules. Hard-out enforcement. Schedule revisions. Human-owned cue locks. Stale-plan rejection. Exact approval binding. One-time application receipts. The agent helps reason about the available options, but the deterministic engine decides whether the resulting cue changes are valid. The user interface was also designed around two different needs. Operators see a dense, human-friendly cue score with timing, readiness, locks, conflicts, approval state, and receipts. Agents receive a semantic tool interface instead of having to guess what buttons or page elements mean. I added focused agent evaluation cases covering direct inspection, safe retiming, exact-plan application, locked-cue refusal, missing unlock authority, readiness updates, and unrelated questions where no LINECALL tool should be selected. Challenges we ran into The hardest challenge was designing useful agent authority without making the agent dangerously powerful. It was not enough to reject an unsafe call after it happened. The interface needed to make unavailable authority genuinely unavailable. That is why the apply tool does not appear before approval, appears only for the approved plan, and disappears immediately after use or invalidation. State management was another major challenge. A plan prepared at revision R1 must not be accepted after the schedule has changed. Every timing mutation therefore carries both an exact plan ID and an expected revision. The schedule rules also had to handle more than simple arithmetic. A timing change can create chronology conflicts, spacing violations, hard-out failures, or collisions with human-locked cues. The system needed to explain those conflicts clearly enough for both the agent and the operator. WebMCP browser support is still a new area, so verification required more than checking that JavaScript functions existed. I tested registration, discovery, tool schemas, handler behavior, the visible interface, and the complete approval lifecycle in a real Chromium production build. I also had to make sure the browser evidence process did not modify the project while the project was being fingerprinted for verification. That required separating temporary browser artifacts from the source tree and tightening the build-input checks. Accomplishments that we're proud of The biggest accomplishment is that LINECALL demonstrates a complete collaboration loop rather than a simple tool-call demo: The agent reads the current state. It compares multiple futures. Deterministic rules reject the unsafe option. The agent prepares an exact preview. The human reviews and approves it. The agent applies that exact plan once. The system advances the revision and leaves evidence. A separate locked request is refused. The project has: 30/30 passing tests. A passing production Vite build. A passing Chromium production interaction rehearsal. WebMCP contract and discovery tests. Agent tool-selection and call-order evaluations. A permanent HTTPS deployment. Seven replayed challenge cases with matching expected calls and arguments. An MIT open-source license. A complete illustrated README and narrated demonstration video. We are especially proud that human approval changes the browser-visible capability surface itself. Approval is not just a message or a modal. It changes what the agent is technically able to call. What we learned We learned that semantic tools are much more useful than exposing a general-purpose interface and asking an agent to guess how it works. A tool such as linecall_compare_retime_options gives the agent a meaningful domain operation. It communicates intent, inputs, constraints, and results directly. That is clearer and safer than asking the agent to click through a timetable. We also learned that safety should be represented in the capability model whenever possible. A missing tool is stronger than a tool that is always available but usually refuses. Another important lesson was that language models and deterministic systems are good at different things. The model is useful for interpreting a request and comparing alternatives. The schedule engine is better at enforcing exact rules. Keeping those responsibilities separate makes the whole system easier to test and trust. Finally, we learned that a convincing WebMCP project needs three kinds of proof: The tools are correctly defined. The product works in a real browser. The authority boundaries behave correctly over time. Like Comment Story Updates Hopyard Designer with webMCP Inspiration Planning a hopyard is a connected design problem. Plant spacing affects the number of plants and the planting-stock cost. Pole spacing changes the structure and material quantities. Wire, anchors, wind loads, and labor all affect the final estimate. Hopyard Designer already helped growers and installers work through these decisions in a visual web app. The WebMCP Challenge gave us a chance to explore a harder question: can an AI agent help compare design alternatives without hiding changes from the farmer or taking control of the final decision? We wanted the farmer and the agent to work in the same design space. The agent should be able to read the current plan, prepare alternatives, and explain the differences. The farmer should be able to inspect each proposal in the existing 2D and 3D views before deciding what to keep. What it does Hopyard Designer calculates planting-stock cost, facility quantities, preliminary structural loads, and a live material estimate from a hopyard design. As the design changes, the app updates: pole and anchor quantities main wire, training wire, and twine lengths hop positions and planting-stock cost preliminary wind and crop-load checks a construction-oriented 2D plan an interactive 3D farm a downloadable estimate PDF For the challenge, we added a WebMCP workflow that lets an agent create alternatives without changing the original plan. In the demo, the agent compares a Korean I-shaped training layout with a North American 18-foot Y-shaped reference. Both options appear side by side with their plant counts, material requirements, estimated costs, and engineering status. The farmer chooses which option to preview. The selected candidate appears in the same 2D and 3D workspace, but it is not committed yet. How we built it The application uses Next.js, React, and TypeScript. Zustand manages the active design and a separate candidate workspace. Konva renders the 2D construction plan, while Three.js renders the farm in 3D. We used BlenderMCP to create a reusable GLB asset kit containing pole variants, anchors, turnbuckles, wire hardware, and low-poly hop geometry. The web renderer places these assets procedurally instead of loading a fixed model of the whole farm. This keeps every candidate editable and allows the design to update immediately. Repeated components use instancing to keep the 3D view responsive, even when the farm contains hundreds of plants and many structural elements. How WebMCP works The design page initially registers five WebMCP tools: get_design_context list_regional_profiles simulate_design show_candidates preview_candidate The agent starts by reading the current design and its calculated results. It can then simulate alternatives and place up to three candidates in the shared comparison tray. When a candidate enters preview, the page dynamically registers two additional tools: apply_candidate discard_preview This changes the available tool set from five to seven. Apply and Discard only exist while a preview is active. After either action, the page returns to five tools. This creates a visible review step. The agent can prepare and preview options, while the farmer uses the shared interface to decide whether to apply or discard the active preview. The apply_candidate tool description explicitly directs the agent to use it only after user approval. WebMCP inputs use strict JSON Schema and are validated again with Zod at runtime. Candidate IDs are deterministic. Preview stores an exact copy of the active design, so Discard can restore it without relying on reverse calculations. The production site uses Chrome's WebMCP Origin Trial. We also built CDP-based checks that verify tool registration, tool invocation, the five-to-seven-to-five lifecycle, responsive layouts, and browser console errors against the live page. Existing product vs. challenge work Hopyard Designer existed before the challenge with: a human-operated design form planting-stock and material calculations preliminary structural-load calculations live Korean material estimates authentication and project saving 2D and 3D visualization estimate PDF export The following work was added for the WebMCP Challenge: seven WebMCP tools with runtime validation deterministic, non-destructive candidate simulation the agent design alternatives tray temporary candidate previews in the existing 2D/3D workspace dynamic Apply and Discard tool registration the five-to-seven-to-five tool lifecycle Korean and North American reference profiles the reusable BlenderMCP GLB asset kit the public /design/demo judge route browser-level WebMCP verification English and Korean UI, help, PDF, narration, and caption support The complete source repository is available under the MIT License. Challenges we ran into Keeping the workflow non-destructive An agent needs enough freedom to explore, but a design tool should not silently overwrite a farmer's work. We separated simulation, display, preview, and application into distinct states. A simulation creates a candidate without touching the active design. The candidate only changes the shared canvas when it enters preview. The original design remains available for exact restoration. Making browser support testable WebMCP availability depends on the browser runtime. A browser without the API can make a correct implementation look broken. We added an Origin Trial token for the production origin and built browser-level checks instead of relying only on mocked unit tests. These checks exercise the real tools through Chrome and verify the complete lifecycle. Rendering a full farm in 3D A detailed plant model looked good by itself but became too expensive when repeated hundreds of times. We replaced it with a low-poly procedural asset kit and used instancing for repeated components. The resulting farm can still be rotated and zoomed while remaining connected to the editable design. Comparing regions without inventing data The Korean profile can use the active HOPEDEN catalog. The North American profile is explicitly identified as a reference configuration. The app does not pretend to provide live US pricing or local engineering approval. Both the interface and the WebMCP results preserve that distinction.
