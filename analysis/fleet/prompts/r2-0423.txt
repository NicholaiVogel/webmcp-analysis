# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Furthermore, naive real-time agent architectures suffer from the polling trap in which agents repeatedly ping game state to check for changes, rapidly burning token budgets and hitting rate limits just asking "Has anything happened yet?" The developer only hosts static WebGL assets achieving zero marginal inference cost while empowering an autonomous agent to act as the game's dynamic Dungeon Master. What it does Crown and Cipher is a 3D open-world detective game set in a low-poly city, running natively in Unity 6 WebGL and driven by a WebMCP agent: Procedural Mystery Generation: Each playthrough procedurally selects a new killer, establishes three essential investigation leads, and generates an indirect knowledge network among city residents. Living NPC Roleplay: Suspects are not rigid chatbots; the agent temporarily possesses individual characters, adhering strictly to each NPC's bounded knowledge graph. Zero-Polling Event Loop: Through an asynchronous, promise-based wait tool, the game halts agent execution until the player speaks or interacts, eliminating token waste during exploration and driving. Dynamic Win Validation: The agent validates clues, enforces investigative requirements, and triggers the victory state once the player pieces together the full case. How we built it The project establishes a bidirectional bridge between Unity's native WebGL runtime and the browser's model context interface: Unity Controller ( WebMCPManager.cs ): Manages procedural case assignment, orchestrates the NPC knowledge matrix, dispatches dialogue events, and calls into native JavaScript functions via [DllImport("__Internal")] . Like 1 Comment Story Updates Inspiration Many schools in Indonesia teach chemistry without a laboratory that is safe or complete enough for students to run experiments themselves. Teachers describe reactions on a whiteboard, and students memorise colour changes they have never actually seen. The missing piece is not information. It is the instructor standing beside you who pours the reagent, points at the bubbles as they form, and stops you before you make an unsafe combination. We wanted to find out whether an AI agent could take that role, and WebMCP is the first thing that makes it possible. A chatbot can describe a reaction. With WebMCP, it can run one. What it does EZI ChemLab is a 3D chemistry and physics lab that an AI agent drives from inside the browser. The student talks to the agent, and the agent operates the bench. There are three practical modes, mapped to Phases D, E and F of the Indonesian national science curriculum: Acids and bases , with indicator colour change and gas evolution Electrolyte and non-electrolyte solutions , tested with a conductivity lamp Density and buoyancy , the classic egg in fresh water against salt water The agent can switch topics, mix substances, read the current state of the bench, explain each stage, raise an educational safety warning, reset the experiment, and write up the observation report at the end. Reagents are not teleported into the beaker. Each one is measured out into its own graduated cylinder first, or lifted on a spatula if it is a powder, and only then poured in one at a time. The amount_ml the agent asked for is something you can read off the glass rather than take on trust. How we built it Seven tools are registered client side through the browser model context API: switch_experiment_mode , mix_substances , get_lab_state , explain_reaction_step , trigger_safety_alert , reset_experiment and render_lab_report . The frontend is Next.js with React Three Fiber. Every object on the page is built from geometric primitives in code, with no third party assets: the glassware is turned on a lathe from a profile the way real glassware is, and the floor tiles and the room the glass reflects are drawn to a canvas at runtime. Bubbles are capped at 110 instances so the simulation runs on the standard school laptops we are aiming at. The backend is Rust with axum, acting as a proxy so that no API key ever reaches the client. One decision shaped everything else: reaction outcomes come from a static lookup table, never from a language model. The visual result of a reaction is a scientific fact, and a hallucinated colour change would teach a student something false. The model writes prose. The table decides the chemistry. Challenges we ran into The WebMCP specification moved the API from navigator.modelContext to document.modelContext in July 2026, and browsers in the field are still split across both locations. Every registration goes through a resolver that checks both, because a page that registers nothing looks exactly like a page that was never built. Refracting glass nearly cost us the experiment. The renderer builds the buffer that transmissive glass reads from opaque objects only, so anything marked transparent inside a beaker is not merely faint, it is absent: the liquid, the bubbles and the electrodes all disappeared behind the very glass that was meant to show them. Worse, our whole browser test suite stayed green while the beaker was empty on screen, because every check ran at 900 pixels and refraction only switches on from 1024 up. We now have a check that runs wide, hides the interface panels so that a text update cannot stand in for a reaction, and insists the contents are actually visible. We also had to design for a judging period that runs for weeks. An API quota running out in mid September would leave the lab looking broken, so step explanations are generated once, reviewed for scientific accuracy, and served as static content. Only the lab report, which depends on what the student actually did, calls a model at run time, and the backend accepts several numbered providers and moves to the next one when a call fails. That is not a claim on paper: in production the first provider currently fails on every request and the second answers, and the report still arrives. Every remaining failure path returns vetted static text with a 200 response rather than an error. Accomplishments that we're proud of Every execute handler returns a structured result containing the visual state, the temperature change and a plain language observation, so the agent narrates what actually happened instead of guessing. Unknown reagent pairs return a structured error listing the valid pairs, which lets the agent correct itself without the student ever noticing. We also built the lab so that it stays usable when WebMCP is not available. A status badge reports what the browser supports, a manual panel calls the exact same handlers rather than mock versions, and the topic buttons in the header run switch_experiment_mode the same way an agent does. The tool layer is genuinely separate from the interface. What we learned Reading matters as much as writing. get_lab_state returns the same view of the bench that the interface shows, so the agent can check what is actually there before it acts rather than assuming its last call succeeded. Together with the structured errors, it is what keeps a long conversation from drifting away from the simulation. We also learned that visible tool call indicators are not decoration. Every call is written to an activity console with the tool name, the outcome, and whether it came from an agent or was run by hand. Watching that line appear at the exact moment the liquid changes colour is what makes the whole thing legible, both to a student and to anyone evaluating it. What's next for EZI ChemLab Reaction rate is the next topic, and it is the one that rewards an agent most. It has four variables to manipulate and two beakers to compare, so the agent stops triggering effects and starts designing an experiment. Thermochemistry follows closely behind, since temperature data already flows through mix_substances . Beyond that: teacher accounts with printable worksheets, offline packaging for schools with limited connectivity, and coverage extending into Phase F electrochemistry.
