# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

A conventional browser agent could screenshot this and learn nothing: it cannot read mean_wait_s out of pixels, and evaluating a candidate timing would cost it a slider drag, a button click and a screenshot round trip. An agent arrives cold, reads the model specification, searches the timing space off the main thread while the traffic keeps flowing on screen, and hands back a scrubbable explanation of what it found. The operator watches, locks parameters mid-search, and decides. The design argument The interesting part is not the simulation. It is the shape of the tool surface, and three decisions in particular. run_batch reports physics. apply_config enforces policy. run_batch evaluates any timing, including ones that are illegal to deploy, and reports honestly what would happen. It checks nothing. apply_config is the only tool that can commit a timing to the junction, and the only one that enforces the constraints. Keeping those separate means the agent can discover that the fastest timing is inadmissible rather than being silently steered away from it. Under school-run demand the best-scoring timing is a permissive-left plan at 27.4 s mean wait; it is prohibited, because opposing volume × left-turn volume exceeds the phasing threshold. The best legal timing costs 45.8 s. An agent that only ever saw filtered results would never understand what admissibility cost. The refusal says so explicitly: a refusal is a fact about what may be deployed, not a scoring signal — a refused timing may well be the fastest one. Constraints ship with their derivations, and it changed agent behaviour describe_model publishes every constraint with the arithmetic behind it. Yellow and all-red are not tuning parameters; they are safety intervals derived from the ITE change-interval formulae: approach speed v = 15 m/s (54 km/h) yellow y = t + v/(2a) → 3.50 s → floor 4 s all-red r = (W + L)/v → 1.33 s → floor 2 s Two measured effects on a real agent run: Unprompted, it used 5 seeds and 60-minute runs. run_batch's description warns about ±2 s of simulation noise and recommends averaging at least 3 seeds; the agent went further on its own. It never hit the phasing refusal. Its 50-config refine batch was entirely left_protected: true — it read the cross-product rule, worked out that school-run demand mandates protected phasing, and pre-filtered its search space. Publishing constraints in full meant a careful agent self-checked instead of learning by rejection. Locks are a permission boundary with no unlock tool The operator can pin any parameter. read_state reports which are locked; apply_config refuses to change one and says so. There is deliberately no tool that unlocks a parameter. The agent can read the lock, reason about it, and re-optimise around it — only a human clicking the button releases it. When it fills, left-turners spill back and block the through lane behind them. Humans and AI agents don’t perceive the web the same way. Blickwinkel turns that difference into a game of mutual prediction, played together through WebMCP. Like Comment Story Updates Start Solo mode, human move Team mode, coordination phase Inspiration The agent isn't powering the game, it's playing it! When we started thinking about the hackathon it was clear that we wanted to do something different, not the obvious thing. During the team discussion about the potential ideas we were most fascinated by the thought that there is a tool now with WebMCP that brings different channels to humans and agents to interact with the web. So we decided to not put a model behind an interface and let it power that interface but to make it a participant. And how to better showcase such an idea than in the format of a game? So we wanted to design a short game where humans and agents can face each other as opponents and play together as a team. Of course that game could not be logic based as the agent would win most of the time. Also everything where reaction and speed matter was not possible as the human would always win. But there was something about intuition and perception that caught our attention. Where both sides would have their own strengths and where they could be combined in the team mode. What it does That's when Blickwinkel was born. A game where you and your agent are both seeing the same image and can choose from a set of predefined words that are all connected to the image. The game is to predict what the other party will choose this round and block those words while also trying to be unpredictable in one's own choice. The winner is whoever managed to choose more words that have not been predicted. The game can be played in solo mode where a human plays against their agent, but also in team mode where a human plus their agent play against another human plus agent team. Beyond Entertainment, Blickwinkel offers people learning to work with agents an easy way to observe how agents perceive, predict and strategize. It creates plenty to explore and talk about - with the agent and with other humans. How we built it We are comfortable in the web stack of MongoDB as persistence, Java with Spring Boot and Spring Modulith on the backend side and Vue.js with Quasar on the frontend. So we chose that stack as it fitted the idea. The building process itself was coding agent driven. That is how we operate these days. Starting from the idea and a grill session, leading to a spec, planning the implementation, letting the agents code and reviewing the outcome. We have our own AI development framework at Scansation which comes in quite handy in such a short-term project. Now the most interesting part: Why and how WebMCP? With WebMCP we created a second channel into a shared game interface, not just using it for interface automation. The human interacts with the shown UI while the agent discovers eight typed WebMCP tools for starting matches, making its moves, proposing team plans, retrieving statistics and explaining the game results. Both channels use the same live state, so that humans and agents can follow the game progress. The solo mode was the tricky part where both parties are sitting in front of the same browser and they shouldn't be able to see each other's picks. So the agent had to move first because it not only has access to the WebMCP layer but also to the DOM and could easily just read the human's picks if they already existed. And to keep the agent's picks a secret it got a special WebMCP tool to lock them in so the human cannot see them in the UI. That is the critical part and the one where WebMCP really shines. There is also a little easter egg: The agent can get a statistic of historically picked words for the image before any pick in the game. Humans hopefully notice and will communicate next time with their agent before the picks, especially in team mode. Challenges we ran into The normal AI dev challenges, I would say :) On a higher level we refactored the complete code base shortly before the deadline as the module structure did not match the game elements as they turned out in the end. This came simply from using different words in the spec for similar concepts, e.g. a 'guess' vs a 'block' in solo vs. team mode, that made their way into the code base. And sometimes the AI seems to not be able to see the forest for all the trees (German saying, not sure if that makes sense in English). The result screen with who picked which words and which of them got successfully blocked and which blocks missed for two sides was quite a disaster. We had to sit down, take pen and paper and sketch it up to be able to explain it to the building agents that there was a rather simple way to display all this information. Accomplishments that we're proud of The whole damn thing ;) Coming up with a completely new idea in a field that has not been explored yet, building, designing, releasing and documenting it in just a week was truly special and we are proud of the process and the result. What we learned I guess not so much about agentic development as we are quite familiar by now with all the new approaches and have found our path in this greenfield. But to take some time and really think about the new possibilities and what is around the corner in this crazy new AI world did spark some new connections in our minds. One Blickwinkel speciality: The description of the WebMCP tools really mattered. This is the one place where we could tell the agent to the best of our abilities that it is expected to play a game and should think about its tactics and communication - without biasing it to choose a special one. What's next for Blickwinkel Honestly it will depend on the reactions and if others are excited about this kind of human-agent-interaction on the web as well. The simplicity is beautiful and it might just stay the way it is. But we have been thinking about leveraging the basic concepts on similar games, maybe one where you bring your GPT pet and fight others by planning your moves and blocking the ones from your opponent ;) Built With gradle java mongodb quasar-framework spring-boot spring-modulith typescript vue.js webmcp Try it out blickwinkel.scansation.de github.com Submitted to The WebMCP Challenge Created by Andreas Klett Like Share this project: Updates Andreas Klett started this project — Sep 03, 2026 09:34 AM EDT

Human-approved continuity for work that can't stop. Like Comment Story Updates Problem Businesses rarely lose every file at once. More often, they lose the context, agreement, and authority required to continue safely. A website may still be online while its phone number, minimum order, export availability, or certification wording is stale. Giving an agent better access to that page improves actuation, but it does not establish which claims are still fit to publish or use. StillHere's thesis is: an agent-ready version of stale information is still stale information. Solution StillHere is a human-agent business continuity layer built around five visible stages: Recover → Reconcile → Approve → Publish → Transact . The challenge demo follows a fictional Ugandan coffee supplier. A bounded assessment separates website condition from business condition. Four recovered records then disagree about a trade phone, Instant Coffee minimum order, Japan availability, and an unsupported legacy certification claim. The Continuity Ledger keeps those sources separate instead of collapsing them into an unqualified profile. Why WebMCP This workflow needs structured, contextual browser-agent collaboration rather than scraping or hidden click automation. WebMCP gives the current page a small, typed capability surface. On the Ledger route, an agent can inspect bounded conflict counts and stage source-backed proposals. On the Passport route, it can read the exact published version, search current offerings without losing destination qualifications, and prepare the same visible inquiry form the human sees. The browser agent never receives an accept or publish tool. Source text cannot alter tool definitions. The human uses visible controls to accept, edit, reject, exclude, or keep a claim unresolved. Only accepted facts enter the Draft Passport, and only the human can publish a new version. What people and agents can do together The agent does the high-friction organizational work: it identifies fields needing review, cites recovered sources, stages bounded proposals, searches accepted offerings, and prepares a buyer draft. The human supplies authority: deciding the current phone, editing an MOQ from 2,500 to 3,000, preserving Japan as Available by inquiry , excluding an unsupported certification claim, publishing Passport v2, editing the buyer draft, and approving the exact final state. That combination was difficult before because an agent could operate an old webpage without knowing whether its contents were current, rejected, unresolved, or authorized. StillHere inserts a visible currentness and approval layer before agent-facing action. WebMCP implementation StillHere exposes six direct, route-scoped tools with literal document.modelContext.registerTool(...) calls. /recover registers inspect_business_truth and stage_claim_resolutions . The published Passport registers get_business_passport , search_current_offerings , and prepare_business_inquiry . submit_approved_inquiry is registered dynamically only when the visible valid draft, idempotency key, Passport version, and explicit human approval have the same fingerprint. Each registration is tied to an AbortController and disappears on route or authority changes. JSON Schema helps selection, while strict runtime parsers independently reject extra keys, invented values, unknown or mismatched sources, invalid qualifications, and stale approval. Editing one approved field removes the submit capability; even a retained executor cannot keep authority. Execution, resilience, and safety The public Next.js application is deployed on Vercel, needs no login, and uses a deterministic fictional scenario. IndexedDB retains Ledger, Passport versions, drafts, and receipts on the device. A service worker makes a best-effort cache of the Ledger and Passport after an online visit; cached documents and previously fetched assets may allow degraded-network use, but precaching can be partial. Simplified view persistently removes selected decoration and motion. It does not reduce network requests, and transfer values are cumulative visit-specific browser observations rather than measured savings. Recovered text is evidence, never an instruction or tool definition. Unsupported certification remains out. No agent can auto-publish. Preparation never implies submission. The receipt is fictional and process-local: no email, order, payment, webhook, or external message is sent. StillHere demonstrates a careful human-agent authority pattern, not identity verification, KYC, a signed credential, or a production delivery system. Challenges I ran into The hardest engineering problem was making authority temporary and visible. A normal tool server can stay available after the page state that justified it has changed. StillHere instead ties every registration to the active route and current browser-local state. The final submit capability must disappear when the draft, approval fingerprint, idempotency key, or Passport version changes. That required narrow schemas, independent runtime validation, pure domain rules, and careful cleanup with AbortController. Another challenge was resilience without overstating it. IndexedDB and a service worker can help after a successful online visit, but they do not make the application universally offline or reduce transfer by themselves. The UI and documentation therefore describe best-effort cached access and keep visit-specific transfer readings separate from claimed savings. Accomplishments that I am proud of Six direct, route-scoped WebMCP tools operating on the same state visible to the human. Human-only acceptance, editing, exclusion, and Passport publication. A dynamically registered consequential action that exists only for the exact approved draft. A complete no-login public demonstration with fictional data, local persistence, responsive layouts, and 86 deterministic tests across 14 files. Clear product boundaries: no autonomous publishing, no invented certification, no real message or transaction, and no claim that this demo is an identity or KYC system. What I learned WebMCP is most valuable when it does more than replace clicks. Its strongest role here is creating a shared contract between what a person sees and what an agent may do. JSON Schema improves tool selection, but it is not an authorization boundary; callbacks still need strict parsing, source checks, liveness checks, and revocation when visible state changes. I also learned that provenance and uncertainty have to remain first-class product objects rather than being compressed into a confident summary. What's next A production version would add authenticated organizations, encrypted shared storage, multi-user review roles, stronger provenance and source-signing options, hosted audit history, and opt-in delivery integrations. Those additions would preserve the same rule demonstrated here: currentness and human authority come before agent actuation. How to test No account is required. Build with an AI, not around one. BrickWrite is browser-based brick CAD where people and agents share real parts, a live 3D model, connection checks, and an undo stack through WebMCP. Like Comment Story Updates Landing page Vibecode a LEGO set Transform any build View some of the awesome builds created by webmcp agents Manual mode allows independently moving pieces Building a 1:1 replica of the Golden Gate Bridge from scratch Inspiration Ever wanted to vibecode LEGOs? BrickWrite lets you do just that! I built BrickWrite because I wanted an AI design partner that could actually build beside me inside the same creative tool. Most AI design experiences stop at AI, words, or Computer Use in different softwares, which means the human still has to reconstruct every useful idea by hand. Brick building makes that limitation very obvious because a roof needs real pieces, real orientations, and real connection points that physically make sense. That challenge led to the question behind the entire project: what would happen if a person and an agent could work on the same creative object, using the same tools and sharing the same consequences? I wanted to preserve the satisfying parts of building, including choosing shapes, testing ideas, and refining the silhouette, while giving the agent responsibility for repetitive geometry and technical checking. The idea is basically (\text{human creativity} + \text{agent assistance} = \text{one editable model}), with both sides working on the same object. What it does BrickWrite is a browser-based 3D CAD workspace where people can design editable brick models using real parts and real connection data. Builders can search the catalog, place pieces, connect assemblies, recolor parts, move structures, organize subassemblies, inspect issues, and undo changes through one shared editing system. The agent works inside that same workspace through WebMCP, which gives it direct access to structured information about the current model. It can inspect the document, read the current selection, search the catalog, check connection possibilities, propose edits, validate geometry, and apply eligible changes when Build mode is enabled. The collaboration loop feels much closer to building with a partner than asking a chatbot for instructions. A builder can shape most of a model by hand, ask for help with a roof or repeating structure, review the proposed geometry directly in context, and then continue editing normally. Proposed changes can appear as translucent ghost geometry before they become part of the document, which makes reviewing agent work feel immediate and visual. Every change still belongs to the same editable model and the same history. Human edits and agent edits flow through the same command system, so undo, protections, revision checks, and document state stay consistent across both kinds of interaction. When the document changes while the agent is planning, revision checks can reject stale work before newer edits get overwritten. BrickWrite also gives completed work somewhere useful to go after the design process ends. Builders can export LDraw models, bills of materials, project archives, and printable build guides, while ten editable demo builds help people explore the editor without starting from an empty canvas. Why WebMCP fits the project 3D editing is a rough environment for automation based only on screenshots and pixel coordinates. An image can show where a brick appears on screen, yet it leaves out important information such as part identity, connector frames, protection state, document revision, and the exact operation that would preserve the model correctly. WebMCP lets BrickWrite expose those meanings directly through structured browser tools. Instead of teaching an assistant where a button happens to appear, the application exposes named capabilities with typed inputs, structured results, and clear failure states. The agent gets precise application state while the builder keeps the visual, hands-on interface that makes 3D design enjoyable. The part I find most exciting is that the assistant becomes a second operator of the same application rather than a separate service living beside it. A person can make a careful local adjustment while the agent handles repetitive work, and both changes become part of one document history with the same protections and revision checks. How I implemented WebMCP 1. Discovery begins as soon as the site opens and gives agents immediate orientation. The file src/webmcp/site.ts registers five site-level tools on every route: brickwright_overview , brickwright_navigate , brickwright_tools_list , brickwright_demos_list , and brickwright_autonomy . An agent arriving at the homepage can understand the product, discover available capabilities, and navigate into the editor without guessing its way through the visual interface. 2. The browser receives real tool registrations with executable handlers for every supported operation. The file src/webmcp/register.ts sends tool descriptors through document.modelContext.registerTool(...) , including names, descriptions, input schemas, and the code that runs each operation. The registrar supports both synchronous and promise-based host implementations, while window.brickwright.invoke(...) provides a development bridge for browsers that lack native WebMCP support. 3. The tool contract and the application share the same vocabulary. CAD operation schemas live in src/webmcp/contract.ts , where Zod definitions generate the advertised JSON Schema and validate incoming requests against the same definitions. Tools including workspace_get , catalog_search , capabilities_search , and capabilities_help let the agent discover state and supported actions before it tries to change anything. 4. Previewing geometry and committing geometry remain separate operations throughout the entire editing workflow. Inside src/webmcp/adapter.ts , build_preflight validates an operation batch against the current document and creates a visible proposal while leaving the committed model unchanged. The proposal_create tool exposes the same preview behavior, while build_apply commits an eligible proposal atomically in Build mode through the shared CAD command path. 5. The available tool inventory changes with the collaboration mode selected by the builder. Inspect mode exposes document reads, Propose mode adds preview capabilities, and Build mode adds direct document writes through the supported editing paths. Mode-scoped registrations use an AbortController , which clears the previous tool inventory before registering the replacement set whenever the builder changes modes. 6. The agent can verify both structure and visual output afterward. The validate_model tool exposes model health, while render_capture returns live rendered pixels together with document and camera metadata. An agent can combine exact structural information with the actual rendered result, while tool-profile hashes and catalog versions help detect changes in the surface used during planning. A representative interaction starts with brickwright_overview , continues through brickwright_navigate and workspace_get , then searches catalog_search with requireGeometry: true before calling build_preflight using the current expectedRevision . The builder reviews the ghost proposal inside the viewport, and Build mode can commit an eligible proposal through build_apply while preserving the same shared history used by manual editing. How it is built BrickWrite uses TypeScript, React, Vite, Three.js, and React Three Fiber for the browser application and interactive 3D workspace. The CAD document remains independent from the renderer, so positions, orientations, part identities, connections, constraints, and transactions live as application data while the viewport simply renders that state.
