# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Who this is for Peer-to-peer marketplaces (used bikes, electronics, furniture, housing) where negotiation is asynchronous, and an unconstrained agent could easily overspend or leak private identity. What it does A buyer delegates a Deal Mission: target price, hard budget, search radius, and item requirements. The human owner reviews the action on /my/approvals/:id , can edit the counteroffer (e.g., adjust to €1,290), and approves it. Once accepted, the listing flips to RESERVED atomically. The agent, not our UI, is doing the talking, so every result is a short self-contained string that ends in a usable next step, and a test asserts each one fits the budget. Guest documents mirror the product. They live in a completely separate database whose every user-settable column matches the product table it will one day become, so claiming a document into a real account is an insert of the same columns — lossless, not a re-entry. Because no engineer has a WebMCP-native browser in CI, we wrote a small in-page polyfill that installs document.modelContext only when a page opts in with ?webmcp=polyfill and no real implementation exists. The same registration and execute() path then runs in ordinary headless Chromium, which gave us a node --test suite and a Python harness that hands the tools to a live Claude model and runs a real agentic loop against the page. Challenges we ran into Keeping the guest schema identical to the product's so that claiming is lossless rather than a reconstruction. Designing get_pdf to be genuinely useful while still capturing a lead. Writing results an agent can relay verbatim without a model misreading a phrase as a system error. The hardest one was restraint. Our first version of the sign-up tool emailed the link. An adversarial review called it what it was: an unauthenticated endpoint that sends mail from our domain to any address a caller names — roughly 1,200 sends an hour from one machine. We cut the send entirely. The agent already has the link in the conversation the person is reading, so delivery added nothing and risked our sending reputation. The tool returns the link and nothing else. Accomplishments we're proud of It runs on the real production data path, not a demo backend. Every document a tool creates is real and has a real claim path into the product. And the surface is honest under pressure: check_fit tells people when Every is not for them, and search_help says when it does not know. What we learned Designing for an agent is not designing an API. It is closer to writing for a colleague who will repeat what you said to a customer, word for word, without checking. That changes every string. What's next The Chrome origin trial, so Chrome and Gemini users can see the tools at all. Then WebMCP inside the signed-in product, so a customer's agent can operate their actual workspace in the same tab. Inspiration What it does How we built it Challenges we ran into Accomplishments that we're proud of What we learned What's next for DungeonQ Inspiration Adaptive cyber defense often jumps from detection straight to action. That is exactly where agent autonomy becomes dangerous: an agent that proposes a high-impact change should not be able to approve the same change. We built DungeonQ to make that boundary interactive, testable, and observable in judge-authored synthetic environments. What it does DungeonQ is a WebMCP-native synthetic security proving ground. A judge can provide a bounded Scenario Pack containing synthetic assets, signals, trust classes, policy thresholds, injected control failures, a requested effect, and expected invariants. A WebMCP agent admits the pack through a strict validator, runs a deterministic decision engine, explains the route and capability envelope, and requests human review. The tool surface then contracts: the agent never receives an approval tool. Only after a person approves the exact proposal digest and revision in the visible UI can the agent apply the browser-local synthetic effect, verify its receipt, compensate it, and return a replayable evidence digest. Three fixed-seed scenarios cover a controlled honey-credential replay, compound edge/evidence failure, and fresh-context false-positive recovery. Judges can also author their own packs and replay them through the browser or CLI. How we used WebMCP DungeonQ exposes state-shaped tools through document.modelContext: dungeonq_scenario_admit dungeonq_status dungeonq_simulate dungeonq_approval_request dungeonq_effect_apply dungeonq_receipt_verify dungeonq_effect_rollback dungeonq_evidence_export This is not a static wrapper around buttons. WebMCP makes the application meaningfully better because an agent can carry a complete new environment into the page, traverse a governed multi-step workflow, and lose capabilities as state changes. Human approval remains an intentionally missing capability. How we built it The dependency-free security core uses browser-safe JavaScript modules shared by Web UI, CLI, tests, and WebMCP. Admission enforces a 128 KiB document bound, closed fields, synthetic namespaces, content safety, cross-field references, budgets, scopes, and bounded arrays. The pure engine produces a canonical SHA-256 input digest, weighted risk score, route safety overlay, failure-composed capability set, exact proposal digest, and invariant results. A governed in-memory state machine binds approval, proposal digest, revision, expected prior state, and idempotency claim. Apply and compensation append protected receipts; Evidence Bundles cover the command transcript and hash-chained audit events. Vinext and the official Sites Vite plugin create the public ChatGPT Sites artifact without changing the core decision path. Challenges we ran into The hard part was not adding more agent power. A state-shaped capability surface can make authority, uncertainty, and recovery legible to both the agent and the person supervising it. A production path would require independently attested signals, durable state and claims, external evidence checkpoints, verified human identity, real policy distribution, isolated effect infrastructure, clock trust, and field acceptance. Like Comment Story Updates Tengu Swag Boykot Flow Restaurants and small shops are the most-attempted and worst-served agent task on the web. Every assistant can find a restaurant. Almost none can do anything with one. The menu lives in a PDF or a photo, the prices are stale, and the booking widget is a third-party iframe an agent cannot reason about. So the agent guesses — and it guesses wrong about the one thing the diner is paying for. We run two real businesses in Santiago, Chile, and we felt this from the other side. Agents were already describing our menu and our catalog to people, from blog posts written years ago. We had no way to be the author of what agents said about us. But the thing that actually kept us from opening the door was not the reading. It was the booking. Nobody wants an agent that reserves a table, or buys $80,000 CLP of paint, on their behalf while they are looking away. So we built for the opposite: the agent does the tedious part and stops. What it does Two businesses that have nothing in common expose the same pattern. Tengu — a kappo omakase restaurant, average table $300–400k CLP. Five tools on the page: get_carta (the live menu with real prices, by section), buscar_plato (search dishes, cocktails, wines and sake), get_guia (long-form guides the restaurant wrote about bluefin, sake and kappo cooking), get_info, and the one that matters — preparar_reserva. Boykot — an art and graffiti supply store, about 3.000 SKUs. Thirteen tools: catalog search, product detail, brand list, quotes, stock subscriptions, promotions, project planning, colour cards — plus agregar_al_carro, ver_mi_carro and guardar_en_lista. preparar_reserva fills the reservation form on the page with the party size, date, time and name the agent gathered in conversation — and then stops. It does not submit. The form is left visible, filled, scrolled into view, with the fields the agent touched marked, and a notice above it that says so and offers to discard. The human checks it and sends it. agregar_al_carro does the same on the store side. The cart gets built. Nobody pays. That is the division of labour we wanted. The agent parses "a table for four next Friday, somewhere quiet, my wife doesn't eat raw fish". The human keeps the part that costs money and social capital. The restaurant's host still sees a normal booking arrive. The read tools matter for a subtler reason: grounding. An agent asked "what's the sake situation at Tengu" now answers from the restaurant's own words and tonight's actual list, instead of from a 2023 blog post. For the first time, the business is the author of what agents say about it. How we built it Eighteen tools across the two sites — five on Tengu, thirteen on Boykot — registered on document.modelContext (with navigator.modelContext as the deprecated alias), feature-detected so each page degrades to an ordinary website when the API is absent: var mc = document.modelContext || navigator.modelContext; if (!mc || typeof mc.registerTool !== 'function') return; Both sites carry origin trial tokens, so the API is native — no ?webmcp flag, no polyfill, nothing for the judge to enable. Open the URL and the tools are there. The in-page tools are deliberately thin: they proxy to the same /api/mcp JSON-RPC server each business already runs for out-of-page agents. A browser agent and a server-side agent get the same answers from the same source. One truth, two transports. The exception is the write-side tools — preparar_reserva and agregar_al_carro only exist in the page, because their whole job is to touch the DOM in front of a human and leave it there. Tengu is static HTML and vanilla JS on Vercel with zero npm dependencies on the page — the smallest attack surface we could manage for something that hands tools to an autonomous caller. Reservations persist to Postgres through SECURITY DEFINER functions behind row-level security that denies all direct access; the page never holds a database credential. Boykot is Next.js, backed by the store's live inventory. Deliberately not exposed: anything that spends money or commits the business. No payment, no confirmation, no cancellation, no order modification. The reservation engine has its own caps underneath — 8 tables per slot, rate limit per name and phone — and the agent surface sits strictly inside them. A tool we don't register is a tool that can't be jailbroken.
