## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.

Tandem is a spaced-repetition study board where students and AI agents share live context, improve weak topics, and build lasting study plans through WebMCP. Like 1 Comment Story Updates Inspiration Study apps remember what a student has practiced, while AI assistants are good at explaining difficult ideas. The problem is that these two sides usually do not share context. A chat assistant cannot reliably see the card on screen, understand which topics the student repeatedly misses, or make its explanation available during the next study session. I built Tandem to explore what happens when a study app and an agent work on the same persistent state instead of communicating through copied text or brittle interface automation. What it does Tandem is a working spaced-repetition study board for students and their AI agents. The student can create decks, study flashcards, reveal answers, grade recall, inspect weak topics, and follow a revision plan. Through WebMCP, an agent can directly access the structured learning state and help with the same workflow. For example, the agent can: Rank topics using real lapse counts and difficulty data Start a study session focused on the weakest material See the exact card currently on screen Check whether an earlier explanation actually improved the student’s results Replace an ineffective explanation and save the new one directly on the card Build a revision plan from the exam date and weak-topic history Request permission to remove a card without being able to approve the deletion itself Agent actions and human actions appear together in a visible activity feed, so the collaboration remains understandable rather than happening invisibly. Why WebMCP This use case needs more than an agent clicking through a website. A student should not have to repeatedly explain which deck, topic, or card they are viewing. Tandem exposes that information as typed WebMCP tools. When the student says “the card currently on screen,” the agent can call get_study_state and receive the exact card, session position, reveal state, and study progress. WebMCP also lets the agent work with durable application state. An explanation written with annotate_card becomes part of the card and remains available in future sessions instead of disappearing in a chat transcript. The tool surface changes with the application state. Tandem exposes 16 live tools on the dashboard. When a study session begins, session-specific tools such as reveal_answer , grade_current_card , queue_cards , and end_session become available, bringing the live surface to 19 tools. They are withdrawn again when the session ends. Human and agent collaboration Tandem deliberately keeps important decisions with the student. For destructive actions, delete_card does not delete anything. It creates a permission request in the interface and returns a pending result. The student sees exactly which card would be removed and how many recorded reviews would be lost. Only the student can press the confirmation button. The agent can later read the decision through get_approval , but it cannot approve its own request. This creates a clear division of responsibility: the agent can inspect, explain, organize, and propose, while the student remains responsible for studying, grading, and irreversible decisions. How I built it Tandem is built with React 19, TypeScript, and Vite and deployed on Vercel. Study data is stored locally in the browser, so the project requires no account or backend. The WebMCP adapter registers tools through document.modelContext , supports contextual registration and withdrawal, and reads current application state when each tool executes. Every tool has a typed input schema, a detailed agent-facing description, structured output, and safety annotations. The app includes 20 tools covering deck inspection, card search and editing, study sessions, note-impact analysis, revision planning, interface highlighting, and human approval. Challenges One challenge was ensuring that tools never operated on stale React state. The executors therefore read the current store at call time instead of capturing an old snapshot when they are registered. Another challenge was designing a dynamic tool surface without duplicate registrations. The registry compares the tools that should currently exist with the tools already registered and changes only the difference. The most important design challenge was human approval. A simple confirm: true argument would only be the agent claiming that permission had been given. Tandem instead separates requesting, deciding, and reading the result into different actions, with the actual decision taking place in the user interface. Accomplishments I am especially proud that Tandem is a complete study product rather than a static WebMCP demonstration. A customer reports an issue through Support, the account context lives in CRM, and the root cause is buried in Billing. An AI agent can help connect those signals — but giving it permanent write access to operational systems creates a different problem: how do you let it act without giving it standing authority to make consequential changes? CorrelAct started with a simple idea: let the agent investigate broadly, but make its authority to act narrow, explicit, and human-approved. It should gather evidence, correlate information, and recommend an action autonomously. But before it creates a task, changes a customer record, or performs any other consequential write, a human reviews exactly what is about to happen. That became the core architecture of CorrelAct. What it does CorrelAct is a human-led operational intelligence platform that uses WebMCP to let a browser-native AI agent work directly across operational workspaces. The agent can: Read customer evidence from Support. Read account and renewal state from CRM. Read invoice and dispute evidence from Billing. Correlate those signals into one operational diagnosis. Submit a focused Proposed Action for human review. Wait for explicit human approval. Receive only the execution capability that was approved. Perform the approved consequential action through a protected backend. Leave a complete audit trail of the investigation, decision, execution, and outcome. Read → Correlate → Propose → Human Approval → Exact Capability Exposed → Constrained Execution → Audited Outcome The demo scenario Our reference scenario involves ACME , a NorthStar customer whose renewal is blocked. The agent discovers evidence across three operational sources: Support shows an escalated customer case reporting an incorrect invoice and blocked renewal. CRM shows ACME's account and persisted renewal state. Billing shows a disputed invoice with a variance and renewal hold. The agent correlates those signals and submits a Proposed Action. At this point, nothing consequential has happened — the run enters AWAITING_APPROVAL , where a human reviewer can inspect the evidence, recommendation, customer, organization, and the exact execution capability being requested. Only after approval does the run become APPROVED . Even then, approval does not execute the action — it authorizes the agent to perform one previously reviewed capability. Dynamic Agent Authority Most agent systems expose their write tools permanently and rely on the backend to reject inappropriate calls. CorrelAct narrows the capability surface earlier than that. If there is no matching approved work, the consequential WebMCP tools — create_task and update_crm_status — simply are not registered for the agent on the Tasks workspace. After a human approves matching work, the appropriate tool becomes available. After that authority is consumed, the executable run disappears and the available tool set is recalculated. The browser agent never holds permanent standing write authority. Authority appears because a human approved specific work — and disappears the moment that work is done. Two governed write paths, one approval boundary We deliberately implemented two different consequential actions to prove the governance model isn't a special case hardcoded around one integration. create_task creates a real GitHub Issue using the scope that was already reviewed and approved. The execution call cannot rewrite the approved task content, priority, team, customer, or organization. update_crm_status applies one approved CRM renewal-status transition — for example, blocked → escalation_open . The agent does not supply the target state at execution time; that transition is frozen inside the Proposed Action before human review. The execution tool receives only enough information to identify the approved run, organization, and evidence-bound customer. Both capabilities pass through the same governance model: Human Approval → Shared controlled-execution boundary (organization · customer · evidence · approval state · execution type · idempotency · audit) → either create_task → GitHub Issue or update_crm_status → CRM record This mattered to us because we wanted to demonstrate that human-gated agent execution is a reusable architectural pattern, not a one-off built around a single API. Same governed boundary. Different consequential action. Like Comment Story Updates Inspiration I’ve been skinny for most of my life. I tried apps like Strong to track my workouts and MacroFactor to manage my nutrition. Both were useful, but each understood only one part of what I was trying to achieve. I still relied on ChatGPT or Claude for advice. That meant repeatedly explaining my training history, diet, recovery, and goals, then manually carrying their suggestions back into each app. I built Hustl because I wanted those pieces to work together. The same problem exists whether someone wants to gain muscle, improve performance, or lose weight without sacrificing strength: good coaching needs the full picture. What it does Hustl connects training, recovery, nutrition, progress, and AI coaching in one app. It also brings in health and activity data from outside Hustl through Apple Health and Health Connect on Android, including data shared by compatible apps such as Google Fit. This gives the coach a broader view of the athlete’s workouts, sleep, heart rate, recovery, and daily activity. An AI assistant can understand what the athlete has trained, how their exercises are progressing, whether they have recovered, what they have eaten, and what their current goals are. It can then help with practical tasks such as: reviewing workout and exercise history; interpreting readiness, sleep, HRV, and resting heart rate; comparing food intake with calorie and macro targets; logging or correcting meals; proposing nutrition targets; building and revising workout templates; adapting a workout when recovery is poor; and showing proposed changes inside the Coach inbox. Hustl supports both MCP and WebMCP. MCP lets compatible assistants work with Hustl directly. WebMCP gives an assistant tools related to the Hustl screen currently open in the browser. The important part is the collaboration. The assistant studies the evidence and explains its recommendation. Hustl turns that recommendation into a concrete proposal. The athlete reviews, refines, accepts, or rejects it. How I built it Hustl is a Flutter application backed by a TypeScript and Next.js API, Supabase and PostgreSQL, native Apple Health and Android Health Connect integrations, and an MCP server. For WebMCP, I built a coordinator that registers tools according to the visible route. Train exposes training and progression tools. Recover exposes readiness data. Nutrition exposes the food diary and nutrition proposals. Coach exposes trends and pending changes. Templates and active workouts expose their own focused capabilities. When the user changes screens, the old tool handles become stale. This prevents an assistant from retaining a capability simply because the user visited that page earlier. Actions use strict schemas and explicit outcomes. Coaching changes normally become pending proposals rather than being applied silently. They appear in Hustl’s regular Coach interface, where the athlete can inspect the rationale and proposed values. For the challenge, I also created a public evaluator using Hustl’s real Flutter interface and WebMCP coordinator. Private services were replaced with deterministic, in-memory data. It contains no production credentials, personal health records, analytics, or backend connection. Its runtime also blocks unexpected network and browser-credential access. Challenges I ran into The first challenge was resisting the temptation to build a small, isolated demo. Hustl is meant to support the whole coaching loop, so the WebMCP experience needed to work across the real training, recovery, nutrition, Coach, template, and workout screens. Navigation was harder than it appeared. The visible screen, browser URL, and registered tool catalogue all needed to agree. I found cases where a detail screen opened without correctly taking ownership of its route. I also had to ensure that tools disappeared and old handles failed safely after navigation, reloads, and account transitions. Proposal state required similar care. A successful request might be pending, applied, duplicated, dismissed, reverted, or rejected by validation. Those outcomes needed to remain distinct in both the tool response and the interface. Finally, I needed to make the source inspectable without publishing Hustl’s private backend or user data. The public evaluator therefore uses synthetic fixtures, explicit no-op integrations, source manifests, and checks for private paths, credentials, and unexpected network origins. Accomplishments that I’m proud of The public evaluator exposes 20 route-scoped WebMCP tools across training, recovery, nutrition, coaching, templates, and active workouts. Those tools support a complete coaching story. An athlete can describe a goal, let the assistant study twelve weeks of training and exercise progression, account for a poor recovery day, compare nutrition with current targets, and receive concrete changes for review. I am especially proud that the safety model is visible in the product: tools follow the screen the athlete is using; stale handles fail closed; proposal status is explicit; duplicate requests do not create duplicate changes; workout and nutrition-target proposals require human review; and the public evaluator cannot access production systems or personal data. This is not a separate interface made for the challenge. It is a safe, deterministic version of Hustl’s real Flutter experience and coaching architecture. What I learned More autonomy does not automatically make an AI coach more useful. Better context and a clear review process matter more. I also learned that the interface can act as a meaningful permission boundary. Route-scoped tools make the assistant’s access easier to understand because its capabilities follow what the athlete can currently see and do. Most importantly, AI collaboration works better when the result becomes part of the product’s normal workflow. A recommendation should not disappear inside a chat transcript. It should become something the athlete can inspect, refine, follow, and revisit. What’s next for Hustl The next step is to make the collaboration continuous rather than limited to a single planning session. I want Hustl to support richer long-term recovery analysis, clearer progression explanations, and weekly coaching check-ins that compare the plan with what actually happened. I also want the same experience to work consistently across web, desktop, and mobile assistants through MCP and WebMCP. The principle will remain the same: Hustl provides the evidence, AI helps interpret and propose, and the athlete controls what changes. Like Comment Story Updates The problem nobody has budget for Every operations team lives inside sites that will never ship an API for them. Monitoring in Grafana. Customer commitments in Cal.com. Payer portals, vendor consoles, admin dashboards. The person holding the session can see everything and change anything, but their agent can do nothing except screenshot the screen and guess where to click. WebMCP fixes this for sites that adopt it. Today that is roughly none of them. We measured three real open-source products, 522k lines of code, 429 places where a tool obviously belongs, and zero WebMCP registrations. So we asked a different question. What if the user adopts WebMCP for the site? The reframe WebMCP turns the login you already have into an API. A signed-in tab already carries every credential and permission the human has. If that tab registers tools with document.modelContext.registerTool , the agent gets a typed, narrow, inspectable interface to the site, and the vendor never has to ship a line of code. Adoption inverts. It no longer waits on ten thousand vendors. It happens one user, one tab, one reviewed pack at a time. What Agentready Network does Agentready Network is a local-first registry and runtime of reviewed action packs . A pack describes what a site can do, on exactly which origin, with which risk labels. The runtime turns that pack into live WebMCP tools inside the user's own signed-in session, then wraps every call in the safety the vendor never provided: Exact origins. A pack binds to one host and a reviewed fingerprint. Drift fails closed. Declarative, never executable. Manifests are JSON. The registry cannot ship code into your browser. Bounded, untrusted output. Results are allowlist-projected, byte-capped, and labeled contentTrust: "untrusted" . Tool output is content, not instruction. Human authority on consequences. Reads flow. Writes need a preview. Consequential actions need one exact, single-use approval bound to origin, tool, and normalized arguments. Change an argument and the grant is void. Verified closure. After a consequential action an inspector reads authoritative state and issues a receipt with no cookies, secrets, or raw bodies. Unknown outcome is reported as in_doubt , never as success. One concrete job, end to end The demo is not a feature tour. It is one incident. An alert fires in Grafana. Customer bookings in Cal.com are about to be affected. Neither site has WebMCP. The agent discovers the reviewed Grafana and Cal.com packs, installs them for this origin, and reads authoritative state. It never receives a credential. The agent prepares the exact continuity action and states what will change and how it will be inspected. The incident is still investigating . The human grants that exact action once, from a control the agent cannot reach. The agent executes once. The inspector verifies and issues one receipt. The incident is resolved . We poison the fingerprint. The pack refuses to run. We export the recorder draft. Every secret is gone before it can be published. Agents investigate. Humans authorize. Outcomes are verified. That is the whole product. What people and agents can now do together that they could not before Work a real incident across two unrelated vendor sites with no API contract between them. The user is the integration layer. Let an agent read freely and prepare freely, while every consequential step waits for a human decision the agent physically cannot forge. Hand a reviewer a receipt, not a screenshot, as proof of what changed. Teach a site once by observing its own traffic, then reuse that pack every session. Why WebMCP, specifically Screenshot-and-click pays the full cost on every step: a screenshot, a vision pass, a click that misses when the viewport shifts. We measured it. Creating one Grafana data source took nine browser actions and 55 seconds by DOM driving, and one WebMCP tool call in 20 milliseconds. A whole diagramming task took 44 calls versus 5. These are single-trial measurements from our audit work, not a benchmark suite, but the shape is unmistakable. The cost moves from per-action to per-app, and it never comes back. WebMCP also gives us the one thing a bookmarklet never had: a standard discovery surface. Any agent that speaks document.modelContext finds our tools without knowing we exist. How we built it Registry, Pack Lab, and runtime in plain HTML, CSS, and JavaScript. No framework. Every tool is registered with the current imperative API, document.modelContext.registerTool(tool, { signal }) , so tools unregister cleanly when a view unmounts. A Chrome MV3 extension injects reviewed read tools into the exact controlled Cal.com and Grafana origins and bridges receipts back to the registry. Reviewed adapters for Cal.com and Grafana were reverse-engineered on the wire, not from source. The recorder wraps fetch and XMLHttpRequest , clusters observed traffic, drafts tools, auto-flags mutating endpoints, and strips secrets before anything is published. Approval, inspection, drift, and redaction are enforced in the shared runtime, so every pack inherits them and no pack can opt out. Node's built-in test runner covers the trust boundaries. All tests pass on the submitted commit. What we deliberately did not claim The public judge path is a deterministic fixture so nobody needs an account. The same runtime drives the real Cal.com and Grafana adapters against controlled localhost instances; the video shows the controlled Grafana and Cal.com state alongside the public lab. The extension checkpoint is read-only. Remembered approvals, arbitrary-site install, generic DOM automation, and automatic rollback are out of scope. Figma taught us the frontier. Its control plane is reachable in-session; its canvas rides a binary WebSocket inside a Worker that no page-context patch can see. We published only what we proved and marked canvas manipulation unsupported. What we learned Discovery is observation, not code reading. Every tool we guessed from source was wrong. Every tool we drafted from the wire worked. Minification cannot rename what crosses the network. Injection inverts the safety burden onto the installer. The vendor never audited these tools, so we had to. That is why approval, inspection, and redaction live in the runtime and not in the pack.
