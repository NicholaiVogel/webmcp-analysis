# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Playable Arena is a benchmark you can keep evaluating after the leaderboard is published. Benchmarks such as SWE-bench and Terminal-Bench answer a valuable but fixed question: under the same tasks, checks, and agent setup, which system performed best? A developer choosing an agent for a real product asks a different question: which failure modes matter for my workflow, which output qualities feel right, and what should my agent test next? Arena preserves both kinds of evidence. Fixed checks measure whether each result meets the requirements. Playable outputs preserve qualities a score cannot settle: clarity, responsiveness, taste, and fit for a particular audience. WebMCP lets the AI agent in your browser continue that evaluation inside the same Arena page. It reads detailed evidence, updates the comparison you can see, and tests the same scenario across shortlisted outputs. You then compare them anonymously and make the subjective choice. Arena turns the fixed benchmark, live verification, and your decision into acceptance checks for the next agent run. The published score never changes. In the recorded demo, the agent reduces 22 published checks to seven relevant criteria, then completes the same six-move, three-push level in all four shortlisted builds. The result is not another leaderboard. It is a concrete plan for what the next run should preserve, test, and improve. The current release proves this pattern with five standardized browser-game tasks and 70 playable benchmark outputs . Today those outputs are produced by coding-agent configurations. The recorded demo uses Codex. Arena supports both WebMCP surfaces: document.modelContext in ChatGPT/Codex in-app browsers and navigator.modelContext in Chrome. The shared evaluation loop Read the evidence. The agent uses WebMCP to select the published checks that matter for the person's goal and updates the comparison they can see. Test the playable outputs. The agent opens the shortlist and completes the same level in each game. Agent Play verifies facts the table alone cannot: whether state is readable, actions are accepted, out-of-date actions are rejected, and a complete run works. Return the decision to the person. Arena presents the builds anonymously. The person plays them and chooses in the UI; only then are identities and published scores revealed. Improve the next run. Arena combines the fixed benchmark, live verification, and human choice into review stages and acceptance checks for the next agent run. Arena does not claim that one model or agent setup is universally best, and it never changes the published benchmark score. Why WebMCP matters WebMCP can automate a workflow end to end. Arena uses it to automate the parts of evaluation that should be automated: reading evidence, replaying scenarios, and gathering results, while keeping subjective judgment with the person. The agent and person work on the same live page. Tool calls update the visible filters, selected builds, game state, and anonymous review. The available tools change with context: benchmark tools appear on the benchmark, comparison tools on a task, game actions only for a compatible active build, and the result tool only after the person chooses. Arena never exposes a tool that lets the agent make the subjective choice or reveal identities early. Without WebMCP, the person would have to read a large result table, open builds one by one, manually repeat scenarios, copy observations into another chat, and reconstruct the comparison. With Arena, the agent handles breadth, interpretation, and repeatable checks while the person contributes the judgment automation cannot supply. The public benchmark stays fixed. What changes is how a developer can use it: what to preserve, what to borrow, which reviews to run, and what must pass next. How it works Arena registers tools for the current page with modelContext.registerTool(...) . When the person moves to another page, the old tools are removed and the relevant ones appear. Generated games run in isolated frames. A small arena.game.v1 agreement lets Arena expose only the actions owned by the current task. Each action carries a revision number, so an out-of-date action is rejected without changing the game. Anonymous review provides no tool that can choose or reveal on the person's behalf. Production runs on Cloudflare Workers. D1 stores anonymous review choices, while a separate Artifact Worker serves the playable builds from another origin. What existed before the challenge Before August 25, Arena was a private playable benchmark. It could give coding-agent configurations the same brief, score their results with fixed checks, keep the games playable, and let a person compare two results anonymously. It had no WebMCP tools, no way for an agent to inspect the detailed evidence or play the builds, and no path from a person's choice to checks for the next run. What I built during the challenge I built the missing end-to-end flow: Added page-specific WebMCP tools so the agent can read evidence and update the comparison visible to the person Added Agent Play so it can read live game state and repeat the same scenario across very different builds Rejected out-of-date actions without changing the game Connected agent-selected shortlists to a human-only anonymous choice and reveal Turned the fixed results, live verification, and human choice into review stages and acceptance checks for the next run Rebuilt the public Benchmark, task, comparison, evidence, navigation, and mobile experiences Separated the public product from private briefs, raw runs, credentials, and production history Added automated leak checks and deployed the UI, playable builds, and anonymous choice storage on Cloudflare I also expanded the working testbed from 3 tasks, 39 builds, and 13 agent configurations to 5 tasks, 70 builds, and 15 configurations . Adding LUMEN YARD and SHOAL meant more than adding two game cards. Each task needed one shared brief, fair checks for every build, independent runs across multiple agent configurations, playable published results, and a shared set of named actions so an agent could repeat the same scenario across implementations that shared no code. The new tasks expose differences in strategy, recovery, board readability, and action feedback that a top-line score alone cannot explain. I also added Antigravity + Gemini 3.8 Flash and fx + GPT-5.6 Sol configurations. HACKATHON.md records the plain-language before/after boundary and dated commit evidence.
