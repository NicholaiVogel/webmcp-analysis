# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Clean sensitive datasets with AI agents—without uploading raw data. WebMCP enables local analysis, human-approved cleaning, capability-gap detection, and safe tool evolution. Like Comment Story Updates Inspiration AI agents are extremely useful for understanding and cleaning data, but there is a fundamental problem with sensitive datasets: normally, the agent needs access to the data itself. Data Airlock explores a different model: An agent can work on a dataset it can never read. The raw file stays on the user's device and is processed locally in the browser. The agent receives only bounded, pseudonymized and aggregate evidence through WebMCP. What it does Data Airlock is a local-first environment for analyzing and cleaning JSONL and CSV datasets with an AI agent while keeping raw records outside the agent boundary. A user can ask ChatGPT to analyze a dataset in natural language. Data Airlock performs the actual work locally and exposes safe WebMCP tools that let the agent: inspect aggregate dataset profiles and quality findings; identify affected pseudonymous fields without revealing their original values; prepare cleaning actions; run a real local second-pass simulation; inspect aggregate simulation impact; detect structural patterns that are not covered by any active capability; create or evolve capabilities with Forge; evaluate candidates locally using aggregate coverage, specificity, overlap and stability metrics; retrieve the open-source source code of cleaning tools when needed; access an interactive Data Airlock guide. The included production demo is a real 500 MiB dataset processed by the same local engine used for user files. Human authority by design The agent can analyze, reason, propose and simulate, but it cannot approve a destructive operation on behalf of the user. The cleaning lifecycle is deliberately: PROPOSE → SIMULATE → HUMAN APPROVAL → EXECUTE Human approval happens independently in the Data Airlock UI. Changing an approved plan invalidates that approval and requires a new simulation and review. This separates two different security boundaries: data access and execution authority . Capability Gap Scan and Forge A fixed set of tools cannot anticipate every structure that may appear in real-world data. Data Airlock therefore includes a local Capability Gap Scanner . It recognizes broad structural families such as date/time formats, locale-dependent numbers, identifiers, encoded tokens, network formats, structured text, Unicode/script mixtures, length distributions and other patterns. If a field contains meaningful structure that no active capability explains, the agent can receive safe aggregate evidence about that gap without seeing the values that caused it. The agent can then use Forge to create a new capability or evolve a related existing one. Before adoption, candidates go through bounded validation and can be evaluated locally against the gap. The agent receives only aggregate metrics such as structural coverage, specificity, overlap and stability. The principle is: The agent can expand its capabilities, not its access to your data. Why WebMCP WebMCP is what makes the architecture possible. Instead of building a separate agent backend or uploading the dataset to an API, the website exposes a controlled set of capabilities directly to the agent. The browser owns the dataset and computation. WebMCP provides the agent with a narrow semantic interface containing only the information it actually needs. This means the agent can participate in a useful end-to-end workflow while the raw dataset remains local. Data Airlock currently exposes read-only analysis and guidance tools, controlled plan-management tools, Forge, and a dynamically gated execution capability that exists only after real human approval. Privacy boundary The agent never receives raw dataset records or original field values through the Data Airlock WebMCP tools. It can receive things such as: aggregate counts; finding categories; pseudonymous field IDs such as field_003 ; cleaning-plan metadata; aggregate simulation impact; aggregate capability-gap evidence; aggregate candidate-evaluation metrics; safe receipts and state; open-source tool source code. The application requires no backend, no account and no API key for local dataset processing. Building it Data Airlock is built in TypeScript and React and runs entirely in the browser. Large datasets are processed using automatic Web Workers. JSONL and CSV are streamed through the local processing pipeline, and output can be written using browser-local storage / file capabilities depending on the environment. The WebMCP layer is intentionally separated from the raw-data engine. Agent-visible results are projected through bounded privacy-safe representations before leaving the local runtime. The production deployment is hosted on Cloudflare Pages. Challenges The hardest part was not detecting data-quality problems. It was preserving a meaningful agent experience while keeping a strict capability boundary. We had to make sure that: raw values never leaked through normal results, errors or edge cases; the agent could not manufacture human approval; stale approvals could not be replayed after a plan changed; WebMCP registrations remained safe across browser-host lifecycle changes; large files stayed practical without moving processing to a backend; Forge could evolve functionality without becoming an arbitrary-code escape hatch; capability discovery produced useful evidence without exposing examples from the dataset. We also built extensive deterministic, privacy, lifecycle and end-to-end tests around those boundaries. What we learned The most interesting lesson was that hiding raw data does not have to make an agent useless. If the local application exposes the right abstractions, an agent can still reason about counts, structural families, impact, coverage and state transitions. That led to the third principle behind Data Airlock: Airlock does not only hide data from the agent — it gives the agent enough safe evidence to know when it still does not know how to handle something. What's next The same architecture can extend beyond dataset cleaning. The broader idea is a capability-oriented interface where agents can work with sensitive local information through safe evidence and constrained actions rather than unrestricted access to the underlying data. Data Airlock is one demonstration of that model. Ask your agent for start_guided_demo , or press "Show me a demo", and you land in a real workspace with a proposal already waiting in the review panel and six tools live. Inspiration Every "agent-ready" app I looked at exposed the same shape of tool: create_task , update_task , delete_task . The model writes straight to the database. That is fine until the model is confidently wrong about your sprint plan, and then you are doing archaeology on a project board, trying to work out what it touched and in what order. Project planning is exactly the wrong domain for blind writes. A plan is an argument about sequencing and effort — it is the thing a lead is paid to have an opinion about. Handing that to an agent as unsupervised INSERTs gets you a plan nobody trusts and everybody re-checks, which is more work than writing it by hand. So I wanted to find out whether WebMCP could carry something other than commands. Can a tool call ask a question and wait for a human's answer? If it can, the agent stops being a thing you supervise and becomes a thing you argue with. What it does Sprintfy is a sprint planner — requirements, sprints, tasks, hour estimates — that exposes its workspace to agents over WebMCP. No agent tool writes to the plan. The loop has three moves: 1. The agent reads the room. get_project_context returns the plan and what the human is currently looking at: active view, selected sprint, status filter, which proposal is open. The agent plans into a context, not a vacuum. 2. The agent proposes a diff. Every write tool authors a change set — an ordered list of operations stored as JSON, rendered in the review panel as a real diff: additions in green, field-level changes as before → after, removals struck through. Nothing has touched the domain tables. An agent can propose a sprint and the twelve tasks inside it as one unit, using local ref ids that resolve to real primary keys only at apply time. 3. The human decides, and the agent hears the answer. apply_pending_changes opens the diff and blocks — the tool call's promise stays open while the person reads it. Approve applies the whole change set in a single Postgres transaction and the tool resolves with what landed. Reject resolves with the reason they typed, delivered back to the agent as the tool result. You do not start from an empty board either. You hand Sprintfy the thing you already have — a backlog note, a PRD as .md , .txt , .pdf or .docx , or a few paragraphs typed in — and it returns a plan sequenced by risk rather than by comfort. A real Turkish brief produced 8 requirements, 4 sprints and 38 tasks in 56 seconds, in Turkish, with the database migration ranked critical and placed first. Sprintfy's own planner is held to the same rule. It does not write the plan either: it authors a change set marked source: "planner" that lands in the same review panel, behind the same gate. How we built it Next.js (App Router) and React on Vercel, Supabase for Postgres, Auth and Realtime, and WebMCP for the agent surface. The architecture is one idea repeated: the write path is a data structure, not a function call. Tools append operations to a change_sets row. A single PL/pgSQL function, apply_change_set , applies them atomically and resolves ref placeholders to real ids as it goes. It is declared security invoker , so row-level security still guards every insert it performs — an agent cannot use it to reach another user's project. On the WebMCP side: Surface detection. The API moved during the spec's life and shipping browsers do not agree yet, so one adapter registers against document.modelContext.registerTool , navigator.modelContext.registerTool , or navigator.modelContext.provideContext , whichever exists, and the header badge reports which one it found. Page-scoped tool sets. Four tools before you sign in, six inside a project. The surface changes as the human navigates. Cancellation is honoured. The AbortSignal passed to apply_pending_changes releases the approval wait, so an agent that walks away does not leave the page stuck on a modal. Tools never throw at the browser. Failures come back as text an agent can recover from, including "these task ids don't exist in this project, call get_project_context again." Planning uses a strict JSON schema derived from the same Zod schema that backs the propose_plan tool — one schema, two authors, so a plan from the model and a plan from an agent are the same shape. Challenges we ran into Tool calls do not wait for React. Two bugs had the same root: an agent could not always see the proposal it had just written, and focus moved the human's view without get_project_context reporting it. A tool call can land before React has committed state, so reading a render closure returns the past. Tools now read from a ref that is written before the state, never from a closure. Both cases became eval scenarios so they cannot come back. Registering the same tool twice. Navigating between pages left the previous page's registration alive and the browser rejected the new one as a duplicate. Fixed with a module-level registry where claiming a name synchronously releases the previous holder. A machine asking a question and getting an HTML redirect. An unauthenticated POST to the planning endpoint was redirected to the sign-in page; Next then read the multipart body as a server action and answered 404. In an app whose premise is that machines are first-class callers, that was the wrong answer to give one. API routes now reply in JSON. The date picker that could not be used. The month grid was absolutely positioned inside a modal that clips its own corners and scrolls its body, so it was sliced off a few pixels below the field. It renders into a portal now, in viewport coordinates, flipping above the field when there is no room below. Knowing where WebMCP actually exists. The seven tools (src/lib/webmcp/platform-tools.ts) — list_stores, list_catalog, get_store_info, search_products, get_product, add_to_cart, get_cart — each with a JSON Schema inputSchema, descriptions written to guide agent tool selection (e.g., "prefer search_products when the shopper has a specific query"), and readOnlyHint annotations so agents can reason about side effects. Data layer — tools call Bizgrid's existing catalog APIs (store listing, full catalog with pagination, search with budget filters, per-product lookup), so agents get live, real prices and stock, never static HTML. Shared cart, shared checkout — add_to_cart writes to the same per-store localStorage cart keys the storefronts already use (src/lib/webmcp/platform-cart.ts), with validation of stock, purchase limits, and variant options (src/lib/webmcp/shared.ts). Every response includes cart_url and checkout_url, so the human opens the exact checkout the agent filled. Agents and humans share one cart and one trusted Paystack flow nothing is simulated or sandboxed. No server changes required because everything is structured client-side on top of existing APIs, the entire WebMCP surface ships with the normal frontend bundle, live at https://www.bizgrid.shop today. For those who want to Cut Through The Noise to Get to The Signal in their YouTube videos. Like Comment Story Updates Step 1 Processing Result Icon Inspiration In a world of AI there is too much noise, this is a simple tool to leverage that very same AI to help cut through the noise to get to the signal of your YouTube videos. What it does TLDW is one web page where you paste a YouTube link and gets the captions, with the moment each line was said. An AI agent opening the page finds two WebMCP tools instead of buttons: get_transcript(url) hands it the captions as timestamped segments, and render_explainer(slides, url) draws whatever the agent wrote back onto the page, every timestamp a link that opens the video at that second, then reads it aloud. The thinking runs on the visitor's own ChatGPT plan, in their own session. How its built Built entirely with AI, Both tools are registered with document.modelContext.registerTool, with navigator.modelContext as a fallback for older builds, each with a JSON schema an agent can read. Errors are returned, never thrown, so a failure arrives as a result the agent can act on. Every fetch has three outcomes, not two: ok, not_measured with a reason, or a structured error, because a tool that cannot tell a failed measurement from a real zero will report the first as the second. Captions come from a transcript API first with a direct fetch behind it, held in memory for ten minutes and never written down. The page is served by a Cloudflare Worker. Read-aloud uses the browser's own voices by default with a voice picker; one opt-in experimental entry renders a natural voice on our server and streams it back. An agent whose browser has no WebMCP yet can paste the same slides into a Render box on the page and get the identical result. It was built from nothing in one evening, live on stream, by a fleet of AI bodies run by one human, with two independent reviews on every change. Challenges We (Myself and my AI Team) only had ~8 total hours for this as that's when I found out about the competition, then immediately started live streaming the start to finish. We had about ~3 hours of prep while waiting for the reset then 5 hours to build. The spec moved while we built: our first registration was on navigator.modelContext only, and Chrome's stable build binds document.modelContext, so the tools registered and nobody could see them. YouTube refuses caption fetches from a server, so the free path failed silently until we made refusal a first-class result and put a transcript API in front of it. Agents that fetched the captions then answered in chat instead of drawing on the page, until the tool text put the obligation before the data. And the browser's speech queue armed from the speak call rather than from what was drawn, so a slide with the wrong shape left a full explainer on screen and nothing to play. Each one was found by a second reader, not by the author. Accomplishments that we're proud of We got it done 40mins past the buzzer but fortunately there was a 12 hour extension, so we polished the video and made minor edits to the description etc (also generated by AI) The tool work on a free ChatGPT account, the desktop app's built-in browser, and with one sentence: explain this video and render it on the page. The page registers two tools, the agent calls them, the explainer appears with timestamps that jump into the YouTube video if you want to watch a particular segment in full, and it also comes with a reads aloud bar with play back controls and voice selection that uses your browser supported voices and 2 x experimental neural voices. Every instinct said add a summarizer, add a model, add a key, and each one would have made it slower, costlier. The second lesson was the error surface: an agent is not a human staring at a stack trace, it reads your failure and decides what to do next, so a tool that throws ends the conversation and a tool that returns a readable error lets the agent try something sensible. The third was the voices, Chrome free supports free neural style voices as well as system voices, the ChatGPT browser uses only the free system voice. We are experimenting with some neural voices but the render time is slower, there could be an option to use something like Elevenlabs but then that would mean have to charge a fee for the service or run ad's on the page. A shared decision canvas where people and agents map hidden assumptions, stress-test plans against real world shocks, and turn uncertainty into resilient action. Like Comment Story Updates Inspiration When working on an app launch, we found ourselves sending planning docs back and forth between us and our agents. That was very problematic. We wanted to move beyond asking an AI, “What could go wrong?” and getting another list to read. What if the agent could work inside the plan itself, connecting assumptions, exploring consequences, and proposing alternatives that a person could inspect and challenge? That became Cascade: a shared decision canvas for people and their agents. What it does Cascade turns a consequential plan into a connected map of objectives, assumptions, dependencies, constraints, risks, and outcomes. Our demo starts with a product launch: six weeks, 500 teams, and a $12,000 budget. What happens if billing arrives three weeks late? An agent can create a separate what-if branch, apply the disruption, and trace modeled downstream effects. It can then stage possible responses, such as launching a free beta first. The human can inspect the map, drag cards with their connections following, compare scenarios, and accept or reject proposed factors and relationships. Applying a shock is allowed inside a what-if branch; proposed mitigations remain drafts awaiting review. Promoting a branch is a human action. Product launch is the starter. Cascade also includes a community tool-lending scenario and a blank workspace for other plans. Why WebMCP Cascade is built around a shared working surface, not a separate chat transcript. WebMCP lets the agent read and act on the structured model behind the page. Tool actions update the same interface the person is watching: branches appear, shocks enter the map, and proposals arrive for review. This makes an otherwise awkward workflow practical: the agent explores alternatives inside the live application while the person retains an inspectable record of the model and controls which proposals are accepted. There is no need to copy the plan into a chat and manually translate the answer back into a diagram. How we built it Cascade uses TypeScript and React, with a Next.js-style App Router implemented through vinext on Vite. React Flow provides the draggable node-and-edge canvas. Custom CSS and a Tailwind CSS build pipeline support the visual design. The app registers 11 imperative WebMCP tools through document.modelContext.registerTool(). They cover reading the workspace, staging factors and relationships, creating branches, applying shocks, proposing mitigations, running stress tests, and comparing or explaining results. Tools use structured schemas and bounded inputs. Version checks on scenario-editing tools help reject stale writes when a person and an agent are working on the same model. Draft revision is limited to unlocked draft factors. A local TypeScript engine propagates shocks through accepted relationships to produce deterministic sensitivity metrics and impact paths. Its outputs are modeling aids. Vitest tests cover stable metrics, shock propagation, draft exclusion from cost and schedule totals, and graph layout. The workspace is stored in browser localStorage and can be exported as JSON. The app does not need its own AI API key; a connected agent uses the page's tools. That agent still receives the workspace data exposed through those tools. Cascade is hosted on ChatGPT Sites with a Cloudflare Workers-compatible build, with source code on GitHub under the MIT license. Challenges we ran into One challenge was making the graph behave like a genuine working surface: cards needed to move freely while their connections stayed anchored. Another was separating exploration from commitment. An agent needs room to test a disruption without silently rewriting the baseline, and people need a clear distinction between proposed and accepted changes. Rehearsing the demo exposed a subtler problem: an agent created a scenario whose description mentioned a delay, but did not actually apply the delay to the model. That reinforced an important lesson: a success message is not proof of a state change. Reliable collaboration needs outcome verification, not just well-described tools. Accomplishments we're proud of We built a working shared canvas where agent actions become visible, reviewable changes rather than suggestions trapped in a conversation. The same decision model supports both the product-launch and community examples, and the app remains usable by a person when WebMCP is unavailable. Most importantly, human review is part of the interaction itself: proposals, locks, scenario branches, and promotion controls make the collaboration boundary visible. What we learned Agent-native design is as much about accountability as capability. Giving an agent tools is only the beginning; the application must make its actions understandable and checkable. We also learned to distinguish a useful model from a confident-looking number. Cascade's purpose is to expose assumptions and explore consequences, not claim certainty about the future. What's next Stronger end-to-end evaluations that verify actual model changes after agent actions. More explicit feedback when a scenario has been created but no disruption has been applied. Improved mitigation-effect modeling, uncertainty handling, and explanation of score contributions. Shared team workspaces with durable persistence. Evidence links and richer review history for the assumptions behind a decision.
