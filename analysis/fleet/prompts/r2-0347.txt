# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

A WebMCP workbench where you and a browser agent triage a network's MACs on one surface: paste raw ARP/DHCP dumps, enrich every address against macadress.com, filter, and export an allowlist. Like Comment Story Updates Mac Inventory WorkBench Sample Data Mac Address Enrichment Export Options ChatGPT Agent Interaction Inspiration Anyone who has done network cleanup knows the loop. You pull an ARP table off a switch, or a DHCP lease file, or a page of nmap output, and you are staring at 150 MAC addresses. Which ones are real devices? Which are VMs? Which are phones cycling through randomized addresses so they never look the same twice? Which OUI was never registered with the IEEE at all? The honest answer is usually a spreadsheet on one monitor and a vendor-lookup site on the other, and an hour of alt-tab. The WebMCP Challenge asked for something specific: a page where a human and a browser agent work the same surface, not a chatbot bolted onto a UI. Network triage turned out to be a near perfect fit. The task is tedious, it is full of small judgment calls, and it produces an artifact someone actually applies afterward: a firewall allowlist. macadress.com already solved the hard part behind an API (OUI and IEEE registration data, device-class inference, virtualization fingerprints, randomization scoring), so the workbench itself could stay thin and honest. What it does Paste raw text. The app extracts every MAC in any common format (colon, hyphen, Cisco dotted, bare hex), enriches each one against macadress.com, and drops the results into a table you can slice by vendor, device category, virtualization platform, "randomized," or "unregistered." When the slice looks right, you export it as an nftables set, a Zeek annotation file, or CSV. Every button on the page is also a WebMCP tool. There are eight: add_mac_addresses , load_sample_data , lookup_mac , enrich_inventory , summarize_inventory , filter_inventory , export_filter_list , clear_inventory . The agent and the person edit one inventory. There is no separate agent view and no "agent mode." If the agent filters to virtualized hosts and builds an nftables set, the human watches it happen in the same table and export box they would have used by hand. How we built it Two pieces, no build step. web/ is static HTML, CSS, and JavaScript. The design rule was one shared state object. app.js defines an ops object with the actual operations. The on-page buttons call ops . The WebMCP tool handlers call ops . Because both paths mutate the same Map of rows and the same listener set re-renders the table, the human sees the agent's work land row by row, and the reverse. web/wmcp.js is the only file that touches the WebMCP spec, on purpose. It resolves the host object ( document.modelContext , falling back to navigator.modelContext ) and supports both the modern registerTool({ name, description, inputSchema, execute }) shape and the older bulk provideContext({ tools }) shape. It wraps every handler so a handler can return a plain JavaScript object and the adapter stringifies it, since execute is required to resolve to a string. worker/ is a Cloudflare Worker that proxies api.macadress.com . The API key lives as a Wrangler secret and never reaches the browser. The Worker also enforces a route allowlist (single lookup and a capped batch only), a per-IP rate limit, and a CORS origin pin. The math that matters A MAC address is 48 bits, so there are 2^48 of them, roughly 2.8 x 10^14. The IEEE hands out the top 24 bits as the OUI and the vendor owns the bottom 24, which is 2^24, or 16,777,216 addresses per registration. Randomized addresses are the reason a hand-built allowlist rots. The naive detector is a single bit: the locally-administered bit, the second-least- significant bit of the first octet. Write b for that octet and use the wedge for bitwise AND: $$b \land \mathtt{0x02} \neq 0 .$$ That flag is necessary but not sufficient, because plenty of legitimate hardware is locally administered. macadress.com layers a confidence score on top, and the workbench only marks a row as randomized when the API returns potentially_randomized with confidence possible or likely . Enrichment runs in batches of 40, so the cost is one upstream call per 40 addresses, with a per-row fallback if the batch endpoint misbehaves. Challenges we ran into The WebMCP surface is still moving. Different runtimes expose different objects and different registration methods. Isolating every assumption into wmcp.js meant the rest of the app never had to care, and a spec change is a one-file diff. Tools have to return strings, but useful strings. A handler that returns { found: 12, added: 9 } is easy to write. Making sure the agent gets back something it can reason about took a pass over every return value and every tool description. The descriptions are the real API, so they say when to call a tool, not just what it does. Percent-encoding broke lookups. The upstream API does not decode %3A , so a MAC sent as 00%3A11%3A22... fails. The Worker forwards the colons and dashes intact and only decodes a caller that pre-encoded, so both callers end up identical. A public Worker URL cannot hold a real secret. The answer was layers instead of one wall: a dedicated low-quota key, an edge WAF rule that rejects any request whose Origin is not the demo page, a rate limit, and a rotatable friction token shipped in config.js . None of them is cryptographic alone. Together they make an abused URL cap out fast. Demo limits during judging. Testing burned through the shared key more than once, so we added a bring-your-own-key path: paste a macadress.com key into the header, it is stored in that browser only and sent as X-Macadress-Key , and the Worker forwards it upstream while skipping the demo gate and the shared rate limit. A shared decision canvas where people and agents map hidden assumptions, stress-test plans against real world shocks, and turn uncertainty into resilient action. Like Comment Story Updates Inspiration When working on an app launch, we found ourselves sending planning docs back and forth between us and our agents. That was very problematic. We wanted to move beyond asking an AI, “What could go wrong?” and getting another list to read. What if the agent could work inside the plan itself, connecting assumptions, exploring consequences, and proposing alternatives that a person could inspect and challenge? That became Cascade: a shared decision canvas for people and their agents. What it does Cascade turns a consequential plan into a connected map of objectives, assumptions, dependencies, constraints, risks, and outcomes. Our demo starts with a product launch: six weeks, 500 teams, and a $12,000 budget. What happens if billing arrives three weeks late? An agent can create a separate what-if branch, apply the disruption, and trace modeled downstream effects. It can then stage possible responses, such as launching a free beta first. The human can inspect the map, drag cards with their connections following, compare scenarios, and accept or reject proposed factors and relationships. Applying a shock is allowed inside a what-if branch; proposed mitigations remain drafts awaiting review. Promoting a branch is a human action. Product launch is the starter. Cascade also includes a community tool-lending scenario and a blank workspace for other plans. Why WebMCP Cascade is built around a shared working surface, not a separate chat transcript. WebMCP lets the agent read and act on the structured model behind the page. Tool actions update the same interface the person is watching: branches appear, shocks enter the map, and proposals arrive for review. This makes an otherwise awkward workflow practical: the agent explores alternatives inside the live application while the person retains an inspectable record of the model and controls which proposals are accepted. There is no need to copy the plan into a chat and manually translate the answer back into a diagram. How we built it Cascade uses TypeScript and React, with a Next.js-style App Router implemented through vinext on Vite. React Flow provides the draggable node-and-edge canvas. Custom CSS and a Tailwind CSS build pipeline support the visual design. The app registers 11 imperative WebMCP tools through document.modelContext.registerTool(). They cover reading the workspace, staging factors and relationships, creating branches, applying shocks, proposing mitigations, running stress tests, and comparing or explaining results. Tools use structured schemas and bounded inputs. Version checks on scenario-editing tools help reject stale writes when a person and an agent are working on the same model. Draft revision is limited to unlocked draft factors. A local TypeScript engine propagates shocks through accepted relationships to produce deterministic sensitivity metrics and impact paths. Its outputs are modeling aids. Vitest tests cover stable metrics, shock propagation, draft exclusion from cost and schedule totals, and graph layout. The workspace is stored in browser localStorage and can be exported as JSON. The app does not need its own AI API key; a connected agent uses the page's tools. That agent still receives the workspace data exposed through those tools. Cascade is hosted on ChatGPT Sites with a Cloudflare Workers-compatible build, with source code on GitHub under the MIT license. Challenges we ran into One challenge was making the graph behave like a genuine working surface: cards needed to move freely while their connections stayed anchored. Another was separating exploration from commitment. An agent needs room to test a disruption without silently rewriting the baseline, and people need a clear distinction between proposed and accepted changes. Rehearsing the demo exposed a subtler problem: an agent created a scenario whose description mentioned a delay, but did not actually apply the delay to the model. That reinforced an important lesson: a success message is not proof of a state change. Reliable collaboration needs outcome verification, not just well-described tools. Accomplishments we're proud of We built a working shared canvas where agent actions become visible, reviewable changes rather than suggestions trapped in a conversation. The same decision model supports both the product-launch and community examples, and the app remains usable by a person when WebMCP is unavailable. Most importantly, human review is part of the interaction itself: proposals, locks, scenario branches, and promotion controls make the collaboration boundary visible. What we learned Agent-native design is as much about accountability as capability. Giving an agent tools is only the beginning; the application must make its actions understandable and checkable. We also learned to distinguish a useful model from a confident-looking number. Cascade's purpose is to expose assumptions and explore consequences, not claim certainty about the future. What's next Stronger end-to-end evaluations that verify actual model changes after agent actions. More explicit feedback when a scenario has been created but no disruption has been applied. Improved mitigation-effect modeling, uncertainty handling, and explanation of score contributions. Shared team workspaces with durable persistence. Evidence links and richer review history for the assumptions behind a decision. What we built The Personal Data Rights Workbench makes a synthetic account's data footprint legible before consequential actions commit. A person or browser agent can inspect a 14-category inventory, read four consent choices and two retention constraints, simulate a complete data-minimization partition, understand feature trade-offs, and stage consent, erasure, or portability actions. The responsive data map reorganizes into Delete , Retained by rule , and Kept by choice . The headline fixture shows exactly 9 / 2 / 3 categories and an honest 92.6% reduction of deterministic demo bytes. The review matrix shows the exact staged action IDs and values. Commitment through the normal visible page control updates inventory and consent, clears staging, and creates an immutable synthetic receipt. 2. How we used WebMCP The top-level page registers nine imperative JavaScript tools for inventory, consent, retention, simulation, plan-bound staging, cancellation, and receipt reading. It prefers document.modelContext and retains navigator.modelContext only for older Chrome preview builds. Registration is scoped with an AbortController and atomic: all nine calls are initiated in one synchronous task, then awaited as a group. If any call throws or rejects, every attempted name is removed, the lifecycle is aborted, and readiness rejects. Tool callbacks use execute(input, { signal }) , while tolerating older callers that omit options. Inputs are validated in code, every non-retained category must be explicitly classified, plans receive unique IDs, and all staging is bound to the exact current plan. No consequential commit tool is exposed through WebMCP. Final commitment uses the normal visible page control and remains subject to Codex/browser safety confirmation; ordinary browser actuation may still reach visible controls. The read-only receipt tool returns only after commitment. 3. Why it matters Privacy controls often split one intention across opaque settings, retention language, and destructive forms. This workbench explores a more inspectable model: structured agent assistance for inventory and planning, explicit user intent for every category, visible consequences, version-bound staging, and a clear commit point. The demo does not determine legal rights or establish compliance. It demonstrates how WebMCP can make a complex workflow composable, visible, and truthful before and after commitment. 4. What we learned Tool quality is inseparable from visible state. The same domain service powers the UI, WebMCP tools, and deterministic rehearsal. A mutating callback rejects if already cancelled, then commits state, synchronously flushes the React subscription update, and returns without awaiting post-mutation work. Confirmed receipts also close every staging path. We also learned that schemas are routing guidance, not authorization; omitted categories must not be interpreted as user intent; every staged action needs a plan version; partial tool registration is unsafe; and receipts should describe only actions that actually committed. For compatibility with the client used in the demo, tools are registered imperatively in the top-level page. How we used AI and Codex This is a new project created during the challenge period. Known Limitations All records, identities, sizes, retention rules, dates, and receipts are deterministic synthetic fixtures.
