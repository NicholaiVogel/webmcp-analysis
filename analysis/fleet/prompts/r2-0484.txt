# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

OpenAI/ChatGPT app still support WebAuthn so we demoed via Chrome, this is surely a feature to allow very soon as the protocol matures. Other: A click is not evidence. A real agent, told to wait, ended its turn instead. So we built the gate to hold the line : a gated call is held open (bounded) until the person acts, answering the exact call that asked. After multiple tests we got 100% success rate , virtually resolving in modern frontier models the need for a true exchange between agents, stable, without latency. Agents still don't lean into discovering WebMCP affordances in the websites. We intuit this is also something that will evolve as the protocol is widely adopted, but for now, many agents need the nudge to search for and prioritize using WebMCP if available. Accomplishments that we're proud of A consequential action that an agent provably cannot complete alone — measured, not asserted. Domain-neutrality shown, not claimed: shop and clinic on one gateway, identical transcript, origins, refusal shape, and gate. In the clinic, restricted records (mental health, substance use, genetic) are impossible for an agent to release — refused at the tool and excluded at the authoritative Worker. Shipped as a reusable layer, not just a demo: a drop-in library (one script tag, zero install for the user), the primitives (participant attribution, the WebAuthn gate, an authoritative Worker), and the conventions (the refusal shape) — ready to become a standard part of WebMCP. What we learned Attribution is the enabler for trust. Once the page can honestly tell an agent's call from a person's, you can stop trying to detect humans heuristically and instead require the one thing only a human has — a hardware gesture. Gates must read stamped fields, never prose; no authorization may depend on a model having understood a sentence. What's next for 3way The honest gap: none of our mitigations can wake an agent that never chose to wait — that's a spec ask we've written up; we suggest expanding the WebMCP to fully accommodate its usability as an A2A exchange. That is useful. It is also the obvious move. I wanted the harder surface: several real apps that stay themselves, each with its own origin and document, and one workspace where a person and an agent share those live apps. I built it so that Root does not sneak around the iframe and hit the child APIs itself. Cross-app work is what people already struggle with. Copy an id. Retype an email. Open the next tab. Hope the page still matches the plan. Agents are already strong at planning. What they cannot do, unless the sites hand them tools, is act on those live pages as part of one governed run. That is what Root is for: an orchestrator between Catalog, Customers, and Cases. Each app keeps its own tools on its own document. Root discovers and invokes them there, and the UI on that page is the evidence. What it does Root is a Mac-style desktop in the browser. Catalog, Customers, and Cases open as real provider windows. Lab can join after a human grant. Each provider is its own deployed site. Root loads it in an iframe with allow="tools" and only talks to tools that document exposes to Root. A person and an agent can run a pass across those windows: Search customers, products, or cases on the live lists Pause for a human row pick when there is a real choice Bind a later step to that selected snapshot (Root carries the object; it does not flatten Ada into a retyped email string) Open a record, or fill a create form and wait for a human persist on stage Keep other provider windows live instead of destroying them when work moves Notify when a wait needs you: after you grant it in inspect Settings, a pending-on-human pause plus a hidden Root tab shows a Notifications API toast (not Push, and not while Root is visible) Root’s own page registers the gateway the agent calls: list_providers , discover_capabilities , prepare_workflow , execute_workflow , invoke_granted_tool , plus inspect, cancel, and window chrome. Prepare freezes an allowlisted graph before anything runs. Execute opens or reuses each window, rediscovers, revalidates, and invokes on the live document. Take control stops the agent on that window. Custom tools never enter pass evidence. Try it: root.danieloyerinde.com with Customers , Catalog , Cases , and Lab . How I built it Four independently deployed Next apps (Root, Accounts, Shop, Support) plus Lab, one Express/tRPC API, and Postgres with tables owned by domain. No cross-domain joins. Support keeps its own copies of customer and order text. Root never mutates child domains through tRPC. On WebMCP: Each child registers tools on document.modelContext and exposes them only to Root’s origin Root’s Permissions-Policy delegates tools into those iframes Discovery uses getTools({ fromOrigins }) ; invoke uses executeTool in the child’s context Root is the author-provided agent that composes nested provider tools; the agent talks to Root’s gateway, and Root invokes tools inside each iframe The workflow layer is prepare then execute. Search, select, open, and create are allowlisted. A later argument may be a bind to an earlier selected snapshot. Create writes only after a human persist on stage. Agent lease is per window so one document serializes while another stays free. Rich fill, preview, and pick presentation run on stage on the live controls, not as a fake overlay of the whole desktop. Challenges I ran into The first hard truth was uniqueness. Multi-tab agents can already visit three sites. “Root opens three iframes” is not enough. The product only wins if the person and the agent share the same live documents under a freeze the agent cannot quietly rewrite. A core challenge was ChatGPT’s in-app browser. It only exposed top-level tools on Root. It did not discover tools registered inside provider iframes. That is exactly where Catalog, Customers, and Cases live. That gap is what pushed me onto a WebMCP-capable Chrome setup (testing flag / extension path) so nested getTools and executeTool could actually run against those documents. One stage window that remounted and killed the previous app made collaboration impossible. Search results and selections vanished when the next step switched providers. I moved to persistent independent windows so Customers can stay while Catalog runs. Binding looked simple until it was not. Typing Ada’s email into Cases again is not a handoff. Root has to deliver the selected snapshot intact and refuse graphs that invent ids from search results instead of an explicit selection. Human pauses were another edge. A pending pick, a create persist, Take control, and a silent timeout are different outcomes. Take control must fail closed as stopped by the user with no retry. A timeout with no gesture is not the same thing. Accomplishments that I'm proud of I shipped a real desktop, not a slide. Multiple provider windows stay live. Prepare refuses illegal tools and arguments. Execute rediscovers and fails closed on drift. The together loop is concrete: the agent fills a search, the person clicks Lin or Silent Mouse on the live list, Root binds that snapshot into a later Cases step without retyping her email, and Take control can stop the run on that window. Domain data lives in Postgres with SQL search. The iframe is not a picture over Root’s own API. Custom providers can still join behind a human grant without entering the typed pass. What I learned WebMCP tools belong to the open document. If Root calls the child’s API itself, the iframe is only decoration. An agent can run searches it already knows without the person. That is not much of a shared loop. Selection, bind, and create-after-persist are the parts where the person actually has to act on the live page. One allowlist scales cleaner than a prepare function per app. The step cap is only a safety limit. It is not tied to how many providers exist. Legal tools can repeat. Illegal ones still fail. Remounting the only window on every step wiped the previous app’s UI. Keeping separate windows open, with a lease per window, matched how people already keep a few apps around. What's next for Root As WebMCP leaves experiment and settles into real browser conventions, I expect clearer nesting rules, better host and agent tooling, and shared patterns for selection, grants, and multi-document work. Root will get simpler as those conventions land. Conclusion As of today, this principle gets shaky towards my final stages, after a final extensive check. A few things met me head-on. The agent can bypass Root. Even with a custom-tool setup where Root would in fact reject invoke when the tool is not granted, the agent could still go around me, because the underlying iframe exposes tools to the parent origin. That path is not quite spelled out in the docs the way you’d hope. Those tools would not show up when you list Root’s gateway tools, but Chrome still exposes them by name (direct invocation), so there is a direct bypass between Chrome and the providers. As WebMCP moves off experiment, the goal is that we get to conventions where this kind of multitasking is better supported, and where the tooling around it is better too. There is also usually a .map error that surfaces via the inspector. After extensive debugging, several bridges on my side were tested and still did not own the failure. The tools I had were limited, so I could not A/B the remaining layers cleanly (fresh tab vs stale session, inspector path vs gateway path, flag and extension in vs out) to confirm where it breaks.
