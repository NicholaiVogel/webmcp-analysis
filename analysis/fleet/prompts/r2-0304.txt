# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Neither felt right for something as personal as a mind map. A mind map is your thinking laid out — I didn't want an agent replacing that, I wanted one that could sit down next to me and actually draw on the same page. When I found WebMCP — a way for a web page to expose its own real functions as tools an agent can call directly, in the browser, no backend required — that was the whole idea in one API. So I built the thing I actually wanted: one canvas, one undo history, a human and an agent both reaching for the same nodes. What it does Canvas Co-Pilot is a mind-mapping canvas that a person and an AI agent can edit at the same time , live, in the same browser tab. Add nodes, branch out ideas, drag things around, color-code by hand — and an agent can do all of that too, through 20 real tools registered via document.modelContext (add a branch, restyle a node, connect two ideas, reorganize the whole layout, export to SVG/PNG/Markdown/Mermaid, import any of those back in). Every change either of us makes lands in one shared undo history, so nothing an agent does is ever outside a person's ability to take back. How we built it Plain HTML, CSS, and JavaScript — no framework, on purpose, so the whole render/state pipeline stays easy to reason about. Dagre handles auto-layout, the canvas itself is hand-rolled SVG with full round-trip fidelity (export a diagram, re-import it, get back exactly what you started with, including every color and shape override). For WebMCP itself, the app checks for native document.modelContext support first and only falls back to the @mcp-b/webmcp-polyfill when it's not there — the header badge tells you honestly which mode you're in, native or polyfilled, rather than pretending it's always native. It's deployed on both Netlify and Vercel. Challenges we ran into Most of the real work wasn't the happy path — it was the bugs that only show up once you actually try to break the thing. A user pasted a Mermaid-style edge list ( root --> human ) into Import, and it silently created 39 broken, half-named nodes instead of failing loudly. The importer's "is this quick-outline shorthand" check was matching on any > character — which also matches an arrow. Fixed with a negative-lookbehind regex that tells an arrow apart from actual shorthand syntax, and now a bad paste tells you it didn't understand instead of quietly corrupting your canvas. "Select all connectors" would silently reset back to nothing the moment you clicked anywhere on the empty canvas — even just panning to look at something. If every connector already had its own color (which they do once you've styled a diagram), the next color change would then land on the invisible graph-wide default instead, and visibly do nothing at all . Took real reproduction work to catch, since it only shows up with an incidental click in between two actions that each look correct on their own. I tried making multiple connectors landing on the same node spread out instead of converging on one point — and it technically worked, with proper diamond/ellipse-aware geometry and everything. But it just looked wrong. "Multiple octopus hands" was the exact feedback, and it was right — I reverted the whole thing. Good reminder that a fix being technically correct doesn't mean it's the right call. Two of the 20 tools had names close enough to trip up an agent, not a human: combine_nodes and connect_nodes sound almost identical but do very different things (one creates a brand-new node, the other just links two that already exist). Caught it by checking the tool descriptions against Chrome's own published guidance for testing WebMCP tools — and fixed it with one clarifying sentence in each description. Accomplishments that we're proud of Getting a second AI vendor to prove the point without any custom integration work: I handed ChatGPT nothing but the live tool schema and a canvas snapshot, and it wrote genuinely correct document.modelContext calling code — right API shape, right pattern — with only two small gaps (a missing await , a guessed return shape) that came from never having seen a live response, not from misunderstanding the standard. That's the whole promise of WebMCP working, not just Claude working. I'm also proud of how much of this session was bug-hunting rather than feature-building. Reproducing the connector-selection bug took building the exact failure chain step by step before I even knew what was wrong — not just patching the first thing that looked broken. What we learned The most validating thing I found wasn't something I built — it was rereading WebMCP's own spec and seeing my own instincts already written into its stated goals: "enable human-in-the-loop workflows," explicitly not "fully autonomous agents operating without human oversight." I hadn't copied that language, I'd just built toward the same idea independently, which is a nice signal I was pointed the right way from the start. I also learned that small stuff in a tool's description matters far more than it looks like it should. Two similar-sounding tool names, or three tools that could all plausibly answer "make it red" — those are exactly the kind of ambiguity that trips up a model even when every individual tool works perfectly in isolation. What's next for Canvas Co-Pilot: WebMCP Mindmap Native support: Chrome 149 and Edge 150 both have live Origin Trials for real (non-polyfilled) document.modelContext — worth registering for so the badge can honestly say "Native" for more visitors, not just the polyfill. Dynamic tools: right now all 20 tools are registered once at load. The spec supports tools that appear only when relevant (e.g. a delete_node tool that only shows up once something's actually selected) — that's a more honest surface for an agent to reason about than one static list. Multiplayer: right now it's one human, one agent. Extending the same shared-state model to multiple people on the same canvas is the natural next step.
