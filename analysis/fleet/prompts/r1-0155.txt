# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

This authorization boundary is enforced by the server and state machine, not by relying on the agent to behave correctly. The experiment then progresses through: DRAFT → AWAITING_APPROVAL → APPROVED → RUNNING → COMPLETED → ANALYZED → REPLICATED Rejected experiments can return to the draft state for revision. Evidence, not fabricated answers NOVA persists the experiment and its observations rather than generating a result only for display. The current simulation produces synthetic experimental observations using deterministic simulation with stochastic noise. This is explicitly disclosed in the application. After execution, the agent can retrieve the persisted observations and request statistical analysis. NOVA calculates effects, confidence intervals, p-values, interaction effects, and condition means from the stored observations. The experiment can then be independently replicated using a new seed. The replication evaluates whether the direction of the result is consistent, whether confidence intervals overlap, and whether the relative effect difference remains below the defined threshold. Provenance NOVA preserves provenance throughout the experiment lifecycle, including experiment IDs, simulation version, seeds, timestamps, observations, analysis records, findings, replications, and state-transition events. This makes it possible to trace a conclusion back to the experiment and measurements that produced it. Why WebMCP The interesting part of NOVA is not simply that it can simulate plant growth. The project explores a different interaction model for the web: a website can expose meaningful capabilities that an external agent can discover and execute. The agent does not need to be given NOVA's internal implementation or a custom integration created specifically for the demonstration. It encounters the website and its exposed capabilities through WebMCP. That allows the website to remain responsible for its own state, validation, authorization, execution, persistence, and evidence while the external agent handles reasoning and orchestration. What I learned Building NOVA required thinking about a website as more than a collection of pages and API endpoints. The WebMCP layer became a capability boundary between the external agent and the application. I also learned that exposing tools is not enough by itself. Each tool has to connect to the same application logic used by the website, preserve authorization rules, validate inputs, produce persistent state changes, and leave an auditable event trail. The most important design decision was therefore keeping the WebMCP tools thin: they expose capabilities, while the server remains the source of truth for scientific state and authorization. Challenges The hardest parts were making the system genuinely stateful and ensuring that an agent could not bypass the experiment lifecycle. A successful tool call had to correspond to a real application operation rather than a simulated response. This meant connecting WebMCP execution to validation, authorization, the experiment state machine, PostgreSQL persistence, statistical analysis, and provenance. Another challenge was making the synthetic simulation useful for experimentation without presenting synthetic results as real scientific measurements. NOVA therefore labels its generated observations and preserves the simulation version and seed as part of the experimental provenance. NOVA is intentionally a constrained scientific demonstration, but the underlying interaction model is the focus: an external agent discovers and operates an executable, stateful environment exposed by the web. A WebMCP shopping mall for agents, with one-click checkout that actually works. Like Comment Story Updates Styled order page after approval: item, delivery region, total and order id. Sandbox, nothing charged. The panel after one click: order confirmed in place, tools still registered, agent reads it back with get_order. The moment of truth on the tools page: item, delivery region, total, one button. No tool can press it. Fallback approval page for a link opened outside the tools page: one button, Touch ID where the browser offers it. Inspiration Agents can't reliably complete checkout. They search fine, compare fine, even fill in a cart, but the step that actually spends money is where almost every agent attempt on the open web falls over. We set out to fix that one failure: a real store and a real purchase path first, because checkout is where agents fail, not discovery. Only then did we look for a tool surface an agent could use with nothing installed, an MCP-like layer that just lives on the page. That's when we found WebMCP. What it does Robodepo is being built as the world's largest shopping mall for agents: the best product information and a completed order, across millions of stores. An agent gets: Better information to find the right product, not just a matching title: get_product already returns a cited evidence pack for this product; every product is the roadmap. A short, checkout-ready shortlist instead of trawling thousands of irrelevant pages ( search_by_activity on the roadmap). A reliable checkout: one call runs the whole pre-purchase path ( create_checkout ). A simple, Touch ID style confirmation before anything is spent: a presence check, not a payment authorisation (WebAuthn). Responses that tell the agent what to do next. Every response carries a state to branch on, a message naming the field and fix, and next actions with the retry prefilled: an error is never a dead end. A real example, trimmed, from create_checkout given a wrong postcode: { "status": "incomplete", "messages": [ { "code": "address_not_accepted", "path": "$.shipping_address", "content": "Use the accepted sandbox address, then call create_checkout again." } ], "next_actions": [ { "tool": "create_checkout", "why": "Retry with the accepted address." } ] } How this is different from what exists. Merchant tooling (Shopify, Google's UCP, Microsoft Copilot Checkout) asks every store to integrate first. Amazon's Buy for Me, Rye and Zinc automate one store's own checkout on the shopper's behalf. Robodepo aggregates instead: a store never integrates or joins anything. Robodepo lists it, discloses it as the source, and buys under the store's published rules on the human's behalf, so the same tools work across every store listed. The shop does nothing. The agent gets information it cannot get elsewhere: source and price side by side, evidence and a shortlist on the roadmap. The human keeps the irreversible step by construction, not policy. Completion is measured, not claimed: a sealed rig checks real agent runs. The nearest things are protocols that ask every shop to integrate, or agents that scrape. How we built it Before the challenge: the store, its purchase API and confirmation page. Built for the challenge: everything at /agent , the 12-tool WebMCP catalogue, the one-call checkout, an in-page approval panel that turns into an order card in place (a separate approval page stays as fallback), the feedback endpoint, the tests, and the public repo. Full write-up: https://robodepo.shop/agent/story.md Each tool (8 working, 4 marked plainly as preview) carries a short description sized to Chrome's WebMCP guidance; the full guide lives at /agent/tools.json , callable on demand with get_tool_guide . We use both halves of the API: the scripted registerTool for the catalogue, and the declarative form attributes ( toolname , tooldescription , toolparamdescription ), which Chrome documents as an origin trial, on the feedback form. The store is a tracer, instrumented so real agents run through it under sealed conditions. Premium levels are committed cryptographically before any run starts, every purchase record gets an independent LLM audit, the protocol is versioned, and a price-integrity check voids any run where prices differ. The rig has been through ten adversarial review passes. The boundary that matters for trust is not where an agent chooses to stop. It is proving, mechanically, that it cannot cross it, rather than asking nicely. The rig runs real agents, ChatGPT, Codex, Claude and Claude Code, through the purchase path run after run. It taught us agents fail when a step is unexplained, so responses name the field, the fix and the next tool, and nine steps became one call. It found a checkout defect no local test could see. Next, it opens as a Test Track for agent developers. The demo runs natively in ChatGPT's in-app browser: open robodepo.shop/agent and ask for a product. Code: https://github.com/Web3Zero/robodepo-webmcp Challenges we ran into The hardest part has been the testing rig and evaluation work behind the store: running real agents through the purchase path again and again, catching failures, fixing the store, re-running. That loop builds the moat: "it works for agents" becomes a checked result. Writing tool descriptions an agent could act on without guessing was its own problem: short enough for a browser to show, full depth a call away. Getting create_checkout right took real care: several steps behind the scenes while looking like one clean call, refusing cleanly the moment an address or quantity doesn't match. Accomplishments that we're proud of A person can hand an agent a plain-English request and watch it search, price and prepare a real sandbox order, with a Touch ID style tap the only irreversible step. No tool can press it: the run cookie, a single-use security code, a single-use order key and a same-origin submission all protect it. The four preview tools say plainly what's coming instead of quietly claiming it's already there. What we learned Depth and brevity aren't opposites when split properly: a short description in the list, the full guide one call away. The boundary that matters for trust is not where an agent chooses to stop; it is proving, mechanically, that it cannot cross it, rather than asking nicely. What's next for Robodepo Robodepo's roadmap groups around what helps an agent buy well, every item already in the catalogue: Search by need: a shortlist for the request instead of thousands of irrelevant pages ( search_by_activity ). The best source of product truth: specs, care, review themes and permitted YouTube transcript evidence, cited, live today for this product through get_product 's include_evidence option; every product is the roadmap. Side by side comparison across products ( compare_products ). One tool to transact across many merchants ( get_shipping_options ). Continued assistance: replenishment reminders and price alerts ( subscribe_replenishment_alerts ). A Test Track: the same harness, open for developers to prove their agents against a real checkout before going live.
