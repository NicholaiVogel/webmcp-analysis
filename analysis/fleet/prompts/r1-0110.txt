# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably

- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.

Like Comment Story Updates GIF Agent build house GIF Agent build pixelart GIF Agent build district GIF Building the beacon with the agent GIF Experimenting with dynamic seasons GIF The final seasonal loop around the beacon Inspiration The idea for Voxel Web MCP came from WorldEdit, a tool I used in voxel sandbox games as a kid. Back then, building anything large meant running around the world, selecting coordinates, and manually entering commands for every wall, region, replacement, or correction. When we first saw WebMCP, we wondered what would happen if an agent could use similar geometric operations directly inside a browser-based 3D world. Instead of telling it which exact blocks to place, could we simply describe the final intention in natural language? A voxel world felt like a particularly demanding test. It is not a form, a store, or a collection of buttons. It is a procedurally generated three-dimensional environment containing terrain, materials, structures, coordinates, and a moving player. If an agent could understand and meaningfully modify that through WebMCP, the same approach could potentially work across many other complex web applications. What it does Voxel Web MCP is a browser-based voxel sandbox where a human player and an AI agent can build together. The player can make requests such as: Build a seaside house with a pier. Inspect this small architectural model and transform it into a full-scale structure. Replace one material throughout a building. Recreate an attached image as voxel pixel art. Copy, move, rotate, mirror, or repeat an existing region. Inspect the terrain around the player before deciding what to build. The agent operates as a world editor around the player. It understands the player's position, viewing direction, targeted block, world boundaries, available materials, and selected regions of voxel geometry. We deliberately did not create semantic tools such as build_house . The application only exposes reusable geometric primitives. The agent must decide for itself what should become a wall, roof, window, tower, road, or complete building. This makes the experience open-ended: the tools are not tied to a collection of predefined demonstrations. How we built it We started with VoxelSrv, an open-source browser voxel game built on noa-engine and Babylon.js, and created our own WebMCP integration layer. The application registers eleven structured tools through the browser's document.modelContext API. They cover: operating guidance for the agent; world boundaries and the material catalog; player position and viewing direction; compact region scanning; batch block placement and replacement; copying, moving, mirroring, rotating, and stacking regions; WorldEdit-style undo. The game runs both its client and authoritative single-player server inside the browser. The server runs in a Web Worker, while WebMCP calls travel from the main page to that worker through correlated messages. World edits are applied by the authoritative server and sent back to the renderer as normal block updates. The world is stored locally in IndexedDB. Players can save, regenerate, export, and import worlds without requiring an external database or game server. We also added a Docker build that compiles the Vite application in a Node.js stage and serves the final static bundle through Nginx. The context problem Writing blocks was not the hardest part. The real challenge was giving the agent an affordable and reliable understanding of a three-dimensional space. The agent should not have to reconstruct the world from screenshots, and sending every voxel as raw JSON would consume an unreasonable amount of context. In one representative region, a raw dump required roughly 49,000 tokens. We therefore designed a progressive inspection system. The agent can begin with a cheap summary, request a heightmap when it needs terrain information, or inspect selected two-dimensional slices when it needs to understand floors, walls, roofs, and elevations. The application also provides an explicit coordinate basis: the player's forward, right, and up directions, along with the exact block being targeted. This allows the agent to interpret requests such as “behind me,” “in front of me,” or “continue to the right” without guessing camera geometry. Challenges we faced The upstream engine was built around an older JavaScript ecosystem. Making it work with a modern Vite build required pinning compatible versions of noa-engine, Babylon.js, the voxel protocol, and several legacy dependencies. The game also uses multiple browser execution contexts. The renderer runs on the main thread, while the authoritative world and terrain generation run in Web Workers. WebMCP edits therefore had to update the server's real world state and remain synchronized with the client's chunk cache and rendered meshes. Other challenges included: keeping world inspection compact enough for an agent's context; providing useful material descriptions without duplicating them across every tool; making large edits visible without flooding the renderer; supporting concurrent tool calls while preserving understandable undo behavior; restoring reliable mouse input after browser focus changes; adapting camera controls for agent browsers that cannot use relative mouse movement; preserving worlds locally and adding portable import and export. What we learned The most surprising result was how much an agent could accomplish with a relatively small set of general-purpose tools. It did not need a dedicated house generator or a library of predefined structures. Once it could inspect the terrain, understand the player, discover available materials, and perform geometric operations, it began producing coherent and often genuinely creative architecture. We also learned that agent context is part of the product's interface. Tool descriptions alone are not enough for spatial work. Coordinate systems, compact representations, world limits, material semantics, and clear operating guidance all directly affect the quality of the result. Most importantly, WebMCP allows the agent to stop being a chat window beside an application and become an active participant inside it. What's next The current version focuses on a single-player creative sandbox, but the same model can extend much further. An agent could work with a normal player's inventory and permissions, assist multiple players in a shared world, automate level-design workflows, manipulate other kinds of 3D editors, or interact with entirely different WebMCP-enabled applications. WebMCP creates a shared interface between agents and web applications. Compatible agents can change without requiring the application to be redesigned around each one, while the application can evolve without changing the basic way agents discover and use its capabilities. Today, that application is a voxel world. Tomorrow, it could be almost anything on the web. So building a web alternative was something which was on my mind for a long time, and when I came to know about this webmcp challenge, I was excited by the ability to actually bring this vision to reality. What it does mimir (named after Norse God of Wisdom) is a local-native pdf reading workspace that runs entirely in your browser. You open a paper, highlight it, draw on it, pin sticky notes to it, and export an annotated copy anytime. But the interesting highlight, and which is relevant to the challenge, is that the opened document is a live tool surface. Your browser agent can do everything you can, much better and (for the most part) faster. It can search a pdf, read and navigate to specific pages, create any custom annotation you want. Sure, summarising and learning from pdf via chat tools like Chatgpt works, but there are a lot of people (researchers, lawyers, students preparing for their competitive exams, to name a few) who are visual learners, and value reading pdf the old fashioned way, but also want agentic capabilities to let their agent handle that part for you. mimir is built exactly for them, for this collaboration, and this is where browser native mcp in the form of webmcp holds a significant role. ABOUT TEXT (untrusted evidence):
A WebMCP safety layer that lets AI agents test commitments against real capacity, propose honest alternatives, and finalize only after explicit human approval. Like Comment Story Updates Inspiration AI agents are becoming increasingly capable of completing tasks, but there is an important difference between doing work and making a promise . An agent can draft a response in seconds, but accepting a deadline may silently overload the user, delay existing work, or affect other people. Most productivity tools show what is scheduled; they do not stop an agent from creating an unsafe commitment. I built Promise Gate to explore a simple principle: An AI agent may analyse and prepare a commitment, but a human should retain authority over the final promise. What it does Promise Gate is a capacity-first commitment system powered by WebMCP. The demonstration begins with a request from Northstar Studio for twelve hours of homepage work by Friday. Promise Gate shows that twenty of the user’s twenty-four safe hours are already promised, leaving only four hours available. Through WebMCP, an AI agent can: Structure the incoming request. Read the user’s available capacity and existing commitments. Test whether the original promise is feasible. Identify the exact deficit and the commitments that would be threatened. Generate honest alternatives. Stage a feasible option for human review. Finalize only an option that the human explicitly approved. In the demo, the original request is blocked because it exceeds safe capacity by eight hours. Promise Gate then offers three transparent alternatives: Deliver a smaller four-hour risk audit by Friday. Move the complete redesign to Tuesday. Explicitly displace existing work, requiring separate consent. Nothing is silently rearranged, and the agent cannot approve its own recommendation. How I built it Promise Gate is a responsive React and TypeScript application built with Vite. The page exposes six WebMCP tools: structure_incoming_request get_capacity_context reserve_original_request generate_counteroffers stage_counteroffer finalize_commitment The tools operate on a deterministic commitment model containing safe capacity, existing promises, deadlines, staged alternatives, human approval state, and schedule versions. The workflow separates reversible agent actions from irreversible human decisions. Human approval is deliberately not exposed as a WebMCP tool. The finalization tool rechecks capacity and verifies that the approved option still matches the current schedule version before creating a receipt. The interface acts as a visible decision ledger. Every tool call changes the page state and adds an entry explaining what happened, so users can understand what the agent did and why. Challenges The biggest challenge was making the safety boundary real rather than decorative. It would have been easy to add an “Approve” button while still allowing an agent to bypass it through another tool. I designed the state model so that finalization fails unless an exact staged option has been approved by a human. It also refuses the original request with a structured OVER_CAPACITY result containing the deficit and threatened commitments. Another challenge was making agent activity understandable on screen. Promise Gate therefore translates tool results into clear visual states such as Blocked by Gate , Awaiting Decision , and Committed , supported by a visible action ledger. Finally, I needed the experience to work both as an agent interface and as a normal responsive website without hiding the important decision behind generic dashboard elements. What I learned I learned that a useful WebMCP integration is not simply a collection of website buttons exposed as tools. The tool surface can encode authority, reversibility, and policy. Tool descriptions and schemas also influence how an agent reasons about a workflow. Separating “generate,” “stage,” and “finalize” creates a much safer interaction than exposing one broad “accept request” action. Most importantly, human-in-the-loop design works best when the human decision is specific. Promise Gate does not ask the user to approve a vague AI plan—it asks them to approve an exact scope, deadline, capacity allocation, and schedule version. What's next The current hackathon demonstration uses transparent fictional data so the complete safety model can be evaluated without requiring an account. The next step would be connecting Promise Gate to real calendars, project-management systems, and communication tools, allowing the same commitment gate to protect real schedules before an agent sends a consequential reply. Remember people. Don’t impersonate them. Keep turns messy relationship notes into visible promises, attention rankings, and editable drafts while the human stays in control. Like Comment Story Updates Inspiration I talk to enough people that promises disappear into notes, calendars, and guilt. Traditional CRMs optimize deals and reporting. I wanted a quieter tool for the relationships where the real question is: what did I say I would do? What it does Keep is a local-first relationship desk. It stores fictional demo contacts in the browser, turns raw call notes into owner-labelled promise chips, ranks people who need attention, and creates editable follow-up drafts. Keep never sends a message. The human remains responsible for anything another person receives. Why WebMCP This workflow depends on live page state: which person is selected, their last interaction, unresolved promises, pipeline position, and whether a draft exists. Screen scraping makes an agent guess. A backend integration separates the agent from the interface where the human reviews the result. Keep registers narrow tools through document.modelContext.registerTool . Those tools call the same store as the human UI, so cards, timelines, promises, suggestions, and drafts update in front of both participants. The active tool set changes with page state. With no selected card, the agent sees discovery tools. Selecting Priya adds her relevant actions. Promise and draft tools appear only when those objects exist. Human and agent together After a call, the human gives the agent one messy sentence. The agent logs the original words, extracts commitments, and moves the card. On Monday morning, who_needs_attention ranks relationships using cadence, overdue promises, and the Waiting on me column. The agent can draft a follow-up, but it cannot send one. mark_sent only records an action after the human confirms it already happened. How I built it The app uses React, TypeScript, Vite, and a small useSyncExternalStore state layer persisted to localStorage . It exposes 14 WebMCP tools with JSON Schema inputs. Read operations use readOnlyHint ; promise extraction marks raw notes with untrustedContentHint . A deterministic commitment parser and draft generator keep the live demo independent of API keys or inference availability. Archiving, dropping a promise, and recording a sent message have in-page confirmation gates. The repository includes eight unit and WebMCP contract tests plus browser acceptance coverage for desktop and mobile. OpenAI Sites hosts the public production build used for judging. Challenges The hardest choice was deciding what the agent must not do. Auto-sending would look powerful in a demo, but it would turn a relationship tool into an impersonation tool. Keep makes the handoff visible instead. The agent can organize, recall, and draft. The person decides what is true and what leaves the browser. The second challenge was keeping agent calls and human actions consistent. Both paths now mutate one store and produce the same visible UI changes. Dynamic registration also required careful cleanup with AbortController as selection and object state changed. What I learned WebMCP is most useful when the browser is not a thin shell over an API. It lets an agent participate in a stateful visual workflow without bypassing the product or duplicating authentication and client state on a server. The best tools are narrow verbs with visible effects. What is next Calendar context is the next useful input, followed by optional encrypted sync. Sending integrations are not on the roadmap. Keep should become better at helping a person remember, not better at pretending to be them.
