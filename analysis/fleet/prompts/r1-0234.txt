# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Different Mermaid diagram types generate completely different SVG structures, so we built adapters that connect the original Mermaid source to the correct rendered nodes, edges, groups, and source lines. Flowcharts, sequence diagrams, class diagrams, states, and architecture diagrams all generate different SVG structures. A human and an AI drawing on the same canvas — and the page can say no. Like Comment Story Updates Inspiration Most WebMCP demos hand an agent tools that read the page. I wanted to hand it tools that touch something a person is touching at the same time, and see what breaks. Everything broke immediately, and in an interesting way. In the first experiment a human drew seven strokes across the agent's work-in-progress. The agent never noticed. Not a bug — WebMCP is pull-only. A page cannot speak to its agent. It has no notify , no event, no way up the pipe. It can only answer when it is called. So the question became: with only that one channel, how much control can a page take back? What it does The page gives an agent nine drawing tools. Ask it for a lion; it draws one. Then pick up the mouse and draw two wheels underneath it while it works. 19:18:40 You Drew a line (9 points) ← you barge in mid-batch … You × 7 more 19:18:48 AI ⛔ Blocked canvas_batch — canvas changed by human 19:18:48 AI Inspected the updated canvas 19:19:02 AI Updated the plan — A cute smiling male lion car, using the completed red user-drawn wheels and connecting them to the mane-body with a simple axle. 19:19:12 AI Drew 39 shapes in one batch Its half-finished mane stops where it stopped, because the rest of that batch was dropped . It cannot draw again until it has looked, and then said what your wheels changed about the plan — and what it is giving up because of them. In this run it said, unprompted: "Both red wheels now have hubs, inner rims, and tread marks. I'll keep those wheel details untouched and add only the axle connection." Then it drew the axle. Not a lion that happens to still have wheels beside it — a lion joined to your wheels by a bar it decided to add. About sixty seconds, start to finish, with nothing scripted anywhere. Every one of those decisions came out of the agent reading tool output. The drawing is deliberately crude. An image model would draw a better lion. The log is the deliverable. How I built it First, a word on what this is not . WebMCP already has a human-in-the-loop hook — requestUserInteraction , which lets a tool pause and ask the person to confirm. That is agent-initiated : the agent decides to ask, the person waits in front of a dialog, and says yes or no to something already drafted. It is consent. This is the opposite shape. It is human-initiated : the person acts whenever they like, without asking, and the agent finds out afterwards that it has been overruled. It is pre-emption. Both belong in a page people and agents share, and the spec currently offers only the first. Someone who is making something does not want to approve the agent's plan — they want to reach in and change it, and have the agent catch up. Then four rules, each one arrived at by watching the previous version fail. 1 — Refuse, don't stop. A page cannot interrupt an agent. But an agent calls a tool every few seconds, so refusing the next call feels, to the person watching, like an instant stop. Every writing tool calls guard() first. 2 — If you cannot push, answer when you are pulled. Everything the page needs to say rides back on the tool the agent already calls. canvas_describe always appends what the human did since the last check. It is the only channel WebMCP offers, so the page uses it as one. 3 — Seeing is not accepting. The first version asked , in prose, for the agent to re-plan around the interruption. It obliged — narrated the change beautifully, then carried on drawing its original picture. So looking stopped being enough: canvas_describe now hands over to a second gate, and only canvas_replan(observed, new_plan, abandoning) opens it. All three fields are required. abandoning is the load-bearing one — a plan you have given nothing up for is the old plan wearing a new sentence. 4 — The human's marks are never painted over. Told to incorporate the wheels, the agent laid its mane straight over them. Nothing was deleted and the counts were honest, but half the wheels vanished from the picture, and the picture is what people read. Paint order is now fixed: whatever the agent draws goes underneath. Challenges I ran into Requests land; prohibitions do not. "Check the canvas before you draw" was ignored, however it was worded. Refusing the call was not. Every rule here is enforced by a code path, not by asking nicely. Batching fixed the speed and broke the premise. A realistic lion took six minutes — the agent called canvas_stroke with three points every four seconds. Adding canvas_batch cut it to one call . The next tester's report was one sentence: "It drew everything at once, so I had no time to barge in." Painting the batch slowly to look interruptible would have been a lie — the picture was already decided. So a batch is now accepted and laid down one shape at a time over a few seconds, and if the human draws during that, the rest is dropped and never happens. Batching gained an honest price: bigger is faster, and bigger loses more. The agent answers in the conversation's language. Asked in Japanese, it wrote its new plan in Japanese, onto an English canvas. Fixed by asking for English in three places — the tool description, each parameter's description, and the return value read immediately before the call. One place was not enough. Accomplishments I'm proud of The measured finding that surprised me most has nothing to do with drawing: A tool's description changes how an agent batches its work. With a neutral description, the agent drew a spiral as 2 points per call, ~40 calls, over a minute. After adding "Pass every point in one call. Each call costs a few seconds, so the number of calls is the wait the user sees" — 121 points in a single call, in 4 seconds. Same tool, same model, 15× fewer round trips, from one paragraph of prose. What I learned That a page under WebMCP is not a passive surface. It is the only party in the room that knows what the person just did, and the return value of a tool is a real communication channel — one the agent reads carefully and acts on. Almost all the design work turned out to be writing. What's next The mechanism is now a standalone file, barge-in.js , that knows nothing about drawing. It knows only who touched the page last, and it is four lines to add to a page: const bi = BargeIn.create({ describeTool: 'doc_read', replanTool: 'doc_replan' }); editor.addEventListener('input', () => { bi.note('you', 'edited a paragraph'); // look() reports this bi.humanActed(); // this refuses the agent }); function doc_insert(p) { bi.guard(); /* … */ } // guard every write function doc_read() { return Object.assign({ text: editor.value }, bi.look()); } The first application already runs, as a second page in the same repo: examples/doc.html , a document a person and an agent write at the same time — six tools, the same barge-in.js behind them, about 250 lines of page on top. Rule 4 changes shape there, and that is the interesting part. On the canvas it means the agent's paint goes underneath. In a document it means a paragraph you have typed in is yours : ⛔ That paragraph belongs to the user — they typed in it. It can never be rewritten or deleted. Write around it: use doc_insert to add a paragraph before or after, and leave theirs exactly as it is. The agent has to compose around you — and on the first live attempt it went further than the rule required: "You replaced paragraph 2 during the edit, so it now belongs to you and must remain unchanged. I'll adapt the surrounding paragraphs to present your sentence as the central instruction and keep the document concise." It did not just leave the sentence alone. It restructured the document around it : the one paragraph it was forbidden to touch became the thing the other two were rewritten to support.
