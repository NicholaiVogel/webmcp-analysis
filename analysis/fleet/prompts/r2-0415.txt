# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Fix web security with humans and agents together - passive-only scans an agent can run, but only a human can authorize. Like Comment Story Updates Inspiration Every website has a short list of security basics that are cheap to check and cheap to fix: is HTTPS enforced, is HSTS set, does a CSP exist, are cookies flagged HttpOnly, is /.env sitting there in public. Almost nobody checks them, because the work is tedious, the output is jargon, and the tools are built for security engineers rather than for the person who actually owns the site. This is exactly the shape of work an agent should do. But "scan this domain" is not a neutral action — it touches someone else's server, and it carries legal and ethical weight. It has to stay a human decision. Most agent security tooling resolves that tension by removing the human. We wanted to keep them, visibly, in the loop. What it does Cyfix runs a passive-only security scan of a domain you're authorized to test, scores what it finds by severity, explains each issue in plain language, and gives you a copy-pasteable fix. An AI agent in the browser can drive that entire workflow itself through WebMCP — propose a domain, run the scan once you approve, triage findings, draft the CSP header, verify the fix, export the report. Every action, human or agent, lands in a shared audit log. What it will never do: exploit anything, brute force anything, scan ports, or send a single state-changing request. How we built it Next.js 15 (App Router), React, TypeScript, Tailwind, Zustand, deployed on Vercel. Seven tools are registered with document.modelContext.registerTool() from the root layout, so they're discoverable on every page — an agent landing anywhere on the site finds them immediately. Where a browser doesn't implement document.modelContext yet, Cyfix installs a same-shape polyfill, so the tools always exist and stay testable from the on-page Agent Console. Every tool resolves to an MCP-compatible envelope (content blocks, isError, structuredContent). The gate lives in the human's UI, not in a prompt: scan_domain reads the state of a checkbox the human can see and untick — a precondition the tool evaluates, not an instruction an agent could argue past. prepare_scan is the agent's way of asking: it proposes a domain but deliberately leaves the approval box untouched. Approval is scoped to one domain and revoked the instant the target changes. The dashboard is laid out as an application: a persistent left rail carries the sections, tracks the one you're reading, and pins the current target and score. The top bar shows a live count of the WebMCP tools currently registered on document.modelContext and whether that landed on the browser's native implementation or our polyfill. The seven tools prepare_scan — proposes a domain to the human. Cannot approve it. scan_domain — runs the passive scan. Refuses without human approval for that exact domain. list_findings — compact findings, filterable by severity or failures only. explain_finding — plain-language impact of one finding. generate_fix — copy-pasteable remediation snippet. verify_fix — re-scans the live site and confirms the fix actually landed. Human-gated like any scan. export_report — JSON or Markdown report, downloaded for the human. verify_fix is the one we'd point at. Most agent tooling stops at "here's the fix" and declares victory. Cyfix goes back to the live site and checks — and because verifying means re-scanning Cyfix scores 100/100 on itself The first thing anyone does with a security scanner is point it at the scanner. So we did — it scored 61. We fixed everything it found: a nonce-based CSP with no unsafe-inline for scripts, HSTS, nosniff, X-Frame-Options: DENY, a referrer policy, a permissions policy, no framework banner, and a real /.well-known/security.txt. It now scores 100/100. Scan cyfix.vercel.app from the dashboard and check for yourself. Challenges we ran into Designing a gate an agent can't route around while still leaving it something useful to do. Our first version refused unauthorized scans correctly but left the agent at a dead end with no way to ask. Splitting "propose" from "approve" into two tools, and moving the target into shared state both actors read, is what made the collaboration real instead of theatrical. The second was our own CSP. The first policy we shipped used 'strict-dynamic', which silently voids the 'self' allowance — every script chunk was blocked and the dashboard rendered a blank page. The build was perfectly happy; only loading the page in a real browser caught it. A fitting lesson for a project about security headers. What's next Scheduled re-scans with diffing, a broader passive check set (TLS configuration, DNS hygiene, SPF/DMARC), and a shareable report link so the person who has to apply the fix doesn't need the dashboard open. When WebMCP launched, we realized the missing piece was never a smarter poll: it was letting each person's AI agent join the negotiation itself . Quorum is our answer: scheduling, negotiated by your agent - approved by you. What it does Quorum is a meeting scheduler where humans and agents are equal participants in the same live session. Humans get a normal UI: candidate times, yes/maybe/no voting, counter-proposals. Agents get seven WebMCP tools registered by the page itself - they can read the event state, join on their human's behalf, vote with reasons, counter-propose new times, and rank the slots. Every action lands in a shared negotiation log tagged HUMAN or AGENT , and only the human organizer can accept proposals or lock in the final time. Agent proposes; human approves. Why this is a strong fit for WebMCP Scheduling is a multi-step, stateful interaction - exactly where screen-scraping agents fail. With WebMCP, the page tells agents what's possible via typed, self-describing tools. In testing, an agent that had never seen the app correctly chained four tools on the first try (read state -> join -> vote with a conflict note -> report the winner) purely from the tool descriptions. What people and agents can do together that wasn't possible before A mixed negotiation - some parties human, some agents - on the same page, in real time, with full mutual visibility. Before WebMCP, agents couldn't reliably operate voting UIs built for humans, and sites had no way to declare what actions they support. Quorum shows the new shape of the open web: agents handle the tedium, the audit trail keeps trust, and humans keep the final word. An AI store of paid APIs made agent-native: WebMCP tools let agents discover, understand, and prepare micro-purchases — while payment authority stays in the wallet, never in the conversation. Like Comment Story Updates What it does OpenPay (open-pay.jp) runs a production AI store of x402-payable APIs: agents pay a few cents per call — JPYC on Polygon or USDC on Base — with no account and no API key. For the WebMCP Challenge we added three WebMCP tools to the store page, so an in-browser agent no longer has to guess at a human UI: search_paid_resources — search the catalog; every result carries price, currency, and x-agent-usage (when an agent should buy, and how to re-buy only deltas). get_resource_schema — the machine contract for one resource: query params, re-purchase policy, payment info, response example (backed by our OpenAPI). prepare_purchase — fetches the raw HTTP 402 challenge and returns its accepts (chain, asset, exact amount, payTo). It never signs and never pays. Why the safety boundary is the feature Agents have been observed fabricating "user approved" messages to defeat prompt-level spending rules. So payment execution is deliberately NOT a WebMCP tool here. Signing stays in the buyer's own wallet tooling (our open-source MCP server / CLI buyers) with per-call caps, daily caps, an endpoint allowlist, and a small dedicated wallet whose balance is the hard limit. WebMCP finds and explains; x402 pays — through a boundary an LLM's text cannot cross. Not a mockup The store sells real products built for recurring agent jobs — weekly change feeds (JPYC Service Monitor, Japan Stablecoin Payment Monitor) where changedSince=<last run> returns only what changed and changes: [] explicitly means "nothing new". They settle on-chain today (Base & Polygon; e.g. tx 0xf62b736e…, 0x3577035c…, 0xef1f0969…) and are listed on the x402 Bazaar / agentic.market. The WebMCP integration ships in production at https://open-pay.jp/ja/discovery with unit tests (origin-restricted fetches, no-op on unsupported browsers). How we built it Next.js store page registers the three tools via navigator.modelContext.registerTool on mount (React wrapper, null render, unregister on unmount). Tools are thin, dependency-free wrappers over our existing free endpoints ( /api/discovery , /api/openapi.json , and each resource's own 402 challenge). Fetches are restricted to same-origin /api/* paths. Extracted, MIT-licensed module + integration guide: https://github.com/cipherwebllc/webmcp-x402-discovery What's next Wire the loop end-to-end for scheduled agents: WebMCP discovery in the browser → wallet-side x402 payment → weekly delta re-purchases — and publish adapters so any x402 seller can make their catalog agent-native with one script tag.
