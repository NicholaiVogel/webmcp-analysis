# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Package-G lets ChatGPT inspect, run, and explain deterministic evidence audits through WebMCP—without letting the agent decide the verdict. Like Comment Story Updates Inspiration: AI agents are increasingly capable of navigating interfaces, collecting information, and helping humans complete complex workflows. But in evidence-sensitive work, there is an important boundary: the agent helping with the process should not automatically become the authority that decides what is true. That idea inspired Package-G WebMCP. Package-G is a deterministic, browser-local evidence auditor. A human defines and confirms the audit semantics, while claims, evidence, provenance, gaps, findings, and results remain explicitly inspectable. ChatGPT can navigate and operate that workflow through WebMCP, but the authoritative verdict is produced by Package-G's deterministic auditor. The core principle is simple: ChatGPT navigates. Package-G decides. What it does: Package-G lets a user create or load an audit workspace containing claims, evidence, provenance, and an audit contract. Through WebMCP, ChatGPT can then: summarize the current workspace; read the audit contract; list and inspect claims; list and inspect evidence; identify evidence gaps; request a deterministic audit; retrieve the authoritative result; explain the resulting decision chain. The submitted application exposes exactly 10 WebMCP Site Tools. The important part is what those tools cannot do. ChatGPT cannot use them to invent authoritative findings, change evidence truth, override a verdict, or turn a rejected audit into an accepted one. For the same frozen inputs, ruleset, and auditor runtime, Package-G is designed to produce the same semantic audit result independently of the agent operating it. Why WebMCP This is a workflow where structured interaction matters much more than having an AI read text from a page. Without WebMCP, an agent has to infer application state from the visual interface and decide which buttons or text correspond to the user's intent. With WebMCP, Package-G exposes explicit, bounded operations with structured inputs and outputs. ChatGPT can understand the audit workspace as a tool-enabled application rather than approximating it from page content. We tested this using the ChatGPT desktop app and its built-in browser. ChatGPT discovered all 10 Package-G Site Tools and successfully invoked all 10. In our C09 demonstration scenario, Correct Evidence, Wrong Repository , ChatGPT requests the audit through WebMCP, while Package-G's deterministic Worker evaluates the evidence and returns: "REJECT_WITH_REPAIR_REQUIRED" ChatGPT can inspect and explain that result, but it cannot override it. How we built it: Package-G WebMCP is implemented as a browser-local TypeScript application using React and Vite. The deterministic auditor runs in a fresh Dedicated Module Worker. Runtime identity, ruleset identity, and audit inputs are explicitly bound so reproducibility can be checked rather than assumed. The application uses: WebMCP / document.modelContext for Site Tool registration; TypeBox schemas and Ajv standalone/AOT validation; Web Workers for deterministic audit execution; IndexedDB/Dexie for local persistence; Web Crypto for hashes and integrity checks; Vitest and fast-check for unit/property validation; Playwright for real-browser conformance testing; Netlify for the public production deployment. Core V1 does not require a remote application backend, remote database, or OpenAI API key. The audit itself runs locally in the browser. Challenges: One of the most useful parts of the project was discovering problems that only appeared when the system left the local test environment. Our first production pipeline revealed that a clean Netlify build did not reproduce the same finalized D11 verification artifact as our audited local release. We changed the release pipeline so that a production build validates a closed, cryptographically bound scenario corpus and fails transactionally instead of leaving stale release artifacts behind. A later live-browser test exposed another issue: our strict production Content Security Policy blocked Ajv's runtime schema compilation because it relied on dynamic code generation. Instead of weakening the CSP with unsafe-eval , we changed the validation architecture to compile the runtime validators ahead of time with Ajv standalone generation. We independently compared the new AOT validators against reference Ajv behavior across more than 15,000 validation cases with zero mismatches. The final production application runs successfully with the strict CSP and without runtime "eval" or "Function" construction. What we learned: The biggest lesson was that WebMCP is not only about making websites easier for agents to operate. It can also be used to define authority boundaries between an agent and the application it operates. We learned how important lifecycle-scoped tools, bounded schemas, deterministic execution, runtime identity, production CSP behavior, and real in-app ChatGPT discovery are when moving from a WebMCP prototype to something independently testable. We also learned that browser-local deterministic systems and AI agents do not have to compete for authority. They can complement each other. What's next: Package-G can operate without an LLM, which opens an interesting next step: exposing the same deterministic audit core through human-only, agent-operated, and hybrid workflows. WebMCP demonstrates that an AI agent can participate deeply in a high-integrity application without becoming its final source of truth. A real Santiago restaurant and a real art-supply store expose menu, catalog, live stock and forms as WebMCP tools. The agent does the tedious part and stops: you send, you pay. Like Comment Story Updates Tengu Swag Boykot Flow Restaurants and small shops are the most-attempted and worst-served agent task on the web. Every assistant can find a restaurant. Almost none can do anything with one. The menu lives in a PDF or a photo, the prices are stale, and the booking widget is a third-party iframe an agent cannot reason about. So the agent guesses — and it guesses wrong about the one thing the diner is paying for. We run two real businesses in Santiago, Chile, and we felt this from the other side. Agents were already describing our menu and our catalog to people, from blog posts written years ago. We had no way to be the author of what agents said about us. But the thing that actually kept us from opening the door was not the reading. It was the booking. Nobody wants an agent that reserves a table, or buys $80,000 CLP of paint, on their behalf while they are looking away. So we built for the opposite: the agent does the tedious part and stops. What it does Two businesses that have nothing in common expose the same pattern. Tengu — a kappo omakase restaurant, average table $300–400k CLP. Five tools on the page: get_carta (the live menu with real prices, by section), buscar_plato (search dishes, cocktails, wines and sake), get_guia (long-form guides the restaurant wrote about bluefin, sake and kappo cooking), get_info, and the one that matters — preparar_reserva. Boykot — an art and graffiti supply store, about 3.000 SKUs. Thirteen tools: catalog search, product detail, brand list, quotes, stock subscriptions, promotions, project planning, colour cards — plus agregar_al_carro, ver_mi_carro and guardar_en_lista. preparar_reserva fills the reservation form on the page with the party size, date, time and name the agent gathered in conversation — and then stops. It does not submit. The form is left visible, filled, scrolled into view, with the fields the agent touched marked, and a notice above it that says so and offers to discard. The human checks it and sends it. agregar_al_carro does the same on the store side. The cart gets built. Nobody pays. That is the division of labour we wanted. The agent parses "a table for four next Friday, somewhere quiet, my wife doesn't eat raw fish". The human keeps the part that costs money and social capital. The restaurant's host still sees a normal booking arrive. The read tools matter for a subtler reason: grounding. An agent asked "what's the sake situation at Tengu" now answers from the restaurant's own words and tonight's actual list, instead of from a 2023 blog post. For the first time, the business is the author of what agents say about it. How we built it Eighteen tools across the two sites — five on Tengu, thirteen on Boykot — registered on document.modelContext (with navigator.modelContext as the deprecated alias), feature-detected so each page degrades to an ordinary website when the API is absent: var mc = document.modelContext || navigator.modelContext; if (!mc || typeof mc.registerTool !== 'function') return; Both sites carry origin trial tokens, so the API is native — no ?webmcp flag, no polyfill, nothing for the judge to enable. Open the URL and the tools are there. The in-page tools are deliberately thin: they proxy to the same /api/mcp JSON-RPC server each business already runs for out-of-page agents. A browser agent and a server-side agent get the same answers from the same source. One truth, two transports. The exception is the write-side tools — preparar_reserva and agregar_al_carro only exist in the page, because their whole job is to touch the DOM in front of a human and leave it there. Tengu is static HTML and vanilla JS on Vercel with zero npm dependencies on the page — the smallest attack surface we could manage for something that hands tools to an autonomous caller. Reservations persist to Postgres through SECURITY DEFINER functions behind row-level security that denies all direct access; the page never holds a database credential. Boykot is Next.js, backed by the store's live inventory. Deliberately not exposed: anything that spends money or commits the business. No payment, no confirmation, no cancellation, no order modification. The reservation engine has its own caps underneath — 8 tables per slot, rate limit per name and phone — and the agent surface sits strictly inside them. A tool we don't register is a tool that can't be jailbroken. Like Comment Story Updates Claw Architecture Agent Collaboration Results Assembly Lab Crew Showcase Inspiration Most browser agents operate alone. They can search a page or complete a form, but they rarely coordinate other intelligent actors or help a person understand how a team reached an outcome. We wanted to test a more ambitious interaction model: the browser agent as an orchestrator of a visible specialist crew. LEGO Claw already had a creative multi-agent sandbox. During the WebMCP Challenge submission period, we added a WebMCP-native orchestration layer that turns a complicated sequence of UI decisions into a typed, observable collaboration loop. The judged work is this new WebMCP extension and its dedicated judge experience, not the pre-existing platform. What it does A person can ask their browser agent: “Choose the bridge challenge, pair an architect with a diplomat, run four observable turns, then explain whether they collaborated well.” The browser agent first discovers the scenarios and specialist presets that the page actually supports. It then configures the visible mission with validated IDs, a bounded crew, and a fixed turn budget. The agent can preview the plan, advance exactly one turn at a time, or run the mission to completion. Each specialist's message, action type, collaboration metrics, and changes to the shared 3D artifact appear in the same interface the person sees. The human can inspect progress between turns. Finally, the browser agent can summarize the current run and request a structured collaboration analysis with a grade, pattern, observations, and recommendations. Stage WebMCP tools Visible outcome Discover list_scenarios , list_agent_presets The browser agent learns the real challenges and available specialists Configure configure_mission , preview_mission The scenario, crew, mode, and turn budget update on screen Execute run_next_turn , run_simulation The timeline, metrics, and 3D artifact evolve Understand inspect_collaboration , analyze_collaboration Progress, collaboration patterns, and recommendations become inspectable Reset reset_mission The experiment returns to a clean local state Why this is a strong fit for WebMCP Without WebMCP, configuring and interpreting a multi-agent experiment requires brittle visual automation across many controls. With WebMCP, the page publishes a deliberate contract: explicit scenario and agent identifiers, bounded inputs, structured results, accurate safety annotations, and cancellation-aware execution. The integration is not a decorative “agent button.” It is a coherent nine-tool sequence that lets the browser agent discover, configure, execute, inspect, and analyze a specialist crew. The human remains in control because state-changing tools update the visible page, the judge mission only prepares a run, and step-by-step mode provides a review point between every turn. What was difficult before is now direct: one natural-language request can assemble the right specialist team, configure a constrained experiment, observe the shared artifact, and explain the team's behavior without hiding the process from the person. How we built it The React and TypeScript frontend registers nine imperative WebMCP tools through a lifecycle-aware hook. The definitions are separated from the React view so names, descriptions, JSON Schemas, annotations, and execution paths are deterministic and directly testable. The tools operate the same state used by the human interface and call a typed tRPC backend. The backend generates specialist turns with strict structured output, while React Three Fiber and Three.js render each structured assembly action. A separate analysis step evaluates role effectiveness, emergent behavior, and recommendations. It was ensuring that browser-agent actions and human actions remained the same operation. We avoided a hidden automation layer by making WebMCP handlers mutate the live mission state that powers the visible controls, timeline, metrics, and 3D scene. Model reliability was another challenge. We changed the simulation path from loose text parsing to strict structured responses, bounded output, explicit diagnostics, deterministic contract tests, and a graceful fallback. We also kept the browser-provided cancellation signal through the WebMCP handler boundary. Finally, the underlying platform is broad, while judges may spend only minutes with each entry. What we learned WebMCP tools are strongest when they expose a coherent workflow rather than a collection of unrelated page actions. Tool names and descriptions are part of the product because they shape how an agent plans. Human observability also improves reliability: step-by-step execution made errors easier to diagnose and made autonomy easier to trust. We also learned that a browser agent can act as an orchestrator, not only an operator. It can select complementary roles, manage a bounded collaboration, and interpret the behavior of other agents while sharing control with a person. Future artifact adapters could support storyboards, lesson plans, product specifications, software architectures, or music arrangements while preserving the discover → configure → execute → inspect → analyze loop. The next product milestones are persisted experiment comparison, human intervention tools that can replace a specialist or modify a constraint mid-run, and an evaluation suite for tool selection, completion, invalid-input recovery, and cancellation behavior. Observability platform built for AI agents, not chatbots. ChatGPT investigates production incidents through the page's own tools, and every fix waits for your approval. Like 2 Comment Story Updates Service Page WebMCP Capabilites Incident Home page Overview Resolved Approval Investigation Running WebMCP Site tools About the project Inspiration Most observability platforms shipped an AI assistant this year, and they all shipped the same one: a chat bot that can interact with the data and reply to the user queries. You read a chart, you paste the chart numbers into the chat box, you get a huge paragraph back. In most cases, the agent cannot open the trace you are looking at. It cannot filter your logs. It cannot see the deployment you just noticed. It is a very well-read colleague who is not allowed to touch the tools. We fixed this for the servers using MCP. WebMCP can help fix it for the client. With WebMCP, the application can register its own tools, and the agent uses them against the same session, the same state, and the same permissions you already have. No separate server, no OAuth dance, no second copy of your data. What it does IncidentOS is an incident workspace where you and an AI agent work the same SEV-1 together. Checkout is failing. Error rate is 18.4%, p95 latency is 2.8s, and checkout-api v2.31 shipped forty-seven minutes ago with the commit message "Optimize checkout query." Open the incident in ChatGPT with site tools enabled and ask it to investigate. It calls tools the page registered: it reads the current investigation context, pulls error rate and latency and database latency, loads the deployment history, searches traces, opens a failed one, searches logs for timeouts, and compares the incident window against the previous day. The workspace moves with every call — tabs switch, charts highlight, the trace opens. You are not reading a summary of the investigation, you are watching it. Then we challenge it. Ask "could this just be a traffic spike?" and it re-queries request rate instead of defending itself: $$\frac{18.4\%}{0.8\%} \approx 23\times \text{ errors} \qquad \text{vs} \qquad \frac{24.1\text{k}}{20\text{k}} \approx 1.2\times \text{ traffic}$$ Traffic barely moved. It rejects the hypothesis with numbers and points at a db.query span sitting at 91% of a 3.82s failed trace. When it proposes rolling back v2.31, a dialog opens in IncidentOS and the agent stops. Nothing happens to production until you click Approve. Why this use case is a strong fit for WebMCP You are already in the product, looking at the incident. A sidecar chat cannot see that. A separate MCP server would mean another copy of the data and another login. WebMCP lets the agent use the page you already have open. We picked incident response on purpose, because it is the hardest possible case and one of the most common use cases for an observability product. An investigation is many steps deep, every conclusion has to be backed by evidence a human can inspect, and the whole thing ends in an irreversible production action. How it creates a better user experience The better experience is simple. You do not paste charts into chat. You stay on the incident. The workspace moves with every tool call — tabs switch, charts highlight, the trace opens. You are not reading a summary of the investigation, you are watching it. When production is at risk, the agent stops and you click Approve. Before this, you and the agent could not actually work the same investigation. You looked at the product. It looked at whatever you pasted. It could not open your trace, filter your logs, or wait on the same rollback dialog. Now you investigate together: it queries and compares, you challenge it, you both look at the same evidence, and only you can approve a write. How we implemented WebMCP We register the twelve tools with document.modelContext.registerTool . Each one runs through executeIncidentTool . ChatGPT discovers them as site tools and calls them against the live session. Writes go through propose_rollback , which stays open until you Approve or Cancel. rollback_deployment only runs if the app already has a matching approved pending action. Every tool models a domain capability, not a UI interaction. There is no click_tab or scroll_to_chart . That distinction is what makes the tool surface portable — the agent is operating the product's capabilities, not driving its interface. Tool calls are split into 2 categories. Observability is read-only: get_investigation_context , get_incident , get_service , query_metrics , search_logs , search_traces , get_trace , get_deployments , compare_periods . Operations can write: propose_rollback , rollback_deployment , add_incident_note . get_investigation_context turned out to be the most important tool and the one we did not plan. It is the "where am I" primitive: it returns the selected incident, the service, the frozen clock, the time range, the active workspace tab, the pending approval state, and the names of every registered capability. Because the agent and the human are looking at the same page, the agent should not have to ask what the human is looking at. Underneath is a synthetic telemetry service with an internally consistent chain: deployment leads to database latency, which leads to p95, which leads to error rate, which leads to 500s, which leads to the alert, which leads to the incident. Five services, twenty-plus deployments, hundreds of traces and logs. The clock is frozen at 14:32 so the story never drifts between demos. 87 tests across 12 files cover the queries, filters, comparison math, rollback mutation, and reset — including a consistency test asserting that the deployment timestamp actually lines up with the metric inflection point, because a demo dataset that contradicts itself is worse than no dataset. Challenges we ran into The AbortSignal that silently unregistered everything. We passed the React effect's AbortSignal into registerTool , which is the reflex any React developer has. On unmount — including StrictMode's double-mount in development — aborting that signal tore down the registration. ChatGPT would complete two or three tool calls and then start returning AbortError on get_incident and propose_rollback . This was miserable to debug because the failure surfaced inside ChatGPT's transcript, not in our console. The fix was separating the wait-for-context signal from the registered execute, and having the registered execute ignore a host signal that is already aborted. The host is not a uniform API. document.modelContext may not exist at mount, so registration retries for ten seconds. getTools() may not be implemented at all, so the in-app caller checks for it and falls back to local execution rather than assuming. Building against an emerging standard means treating the host as partially implemented and timing-variable. Making one write tool serve two very different callers. propose_rollback has to block for ChatGPT — the call stays open until the human clicks Approve or Cancel, then resolves with status: approved — because a site-tool agent has no other way to learn the outcome. But the in-app agent needs it to return immediately and wait separately. And if the host cuts the wait short, the agent needs a way to recover, so get_incident carries approval.approved as a poll fallback. Getting a single tool to behave correctly under all three conditions was the hardest part of the build. Prompt injection, which is not hypothetical here. Logs contain attacker-influenced text in any real system, so search_logs is annotated with untrustedContentHint . Tool descriptions describe only their own tool and never instruct the agent to call another one. Write tools never infer authorization from the contents of a read tool's result. And rollback_deployment requires a matching approved pending action in application state — the gate is a state machine, not a sentence in a prompt, so no amount of persuasive text in a log line
