## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.

  here; the agent is central to the product, not a bolt-on.

- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

When WebMCP launched, we realized the missing piece was never a smarter poll: it was letting each person's AI agent join the negotiation itself . Agents get seven WebMCP tools registered by the page itself - they can read the event state, join on their human's behalf, vote with reasons, counter-propose new times, and rank the slots. What people and agents can do together that wasn't possible before A mixed negotiation - some parties human, some agents - on the same page, in real time, with full mutual visibility. A shared visual workspace where you shape the brief and Codex turns it into polished images—then returns them to your canvas. Like Comment Story Updates Inspiration Most AI image workflows collapse an entire creative project into one long prompt buried in chat. That makes the work difficult to inspect, refine, reuse, or hand off. References, constraints, visual direction, and prior results all become conversational context instead of durable project state. I built Prompt Canvas to explore a different model: a shared visual workspace where the human directs the creative work and Codex executes it. The brief, references, creative direction, results, and variations remain visible on a spatial canvas. The human can edit those elements directly, while Codex can read and update the same live project through WebMCP. What it does Prompt Canvas begins with a curated library of image-making recipes. These range from simple tasks—creating an image from words, changing a background, or removing an object—to more structured systems for posters, brand exploration, sequential storytelling, technical visuals, and reference-driven transformations. Starting a recipe creates a focused project on a tldraw canvas. Depending on the task, the project may include: a Brief describing the intended outcome; References with explicit roles and preservation requirements; a Direction surface for composition, style, format, and mood; a dominant Result area; Variations for continued exploration. Users can shape the project manually or ask Codex to help. Through Prompt Canvas’s WebMCP Website Tools, Codex can search the official recipe library, retrieve an exact approved recipe version, create or update a project, inspect its current revision, prepare generation context, and return generated assets to the correct canvas output. Image generation remains native to Codex. Prompt Canvas supplies the structured creative context and receives the result; it does not introduce a separate page-owned generation service. The result is a single inspectable workspace where the human and agent operate on the same project rather than maintaining separate versions in chat and in the application. How I built it Prompt Canvas is a React and TypeScript application built on the tldraw SDK. Recipes are schema-backed YAML documents that define prompts, controls, references, output slots, layout, preservation rules, and supported operations. The application compiles those recipes into custom tldraw panel shapes while retaining the full underlying recipe snapshot for the agent. The official recipe library is curated and versioned. On the published ChatGPT Site, approved recipes are served from Cloudflare D1. User-created recipes remain local to the user’s browser and are never silently added to the official catalog. Prompt Canvas exposes 11 semantic Website Tools through WebMCP. These tools cover recipe discovery, exact recipe retrieval, project creation and updates, project inspection, generation-context preparation, and generated-asset return. The project also includes: immutable official recipe versions and content hashes; revision numbers and stale-write rejection; local project persistence; validated reference and generated-asset handling; explicit output-slot targeting; parent-child output lineage; undo and reload durability; deterministic catalog and browser tests. Challenges The largest design challenge was making the canvas feel like a creative workbench rather than a visual programming graph. Early versions displayed nearly every prompt variable as a separate connected card. Although technically accurate, the interface visually resembled an automation workflow and gave configuration more importance than the image itself. I simplified the interaction model around a smaller set of creative surfaces: Brief, References, Direction, Result, and Variations. Permanent dependency arrows were removed from the primary workflows, controls were grouped into meaningful decisions, and the Result became the visual center of the project. A second challenge was explaining the collaboration boundary clearly. Clicking a button on the Site cannot itself perform native Codex image generation. The application therefore needed to communicate that the user shapes the project in Prompt Canvas, then asks Codex to act on its current state through WebMCP. The final interface makes that division of labor visible from the first screen, previews the information Codex will use, and explains where the resulting image will return. The third challenge was preserving trust across two interfaces. Codex must always act on the newest project revision, respect the selected recipe version, return assets to the intended output, and avoid overwriting newer human edits. Revision checks, exact recipe identity, validation, and output lineage were essential to making the workflow reliable. What I learned WebMCP is most powerful when it exposes an application’s real semantic actions rather than asking an agent to imitate mouse and keyboard behavior. The agent does not need another copy of the user interface. It needs structured access to concepts such as “search recipes,” “inspect the active project,” “use the latest creative direction,” and “return this image to the primary result.” I also learned that agent collaboration must be explained before the first handoff. Users should understand what they control, what Codex will use, what the agent is about to do, and what remains editable afterward. What’s next The next frontier is deeper support for multi-reference creative work: assigning separate images authority over identity, composition, palette, product geometry, or visual style. I also plan to expand the curated recipe library, introduce reusable style and constraint kits, and develop richer result branching and comparison while keeping the workspace simple, inspectable, and local-first. Like 1 Comment Story Updates Agent Stage: two showcase scripts rendered by svgent, a terminal and an app Inspiration svgent is a client-only studio for fictional coding-agent sessions. A script describes a chat window or a terminal, with typing, thinking, tool runs, approvals and choices, and the studio renders it to SVG, PNG, GIF and MP4. People use it for READMEs, docs, talks and posts, where a recording of a real session would leak secrets and could not be re-shot or translated. Before this, the studio's AI assist was copy and paste: copy a prompt into a chat, paste the JSON back. WebMCP replaces that with tool calls on the page. The page can also answer with facts a language model cannot see: how long a page runs, when each message lands, what the frame looks like at eleven seconds. The agent works on the stage itself, not on a guess about it. What it does Agent Stage is the studio with WebMCP site tools. The agent in ChatGPT's built-in browser writes the script, sets the surface, look, camera and pages, measures the result, looks at a frame, proposes rewrites, and asks to export. The person keeps the decisions: rewrites and exports wait on a card, every string the script puts on the stage is listed, and each change can be undone. load_script validates a script and previews it at once. direct_camera turns on a deterministic follow camera. inspect_timeline returns per-message timing and a review. snapshot_frame returns a PNG of any moment. fit_duration lands a page on an exact length and reports what it changed. propose_patch puts rewrites on a card. approve_proposal exists only while a proposal is pending and waits for the person's click. export asks first. The rail shows every call. The "Every word on the stage" list holds every string the script puts on the stage, including what a collapse or a page turn hides. The tool descriptions tell the agent to treat what it knows from the conversation as private and to use stand-ins for real names, unless the person relaxes that on the page or in the chat. Credentials never pass. A loaded script keeps only the fields that render. Looks, fonts, images and camera go through their own tools. Live: https://agent.svgent.zakideee.dev/ Code: https://github.com/zakideee/svgent (the page is apps/webmcp/ ) How we built it 13 tools on document.modelContext , with navigator.modelContext as the fallback, registered with an AbortSignal for teardown. approve_proposal is registered only while a proposal is pending. Results are plain objects plus an MCP-style content array (text, and an image part for frames). The studio package gained a small imperative handle: read, replace and patch the project, seek, play, export, render a frame, spotlight a message. An agent's edit goes through the same state the person's controls use, so undo, autosave, validation and preview all see it. Text layout and rasterization run in WASM (boundsvg) in the browser. The animated SVG is CSS keyframes with no JavaScript. There is no server; nothing leaves the tab except the files the person downloads. The submission is apps/webmcp/ : the WebMCP tools, the agent rail, the privacy default, the showcase scripts and the share card, plus the studio handle ( StudioHandle , chrome , renderFrame , spotlight ) and one preview aspect-ratio fix. The studio, scene and render packages predate the challenge. Challenges we ran into ChatGPT's browser exposes document.modelContext , Chromium exposes navigator.modelContext , and the API can appear after the page has loaded. Registration prefers the document, polls for a late API, and reports the outcome in the rail. A dynamic tool ( approve_proposal ) that unregisters itself while a call is in flight fails that call. It now stays registered for a short grace period after the proposal resolves. A script an agent writes from a conversation can carry real names, paths, hosts and keys from that conversation. The privacy default, the script allowlist and the "every word" list exist for that. Accomplishments that we're proud of The whole loop runs in the ChatGPT desktop app (built-in browser, GPT-5.6 Sol) and in Chromium with WebMCP enabled, and the demo video is a recording of it. The agent edits through the same state as the person's controls, so undo, autosave, validation and preview treat both alike. Four of the showcase scripts are problems agent-app users have: a clip for the team channel without the secrets; a reproduction of a decline that was missed, when recording is not allowed; three slides that walk a colleague through choices and approvals; a README hero for your own MCP server. What we learned A page can hand an agent facts it cannot infer (timing, frames, what would render), and that is worth more than letting the agent guess well. Approval and visibility have to be part of the tools, not a note in a prompt.
