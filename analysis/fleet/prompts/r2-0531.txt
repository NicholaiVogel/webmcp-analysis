Corotum helps you keep AI agent skills consistent across every machine and AI agent. Instead of copying and fixing drift, you manage one desired state and sync it safely through Git or Corotum Cloud. Like Comment Story Updates Inspiration I use multiple AI agents on different machines, and I kept running into the same problem: their skills were never quite the same. A skill would be installed on my Mac but missing on a VPS. Another would be outdated somewhere else. Sometimes I had changed a skill locally and forgot about it. The usual solution was copying folders around and trying to remember which version was the right one. That became the starting point for Corotum. I wanted one place to define which skills I use, which versions should be installed, and which agents should get them. I also wanted to see how far I could take the idea during a 7-day build challenge for the WebMCP Challenge. What it does Corotum manages and synchronizes AI agent skills across machines and agents. It keeps a desired state and compares it with what is actually installed on a machine. From that comparison it works out what needs to change, applies it, and verifies the result. There are two sync modes. Git Sync uses your own Git repository and does not require a Corotum account. Corotum Cloud hosts the desired state and adds a dashboard, devices, revisions, sync status, and WebMCP. The CLI can add, remove, adopt, update, restore, and target skills to specific agents. Versions are locked to exact Git revisions, so running sync does not unexpectedly update a skill to whatever happens to be latest. Corotum also treats local changes carefully. If a managed skill was modified by hand, it is marked as drifted instead of being overwritten. Skills that Corotum does not manage are not deleted during normal synchronization. How I built it Corotum is a TypeScript monorepo using Bun workspaces. The CLI runs on Bun and is compiled into standalone binaries. The web app uses Next.js with vinext on Cloudflare Workers, with D1 for the hosted state. The main sync flow is: Desired State + Actual State → Diff → Reconcile Plan → Apply → Verify Git Sync and Corotum Cloud use the same synchronization model. The dashboard, API, and WebMCP also use the same application services instead of having separate implementations of the same operations. For private repositories, Corotum uses Git credentials already configured on the user's machine. Those credentials are never sent to or stored by Corotum Cloud. Challenges Most of the work was not actually copying files. It was deciding exactly what every operation should mean when several machines can be in different states. For example, remove and unmanage both remove a skill from the desired state, but they cannot behave the same way. remove should eventually delete the managed copy from every device. unmanage should stop managing it but leave the local files in place. Drift was another case that needed explicit rules. If somebody edits a managed skill locally, a normal sync should not silently destroy those changes. Offline devices made this harder. A machine might reconnect several revisions later, so looking only at the newest snapshot is not always enough to understand what should happen locally. Private repositories had a similar constraint. The Cloud can coordinate the desired state, but it cannot assume that it has access to the repository. Resolution sometimes has to happen on a device that already has Git access. What I learned The project started as a fairly simple "sync skills between computers" idea. Most of the complexity turned out to be around ownership and state. Once I separated the shared desired state from the actual state of each device, a lot of the behavior became easier to define. Locking skills to exact Git revisions was another important decision. It keeps sync and update as two separate operations: sync reproduces the selected state, while update intentionally changes it. What's next The first version is deliberately limited to AI agent skills. The same model could later be used for other parts of an agent setup, such as MCP servers, prompts, rules, profiles, agent configuration, and team policies. The web is becoming AI native. Security should be too. PatrAgent gives agents the possibility to scan text, mcp server, files and urls for prompt injections before content lands into context. Like 1 Comment Story Updates Patronus WebMCP Security Scanner About the project Inspiration Autonomous agents increasingly work with content they did not create: repository files, uploaded documents, MCP tool descriptions, prompts, and resources. That content can contain prompt injections designed to redirect an agent before it has a chance to evaluate whether the source is trustworthy. We wanted to move that security decision in front of the context boundary. Instead of asking an agent to read potentially hostile content and then judge it, Patronus lets the agent scan the content first and receive only a compact security result. What it does Patronus WebMCP Security Scanner gives people and agents access to the same prompt-injection security layer. People can use the visual interface to: scan text for prompt injections; inspect an MCP server's tool, prompt, and resource metadata without executing any of its capabilities; scan the normalized static surface of a public HTTPS page; and upload source code or text documents for analysis. Agents discover four typed WebMCP tools directly from the page: scan_text scan_mcp_server scan_url scan_file The repository also contains an installable Codex plugin that can scan an entire repository before the agent reads it. A deterministic local helper validates and uploads supported files directly to the scanner. The agent receives only filenames, opaque file IDs, and compact verdicts, so the candidate file contents never enter the model context before the security decision. Capabilities Interactive security scanner The hosted application exposes four read-only WebMCP tools backed by Patronus Ark: scan_text checks a bounded text candidate for prompt injection. scan_file checks an uploaded source-code or text file through an opaque file ID. scan_mcp_server inspects the advertised tools, prompts, and resources of a public MCP server without executing any of them. scan_url checks the complete normalized static body of one public HTTPS page. The same capabilities are available through the visual interface. When an agent invokes a tool, its result is reflected in the page so the person and the agent share the same observable security state. Repository scan before context The installable Codex plugin lets a person ask an agent to scan a repository before reading its files. The workflow deliberately separates deterministic file handling from model-visible context: A local helper selects supported files, validates their type and size, and uploads their bytes directly to the hosted scanner. It returns a content-free upload manifest. Prepared entries contain only a filename, byte size, and opaque file_id ; skipped entries contain only a filename and reason. The agent calls the scan_file WebMCP tool once for every prepared ID and receives compact verdicts and bounded evidence. The plugin reports every detected incident and the final scan coverage without modifying, deleting, quarantining, or repairing repository files. This means potentially hostile source text does not need to enter the model context just to reach the classifier. Uploaded objects are short-lived and are deleted after scanning. The result is a bounded prompt-injection check, not a claim that the repository is free of every possible security issue. WebMCP iframe security manifest The Patronus website embeds the security manifest as a small cross-origin iframe in its shared footer. It provides the origin-bound WebMCP tool patronus_security_manifest_v1 . The website-scan flow works as follows: A compatible agent is asked whether one exact public HTTPS URL is safe to use. The website-scan skill addresses only the trusted Patronus iframe and supplies that exact URL through fixed bridge controls. Inside its own origin, the iframe discovers and invokes its own WebMCP tool. It rejects a missing, duplicated, or same-named tool from another origin. The Patronus Control Plane fetches the anonymous static page surface, converts the complete normalized document body into one Ark candidate, and keeps other advertised security surfaces as separate candidates. The iframe returns only a bounded verdict, tool identity, URL identity, digests, cache metadata, and coverage. The agent treats missing, mismatched, failed, or truncated results as unverified rather than benign. Iframe embedding and WebMCP exposure are restricted to the configured Patronus website origins. The manifest does not execute capabilities from the scanned page and does not claim to assess authenticated state, later DOM mutations, privacy, malware, reputation, or every security risk. The current browser harness may still add navigation or page observations to model context automatically. The demo therefore shows the intended pre-context security sequence and a practical origin-bound WebMCP bridge, while a future native tools-only harness is needed to guarantee that no parent-page content is exposed before the verdict. Why WebMCP This use case needs more than UI automation. Scraping the DOM or clicking through a form would force an agent to inspect the very content we are trying to keep outside its context. WebMCP provides a typed capability boundary instead. The page explicitly describes what an agent may do, validates structured inputs, and returns bounded results. The same calls also update the visible interface, so a person can observe the result and stay in the loop while the agent performs the scan. That creates a workflow that was previously difficult: a person can point an autonomous agent at an unknown repository, and the agent can evaluate it for prompt injections before reading or reasoning over its contents. How we built it The application is written in TypeScript with React and Vinext and runs on Cloudflare Workers. It registers its agent-facing capabilities with document.modelContext.registerTool() and defines strict JSON schemas for every input. Prompt-injection analysis is powered by Patronus Ark . Text is sent directly for analysis. File scanning uses short-lived Cloudflare R2 sessions: the browser or local helper uploads a file, WebMCP receives only an opaque file_id , and the server deletes the object after scanning. MCP inspection is intentionally read-only. The server calls only initialize , tools/list , prompts/list , and resources/list ; it never executes remote tools, prompts, or resources. The endpoint also rejects credentials, localhost, literal private addresses, unsafe redirects, and oversized responses. Patronus Ark: CPU-first security Patronus Ark is Casdo Labs' CPU-first security stack. It is built around our own multilingual security models and shared-encoder architectures, allowing multiple security tasks to reuse a common representation instead of requiring a separate heavyweight model for every detector. We believe an agent's security layer should not have to compete with the agent itself for scarce GPU capacity. When GPUs are occupied by large language models, security still needs to remain available, responsive, and always on. A CPU-first architecture makes it possible to run protection close to the workload and helps keep essential security affordable—or even free—for a much broader group of users. The Ark API behind this demo currently runs on only four vCPUs and still provides latency that is practical for an interactive scanning workflow. The API service and its integration were built as part of this hackathon, while the underlying Ark architecture and model research build on several months of prior research and development. Casdo Labs' long-term vision is a safer future for autonomous agents and the people who rely on them. Agents are rapidly becoming faster and more capable; we believe their security infrastructure must become widely accessible just as quickly. Challenges we face

A reusable WebMCP privacy boundary that lets agents act on sensitive workflows without receiving the raw private values behind the decision. Like Comment Story Updates Sealed’s WebMCP privacy boundary: private values stay page-local while agents receive only allowlisted decisions or opaque references. Inspiration AI agents are becoming capable of acting directly on websites, but many useful workflows involve information that should not automatically become part of the agent's context. A rental application is a simple example: an agent may need to know whether an applicant satisfies an income requirement, but it does not need the applicant's actual income. The same applies to identity data, age checks, financial values, health information, and many other private facts. Sealed explores a simple idea: The agent gets the decision — not the secret. What it does Sealed is a reusable WebMCP privacy boundary for agentic web applications. The page exposes a small, state-aware set of WebMCP tools. Public information can move normally, while sensitive facts are evaluated locally inside the page and only allowlisted results are returned to the agent. The primary rental demo shows the full pattern: Public applicant information can be updated by the agent. A private income_3x_rent predicate is evaluated locally. The agent receives only satisfied or not satisfied ; the income itself is returned as value: "withheld" . A passport verification requires explicit human approval. Approval creates a random, session-bound opaque reference that does not encode the passport number. Every private crossing is recorded in a visible Boundary Ledger. Human review returns submitted: false ; Sealed has no final-submission tool. After review, the WebMCP capability surface contracts from five tools to only two safe read/flag operations. A second Membership scenario reuses the same primitives to evaluate age_18_plus without exposing the user's date of birth. Why WebMCP WebMCP is load-bearing in Sealed. Without structured site tools, an agent would have to infer meaning from DOM content, accessibility trees, or screenshots. That is especially problematic around sensitive data because the agent may end up observing more information than the task actually requires. With WebMCP, the page defines the capability boundary explicitly. Sealed registers tools through document.modelContext.registerTool(...) , including: get_application_context set_public_fields flag_uncertain request_private_binding evaluate_private_requirement request_review The available tool surface changes with workflow state. The agent can ask for a useful decision, but no tool exists that returns the underlying private value. How I built it Sealed is built with Next.js, React, TypeScript, and WebMCP and is deployed on Vercel. The privacy boundary has several layers: Fixed private predicates The agent selects from predefined checks such as income_3x_rent or age_18_plus ; it cannot construct arbitrary queries over private values. Local execution Private values are generated and retained page-locally. Predicate evaluation happens inside the application. Guarded egress Private operations pass through a single allowlisted response path that releases only approved fields such as status, requirement, and value: "withheld" . Human-approved opaque bindings Consequential credential binding requires explicit user approval and returns only a random session-bound reference. Boundary Ledger Each private operation records the exact sanitized payload released across the boundary. State-dependent capabilities Once human review is requested, Sealed removes write/private tools and leaves only two safe operations. Challenges I ran into The hardest part was separating three different things that initially looked like the same problem: page registration, browser discovery, and agent invocation. A page can successfully register WebMCP tools while the current ChatGPT browser session has not yet attached those tools to the conversation. I reproduced cases where the page showed five registered tools while the agent still reported that site tools were unavailable. Testing against the official Chrome Labs WebMCP demo helped isolate the difference between application behavior and client-session discovery. That led to an important UI correction: Sealed now says “Site tools registered” , rather than claiming that an agent is connected simply because local registration succeeded. I also had to guard against stale sessions, repeat probing of private predicates, response/ledger drift, and accidental leakage through seemingly harmless response fields. Accomplishments I am proud of The final implementation demonstrates a complete human-agent privacy workflow rather than a single tool call. The strongest result is that the same private operation produces both: the agent-visible sanitized response, and the visible Boundary Ledger entry from the same guarded source of truth. The rental flow demonstrates public writes, private decision-only evaluation, explicit human approval, opaque binding, human review without submission, and dynamic capability reduction. The membership scenario shows that the pattern is reusable rather than hard-coded to one application. What I learned WebMCP is not only useful for making agents more capable. It can also make the boundary between a web application and an agent more explicit. The most useful question became: What is the minimum information the agent needs to complete this task? For many workflows, the answer is not the private value itself. It is a decision, status, capability, or reference derived from that value. I also learned that real browser behavior matters as much as implementing the API correctly. Registration, discovery, invocation, approvals, and session lifecycle all have to be tested end to end. What's next Sealed is intentionally narrow for this challenge. Future work could explore additional private decision primitives, external verifier-backed references, and reusable SDK-level abstractions for application developers. For now, the project focuses on one core principle: Useful decisions can cross the boundary. Raw private values do not have to. Like 1 Comment Story Updates Landing Page Guide Mode Variant Window Advanced Mode Inspiration I study anthropology, which in practice means I spend a lot of time around genomic data that isn't mine. Population panels, ancient DNA, samples from communities who agreed to one specific study and nothing beyond it. Consent in this field is narrow and it's supposed to stay narrow. That makes most genomics tooling unusable for me. Every variant browser I found opens the same way, upload your raw file to our server. I can not click that with a participant's genotypes, and I wouldn't click it with my own either. WebMCP removes the upload from the equation. The tools are declared by the page and run in the tab where the file already is, so the model can operate on data that never moves. That was enough to make the tool worth building. What it does LocusLocal is a variant-triage workbench. Drop in a VCF or a consumer raw export, it is parsed in a Web Worker, annotated against a bundled 98,262-variant ClinVar subset, and analysed entirely inside the tab. The demo genome is 250,000 markers from 1000 Genomes sample NA12878. Two audiences, one analysis engine. Guided mode answers the questions a person reading their own export actually has: how much of the file was read, how much of it ClinVar knows about, what they carry, how strong the evidence is, and what the analysis cannot tell them. Advanced mode gives the full table, filter stack, sorting and manual selection. One click either way, and an agent can make that click too. How I built it Vanilla TypeScript and Vite 8, no UI framework, deployed on a Cloudflare Worker that runs before static assets so the security headers can't be skipped. Tools are grouped into read_* , set_* , act_* , explain_* , and history . Chrome's secure-tools guidance applied throughout. readOnlyHint on all 13 read_* / explain_* tools and on none of the mutating ones; untrustedContentHint on analysis tools, whose output contains text from a user-supplied file; descriptions that state the visible UI effect. What's next for LocusLocal Pharmacogenomics (CPIC/PharmGKB). Drug-response markers are the genomics question with the most immediately actionable answer, and the annotation set is small enough to bundle under the same no-egress constraint. Polygenic scores, honestly presented. The interesting design problem is communicating a population-relative distribution to someone who wants a yes/no with the ancestry-portability caveat in the interface rather than a footnote. Trio and family-set support. Multi-sample VCFs, inheritance patterns, and a compare_samples tool, the point at which the shared-selection model gets genuinely harder and more interesting. A second annotation source (gnomAD frequencies) so "rare" stops meaning "not in ClinVar". Lift-over for GRCh38 so coordinates become comparable rather than merely disclaimed, retiring the coordinatesComparable: false path. Turn the music you love into a piano lesson made for you. Like 1 Comment Story Updates 1 Duet Piano Studio Agent created lesson Inspiration Duet began with a gap we kept running into: an agent could give us a good music lesson, but it could not reach the piano. We could ask, “Can you help me practise these four bars?” and receive sensible advice—slow the piece down, isolate the right hand, repeat the difficult section—but the useful part stopped at the chat box. We still had to find the music, change the tempo, set the loop, remember the notes and rebuild the lesson ourselves. We wanted the agent to meet the learner inside the instrument. That became Duet: a browser piano where the learner and their agent work on the same piece, using the same transport and seeing the same lesson change in real time. What it does Duet turns a natural-language request into a visible, playable music lesson. A learner can ask: Load Minuet in G. Keep only the right hand, slow it to 70 per cent, loop bars 1–4, add a one-bar count-in and metronome, highlight the opening phrase, and start practice. Through WebMCP, the agent can carry out each part of that request directly. The piece loads, the tempo changes, the left hand is removed, the loop and count-in appear, the requested keys light up and practice mode begins. The learner does not receive another list of instructions. They receive a lesson they can immediately play. Duet includes: A responsive browser piano playable with mouse, touch or A–Z/0–9 keys Fourteen public-domain pieces and exercises Demo, Play Along and Practice modes Tempo changes, transposition, simplification and hand isolation Bar-level slicing and looping Count-in, metronome, seeking and hand-mix controls Visible key highlights and expected-note practice Agent-supplied structured musical arrangements Microphone permission and monophonic phrase-capture support A shared activity history showing what the learner and agent changed Why WebMCP matters This would be a much weaker product if the agent were simply clicking buttons. Music has meaningful concepts: pieces, bars, beats, notes, hands, tempo, loops and phrases. Duet exposes those concepts through 21 structured WebMCP tools. The agent can ask what Duet supports, inspect the active piece, read a bounded section of the score, transform the music and verify the resulting transport state. It does not need to guess screen coordinates or depend on fragile DOM selectors. The learner stays in control. Sound still requires a human gesture because of browser audio rules, and microphone access still requires explicit browser permission. Duet reports those boundaries honestly instead of pretending an action succeeded. How we built it Duet is a React and TypeScript browser application. The interface and WebMCP tools share one Zustand command and state layer, so an agent action produces the same visible result as a human action. Zod validates tool inputs before they reach the music engine. Playback uses the Web Audio API with an audio-clock transport. This supports reliable play, pause, resume, seek, looping, count-ins, metronome clicks and separate left- and right-hand mix controls. The 21 tools register through document.modelContext.registerTool . They cover capability discovery, state and score reading, playback, transformations, highlighting, practice, transport configuration and captured phrases. We tested the WebMCP experience with both OpenAI Codex and Anthropic Claude. This was important to us: Duet should present a clear musical tool surface to any compatible agent, not depend on behaviour unique to one client. Challenges The hardest part was keeping three realities synchronized: what the learner sees, what the agent reads and what the browser is actually playing. Browser audio also introduced constraints that a normal interface can hide. Audio must be unlocked by a human interaction, scheduled voices must stop cleanly and pause/resume must preserve the real musical position. Another challenge was returning enough score information for an agent without exceeding the WebMCP response budget. We added bounded pagination so an agent can read longer pieces safely rather than receiving silently truncated data. We also had to resist adding visual effects that looked impressive but distracted from practice. The final interface focuses on a realistic keyboard, the active musical phrase and the controls a learner genuinely needs. What we learned The biggest lesson was that WebMCP works best when a website exposes the language of its domain rather than a list of UI actions. “Click the third button” is brittle. “Loop bars 1–4, isolate the right hand and start practice” is understandable, verifiable and useful. We also learned that agent actions need immediate visual feedback. When the tempo, loop, highlights and practice state change on screen, the learner can understand what happened and continue from there. The agent becomes a collaborator rather than an invisible automation layer.
