Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.

- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by

- 3-4: thin prototype; contradictions between surfaces; placeholder content.

API could theoretically have enabled something similar.

  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.

But it needed to do more than block data for the agent. I wanted it to control data access in a way that preserved the agent's ability to reason about the data. What it does WebMCP Guard is an SDK that wraps WebMCP functions written with the Imperative API and injects controls. It has a corresponding management console that allows the organization to define policies. It has the following types of policies Data Protection This gives the company control over what data the agent can see. It classifies sensitive data, including names, SSN, credit cards, and more, and transforms them before the agent sees it. It can replace this data with a unique token. If the same piece of data appears across multiple records, it will use the same token identifier, which allows the agent to reason about the data without actually knowing what it is. In some cases, it can contextualize the data while removing the specificity. For example, it can replace a DOB from a patient health record with an age range. Human confirmation To prevent errant destructive actions polices can be created that require the user to approve (via an on-page modal) an action before it can be completed. This is most often used before an agent takes an irreversible action, such as deleting a record. Posture Assessment It can restrict what types of agents can access the tools. For example, you can block unidentified agents or restrict it to agents from one provider, such as OpenAI. Justification Policies can require the agent to provide a written justification before a sensitive action runs — bulk export, for example. The requirement is injected directly into the tool's input schema, so the agent learns about it from the tool definition rather than from a refusal. The agent is instructed to stop and ask its user for the reason and relay it verbatim, and the justification is evaluated and stored on the audit record as the human's stated reason. MODE lets anyone reshape a website by talking to an agent, turning cluttered interfaces into personal, accessible experiences stored in cookies. Like Comment Story Updates Inspiration The web is usually designed as a one-size-fits-all experience. A company decides where every element belongs, which promotions deserve attention, how much information appears at once, and what “accessible” means for the average visitor. The user can sometimes switch between light and dark mode or increase the browser’s text size, but those controls barely scratch the surface of what different people actually need. We were inspired by a simple question: What if a website could keep its trusted content and functionality while allowing each person to decide how that content should be presented? Someone with low vision may need larger text, stronger contrast, and fewer distracting elements. Someone with ADHD may want promotions and recommendations removed. A price-conscious shopper may want images hidden and products sorted by category and price. Another person may simply dislike the site’s visual design and want it reorganized into a calmer marketplace. Today, these changes often require browser extensions, custom CSS, accessibility tools, or technical knowledge. MODE explores a more natural interaction: the user describes the experience they want in ordinary language, and an agent adapts the website using capabilities intentionally exposed by the developer. MODE stands for My Own Display Experience . Its guiding principle is: The website owns the facts and functionality. The user owns the experience. What it does MODE is a WebMCP-powered preference layer that lets people reshape a website by talking to an agent. Our demonstration begins with Cartly , a fictional Amazon-style storefront. Its initial retail interface is intentionally dense: prominent promotions, crossed-out prices, sponsored products, recommendations, compact typography, multiple navigation regions, filters, product imagery, ratings, delivery information, and many elements competing for attention. The user opens the MODE sidebar and enters a request such as: “This page is overwhelming. Turn it into a calm, curated marketplace.” “Remove the crossed-out previous prices, but keep the promotional section.” “Make the text larger, use higher contrast, and reduce motion.” “I only care about comparing prices. Hide the images and sort from lowest to highest.” “Organize the products by category and then by price.” “Move the Cloud task chair before the Orbit LED desk lamp.” “Put the price above the title on every product card.” An agent interprets the request, inspects the state and capabilities exposed by the page, and applies only developer-approved actions. The result appears immediately on the same website without requiring the user to approve a separate preview. MODE can change: Page layout and information density Text size, contrast, color theme, and motion Visibility of promotions and sponsored content Visibility of product imagery, descriptions, ratings, filters, and crossed-out prices Product ordering Placement of products, sections, controls, and fields within safe structural groups Search terms and catalog filters Saved presentation profiles Cart contents and quantities through declared commerce actions The demonstration is not just a static redesign. Search, department selection, product filtering, sorting, add-to-cart, cart quantities, removal, and persistence all work as real interactions. At the same time, MODE preserves the developer’s authority over trusted information. The agent cannot invent or alter product names, prices, ratings, inventory, shipping promises, or checkout behavior. It also cannot execute undeclared actions, move elements across unsafe structural boundaries, or hide the controls needed to undo its changes. The page exposes 237 stable semantic element targets and 19 developer-approved WebMCP actions . Each meaningful region—including individual product fields—has a stable identity. This allows the agent to distinguish between concepts that may look similar in the raw DOM, such as a crossed-out previous price and an unrelated promotional banner. Preferences are remembered locally. Display settings, visibility overrides, and element positions are stored in first-party cookies, while named profiles and cart state are stored in local storage. A returning user therefore sees the experience they requested rather than being forced back into the original design. Every transformation is reversible: Revert last change restores the complete state before the previous agent request. A request containing several actions is treated as one transaction. Return to original restores the developer’s default storefront. Even the reset operation can be reverted if the user changes their mind. How we built it We built MODE as a React application using Vinext, Vite, TypeScript, and the OpenAI Sites-compatible project structure. The architecture has several connected layers. 1. A functional storefront We first built Cartly as a complete retail demonstration rather than a collection of placeholders. It includes a searchable product catalog, department navigation, ratings, price ranges, delivery filters, shipping filters, multiple sorting options, and a persistent cart. This was important because MODE needed to demonstrate that personalization can reorganize an application without breaking its underlying functionality. The products remain the same products, search remains search, and the cart continues working regardless of how the interface is presented. 2. A developer-controlled preference model We created a typed preference schema that defines exactly which presentation properties may change. It includes layout, density, text scale, theme, contrast, reduced motion, element visibility, product ordering, and related display preferences. Incoming values are validated against this schema. Unknown properties and invalid values are discarded. This means the agent is not given unrestricted access to application code or arbitrary CSS. It operates within an explicit contract established by the site. MODE also provides several complete experience presets: Retail default Calm marketplace Accessible shopping Price comparison These presets can be applied as starting points and then refined through additional natural-language requests. 3. A semantic element manifest One of the most important parts of MODE is its semantic page-element manifest. Rather than asking the agent to reason from anonymous DOM nodes, generated class names, or screen coordinates, the page describes its interface using stable identifiers such as: promotion.stage catalog.products product.cloud-task-chair.card product.cloud-task-chair.title product.cloud-task-chair.price product.cloud-task-chair.previous-price product.cloud-task-chair.add-to-cart Each entry includes information about the element’s role, hierarchy, visibility, protection status, and whether it can be repositioned. This semantic layer is what makes a precise request like “remove crossed-out prices” reliably different from “remove promotions.” 4. Safe element repositioning Repositioning introduced an additional structural challenge. Allowing an agent to place any element at any coordinate would create overlapping content, inaccessible controls, broken responsive layouts, and configurations that work at only one screen size. Instead, MODE uses developer-approved placement groups. An element can move before or after another element only when both belong to the same compatible group. For example: Products can be reordered among products. Product fields can be reordered within their product card. Major page sections can be reordered within the page flow. Header controls can be reordered within the appropriate header region. A product price cannot be moved into the footer. Protected recovery controls cannot be moved or hidden.
