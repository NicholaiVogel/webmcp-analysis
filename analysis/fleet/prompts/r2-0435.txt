# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Pocket - WebMCP Poker Live Game With Staged Recommendation Bring Your Own Copilot in Multiplayer WebMCP Copilot in a Live Hand Inspiration Most web applications are built for people. When an AI agent tries to help someone use one, it often has to reconstruct what is happening from the page, or depend on the user to explain everything correctly. I wanted to explore a different model: what does an application look like when a user can bring their own agent with them, and the application is designed to work with it? Poker turned out to be a great environment for testing that idea. A poker decision can depend on public information like the board and pot, private information like your hole cards, the complete history of the hand, exact rules about which actions are legal, and a game state that may change while an agent is still thinking. There are also multiple people interacting with the same application, each with a different view of what they are allowed to know. But there is another kind of context too: information that belongs to the player rather than the poker application. Your agent might know how you like to play, strategies you've been working on, your appetite for risk, previous hands you've discussed, or your own observations about the people you're playing with. Pocket shouldn't need to own that information in order for it to be useful. That led to Pocket: a playable Texas Hold'em game where every seat can have two minds - the player and their AI copilot. What it does Pocket lets you play Texas Hold'em against bots or with other people while using a compatible AI agent as a copilot during the hand. Normally, asking an AI for poker advice means explaining your cards, the board, pot, stacks, previous betting, and what you can do next. Pocket already knows all of those things, so it exposes them directly through three WebMCP tools: get_current_situation gives the agent the exact current game state, including the player's private cards, board, pot, stacks, whose turn it is, and the legal actions with precise raise limits. get_hand_history gives the agent Pocket's authoritative record of how the hand reached the current situation. stage_recommendation lets the agent send its recommended move and explanation back into Pocket's Copilot panel. That creates a full application → agent → application loop. Pocket supplies the facts about the game, the agent reasons over them, and its recommendation comes back into the interface where the player is actually making the decision. The important part is that Pocket doesn't have to be the agent. A user can bring an agent that has its own context, preferences, memory, or way of reasoning and combine that with authoritative state supplied by the application at the moment it's needed. Pocket knows the table. Your agent can know you. That separation is especially interesting to me from a privacy perspective. Personal strategy, notes about other players, previous conversations, and other private context don't need to become part of Pocket's user profile or database just so an AI feature can use them. The application can expose what it knows, while personal context can remain with the user's chosen agent. I also deliberately did not give the agent a tool for folding, checking, calling, or raising. The engine itself needs to know everyone's cards, but a player's interface, and their copilot, should only receive the information that particular player is entitled to see. The visible game and the WebMCP tools are both derived from that same player-safe state. That means the agent isn't getting a privileged version of the game behind the scenes. I kept the WebMCP surface intentionally small. The three tools basically correspond to three useful questions: What is happening right now? How did we get here? What does the agent recommend? Pocket also tracks the game, hand, and state version. When the agent returns a recommendation, Pocket verifies that it still belongs to the current situation before displaying it. If someone has acted and the table has moved on, the old recommendation is rejected instead of being presented as current advice. Every player can occupy the same shared game while still having a different private view of it, and potentially a completely different copilot with its own private context. Call the play. Lock your vision. Let AI replan the rest. Like 1 Comment Story Updates NextPlay Call the play. Lock your vision. Let AI replan the rest. Inspiration Basketball play design is collaborative by nature: a coach sketches an idea, tests the timing, changes a screen or route, and keeps refining until the sequence works. But most AI tools break that workflow. They generate a diagram, description, or recommendation somewhere outside the actual product. Once the coach edits the board, the AI no longer understands the current state—or which decisions are intentional and must not be overwritten. We built NextPlay around a simple question: What would a basketball tactics board look like if the coach and an AI agent could work on the same live play? WebMCP made that possible. Instead of relying on screenshots or a hidden copy of the play, the page exposes structured tools that let the agent read and modify the exact state the coach is viewing. What It Does NextPlay is a browser-native basketball tactics board for human–AI collaboration. A coach can ask an agent to create a sideline out-of-bounds play for a right-corner three. The agent: Reads the current formation, clock, actions, locks, and revision. Adds six structured basketball actions. Validates the play against deterministic execution constraints. Animates the result directly on the court. Then the coach can intervene through the normal interface. In our core demo, the coach: Moves A3’s screen to the right_elbow . Locks A3. Locks O2’s route in A4. Shortens the clock from 4.2 seconds to 2.0 seconds. That creates a clock-overflow error because A6 finishes too late. The agent then rereads the live page, sees the coach’s edits and locks, and retimes only the unlocked pass and shot in A5 and A6. A3 and A4 remain unchanged, the repaired play passes all seven validation checks, and the final animation completes within the new two-second clock. That second turn is the heart of NextPlay: the AI does not start over or overwrite the coach. It adapts around the coach’s decisions. Why WebMCP Matters The important state in NextPlay is live and page-local: Current player positions The action timeline The shortened clock The selected action Coach-made edits Locked actions Validation results The current play revision A generic assistant would have to infer that state from pixels, manipulate small controls, or work from an outdated description. NextPlay instead exposes exactly five semantic WebMCP tools: get_play_state add_play_actions validate_play animate_play update_play_action There is deliberately no agent tool for locking or unlocking actions. Locks are a coach-only authority boundary. This means the coach remains in control while the agent handles structured construction and replanning. How We Built It NextPlay is built with React, TypeScript, Zustand, Zod, Vite, and Vercel . We designed the application around one architectural rule: Every persistent mutation—whether initiated by the coach or the agent—must pass through the same command and transaction layer. The WebMCP tools do not maintain a separate copy of the play. Their handlers call the same application commands used by the visible coach interface. As a result, agent changes immediately appear on the: Court Timeline Action inspector Validation panel Activity rail Each successful content mutation increments the play revision exactly once. Write tools can include an expected revision, allowing NextPlay to reject stale updates when the page has changed since the agent last read it. We also implemented atomic action batches. When the agent creates the initial play, all six actions are accepted together or none are committed. The validation engine checks deterministic structural properties such as: Whether all actions fit within the clock Whether one player has incompatible overlapping actions Whether referenced players and actions are valid Whether possession order is consistent Whether the play contains the required inbound pass and shot Whether locked coach actions were preserved NextPlay does not claim that a play is tactically optimal, likely to score, or physically realistic. It validates the structure and timing of an animated tactical diagram. Challenges We Faced Preserving Human Authority The hardest product question was not how to let the agent edit the play—it was how to stop the agent from erasing intentional human decisions. We solved this with coach-only action locks. Before every agent mutation, NextPlay snapshots locked actions and verifies that they remain unchanged. Attempts to modify a locked action return an ACTION_LOCKED error without changing the play revision. Keeping the Agent and Interface Synchronized It would have been easy to build a demo where the agent edits hidden JSON while the UI displays something similar. Instead, we made the visible application state the source of truth. Tool success is returned only after the updated state has been committed through the same data model used by the coach interface. Handling Stale Agent State A coach may change the play after the agent reads it. Without concurrency protection, the next agent write could accidentally overwrite a newer version. Revision-aware writes let the application detect that situation and ask the agent to reread the play before continuing. Making Validation Honest We wanted the validator to be useful without making exaggerated basketball claims. That required carefully separating deterministic facts like timing, possession order, references, and lock preservation from subjective questions like whether the play would fool a real defense. Building a Reliable Live Demo A hackathon project has to work repeatedly, not just once. We reduced the scope to one polished sideline out-of-bounds scenario, kept the WebMCP surface to five tools, added strict runtime schemas, tested fresh-context production flows, and included an honest manual fallback for browsers that do not support WebMCP. What We Learned The biggest lesson was that giving an agent more autonomy is not always the same as making it more useful. In collaborative software, an agent needs three things: Semantic access to the real application state. Clear authority boundaries defining what it may change. Observable, revision-aware actions that both the user and the system can verify. WebMCP turns the page from a visual interface the agent must guess at into a structured collaboration environment. We also learned that the most compelling agent experiences are not single-prompt generation demos. They are iterative workflows where a human changes the constraints and the agent successfully adapts without losing prior intent. What We Are Proud Of NextPlay demonstrates a complete human–agent loop: Intent → structured construction → validation → animation → human intervention → constraint violation → agent repair The coach remains the decision-maker. The agent accelerates execution. That is the interaction model we believe will matter far beyond basketball: humans defining intent and protecting critical decisions while agents operate directly inside live, structured applications. Like Comment Story Updates A catalog of tested WebMCP tools for sites that have not shipped any, plus the extension that installs them and the agent that writes them for you. Why I built it I have spent this year putting WebMCP tools onto a production site. The problem is who has to ship it. WebMCP only works if the site adds it. That is the right design, but it splits the web in two. A few sites will offer tools. The rest will still use actuation. We created a way to use the protocol on sites that have not adopted it, and an argument aimed at those sites: here are the tools for your pages, here is proof they work, here is a user already calling them. What it does Point the extension at a site. It asks a public catalog whether anyone has published tools for that hostname, shows you what they would touch, and on your say-so installs them into the page's real WebMCP surface. From there they are ordinary tools. Chrome's own agent sees them, my extension sees them, and I drive them today with a browser extension with an agent-in-browser on Chrome and with Codex. Nobody uploads code. A tool is a name, a description, an input schema, and steps from a fixed set of nine operations. One interpreter runs them, and it cannot reach the network, touch storage, or point at anything the tool did not declare. Every tool is run against the real page before publishing, and both its result and everything it touched are recorded. What I learned Single page apps were the hard part. A site like that never reloads, so tools installed on the home route are still in the agent's list after the user clicks into a product page, pointing at elements that are gone. Browsers only announce a real page load. A route change inside a single page app arrives as a separate event, and if you do not listen for it you never learn the page changed. So the extension listens for both: a real load reinstalls everything, a route change only re-decides which tools still apply. The catalog makes that cheap, because the answer for a hostname is one lookup it can repeat on every route change with no help from the site. The other lesson was about who gets to write a tool. Use agents to write the code, host them locally, and inject them via an extension you own. Then any webmcp enabled site you have crawled can use the webmcp api and tools for now. The honest limit is that as pages change, you'll need to recrawl.
