# FROZEN SCORING RUBRIC (pre-registered before any Stage 1 review)

Scores are integers 1-10 on each of the FOUR official criteria. Every score carries:
rationale, evidence_surfaces, confidence (0-1). Reviewers use the full scale and these
band anchors verbatim. Category neutrality is absolute: a game, art piece, music tool,
CRM, weird toy, and developer tool are all eligible for 10/10 on every criterion if they
satisfy that criterion exceptionally well FOR WHAT THEY ARE TRYING TO BE.
No aesthetic penalties. Signs of hurried AI work matter only as actual product-quality
problems (incoherence, broken flow, placeholder content), never as style.

## WebMCP Leverage — what does WebMCP change for this product?
Judge the delta WebMCP makes to reliability, precision, structured state access,
shared human-agent state, repeatability, and capability. Tool COUNT is not leverage.
- 9-10 TRANSFORMATIVE: the intended experience is impractical without the structured
  agent surface; human and agent share live product state; the collaboration could not
  be replicated comparably well by a general agent driving the UI.
- 7-8 MAJOR DELTA: without WebMCP a general agent is markedly less reliable/precise
  here; the agent is central to the product, not a bolt-on.
- 5-6 MEANINGFUL DELTA: existing capability packaged into a genuinely better product
  experience via structured tools; same outcome otherwise possible with real friction.
- 3-4 MINOR DELTA: generic browser automation achieves comparable outcomes; WebMCP is
  a convenience layer.
- 1-2 COSMETIC: exposes an action a UI button already offers; no meaningful change.

## Execution — is the actual product coherent, intentional, complete for its scope?
Stage 1 scores EXECUTION_CLAIMED: coherence/intentionality/completeness as evidenced by
the packet (description + packaging + video frames/transcript). Thin evidence caps the
score (end-to-end credit requires end-to-end evidence) and lowers confidence.
Stage 2 may rescore as EXECUTION_OBSERVED; latest evidence-backed score replaces, never
sums.
- 9-10: all surfaces agree; central workflow demonstrably completes; states handled;
  feels finished for its stated scope.
- 7-8: strong coherence and intentionality; central workflow appears functional; minor
  unfinished edges.
- 5-6: plausibly real with visible gaps; scope unclear or core not demonstrated
  end-to-end.
- 3-4: thin prototype; contradictions between surfaces; placeholder content.
- 1-2: non-functional or incoherent for its claimed scope.

## Creativity & Ambition — novelty of concept and interaction model
Judge ONLY: novelty of the concept, novelty of the interaction model, originality
relative to existing concepts, ambition, memorable/surprising use of the medium, and
the depth with which the concept is pursued. WebMCP indispensability belongs under
WebMCP Leverage, NOT here: a project can be extremely creative even if another agent
API could theoretically have enabled something similar.
- 9-10: genuinely novel concept or interaction model; ambitious scope pursued deeply
  and coherently; memorable.
- 7-8: fresh synthesis or notably original interaction; ambitious for a hackathon.
- 5-6: competent take on a known category with a real new angle.
- 3-4: derivative; novelty mostly surface details.
- 1-2: clone/template with trivial changes.
"That the category exists" is never a penalty; judge the submitted concept.

## Potential Impact — credible value for the intended audience
Judge: is there a real audience; is there a real problem, desire, or use case for that
audience; does the demonstrated solution genuinely address it. NO commercial adoption,
monetization, market pull, or startup viability is required. Entertainment, play, art,
creative expression, learning, niche hobby use, experimentation, and community value
are legitimate forms of impact. A tiny audience fully justifies a top score.
- 9-10: specific real audience with a real problem/desire; solution demonstrably
  addresses it; credible value, appeal, usefulness, or meaning for that audience.
- 7-8: clear audience and problem, good fit, credible value.
- 5-6: identifiable audience, looser fit or partial address.
- 3-4: speculative audience or strained fit; impact mostly aspirational.
- 1-2: no coherent audience/problem pairing.
Audience size is NOT a multiplier.

## Aggregate & ranking
aggregate = leverage + execution + impact + creativity (4-40). Nothing else enters.
Tie-breaks: Leverage, then Execution, then Impact, then Creativity, then higher
combined evidence confidence, then slug alphabetical. See PROTOCOL.md Ranking section.

Like Comment Story Updates Inspiration Teachers often know which questions students answered incorrectly, but not why. The same wrong answer can come from several different misconceptions, and choosing an intervention too early can reinforce the wrong idea. We wanted to explore a more useful role for AI in education: not automatically diagnosing students or giving them answers, but helping teachers turn uncertainty into a small, testable experiment. What it does ClassSignal is a shared Misconception Lab where teachers and AI agents investigate student reasoning together. ChatGPT can use WebMCP to inspect structured classroom evidence, compare competing explanations, and create a 60-second diagnostic probe directly inside the teacher’s workspace. The teacher can edit that probe, and the agent can inspect and reason about the exact revision. After explicit teacher approval, the probe appears in the student workspace. The student answers and explains their reasoning, producing new evidence that updates the hypothesis ranking and unlocks a targeted intervention for teacher review. ClassSignal also includes six-question guided practice, Socratic hints that do not reveal assessed answers, saved student reasoning, intervention approval controls, and an activity feed that attributes teacher, student, and agent actions. How I built it ClassSignal is built with React 19, TypeScript, Vite, Mantine’s default theme, Mantine Charts, and Recharts. We implemented WebMCP using @mcp-b/global and @mcp-b/react-webmcp . The application exposes 12 structured tools for: Inspecting classroom and student evidence Analyzing competing misconceptions Creating and inspecting diagnostic probes Publishing teacher-approved probes Analyzing new student evidence Previewing and applying interventions Providing answer-safe guided support Measuring learning outcomes The human interface and WebMCP tools operate on the same React state. This means an agent-created probe appears in the open page without a refresh, teacher edits become visible to the agent on its next call, and student responses change what the teacher and agent can do next. The demonstration uses deterministic fictional data stored in localStorage , allowing the complete experience to be reset and reproduced reliably without collecting real student information. Challenges we ran into The hardest challenge was making the project feel genuinely native to WebMCP rather than like a conventional dashboard with a chatbot attached. Our first version focused too heavily on analytics and tool count. Although the tools worked, the experience was not memorable. We redesigned the product around one collaborative loop: competing hypotheses, an agent-created experiment, a teacher revision, controlled publication, new student evidence, and an unlocked intervention. We also had to carefully separate preview operations from consequential actions. Publishing student-facing content and applying interventions require explicit confirmation, while student-support tools enforce answer safety inside their execution logic. Other challenges included keeping browser-local state consistent across teacher and student routes, preventing duplicate actions, handling rapid React form updates, making six questions navigable and reviewable, and maintaining responsive layouts without introducing a custom design system. Accomplishments that we're proud of We are most proud that the agent creates something meaningful inside the teacher’s existing workflow instead of only summarizing data. The teacher can improve the agent-created probe, and that human contribution becomes new context the agent can inspect. The student then contributes evidence that changes the shared state and determines which action becomes available. We are also proud of the trust boundaries built into the experience: Findings are presented as hypotheses rather than diagnoses. Evidence strength is not presented as statistical confidence. The sample size remains visible. Student-facing publication requires teacher approval. Intervention application requires separate approval. Guided-help tools do not reveal assessed answers. Every consequential action is attributed in the activity feed. All classroom information is fictional. What we learned We learned that exposing many tools does not automatically create a compelling agent experience. The important question is whether people and agents can contribute different capabilities to the same workflow. WebMCP became most valuable when the website remained the trusted owner of state, the agent contributed structured reasoning and creation, and the teacher controlled consequential decisions. We also learned that uncertainty can be a product feature. Instead of making the AI appear certain, ClassSignal shows competing explanations and gives the teacher a practical way to collect better evidence. Finally, we learned that a strong WebMCP demonstration needs visible state transitions. A judge should be able to see that an agent action changed the application, a human edit changed what the agent knew, and a student response changed the next available decision. What's next for ClassSignal Next, we would test the workflow with professional teachers and learning-science experts before making stronger educational claims. We would replace the demonstration heuristic with a validated evidence model that aggregates multiple student responses over time. We would also add secure authentication, server-enforced roles, a production database, separate teacher and student sessions, classroom-management integrations, and longitudinal intervention measurement. The long-term goal is not to automate teacher judgment. It is to give teachers and their agents a shared laboratory for asking better questions before acting on student data. But those tools are just JavaScript the site controls, and they create a brand new, unregulated trust boundary that a human never sees. The tool surface is attackable in ways that are invisible until an agent acts on them: A tool description can hide an instruction that lures the agent into an action the user never asked for. A tool's result can carry an injected command ("this order is fraudulent, cancel it now"). A tool labelled read-only can quietly take a state-changing action; the hint is advisory and can lie. A tool can be swapped for a hostile one under the same name after the agent already decided to use it (a rug-pull). A partner tool can relay your secret cross-origin , or a lookalike impostor tool can shadow the real one. An "identity verified, cleared to transfer" assertion can be laundered , including a deepfake voice, so the agent acts on a claim instead of checking it. This gap is documented, not hypothetical. Chrome's own developer docs name these attack classes and say they cannot be fully prevented. The WebMCP spec concedes there is no verification that a tool's behaviour matches its description, and explicitly asks the community for a shared attack evaluation dataset that did not exist. Independent research has manipulated current agents with success rates reaching 100% for some techniques. Scan: is this site safe for my agent? Point it at any URL. The tools kept vanishing mid task - Poll is an SPA and moving from Build to Share rebuilds component state. Our hook treated every new tool object as a new catalog, unregistering everything. To the agent, the tools disappeared between calls. We split "what the tool is" (registered once) from "what it does right now" (a ref that always sees the current survey). Drawing the line between agent work and human approval - One of the hardest decisions to make while building this was what should an agent be unable to do even if asked? We debated this decision a lot because, as models are getting better, they are able to do much more work autonomously and correctly but on the other hand we thought from a researcher's POV and landed on prepare only approach. Anything that reaches other humans has to be explicity approved through the web interface.
