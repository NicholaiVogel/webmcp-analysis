What if it were also designed for agents to act? \n\n Inspiration \n\n AI agents are becoming increasingly capable, but interacting with the web still often feels like teaching a machine to imitate a human. \n\n Find a button.\nRead its label.\nGuess what it does.\nClick it.\nWait for the page to change.\nRepeat. \n\n Humans need visual interfaces because we navigate by seeing and clicking. \n\n Agents shouldn't have to. \n\n That led to the question behind Agent Mission Control: \n\n \n What would a web application look like if it were designed for both humans and AI agents from the beginning? \n \n\n WebMCP gave me a way to explore that question, and gave me a new way to explore thtis idea.. \n\n Instead of treating the browser as a collection of pixels that an agent must interpret, a website can expose structured capabilities that describe what the agent is actually allowed to do. \n\n So I built Agent Mission Control , an experimental WebMCP-native task environment where a human can manage work visually while an AI agent can interact with the same application through structured tools. \n\n The goal isn't to replace the interface. \n\n It's to give the web two interfaces to the same application : \n\n a visual interface for humans, and a semantic tool interface for agents. \n\n So I built agent-mission-control-webmcp to test a different model: one application with two interfaces — a visual interface for humans and a structured capability interface for AI agents — both operating on the same underlying application logic. \n\n \n\n What it does \n\n Agent Mission Control turns a normal task-management web application into an agent-addressable workspace . \n\n A human can interact with the application through the UI. \n\n An AI agent can discover WebMCP tools exposed by the page and use those structured capabilities to work with the same underlying tasks. \n\n Instead of asking an agent to: \n\n \n "Look around the page, find the right button, click it, and hope the UI hasn't changed..." \n \n\n the application can expose explicit operations the agent can understand and invoke. \n\n The important part is not simply that an agent can control a task app. \n\n The important part is how . \n\n The agent is no longer pretending to be a human operating a website. \n\n The website is speaking to the agent directly. \n\n \n\n Why WebMCP? \n\n Traditional browser automation often starts from the presentation layer. \n\n WebMCP lets us start from intent . \n\n A button might visually say: \n\n Complete \n\n But the capability behind it can communicate something much richer: \n complete_task(taskId)\n \n with structured parameters, predictable behavior, and application-defined semantics. \n\n That changes the relationship between websites and AI agents. \n\n Instead of: \n Agent\n ↓\ninterpret pixels / DOM\n ↓\nguess user interface\n ↓\nclick\n ↓\nApplication\n \n Agent Mission Control explores: \n Human ───────→ Visual UI ───────┐\n │\n ▼\n Shared Task Logic\n ▲\n │\nAI Agent ───→ WebMCP Tools ─────┘\n \n Both interfaces operate on the same application logic . \n\n That was a key architectural decision. \n\n WebMCP isn't an automation layer bolted onto the side of the application. \n\n It becomes another interface into the application itself. \n\n \n\n Human + Agent Collaboration \n\n The most interesting possibility isn't fully autonomous agents. \n\n It's shared control . \n\n Humans are good at goals, judgment, context, and deciding what should happen. \n\n Agents are good at translating intent into structured actions and carrying out repetitive operations. \n\n Agent Mission Control explores a simple model: \n\n Human defines the mission.\nThe application defines the allowed capabilities.\nThe agent executes through those capabilities.\nThe human remains in control. \n\n This creates an interesting middle ground between a traditional website and unrestricted browser automation. \n\n The website itself participates in defining what an agent can do. \n\n \n\n How I built it \n\n Agent Mission Control is built as a web application with WebMCP integrated directly into its task workflow. \n\n The application exposes a small set of task-oriented WebMCP tools. \n\n Rather than implementing separate automation logic, the WebMCP layer connects to the same task service used by the React interface. \n\n Conceptually: \n ┌── Human UI\n │\nTaskService ─┤\n │\n └── WebMCP Tools → AI Agent\n \n This was deliberate. \n\n If the human interface and agent interface implement separate business logic, they can eventually disagree. \n\n By sharing the same underlying service, actions performed through WebMCP can follow the same application behavior as actions performed through the UI. \n\n The project also includes a browser test path for discovering registered tools, invoking them with structured arguments, and verifying that the resulting state is reflected back in the application. \n\n \n\n Challenges I ran into \n\n 1. Designing tools instead of exposing buttons \n\n My first challenge was conceptual. \n\n A WebMCP tool shouldn't simply be a remote-control version of every button on the page. \n\n The question became: \n\n \n What capability should the application expose to an agent? \n \n\n That forced me to think in terms of application semantics rather than UI components. \n\n \n\n 2. Keeping humans and agents on the same source of truth \n\n It would have been easy to create a separate "AI API." \n\n But then I would effectively have two applications: \n\n one for humans and one for agents. \n\n Instead, I structured the project so both paths converge on shared task logic. \n\n That made WebMCP feel less like an integration and more like a second interface to the application . \n\n \n\n 3. Testing an emerging browser capability \n\n WebMCP is still an emerging technology. \n\n Testing required thinking beyond normal frontend tests: \n\n \n Are tools actually registered? \n Can an agent discover them? \n Are arguments structured correctly? \n Does execution reach the same application logic? \n Does the resulting state appear correctly in the human UI? \n \n\n Building around an emerging browser capability was one of the most challenging — and interesting — parts of the project. \n\n \n\n Accomplishments I'm proud of \n\n The thing I'm most proud of isn't the number of tools. \n\n It's proving a simple architectural idea: \n\n \n A web application doesn't have to choose between being human-friendly and agent-friendly. \n \n\n The same application can expose a visual experience to a person and structured capabilities to an AI agent without duplicating the underlying workflow. \n\n Agent Mission Control is intentionally small, but that makes the experiment easier to see. \n\n This isn't a task manager with AI added to it. \n\n The task manager is the demonstration of a different interface model for the web. \n\n \n\n What I learned \n\n Before building this project, I mostly thought about agent/browser interaction as automation. \n\n WebMCP changed the question. \n\n Instead of asking: \n\n \n "How can an AI operate this website?" \n \n\n I started asking: \n\n \n "How should this website expose itself to AI?" \n \n\n That sounds like a small distinction. \n\n It isn't. \n\n It shifts responsibility from agents constantly reverse-engineering interfaces toward applications explicitly describing safe, meaningful capabilities. \n\n And it suggests that the future web may not have one interface. \n\n It may have at least two: \n\n one optimized for people, and one optimized for agents. \n\n \n\n What's next \n\n Agent Mission Control is a proof of concept, but the pattern extends far beyond task management. \n\n Imagine websites exposing carefully designed agent capabilities for: \n\n \n project management, \n commerce, \n scheduling, \n content workflows, \n developer tools, \n administrative systems, \n and collaborative workspaces. \n \n\n The next step is exploring richer permission boundaries, confirmation flows, tool discovery, multi-step missions, and clearer visibility into what an agent is doing on behalf of a human. \n\n Ultimately, I want to explore a web where agents don't need to pretend to be humans. \n\n Humans get interfaces.\nAgents get tools.\nBoth collaborate through the same application. \n\n That's the web Agent Mission Control is trying to prototype. \n\n \n\n \n Built With \n\n chrome css3 github html5 node.js pnmp react typescript vite vitest webmcp \n \n\n \n Try it out \n\n \n \n \n
