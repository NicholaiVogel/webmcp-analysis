The hardest part has never been the rendering. It's the dozens of small edits between "what if this street were safer?" and a picture you can bring to a city council meeting. WebMCP collapses that gap: the browser agent you already have becomes the operator of a professional design tool, in your own signed-in tab, with you watching every move. What it does Open 3dstreet.app in ChatGPT's in-app browser (or Chrome 149+) and the page registers 26 WebMCP tools with document.modelContext . No extension, no relay, no setup. Then just talk: "Make a street with two drive lanes, protected bike lanes, and wide sidewalks with street trees" : the agent composes a managed street segment by segment. Each segment type carries the same presets a human gets from the sidebar (surface, markings, vehicles, pedestrians), so a "bus lane" comes with buses and BUS stencils instead of a grey slab. "Set the location to 4th & King in San Francisco" : server-side elevation lookup anchors the scene into Google's 3D Tiles. getGeoContext then gives the agent a machine-readable bridge between scene coordinates and lat/lon, including the compass bearing of the street's centerline and both endpoints, so it can align a design with the real road. "Take a plan-view snapshot" : the tool orients a north-up top-down camera and returns an image content block plus camera metadata (tilt, north-up, ground extent), so the agent sees its own work and can self-correct. Every mutation goes through the editor's command system: fully undoable, visible live in a transcript panel ( webmcp · managedStreetCreate …), and gated by a one-click Read-only toggle. The first tool call of a session dismisses the welcome modal and opens the Console tab, so the human always sees the agent at work. Read tools ( getScene , getSessionInfo , listMixins , listSegmentPresets ) let the agent orient itself before acting, and creation tools wait for the street to actually mount and report back what rendered, so "created" is backed by geometry rather than a hopeful return value. How we built it One registry, three LLM consumers. 3DStreet already had a tool registry feeding an in-editor assistant and an MCP relay for desktop AI apps. During the submission period we added a third transport: a React hook that feature-detects document.modelContext and registers every tool via registerTool({ name, description, inputSchema, execute }) , funneling execution through one shared executor so WebMCP, the relay, and the in-editor chat behave identically. We registered Chrome origin-trial tokens for our domains, so stock Chrome 149–156 needs no flag . Then we iterated through four rounds of live testing with an OpenAI WebMCP agent, treating every failure as a tool-surface bug compiled by Sol 5.6, then reviewed and fixed with Fable 5.1: Round 1: safety rails. Destructive tools are fenced to the user-editable scene subtree (an agent can't delete the camera rig); component names are validated against A-Frame's registry so hallucinated writes fail loudly; every error is written for the model . Round 2: grounding. The agent couldn't tell which side of the street was north, put a bus model in the stencil painter (sideways buses), and reported success for content that never rendered. We added getGeoContext , north-up plan snapshots with camera metadata, schema validation for every street field with the valid values listed in the error, per-type segment presets, and post-create readback. Round 3: guidance. The agent built synthetic buildings on top of the real Google 3D Tiles ones, then verified from street level. Fix: tool descriptions now lead with the geo rule, plan view is the default verification snapshot in geo scenes, and each mutating result ends with a nextStep nudge. Round 4: persistence and payload. Agent-built scenes vanished on reload, and a full-res PNG snapshot was 2.5 MB of base64. Added saveScene / loadScene , an unsaved-edits nudge, a 1280 px JPEG snapshot, and the build version in getSessionInfo so an agent can tell when it's hitting a stale deploy. Challenges we ran into Auth inside agent browsers. Our first runs hit unreliable third-party sign-in popups in embedded agentic browsers, so we shipped a demo carve-out: geospatial anchoring works signed-out for California locations (server-enforced bounding box + expiry). By round 2, sign-in was working in ChatGPT's browser, so we removed the warning but kept the carve-out so judges can try the demo with zero friction. Spec drift mid-trial. navigator.modelContext became document.modelContext in Chrome 150; bulk provideContext gave way to per-tool registerTool . We support both generations with feature detection. Testing a consumer that barely exists. Few agents call WebMCP tools yet, so we built a headless-Chromium harness that shims modelContext , registers the real page, and round-trips every tool, including verifying that the read-only gate and scene-containment guards refuse correctly. The agent believes the tool. When a create call returned "ok" for a segment that silently dropped a field, the agent moved on. Readback and validation errors turned out to matter more than any new capability. Image data transfer. It was not possible during our testing to use the output images generated from 3DStreet to be used as input images for ChatGPT AI Image Modification (whether through the compliant WebMCP protocol, or download, or DOM manipulation). I gave up debugging this and figured it's a work in progress on OpenAI MCP Client side to be able to use web outputs as model inputs. EDIT: finally got it working, sort of, it downloaded it to the file system and then read it back to do further AI image renders. What we learned Tool descriptions are the prompt . WebMCP has no system-prompt channel, so every description, error string, and nextStep line is agent UX. Three of our four testing rounds shipped mostly copy and defaults, not code. And an agent driving the user's own session, with undo and a visible transcript, is a fundamentally better trust model than headless automation: the human sees, and can reverse, everything. We had to add a lot of commands that are different types of state and documentation like geo location status / objects available / street segments available / etc. What's next A more general getInstructions orientation tool, auto-reopening the last scene on a bare URL so a returning agent picks up where it left off, a fetchable snapshot link for the human, and the same tool surface via Gemini in Chrome the day it consumes WebMCP. It still doesn't know how to place streets in the correct orientation. We'll need to leverage existing OSM street paths / nodes for that.
