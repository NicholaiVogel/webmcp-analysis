But once we started breaking down what would actually have to exist underneath it, three days suddenly looked very small. \n\n Before you can make the web dramatically faster or more intelligent, there is a boring but fundamental problem: information coming from different places has to remain trustworthy. If two systems disagree, an agent can't just pick one, merge them and confidently move on. \n\n So we took that one problem and made it the hackathon. \n\n That became Research Integrity Desk. \n\n We thought narrowing the scope would make the build manageable. \n\n It did not. \n\n What it does \n\n Research Integrity Desk is our attempt at the first layer of that larger problem: keeping information understandable and trustworthy when AI is working across different sources. \n\n Instead of treating everything an agent finds as one giant pool of context, we care about where information came from, what changed, what disagrees and what still needs a human decision. \n\n It is intentionally a much smaller problem than Elastic Web. \n\n But after building it, we are fairly convinced it is one of the problems that has to be solved first. \n\n How we built it \n\n The funny thing is that even the "smaller" project immediately became an orchestration problem. \n\n We built with WebMCP and used AI heavily throughout development. Codex was useful, but painfully slow for the pace of a three-day hackathon. There were limits on how many agents we could effectively keep working, so we started building infrastructure around the infrastructure. \n\n First an orchestrator. \n\n Then a workspace to keep track of what everybody was doing. \n\n Then graphs and loops because agents would lose context. \n\n Then checks because agents would confidently say something was finished when it wasn't. \n\n Then evals because checking everything manually stopped being realistic. \n\n Then skills. \n\n Then enough skills that we needed a skill router. \n\n Then memory buckets so agents got the context they needed without drowning in the entire project. \n\n Somewhere in there we realised that managing the agents had become a genuine engineering problem of its own. \n\n Challenges we ran into \n\n And then we started running out of credits. \n\n ChatGPT limits became a constraint. Codex was slow. Work moved between different tools and models depending on what could still actually run. \n\n Anti-Gravity became part of the workflow partly because it still had credits. \n\n Anti-Gravity was also a hallucination machine. \n\n It could very confidently announce that something had been implemented when we would open the product and discover that, in reality, absolutely nothing had happened. \n\n So now we needed a controller. \n\n Hermes went above the other agents as an outside critic. I deliberately wouldn't let it build. Its job was to be obnoxious: question everything, critique everything, find the smallest inconsistencies and check whether the work agents claimed to have done actually existed. \n\n Strangely, that worked. \n\n Buzz helped us keep track of the moving pieces. Agent Grid helped as work spread across agents. Evals and verification loops became increasingly important because after enough hours of nonstop development, "the agent said it works" is not a testing strategy. \n\n At one point, a part of the build that should have been straightforward consumed almost 28 hours once coding, testing, breaking and verifying were included. \n\n And then there was the website. \n\n AI repeatedly wanted to build us a beautiful presentation about the product rather than the actual working product. It kept drifting towards an interactive slide deck. \n\n So even after writing the functionality, we had to keep forcing the real code back into the experience and testing that what judges would see was actually running. \n\n We had scoped down because three days wasn't enough for the big idea. \n\n Then we discovered just how much engineering it takes to make even the small idea reliable. \n\n Accomplishments that we're proud of \n\n Honestly: that it works. \n\n We could have used the three days to make a beautiful simulation of Elastic Web. \n\n Instead, we kept cutting scope until we had something we could actually implement, test and verify. \n\n And somehow we shipped it while simultaneously dealing with model limits, exhausted credits, slow agents, hallucinated implementations and an orchestration stack that we hadn't planned on building. \n\n Research Integrity Desk is a small part of the original idea. \n\n But it is real. \n\n That matters more to us than pretending we built the whole thing. \n\n What we learned \n\n We learned that there are layers underneath "AI can do this" that are very easy to ignore in a demo. \n\n Who remembers what happened? \n\n Who checks whether it actually happened? \n\n Which agent should have which capability? \n\n Which information should it see? \n\n How do you know when two systems disagree? \n\n What happens when a model confidently invents its own version of reality? \n\n How do you keep several agents working without them undoing each other's work? \n\n We ended up needing workspaces, orchestration, graphs, loops, skill routing, memory, controllers, checks and evals just to keep the development process reliable. \n\n Which was slightly hilarious, because those were variations of the same problems we had started thinking about in the product. \n\n The more we built, the less this looked like a problem you solve by simply adding a smarter model. \n\n There is an entire systems layer around the model that matters. \n\n Probably more than we appreciated when we started. \n\n What's next for Vedaxi – Research Integrity Desk \n\n The strange outcome of the hackathon is that we started with a huge idea, deliberately made it much smaller, and finished with an even better understanding of how huge the original problem actually is. \n\n Research Integrity Desk is one layer. \n\n There are many more. \n\n Some became obvious from the product itself. Others became painfully obvious from trying to coordinate the agents building it. \n\n Elastic Web is still the larger direction, and we are deliberately not spelling out that entire system here before we build it. \n\n But these three days gave us something more useful than a giant prototype. \n\n They gave us a working first layer, a much clearer map of the problems underneath it, and a fairly ridiculous list of things that have to work before the larger idea can. \n\n We came here intending to build the big thing. \n\n Instead, we learned what has to exist before the big thing can be built. \n\n And somehow, between the credit limits, hallucinating agents, graphs, loops, evals and a controller whose main job was telling everybody else they were wrong, we actually shipped something. \n\n \n\n \n Built With \n\n agentgrid antigravity buzz claude css3 cursor github google-gemini hermes html5 javascript json-rpc model-context-protocol node.js openai-codex playwright postmessage-rpc react three.js typescript vercel vite vitest webgl webmcp \n \n\n \n Try it out \n\n \n \n \n vedaxi-integrity-desk.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n luxurylifestyleco Shah \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n\n \n Syed Hasan \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n luxurylifestyleco Shah \n started this project\n \n —\n \n 2 days ago \n \n \n\n
