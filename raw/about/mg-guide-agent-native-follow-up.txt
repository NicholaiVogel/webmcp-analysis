That work matters because relationships are personal, but it can also become repetitive and fragmented across meetings, notes, CRM systems, inboxes, and different tools. \n\n We have been building MG Guide as part of a broader effort to create a governed AI workspace that can work behind salespeople and sales teams without taking judgment or relationship ownership away from them. \n\n \n Our goal is simple: let AI help prepare the work, while the person remains responsible for the relationship. \n \n\n For The WebMCP Challenge , that idea took on a new form. \n\n What WebMCP changed for us \n\n Before this challenge, MG Guide already had a meeting follow-up workflow and the broader foundation we had been building around meeting context, relationship context, follow-up planning, and governed AI workflows. \n\n WebMCP gave us a new way to think about how an AI agent could interact with that experience. \n\n Instead of building a separate interface just for an agent, or asking an agent to interpret buttons and page structure, we could let the website itself clearly expose the actions that were safe and useful for an agent to perform. \n\n That led us to a simple model: \n\n \n ACTION → STATE → ARTIFACT → HUMAN CONTROL \n \n\n The agent can help process the meeting, understand the current follow-up state, and retrieve the prepared follow-up draft. The person still reviews the result and decides what happens next. \n\n That became one of the most important lessons from the project: \n\n \n The website itself can become a shared workspace between a person and an AI agent. \n \n\n What we built for the challenge \n\n For the WebMCP Challenge, we meaningfully extended the existing MG Guide experience with a browser-native WebMCP layer. \n\n The live MG Guide page now exposes exactly three capabilities to a compatible browser agent: \n\n \n ACTION — process the meeting follow-up \n STATE — understand where the follow-up currently stands \n ARTIFACT — retrieve the draft that was prepared \n \n\n This creates one shared experience instead of one interface for the person and another interface for the agent. \n\n When everything is clear, MG Guide can prepare a useful follow-up draft. \n\n When the relationship is unclear or ambiguous, the system stops and asks for human review instead of guessing. \n\n That distinction matters to us. In relationship-based work, a good AI system should know not only when it can help, but also when it should stop. \n\n \n Agent can prepare. Only a person can review and send. \n \n\n What we learned \n\n This challenge changed how we think about agent-native software. \n\n The page can be the shared contract \n\n One of our biggest takeaways was that an AI agent does not always need its own separate interface. \n\n The same page a person uses can expose a small, intentional set of capabilities that an agent can understand and use. That keeps the human and the AI working from the same experience instead of creating two disconnected versions of the workflow. \n\n Safe refusal is part of good design \n\n We intentionally built an ambiguous-contact scenario into the demo. \n\n If MG Guide cannot confidently connect the meeting to the right relationship, it does not continue automatically. It stops. \n\n That may look like less automation, but for us it represents better automation. \n\n Trust is especially important when AI is working around relationships, financial conversations, customer information, and follow-up communication. \n\n Human control should be designed in from the beginning \n\n We did not want “human in the loop” to be a sentence we added at the end of the project. We wanted it reflected in the experience itself. \n\n The agent can prepare context, state, and a draft, but the final customer-facing action remains with the person. \n\n That boundary became one of the clearest principles of the project. \n\n Browser behavior matters more than we expected \n\n We also learned that making an agent-capable web experience reliable is not only about the AI. \n\n Browser behavior, tool discovery, origin boundaries, caching, and how the page is served all affect whether the experience actually works for a person and an agent together. \n\n That pushed us to think more seriously about the browser as part of the agent environment, not simply as a screen. \n\n Where this is leading us \n\n The WebMCP Challenge also surfaced a bigger idea for the future of MG Guide and the governed AI ecosystem we are building around our sales teams. \n\n This challenge primarily demonstrates an outbound pattern: \n\n \n MG Guide exposes safe capabilities from our governed environment to a browser agent. \n \n\n But we are increasingly interested in the opposite direction too. \n\n What happens when a salesperson finds useful information somewhere else on the web and wants to intentionally bring that information back into their governed AI workspace? \n\n For example: \n\n \n useful research before a meeting; \n a company website; \n an article relevant to a relationship; \n publicly available information about a business; \n information a salesperson intentionally selects while preparing for a conversation. \n \n\n We do not want that to become uncontrolled web scraping or automatic memory collection. \n\n Instead, we see an opportunity for a governed intake experience . \n\n The person could intentionally select information, identify why it matters, and bring it into MG Guide with context about where it came from and what it is allowed to inform. \n\n That information could then become evidence available to the governed AI environment without automatically becoming permanent memory or authorizing an external action. \n\n WebMCP and a future Chrome extension companion \n\n This is also where a browser extension becomes interesting to us. \n\n On websites that support WebMCP, we would prefer to use the structured capabilities the site intentionally exposes. \n\n But many websites will not expose WebMCP immediately. A future Chrome extension companion could provide a user-controlled bridge. \n\n The salesperson could choose the information they want to bring into MG Guide, explain what they want to use it for, and send it through the same governed intake boundary. \n\n Conceptually: \n WebMCP-enabled website\n→ structured information selected through the site's declared capabilities\n→ governed intake\n→ MG Guide\n Website without WebMCP\n→ information explicitly selected by the person through a browser extension\n→ governed intake\n→ MG Guide\n \n In both cases, the important part is not simply collecting more information. \n\n The important part is preserving: \n\n \n where the information came from; \n why the person brought it in; \n what workflow it is allowed to support; \n whether it should remain temporary or become durable context; \n and what actions still require human approval. \n \n\n That is becoming an important part of how we think about building AI for real sales teams. \n\n The larger vision \n\n MG Guide is ultimately one piece of a broader governed AI ecosystem we are building to work behind salespeople and sales teams from a virtual perspective. \n\n We do not see the goal as replacing the salesperson. \n\n We see the goal as reducing the amount of time they spend reconstructing context, searching across systems, preparing repetitive work, and trying to remember what happened across dozens of relationships. \n\n The human should be able to spend more time on judgment, communication, leadership, and the relationship itself. \n\n The AI should help organize and prepare the work around them. \n\n WebMCP gave us a practical glimpse of what that can look like directly inside the browser. \n\n Existing project vs. new WebMCP work \n\n MG Guide existed before the WebMCP Challenge. \n\n The pre-existing project included the core meeting-follow-up workflow and the broader foundation we were building around meeting context, relationship context, follow-up planning, Google Workspace, and our governed MG Guide architecture. \n\n During the WebMCP Challenge submission period, we significantly extended that work with: \n\n \n a new browser-agent interaction model; \n a shared human-and-agent web experience; \n the WebMCP tool surface; \n safer ambiguity handling; \n browser-held workflow state; \n dedicated WebMCP testing; \n live browser validation; \n and the challenge-specific presentation and judge experience. \n \n\n We documented that distinction clearly in the public repository so the challenge-period work can be evaluated independently from the foundation that came before it. \n\n Try it \n\n Live product: \n https://ai-rolodex-landing-831270426395.us-east4.run.app/mg-guide/ \n\n Public source: \n https://github.com/themg-max/mg-guide-agentic-sales-workspace \n\n Judge start: \n JUDGE_START_HERE.md \n\n WebMCP judge guide: \n competition/webmcp/README.md \n\n Testing guide: \n competition/webmcp/JUDGE_TESTING.md \n\n Competition Delta: \n competition/webmcp/COMPETITION_DELTA.md \n\n What this demonstrates \n\n MG Guide turns post-meeting follow-up into a shared human-agent workflow: \n\n \n The agent prepares, the person understands, and the human remains in control. \n \n\n For us, that is the most important promise behind the project. \n\n \n\n \n Built With \n\n css google-cloud-run html javascript python webmcp \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Aaron Chandler \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n\n\n\n\n\n\n\n\n \n \n\n \n\n \n \n \n \n \n Devpost \n \n About \n Careers \n Contact \n Help \n \n \n \n\n \n \n
