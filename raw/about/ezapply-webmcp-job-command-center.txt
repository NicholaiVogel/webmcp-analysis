You can spend hours searching through listings, comparing requirements, figuring out where your skills fit, and writing a different cover letter for every application. \n\n AI agents can make a lot of that process much faster. They can search, analyze job descriptions, identify skill gaps, and even write application drafts. But there is one part we didn't want an agent to handle on its own: actually submitting the application . \n\n That led us to the idea behind EzApply . \n\n We wanted to build something where the agent takes care of the repetitive work, while the candidate stays in control of the decisions that matter. When we came across WebMCP , it felt like a natural fit. Instead of an agent trying to scrape a page or interact with a UI blindly, WebMCP lets the website expose structured tools that an agent can use directly. \n\n So we thought: what if applying for jobs felt less like filling out endless forms and more like having an AI co-pilot? \n\n That's what EzApply is built around. \n\n What it does \n\n EzApply is a Job Application Command Center built with WebMCP. \n\n The agent can take a job from discovery all the way to a ready-to-submit application, but the candidate always has the final say. \n\n We currently expose six WebMCP tools: \n\n \n search_jobs — Finds jobs based on keywords, salary requirements, and remote preferences. \n score_job_fit — Compares the candidate's skills with a job's requirements and calculates a fit percentage. \n identify_skill_gap — Shows which skills are missing and gives suggestions for improving the candidate's resume. \n generate_application_draft — Creates a tailored cover letter and sends it to the Approval Queue. \n save_to_drafts — Saves changes made by the candidate to an AI-generated application. \n submit_application — Handles the final submission, but only after the candidate explicitly confirms it. \n \n\n Human-in-the-Loop Approval \n\n This is the part of EzApply we're most proud of. \n\n AI can prepare an application, but it doesn't get to decide when it is submitted. \n\n Every generated application goes into an Approval Queue . The candidate can read the cover letter, make changes directly, and then approve it. \n\n The submit_application tool also checks for candidateConfirmation: true inside its execute() function. This means the safety check isn't only part of the interface. The tool itself refuses to submit an application without explicit confirmation. \n\n We wanted this to be a real safety boundary rather than just a button that looks like one. \n\n Agent Console \n\n We also wanted users to understand what the agent was actually doing. \n\n The Agent Console displays WebMCP tool calls as they happen, including timestamps and status information. This makes the agent's actions visible instead of turning the whole process into a black box. \n\n The 1-Click Pipeline \n\n EzApply also has a one-click workflow that demonstrates how the tools can work together: \n\n Search → Score → Identify Skill Gaps → Generate Draft → Human Review \n\n The agent handles the tedious parts in sequence, while the candidate takes over when a decision actually matters. \n\n How we built it \n\n One of our goals was to keep the project simple enough that the WebMCP integration remained the focus. \n\n The entire application is contained in a single HTML file of roughly 70KB , with inline CSS and JavaScript and no production dependencies. \n\n We register our tools through document.modelContext using WebMCP's registerTool() API and provide proper inputSchema definitions so an agent knows what each tool expects. \n\n For example: \n document . modelContext . registerTool ( { \n name : "search_jobs" , \n description : "Searches available tech jobs by keywords, salary, and remote status." , \n inputSchema : { \n type : "object" , \n properties : { \n query : { \n type : "string" , \n description : "Job title or skill keyword" \n } , \n minSalary : { \n type : "number" \n } , \n remoteOnly : { \n type : "boolean" \n } \n } , \n required : [ "query" ] \n } , \n execute : async ( input ) = > { \n const results = jobs . filter ( j = > matchesQuery ( j , input ) ) ; \n\n return { \n success : true , \n count : results . length , \n jobs : results\n } ; \n } \n } ) ; \n \n We also added a small in-memory modelContext fallback. If WebMCP isn't available in the browser, the app can still be explored normally. When WebMCP is available, the same tools are exposed through the native protocol. \n\n For the interface, we went with an aviation-inspired command-center theme. Job cards look like boarding passes, jobs have flight-style codes, and the overall interface is designed to feel like you're managing a journey from discovery to application. \n\n The project is deployed on Vercel using Vite as a minimal static setup. \n\n Challenges we ran into \n\n Getting the human approval step right \n\n We didn't want the approval step to feel like unnecessary friction. At the same time, we didn't want to hide an important decision behind a single confirmation button. \n\n We ended up using an inline-editable application draft so the candidate can make changes without leaving the workflow. The approval card is intentionally prominent, making it clear that this is the point where the human takes control. \n\n Making WebMCP visible \n\n One challenge with a protocol like WebMCP is that most of the interesting work happens behind the scenes. \n\n A user doesn't necessarily know that an agent just called search_jobs or score_job_fit . \n\n That's why we built the Agent Console. It turns those normally invisible interactions into something users can actually watch, which also helped us understand and debug the agent workflow while building the project. \n\n Keeping everything in one file \n\n We deliberately challenged ourselves to keep the application lightweight. \n\n Instead of reaching for a framework, component library, or large collection of dependencies, we built the application with plain HTML, CSS, and JavaScript. \n\n That made the project easier to deploy and kept the focus on what we were actually trying to demonstrate: WebMCP and human-agent collaboration. \n\n Accomplishments that we're proud of \n\n \n Six working WebMCP tools that can be used together as a complete workflow \n A 1-click agent pipeline that demonstrates tool orchestration from job search to application draft \n A genuine human approval boundary for the final submission step \n The candidateConfirmation check is enforced inside the tool itself, not just in the UI \n A complete application in roughly 70KB with zero production dependencies \n A real-time Agent Console that makes agent activity transparent \n A polished interface that makes an otherwise abstract WebMCP concept easy to understand \n \n\n What we learned \n\n Building EzApply changed how we think about agents on the web. \n\n The biggest lesson was that agents don't always need to control the entire experience. In many cases, the better approach is to give the agent well-defined tools and let the human remain responsible for important decisions. \n\n WebMCP made that model much easier to explore. Instead of relying on DOM scraping or trying to interpret screenshots, the website can expose structured tools with clear inputs and outputs. \n\n We also learned that human-in-the-loop isn't necessarily a compromise . The approval step actually makes the experience feel safer because the user can see exactly what the AI produced before anything important happens. \n\n And because the tools run directly in the browser, we were able to build and deploy the prototype without creating a separate backend just to demonstrate the agent interaction. \n\n Most importantly, EzApply showed us a different way of thinking about the web: not just as pages that agents have to figure out, but as experiences that can actively provide agents with useful capabilities. \n\n What's next for EzApply — WebMCP Job Command Center \n\n EzApply is currently a prototype, but there are several directions we'd like to take it. \n\n Real job listings \n\n Connect the search workflow to real job sources such as LinkedIn, Indeed, and Greenhouse so the agent can work with actual opportunities. \n\n Resume parsing \n\n Add a WebMCP tool that can process an uploaded resume and automatically extract skills, experience, and other relevant information. \n\n Multi-agent workflows \n\n Experiment with separate agents for different parts of the process — for example, one for job research, one for application writing, and another for reviewing the final draft. \n\n Application tracking \n\n Keep track of submitted applications and let the agent help with follow-ups and status updates. \n\n Interview preparation \n\n Once an application is submitted, use the job description to generate role-specific interview questions and preparation material. \n\n Ultimately, we'd like EzApply to become more than an application generator. We want it to be a job-search co-pilot where the AI handles the work, but the candidate stays in control. \n\n \n\n \n Built With \n\n css3 github html5 javascript vercel vite webmcp \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Manisana Yumnam \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n huhhh \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Manisana Yumnam \n started this project\n \n —\n \n 3 days ago \n \n \n\n
