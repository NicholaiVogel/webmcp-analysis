Point any WebMCP-capable agent at the site or scan the QR. Inspiration Your repos show what you shipped. They do not show the engineer behind them. A CV can say "reliable," "consistent," or "quality-focused," but those are claims. Chapa tries to turn the work itself into evidence. Chapa analyzes 12 months of engineering activity and builds an Impact Profile across four core dimensions: Delivery, Quality, Consistency, and Breadth. An optional fifth dimension, Craft, appears when a developer provides a report from an AI coding tool. The profile includes a developer archetype, composite score, and trend over time. An internal confidence score adjusts the composite when data is incomplete. GitHub can be the starting point, but the profile is not limited to GitHub. Chapa can combine activity from GitLab, Bitbucket, Codeberg, and enterprise-managed GitHub accounts uploaded through the Chapa CLI. The result is a live SVG badge that can sit in a README and evolve as the developer's work evolves. Badges marked Verified metrics carry an HMAC-SHA256 signature, so their verification records can be authenticated and tampering detected. But there was a problem. The badge could show your engineering impact, but it could not explain it. Why is Quality 62? What caused the score to fall this month? What would happen if Delivery improved by ten points? How does this profile compare with another developer's? A static badge cannot answer those questions. An agent can. Why WebMCP WebMCP changes Chapa from something an agent can merely look at into something an agent can understand. Behind the badge is structured state: dimension scores, normalized submetrics, archetype, confidence, trend history, verification data, and badge configuration. Trying to infer that state from the DOM would be fragile and incomplete. With WebMCP, Chapa exposes the underlying model directly. An agent can call explain_dimension and receive the score, formula, normalized submetrics, and an improvement tip. It can call get_impact_history to reason about changes over time, or compare_profiles to compare two developers dimension by dimension. The agent is no longer interpreting pixels. It is working with the same engineering model that produced them. Creator Studio made the fit even stronger. Studio was already terminal-first: users type commands such as /set colorPalette indigo or /preset holographic . That command registry already defined Chapa's mutation vocabulary. WebMCP became another interface to the same system rather than a separate agent API. Human clicks, terminal commands, and agent tool calls all converge on the same underlying actions. What people and agents can do together Understand the profile Instead of searching through panels, you can ask: "Why did my score drop this month?" The agent can inspect the impact history, explain the affected dimensions, and answer using the same numbers Chapa displays. suggest_improvements runs Chapa's existing insight engine against the real profile, so recommendations come from the developer's own activity rather than generic advice. Explore what could change simulate_score lets an agent change hypothetical dimension values and calculate the resulting composite score, tier, and delta. Nothing is persisted. That means the agent can answer questions like: "What happens if I improve Quality to 80?" before anything changes. Compare engineering profiles compare_profiles validates another public handle, loads both profiles, and returns the delta for every dimension. What previously required opening two profiles and comparing them manually becomes a structured question an agent can answer. Understand verification explain_verification explains what a Chapa signature proves, what it does not prove, when the verification record expires, and whether it uses the current or legacy format. Verification becomes something a person can actually understand rather than just a cryptographic status indicator. Shape the badge Creator Studio contains seven visual style categories. Instead of navigating controls, a developer can describe what they want: "Make it minimal, remove the glow, and use the terminal preset." The agent translates that intent into the same /preset and /set commands a person would type. Those commands appear in the Studio transcript as they execute. The agent does not get a secret mutation path. It uses the same one the human does. Human control stays at the boundary The most important design decision was deciding what the agent should not control. Agents can inspect, explain, compare, simulate, preview, and restyle freely. Persistence is different. save_badge_config creates a proposal in the UI and waits for the developer to approve it. The agent can help shape the result; the human decides when it becomes real. In production, confirmation persists the configuration, invalidates the badge cache, and updates the public share page and live SVG. In judge demo mode, confirmed saves remain local. How I implemented WebMCP Chapa registers 19 WebMCP tool registrations across four surfaces, using 18 distinct tool names because Creator Studio and public profiles both register explain_dimension . Landing page ( / ) get_site_capabilities , find_profile Creator Studio ( /studio and /studio?demo=1 ) list_style_options , apply_badge_style , apply_preset , preview_badge , reset_badge_config , save_badge_config , simulate_score , suggest_improvements , explain_dimension Public profile ( /u/{handle} ) get_impact_profile , get_impact_history , verify_badge , compare_profiles , explain_dimension , get_embed_snippet Verification page ( /verify/{hash} ) get_verification_record , explain_verification A shared useModelContextTools hook registers each catalog on document.modelContext . A catalog signature keys registration so updated definitions register cleanly, and an AbortController removes tools when the component unmounts. In Creator Studio, Quick Controls, terminal commands, and WebMCP calls all resolve to command text and pass through the same executeCommand registry. This keeps the terminal transcript, React state, live preview, and pending save configuration on one shared mutation path. Trust and safety Public profile and verification tools are read-only. Any tool that may return user-controlled text, such as a display name from a source platform, sets untrustedContentHint to true . Free-text values are length-bounded and control characters are removed at the tool boundary. The server also removes private data before it reaches the browser. For example, a profile's confidence value and penalty reasons never enter the React Server Component payload for a visitor viewing another developer's profile. verify_badge strips confidence again at the client boundary as defense in depth. A feature flag named webmcp_enabled controls the entire WebMCP surface. A database value can override the environment configuration, allowing the tools to be disabled without a deployment. Challenges One of the most useful bugs I found was not in a tool. It was in the trust model around one. explain_dimension is used in two contexts. In Creator Studio, the data belongs to the developer viewing it. On a public profile, some of that data originates from another developer. The original tool factory hardcoded the trusted annotation. Nothing exploitable was exposed because no user-controlled text was present in the current submetrics. But the next field containing something like a repository name could have crossed the boundary incorrectly. I changed the factory so trust context is a required parameter. Each caller now has to declare what it knows. The second challenge appeared in badge caching. Because badge content can be localized, it was possible for the rendered locale and cache key locale to disagree. An English badge could therefore end up in a Spanish cache slot. I replaced those independent decisions with a single resolveBadgeLocale entry point that returns both the localized strings and the corresponding cache key. The caller can no longer accidentally pair one locale with another locale's cache entry. What I am proud of WebMCP did not become a parallel control plane bolted onto Chapa. The agent uses the same domain model and, in Creator Studio, the same command registry as the person using the interface. That gives Chapa a clear collaboration boundary: the agent can understand, explain, compare, simulate, and help shape your engineering profile; the human remains in control of what persists. That feels much closer to the kind of human-agent interaction I want Chapa to represent. What I learned Designing tools forces you to be honest about your domain model. The easiest WebMCP tools to build were the ones sitting on clean, deterministic functions: score explanation, simulation, and the insight engine. The awkward tools exposed places where the application itself had unclear boundaries. I also learned that untrustedContentHint cannot be the security boundary. It is information for a consumer I do not control. The real boundary has to exist earlier: minimize the data, redact it on the server, bound untrusted text, and only then describe its trust level to the agent. What is next The larger direction: Chapa started as a badge that represents engineering impact. With WebMCP, that badge becomes something you can have a conversation with.
