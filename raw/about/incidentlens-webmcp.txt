They fail because the useful evidence is scattered across alerts, logs, metrics, deployment history, and runbooks. \n\n During an outage, an engineer may need to jump between several screens just to answer basic questions: \n\n \n What changed? \n When did the degradation begin? \n Which service is responsible? \n Was there a deployment immediately before the incident? \n What is the safest remediation? \n \n\n AI agents can help with this investigation, but traditional websites are primarily designed for humans. An agent often has to interpret visual interfaces, navigate pages, and extract information indirectly. \n\n IncidentLens WebMCP explores a different approach: make the incident-response application itself agent-native. \n\n Using WebMCP, IncidentLens exposes structured incident investigation capabilities directly to compatible AI agents while preserving the same dashboard for human operators. \n\n What it does \n\n IncidentLens is an incident-response console that combines: \n\n \n alerts \n application logs \n infrastructure metrics \n deployment history \n incident timelines \n root-cause hypotheses \n remediation recommendations \n \n\n The dashboard can be used normally by an engineer, but it also exposes these capabilities as structured WebMCP tools. \n\n An AI agent can investigate an incident through a workflow such as: \n list_incidents\n ↓\nget_incident\n ↓\nget_alerts\n ↓\nsearch_logs\n ↓\nget_metrics\n ↓\nget_recent_deployments\n ↓\nbuild_timeline\n ↓\nanalyze_root_cause\n ↓\nsuggest_remediation\n \n For example, a user can ask: \n\n \n Investigate INC-102. Determine what changed before the outage, identify the most likely root cause, and recommend the safest recovery action. \n \n\n Instead of trying to visually navigate the application, the agent can call the relevant WebMCP tools and receive structured results. \n\n Why WebMCP matters \n\n Without WebMCP, an AI agent interacting with an operational dashboard may need to: \n\n \n understand the page layout, \n locate the correct controls, \n navigate multiple views, \n interpret visual information, \n extract relevant values, \n repeat the process for every investigation step. \n \n\n IncidentLens exposes the underlying capabilities directly. \n\n For example: \n search_logs ( { \n incidentId : "INC-102" , \n query : "connection timeout" \n } ) \n \n can return structured evidence that an agent can reason over immediately. \n\n This makes the interaction more deterministic, composable, and transparent. \n\n The human interface and the agent interface coexist: engineers can continue using the dashboard normally while agents gain a structured way to assist them. \n\n Human-in-the-loop safety \n\n Incident response can involve high-impact actions. \n\n For that reason, IncidentLens separates investigation from execution . \n\n Agents can autonomously: \n\n \n inspect evidence, \n correlate telemetry, \n construct timelines, \n generate hypotheses, \n and recommend remediation. \n \n\n Potentially destructive actions such as rollbacks or service restarts remain subject to explicit human approval. \n\n The goal is not to replace the incident commander. It is to give them a much faster investigation partner. \n\n Example incident \n\n One demonstration incident begins shortly after deployment v2.4.1 . \n\n IncidentLens correlates several pieces of evidence: \n Deployment v2.4.1\n ↓\nDatabase connection usage rises\n ↓\nConnection pool becomes saturated\n ↓\nRequest latency increases\n ↓\nHTTP 5xx errors spike\n \n Rather than showing only an AI-generated answer, IncidentLens exposes the evidence used to reach the conclusion so the operator can independently verify it. \n\n How we built it \n\n IncidentLens is implemented as a web application with WebMCP-enabled tools exposed from the browser. \n\n The application contains a simulated production environment with realistic: \n\n \n incidents \n alerts \n logs \n time-series metrics \n deployment events \n service metadata \n \n\n Each investigation capability has a structured input and output contract so an AI agent can invoke it directly. \n\n The architecture is intentionally simple: \n Human / AI Agent\n │\n ▼\nIncidentLens Web UI\n │\n ├── Human-facing dashboard\n │\n └── WebMCP tools\n │\n ▼\n Incident data layer\n │\n ┌───────┼─────────┐\n ▼ ▼ ▼\n Logs Metrics Deployments\n \n This allowed us to focus on demonstrating how WebMCP changes the interaction model rather than hiding the core idea behind unnecessary infrastructure. \n\n Challenges \n\n One of the biggest design challenges was deciding what should become a tool. \n\n Simply exposing every button on a web page would not create a useful agent interface. \n\n Instead, we designed tools around meaningful operational capabilities such as: \n search_logs\nget_metrics\nget_recent_deployments\nbuild_timeline\nanalyze_root_cause\n \n Another challenge was maintaining human oversight. Incident response is an area where an incorrect automated action can make an outage worse, so the system intentionally keeps remediation execution separate from investigation and recommendation. \n\n We also focused on returning structured, inspectable evidence rather than asking users to trust an unexplained AI conclusion. \n\n What we learned \n\n The most important lesson was that agent-enabled websites should not simply reproduce the existing UI as tools. \n\n The strongest WebMCP tools represent intent and capabilities , not mouse clicks. \n\n For example: \n "Search incident logs for database errors"\n \n is considerably more useful to an agent than: \n "Click the Logs tab"\n \n WebMCP makes it possible for a website to support both interaction models simultaneously: \n\n a visual interface for people and a structured capability interface for agents. \n\n What's next \n\n IncidentLens could be extended with integrations for real observability and operations systems such as: \n\n \n OpenTelemetry \n Prometheus \n Grafana \n Kubernetes \n cloud monitoring platforms \n deployment systems \n ticketing and incident-management platforms \n \n\n A future version could also introduce approval-gated remediation tools, persistent incident memory, multi-agent investigations, and automatic post-incident reports. \n\n Our longer-term vision is an operations console where humans remain in control while AI agents can reliably understand and operate the underlying application through explicit, structured capabilities. \n\n \n\n \n Built With \n\n agents ai css3 devops
