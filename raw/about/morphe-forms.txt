Morphe takes a different approach: use a common standard so one integration works across many clients — the "USB-C of AI." \n\n We wanted to prove that idea on a real product, not a toy. \n\n A form builder was a natural fit for WebMCP. Forms are highly interactive, but difficult for agents to operate. An API can expose data, but WebMCP lets an agent actually operate the application in the browser . \n\n What it does \n\n Morphe is a form builder originally built as part of a larger platform. For this hackathon, we extracted it into a standalone product and added MCP at two levels. \n\n Through backend MCP, agents can create, manage, publish, submit, analyse, and export forms . \n\n Through WebMCP, agents can operate the actual web app — opening the form list, entering the editor, viewing submissions, opening previews, and navigating the app via the use of tools. \n\n The key idea is that humans and agents share the same workspace . There is no separate agent mode or shadow API. Both use the same data, validation, and business logic. \n\n How we built it \n\n Morphe uses FastAPI + React/Vite , deployed on Render and Vercel. \n\n Because WebMCP is still a draft standard, the frontend detects support through document.modelContext . If available, we register our tools; otherwise, the app works normally. \n\n We exposed 20 WebMCP tools across two groups: \n\n \n Form operations: create, update, publish, submit, analytics, and export. \n Navigation: move between the form list, editor, submissions, preview, and other views. \n \n\n Navigation uses the application's real router, so agents operate the actual SPA rather than simulating page changes. \n\n Challenges \n\n The biggest challenge was building around an emerging standard while keeping the product reliable without it. \n\n We also dealt with production-only routing failures, a CDN issue affecting a specific API path, CORS between separately deployed services, and extracting the application from its larger codebase. \n\n Accomplishments \n\n We turned an existing project into a standalone, deployed product with: \n\n \n 20 WebMCP tools \n Backend MCP support \n Agent-driven browser navigation \n Graceful degradation when WebMCP isn't supported \n \n\n What we learned \n\n WebMCP isn't just useful for AI. Designing interfaces that are easier for agents to understand can also improve accessibility and usability for people. \n\n We also learned that emerging standards require graceful degradation: detect what the platform supports, enhance when possible, and never make the core product depend on it. \n\n What's next \n\n Morphe will become the foundation for the larger platform. Next we're planning Postgres persistence, authentication, richer analytics, conditional logic, embeds, and a larger agent tool surface . \n\n The goal remains simple: humans and AI should be able to operate the same product, without bespoke integrations for every AI client. \n\n \n\n \n Built With \n\n alembic dnd-kit fastapi model-context-protocol-(mcp) python react react-router recharts render sqlalchemy sqlite streamable-http typescript vercel vite webmcp \n \n\n \n Try it out \n\n \n \n \n web-omega-five-19.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n I worked on both the backend and frontend with an AI coding agent.
