Thumbnail: data/webmcp-challenge/roast-devpost-thumb.png Demo: https://crowley.nl/webmcp-challenge/ Essay: https://crowley.nl/blog/webmcp-consent-theater.html Built with: javascript, webmcp, mcp, html5, css3, elevenlabs, github-actions, security Project Story (pasted into "About the project") Inspiration I first heard about WebMCP on Greg Isenberg's YouTube channel, where the conversation was all possibility: agents driving websites through your own browser, no scraping, no brittle automation. I love MCP, so I started reading the proposal properly. What struck me was the gap: the security story was thin. WebMCP's best trick is that the agent inherits your logged-in session - and that same trick is the loaded gun. So I asked the obvious questions. How does consent actually work here? What could go wrong? And when it goes wrong, what would stop it going wrong again? What it does ROAST is a fake coffee shop an AI agent can drive through WebMCP - and misuse. It plays four acts: No consent - the agent acts silently on your session Naive consent - a dialogue shows the tool's friendly description; feels safe Poisoned consent - the same dialogue, with three real attacks underneath: label mismatch, tool substitution, and a hidden-instruction manifest. You approve a coffee; your shipping address changes, your account closes The mandate - the proposal. You grant bounded authority up front: two coffees, $30, never my address, ask before paying. Every call is checked against the executed tool and the hidden chain, before any dialogue renders The model is Intent → Authority → Effect . Inside the mandate the agent just works - no prompt fatigue. Outside it, the call is refused before a dialogue exists to be fooled. At the boundary (paying), it escalates to the human. Once. A built-in test rig asserts all nine cases - three attacks, six legitimate paths - live on the page. How we built it Vanilla JavaScript, no framework, one funnel: every tool call (simulated or real) resolves through request → resolvePlan → mandate check → consent gate → execute → log . The attacks are pure functions that warp the mapping between what is shown and what runs - which makes them honest test cases, not theatre. Tools register for real via navigator.modelContext where the browser supports it; a deterministic sim harness plays the same pipeline everywhere else. The instrumentation panel shows intent, consent, and effect side by side - the technical truth lives "below the waterline" of the UI. Challenges we ran into The honest one: the mandate check runs inside the page, and the page is the attacker. We state this in the UI rather than hide it. In a real deployment the mandate belongs in the browser or the agent - the layer a site cannot rewrite. ROAST prototypes it in the page because the page is what a demo controls. That is the proposal to the spec, not a shipped fix. The other challenge was UX density: showing an attack, a refusal, and the raw call log without drowning the visitor - solved with plain-English verdicts above the waterline and the technical log beneath it. What we learned The consent moment is the whole human-agent interface, and a dialogue that renders a human-authored description is a dialogue that can lie. Better warnings do not fix this; bounded authority does. Checking the executed call against a standing mandate defeats all three attacks with one invariant: an effect may only execute when it matches both the declared tool and the human's current mandate. What's next for ROAST Take the mandate out of the page: a browser-level or agent-level authority layer for WebMCP, mandates expressed in the user's own words and parsed to scopes, and fingerprinted tool manifests so substitution is detectable across the boundary. The write-up and the argument live at crowley.nl/webmcp-challenge/ .
