Escape a lab together with AI through WebMCP, powered by Gua—my game UI testing and automation library for Godot and Unity. Like Comment Story Updates 1 Title image play scene image Inspiration WebMCP is usually discussed as a way for AI agents to interact with websites. I wanted to explore what would happen if that interaction extended into a game running in the browser: could a human and an AI enter the same game world, take on different roles, and complete a mission together? I have been developing Gua , a UI testing and automation library for Godot and Unity. Gua was created to make game UI tests easier to build. Its structured, reliable actions also provide a foundation for AI agents to interact with games. This project originally started as a sample game for demonstrating what Gua could do. For the WebMCP Challenge, however, I wanted to explore a more playful idea: what if a human and an AI could share the same game and work toward a common goal? That idea became AI Lovey-Dovey Kyun-Kyun!—a cooperative escape game in which a human player and an AI agent work together to escape from a laboratory. WebMCP exposes the game’s capabilities to the AI through the browser, while Gua connects those actions to the running game. What it does This is not a game where the AI only gives you hints. The human controls the field operative, while the AI observes authorized semantic and spatial state and operates designated control systems. They share one running game, but they have different information and abilities. By working together and taking actions in the game, you solve its puzzles and escape from the laboratory. To start playing, open the game in a WebMCP-enabled browser and tell your AI agent: Let's play this game together using WebMCP: https://link1345.github.io/gua-sample-actiongame/ The AI agent can then access the actions exposed by the game and join you in the escape. The AI does not rely on screenshots or visual guesswork. Through WebMCP and Gua, it can understand selected semantic information exposed by the game, such as the player’s position, distances to obstacles, the state of doors and hazards, and designated UI elements. The AI uses this structured information to assess the current situation, choose an appropriate action, and coordinate with the human player. The game controls exactly which information and actions are available to the AI, allowing it to participate as a game-world agent without exposing the entire internal state. How we built it I have been developing Gua, a UI testing and automation library for Godot and Unity inspired by Playwright's design principles. For this project, I extended Gua so that semantic game UI actions—such as pressing buttons and entering text—can be exposed through WebMCP and invoked by an AI agent. The game itself is built with Godot and exported as a regular web game. When it runs in the browser, WebMCP exposes the available actions to the AI agent, while Gua translates each requested action into an operation inside the running game engine. This architecture allows a human player and an AI agent to interact with the same game without rebuilding it as a conventional web application. Gua and its native Godot and Unity automation support existed before the challenge. During the submission period, I added the reusable WebMCP adapter, the Godot Web bridge, player-facing observation boundaries, browser validation, and this cooperative reference game. Challenges we ran into Before this project, Gua was designed primarily for automating native game builds. Adding WebMCP support was not simply a matter of exposing the existing testing API in a browser. A UI testing client may need detailed information about the entire interface. An AI agent playing a game, however, should receive only the state and actions intentionally made available to it. I therefore needed to support a new browser-facing interface while keeping the agent-facing surface limited and explicit. The solution came from Gua's existing architecture. Its core automation logic was already separated from its external interfaces, so I could add WebMCP as a new adapter and reuse the same semantic UI operations. The adapter exposes only the intended game actions and translates them into existing Gua operations, without spreading browser-specific code throughout the core library. As a result, the existing native automation behavior remained largely unchanged. This project became a practical test of Gua's architecture and showed that it could support a new AI-agent use case without requiring a major rewrite. Accomplishments that I'm proud of I am proud that this project produced more than a one-off WebMCP game integration. I added a reusable WebMCP path to Gua, allowing a Godot web game to expose selected semantic state and actions to an AI agent without rebuilding the game as a conventional HTML application or hard-coding every browser tool into the game itself. AI Lovey-Dovey Kyun-Kyun! demonstrates that architecture in a real cooperative experience. The human and AI share the same running game, but each has different information and abilities. The AI is not limited to offering advice from outside the game: it can observe authorized game state, operate designated systems, and coordinate directly with the player. I am especially proud of the deliberately narrow agent-facing surface. WebGL controls are not automatically exposed as browsable DOM elements, and Gua reveals only the semantic state and actions permitted by the game. Human-only controls can remain outside the agent-facing projection, while agent-specific actions do not need to appear in the visible interface. Raw input is disabled by default, further reducing unintended interaction paths. This is not a complete security sandbox, but it provides game developers with a practical capability boundary for AI participation. The result is both a playable human–AI cooperative game and a reusable foundation for exploring other agent-native experiences in game engines. What we learned Implementing WebMCP taught me that connecting an AI agent to a game involves more than simply registering browser tools. The more important challenge is designing the boundary between the game and the agent: deciding which game states the agent needs, which actions it should be allowed to perform, and how those actions should be described clearly. I also learned that Gua's semantic UI automation model maps naturally to WebMCP. Operations originally designed for automated testing—such as pressing a named button or entering text into a specific field—can also become structured tools that an AI agent can understand and invoke. This changed how I think about Gua. It is not limited to running UI tests; it can also act as an interaction layer connecting human players, AI agents, and games. Finally, adding this capability without a major rewrite demonstrated the practical value of keeping the automation core separate from game-engine and browser integrations. Building the game also showed how a growing game can expose more actions and world objects than an agent needs at one moment. To keep the interaction focused, I extended Gua so agents can narrow the available actions to their current situation and look only at nearby world objects. This demo has a small action set, but its AI can now focus on the doors, hazards, and mission areas around the field operator. Because these capabilities live in Gua’s reusable interaction layer, the same approach can scale to larger Godot and Unity games without redesigning their WebMCP integration. What's next for AI Lovey-Dovey Kyun-Kyun! This project is already available as an open-source Godot sample for Gua. Rather than developing it into a commercial title, I will maintain it as a small, reproducible reference implementation of a human–AI cooperative game built with WebMCP and Gua. Gua supports both Godot and Unity. This sample demonstrates the Godot Web integration, while the reusable semantic model provides a foundation for future WebMCP-enabled experiences across supported engines. PR #103 adds the fixed find_game_input_actions WebMCP tool. AI agents can search the currently authorized Semantic Game Action map by context, ID, description, aliases, value type, category, tags, and active state. This keeps the WebMCP tool surface stable instead of registering a separate browser tool for every possible game action. Private actions are excluded before filtering, and the latest descriptor is revalidated when an action is executed. PR #111 extends find_world_objects and wait_for_world_object with spatial radius queries. The AI can now request objects within a specified distance of an authorized reference object, optionally limit the result, and receive distance-ordered matches from one Player-projected world snapshot. In this demo, the AI can use the field operator as the reference object and retrieve only the nearby doors, hazards, and mission areas instead of reading the entire World Object Tree and calculating every distance itself. These additions do not change the game-specific WebMCP integration. The game continues to register Gua’s reusable WebMCP adapter, while the improved discovery and spatial-query capabilities are provided by the updated Gua runtime. This demonstrates how an existing game can gain more scalable agent capabilities by updating the shared automation layer rather than implementing new browser tools for each game.
