\n \n 1 2 3 4 5 \n\n\n\n \n Inspiration \n\n Returns sound simple, but the actual workflow is usually not. \n\n A customer asks, “Can I return this order?”, and suddenly a support operator has to find the order, read the right return policy, check the return window, look at the item condition, compare different resolutions, draft a response, and sometimes prepare an RMA. \n\n We wanted to explore what this workflow would look like if the website was designed not only for humans, but also for AI agents. \n\n Instead of asking an agent to read the page, guess which button to click, and simulate a human user, we wanted the website to expose its real capabilities directly. \n\n That is where WebMCP became a really good fit for the project. \n\n \n\n What it does \n\n Returns Desk is a WebMCP-powered returns workspace for small e-commerce teams. \n\n It exposes six WebMCP tools: \n\n \n search_orders \n get_return_policy \n check_return_eligibility \n compare_resolution_options \n draft_customer_message \n submit_rma_for_approval \n \n\n An agent can use these tools to move through a real returns workflow step by step. \n\n For example, a user can ask the agent to find order ORD-1001 , check whether it is eligible for return, and compare the available resolution options. \n\n The agent can then call the website tools directly instead of trying to operate the UI like a human. \n\n The main idea is simple: \n\n AI handles the repetitive work, while humans stay in control of important decisions. \n\n \n\n How we built it \n\n We built the frontend with React and TypeScript, and deployed the application with Cloudflare Workers. \n\n The WebMCP layer exposes the same business capabilities that already exist in the application, instead of creating a separate demo-only flow. \n\n That means the human-facing UI and the agent-facing tools are connected to the same returns logic. \n\n We also tried to keep the policy and eligibility logic as deterministic as possible. \n\n Instead of asking an LLM to freely interpret every return case, the application uses structured rules such as return windows, final-sale restrictions, item condition, and available resolution options. \n\n For write-related actions, we added an approval boundary so the agent can prepare a request without silently completing a consequential action. \n\n \n\n Challenges we ran into \n\n One of the biggest challenges was deciding what should actually become a WebMCP tool. \n\n At first, it is easy to think in terms of UI actions like “click this button” or “open this page”. \n\n But that would miss the point of WebMCP. \n\n We realized the tools should represent meaningful business capabilities instead, such as check_return_eligibility or compare_resolution_options . \n\n Another challenge was deciding where automation should stop. \n\n We wanted the agent to be genuinely useful, but we did not want it to silently perform important write actions. \n\n That led us to separate read and decision-support tools from approval-related actions. \n\n We also had to test the production site in a real WebMCP environment and make sure ChatGPT could actually discover the tools, not just see them in source code. \n\n \n\n Accomplishments that we're proud of \n\n We are especially proud that Returns Desk works as both a normal website and an agent-ready website. \n\n A human can still use the UI normally, but an AI agent can discover structured capabilities through WebMCP. \n\n We successfully exposed six WebMCP tools in the production site and verified that they can be discovered through ChatGPT Desktop Site Tools. \n\n We are also proud of the human-in-the-loop design. \n\n The agent can handle order lookup, policy retrieval, eligibility checks, resolution comparison, and preparation work, while important actions still remain reviewable by a human. \n\n Another thing we are proud of is keeping the demo safe and repeatable. \n\n The project uses isolated demo data, so no real payments, refunds, emails, shipments, or customer accounts are affected. \n\n \n\n What we learned \n\n The biggest thing we learned is that making a website “AI-ready” is not the same as adding a chatbot. \n\n The more interesting question is: \n\n What capabilities should the website expose so an agent can understand and use it reliably? \n\n WebMCP made us think much more carefully about tool design, schemas, responsibilities, and safety boundaries. \n\n We also learned that a good agent workflow depends heavily on the tools underneath it. \n\n Clear tools make the workflow easier to understand, test, and trust. \n\n This project also helped us connect a lot of engineering pieces together: frontend, backend logic, APIs, structured tools, deployment, and agent interaction. \n\n \n\n What's next for Returns Desk \n\n The current version is built around a deterministic demo returns workflow. \n\n The next step would be connecting it to real commerce infrastructure. \n\n Possible future integrations include: \n\n \n Shopify orders and inventory \n real return and refund systems \n shipping and return-label providers \n merchant-configurable return policies \n customer support platforms \n richer approval and audit workflows \n \n\n We would also like to explore more advanced agent workflows where an agent can handle most of the repetitive returns process while keeping merchants informed and in control. \n\n The long-term idea is to make Returns Desk an agent-ready operations layer for e-commerce returns, not just another support dashboard. \n\n \n\n \n Built With \n\n cloudflare d1 react typescript webmcp workers \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n
