Instead of manually choosing every option, a user could simply tell ChatGPT what they want and let the agent operate the existing website. \n\n What I built \n\n I added WebMCP support directly to the existing Hamburger Roulette website. \n\n The site now exposes three tools to ChatGPT: \n\n \n get_available_filters — returns the modes, templates, and tags supported by the site \n burger_spin — applies preferences and runs the existing roulette \n reroll_one — replaces only one result while keeping the others \n \n\n For example, a user can ask ChatGPT to generate three meal burgers, and ChatGPT can use the site's own roulette logic to produce the results. \n\n The user can then naturally ask to replace just one of the suggestions. \n\n How I built it \n\n The original application already had its roulette and filtering logic implemented in JavaScript. \n\n Rather than creating a separate API or duplicating that logic, I exposed the existing functionality through WebMCP using document.modelContext.registerTool() . \n\n This means the same application logic is used whether a person operates the website manually or ChatGPT operates it through WebMCP. \n\n The existing website remains fully usable in browsers that do not support WebMCP. \n\n Challenges and what I learned \n\n The biggest design question was deciding what should remain a human interaction and what should become an agent tool. \n\n Simply exposing a "spin" button was possible, but WebMCP became more useful when the agent could understand the available filters, translate natural-language preferences into those filters, and perform follow-up actions such as rerolling a single result. \n\n I also learned that WebMCP can be added incrementally to an existing website without rebuilding the application around AI. \n\n That was the most interesting part of this project: the website remains the source of its own functionality, while WebMCP gives an agent a structured way to use it.
