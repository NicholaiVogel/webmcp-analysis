Listing many is slow. Every garment needs identification, sizing, condition assessment, pricing, descriptions, images and publishing. The buyer side is just as messy: every item is one-of-one, sizing varies, condition is subjective, defects matter, and once an item is gone, it is gone. \n\n That makes recommerce a strong test case for agentic shopping. A buyer may not want to click through filters. They may simply ask: \n\n \n Find me a genuine black leather jacket around UK size 10, in excellent condition, under R1,200. Avoid faux leather and obvious defects. \n \n\n A normal storefront struggles with that kind of intent. A browser automation agent can try to infer meaning from the page, but it is still guessing from a human UI. \n\n Reloop asks a different question: \n\n What if commerce applications exposed trusted, page-defined capabilities directly to AI agents while still requiring explicit human approval for consequential actions? \n\n For the WebMCP Challenge, we built a focused public implementation of that idea. \n\n \n\n What it does \n\n Reloop is a reference implementation for trustworthy AI commerce using WebMCP. \n\n It demonstrates a complete human-agent commerce flow: \n\n \n The agent discovers the tools exposed by the page. \n The user describes what they want in natural language. \n The agent searches deterministic one-of-one inventory. \n It inspects item details such as material, size, condition, price, defects and availability. \n It compares candidates and recommends the best match with supporting evidence. \n The human explicitly approves the exact item in natural language. \n Only then can the write-path reservation tool change demo state. \n The storefront updates visibly. \n \n\n The demo is intentionally narrow: a recommerce storefront with synthetic inventory. The underlying pattern is broader: read and reasoning actions can be agent-friendly, while write actions remain application-controlled and human-approved. \n\n \n\n Why WebMCP is a strong fit \n\n Most AI web interactions still depend on fragile patterns: \n\n \n the agent reads arbitrary HTML and guesses what the page means \n the agent clicks through a UI designed for humans \n the app has little control over which actions are safe or intended \n \n\n WebMCP changes the boundary. \n\n In Reloop, the page explicitly registers meaningful commerce capabilities. The agent does not need to scrape the storefront or invent a workflow. It discovers tools that represent the actual tasks a buyer needs: \n\n \n search_inventory \n inspect_item \n find_best_match \n compare_items \n recommend_alternatives \n reserve_item \n \n\n Those tools are not generic database operations. They are application-level capabilities that map to shopping intent. \n\n That is why WebMCP matters here: it lets the website describe what an agent can do, while the application keeps authority over business logic, validation and state changes. \n\n \n\n Better user experience \n\n For the human, Reloop turns a messy search into a guided conversation. \n\n Instead of filtering by imperfect categories, the user can describe the outcome they want. The agent can then do the tedious work: search, inspect, compare, eliminate poor matches and explain why one item is the strongest choice. \n\n For the agent, the experience is also better. It receives structured tool responses rather than trying to interpret visual layout, DOM fragments or arbitrary copy. \n\n For the application, the experience is safer. The app decides which capabilities exist, how inputs are validated, what evidence is returned, and when a write action is allowed. \n\n The result is not autonomous shopping for its own sake. It is a collaboration: \n\n the agent reasons, the application enforces, and the human decides. \n\n \n\n What people and agents can do together now \n\n Reloop shows a workflow that is difficult to do well with a normal storefront alone: \n\n \n express nuanced buyer intent in natural language \n evaluate one-of-one inventory with inconsistent attributes \n compare items on fit, condition, material, price and defects \n preserve the evidence behind a recommendation \n keep the human in control of irreversible actions \n update application state only after explicit approval \n \n\n That last point matters. \n\n The agent is allowed to search, inspect, compare and recommend freely. But reservation is different. reserve_item is the write path, so it requires explicit natural-language approval for the exact SKU in the tool request. A vague instruction such as “Reserve RL-001” is rejected. Approval language such as “I approve RL-001. Please reserve RL-001 for me.” allows the reservation only if the item exists and is still available. \n\n The live deployment has been retested with this boundary: “Reserve RL-001.” returns an approval-required response without changing state. “I approve RL-001. Please reserve RL-001 for me.” succeeds and changes the storefront from 23 → 22 available with RL-001 AVAILABLE → RESERVED . \n\n \n\n How we implemented WebMCP \n\n The public challenge repository contains a focused Next.js implementation of the WebMCP layer. \n\n The demo registers six Reloop Site Tools using document.modelContext.registerTool(...) . Each tool exposes a specific commerce capability to the client. The matching and reservation logic remains separate from the protocol boundary so the WebMCP layer acts as the agent-facing interface, not the entire application. \n\n The implementation includes: \n\n \n a Next.js demo shell \n deterministic synthetic inventory \n recommerce matching and reservation logic \n WebMCP tool registration \n explicit approval validation for the write-path reservation tool \n a human-visible storefront state \n focused tests and verification commands \n an AGPLv3 open-source license \n \n\n The repository README documents the architecture, tool flow, human approval boundary, local setup and verification path. \n\n \n\n Challenges we ran into \n\n The hardest design challenge was deciding what the tools should represent. \n\n It would have been easy to expose low-level CRUD functions, but that would not show the real promise of WebMCP. We wanted the agent to work with commerce intent, not database plumbing. \n\n The second challenge was trust. \n\n A shopping assistant that can reserve items without the user’s clear approval is not a better experience. It is just a faster way to make mistakes. We deliberately separated read/reasoning actions from write actions so the agent can help without silently committing the user to an outcome. \n\n The final approval-boundary fix was important: the first implementation used a visible storefront approval gate. The stronger version now validates explicit natural-language approval for the exact SKU inside the reserve_item tool request itself. That keeps the agent-commerce UX conversational while still making the safety boundary application-enforced. \n\n The third challenge was scope. \n\n Reloop could become a much larger product, but this challenge needed a tight, inspectable implementation. We chose a deterministic synthetic storefront so judges can reproduce the same flow, evaluate the WebMCP behavior, and inspect the code without relying on private systems or real customer data. \n\n \n\n Accomplishments that we’re proud of \n\n We are proud that Reloop is more than a technical proof of concept. \n\n It demonstrates a coherent product experience: \n\n \n live hosted demo \n public open-source repository \n discoverable WebMCP tools \n natural-language shopping flow \n evidence-based recommendation \n comparison against alternatives \n explicit natural-language approval for the exact SKU \n application-enforced write boundary \n visible state change in the storefront \n deterministic data and verification commands \n \n\n Most importantly, it shows a reusable pattern for agentic commerce: applications can expose structured capabilities to agents without giving up control of safety-critical actions. \n\n \n\n What we learned \n\n The biggest learning was that preparing inventory for AI-assisted selling also prepares it for AI-assisted buying. \n\n Structured item data is useful twice: \n\n \n It helps sellers turn messy physical inventory into usable listings. \n It helps buyer agents reason over unique items with evidence. \n \n\n WebMCP made that second half more concrete. Instead of treating a website as a surface to be scraped, we could treat it as an intentional collaboration layer between the human, the agent and the application. \n\n We also learned that the most interesting part of agentic commerce is not the final transaction. It is the trust boundary before the transaction: the agent can help the user reach a decision, but the application must enforce what counts as explicit approval before changing state. \n\n \n\n What’s next for Reloop \n\n The challenge implementation is intentionally scoped, but the pattern can extend far beyond this demo. \n\n The same architecture could apply to: \n\n \n recommerce marketplaces \n rentals \n ticketing \n bookings \n travel \n procurement \n other approval-sensitive workflows \n \n\n The next step would be connecting the agent-facing shopping layer to the broader Reloop seller workflow, so newly processed second-hand inventory can become discoverable by both humans and agents. \n\n Longer term, Reloop points toward a version of the web where agent accessibility is not retrofitted through scraping or browser automation, but designed directly into the application. \n\n Reloop is one-of-one commerce, ready for people and their agents. \n\n \n\n \n Built With \n\n agplv3 next.js node.js pnpm react typescript vercel webmcp zod \n \n\n \n Try it out \n\n \n \n \n reloop-webmcp.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n Founder and builder.
