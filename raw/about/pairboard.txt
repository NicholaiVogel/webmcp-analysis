Agents can already drive that UI, but they do it by guessing at buttons. WebMCP flips that. A page can expose the same capabilities as tools — document.modelContext.registerTool , getTools , executeTool — so an agent uses the site the way a developer would use an API, while a person still uses the normal interface. \n\n TaskRabbit is the perfect test of that idea. A move-in is never one listing. It is furniture assembly, cleaning, and TV mounting, coordinated under a budget, with a human still in the loop before anything is booked. We wanted a marketplace that looks like a real service site and behaves like an MCP server in the browser. \n\n What it does \n\n TaskFlow is a dual-use TaskRabbit-style marketplace. \n\n For people: browse services, compare Taskers, and book from a profile — search, listings, hourly rates, availability, confirm. \n\n For agents: the same pages register WebMCP tools ( searchServices , findTaskers , getTaskerAvailability , getTaskerPricing , createTaskRequest , scheduleTask , …). An in-page agent dock takes an outcome like “I just moved in. Make my home ready tonight. I have a $250 budget.” It discovers those tools, builds a plan (Marcus $85, Sarah $95, David $60 = $240), and waits for approval before it schedules. \n\n Both paths write to the same booking store. My Tasks shows You booked next to Booked by agent . One website, two clients, one set of capabilities. \n\n How we built it \n\n \n Next.js App Router , TypeScript, Tailwind, and shadcn/ui — no backend, no real payments, no live TaskRabbit API. \n A shared marketplace layer ( search , findTaskers , pricing, create/schedule). Human buttons call those functions. WebMCP execute callbacks wrap the same functions. \n A spec-faithful document.modelContext polyfill so the demo runs in current browsers, using the official WebMCP shape if the native API exists. \n A deterministic planner (no LLM) so the killer demo is reliable, with staged delays so the tool activity is visible. \n A TaskRabbit-like light marketplace plus a dark agent dock that keeps Show WebMCP on screen for judges. \n \n\n Challenges we ran into \n\n WebMCP is still a draft. Most browsers do not ship document.modelContext , so we had to match the spec closely without pretending the API is everywhere. \n\n The harder product problem was not building another chatbot. The original instinct was an AI-only command center. That hid the point. WebMCP only lands if the human site is real and the agent uses that site’s tools — not a parallel fake API. \n\n Shared state was picky too: a full navigation wiped in-memory bookings until we persisted them and tagged each row by source ( human | agent ). Tool registration also had to survive hot reload without double-registering names. \n\n Accomplishments that we're proud of \n\n \n A 2–3 minute demo where you book Marcus as a person, then let the agent plan a $240 move-in, and both appear on My Tasks . \n Judges can see WebMCP: live getTools / executeTool calls, not a hidden prompt. \n Human-in-the-loop: the agent never books until Approve & Schedule . \n One implementation for both audiences — not two products glued together. \n \n\n What we learned \n\n Agent-native websites are not “add a chat sidebar.” They are capability design : the same operations must be safe, named, and schema’d for a model and obvious in a UI for a person. \n\n We also learned why the spec cares about annotations ( readOnlyHint , untrustedContentHint ) and approval. Tool descriptions are easy to trust too much. Keeping consequential actions behind a human confirm is the product, not a footer. \n\n What's next for TaskFlow \n\n \n Native WebMCP in a supporting browser, dropping the polyfill on that path. \n Declarative tools from real forms, as the spec’s declarative section lands. \n A real LLM planner behind the same tools, with the deterministic demo kept as a fixture. \n Richer trust UX: show which origin registered a tool, and treat tool output as untrusted when the hint says so. \n \n\n TaskFlow’s bet is simple: the next marketplace is designed for both hands and agents. \n\n \n\n \n Built With \n\n javascript mcp next.js radix react shadcn/ui tailwind vite webmcp \n \n\n \n Try it out \n\n \n \n \n taskflow-psi-seven-66.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Khalil HAIF \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Khalil HAIF \n started this project\n \n —\n \n a day ago \n \n \n\n
