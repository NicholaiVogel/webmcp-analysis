A local-first visual analytics workspace where humans and WebMCP-connected AI agents explore shared data and make visible changes in the same live canvas. Like 1 Comment Story Updates Demo with Bar Chart Demo with Donut Chart Demo with Matrices and Line Chart Inspiration I started Data Canvas with a simple question: what would an analytics app look like if an AI agent worked inside the workspace instead of through a separate chat, API, or UI automation layer? I wanted one thing to stay true throughout the project. If an agent creates a chart, I should see it and keep working with it. If I change a filter, the agent should see that change on its next action. We should not end up with two versions of the analysis. That idea became Data Canvas. What it does Data Canvas is a local-first visual analytics workspace for exploring data in the browser. You can import CSV, TSV, JSON, and NDJSON files, inspect the data, build charts, filter and transform it, create metrics, connect datasets, make selections, add annotations, and undo or redo changes. A WebMCP-connected AI agent works with the same workspace. It can inspect a dataset, analyze it, create or update a visualization, apply filters, highlight data, define metrics, add annotations, and more. Its changes appear directly on the canvas, alongside the work done through the UI. The data and analytical engine run in the browser with DuckDB-Wasm. Data Canvas has no application backend, cloud database, authentication service, or built-in LLM. How I built it The most important architectural decision was to give the UI and WebMCP the same path into the application. Both go through one action dispatcher. A chart created through WebMCP is a normal Data Canvas visualization. A filter created by an agent is the same filter the UI understands. Undo and redo work across actions from either side. DuckDB-Wasm owns the imported rows and runs the analytical queries. Zustand holds workspace state and history. React renders the interface, and ECharts renders the visualizations. The WebMCP layer currently defines 19 semantic tools around real Data Canvas operations. Agents can ask the application to analyze data, create a visualization, apply a filter, define a metric, or connect datasets. They cannot submit arbitrary SQL, JavaScript, DOM selectors, or ECharts configuration. Challenges I ran into The hard part was not registering WebMCP tools. It was making sure I did not build the application twice, once for humans and again for agents. That affected a lot of small decisions. Agent writes carry the workspace revision they observed, so an outdated action cannot overwrite newer human work. Human and agent actions also use the same domain rules instead of maintaining separate implementations. Data access needed the same care. Dumping an entire dataset into every agent call would defeat much of the point of a local-first analytics app. The tools instead expose schemas, statistics, aggregates, bounded previews, and the data needed for a particular analysis. Accomplishments that I'm proud of I'm most proud of the human-agent equivalence in the application. The codebase tests equivalent operations through the human and WebMCP paths and checks that they produce the same workspace state. Agent-created objects remain normal workspace objects, stale writes are rejected, and undo can reverse changes made by either side. I also like that none of this required adding an AI backend to Data Canvas. The application remains a browser-native analytics tool on its own. WebMCP gives an external agent a structured way to participate in it. What I learned I originally thought a capable agent would need very powerful tools. Building Data Canvas pushed me in the opposite direction. The useful tools turned out to be the ones that match operations the application already understands. create_visualization , apply_filter , or create_metric give the agent enough control to do real work while keeping the result valid, visible, and editable in Data Canvas. For me, that is the interesting part of WebMCP. The agent does not need to learn how to click through the interface when the application can expose what those controls actually mean. What's next for Data Canvas The biggest missing piece is local persistence. The current workspace lives in memory, so a reload starts a new session. Next, I want to persist complete workspaces locally and make them portable between browsers while keeping Data Canvas backend-free. I also want to extend the agent evaluations to longer workflows where a human and an agent repeatedly hand the analysis back and forth.
