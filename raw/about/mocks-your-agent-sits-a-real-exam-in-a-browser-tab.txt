Like Comment Story Updates How I switch my ChatGPT's MBTI. lol ChatGPT gets better result without using tools Inspiration There are so many AI tools and agents, we don't know which one to choose. And most people are not researchers. I'm not either. I build things. The evaluation that exists is expensive and heavy for us normal people. I don't need an academic, precise number. But I don't want to vibe-pick my AI either. I need to answer, for my task, in a practical way: the expensive model, or the cheap one, or a mix? another skill, or a better prompt? more tools, or fewer? And I need the answer written down. AI isn't like software. When a change breaks software, you find out straight away and roll back. When a change makes an agent worse, you find out weeks later, and by then you've forgotten which version was the good one. WebMCP is what makes this light enough to actually use. If the benchmark is a web page, and the page hands the agent its tools, then the agent you already have sits the exam directly. Nothing to install, nothing to log into, no API key. What it does mocks puts 15 live benchmarks in a browser tab. Open one, tell your agent to sit it, and watch it work. Each answer is scored by that task's own judge.py , fetched from the exact commit its leaderboard grades against and run unmodified in the browser. Not a copy of the scoring. Name the setup you're running, and the result goes on the board under that name. Run it again with one thing changed, and you have a comparison you can still read in a month. How we built it Six WebMCP tools. start_run , get_next_case and submit_answer run the exam. list_case_files , search_pdf_text and read_pdf_page_text exist because one task's answers are inside a 17-page PDF. They exist because the page is open — not because you installed anything. You get them by visiting a URL and lose them by leaving. get_next_case hands over the question and nothing else. The page holds every expected answer, because the judge can't run without them, and never lets them out. submit_answer returns recorded: true — not whether the case passed. On a 23-case task a per-case mark isn't a verdict, it's feedback for the next answer. There is no per-task code anywhere in this repo. Every task ships the same contract, so a task published tomorrow works the day it lands. Today that is 12 of 15 tasks and 297 cases. The three refusals are worked out from each task's own judge, not from a list we wrote. Two of them are graded on what the solution says about itself, backed by a video, and typed into an anonymous page that would be a claim rather than a result. Challenges we ran into Every real bug was the same one: we assumed something the data doesn't actually guarantee. And the fake data in our tests was tidier than the real thing, so the tests passed. The scoring scripts don't say "passed". They print a number — 1.0, or 0.4. We assumed they also printed a true/false. None of the 53 do. So the page put FAILED next to every correct answer, while the overall grade right beside it said passed. The database gives times back as dates, not text. We sorted the board by time, comparing them as text. With one run on the board there's nothing to sort, so it looked fine. The second run crashed the page. The database doesn't keep the order things were written in. The MBTI scoring script prints several things — the four-letter type, the percentages, and a label saying what kind of task it is: "personality". We showed the first one. The database reorders by name length, so "personality" came out first, and the board announced a model's personality type as "personality". Accomplishments that we're proud of A task's own judge.py runs in the browser, unmodified. Not a port, not a reimplementation — the same file its leaderboard grades with, fetched from the same commit and executed in Pyodide. That's what makes a score here mean the same thing it means there. You can watch it work. Every tool call the agent makes lands on the page as it happens — took the case, found the document, opened page nine, committed to a number. The page never touches the model. It only writes down what came through its own front door. What we learned The site measured our own tools and found them wanting. On the PDF task, GPT-5.6 scored 14 of 23 using the text tools we built. We ran it again and told it to ignore those PDF tools and just open the PDF and look. It scored 17 . The gain wasn't spread out. Every question that needed reading a length off a chart went from failed to passed, all three! So the page stopped recommending those tools for chart questions. They're still there, because they're the right instrument for the other PDF task, which is all tables. But a value plotted in a figure isn't text, and no amount of text extraction will find it. That is the site doing the job it exists to do, on itself. What's next for mocks — your agent sits a real exam, in a browser tab Server-side judging. Worth saying, because the whole point is that a number should mean what it says it means. Judging happens in your browser. The page runs judge.py client-side and then posts the result. So the board records what a browser claimed it scored. A curl can post a perfect score without answering anything. The fix is server-side judging, but we ran out of time for this challenge. Then sign-in , so a name on the board means something. Then per-case views — which cases a change broke, not just whether the average moved.
