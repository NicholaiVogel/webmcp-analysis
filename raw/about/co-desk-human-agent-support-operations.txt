Operations \n\n The idea \n\n Co-Desk is a human + agent support desk : a single live ticket queue that a person and an AI agent operate together , in real time, over WebMCP. \n\n Why WebMCP \n\n Before WebMCP, an agent helping with a real web workflow could only navigate the page and click — slow, brittle, and hard to verify. Co-Desk inverts this: instead of the agent guessing at our UI, the site declares its own operations as structured tools the agent can call. A person opens the app and works; an agent discovers those tools and acts inside the real workflow. \n\n What people and agents can do together now \n\n A support team can hand the agent the whole routine workload — opening requests, adding notes, routing to teams, escalating, resolving the mechanical cases — while the human watches the same screen update live and owns the judgment calls. One shared queue, two operators, with the human always in the loop. That is the collaboration WebMCP makes possible. \n\n How we built it \n\n \n 10 WebMCP tools ( listOpenTickets , getTicket , createTicket , addNote , updateStatus , assignToTeam , escalateTicket , resolveTicket , searchTickets , summarizeQueue ), each with a JSON Schema and real effects on a shared store. \n Every action — human or agent — is written to one localStorage store and rendered live, so the queue and an activity feed update on screen. \n Plain HTML/CSS/JS, no build step — trivially deployable. \n \n\n Registration is done against document.modelContext : \n await document . modelContext . registerTool ( { \n name : "resolveTicket" , \n description : "Resolve a ticket with a short resolution summary." , \n inputSchema : { \n type : "object" , \n properties : { \n ticketId : { type : "string" } , \n resolution : { type : "string" } , \n } , \n required : [ "ticketId" , "resolution" ] , \n } , \n execute : async ( input ) = > { /* real action on the shared queue */ } , \n } ) ; \n \n Challenges \n\n The hardest part was keeping one source of truth. Tools and the human UI both mutate the same queue, so we made them share one store and one change-notification path. That guarantees an agent's action and a human click are never out of sync. \n\n Try it \n\n Open the live URL in ChatGPT's in-app browser or Chrome with WebMCP enabled, then ask the agent: "Summarize the queue, then handle the password-reset ticket — add a note, route it to account, and show me before resolving." \n\n \n\n \n Built With \n\n agent chrome css html human-in-the-loop javascript localstorage web-api webmcp \n \n\n \n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Kitematic-AI Maghaireh \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Kitematic-AI Maghaireh \n started this project\n \n —\n \n 2 days ago \n \n \n\n
