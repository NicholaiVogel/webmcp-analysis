Modern DevOps teams have powerful monitoring tools, dashboards, CI/CD systems, cloud consoles, logs, and AI assistants, yet incident recovery is still fragmented. \n\n When production fails, engineers jump between alerts, logs, GitHub, Kubernetes, deployment dashboards, runbooks, and communication tools while downtime continues. \n\n DevPilot AI was originally built to compress this workflow into a human-approved AI incident recovery platform. \n\n The WebMCP Challenge gave me the opportunity to take the next step: make DevPilot not only usable by humans, but directly understandable and operable by AI agents. \n\n Instead of forcing an agent to visually navigate a complex DevOps dashboard, DevPilot WebMCP exposes structured tools that clearly describe what an agent can inspect and what actions it can request. \n\n The goal is a web application where the developer and their AI agent can investigate and resolve production incidents together. \n\n What it does \n\n DevPilot WebMCP is an agent-native DevOps control plane for detecting, diagnosing, and recovering from production incidents. \n\n The existing DevPilot platform already brings together infrastructure alerts, deployment failures, logs, incident memory, AI diagnosis, remediation planning, GitHub workflows, and human-approved recovery actions. \n\n For the WebMCP Challenge, DevPilot is being extended with structured WebMCP tools for agent interaction. \n\n The WebMCP interface is designed around capabilities such as: \n\n \n Analyze application and infrastructure incidents \n Inspect service and deployment health \n Diagnose likely root causes \n Retrieve incident context and historical information \n Generate structured remediation plans \n Explain why a deployment failed \n Prepare recovery actions \n Verify system health after remediation \n \n\n This means a developer can work with an AI agent through natural language while the agent interacts with DevPilot through explicit structured tools instead of guessing how to click through the interface. \n\n A workflow can look like: \n\n \n A production problem is detected. \n The developer asks their AI agent to investigate it. \n The agent discovers DevPilot's available WebMCP tools. \n DevPilot returns structured incident and infrastructure context. \n The agent requests a diagnosis and remediation plan. \n DevPilot presents the proposed action to the human. \n The human reviews or approves the action. \n DevPilot verifies recovery and records the result. \n \n\n The human remains responsible for high-impact actions while the agent handles investigation, information gathering, and repetitive operational work. \n\n Why WebMCP \n\n DevOps applications are an especially strong fit for WebMCP because their interfaces can contain dozens of dashboards, tables, alerts, logs, buttons, and operational workflows. \n\n A traditional browser agent has to interpret these visual interfaces and infer what each element means. \n\n WebMCP lets DevPilot expose the underlying capabilities directly. \n\n Instead of an agent searching the screen for an incident and guessing which controls to use, it can discover a structured tool such as an incident-analysis or service-health capability with a defined schema. \n\n This makes agent interactions more reliable, explainable, and efficient. \n\n Most importantly, WebMCP allows the human-facing application and the agent-facing interface to exist together. \n\n Humans keep the rich visual operations cockpit. \n\n Agents receive precise structured tools. \n\n Together they can perform workflows that would otherwise require engineers to manually gather information from many different systems. \n\n How I built it \n\n DevPilot is a full-stack AI DevOps platform. \n\n The frontend is built with Next.js and React and provides the operations cockpit used by developers. \n\n The backend is built with Python and FastAPI and handles incident workflows, AI analysis, authentication, persistence, and external integrations. \n\n Neon PostgreSQL provides persistent storage. \n\n OpenAI is used for AI-assisted diagnosis and remediation workflows. \n\n GitHub integration supports development and remediation workflows, while the platform also contains production monitoring, CI/CD checks, Docker support, and infrastructure-oriented recovery capabilities. \n\n For the WebMCP Challenge, I am extending the web application using the WebMCP API so the browser can register DevPilot capabilities as structured agent tools. \n\n Each WebMCP tool is designed with: \n\n \n A clear tool name \n A precise description \n Structured input schemas \n Restricted operational scope \n Predictable outputs \n Human approval for sensitive actions \n \n\n The challenge-specific implementation is being developed after the WebMCP Challenge start date and documented separately in the repository and commit history. \n\n Human + Agent Collaboration \n\n DevPilot is intentionally not designed to remove engineers from incident response. \n\n The agent handles tasks that are expensive for humans but safe to automate: \n\n \n Gathering context \n Reading health information \n Correlating incident signals \n Identifying likely root causes \n Retrieving previous incident knowledge \n Preparing remediation plans \n \n\n The human remains in control of consequential infrastructure actions. \n\n This creates a workflow where the AI agent acts like an extremely fast operations investigator while the engineer acts as the decision maker. \n\n WebMCP is the bridge that makes this collaboration reliable. \n\n Challenges I ran into \n\n One of the biggest design challenges is deciding what should become an agent tool and what should remain a human-controlled action. \n\n DevOps systems can affect real infrastructure, so simply giving an agent unrestricted operational access would be unsafe. \n\n The WebMCP layer therefore needs narrowly scoped tools, explicit schemas, predictable responses, and approval boundaries. \n\n Another challenge is converting information that was originally optimized for visual dashboards into structured results that agents can reason about reliably. \n\n The final challenge is preserving the existing human experience while introducing a second, agent-native interaction layer without duplicating the entire application. \n\n Accomplishments that I'm proud of \n\n I am proud that DevPilot already functions as more than a chatbot. \n\n It is a working DevOps control plane connecting incident signals, AI diagnosis, remediation planning, monitoring, deployment workflows, and human approval. \n\n The WebMCP extension evolves that architecture further by allowing AI agents to interact with the same operational capabilities through a purpose-built machine interface. \n\n Rather than redesigning the application only for AI, the project explores a web where humans and agents have interfaces designed specifically for each of them while sharing the same underlying application. \n\n What I learned \n\n Building DevPilot has taught me that useful AI systems need more than model responses. \n\n They need structured context, predictable tools, observability, permissions, validation, and clear human control. \n\n WebMCP introduces another important principle: websites should not require AI agents to reverse-engineer their interfaces. \n\n If applications can explicitly describe what agents are allowed to do, agent interactions can become significantly more reliable. \n\n What's next for DevPilot WebMCP \n\n The next step is expanding DevPilot's WebMCP interface into a complete agent-native operations API for the browser. \n\n Future capabilities could include: \n\n \n Repository and CI/CD investigation \n Kubernetes health analysis \n Deployment rollback planning \n Infrastructure drift investigation \n Security incident triage \n Cost anomaly analysis \n Multi-agent incident collaboration \n Persistent incident memory \n Organization-level policy and approval controls \n \n\n The long-term vision is for DevPilot to become an operations environment where engineers and AI agents continuously collaborate to keep software reliable. \n\n What it does \n\n How we built it \n\n Challenges we ran into \n\n Accomplishments that we're proud of \n\n What
