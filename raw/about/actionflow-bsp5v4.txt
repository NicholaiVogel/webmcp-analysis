today stop at giving answers . We wanted to build something that could actually help users accomplish tasks on the web . \n\n Our biggest inspiration was the idea that WebMCP should be a first-class part of the product , rather than something added at the end just to say that the project uses MCP. \n\n We imagined a system where a user can describe a goal in natural language, and an AI agent can discover the capabilities available through WebMCP, plan the necessary steps, execute them, and keep the user in control of important actions. \n\n That led us to ActionFlow : an AI-powered web agent designed around the principle of: \n\n \n Tell it what you want accomplished, not which buttons to click. \n \n\n \n\n What it does \n\n ActionFlow converts natural-language goals into actionable workflows. \n\n A user can give ActionFlow a request such as: \n\n \n “Find the best Java development internships for me, compare the opportunities, and prepare the applications for the top matches.” \n \n\n ActionFlow then: \n\n \n Understands the user's objective. \n Breaks the objective into smaller tasks. \n Discovers and selects appropriate WebMCP capabilities. \n Collects and analyzes information. \n Compares and ranks results. \n Builds an execution plan. \n Requests user approval before consequential actions. \n Executes approved actions through WebMCP. \n Verifies the result. \n Records the complete workflow in an activity log. \n \n\n The application also provides a WebMCP Tool Explorer , allowing users and judges to see exactly which capabilities the agent is using. \n\n \n\n How we built it \n\n ActionFlow is built as a full-stack application with an AI-agent layer at its center. \n\n Frontend \n\n We built the interface using: \n\n \n React \n TypeScript \n Vite \n Tailwind CSS \n \n\n The frontend provides the command center, agent execution view, approval interface, WebMCP tool explorer, and activity history. \n\n Backend \n\n The backend is designed around: \n\n \n Java \n Spring Boot \n REST APIs \n PostgreSQL \n Real-time agent execution updates \n \n\n The backend manages users, tasks, workflows, tool execution, approvals, and activity logs. \n\n AI Agent \n\n The agent follows a structured workflow: \n\n Understand → Plan → Discover → Execute → Observe → Reason → Verify \n\n Rather than hard-coding a sequence of UI interactions, the agent can select the appropriate capabilities based on the user's objective. \n\n WebMCP \n\n WebMCP is the key part of ActionFlow. \n\n We expose meaningful capabilities such as: \n\n \n search_web \n extract_information \n compare_results \n analyze_requirements \n create_plan \n request_approval \n execute_action \n verify_result \n \n\n This makes WebMCP part of the application's core architecture , rather than a superficial integration. \n\n Safety \n\n ActionFlow also uses an approval layer. \n\n The agent can research and prepare actions autonomously, but potentially consequential actions require explicit user approval. \n\n \n\n Challenges we ran into \n\n One of our biggest challenges was deciding where WebMCP actually provides value . \n\n It would have been easy to build a conventional web application and expose a few functions as MCP tools. However, that would not demonstrate the real potential of the technology. \n\n We therefore had to rethink the architecture around capabilities rather than pages and buttons . \n\n Other challenges included: \n\n \n Designing useful high-level WebMCP tools. \n Coordinating multiple tool calls within one workflow. \n Maintaining state across multi-step tasks. \n Handling failures and unexpected tool results. \n Designing approval points without making the experience frustrating. \n Making the agent's actions understandable to the user. \n Keeping the architecture flexible enough to add new capabilities later. \n \n\n The hardest conceptual challenge was balancing autonomy with control : the agent should be capable of accomplishing meaningful tasks while the user remains in charge of consequential decisions. \n\n \n\n Accomplishments that we're proud of \n\n We're especially proud that WebMCP isn't simply an additional feature in ActionFlow. \n\n It is part of the fundamental interaction model . \n\n We created a workflow where: \n\n \n Natural language → AI planning → WebMCP capabilities → real actions → verification \n \n\n We are also proud of the transparency of the system. \n\n Instead of hiding what the AI is doing, ActionFlow exposes the workflow through its activity log and tool explorer. \n\n Users can see: \n Understanding request\n ↓\nPlanning workflow\n ↓\nDiscovering WebMCP capabilities\n ↓\nExecuting tools\n ↓\nAnalyzing results\n ↓\nRequesting approval\n ↓\nExecuting approved action\n ↓\nVerifying result\n \n This makes the system easier to understand, debug, and trust. \n\n \n\n What we learned \n\n We learned that building an agentic application is very different from building a traditional web application. \n\n A traditional application generally follows: \n\n \n User → UI → API → Database \n \n\n ActionFlow follows a much more dynamic model: \n\n \n User → Goal → Agent → Capabilities → Results → Reasoning → Action \n \n\n We also learned that tool design matters as much as model intelligence . \n\n Giving an agent poorly designed tools can make an otherwise capable agent ineffective. High-level, well-defined capabilities allow the agent to reason about what it can accomplish rather than simply reproduce a predefined workflow. \n\n Most importantly, we learned that WebMCP becomes significantly more interesting when it is treated as an interface between an intelligent agent and real web capabilities , rather than merely another API format. \n\n \n\n What's next for ActionFlow \n\n ActionFlow is designed to grow into a general-purpose web task orchestration platform . \n\n Our next steps include: \n\n More WebMCP capabilities \n\n Add specialized tools for: \n\n \n Research \n Shopping \n Travel \n Education \n Developer workflows \n Job and internship discovery \n Productivity \n \n\n Multi-agent workflows \n\n Different specialized agents could collaborate: \n Research Agent\n ↓\nAnalysis Agent\n ↓\nPlanning Agent\n ↓\nExecution Agent\n ↓\nVerification Agent\n \n Personalization \n\n ActionFlow could learn user preferences, constraints, and recurring workflows while keeping the user in control of their data. \n\n Better verification \n\n Future versions will automatically verify whether an action actually achieved its intended outcome instead of assuming successful execution. \n\n Workflow marketplace \n\n Eventually, users could discover and share reusable ActionFlow workflows for common tasks. \n\n The bigger vision \n\n Our long-term goal is simple: \n\n \n Turn the web from something users manually navigate into something AI agents can safely and meaningfully operate on their behalf. \n \n\n ActionFlow is our first step toward that vision. \n\n \n\n \n Built With \n\n api \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n T R Ajay Dharrsan \n \n
