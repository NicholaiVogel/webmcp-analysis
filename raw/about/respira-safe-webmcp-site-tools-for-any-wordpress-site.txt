Respira already gives agents safe, structured access to WordPress through MCP: 319 tools, staged edits, approvals, rollback. So the question wrote itself: what happens when the agent is not on the other end of a connector, but standing on the same page as you? What it does Open a Respira-powered WordPress site inside ChatGPT's browser and sign in. The page registers a curated set of site tools on document.modelContext : read the site's context, list and read pages, stage an edit as a reviewable duplicate, approve or reject it , audit SEO and readability, find and fix WooCommerce catalog gaps. Every staged draft also returns a tokenized preview link, so the proposed change can be shown to someone with no WordPress login. The agent-only tools are the point. Approve-duplicate and reject-duplicate would be meaningless as buttons, but as site tools they give the agent a safe write path with a human approval gate, on the page you are both looking at. Nothing goes live without a yes, and everything rolls back. How i built it WordPress has an Abilities API, and an open-source bridge ( code-atlantic/webmcp-abilities , GPL) that maps abilities to WebMCP tools. Respira registers its production tool catalog as abilities, the bridge exposes them to the page, and a REST layer executes them with WordPress's own authentication and per-tool permission callbacks. The patched, working bridge is open source at respira-press/webmcp-for-wordpress . Challenges i ran into The bridge had never actually worked in a real agent browser, and finding out why became the project. Four bugs, each masking the next: Discovery ran as an anonymous visitor. The tools fetch sent cookies without WordPress's REST nonce: 401, zero tools registered, on every default-configured site. Execution died at WordPress core's door. The bridge put its CSRF token in the header core reserves for its own nonce, so core rejected every call before the handler ran. ChatGPT's modelContext is a frozen object implementing only registerTool . The bridge's batch provideContext call threw silently and nothing registered. Ability names contain a slash that stock Apache rejects when URL-encoded , so execution 404ed on every Apache host. i debugged blind inside ChatGPT's browser with an on-page diagnostic badge: a screenshot from inside the agent browser was the only ground truth. Then one more wall: 296 registered tools tripped ChatGPT's per-page limit and disabled WebMCP for the document entirely. The fix was editorial, not technical: a curated, page-scoped set of ~30 tools. Accomplishments i am proud of As far as i can tell, this is the first WordPress site with working WebMCP site tools in ChatGPT . Every fix shipped to production the same day in Respira for WordPress v8.7.1, so paying customers run this code today. The bridge fixes are reported upstream with a standing PR offer, and the field data from this fleet now feeds WordPress core's agent identity proposal . What i learned The gap between "implements the spec" and "works in a real agent browser" is where all the work lives. And agent browsers impose an attention budget: fewer, better-scoped tools beat an exhaustive catalog. What's next Anonymous visitor tools (public read-only search and product Q&A), per-role tool sets, and landing the bridge fixes upstream so every WordPress site gets a working WebMCP path.
