Agents want structured actions : search with parameters, fetch product details, compare specs, add to cart. Today, most agents are forced to scrape UIs or guess which button to click. That’s slow, brittle, and frustrating. \n\n WebMCP changes that. It lets a website expose tools directly to agents via document.modelContext.registerTool() . That inspired ShopMCP : an e-commerce app where you browse normally while your agent uses purpose-built tools on the same backend — so both stay in sync. \n\n We wanted to answer one question for the OpenAI WebMCP Challenge: \n\n \n What becomes possible when a web app is designed for people **and * their agents from day one?* \n \n\n \n\n What we built \n\n ShopMCP is a playful e-commerce storefront with: \n\n \n 24 products across Electronics, Home, Fashion, and Books \n Human UI : search, category filters, product pages, cart, Google sign-in \n Agent tools (WebMCP):\n\n \n search_products — query, category, max price, sort \n get_product — full product details by ID \n add_to_cart — add items (auth required) \n get_cart — view current cart \n compare_products — side-by-side comparison of 2–4 products \n \n Agent Activity panel — live feed when tools run, so human + agent collaboration is visible \n \n\n Live demo: https://shopmcp-phi.vercel.app \n\n \n\n How we built it \n\n \n \n Layer \n Tech \n \n \n \n Frontend \n Vite, React, TypeScript, Tailwind CSS v4 \n \n \n Auth \n Clerk (Google + email) \n \n \n API \n Vercel serverless functions ( /api/* ) \n \n \n Data \n In-memory cart + seeded product catalog \n \n \n WebMCP \n Imperative API in src/webmcp/registerTools.ts \n \n \n\n Architecture principle: one API, two clients. \n\n Both the React UI and WebMCP tools call the same endpoints. When an agent runs add_to_cart , the human’s cart updates on the next refresh — and the agent panel logs the action in real time via a webmcp:action event bridge. \n Human (Browser UI) ──┐\n ├──► /api/products, /api/cart ──► Shared state\nAgent (WebMCP tools) ─┘\n \n WebMCP tools are registered on app mount when document.modelContext is available: \n await document . modelContext . registerTool ( { \n name : "search_products" , \n description : "Search the product catalog" , \n inputSchema : { type : "object" , properties : { query : { type : "string" } } } , \n execute : async ( input ) = > { /* calls same API as UI */ } \n } ) ; \n \n \n\n What we learned \n\n \n WebMCP is a UX design problem, not just an API. Tool names, descriptions, and JSON schemas matter as much as UI copy. A vague tool confuses agents like a vague button confuses users. \n Shared state is the collaboration layer. The win isn’t “agent can click buttons” — it’s “agent and human see the same cart.” Single source of truth via API was essential. \n Auth boundaries need to be explicit. Product search is public; cart actions require sign-in. Tools return clear errors ( "Sign in required" ) instead of failing silently. \n Human-visible agent activity builds trust. The live feed on /shop , /cart , and /agent makes collaboration tangible — you see what the agent did and when . \n WebMCP is still emerging. Testing needs Chrome’s chrome://flags/#enable-webmcp-testing or ChatGPT’s in-app browser. Graceful fallbacks (banner when WebMCP is off) improve the judge experience. \n \n\n \n\n Challenges we faced \n\n 1. Vercel serverless import paths \nAPI routes failed in production with FUNCTION_INVOCATION_FAILED . Vercel’s TypeScript build required explicit .js extensions and correct relative paths ( ../../lib/ from nested routes). Local vite dev masked this until deploy. \n\n 2. Clerk + production domains \nGoogle sign-in worked locally but needed the Vercel URL added in Clerk’s dashboard. A small config step, easy to miss. \n\n 3. Build-time vs runtime env vars \n VITE_CLERK_PUBLISHABLE_KEY must be set in Vercel before build so the client bundle includes it. We learned to configure env vars first, then redeploy. \n\n 4. Designing tools agents can actually use \nEarly drafts had overly generic tools. We split into focused actions (search vs compare vs cart) with strict inputSchema — closer to how a good REST API is designed. \n\n 5. Making collaboration obvious in 3 minutes \nJudges need to see human + agent value quickly. The Agent Activity sidebar and /agent dashboard were added specifically to make WebMCP visible without opening DevTools. \n\n \n\n Why this fits WebMCP \n\n E-commerce is a strong WebMCP use case because shopping is intent-rich : \n\n \n “Find earbuds under $ 150” → search_products({ query: "earbuds", maxPrice: 150 }) \n “Compare these three” → compare_products({ productIds: ["p1","p3","p8"] }) \n “Add the best one” → add_to_cart({ productId: "p1", quantity: 1 }) \n \n\n That’s hard to do reliably via UI automation. WebMCP exposes what the user means , not where to click . \n\n \n\n What’s next \n\n \n Persistent cart (database instead of in-memory) \n Agent-initiated checkout flows \n Declarative WebMCP for HTML forms \n Deeper ChatGPT in-app browser integration \n \n\n \n\n ShopMCP — Shop together: humans browse, agents act. \n\n \n\n \n\n \n Built With \n\n agent ai clerk codex e-commerce javascript json node.js openai react restapi shoppingcart tailwind typescript vercel vite webmcp \n \n\n \n Try it out \n\n \n \n \n shopmcp-phi.vercel.app \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n I built this project for fun. \n \n\n \n \n \n \n \n \n\n \n Yuvraj Pharande \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Yuvraj Pharande \n started this project\n \n —\n \n 3 days ago \n \n \n\n
