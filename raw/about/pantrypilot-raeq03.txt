\nPantryPilot turns simple meal goals into an optimized grocery order. Plan meals, compare prices, respect allergies, and approve every purchase with a human-in-the-loop WebMCP agent.\n \n\n \n \n\n \n \n \n \n \n \n Like\n \n \n\n \n\n \n \n Comment\n \n\n \n \n \n\n \n \n \n \n \n \n \n Story \n \n \n \n \n Updates \n \n \n \n \n \n \n\n\n \n \n\n\n \n \n \n \n\n \n\n \n \n \n \n \n\n\n \n\n\n\n \n Inspiration \n\n Most grocery tools optimize one product at a time — but real shopping means juggling a budget,\ndietary preferences, allergies, pantry items you already own, and substitutions when something is\ntoo expensive or unsafe. And AI agents? They can't reliably drive a grocery website at all: layouts\nshift, checkouts change, captchas appear. An agent guessing at buttons and dropdowns is a broken\nexperience. \n\n The WebMCP Challenge inspired us to invert that model. Instead of an agent scraping a messy DOM,\nwhat if the app handed the agent explicit, typed, discoverable tools — with the hard parts\n(budgets, allergies, approvals) encoded directly in the tools themselves? \n\n What it does \n\n PantryPilot is an agent-native grocery planning workspace. You set your constraints — budget,\ndiet, allergies, pantry items, preferred stores — and an AI agent plans your meals, builds the\ngrocery list, finds cheaper and safer substitutions, optimizes the basket, and validates safety.\nThen you review everything and explicitly approve the final basket. No payment is ever\nprocessed. \n\n In the built-in demo: 2 adults, $85/week, vegetarian, peanut allergy, pantry with rice, garlic,\nolive oil and black beans . The agent detects a peanut-containing product and removes it, finds a\npeanut-free alternative, optimizes under budget, and shows the savings — then stops and asks for\nhuman approval . \n\n How we built it \n\n We built PantryPilot with Next.js 14 , TypeScript , and Tailwind CSS — no backend, no API\nkeys, 30+ seeded products. The heart of the project is 9 genuinely functional WebMCP tools \nregistered on document.modelContext : \n document.modelContext.registerTool({\n name: "search_products",\n description: "Search safe and affordable grocery products",\n inputSchema: {\n type: "object",\n properties: {\n query: { type: "string" },\n dietaryTags: { type: "array", items: { type: "string" } },\n excludeAllergens: { type: "array", items: { type: "string" } },\n maxPrice: { type: "number" },\n store: { type: "string" },\n limit: { type: "number" }\n }\n },\n execute: async (input) => searchProducts(input)\n});\n \n search_products · get_product_details · create_meal_plan · build_grocery_list ·\n optimize_basket · suggest_substitutions · validate_basket · request_human_approval ·\n save_user_preferences \n\n Basket optimization is a constrained minimization — keep total spend within budget $B$ while\nexcluding every allergen in set $A$: \n\n min ∑ i p i q i s.t. ∑ i p i q i ≤ B , allergens ( i ) ∩ A = ∅ \n\n The critical architectural choice: when no WebMCP runtime is present (Firefox, Safari, Edge), the\nUI falls back to a local simulator that calls the exact same functions — one codebase, two\npathways, so the demo works in every browser. \n\n Challenges we ran into \n\n \n Tool schema design — JSON Schemas are the agent's entire world. Every filter the agent needs\n(allergen exclusions, budget caps, stores) had to be first-class in the schema, not inferred. \n Strict validation — validate_basket must catch allergy, dietary, budget, and stock issues\nand report them as structured checks, warnings, and errors rather than silent failures. \n Human approval as a hard gate — making the agent unable to finish without calling\n request_human_approval was a deliberate design decision, not a UI courtesy. \n Graceful degradation — keeping the simulator and the WebMCP pathway on the same functions\ntook discipline, but it's what makes the app portable. \n \n\n Accomplishments that we're proud of \n\n A live agent timeline and WebMCP tool inspector make every agent action visible . The full demo\nruns end-to-end in under three minutes: profile → search → allergy catch → plan → optimize →\nvalidate → approve. \n\n What we learned \n\n \n Schema design is API design for agents — predictable inputs/outputs beat cleverness. \n Transparency (timeline + inspector) is what makes humans comfortable delegating. \n Fallbacks aren't a nice-to-have; they're what makes a demo survive any machine. \n \n\n What's next \n\n Real retailer integrations, persistent accounts, multi-store optimization, and richer dietary\nmodels — all through the same tool interface. \n\n \n PantryPilot is not an autonomous checkout bot. It's a collaboration layer where agents handle the\nlegwork and humans make the decisions. \n \n\n \n\n \n Built With \n\n css css3 html5 javascript json localstorage next.js node.js npm react schema tailwind typescript webmcp \n \n\n \n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Amimul Ahsan \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Amimul Ahsan \n started this project\n \n —\n \n 2 days ago \n \n \n\n
