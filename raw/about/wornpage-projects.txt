The app has a next action field; work items could drive an agentic memory ledger, But really, and simply, WebMCP drives the app here. The work tracker can give work (and meaning) to the agent who then drafts tasks and goes through review and human approval. This human-in-the-loop demonstration that I have here was not novel, now, there are a lot of tools out there. I chose the name Wornpage because I wanted the pages to feel well-worn, through simple, repeatable steps. \n\n What it does \n\n The web interface has pages for work items, review, computed next action. It is a generalists toolkit for deciding what to work on next. The seed data is an every-day occurence, cleaning the house, fixing a toilet (hiring a plumber), etc. \n\n Why is this use case a strong fit for WebMCP? \n\n What was started as MCPv2 in a private repo was extended here with WebMCP. What this afforded was a new way of looking at the website. Instead of static work item creation, editing and closing, in traditional way (as a CRUD app), we can utilize tools in the browser with WebMCP that offer a unique approach. Working with an agent, building on projects and developing business plans require a workflow that is dependent on human review. WebMCP allows this. \n\n How does it create a better user experience? \n\n Web creates an experience of open source javascript accessible to people with varying uses, abilities and needs. MCP brings the agentic self improvement to a project workspace. Together, web users and webMCP protocol handlers can work together to harmonize on work and to make the app more accessible. Every step produces a receipt of what was done. Buttons are able to be run by the person, and the person can decide what to do next. AI can also suggest a recommended action, but the person decides what to do next. \n\n What can people and agents do together that was difficult before? \n\n Self learn from recent decisions, decide on new business ideas. A backend exists at Projects , but it is closed source, and WebMCP was added concurrently to the challenge.). This is a team/enterprise human-in-the loop workspace. \n\n How it was built \n\n The entry uses SvelteKit and Wornpage design system components I build. It was made using long agent runs to modernize and align with a North Star: the user should be able to open the app and see what to do next. The design system and tools leverage javascript where updating parts of a page based on something else is efficient. What started as vanilla JS was organized into the Svelte routes I have today. The production effort is hosted on Cloudflare workers and leverages digital objects, R2, and many other features in the platform. I wanted this extension to be a publically identifiable extension to it. When I saw that WebMCP existed and this challenge, I immediately knew I could extend the app into this space. \n\n How did you implement WebMCP? \n\n I used codex on high or max reasoning to implement WebMCP. I had already implemented MCPv2 recently, so the memory of that was useful in designing an extension to my current project with the new protocol. I know that the app is a little bit of a showcase of WebMCP, but I tried my best to make it actually useful. I design components and can hopefully spot areas where the AI used too much meta-commentary, or limit it first through that design. Eventually, this might be moved into a whole other product vertical. I hope the app and the webMCP contracts allow easy rewriting. \n\n \n\n \n Built With \n\n cloudflare-pages css html javascript playwright svelte sveltekit vite webmcp \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n projects-webmcp-extension.pages.dev \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Private user \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Private user \n posted an update\n \n —\n \n 4 days ago \n \n \n\n Over the last two days, I substantially rebuilt Wornpage Projects’ WebMCP experience around visible, reproducible human–agent collaboration. \n\n The app now exposes nine page-scoped tools across Guide, Priority, Work, Review, and Next: \n\n \n Guide derives real workspace scopes and gives the agent an editable, bounded brief. \n Priority exposes one current recommendation without navigating or changing data. \n Work lets an agent inspect the rendered workspace, apply a reversible search, or atomically create up to three Draft items. Drafts are never started automatically. \n Review exposes exact queue evidence and reversible filtering with explicit denominators. \n Next lets an agent prepare an evidence-backed proposal, but it remains unsaved until a person chooses Save or Discard. \n \n\n I also added a global WebMCP status pill and accessible tool-catalog dialog. It shows whether native WebMCP is actually ready, which tools are registered on the current page, and what authority each tool has. \n\n Agent actions now appear in a branch-aware Verified action trail. Read, scope, and preparation receipts are recorded, while the final human decision remains visibly pending rather than being falsely marked complete. \n\n Beyond the WebMCP layer, I split large Work, Review, and Next route implementations into smaller focused components, consolidated shared state and evidence logic, removed obsolete CSS and unused code paths, and strengthened keyboard, focus, responsive, and accessibility behavior. \n\n Finally, I added a deterministic browser preflight that reproduces the complete demonstration, verifies exact tool catalogs and workspace counts, checks keyboard destinations and action-trail states, and fails on browser errors, unexpected writes, or horizontal overflow. \n\n The result is no longer just a scripted agent demo: a judge can open the live app, give an agent the brief shown on the page, and reproduce the same bounded workflow while retaining control of every consequential action. \n\n Live: https://projects-webmcp-extension.pages.dev/ \nSource: https://github.com/wornpage/projects-webmcp-extension \n\n\n \n \n \n\n \n Log in \n or\n sign up for Devpost \n to join the conversation.\n \n\n \n\n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n \n Private user \n started this project\n \n —\n \n 9 days ago \n \n \n\n
