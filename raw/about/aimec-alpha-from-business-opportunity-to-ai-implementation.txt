AIMEC Alpha turns business automation ideas into AI implementation plans. Via WebMCP, people and agents can run ROI and readiness diagnostics, delegate to two AI specialists, and inspect the results. Like Comment Story Updates Inspiration Businesses rarely struggle to find AI ideas. They struggle to decide which ideas are worth pursuing, whether their data and processes are ready, and what a practical implementation would require. I built AIMEC Alpha to connect those decisions in one workflow. Instead of stopping at a conversational recommendation, I wanted users to move from a business problem to measurable assumptions, an opportunity assessment, and a proposed implementation plan—with results they could inspect. WebMCP made this an opportunity to design for both people and their browser agents. A person can work through the interface, while an agent can discover and invoke the same capabilities through structured tools. What it does AIMEC Alpha evaluates a business automation opportunity using five diagnostics: AI return on investment AI operating costs Data readiness Agentic automation readiness Overall AI readiness Two complementary specialists then help interpret the findings: The AI Opportunity Analyst combines diagnostic results with the supplied business context to assess the opportunity, identify risks, and recommend whether to proceed, pilot, or hold. The AI Solution Architect receives the handoff and proposes a bounded architecture, implementation phases, and human approval points. The workflow then recalculates ROI using the estimated operating costs. Both specialists use a locally hosted Qwen model through Ollama. Financial calculations remain deterministic Python functions; the model provides interpretation and planning. The demo includes synthetic invoice-processing and customer-support scenarios. Users can change the assumptions and evaluate a different case. It proposes implementations—it does not connect to an ERP, process real invoices, or carry out business changes. Why WebMCP matters A conventional web application makes its functionality available primarily through buttons and forms. Browser agents often have to infer how those controls work. AIMEC Alpha exposes seven structured WebMCP interfaces: get_available_tools run_tool get_available_agents delegate_task get_task_status get_task_result get_execution_evidence These interfaces let a browser agent discover approved operations and their input schemas, submit a business case, and retrieve the resulting job status, output, and evidence without reconstructing the workflow from screen content. The human-facing interface remains available alongside those tools. People can review the assumptions and inspect the corresponding results in the same browser session. The value is not simply asking an LLM to calculate ROI. It is connecting discoverable capabilities, deterministic calculations, specialist interpretation, persistent task state, and inspectable results through a shared interface for people and agents. How I built it I extended existing AIMEC building blocks for capability registration, HTTP services, task persistence, and execution logging. The challenge-specific work added the WebMCP interface, browser workflow, business-agent integration, and isolated demo packaging. The application uses: Python services for diagnostics, capability execution, and specialist workflows. Qwen3:1.7b through Ollama for server-local model inference. SQLite for persistent jobs and execution events. JavaScript and document.modelContext.registerTool for native WebMCP registration. Docker Compose for the isolated runtime. Caddy for the public HTTPS endpoint. The Analyst and Architect have separate prompts and output contracts but share one model runtime. Their handoff follows an explicit, programmed workflow within the advisory service; it is not an unrestricted autonomous agent network. Results are associated with session-owned jobs. Execution evidence includes provider events and result hashes, allowing the application to check that a saved artifact matches the recorded provider output. Challenges I faced Making the model useful on a small VPS Running local inference on a CPU-only server required balancing response length, memory use, and execution time. I selected a small model, disabled its thinking mode for this workflow, bounded generation, and adjusted timeouts. A healthy model server does not necessarily mean an inference request will complete successfully, so testing the actual workflow was essential. Keeping browser sessions and results connected Early testing exposed problems restoring jobs across browser sessions. Cookie behavior and initialization order mattered: a completed backend job was not useful if the browser could no longer retrieve its result. I worked through session handling and tested status, result, and evidence retrieval together. Separating valid JSON from valid specialist output A model can return JSON that does not satisfy the application's required fields or values. I encountered an intermittent execution failure even while the underlying services remained healthy. That reinforced the importance of strict output validation and more specific failure reporting. The application does not replace failed model output with a fabricated success. Improving structured-output reliability remains an important next step. Keeping the demonstration honest I distinguished between deterministic calculations, model-generated proposals, and actions the system actually performs. I also separated native WebMCP tool checks from the broader claim that an external browser agent can independently choose and complete every workflow. What I learned WebMCP is most valuable when the underlying application has clear capabilities and meaningful execution boundaries. Registering a tool is only the beginning: its inputs, permissions, task lifecycle, results, and failure behavior also need to be understandable. I learned that small local models can contribute useful interpretation when paired with deterministic tools and narrow responsibilities. They still require validation, realistic time budgets, and careful handling of failures. I also learned that execution evidence has limits. A matching result hash supports artifact integrity; it does not prove that a recommendation is financially correct or that every model-generated statement is justified. What I accomplished I deployed a public HTTPS demo with seven registered WebMCP interfaces, five business diagnostics, and two local-model specialists. Live testing demonstrated direct diagnostic execution and the Analyst-to-Architect workflow, including completed jobs, saved results, and verified result digests. The public demo export also passed ten offline tests covering business logic and packaging, with mocked model responses clearly distinguished from live inference. I published an isolated, MIT-licensed repository with the source, setup instructions, third-party notices, and a judge walkthrough. What's next My immediate priorities are stronger schema-constrained model output, clearer failure diagnostics, and repeated end-to-end reliability testing. Beyond the demonstration, I want to evaluate the assessments with real business users, improve the assumptions behind cost and readiness estimates, and add permissioned integrations that connect proposed plans to measurable pilot outcomes. The goal is to help businesses move from “I should use AI” to a specific, reviewable next step.
