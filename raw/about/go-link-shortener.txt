\n\n Instead of building a separate chatbot or a remote MCP server, I wanted the existing website itself to expose its capabilities directly to AI agents while remaining fully usable by humans. \n\n The result is an agent-native URL shortener where the same application can be used through its normal UI or through structured WebMCP tools. \n\n What it does \n\n Go Link Shortener allows users to create custom short URLs, redirect visitors efficiently, and collect click analytics. \n\n With WebMCP enabled, the website exposes three capabilities directly to AI agents: \n\n \n create_short_link — creates a short URL using the existing HTML form and server-side validation. \n resolve_short_link — returns the destination behind an existing alias. \n get_link_analytics — returns aggregate traffic information such as total clicks and the latest click timestamp. \n \n\n This enables interactions such as: \n\n \n "Create /webmcp pointing to the WebMCP documentation." \n \n\n or: \n\n \n "Where does /webmcp redirect, and how many times has it been opened?" \n \n\n The agent can discover and execute the appropriate tools without visually locating controls or automating clicks. \n\n How I built it \n\n The backend is written in Go using Fiber v3 , with PostgreSQL as the persistent datastore and Redis for fast URL resolution. \n\n I deliberately kept the existing server-rendered architecture instead of introducing a frontend framework only for WebMCP. \n\n For link creation, I used the Declarative WebMCP API . The existing HTML form is exposed as the create_short_link tool, so both humans and agents go through the same validation and persistence code. \n\n For read operations, I used the Imperative WebMCP API through: \n document . modelContext . registerTool ( . . . ) \n \n Two read-only tools are registered when WebMCP is available: \n resolve_short_link\nget_link_analytics\n \n They call lightweight JSON endpoints implemented in the existing Go application. \n\n The integration is implemented as progressive enhancement. If a browser does not support WebMCP, the website continues working normally. \n\n Privacy and safety \n\n The original application records redirect events for analytics, including information useful for internal traffic analysis. \n\n I intentionally designed the WebMCP interface to expose only aggregate information. \n\n The get_link_analytics tool returns: \n\n \n total clicks \n latest click timestamp \n \n\n It does not expose raw IP addresses, User-Agent strings, referrers, or individual click events. \n\n Read operations are also explicitly marked with readOnlyHint: true , giving agents additional information about which actions are safe to execute without modifying application state. \n\n Challenges I faced \n\n One of the most interesting challenges was that implementing the tools themselves was not enough. \n\n WebMCP requires the document to run in the appropriate browser security context, so I had to configure origin isolation using: \n Cross-Origin-Opener-Policy: same-origin\nCross-Origin-Embedder-Policy: require-corp\n \n I also added configurable support for the WebMCP Origin Trial token so the application can participate in the browser experiment without hardcoding environment-specific credentials. \n\n Another challenge was deciding where WebMCP should stop. \n\n It would have been easy to create a parallel API layer, duplicate validation in JavaScript, or rebuild the UI using a frontend framework. Instead, I kept the existing application as the source of truth and exposed only the capabilities an agent actually needs. \n\n That kept the implementation small, maintainable, and aligned with the progressive nature of WebMCP. \n\n What I learned \n\n The biggest lesson was that making a website agent-friendly is very different from adding AI to a website. \n\n There is no LLM inside Go Link Shortener. \n\n Instead, WebMCP gives external agents a structured contract describing what the website can do. \n\n This changes the integration model from: \n Agent → inspect DOM → understand UI → simulate clicks\n \n to: \n Agent → discover tools → execute structured action\n \n I also learned that good tool design matters as much as implementation. Tool names, descriptions, JSON schemas, read-only annotations, error handling, and privacy boundaries directly affect how reliably an agent can interact with the application. \n\n What's next \n\n The next steps would be to expand the agent-native interface with capabilities such as: \n\n \n listing and searching previously created links \n safely deleting or disabling short links \n richer aggregate analytics \n expiration dates \n QR code generation \n authenticated link management \n \n\n The important part is that these features can continue using the same architecture: normal web functionality for humans, structured WebMCP capabilities for agents. \n\n Go Link Shortener remains a simple web application. \n\n It just no longer assumes that every visitor using it has fingers. \n\n \n\n \n Built With \n\n ai-agents chrome context docker fiber go html javascript json model postgresql redis rest-api webmcp \n \n\n \n Try it out \n\n \n \n \n e.hugojava.dev \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Vitor Hugo \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Vitor Hugo \n started this project\n \n —\n \n 4 days ago \n \n \n\n
