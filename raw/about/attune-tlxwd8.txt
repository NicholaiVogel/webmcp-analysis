Design physical products with your browser agent, find who can make it Like Comment Story Updates Attune Design Attune Let the design find its maker. Inspiration I came into this challenge from a UX/UI and product design background. At first I kept asking: what can an agent do on a website? While building Attune, a better question took over: What should the person and the agent do together? A person may be better at looking at a design, moving something by eye, and deciding what feels right. An agent can help with exact values, repeated edits, relationships, checks, and multi-step work. The useful part is when both work on the same object , without the person having to explain that object again and again. That became Attune. What Attune does Attune is a shared workspace for designing physical products . The person gets the visual canvas. The browser agent gets WebMCP tools. Both work on the same underlying design. If I already selected something, I should not need to describe which part I mean. If the design already knows a measurement, the agent should not guess it from the screen. If I change something myself, the agent should continue from the new state. The goal is not “AI, finish the whole design for me.” It is closer to: I decide → the agent helps → I adjust → Attune checks → we continue. Why WebMCP here? A 2D engineering sketch is more than pixels. It contains entities, dimensions, constraints, groups, solver state, versions, and relationships between parts. A small edit can also affect what happens later. Without a structured interface, an agent has to reconstruct too much of that from the visible UI. With WebMCP, Attune can give the agent direct actions over the same design state the person is using. That lets the agent answer four useful questions: What am I working on? What can I change here? What would this change affect? What can happen next? Attune also does not expose one giant toolbox on every page. Design tools appear while editing. Manufacturing tools appear later. Buyer and Maker actions stay separate. Important commercial actions still require human confirmation. Chrome WebMCP WebMCP tools Not every tool is active at once. The current page, project state, and the person's access decide what is exposed. Co-creation, not autopilot Building the design side taught me that precise design is not really a one-prompt problem. Even a simple request can depend on what should stay fixed when something else moves. Recent Autodesk research on AI CAD editing points to the same problem: current models are improving, but matching the designer's exact intent is still difficult. That helped clarify the roles: The person provides intent and judgement. The agent helps interpret and carry out the request. The application owns the exact result. Attune works with real 2D geometry and constraints rather than treating the canvas as only a picture. Autodesk Research - AI CAD editing Why manufacturing? Manufacturing made this interaction more meaningful because a design action can have consequences outside the screen. Moving one feature can affect a constraint. It can affect whether a Maker can make the part. A later design edit can also make an older quote belong to the wrong version. So I started thinking about WebMCP actions as steps on a path: see the work → understand the change → check the result → know what can happen next The model can help understand what I want. It should not invent whether something is actually manufacturable. The design becomes the query Once the design is ready, another problem appears: Who can make this? Today that often becomes another translation step: “CNC shop”, “aluminium fabrication”, “laser cutting”. But the design already contains more useful information than those words: geometry, dimensions, material, quantity, and requirements. The longer-term idea behind Attune is: Let the design itself become the query. The person can then add what matters: prefer somebody nearby, need it quickly, preserve these mounting points, or show a specialist if nobody local fits. And Makers are not always sellers. A shop that machines one part may buy finishing, electronics, packaging, or another process from somebody else. Today's Maker can be tomorrow's customer. That is why I see the future as a network of Makers, with local opportunity and global reach, rather than only a one-way marketplace. From design to a real order I did not want the demo to end at a fake Buy button. Attune keeps an exact saved version attached to the manufacturing request. The Maker reviews that version. The quote belongs to that version. The Buyer accepts that version. If the design changes later, the old quote should not quietly become approval for something different. The challenge path is: Design → Buyer Request → Maker Review → Buyer Order → Maker Job / Shopify Shopify Draft Orders How I built it Attune uses Next.js, React, TypeScript, CanvasKit/Skia, Maker.js, PlaneGCS, Liveblocks, Yjs, Neon/PostgreSQL, Shopify, Cloudflare R2, Kumo, and WebMCP . The human interface and the WebMCP path use the same underlying design and workflow rules. They are not two separate versions of the product. Challenges I ran into This was more ambitious than I understood at the start. I was learning CAD-style interaction, geometric constraints, realtime collaboration, WebMCP, permissions, Shopify, and backend state at the same time. The 2D sketch workspace was the hardest part. Drawing geometry that looks right is much easier than building interaction where selections, dimensions, constraints, and later edits still mean what the person intended. I also learned how to work better with coding agents. Long runs could sometimes carry an older architectural assumption forward after the product had changed. I moved toward smaller tasks, checking the current code, running tests, and committing between milestones. Limited agent usage made that discipline even more important. The build became narrower than the product I first imagined, but kept the path: design → consequence → Maker → quote → commerce.** What I learned The biggest lesson was that a good agent experience can mean asking the person to explain less . If I already selected something, do not make me describe it again. If the site knows a measurement, do not guess it. If the design changed, do not continue from an old picture. The question stopped being: “How many things can the agent do?” and became: “How much of the work can the website help the agent understand?” What's next I want to improve direct editing, constraint feedback, and the way the agent understands the purpose of parts, not only their geometry. Beyond that is the Maker network: more Makers publishing what they can actually do, designs that search that network, Makers buying from other Makers, and the same agreed design staying connected through production and delivery.
