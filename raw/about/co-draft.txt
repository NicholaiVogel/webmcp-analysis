For a document editor, that means the agent has to figure out what the user is looking at, where content belongs, and what actions are available. \n\n We wanted to try a different approach using WebMCP : let the website expose its actual application state and capabilities as structured tools that an AI agent can call directly. \n\n That became Co/Draft — a document where humans and agents edit together. \n\n The core interaction is deliberately simple. A human writes and selects content normally, while an agent can use tools such as get_document_state , get_selection , add_comment , and insert_block . The agent therefore works with the same structured document state that the human sees, rather than trying to reconstruct it from the UI. \n\n How we built it \n\n Co/Draft is a lightweight React + TypeScript application using Zustand for document state. \n\n The document is represented as structured blocks rather than one large piece of HTML. Each block has an ID, text, creation source, and author information. Comments are also attached to specific block IDs, which gives the agent an unambiguous way to refer to a section of the document. \n\n On top of this state, we registered five WebMCP tools: \n\n \n get_document_state — lets the agent read the current document, pending suggestions, and comments. \n get_selection — tells the agent which block the human is currently working on. \n insert_block — lets the agent propose a new section. \n add_comment — lets the agent leave feedback on a specific block. \n resolve_comment — lets the agent mark feedback as resolved. \n \n\n These tools are registered through document.modelContext , using a React hook so that the tools operate against the same live state as the UI. \n\n We also added a small human-in-the-loop trust boundary . An agent doesn't directly insert arbitrary content into the document. Instead, insert_block creates a visible pending suggestion. The human can then accept or reject it. \n\n That gives us a workflow like: \n\n Human writes → Agent reads → Agent reviews → Agent proposes → Human approves → Document changes \n\n The agent can participate meaningfully without silently taking control of the document. \n\n For collaboration, the prototype uses the browser's BroadcastChannel API. This allows multiple tabs in the same browser to exchange document mutations and presence information without requiring a backend. The project is intentionally a prototype rather than a production collaborative editor. \n\n What we learned \n\n The biggest thing we learned was that giving an agent structured tools changes the interaction completely . \n\n Instead of asking an agent to “look at the page and figure out what to do,” we can give it explicit capabilities: \n get_document_state()\nget_selection()\nadd_comment(blockId, text)\ninsert_block(text, afterBlockId)\nresolve_comment(commentId)\n \n This makes the boundary between the application and the agent much clearer. \n\n We also learned that the interesting part isn't simply allowing an agent to edit. The more important question is how much control the agent should have . \n\n For example, comments are relatively low-risk, so an agent can add one directly. Inserting actual document content is more consequential, so we introduced an approval step. \n\n That led us to think about agents less like automated scripts and more like collaborators with explicitly defined permissions . \n\n We also learned about the practical distinction between exposing application functionality to an agent and actually building a collaborative application. WebMCP solves the first problem very nicely, but synchronization, persistence, identity, and conflict resolution are separate engineering problems. \n\n The challenges \n\n One of our biggest challenges was synchronization. \n\n Our first implementation used BroadcastChannel to send mutations such as: \n editBlock\naddComment\nresolveComment\nproposeBlock\nacceptSuggestion\ndeleteBlock\n \n between tabs. \n\n However, simply broadcasting mutations isn't enough to create a reliable shared document. Each tab initially creates its own in-memory state, so two tabs can start with different randomly generated block IDs. A mutation referring to a block that only exists in the sender's state cannot be correctly applied by another tab. \n\n This forced us to think about an important distinction: \n\n sharing events is not the same thing as sharing state. \n\n A reliable prototype needs both a consistent initial document and a way for a newly opened tab to obtain the current state before applying future mutations. \n\n We therefore treated the synchronization layer as a separate problem from WebMCP itself. The eventual direction is a lightweight state handshake for new tabs, while keeping the mutation-based synchronization simple enough for a hackathon demo. \n\n Another challenge was deciding what not to build. \n\n It would be possible to turn Co/Draft into a much larger system with a backend, WebSockets, persistent documents, authentication, CRDTs, conflict-free editing, and cross-device collaboration. But that would move attention away from the actual experiment we wanted to demonstrate: \n\n \n Can a web application expose meaningful, structured capabilities to an AI agent so that the agent can genuinely collaborate with a human? \n \n\n For this project, we chose to keep that question at the center. \n\n Why this matters \n\n Co/Draft is intentionally small, but the idea can extend much further. \n\n A document editor is just one example. The same pattern could apply to design tools, spreadsheets, project-management applications, whiteboards, educational software, or any interactive application where an AI agent needs to understand and manipulate structured state. \n\n Instead of building agents that merely see interfaces, we can build applications that explicitly tell agents: \n\n “Here is what I am. Here is what you can understand. Here is what you are allowed to do.” \n\n That is the direction we wanted to explore with Co/Draft. \n\n \n\n \n Built With \n\n agents api apis broadcastchannel collaboration collaborative context design document.modelcontext editing generative human-in-the-loop javascript jspdf model protocol react real-time responsive typescript usewebmcp vite web webmcp zustand \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n codraft.netlify.app \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Druvan Karthik Kareke \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Druvan Karthik Kareke \n started this project\n \n —\n \n 3 days ago \n \n \n\n
