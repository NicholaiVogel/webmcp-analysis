A shared hopyard design workspace where farmers and AI agents plan poles, wire, cost, and structural load together — agents propose alternatives, farmers decide, powered by WebMCP. Like Comment Story Updates Hopyard Designer with webMCP Inspiration Planning a hopyard is a connected design problem. Plant spacing affects the number of plants and the planting-stock cost. Pole spacing changes the structure and material quantities. Wire, anchors, wind loads, and labor all affect the final estimate. Hopyard Designer already helped growers and installers work through these decisions in a visual web app. The WebMCP Challenge gave us a chance to explore a harder question: can an AI agent help compare design alternatives without hiding changes from the farmer or taking control of the final decision? We wanted the farmer and the agent to work in the same design space. The agent should be able to read the current plan, prepare alternatives, and explain the differences. The farmer should be able to inspect each proposal in the existing 2D and 3D views before deciding what to keep. What it does Hopyard Designer calculates planting-stock cost, facility quantities, preliminary structural loads, and a live material estimate from a hopyard design. As the design changes, the app updates: pole and anchor quantities main wire, training wire, and twine lengths hop positions and planting-stock cost preliminary wind and crop-load checks a construction-oriented 2D plan an interactive 3D farm a downloadable estimate PDF For the challenge, we added a WebMCP workflow that lets an agent create alternatives without changing the original plan. In the demo, the agent compares a Korean I-shaped training layout with a North American 18-foot Y-shaped reference. Both options appear side by side with their plant counts, material requirements, estimated costs, and engineering status. The farmer chooses which option to preview. The selected candidate appears in the same 2D and 3D workspace, but it is not committed yet. How we built it The application uses Next.js, React, and TypeScript. Zustand manages the active design and a separate candidate workspace. Konva renders the 2D construction plan, while Three.js renders the farm in 3D. We used BlenderMCP to create a reusable GLB asset kit containing pole variants, anchors, turnbuckles, wire hardware, and low-poly hop geometry. The web renderer places these assets procedurally instead of loading a fixed model of the whole farm. This keeps every candidate editable and allows the design to update immediately. Repeated components use instancing to keep the 3D view responsive, even when the farm contains hundreds of plants and many structural elements. How WebMCP works The design page initially registers five WebMCP tools: get_design_context list_regional_profiles simulate_design show_candidates preview_candidate The agent starts by reading the current design and its calculated results. It can then simulate alternatives and place up to three candidates in the shared comparison tray. When a candidate enters preview, the page dynamically registers two additional tools: apply_candidate discard_preview This changes the available tool set from five to seven. Apply and Discard only exist while a preview is active. After either action, the page returns to five tools. This creates a visible review step. The agent can prepare and preview options, while the farmer uses the shared interface to decide whether to apply or discard the active preview. The apply_candidate tool description explicitly directs the agent to use it only after user approval. WebMCP inputs use strict JSON Schema and are validated again with Zod at runtime. Candidate IDs are deterministic. Preview stores an exact copy of the active design, so Discard can restore it without relying on reverse calculations. The production site uses Chrome's WebMCP Origin Trial. We also built CDP-based checks that verify tool registration, tool invocation, the five-to-seven-to-five lifecycle, responsive layouts, and browser console errors against the live page. Existing product vs. challenge work Hopyard Designer existed before the challenge with: a human-operated design form planting-stock and material calculations preliminary structural-load calculations live Korean material estimates authentication and project saving 2D and 3D visualization estimate PDF export The following work was added for the WebMCP Challenge: seven WebMCP tools with runtime validation deterministic, non-destructive candidate simulation the agent design alternatives tray temporary candidate previews in the existing 2D/3D workspace dynamic Apply and Discard tool registration the five-to-seven-to-five tool lifecycle Korean and North American reference profiles the reusable BlenderMCP GLB asset kit the public /design/demo judge route browser-level WebMCP verification English and Korean UI, help, PDF, narration, and caption support The complete source repository is available under the MIT License. Challenges we ran into Keeping the workflow non-destructive An agent needs enough freedom to explore, but a design tool should not silently overwrite a farmer's work. We separated simulation, display, preview, and application into distinct states. A simulation creates a candidate without touching the active design. The candidate only changes the shared canvas when it enters preview. The original design remains available for exact restoration. Making browser support testable WebMCP availability depends on the browser runtime. A browser without the API can make a correct implementation look broken. We added an Origin Trial token for the production origin and built browser-level checks instead of relying only on mocked unit tests. These checks exercise the real tools through Chrome and verify the complete lifecycle. Rendering a full farm in 3D A detailed plant model looked good by itself but became too expensive when repeated hundreds of times. We replaced it with a low-poly procedural asset kit and used instancing for repeated components. The resulting farm can still be rotated and zoomed while remaining connected to the editable design. Comparing regions without inventing data The Korean profile can use the active HOPEDEN catalog. The North American profile is explicitly identified as a reference configuration. The app does not pretend to provide live US pricing or local engineering approval. Both the interface and the WebMCP results preserve that distinction. Accomplishments that we're proud of A working five-to-seven-to-five WebMCP tool lifecycle Deterministic alternatives that do not mutate the baseline design Exact restoration after Discard Human selection and review in the same 2D and 3D workspace Real WebMCP calls rather than simulated agent results Procedural Blender assets that respond to design changes A public demo that works without an account Protected authentication and project-saving routes for normal users English and Korean interfaces and estimate PDFs Automated tests for WebMCP contracts, candidate state, responsive layouts, accessibility, and deployment What we learned A useful agent interface is not the same as automating clicks. The agent works better when the page exposes clear operations with validated inputs, stable identifiers, and results that explain what changed. This is more reliable than asking an agent to infer the meaning of visual controls. We also learned that dynamic tool registration can communicate application state. In this project, the presence of Apply and Discard tells the agent that a candidate preview is active. The shared preview gives the farmer a practical way to verify an agent's proposal. The agent can explore alternatives quickly, but the farmer still sees the same plan, quantities, safety status, and estimate before making a decision. What's next for Hopyard Designer — WebMCP for Hop Farms We plan to add more regional construction profiles, supplier integrations, and project revision history. Future versions could allow growers to: compare contractor proposals save approved agent changes as project revisions review how each input affects materials and cost connect additional regional price catalogs export a complete design package for a local engineer keep an auditable record of human and agent decisions The goal is not to replace the farmer, installer, or engineer. It is to make the design process easier to inspect, compare, and communicate. I built this tool because I needed it myself: managing pole spacing, wire, wind load, and cost by hand was getting out of hand, so I started building something I could actually use on my own farm, with the idea of eventually turning it into a real service for other growers. Then WebMCP came along, and something changed. It wasn't just "adding an AI feature" to an existing app anymore — the app and the agent started to feel like one body, working through the same design, the same numbers, the same decisions, together. It's a small step, but I hope it's a sign of the AI wind starting to blow into agriculture too.
