adding human authentiation to agent workflows Like Comment Story Updates What it does A Chrome extension that holds every WebMCP write until a human approves it. Reads run freely, around 5ms, no prompt. Works on any WebMCP site, including sites that never adopted anything and don't know it exists. No SDK, no code change, nothing for the site to install. The approval card shows the tool name, the real arguments, and the site. Not a yes/no on an opaque tool name Catches sites that lie. A tool that declares readOnlyHint: true and then fires a POST while running is held at the network layer. "Always allow" is per site + tool, listed in the popup, and revocable there. A cache you can't see or undo isn't consent. A declined call tells the agent plainly that a human declined it and not to retry, instead of a generic error it would just try again. How we built it A document_start content script in the MAIN world replaces registerTool before any page script runs. The site registers its tools the normal way and is calling our wrapper. It never finds out. MAIN world is what makes this possible. The default isolated world hands the script a private copy of the context, and you'd patch something the page never reads. MAIN-world scripts can't touch chrome.* , so decisions cross a private MessagePort → an isolated-world bridge → chrome.runtime → an MV3 service worker that owns the queue, the allow list and the badge. Classification is one line: def.annotations?.readOnlyHint !== true . No annotation means gated. It never reads the tool's name or description to guess intent — that's attacker-authored text, and putting it in charge of a security decision is the problem we're solving. window.fetch is patched too, with a call stack tracking which tool is executing, so a "read-only" tool that POSTs gets caught. Pending proposals live in chrome.storage.session so they survive service-worker eviction. The allow list is in chrome.storage.local , keyed origin::toolName .
