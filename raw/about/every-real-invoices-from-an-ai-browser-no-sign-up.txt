A marketing site that publishes 17 WebMCP tools, so an agent can make a real invoice for someone who has no account. Like Comment Story Updates ChatGPT's built-in browser listing the 17 Site tools every.ai registers, beside the live generator page. Inspiration every.ai had two landing pages promising a free invoice generator and a free proposal generator to small service businesses. Neither had a generator behind it. We built one during the Challenge window, and made it agent-first from the first commit, because a generator is the one corner of a marketing site where "an agent fills in a form and gets a real result" is the whole product. Then we found the sharper reason to do it. Asked in plain language for "a free invoice tool I can use without making an account", ChatGPT recommended three competitors and then volunteered a correction about us: that Every requires a Google sign-up, so it does not qualify. It cited every.ai. Reading our marketing pages, that was a fair conclusion — the pages talk about trials and sign-in, because that is what the product needed before this week. That is the problem WebMCP actually solves. Search forms a view of what your site can do, and that view is stale the moment you ship. A page that publishes tools does not have to argue with the model. It just hands over the capability, and the agent updates. In our demo video you can watch that happen live : the agent tells the user Every needs an account, opens the page, and corrects itself on camera — "the earlier answer was indeed outdated: the page explicitly says no account is needed" — and then makes the invoice. What it does every.ai is a static Astro marketing site. It also registers 17 tools on document.modelContext , so an agentic browser can act for a visitor who has never signed up. They cover the whole arc of a visit. Decide. about_every and check_fit answer what Every is, what it costs from live pricing data, and whether it suits the business the visitor describes — including saying plainly when it does not. search_help answers from a build-time index of the site's own content and admits when it has no answer instead of guessing. Do. create_invoice , update_invoice , create_proposal , update_proposal , convert_estimate_to_invoice , get_document , list_my_documents and get_pdf create and revise real invoices, estimates and proposals. Not previews. Each one is created immediately, gets a public link, and is kept for 30 days. No account at any point. Leave. request_signup_link returns a single link that opens an Every account already holding everything the agent just made. open_app points existing customers at the right page. request_demo reaches sales. calculate_stack_cost and score_warm_lead expose the site's own calculators. get_more_tools records what an agent wanted and could not find, which becomes our roadmap signal. Why this is a strong fit for WebMCP, and what is newly possible A free tool that only a human can operate sits and waits for a human. The visitor has to find the page, understand the form, and fill it in. WebMCP moves the tool to where the person already is — mid-sentence, in the conversation where they said "I need to invoice this client." Three things became possible that were not before: A stranger can transact with us. Not a demo account, not a sandbox: a real document at a real URL that they can send to their client, with no sign-up, created by their agent on their behalf. The page can correct the model. Our video is the proof. Static marketing copy loses that argument; a tool surface wins it, because the tool is the ground truth. We can hear demand. get_more_tools means an agent that wants something we do not offer tells us so, in the moment, in its own words. How we built it WebMcpTools.tsx is a headless React island mounted once on the site. It feature-detects document.modelContext (falling back to the deprecated navigator.modelContext ) and, on a browser without WebMCP, registers nothing and renders nothing. Each tool is registered with registerTool : a JSON Schema inputSchema , annotations ( readOnlyHint , and untrustedContentHint on anything relaying text a third party wrote), and an execute that calls the same typed API client the site's human-facing forms use — so a document created by an agent and one created by a person land in the same session and the same list. Two design rules shaped everything. Results are written to be read aloud. The agent, not our UI, is doing the talking, so every result is a short self-contained string that ends in a usable next step, and a test asserts each one fits the budget. Guest documents mirror the product. They live in a completely separate database whose every user-settable column matches the product table it will one day become, so claiming a document into a real account is an insert of the same columns — lossless, not a re-entry. Because no engineer has a WebMCP-native browser in CI, we wrote a small in-page polyfill that installs document.modelContext only when a page opts in with ?webmcp=polyfill and no real implementation exists. The same registration and execute() path then runs in ordinary headless Chromium, which gave us a node --test suite and a Python harness that hands the tools to a live Claude model and runs a real agentic loop against the page. Challenges we ran into Keeping the guest schema identical to the product's so that claiming is lossless rather than a reconstruction. Designing get_pdf to be genuinely useful while still capturing a lead. Writing results an agent can relay verbatim without a model misreading a phrase as a system error. The hardest one was restraint. Our first version of the sign-up tool emailed the link. An adversarial review called it what it was: an unauthenticated endpoint that sends mail from our domain to any address a caller names — roughly 1,200 sends an hour from one machine. We cut the send entirely. The agent already has the link in the conversation the person is reading, so delivery added nothing and risked our sending reputation. The tool returns the link and nothing else. Accomplishments we're proud of It runs on the real production data path, not a demo backend. Every document a tool creates is real and has a real claim path into the product. And the surface is honest under pressure: check_fit tells people when Every is not for them, and search_help says when it does not know. What we learned Designing for an agent is not designing an API. It is closer to writing for a colleague who will repeat what you said to a customer, word for word, without checking. That changes every string. What's next The Chrome origin trial, so Chrome and Gemini users can see the tools at all. Then WebMCP inside the signed-in product, so a customer's agent can operate their actual workspace in the same tab. New work vs prior work every.ai existed before the Challenge, and this submission is evaluated only on what was added during the Submission Period. All of it was built on 2026-09-02 and 2026-09-03 , inside the window, with dated commit history in the public repository: the tool layer, the polyfill, the test suite, the agent-simulation harness, the guest document store and its API, the generator pages, /for-agents , and llms-full.txt . Before this window, the two generator URLs were six-line landing stubs with nothing behind them and the site registered no tools at all.
