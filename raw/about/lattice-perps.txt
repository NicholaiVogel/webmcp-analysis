Lattice Perps is our answer: a browser-local paper-trading experience where a human and a browser agent can use the same interface, the same account, and the same visible evidence. \n\n The project is inspired by Hyperliquid perpetual markets, but this public showcase intentionally stops at deterministic local simulation. \n\n What it does \n\n Lattice Perps is a paper trading flight recorder for WebMCP. \n\n The app starts with one browser-local paper account containing $100,000 of simulated USD and four fixed markets: \n\n \n BTC \n ETH \n SOL \n HYPE \n \n\n A human can place market or limit orders from the visible interface. Market orders fill at the displayed simulated mark price. Limit orders rest locally and can be cancelled by their local order ID. \n\n A browser agent can perform the same paper-trading actions through six WebMCP tools: \n\n \n paper_get_markets \n paper_get_portfolio \n paper_get_open_orders \n paper_get_activity \n paper_place_order \n paper_cancel_order \n \n\n Every human action, system event, and WebMCP call is written to the visible Agent Tape . The portfolio panel updates from the same underlying account state, showing equity, available balance, margin used, realised PnL, unrealised PnL, positions, open orders, and fills. \n\n The key idea is simple: \n\n \n One local account. One shared state. Two ways to interact. \n \n\n You can trade from the page or ask your browser agent: \n\n \n Buy 0.05 BTC at market, then show my paper portfolio. \n \n\n The result is visible in the Agent Tape and reflected in the portfolio immediately. \n\n How we built it \n\n The app is built with React, TypeScript, and Vite. \n\n The human interface and WebMCP tools share one LocalTradingStore . This prevents the UI and agent surface from developing separate balances, positions, orders, or activity histories. \n\n The store provides: \n\n \n deterministic simulated markets and mark prices \n market and limit order handling \n position netting and PnL calculations \n simulated fees and margin checks \n local order cancellation \n browser persistence through localStorage when available \n an in-memory fallback when browser storage is unavailable \n a visible activity history for human and WebMCP actions \n \n\n WebMCP registration is feature-detected through the browser's document.modelContext surface. If WebMCP is unavailable, the human trading interface still works. Tool inputs use explicit schemas and reject unexpected fields so the agent surface remains narrow and predictable. \n\n The project also includes automated tests for the local trading store, WebMCP tool definitions, and the rendered paper-trading interface. \n\n Safety by design \n\n This showcase deliberately has: \n\n \n no wallet connection \n no exchange connection \n no network order submission \n no real funds \n no private keys \n no deposits or withdrawals \n no production trading capability \n \n\n WebMCP is treated as an invocation layer, not an authentication or authorization mechanism. The public demo is designed to make the interaction model visible without pretending that a browser tool registration is equivalent to trading authority. \n\n Challenges \n\n The hardest part was making the human and agent paths genuinely share state. A separate “agent balance” or fake tool response would have made the demo look convincing while hiding the real interaction model. Instead, both paths call the same store and produce the same portfolio projections and activity records. \n\n Another challenge was making the demo useful even when the browser does not support WebMCP. The interface therefore remains complete on its own, while WebMCP enhances it when the browser exposes the API. \n\n Finally, we had to make the boundaries clear. A trading demo can easily imply that a real exchange, wallet, or signer is involved. The local simulation, explicit labels, and Agent Tape are designed to keep the demo honest. \n\n What we learned \n\n We learned that agent-native interfaces benefit from visible evidence, not just successful tool calls. A tool invocation is much easier to understand when the user can see its source, timestamp, status, and effect on the shared account. \n\n We also learned that deterministic simulation is valuable for WebMCP development. It makes the experience reproducible, easy to reset, and safe to demonstrate while the browser API and authority model are still evolving. \n\n What's next \n\n A future version could connect this interaction model to a separately approved testnet account behind explicit human authority, policy checks, and post-action reconciliation. \n\n For this submission, we intentionally keep the public experience local, deterministic, and risk-free. \n\n \n\n \n Built With \n\n chrome css3 html5 hyperliquid javascript localstorage openai react sites testing-library typescript vite vitest web-storage-api webmcp \n \n\n \n Try it out \n\n \n \n \n lattice-perps-testnet.tonyl-bw.chatgpt.site \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n The Ton Le \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n The Ton Le \n started this project\n \n —\n \n 4 days ago \n \n \n\n
