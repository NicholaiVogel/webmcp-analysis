Even Shopify's own storefronts ship this out of the\nbox now. But nobody's building for the person actually running the store.\nMost small merchants are one person juggling orders, stock, customer\nmessages, and everything else on their own. That felt like the real gap. \n\n What it does \n\n Merchant HQ is a back-office dashboard for a small store. You can click\naround it normally, or hand it to a WebMCP agent and ask it to check what\norders need fulfilling, restock something low, draft a reply to a customer,\nor set up a discount code. Whatever the agent does shows up live on your\nscreen, the same page you're looking at, no refresh needed. Each change gets\na quick colored flash so you can tell at a glance whether you did it or the\nagent did, and everything gets logged in an activity panel with the full\ndetails of what happened. \n\n Eight tools cover four areas: orders, inventory, messages, and discounts.\nCreating a discount code is the one action that actually costs the merchant\nmoney, so that specific tool won't run without the human approving it first,\nusing WebMCP's requestUserInteraction API. \n\n How I built it \n\n Next.js on Vercel, with the data (orders, inventory, messages, discounts)\nstored in Vercel KV so it actually persists. Each visitor gets their own\nsandboxed demo store. The tools are registered with\ndocument.modelContext.registerTool, and every one of them calls the same\nfunctions the regular UI buttons call, so there's never two different\nversions of what "true" looks like. \n\n Challenges \n\n The trickiest bug: WebMCP tool calls were updating the server correctly, but\nthe dashboard just sat there until you refreshed. Turned out the UI panels\nwere holding their own local copy of the data instead of reading from\nsomething shared. Had to rebuild that part so every panel reacts live to any\nchange, no matter which path it came from. \n\n The other one: requestUserInteraction is real, spec-defined, and I built it\ncorrectly, but I couldn't get either Chrome's tool inspector or ChatGPT's\nbrowser to actually trigger it end to end. Rather than silently skip the\nconfirmation when that happens, the tool just refuses and says so clearly. \n\n What I learned \n\n The interesting part of WebMCP isn't "an agent can click things for me," it's\nthat a page can hand an agent something completely different from a UI:\nstructured, chainable, inspectable actions instead of a screen to guess at.\nBuilding the activity log also made it obvious that trust is the real\nproblem in agentic commerce right now, not capability. Knowing an agent\ntechnically can do something isn't the same as knowing what it actually\ndid to your store. \n\n \n\n \n Built With \n\n chatgpt chrome git javascript json-schema next.js node.js react redis rest-api tailwind-css upstash vercel vercel-kv webmcp \n \n\n \n Try it out \n\n \n \n \n merchant-hq.vercel.app \n \n \n \n GitHub Repo \n \n \n \n youtu.be \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Koushik-Salammagari SALAMMAGARI \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Koushik-Salammagari SALAMMAGARI \n started this project\n \n —\n \n a day ago \n \n \n\n
