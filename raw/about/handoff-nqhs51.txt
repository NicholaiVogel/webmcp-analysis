It's slow, it's fragile, and it treats the agent like a human with a mouse instead of software that could just... call a function. \n\n Task management felt like the clearest place to make that contrast obvious. A Kanban board is something people already share with teammates why not share it with an agent too, and let both act on the same live state at the same time? \n\n What it does \n\n Handoff is a collaborative Kanban board. A human drags cards between To Do, In Progress, and Done exactly like any other Kanban tool. An AI agent manages the same board through seven WebMCP tools registered directly on the page: \n\n \n create_task , list_tasks , move_task , update_task , delete_task the core actions any task manager needs \n prioritize_tasks applies a batch of priority changes the agent has already reasoned about (via list_tasks ), atomically, in one call \n summarize_board a natural-language rollup of what's open, in progress, and done \n \n\n Both the human and the agent are working against the exact same Supabase-backed state, synced live over Supabase Realtime. When the agent creates or moves a card, it shows an "agent" badge and a brief highlight pulse, so at a glance you can see who did what. A live activity log underneath the board narrates the handoff as it happens: "You moved 'Fix login bug' to In Progress," "Agent created 'Update docs.'" \n\n There's no chat window bolted onto the side. The agent works through the same UI you're looking at. \n\n Why WebMCP fits this use case \n\n Without WebMCP, an agent that wants to help manage your board has exactly two bad options: a bespoke backend API it has to be specifically integrated with, or screen-scraping a drag-and-drop UI that was never designed to be driven programmatically, inferring which <div> is a card, simulating a drag gesture, and hoping the DOM didn't change underneath it. \n\n WebMCP replaces both of those with the page just telling the agent what it can do. document.modelContext.registerTool() exposes move_task with a typed schema ( id , status ) instead of forcing an agent to identify and drag a specific card. The agent doesn't need a separate integration, and it doesn't need to understand your UI, it needs to understand your tools, which you've defined precisely. \n\n That's the UX improvement in one sentence: an agent can now say "reprioritize my sprint so the login bug is high priority" and it works , live, immediately reflected in the same board a human is looking at, without OpenAI, Anthropic, or anyone else needing to have built a Handoff-specific integration ahead of time. The website itself is the integration. \n\n What's newly possible \n\n Before WebMCP, "human and agent share a task board" basically meant the agent had its own separate interface (a chat window, a CLI) that happened to write to the same database, two disconnected experiences bolted together. WebMCP lets both parties act through the same page, the same session, the same state, at the same time. You can watch a card move because you dragged it, or because you asked an agent to move it, and the board doesn't care which, it just reacts. That's a genuinely different interaction model, not just a faster version of the old one. \n\n How we built it \n\n \n Next.js / React , deployed on Vercel \n Supabase (Postgres + Realtime) for shared task storage; every client (human tab or agent-driven tab) subscribes to the same Realtime channel, so changes from either side propagate instantly \n WebMCP , implemented via direct document.modelContext.registerTool() calls (see hooks/useWebMCPTools.js ) each tool's execute function calls the exact same functions the drag-and-drop UI calls ( hooks/useTasks.js ), so there is one source of truth for board logic, not a parallel "agent path" that could drift out of sync with the human path \n @hello-pangea/dnd for the human-facing drag-and-drop \n The activity log is derived from the same Realtime subscription that drives the board, no separate logging table, just an in-memory feed of what the subscription already sees \n \n\n Challenges we ran into \n\n WebMCP is genuinely early. I hit a real interoperability bug where a React wrapper library's handler callback wasn't being translated into the native execute property the browser's registerTool() implementation expects, which surfaced as execute is not a function only at call time, not at registration time, which made it harder to catch. We moved to calling the native imperative API directly rather than depending on a wrapper layer, which fixed it and also made the WebMCP usage more explicit in the codebase. \n\n Accomplishments \n\n A full round trip, human drags a card, agent calls a tool, board updates live for both working end to end, verified both through direct browser console calls to document.modelContext.executeTool() and through a real natural-language agent (Google's Model Context Tool Inspector) discovering and calling our tools correctly. \n\n What's next \n\n Multi-board support, authenticated multi-user boards, and finer-grained permissions per tool (e.g., a read-only list_tasks -only agent versus a full-access one) \n\n Built with \n\n Next.js, React, Supabase, Supabase Realtime, WebMCP ( document.modelContext.registerTool ), @hello-pangea/dnd, Vercel \n\n \n\n \n Built With \n\n nextjs supabase supabaserealtime webmcp \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n handoff-webmcp.vercel.app \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Bilal Nadeem \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Bilal Nadeem \n started this project\n \n —\n \n a day ago \n \n \n\n
