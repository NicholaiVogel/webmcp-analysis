A trip finder with real, slow fare searches and a Cancel button that actually cancels - timers clear, nothing lands after, and the agent knows exactly what it never saw. Like Comment Story Updates The trip finder: destinations, budget, and dates Tool console: get_brief tool called live via WebMCP WebMCP surface: long-running tools accept execute(args, {signal}) and are genuinely abortable - a cancelled search stops mid-flight, not just in the UI. Inspiration "Somewhere warm under ₹40,000 for four days from Bengaluru" is a complete brief to a friend and an impossible query to a travel site, which wants a destination first, then makes you wait through a slow search per place - with no way to say "that's enough, I've seen what I need." What it does Jhola exposes catalogue, fare search, stay availability, and hold as tools. The agent runs one slow search across twelve destinations while results land one card at a time; the moment the traveller has seen enough, they press Cancel and the search stops honestly - timers cleared, nothing lands afterward, the agent told exactly what was found and what was never searched. A cancelled search returns a first-class partial report, never an error. Booking is irreversible, so there's no book tool at all - Book is a human-only button; holding is reversible, so hold_itinerary is a tool. How we built it execute(args, { signal }) , honoured all the way through: search_fares and check_stays advance through staged timers that obey the AbortSignal Chrome hands every tool call. One AbortController per call, shared by all four ways a call can end - the in-flight strip's own Cancel, the tool console's Cancel, the cancel_call tool, or the caller's own signal - and the activity log always says which one fired. Challenges we ran into Building runtime fallbacks for when Chrome's real cancellation bridge has gaps: if a Cancel click doesn't visibly end the in-flight record within 250ms, the console aborts the call directly and says so; if executeTool() 's own promise doesn't resolve with the string the call actually produced, the console reads it off the call's own record instead - both proven against a simulated broken bridge, not just the happy path. And, like its sibling apps, a self-abort race in hold_itinerary 's dynamic registration, found and fixed with the same deferred-abort pattern. Accomplishments that we're proud of A cancel that is actually honest - a stopped search names exactly what it never searched, instead of pretending it finished or silently discarding the question. What we learned Real cancellation UX needs a fallback story, not just a happy-path signal - a judge's browser, a flaky bridge, or a headless test environment can all diverge from the ideal case, and the app has to stay honest in every one. What's next A price-drop watch tool that re-checks a held itinerary's fare periodically and surfaces it only if it's dropped, without the traveller having to ask again.
