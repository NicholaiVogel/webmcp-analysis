That creates friction: users copy data into chat, interpret the answer, and then manually reconcile it back into their working system. \n\n Sourcing Scenario Room came from the idea that this interaction should be different: the buyer and the AI agent should operate on the same visible sourcing state through WebMCP, while the human keeps decision authority. \n\n What it does \n\n The application starts from a fictional sourcing case with three supplier offers evaluated across five dimensions: price, delivery lead time, capacity, quality, and supply risk. \n\n The buyer can express sourcing intent in natural language. Through WebMCP, the agent reads the current application state and updates the shared workspace directly. \n\n A typical flow is: \n\n \n The agent reads the current sourcing case. \n The buyer makes delivery within 12 weeks mandatory, prioritizes supply continuity, and asks to keep two suppliers alive. \n The agent updates the workspace and creates an AGENT PROPOSAL. \n The agent generates a negotiation plan for the live shortlist. \n The buyer revises the proposal directly in the application, for example by keeping Boreal in the shortlist while limiting the acceptable price premium to 3%. \n The workspace becomes HUMAN-REVISED. \n The agent reads that revision and adapts the negotiation plan accordingly. \n \n\n The agent can propose and adapt, but it cannot award a supplier. Decision authority remains with the human buyer. \n\n How we built it \n\n Sourcing Scenario Room is a client-side React/Vite application using native WebMCP through document.modelContext.registerTool() . \n\n It exposes three WebMCP tools: \n\n \n get_sourcing_case \n update_sourcing_scenario \n draft_negotiation_plan \n \n\n The human interface and the WebMCP tools operate on the same canonical React sourcing state through shared application actions. \n\n There is no backend, database, authentication layer, OpenAI API integration, or external API dependency. \n\n Challenges we ran into \n\n The main challenge was designing a demo that made the human-agent interaction clear without hiding it behind unnecessary complexity. \n\n I deliberately limited the case to five sourcing dimensions, three suppliers, and three WebMCP tools. \n\n Another challenge was preserving human decision authority. The application therefore makes the state transitions explicit: \n\n BASE CASE → AGENT PROPOSAL → HUMAN-REVISED \n\n This makes it visible when the agent has proposed something, when the human has changed it, and when the agent is responding to the latest human decision. \n\n Accomplishments that we're proud of \n\n The most important result is that the agent is not simply generating advice beside the application. \n\n The buyer and agent work through the same sourcing workspace. The agent can read the current state, modify the scenario, generate a negotiation artifact, observe a later human revision, and adapt to it. \n\n That creates a genuine human-agent loop while keeping supplier selection authority with the buyer. \n\n What we learned \n\n The biggest insight was that WebMCP changes the interaction model. \n\n The valuable part is not simply allowing an AI to call functions. It is enabling the human and the agent to collaborate through the same visible application state. \n\n Human revisions become first-class inputs to the next agent action instead of context that must be manually reconstructed in chat. \n\n What's next for Sourcing Scenario Room \n\n The same pattern could extend to richer procurement workflows such as tender preparation, supplier risk, negotiation tracking, sourcing approvals, and contract review. \n\n More broadly, the approach could apply to enterprise workflows where humans and agents need to collaborate on structured decisions while preserving explicit human authority. \n\n \n\n \n Built With \n\n css html javascript react typescript vite webmcp \n \n\n \n Try it out \n\n \n \n \n sourcing-scenario-room.replit.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Camilo González \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Camilo González \n started this project\n \n —\n \n 2 days ago \n \n \n\n
