The important context ends up fragmented across systems. Teams need to understand what happened, decide what to do, control consequential changes, and preserve a reliable record. \n\n AmbiOS AI explores a different model: \n\n What if an AI agent could investigate operational context while people remain responsible for meaningful decisions? \n\n WebMCP helps with the browser side of that model. A compatible browser agent can use structured tools exposed by the active AmbiOS workspace instead of trying to infer state from screenshots, DOM structure, or button locations. \n\n AmbiOS AI is a governed workspace for people and agents working through operational incidents together. The agent investigates available context and prepares structured proposals. AmbiOS keeps identity, workspace scope, policy, approval, execution, verification, and audit authority on the backend. \n\n What it does \n\n AmbiOS AI helps teams investigate operational work across connected systems. \n\n A user opens an AmbiOS workspace and reviews an incident, service, deployment target, provider connection, or action record. A compatible browser agent can use WebMCP tools to retrieve structured context from the active workspace. \n\n The agent can: \n\n \n Read workspace readiness and available capabilities. \n Inspect active incidents. \n Review incident context and linked systems. \n Inspect verified provider connection and mapping status. \n Read action, approval, verification, and audit state. \n Prepare a structured proposal. \n Retrieve a backend policy decision. \n Explain what is known, unknown, blocked, or awaiting review. \n \n\n AmbiOS does not treat chat as permission. \n\n For consequential work, AmbiOS follows this workflow: \n Investigate\n→ verify available context\n→ prepare a structured proposal\n→ evaluate policy\n→ request exact approval\n→ execute through an authorized provider adapter\n→ verify the outcome\n→ record the audit trail\n \n The user reviews the exact target, scope, risk, approval requirement, and verification plan before any consequential external action proceeds. \n\n Core workflow \n\n A typical AmbiOS workflow looks like this: \n User opens an incident\n→ AmbiOS loads workspace readiness\n→ Agent inspects incident context\n→ Agent reads linked systems and mapped resources\n→ Agent identifies verified facts and unknowns\n→ Agent prepares a structured proposal\n→ AmbiOS evaluates policy\n→ User approves or denies the exact proposed action\n→ AmbiOS executes only when backend requirements are satisfied\n→ AmbiOS verifies the defined outcome\n→ Runs, Console, and Canvas show the resulting record\n \n If a prerequisite is missing, AmbiOS does not silently continue. \n\n For example: \n Deployment target is not mapped\n→ action becomes blocked\n→ AmbiOS explains what is missing\n→ user configures the required mapping\n→ AmbiOS verifies the mapping with a safe read\n→ the action resumes from its stored context\n→ approval remains required before execution\n \n WebMCP use case \n\n WebMCP fits AmbiOS because the agent needs current, structured workspace context from the browser session. \n\n A chat transcript does not reliably show: \n Which workspace is active\nWhich incident is selected\nWhich systems are linked\nWhich provider connections are configured\nWhich resources are mapped\nWhich action is blocked\nWhich approval is pending\nWhich execution is running\nWhich verification passed or failed\n \n With WebMCP, the active AmbiOS site exposes structured browser tools for compatible agents. \n\n The agent does not need to scrape the page or guess how the interface works. It receives structured information from the same workspace the user is viewing. \n\n WebMCP supports the browser-side collaboration layer. \n\n AmbiOS still enforces all consequential authority in backend services. \n WebMCP\n→ browser-native structured context and tool access\n\nAmbiOS backend\n→ authentication\n→ organization and workspace scope\n→ provider capabilities\n→ resource mappings\n→ policy\n→ approval\n→ execution\n→ verification\n→ audit\n \n https://webmcp.com/report/f5270653-0587-4512-acf6-461d86e0ebcb \n\n WebMCP does not grant the agent unrestricted provider access. It does not expose provider credentials. It does not replace approval or backend authorization. \n\n Remote MCP and ChatGPT \n\n AmbiOS also supports remote MCP access through OAuth. \n\n This lets users connect their own ChatGPT account to their authorized AmbiOS workspace. \n ChatGPT\n→ MCP OAuth authorization\n→ AmbiOS validates user and workspace scope\n→ ChatGPT receives authorized MCP tool access\n→ AmbiOS returns structured, scoped results\n \n ChatGPT acts as an MCP client. \n\n AmbiOS remains responsible for: \n Authentication\nOrganization and workspace authorization\nProvider capability checks\nResource mapping validation\nPolicy\nApproval\nExecution\nVerification\nAudit\n \n A successful ChatGPT OAuth connection does not automatically mean that a provider is connected, a target is mapped, an action is approved, or an external action has completed. \n\n Provider model \n\n AmbiOS treats each connected provider as a separate system with separate permissions, resources, APIs, and failure modes. \n\n A connected account is not the same as an authorized action. \n\n Before AmbiOS can perform a provider action, it must confirm: \n Provider connection exists\n→ connection belongs to the current workspace\n→ safe provider verification succeeds\n→ required provider capability exists\n→ target resource is visible\n→ target resource is explicitly mapped\n→ policy allows the action\n→ exact approval exists where required\n→ action is safe to execute\n→ outcome can be independently verified\n \n Provider connection states are explicit: \n Not configured\nAuthorization pending\nConnected, verification required\nConnected, limited access\nConnected, verified\nNeeds re-authentication\nSyncing\nSync failed\nUnavailable\nUnsupported\nPlanned\n \n AmbiOS does not imply that every connected vendor works with every other vendor. \n\n Cross-system workflows are controlled sequences. \n GitHub action succeeds\n→ Cloudflare preview deployment fails\n \n AmbiOS records partial success. It does not claim the workflow completed. \n GitHub PR created\nCloudflare deployment failed\nNo production change confirmed\nReview failure details\nRetry or create a separately approved compensating action\n \n Security and governance \n\n AmbiOS separates agent reasoning from operational authority. \n\n The agent can inspect data, explain evidence, and prepare a proposal. \n\n The backend controls actual actions. \n Authenticated user\n→ organization scope\n→ workspace scope\n→ role and capability checks\n→ verified provider connection\n→ explicit resource mapping\n→ policy evaluation\n→ exact human approval\n→ execution revalidation\n→ independent verification\n→ audit record\n \n A message such as “yes,” “approve,” or “do it” is not enough to authorize an external action. \n\n Each approval is bound to the exact action. \n Approver\nOrganization\nWorkspace\nAction\nProvider\nTarget resource\nEnvironment\nArguments hash\nPolicy decision\nRisk level\nExpiry\nSingle-use state\n \n Immediately before execution, AmbiOS rechecks the approval, user role, provider capability, mapping, target, arguments, preconditions, and idempotency state. \n\n Action states \n\n AmbiOS tracks meaningful work through a durable lifecycle: \n DRAFT\n→ CONTEXT_GATHERED\n→ BLOCKED_MISSING_PREREQUISITE\n→ PROPOSED\n→ POLICY_EVALUATED\n→ AWAITING_APPROVAL\n→ APPROVED\n→ QUEUED\n→ EXECUTING\n→ VERIFYING\n→ SUCCEEDED\n→ FAILED\n→ PARTIALLY_SUCCEEDED\n→ DENIED\n→ CANCELLED\n→ EXPIRED\n \n The same state should appear across: \n Agent\nIncidents\nApprovals\nDeployment\nRuns\nConsole\nServices\nSystems\nCanvas\n \n A user should not have to guess whether an action was proposed, approved, queued, running, blocked, denied, failed, or verified. \n\n Audit and verification \n\n AmbiOS does not treat request submission as completed work. \n\n A provider request might be accepted while the desired result still fails. \n\n For example: \n GitHub request accepted\ndoes not prove the pull request exists as intended\n\nCloudflare deployment request accepted\ndoes not prove the preview is healthy\n\nAgent explanation\ndoes not prove root cause or verification\n \n AmbiOS records material workflow events: \n Agent run started\nReadiness checked\nTool invoked\nProposal created\nPolicy evaluated\nApproval requested\nApproval approved\nApproval denied\nAction queued\nExecution started\nProvider response received\nVerification started\nVerification passed\nVerification failed\nAction completed\nAction failed\nAction partially succeeded\n \n Verification checks the provider or target independently. \n\n Examples: \n GitHub:\nConfirm expected branch, pull request, source branch, base branch, and revision.\n\nCloudflare:\nConfirm expected project, preview deployment, deployment status, preview URL, and health endpoint.\n\nInternal record:\nConfirm persisted action state, expected derived state, and audit completion.\n \n Canvas collaboration \n\n The AmbiOS Canvas is an operational view of persisted work. \n\n It is not a whiteboard and it is not a decorative vendor graph. \n\n The Canvas can show: \n Incident\nService\nRepository\nDeployment target\nProvider connection\nEvidence\nProposal\nPolicy decision\nApproval\nExecution\nVerification\nAudit record\n \n Relationships use explicit labels: \n source_of_change\ndeploys_to\nrequires_approval\nverified_by\ntriggered_proposal\nproduced_audit_event\nawaits_configuration\nblocked_by\n \n The agent cursor represents real workflow state. \n Inspecting\nBlocked\nProposal ready\nAwaiting approval\nApproved\nQueued\nExecuting\nVerifying\nSucceeded\nFailed\nPartially succeeded\n \n The cursor does not imply work that has not occurred. \n\n Technical architecture \n Vercel Next.js frontend\n→ AmbiOS user interface\n→ WebMCP browser registration\n→ Agent workspace\n→ Canvas\n→ typed frontend API client\n\nCloudflare Hono Core Worker\n→ authentication validation\n→ workspace and organization scope\n→ incident, action, approval, audit, and Canvas APIs\n→ MCP OAuth\n→ MCP metadata\n→ MCP tool endpoints\n→ D1-backed durable state\n\nCloudflare Connector and Execution Worker\n→ provider connection lifecycle\n→ provider OAuth callbacks\n→ webhook validation\n→ queue processing\n→ approved provider actions\n→ verification\n→ retries and recovery\n\nCloudflare D1, KV, R2, and Queues\n→ durable state\n→ short-lived state\n→ artifacts\n→ retryable background work\n \n AmbiOS uses Cloudflare Workers for thin request paths and durable background processing for provider-dependent or retryable work. Cloudflare Workers Free currently includes 100,000 requests per day and 10 ms of CPU time per invocation, so request handlers should validate, read minimal state, and delegate long-running work to queues. developers.cloudflare \n\n What has been built \n\n AmbiOS includes: \n Next.js frontend\nCloudflare Hono Core Worker\nCloudflare Connector Worker\nMCP route handling\nMCP OAuth route handling\nProtected-resource metadata\nAuthorization-server metadata\nShared MCP resource registry\nShared service-origin configuration\nOpenAPI contract\nInteractive smoke-harness structure\nWebMCP registration code\nWorkspace, incident, action, policy, approval, audit, provider, and Canvas foundations\n \n The repository also contains project-level build, lint, test, security, deployment, and documentation foundations. Compatible browser agents can use those tools instead of relying on page scraping. Browser support and client behavior are evolving, so AmbiOS uses feature detection and preserves normal UI behavior when WebMCP is unavailable. developer.chrome \n\n OAuth must match exactly \n\n Remote MCP requires consistent public configuration. \n\n The MCP URL, protected resource metadata, OAuth issuer, authorization endpoint, token endpoint, resource audience, scope registry, and OpenAI submission configuration must agree. \n\n A mismatch can prevent an MCP client from completing authorization. \n\n AmbiOS uses a shared MCP resource registry and service-origin configuration to reduce URL and scope drift. [github_mcp_direct] \n\n Provider integration is capability-based \n\n OAuth connection alone does not prove an intended resource is accessible or that an action is safe. \n\n AmbiOS separates: \n Connection\nCapability\nResource mapping\nPolicy\nApproval\nExecution\nVerification\n \n This prevents a provider logo or connected status from being mistaken for unrestricted authority. \n\n Cross-vendor work is sequential \n\n GitHub, Cloudflare, Snyk, Socket.dev, Notion, Shopify, and other vendors do not share one transaction coordinator. \n\n AmbiOS models multi-vendor workflows as controlled sequences: \n Validate prerequisites\n→ create proposal\n→ evaluate policy\n→ obtain approval\n→ execute one step\n→ verify one step\n→ execute next step\n→ verify next step\n→ record partial success or failure\n→ offer recovery option\n \n AmbiOS does not claim atomic cross-vendor execution. \n\n What we learned \n\n WebMCP is a context layer \n\n WebMCP is not the AI model.\nWebMCP is not the provider API.\nWebMCP is not the authorization boundary.\nWebMCP is not a sandbox. \n\n WebMCP gives compatible browser agents structured access to the active web workspace. \n\n AmbiOS provides the governance layer around that access. \n\n Human approval enables safe delegation \n\n The useful alternative to uncontrolled automation is not a blocked workflow. \n\n It is a workflow where: \n Agent investigates\n→ agent explains\n→ agent proposes\n→ human reviews exact scope\n→ human approves or denies\n→ backend executes only approved work\n→ system verifies the result\n→ audit record persists\n \n A provider connection is only the first step \n\n A connected provider account does not prove: \n Correct workspace\nCorrect resource\nCorrect environment\nCorrect permission\nCorrect policy\nCorrect approval\nCorrect outcome\n \n AmbiOS must verify each layer. \n\n UI must represent state \n\n A chat transcript is not enough for governed work. \n\n The user needs visible state for: \n Readiness\nEvidence\nProposal\nPolicy\nApproval\nExecution\nVerification\nAudit\n \n What is next \n\n Near-term \n Complete deployed MCP OAuth verification.\nComplete
