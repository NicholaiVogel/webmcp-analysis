But greater capability also creates a new problem. \n\n As tasks become longer and the amount of context grows, it becomes harder for an AI system to maintain reliable reasoning across everything it has to process. Important details can be missed, reasoning can drift, and hallucinations can become harder to detect. \n\n That is why I believe greater AI capability should be paired with clearer Human Gates. \n\n Diamond Control started from this idea: let the agent do as much useful work as possible, but keep explicit Human checkpoints at the decisions where correctness, authority, or risk really matter. \n\n I did not want the Human to approve every small step. I wanted the AI to be able to work independently until it reaches a decision that genuinely belongs to the person. \n\n What it does \n\n Diamond Control is a human-gated agent workspace built with WebMCP. \n\n It gives an AI agent a structured way to understand the current workflow, identify what needs attention, recommend a bounded next move, prepare that action, and request Human review. \n\n The application exposes five WebMCP tools: \n\n \n get_workspace_state \n get_attention_items \n recommend_next_move \n prepare_action \n request_human_gate \n \n\n The first three tools read or recommend without changing the workflow. \n\n prepare_action can create a reversible proposed action, and request_human_gate can move that proposal into AWAITING_HUMAN . \n\n But no WebMCP tool can approve or reject an action. \n\n The final decision remains in the visible Human Gate. \n\n In the demo, the agent identifies the proof-repair lane, recommends Review and run proof validation , prepares the proposal, and requests Human review. \n\n The workflow enters AWAITING_HUMAN , where the agent stops. \n\n The Human then chooses Reject, and Diamond Control produces a NO_ACTION proof receipt showing that the decision was made by the Human. \n\n How I built it \n\n Diamond Control is a browser-based application built with TypeScript/JavaScript, HTML, CSS, and WebMCP. \n\n The main design goal was not simply to connect an AI agent to a web interface. I wanted the workflow itself to expose enough structure that the agent would not have to guess what the page means from buttons and text alone. \n\n WebMCP provides explicit tools for: \n\n \n reading workflow state \n discovering items that need attention \n recommending a next move \n preparing a bounded action \n requesting Human review \n \n\n Behind those tools is a small state model that separates agent preparation from Human authority. \n\n A proposal can move through states such as PROPOSED and AWAITING_HUMAN , but only the visible Human controls can produce an APPROVED or REJECTED decision. \n\n I also added a fail-closed rule: if one proposal is already waiting at the Human Gate, the agent cannot silently replace it with another proposal. The Human must resolve the existing decision first. \n\n The project is intentionally browser-side and small. It does not depend on a backend, database, authentication system, private user records, or an automatic approval service. \n\n Challenges I ran into \n\n The main challenge was not making the agent more capable. \n\n The harder problem was deciding exactly where that capability should stop. \n\n I had to separate several concepts that can easily become mixed together in an AI workflow: \n\n \n reading information versus changing state \n recommending an action versus executing a decision \n preparing work versus authorizing it \n agent capability versus Human authority \n successful automation versus correct execution \n \n\n Another challenge was making the boundary visible and testable rather than keeping it as an instruction written only in a prompt. \n\n That is why Diamond Control uses explicit workflow states, a visible Human Gate, and a proof receipt after the decision. \n\n I also learned that long AI workflows need clear checkpoints. If every small action requires Human confirmation, the system becomes too manual. But if the AI is allowed to continue without clear boundaries, it becomes difficult to know when Human judgment is actually required. \n\n Finding that balance became the central design problem of the project. \n\n Accomplishments that I'm proud of \n\n I am proud that Diamond Control demonstrates a complete agent-to-Human workflow rather than only exposing a collection of WebMCP tools. \n\n The demo shows a natural-language request moving through the entire process: \n\n \n the agent reads the workspace \n identifies what needs attention \n recommends one next move \n prepares the action \n requests Human review \n stops at AWAITING_HUMAN \n the Human makes the final decision \n the system produces a proof receipt \n \n\n I am also proud that the authority boundary is enforced by the application itself. \n\n The agent cannot approve or reject an action, and it cannot replace another proposal while an unresolved Human Gate is open. \n\n For me, this is important because Human control should not depend only on asking an AI model to behave correctly. The workflow should make the boundary explicit. \n\n What I learned \n\n I learned that WebMCP becomes much more useful when it gives an AI agent a flexible, structured way to understand and interact with a workflow, instead of limiting the interaction to a small set of rigid buttons. \n\n A good agent interface should expose meaningful state, available actions, constraints, and decision boundaries. \n\n This allows the AI to adapt its help to the situation while still operating inside explicit rules. \n\n For me, the value of WebMCP is not just automation. \n\n It is making the collaboration between the Human, the interface, and the AI more flexible without losing control. \n\n I also learned that giving an agent more autonomy does not necessarily mean giving it more authority. \n\n Those are two different things, and separating them can allow an AI system to do substantially more work while still preserving the decisions that should remain Human. \n\n What's next for Diamond Control \n\n The next step is to make the boundaries between autonomous AI work and Human authority much more complete and explicit. \n\n With stronger boundaries, agents should be able to run longer tasks on their own, carry work across multiple steps, and automatically bring the workflow to the correct Human Gate when a real decision is required. \n\n The goal is to reduce unnecessary manual coordination. \n\n Humans should not have to supervise every small step. They should be asked to intervene only at clear checkpoints where judgment, authority, or risk actually matters. \n\n Over time, I would also like to extend the same pattern to more complex workflows, more types of actions, stronger proof and recovery mechanisms, and multiple agent environments. \n\n If these boundaries are designed well, AI agents can become more autonomous while execution still remains aligned with the correct level of Human authority. \n\n \n\n \n Built With \n\n css github-page html javascript webmcp \n \n\n \n Try it out \n\n \n \n \n kiencuongnguyen88.github.io \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n kiencuongnguyen88 Nguyen \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n kiencuongnguyen88 Nguyen \n started this project\n \n —\n \n 6 days ago \n \n \n\n
