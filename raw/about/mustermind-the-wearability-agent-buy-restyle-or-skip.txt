The first shopping agent that can tell you not to buy. Buy, restyle, wait or skip — every verdict cited to you, to product data, or to the rules, live over WebMCP. Like Comment Story Updates Inspiration We started somewhere else. The first idea was a size recommender — obvious fashion-commerce problem. Then we opened DevTools on a live AJIO product page and found something that reframed the whole project. Sitting in window.__PRELOADED_STATE__ , invisible to any agent driving the DOM, was a size chart already converted to centimetres , an explicit measurementType: "Garment Measurement" provenance flag, live per-size stock counts, and — the thing we didn't expect — a crowd fit distribution: Perfect 64% · Tight 15% · Too Tight 5% · Loose 11% · Too Loose 3% over 2,100 raters The page already knew this garment runs small. It had no way to tell an agent. But the moment that actually defined the product came later. Our first working version ranked a ₹320 polo as the top buy for a client dinner. It was cheap, in stock, not a duplicate, and technically satisfied every constraint. It was also completely wrong — a polo does not become client-dinner appropriate because it is cheap. That is the failure mode of every shopping agent we've used. They can only say buy , so they optimise for the one signal they can read: price and availability. We rebuilt the engine around a different question — what if the agent could say no? What it does Mustermind is a wearability decision layer. You give it an occasion, a budget, a PIN code, a deadline, fits you avoid, and a rough list of what you already own. It scores live AJIO products on four axes: product facts, your constraints, purchase risk, and rewear value. Every garment gets one of four verdicts: Verdict Meaning buy Worth buying for this occasion restyle You can already assemble this look from what you own wait Right piece, wrong price or arrives too late skip Violates a stated constraint, duplicates something owned, or can't be delivered Every verdict carries the factors behind it, and every factor is tagged with its source — you, product data, or the rules. A real card from the running app: RESTYLE — You can get this look from what you own U.S. Polo Assn. · Men Button Down-Collar Tailored Fit Shirt · ₹1,175 + Within budget [user] ₹1,175 against a ₹3,000 ceiling − Close to what you own [rules] You already have White Shirts; this adds a colour, not a category · Rewear value [rules] Pairs with 1 item you already own + Right register [rules] Shirts suits client dinner + Fit confidence [product] 90% — garment measurements published, 77 fit ratings + Suggested size M [product] 16% of 77 raters found this loose vs 5% tight, so one size down · Deliverable, no date [product] Serviceable at 560029; the delivery API did not return a date That last line matters as much as the verdict. The delivery API returned no date, so the app doesn't invent one. Load the default brief and Mustermind recommends nothing. Two restyles, five skips, four different skip reasons. Then tell the agent "I could stretch to ₹5,500" and a blazer becomes the single buy — on screen, with the reason visible, and the change written to a Decision Ledger showing that you made it. How we built it Zero npm dependencies. Node 20 and vanilla HTML/CSS/JS. Nothing to install, no lockfile, no bundler — a judge can read the entire thing. It ships as a ~55 MB Alpine container running non-root. Five WebMCP tools , registered on document.modelContext with navigator.modelContext as a fallback probe, behind feature detection: Tool readOnlyHint untrustedContentHint get_current_style_brief ✅ — get_product_truth ✅ ✅ evaluate_wearability ✅ ✅ record_user_tradeoff — — prepare_purchase_handoff — — Five, deliberately. Tool selection degrades as the set grows, and each description is written as product surface — when to call it, what changes state, and when to ask instead of assert . The verdict engine is a rule engine, not a model. This was a deliberate constraint: the agent has to narrate why a verdict is what it is, and a scorer you cannot read gives it nothing to say. Gradient boosting would have scored marginally better and been useless on camera. Crowd fit becomes a directional prior. Too Tight and Too Loose count double — they signal a full size off, not a preference: $$\text{skew} = \frac{\left(t + 2t^{+}\right) - \left(l + 2l^{+}\right)}{100}$$ where $t, l$ are the tight and loose percentages and $t^{+}, l^{+}$ the too tight / too loose ones. We call RUNS_SMALL above a weighted gap of 6. At the rater counts these products carry, the standard error on a $p \approx 0.20$ proportion over $n = 2100$ is $$\sigma = \sqrt{\frac{p(1-p)}{n}} \approx 0.0087 \approx 0.9\ \text{pp}$$ so a 6-point weighted gap is several standard errors — signal, not noise. Below 50 raters we return INSUFFICIENT_DATA and refuse to call it at all. Two public AJIO sources , called server-side only: the PDP aggregator and the delivery-promise API, with a 60-second cache and hard timeouts. The style-code invariant is strict — only codes this server obtained from AJIO's own search, or ships fixtures for. Never a code supplied by the browser. No anti-bot sensor header is sent, stored or committed anywhere. If a call would need one, the app falls back to clearly-labelled fixtures instead. There's a grep in the verification step that fails the build if such a string ever appears in the tree. 55 assertions, no test framework. node scripts/selfcheck.js . Challenges we ran into The WebMCP API is not the MCP API. Our tools returned {content:[{type:'text',text:...}]} — the envelope a remote MCP server uses. Chrome's execute returns a plain string . Every result would have arrived as a stringified wrapper the agent had to unwrap. We also assumed an unregisterTool method; there isn't one — unregistration is an AbortSignal passed at registration. Both were caught only by reading Chrome's docs against our own code. The silent one: origin isolation. WebMCP is only exposed in origin-isolated documents. Without Origin-Agent-Cluster: ?1 , document.modelContext is simply undefined — no error, no warning, nothing to debug. You'd naturally blame your Chrome version and go chasing an upgrade that was never the problem. Real data is hostile in small ways. numUserRatings is "2.1K" , a display string — parse it naively and you fabricate a rater count. Percentages arrive as "15 %" , with a space. The size chart is a superset of what's purchasable (8 charted, 5 buyable on one real product), so recommendations must come from the intersection. One live product returned a fittingType of " " — whitespace, which is truthy, and rendered a factor row with blank evidence. A truthful API answer that was useless. Our demo fixtures had invented SKUs. The live delivery API dutifully returned "not serviceable" for them — which is true, and means the SKU doesn't exist , not that the garment can't be delivered. We were putting fabricated products on real-looking hard fails. Fixture products no longer consult live delivery. A regression we caused ourselves. When live search landed, it loaded eight real style codes — and the PDP allowlist, which only knew about fixtures, rejected every one. The app rendered empty under a confident "Live AJIO data" badge. Fixing it meant sharpening the invariant rather than loosening it: codes AJIO's own search returned are server-obtained, so they earn a session allowlist; browser-supplied codes never do. Then the fix had its own bug — the search cache outlived the session allowlist, so the first Reset handed back codes the adapter then refused. Both are now regression-tested. Knowing when to stop being clever. The hardest call was making wrong register a hard stop instead of a weighted negative. Softening it makes price pull junk back to the top of the list, and the whole argument collapses. Accomplishments that we're proud of It opens with zero buys. A recommender that cannot say "you already own something that works" will eventually sell you a fourth white shirt. Getting the rules honest enough to recommend nothing — and then having that be the most compelling thing on screen — is the accomplishment. Four skips, four different reasons. Wrong register, already owned, avoided fit, undeliverable. Not one score threshold wearing four hats. The agent cannot spend your money. prepare_purchase_handoff is two-phase: it returns AWAITING_CONFIRMATION , a card appears, and only a real DOM click mints a single-use token — bound to style code and size, expiring in 60 seconds. Guessing an ID, replaying a used one, or swapping the size after confirmation all fail, and all four are asserted. There is no cart, checkout, login, orders or payment access anywhere in the codebase. It degrades honestly. Fixture mode is labelled in a banner, a header badge, and a per-card pill, and tool results carry dataSource so the agent discloses it. Serviceable-with-no-date says exactly that. Too-few-raters refuses to call the fit. It works without WebMCP. Every tool has a visible control equivalent, and the header says so. Progressive enhancement, not a demo that only exists behind a flag. What we learned Tool descriptions are the product, not documentation. They encode call ordering, failure semantics, and when the agent should ask rather than assert. We rewrote them more times than we rewrote the engine. Structured refusal is a feature. INSUFFICIENT_DATA , "the delivery API did not return a date", "this is demo data" — every one of these is less satisfying than a confident answer and more useful than a wrong one. Calibration beats confidence. Source attribution changes the interaction. Once every factor is tagged user / product / rules , the shopper stops arguing with a black box and starts arguing with a specific line. "You already have White Shirts" is contestable in a way that a 0.73 confidence score never is. Provenance has to be modelled, not assumed. The fixture-SKU delivery bug and the empty-live-results bug were both provenance failures — treating data from one origin as if it came from another. productProvenance and the session allowlist exist because of them. Write the assertion when you fix the bug. Four real bugs were caught by the self-check during the build, and two of them were regressions of things we'd already fixed once. What's next for MusterMind - The wearability agent — buy, restyle, or skip Sharpen restyle . It currently fires on near-duplicate plus low rewear, which is right for a two-item wardrobe and too eager against a full one. It needs a formality gradient, not just category adjacency. Rewear value that understands clothes. Today it counts pairings by category. No colour theory, no formality ladder, no notion that you might simply dislike the thing. Purchase history as a fit prior. The honest ceiling right now is a crowd nudge — "middle of the ladder, moved one step if enough raters say it runs small." It does not claim to know your body, and it shouldn't until it can. Returns keyed by reason code ( SIZE_TOO_SMALL vs damaged ) would make it a real fit model — and that data is private and session-scoped, which is exactly the WebMCP argument again. Occasion rules that aren't a hand-written table. Three occasions live in a lookup today. Multi-retailer. The normalizer is written against one aggregator shape, but the verdict engine is retailer-agnostic. The interesting version of this compares a garment you're considering against a wardrobe assembled from everywhere you've shopped. A shared wardrobe surface. Right now the wardrobe is self-reported and lives in the session. The version we actually want is one an agent can help you maintain over months — and that's a genuinely new kind of web object, jointly edited by a person and their agent, that neither could keep current alone.
