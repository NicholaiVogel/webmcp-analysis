Verify the state. \n\n How I built it \n\n The project uses WebMCP's imperative API to register a structured website tool that agents can discover and execute. \n\n The execution flow is: \n\n \n The WebMCP tool performs the requested action. \n The application receives a declared result. \n Runtime Truth independently queries the authoritative post-action state. \n The declared result and observed state are compared. \n A mismatch is surfaced as execution-state divergence. \n \n\n The demo uses deterministic fault injection so the failure can be reproduced consistently. \n\n The application is built with Python, Flask, JavaScript, and WebMCP, and deployed on Render. \n\n Challenges \n\n The most important challenge was separating tool execution from verification . \n\n If verification simply trusts the same response that declares success, it cannot detect false-success states. \n\n I also had to test WebMCP registration, discovery, and execution independently. The final implementation was verified using Chrome's WebMCP testing support: \n\n \n tool registration \n tool discovery \n WebMCP tool execution \n independent post-action state verification \n \n\n What I learned \n\n A successful tool response is a claim about execution, not necessarily proof of the resulting state. \n\n As WebMCP makes websites increasingly agent-native, verification may become especially important for consequential actions such as purchases, reservations, submissions, and workflow changes. \n\n I also came across Greg Isenberg's discussion of an "agent mystery shopper" concept for testing whether agents can actually complete important website journeys. \n\n Runtime Truth approaches a narrower technical version of that problem: \n\n When a tool declares success, did the expected state transition actually occur? \n\n I see that discussion as an independent signal that completion verification is becoming relevant as agents perform more real-world actions on the web. \n\n What's next \n\n Runtime Truth is intentionally small. \n\n The next step would be testing the same verification pattern across additional state-changing actions such as purchases, submissions, and asynchronous workflows. \n\n For this challenge, the goal is narrower: \n\n demonstrate clearly that tool success and state truth are not always the same thing. \n\n \n\n \n Built With \n\n flask github html javascript python render restapi webmcp \n \n\n \n Try it out \n\n \n \n \n runtime-truth.onrender.com \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Deep Echo \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Deep Echo \n started this project\n \n —\n \n 7 days ago \n \n \n\n
