can actually use the security console, not just summarize screenshots? \n\n Security teams already deal with fragmented alerts, timelines, assets, evidence, and response actions. AI can help analysts investigate faster, but giving an agent unrestricted autonomy in a high-stakes workflow is dangerous, especially when the agent may read attacker-controlled evidence. \n\n BreachGlass explores a safer model: the AI investigates, the human decides, and WebMCP connects both inside the same live interface. \n\n What it does \n\n BreachGlass is an agent-native cybersecurity incident response console powered by WebMCP. \n\n The demo simulates a critical incident involving credential theft and lateral movement. Through WebMCP tools, an AI agent can: \n\n \n load the active incident; \n search critical security events; \n inspect affected assets; \n reconstruct attacker movement; \n inspect forensic evidence; \n detect untrusted prompt-injection-style content; \n propose containment actions; \n request execution of containment. \n \n\n The key safety boundary is that containment cannot execute automatically. When the agent calls execute_containment before approval, BreachGlass returns HUMAN_APPROVAL_REQUIRED . Only after the human analyst approves the proposal in the UI can the agent execute the containment action and update the incident state to INCIDENT CONTAINED . \n\n How we built it \n\n BreachGlass is built as a React and TypeScript web application deployed on Cloudflare Pages. \n\n The application exposes seven WebMCP tools: \n\n \n get_incident \n search_events \n get_asset \n trace_activity \n inspect_evidence \n propose_containment \n execute_containment \n \n\n The tools are intentionally separated by risk. Investigation tools are read-only. Evidence inspection marks hostile content as untrusted. Containment proposal is safe and read-only. Containment execution is state-changing and requires explicit human approval. \n\n This lets the agent work with structured capabilities instead of scraping the UI, while keeping dangerous actions under human control. \n\n Challenges \n\n The main challenge was designing a workflow where the AI agent is genuinely useful without becoming unsafe. \n\n I wanted BreachGlass to show more than a chatbot summarizing an alert. The agent needed to investigate a realistic incident, encounter hostile evidence, ignore malicious instructions, propose containment, and then be blocked until a human explicitly approved the action. \n\n Another challenge was making the demo understandable quickly. The product had to show the incident state, the attack path, the untrusted evidence, the agent activity, and the human approval flow in one coherent experience. \n\n Accomplishments \n\n I am proud that BreachGlass demonstrates a complete human-agent incident response loop: \n\n \n structured WebMCP investigation; \n prompt-injection-aware evidence handling; \n attack path reconstruction; \n containment proposal; \n human approval; \n state-changing execution after approval. \n \n\n The most important moment in the demo is not that the agent can execute an action. It is that the agent cannot execute it until the human approves it. \n\n What we learned \n\n Building BreachGlass reinforced how important tool design is for agent-native applications. \n\n WebMCP makes it possible for a website to expose clear, structured actions to an AI agent. But the application still needs to define trust boundaries: which tools are read-only, which data is untrusted, and which actions require explicit human approval. \n\n The lesson is that good agent experiences are not just about giving AI more tools. They are about giving AI the right tools with the right safety model. \n\n What's next \n\n Future improvements could include: \n\n \n multiple incident scenarios; \n persistent audit logs of WebMCP tool calls and approvals; \n integrations with SIEM, EDR, identity, and ticketing systems; \n role-based approval workflows; \n richer evidence sandboxing; \n replayable incident timelines for security training and tabletop exercises. \n \n\n The long-term goal is to explore how AI agents can help security teams respond faster while keeping humans in control of high-impact decisions. \n\n \n\n \n Built With \n\n ai-agents cloudflare cybersecurity human-in-the-loop incident-response prompt-injection react typescript vite webmcp \n \n\n \n Try it out \n\n \n \n \n breachglass.pages.dev \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n I designed and built BreachGlass end-to-end: the React/TypeScript UI, the simulated incident model, the seven WebMCP tools, the prompt-injection-aware evidence flow, the human approval gate for containment, the Cloudflare Pages deployment, the README, and the demo video. \n \n\n \n \n \n \n \n \n\n \n Fran G \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 3 \n \n \n\n\n \n 3 people like this:\n \n\n \n \n \n \n \n \n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Fran G \n started this project\n \n —\n \n 3 days ago \n \n \n\n
