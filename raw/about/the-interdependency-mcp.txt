That is brittle, wasteful, and difficult to verify. \n\n The Interdependency already maintains skill-lib : a public library of structured agent skills with canonical sources, dependency information, boundaries, usage guidance, and validation tooling. WebMCP provides the missing browser-native boundary: a website can expose explicit tools to an agent instead of requiring the agent to guess how the site works. \n\n What it does \n\n The Interdependency WebMCP gives agents structured access to capabilities exposed by The Interdependency website while preserving the same website for human use. \n\n The initial WebMCP surface operates on the skill registry, with operations such as: \n\n \n discover available skills \n find skills relevant to a task \n inspect a skill \n resolve dependencies and prerequisite closure \n retrieve boundaries and usage guidance \n expose the smallest relevant capability set for the current task \n \n\n The WebMCP implementation belongs to the website that exposes those capabilities. The reusable webmcp skill belongs separately in skill-lib , where it teaches agents how to construct, validate, and maintain a WebMCP surface. \n\n This keeps implementation ownership and procedural knowledge distinct while sharing one canonical source of truth. \n\n How we built it \n\n The existing website is an Eleventy/Node knowledge system backed by public GitHub repositories. \n\n During the WebMCP Challenge we are extending that existing site with browser-native WebMCP tools using document.modelContext.registerTool(...) . \n\n The architecture is: \n\n canonical skill sources → registry → website capability layer → WebMCP tools → agent \n\n Human-facing pages and agent-facing tools therefore derive from the same underlying information rather than becoming separate, drifting interfaces. \n\n Challenges \n\n The principal design problem was deciding where WebMCP belongs. \n\n Putting the WebMCP runtime inside skill-lib would make the skill library responsible for another application's runtime. Making every skill itself a WebMCP function would incorrectly collapse procedural knowledge into executable operations. \n\n The resulting separation is: \n\n \n the website owns the WebMCP runtime and registered tools \n skill-lib owns the reusable WebMCP setup and validation skill \n canonical skills remain authoritative knowledge objects \n WebMCP exposes operations over those objects\n## What I'm most proud of \n \n\n I'm most proud of msdmd — Module Self-Declared Metadata Markdown . \n\n It started from a simple problem: documentation, capability maps, dependency graphs, ownership records, tests, and agent instructions all tend to drift away from the code they describe. \n\n msdmd reverses that relationship. A module declares structured metadata about itself, close to the source that gives those declarations meaning. Other surfaces are then derived and checked from those declarations rather than maintained independently. \n\n That idea became the foundation of skill-lib : documentation coverage, capability inventories, dependency topology, ownership, contracts, boundaries, generated agent instructions, and other tools all build from the same underlying convention. \n\n What I'm proud of is not the syntax itself. It is the architectural consequence: \n\n one source can describe itself well enough that humans, tests, documentation systems, and agents can all derive useful views without creating competing truths. \n\n WebMCP extends that same idea into the browser: instead of an agent guessing what a website can do, the site can declare its capabilities directly. \n\n What we learned \n\n WebMCP is most useful when it is not simply an alternate way to click buttons. \n\n Its stronger role is to make a web application's actual capability model explicit to agents. That reduces interface guessing, unnecessary context consumption, and divergence between what humans can see and what agents can reliably do. \n\n For a structured skill registry, this also makes selective disclosure possible: an agent can receive the smallest relevant capability closure instead of loading an entire library into context. \n\n What's next \n\n The immediate goal is a small, fully tested WebMCP surface over the skill registry. \n\n After that, the same pattern can extend to other parts of The Interdependency website while preserving explicit boundaries, provenance, validation, and human control. \n\n hmmm — the interesting boundary is not whether every website should expose more tools, but whether it can expose exactly the capabilities it actually owns, no more and no less. \n\n \n\n \n Built With \n\n actions css3 eleventy github html5 javascript markdown node.js pagefind playwright webmcp \n \n\n \n Try it out \n\n \n \n \n interdependentway.org \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n I conceptualized, then coordinated agent output to completion. my greatest accomplishment and contribution is hmmm.
