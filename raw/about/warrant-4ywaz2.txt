How I built it Seven tools registered on document.modelContext at load. The call is written out in src/webmcp/registry.ts rather than delegated to a wrapper, so the thing the spec names is in the repository where a reader — or a grep — finds it. Unregistration is the AbortSignal the spec provides: unmounting a tool's component aborts it. Minted tools are React components. Each holds one registerTool registration, so revoking a tool unmounts its component, which aborts its signal and removes it from the surface. The tool count in the corner is read from the live registry, not from state. propose_tool accepts a generalisation with per-parameter rationale, then refuses to act on it . The page checks every promoted field against its own declared operations — a field with no filter operations cannot become a parameter, a date without relative_ok cannot carry a relative default, a restricted field cannot be exposed by anyone including the person — and returns structured refusals with the constraint named. Edge cases are generated from the structure and executed against the real dataset before the tool exists. The observed column is a result, not a guess. A rejected case blocks minting. Withholding happens in the query layer, before a result is handed to anyone. It is not a rule the model is asked to respect; there is no code path that returns a restricted field. No backend, no accounts, no network calls. All data is synthetic and generated deterministically, so every judge sees identical numbers. Tools that notice when the page moves under them Reading the write-ups of the other entries in this challenge, ten name drift — a tool's description or schema going stale against the page it describes. Several bind their own author-written tools to a revision or a fingerprint to catch it: Captain's Table with capability epochs, Reflex with semantic fingerprints, Cadence with exact-revision validation, Canon Ledger with fingerprint-bound route state. So the mechanism is not new, and the write-up should not pretend otherwise. What differs here is narrower than an earlier draft of this claimed, and it is two things. The fingerprint is of the page's declared structure , not of the artefact a person approved. Understudy's allowlist is bound to what its recording did; Agentic Service Dispatch's approval is bound to the draft it approved. Both catch a change to the thing that was agreed. Neither catches a field being reclassified six months later by someone who never heard of that tool — which is the failure this page is built around, because a tool a person minted on a Tuesday is maintained by nobody. And the consequence is removal, not refusal . Reflex refuses execution when its fingerprint stops matching, which is the right call at call time. Here the tool leaves getTools() entirely, so an agent listing the page's tools never sees it and never forms a plan around it. bench/host-check.py verifies that through the host rather than through this page's own bookkeeping. So a minted tool records a fingerprint of the structure it was approved against. When the page changes — reclassify a field in the tool surface panel and see it — the tool's contract is re-validated. If it now returns something policy forbids, the component unmounts, its AbortSignal fires, and the browser stops offering it. The accepted edge cases become a regression suite: one click re-runs them, and any case whose behaviour changed comes back unreviewed, keeping the tool out until a person approves it again. A tool that goes quiet is better than a tool that keeps answering confidently about a page that has moved. The capability outlives the session, and then the person who made it A tool that vanishes on reload is a demonstration. Minted tools are kept per site — the contract, the reviewed edge cases, the fingerprint they were approved against — so the surface a person built is there when they come back, and is not there on a site it was not made for. Working state is deliberately not kept: a half-written proposal or a write waiting on confirmation belongs to the session. What someone made does not. And it can be shared as a link. The link carries the contract, not a registration: the receiving page re-validates it against its own structure and re-runs every edge case on its own data before that person is asked to approve. Fields their page classifies as restricted stay locked even if the sender exposed them. So the work stops being personal. The person who actually does the job every month creates the capability, and the rest of the team's agents — different models, different browsers — get it after their own page has checked it. Nobody filed a ticket and nobody deployed anything. Human confirmation is implemented as a tool call that resolves only after a person acts, which the current API supports. The harder design problem was where generalisation should live. Rules are brittle, a model alone is unaccountable, and a person asked to specify everything will not bother. Splitting it — structure from the page, inference from the agent, authority from the person — is the whole design, and the page keeps a rule-based draft so the demo never depends on a model behaving. One piece of feedback for the spec Running this against Chrome rather than reading about it produced two observations, and being precise about them matters more than the observations themselves. The first is a calling convention: document.modelContext.executeTool(tool, args) takes its arguments as a JSON string and returns its result serialized the same way, while the tool's own inputSchema describes an object and its execute receives one. The object form fails with UnknownError: Failed to parse input arguments , which does not point at serialization. I first wrote this up as something no other entry mentions. Checking the corpus showed otherwise: thirty-four write-ups mention executeTool , and depending on how tightly you match, thirteen to fifteen of them describe the string argument. Three quote the same error text. That is a better argument for documenting it than novelty would have been. The second is about annotations, and the mistake was mine. This page was sending destructiveHint , idempotentHint and openWorldHint , which Chrome accepts and discards. WebMCP defines exactly two annotations ; those three belong to the wider MCP vocabulary. Placard, another entry here, says so and enforces it with a test. The page now sends only readOnlyHint and untrustedContentHint , and the type makes the others unrepresentable. What is left after the correction is a request rather than a bug. A page that lets a person mint a tool that acts has one bit to describe it with. readOnlyHint: false says "this is not a read"; it cannot distinguish appending a note from deleting a record, and it cannot carry how many rows one call will touch — which is exactly what the approver was shown and exactly what the client calling it later cannot see. This page compensates with a description and a confirmation step it invented itself. A host cannot act on either. All of it is written up as a filable issue in docs/spec-issue.md — in the spec's own terms, with nothing in it that depends on this project. It is not filed: that is a public action on my account and saying so is more useful than implying otherwise. That request sits alongside three others in docs/spec-note.md : a declared context class per field, a conventional shape for "an identifier the agent may pass back but not read", and a structural fingerprint tools can be bound to. Twenty-four entries use the word fingerprint , but most of them mean something else — stable selectors, DOM digests, consent tokens. Checking each: four bind a capability to a revision or a fingerprint — Captain's Table with capability epochs, Cadence with exact-revision validation, Canon Ledger with fingerprint-bound route state, StillHere with draft, key, version and approval sharing one. Reflex refuses execution when a semantic fingerprint stops matching. Assistant Studio binds consent rather than a tool. That is the defensible count, and it is smaller than the one an earlier draft gave. Four incompatible schemes for one problem is still the signal — that people keep inventing it is the argument for putting it in the spec. What I learned Four things, each of which cost a claim this write-up had already made: Attacking the running page found what reading it did not. Three real holes — grouping put a withheld field in the key position, a filter on an unfilterable field made the row count an oracle, and a reclassified field's filterOps survived in an already minted tool. All three were in code I had read and believed. The same fix has to be found in every place it belongs. One site read the policy live and refused correctly; the other had snapshotted it at module load and did not. A corpus claim is wrong until it is counted, and then counted again. 169, then 470, then 868. Every count in this write-up moved in the unflattering direction on the last recount. Two of my own sentences contradicted each other in the document whose thesis is that every checkable claim was checked. Both are fixed and both are recorded. The long version, with each retraction named: docs/what-i-got-wrong.md . What's next The four layers this page publishes about itself are a guess at a general shape. If pages are going to let people mint tools, they will need a shared way to say what may vary, what may be composed, and what may never leave.
