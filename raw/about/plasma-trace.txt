Objects\nthis small are difficult to track with radar or optical systems, yet at\norbital velocities they carry enough energy to damage spacecraft. \n\n NASA-funded research has been exploring an indirect approach: a charged\nfragment moving through ionospheric plasma can excite nonlinear waves —\nsolitons — that might be detectable even when the object itself is not.\nThe physics comes from Sen et al. (2015) on forced-KdV soliton excitation\nby charged orbital debris, developed further in Christine Hartzell's NASA\nNIAC work at the University of Maryland. \n\n I did not invent that science, and this project does not claim to. What\ninterested me was a different question: exploring a model like this means\nsweeping parameters — size, velocity, altitude, day/night ionosphere —\nand that is exactly the kind of tedious, click-heavy loop where a human\nand an agent should be able to work on the same instrument instead of in\nseparate tools. \n\n What it does: \n\n Plasma-trace is a browser-based forward model for debris detectability.\nSet a fragment's size, relative speed, and altitude, pick a daytime or\nnight-time ionosphere, and it returns a detectability score plus a\nbreakdown across eight altitude bins. \n\n The point is that there are two ways to drive it, and they are the same\ninstrument: \n\n \n A person drags sliders and watches the chart redraw. \n An AI agent calls WebMCP tools registered on the page — and the\nsliders and chart move exactly as if a person had dragged them. \n \n\n Why WebMCP is a strong fit: \n\n Scientific parameter exploration is a bad fit for the usual ways agents\ninteract with web pages. Screen-scraping a slider is fragile and\nlossy: an agent reading "38/100" off the DOM has a rendered string, not\na result it can reason over. \n\n WebMCP changes the contract. The page exposes typed tools with schemas,\nso the agent calls a function and gets structured data back, while the\nhuman sees the same state update visually. Neither operator is\nsecond-class. That is what makes this feel like a shared instrument\nrather than an agent puppeting a UI built for someone else. \n\n What people and agents can do together that was difficult before: \n\n The clearest example is sweep_altitude . A person exploring where a\n5 mm fragment is most detectable has to drag the altitude slider through\neight positions and read the chart each time. An agent runs the whole\nsweep in one call and returns the best altitude with the full profile —\nwhile the human watches the same chart update. \n\n Before WebMCP, that meant either building a separate API (and now the\nhuman and agent are using different systems that can drift apart) or\nhaving the agent scrape the UI (fragile, and it gets strings instead of\ndata). Here there is exactly one code path. \n\n explain_regime is the inverse case: the agent asks the instrument to\nexplain why detectability peaks where it does, so the reasoning comes\nfrom the page's own model rather than the language model's guess. \n\n How I built it: \n\n One self-contained index.html — no backend, no database, no build\nstep. Chart.js from a CDN is the only dependency. \n\n \n runForwardModel() computes detectability from an altitude-dependent\nplasma density term, a size factor, and a speed factor. \n The sliders call that function directly. \n Four tools are registered with document.modelContext.registerTool() :\n set_debris_params , run_forward_model , sweep_altitude , and\n explain_regime . Each one calls the same functions the sliders call\nand updates the same chart. There is no parallel agent code path —\nthat constraint is the whole design. \n The page feature-detects document.modelContext and degrades\ngracefully: in a non-WebMCP browser it shows a banner explaining how\nto enable it, and every slider still works. \n \n\n Challenges: \n\n The WebMCP API is new enough that several third-party guides describe it\nincorrectly — a number of them say navigator.modelContext when the\nspec defines document.modelContext . Writing that line from memory or\nfrom a blog post would have produced a page that looks completely normal\nand silently registers nothing. I sourced the signature from the W3C\nexplainer and cross-checked it against the spec IDL. \n\n A second one: executeTool takes its arguments as a JSON string, not an\nobject. Passing an object returns "Failed to parse input arguments" with\nno further detail. Worth knowing if you are testing via\n navigator.modelContextTesting in the console. \n\n What's real, and what isn't \n\n I would rather be precise about this than oversell it. \n\n Real: the forward model runs in-page, the WebMCP registration is\nfunctional, the deploy is live, and agent tool calls demonstrably move\nthe same sliders and chart a person uses. \n\n Simplified: the ionosphere data is hardcoded. The model uses\nclosed-form terms, not a plasma solver. Nothing here is validated\nagainst observations. \n\n Not claimed: this does not detect debris. It is not an early-warning\nsystem — solitons propagate near the ion-acoustic speed while debris\nmoves far faster, so this is a mapping and survey concept, not a\ncollision alarm. The science is attributed to published research. \n\n The contribution I am putting forward is the interaction pattern: a\nscientific instrument that a human and an agent operate through one\nshared set of functions. \n\n What's next \n\n Real ionosphere data (IRI or GNSS TEC) instead of hardcoded values, a\ntrained ML model for the inverse problem — recovering fragment\nproperties from an observed signature, which is not analytically\nsolvable and is exactly what the NIAC team is working on — and\nmulti-sensor localisation. \n\n \n\n \n Built With \n\n chart.js css3 html5 javascript webmcp \n \n\n \n Try it out \n\n \n \n \n plasma-trace.netlify.app \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Inam Kakar \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Inam Kakar \n started this project\n \n —\n \n 2 days ago \n \n \n\n
