Your AI agent reviews an employment contract through tools the page registers in your browser and the blurred document snaps into clarity as you decide each redline. Like Comment Story Updates Inspiration You get an offer. The salary is great — and the contract is 22 pages of fine print with a 48-hour signature deadline. About 30% of US workers are bound by non-competes, and most people sign without understanding what they're signing. A lawyer costs $400/hour. The alternative used to be asking an AI "is this enforceable?" and getting a confident essay you then had to reconstruct into something actionable. Redline is for the person who actually has: a document, a deadline, and an AI agent they already use. What it does Paste an employment contract (or open one of three deliberately overreaching samples) and it loads blurred — the way a 22-page contract actually feels. Your AI agent then works inside the page: it reads every clause, flags the risky ones with severity and grounded reasons, and proposes concrete redline language. Each proposal lands as a decision card under the exact sentence it modifies. You decide each one — Keep as-is, or Redline it — and accepted changes roll up into a negotiation email, Current vs Proposed side by side, one click to copy. As the agent assesses each clause, it snaps into clarity — but clarity is computed, not decorative: a clause only clears once it's assessed and every redline on it is decided. Reset a verdict and it re-flags. The blur is the progress bar. Why this is a strong fit for WebMCP A contract-review tool needs an agent to see inside the document, clause by clause, and write back into it. That is exactly what WebMCP enables: Redline registers seven tools on document.modelContext — get_sample_contract , get_document_state , extract_clauses , get_clause_text , assess_clause , get_enforceability_context , export_negotiation_email . Two-phase dynamic registration: at boot only a get_sample_contract tool exists; once a document is loaded, the app retires it via WebMCP's signal-based lifecycle and registers the six analysis tools. The tool list always matches what is meaningful right now. Grounded analysis, not vibes: get_enforceability_context hands the agent real data — non-compete enforceability across 20 US states (earnings thresholds, void-by-default rules, notice requirements), training-repayment-agreement traps in 5 states, and heuristic families for NDAs, arbitration, and IP assignment. When Redline says a five-year worldwide non-compete is high-severity in Washington, it quotes RCW 49.62. No API keys, no backend, no scraping. The page is the tool provider and the browser is the whole stack (static assets on Cloudflare Workers). What people and agents can do together now The old pattern: ask an AI, get an essay, copy fragments into a text editor, lose the structure. Here the agent proposes and the human decides — and the boundary is enforced by the data flow itself: agent tools write proposals and assessments into clause threads, but redline verdicts can only come from the UI. What was six screens of copy-paste is now one grounded pass with the human keeping the pen on every change. Because all state is derived (blur, completion, the email draft are computed from assessments and verdicts — never stored as flags), the UI can't claim progress the human didn't actually make. How we built it React 19 + TypeScript (strict), Vite, Cloudflare Workers static assets — no backend, no keys. All tool reads go through a live session ref (tools never read stale React state); writes flow actions → store → UI in one direction. The email composer is deterministic: the page and export_negotiation_email emit byte-identical output. The decision UI (FlagBadge, RedlineCard, ClauseChat) renders proposals inline in the document; a 500ms transition snaps each clause from blurred to clear as decisions land. Challenges we ran into WebMCP's registration lifecycle has no unregister API — tools are retired through abort signals, which shaped our two-phase registration design. Making blur honest took a derived rule: early versions cleared clauses on assessment alone; the shipped version requires every redline on the clause to be decided. Keeping page and tool output identical forced us to make the email composer a pure function both paths call. Live agent testing caught real bugs (duplicate redline proposals on re-assessment, chat auto-expand behavior) that we fixed with a pure redline-planning function and better thread state. What we learned The WebMCP model inverts the usual architecture: the app doesn't call the model, the agent calls the app. Designing tools for another developer (the agent platform) forced us to make state readable, actions explicit, and UI claims derived from data — which made the app better for humans too. What's honest about this demo The samples are drafted overbroad — that's the test. But nothing is scripted: the app ships data and heuristics, not verdicts, and accepts whatever a competent model actually produces through the tools. Different model, different analysis — same structure to hold it.
