But when it comes time to actually interact with it, we are still mostly staring at a text box. \n\n Type a prompt.\nWait.\nRead a long response.\nType again. \n\n It works, but it can feel surprisingly disconnected. \n\n I kept thinking about a simple question: \n\n \n If AI is becoming capable of doing things like a person, why are we still interacting with it like a search box? \n \n\n Humans don't communicate through words alone. \n\n We use our voice. We look at each other. We react. We gesture. We pay attention. We pause. We interrupt. We change our expression when something is important. \n\n Those small signals make communication easier to understand. \n\n So we wanted to explore a different kind of AI interface. \n\n \n What if an AI agent had a body? \n \n\n That question became Persona . \n\n The goal wasn't to create a character that simply talks to you or to make AI pretend to be human. \n\n The goal was to explore whether an AI agent could have a presence — a way to communicate its intent through voice, attention, expressions, gestures, and visible actions while still doing useful work. \n\n WebMCP made this idea especially interesting. \n\n Instead of an AI agent trying to figure out which button to click or how a webpage happens to be structured, the webpage can explicitly expose capabilities that the agent can discover and use. \n\n That gave us an opportunity to build something where the agent doesn't just talk about what it wants to do. \n\n It can actually interact with the webpage through structured tools. \n\n And if an agent can control actions on the web, why shouldn't it also be able to control how it communicates with the person standing on the other side of the interaction? \n\n That became the idea behind Persona: \n\n \n Give the agent a body. Give that body meaningful capabilities. Then let WebMCP connect the agent to them. \n \n\n \n\n What it does \n\n Persona is an embodied WebMCP AI agent interface. \n\n It gives an AI agent a digital body that can listen, speak, look, react, gesture, and perform structured tasks . \n\n Instead of treating the avatar as a visual layer placed on top of a chatbot, Persona makes the avatar part of the agent interaction itself. \n\n A user can communicate naturally through voice, while an AI agent can discover and call WebMCP tools exposed by Persona. \n\n The agent can: \n\n \n Understand the user's spoken intent \n Create tasks and missions \n Read the current task state \n Update tasks when requirements change \n Complete tasks \n Present results \n Speak to the user \n Change its expression \n Direct its attention and gaze \n Perform gestures \n \n\n The WebMCP tools exposed by Persona include: \n get_user_transcript\ncreate_task\nget_tasks\nupdate_task\ncomplete_task\nshow_result\nspeak\nset_expression\nset_attention\nperform_gesture\n \n This allows the agent to interact with two sides of the application: \n\n What it is doing and how it is communicating while doing it . \n\n For example, a user can say: \n\n \n "Prepare me for a data science technical interview tomorrow." \n \n\n The agent can turn that request into a structured mission instead of simply returning a large block of advice. \n\n The user can then change their mind: \n\n \n "Actually, focus much more on machine learning." \n \n\n The agent can update the mission and continue from the current state. \n\n At the same time, Persona can communicate through speech, attention, expressions, and gestures. \n\n This creates an interaction loop where: \n\n Human intent → Agent reasoning → WebMCP action → Application state → Embodied response \n\n The interview-preparation scenario is our concrete demonstration of this idea. \n\n But Persona itself isn't meant to be just an interview coach. \n\n The larger idea is an embodied interface for web agents . \n\n The avatar is not there just to look good. \n\n The agent can actually control it through WebMCP. \n\n That is what turns Persona from an animated chatbot into an exploration of what an agent-native web interface could look and feel like. \n\n \n\n How we built it \n\n Persona is a browser-based application built with: \n\n \n React \n TypeScript \n Vite \n Three.js \n VRM \n @pixiv/three-vrm \n WebMCP \n Web Speech API \n Web Audio API \n \n\n The project combines an agent-facing tool layer with an embodiment runtime. \n\n WebMCP tool layer \n\n The core of the WebMCP integration is the application's ability to expose structured capabilities through document.modelContext . \n\n Instead of exposing arbitrary UI elements, Persona exposes tools that represent meaningful actions an agent can perform. \n\n For example: \n document . modelContext . registerTool ( . . . ) \n \n The tools cover two main areas. \n\n Agent actions \n create_task\nget_tasks\nupdate_task\ncomplete_task\nshow_result\n \n These allow the agent to work with structured application state. \n\n Embodiment actions \n get_user_transcript\nspeak\nset_expression\nset_attention\nperform_gesture\n \n These allow the agent to communicate through Persona's digital body. \n\n This separation was important to us. \n\n The AI agent doesn't need to know how the avatar is implemented internally. \n\n It doesn't need to manipulate Three.js objects, animation clips, or VRM parameters. \n\n It can simply use a meaningful capability such as: \n speak(...)\nset_expression(...)\nset_attention(...)\nperform_gesture(...)\n \n Persona handles the underlying implementation. \n\n The embodiment runtime \n\n The visual body is a VRM character rendered through Three.js. \n\n Around that character, we built systems for: \n\n \n Voice input \n Voice output \n Speech-driven mouth movement \n Facial expressions \n Eye gaze and attention \n Gestures \n Behavioral state \n Micro-reactions \n Interruption handling \n Session continuity \n \n\n One of the most important design decisions was separating agent intent from embodiment . \n\n The agent decides what it wants to accomplish or communicate . \n\n WebMCP provides the structured interface through which it can do that. \n\n Persona's runtime determines how that intent appears to the human . \n\n For example, the same agent decision can involve both an actual task action and an embodied response. \n\n The agent may update a task while also speaking to the user and directing its attention toward them. \n\n This means the avatar isn't just an animation layer. \n\n It becomes another interface through which the agent communicates. \n\n Why WebMCP matters here \n\n Without WebMCP, an agent could generate instructions describing what should happen. \n\n With WebMCP, Persona can expose the actual capabilities of the webpage in a form the agent can discover and call. \n\n That distinction is important. \n\n We aren't trying to make the AI look like it is operating the application. \n\n We're giving the agent structured ways to actually interact with it. \n\n \n\n Challenges we ran into \n\n The difficult part wasn't putting a 3D character on a webpage. \n\n The difficult part was making the character feel like part of the interaction rather than a decoration sitting beside a chatbot . \n\n Voice interaction introduced several problems. \n\n We had to handle microphone state, speech synthesis, turn-taking, interruptions, and make sure Persona didn't accidentally respond to its own generated speech. \n\n Then we encountered a more subtle problem: \n\n \n When should an AI agent actually move? \n \n\n If an avatar constantly moves, looks around randomly, changes expressions without context, or performs gestures at the wrong moment, the result becomes distracting very quickly. \n\n So we worked on behavioral state, attention, micro-reactions, speech-driven animation, and controlled gesture selection. \n\n We also had to make sure WebMCP actions interacted with the current application state , rather than relying on stale state from the interface. \n\n That became especially important once the agent could create, update, and complete tasks. \n\n Another challenge was deciding how much embodiment is actually useful. \n\n It is tempting to add more animations because they look impressive. \n\n But we learned that more movement doesn't necessarily mean better communication . \n\n Sometimes a small change in gaze or expression communicates more than a large gesture. \n\n The challenge gradually changed from: \n\n \n "How do we animate a character?" \n \n\n to: \n\n \n "How should an agent's behavior communicate its intent?" \n \n\n That shift influenced a lot of Persona's implementation. \n\n \n\n Accomplishments that we're proud of \n\n The biggest accomplishment is that Persona went beyond: \n\n \n "An AI avatar that talks." \n \n\n We built a working interaction where an AI agent can use WebMCP to interact with both the work and the body of the application. \n\n The agent can manage structured tasks while also controlling how Persona communicates with the human. \n\n We're especially proud of the smaller pieces that make the interaction feel more alive: \n\n \n Speech-driven mouth movement \n Contextual facial expressions \n Attention and gaze behavior \n Agent-controlled gestures \n Micro-reactions \n Voice interaction \n Interruption handling \n Persistent task state \n Structured WebMCP actions \n Agent-controlled result presentation \n \n\n None of these features alone is Persona. \n\n Together, they create something we found much more interesting: \n\n \n An AI agent that doesn't just produce an answer — it has a way to behave while working with you. \n \n\n We're also proud that WebMCP isn't simply an integration hidden somewhere in the code. \n\n It is part of the interaction model. \n\n The agent uses WebMCP to access the application's capabilities, and those capabilities include both useful work and embodied communication . \n\n That made WebMCP feel less like another API layer and more like a foundation for experimenting with a different kind of web experience. \n\n Most importantly, Persona gave us a chance to explore an idea we genuinely wanted to see working: \n\n \n What happens when an AI agent is no longer just a voice in a chat window, but has a presence inside the interface it is using? \n \n\n \n\n What we learned \n\n Building Persona changed the way we think about AI interfaces. \n\n We started with a fairly simple assumption: \n\n \n Better AI should mean better answers. \n \n\n But as we built the project, we realized that the interface becomes increasingly important as agents become more capable. \n\n A highly capable agent can reason, use tools, and complete tasks — but if every interaction is still reduced to a stream of text, some of that capability remains difficult for humans to understand. \n\n Embodiment doesn't make an AI smarter. \n\n But it can give the agent another communication channel. \n\n A spoken response can be accompanied by attention. \n\n A result can be presented rather than buried inside a paragraph. \n\n A change in task direction can be reflected immediately in the interface. \n\n An agent action can have a visible consequence. \n\n We also learned something important while working with WebMCP. \n\n At first, it is natural to think about WebMCP in terms of individual tools: \n\n \n "What tools should we expose?" \n \n\n But the more interesting question became: \n\n \n "What becomes possible when the webpage itself is designed as a shared environment for humans and agents?" \n \n\n That changed how we approached the project. \n\n We stopped thinking only about how an agent could use a webpage. \n\n We started thinking about how a webpage could be designed for both humans and agents from the beginning . \n\n That's the direction that excites us most. \n\n \n\n What's next for Persona — The Embodied WebMCP AI Agent \n\n The interview-preparation experience is only our starting point. \n\n We want Persona to become a more general embodiment layer for web agents . \n\n The same foundation could eventually support: \n\n \n Learning companions \n Presentation and communication practice \n AI coaching \n Simulations and role-play \n Customer-facing agents \n Collaborative work assistants \n Interactive education \n Accessibility-focused interfaces \n \n\n We also want to explore deeper coordination between an agent's reasoning, tools, memory, and physical behavior . \n\n For example, an agent shouldn't simply perform an action and then announce it. \n\n Its behavior could help communicate why it is doing something, what changed, and what needs the user's attention. \n\n But we also want to be careful about embodiment. \n\n The goal isn't to make AI theatrical or constantly animated. \n\n The goal is to make interaction more understandable, expressive, and human-friendly . \n\n As agents become capable of doing more work on behalf of people, we believe the interface between humans and those agents will matter just as much as the underlying intelligence. \n\n Today, most AI interfaces ask humans to adapt to machines. \n\n We want to explore the other direction: \n\n \n What if machines could adapt to the way humans naturally communicate? \n \n\n WebMCP gives agents a structured way to interact with the web. \n\n Persona explores what that web could feel like when the agent has a presence inside it. \n\n And that's the experiment we're taking forward: \n\n \n Don't just give an AI agent a brain. Give it a way to be present. \n \n\n \n\n \n Built With \n\n antigravity chatgpt css3 html5 javascript react three.js typescript vite vrm webgl webmcp webspeechapi \n \n\n \n Try it out \n\n \n \n \n persona-iota-sepia.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Pratik Aher \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Pratik Aher \n started this project\n \n —\n \n 2 days ago \n \n \n\n
