It can decide what it thinks should happen next. It can even be given a list of valid actions. \n\n None of that answers the important question: \n\n \n Is this action valid right now? \n \n\n That question belongs to the application. \n\n I built BOUNDARY around one simple idea: \n\n Agents don't have authority. Applications do. \n\n The application's current state should be the thing that decides which transitions are possible — not the agent's reasoning, not a system prompt, and not whatever the agent happens to believe is allowed. \n\n What it does \n\n BOUNDARY is a state authoritative workflow for WebMCP applications. \n\n An agent can request any tool at any time. BOUNDARY does not assume the request is valid just because the tool exists. \n\n Every request goes through the same workflow engine: \n CURRENT STATE + REQUESTED ACTION\n ↓\n WORKFLOW ENGINE\n ↙ ↘\n ALLOW BLOCK\n \n If the current state authorizes the transition, it happens. \n\n If it doesn't, the application rejects it. \n\n The demo makes this visible rather than hiding it behind a policy document. \n\n At INITIAL , select_device_type is valid. \n\n Once the workflow moves forward, that authority changes. \n\n Later, confirm_submission is valid in AWAITING_CONFIRMATION . After the submission happens, the exact same tool becomes invalid. \n\n The tool didn't change. \n\n The application's state did. \n\n BOUNDARY also includes a Security Lab that deliberately attempts invalid transitions: \n\n \n Force submission from the wrong state \n Skip required evidence \n Bypass validation \n Reuse stale authority after the workflow has advanced \n \n\n All four are rejected by the same engine. \n\n Every attempt is recorded in the Black Box with the action, state, result, and reason. \n\n How I built it \n\n BOUNDARY is a Svelte 5 application built with Vite and a deliberately small architecture. \n\n The important part is the WorkflowEngine . \n\n There isn't one set of rules for the UI and another for the WebMCP tools. There isn't a separate security layer that has to stay synchronized with the workflow. \n\n Every WebMCP tool ultimately delegates to the same transition function: \n WebMCP Tool\n ↓\nattemptTransition(action, payload)\n ↓\nCurrent workflow state\n ↓\nALLOW / BLOCK\n ↓\nState transition + audit event\n \n The workflow engine owns the state, valid transitions, blocking conditions, evidence requirements, and transition decisions. \n\n That makes the central rule an architectural constraint: \n\n No agent action can change workflow state unless the current state authorizes that transition. \n\n The UI simply exposes what the engine is already enforcing. \n\n The Black Box then makes those decisions observable, so a judge can watch the same request go from accepted to rejected as the workflow changes. \n\n Challenges I ran into \n\n The hardest part wasn't building a state machine. \n\n It was making sure we actually had one state machine. \n\n During development, we had separate pieces of logic that could have become competing sources of truth. That was exactly the problem BOUNDARY was supposed to demonstrate, so we removed that ambiguity. \n\n I consolidated the workflow into a single engine and made the WebMCP tools thin wrappers around it. \n\n The other challenge was resisting the temptation to make the project look more complicated than the idea. \n\n I initially explored a more elaborate visual presentation, but the more important question became: \n\n Can someone look at the application and immediately see the authority boundary being enforced? \n\n That led me toward a much simpler interface: state, available tools, the engine's decision, and the Black Box. \n\n The result is less of a dashboard and more of a live experiment. \n\n Accomplishments i'm proud of \n\n The biggest one is that the core idea is directly observable. \n\n You don't have to trust a README that says BOUNDARY prevents invalid actions. \n\n You can try one. \n\n At one point in the workflow: \n confirm_submission\n→ ACCEPTED\n→ SUBMITTED\n \n Then, seconds later: \n confirm_submission\n→ BLOCKED\n→ stale authority\n \n Same tool. \n\n Same application. \n\n Different state. \n\n That's the boundary. \n\n I also built a dedicated adversarial mode instead of only demonstrating the happy path. \n\n The Security Lab attacks the workflow with force submit, evidence skipping, validation bypass, and stale authority. The engine rejects each attempt. \n\n Most importantly, the agent doesn't get a special escape hatch. \n\n Even if the agent ignores the application's suggested next action and requests something completely different, the workflow engine still decides. \n\n What I learned \n\n The biggest lesson was that telling an agent what it is allowed to do is not the same as enforcing what it is allowed to do. \n\n A system prompt can describe valid transitions. \n\n A tool description can describe prerequisites. \n\n An agent can even reason correctly most of the time. \n\n But if correctness depends on the agent remembering and obeying those instructions, the agent has effectively become part of the security boundary. \n\n BOUNDARY flips that relationship. \n\n The agent can request. \n\n The application decides. \n\n I also learned that a good security demo shouldn't just show that the happy path works. It should deliberately create the moment where the system is expected to say no . \n\n That is where the architecture becomes visible. \n\n What's next for BOUNDARY \n\n BOUNDARY currently demonstrates the primitive inside a controlled workflow. \n\n The next step is to make that primitive easier to drop into real WebMCP applications without rebuilding the enforcement layer from scratch. \n\n That means moving toward a reusable workflow authority layer where applications define their states and transitions, expose their tools, and let BOUNDARY enforce the relationship between the two. \n\n The long term idea is simple: \n\n Don't ask the agent to know what it is allowed to do. Give the application the final say. \n\n Project Story \n\n BOUNDARY started with a question: \n\n What happens when an agent has a tool that exists, but isn't valid anymore? \n\n That sounds obvious until you look at how agentic systems actually work. \n\n Agents see tools. They read descriptions. They decide what to call. In many systems, the application's current workflow state is treated as context the agent should reason about. \n\n I thought that boundary was backwards. \n\n If an application knows that a claim hasn't been validated, why should an agent be trusted to remember that confirm_submission isn't valid yet? \n\n If the workflow has already moved past submission, why should the agent be trusted not to reuse an earlier action? \n\n So I built BOUNDARY around a single invariant: \n\n \n The application's state determines what actions are valid. \n \n\n The interesting part wasn't implementing that rule. It was proving it. \n\n I built a workflow where the available WebMCP tools change as the application moves through its states. Then it was deliberately attacked. \n\n A tool that works in one state is tried again after the state changes. \n\n A submission is forced from the beginning. \n\n Evidence requirements are skipped. \n\n Validation is bypassed. \n\n Old authority is reused. \n\n The engine makes the decision every time. \n\n There is no second rules engine for the UI. No special exception for the agent. No system prompt instruction that can override the workflow. \n\n Every request reaches the same transition function. \n\n That ended up being the most important architectural decision in the project. \n\n I also made every decision visible through the Black Box. Instead of simply displaying "blocked," BOUNDARY shows the action that was requested, the state it was requested from, the resulting decision, and why the transition was rejected. \n\n The final demo became less about showing features and more about watching an assumption fail. \n\n The agent can see the tool. \n\n The tool exists. \n\n The agent can request it. \n\n And the application still says no. \n\n That is BOUNDARY. \n\n \n\n \n Built With \n\n agenticai svelte vite webmcp \n \n\n \n Try it out \n\n \n \n \n boundary-iota.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Hillary Ikhais \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n I'm an ML engineer who loves building AI products fast.
