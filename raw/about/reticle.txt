The problem is what happens after they write it. \n\n An agent can change five files, run a command, see a successful response, and decide the task is complete. But the application can still be broken. \n\n We built Reticle around a simple idea: agents shouldn't be trusted to decide whether their own work is correct. They should have proof. \n\n WebMCP made this idea even more interesting. If agents are going to operate real web applications, the web itself needs a better interface for agents to interact with and verify what is actually happening. \n\n What it does \n\n Reticle is an open-source verification layer for coding agents. \n\n It lets an agent test a real running application and verify behavior across the stack, including network requests, console errors, application state, routing, and persistence. \n\n Instead of returning something vague like “the page looks correct,” Reticle produces deterministic evidence and a clear PASS/FAIL result that the agent can use to decide what to do next. \n\n For the WebMCP challenge, we extended this idea to web workflows. Reticle gives agents structured capabilities for interacting with and verifying applications, reducing their dependence on screenshots, DOM guessing, and brittle browser automation. \n\n The goal is simple: turn “I think it works” into “here's the proof.” \n\n How we built it \n\n We built Reticle as an open-source developer tool that sits between the coding agent and the running application. \n\n The agent can invoke Reticle through MCP, while Reticle connects to the actual application and collects evidence from the runtime. We designed the verification layer to be as deterministic as possible rather than asking another LLM to judge whether the application is correct. \n\n For the WebMCP challenge, we focused on exposing these capabilities through the web so an agent can discover what it can do, execute real workflows, and verify the resulting state. \n\n The architecture is intentionally modular: agents handle reasoning and implementation, while Reticle handles observation and verification. \n\n Challenges we ran into \n\n The hardest part was defining what “correct” actually means. \n\n Checking whether a button exists is easy. Proving that clicking it triggered the correct API call, changed the correct application state, persisted the result, and left the application without errors is much harder. \n\n We also had to deal with the reality of modern web applications. Framework state, asynchronous requests, client-side routing, browser state, and persistence all behave differently, and a useful verification system has to observe more than just what is visible on screen. \n\n Another challenge was keeping Reticle useful to agents rather than just humans. The output has to be structured enough for an agent to understand what failed and what it should investigate next. \n\n Accomplishments that we're proud of \n\n We're proud that Reticle is not just a conceptual WebMCP demo. \n\n It is an open-source verification system that can already be used with real coding agents and real applications. \n\n We have built a workflow where an agent can make a change, run Reticle, receive concrete evidence about what happened, and use that evidence to continue debugging. \n\n Most importantly, we think we are attacking a problem that will become more important as coding agents become more autonomous: verification is becoming as important as generation. \n\n What we learned \n\n We learned that giving an agent more tools isn't necessarily enough. \n\n The quality of an agent's output depends heavily on the quality of the feedback loop around it. If the agent cannot reliably observe the consequences of its actions, it is forced to guess. \n\n WebMCP reinforced another belief for us: the web should not only be designed for humans. As agents become first-class users of software, websites need machine-readable capabilities and predictable ways for agents to interact with them. \n\n The interesting future isn't agents replacing interfaces. It is interfaces becoming understandable to both humans and agents. \n\n What's next for Reticle \n\n We're working toward making Reticle a verification protocol and infrastructure layer for coding agents. \n\n Today, agents can generate code and run tests. We want them to be able to prove that real applications work . \n\n That means expanding verification beyond individual checks into complete real-world workflows, making the protocol easier for agents and developers to adopt, and building a larger ecosystem around standardized verification. \n\n Our long-term goal is straightforward: \n\n Agents should not ship code because they believe it works. They should ship it because they can prove it works. \n\n \n\n \n Built With \n\n chromium mcp playwright rust typescript websocket \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n youtu.be \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Divyanshu Shekhar \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Divyanshu Shekhar \n posted an update\n \n —\n \n 8 days ago \n \n \n\n Live Codex Video: https://drive.google.com/file/d/1IDS2OccBmZweNtIIEoQin5cCBn8HwzTo/view?usp=sharing \n\n\n \n \n \n\n \n Log in \n or\n sign up for Devpost \n to join the conversation.\n \n\n \n\n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n \n Divyanshu Shekhar \n started this project\n \n —\n \n 8 days ago \n \n \n\n
