It's slow, brittle, and worst of all,\ninvisible: the human has no idea what's happening until the agent reports\nback a summary at the end. \n\n WebMCP flips that entirely. A page can declare what an agent is\nallowed to do \nsearch_products\nadd_to_cart\ncheckout\nwith typed schemas, so the agent calls real functions instead of pretending to be a\nmouse. We wanted to build something that showed off what changes once a\nhuman and an agent aren't just near each other, but genuinely sharing\nthe same piece of state in real time. Grocery shopping felt like the\nperfect testbed: it's repetitive, constraint-heavy work ("stay under\nbudget," "keep it vegetarian," "don't forget the eggs") that's exactly\nwhat an agent is good at, while still being something people want a say\nin; nobody wants an AI silently deciding what's for dinner. \n\n That became Co-Shop : a storefront where you and your agent literally\nshare one cart. \n\n What it does\nCo-Shop is a grocery catalog with a shared cart. A human can browse and\nadd items by clicking, same as any store. An AI agent through\nChatGPT's WebMCP-enabled browser, or any WebMCP-aware client can call\ninto the same cart through seven registered tools: \n\n \n search_products free-text / category / tag / price search \n add_to_cart , remove_from_cart , update_quantity direct cart edits \n get_cart read the current shared state, including what the human added \n plan_dinners a compound tool: give it a day count, a diet, and a\nbudget, and it picks matching dinners and adds all of them in one call \n checkout places the order and clears the cart \n \n\n Every action human or agent shows up instantly with a badge ( YOU or\n AGENT ), a highlight animation on agent-added items, and a live activity\nfeed narrating the back-and-forth. Ask your agent "plan a week of\nvegetarian dinners under $40" and watch the cart fill up in front of you,\nstill fully editable. \n\n How i built it \n\n The whole app is a single Next.js (App Router) page with one client\ncomponent holding the cart and activity-log state. On mount, it registers\nall seven tools with document.modelContext.registerTool(...) , each with\na JSON Schema inputSchema and an execute function but critically,\nthose execute functions call the same internal helpers\n( addToCart , removeFromCart , checkout , etc.) that the UI's own click\nhandlers call. That was the core design decision: there's no separate\n"agent path" and "human path," just one state, mutated from two places. \n\n Tools are registered inside a useEffect and cleaned up via an\n AbortController passed as the registration's signal . Every execute \nreturns the WebMCP content-array shape\n( { content: [{ type: "text", text: JSON.stringify(...) }] } ) so the\nagent gets structured JSON back not just a confirmation string which\nmatters a lot for a compound tool like plan_dinners , where the agent\nneeds to know things like "only 5 of 7 requested days fit the budget." \n\n Challenges i ran into \n\n \n Stale closures. Tools are registered once on mount, so their\n execute functions would otherwise capture a stale snapshot of the\ncart. We solved this by keeping the state update functions themselves\nas the single source of truth (via setState functional updates)\nrather than reading from a captured variable. \n Making agent actions legible, not just correct. It's not enough for\nthe tool calls to work a judge (or a shopper) needs to see the\ndifference between "I added this" and "the agent added this" at a\nglance. That's what drove the AGENT/YOU badges, the purple pulse\nanimation, and the activity feed. \n Testing without a live agent. Early on, we stubbed\n document.modelContext in a headless browser to exercise the tools\nprogrammatically before ever touching a real agent client — that caught\na few bugs (like quantity handling on update_quantity ) well before we\ntested against ChatGPT's actual WebMCP browser. \n Getting the deploy pipeline right on a deadline. Wiring up GitHub,\nVercel, and an MIT license that GitHub actually detects in the About\nsection took more back-and-forth than the code itself. \n \n\n What i learned \n\n WebMCP's real power isn't "agents can now click your buttons for you" \nit's that a page and an agent can share one source of truth instead of\ntwo. That's a genuinely different interaction model from screen-scraping\nor API wrapping, and it's why an agent's actions in Co-Shop feel like\nsomeone else shopping with you, not an AI doing your shopping for you\nsomewhere off-screen. \n\n What's next \n\n Natural extensions: letting the agent negotiate substitutions when a\ndiet/budget can't be satisfied exactly, a compare_products tool for\nside-by-side agent recommendations, and multi-user shared carts where two\nhumans and an agent are all in the same session at once. \n\n \n\n \n Built With \n\n css3 javascript model-context-protocol nextjs react vercel webmcp \n \n\n \n Try it out \n\n \n \n \n co-shop-gules.vercel.app \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Toheeb Olanrewaju Olagoke \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Toheeb Olanrewaju Olagoke \n started this project\n \n —\n \n 4 days ago \n \n \n\n
