Everything after that is where claims die: submit, then wait 4–8 weeks; read a rejection that contradicts the airline's own operations log; challenge it; wait another 4 weeks; escalate — but only when the escalation is ripe. \n\n The work is small. The calendar is enormous. That's the persistence gap: whether you get what the policy says you're owed depends less on the merits than on whether you have the knowledge, time and stubbornness to keep coming back for three months. \n\n The thesis\nThe hard part of agentic AI isn't making an agent reason once. It's making it reliably stay with a real-world problem until the problem is actually resolved. \n\n Agents reason. Workflows remember. \n\n A stateless caseworker (4 tools, 10-step loop) and an independent verifier do the thinking; a Restate workflow owns the case. The agent forgets everything when it returns; the workflow survives kill -9, waits days for a human, and cannot execute a consequential action twice. \n\n That split is why NanoClaw was evaluated and rejected — its persistent sessions would have competed with the workflow for owning case memory. \n\n Tools, not an oracle. No tool returns a verdict. A check_eligibility() backed by a rules engine would have made the benchmark a test of whether the agent can call one function. \n\n Independent verification. The verifier sees the case and the policy but not the caseworker's working — a second opinion, not a reviewer inheriting a wrong turn. It can reject; a rejection citing no clause is downgraded to a pass. \n\n Human approval that is enforced, not requested. Every consequential action blocks on a durable promise, and the rejection branch returns before any outbound call is reachable. \n\n Results — two suites\nSuite A · reasoning · 28 synthetic cases. \n\n Primary metric is Case Resolution Accuracy: a case counts only when the next action, the compensation figure and the other entitlements are all correct at once. \n\n System CRA Model calls Cost\nBaseline — one direct prompt, no tools, no verifier 0.82 28 $1.37\nFull agent — tools, loop, independent verifier 0.93 102 $3.77\nSame model, same policy, same cases, same schema, same grader, same endpoint. \n\n The best possible constant answer on this suite is 0.25. Read +0.11 as directional, not significant — it is three cases, and this project has no valid variance estimate; the one it had was withdrawn in FAILURES.md F-008. \n\n Suite B · durability · 6 failure-injection scenarios. \n\n 6/6 passed (6/6 again inside Docker), workflow completion 1.00, failure recovery 1.00, state preserved after kill -9 1.00, and 0 duplicate consequential actions. \n\n The load-bearing one is D06: SIGKILL the worker inside the submission window — the carrier received 2 submission attempts and 1 claim landed, because the idempotency key is generated inside a durable step and is stable across replay. \n\n In D05, when the human refuses, the carrier is called zero times, not once and then reversed. \n\n The baseline scores nothing here, and that is not reported as a win. \n\n The biggest improvement\nOn the reasoning axis, the independent verifier — not the tools. \n\n The agent made 1.4 tool calls per case and called calculate three times in 28 cases. The verifier is isolated by case R16, a partial settlement that fails under the baseline and under tools-only and passes only with verification. \n\n It costs 3.6× the model calls for +0.11. \n\n But the improvement that mattered wasn't a component. It was answering where does the case remember itself? and being strict about it — which is why there is no database, why FastAPI holds no case state, and why a crash produces two attempts and one claim instead of two claims. \n\n The main failure mode we did not fix\nThe agent asserts money it never computed. \n\n Both remaining wrong cases fail on duty-of-care arithmetic; calculate was available on both and called on neither, despite a bolded prompt instruction with an example. \n\n It does the sums in its head because it is capable of doing them in its head and confident about it. \n\n That is invisible in an aggregate score and it is the one that reaches the passenger: a confident, well-cited, correctly-formatted claim letter with the wrong number in it. \n\n Corrective experiment EXP-005 is specified and recorded as unrun. \n\n Hot take\nWhen a control moves and you did not touch the control, stop theorising about the treatment. \n\n Three times this project reported infrastructure as capability: a required schema field zeroed a well-formed verdict; six cases were never sent to the model and were scored as six wrong answers, standing as the headline comparison for two days; a gateway served a different model while every result file recorded the one that was requested. \n\n All three looked exactly like reasoning results. What caught all three was the baseline moving when nothing about the baseline had changed. \n\n A missing answer is not a wrong answer. If your grader can't tell them apart, it will report your infrastructure as your agent's reasoning. \n\n The model field is not provenance. The endpoint is. \n\n Re-run your control, not just your treatment. \n\n And the thing I got wrong at the start: I assumed the reasoning would be hard and durability would be plumbing. \n\n A single prompt already handles most of these cases. What a single prompt cannot do is still be holding the case in week six. \n\n Reproducing it\ngit clone https://github.com/yablokolabs/c2c-agent.git && cd c2c-agent \n\n make setup \n\n make test — 165 tests, no model calls, no services \n\n make reproduce — baseline + agent + comparison \n\n The headline result needs no Restate server, no Docker and no Telegram. \n\n For the durability half: \n\n make up && make failure-tests && make down \n\n Deliverables\nDeliverable Location\n01 · Code + improvement changelog the repo · IMPROVEMENT_CHANGELOG.md\n02 · Reproduction guide REPRODUCTION_GUIDE.md\n03 · Solution video script in docs/DEMO_SCRIPT.md, submitted separately\n04 · Agent trajectories trajectories/README.md\nFailure journal: FAILURES.md \n\n Experiments including removed ones: experiments/ \n\n Raw results: evaluation/results/ \n\n Raw results are never overwritten, each carrying its commit, model, backend and prompt digests. \n\n \n\n \n Built With \n\n claude docker fastapi python telegram \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n CEO Balasa \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n 1 \n \n \n\n\n \n 1 person likes this:\n \n\n \n \n \n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n CEO Balasa \n started this project\n \n —\n \n 5 days ago \n \n \n\n
