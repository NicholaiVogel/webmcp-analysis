The agent clicks buy, submits the form, or empties the\ncart, and you find out afterward. That gives up two things the open web needs as agents\narrive: control, meaning you decide what actually changes, and access, meaning anyone can\noperate the page, not only people who can see it and use a mouse. WebMCP's own guidance also\nwarns about prompt injection, where a malicious page or a hijacked agent issues tool calls a\nperson never asked for. We wanted a design that answered both at once. \n\n What it does \n\n Baton is a small grocery store. It works normally for a person, who can browse, add items,\nreview the cart, and check out. It also registers five WebMCP tools, so an agent can do the\nsame things from a request like "add oat milk, then check out." \n\n The read tools, search_products and review_cart , run right away. The tools that change\nstate, add_to_cart , remove_from_cart , and checkout , never mutate anything directly.\nThey create a proposal on screen and return text saying the action is awaiting confirmation,\nso a well-behaved agent waits. Every action is narrated through an ARIA-live region and a\nplain-language card, and confirmed or rejected actions land in a visible timeline. Checkout is\na mock. No payment is taken and no order is sent anywhere. \n\n How we built it \n\n Vanilla JavaScript, HTML, and CSS, with no framework, no build step, and no backend, deployed\nas static files to Cloudflare Pages. The tools live in a local registry the page's own\ninterface calls directly, and the same tools are separately registered with\n document.modelContext for the agent, so the human interface never depends on the agent-side\nAPI being present. \n\n The confirmation step is enforced inside the tool, not the interface. A tool that changes\nstate does not change it in execute() . It sets one pending proposal and returns text that\ntells the agent to wait. State only changes when the person clicks Confirm, so there is no code\npath from a tool call to a state change that skips the person. \n\n We also shipped a "Real agent" console in the page itself: paste any OpenAI-compatible LLM\nkey, and a real model plans the tool calls, which run through the same WebMCP interface and the\nsame confirmation step. We used it to test the flow with a real third-party model\n( gpt-4o-mini via a model gateway) driving the tools end to end on the live deployed page. \n\n Challenges we ran into \n\n Testing against a real WebMCP client was harder than expected. ChatGPT's web app\n( chatgpt.com ) turned out not to be a WebMCP client at all: it web-searches the page\nserver-side and told us directly that it "does not expose the page's document.modelContext \nWebMCP tool registry." Chrome's WebMCP flag needs Chrome 149+, which isn't available on our\ndev machine. That's what led to building the in-page "Real agent" console: it let us prove a\nreal third-party model driving the tools end to end, without depending on a specific browser. \n\n Accomplishments that we're proud of \n\n The confirmation step is genuinely enforced in the tool layer, not just the UI, so there is no\nway for any agent, well-behaved or not, to skip it. And the same mechanism does two jobs at\nonce: it is an accessibility story, because the agent operates the page's own tools instead of\na scraped DOM, and it is a prompt-injection defense, because an injected instruction can call\n checkout , but it only ever produces a proposal, never an order. \n\n What we learned \n\n How new WebMCP still is, down to which real clients actually support it today. And that a\nconfirmation step designed for accessibility turns out to double as a security boundary,\nwithout any extra code, because both problems have the same shape: an agent should be able to\nact, but a person should always get the last word. \n\n What's next for Baton \n\n A larger catalog and a second task, like a form or a booking, to show the design works beyond\nshopping. A per-tool policy, where some proposals are approved automatically and high-stakes\nones always ask. And a shared session, where a helper and the person they assist both see the\nsame page. \n\n \n\n \n Built With \n\n cloudflare cloudflare-pages css html javascript model-context-protocol openai webmcp \n \n\n \n Try it out \n\n \n \n \n baton-cqy.pages.dev \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Adil Kazani \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n AI DevRel & Blockchain Developer \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Adil Kazani \n started this project\n \n —\n \n 4 days ago \n \n \n\n
