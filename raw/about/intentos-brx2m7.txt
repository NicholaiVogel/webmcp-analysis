But when an agent starts working, the important question is not just "Can it complete the task?" \n\n It is: \n\n "Can it complete the task without violating what the human actually intended?" \n\n Today, that agreement is often buried in chat history, scattered across settings, or left for the agent to infer. IntentOS explores a different approach: make the human's intent explicit, structured, and available to the agent as a set of tools. \n\n What we built \n\n IntentOS is a human intent layer for AI agents. \n\n It lets a person define: \n\n \n A goal \n Non-negotiable constraints \n Flexible preferences \n Actions that require human approval \n \n\n An agent can then use WebMCP tools to read that intent, propose actions, and receive an explainable verdict before proceeding. \n\n The three possible outcomes are: \n\n \n SAFE — the proposal fits the current intent. \n REQUIRES_APPROVAL — the action is allowed only after the human decides. \n CONFLICT — the proposal violates a non-negotiable constraint. \n \n\n The important part is that a conflict does not silently disappear. It becomes a visible decision for the human. \n\n The experience \n\n Imagine a user creates this intent contract: \n\n \n Launch a landing page for my AI automation service. \n\n Budget must remain ₹0. \n\n Do not use fake, fabricated, or unverified customer testimonials. \n\n Publishing requires my approval. \n \n\n The agent wants to improve the landing page. \n\n First, it proposes: \n\n \n "Add customer testimonials to increase visitor trust." \n \n\n IntentOS evaluates the proposal and returns CONFLICT . \n\n The human rejects it. \n\n The agent then proposes: \n\n \n "Add a What We Automate section instead of testimonials." \n \n\n IntentOS evaluates the new proposal and returns SAFE . \n\n Later, the agent proposes publishing the landing page. IntentOS returns REQUIRES_APPROVAL , so the human gets the final decision. \n\n This is the experience we wanted to explore: \n\n The agent can act independently, but it cannot quietly redefine the agreement. \n\n Why WebMCP? \n\n WebMCP makes this interaction possible in a more direct way. \n\n Instead of an agent trying to navigate a dashboard, guess which buttons to click, or interpret unstructured page content, IntentOS exposes structured tools such as: \n\n \n get_intent_state \n create_intent_contract \n add_constraint \n propose_action \n resolve_intent_conflict \n update_intent_contract \n \n\n These tools give the agent a clear interface for working with the user's intent. \n\n The agent does not need to guess how to submit a proposal. It can call propose_action with a structured action and reason, receive a verdict, and then use the result to decide what to do next. \n\n That is the core WebMCP idea we wanted to explore: \n\n A website should not only be designed for people to click through. It should also expose meaningful capabilities that agents can use directly. \n\n How we built it \n\n IntentOS is a React + TypeScript application built with Vite. \n\n The application has four main parts: \n\n 1. Intent Contract \n\n A structured representation of the human's goal, constraints, preferences, and approval requirements. \n\n 2. Conflict Engine \n\n A deterministic, explainable evaluation engine that checks agent proposals against the contract. \n\n We deliberately kept this engine separate from the UI and did not use an LLM to decide whether a proposal violates a constraint. \n\n For this prototype, we wanted the verdict to be predictable and understandable. \n\n 3. Human Approval Queue \n\n When an agent proposes something that conflicts with the contract or requires approval, the proposal appears in a visible queue. \n\n The human can approve or reject it. \n\n The decision is recorded in the activity timeline. \n\n 4. WebMCP Integration \n\n The application registers six tools through document.modelContext.registerTool() . \n\n The tools share the same state and action system as the UI, so the agent-facing interface and the human-facing interface operate on the same underlying contract. \n\n We also built a clearly labeled development test harness for exercising the tool handlers during development. \n\n What we learned \n\n The biggest lesson was that agent autonomy and human control are not necessarily opposites . \n\n An agent does not need to ask for permission before every small decision. It needs to understand which decisions it can make and which decisions belong to the human. \n\n That distinction led us to separate: \n\n \n Non-negotiable constraints — the agent may not violate them. \n Flexible preferences — the agent may decide within them. \n Approval-gated actions — the agent must wait for a human decision. \n \n\n We also learned that WebMCP changes how we think about web application design. \n\n The UI is no longer the only interface. A well-designed application can expose structured capabilities that make agent interaction more reliable and less dependent on guessing. \n\n Challenges \n\n The biggest technical challenge was working with an emerging browser API while keeping the application usable when WebMCP is unavailable. \n\n We implemented feature detection and honest status reporting rather than pretending an agent was connected. \n\n The application can still be used normally, while the WebMCP integration becomes available in a compatible browser environment. \n\n Another challenge was making the conflict engine explainable. \n\n A simple "blocked" message is not enough. The user needs to understand: \n\n \n What the agent proposed \n Which constraint was involved \n Why the proposal was blocked \n What decision the human can make \n \n\n That is why IntentOS records proposals, verdicts, and human decisions in the activity timeline. \n\n What is next \n\n This prototype focuses on the interaction model: human intent → agent proposal → evaluation → human decision → agent adaptation . \n\n The next step would be connecting IntentOS to a more capable agent that can use these tools across a real workflow, such as building and publishing a website, managing a project, or coordinating business tasks. \n\n We believe the most useful agent-native applications will not simply give agents more power. \n\n They will give agents better boundaries . \n\n And those boundaries should be understandable to the people who define them. \n\n Built for the WebMCP Challenge \n\n IntentOS explores how a website can become more useful when humans and agents work together through structured tools. \n\n The goal is not to replace human judgment. \n\n It is to make that judgment explicit, reusable, and available at the moment an agent needs it. \n\n \n\n \n Built With
