But most websites are still designed only for humans. \n\n I asked a simple question: \n\n What if a real city could become usable by AI agents, without taking control away from people? \n\n This question led me to HELLOBUSAN. \n\n I chose Busan as my real-world testbed because a single human goal can require many different services: discovering places, checking events, comparing restaurants, calculating routes, managing time, estimating costs, and eventually making reservations. \n\n Normally, people have to move between many websites and applications to complete these tasks. \n\n I wanted to explore a different model: \n\n The human expresses the goal. \n\n The Agent handles the complexity. \n\n WebMCP connects the Agent to real web capabilities. \n\n The human remains in control of consequential actions. \n\n HELLOBUSAN is therefore not just another AI travel planner. \n\n It is an experiment in designing a new relationship between Humans, Agents, and Cities. \n\n What it does \n\n HELLOBUSAN allows a person to describe what they want to accomplish in natural language. \n\n For example: \n\n \n “Plan a six-hour rainy-day trip in Busan for my family within a ₩50,000 budget.” \n \n\n Instead of manually searching multiple services, the Agent can use WebMCP tools to discover information and coordinate actions. \n\n The Agent can: \n\n \n Search places, restaurants, and events \n Retrieve detailed information \n Check relevant conditions such as weather \n Calculate routes and travel time \n Estimate and optimize the budget \n Build and update an itinerary \n Coordinate multiple services around one user goal \n \n\n The key difference is that HELLOBUSAN does not treat autonomy as unlimited permission. \n\n I designed an Agent Permission Model: \n Search ALLOW\nCompare ALLOW\nRoute ALLOW\nSchedule ALLOW\nReservation ASK\nPayment DENY\n\n \n How I built it \n\n HELLOBUSAN is designed as a WebMCP-based agentic interface with a Cloudflare-native backend. \n\n Instead of requiring an Agent to interpret a website only through visual elements, HELLOBUSAN exposes structured capabilities through WebMCP tools. \n\n My tool architecture includes capabilities such as: \n\n \n search_places \n search_restaurants \n search_events \n get_place_details \n get_weather \n calculate_route \n estimate_cost \n get_itinerary \n update_itinerary \n request_reservation \n \n\n Each capability has a defined purpose and structured input/output schema. \n\n I separated read operations, reversible actions, and consequential actions so that the Agent's level of autonomy can be controlled. \n\n The application architecture uses: \n\n \n React and TypeScript for the user interface \n WebMCP for Agent-facing web capabilities \n Cloudflare Workers for application logic and API routing \n Cloudflare D1 for persistent application data \n Cloudflare Durable Objects for stateful trip sessions and coordination \n REST APIs and structured JSON data for service integration \n \n\n A key design decision was to make permissions a system-level boundary rather than merely a visual setting. \n\n The interface may show that payment is disabled, but the backend must also enforce that restriction. \n\n I also designed an Agent Activity Log so that users can understand what the Agent is doing instead of experiencing an invisible autonomous process. \n\n Challenges I ran into \n\n The hardest challenge was not generating an itinerary. \n\n It was deciding where autonomy should stop. \n\n Giving an Agent more capabilities is technically attractive, but greater capability also creates greater responsibility. \n\n I identified three different levels of action: \n\n \n READ: The Agent can retrieve and understand information. \n ACT: The Agent can perform reversible actions such as organizing an itinerary. \n COMMIT: The Agent performs a consequential action that may affect the user. \n \n\n The third category requires human approval. \n\n This became particularly important when designing reservations and payments. \n\n I deliberately avoided the assumption that: \n\n \n “The user asked for a trip, therefore the Agent can do anything necessary to complete it.” \n \n\n Instead, the system distinguishes between intent and authority. \n\n A user's intention to “plan a trip” does not automatically grant permission to spend money or make an irreversible commitment. \n\n Another challenge was making WebMCP meaningful rather than decorative. \n\n I did not want to build a conventional travel application and simply add a WebMCP label. \n\n The Agent interaction itself had to depend on structured capabilities. \n\n I therefore designed the product around a comparison between conventional web interaction and WebMCP-based interaction, focusing on task steps, tool usage, errors, completion, and human approvals. \n\n Accomplishments that I'm proud of \n\n My biggest accomplishment is that HELLOBUSAN turned WebMCP from a technical capability into a visible user experience. \n\n The user does not need to understand WebMCP. \n\n They simply express a goal. \n\n Behind the interface, the Agent discovers available capabilities, calls structured tools, reasons over the results, updates the itinerary, and stops when human authorization is required. \n\n I am especially proud of the Agent Wallet concept. \n\n Instead of treating an Agent as either “fully autonomous” or “not autonomous,” I give the user granular control over what the Agent can do. \n\n I am also proud of the Agent Activity / Black Box experience. \n\n Users can see: \n\n \n What the Agent is doing \n Which tool it is using \n What information it found \n What it changed \n Which permission it used \n Where human approval is required \n \n\n This makes autonomy visible. \n\n Most importantly, the prototype demonstrates a different philosophy of agentic computing: \n\n \n The goal is not to maximize what the Agent can do.\nThe goal is to maximize what the Agent can safely do on behalf of a human. \n \n\n What I learned \n\n The biggest lesson was that the hardest problem in agentic systems is not capability. \n\n It is control. \n\n An Agent that can only answer questions is limited. \n\n An Agent that can take actions is useful. \n\n But an Agent that can take consequential actions without clearly defined authority creates a trust problem. \n\n WebMCP made me think beyond the question: \n\n \n “How can an Agent use the web?” \n \n\n I began asking: \n\n \n “How should the web communicate its capabilities and boundaries to an Agent?” \n \n\n And then: \n\n \n “How should a human control those capabilities?” \n \n\n This led me to a new mental model: \n\n Intent → Capability → Action → Approval \n\n I also learned that the best Agent experience should not hide autonomy. \n\n It should make autonomy understandable. \n\n The user should know when the Agent is thinking, what it is doing, what it is allowed to do, and when a decision belongs to them. \n\n This changed HELLOBUSAN from a travel application into an experiment in Human-Agent Interaction Design. \n\n What's next for HELLOBUSAN \n\n Busan is only the beginning. \n\n My next step is to expand HELLOBUSAN from a travel planner into an Agent-ready city interface. \n\n Restaurants, museums, cultural venues, hotels, transportation providers, local businesses, and public services could expose structured capabilities that Agents can discover and use. \n\n Instead of every Agent learning how to navigate every website independently, the web could increasingly provide explicit, machine-readable capabilities. \n\n This could enable a future where a person does not need to understand which website or application to use. \n\n They simply express an intent: \n\n \n “I need to spend Saturday in Busan with my family.” \n \n\n The Agent coordinates the available city services within the permissions defined by the person. \n\n My long-term vision is not: \n\n \n “AI controls the city.” \n \n\n It is: \n\n \n “People control their Agents, and Agents make the city easier to use.” \n \n\n HELLOBUSAN is my first experiment toward that future. \n\n You decide. \n\n Your Agent acts. \n\n Busan responds. \n\n \n\n \n Built With \n\n cloudflare-d1 cloudflare-durable-objects cloudflare-workers html
