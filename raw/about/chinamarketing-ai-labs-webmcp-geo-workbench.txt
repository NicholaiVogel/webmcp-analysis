The agent prepares a 75-credit run, but execution stays with the human and only pre-captured demo evidence is loaded. Inspiration GEO assessments get complicated quickly. A single project can involve dozens of questions, several AI engines and hundreds of observations. We already had a structured way to review that evidence, but browser-native agents raised a more interesting question: what happens if the agent can work with the application itself instead of trying to understand it from rendered pages? That is what we wanted to test with WebMCP. We did not want to give an agent unrestricted access. The idea was to let it investigate an assessment, find evidence and prepare the next piece of work, while the person using the application could see what was happening and stay in control of anything consequential. What it does The WebMCP GEO Workbench is a small, self-contained version of a GEO assessment workspace. A completed assessment is already loaded into the application. From ChatGPT, the agent can use the site's WebMCP tools to understand the project, inspect the questions, search retained evidence, bring relevant opportunities into view, create a follow-up assessment, edit that draft and prepare a quote for a possible next run. The agent is working with the same app state the user sees, not a separate agent-only layer. If it searches for observations where alternatives appear while the assessed entity is absent, the Evidence view changes to show those same observations. If it creates a follow-up, the draft appears in the application. If it prepares a run, the quote appears there too. The agent can prepare the run, but it cannot execute it, call external AI providers or spend credits. The final action stays with the person using the application. How we built it The project is a standalone React and TypeScript application deployed on Cloudflare Workers. The normal interface and the WebMCP tools use the same application service and local state. We did not build one workflow for the browser and another for the agent. The site registers eight tools directly with document.modelContext.registerTool(...) . They cover project context, assessment summaries, question plans, evidence search, opportunities, follow-up creation and editing, and run preparation. For the challenge demo we use a sanitised assessment fixture with 22 questions, five captured engines and 110 retained observations. There is no live model execution behind the demo. The final human action loads pre-captured evidence and says so clearly in the interface. The challenge app is also separate from our production systems, credentials, billing and private assessment data. Challenges we ran into One of the harder decisions was where to stop. We wanted the agent to be useful, but not to turn the demo into a fully autonomous workflow. So it can investigate, draft and prepare the next run, but the final execution stays with the person using the app. Another challenge was keeping what the agent found and what the user sees in the browser in sync. Returning six matching evidence IDs in chat is useful, but it is much better when those same six records appear immediately in the Evidence view. We also had to keep the demo grounded in what the assessment actually contains. The records shown here are retained observations from a bounded assessment, not permanent rankings or proof of why an external model produced a particular answer. Accomplishments that we're proud of The part we are happiest with is that the demo feels like one shared application rather than a chat window controlling a separate automation layer. The agent can search retained evidence and the same records appear in the browser. It can create a follow-up and the draft appears in the workspace. It can prepare a run and the quote appears there too. We also kept the boundary around execution intact. The agent can investigate and prepare, but the final action still requires a person. Finally, we kept the challenge build isolated from production. The public demo uses sanitized, pre-captured assessment data and does not expose production credentials, private customer data, billing or live provider execution. What we learned The main thing we learned was that WebMCP works best when the agent can use the same application state as the person looking at the screen. That sounds obvious, but it changed how we thought about the tools. Instead of asking ChatGPT to work out what was happening from the page, we could expose the parts of the application it actually needed: the assessment context, evidence, opportunities and follow-up draft. We also found that the agent did not need full control to be useful. It could do most of the investigation and preparation, while the final execution still stayed with the user. The evidence-search interaction was probably the clearest example. ChatGPT found the matching records through WebMCP, and those same records appeared immediately in the app. What's next for ChinaMarketing.AI Labs — WebMCP GEO Workbench This is a small experimental build, not a production feature. Our next step is to look at which parts of this interaction model are useful enough to bring into the main ChinaMarketing.AI GEO workspace. The same pattern could also be useful in other evidence-heavy applications where an agent needs structured access to the work without being given unrestricted authority.
