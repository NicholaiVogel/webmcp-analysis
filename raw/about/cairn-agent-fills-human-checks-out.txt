WebMCP replaces all of that guessing with typed, described tools an\nagent can call directly: search_products , filter_products , add_to_cart ,\n apply_coupon , and more, each with a real JSON Schema instead of a DOM\nselector to reverse-engineer. \n\n How does it create a better user experience? \n\n The agent and the human work the same visible cart in the same tab, live —\nnot a hidden background process the human has to double-check afterward.\nEvery tool call the agent makes shows up immediately, both as a highlighted\nproduct card and as an entry in a small on-screen activity log, so the human\nalways sees exactly what the agent did and why, as it happens. \n\n What can people and agents do together that was difficult or impossible before? \n\n Before WebMCP, "let an agent shop for me" meant one of two extremes: full\ncheckout automation with no human oversight, or an agent that can only\ndescribe what it would do with no way to actually act. Cairn is the middle\npath — the agent does the tedious part (searching, comparing, filling the\ncart, testing a coupon) while the human keeps the one decision that\nmatters. There is no tool that can complete a purchase. It isn't hidden\nbehind a confirmation step — it was never registered. An agent asked to\n"check out" has nothing to call, no matter how it's asked. Neither side can\nfinish the transaction alone; the collaboration loop only closes when a\nhuman clicks the real button in the UI. \n\n How did you implement WebMCP? \n\n Built as a static HTML/CSS/JS site (no framework, no build step) so it\ndeploys anywhere with zero configuration. cart.js holds all cart state and\nlogic — search, filter, add/remove, quantity updates, coupon math — as a\nsingle module. Both the human-facing UI ( app.js ) and the agent-facing\ntools ( webmcp-tools.js ) call the same functions in that module, so\nthere's genuinely one cart, not two systems kept in sync. Tools are\nregistered with document.modelContext.registerTool() — the current API;\nthe earlier navigator.modelContext name was deprecated in Chromium 150 and\nintentionally not used. Eight tools are registered in total\n( search_products , filter_products , get_product_details , add_to_cart ,\n update_cart_quantity , remove_from_cart , apply_coupon ,\n get_cart_summary ), with read-only tools marked via readOnlyHint: true .\nNo purchase-completing tool is registered anywhere in the codebase. \n\n Inspiration \n\n Cairns are trail markers — stones stacked by one traveler for the next one\nto find. That's the shape of good human-agent collaboration: each side\nleaves useful, visible work for the other, and no one silently takes over\nthe whole trip. \n\n What it does \n\n Lets a shopper and their AI agent build a shared cart together in a\nspecialty coffee gear store — searching, filtering, adding items, and\napplying coupons — while keeping the actual purchase decision exclusively in\nhuman hands. \n\n How we built it \n\n Vanilla JS, no framework, no backend — a single shared state module\n( cart.js ) that both the UI and the WebMCP tool layer call into, so the\nagent and the human are never looking at two different versions of the cart. \n\n Challenges we ran into \n\n Making the "no checkout tool" boundary feel like a deliberate design\nstatement rather than a missing feature — solved by narrating it explicitly\nin the UI copy itself ("Checkout — human only") and in the on-screen tool\nlog, so it reads as intentional the moment you look at the page. \n\n Accomplishments \n\n A working, deployable demo where an agent's actions and a human's actions\nvisibly share one piece of state in real time, with a hard, code-level\nboundary around the one action that shouldn't be automatable. \n\n What's next \n\n Multi-agent carts (two shoppers, two agents, one shared list), and an\noptional prepare_order read-only tool that hands the human a pre-filled\nsummary without ever being able to submit it itself. \n\n Built with \n\n document.modelContext.registerTool (WebMCP), HTML, CSS, JavaScript \n\n \n\n \n\n \n Built With \n\n css html
