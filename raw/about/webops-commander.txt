When AI agents need to interact with those applications, they often have to interpret pages visually, reason about buttons and forms, and reproduce workflows that were never designed for machine interaction. \n\n WebMCP suggests a different future: websites can expose intentional, structured capabilities directly to AI agents while continuing to provide rich interfaces for humans. \n\n That idea inspired WebOps Commander . \n\n We wanted to explore a question: \n\n \n What would an incident-response application look like if it were designed for humans and AI agents from the beginning? \n \n\n Instead of building another chatbot or allowing an agent to blindly click through an operations dashboard, WebOps Commander gives the agent structured operational capabilities through WebMCP while preserving explicit human control over consequential actions. \n\n What it does \n\n WebOps Commander is an agent-native incident-response command center built around a deterministic simulated production outage. \n\n A fictional e-commerce platform experiences a severe checkout incident shortly after a new version of checkout-service is deployed. \n\n The human operator sees a visual operations dashboard containing: \n\n \n live service health \n checkout error rate \n p95 latency \n order throughput \n estimated revenue impact \n service dependencies \n logs \n distributed traces \n deployment history \n incident status \n agent activity \n \n\n At the same time, a compatible AI agent receives structured WebMCP tools that allow it to investigate the same system directly. \n\n The agent can: \n\n \n inspect the active incident \n inspect service health \n query metrics \n search logs \n inspect traces \n inspect service dependencies \n inspect recent deployments \n compare releases \n search operational runbooks \n estimate customer impact \n simulate a rollback \n request a production-changing action \n wait for explicit human approval \n execute an approved rollback \n observe system recovery \n update and resolve the incident \n \n\n The core workflow is: \n\n Observe → Investigate → Correlate → Simulate → Request Approval → Human Approves → Execute → Recover \n\n Why WebMCP? \n\n Without WebMCP, an AI agent interacting with an operations platform may need to determine which page contains deployment information, interpret charts, find buttons, understand forms, and infer what actions are safe to perform. \n\n That approach can be brittle. \n\n With WebMCP, WebOps Commander intentionally exposes structured capabilities such as: \n\n query_service_metrics \n\n search_logs \n\n search_traces \n\n get_recent_deployments \n\n compare_deployments \n\n simulate_rollback \n\n request_rollback \n\n execute_approved_action \n\n The agent does not need to guess how the user interface works. \n\n The website tells the agent what capabilities are available, what inputs they accept, and what actions are permitted. \n\n The human interface and agent interface operate on the same application state, so WebMCP actions are immediately visible inside the command center. \n\n Human + Agent Collaboration \n\n WebOps Commander is intentionally not designed around full autonomy. \n\n Investigation is safe for the agent to perform independently. \n\n Consequential actions are different. \n\n For example, the agent can determine that a rollback is likely to resolve the incident and simulate its expected impact, but it cannot immediately change the simulated production environment. \n\n Instead, it creates a pending action: \n\n Rollback checkout-service from v2.18.4 to v2.18.3 \n\n The human sees the proposed action together with: \n\n \n the agent's reasoning \n expected recovery \n current error rate \n expected post-rollback error rate \n estimated risk \n \n\n The human can then approve or reject the action. \n\n Only an approved action can be executed. \n\n This creates a clear separation between: \n\n Agent investigation \n\n Agent recommendation \n\n Human authorization \n\n Agent execution \n\n Every WebMCP interaction is also recorded in the visible agent activity timeline. \n\n The Incident \n\n The demonstration focuses on one deliberately small but polished scenario: Checkout Meltdown . \n\n A deployment of checkout-service v2.18.4 introduces stricter payment-token issuer validation. \n\n Shortly afterward: \n\n \n checkout failures increase from approximately 0.6% to 18.4% \n p95 checkout latency increases from approximately 620 ms to 4.7 seconds \n completed orders fall by approximately 38% \n estimated revenue exposure reaches approximately $21.4K per simulated minute \n \n\n Other services remain healthy. \n\n Through metrics, logs, traces, deployment history, and release comparison, the agent can correlate the incident with v2.18.4 . \n\n It can then simulate a rollback to v2.18.3 , request authorization, and—after human approval—execute the remediation. \n\n The command center visually shows the system recovering. \n\n How we are building it \n\n WebOps Commander is intentionally scoped as a focused hackathon demonstration rather than a production observability platform. \n\n The application uses a deterministic simulation instead of real cloud infrastructure so that every judge can reproduce the same incident without accounts, API keys, external services, or unreliable dependencies. \n\n The planned architecture consists of: \n\n \n Next.js \n React \n TypeScript \n Tailwind CSS \n shadcn/ui \n WebMCP \n Zod \n Zustand \n Recharts \n Vitest \n Playwright \n GitHub Actions \n \n\n Operational state, telemetry, logs, traces, deployments, and recovery behavior are simulated locally. \n\n WebMCP is the primary agent interface. \n\n The project does not require an embedded chatbot or external LLM API—the compatible AI agent interacting with the website is the agent. \n\n Challenges \n\n The most interesting challenge is not simply exposing functions to an AI agent. \n\n It is deciding what an agent should be allowed to do. \n\n Read-only investigation tools should be easy to invoke. \n\n Simulation should be safe. \n\n Production-changing operations should be protected. \n\n That led us to design a small capability model with separate categories for: \n\n \n read operations \n simulations \n approval requests \n consequential actions \n \n\n Another important challenge is making agent activity understandable to the human operator. WebOps Commander therefore visualizes WebMCP invocations in an audit timeline so users can see what the agent inspected, what it concluded, and what it attempted to change. \n\n What we learned \n\n WebMCP changes the way a web application can be designed. \n\n Instead of treating AI agents as external automation systems that must reverse-engineer a user interface, the application can expose a deliberate machine-facing capability layer alongside its human interface. \n\n The result is not simply easier automation. \n\n It enables a different interaction model: \n\n \n Humans provide intent and authority. Agents investigate and execute structured workflows. Websites provide the contract connecting them. \n \n\n What's next \n\n After the hackathon, WebOps Commander could be expanded to explore: \n\n \n multiple incident scenarios \n richer permission policies \n tool-level access control \n real observability integrations \n real deployment systems \n multi-agent operational workflows \n reusable WebMCP patterns for infrastructure products \n \n\n For this challenge, however, the focus remains intentionally narrow: \n\n one incident, one excellent human-agent workflow, and a clear demonstration of why WebMCP matters. \n\n \n\n \n Built With \n\n actions css github next.js playwright react recharts shadcn/ui tailwind typescript vercel vitest webmcp zod zustand \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n Love Jayesh Ahir \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Love Jayesh Ahir \n started this project\n \n —\n \n 2 days ago \n \n \n\n
