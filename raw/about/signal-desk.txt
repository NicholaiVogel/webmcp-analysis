We wanted to answer the harder question that follows: once an agent can operate your app, what stops it from quietly doing the wrong thing? \n\n Product and support teams get launch feedback from everywhere — support tickets, community posts, sales calls, release comments. The hard part is never reading one message. It is finding the repeated pain, proving it with evidence, deciding what product should do next, and being able to show later who decided what. \n\n That workflow is a good stress test for agent governance, because every step produces a claim someone will eventually be held to. \n\n What it does \n\n Signal Desk is a customer-request triage workspace where a human and an agent share one visible surface. \n\n The agent can search requests, group them into pain patterns, explain the evidence behind a pattern, draft a customer-impact brief, and propose product-owned actions. What it cannot do is decide. \n\n Three properties hold no matter who is driving: \n\n \n Every claim is traceable. Each brief claim links back to the specific customer requests supporting it. There are no unsourced assertions. \n Writes are approval-gated. The agent proposes product actions into a review queue. A human approves before anything is treated as decided. \n One shared decision log. Human and agent changes land in the same audit trail — what changed, who changed it, when. \n \n\n The demo case is an admin import launch: customers import their workspaces successfully, then stall because nobody knows the next required admin step, the owner, or the validation path. \n\n How WebMCP is used \n\n Signal Desk registers 8 tools on the page, split deliberately between reads and gated writes: \n\n \n \n Tool \n Type \n \n \n \n search_signals \n read \n \n \n explain_evidence \n read \n \n \n get_audit_trail \n read \n \n \n cluster_signals \n write \n \n \n draft_brief \n write \n \n \n propose_actions \n write — lands in an approval queue, never auto-applied \n \n \n set_review_state \n write — records an audit event \n \n \n reset_demo \n write \n \n \n\n The design decisions that matter: \n\n \n Tool calls mutate the same state the UI renders. There is no shadow model. A human watching the screen sees exactly what the agent did, as it happens. \n Calls are idempotent. Re-running propose_actions or set_review_state does not duplicate proposals or double-apply approvals — important when an agent retries. \n Writes are separated from decisions. The agent's most consequential tool, propose_actions , deliberately cannot finalize anything. \n Every state change emits an audit event , tagged by actor, so agent activity is reconstructable after the fact. \n \n\n Tools are registered through document.modelContext.registerTool with a navigator.modelContext fallback. \n\n What this enables that was hard before: an agent can run a real multi-step operational workflow inside a business app — not by scraping the DOM or driving synthetic clicks, but through typed tools with schemas — while a human keeps veto power over every consequential write. \n\n What makes it useful \n\n The interesting claim is not that an agent can triage faster. It is that you can let an agent into a workflow with real consequences and still answer, afterwards, three questions auditors and managers actually ask: \n\n \n What did the agent change? \n What evidence was that based on? \n Who approved it? \n \n\n Most agent integrations cannot answer any of the three. Signal Desk is built so all three are answerable by construction rather than by logging bolted on afterwards. \n\n How we built it \n\n A lightweight static web app — HTML, CSS, and vanilla JavaScript — with a small Worker wrapper for hosting. Synthetic, public-safe customer-request data; no private accounts, no external services, no local background process. State lives in browser localStorage and is resettable via reset_demo . \n\n Deployed as a public HTTPS app on ChatGPT Sites. Full source is on GitHub under the MIT license. \n\n It also works without WebMCP. In a browser with no WebMCP host, the app degrades to a normal operator UI, and a Run Triage button exercises the identical workflow locally. The agent path is an enhancement to a product that stands on its own — not a demo that collapses without a special browser. \n\n Challenges \n\n The main challenge was resisting the pull toward a technical proof of concept. \n\n A WebMCP demo is easy to build as a page with buttons wired to tool handlers. Making it behave like a product meant adding the things that are unglamorous but load-bearing: review states, evidence links, idempotent tool calls so agent retries do not duplicate work, a fallback path for non-WebMCP browsers, and an audit trail that treats human and agent actions as equal citizens. \n\n The second challenge was drawing the write boundary in the right place. The first version let the agent apply actions directly, which demoed well and was exactly wrong. Splitting propose_actions from set_review_state — proposal from decision — is what turned it from an automation demo into something you could imagine shipping. \n\n What's next \n\n \n Real connectors (support inbox, community forum, CRM notes) behind the same evidence contract \n Per-tool permission scopes, so an operator can grant an agent read and draft access without proposal rights \n Exportable decision records for teams that need the audit trail outside the app \n \n\n \n\n \n Built With \n\n chatgpt css github html javascript sites webmcp \n \n\n \n Try it out \n\n \n \n \n signal-desk-webmcp.lakshyindy.chatgpt.site \n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n The WebMCP Challenge \n \n\n\n \n\n\n \n\n \n \n\n \n \n Created by\n \n\n \n \n \n \n I designed and built Signal Desk as a solo project, including the product workflow, WebMCP tool integration, evidence-linked brief drafting, approval-gated action review, audit trail, browser fallback, deployment, testing, and demo assets. \n \n\n \n \n \n \n \n \n\n \n Lakshmi narayana .U \n \n \n\n \n\n \n \n \n \n\n \n \n \n \n \n \n \n \n \n\n \n \n \n \n \n\n \n\n \n\n\n \n \n \n \n \n\n \n \n \n \n \n \n \n \n \n Like\n \n \n\n\n \n \n \n\n \n \n\n \n\n\n \n \n \n \n Share this project:\n \n\n\n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n \n \n \n \n \n \n\n \n\n \n \n \n \n\n \n \n \n\n \n \n \n \n \n\n\n\n \n \n \n Updates \n\n \n \n \n \n \n\n \n \n \n \n \n \n Lakshmi narayana .U \n started this project\n \n —\n \n 9 days ago \n \n \n\n
