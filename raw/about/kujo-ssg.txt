\n \n WebMCP review step 4 \n \n \n \n \n \n\n \n \n WebMCP review step 5 \n \n 1 2 3 4 5 6 7 \n\n\n\n \n Inspiration \n\n I wanted Kujo SSG to generate extremely fast static sites, stay simple to work with, and fit the way software is being built now, with AI agents doing more of the work. \n\n That means treating agents as first-class users. \n\n The site structure, CLI, machine-readable context, and WebMCP support are all built around making it easier for agents to understand and interact with a site without scraping pages and guessing what everything does. \n\n What it does \n\n Kujo SSG is a static site generator built as part of the Kujo programming language ecosystem. \n\n It turns structured content, templates, components, assets, and configuration into static websites that can be deployed almost anywhere. \n\n It also gives those sites an agent-facing layer. \n\n Kujo sites can expose functionality through WebMCP, publish llms.txt and other machine-readable context, and give AI clients a cleaner way to interact with a site than browser automation. \n\n It can also be extended with things like themes, plugins, commerce, CMS functionality, and AI integrations while still producing static output. \n\n How we built it \n\n The Kujo SSG follows the same approach as the rest of the ecosystem: small pieces, explicit behavior, strong defaults, and composable tooling. \n\n The build pipeline handles content discovery, routing, templates, rendering, assets, and final site generation. \n\n Around that, I built support for reusable themes, plugins, site configuration, structured metadata, AI-readable documentation, and WebMCP. \n\n WebMCP fit naturally because Kujo was already being built around structured interfaces for agents. \n\n Instead of teaching an agent how to click around a website, the site can expose the actions directly. \n\n Challenges we ran into \n\n The main challenge was adding capability without losing the simplicity of a static site generator. \n\n It is easy to keep adding features until you have basically rebuilt a dynamic framework with a static export step. \n\n I wanted plugins, themes, commerce, AI integrations, and WebMCP to work around the static model instead of replacing it. \n\n Agent interaction was another challenge. \n\n Humans can look at a page and understand what buttons, forms, and navigation are supposed to do. Agents should not have to reverse-engineer that every time, wasting time and tokens on browser use. \n\n WebMCP gives us a much cleaner way to expose that functionality directly. \n\n Accomplishments that we're proud of \n\n Kujo SSG has grown into more than a basic static site generator. \n\n I've used it for real websites, documentation, content-heavy sites, commerce examples, plugin and theme systems, AI integrations, and WebMCP-enabled functionality. \n\n It also works as part of the wider Kujo ecosystem instead of being a standalone tool. \n\n That gives developers access to things like MCP, RAG, evaluation, observability, context management, specifications, validation, and other agent-focused tooling around the development process. \n\n With WebMCP, the final website can now take part in that agent workflow too. \n\n What we learned \n\n A lot of value in building AI-native software comes from making software easier for agents to understand and operate. \n\n Clear contracts are better than guessing, structured data is better than scraping, explicit tools are better than hoping an agent clicks the right thing and deterministic systems become more important as more of the development process becomes probabilistic. \n\n Static sites work really well for that. \n\n The final output is still just HTML, CSS, JavaScript, and assets, while the tooling around it can be much more capable. \n\n What's next for Kujo SSG \n\n I want WebMCP support to become a standard part of how Kujo sites expose functionality to agents. \n\n That sits alongside llms.txt , MCP integrations, structured site metadata, and the rest of Kujo's agent tooling. \n\n I'm also continuing to expand the SSG around commerce, CMS functionality, plugins, themes, reusable site kits, and AI workflows. \n\n The goal is to make sites that are easy for humans to use and easy for agents to understand, modify, and interact with. \n\n Static where static makes sense. \n\n Agent-native where agents make sense. \n\n \n\n \n Built With \n\n ai css html javascript kujo kujolang ssg \n \n\n \n Try it out \n\n \n \n \n GitHub Repo \n \n \n \n\n \n\n \n\n \n \n Submitted to\n \n\n \n \n \n \n \n\n \n \n
